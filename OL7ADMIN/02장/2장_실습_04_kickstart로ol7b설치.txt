================================================================================
 제2장 실습 04 — kickstart 로 ol7b 설치
 대상   : ol7a (kickstart 작성·검증·HTTP 제공), ol7b (설치 대상)
 목표   : ol7a 의 anaconda-ks.cfg 를 고쳐 ol7b 용 kickstart 를 만들고, ksvalidator 로
          검사한 뒤 HTTP 로 내보내 inst.ks= 부트 옵션으로 ol7b 를 무인 설치한다.
          설치 뒤 ol7b 에 남은 기록으로 kickstart 가 어떻게 적용됐는지 확인한다
 배경   : kickstart 는 옵션 구역, %packages, %pre/%post 세 구역으로 된 설치 응답 파일이다.
          설치가 끝나면 Anaconda 가 쓴 원본은 /root/original-ks.cfg, 실제로 적용된
          설정을 다시 적은 것은 /root/anaconda-ks.cfg 로 남는다. 설치 프로그램은 부트
          메뉴에서 Tab 으로 넣은 inst.ks=URL 을 dracut 단계에서 내려받는다(본문 2.4·2.5절)
 소요   : 준비 약 20분, 설치 약 6분
 선행   : ol7a 는 ol7-base, ol7b 는 ol7b-base. 설치 자체는 2026-11-11 20:02~20:11 에
          수행했고 그 기록을 [10]~[12] 에 그대로 옮겼다(labs/02/k2_post.log, cap02/k0*.png)
 계정   : root
 주의   : 실제 설치는 ol7b 의 디스크를 지운다(clearpart --all). 이 실습을 다시 할 때는
          ol7b 재설치 대신 [8] 의 curl 로 설치 프로그램의 요청을 흉내 낸다
 되돌림 : HTTP 서버 종료, firewall-cmd --list-ports 가 빈 줄. ol7a 의 /root 에는
          ks-ol7b.cfg 만 남는다

 [2] 내보내기 전 점검 — 이 파일로 설치하면 어떤 호스트가 생기는가
--------------------------------------------------------------------------------

-- 복사한 파일에는 원본 서버의 신원이 그대로 들어 있다. 네트워크 줄을 뽑아 본다.
[root@ol7a ~]# grep -n '^network' /root/ks-ol7b.cfg
17:network  --bootproto=static --device=ens32 --gateway=172.16.225.2 --ip=172.16.225.61 --nameserver=172.16.225.2 --netmask=255.255.255.0 --ipv6=auto --activate
18:network  --bootproto=dhcp --device=ens33 --onboot=off --ipv6=auto
19:network  --hostname=ol7a.example.com
-- 17번 줄의 --ip=172.16.225.61, 19번 줄의 ol7a.example.com 이 그대로 들어 있다.
-- 18번 줄 ens33 은 ol7b 에 없는 장치다.
-- 그 주소와 이름이 이미 쓰이고 있는지 이름 해석과 ping 으로 확인한다.
[root@ol7a ~]# getent hosts 172.16.225.61 ol7a.example.com
172.16.225.61   ol7a.example.com ol7a
fe80::87f4:d993:7b43:e0c1 ol7a.example.com
-- 그 주소와 이름은 이미 ol7a 다(/etc/hosts 와 IPv6 링크 로컬 주소).
[root@ol7a ~]# ping -c 2 -W 1 172.16.225.61 | tail -2
2 packets transmitted, 2 received, 0% packet loss, time 1018ms
rtt min/avg/max/mdev = 0.030/0.032/0.035/0.006 ms
-- 2개 보내 2개 받음. 그 주소는 살아 있다.
-- 증상   : 복사한 kickstart 로 설치하면 172.16.225.61·ol7a.example.com 서버가 하나 더 생긴다
-- 원인   : anaconda-ks.cfg 는 원본 서버의 신원(IP, 호스트 이름, NIC)을 그대로 담고 있다
-- 조치   : [3] 에서 --ip 와 --hostname 을 ol7b 값으로 바꾸고 ens33 줄을 지운다
-- 재확인 : [3] 의 grep 이 .62·ol7b.example.com 을 보여 주고 getent 가 ol7b 로 해석한다
-- 이 오류는 ksvalidator 가 잡지 못한다. 문법은 맞기 때문이다.

--------------------------------------------------------------------------------
 [3] 신원·디스크 지시어 고치기
--------------------------------------------------------------------------------

-- --ip 와 --hostname 을 ol7b 값으로, ol7b 에는 없는 ens33 줄은 지운다.
-- clearpart --none 은 "기존 파티션을 지우지 않음"이다. 새 VM 디스크에 다른 OS 흔적이
-- 있어도 멈추지 않게 --all 로 바꾸고, zerombr(빈 디스크 초기화 묻지 않음)와
-- reboot(설치 후 자동 재부팅)를 더한다.
[root@ol7a ~]# sed -i -e 's/--ip=172.16.225.61/--ip=172.16.225.62/' -e 's/ol7a.example.com/ol7b.example.com/' -e '/--device=ens33/d' -e 's/^clearpart --none --initlabel/clearpart --all --initlabel\nzerombr\nreboot/' /root/ks-ol7b.cfg
[root@ol7a ~]# diff /root/anaconda-ks.cfg /root/ks-ol7b.cfg
7c7
< graphical
---
> text
9c9
< firstboot --enable
---
> firstboot --disable
17,19c17,18
< network  --bootproto=static --device=ens32 --gateway=172.16.225.2 --ip=172.16.225.61 --nameserver=172.16.225.2 --netmask=255.255.255.0 --ipv6=auto --activate
< network  --bootproto=dhcp --device=ens33 --onboot=off --ipv6=auto
< network  --hostname=ol7a.example.com
---
> network  --bootproto=static --device=ens32 --gateway=172.16.225.2 --ip=172.16.225.62 --nameserver=172.16.225.2 --netmask=255.255.255.0 --ipv6=auto --activate
> network  --hostname=ol7b.example.com
34c33,35
< clearpart --none --initlabel
---
> clearpart --all --initlabel
> zerombr
> reboot
-- 17,19c17,18: 세 줄이 두 줄로 바뀜(ens33 줄 삭제). 34c33,35: clearpart 한 줄이 세 줄로.
--   clearpart --all  기존 파티션을 모두 지움. --initlabel 은 빈 디스크에 파티션 표를 만듦
--   zerombr          파티션 표가 없는 디스크를 초기화할지 묻지 않음
--   reboot           설치가 끝나면 자동 재부팅
-- sed 의 치환 결과에 \n 을 넣어 한 줄을 세 줄로 만들었다(GNU sed).
[root@ol7a ~]# grep -n '^network' /root/ks-ol7b.cfg; getent hosts 172.16.225.62
17:network  --bootproto=static --device=ens32 --gateway=172.16.225.2 --ip=172.16.225.62 --nameserver=172.16.225.2 --netmask=255.255.255.0 --ipv6=auto --activate
18:network  --hostname=ol7b.example.com
172.16.225.62   ol7b.example.com ol7b
-- 이제 .62 와 ol7b 이름이 짝이 맞는다.

 [5] 문법 검사
--------------------------------------------------------------------------------

-- -v RHEL7 로 7 문법을 지정한다. 지정하지 않으면 최신 문법(DEVEL)으로 검사한다.
[root@ol7a ~]# ksvalidator -v RHEL7 /root/ks-ol7b.cfg; echo "rc=$?"

-- 출력 없음, rc=0. 정상 파일에는 아무 말도 하지 않는다.
-- -l 목록에 OL7 도 있었다. Oracle 이 붙인 별칭이다. 같은 결과인지 본다.
[root@ol7a ~]# ksvalidator -v OL7 /root/ks-ol7b.cfg; echo "rc=$?"
rc=0
-- OL7 도 같은 결과다. 이 과정은 RHEL7 로 쓴다.

 [6] Anaconda 가 이해하는 형태 — ksflatten
--------------------------------------------------------------------------------

-- ksflatten 은 %include 를 펼치고 파일을 파싱한 뒤 다시 써 준다. 설치 프로그램이
-- 읽는 순서·형식에 가깝다. 주석과 빈 줄을 빼고 본다.
[root@ol7a ~]# ksflatten -v RHEL7 -c /root/ks-ol7b.cfg 2>&1 | grep -v -E '^#|^$' | cut -c1-100
keyboard --vckeymap=us --xlayouts='us'
-- 원본과 다른 점
--   keyboard·rootpw·lang·user 가 맨 앞으로 오는 등 순서가 바뀌었다(파서 내부 순서)
--   network  --hostname=ol7b.example.com 이 network  --bootproto=dhcp --hostname=… 로 바뀌었다.
--   장치 없는 network 줄에 기본값 dhcp 가 채워진 것이다. ol7b 의 anaconda-ks.cfg([12])도 같다
--   reboot 이 위로 올라오고 zerombr 가 clearpart 앞으로 갔다
--   %addon·%anaconda 구역이 보이지 않는다. 이 ksflatten 은 addon 구역을 다시 쓰지 않는다
-- 그래서 ksflatten 결과를 설치용 파일로 쓰면 Kdump 설정이 빠진다. 확인용으로만 쓴다.

 [7] HTTP 로 내보내기
--------------------------------------------------------------------------------

[root@ol7a ~]# mkdir -p /var/www/ks && cp /root/ks-ol7b.cfg /var/www/ks/ && chmod 644 /var/www/ks/ks-ol7b.cfg && ls -l /var/www/ks
total 4
-rw-r--r--. 1 root root 1790 Nov 16 11:58 ks-ol7b.cfg
-- 웹 서버가 읽을 수 있게 644. /root 의 원본은 600 이라 그대로 두면 다른 사용자가 읽지 못한다.
-- 설치 프로그램은 ol7b 쪽에서 들어오므로 ol7a 방화벽에 8000/tcp 를 연다.
-- --permanent 를 붙이지 않았으니 재부팅·reload 하면 사라지는 임시 규칙이다.
[root@ol7a ~]# firewall-cmd --add-port=8000/tcp; firewall-cmd --list-ports
success
8000/tcp
-- success 뒤 list-ports 에 8000/tcp. 지금 바로 적용되지만 reload·재부팅하면 사라진다.
-- 파이썬 2.7 의 내장 웹 서버. 현재 디렉터리를 그대로 내보낸다.
-- 웹 서버의 작업 디렉터리가 내보낼 디렉터리여야 한다. 셸을 하나 띄워 cd 한 뒤 python 으로 바꾼다(exec).
[root@ol7a ~]# nohup sh -c 'cd /var/www/ks; exec python -m SimpleHTTPServer 8000' >/tmp/http.log 2>&1 </dev/null &
[root@ol7a ~]# sleep 2; ss -ltnp | grep 8000
LISTEN 0      5            0.0.0.0:8000      0.0.0.0:*    users:(("python",pid=2417,fd=3))  
-- 열: State LISTEN, Recv-Q 0, Send-Q 5(백로그), 로컬 주소 0.0.0.0:8000(모든 주소), 프로세스 python.
-- 처음에는 @cd 로 디렉터리를 바꾼 뒤 nohup 을 띄웠는데 러너가 cd … && nohup … & 꼴로 실행해
-- 600초 시간 제한에 걸렸다. sh -c 로 cd 와 exec 를 한 프로세스 안에 넣어 해결했다.

--------------------------------------------------------------------------------
 [8] ol7b 쪽에서 받아 보기 — 설치 프로그램이 할 일을 미리
--------------------------------------------------------------------------------

-- 설치 프로그램은 dracut 안에서 이 URL 을 그대로 내려받는다. 같은 요청을 curl 로.
-- -w 로 HTTP 상태 코드와 받은 바이트 수만 찍는다.
[root@ol7b ~]# curl -s -o /tmp/ks.cfg -w '%{http_code} %{size_download}\n' http://172.16.225.61:8000/ks-ol7b.cfg
200 1790
-- 상태 200, 받은 바이트 1790. [7] 의 ls -l 크기와 같다.
-- 이 ks 와, ol7b 를 실제로 설치할 때 쓴 ks(ol7b 의 /root/original-ks.cfg)가 같은지.
[root@ol7b ~]# diff /tmp/ks.cfg /root/original-ks.cfg && echo SAME
SAME
-- 지금 내보낸 파일이 2026-11-11 실제 설치에 쓴 파일과 한 글자도 다르지 않다.
-- 경로를 틀리게 적으면 서버는 무엇을 돌려주는가.
[root@ol7b ~]# curl -s -o /dev/null -w '%{http_code}\n' http://172.16.225.61:8000/ks-ol7.cfg
404
-- 경로가 틀리면 404. 설치 프로그램이라면 "Kickstart file … is missing" 으로 끝난다([9]).
[root@ol7a ~]# cat /tmp/http.log
172.16.225.62 - - [16/Nov/2026 11:58:32] "GET /ks-ol7b.cfg HTTP/1.1" 200 -
172.16.225.62 - - [16/Nov/2026 11:58:33] code 404, message File not found
172.16.225.62 - - [16/Nov/2026 11:58:33] "GET /ks-ol7.cfg HTTP/1.1" 404 -
-- 형식: 요청한 주소, 시각, 요청 줄, 상태 코드. 설치 프로그램이 파일을 실제로 받아 갔는지
-- 확인할 때 이 로그를 본다. 요청이 아예 없다면 문제는 서버가 아니라 부트 줄이나 네트워크다.
