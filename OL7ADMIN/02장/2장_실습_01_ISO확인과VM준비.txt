================================================================================
 제2장 실습 01 — 설치 ISO 확인과 VM 준비
 대상   : 호스트(Windows, PowerShell), ol7a (os-installed 스냅샷)
 목표   : 설치 ISO 가 정말 7.9 인지, 받은 그대로인지 확인하고, 설치 대상 VM 의
          하드웨어(디스크 5개, NIC 2개, 메모리·CPU)가 설계대로인지 OS 안에서 대조한다
 배경   : 설치 매체는 이름이 아니라 내용으로 판별한다. 매체 루트의 .treeinfo 가
          배포판 이름·버전·빌드 시각을 담고, isolinux.cfg 가 부트 메뉴를 정한다.
          받은 파일이 손상되지 않았는지는 SHA-256 체크섬과 매체에 심어진 MD5 로
          두 번 확인할 수 있다. 하드웨어 요건은 논리 CPU 2개 이상, CPU 당 1GB
          메모리를 권장한다(본문 2.1절).
 소요   : 약 20분 (체크섬 계산 2회 포함)
 선행   : ol7a 를 os-installed 스냅샷으로 되돌림. VM 의 CD 드라이브에 OEL7V9.iso 연결
 계정   : root (ol7a), 호스트는 일반 사용자 PowerShell
 주의   : 조회 위주. /mnt 에 ISO 를 읽기 전용으로 마운트했다가 마지막에 해제한다
 되돌림 : umount /mnt 후 findmnt /mnt 가 아무것도 출력하지 않으면 시작 상태와 같다

 [1] 블록 장치에서 설치 매체 찾기
--------------------------------------------------------------------------------

-- VMware 의 가상 CD 는 IDE 장치라 리눅스에서 sr0 으로 보인다.
-- -o 로 열을 고른다: NAME 장치 이름, SIZE 크기, TYPE disk/part/lvm/rom,
-- FSTYPE 파일 시스템, LABEL 볼륨 레이블, MOUNTPOINT 마운트 위치.
[root@ol7a ~]# lsblk -o NAME,SIZE,TYPE,FSTYPE,LABEL,MOUNTPOINT
NAME         SIZE TYPE FSTYPE      LABEL                MOUNTPOINT
sdd           10G disk                                  
sdb           10G disk                                  
sr0          4.5G rom  iso9660     OL-7.9 Server.x86_64 
sde           10G disk                                  
sdc           10G disk                                  
sda           40G disk                                  
├─sda2        39G part LVM2_member                      
│ ├─ol-swap  3.9G lvm  swap                             [SWAP]
│ └─ol-root 35.1G lvm  xfs                              /
└─sda1         1G part xfs                              /boot
-- 열 해설
--   NAME       sr0 이 CD, sda~sde 가 SCSI 디스크. 트리 기호(├─ └─)는 부모·자식 관계
--   SIZE       sr0 4.5G 는 ISO 크기(GiB 표시)
--   TYPE       rom(광학), disk, part(파티션), lvm(논리 볼륨)
--   FSTYPE     iso9660 은 CD 파일 시스템, LVM2_member 는 LVM 물리 볼륨
--   LABEL      OL-7.9 Server.x86_64 — 부트 줄의 inst.stage2=hd:LABEL=… 가 이 값을 찾는다
--   MOUNTPOINT sr0 은 비어 있다. 설치가 끝나면 CD 는 마운트되지 않은 채 남는다
-- 디스크가 sdd, sdb, sr0 … 순서로 섞여 나온다. 장치를 찾은 순서다. 이름은 부팅마다
-- 바뀔 수 있다(UEK 의 비동기 SCSI 검색). 이 스냅샷에는 scsi_mod.scan=sync 가 없다.

 [2] 매체 레이블과 정확한 크기
--------------------------------------------------------------------------------

-- blkid 는 장치의 슈퍼블록을 직접 읽어 파일 시스템 종류와 레이블을 보여 준다.
-- blockdev --getsize64 는 장치 크기를 바이트로 준다. 호스트의 ISO 파일 크기와 같아야
-- 체크섬 비교가 의미 있다(크기가 다르면 체크섬은 볼 필요도 없다).
[root@ol7a ~]# blkid /dev/sr0
/dev/sr0: UUID="2021-05-28-10-00-48-00" LABEL="OL-7.9 Server.x86_64" TYPE="iso9660" PTTYPE="dos" 
-- iso9660 에는 UUID 가 따로 없어 볼륨 생성 시각(2021-05-28 10:00:48)을 UUID 자리에 보여 준다.
-- PTTYPE="dos" 는 ISO 앞부분에 MBR 파티션 표가 함께 들어 있다는 뜻이다(USB 로 구워도 부팅되게).
[root@ol7a ~]# blockdev --getsize64 /dev/sr0
4857004032
-- 호스트 파일 크기와 같다.
-- 크기가 같아야 체크섬을 비교할 의미가 있다.

 [4] .treeinfo 와 .discinfo — 버전 판별의 근거
--------------------------------------------------------------------------------

-- .treeinfo 는 설치 프로그램이 읽는 매체 설명서다. [general] 에 배포판 정보,
-- [images-x86_64] 에 부팅용 커널·initrd 위치, [stage2] 에 설치 프로그램 런타임 위치가 있다.
-- 파일 전체는 70줄 남짓이다. 버전 판별에 쓰는 세 구역([general]·[stage2]·[tree])만 sed 로 뽑는다.
-- 그 밖에 [images-*]·[addon-*]·[checksums] 구역이 있다는 것은 grep '^\[' 로 따로 본다.
[root@ol7a ~]# grep '^\[' /mnt/.treeinfo | paste -sd ' '
[general] [header] [images-x86_64] [images-xen] [media] [product] [stage2] [tree] [variant-Server] [addon-Server-HighAvailability] [addon-Server-ResilientStorage] [checksums]
-- 구역이 12개다. [checksums] 에는 부팅 이미지의 SHA-256 이 들어 있어 설치 프로그램이 스스로 검증한다.
[root@ol7a ~]# sed -n -e '/^\[general\]/,/^$/p' -e '/^\[stage2\]/,/^$/p' -e '/^\[tree\]/,/^$/p' /mnt/.treeinfo
[general]
; WARNING.0 = THIS SECTION IS KEPT ONLY FOR COMPATIBILITY REASONS
; WARNING.1 = Consider using other sections (product, base_product, tree, variant-*) instead
arch = x86_64
family = Oracle Linux
name = Oracle Linux 7.9
packagedir = Packages
platforms = x86_64,xen
repository = .
timestamp = 1622221243.02
variant = Server
version = 7.9

[stage2]
mainimage = LiveOS/squashfs.img

[tree]
arch = x86_64
build_timestamp = 1622221243.02
platforms = x86_64,xen
variants = Server
-- 판별 근거
--   family / version    Oracle Linux / 7.9      배포판과 버전
--   name                Oracle Linux 7.9        부트 메뉴 제목에 쓰이는 이름
--   arch                x86_64                  64비트 Intel·AMD
--   timestamp           1622221243.02           매체를 만든 시각(유닉스 시간)
--   variant             Server                  OL7 매체는 Server 하나뿐이다
--   [stage2] mainimage  LiveOS/squashfs.img     Anaconda 가 든 이미지
-- .discinfo 는 옛 형식의 요약본이다. 첫 줄이 빌드 시각(유닉스 시간)이다.
[root@ol7a ~]# cat /mnt/.discinfo
1622220794.977668
OL-7.9 x86_64
x86_64
-- .discinfo 시각은 .treeinfo 보다 약 7분 앞선다.
-- timestamp 를 사람이 읽는 날짜로 바꾼다. -u 로 UTC 기준.
[root@ol7a ~]# date -u -d @1622221243
Fri May 28 17:00:43 UTC 2021
-- 2021-05-28.
-- 7.9 첫 출시(2020년 말)보다 반년 늦은 재빌드판이다.
-- 증상   : 파일 이름 OEL7V9.iso 와 릴리스 노트만 보고 "7.9 첫 출시판" 이라 판단할 뻔했다
-- 원인   : 파일 이름은 받은 사람이 붙인 것이고, 같은 7.9 도 커널을 바꾼 재빌드판이 있다
-- 조치   : .treeinfo 의 version 과 timestamp, 들어 있는 커널 파일 이름([7])으로 판별한다
-- 재확인 : [8] 에서 설치된 UEK 가 릴리스 노트의 2011.6.2 가 아니라 2102.201.3 임을 본다

 [5] 부트 메뉴 정의 — isolinux.cfg
--------------------------------------------------------------------------------

-- BIOS 방식 VM 이라 isolinux 가 부트 메뉴를 그린다(UEFI 면 EFI/BOOT/grub.cfg).
-- 메뉴 항목 이름, 기본 선택, 대기 시간, 커널에 넘기는 인자만 골라 본다.
[root@ol7a ~]# grep -n -E '^(default|timeout)|menu label|menu default|append' /mnt/isolinux/isolinux.cfg
1:default vesamenu.c32
2:timeout 600
64:  menu label ^Install Oracle Linux 7.9
66:  append initrd=initrd.img inst.stage2=hd:LABEL=OL-7.9\x20Server.x86_64 quiet
69:  menu label Test this ^media & install Oracle Linux 7.9
70:  menu default
72:  append initrd=initrd.img inst.stage2=hd:LABEL=OL-7.9\x20Server.x86_64 rd.live.check quiet
82:  menu label Install Oracle Linux 7.9 in ^basic graphics mode
88:  append initrd=initrd.img inst.stage2=hd:LABEL=OL-7.9\x20Server.x86_64 xdriver=vesa nomodeset quiet
92:  menu label ^Rescue a Oracle Linux system
98:  append initrd=initrd.img inst.stage2=hd:LABEL=OL-7.9\x20Server.x86_64 rescue quiet
101:  menu label Run a ^memory test
112:  menu label Boot from ^local drive
119:  menu label Return to ^main menu
-- 열: 줄 번호, 그 줄 내용
--   default vesamenu.c32  그래픽 메뉴 모듈. timeout 600 은 1/10초 단위라 60초
--   menu default          69번 줄 항목(Test this media)이 기본 선택이다
--   append                커널 인자. 66번과 72번은 rd.live.check 하나만 다르다
--   ^                     메뉴 단축키 표시(^I 면 i 키)
-- basic graphics mode 는 xdriver=vesa nomodeset 으로 그래픽 카드 문제를 피하는 항목,
-- Rescue 는 20장에서 쓰는 rescue 모드다.

 [9] SHA-256 체크섬 — VM 안에서 매체를 직접 읽어 계산
--------------------------------------------------------------------------------

-- 호스트에서 구한 값과 같은지 보려고 VM 안에서 장치 전체를 읽는다.
-- time 으로 4.5GB 를 읽는 데 걸린 시간도 남긴다.
[root@ol7a ~]# time sha256sum /dev/sr0
28d2928ded40baddcd11884b9a6a611429df12897784923c346057ec5cdd1012  /dev/sr0

real    0m32.273s
user    0m0.148s
sys     0m9.142s
-- 4.5GB 를 32초에 읽었다.
-- 값은 호스트 Get-FileHash 결과([변형])와 같다.
-- 공급처가 준 체크섬을 파일로 저장해 두고 -c 로 대조하는 방식이 실무 절차다.
-- 형식은 "체크섬 두 칸 공백 파일 이름". 호스트의 Get-FileHash 값을 소문자로 넣는다.
[root@ol7a ~]# echo '28d2928ded40baddcd11884b9a6a611429df12897784923c346057ec5cdd1012  /dev/sr0' > /root/OEL7V9.sha256
[root@ol7a ~]# sha256sum -c /root/OEL7V9.sha256
/dev/sr0: OK

--------------------------------------------------------------------------------
 [10] 다른 도구로 대조하다 생긴 실수 — 알고리즘 혼동
--------------------------------------------------------------------------------

-- 다운로드 페이지에 SHA-1 과 SHA-256 이 함께 실려 있으면 명령을 섞어 쓰기 쉽다.
-- SHA-256 값을 담은 파일을 sha1sum 으로 검사해 본다.
[root@ol7a ~]# sha1sum -c /root/OEL7V9.sha256; echo "rc=$?"
sha1sum: /root/OEL7V9.sha256: no properly formatted SHA1 checksum lines found
rc=1
-- 증상   : "no properly formatted SHA1 checksum lines found", rc=1
-- 원인   : 파일 안의 값이 64자리(SHA-256)라 40자리 SHA-1 형식이 아니다. 값이 틀린 것이 아니다
-- 조치   : 대조 파일과 같은 알고리즘의 명령(sha256sum)을 쓴다. SHA-1 로 하려면 값을 따로 구한다
-- 재확인 : sha1sum 결과 66aba21c…b1c6 이 [변형] 의 호스트 SHA1 값과 같다
-- SHA-1 로 대조하려면 SHA-1 값을 따로 구해야 한다.
[root@ol7a ~]# sha1sum /dev/sr0
66aba21caabf919fc2582ac4a2755e05c685b1c6  /dev/sr0

 [11] 매체에 심어진 MD5 — 부트 메뉴 "Test this media" 와 같은 검사
--------------------------------------------------------------------------------

-- 부트 메뉴의 미디어 검사는 rd.live.check 인자로 checkisomd5 를 돌린다.
-- 설치된 시스템에서도 같은 도구로 같은 검사를 할 수 있다.
[root@ol7a ~]# rpm -q isomd5sum
package isomd5sum is not installed
[root@ol7a ~]# checkisomd5 --md5sumonly /dev/sr0; echo "rc=$?"
/tmp/_ol7lab_root.sh: line 1: checkisomd5: command not found
rc=127
-- 증상   : "checkisomd5: command not found", rc=127(명령 없음)
-- 원인   : 설치 매체에는 들어 있지만 Infrastructure Server 선택에는 isomd5sum 이 없다
-- 조치   : 마운트한 ISO 의 RPM 을 rpm -ivh 로 바로 설치한다(아래)
-- 재확인 : checkisomd5 --md5sumonly 가 기준 MD5 를 보여 준다
-- 마운트한 ISO 의 Packages 에서 바로 설치한다. 저장소 설정 없이 rpm 에 파일을 직접 준다.
[root@ol7a ~]# ls /mnt/Packages/ | grep isomd5sum
isomd5sum-1.0.10-5.el7.x86_64.rpm
[root@ol7a ~]# rpm -ivh /mnt/Packages/isomd5sum-*.rpm
warning: /mnt/Packages/isomd5sum-1.0.10-5.el7.x86_64.rpm: Header V3 RSA/SHA256 Signature, key ID ec551f03: NOKEY
Preparing...                          ########################################
Updating / installing...
isomd5sum-1:1.0.10-5.el7              ########################################
-- NOKEY 경고는 Oracle 공개 키를 rpm DB 에 가져오지 않았다는 뜻이다. 설치는 그대로 된다.
-- --md5sumonly 는 검사하지 않고 ISO 에 심어 둔 기준 MD5 정보만 보여 준다.
[root@ol7a ~]# checkisomd5 --md5sumonly /dev/sr0
/dev/sr0:   a3057047e8cf1684a02dbae060fc2e14
Fragment sums: fd811216663bf4bc3dad3c62b357f33faa235a9f0ab41c1caad6a6ccceb4
Fragment count: 20
-- 첫 줄이 매체 전체 MD5, 둘째·셋째 줄은 매체를 20조각으로 나눈 조각별 합계다.
-- 실제 검사. 진행률을 \r 로 덮어쓰며 찍으므로 줄바꿈으로 바꾸고 마지막 네 줄만 본다.
[root@ol7a ~]# time checkisomd5 --verbose /dev/sr0 2>&1 | tr '\r' '\n' | tail -4
The media check is complete, the result is: PASS.

It is OK to use this media.


real    0m14.041s
user    0m1.156s
sys     0m6.655s
-- "PASS" 와 "It is OK to use this media." 가 부트 메뉴 미디어 검사가 끝날 때 보이는 문장이다.

 [12] VM 하드웨어를 OS 안에서 확인
--------------------------------------------------------------------------------

-- .vmx 에 적은 메모리·CPU 가 OS 에 그대로 보이는지.
[root@ol7a ~]# free -m; nproc
              total        used        free      shared  buff/cache   available
Mem:           3646         154         117           8        3374        3267
Swap:          3967           0        3967
2
-- free 의 total 3646MB 는 4096MB 에서 커널 예약분과 Kdump 예약(280MB)이 빠진 값이다.
-- buff/cache 는 앞에서 읽은 ISO 캐시다. 여유는 available.
-- nproc 2 = numvcpus 2.
-- 디스크는 -d 로 파티션을 빼고 디스크만. HCTL 은 Host:Channel:Target:LUN,
-- 곧 .vmx 의 scsi0:N 번호와 대응한다.
[root@ol7a ~]# lsblk -d -o NAME,HCTL,SIZE,TYPE,MODEL
NAME HCTL        SIZE TYPE MODEL
sdd  2:0:3:0      10G disk VMware Virtual S
sdb  2:0:1:0      10G disk VMware Virtual S
sr0  1:0:0:0     4.5G rom  VMware IDE CDR10
sde  2:0:4:0      10G disk VMware Virtual S
sdc  2:0:2:0      10G disk VMware Virtual S
sda  2:0:0:0      40G disk VMware Virtual S
-- HCTL 의 T(타깃)가 .vmx 의 scsi0:N 의 N 이다. sda=2:0:0:0=scsi0:0, sdb=2:0:1:0=scsi0:1.
-- 이름은 바뀌어도 HCTL 은 그대로다.
-- 디스크를 지우기 전에는 HCTL 로 대상을 확인한다.
-- sr0 은 1:0:0:0, IDE 컨트롤러 쪽이다. MODEL 의 CDR10 은 VMware 가상 CD 이름이다.
-- NIC 두 개. -br 은 한 줄 요약.
[root@ol7a ~]# ip -br link
lo               UNKNOWN        00:00:00:00:00:00 <LOOPBACK,UP,LOWER_UP> 
ens32            UP             00:0c:29:ac:5e:a0 <BROADCAST,MULTICAST,UP,LOWER_UP> 
ens33            UP             00:0c:29:ac:5e:aa <BROADCAST,MULTICAST,UP,LOWER_UP> 
-- 00:0c:29 는 VMware 자동 MAC 대역.
-- ens33 은 링크만 UP, 주소 없음(실습 03 [10]).
-- .vmx 의 lsilogic·e1000 이 리눅스에서 어떤 장치로 보이는지.
[root@ol7a ~]# lspci | grep -i -E 'ethernet|scsi|ide|vga'
00:07.1 IDE interface: Intel Corporation 82371AB/EB/MB PIIX4 IDE (rev 01)
00:0f.0 VGA compatible controller: VMware SVGA II Adapter
00:10.0 SCSI storage controller: Broadcom / LSI 53c1030 PCI-X Fusion-MPT Dual Ultra320 SCSI (rev 01)
02:00.0 Ethernet controller: Intel Corporation 82545EM Gigabit Ethernet Controller (Copper) (rev 01)
02:01.0 Ethernet controller: Intel Corporation 82545EM Gigabit Ethernet Controller (Copper) (rev 01)
-- e1000 이 Intel 82545EM, lsilogic 이 LSI 53c1030 으로 보인다. ens32·ens33 의 32·33 은
-- PCI 슬롯 번호에서 나온 이름이다.
[root@ol7a ~]# systemd-detect-virt; dmidecode -s system-product-name
vmware
VMware Virtual Platform
-- systemd-detect-virt 는 가상화 종류(vmware), dmidecode 는 BIOS 가 알려 주는 제품 이름이다.

 [13] 설치 프로그램이 본 메모리
--------------------------------------------------------------------------------

-- 메모리가 모자라면 Anaconda 가 그래픽 대신 텍스트 모드로 내려간다(INS 3장 Text-Based
-- Installations). 실제 설치 때 Anaconda 가 메모리를 어떻게 판정했는지 로그에서 찾는다.
[root@ol7a ~]# grep -n -i -E 'memory|mem:|text mode' /var/log/anaconda/anaconda.log | head -10
4:19:39:55,281 INFO anaconda: check_memory(): total:3968, needed:320, graphical:410
23:19:39:55,782 INFO anaconda: check_memory(): total:3968, needed:320, graphical:410
-- check_memory() 는 전체(total) 3968MB 를 설치 최소(needed) 320MB, 그래픽 설치 기준
-- (graphical) 410MB 와 비교한다. total 이 graphical 보다 작으면 텍스트 모드로 내려간다.
-- 증상   : (설계한 오류) 메모리를 적게 준 VM 에서 그래픽 화면 대신 텍스트 설치가 뜬다
-- 원인   : check_memory() 의 total 이 graphical 기준보다 작다. 이 랩은 4GB 라 재현하지 않았다
-- 조치   : VM 메모리를 늘리거나, 텍스트 설치를 받아들이고 디스크 배치는 kickstart 로 지정한다
-- 재확인 : 다음 설치의 anaconda.log 에서 같은 줄의 total 이 graphical 보다 큰지 본다
