 제16장 실습 07 — 오류 재현: 기본 보안 조치(코어 덤프, noexec, 서비스 정리)
 대상   : ol7a
 목표   : 코어 덤프를 limits·sysctl 로 막고, 그 설정이 로그인 세션과 systemd 서비스에
          다르게 적용되는 것을 확인한다. /tmp 를 noexec·nosuid·nodev 로 마운트해 설치
          스크립트가 어떻게 실패하는지 보고, 듣고 있는 서비스를 목록으로 정리한다
 배경   : 코어 파일에는 프로세스 메모리가 그대로 담긴다. 암호·키가 섞일 수 있어 운영
          서버에서는 막는다. limits.conf 는 pam_limits 가 로그인 때 적용하므로 PAM 을
          거치지 않는 systemd 서비스에는 닿지 않는다. 마운트 옵션 noexec 는 그 파일
          시스템에서 execve() 를 막고, nosuid 는 setuid 비트를, nodev 는 장치 파일을
          무시한다(본문 16.8)
 소요   : 약 25분
 선행   : ol7-base 스냅샷
 계정   : root, student
 주의   : /tmp 위에 tmpfs 를 덮어 마운트한다. 덮인 원래 /tmp 의 파일은 마운트를 푸는
          동안 보이지 않는다. postfix 를 잠시 멈췄다가 되돌린다
 되돌림 : limits.d·sysctl.d 추가 파일 삭제, coretest 서비스 삭제, /tmp 는 루트 파일
          시스템의 디렉터리, fstab 원본, postfix 활성.
          확인: findmnt /tmp, md5sum /etc/fstab, systemctl is-active postfix

-- 코어 덤프 관련 커널 값 세 개
[root@ol7a ~]# sysctl kernel.core_pattern kernel.core_uses_pid fs.suid_dumpable

kernel.core_uses_pid = 1

-- core_uses_pid = 1 : 파일로 쓸 때 이름 뒤에 .PID 를 붙인다
-- fs.suid_dumpable = 0 : 이미 보안 가이드의 권고값이다

 [1] 코어 파일이 생기는 것 확인
--------------------------------------------------------------------------------

-- soft 한도를 올리고 sleep 에 SIGSEGV 를 보내 코어를 만든다. 코어는 현재 디렉터리(홈)에 생긴다
[student@ol7a ~]$ ulimit -c unlimited; sleep 30 & sleep 1; kill -SEGV $!; wait; ls -l core.*
/tmp/_ol7lab_student.sh: line 1:  2159 Segmentation fault      (core dumped) sleep 30
-rw-------. 1 student student 397312 Nov 16 17:17 core.2159
-- soft 를 unlimited 로 올리자 core.2159 가 홈에 생겼다(397312 바이트, 모드 600)
-- core_pattern 이 abrt 파이프인데도 파일이 생겼다. abrt-hook-ccpp 가 사용자 한도를 보고 현재 디렉터리에 사본을 남긴다
-- 줄 앞의 /tmp/_ol7lab_student.sh: line 1: 은 러너가 명령을 담은 스크립트 이름이다. 터미널이면 bash 가 같은 자리에 찍힌다
-- (core dumped) 는 bash 가 자식의 종료 상태를 보고 붙인 표시다

-- 코어 안에 프로세스 환경 변수가 들어 있다. 문자열 몇 개만 본다
-- 환경 변수는 NUL 로 구분돼 있어 tr 로 줄바꿈으로 바꾼 뒤 찾는다
[student@ol7a ~]$ tr '\0' '\n' < core.* | grep -a -E '^(HOME|USER|LOGNAME)=' | sort -u
HOME=/home/student
LOGNAME=student
USER=student
-- sleep 같은 작은 프로그램의 코어에서도 환경 변수가 그대로 나왔다
-- DB 접속 문자열·암호를 환경 변수나 메모리에 든 프로그램이면 그 값도 이렇게 읽힌다
-- 코어 파일 모드는 600 이지만 root 와 백업 프로그램은 읽을 수 있다
[student@ol7a ~]$ rm -f core.*

 [2] limits 로 막기
--------------------------------------------------------------------------------

-- hard 를 0 으로 둔다. soft 만 0 이면 사용자가 ulimit -c 로 다시 올릴 수 있다
[root@ol7a ~]# echo '*    hard    core    0' > /etc/security/limits.d/90-nocore.conf; cat /etc/security/limits.d/90-nocore.conf
*    hard    core    0
-- 형식: 도메인 · 종류(hard/soft) · 항목 · 값. * 는 모든 사용자
-- 파일 이름의 90- 은 읽는 순서. limits.conf 다음에 limits.d 를 이름순으로 읽는다

-- 새 로그인 세션에서 확인(su - 도 PAM session 을 거친다)
[student@ol7a ~]$ echo "soft=$(ulimit -c) hard=$(ulimit -Hc)"; ulimit -c unlimited; echo "rc=$?"
soft=0 hard=0
/tmp/_ol7lab_student.sh: line 1: ulimit: core file size: cannot modify limit: Operation not permitted
rc=1
-- 새 로그인 세션(su - student)에서 hard 가 0 이 됐다
-- 사용자가 올리려 하자 cannot modify limit: Operation not permitted, rc=1
-- 일반 사용자는 hard 한도를 낮출 수만 있고 올릴 수 없다

[student@ol7a ~]$ sleep 30 & sleep 1; kill -SEGV $!; wait; ls core.* 2>&1
/tmp/_ol7lab_student.sh: line 1:  2343 Segmentation fault      (core dumped) sleep 30
ls: cannot access core.*: No such file or directory
-- 같은 SIGSEGV 에 (core dumped) 는 찍혔지만 파일은 없다
-- 커널은 파이프형 core_pattern 이면 한도와 상관없이 abrt 를 부른다. abrt 가 한도 0 을 보고 파일을 남기지 않았다
-- (core dumped) 표시만 보고 "코어가 남았다" 고 판단하지 않는다. 파일과 /var/spool/abrt 를 본다

 [3] root 에도 * 가 적용되는가
--------------------------------------------------------------------------------

[root@ol7a ~]# su - root -c 'echo "soft=$(ulimit -c) hard=$(ulimit -Hc)"'
soft=0 hard=0
-- 새 판 limits.conf(5) 에는 "wildcard 는 root 에 적용되지 않는다" 는 문장이 있다. 7.9 의 pam 과 man 을 본다
[root@ol7a ~]# rpm -q pam; man -P cat limits.conf 2>/dev/null | grep -i -c 'root'
pam-1.1.8-23.0.1.el7.x86_64
0
-- 증상   : 새 판 문서와 달리 su - root 의 한도도 soft=0 hard=0
-- 원인   : 7.9 의 pam-1.1.8 은 * 를 root 에도 적용한다. 7.9 의 man 페이지에 root 예외 문장이 없다(grep 결과 0)
-- 조치   : root 만 다르게 하려면 root 를 사용자 이름으로 따로 적는다(예: root hard core unlimited)
-- 재확인 : su - root -c 'ulimit -Hc'
-- 새 판 limits.conf(5) 에는 "group and wildcard limits are not applied to the root user" 가 있다
-- 같은 설정 파일이 OS 판에 따라 root 에 다르게 적용된다. 문서보다 실측을 믿는다
-- 러너의 root 세션은 이 파일을 넣기 전에 열려서 아직 unlimited 다([5])
-- 한도는 세션이 열릴 때 정해진다. 이미 열린 세션에는 소급되지 않는다

 [4] 오류 재현 ② — systemd 서비스에는 적용 안 됨
--------------------------------------------------------------------------------

-- 시험용 서비스. 시작 직후 한도를 찍고, 올려 본 뒤 다시 찍고 대기한다
-- root 는 hard 한도도 스스로 올릴 수 있어(CAP_SYS_RESOURCE) 시험이 안 된다. User=student 로 돌린다
[root@ol7a ~]# cat > /usr/local/bin/coretest.sh <<'EOF'
#!/bin/bash
echo "before soft=$(ulimit -c) hard=$(ulimit -Hc)"
ulimit -c unlimited && echo "raise=ok" || echo "raise=fail"
echo "after  soft=$(ulimit -c) hard=$(ulimit -Hc)"
exec sleep 600
EOF
[root@ol7a ~]# chmod 755 /usr/local/bin/coretest.sh
[root@ol7a ~]# printf '[Unit]\nDescription=core limit test\n[Service]\nUser=student\nExecStart=/usr/local/bin/coretest.sh\n' > /etc/systemd/system/coretest.service; cat /etc/systemd/system/coretest.service
[Unit]
Description=core limit test
[Service]
User=student
ExecStart=/usr/local/bin/coretest.sh
-- 유닛 파일 다섯 줄. User=student 로 student 권한에서 돈다
-- root 서비스라면 ulimit -c unlimited 가 hard 까지 올려 버린다(CAP_SYS_RESOURCE). 한도 시험이 안 된다
[root@ol7a ~]# systemctl daemon-reload; systemctl start coretest; sleep 1; journalctl -u coretest --no-pager -n 3 -o cat
before soft=0 hard=unlimited
raise=ok
after  soft=unlimited hard=unlimited
-- 시작 직후 soft 0, hard unlimited. limits.d 의 hard 0 이 적용되지 않았다
-- 서비스가 한도를 올리는 데 성공했다(raise=ok, soft unlimited)
-- systemd 가 띄운 프로세스는 PAM 을 거치지 않는다. pam_limits 가 읽는 limits.d 가 닿지 않는다

-- 실행 중인 프로세스의 한도를 /proc 에서 직접 본다
[root@ol7a ~]# P=$(systemctl show -p MainPID coretest | cut -d= -f2); echo "MainPID=$P"; grep -E 'Limit|core' /proc/$P/limits
MainPID=2687
Limit                     Soft Limit           Hard Limit           Units     
Max core file size        unlimited            unlimited            bytes     
-- /proc/PID/limits 는 실행 중인 프로세스의 실제 한도다. Soft·Hard 모두 unlimited
-- 셸이 exec sleep 으로 바뀌었으니 MainPID 2687 은 sleep 이다. 한도는 exec 를 거쳐도 유지된다

-- 서비스 프로세스에 SIGSEGV. core_pattern 이 abrt 파이프라 코어는 abrt 가 받는다. 명령마다 셸이 새로 떠서 PID 를 다시 구한다
[root@ol7a ~]# P=$(systemctl show -p MainPID coretest | cut -d= -f2); kill -SEGV $P; sleep 3; systemctl status coretest --no-pager | sed -n 3,4p; ls -d /var/spool/abrt/ccpp-* 2>&1 | tail -1
   Active: failed (Result: core-dump) since Mon 2026-11-16 17:17:46 KST; 2s ago
  Process: 2687 ExecStart=/usr/local/bin/coretest.sh (code=dumped, signal=SEGV)
/var/spool/abrt/ccpp-2026-11-16-17:17:43-2159
-- 증상   : limits.d 에 hard 0 을 넣었는데 서비스가 SIGSEGV 로 code=dumped
-- 원인   : 서비스는 PAM 로그인 세션이 아니라 limits.d 가 적용되지 않았다. 위 /proc 의 한도가 unlimited
-- 조치   : 유닛 drop-in 에 [Service] LimitCORE=0
-- 재확인 : /proc/PID/limits 의 Max core file size 가 0 0, 서비스 안의 ulimit 상향이 거부
-- Active: failed (Result: core-dump), Process … (code=dumped, signal=SEGV). systemd 가 덤프로 끝났다고 기록했다
-- 끝 줄은 abrt 의 저장 디렉터리 중 이름순 마지막이다. 이름 끝 2159 는 [1] 의 student sleep 이다
-- 서비스 덤프의 판정은 status 의 code=dumped 로 했다

-- systemd 의 전체 기본값 자리
[root@ol7a ~]# grep -n 'DefaultLimitCORE' /etc/systemd/system.conf
49:#DefaultLimitCORE=
-- 모든 서비스의 기본값 자리. 주석이라 커널 기본(soft 0, hard unlimited)을 그대로 쓴다
-- 여기를 바꾸면 systemctl daemon-reexec 가 필요하다. 이 실습은 유닛 하나에만 적용한다

-- 조치 : 유닛에 LimitCORE=0. drop-in 으로 넣는다
[root@ol7a ~]# mkdir -p /etc/systemd/system/coretest.service.d; printf '[Service]\nLimitCORE=0\n' > /etc/systemd/system/coretest.service.d/nocore.conf
[root@ol7a ~]# systemctl daemon-reload; systemctl cat coretest | tail -3; systemctl restart coretest; sleep 2; journalctl -u coretest --no-pager -n 3 -o cat
# /etc/systemd/system/coretest.service.d/nocore.conf
[Service]
LimitCORE=0
/usr/local/bin/coretest.sh: line 3: ulimit: core file size: cannot modify limit: Operation not permitted
raise=fail
after  soft=0 hard=0
-- systemctl cat 끝 세 줄에 drop-in 이 붙었다. 원래 유닛 파일은 고치지 않았다
-- 재시작 뒤 같은 스크립트가 올리기에 실패했다(raise=fail). after 도 soft 0 hard 0
-- 오류 줄이 /usr/local/bin/coretest.sh: line 3 으로 시작한다. 서비스 안에서 난 오류다
-- journal -n 3 이라 before 줄은 위로 밀려 잘렸다
[root@ol7a ~]# systemctl show -p LimitCORE coretest; P=$(systemctl show -p MainPID coretest | cut -d= -f2); grep core /proc/$P/limits
LimitCORE=0
Max core file size        0                    0                    bytes     
-- systemctl show 의 LimitCORE=0 과 /proc 의 0 0 이 일치한다
-- 설정 확인은 show, 실제 적용 확인은 /proc. 둘을 함께 본다
-- [OL8/9] systemd 239 이후는 LimitCORE=soft:hard 형식으로 둘을 따로 줄 수 있다

 [5] sysctl 로 막기 — 한도와 무관하게
--------------------------------------------------------------------------------

-- core_pattern 을 파이프로 바꾸면 커널이 코어를 파일로 쓰지 않고 그 프로그램에 넘긴다
-- /bin/false 는 받은 내용을 버리고 끝난다. suid_dumpable=0 : setuid 프로그램은 덤프 안 함
[root@ol7a ~]# printf 'kernel.core_pattern = |/bin/false\nfs.suid_dumpable = 0\n' > /etc/sysctl.d/90-nocore.conf; sysctl -p /etc/sysctl.d/90-nocore.conf
-- sysctl -p 파일 : 그 파일만 읽어 즉시 적용. 재부팅 때는 systemd-sysctl 이 sysctl.d 를 읽는다
-- 이 값이 abrt 파이프를 대체했다. abrt 가 코어를 받지 못한다
kernel.core_pattern = |/bin/false
fs.suid_dumpable = 0

-- 러너의 root 셸은 limits 파일을 넣기 전에 열린 세션이라 hard 가 unlimited 다. 그래도 파일이 생기지 않는다
[root@ol7a ~]# cd /root; ulimit -c unlimited; sleep 30 & sleep 1; kill -SEGV $!; wait; ls -l /root/core.* 2>&1
/tmp/_ol7lab_root.sh: line 1:  4055 Segmentation fault      (core dumped) sleep 30
ls: cannot access /root/core.*: No such file or directory
-- 러너 root 세션은 hard unlimited 라 soft 를 올릴 수 있었다. 그래도 파일이 없다
-- core_pattern 이 |/bin/false 라 커널이 코어를 /bin/false 에 넘겼고, /bin/false 는 버렸다
-- 한도와 무관하게 서버 전체에서 코어를 막는 방법이다. 장애 분석용 코어도 사라지니 정책으로 정한다

 [6] /tmp 를 noexec·nosuid·nodev 로

[root@ol7a ~]# cp -p /etc/fstab /root/fstab.orig

[root@ol7a ~]# mount /tmp; findmnt /tmp
TARGET SOURCE FSTYPE OPTIONS
/tmp   tmpfs  tmpfs  rw,nosuid,nodev,noexec,relatime,seclabel,size=524288k

 [7] 오류 재현 ① — 설치 스크립트 실행 실패
--------------------------------------------------------------------------------

-- 설치 프로그램이 /tmp 에 도우미 스크립트를 풀고 실행하는 상황
[root@ol7a ~]# printf '#!/bin/bash\necho "installer step OK"\n' > /tmp/setup.sh; chmod 755 /tmp/setup.sh; ls -l /tmp/setup.sh
-rwxr-xr-x. 1 root root 37 Nov 16 17:17 /tmp/setup.sh
-- 755, 실행 비트가 있다
[root@ol7a ~]# /tmp/setup.sh; echo "rc=$?"
/tmp/_ol7lab_root.sh: line 1: /tmp/setup.sh: Permission denied
rc=126
-- 증상   : 모드 755 인 /tmp/setup.sh 가 Permission denied, rc=126
-- 원인   : /tmp 가 noexec. 커널이 그 파일 시스템의 execve() 를 거부했다
-- 조치   : 설치 작업용 디렉터리를 noexec 가 아닌 곳에 두고 TMPDIR 로 지정
-- 재확인 : /u01/stage/tmp/setup.sh 가 installer step OK, rc=0
-- rc 126 은 "찾았지만 실행할 수 없음". 명령이 없을 때의 127 과 다르다
-- 권한 비트만 보고는 원인을 모른다. findmnt 의 OPTIONS 를 같이 본다

-- 권한 비트는 755 다. 막은 것은 마운트 옵션이다
[root@ol7a ~]# findmnt -n -o OPTIONS /tmp
rw,nosuid,nodev,noexec,relatime,seclabel,size=524288k
-- noexec 가 원인이다

-- 해석기를 직접 부르면 실행된다. noexec 는 execve() 만 막고 파일 읽기는 막지 않는다
[root@ol7a ~]# bash /tmp/setup.sh; echo "rc=$?"
installer step OK
rc=0
-- 해석기 bash 에 파일을 인자로 주면 실행된다. bash 는 파일을 읽을 뿐 execve() 하지 않는다
-- noexec 는 "스크립트 실행 금지" 가 아니다. 보안 가이드도 바이너리만 막는다고 적었다

-- 조치 : 설치 작업용 임시 디렉터리를 noexec 가 아닌 곳으로. TMPDIR 을 따르는 프로그램이 많다
[root@ol7a ~]# mkdir -p /u01/stage/tmp; cp -p /tmp/setup.sh /u01/stage/tmp/; TMPDIR=/u01/stage/tmp; $TMPDIR/setup.sh; echo "rc=$?"
installer step OK
rc=0
-- 같은 파일을 /u01 아래로 옮기자 실행됐다. 루트 파일 시스템에는 noexec 가 없다
-- 오라클 설치 도구도 TMPDIR·TMP 를 따른다. /tmp 를 바꾸지 않고 설치를 진행하는 방법이다

--------------------------------------------------------------------------------
 [8] nosuid·nodev 확인
--------------------------------------------------------------------------------

-- setuid 를 붙인 id 를 /tmp 와 /u01 에 하나씩 둔다. noexec 를 피하려고 /tmp 는 잠시 exec 로 다시 마운트한다
[root@ol7a ~]# mount -o remount,exec /tmp; findmnt -n -o OPTIONS /tmp
rw,nosuid,nodev,relatime,seclabel,size=524288k
-- nosuid 를 보려면 실행이 돼야 해서 잠시 exec 로 바꿨다. remount 는 다른 옵션을 유지한다
[root@ol7a ~]# cp /usr/bin/id /tmp/id.suid; cp /usr/bin/id /u01/stage/id.suid; chmod 4755 /tmp/id.suid /u01/stage/id.suid; ls -l /tmp/id.suid /u01/stage/id.suid
-rwsr-xr-x. 1 root root 37400 Nov 16 17:17 /tmp/id.suid
-rwsr-xr-x. 1 root root 37400 Nov 16 17:17 /u01/stage/id.suid
-- 두 곳에 같은 id 를 두고 4755(setuid root) 를 붙였다. 권한 표시의 s 가 setuid
[student@ol7a ~]$ /u01/stage/id.suid; /tmp/id.suid
uid=1000(student) gid=1000(student) euid=0(root) groups=1000(student),10(wheel) context=unconfined_u:unconfined_r:unconfined_t:s0-s0:c0.c1023
uid=1000(student) gid=1000(student) groups=1000(student),10(wheel) context=unconfined_u:unconfined_r:unconfined_t:s0-s0:c0.c1023
-- 첫 줄(/u01) 에는 euid=0(root) 가 있다. setuid 가 동작했다
-- 둘째 줄(/tmp) 에는 euid 가 없다. nosuid 가 setuid 비트를 무시했다
-- 뒤의 context= 는 SELinux 문맥 표시다. 이 과정에서는 다루지 않는다

-- nodev : 장치 파일을 만들 수는 있어도 열 수 없다
[root@ol7a ~]# mknod -m 666 /tmp/null2 c 1 3; echo test > /tmp/null2; echo "rc=$?"
/tmp/_ol7lab_root.sh: line 1: /tmp/null2: Permission denied
rc=1
-- nodev : 장치 파일은 만들어졌지만 열 수 없다. root 도 Permission denied
-- 사용자가 쓸 수 있는 곳에 장치 파일을 몰래 만들어 디스크를 직접 읽는 공격을 막는다
[root@ol7a ~]# rm -f /tmp/id.suid /u01/stage/id.suid /tmp/null2; mount -o remount,noexec /tmp; findmnt -n -o OPTIONS /tmp
rw,nosuid,nodev,noexec,relatime,seclabel,size=524288k
-- 시험 파일을 지우고 noexec 를 되살렸다. [6] 과 같은 옵션

 [변형] tmp.mount 유닛으로 같은 /tmp 만들기
--------------------------------------------------------------------------------

-- fstab 대신 systemd 가 제공하는 tmp.mount 를 쓰는 방법. 기본 옵션부터 본다
[root@ol7a ~]# grep -E '^(What|Where|Type|Options)' /usr/lib/systemd/system/tmp.mount; systemctl is-enabled tmp.mount; echo "rc=$?"
What=tmpfs
Where=/tmp
Type=tmpfs
Options=mode=1777,strictatime
disabled
rc=1
-- 패키지가 제공하는 tmp.mount 는 disabled. 옵션은 mode=1777,strictatime 뿐이고 noexec 가 없다
-- 이 유닛을 쓰려면 drop-in 으로 Options= 를 바꿔 enable 한다

-- fstab 줄이 있으면 systemd-fstab-generator 가 같은 이름(tmp.mount)의 유닛을 만든다
[root@ol7a ~]# systemctl cat tmp.mount | head -12
# /run/systemd/generator/tmp.mount
# Automatically generated by systemd-fstab-generator

[Unit]
SourcePath=/etc/fstab
Documentation=man:fstab(5) man:systemd-fstab-generator(8)
Before=remote-fs.target

[Mount]
What=tmpfs
Where=/tmp
Type=tmpfs
-- 지금 보이는 tmp.mount 는 /run/systemd/generator 의 것이다. fstab 의 /tmp 줄에서 만들어졌다
-- fstab 과 tmp.mount 는 같은 이름의 유닛이 된다. 둘을 함께 쓰면 어느 쪽이 이길지 헷갈리니 하나만 쓴다
-- head -12 로 잘랐다. 뒤에 Options= 줄이 이어진다

-- 실습 러너가 /tmp 에 둔 스크립트를 열고 실행 중이다. 지연 해제(-l)로 푼다
