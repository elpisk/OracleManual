================================================================================
 제16장 실습 05 — TCP Wrappers: hosts.allow 와 hosts.deny
 대상   : ol7a(서버: sshd, vsftpd), ol7b(접속 시험)
 목표   : 어떤 데몬이 libwrap 을 쓰는지 ldd 로 가려내고, hosts.allow·hosts.deny 로
          sshd·vsftpd 를 출발지별로 제한한다. 두 파일의 평가 순서를 실제 접속으로
          확인하고, libwrap 을 쓰지 않는 서비스에는 규칙이 효과가 없는 것과 ALL 을
          잘못 넣어 자기 자신까지 막는 실수를 재현한다
 배경   : TCP Wrappers 는 연결을 받은 데몬이 libwrap 의 hosts_access() 를 불러
          허용 여부를 묻는 방식이다. 패킷 필터가 아니라 응용 수준 검사라 데몬이
          libwrap 을 링크해야만 동작한다. hosts.allow 를 먼저 보고, 맞는 줄이 없으면
          hosts.deny 를 보고, 둘 다 없으면 허용한다. 파일은 연결마다 다시 읽는다
          (본문 16.7)
 소요   : 약 25분
 선행   : ol7-base, ol7b-base 스냅샷
 계정   : root
 주의   : hosts.deny 실험 전에 강사 PC(러너) 주소의 sshd 허용 줄을 hosts.allow 맨 위에
          먼저 넣는다. 이 줄이 없으면 [9] 에서 새 SSH 접속이 모두 끊긴다
 되돌림 : hosts.allow·hosts.deny 가 주석만 있는 원래 내용, vsftpd·tcp_wrappers 제거,
          ftp 서비스 닫힘. 확인: md5sum /etc/hosts.allow /etc/hosts.deny

--------------------------------------------------------------------------------
 [1] 어떤 데몬이 libwrap 을 쓰는가
--------------------------------------------------------------------------------

-- libwrap.so.0 을 링크한 실행 파일만 hosts.allow·hosts.deny 를 읽는다
[root@ol7a ~]# ldd /usr/sbin/sshd | grep libwrap
        libwrap.so.0 => /lib64/libwrap.so.0 (0x00007facdbe42000)
-- sshd 는 libwrap.so.0 을 링크했다. 괄호 안 값은 매핑 주소라 실행마다 다르다
-- 7.9 의 openssh 는 --with-tcp-wrappers 로 빌드돼 있다
-- 판정은 sshd 가 연결을 accept 한 직후, 키 교환 전에 한다

-- 기본 설치의 다른 데몬과 비교한다. 1 = 링크함, 0 = 링크 안 함
[root@ol7a ~]# for b in /usr/sbin/sshd /usr/sbin/rpcbind /usr/sbin/crond /usr/sbin/chronyd /usr/libexec/postfix/master /usr/bin/python2.7; do printf '%-30s %s\n' $b $(ldd $b 2>/dev/null | grep -c libwrap); done
/usr/sbin/sshd                 1
/usr/sbin/rpcbind              1
/usr/sbin/crond                0
/usr/sbin/chronyd              0
/usr/libexec/postfix/master    0
/usr/bin/python2.7             0
-- 1 = libwrap 링크, 0 = 링크 안 함
--   sshd·rpcbind  1  hosts.allow·hosts.deny 를 읽는다
--   crond·chronyd·postfix master·python  0  규칙을 넣어도 무시된다
-- rpcbind 는 NFS(14장)가 쓰는 포트 매퍼다. NFS 접근도 TCP Wrappers 로 제한할 수 있다는 뜻
-- chronyd 는 UDP 라 처음부터 대상이 아니다. TCP Wrappers 는 이름 그대로 TCP 용이다
-- 2>/dev/null : 파일이 없을 때의 ldd 오류를 숨겼다. 여섯 개 모두 있었다
-- 기본 설치에서 libwrap 대상은 sshd 와 rpcbind 둘뿐이다

[root@ol7a ~]# ldd /usr/sbin/vsftpd | grep libwrap; grep -E '^(tcp_wrappers|listen|anonymous_enable)' /etc/vsftpd/vsftpd.conf
        libwrap.so.0 => /lib64/libwrap.so.0 (0x00007fd765ead000)
anonymous_enable=YES

tcp_wrappers=YES
-- vsftpd 도 libwrap 을 링크했고 tcp_wrappers=YES 다. 기본 설정 그대로 hosts 파일을 읽는다
-- anonymous_enable=YES : 익명 FTP 허용(14장). 여기서는 인사말만 볼 것이라 상관없다
-- listen=NO, listen_ipv6=YES : IPv6 소켓 하나로 IPv4 도 받는다(아래 ss 의 *:21)
-- vsftpd 는 standalone 데몬이다. xinetd 없이 libwrap 을 직접 부른다

[root@ol7a ~]# systemctl start vsftpd; firewall-cmd --add-service=ftp; ss -ltn | grep ':21 '
success
LISTEN 0      32                 *:21              *:*          
-- vsftpd 가 21 을 듣는다. 방화벽에는 ftp 서비스를 runtime 으로 열었다
-- firewall-cmd 의 success 가 ss 출력보다 먼저 나왔다
-- 방화벽이 막으면 TCP Wrappers 까지 오지도 않는다. 둘 다 열려야 시험이 된다

-- 접속 시험 기준값. ssh 는 키가 없으니 인증 단계에서 거절되면 "도달함"이다
-- BatchMode=yes : 암호를 묻지 않음, ConnectTimeout=5 : 5초 제한
[root@ol7b ~]# ssh -o BatchMode=yes -o StrictHostKeyChecking=no -o ConnectTimeout=5 ol7a true; echo "rc=$?"
Warning: Permanently added 'ol7a,172.16.225.61' (ECDSA) to the list of known hosts.
Permission denied (publickey,gssapi-keyex,gssapi-with-mic,password).
rc=255
-- 기준값. ol7b 의 ssh 는 sshd 까지 가서 인증 단계에서 거절됐다
-- Permission denied 목록은 서버가 제시한 인증 방법이다. 키가 없고 BatchMode 라 암호도 못 쓴다
-- rc=255 는 ssh 의 오류 종료. 여기서는 "도달했다" 는 표시로 읽는다
-- Warning 줄은 첫 접속이라 ol7b 의 known_hosts 에 ol7a 키를 넣었다는 알림

-- FTP 는 제어 연결 인사말만 본다. QUIT 을 보내고 끊는다
[root@ol7b ~]# echo QUIT | ncat -w 5 ol7a 21; echo "rc=$?"
220 (vsFTPd 3.0.2)
221 Goodbye.
rc=0
-- 기준값. 220 인사말과 QUIT 응답 221. FTP 제어 연결이 정상
-- 3.0.2 는 7.9 의 vsftpd 판
-- 데이터 연결(목록·전송)은 쓰지 않는다. 인사말만으로 판정 결과가 보인다

 [3] 관리 경로 먼저 열어 두기
--------------------------------------------------------------------------------

-- 러너가 접속한 주소의 sshd 를 hosts.allow 맨 위에 둔다. 실무에서도 관리 PC 가 먼저다
[root@ol7a ~]# cp -p /etc/hosts.allow /root/hosts.allow.orig; cp -p /etc/hosts.deny /root/hosts.deny.orig
[root@ol7a ~]# echo "sshd: ${SSH_CLIENT%% *}" >> /etc/hosts.allow; grep -v '^#' /etc/hosts.allow
sshd: 172.16.225.1
-- 관리 PC 허용 줄 하나. ${SSH_CLIENT%% *} 는 SSH_CLIENT 의 첫 필드(주소)만 남긴다
-- 이 줄은 [변형] 전까지 hosts.allow 맨 위에 있다
-- 원본 두 파일은 /root 에 사본을 떴다. 되돌릴 때 쓴다

--------------------------------------------------------------------------------
 [4] hosts.deny 로 ol7b 의 sshd 막기
--------------------------------------------------------------------------------

-- 형식 : 데몬목록 : 클라이언트목록 [: 옵션]
[root@ol7a ~]# echo "sshd: 172.16.225.62" >> /etc/hosts.deny; grep -v '^#' /etc/hosts.deny
sshd: 172.16.225.62
-- hosts.deny 에 ol7b 주소 하나. 형식은 데몬 : 클라이언트
-- 데몬 이름은 실행 파일 이름(argv[0])이다. sshd, vsftpd

-- sshd 재시작 없이 바로 적용되는지 본다
[root@ol7b ~]# ssh -o BatchMode=yes -o ConnectTimeout=5 ol7a true; echo "rc=$?"
Connection timed out during banner exchange
rc=255
-- 증상   : ol7b 의 ssh 가 5초 뒤 "Connection timed out during banner exchange"
-- 원인   : hosts.deny 의 sshd: 172.16.225.62 에 걸렸다. sshd 가 인사말(banner) 없이 연결을 닫았다
-- 조치   : 허용하려면 hosts.allow 에 같은 줄을 넣는다([5])
-- 재확인 : [5] 에서 다시 Permission denied(인증 단계 도달)
-- sshd 재시작 없이 바로 적용됐다. libwrap 은 연결마다 파일을 읽는다
-- 7.9 의 OpenSSH 7.4 클라이언트는 이 경우 banner exchange 시간 초과로 보인다
-- 방화벽 거부(즉시 응답)와 달리 ConnectTimeout 5초를 다 기다렸다
-- TCP 연결은 맺어졌다. 막힌 곳은 sshd 안이다

-- 서버 쪽 기록
[root@ol7a ~]# grep 'refused connect' /var/log/secure | tail -1
Nov 16 12:48:51 ol7a sshd[2305]: refused connect from 172.16.225.62 (172.16.225.62)
-- 서버 쪽 기록. sshd[2305] 가 refused connect from 을 남겼다
-- 괄호 앞은 이름, 괄호 안은 주소. 역방향 조회 전이라 둘 다 주소다
-- 이 줄이 TCP Wrappers 거부의 증거다. 방화벽 거부는 여기 남지 않는다([변형])

-- FTP 는 영향 없다. 데몬 이름이 다르다
[root@ol7b ~]# echo QUIT | ncat -w 5 ol7a 21; echo "rc=$?"
220 (vsFTPd 3.0.2)
221 Goodbye.
rc=0
-- 같은 ol7b 에서 FTP 는 그대로 된다. 규칙은 데몬 이름(sshd)별이다
-- 모든 데몬을 막으려면 ALL 을 쓴다([9])

--------------------------------------------------------------------------------
 [5] 평가 순서 — allow 가 deny 를 이긴다
--------------------------------------------------------------------------------

[root@ol7a ~]# echo "sshd: 172.16.225.62" >> /etc/hosts.allow
[root@ol7b ~]# ssh -o BatchMode=yes -o ConnectTimeout=5 ol7a true; echo "rc=$?"
Permission denied (publickey,gssapi-keyex,gssapi-with-mic,password).
rc=255
-- allow 에 같은 줄을 넣자 다시 인증 단계까지 갔다
-- 파일을 고친 직후다. 재시작 없음

-- tcpdmatch 데몬 주소 : 두 파일을 읽어 판정만 보여 준다. 실제 접속은 하지 않는다
[root@ol7a ~]# tcpdmatch sshd 172.16.225.62
client:   address  172.16.225.62
server:   process  sshd
access:   granted
-- tcpdmatch : 두 파일을 실제 판정 순서대로 읽어 결과만 보인다
-- 같은 주소가 allow 와 deny 에 다 있으면 allow 가 먼저라 granted
-- client·server·access 세 줄. 판정에 쓴 줄 위치는 -d 없이 보이지 않는다

[root@ol7a ~]# sed -i '/^sshd: 172.16.225.62$/d' /etc/hosts.allow; tcpdmatch sshd 172.16.225.62 | tail -1
access:   denied
-- allow 에서 그 줄을 지우자 denied. 접속하지 않고 판정을 확인했다
-- sed -i '/패턴/d' : 그 줄만 지운다. ^ $ 로 줄 전체를 맞춰 다른 줄을 건드리지 않았다

--------------------------------------------------------------------------------
 [6] vsftpd 제한과 옵션
--------------------------------------------------------------------------------

[root@ol7a ~]# echo "vsftpd: 172.16.225.62" >> /etc/hosts.deny
[root@ol7b ~]# echo QUIT | ncat -w 5 ol7a 21; echo "rc=$?"
421 Service not available.
-- vsftpd 를 막자 vsftpd 가 421 Service not available. 를 보내고 끝냈다
-- sshd 와 달리 FTP 는 거부 응답 문장을 돌려준다. 데몬마다 거부를 보이는 방식이 다르다
-- ncat 의 rc=0 은 연결은 됐다는 뜻이다. 판정은 연결을 받은 뒤 데몬 안에서 일어난다
-- vsftpd 는 거부해도 secure 가 아니라 vsftpd 자체 로그 방식에 따른다
rc=0

-- 같은 거부를 twist 옵션으로. 거부 대신 지정한 명령의 출력을 클라이언트에 보낸다
[root@ol7a ~]# sed -i 's/^vsftpd: 172.16.225.62$/vsftpd: 172.16.225.62 : twist \/bin\/echo "421 FTP closed for %a"/' /etc/hosts.deny; grep -v '^#' /etc/hosts.deny
sshd: 172.16.225.62
vsftpd: 172.16.225.62 : twist /bin/echo "421 FTP closed for %a"
-- 셋째 필드에 옵션. twist 는 데몬 대신 이 명령을 실행해 출력을 클라이언트에 보낸다
-- %a 는 클라이언트 주소로 바뀐다
-- 다른 확장: %h 호스트 이름, %d 데몬 이름, %c 클라이언트 정보
[root@ol7b ~]# echo QUIT | ncat -w 5 ol7a 21; echo "rc=$?"
421 FTP closed for 172.16.225.62
Ncat: Connection reset by peer.
rc=1
-- 클라이언트에 421 FTP closed for 172.16.225.62 가 그대로 보였다. %a 가 주소로 확장됐다
-- echo 가 끝나며 연결이 끊겨 ncat 은 Connection reset by peer, rc=1
-- twist 는 판정을 바꾸지 않는다. 거부 문장을 원하는 대로 만들 뿐이다
-- twist 대신 spawn 을 쓰면 명령을 실행하고 원래 판정(거부)을 계속한다

-- tcpdchk : 두 파일의 문법·데몬 이름을 점검한다. -v : 규칙을 풀어서 보여 줌
[root@ol7a ~]# tcpdchk -v 2>&1 | grep -v '^$' | head -20
/tmp/_ol7lab_root.sh: line 1: tcpdchk: command not found
-- 7.9 의 tcp_wrappers-7.6-77 에는 tcpdchk 가 없다. 확인한 도구는 tcpdmatch 뿐이다
-- 문법 점검은 tcpdmatch 로 데몬·주소 몇 개를 넣어 판정을 직접 본다
-- 다른 배포판 문서의 tcpdchk 예는 7.9 에서 그대로 쓸 수 없다

--------------------------------------------------------------------------------
 [7] 오류 재현 ① — libwrap 을 쓰지 않는 서비스
--------------------------------------------------------------------------------

-- 8080 에 ncat 리스너를 띄우고 방화벽을 연 다음, hosts.deny 에 ncat 을 넣는다
[root@ol7a ~]# nohup ncat -lk 8080 >/dev/null 2>&1 </dev/null &
[root@ol7a ~]# firewall-cmd --add-port=8080/tcp; echo "ncat: 172.16.225.62" >> /etc/hosts.deny
success
[root@ol7b ~]# echo hi | ncat -w 3 ol7a 8080; echo "rc=$?"
rc=0
-- hosts.deny 에 ncat 을 넣었는데 ol7b 의 hi 가 그대로 들어갔다

[root@ol7a ~]# ldd /usr/bin/ncat | grep -c libwrap; tcpdmatch ncat 172.16.225.62 | tail -1
0
access:   denied
-- 증상   : hosts.deny 에 ncat: 172.16.225.62 가 있어도 ol7b 의 8080 접속 성공(rc=0)
-- 원인   : ncat 은 libwrap 을 링크하지 않는다(ldd 결과 0). 데몬이 묻지 않으니 파일은 읽히지 않는다
-- 조치   : 방화벽 rich rule 로 같은 출발지를 거부한다
-- 재확인 : 아래 ncat 이 Connection refused
-- tcpdmatch 는 denied 라고 말한다. tcpdmatch 는 파일만 볼 뿐 데몬이 libwrap 을 쓰는지는 모른다
-- 판정 도구와 실제 동작이 어긋나는 대표 사례다. 먼저 ldd 로 대상인지 본다
-- 오류 메시지도 경고도 없다. 그래서 오래 모르고 지나친다

-- 이런 서비스는 방화벽에서 막는다. 같은 출발지를 rich rule 로 거부
[root@ol7a ~]# firewall-cmd --add-rich-rule='rule family="ipv4" source address="172.16.225.62/32" port port="8080" protocol="tcp" reject'
success
[root@ol7b ~]# echo hi | ncat -w 3 ol7a 8080; echo "rc=$?"
Ncat: Connection refused.
-- rich rule 의 reject 는 icmp-port-unreachable 이라 Connection refused 로 보인다(실습 03)
-- 패킷 단계에서 막았으니 ncat 이 libwrap 을 쓰든 말든 상관없다
rc=1
[root@ol7a ~]# firewall-cmd --remove-rich-rule='rule family="ipv4" source address="172.16.225.62/32" port port="8080" protocol="tcp" reject'; sed -i '/^ncat:/d' /etc/hosts.deny
success
-- rich rule 과 ncat 줄을 지웠다

--------------------------------------------------------------------------------
 [8] 패턴 — 대역, 도메인, EXCEPT
--------------------------------------------------------------------------------

-- 172.16.225. : 점으로 끝나면 앞부분 일치. .example.com : 점으로 시작하면 도메인 끝부분 일치
[root@ol7a ~]# sed -i '/^sshd: 172.16.225.62$/d' /etc/hosts.deny; echo "sshd: 172.16.225. EXCEPT 172.16.225.1" >> /etc/hosts.deny; grep -v '^#' /etc/hosts.deny
vsftpd: 172.16.225.62 : twist /bin/echo "421 FTP closed for %a"
sshd: 172.16.225. EXCEPT 172.16.225.1
-- 172.16.225. 은 점으로 끝나 앞부분 일치. EXCEPT 뒤의 .1 은 뺀다
[root@ol7a ~]# tcpdmatch sshd 172.16.225.62 | tail -1; tcpdmatch sshd 172.16.225.1 | tail -1; tcpdmatch sshd 10.0.0.5 | tail -1
access:   denied
access:   granted
access:   granted
-- .62 denied, .1 granted(EXCEPT), 10.0.0.5 granted(패턴 밖)
-- 관리 PC 를 빼는 데 EXCEPT 를 쓰면 줄 하나로 대역 거부와 예외를 함께 적는다
-- 10.0.0.5 는 어느 줄에도 맞지 않아 기본 허용
-- 기본 거부가 필요하면 마지막에 ALL 을 둔다

[root@ol7a ~]# sed -i 's/^sshd: 172.16.225. EXCEPT 172.16.225.1$/sshd: .example.com/' /etc/hosts.deny
[root@ol7a ~]# tcpdmatch sshd ol7b.example.com | sed -n '1,3p;$p'
client:   hostname ol7b.example.com
-- 도메인 패턴 .example.com 은 이름으로 비교한다. tcpdmatch 에 이름을 주자 hostname 과 address 를 함께 풀었다
client:   address  172.16.225.62
server:   process  sshd
access:   denied
-- 이름 끝이 .example.com 이라 denied
-- sed -n '1,3p;$p' 로 머리 세 줄과 끝 줄만 남겼다
[root@ol7b ~]# ssh -o BatchMode=yes -o ConnectTimeout=5 ol7a true; echo "rc=$?"
Connection timed out during banner exchange
rc=255
-- ol7b 의 실제 접속도 막혔다. sshd 가 주소 172.16.225.62 를 /etc/hosts 로 역방향 조회해 ol7b.example.com 을 얻었다
-- 역방향 조회가 안 되는 환경(DNS 없음, hosts 미등록)에서는 도메인 패턴이 맞지 않는다
-- 조회가 느리면 연결마다 지연이 생긴다. 운영에서는 주소 패턴을 권한다

--------------------------------------------------------------------------------
 [9] 오류 재현 ② — hosts.deny 에 ALL: ALL
--------------------------------------------------------------------------------

-- 흔한 "기본 거부" 설정. 허용 목록을 다 쓰기 전에 deny 부터 넣었다
[root@ol7a ~]# cp -p /root/hosts.deny.orig /etc/hosts.deny; echo "ALL: ALL" >> /etc/hosts.deny; grep -v '^#' /etc/hosts.allow /etc/hosts.deny
/etc/hosts.allow:sshd: 172.16.225.1
/etc/hosts.deny:ALL: ALL
-- hosts.deny 를 원본으로 돌리고 ALL: ALL 한 줄. allow 에는 관리 PC 의 sshd 만 남았다
-- vsftpd twist·도메인 줄은 이 복원으로 함께 사라졌다

-- ol7a 자기 자신에서 ssh·ftp 를 해 본다
[root@ol7a ~]# ssh -o BatchMode=yes -o StrictHostKeyChecking=no -o ConnectTimeout=5 localhost true; echo "rc=$?"
Connection timed out during banner exchange
rc=255
-- ol7a 자신의 ssh localhost 도 banner exchange 시간 초과
[root@ol7a ~]# echo QUIT | ncat -w 5 localhost 21; echo "rc=$?"
421 Service not available.
-- localhost 의 FTP 도 421. 루프백도 클라이언트 주소일 뿐 예외가 아니다
-- 서버 안의 감시 스크립트·백업 도구가 localhost 로 붙는 경우 함께 멈춘다
rc=0
[root@ol7b ~]# ssh -o BatchMode=yes -o ConnectTimeout=5 ol7a true; echo "rc=$?"
Connection timed out during banner exchange
rc=255
-- 증상   : ALL: ALL 뒤 ol7a 자신의 ssh localhost·FTP, ol7b 의 ssh 가 모두 거부
-- 원인   : allow 에 맞는 줄이 없는 모든 연결이 deny 의 ALL: ALL 에 걸린다. 127.0.0.1 도 포함
-- 조치   : allow 에 ALL: LOCAL 127.0.0.1 [::1] 과 필요한 클라이언트를 먼저 적는다
-- 재확인 : 아래 localhost·ol7b 의 ssh 가 인증 단계까지, ol7b 의 FTP 가 220

-- 강사 PC 는? hosts.allow 의 첫 줄 덕분에 판정이 다르다
[root@ol7a ~]# tcpdmatch sshd ${SSH_CLIENT%% *} | tail -1; tcpdmatch sshd 127.0.0.1 | tail -1
access:   granted
access:   denied
-- 관리 PC(172.16.225.1) granted, 127.0.0.1 denied
-- [3] 의 안전줄 덕분에 강사 PC 의 새 접속은 이 순간에도 가능했다
-- 이 줄이 없었다면 러너는 재접속할 방법이 없다. 콘솔로만 복구된다

-- 조치 : 자기 자신(LOCAL·루프백)과 관리 대역을 allow 에 명시한다
[root@ol7a ~]# echo "ALL: LOCAL 127.0.0.1 [::1]" >> /etc/hosts.allow; echo "sshd vsftpd: 172.16.225.62" >> /etc/hosts.allow; grep -v '^#' /etc/hosts.allow
sshd: 172.16.225.1
ALL: LOCAL 127.0.0.1 [::1]
sshd vsftpd: 172.16.225.62
-- LOCAL 은 점 없는 이름(localhost 등). [::1] 은 IPv6 루프백의 표기
-- 데몬 목록에는 공백으로 여러 데몬을 적는다(sshd vsftpd)
-- 쉼표도 쓸 수 있다. 줄 순서: 관리 PC → 자기 자신 → 업무 클라이언트
[root@ol7a ~]# ssh -o BatchMode=yes -o ConnectTimeout=5 localhost true; echo "rc=$?"
Host key verification failed.
rc=255
-- Host key verification failed. 는 sshd 까지 갔다는 뜻이다
-- 처음 시도(ALL: ALL)는 banner 단계에서 끊겨 localhost 호스트 키가 known_hosts 에 남지 않았다
-- 이번에는 StrictHostKeyChecking=no 를 빼서 BatchMode 가 낯선 호스트 키를 거부했다. TCP Wrappers 와는 무관
[root@ol7b ~]# ssh -o BatchMode=yes -o ConnectTimeout=5 ol7a true; echo "rc=$?"
Permission denied (publickey,gssapi-keyex,gssapi-with-mic,password).
rc=255
-- ol7b 는 인증 단계까지
-- deny 의 ALL: ALL 은 남아 있다. 나머지 주소는 계속 거부된다
[root@ol7b ~]# echo QUIT | ncat -w 5 ol7a 21; echo "rc=$?"
220 (vsFTPd 3.0.2)
221 Goodbye.
rc=0
-- ol7b 의 FTP 도 220 인사말로 돌아왔다
-- 이것이 "기본 거부 + 명시 허용" 의 완성형이다

--------------------------------------------------------------------------------
 [변형] 같은 차단을 방화벽으로 — 클라이언트가 보는 차이
--------------------------------------------------------------------------------

-- TCP Wrappers 를 원래대로 돌리고, ol7b 의 ssh 를 rich rule 로 거부한다
[root@ol7a ~]# cp -p /root/hosts.allow.orig /etc/hosts.allow; cp -p /root/hosts.deny.orig /etc/hosts.deny
[root@ol7a ~]# firewall-cmd --add-rich-rule='rule family="ipv4" source address="172.16.225.62/32" service name="ssh" reject'
success
-- TCP Wrappers 는 원본으로, 대신 rich rule 로 ol7b 의 ssh 서비스를 거부했다
-- service name="ssh" 는 ssh 서비스 정의의 포트(22/tcp)로 풀린다
[root@ol7b ~]# ssh -o BatchMode=yes -o ConnectTimeout=5 ol7a true; echo "rc=$?"
ssh: connect to host ol7a port 22: Connection refused
rc=255
-- 클라이언트 메시지가 ssh: connect to host ol7a port 22: Connection refused 로 바뀌었다
-- TCP Wrappers(banner exchange 시간 초과) 와 메시지가 다르다. 연결 자체가 맺어지지 않았다
-- 즉시 돌아왔다. 5초를 기다리지 않았다
-- 판정 위치가 커널(방화벽)이냐 데몬(libwrap)이냐가 메시지를 가른다
-- 두 방법을 겹쳐 쓰면 한쪽 실수를 다른 쪽이 막는다
-- 8 로 옮길 서버라면 처음부터 방화벽 쪽으로 설계한다

-- 방화벽 거부는 sshd 까지 오지 않으니 /var/log/secure 에 새 줄이 없다
[root@ol7a ~]# grep -c 'refused connect' /var/log/secure
4
-- refused connect 기록은 4 건 그대로다([4]·[8]·[9] 의 ol7b·localhost 몫)
-- 방화벽 거부는 패킷이 sshd 까지 오지 않아 secure 에 남지 않는다. 로그가 필요하면 rich rule 에 log 를 붙인다
[root@ol7a ~]# firewall-cmd --remove-rich-rule='rule family="ipv4" source address="172.16.225.62/32" service name="ssh" reject'
success
