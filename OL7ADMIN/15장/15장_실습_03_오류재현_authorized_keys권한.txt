================================================================================
 제15장 실습 03 — 오류 재현: authorized_keys 경로의 권한
 대상   : ol7a (클라이언트, student), ol7b (서버, student)
 목표   : 홈 디렉터리·~/.ssh·authorized_keys 의 권한과 소유자를 하나씩 바꿔 가며
          키 인증이 언제 거부되는지 확인한다. 클라이언트는 이유를 알려 주지 않으므로
          서버의 /var/log/secure 에서 거부 이유를 읽는다
 배경   : sshd 는 StrictModes yes(기본값)일 때 authorized_keys 를 읽기 전에 그 파일과
          상위 디렉터리를 홈까지 검사한다. 소유자가 본인이나 root 가 아니거나, 그룹·
          다른 사용자가 쓸 수 있으면 남이 키를 끼워 넣을 수 있다고 보고 파일을
          무시한다. 읽기 권한은 문제 삼지 않는다 (본문 15.2, 15.4)
 소요   : 약 30분
 선행   : ol7-base, ol7b-base 스냅샷
 계정   : student (접속), root (권한 변경·로그 확인)
 주의   : [8] 에서 ol7b 의 StrictModes 를 잠시 끈다. 같은 단계에서 되돌린다
 되돌림 : 권한 700/700/600, StrictModes 기본값, 두 노드의 /home/student/.ssh 삭제
          → stat, sshd -T | grep strictmodes
================================================================================

-- 키 배포 단계의 암호 입력은 SSH_ASKPASS 도우미(/usr/local/bin/ask)가 대신한다.
-- 시험 접속은 모두 BatchMode=yes 로 한다. 키 인증이 안 되면 암호를 묻지 않고 바로 실패한다.

--------------------------------------------------------------------------------
 [0] 시작 전 상태 기록
--------------------------------------------------------------------------------

[root@ol7b ~]# stat -c '%a %U:%G %n' /home /home/student; ls -ld /home/student/.ssh
755 root:root /home
-- /home 은 755 root. sshd 는 홈 위쪽(/home, /)도 root 소유·쓰기 금지인지 본다.
-- stat -c '%a %U:%G %n': 8진 권한, 소유자:그룹, 이름. 이 실습 내내 이 형식을 쓴다.
700 student:student /home/student
-- 홈 700 student. useradd 기본값이다.
ls: cannot access /home/student/.ssh: No such file or directory
-- 키가 아직 없다. [1] 에서 만든다.
-- 서버 설정은 sshd_config 를 grep 하지 않고 sshd -T 로 본다. 주석 줄에 속지 않는다.
[root@ol7b ~]# sshd -T | grep -E '^(strictmodes|authorizedkeysfile|pubkeyauthentication|loglevel) '
pubkeyauthentication yes
strictmodes yes
loglevel INFO
authorizedkeysfile .ssh/authorized_keys
-- strictmodes yes 가 이 실습의 주인공. 7.9 기본값이고 sshd_config 에는 주석으로만 있다.
-- loglevel INFO: 거부 이유 한 줄은 남지만 검사 과정은 남지 않는다([7] 에서 DEBUG).
-- authorizedkeysfile 의 상대 경로는 사용자 홈 기준이다.
-- pubkeyauthentication yes: 공개 키 인증 자체는 켜져 있다. 이 값이 원인인 경우는 드물다.

--------------------------------------------------------------------------------
 [1] 준비 — 키 만들고 배포
--------------------------------------------------------------------------------

[student@ol7a ~]$ ssh-keygen -t rsa -N '' -f ~/.ssh/id_rsa -q; ssh-keyscan -t ecdsa ol7b 2>/dev/null > ~/.ssh/known_hosts
[student@ol7a ~]$ SSH_ASKPASS=/usr/local/bin/ask DISPLAY=:0 ssh-copy-id ol7b 2>&1 | grep Number
Number of key(s) added: 1
-- 02 에서 본 절차를 한 줄로 줄였다. 질문은 student 암호 하나.
-- -q 로 키를 조용히 만들고 known_hosts 는 keyscan 으로 미리 채웠다.
-- grep Number 로 결과 한 줄만 남겼다. 나머지 INFO 줄은 02 [5] 와 같다.
[root@ol7b ~]# stat -c '%a %U:%G %n' /home/student /home/student/.ssh /home/student/.ssh/authorized_keys
700 student:student /home/student
700 student:student /home/student/.ssh
600 student:student /home/student/.ssh/authorized_keys
-- 기준값: 700 / 700 / 600, 모두 student. 아래 단계는 이 중 하나씩만 바꾼다.
-- 시험 접속은 원격에서 echo OK 를 실행하고 종료 코드를 찍는다.
-- BatchMode=yes 라 키가 거부되면 암호로 넘어가지 않고 바로 끝난다.
-- 시험 접속. 이후 단계에서 같은 명령을 되풀이한다.
[student@ol7a ~]$ ssh -o BatchMode=yes ol7b 'echo OK'; echo rc=$?
OK
rc=0
-- OK 와 rc=0. 이후 단계에서 결과는 이 두 줄 아니면
-- Permission denied 와 rc=255 둘 중 하나다.

--------------------------------------------------------------------------------
 [2] ~/.ssh 를 755 로 — 다른 사람이 읽을 수만 있게
--------------------------------------------------------------------------------

[root@ol7b ~]# chmod 755 /home/student/.ssh; stat -c '%a %n' /home/student/.ssh
755 /home/student/.ssh
-- 그룹·다른 사용자에게 읽기·실행만 준다. 쓰기는 여전히 student 만.
-- chmod 는 root 가 ol7b 에서 했다. 실제로는 사용자 자신이 실수로 바꾸는 경우가 많다.
[student@ol7a ~]$ ssh -o BatchMode=yes ol7b 'echo OK'; echo rc=$?
OK
rc=0
-- 통과. 읽기 권한은 sshd 가 문제 삼지 않는다.
-- sshd 는 "남이 쓸 수 있는가"만 본다. 읽기는 비밀 유지 문제라 별개로 다룬다.
-- 다만 다른 사용자가 known_hosts·공개 키 이름을 볼 수 있으니 700 을 권한다.

--------------------------------------------------------------------------------
 [3] 오류 ① — ~/.ssh 를 그룹이 쓸 수 있게(775)
--------------------------------------------------------------------------------

[root@ol7b ~]# chmod 775 /home/student/.ssh; stat -c '%a %n' /home/student/.ssh
775 /home/student/.ssh
-- g+w: student 그룹의 다른 구성원이 이 디렉터리에 파일을 만들고 지울 수 있다.
-- authorized_keys 를 지우고 자기 키로 바꿔 넣을 수 있다는 뜻이 된다.
-- 디렉터리의 w 는 "안의 파일 이름을 바꾸고 지울 권한"이다. 파일 내용 권한과 별개다.
[student@ol7a ~]$ ssh -o BatchMode=yes ol7b 'echo OK'; echo rc=$?
Permission denied (publickey,gssapi-keyex,gssapi-with-mic,password).
rc=255
-- 클라이언트가 받는 말은 이것뿐이다. 서버가 받는 방식 목록에는 publickey 가 여전히 있다.
-- 즉 서버 설정 문제처럼 보이지 않는다. 그래서 로그를 봐야 한다.
-- 클라이언트에서 ssh -v 를 해도 Offering 다음에 바로 다음 방식으로 넘어갈 뿐이다.
-- 클라이언트는 "Permission denied" 만 받는다. 이유는 서버 로그에 있다.
[root@ol7b ~]# grep sshd /var/log/secure | tail -3
Nov 16 12:43:53 ol7b sshd[5517]: pam_unix(sshd:session): session closed for user student
Nov 16 12:43:54 ol7b sshd[5722]: Authentication refused: bad ownership or modes for directory /home/student/.ssh
-- 필드: 시각, 호스트, sshd[PID], 메시지. PID 5722 가 이번 접속을 받은 프로세스.
-- 문제의 경로를 정확히 짚어 준다. 디렉터리인지 파일인지도 구분한다.
-- tail -3 은 최근 세 줄. 접속이 많은 서버에서는 grep 'Authentication refused' 로 좁힌다.
Nov 16 12:43:54 ol7b sshd[5722]: Connection closed by 172.16.225.61 port 57160 [preauth]
-- [preauth]: 인증 전에 끊겼다. 클라이언트가 다른 방법이 없어 포기한 것.
-- 윗줄 session closed 는 [1] 의 성공한 접속이 끝난 기록이다.
-- 같은 내용이 journal 에도 있다. -u sshd 로 sshd 것만.
[root@ol7b ~]# journalctl -u sshd --no-pager -n 3 -o cat
Accepted publickey for student from 172.16.225.61 port 57158 ssh2: RSA SHA256:zY18xECe3lkHbys5aRoAg/Yw8vZ/ML6CrYK3NJ1chwY
-- journal 에도 같은 줄이 있다. -o cat 은 시각·호스트 머리를 뺀 메시지만.
-- 57158 은 755 때 성공한 접속, 57160 은 775 때 거부된 접속.
-- secure 파일과 journal 은 같은 메시지를 받는다. rsyslog 가 없는 서버면 journal 만 본다.
Authentication refused: bad ownership or modes for directory /home/student/.ssh
Connection closed by 172.16.225.61 port 57160 [preauth]
[root@ol7b ~]# chmod 700 /home/student/.ssh
[student@ol7a ~]$ ssh -o BatchMode=yes ol7b 'echo OK'; echo rc=$?
OK
rc=0
-- 700 으로 되돌리자 바로 통과. sshd 재시작은 필요 없다. 접속할 때마다 검사한다.

-- 증상   : 키 인증 "Permission denied (publickey,gssapi-keyex,gssapi-with-mic,password)."
-- 원인   : ~/.ssh 가 775(그룹 쓰기). secure 로그 "bad ownership or modes for directory /home/student/.ssh"
-- 조치   : chmod 700 /home/student/.ssh
-- 재확인 : 같은 접속이 OK, rc=0

--------------------------------------------------------------------------------
 [4] authorized_keys 의 권한 — 644 와 664
--------------------------------------------------------------------------------

[root@ol7b ~]# chmod 644 /home/student/.ssh/authorized_keys; stat -c '%a %n' /home/student/.ssh/authorized_keys
644 /home/student/.ssh/authorized_keys
-- 파일을 다른 사람이 읽을 수 있게. 공개 키 목록이라 읽혀도 큰 문제는 없다.
-- 다만 어떤 키가 이 계정에 들어올 수 있는지가 드러난다. 그래서 600 을 권한다.
[student@ol7a ~]$ ssh -o BatchMode=yes ol7b 'echo OK'; echo rc=$?
OK
rc=0
-- 통과. 공식 문서도 600 을 권하지만 644 는 거부하지 않는다.
-- 읽기만 열린 상태는 남이 키를 바꿀 수 없으니 sshd 기준으로는 안전하다.
[root@ol7b ~]# chmod 664 /home/student/.ssh/authorized_keys; stat -c '%a %n' /home/student/.ssh/authorized_keys
664 /home/student/.ssh/authorized_keys
-- g+w. 그룹 구성원이 이 파일에 자기 키를 한 줄 덧붙일 수 있다.
[student@ol7a ~]$ ssh -o BatchMode=yes ol7b 'echo OK'; echo rc=$?
Permission denied (publickey,gssapi-keyex,gssapi-with-mic,password).
rc=255
-- 거부.
-- 664 는 g+w 가 들어 있다.
[root@ol7b ~]# grep 'Authentication refused' /var/log/secure | tail -1
Nov 16 12:43:54 ol7b sshd[6403]: Authentication refused: bad ownership or modes for file /home/student/.ssh/authorized_keys
-- 이번에는 for file. 디렉터리와 파일을 구분해 알려 준다.
-- PID 6403 은 664 로 바꾼 뒤의 접속이다.
-- grep 'Authentication refused' 로 찾으면 다른 sshd 줄에 묻히지 않는다.
[root@ol7b ~]# chmod 600 /home/student/.ssh/authorized_keys
-- 600 으로 되돌렸다.
-- 확인 접속은 생략했다. [6] 의 마지막에서 같은 상태로 OK 를 본다.

--------------------------------------------------------------------------------
 [5] 오류 ② — 홈 디렉터리 권한
--------------------------------------------------------------------------------

-- 공동 작업용으로 홈을 그룹에 열어 주는 경우가 있다. 그룹 쓰기까지 열면?
[root@ol7b ~]# chmod 775 /home/student; stat -c '%a %n' /home/student
775 /home/student
-- 홈에 그룹 쓰기. 공동 작업 디렉터리를 홈으로 쓰는 팀에서 생기는 설정이다.
-- ~/.ssh 와 authorized_keys 는 700·600 그대로다. 홈 하나만 바꿨다.
-- 홈에 쓰기가 되면 ~/.ssh 자체를 다른 이름으로 바꾸고 새로 만들 수 있다.
-- 디렉터리 쓰기 권한은 그 아래 항목 이름을 바꿀 수 있다는 뜻이라 홈도 검사 대상이다.
[student@ol7a ~]$ ssh -o BatchMode=yes ol7b 'echo OK'; echo rc=$?
Permission denied (publickey,gssapi-keyex,gssapi-with-mic,password).
rc=255
-- 거부. ~/.ssh 와 파일은 그대로 700·600 인데도 실패한다.
-- 클라이언트 메시지는 [3] 과 똑같다.
[root@ol7b ~]# grep 'Authentication refused' /var/log/secure | tail -1
Nov 16 12:43:55 ol7b sshd[6635]: Authentication refused: bad ownership or modes for directory /home/student
-- 경로가 /home/student 로 한 단계 올라갔다. 검사가 홈까지 거슬러 올라간다는 증거.

-- 증상   : ~/.ssh·authorized_keys 권한이 맞는데도 Permission denied, rc=255
-- 원인   : 홈 디렉터리 775. 로그 "bad ownership or modes for directory /home/student"
-- 조치   : chmod 700 /home/student (또는 g-w 만 빼서 751·755)
-- 재확인 : 751 에서 OK, rc=0 (아래)
-- 다른 사용자 쓰기(o+w)도 같다. 읽기·실행만 연 755·751 은 통과한다.
[root@ol7b ~]# chmod 757 /home/student; stat -c '%a %n' /home/student
757 /home/student
-- 다른 사용자 쓰기(o+w)만 열었다. 그룹은 읽기·실행.
[student@ol7a ~]$ ssh -o BatchMode=yes ol7b 'echo OK'; echo rc=$?
Permission denied (publickey,gssapi-keyex,gssapi-with-mic,password).
rc=255
-- 역시 거부. 그룹이든 다른 사용자든 쓰기 비트 하나면 충분하다.
-- 757 은 실무에서 잘 안 쓰지만 chmod -R 실수로 생긴다.
[root@ol7b ~]# chmod 751 /home/student; stat -c '%a %n' /home/student
751 /home/student
-- 그룹 읽기·실행, 다른 사용자 실행만. 쓰기는 student 만.
[student@ol7a ~]$ ssh -o BatchMode=yes ol7b 'echo OK'; echo rc=$?
OK
rc=0
-- 통과. 홈을 열어야 한다면 쓰기만 빼고 연다.
-- 웹 서버가 ~/public_html 을 읽어야 하는 경우 등에 751·755 를 쓴다.
[root@ol7b ~]# chmod 700 /home/student
-- 홈을 기준값 700 으로 되돌렸다.
-- 홈 권한은 세 가지 중 가장 놓치기 쉽다. ~/.ssh 만 보고 끝내기 때문이다.

--------------------------------------------------------------------------------
 [6] 소유자 — 파일을 root 가 만들어 둔 경우
--------------------------------------------------------------------------------

-- 관리자가 root 로 키를 붙여 넣고 소유자를 안 바꾸는 실수. root 소유는 허용되는가?
[root@ol7b ~]# chown root:root /home/student/.ssh/authorized_keys; stat -c '%a %U:%G %n' /home/student/.ssh/authorized_keys
600 root:root /home/student/.ssh/authorized_keys
-- 관리자가 root 로 cat >> 한 뒤 chown 을 잊은 상황. 권한은 600 그대로.
-- 이 상황은 키 배포 스크립트를 root 로 돌릴 때 자주 생긴다.
[student@ol7a ~]$ ssh -o BatchMode=yes ol7b 'echo OK'; echo rc=$?
Permission denied (publickey,gssapi-keyex,gssapi-with-mic,password).
rc=255
-- 거부. 이번에는 secure 로그를 찍지 않았지만 원인은 소유자가 아니다.
-- sshd 는 authorized_keys 를 사용자 권한(student)으로 연다. root 소유 600 은 열지 못한다.
-- LogLevel INFO 에서는 이 경우 Authentication refused 줄이 남지 않는다. 그래서 더 찾기 어렵다.
-- root 소유에 600 이면 sshd(사용자 권한으로 파일을 여는 단계)가 읽지 못한다. 644 로 열면?
[root@ol7b ~]# chmod 644 /home/student/.ssh/authorized_keys
-- root 소유 그대로 다른 사람 읽기를 열었다.
[student@ol7a ~]$ ssh -o BatchMode=yes ol7b 'echo OK'; echo rc=$?
OK
rc=0
-- 통과. 소유자 조건은 "본인 또는 root" 다. root 소유 644 는 허용된다.
-- [변형] 에서 이 성질을 이용해 키를 홈 밖으로 옮긴다.
-- 정리: root 소유는 괜찮지만 student 가 읽을 수 있어야 한다.
-- 다른 일반 사용자 소유라면?
[root@ol7b ~]# chown nobody:nobody /home/student/.ssh/authorized_keys; chmod 644 /home/student/.ssh/authorized_keys
-- 본인도 root 도 아닌 사용자 소유. nobody 가 이 파일을 고칠 수 있다.
-- 홈을 다른 서버에서 rsync 로 옮겼는데 UID 가 달라 생기는 경우와 같다.
[student@ol7a ~]$ ssh -o BatchMode=yes ol7b 'echo OK'; echo rc=$?
Permission denied (publickey,gssapi-keyex,gssapi-with-mic,password).
rc=255
-- 거부.
[root@ol7b ~]# grep 'Authentication refused' /var/log/secure | tail -1
Nov 16 12:43:56 ol7b sshd[7437]: Authentication refused: bad ownership or modes for file /home/student/.ssh/authorized_keys
-- 권한(644)은 [4] 에서 통과한 값인데 거부. 이번 이유는 소유자다.
-- 메시지가 ownership or modes 로 같아서 stat 으로 소유자와 권한을 둘 다 본다.
-- UID 불일치라면 ls -ln 으로 숫자 UID 를 보는 것이 빠르다.
[root@ol7b ~]# chown student:student /home/student/.ssh/authorized_keys; chmod 600 /home/student/.ssh/authorized_keys
[student@ol7a ~]$ ssh -o BatchMode=yes ol7b 'echo OK'; echo rc=$?
OK
rc=0
-- student 소유 600 으로 되돌리자 통과.
-- 소유자 조건은 chown 한 번으로 바로 풀린다. 재시작은 필요 없다.

--------------------------------------------------------------------------------
 [7] 거부 이유를 더 자세히 — LogLevel DEBUG 로 한 번
--------------------------------------------------------------------------------

-- LogLevel 을 DEBUG 로 올리면 sshd 가 어떤 파일을 어떤 순서로 검사했는지 secure 로그에 남긴다.
-- 설정을 바꾸고 reload 하면 새 접속부터 적용된다.
[root@ol7b ~]# cp -p /etc/ssh/sshd_config /root/sshd_config.orig; echo 'LogLevel DEBUG' >> /etc/ssh/sshd_config; sshd -t && systemctl reload sshd; sshd -T | grep loglevel
loglevel DEBUG
-- 같은 키워드가 기본 파일에 없어서 덧붙여도 적용됐다(05 [4] 와 대조).
-- DEBUG 는 DEBUG1 과 같다. 운영 서버에서는 로그가 많아져 오래 두지 않는다.
-- sshd -t && reload: 검사에 통과했을 때만 반영한다. 05 에서 이 습관을 다룬다.
[root@ol7b ~]# chmod 775 /home/student/.ssh
-- [3] 과 같은 오류를 다시 만든다.
-- 이번에는 검사 과정까지 로그에 남는지 본다.
[student@ol7a ~]$ ssh -o BatchMode=yes ol7b 'echo OK'; echo rc=$?
Permission denied (publickey,gssapi-keyex,gssapi-with-mic,password).
rc=255
[root@ol7b ~]# grep -E 'trying public key file|bad ownership|Authentication refused|Failed publickey|userauth_pubkey: test' /var/log/secure | tail -5 | cut -c17-130
ol7b sshd[7437]: Authentication refused: bad ownership or modes for file /home/student/.ssh/authorized_keys
-- 첫 줄은 [6] 의 nobody 소유 때 기록(PID 7437). 이번 접속은 PID 7915 다.
ol7b sshd[7915]: debug1: userauth_pubkey: test whether pkalg/pkblob are acceptable for RSA SHA256:zY18xECe3lkHbys5
-- 클라이언트가 공개 키를 내밀었다. 받아 줄지 시험하는 단계.
-- test whether ... acceptable: 서명 없이 공개 키만으로 묻는 질의(02 [7] 의 Offering).
ol7b sshd[7915]: debug1: trying public key file /home/student/.ssh/authorized_keys
-- 읽을 파일을 정한 뒤 경로 검사를 한다.
ol7b sshd[7915]: Authentication refused: bad ownership or modes for directory /home/student/.ssh
-- 검사에 걸려 파일을 열지 않았다.
ol7b sshd[7915]: Failed publickey for student from 172.16.225.61 port 57262 ssh2: RSA SHA256:zY18xECe3lkHbys5aRoAg
-- 결과는 Failed publickey. INFO 에서는 이 줄이 없었다.
-- 순서가 그대로 보인다: 키 질의 → 파일 결정 → 경로 검사 → 거부.
-- cut -c17-130 으로 시각을 떼고 130자에서 잘랐다. 지문 뒷부분이 잘린 이유.
[root@ol7b ~]# cp -p /root/sshd_config.orig /etc/ssh/sshd_config; sshd -t && systemctl reload sshd; chmod 700 /home/student/.ssh; sshd -T | grep loglevel
loglevel INFO
-- 원본으로 되돌리고 reload. ~/.ssh 도 700.
-- 디버그 줄은 secure 에 그대로 남아 있다. 장애 분석 뒤 잊지 말고 LogLevel 을 되돌린다.

--------------------------------------------------------------------------------
 [8] StrictModes no — 검사를 끄면
--------------------------------------------------------------------------------

-- 검사를 끄면 그룹이 쓸 수 있는 ~/.ssh 도 통과한다. 운영 서버에서는 쓰지 않는다.
[root@ol7b ~]# echo 'StrictModes no' >> /etc/ssh/sshd_config; sshd -t && systemctl reload sshd
[root@ol7b ~]# sshd -T | grep strictmodes; chmod 775 /home/student/.ssh
strictmodes no
-- 이번에도 덧붙인 값이 적용됐다. 기본 파일의 StrictModes 는 주석이라서다.
-- 덧붙인 줄은 [7] 의 원본 복구로 지워진 상태에서 새로 넣었다.
[student@ol7a ~]$ ssh -o BatchMode=yes ol7b 'echo OK'; echo rc=$?
OK
rc=0
-- ~/.ssh 775 인데 통과. 검사를 끄면 [3]~[6] 의 거부가 모두 사라진다.
-- 대신 그룹 구성원이 키를 넣어 student 로 들어올 수 있게 된다.
-- 검사를 끄는 대신 권한을 고치거나 AuthorizedKeysFile 을 옮긴다([변형]).
[root@ol7b ~]# cp -p /root/sshd_config.orig /etc/ssh/sshd_config; sshd -t && systemctl reload sshd; sshd -T | grep strictmodes
strictmodes yes
-- 되돌리자 같은 775 상태에서 다시 거부된다(아래).
-- reload 뒤 새 접속부터 적용. ~/.ssh 는 아직 775 다.
[student@ol7a ~]$ ssh -o BatchMode=yes ol7b 'echo OK'; echo rc=$?
Permission denied (publickey,gssapi-keyex,gssapi-with-mic,password).
rc=255
[root@ol7b ~]# chmod 700 /home/student/.ssh

--------------------------------------------------------------------------------
 [9] 클라이언트 쪽 검사 — 개인 키와 ~/.ssh
--------------------------------------------------------------------------------

-- 클라이언트도 개인 키 권한을 본다. 그룹 읽기(640)만 열어도 키를 버린다.
[student@ol7a ~]$ chmod 640 ~/.ssh/id_rsa; ssh -o BatchMode=yes ol7b 'echo OK'; echo rc=$?
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
@         WARNING: UNPROTECTED PRIVATE KEY FILE!          @
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
Permissions 0640 for '/home/student/.ssh/id_rsa' are too open.
-- 그룹 읽기만 열어도 거부. 클라이언트 검사는 서버보다 엄격하다(읽기도 안 됨).
-- 경고문은 02 [8] 의 644 때와 같고 숫자만 0640 이다.
It is required that your private key files are NOT accessible by others.
This private key will be ignored.
Load key "/home/student/.ssh/id_rsa": bad permissions
Permission denied (publickey,gssapi-keyex,gssapi-with-mic,password).
rc=255
-- 클라이언트 검사는 이유를 화면에 쓴다. 서버 검사와의 차이.
-- 서버는 이유를 숨긴다(공격자에게 정보를 주지 않으려고). 클라이언트는 사용자를 돕는다.
[student@ol7a ~]$ chmod 600 ~/.ssh/id_rsa
-- 클라이언트 쪽 ~/.ssh 디렉터리 권한은 보는가?
[student@ol7a ~]$ chmod 777 ~/.ssh; ssh -o BatchMode=yes ol7b 'echo OK'; echo rc=$?; chmod 700 ~/.ssh
OK
-- 클라이언트 쪽 ~/.ssh 777 은 통과했다. 7.4 의 ssh 는 디렉터리 권한을 보지 않는다.
-- 서버 쪽(ol7b) 권한은 이 단계 내내 기준값이었다.
-- 그래도 777 이면 다른 사람이 known_hosts·config 를 바꿀 수 있다. 700 으로 되돌렸다.
rc=0

--------------------------------------------------------------------------------
 [10] 한 번에 보기 — namei
--------------------------------------------------------------------------------

-- namei -l : 경로의 각 구성 요소 권한·소유자를 한 줄씩. 키 인증 장애 때 맨 먼저 칠 명령.
[root@ol7b ~]# chmod 775 /home/student; namei -l /home/student/.ssh/authorized_keys
f: /home/student/.ssh/authorized_keys
-- namei -l: 경로를 / 부터 한 단계씩, 권한·소유자·그룹·이름 순으로.
-- util-linux 에 들어 있어 7.9 기본 설치에서 바로 쓴다.
dr-xr-xr-x root    root    /
drwxr-xr-x root    root    home
drwxrwxr-x student student student
-- 이 줄 하나로 홈의 그룹 쓰기(rwx 가운데 w)가 보인다. stat 을 여러 번 칠 필요가 없다.
-- 홈만 775, 나머지는 정상.
drwx------ student student .ssh
-rw------- student student authorized_keys
-- / 와 home 은 root 소유 쓰기 금지. ~/.ssh·파일은 기준값.
-- / 가 dr-xr-xr-x(555)인 것은 7.9 의 기본값이다.
[root@ol7b ~]# chmod 700 /home/student; namei -l /home/student/.ssh/authorized_keys
f: /home/student/.ssh/authorized_keys
dr-xr-xr-x root    root    /
drwxr-xr-x root    root    home
drwx------ student student student
drwx------ student student .ssh
-rw------- student student authorized_keys
-- 되돌린 뒤. 네 단계 모두 student 만 쓰기 가능.

--------------------------------------------------------------------------------
 [변형] 다른 위치의 authorized_keys — AuthorizedKeysFile
--------------------------------------------------------------------------------

-- 키를 홈 밖(/etc/ssh/keys/사용자)에 두면 사용자가 자기 키를 고칠 수 없게 관리할 수 있다.
[root@ol7b ~]# mkdir -p /etc/ssh/keys; install -m 644 -o root -g root /home/student/.ssh/authorized_keys /etc/ssh/keys/student; ls -l /etc/ssh/keys
total 4
-rw-r--r--. 1 root root 406 Nov 16 12:43 student
-- install -m 644 -o root: 복사와 권한·소유자 지정을 한 번에. 파일 이름은 사용자 이름.
-- 406바이트: student 의 RSA 2048 공개 키 한 줄.
-- [1] 에서 -b 없이 만들어 2048비트다. 02 의 3072 키(570바이트)보다 짧다.
[root@ol7b ~]# sed -i 's|^AuthorizedKeysFile.*|AuthorizedKeysFile /etc/ssh/keys/%u|' /etc/ssh/sshd_config; sshd -t && systemctl reload sshd; sshd -T | grep authorizedkeysfile
authorizedkeysfile /etc/ssh/keys/%u
-- %u 는 사용자 이름으로 바뀐다. %h(홈)도 쓸 수 있다.
-- 원래 줄을 sed 로 고쳤다. AuthorizedKeysFile 은 기본 파일에 살아 있는 줄이라 덧붙이면 안 된다.
[root@ol7b ~]# mv /home/student/.ssh/authorized_keys /root/ak.student
-- 홈의 파일은 치웠다. 이제 키는 /etc/ssh/keys/student 에만 있다.
[student@ol7a ~]$ ssh -o BatchMode=yes ol7b 'echo OK'; echo rc=$?
OK
-- 통과. root 소유 644 라 student 가 자기 키를 고칠 수 없다.
-- 키 추가·회수를 관리자만 하게 만드는 구성이다.
-- 공유 계정(oracle 등)에 여러 사람이 키를 넣는 환경에서 쓸 만하다.
-- [OL8/9] 중앙 관리가 필요하면 AuthorizedKeysCommand(SSSD 등)로 키를 가져오는 방법도 있다.
rc=0
[root@ol7b ~]# grep sshd /var/log/secure | tail -2
Nov 16 12:43:59 ol7b sshd[9980]: Disconnected from 172.16.225.61 port 57310
Nov 16 12:43:59 ol7b sshd[9960]: pam_unix(sshd:session): session closed for user student
-- 정상 접속은 secure 에 Accepted 와 session opened/closed 가 남는다. 여기서는 끝의 두 줄.
-- 거부 줄이 없으니 새 위치의 키로 들어온 것이다.
[root@ol7b ~]# cp -p /root/sshd_config.orig /etc/ssh/sshd_config; sshd -t && systemctl reload sshd; rm -rf /etc/ssh/keys; mv /root/ak.student /home/student/.ssh/authorized_keys
[root@ol7b ~]# sshd -T | grep authorizedkeysfile
authorizedkeysfile .ssh/authorized_keys
-- 원본 설정과 원래 파일 위치로 되돌렸다.
-- /etc/ssh/keys 는 지웠다.
-- 되돌린 뒤 홈의 authorized_keys 로 다시 접속된다(아래 OK).
[student@ol7a ~]$ ssh -o BatchMode=yes ol7b 'echo OK'; echo rc=$?
OK
rc=0
