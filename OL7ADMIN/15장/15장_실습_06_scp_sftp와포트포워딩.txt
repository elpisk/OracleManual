 [2] scp — 파일 하나, 디렉터리 통째로
--------------------------------------------------------------------------------

-- 형식: scp 원본 대상. 원격 쪽은 [사용자@]호스트:경로. 경로를 비우면 원격 홈.
[root@ol7a ~]# scp /root/xfer/services ol7b:/tmp/
-- 출력이 없다. 터미널이 없으면 scp 는 진행 막대를 찍지 않는다.
-- 대상 경로가 디렉터리(/tmp/)면 같은 이름으로 그 안에 놓인다.
-- 원격 쪽 경로는 ol7b 의 셸이 해석한다. ~ 나 변수를 쓸 때 주의한다.
-- -r : 디렉터리 재귀. -p : 시간·권한 보존. -q : 진행 표시 끔.
[root@ol7a ~]# scp -rq /root/xfer ol7b:/tmp/xfer-r; scp -rpq /root/xfer ol7b:/tmp/xfer-rp
-- 대상 xfer-r 이 없으므로 원본 디렉터리가 그 이름으로 복사된다.
-- 대상이 이미 있으면 그 안에 xfer 가 하나 더 생긴다. 두 번 실행할 때 흔한 실수.
[root@ol7b ~]# ls -l --time-style=+%F_%R /tmp/xfer-r/sub/note.txt /tmp/xfer-rp/sub/note.txt
-rw-r--r--. 1 root root 6 2026-01-01_09:00 /tmp/xfer-rp/sub/note.txt
-rw-r--r--. 1 root root 6 2026-11-16_16:10 /tmp/xfer-r/sub/note.txt
-- -p 를 준 쪽(xfer-rp)은 2026-01-01_09:00 그대로, 안 준 쪽(xfer-r)은 복사한 시각 16:10.
-- 백업 파일을 옮길 때 시각이 바뀌면 "며칠 된 파일 지우기" 같은 정리 스크립트가 엉뚱하게 돈다.
-- 내용이 같은지 체크섬으로 확인한다.
[root@ol7a ~]# cd /root/xfer && md5sum data.bin services sub/note.txt
4c8c1835593230d6e46bfae886284262  data.bin
8e0abe8547f0411554a35b97447b2fbd  services
b1946ac92492d2347c6235b4d2611184  sub/note.txt
-- 원본(ol7a)의 체크섬. 32자리 16진수 + 파일 이름.
-- 상대 경로로 찍으려고 cd 한 뒤 md5sum 했다.
[root@ol7b ~]# cd /tmp/xfer-rp && md5sum data.bin services sub/note.txt
4c8c1835593230d6e46bfae886284262  data.bin
8e0abe8547f0411554a35b97447b2fbd  services
b1946ac92492d2347c6235b4d2611184  sub/note.txt
-- ol7b 쪽 사본과 세 파일 모두 같다. 전송 뒤에는 이렇게 양쪽을 대조한다.
-- 프롬프트의 노드 이름(ol7a·ol7b)으로 어느 쪽 출력인지 구분한다.
-- 원격 → 로컬, 그리고 진행 표시가 켜진 기본 출력(터미널이 없어서 마지막 줄만 나온다).
[root@ol7a ~]# scp ol7b:/etc/os-release /tmp/os-release.ol7b; head -2 /tmp/os-release.ol7b
NAME="Oracle Linux Server"
VERSION="7.9"
-- 원격 → 로컬 방향. 원격 쪽을 앞에 쓰면 된다. 원본과 대상의 순서가 cp 와 같다.
-- 원격 파일 두 개를 한 번에 받으려면 원격 쪽에 글롭을 따옴표로 감싸 넘긴다.
-- -l : 대역 제한(Kbit/s). 20MB 를 8000Kbit/s 로 → 약 20초
[root@ol7a ~]# time scp -q -l 8000 /root/xfer/data.bin ol7b:/tmp/limited.bin

real    0m20.385s
-- -l 8000 은 Kbit/s. 8000Kbit/s = 1000KB/s 쯤이라 20MiB 에 약 20초. 실측 20.385초.
-- user·sys 는 0.1초 남짓. 시간 대부분은 대역 제한으로 기다린 것이다.
-- 운영 중인 DB 서버의 백업 전송은 이렇게 대역을 줄여 업무 트래픽을 지킨다.
-- [OL8/9] OL9 의 scp 는 SFTP 프로토콜을 쓴다. -l 같은 옵션은 그대로다.
user    0m0.041s

 [3] sftp 배치 모드
--------------------------------------------------------------------------------

-- -b 파일 : 명령을 파일에서 읽음. 배치 모드는 BatchMode=yes 가 자동으로 붙어 암호를 묻지 않는다.
[root@ol7a ~]# printf 'cd /tmp\nmkdir sftp_t\ncd sftp_t\nput /root/xfer/services\nlcd /tmp\nget services services.back\nls -l\nbye\n' > /root/batch1; cat /root/batch1
cd /tmp
mkdir sftp_t
cd sftp_t
put /root/xfer/services
lcd /tmp
get services services.back
ls -l
bye
-- 배치 파일 내용. 원격 cd·mkdir·put, 로컬 lcd, 다시 받아오기(get), 목록, 종료.
-- l 로 시작하는 명령(lcd, lls)은 로컬 쪽.
[root@ol7a ~]# sftp -b /root/batch1 ol7b
sftp> cd /tmp
sftp> mkdir sftp_t
sftp> cd sftp_t
sftp> put /root/xfer/services
sftp> lcd /tmp
sftp> get services services.back
sftp> ls -l
-rw-r--r--    1 root     root       670293 Nov 16 16:10 services
sftp> bye
-- 배치 모드는 실행한 명령을 sftp> 프롬프트와 함께 찍는다. 로그로 남기기 좋다.
-- ls -l 은 원격 파일 목록. 크기 670293 이 원본과 같다.
-- 암호를 묻지 않았다. -b 는 BatchMode=yes 를 함께 켠다. 키가 없으면 그냥 실패한다.
[root@ol7a ~]# md5sum /root/xfer/services /tmp/services.back
8e0abe8547f0411554a35b97447b2fbd  /root/xfer/services
8e0abe8547f0411554a35b97447b2fbd  /tmp/services.back
-- put 한 것을 다시 get 했는데 체크섬이 같다.
-- get 의 두 번째 인자는 로컬 파일 이름이다.

 [4] 배치 안의 명령이 실패하면
--------------------------------------------------------------------------------

-- 없는 파일을 get 하는 줄을 가운데 넣는다.
[root@ol7a ~]# printf 'cd /tmp/sftp_t\nget nofile.txt\nput /etc/hosts\nbye\n' > /root/batch2; sftp -b /root/batch2 ol7b; echo rc=$?
sftp> cd /tmp/sftp_t
sftp> get nofile.txt
File "/tmp/sftp_t/nofile.txt" not found.
-- 없는 파일 get 에서 실패했다.
-- 메시지는 원격 경로를 절대 경로로 보여 준다.
rc=1
-- 그 뒤의 put /etc/hosts 와 bye 는 찍히지 않았다. 첫 실패에서 멈추고 rc=1.
[root@ol7b ~]# ls /tmp/sftp_t
services
-- ol7b 확인: hosts 가 올라가지 않았다. 앞 단계의 services 만 있다.

-- 증상   : sftp -b 가 "File \"/tmp/sftp_t/nofile.txt\" not found." 뒤 멈춤, rc=1, put 미실행
-- 원인   : 배치 모드는 명령 하나가 실패하면 나머지를 실행하지 않는다
-- 조치   : 실패해도 되는 줄 앞에 - (-get nofile.txt). 필요한 줄은 그대로 두고 rc 를 검사
-- 재확인 : 다시 실행하면 put·bye 까지 진행, rc=0, ol7b 에 hosts 생김
-- 줄 앞의 - : 그 명령이 실패해도 계속한다.
[root@ol7a ~]# sed -i 's/^get nofile/-get nofile/' /root/batch2; sftp -b /root/batch2 ol7b; echo rc=$?
sftp> cd /tmp/sftp_t
sftp> -get nofile.txt
File "/tmp/sftp_t/nofile.txt" not found.
sftp> put /etc/hosts
sftp> bye
rc=0
-- 같은 실패 메시지가 찍혔지만 계속 진행했고 rc=0. 실패 사실은 rc 에 반영되지 않는다.
[root@ol7b ~]# ls /tmp/sftp_t
hosts
services
-- hosts 가 올라갔다.
-- 전송 스크립트는 rc 로 성공을 판단한다. - 를 붙인 줄의 실패는 따로 확인해야 한다.

 [5] rsync — 바뀐 것만
--------------------------------------------------------------------------------

-- -a : 재귀 + 권한·시간·링크 보존, -v : 보낸 파일 목록, 원본 끝의 / 는 "디렉터리 안의 것"
[root@ol7a ~]# rsync -av /root/xfer/ ol7b:/tmp/xfer-rs/ | tail -6
services
sub/
sub/note.txt

sent 21,647,360 bytes  received 119 bytes  43,294,958.00 bytes/sec
total size is 21,641,819  speedup is 1.00
-- 첫 실행: 세 파일을 모두 보냈다(tail -6 로 앞의 목록 일부는 잘렸다).
-- sent 약 21.6MB, speedup 1.00 은 전체를 그대로 보냈다는 뜻이다.
-- 전송 속도는 약 43MB/s. 같은 호스트의 가상 스위치라 빠르다.
-- 다시 돌리면 보낼 것이 없다.
[root@ol7a ~]# rsync -av /root/xfer/ ol7b:/tmp/xfer-rs/ | tail -3

sent 130 bytes  received 13 bytes  286.00 bytes/sec
total size is 21,641,819  speedup is 151,341.39
-- 두 번째: 보낸 것은 130바이트. 크기·시각이 같아 파일 목록만 비교하고 끝났다.
-- speedup = 전체 크기 / 실제 전송량. 다시 돌려도 비용이 거의 없다.
-- 그래서 rsync 는 cron 으로 반복하는 동기화에 맞는다.
-- 하나를 바꾸고, 하나를 지운 뒤 --delete 와 -n(미리 보기)
[root@ol7a ~]# echo world >> /root/xfer/sub/note.txt; rm /root/xfer/services
[root@ol7a ~]# rsync -avn --delete /root/xfer/ ol7b:/tmp/xfer-rs/ | head -5
sending incremental file list
deleting services
./
sub/note.txt
-- -n(미리 보기): 원본에서 지운 services 를 deleting 으로, 바뀐 note.txt 를 보낼 목록으로 보인다.
-- ./ 는 디렉터리 시각이 바뀌어 갱신 대상에 든 것. 실제로는 아무것도 하지 않았다.
-- head -5 로 잘랐다. 끝의 통계 줄은 보이지 않는다.
[root@ol7a ~]# rsync -av --delete /root/xfer/ ol7b:/tmp/xfer-rs/ | tail -2; ssh ol7b ls /tmp/xfer-rs
sent 191 bytes  received 61 bytes  504.00 bytes/sec
total size is 20,971,532  speedup is 83,220.37
data.bin
sub
-- 실행 뒤 대상에는 data.bin 과 sub 만 남았다. services 가 지워졌다.
-- 원본과 대상을 바꿔 쓰면 원본 쪽이 지워진다. --delete 앞에는 늘 -n.
-- [OL8/9] OL8 은 rsync 3.1.3, OL9 는 3.2.3. 이 실습의 옵션은 모두 같다.
-- [OL8/9] rsync 3.1.2(7.9) 는 --info=progress2 등 대부분 옵션이 8/9 의 3.1.3·3.2 와 같다.

 [6] 로컬 포워딩 -L — ol7b 의 127.0.0.1 서비스에 닿기
--------------------------------------------------------------------------------

-- ol7b 에 127.0.0.1:8000 에서만 듣는 작은 웹 서버를 띄운다(Python 2.7 표준 모듈).
[root@ol7b ~]# mkdir -p /tmp/www; echo 'served by ol7b 127.0.0.1:8000' > /tmp/www/hello.txt
[root@ol7b ~]# nohup python -c 'import os, BaseHTTPServer as B, SimpleHTTPServer as S; os.chdir("/tmp/www"); B.HTTPServer(("127.0.0.1", 8000), S.SimpleHTTPRequestHandler).serve_forever()' >/tmp/http.log 2>&1 </dev/null &
[root@ol7b ~]# ss -ltnp | grep 8000; curl -s http://127.0.0.1:8000/hello.txt
LISTEN 0      5          127.0.0.1:8000      0.0.0.0:*    users:(("python",pid=10420,fd=3))
-- 웹 서버는 127.0.0.1:8000 에만 연다. 밖에서는 처음부터 닿지 않는 서비스다.
-- Python 2.7 표준 모듈(BaseHTTPServer)이라 별도 설치가 없다.
-- 백로그 5 는 Python 기본값이다.
served by ol7b 127.0.0.1:8000
-- 밖에서 직접은 닿지 않는다.
[root@ol7a ~]# curl -sS -m 5 http://ol7b:8000/hello.txt; echo rc=$?
curl: (7) Failed connect to ol7b:8000; No route to host
rc=7
-- ol7a 에서 직접: No route to host. 127.0.0.1 전용이라는 이유보다 먼저 ol7b 의 firewalld 가
-- 8000 을 거부하면서 icmp-host-prohibited 를 돌려준 결과다. 22번만 열린 서버의 전형.
-- -N : 원격 명령 없이 포워딩만, -L 로컬포트:목적지:목적지포트 (목적지는 ol7b 에서 본 이름)
[root@ol7a ~]# nohup ssh -N -L 18000:localhost:8000 ol7b >/tmp/fwd1.log 2>&1 </dev/null &
-- 출력 없이 뒤로 떴다. 연결과 인증이 끝날 때까지 3초 기다린 뒤 확인한다.
-- -f 를 쓰면 ssh 가 인증 뒤 스스로 뒤로 간다. 여기서는 nohup ... & 를 썼다.
[root@ol7a ~]# ss -ltnp | grep 18000
LISTEN 0      128        127.0.0.1:18000      0.0.0.0:*    users:(("ssh",pid=2530,fd=5))     
LISTEN 0      128            [::1]:18000         [::]:*    users:(("ssh",pid=2530,fd=4))     
-- ssh(pid 2530)가 18000 을 연다. 127.0.0.1 과 [::1] 두 루프백에만.
-- 다른 PC 에서 이 포트를 쓰려면 -L 0.0.0.0:18000:... 또는 -g 가 필요하다.
-- 그때는 ol7a 의 firewalld 에서도 18000 을 열어야 한다.
[root@ol7a ~]# curl -s http://localhost:18000/hello.txt
served by ol7b 127.0.0.1:8000
-- ol7a 의 18000 → SSH 연결 → ol7b 에서 localhost:8000. 목적지 이름은 ol7b 가 해석했다.
-- 방화벽은 22번만 열려 있는데 8000 의 내용을 받았다.
[root@ol7b ~]# tail -1 /tmp/http.log
127.0.0.1 - - [16/Nov/2026 16:11:04] "GET /hello.txt HTTP/1.1" 200 -
-- ol7b 웹 서버 로그의 접속 주소는 127.0.0.1. 웹 서버는 ol7a 를 모른다. sshd 가 대신 접속했다.
[root@ol7b ~]# ss -tnp | grep ':8000 '
-- 요청이 끝나 연결이 닫혔으므로 비었다. 요청 중에는 sshd 가 8000 에 붙은 줄이 보인다.

--------------------------------------------------------------------------------
 [7] 오류 ① — 이미 쓰는 로컬 포트로 포워딩
--------------------------------------------------------------------------------

-- 같은 18000 으로 하나 더. ssh 는 경고만 내고 연결은 유지한다(포워딩 없는 빈 세션).
[root@ol7a ~]# timeout 8 ssh -N -L 18000:localhost:8000 ol7b; echo rc=$?
bind: Address already in use
channel_setup_fwd_listener_tcpip: cannot listen to port: 18000
Could not request local forwarding.
-- 같은 18000 은 이미 [6] 의 ssh 가 쓰고 있다.
-- 세 줄 모두 클라이언트 쪽 메시지. 서버에는 아무 기록이 없다.
rc=124
-- 경고 세 줄을 찍고도 ssh 는 계속 살아 있었다. 8초 뒤 timeout 이 죽여서 rc=124.
-- 포워딩 없는 빈 세션이다. 스크립트였다면 터널이 열린 줄 알고 넘어갔을 것이다.
-- ExitOnForwardFailure=yes : 포워딩을 못 열면 바로 끝낸다(스크립트에서는 이 옵션을 쓴다).
[root@ol7a ~]# ssh -o ExitOnForwardFailure=yes -N -L 18000:localhost:8000 ol7b; echo rc=$?
bind: Address already in use
channel_setup_fwd_listener_tcpip: cannot listen to port: 18000
Could not request local forwarding.
rc=255
-- ExitOnForwardFailure=yes: 같은 실패에서 바로 끝나고 rc=255.

-- 증상   : "bind: Address already in use", "Could not request local forwarding.", 세션은 유지(rc=124)
-- 원인   : 로컬 18000 을 이미 다른 프로세스(ssh pid 2530)가 LISTEN
-- 조치   : ss -ltnp 로 주인을 확인하고 다른 포트(18010)를 쓴다. 스크립트에는 ExitOnForwardFailure=yes
-- 재확인 : 18010 으로 연 포워딩에서 curl 성공, rc=0 (아래)
[root@ol7a ~]# ss -ltnp | grep -E ':(18000|18010) '
LISTEN 0      128        127.0.0.1:18000      0.0.0.0:*    users:(("ssh",pid=2530,fd=5))     
LISTEN 0      128            [::1]:18000         [::]:*    users:(("ssh",pid=2530,fd=4))     
-- 18000 의 주인은 여전히 2530. 18010 은 아직 없다.
-- 실패한 두 ssh 는 포트를 남기지 않았다.
[root@ol7a ~]# timeout 8 ssh -o ExitOnForwardFailure=yes -N -L 18010:localhost:8000 ol7b & sleep 3; curl -s http://localhost:18010/hello.txt; wait; echo rc=$?
served by ol7b 127.0.0.1:8000
rc=0
-- 18010 으로 열자 응답이 왔다. timeout 8 로 끝났지만 wait 의 rc 는 curl 쪽 0 이다.

--------------------------------------------------------------------------------
 [8] 원격 포워딩 -R — 반대 방향
--------------------------------------------------------------------------------

-- ol7a 에 127.0.0.1:8001 웹 서버를 띄우고, ol7b 의 18001 이 그곳으로 이어지게 한다.
[root@ol7a ~]# mkdir -p /tmp/www; echo 'served by ol7a 127.0.0.1:8001' > /tmp/www/hello.txt
[root@ol7a ~]# nohup python -c 'import os, BaseHTTPServer as B, SimpleHTTPServer as S; os.chdir("/tmp/www"); B.HTTPServer(("127.0.0.1", 8001), S.SimpleHTTPRequestHandler).serve_forever()' >/tmp/http.log 2>&1 </dev/null &
[root@ol7a ~]# nohup ssh -N -o ExitOnForwardFailure=yes -R 18001:localhost:8001 ol7b >/tmp/fwd2.log 2>&1 </dev/null &
-- -R 원격포트:목적지:포트. 목적지 localhost 는 이번에는 ol7a 자신(클라이언트 쪽에서 해석).
[root@ol7b ~]# ss -ltnp | grep 18001
LISTEN 0      128        127.0.0.1:18001      0.0.0.0:*    users:(("sshd",pid=10493,fd=9))  
LISTEN 0      128            [::1]:18001         [::]:*    users:(("sshd",pid=10493,fd=8))  
-- 포트를 연 것은 ol7b 의 sshd(pid 10493, 이 접속의 세션 프로세스). 127.0.0.1·[::1] 에만.
-- -L 은 클라이언트 ssh 가, -R 은 서버 sshd 가 포트를 연다.
[root@ol7b ~]# curl -s http://localhost:18001/hello.txt
served by ol7a 127.0.0.1:8001
-- ol7b 에서 자기 18001 로 접속했는데 ol7a 의 웹 서버가 답했다. 방향이 -L 과 반대다.
-- GatewayPorts 기본값 no : 원격 포트는 ol7b 의 루프백에만 열린다.
[root@ol7b ~]# sshd -T | grep -E '^(gatewayports|allowtcpforwarding) '
gatewayports no
allowtcpforwarding yes
-- GatewayPorts no: 원격 포트를 루프백에만 열게 하는 서버 설정. 그래서 위 ss 가 127.0.0.1 이었다.
-- clientspecified 로 바꾸면 -R 0.0.0.0:18001:... 처럼 클라이언트가 주소를 고를 수 있다.

--------------------------------------------------------------------------------
 [9] 오류 ② — 서버가 포워딩을 막은 경우 (AllowTcpForwarding no)
--------------------------------------------------------------------------------

[root@ol7b ~]# cp -p /etc/ssh/sshd_config /root/sshd_config.orig; echo 'AllowTcpForwarding no' >> /etc/ssh/sshd_config; sshd -t && systemctl reload sshd; sshd -T | grep allowtcpforwarding
allowtcpforwarding no
-- 원본을 남기고 끝에 덧붙였다. 기본 파일에 살아 있는 줄이 없어 덧붙인 값이 적용됐다.
-- reload 는 새 접속부터 적용된다.
-- 이미 열려 있던 포워딩은? 설정은 새 접속부터 적용된다.
[root@ol7a ~]# curl -s http://localhost:18000/hello.txt
served by ol7b 127.0.0.1:8000
-- [6] 에서 연 포워딩은 아직 된다. 이 세션은 옛 설정으로 돌고 있다.
-- 포워딩 ssh 를 끊고 다시 연다.
[root@ol7a ~]# pkill -f 'ssh -N'; sleep 1; nohup ssh -N -L 18000:localhost:8000 ol7b >/tmp/fwd3.log 2>&1 </dev/null &
[root@ol7a ~]# ss -ltn | grep 18000; curl -sS -m 5 http://localhost:18000/hello.txt; echo rc=$?
LISTEN 0      128        127.0.0.1:18000      0.0.0.0:*          
LISTEN 0      128            [::1]:18000         [::]:*          
curl: (52) Empty reply from server
rc=52
-- 다시 연 포워딩: 포트는 열린다(LISTEN 두 줄). 연결하는 순간 서버가 채널을 거부했다.
-- curl 은 TCP 는 붙었는데 아무 응답이 없어 (52) Empty reply from server.
-- 로컬 포트가 열렸다고 터널이 되는 것은 아니다.
[root@ol7a ~]# cat /tmp/fwd3.log
channel 2: open failed: administratively prohibited: open failed
-- 이유는 클라이언트 ssh 의 로그(stderr)에 있다. 백그라운드로 띄웠다면 그 파일을 봐야 한다.
[root@ol7a ~]# ssh -o ExitOnForwardFailure=yes -N -R 18001:localhost:8001 ol7b; echo rc=$?
Error: remote port forwarding failed for listen port 18001
rc=255
-- -R 은 포트를 여는 단계에서 바로 거부. ExitOnForwardFailure 로 rc=255.
[root@ol7b ~]# grep -iE 'refused (local|remote) port forward|forwarding' /var/log/secure | tail -2 | cut -c17-
ol7b sshd[10579]: refused local port forward: originator ::1 port 32938, target localhost port 8000
-- 서버 쪽 기록: -L 요청 거부. originator ::1 은 ol7a 의 curl 이 [::1]:18000 으로 붙었다는 것.
-- -R 거부는 INFO 에서 secure 에 남지 않았다(tail -2 에 한 줄뿐).

-- 증상   : curl "(52) Empty reply from server", ssh 로그 "administratively prohibited"
-- 원인   : 서버 ol7b 의 AllowTcpForwarding no. 설정 뒤 새로 연 포워딩만 영향을 받음
-- 조치   : 원본 sshd_config 복구, sshd -t && reload, 포워딩을 끊고 다시 연다
-- 재확인 : curl 이 served by ol7b 127.0.0.1:8000 (아래)
-- 조치: 설정을 되돌리고 reload, 포워딩을 다시 연다.
[root@ol7b ~]# cp -p /root/sshd_config.orig /etc/ssh/sshd_config; sshd -t && systemctl reload sshd; sshd -T | grep allowtcpforwarding
allowtcpforwarding yes
-- reload 뒤 다시 yes.
-- 앞에서 열린 포워딩은 끊고 새로 연다.
[root@ol7a ~]# pkill -f 'ssh -N'; sleep 1; nohup ssh -N -L 18000:localhost:8000 ol7b >/tmp/fwd4.log 2>&1 </dev/null &
[root@ol7a ~]# curl -s http://localhost:18000/hello.txt
served by ol7b 127.0.0.1:8000
-- 새로 연 포워딩이 다시 동작한다.

 [변형] 동적 포워딩 -D — SOCKS 프록시
--------------------------------------------------------------------------------

-- -D 포트 : ol7a 에 SOCKS 서버를 연다. 목적지는 요청마다 정해지고 ol7b 에서 접속한다.
[root@ol7b ~]# nohup python -c 'import os, BaseHTTPServer as B, SimpleHTTPServer as S; os.chdir("/tmp/www"); B.HTTPServer(("127.0.0.1", 8000), S.SimpleHTTPRequestHandler).serve_forever()' >/tmp/http.log 2>&1 </dev/null &
[root@ol7a ~]# nohup ssh -N -D 1080 ol7b >/tmp/fwd5.log 2>&1 </dev/null &
-- -D 1080: ol7a 의 1080 에 SOCKS 프록시. 1080 은 SOCKS 의 관례 포트다.
-- --socks5-hostname : 이름 해석도 ol7b 쪽에서. 그래서 localhost 는 ol7b 자신이다.
[root@ol7a ~]# curl -s --socks5-hostname localhost:1080 http://localhost:8000/hello.txt
served by ol7b 127.0.0.1:8000
-- 목적지(localhost:8000)를 미리 정하지 않았는데 같은 결과. 요청마다 ol7b 가 접속했다.
[root@ol7a ~]# curl -s --socks5-hostname localhost:1080 -o /dev/null -w '%{http_code}\n' http://yum.oracle.com/
301
-- 인터넷 주소도 된다. 301 은 yum.oracle.com 의 https 이동 응답. ol7b 에서 나간 요청이다.
-- 브라우저에 SOCKS 프록시로 지정하면 ol7b 에서만 보이는 내부 웹 화면을 볼 수 있다.
[root@ol7a ~]# pkill -f 'ssh -N'; sleep 1; ss -ltn | grep -c ':1080 '
0
[root@ol7b ~]# pkill -f SimpleHTTPServer; sleep 1; ss -ltn | grep -c ':8000 '
0
-- 1080·8000 모두 닫혔다.
-- grep -c 는 줄 수만 센다. 0 이면 없음.
