================================================================================
 제3장 실습 01 — 부팅 순서 추적
 대상   : ol7a
 목표   : systemd-analyze 의 time·blame·critical-chain 으로 부팅 시간을 단계별로
          나눠 읽고, journalctl -b 에서 커널 → initramfs → systemd 로 넘어가는
          지점을 찾는다. /proc/cmdline 으로 실제 쓰인 부트 파라미터를 확인한다
 배경   : 전원을 켜면 펌웨어(BIOS) → GRUB 2 → 커널 → initramfs → systemd 순서로
          제어가 넘어간다. systemd 는 PID 1 로 떠서 기본 타깃에 필요한 유닛을
          병렬로 올린다. 병렬 기동 때문에 "가장 오래 걸린 서비스"와 "부팅을
          늦춘 서비스"가 다를 수 있다 (본문 3.1)
 소요   : 약 20분
 선행   : ol7-base 스냅샷에서 막 부팅한 상태
 계정   : root
 주의   : 조회 위주. [변형] 에서 재부팅을 한 번 한다
 되돌림 : /tmp 에 만든 SVG 두 개만 지운다. 확인은 ls /tmp/boot*.svg (없어야 함)
================================================================================

-- 이 실습의 출력에는 두 가지 손질이 있다. 명령줄에 그대로 보이므로 숨긴 것이 아니다.
--   · systemd-analyze critical-chain 은 시간이 걸린 유닛을 빨간색 제어 문자로 칠한다.
--     문서에 옮길 수 없어 sed 's/\x1b\[[0-9;]*m//g' 로 제어 문자만 지웠다.
--   · journal 한 줄이 200자를 넘는 것이 많아 cut -c 로 앞부분만 남긴 곳이 있다.

 [1] systemd-analyze — 부팅 시간을 세 덩어리로
--------------------------------------------------------------------------------

-- 인자 없이 치면 systemd-analyze time 과 같다.
-- 커널이 시작된 뒤 initrd 를 거쳐 userspace(실제 루트의 systemd)가 기본 타깃에 닿기까지를 나눠 보여 준다.
[root@ol7a ~]# systemd-analyze
Startup finished in 1.057s (kernel) + 1.613s (initrd) + 4.391s (userspace) = 7.062s
-- kernel 1.057초 : 커널 시작부터 initramfs 의 systemd 가 뜰 때까지
-- initrd 1.613초 : initramfs 에서 루트를 찾아 switch-root 할 때까지
-- userspace 4.391초 : 실제 루트의 systemd 가 multi-user.target 에 닿을 때까지
-- 합계 7.062초. BIOS 시스템이라 firmware·loader 항목이 없다.
-- 펌웨어 POST 시간은 여기 들어가지 않는다.

 [3] critical-chain — 기본 타깃까지의 사슬
--------------------------------------------------------------------------------

-- critical-chain 은 기본 타깃(multi-user.target)에서 출발해, 그 타깃이 기다린 유닛 중
-- 가장 늦게 active 가 된 것을 따라 아래로 내려간다. 앞 두 줄은 @·+ 기호의 뜻을 알려 주는 안내문이다.
[root@ol7a ~]# systemd-analyze critical-chain | sed 's/\x1b\[[0-9;]*m//g'
The time after the unit is active or started is printed after the "@" character.
The time the unit takes to start is printed after the "+" character.

multi-user.target @4.387s
└─tuned.service @2.610s +488ms
  └─network.target @2.609s
    └─network.service @2.409s +199ms
      └─NetworkManager-wait-online.service @1.953s +455ms
        └─NetworkManager.service @1.911s +40ms
          └─network-pre.target @1.911s
            └─firewalld.service @1.643s +267ms
              └─polkit.service @1.358s +282ms
                └─basic.target @1.296s
                  └─paths.target @1.296s
                    └─brandbot.path @1.296s
                      └─sysinit.target @1.293s
                        └─systemd-update-utmp.service @1.285s +7ms
                          └─auditd.service @1.254s +29ms
                            └─systemd-tmpfiles-setup.service @1.244s +9ms
                              └─rhel-import-state.service @1.221s +22ms
                                └─local-fs.target @1.218s
                                  └─boot.mount @1.185s +23ms
                                    └─local-fs-pre.target @1.184s
                                      └─lvm2-monitor.service @595ms +588ms
                                        └─lvm2-lvmetad.service @632ms
                                          └─lvm2-lvmetad.socket @584ms
                                            └─-.slice
-- 아래에서 위로 읽는다.
-- 맨 아래 -.slice 가 출발점, 맨 위 multi-user.target 이 도착점이다.
-- 사슬: lvm2 → boot.mount → local-fs → sysinit → basic → polkit → firewalld → NetworkManager
--       → NetworkManager-wait-online → network → network.target → tuned → multi-user.
-- + 가 큰 유닛: lvm2-monitor 588ms, tuned 488ms, NetworkManager-wait-online 455ms.
-- 사슬 맨 위의 multi-user.target @4.387s 는 [1] 의 userspace 4.391초와 거의 같다.
-- 그런데 tuned 는 2.610+0.488 = 약 3.1초에 끝났다.
-- multi-user 가 그 뒤 1.3초를 더 기다린 이유가 사슬에 없다.

 [4] 오류 흐름 — blame 1위를 사슬로 판단하기
--------------------------------------------------------------------------------

-- blame 맨 위 서비스를 보고 "이것이 부팅을 늦췄다"고 단정하는 실수가 흔하다.
-- 반대로 critical-chain 에 안 보인다고 "무관하다"고 단정하는 것도 같은 실수다. 둘 다 확인한다.
-- 1위 유닛 이름을 awk 로 뽑아 critical-chain 에 넣는다. 인자로 유닛을 주면 그 유닛까지의 사슬만 나온다.
[root@ol7a ~]# systemd-analyze blame | head -1
          1.770s kdump.service
-- blame 1위는 kdump.service 다. [3] 의 사슬에는 kdump 가 보이지 않는다.
[root@ol7a ~]# systemd-analyze critical-chain $(systemd-analyze blame | awk 'NR==1{print $2}') | sed 's/\x1b\[[0-9;]*m//g' | head -8
The time after the unit is active or started is printed after the "@" character.
The time the unit takes to start is printed after the "+" character.

kdump.service +1.770s
└─network-online.target @2.611s
  └─network.target @2.609s
    └─network.service @2.409s +199ms
      └─NetworkManager-wait-online.service @1.953s +455ms
-- kdump 는 network-online.target @2.611s 뒤에 시작해 1.770초가 걸렸다.
-- 2.611 + 1.770 = 4.381초.
-- multi-user.target 도달 4.387초와 6ms 차이다.
-- 시간만 보면 kdump 가 끝나자마자 multi-user 에 닿았다.

-- 그 유닛의 순서 관계를 본다.
-- After    : 이 유닛이 기다리는 유닛
-- Before   : 이 유닛을 기다리는 유닛
-- WantedBy : 이 유닛을 끌어오는 타깃
[root@ol7a ~]# systemctl show -p Type -p After -p Before -p WantedBy kdump.service
Type=oneshot
WantedBy=multi-user.target
Before=abrt-vmcore.service
After=systemd-journald.socket network.target basic.target remote-fs.target system.slice network-online.target
-- Type=oneshot : 명령이 끝나야 active 가 된다.
-- kdump 의 1.770초 동안 이 유닛은 activating 이었다
-- Before=abrt-vmcore.service : kdump 뒤에 서는 유닛이 하나 있다
-- After 에 network-online.target 이 있어 네트워크가 다 올라온 뒤에 시작한다

-- multi-user.target 이 kdump 를 기다리는지 본다. 타깃은 Wants 로 끌어온 유닛에 자동으로 After 를 단다.
[root@ol7a ~]# systemctl show -p After multi-user.target | tr ' ' '\n' | grep -nE 'kdump|tuned'
33:tuned.service
-- multi-user.target 의 After 목록(33번째 줄)에 tuned 는 있지만 kdump 는 없다.
-- critical-chain 이 kdump 를 따라가지 않은 이유다.

-- 시각을 직접 비교한다. 단위는 부팅 후 마이크로초(monotonic)다.
-- InactiveExitTimestampMonotonic : 시작 명령이 나간 시점
-- ActiveEnterTimestampMonotonic  : active 가 된 시점
[root@ol7a ~]# for u in kdump tuned multi-user.target; do systemctl show -p Id -p InactiveExitTimestampMonotonic -p ActiveEnterTimestampMonotonic $u; echo; done
Id=kdump.service
InactiveExitTimestampMonotonic=5287324
ActiveEnterTimestampMonotonic=7058240

Id=tuned.service
InactiveExitTimestampMonotonic=5281396
ActiveEnterTimestampMonotonic=5770085

Id=multi-user.target
InactiveExitTimestampMonotonic=7058544
ActiveEnterTimestampMonotonic=7058544
--   kdump      : 5.287초 시작 → 7.058240초 active
--   tuned      : 5.281초 시작 → 5.770초 active
--   multi-user : 7.058544초에 시작과 동시에 active
-- multi-user 는 kdump 가 active 가 된 뒤 0.3ms 만에 도달했다.
-- tuned 는 1.3초 전에 끝났다.
-- 증상   : blame 1위 kdump.service(1.770s)가 critical-chain 에 없어 "부팅과 무관"으로 보임
-- 원인   : critical-chain 은 After= 관계만 따라간다. multi-user 의 After 목록에 kdump 가 직접 없다.
--          그러나 시각을 비교하면 multi-user 는 kdump 완료 직후에 닿았다. Before=abrt-vmcore.service 처럼
--          다른 유닛을 거친 순서 관계가 있을 수 있다
-- 조치   : 판단은 사슬 하나가 아니라 blame·critical-chain·유닛의 Active 시각을 함께 보고 한다
-- 재확인 : ActiveEnterTimestampMonotonic 의 kdump 7058240 과 multi-user 7058544 비교([더 해 보기] 1 에서 kdump 를 빼고 측정)

 [7] initramfs 에서 실제 루트로 — Switching root

[    0.158744] ol7a.example.com kernel: Kernel command line: BOOT_IMAGE=/vmlinuz-5.4.17-2136.338.4.2.el7uek.x8

--------------------------------------------------------------------------------
 [8] /proc/cmdline — 이번 부팅에 실제로 쓰인 파라미터
--------------------------------------------------------------------------------

-- GRUB 이 커널에 넘긴 문자열 그대로다. 설정 파일이 아니라 이 파일이 "실제로 무엇으로 부팅했나"의 답이다.
-- tr 로 공백을 줄바꿈으로 바꾸고 cat -n 으로 번호를 붙여 하나씩 짚는다.
[root@ol7a ~]# tr ' ' '\n' < /proc/cmdline | cat -n
     1  BOOT_IMAGE=/vmlinuz-5.4.17-2136.338.4.2.el7uek.x86_64
     2  root=/dev/mapper/ol-root
     3  ro
     4  crashkernel=auto
     5  rd.lvm.lv=ol/root
     6  rd.lvm.lv=ol/swap
     7  rhgb
     8  quiet
     9  console=tty0
    10  console=ttyS0,115200
    11  scsi_mod.scan=sync
-- 1  BOOT_IMAGE : GRUB 이 붙이는 커널 파일 경로. 커널은 쓰지 않는다
-- 2·3 root=… ro : 루트 장치, 처음엔 읽기 전용. systemd 가 fstab 대로 rw 로 다시 붙인다
-- 4  crashkernel=auto : kdump 용 메모리 예약. blame 1위 kdump 가 이 영역을 쓴다
-- 5·6 rd.lvm.lv : initramfs 가 활성화할 LV 두 개(root, swap)
-- 7·8 rhgb quiet : 그래픽 부팅 화면, 메시지 줄이기
-- 9·10 console= : tty0(VM 화면)과 ttyS0(직렬 포트). 랩 콘솔 캡처용 설정, 마지막 것이 /dev/console
-- 11 scsi_mod.scan=sync : 랩 설정. SCSI 디스크를 순서대로 스캔해 sda 가 늘 OS 디스크가 되게 한다
