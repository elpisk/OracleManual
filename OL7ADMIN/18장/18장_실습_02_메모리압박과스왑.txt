================================================================================
 제18장 실습 02 — 메모리 압박과 스왑, OOM 킬러
 대상   : ol7a (메모리 3.6GB, 스왑 3.9GB)
 목표   : 페이지 캐시와 익명 메모리를 따로 채워 free 의 free·available 열이
          어떻게 다르게 움직이는지 보고, 메모리를 넘치게 써서 vmstat 의 si·so
          와 스왑 사용량을 확인한다. 스왑을 끈 상태에서 OOM 킬러를 일으켜
          dmesg 기록으로 누가 왜 죽었는지 읽는다
 배경   : 리눅스는 남는 메모리를 페이지 캐시로 쓴다. 그래서 free 열은 늘 작고,
          "지금 새로 쓸 수 있는 양"은 캐시 중 회수할 수 있는 몫을 더한 available
          열이 알려 준다. 익명 메모리(프로세스가 malloc 한 것)가 실제 메모리를
          넘으면 스왑으로 밀려나고, 스왑까지 모자라면 커널이 점수가 가장 높은
          프로세스 하나를 죽인다(본문 18.3)
 소요   : 약 30분
 선행   : ol7-base 스냅샷. 끝나고 스냅샷으로 되돌리는 것을 권한다(⚠)
 계정   : root
 주의   : OOM 킬러가 실제로 프로세스를 죽인다. 시험용 프로세스만 죽도록
          범위를 잡았다. /var/tmp 에 2GB 파일을 잠깐 만든다
 되돌림 : 시험 프로세스 0개, swapon 으로 스왑 다시 켬, 시험 파일 삭제.
          확인은 free -m · swapon -s · ls /var/tmp

 [1] free 의 여섯 열
--------------------------------------------------------------------------------
-- -m : MiB 단위. -h 는 사람이 읽는 단위를 골라 준다.
[root@ol7a ~]# free -h
              total        used        free      shared  buff/cache   available
Mem:           3.5G        169M        3.2G        8.6M        164M        3.2G
Swap:          3.9G          0B        3.9G
-- 여섯 열
--   total       : 커널이 관리하는 메모리. 4GB VM 에서 3.5G(3629MB)
--   used        : total - free - buff/cache. 프로세스와 커널이 쓰는 몫
--   free        : 아무 데도 안 쓰인 메모리
--   shared      : tmpfs·공유 메모리(meminfo 의 Shmem 8880 kB)
--   buff/cache  : 페이지 캐시 + 버퍼 + 회수할 수 있는 slab
--   available   : 스왑 없이 새로 쓸 수 있다는 커널 추정치
-- Swap 줄은 total·used·free 셋만 있다

 [3] 페이지 캐시 채우기 — free 열만 보면 틀린다
--------------------------------------------------------------------------------
-- 캐시를 비우고 시작한다. drop_caches 에 3 을 쓰면 페이지 캐시와
-- dentry·inode 캐시를 버린다.
-- sync 로 더러운 페이지를 먼저 내려야 버릴 수 있는 몫이 커진다.
[root@ol7a ~]# sync; echo 3 > /proc/sys/vm/drop_caches; free -m
              total        used        free      shared  buff/cache   available
Mem:           3629         164        3394           8          69        3308
-- 캐시를 버리자 buff/cache 164 → 69, free 3294 → 3394. 출발점이다
Swap:          3967           0        3967
-- 2GB 파일을 쓰고 다시 읽는다. 읽은 내용은 페이지 캐시에 남는다.
[root@ol7a ~]# dd if=/dev/zero of=/var/tmp/cache.dat bs=1M count=2000 status=none; cat /var/tmp/cache.dat >/dev/null; free -m
              total        used        free      shared  buff/cache   available
Mem:           3629         162        1388           8        2078        3246
-- 2GB 파일 하나를 쓰고 읽었더니 buff/cache 69 → 2078, free 3394 →
-- 1388
-- used 는 162 그대로, available 은 3308 → 3246 으로 거의 그대로다
Swap:          3967           0        3967
-- 흔한 감시 스크립트를 흉내 낸다. free 열이 1024MB 아래면 경보를
-- 낸다.
[root@ol7a ~]# f=$(free -m | awk '/^Mem:/{print $4}'); a=$(free -m | awk '/^Mem:/{print $7}'); [ $f -lt 1024 ] && echo "ALERT: low memory free=${f}MB" ; echo "available=${a}MB"
available=3246MB
-- 경보 기준 1024 에는 닿지 않아 ALERT 줄은 안 나왔다. 파일이 2GB 라
-- free 가 1388 에서 멈췄다
-- 증상   : free 열이 3394 → 1388 MB 로 59% 줄었다. free 열만 보는
--          감시라면 "메모리가 반 넘게 사라졌다" 로 읽는다
-- 원인   : 늘어난 것은 buff/cache(2078) 다. 읽은 파일 내용을 캐시에
--          둔 것이고,
--          필요하면 커널이 바로 회수한다
-- 조치   : 판단은 available(3246) 과 스왑 입출력으로 한다. free 열
--          경보는 쓰지 않는다
-- 재확인 : 아래에서 캐시를 버리자 free 가 3085 로 돌아왔다
-- 캐시를 다시 버리면 free 가 돌아오는지 본다. 돌아오면 그 메모리는
-- 원래 쓸 수 있던 것이다.
[root@ol7a ~]# echo 3 > /proc/sys/vm/drop_caches; free -m; rm -f /var/tmp/cache.dat
              total        used        free      shared  buff/cache   available
Mem:           3629         161        3085           8         381        3248
-- free 1388 → 3085. buff/cache 381 이 남은 것은 rm 전이라 파일
-- 일부가 다시 읽혔기 때문이다
-- available 은 이 과정 내내 3246~3248 로 움직이지 않았다
Swap:          3967           0        3967

 [4] 익명 메모리 — 프로세스가 직접 잡은 메모리
--------------------------------------------------------------------------------
-- 메모리를 정해진 만큼 잡고 버티는 작은 프로그램을 쓴다.
--   인자 1 : 잡을 MB(50MB 씩 0.1초 간격으로 늘린다)  2 : 버틸 초  3 : 1 이면 잡은 페이지를 계속 건드린다
-- bytearray 는 0 으로 채워 만들어지므로 페이지가 실제로 할당된다.
[root@ol7a ~]# mkdir -p /root/load; cat > /root/load/memhog.py <<'EOF'
import sys, time
mb, secs = int(sys.argv[1]), int(sys.argv[2])
touch = len(sys.argv) > 3 and sys.argv[3] == "1"
blk = []
for i in range(mb // 50):
    blk.append(bytearray(50 << 20))
    time.sleep(0.1)
end = time.time() + secs
while time.time() < end:
    if touch:
        for b in blk:
            for off in range(0, len(b), 4096):
                b[off] = 1
    else:
        time.sleep(1)
EOF
-- 같은 파이썬을 이름만 다르게 부르려고 심볼릭 링크를 둔다. 프로세스
-- 이름(comm)이 링크 이름이 된다.
[root@ol7a ~]# ln -s /usr/bin/python2.7 /root/load/dbsim; ln -s /usr/bin/python2.7 /root/load/runaway; ln -s /usr/bin/python2.7 /root/load/batch; ls -l /root/load

--------------------------------------------------------------------------------
 [7] OOM 킬러 준비 — 스왑을 끈다
--------------------------------------------------------------------------------
-- 스왑이 있으면 OOM 전에 한참 스왑으로 버텨 VM 이 느려진다.
-- 실습에서는 스왑을 끄고 바로 부족하게 만든다.
-- swapoff 는 스왑에 있던 페이지를 메모리로 다시 읽어 들인 뒤에야
-- 끝난다.
[root@ol7a ~]# pkill -x dbsim; sleep 2; swapoff -a; swapon -s; free -m
              total        used        free      shared  buff/cache   available
Mem:           3629         159        3408           8          61        3317
Swap:             0           0           0
-- dbsim 을 먼저 끝내 스왑에 남은 페이지가 없으므로 swapoff 가 바로
-- 끝났다
-- swapon -s 는 아무것도 찍지 않았고 free 의 Swap total 이 0 이 됐다
-- dbsim 이 2GB 를 잡은 상태에서 runaway 가 조금씩 늘어나 2.4GB 를
-- 원한다. 둘을 합치면 메모리보다 크다.
[root@ol7a ~]# nohup /root/load/dbsim /root/load/memhog.py 2000 600 >/dev/null 2>&1 </dev/null &
[root@ol7a ~]# P=$(pgrep -x dbsim); echo "dbsim pid=$P rss=$(ps -o rss= -p $P) oom_score=$(cat /proc/$P/oom_score) adj=$(cat /proc/$P/oom_score_adj)"
dbsim pid=2449 rss=2054500 oom_score=1035 adj=0
-- oom_score 1035 : 메모리 거의 전부를 혼자 가졌다는 점수. 0~1000
-- 범위에 더해지는 보정 때문에 1000 을 조금 넘는다
-- rss 2054500 KB : 2000MB 를 다 잡았다. 남은 available 은 1.3GB
-- 남짓
-- runaway 가 2.4GB 를 원하므로 중간에 반드시 모자란다

--          낮춘다([변형])

 [9] 메모리 사용량 순위로 확인
--------------------------------------------------------------------------------
-- 범인을 찾을 때는 RSS 순위를 본다. 죽은 쪽(dbsim)이 아니라 늘어난
-- 쪽(runaway)이 원인이다.
[root@ol7a ~]# ps -eo pid,rss,vsz,pmem,comm --sort=-rss | head -6
  PID   RSS    VSZ %MEM COMMAND
 2508 2461748 2584808 66.2 runaway
 1055 22396 360216  0.6 firewalld
 1412 11296 575772  0.3 tuned
    1  6044 151816  0.1 systemd
  990  5984 615108  0.1 polkitd
-- RSS 1위 runaway 2461748 KB(%MEM 66.2). 그다음 firewalld 22MB
-- 부터는 작다
-- OOM 뒤에 남은 큰 프로세스가 원인 후보 1순위다
-- 열: PID, RSS(KB), VSZ(KB), %MEM, COMMAND. --sort=-rss 는 RSS
-- 내림차순
-- 장애 뒤라도 원인 프로세스가 아직 살아 있으면 이 순위로 바로
-- 잡힌다
[root@ol7a ~]# pkill -x runaway; sleep 2; free -m
              total        used        free      shared  buff/cache   available
Mem:           3629         158        3411           8          59        3319
Swap:             0           0           0
-- runaway 를 끝내자 available 3319 로 돌아왔다

--------------------------------------------------------------------------------
 [변형] oom_score_adj 로 지킬 프로세스를 빼면
--------------------------------------------------------------------------------
-- 같은 상황을 다시 만들되 dbsim 의 oom_score_adj 를 -1000 으로
-- 둔다.
-- (Oracle DB 는 systemd 유닛의 OOMScoreAdjust= 나
-- /proc/PID/oom_score_adj 로 같은 일을 한다)
[root@ol7a ~]# nohup /root/load/dbsim /root/load/memhog.py 2000 600 >/dev/null 2>&1 </dev/null &
[root@ol7a ~]# P=$(pgrep -x dbsim); echo -1000 > /proc/$P/oom_score_adj; echo "dbsim pid=$P oom_score=$(cat /proc/$P/oom_score) adj=$(cat /proc/$P/oom_score_adj)"
dbsim pid=2645 oom_score=0 adj=-1000
-- adj -1000 을 쓰자 oom_score 가 0 이 됐다. 고를 대상에서 빠진다
[root@ol7a ~]# dmesg -c >/dev/null
[root@ol7a ~]# nohup timeout 120 /root/load/runaway /root/load/memhog.py 2400 60 >/dev/null 2>&1 </dev/null &
[root@ol7a ~]# ps -o pid,rss,etime,comm -C dbsim,runaway; dmesg | grep -E 'Out of memory|Killed process' | cut -c1-200
  PID   RSS     ELAPSED COMMAND
 2645 2050624     00:28 dbsim
[   92.633509] Out of memory: Killed process 2702 (runaway) total-vm:1509524kB, anon-rss:1382292kB, file-rss:8kB, shmem-rss:0kB, UID:0 pgtables:2792kB oom_score_adj:0
-- dbsim(2645) 은 살아 있고 RSS 2050624. 이번에는 runaway 가
-- anon-rss 1382292kB 에서 죽었다
-- 남은 메모리가 1.4GB 남짓이라 runaway 는 2.4GB 에 닿지 못했다
-- -1000 은 강력하다. 이 값을 단 프로세스가 폭주하면 다른 것이 다
-- 죽는다. 지킬 것만 고른다
