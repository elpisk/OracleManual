 제13장 실습 05 — 오류 재현: 게이트웨이와 이름 해석
 대상   : ol7a (장애 쪽), ol7b (정상 쪽, 비교 상대)
 목표   : 기본 게이트웨이 누락, 잘못된 DNS 서버, nsswitch.conf 의 hosts 순서가
          각각 무엇을 막고 무엇은 막지 않는지 구분한다. ping IP·ping 이름·
          ip route·getent hosts·dig 다섯 가지로 원인을 좁힌다
 배경   : 패킷이 나가려면 경로가 있어야 하고(같은 서브넷은 연결 경로, 그 밖은 기본
          경로), 이름으로 부르려면 해석이 먼저 돼야 한다. 해석 순서는 nsswitch.conf
          가 정하고 getent 는 그 순서를 따른다. dig 는 nsswitch 를 거치지 않고 DNS 서버에
          직접 묻는다. 증상이 같아 보여도 도구마다 결과가 갈린다 (본문 13.2·13.8)
 소요   : 약 40분
 선행   : ol7-base, ol7b-base 스냅샷
 계정   : root
 주의   : ens32 의 게이트웨이·DNS 를 바꾼다. SSH 는 같은 서브넷(172.16.225.0/24)에서
          들어오므로 게이트웨이를 지워도 끊기지 않는다. 끝에서 원래 값으로 되돌린다
 되돌림 : ens32 게이트웨이 172.16.225.2, DNS 172.16.225.2, nsswitch.conf·hosts 원본
          → ip route, cat /etc/resolv.conf, md5sum 으로 [0] 과 비교

 [0] 시작 전 상태 기록

-- 바꿀 대상 다섯 가지를 먼저 남긴다. 기본 경로, resolv.conf, nsswitch.conf, hosts, ifcfg 의 GATEWAY·DNS.
[root@ol7a ~]# ip route; cat /etc/resolv.conf; grep '^hosts' /etc/nsswitch.conf
default via 172.16.225.2 dev ens32 proto static metric 100 
172.16.225.0/24 dev ens32 proto kernel scope link src 172.16.225.61 metric 100 
# Generated by NetworkManager
search example.com
nameserver 172.16.225.2
hosts:      files dns myhostname
-- 기본 경로는 ens32 로 172.16.225.2 를 거친다. DNS 서버도 같은 172.16.225.2(VMware NAT 장치)다
-- 게이트웨이와 DNS 가 같은 주소라는 점이 [3] 의 결과를 가른다
[root@ol7a ~]# grep -E 'GATEWAY|DNS|IPADDR|PREFIX' /etc/sysconfig/network-scripts/ifcfg-ens32
IPADDR=172.16.225.61
PREFIX=24
GATEWAY=172.16.225.2
DNS1=172.16.225.2
-- 프로필 쪽 값이다. GATEWAY 와 DNS1 이 ifcfg 에 들어 있다
[root@ol7a ~]# md5sum /etc/nsswitch.conf /etc/hosts /etc/sysconfig/network-scripts/ifcfg-ens32
9f5dc50f774b41b956c492cb4d1e2fcb  /etc/nsswitch.conf
5e5f1b23bb020ca54fbc242afeef2734  /etc/hosts
f552067d2505b12131aa64d5d47de68c  /etc/sysconfig/network-scripts/ifcfg-ens32
-- 세 파일의 지문을 [되돌림] 에서 다시 비교한다. 원본은 /root 에 복사해 둔다
[root@ol7a ~]# cp -p /etc/sysconfig/network-scripts/ifcfg-ens32 /etc/nsswitch.conf /etc/hosts /root/

 [1] 정상일 때의 다섯 가지 확인

-- 이 실습에서 쓸 진단 도구 dig 는 bind-utils 패키지에 있다. 장애를 만들기 전에 설치한다.
-- 이름 해석이 깨진 뒤에는 yum 도 저장소 이름을 해석하지 못한다.
[root@ol7a ~]# rpm -q bind-utils || yum -y -q install bind-utils
bind-utils-9.11.4-26.0.1.P2.el7_9.16.x86_64
-- 이미 설치돼 있어 || 뒤의 yum 은 돌지 않았다. ol7-base 에 bind-utils 가 들어 있다

-- 확인 순서는 안쪽에서 바깥쪽이다.
--   ① 같은 서브넷의 상대(ol7b)  ② 게이트웨이  ③ 서브넷 밖의 IP  ④ 이름 해석  ⑤ 서브넷 밖의 이름
-- -c 2 는 두 번만 보내고 끝, -W 2 는 응답을 2초까지 기다린다는 뜻이다.
[root@ol7a ~]# ping -c 2 -W 2 172.16.225.62 | grep transmitted
2 packets transmitted, 2 received, 0% packet loss, time 1025ms
[root@ol7a ~]# ping -c 2 -W 2 172.16.225.2 | grep transmitted
2 packets transmitted, 2 received, 0% packet loss, time 1005ms
[root@ol7a ~]# ping -c 2 -W 2 8.8.8.8 | grep transmitted
2 packets transmitted, 2 received, 0% packet loss, time 1001ms
-- grep transmitted 로 요약 줄만 봤다. 세 곳 모두 보낸 2개를 다 받았다(0% packet loss)
-- 8.8.8.8 까지 된다는 것은 게이트웨이를 지나 인터넷까지 경로가 있다는 뜻이다
[root@ol7a ~]# getent hosts ol7b; getent hosts yum.oracle.com | head -1
172.16.225.62   ol7b.example.com ol7b
2600:140b:2c00:58c::2a7d e10877.dscd.akamaiedge.net yum.oracle.com public-yum.oracle.com.edgekey.net
-- ol7b 는 /etc/hosts 에서, yum.oracle.com 은 DNS 에서 풀렸다. head -1 로 첫 주소만 봤다
-- getent hosts 는 IPv6 주소를 먼저 묻는다. 그래서 2600:… 이 나왔다
[root@ol7a ~]# ping -c 2 -W 2 yum.oracle.com | sed -n '1p;$p'
PING e10877.dscd.akamaiedge.net (2.18.101.231) 56(84) bytes of data.
rtt min/avg/max/mdev = 140.025/140.837/141.649/0.812 ms
-- sed -n '1p;$p' 는 첫 줄과 마지막 줄만 찍는다. ping 은 IPv4 주소 2.18.101.231 로 갔다
-- 다섯 가지 모두 정상. 이 결과가 장애 때 비교할 기준선이다

 [2] 오류 ① — 기본 게이트웨이를 지운다

-- 운영 중에 프로필을 정리하다 GATEWAY 가 빠진 상황이다.
-- ipv4.gateway 에 빈 문자열을 주면 값을 지운다.
-- nmcli device reapply 는 주소를 내리지 않고 바뀐 프로필만 다시 입힌다. SSH 가 유지된다.
[root@ol7a ~]# nmcli connection modify ens32 ipv4.gateway ''
[root@ol7a ~]# nmcli device reapply ens32; sleep 2; ip route
Connection successfully reapplied to device 'ens32'.
172.16.225.0/24 dev ens32 proto kernel scope link src 172.16.225.61 metric 100 

-- 파일에 무엇이 바뀌었는지는 [0] 에서 떠 둔 사본과 diff 로 본다
[root@ol7a ~]# diff /root/ifcfg-ens32 /etc/sysconfig/network-scripts/ifcfg-ens32
18d17
< GATEWAY=172.16.225.2
-- ip route 에서 default 줄이 사라졌다. 연결 경로 한 줄만 남았다
-- diff 의 18d17 은 원본 18번째 줄이 지워졌다(delete)는 뜻이다. GATEWAY 키가 파일에서 빠졌다
-- 즉시 반영됐다. reapply 가 경로를 다시 계산했다

 [3] 게이트웨이가 없을 때 무엇이 되고 무엇이 안 되나
--------------------------------------------------------------------------------

-- [1] 과 같은 순서로 다시 확인한다. 안쪽부터 하나씩
[root@ol7a ~]# ping -c 2 -W 2 172.16.225.62 | grep transmitted
2 packets transmitted, 2 received, 0% packet loss, time 1006ms
[root@ol7a ~]# ping -c 2 -W 2 172.16.225.2 | grep transmitted
2 packets transmitted, 2 received, 0% packet loss, time 1006ms
[root@ol7a ~]# ping -c 2 -W 2 8.8.8.8
connect: Network is unreachable
-- 같은 서브넷 두 곳은 여전히 된다. 서브넷 밖 8.8.8.8 만 즉시 실패했다
-- connect: Network is unreachable 은 패킷을 보내기 전에 커널이 낸 오류다. 기다림이 없다

-- 이름 해석은 될까. DNS 서버 172.16.225.2 는 같은 서브넷이다.
[root@ol7a ~]# getent hosts yum.oracle.com | head -1
2600:140b:1e00:b84::2a7d e10877.dscd.akamaiedge.net yum.oracle.com public-yum.oracle.com.edgekey.net
-- 이름 해석은 된다. DNS 서버가 같은 서브넷이라 게이트웨이 없이 닿기 때문이다
[root@ol7a ~]# ping -c 2 -W 2 yum.oracle.com
connect: Network is unreachable
-- 이름은 풀렸지만 그 주소로 갈 길이 없다. 같은 오류 문구가 나온다

-- 커널에게 8.8.8.8 로 가는 길을 직접 묻는다
[root@ol7a ~]# ip route get 8.8.8.8
RTNETLINK answers: Network is unreachable
-- ip route get 이 커널의 판단을 그대로 보여 준다. 경로 표에 8.8.8.8 에 맞는 줄이 없다

-- 실무에서 처음 눈에 띄는 증상은 대개 yum 이다.
[root@ol7a ~]# yum -q makecache fast 2>&1 | tail -3
Trying other mirror.
https://yum.oracle.com/repo/OracleLinux/OL7/latest/x86_64/repodata/repomd.xml: [Errno 14] curl#7 - "Failed to connect to 2600:140b:2c00:58c::2a7d: Network is unreachable"
Trying other mirror.
-- tail -3 으로 끝 세 줄만 봤다. 미러를 돌아가며 시도하다 모두 실패한다
-- Failed to connect to 2600:…: Network is unreachable. 주소는 얻었고(이름 해석 성공) 연결 단계에서 실패했다
-- 이름 해석이 원인이었다면 Could not resolve host 가 나온다
-- 오류 흐름
-- 증상   : ping 8.8.8.8 → connect: Network is unreachable, yum → Failed to connect to ...: Network is unreachable
-- 원인   : 기본 경로(default via 172.16.225.2)가 없다. ip route 에 연결 경로 한 줄뿐, diff 로 GATEWAY 가 빠진 것 확인
-- 조치   : nmcli connection modify ens32 ipv4.gateway 172.16.225.2 → nmcli device reapply ens32
-- 재확인 : ip route 에 default via 172.16.225.2, ping 8.8.8.8 이 0% packet loss

-- 상대편에서 보면 ol7a 는 멀쩡하다. ol7b 에서 ol7a 로 ping 과 22번 포트를 확인한다.
-- /dev/tcp/주소/포트 는 bash 가 TCP 연결을 열어 보는 기능이다. 열리면 0 을 돌려준다.
[root@ol7b ~]# ping -c 2 -W 2 ol7a | tail -2; timeout 3 bash -c '</dev/tcp/172.16.225.61/22' && echo "22 open"
-- ol7b 에서는 ol7a 에 ping 도 되고 22번 포트도 열린다. 들어오는 쪽은 같은 서브넷이라 문제가 없다
-- 원격에서 "서버는 살아 있는데 밖으로 못 나간다"는 증상이 이것이다
2 packets transmitted, 2 received, 0% packet loss, time 1051ms
rtt min/avg/max/mdev = 0.252/0.391/0.531/0.140 ms
22 open
[root@ol7b ~]# ip route; ping -c 2 -W 2 8.8.8.8 | grep transmitted
default via 172.16.225.2 dev ens32 proto static metric 100 
172.16.225.0/24 dev ens32 proto kernel scope link src 172.16.225.62 metric 100 
2 packets transmitted, 2 received, 0% packet loss, time 1003ms
-- 정상 노드 ol7b 의 경로 표에는 default 줄이 있고 8.8.8.8 도 된다. 두 노드의 ip route 를 나란히 보면 차이가 바로 보인다

[root@ol7a ~]# ping -c 2 -W 2 8.8.8.8 | tail -2; diff /root/ifcfg-ens32 /etc/sysconfig/network-scripts/ifcfg-ens32 && echo SAME
2 packets transmitted, 2 received, 0% packet loss, time 1000ms

20a20

 [5] 잘못된 DNS 서버
--------------------------------------------------------------------------------

-- 이번에는 경로는 정상이고 DNS 서버 주소만 틀린 경우다. 172.16.225.99 는 아무도 쓰지 않는 주소다.
-- ipv4.dns 에 값을 주면 목록 전체를 그 값으로 바꾼다(+ 를 붙이면 추가).
[root@ol7a ~]# nmcli connection modify ens32 ipv4.dns 172.16.225.99
[root@ol7a ~]# nmcli device reapply ens32; sleep 2; cat /etc/resolv.conf
Connection successfully reapplied to device 'ens32'.
# Generated by NetworkManager
search example.com
nameserver 172.16.225.99
-- 프로필의 DNS 가 바뀌자 reapply 가 resolv.conf 를 곧바로 다시 썼다(실습 01 의 손 편집과 다르다)

-- 이름으로 부르면 시간이 걸린다. time 으로 얼마나 걸리는지 같이 잰다.
[root@ol7a ~]# time ping -c 1 -W 2 yum.oracle.com
ping: yum.oracle.com: Name or service not known

real    0m12.299s
user    0m0.000s
sys     0m0.003s
-- 실패까지 12.3초. 리졸버가 응답 없는 서버를 기다리고 다시 묻는 시간이다
-- 기본값은 시도마다 5초 시간 초과, 2회 시도다(resolv.conf(5) 의 timeout·attempts). IPv4·IPv6 질의가 겹쳐 12초 남짓이 됐다
-- 사용자에게는 "느리다가 실패한다"로 보인다. [3] 의 즉시 실패와 다르다

-- IP 로 부르면 바로 된다. 경로는 멀쩡하다는 뜻이다.
[root@ol7a ~]# ping -c 1 -W 2 8.8.8.8 | grep transmitted
1 packets transmitted, 1 received, 0% packet loss, time 0ms
-- IP 로 하는 통신은 DNS 와 상관없다

-- /etc/hosts 에 있는 이름은 된다.
[root@ol7a ~]# getent hosts ol7b; ping -c 1 -W 2 ol7b | grep transmitted
172.16.225.62   ol7b.example.com ol7b
1 packets transmitted, 1 received, 0% packet loss, time 0ms
-- ol7b 는 files 단계에서 풀려 DNS 까지 가지 않는다. 그래서 바로 된다

-- dig 로 DNS 서버에 직접 묻는다. @서버 를 주면 resolv.conf 대신 그 서버에 묻는다.
-- +short 는 답의 주소만 보인다. +time=2 +tries=1 은 2초씩 한 번만 기다리게 한다.
[root@ol7a ~]# dig +time=2 +tries=1 yum.oracle.com

; <<>> DiG 9.11.4-P2-RedHat-9.11.4-26.0.1.P2.el7_9.16 <<>> +time=2 +tries=1 yum.oracle.com
;; global options: +cmd
;; connection timed out; no servers could be reached
-- dig 는 resolv.conf 의 172.16.225.99 에 묻고 2초 뒤 포기했다
-- no servers could be reached 는 서버가 응답하지 않았다는 뜻이다. 이름이 없으면 status: NXDOMAIN 이 나온다
[root@ol7a ~]# dig +short @172.16.225.2 yum.oracle.com
public-yum.oracle.com.edgekey.net.
e10877.dscd.akamaiedge.net.
2.18.101.231
-- @172.16.225.2 로 서버를 직접 지정하자 바로 답이 왔다. 서버 주소 설정만 틀렸다는 증거다
-- +short 출력은 CNAME 두 단계(edgekey → akamaiedge)를 거쳐 A 레코드 2.18.101.231 에 닿았다
-- 오류 흐름
-- 증상   : ping yum.oracle.com 이 12.3초 뒤 Name or service not known, ping 8.8.8.8·ping ol7b 는 정상
-- 원인   : resolv.conf 의 nameserver 가 응답 없는 172.16.225.99. dig 는 timed out, dig @172.16.225.2 는 응답
-- 조치   : nmcli connection modify ens32 ipv4.dns 172.16.225.2 → nmcli device reapply ens32
-- 재확인 : resolv.conf 에 nameserver 172.16.225.2, getent hosts yum.oracle.com 이 1초 안에 주소를 돌려준다

--------------------------------------------------------------------------------
 [7] getent 와 dig 는 다른 길로 간다
--------------------------------------------------------------------------------

-- ol7b 는 /etc/hosts 에만 있는 이름이다. VMware NAT 의 DNS 는 모른다.
[root@ol7a ~]# getent hosts ol7b; echo "dig: [$(dig +short ol7b)]"
172.16.225.62   ol7b.example.com ol7b
dig: []
-- getent 는 files 에서 ol7b 를 찾았고 dig 는 DNS 서버에 물어 빈 답을 받았다
-- 두 결과가 다르면 그 이름은 /etc/hosts 에만 있다

-- 같은 이름을 hosts 와 DNS 양쪽에 다르게 두면 어느 쪽이 이기는지 본다.
-- 10.10.10.10 은 일부러 넣은 가짜 주소다.
[root@ol7a ~]# echo '10.10.10.10 yum.oracle.com' >> /etc/hosts; tail -1 /etc/hosts
10.10.10.10 yum.oracle.com
-- 같은 이름을 getent 와 dig 로 각각 묻는다. dig 출력은 tail -1 로 마지막 A 레코드만 본다
[root@ol7a ~]# getent hosts yum.oracle.com | head -1; dig +short yum.oracle.com | tail -1
2600:140b:2c00:581::2a7d e10877.dscd.akamaiedge.net yum.oracle.com public-yum.oracle.com.edgekey.net
2.18.101.231
-- ping 이 실제로 어느 주소로 보내는지 첫 줄만 본다
[root@ol7a ~]# ping -c 1 -W 2 yum.oracle.com | head -1
PING yum.oracle.com (10.10.10.10) 56(84) bytes of data.
-- 세 도구가 세 가지 답을 냈다
--   getent hosts  IPv6 를 먼저 묻는다. /etc/hosts 에는 IPv4 줄만 있어 DNS 의 AAAA(2600:…)로 넘어갔다
--   dig           nsswitch 를 거치지 않는다. DNS 의 A 레코드 2.18.101.231
--   ping          IPv4 주소를 찾는다. files 가 먼저라 /etc/hosts 의 가짜 10.10.10.10 으로 보냈다
-- /etc/hosts 에 남은 옛 주소 한 줄이 서비스 장애가 되는 경로다. 응용 프로그램은 ping 과 같은 길로 간다

--------------------------------------------------------------------------------
 [8] nsswitch.conf 의 hosts 순서를 바꾼다
--------------------------------------------------------------------------------

-- hosts: 줄의 순서가 "먼저 물어볼 곳"이다. dns 를 앞으로 옮긴다.
[root@ol7a ~]# sed -i 's/^hosts:.*/hosts:      dns files myhostname/' /etc/nsswitch.conf; grep '^hosts' /etc/nsswitch.conf
hosts:      dns files myhostname
[root@ol7a ~]# diff /root/nsswitch.conf /etc/nsswitch.conf
42c42
< hosts:      files dns myhostname
---
> hosts:      dns files myhostname
-- 42c42 는 42번째 줄 하나가 바뀌었다는 뜻이다

-- 데몬을 재시작하지 않았다. 새로 뜨는 프로세스는 nsswitch.conf 를 그때 읽는다.
-- 순서를 바꾼 뒤 같은 질문을 한다. 가짜 10.10.10.10 줄은 /etc/hosts 에 아직 있다
[root@ol7a ~]# getent hosts yum.oracle.com | head -1
2600:140b:2c00:1185::2a7d e10877.dscd.akamaiedge.net yum.oracle.com public-yum.oracle.com.edgekey.net
[root@ol7a ~]# getent hosts ol7b
172.16.225.62   ol7b.example.com ol7b
-- yum.oracle.com 은 DNS 가 먼저라 진짜 주소가 나왔다. ol7b 는 DNS 가 모르니 다음 순서인 files 에서 풀렸다
-- 순서를 바꿔도 둘 다 풀리기는 한다. 같은 이름이 양쪽에 있을 때 어느 값을 쓰는지가 달라진다

--------------------------------------------------------------------------------
 [9] 오류 ② — hosts 줄에서 files 가 빠졌을 때
--------------------------------------------------------------------------------

-- 누군가 DNS 만 쓰겠다며 files 를 지운 상황이다.
[root@ol7a ~]# sed -i 's/^hosts:.*/hosts:      dns myhostname/' /etc/nsswitch.conf; grep '^hosts' /etc/nsswitch.conf
hosts:      dns myhostname

-- files 가 없는 상태에서 /etc/hosts 에만 있는 이름을 부른다
[root@ol7a ~]# ping -c 1 -W 2 ol7b
ping: ol7b: Name or service not known
-- 파일에는 줄이 그대로 있는지 확인한다
[root@ol7a ~]# grep ol7b /etc/hosts
172.16.225.62   ol7b.example.com   ol7b
[root@ol7a ~]# getent hosts ol7b; echo "getent rc=$?"
getent rc=2
-- /etc/hosts 에 ol7b 줄이 그대로 있는데도 ping 과 getent 가 실패했다. getent 의 종료 코드 2 는 "찾지 못함"이다

-- IP 로는 된다.
[root@ol7a ~]# ping -c 1 -W 2 172.16.225.62 | grep transmitted
1 packets transmitted, 1 received, 0% packet loss, time 0ms
-- 통신 자체는 멀쩡하다. 이름만 안 된다

-- myhostname 은 자기 호스트 이름만 해석해 주는 모듈이다. files 가 없어도 자기 이름은 된다.
[root@ol7a ~]# getent hosts ol7a.example.com; getent hosts $(hostname)
fe80::87f4:d993:7b43:e0c1 ol7a.example.com
fe80::87f4:d993:7b43:e0c1 ol7a.example.com
-- 자기 이름은 myhostname 이 풀었다. 다만 /etc/hosts 의 172.16.225.61 이 아니라 ens32 의 IPv6 링크 로컬 주소다
-- 자기 이름으로 리스너를 여는 프로그램(예: 오라클 리스너의 HOST=호스트이름)이 엉뚱한 주소에 묶일 수 있다
-- 오류 흐름
-- 증상   : ping ol7b → ping: ol7b: Name or service not known, getent hosts ol7b → rc=2
-- 원인   : nsswitch.conf 의 hosts 줄에서 files 가 빠져 /etc/hosts 를 아무도 읽지 않는다
-- 조치   : 원본으로 되돌린다(hosts: files dns myhostname). 데몬 재시작은 필요 없다
-- 재확인 : getent hosts ol7b 가 172.16.225.62, ping ol7b 가 0% packet loss

-- [0] 의 사본으로 덮어 되돌린다. -p 로 권한과 시각도 원본대로
[root@ol7a ~]# cp -p /root/nsswitch.conf /etc/nsswitch.conf; grep '^hosts' /etc/nsswitch.conf
hosts:      files dns myhostname
[root@ol7a ~]# getent hosts ol7b; ping -c 1 -W 2 ol7b | grep transmitted
172.16.225.62   ol7b.example.com ol7b
1 packets transmitted, 1 received, 0% packet loss, time 0ms
-- 원본을 덮자 바로 풀렸다. nsswitch.conf 는 프로그램이 이름을 찾을 때마다 읽힌다(nscd 를 쓰지 않을 때)

--------------------------------------------------------------------------------
 [10] 이름 해석 진단 순서 — ol7b 에서 같은 다섯 가지
--------------------------------------------------------------------------------

-- 정상 노드에서 같은 명령을 쳐 두면 장애 노드의 결과와 한 줄씩 비교할 수 있다.
[root@ol7b ~]# grep '^hosts' /etc/nsswitch.conf; cat /etc/resolv.conf
hosts:      files dns myhostname
# Generated by NetworkManager
search example.com
nameserver 172.16.225.2
[root@ol7b ~]# getent hosts ol7a; getent hosts yum.oracle.com | head -1
172.16.225.61   ol7a.example.com ol7a
2600:140b:2c00:58c::2a7d e10877.dscd.akamaiedge.net yum.oracle.com public-yum.oracle.com.edgekey.net
[root@ol7b ~]# rpm -q bind-utils
bind-utils-9.11.4-26.0.1.P2.el7_9.16.x86_64
-- 정상 노드의 기준값이다. hosts 줄, DNS 서버, 두 이름의 해석 결과가 모두 ol7a 의 [0]·[1] 과 같다
-- 장애 노드와 비교할 다섯 가지를 정리하면 다음과 같다
--   ① ping 같은 서브넷 IP  ② ping 게이트웨이  ③ ping 밖의 IP(8.8.8.8)
--   ④ getent hosts 이름(nsswitch 순서)  ⑤ dig 이름(DNS 서버 직행)

--------------------------------------------------------------------------------
 [변형] 런타임만 바꾸기 — ip route 로 게이트웨이 지우기
--------------------------------------------------------------------------------

-- [2] 는 프로필을 고쳤다. 이번에는 커널 경로 표만 바꾼다. 재부팅이나 연결 재활성화 때 프로필 값이 돌아온다.
[root@ol7a ~]# ip route del default; ip route
172.16.225.0/24 dev ens32 proto kernel scope link src 172.16.225.61 metric 100 
[root@ol7a ~]# ping -c 1 -W 2 8.8.8.8
connect: Network is unreachable
-- 런타임으로 지워도 증상은 [3] 과 같다
-- 프로필과 파일 쪽은 어떤지 본다
[root@ol7a ~]# nmcli -g ipv4.gateway connection show ens32; grep GATEWAY /etc/sysconfig/network-scripts/ifcfg-ens32
172.16.225.2
GATEWAY=172.16.225.2
-- 프로필과 파일에는 게이트웨이가 그대로 있다. 커널 경로 표만 비었다
-- 이 상태는 누가 ip route del 을 쳤는지 흔적이 남지 않는다. 프로필과 커널을 비교해야 찾을 수 있다

-- 프로필은 그대로이므로 reapply 하면 기본 경로가 돌아온다.
[root@ol7a ~]# nmcli device reapply ens32; sleep 2; ip route
Connection successfully reapplied to device 'ens32'.
default via 172.16.225.2 dev ens32 proto static metric 100 
-- reapply 가 프로필의 GATEWAY 로 기본 경로를 다시 넣었다
172.16.225.0/24 dev ens32 proto kernel scope link src 172.16.225.61 metric 100 

-- ip route add 로 직접 넣는 방법도 있다. 이것도 런타임 전용이다.
[root@ol7a ~]# ip route del default; ip route add default via 172.16.225.2 dev ens32; ip route
-- 손으로 넣은 경로에는 proto static 과 metric 100 이 없다. NetworkManager 가 넣은 줄과 꼬리표로 구분된다
default via 172.16.225.2 dev ens32 
172.16.225.0/24 dev ens32 proto kernel scope link src 172.16.225.61 metric 100 
[root@ol7a ~]# nmcli device reapply ens32; sleep 2; ip route
Connection successfully reapplied to device 'ens32'.
default via 172.16.225.2 dev ens32 proto static metric 100 
-- 다시 reapply 하자 NetworkManager 의 경로(proto static metric 100)로 바뀌었다
172.16.225.0/24 dev ens32 proto kernel scope link src 172.16.225.61 metric 100
