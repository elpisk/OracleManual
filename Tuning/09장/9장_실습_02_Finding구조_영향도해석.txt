================================================================================
 9장 실습 02 — Finding·Recommendation·Rationale 구조와 영향도(Impact) 해석  🔒
 목표: 실습 01에서 만든 태스크의 보고서에서 세 층 구조(Finding→Recommendation
       →Action/Rationale)를 짚고, 영향도(Impact)와 이득(Benefit)을 구분해 읽는다.
       영향도(마이크로초)를 초로 잘못 읽는 이상을 재현하고 교정한다.
 환경: non-CDB=orcl 19.3 (SYS AS SYSDBA). 단일 인스턴스.
 참조: 실습 01의 태스크 TUNING_CH9_ADDM_296 (스냅샷 295~296)
 라이선스: 🔒 Diagnostics Pack 필요. 미보유 대안은 하단 참조.
 주의: 개인 실습 환경 전용.
================================================================================

$ sqlplus / as sysdba

SYS@orcl> SET LINESIZE 200 PAGESIZE 100

--------------------------------------------------------------------------------
-- [1] (조치 전 상태) 최상위 Finding의 상세를 보고서에서 확인한다.
--------------------------------------------------------------------------------
SYS@orcl> SET LONG 1000000 PAGESIZE 0 LINESIZE 80
SYS@orcl> SELECT DBMS_ADDM.GET_REPORT('TUNING_CH9_ADDM_296') FROM dual;

Finding 1: Top SQL Statements
Impact is 3.35 active sessions, 60.78% of total activity.
---------------------------------------------------------
SQL statements consuming significant database time were found.

   Recommendation 1: SQL Tuning
   Estimated benefit is 1.73 active sessions, 31.37% of total activity.
   Action
      Run SQL Tuning Advisor on the SELECT statement with SQL_ID
      "9vmszgd1ft9x0".
      Related Object
         select /*+ full(d) */ count(*), sum(d.amt) from claim_details d
   Rationale
      The SQL spent 100% of its database time on CPU, I/O and Cluster waits.
   Rationale
      SQL with SQL_ID "9vmszgd1ft9x0" was executed 5912 times and had an
      average elapsed time of 0.032 seconds.

   Recommendation 2: SQL Tuning
   Estimated benefit is 1.62 active sessions, 29.41% of total activity.
   ... (또 다른 SQL_ID 대상)

-- 세 층 구조 확인:
--   Finding(영향도 60.78%) > Recommendation(이득 31.37% / 29.41%)
--   > Action(특정 SQL_ID에 SQL Tuning Advisor 실행) + Rationale(근거들)

--------------------------------------------------------------------------------
-- [2] (해석) 영향도 vs 이득
--   · 영향도(Impact)   = 이 Finding이 유발한 DB Time 비중  → 60.78%
--   · 이득(Benefit)    = 이 권고 구현 시 절약될 DB Time 비중(상한)
--   · 이득은 'Finding 영향도'가 아니라 '전체 DB Time'에 대한 % 다.
--   · Rec1+Rec2 이득 = 31.37 + 29.41 = 60.78% = Finding 영향도
--     → 두 권고는 서로 다른 SQL을 겨냥하며, 둘 다 처리해야 Finding이 해소된다.
--------------------------------------------------------------------------------

--------------------------------------------------------------------------------
-- [3] (이상 징후 재현) 뷰의 impact 값을 그대로 '초'로 읽는 실수.
--------------------------------------------------------------------------------
SYS@orcl> SELECT finding_name, impact
  2       FROM dba_advisor_findings f JOIN dba_advisor_tasks t USING (task_id)
  3       WHERE t.task_name='TUNING_CH9_ADDM_296' AND f.type='PROBLEM'
  4       ORDER BY impact DESC FETCH FIRST 1 ROWS ONLY;

FINDING_NAME                         IMPACT
-------------------------------- ----------
Top SQL Statements                348720000

--    → 이상: "348,720,000초? DB Time 574초를 훨씬 넘는다!" 는 오해가 생긴다.
--    → 원인: DBA_ADVISOR_FINDINGS.impact 는 마이크로초(μs) 단위다.
--    → 조치: 1,000,000 으로 나눠 초로 환산한다.

--------------------------------------------------------------------------------
-- [4] (조치) impact를 초로 환산해 다시 조회한다.
--------------------------------------------------------------------------------
SYS@orcl> SELECT finding_name, type,
  2         ROUND(impact/1000000,2) AS impact_sec
  3       FROM dba_advisor_findings f JOIN dba_advisor_tasks t USING (task_id)
  4       WHERE t.task_name='TUNING_CH9_ADDM_296'
  5       ORDER BY impact DESC;

FINDING_NAME                     TYPE         IMPACT_SEC
-------------------------------- ------------ ----------
Top SQL Statements               PROBLEM          348.72
Hard Parse                       SYMPTOM           35.28
Hard Parse Due to Literal Usage  PROBLEM           33.38
Commits and Rollbacks            PROBLEM           21.15
Commits and Rollbacks            SYMPTOM           21.15
Soft Parse                       PROBLEM           13.65
normal, successful completion    INFORMATION            0

--------------------------------------------------------------------------------
-- [5] (재확인·검증) 환산값이 % 와 일치하는지 확인한다.
--   · Top SQL 348.72초 ÷ 574초(총 DB Time) = 0.6076 ≈ 60.78%  → 일치
--   · Finding 유형이 그대로 보인다: Hard Parse=SYMPTOM, Literal Usage=PROBLEM
--     조치는 PROBLEM(리터럴)에 한다. SYMPTOM만 보고 공유 풀을 키우지 않는다.
--   · Commits and Rollbacks가 PROBLEM·SYMPTOM 두 줄 = 같은 문제를 두 각도로
--     세는 겹침. 이 때문에 여러 Finding 영향도 합이 100%를 넘을 수 있다.
--   · normal, successful completion = INFORMATION(문제 아님).
--   ※ 위 수치는 이 부하·하드웨어의 실측이다. 학습자 환경에선 <환경값>.
--------------------------------------------------------------------------------

 라이선스 없이 같은 것을 보는 대안 경로 (Diagnostics Pack 미보유 시)
 - DBA_ADVISOR_FINDINGS/DBA_ADDM_FINDINGS는 쓸 수 없다.
 - 상위 SQL은 V$SQL을 elapsed_time/executions로 정렬해 '영향도 큰 것'을 대신 찾는다.
   SYS@orcl> SELECT sql_id, executions, ROUND(elapsed_time/1e6,2) elapsed_s
     2       FROM v$sql ORDER BY elapsed_time DESC FETCH FIRST 5 ROWS ONLY;
 - 하드 파싱은 V$SYSSTAT의 parse count(hard) 델타로 본다.
 판정 기준은 ADDM과 같다: DB Time(=시간) 비중이 큰 것부터.
