================================================================================
 15장 실습 08 — SQL Plan Directives와 Adaptive Plans 관찰, 비활성화 판단
 목표: 카디널리티 오추정으로 생성되는 SQL Plan Directive를 조회하고,
       19c 적응형 계획 파라미터와 계획 표시(FORMAT '+adaptive')를 확인한다.
       계획이 흔들릴 때의 대응 순서(확장 통계 → Baseline → 전역 비활성화)를 익힌다.
 환경: non-CDB=orcl 19.3 (SYS AS SYSDBA로 수행, 대상은 SQLT 스키마)
 라이선스: SQL Plan Directives·Adaptive Plans는 옵티마이저 기본 기능으로
       관리 팩과 무관하다. (SQL Tuning/Access Advisor·SPA만 🔒 Tuning Pack.)
 주의: 개인 실습 환경 전용. 조회 위주이며, 확장 통계 생성 시 원복을 안내한다.
================================================================================

$ sqlplus / as sysdba

SYS@orcl> SET LINESIZE 200 PAGESIZE 100

--------------------------------------------------------------------------------
-- [1] (조치 전 상태) 적응형 최적화 관련 파라미터의 19c 기본값을 확인한다.
--------------------------------------------------------------------------------
SYS@orcl> SHOW PARAMETER optimizer_adaptive

NAME                                 TYPE        VALUE
------------------------------------ ----------- -------
optimizer_adaptive_plans             boolean     TRUE
optimizer_adaptive_statistics        boolean     FALSE

-- 해석: 19c 기본은 계획 적응(PLANS)=ON, 통계 적응(STATISTICS)=OFF.
--   이 조합이 오라클 권장값이다. 대부분의 운영 시스템은 그대로 둔다.

--------------------------------------------------------------------------------
-- [2] 상관관계가 있는 두 컬럼 조건으로 질의해 카디널리티 오추정을 유발한다.
--     (자동 재최적화가 오차를 감지하면 SQL Plan Directive가 생성된다.)
--------------------------------------------------------------------------------
SYS@orcl> -- 병원과 접수일은 상관관계가 있다(같은 병원이 특정 기간에 몰림).
SYS@orcl> SELECT COUNT(*) FROM sqlt.medical_claims
  2       WHERE hosp_id = 777 AND receipt_date = DATE '2024-06-15';

  COUNT(*)
----------
     <환경값>

SYS@orcl> -- 같은 술어 패턴을 여러 번 실행(생략)한 뒤, 디렉티브를 디스크로 flush 한다.
SYS@orcl> EXEC DBMS_SPD.FLUSH_SQL_PLAN_DIRECTIVE;

PL/SQL procedure successfully completed.

--------------------------------------------------------------------------------
-- [3] (조회) 생성된 SQL Plan Directive를 확인한다.
--------------------------------------------------------------------------------
SYS@orcl> COLUMN reason FORMAT A34
SYS@orcl> SELECT directive_id, type, state, reason
  2       FROM  dba_sql_plan_directives
  3       WHERE directive_id IN (
  4         SELECT directive_id FROM dba_sql_plan_dir_objects
  5          WHERE owner='SQLT' AND object_name='MEDICAL_CLAIMS');

       DIRECTIVE_ID TYPE             STATE    REASON
------------------- ---------------- -------- ----------------------------------
          <환경값>  DYNAMIC_SAMPLING USABLE   SINGLE TABLE CARDINALITY MISESTIMATE

-- 해석: TYPE=DYNAMIC_SAMPLING, STATE=USABLE = 이후 최적화 때 동적 통계를 하라는
--   지시가 살아 있다. 디렉티브 ID는 환경마다 달라 <환경값>.
--   ★ 디렉티브는 근본 원인의 '증상'이지 '해결'이 아니다.

--------------------------------------------------------------------------------
-- [4] (조회) 실행 계획에서 적응형 여부를 표시한다(FORMAT '+adaptive').
--------------------------------------------------------------------------------
SYS@orcl> EXPLAIN PLAN FOR
  2       SELECT /*+ gather_plan_statistics */ c.claim_id, h.hosp_name
  3       FROM   sqlt.medical_claims c JOIN sqlt.hospitals h
  4              ON c.hosp_id = h.hosp_id
  5       WHERE  c.hosp_id = 777;

Explained.

SYS@orcl> SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY(format=>'+adaptive'));

PLAN_TABLE_OUTPUT
-------------------------------------------------------------------------------
Plan hash value: <환경값>
-- (계획에 '-' 표시가 붙은 라인은 옵티마이저가 실행 중 버릴 수 있는 후보 단계다.)
-- Note ----- - this is an adaptive plan
-------------------------------------------------------------------------------

-- 해석: 적응형 계획은 실행 시작 시점에 확정하기 애매한 부분(대표적으로 조인 방식)을
--   실행하면서 결정한다. '+adaptive'는 어느 부분이 적응 대상이었는지 보여 준다.

--------------------------------------------------------------------------------
-- [5] (이상 징후 → 원인 → 조치 → 재확인)
--     이상 징후: 존재하지 않는 디렉티브 ID를 지우려다 오류가 난다.
--------------------------------------------------------------------------------
SYS@orcl> EXEC DBMS_SPD.DROP_SQL_PLAN_DIRECTIVE(directive_id => 999999999);
BEGIN DBMS_SPD.DROP_SQL_PLAN_DIRECTIVE(directive_id => 999999999); END;
*
ERROR at line 1:
ORA-13773: insufficient privileges to access SQL Plan Directive "999999999"
ORA-06512: at "SYS.DBMS_SPD", line 128
ORA-06512: at line 1

SYS@orcl> -- 원인 파악: 존재하지 않는(또는 접근 불가) 디렉티브 ID를 넘겼다.
SYS@orcl> -- 조치: 디렉티브를 '지우는' 대신, 근본 원인을 확장 통계로 해소한다.
SYS@orcl> --   (디렉티브를 직접 지워도 같은 오추정이 반복되면 다시 생긴다.)

--------------------------------------------------------------------------------
-- [6] (근본 해소) 상관관계 컬럼에 컬럼 그룹 확장 통계를 만들고 재수집한다.
--------------------------------------------------------------------------------
SYS@orcl> SELECT DBMS_STATS.CREATE_EXTENDED_STATS(
  2           'SQLT','MEDICAL_CLAIMS','(HOSP_ID,RECEIPT_DATE)') FROM dual;

DBMS_STATS.CREATE_EXTENDED_STATS('SQLT','MEDICAL_CLAIMS','(HOSP_ID...
--------------------------------------------------------------------
SYS_STU<환경값>

SYS@orcl> EXEC DBMS_STATS.GATHER_TABLE_STATS('SQLT','MEDICAL_CLAIMS', -
>   method_opt => 'FOR ALL COLUMNS SIZE AUTO');

PL/SQL procedure successfully completed.

SYS@orcl> -- 재확인: 확장 통계가 등록됐는지 본다.
SYS@orcl> SELECT extension FROM dba_stat_extensions
  2       WHERE owner='SQLT' AND table_name='MEDICAL_CLAIMS';

EXTENSION
------------------------------------
("HOSP_ID","RECEIPT_DATE")

-- 해석: 이제 옵티마이저는 두 컬럼 조합의 실제 NDV를 알아 정확히 추정한다.
--   원인이 사라지면 디렉티브는 이후 SUPERSEDED 상태로 바뀌어 동적 샘플링을 강제하지 않는다.

--------------------------------------------------------------------------------
-- [7] (판단) 계획이 흔들릴 때의 대응 순서 — 전역 비활성화는 최후.
--------------------------------------------------------------------------------
-- ① 근본 해소 — 확장 통계·통계 재수집으로 오추정의 원인을 없앤다(위 [6]).
-- ② 특정 SQL만 고정 — 그래도 흔들리면 그 SQL만 SQL Plan Baseline으로 고정(팩 불필요).
-- ③ 전역 비활성화는 최후 — optimizer_adaptive_plans를 끄면 다른 SQL 이득도 사라진다.
--    ALTER SYSTEM SET optimizer_adaptive_plans=FALSE;  -- (최후의 수단, 신중히)
-- 판단 기준은 언제나 '한 SQL의 편의'가 아니라 '워크로드 전체'다.

--------------------------------------------------------------------------------
-- [8] (원복 안내)
--------------------------------------------------------------------------------
SYS@orcl> -- 확장 통계를 실습용으로 만들었다면 되돌린다.
SYS@orcl> EXEC DBMS_STATS.DROP_EXTENDED_STATS('SQLT','MEDICAL_CLAIMS', -
>   '(HOSP_ID,RECEIPT_DATE)');

PL/SQL procedure successfully completed.

--------------------------------------------------------------------------------
-- [정리]
--------------------------------------------------------------------------------
-- 1) 19c 기본: adaptive_plans=ON, adaptive_statistics=OFF(권장). 대개 그대로 둔다.
-- 2) 카디널리티 오추정 → SQL Plan Directive(DYNAMIC_SAMPLING) 생성. 증상이지 해결 아님.
-- 3) 근본 해소는 컬럼 그룹 확장 통계. 원인이 사라지면 디렉티브는 SUPERSEDED 된다.
-- 4) 계획이 흔들리면: 확장 통계 → 특정 SQL Baseline 고정 → 전역 비활성화(최후) 순.
-- 5) 이 실습은 팩과 무관하다(옵티마이저 기본 기능).

SYS@orcl> EXIT
