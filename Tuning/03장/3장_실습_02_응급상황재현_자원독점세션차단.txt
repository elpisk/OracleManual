 3장 실습 02 — 응급 상황 재현과 자원 독점 세션 식별·차단 (WL_04_lock.sql)
 목표: 긴급 대응 5단계(증상 수집 → 하드웨어/CPU 점검 → CPU vs 대기 판별 →
       응급 조치 → 안정성 검증)를 따라, 자원을 독점한 세션을 식별하고
       근거를 캡처한 뒤 차단하는 절차를 익힌다.
 환경: non-CDB=orcl 19.3. 관찰은 SYS@orcl>, 부하는 SQLT@orcl>.
       부하 스크립트: 공용 WL_04_lock.sql (터미널 A/B).
 주의: 개인 실습 환경 전용. KILL SESSION 은 반드시 근거 캡처 후에만 실행한다.

--------------------------------------------------------------------------------
-- [1] (증상 수집 · 긴급 1단계) 응급 상황을 재현한다.
--     터미널 A 가 REVIEW_LOG_WL 한 행을 UPDATE 후 커밋 없이 대기,
--     터미널 B 가 같은 행을 UPDATE 하려다 멈춘다(자원 독점).
--------------------------------------------------------------------------------
-- (터미널 A) SQLT@orcl>
SQLT@orcl> DEFINE wl_role = SETUP
SQLT@orcl> @WL_04_lock.sql
[준비] REVIEW_LOG_WL 생성 완료 (1000행 이하).
SQLT@orcl> DEFINE wl_role = A
SQLT@orcl> @WL_04_lock.sql
[세션 A] 나의 SID = 596 , SERIAL# = <환경값>
[세션 A] UPDATE 1 행 완료. 커밋하지 않는다 (TX 잠금 보유 중).
[세션 A] 60 초 동안 잠금을 유지한다...

-- (터미널 B) SQLT@orcl>  ※ A 직후 실행 → 화면이 멈춘다(업무 정지 증상).
SQLT@orcl> DEFINE wl_role = B
SQLT@orcl> @WL_04_lock.sql

-- 증상 요약: "청구 화면이 멈췄다"는 신고 = 응답시간 문제.
--   '마지막으로 좋았던 이후 무엇이 바뀌었나?' → 특정 트랜잭션이 커밋되지 않음.

--------------------------------------------------------------------------------
-- [2] (CPU vs 대기 판별 · 긴급 3단계) CPU는 남는데 느린가?
--------------------------------------------------------------------------------
$ sqlplus / as sysdba

SYS@orcl> SELECT event, wait_class, COUNT(*) sessions
  2       FROM  v$session
  3       WHERE type='USER' AND status='ACTIVE' AND wait_class <> 'Idle'
  4       GROUP BY event, wait_class
  5       ORDER BY sessions DESC;

EVENT                            WAIT_CLASS    SESSIONS
-------------------------------- ------------ ---------
enq: TX - row lock contention    Application          1

-- 해석: Idle 을 제외한 활성 대기의 대기 클래스가 Application 이다.
--   CPU 포화가 아니라 직렬화(잠금 경합)다 → 자원 독점 세션을 찾는다.
--   (Idle 이벤트인 SQL*Net message from client 를 병목으로 오판하지 않으려고
--    wait_class <> 'Idle' 조건을 두었다.)

--------------------------------------------------------------------------------
-- [3] (자원 독점 세션 식별) 누가 무엇을 붙잡고 있나.
--------------------------------------------------------------------------------
SYS@orcl> SELECT sid, username, event, blocking_session blk, wait_class
  2       FROM  v$session WHERE username='SQLT' ORDER BY sid;

       SID USERNAME EVENT                            BLK WAIT_CLASS
---------- -------- -------------------------------- --- -----------
       596 SQLT     SQL*Net message from client          Idle
       597 SQLT     enq: TX - row lock contention    596 Application

SYS@orcl> SELECT holding_session FROM dba_blockers;

HOLDING_SESSION
---------------
            596

-- 해석: 자원 독점 세션(블로커)은 596 이다. 597 은 피해자(대기자)다.
-- ★ 오판 주의 ★ 596 은 Idle 이라 '한가해 보인다'. 그러나 커밋하지 않은
--   트랜잭션으로 잠금을 붙잡은 진짜 원인이다. 바쁜 597 을 죽이면 안 된다.

--------------------------------------------------------------------------------
-- [4] (이상 징후 → 원인 → 조치 → 재확인) 성급한 조치의 함정.
--     이상 징후: 팀장이 "바쁜 세션(597)부터 죽이라"고 지시.
--------------------------------------------------------------------------------
SYS@orcl> -- 만약 597(대기자)을 죽이면?
SYS@orcl> -- 원인: 597 은 피해자다. 597 을 죽여도 596 이 여전히 잠금을 쥐고 있어
SYS@orcl> --   다음 대기자가 또 막힌다. 증상은 잠깐 사라졌다가 재발한다.
SYS@orcl> -- 조치: 대상은 블로커 596 이다. 단, 죽이기 전에 근거부터 캡처한다.
SYS@orcl> -- 재확인: 아래 [5]~[7]로 캡처→차단→검증 순서를 지킨다.

--------------------------------------------------------------------------------
-- [5] (근거 캡처) 종료 전에 블로커·대기자·잠금·SQL 을 파일로 남긴다.
--------------------------------------------------------------------------------
SYS@orcl> SPOOL /tmp/emergency_before_<환경값>.txt
SYS@orcl> SELECT sid, type, lmode, request, block FROM v$lock WHERE type='TX' ORDER BY sid;

       SID TYPE      LMODE    REQUEST      BLOCK
---------- ---- ---------- ---------- ----------
       596 TX            6          0          1
       597 TX            0          6          0

SYS@orcl> SELECT sid, serial#, sql_id, prev_sql_id FROM v$session WHERE sid IN (596,597);
       SID    SERIAL# SQL_ID        PREV_SQL_ID
---------- ---------- ------------- -------------
       596   <환경값> <환경값>      <환경값>
       597   <환경값> <환경값>      <환경값>
SYS@orcl> SPOOL OFF

-- 해석: block=1 인 596 이 보유자, request=6 인 597 이 대기자. SERIAL# 은 종료
--   명령에 필요하므로 반드시 캡처한다. 값은 환경마다 다르므로 <환경값>.

--------------------------------------------------------------------------------
-- [6] (응급 조치 · 긴급 4단계) 캡처 후 블로커를 차단한다.
--------------------------------------------------------------------------------
SYS@orcl> ALTER SYSTEM KILL SESSION '596,<환경값>' IMMEDIATE;

System altered.

-- (터미널 B) 잠금이 풀리며 대기자 597 의 UPDATE 가 완료된다.
[세션 B] 블로킹 해소됨. UPDATE 1 행 완료. 대기했던 시간(초) = <환경값>

--------------------------------------------------------------------------------
-- [7] (안정성 검증 · 긴급 5단계) 차단 후 상태를 재확인한다.
--------------------------------------------------------------------------------
SYS@orcl> SELECT sid, event, blocking_session blk, wait_class
  2       FROM  v$session WHERE username='SQLT' ORDER BY sid;

       SID EVENT                            BLK WAIT_CLASS
---------- -------------------------------- --- -----------
       597 SQL*Net message from client          Idle

-- 해석: 블로커 596 은 종료됐고, 597 의 BLK 가 비었다. 자원 독점 해소 확인.
--   '조치 전(596 독점) → 조치(캡처 후 KILL) → 조치 후(BLK 비움)'의 3단 완성.

--------------------------------------------------------------------------------
-- [정리]
--------------------------------------------------------------------------------
-- 1) 긴급 대응은 증상 수집 → CPU/대기 판별 → 식별 → (캡처 후) 조치 → 검증 순.
-- 2) 자원 독점 세션은 유휴(Idle)일 수 있다(596). 바쁜 대기자(597)를 죽이지 않는다.
-- 3) KILL 전에 SID·SERIAL#·잠금·SQL 을 캡처한다. 종료하면 증거가 사라진다.
-- 4) 응급 조치는 서비스 회복이 목표. 근본 원인(커밋 누락)은 회복 후 분석한다.
SQLT@orcl> DEFINE wl_role = CLEANUP
SQLT@orcl> @WL_04_lock.sql
[정리] REVIEW_LOG_WL 을 삭제했다. 잔재 = 0개.
SQLT@orcl> EXIT
