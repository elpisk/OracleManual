# 1. Product Vision

## 1.1 제품명

**Oracle Database 19c 성능 튜닝 실무 과정**

## 1.2 핵심 비전

느린 데이터베이스 앞에서 **무엇부터 볼지 아는 사람**을 만든다.

이 과정은 "이 파라미터를 이렇게 바꾸면 빨라진다"는 처방 모음이 아니다. 성능 문제를 마주했을 때
**측정 → 병목 지목 → 원인 규명 → 조치 → 재측정**의 절차를 스스로 돌릴 수 있게 하는 것이 목표다.
그래서 이 과정의 중심에는 특정 기능이 아니라 **DB Time**이라는 하나의 축이 있다. 모든 진단은
"이 작업이 DB Time의 몇 %를 쓰고 있는가"로 환원된다.

세 가지를 특히 경계한다.

1. **히트율 신앙** — 버퍼 캐시 히트율 99%인데 응답시간이 나쁜 상황을 직접 만들어 본다.
2. **권고 맹신** — ADDM·어드바이저의 권고를 그대로 적용하면 안 되는 사례를 판별하게 한다.
3. **근거 없는 조치** — 조치 전 상태를 캡처하지 않은 튜닝은 튜닝이 아니라 도박임을 절차로 각인시킨다.

# 2. 교육 대상

## 2.1 운영 DBA (주 대상)

### 사전 지식

- Oracle 아키텍처(인스턴스·SGA·백그라운드 프로세스)를 설명할 수 있다
- SQL\*Plus로 SYSDBA 접속, 파라미터 조회·변경, 인스턴스 기동·종료를 할 수 있다
- `V$` 뷰를 조회해 본 경험이 있다

ADMIN 과정 이수를 권장하지만 **전제하지는 않는다.** ADMIN 29~33장에서 다룬 모니터링·튜닝 내용은
이 과정에 흡수되어 있어 미이수자도 완결된다(챕터 목록 2-1 참조).

## 2.2 SQL 튜닝 과정 이수자 / 백엔드 개발자 (부 대상)

SQL 한 문장을 고치는 법은 알지만 "왜 어제는 빨랐는데 오늘 느린가", "내 SQL이 아니라 시스템이
문제인 건 어떻게 아는가"에 답하지 못하는 사람. SQL 튜닝 과정(14챕터)의 상위 과정으로 이어진다.

# 3. 최종 교육 목표

## Level 1. 성능을 수치로 말하기
- 응답시간과 처리량을 구분해 목표를 수치로 정의한다
- DB Time·시간 모델·대기 클래스로 현재 상태를 서술한다
- 누적값과 델타값의 차이를 알고 델타로 판단한다

## Level 2. 진단 도구 선택
- 문제의 성격(상시·간헐·특정 시점)에 따라 AWR·ADDM·ASH·V$ 중 무엇을 쓸지 고른다
- Diagnostics Pack 라이선스 유무에 따른 대안 경로를 안다

## Level 3. 보고서 판독
- AWR 보고서의 Load Profile·Top 10 Events·SQL 섹션에서 병목을 지목한다
- ADDM Finding의 영향도를 읽고 권고 채택 여부를 판단한다
- ASH로 특정 10분 구간을 재구성한다

## Level 4. 대기 이벤트로 원인 추적
- 상위 대기 이벤트에서 원인 세그먼트·세션·SQL까지 좁혀 들어간다
- Idle 이벤트를 병목으로 오판하지 않는다

## Level 5. 상시 모니터링 체계
- 메트릭 임계값을 이력 분포에 근거해 설정한다
- 알림이 울렸을 때의 대응 절차를 문서화한다

## Level 6. 어드바이저 활용
- SQL Tuning/Access Advisor, SPA, Statistics Advisor를 실행하고 권고를 해석한다
- 자동 유지관리 작업이 성능에 미치는 영향을 통제한다

## Level 7. 메모리 구성
- SGA·PGA 구조를 이해하고 어드바이저 근거로 크기를 조정한다
- `ORA-04031`·`ORA-04036`을 재현하고 해소한다

## Level 8. 시스템 자원 판별
- 병목이 DB 안인지 밖인지(CPU·I/O·네트워크) 판별한다
- I/O 캘리브레이션 결과를 해석한다

# 4. 교육 환경

## 4.1 데이터베이스

| 항목 | 값 |
|---|---|
| 버전 | Oracle Database 19c (19.3.0) Enterprise Edition |
| 구조 | **non-CDB** (`orcl`), ARCHIVELOG 모드. DB 블록 8KB, SGA_TARGET 약 1.5GB / PGA_AGGREGATE_TARGET 약 700MB |
| 접속 | `sqlplus / as sysdba` (프롬프트 `SYS@orcl>`), 업무 계정은 별도 |
| 필수 조건 | **개인 실습 환경 전용.** 파라미터 변경·인스턴스 재기동·부하 유발이 포함된다 |

## 4.2 실습 데이터

**진료비청구심사 스키마를 재사용한다.** 별도 생성 시간이 들지 않고, SQL 튜닝 과정과 실습 환경이
이어진다.

| 테이블 | 건수 | 이 과정에서의 쓰임 |
|---|---|---|
| HOSPITALS | 1,000 | 소형 참조 테이블 — KEEP 풀 실습 |
| PATIENTS | 50,000 | 조인 대상 |
| DRUG_MASTER | 10,000 | 소형 참조 테이블 — 결과 캐시 실습 |
| MEDICAL_CLAIMS | 300,000 | 주 부하 대상. HOSP_ID 1~50에 청구 50% 집중(스큐) |
| CLAIM_DETAILS | 899,894 | 대량 스캔·정렬 대상 |
| DISEASES | 399,551 | 조인 대상 |
| REVIEW_LOG | 500,000 | 대량 삽입·잠금 경합 대상 |

생성 스크립트: `SQLTUNING/진료비청구심사_스키마_생성스크립트_수정본.md` (2026-08-26 저장소 흡수 전에는 `elpisk/oracle-medical-claims-practice`)

## 4.3 라이선스 (중요)

**AWR · ADDM · ASH · `DBA_HIST_*` · `V$ACTIVE_SESSION_HISTORY`는 Diagnostics Pack 라이선스가
필요하다.** 교육용으로 무심코 쓰다가 실무에서 그대로 따라 하면 라이선스 위반이 된다.

| 처리 | 내용 |
|---|---|
| 1장 | 라이선스 절을 둔다 — 팩 구분, `DBA_FEATURE_USAGE_STATISTICS` 확인법, `CONTROL_MANAGEMENT_PACK_ACCESS` 의미 |
| 6·8·9·10·11·15장 | 도입부에 라이선스 표기를 **반복**한다 |
| 6장 | **Statspack** 설치·스냅샷·보고서를 한 절로 넣는다 |
| 각 진단 챕터 | "라이선스 없이 같은 것을 보는 법"을 V$ 뷰 직접 조회로 병기한다 |
| 실습문제 | 대안 경로를 묻는 문항을 배치한다 |

## 4.4 권한 모델

| 환경 | 계정 | 용도 |
|---|---|---|
| A — 진단 | `SYS AS SYSDBA` | 파라미터, V$/DBA_HIST, AWR·ADDM·ASH, 어드바이저 |
| B — 업무 | `SQLT`(진료비 스키마 소유) | 부하 실행 대상, 업무 SQL |
| C — 관찰용 | `MON`(신규, `SELECT ANY DICTIONARY`) | 권한 최소화 환경에서 무엇이 보이고 안 보이는지 대조하는 실습용 |

C 환경은 12장(모니터링 권한 설계)과 라이선스 대안 실습에서 쓴다.

# 5. 부하 생성 스크립트 (과정 공용 자산)

성능 데이터는 부하 없이 생기지 않는다. 조회만 하는 실습으로는 AWR·ASH가 비어 아무것도 배울 수
없다. **1장 파일럿보다 먼저 제작한다.**

위치: `Tuning\부하스크립트\` · 대상 스키마: `SQLT`

| 스크립트 | 유발하는 것 | 관찰 지표 | 쓰이는 챕터 |
|---|---|---|---|
| `WL_01_parse.sql` | 리터럴 SQL 반복 실행으로 하드 파싱 폭증 | `parse count (hard)`, 라이브러리 캐시 커서 수, 공유 풀 사용량 | 2·18 |
| `WL_02_io.sql` | CLAIM_DETAILS 대량 전체 스캔 + 랜덤 단일 블록 읽기 | `db file scattered/sequential read`, 물리 읽기 | 14·17·20 |
| `WL_03_sort.sql` | 대량 정렬·해시 조인으로 PGA 압박 | `sorts (disk)`, `V$SQL_WORKAREA` 1-pass/multi-pass | 19 |
| `WL_04_lock.sql` | REVIEW_LOG 동일 행 갱신으로 행 잠금 경합 | `enq: TX - row lock contention`, `BLOCKING_SESSION` | 3·12·14 |
| `WL_05_commit.sql` | 소량 DML + 잦은 커밋 | `log file sync`, `user commits` | 14 |
| `WL_06_mixed.sql` | 위 조합 — AWR 스냅샷 구간용 종합 부하 | Load Profile 전반 | 5·6·8·9·10·11 |

## 5.1 스크립트 공통 요건

각 스크립트 머리에 주석으로 다음을 명시한다.

```text
목적       : 무엇을 유발하는가
전제       : 필요한 권한·객체·파라미터 상태
소요 시간  : 기본 실행 시간과 조절 방법(반복 횟수 변수)
관찰 지표  : 실행 후 무엇을 조회해 확인하는가
되돌리기   : 생성 객체 삭제, 변경 파라미터 원복 절차
주의       : 개인 실습 환경 전용임을 명시
```

- 반복 횟수·병렬 세션 수를 상단 변수로 뽑아 환경에 맞게 조절할 수 있게 한다.
- **원본 데이터를 훼손하지 않는다.** 대량 DML은 복제 테이블(`*_WL`)에서만 수행하고 스크립트 끝에서 정리한다.
- 여러 세션이 필요한 부하는 실행 방법(별도 터미널 N개)을 주석에 적는다.

# 8. Chapter 상세

## Chapter 1 — 성능 튜닝 개요
**주요 내용** 응답시간 vs 처리량 / 튜닝이 필요한 시점 판단 / 도구 지도(V$·AWR·ADDM·ASH·Advisor) / 관리 팩 라이선스 / 목표를 수치로 정의하는 법
**실습** 5개 (지표 조회, 도구 진입점, 라이선스 확인, 목표 정의, 환경 기준선)
**DBA Point** "느리다"는 신고를 수치로 번역하지 못하면 튜닝은 시작되지 않는다
**Common Error** 목표 없이 파라미터부터 바꾸기

## Chapter 2 — 성능을 고려한 설계와 개발
**주요 내용** 확장성 저해 요소 / 바인드 변수와 커서 공유 / 커넥션 비용 / 배열 처리 / 배포 전 워크로드 테스트
**실습** 5개 ★ (`WL_01_parse`)
**DBA Point** 설계 단계에서 정해진 성능 한계는 튜닝으로 못 넘는다
**Common Error** 리터럴 SQL을 개발 편의로 방치

## Chapter 3 — 성능 개선 방법론과 긴급 대응
**주요 내용** Oracle Performance Improvement Method / 증상→원인 절차 / 응급 진단 체크리스트 / 블로킹 세션 처리 / 조치 전 근거 캡처
**실습** 5개 ★ (`WL_04_lock`)
**DBA Point** 응급 조치와 근본 원인 분석을 분리한다
**Common Error** 세션을 죽이고 원인 기록을 남기지 않음

## Chapter 4 — 성능을 위한 데이터베이스 구성
**주요 내용** 초기 파라미터 / Undo 보존 / 임시 테이블스페이스 / 전용 vs 공유 서버 / 블록 크기와 행 이주
**실습** 5개 (`ORA-01555`·`ORA-01652` 재현 포함)
**DBA Point** 구성 실수는 튜닝으로 덮이지 않는다
**Common Error** Undo·Temp 부족을 SQL 문제로 오인

## Chapter 5 — 성능 측정의 기준: 통계와 DB Time
**주요 내용** DB Time 정의 / 시간 모델(`V$SYS_TIME_MODEL`) / 대기 클래스 / `STATISTICS_LEVEL` / 누적값과 델타
**실습** 6개 ★ (`WL_06_mixed`)
**DBA Point** 이 과정의 모든 판단이 여기서 출발한다
**Common Error** 누적 통계를 그대로 읽고 내리는 오판

## Chapter 6 — 통계 수집 ① 자동 수집과 AWR 인프라
**주요 내용** 스냅샷 주기·보존 / 베이스라인 / SYSAUX 용량 / **Statspack 대안**
**실습** 6개 ★🔒
**DBA Point** 필요한 구간은 베이스라인으로 보호해야 살아남는다
**Common Error** 보존 기간 초과로 사고 당시 데이터 소실

## Chapter 7 — 통계 수집 ② 히스토그램·확장 통계·시스템 통계
**주요 내용** 히스토그램 종류와 생성 조건 / `METHOD_OPT` / 컬럼 그룹·표현식 통계 / 시스템 통계 / 통계 Preferences / Optimizer Statistics Advisor *(ADMIN 33장 심화)*
**실습** 7개 (진료비 스키마의 HOSP_ID 편중 활용)
**DBA Point** 통계는 옵티마이저가 보는 세계의 전부다
**Common Error** 전체 재수집을 만능으로 여김

## Chapter 8 — AWR 보고서 읽기
**주요 내용** 보고서 구조 / Load Profile / Top 10 Foreground Events / SQL 정렬 섹션 / Instance Activity / Advisory 섹션
**실습** 7개 ★🔒
**DBA Point** 상위 대기 하나만 보고 결론 내지 않는다 — DB Time 비중과 함께 본다
**Common Error** 부하가 없는 구간 보고서로 "문제 있다"고 판정

## Chapter 9 — ADDM
**주요 내용** Finding·Recommendation·Rationale 구조 / 영향도 / ADDM 뷰 직접 조회 / 권고 채택 기준
**실습** 5개 ★🔒
**DBA Point** 권고는 가설이지 결론이 아니다
**Common Error** 영향도 낮은 권고에 시간 쓰기

## Chapter 10 — ASH
**주요 내용** 샘플링 원리 / ASH 보고서 / 구간 지정 / 세션 단위 재구성 / `DBA_HIST_ACTIVE_SESS_HISTORY`

**Common Error** 부하 증가를 성능 저하로 보고

## Chapter 12 — 경고·메트릭 기반 상시 모니터링 *(ADMIN 32장 흡수·심화)*

**실습** 5개

**Common Error** 절대값 기준 상위 SQL 선별

## Chapter 14 — V$ 뷰 인스턴스 튜닝 ② 대기 이벤트 분석

# 9. 산출물 규격

기존 과정(`OracleManual\제작_가이드.md` 3장)과 동일하다.

| 파일 | 규격 |
|---|---|
| `{N}장_{제목}.docx` | 26,000~30,000자, Heading 1/2/3, 맑은 고딕 + Consolas, Note·Best Practice·실무시나리오·Quiz 박스, 퀴즈 6문항 + 요약 + 실습 개요 |
| `{N}장_{제목}.pptx` | 35~55슬라이드, 다크 타이틀/섹션 + 붉은 헤더, 발표자 노트 226~400자 필수 |
| `{N}장_실습문제.docx` | 객관식 50문항 (하20/중20/상10) |
| `{N}장_실습문제_정답.docx` | 정답 + 해설 |

| `{N}장_실습_{NN}_{주제}.txt` | 세션 트랜스크립트. 챕터당 5~8개 |

## 9.1 이 과정 고유 규격

- **트랜스크립트에는 반드시 "조치 전 상태 → 조치 → 조치 후 상태" 3단 캡처가 들어간다.** 성능 실습은 전후 비교가 없으면 학습이 성립하지 않는다.
- **부하 스크립트 실행 구간을 명시한다** — 어느 시점에 어떤 `WL_` 스크립트를 몇 초간 돌렸는지 트랜스크립트에 남긴다.
- **수치는 실측값만 쓴다.** 환경에 따라 달라지는 값은 `<환경값>`으로 두고 "무엇과 무엇을 비교해 무엇을 판정하는가"를 서술한다.
- 🔒 실습에는 라이선스 표기와 대안 경로를 함께 싣는다.
