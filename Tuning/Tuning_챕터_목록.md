## 2. 다른 과정과의 관계 — v1에서 바뀐 부분

**v1은 ADMIN 31~33장과 겹치는 주제를 이 과정에서 빼는 방향이었다. v2는 반대로 흡수한다.** 성능 튜닝을 배우러 온 사람에게 "그건 ADMIN 과정에서 들으셨을 겁니다"라고 넘기면 과정이 끊긴다. ADMIN을 듣지 않은 수강생도 이 과정만으로 완결되게 한다.

### 2-1. ADMIN에서 가져오는 내용

| ADMIN | 주제 | 이 과정에서의 처리 |
|---|---|---|
| 29·30장 | 자동 유지관리 작업, 유지관리 윈도우 | **15장에 흡수.** 통계 수집·SQL 튜닝 어드바이저가 자동 작업으로 언제 도는지, 그것이 성능에 어떤 영향을 주는지 관점으로 재구성 |
| 31장 | 모니터링·튜닝 개요, AWR/ADDM 개념, Advisory Framework | **1·5·8·9장에 분산 흡수.** 개념 소개는 앞부분에서 압축하고, 각 도구는 해당 챕터에서 실무 판독으로 확장 |
| 32장 | 서버 생성 알림, 메트릭 임계값, 대기 이벤트·세션·서비스 모니터링 | **12장으로 독립.** ADMIN이 "설정하는 법"이었다면 여기서는 "임계값을 얼마로 잡을 것인가, 알림이 울렸을 때 무엇부터 보는가" |
| 33장 | SQL 튜닝 프로세스, 옵티마이저 통계 Preferences, Statistics Advisor, SQL Plan Directives, Adaptive Plans, SQL Tuning/Access Advisor, SPA | **7·15장에 흡수.** 통계 관련은 7장, 어드바이저·적응형 기능은 15장 |

**중복이 아니라 심화다.** 같은 주제를 다시 다룰 때는 ADMIN에서 어디까지 다뤘는지 각 챕터 도입부에 한 줄로 밝히고, 이 과정에서 무엇을 더 하는지 명시한다.

### 2-2. SQL 튜닝 과정과의 경계 (v1과 동일, 유지)

| 과정 | 층위 | 다루는 것 |
|---|---|---|
| **SQLT 14챕터** | SQL 한 문장 | 실행계획 판독, 인덱스 설계, 조인 방식, SARGable, 페이징, 측정 |
| **TUNING (이 과정)** | 인스턴스·시스템 | DB Time 기반 진단, AWR/ADDM/ASH 판독, 대기 이벤트 추적, 어드바이저 활용, SGA·PGA·I/O 구성 |

**SQL 한 문장을 어떻게 고쳐 쓸 것인가로 결론이 나면 거기서 멈추고 SQLT로 넘긴다.** 이 과정의 종착점은 "어느 SQL이, 어떤 대기 때문에, 전체 DB Time의 몇 %를 쓰는가"와 "어드바이저가 무엇을 권고했고 그 권고를 채택할 것인가"까지다.

### 3-1. PTG 챕터 중 축소·제외한 것

| PTG | 처리 |
|---|---|
| 12장 In-Memory Column Store, Memoptimized Rowstore | **별도 라이선스 기능**이라 16장에서 "존재와 적용 조건"만 언급하고 실습 제외 |
| 6장 Performance Hub Active Report | EM 의존이라 8장에서 개념만 |
| 17장 Orion 캘리브레이션 도구 | 20장에서 DB 내부 `DBMS_RESOURCE_MANAGER.CALIBRATE_IO` 중심으로 다루고 Orion은 소개만 |

### 3-2. 구성상 판단

- PTG 12장(SGA 전반)은 독립 챕터로 두지 않고 16·17·18장에 나눴다. ASMM은 메모리 할당과 같이 봐야 이해되고, 나머지는 버퍼 캐시·공유 풀 각 챕터에 붙는 편이 자연스럽다.
- PTG 15·16장(결과 캐시·PGA)은 각각 단독으로 26,000자를 채우기 어려워 "SGA 밖의 메모리"로 묶었다.
- 신설한 12·15장은 ADMIN 흡수분이 주 근거라 PTG 의존도가 낮다. 두 챕터는 **ADMIN 본문 docx를 실제로 열어 서술 수준을 확인한 뒤** 그보다 한 단계 깊게 쓴다.

## 4. 실습 환경

이 과정은 **부하가 있어야 성능 데이터가 나온다.** 조회만 하는 실습으로는 AWR·ASH가 비어 아무것도 배울 수 없다.

| 항목 | 내용 |
|---|---|
| 권한 | SYSDBA. 대부분의 실습이 인스턴스 파라미터와 V$/DBA_HIST 뷰를 다룬다 |
| 실습 데이터 | **진료비청구심사 스키마를 재사용한다**(HOSPITALS 1,000 / PATIENTS 50,000 / DRUG_MASTER 10,000 / MEDICAL_CLAIMS 300,000 / CLAIM_DETAILS 899,894 / DISEASES 399,551 / REVIEW_LOG 500,000). 생성 스크립트는 `elpisk/oracle-medical-claims-practice`에 있다 |
| 부하 생성 | **과정 공용 부하 스크립트 `WL_01`~`WL_06`을 만든다**(아래 4-1) |
| 메모리 실습 | SGA·PGA 파라미터를 바꾸고 재기동하는 실습이 있다. 개인 실습 환경 전용임을 각 트랜스크립트 머리에 경고로 넣는다 |

### 4-1. 공용 부하 스크립트 (확정)

| 이름 | 유발하는 것 | 쓰이는 챕터 |
|---|---|---|
| `WL_01_parse.sql` | 하드 파싱 폭증(리터럴 SQL 반복) | 2·18장 |
| `WL_02_io.sql` | 대량 전체 스캔·랜덤 읽기 | 14·17·20장 |
| `WL_03_sort.sql` | 대량 정렬·해시(PGA 압박) | 19장 |
| `WL_04_lock.sql` | 행 잠금 경합·블로킹 | 3·12·14장 |
| `WL_05_commit.sql` | 잦은 커밋(log file sync) | 14장 |
| `WL_06_mixed.sql` | 위 조합 — AWR 구간용 종합 부하 | 5·6·8·9·10·11장 |

- 위치: `Tuning\부하스크립트\`. 각 스크립트 머리에 목적·전제·소요 시간·되돌리는 법을 주석으로 단다.
- 대상은 진료비 스키마이며, 원본 데이터를 훼손하는 작업(대량 DML)은 복제 테이블에서만 수행한다.
- **1장 파일럿보다 먼저 만든다.** 5장부터 부하가 필요하고, 트랜스크립트의 실측 출력이 이 스크립트에 의존한다.

### 4-2. 라이선스 방침 (확정)

**AWR·ADDM·ASH·`DBA_HIST_*`·`V$ACTIVE_SESSION_HISTORY`는 Diagnostics Pack 라이선스가 필요하다.** 교육용으로 아무 생각 없이 쓰다가 실무에서 그대로 따라 하면 라이선스 위반이 되므로 다음과 같이 처리한다.

1. **1장에 라이선스 절을 둔다** — 어떤 기능이 어느 팩에 속하는지, `DBA_FEATURE_USAGE_STATISTICS`로 사용 이력을 확인하는 방법, `CONTROL_MANAGEMENT_PACK_ACCESS` 파라미터의 의미.
2. **해당 챕터(6·8·9·10·11·15장) 도입부에 라이선스 표기를 반복한다.** 한 번 쓰고 마는 것이 아니라 각 장에서 다시 짚는다.
3. **미보유 환경 대안을 병기한다** — 6장에 **Statspack** 설치·스냅샷·보고서를 한 절로 넣고, 각 진단 챕터마다 "라이선스 없이 같은 것을 보는 법"을 V$ 뷰 직접 조회로 제시한다. 실습문제에도 대안 경로를 묻는 문항을 배치한다.
