================================================================================
 13장 실습 02 — V$SYSSTAT 주요 통계 델타 계산
 목표: V$SYSSTAT 값이 인스턴스 기동 이후 누적임을 확인하고, 두 시점의 델타를
       초·트랜잭션당으로 정규화한다. 누적 절대값을 그대로 판정에 쓰는 오류를
       재현하고, 델타·비율로 교정한다. 하드 파싱 비율도 파생 지표로 계산한다.
 환경: non-CDB=orcl 19.3 (SYS AS SYSDBA로 수행)
 부하: 시작 스냅샷을 뜬 뒤 다른 세션에서 WL_06_mixed.sql을 60초간 돌리고
       종료 스냅샷을 뜬다.  주의: V$ 조회는 읽기 전용, 라이선스 불필요.
================================================================================

$ sqlplus / as sysdba

SYS@orcl> SET LINESIZE 200
SYS@orcl> SET PAGESIZE 100

--------------------------------------------------------------------------------
-- [1] (조치 전 상태) 주요 부하 통계의 '누적값'을 먼저 본다.
--------------------------------------------------------------------------------
SYS@orcl> SELECT name, value FROM v$sysstat
  2       WHERE name IN ('session logical reads','physical reads',
  3         'parse count (hard)','parse count (total)','execute count',
  4         'user commits','sorts (disk)','sorts (memory)')
  5       ORDER BY name;

NAME                             VALUE
------------------------------ ---------
execute count                     338398
parse count (hard)                112198
parse count (total)               185227
physical reads                     70100
session logical reads          356228457
sorts (disk)                           0
sorts (memory)                     60198
user commits                       63992

-- 이상 징후(오판 재현): 신입 DBA가 "session logical reads 3.56억이라니
--   논리읽기가 폭증했다. 버퍼 캐시를 키우자"고 제안한다.
-- 원인 파악: 이 값은 기동 이후 누적이다. 10분치인지 3주치인지 모르면
--   많다/적다를 말할 수 없다 → 절대값은 판정 근거가 아니다.

--------------------------------------------------------------------------------
-- [2] (조치) 시작값을 저장한다. 이후 60초 부하 구간과 비교한다.
--------------------------------------------------------------------------------
SYS@orcl> -- 시작 스냅샷(부하 유발 직전)
SYS@orcl> SELECT name, value FROM v$sysstat
  2       WHERE name IN ('session logical reads','execute count','user commits');

NAME                             VALUE
------------------------------ ---------
session logical reads          356228457
execute count                     338398
user commits                       63992

SYS@orcl> -- ★ 여기서 다른 세션에서 WL_06_mixed.sql 을 약 60초간 실행한다.
SYS@orcl> --   (부하 구간을 만들어야 통계가 움직인다)

--------------------------------------------------------------------------------
-- [3] (조치 후 상태) 60초 뒤 종료 스냅샷을 뜬다. 값은 <환경값>이다.
--------------------------------------------------------------------------------
SYS@orcl> SELECT name, value FROM v$sysstat
  2       WHERE name IN ('session logical reads','execute count','user commits');

NAME                             VALUE
------------------------------ ---------
session logical reads          362520100     <- <환경값>
execute count                     349530     <- <환경값>
user commits                       66102     <- <환경값>

--------------------------------------------------------------------------------
-- [4] (해석) 델타를 구해 초·트랜잭션당으로 정규화한다.
--------------------------------------------------------------------------------
-- Δ session logical reads = 362,520,100 - 356,228,457 = 6,291,643
-- Δ execute count         =     349,530 -     338,398 =    11,132
-- Δ user commits          =      66,102 -      63,992 =     2,110
-- 경과 시간 = 60초 (부하 구간)
--
-- 초당 논리읽기 = 6,291,643 / 60      ≈ 104,861 LIO/s
-- 초당 실행     =    11,132 / 60      ≈     186 execs/s
-- 초당 커밋     =     2,110 / 60      ≈    35.2 commits/s
-- 트랜잭션당 논리읽기 = 6,291,643 / 2,110 ≈ 2,982 LIO/txn
--
-- 해석: 이제야 판정이 가능하다. 초당 10만 LIO는 이 부하 구간의 처리량이고,
--   트랜잭션당 약 2,982 LIO는 '한 건이 얼마나 무거운가'다. 이 값을 정상
--   기준선과 대비해야 부하 증가인지 성능 저하인지 갈린다.
-- 교훈: [1]의 절대값 3.56억은 판정 근거가 아니었다. 델타·정규화가 근거다.
--   → 버퍼 캐시 확대 제안은 근거가 선 뒤에 검토한다(성급한 조치 보류).
-- 재확인: [1]의 오판(절대값→폭증 단정)이 교정되었는지 되짚는다. physical
--   reads 70,100이 논리읽기 델타(629만)에 비해 극히 작으므로 캐시 미스는 미미
--   → 버퍼 캐시 확대는 근거 없음이 재확인된다. 조치 대상은 캐시가 아니라
--   풀 스캔 SQL과 하드 파싱이다([5]와 실습 04·05로 이어짐).

--------------------------------------------------------------------------------
-- [5] (해석) 파생 지표 — 하드 파싱 비율을 계산한다.
--------------------------------------------------------------------------------
-- 하드 파싱 비율 = parse count (hard) / parse count (total)
--             = 112,198 / 185,227 ≈ 0.606 → 약 60.6%
--
-- 해석: 정상은 0에 가까워야 한다(문장당 1회 하드 파싱, 이후 소프트 파싱·실행).
--   60.6%는 비정상적으로 높다 → 바인드 미사용(리터럴 SQL)을 강하게 의심한다.
--   이 원인은 실습 04에서 V$SQL로 눈으로 확인한다.
-- 참고: 구간 하드 파싱률도 Δparse count (hard)/경과초로 구해, 초당 100건을
--   넘으면 공유 풀·라이브러리 캐시 래치 경합을 함께 점검한다.

--------------------------------------------------------------------------------
-- [정리]
--------------------------------------------------------------------------------
-- 1) V$SYSSTAT 값은 누적이다. 절대값 하나로는 아무것도 판정하지 못한다.
-- 2) 두 시점 델타를 경과초로 나누면 초당(처리량), Δcommits로 나누면
--    트랜잭션당(한 건의 무게)이 되어 비로소 판정 근거가 된다.
-- 3) sorts (disk)=0, sorts (memory)=60,198 → 정렬이 전부 메모리(PGA 정상).
-- 4) 하드 파싱 비율 60.6%는 심각. 파생 지표가 절대값 순위표가 못 보는
--    문제를 드러낸다.
-- ※ 종료값은 환경에 따라 다른 <환경값>이다. 절차와 판정 기준을 익히는 것이 목표.

SYS@orcl> EXIT
