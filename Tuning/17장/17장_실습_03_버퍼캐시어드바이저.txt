================================================================================
 17장 실습 03 - 버퍼 캐시 어드바이저로 크기 변경 효과 예측
 목표: V$DB_CACHE_ADVICE로 캐시 크기별 물리 읽기(계수)를 조회해, 더
       키워도 소용없는 수렴 구간을 찾는다. '히트율이 높으니 충분'이 아니라
       '어드바이스가 수렴했으니 충분'으로 판단하는 규율을 익힌다.
 환경: non-CDB=orcl 19.3 (SYS AS SYSDBA). 읽기 전용 조회.
 주의: 개인 실습 환경 전용. 어드바이스는 워크로드를 반영하므로 대표 부하
       후에 조회해야 의미가 있다. 절대값은 <환경값>으로 읽는다.
================================================================================

$ sqlplus / as sysdba

SYS@orcl> SET LINESIZE 200
SYS@orcl> SET PAGESIZE 100

--------------------------------------------------------------------------------
-- [1] (조치 전 확인) 어드바이스가 수집 중인지(파라미터 ON) 확인한다.
--------------------------------------------------------------------------------
SYS@orcl> SELECT name, value FROM v$parameter WHERE name='db_cache_advice';

NAME               VALUE
------------------ ------
db_cache_advice    ON

-- 해석: ON이면 어드바이스가 수집된다(기본값). OFF였다면 ALTER SYSTEM으로
--   ON으로 바꾼 뒤 통계가 안정될 때까지 기다려야 한다.

--------------------------------------------------------------------------------
-- [1-1] (이상 징후 -> 원인 -> 조치 -> 재확인)
--     block_size 필터를 빼고 조회해 값이 뒤섞여 나오는 오판을 재현한다.
--------------------------------------------------------------------------------
SYS@orcl> SELECT name, block_size, COUNT(*)
  2       FROM  v$db_cache_advice
  3       WHERE name='DEFAULT'
  4       GROUP BY name, block_size;

NAME       BLOCK_SIZE   COUNT(*)
-------- ----------- ----------
DEFAULT        8192          20

-- 이상 징후: block_size 없이 name만으로 조회하면 표준 외 블록 크기 캐시가
--   섞일 수 있어(여러 block_size) 계수 해석이 꼬인다.
-- 원인: 어드바이스는 (name, block_size)별로 관리된다. 필터가 없으면 서로
--   다른 블록 크기의 행이 한데 섞여 나온다.
-- 조치: block_size=8192(표준 블록 크기)를 반드시 명시해 한 캐시만 본다.
-- 재확인: 아래 [2]에서 block_size=8192로 좁혀 20개 행만 정확히 조회한다.

--------------------------------------------------------------------------------
-- [2] (조회) DEFAULT 풀(8K)의 크기별 물리 읽기 계수를 조회한다.
--------------------------------------------------------------------------------
SYS@orcl> SELECT ROUND(size_for_estimate) cache_mb, size_factor factor,
  2         estd_physical_read_factor rd_factor, estd_physical_reads
  3       FROM  v$db_cache_advice
  4       WHERE name='DEFAULT' AND block_size=8192
  5       ORDER BY size_for_estimate;

  CACHE_MB     FACTOR   RD_FACTOR  ESTD_PHYSICAL_READS
---------- ---------- ----------- --------------------
        80     0.0926    446.8807             33631793
       160     0.1852      2.6614               200293
       240     0.2778      1.4789               111300
       320     0.3704      1.1634                87559
       400     0.4630      1.0067                75761
       480     0.5556      1.0000                75259
       560     0.6481      1.0000                75259
       640     0.7407      1.0000                75259
       800     0.9259      1.0000                75259
       864     1.0000      1.0000                75259
       960     1.1111      1.0000                75259
      1600     1.8519      1.0000                75259

--------------------------------------------------------------------------------
-- [3] (해석) 세 구간으로 나눠 읽는다.
--------------------------------------------------------------------------------
-- * 위험 구간(80MB): 계수 446.88 -> 물리 읽기가 약 447배(3천 3백만)로 폭증.
--     이 크기로 줄이면 절대 안 된다.
-- * 개선 구간(160~400MB): 계수 2.66 -> 1.0으로 가파르게 하락.
--     이 구간에 현재 크기가 있었다면 확대가 물리 읽기를 실질적으로 줄인다.
-- * 수렴 구간(480MB 이상): 계수 1.0. 더 키워도 물리 읽기가 75,259에서 불변.
--     현재 864MB는 이미 이 구간을 넘었다 -> 확대는 무효.
-- => 판정: 이 워크로드의 '충분한 크기'는 약 480MB. 현재 864MB는 넉넉하며,
--     다른 구조(공유 풀.PGA)가 필요하면 회수해도 물리 읽기에 영향 없다.

--------------------------------------------------------------------------------
-- [4] (대조) 히트율만 봤다면 못 내릴 결론임을 확인한다.
--------------------------------------------------------------------------------
SYS@orcl> -- 히트율은 99.98%로 '충분'해 보이지만, 그 값은 크기를 바꾸면
SYS@orcl> -- 어떻게 될지를 말해 주지 못한다. 반면 어드바이스는 크기를 축으로
SYS@orcl> -- 물리 읽기를 함수로 보여 준다. 크기 판단의 근거는 어드바이스다.
SYS@orcl> -- (주의) 캐시를 20% 넘게 바꾸면 기존 어드바이스는 폐기되고 새 크기
SYS@orcl> -- 기준으로 재수집된다. 변경 후에는 통계 안정 시간을 준 뒤 다시 본다.

--------------------------------------------------------------------------------
-- [정리]
--------------------------------------------------------------------------------
-- 1) V$DB_CACHE_ADVICE는 크기별 물리 읽기를 시뮬레이션한다(계수=현재 대비 배수).
-- 2) 80MB=위험(447배), 160~400MB=개선, 480MB↑=수렴(불변).
-- 3) 현재 864MB는 수렴 구간을 넘었다 -> 더 키워도 소용없고 회수 가능.
-- 4) 크기 판단은 히트율이 아니라 어드바이스로 한다.
-- * V$DB_CACHE_ADVICE 조회는 라이선스와 무관하다.

SYS@orcl> EXIT
