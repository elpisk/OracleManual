================================================================================
 17장 실습 01 - 버퍼 캐시 구성과 현재 크기.사용률 확인
 목표: 버퍼 캐시가 어떤 풀로, 얼마나 크게 구성돼 있고 풀별 히트율이
       어떤지 조회한다. 조회 중 별칭 예약어 충돌(ORA-00904)을 재현하고
       원인을 찾아 수정한다. '높은 히트율'을 곧 '좋은 상태'로 오판하지
       않도록, 다음 실습(02)로 이어지는 관찰 포인트를 남긴다.
 환경: non-CDB=orcl 19.3 (SYS AS SYSDBA로 수행). 읽기 전용 조회 위주.
 주의: 개인 실습 환경 전용. 절대값은 환경 의존이므로 <환경값>으로 읽는다.
================================================================================

$ sqlplus / as sysdba

SYS@orcl> SET LINESIZE 200
SYS@orcl> SET PAGESIZE 100

--------------------------------------------------------------------------------
-- [1] (조치 전 상태) 버퍼 캐시가 어떤 풀로 구성돼 있는지 먼저 본다.
--     풀 크기 파라미터를 조회한다.
--------------------------------------------------------------------------------
SYS@orcl> SELECT name, display_value
  2       FROM  v$parameter
  3       WHERE name IN ('db_cache_size','db_keep_cache_size',
  4              'db_recycle_cache_size')
  5       ORDER BY name;

NAME                     DISPLAY_VALUE
----------------------- --------------
db_cache_size           0
db_keep_cache_size      48M
db_recycle_cache_size   0

-- 해석: db_cache_size=0 -> DEFAULT 풀은 ASMM(sga_target>0)이 자동 관리한다.
--   db_keep_cache_size=48M -> KEEP 풀은 명시적으로 48M 설정돼 있다.
--   KEEP/RECYCLE은 자동 조정 대상이 아니라 이렇게 직접 크기를 준다.

--------------------------------------------------------------------------------
-- [2] (이상/오류 -> 원인 -> 조치 -> 재확인)
--     풀별 크기.히트율을 보려다 별칭 buffers로 오류를 낸다.
--------------------------------------------------------------------------------
SYS@orcl> SELECT name, set_msize buffers,
  2         ROUND(set_msize*block_size/1024/1024,1) mb
  3       FROM  v$buffer_pool_statistics
  4       WHERE set_msize > 0;
SELECT name, set_msize buffers,
                       *
ERROR at line 1:
ORA-00904: "BUFFERS": invalid identifier

-- 원인: buffers 별칭이 특정 문맥에서 예약 식별자로 취급돼 충돌했다.
--   에러의 별표(*) 위치가 buffers 별칭을 가리킨다.
-- 조치: 별칭을 예약어와 충돌하지 않는 buf_cnt로 바꿔 재조회한다.
SYS@orcl> SELECT name, set_msize buf_cnt,
  2         ROUND(set_msize*block_size/1024/1024,1) mb,
  3         ROUND(100*(1-physical_reads/
  4               GREATEST(db_block_gets+consistent_gets,1)),2) hit_pct
  5       FROM  v$buffer_pool_statistics
  6       WHERE set_msize > 0;

NAME         BUF_CNT         MB    HIT_PCT
-------- ----------- ---------- ----------
DEFAULT        11268         44        100
DEFAULT       105732        826      99.98
KEEP            5874       45.9        100

-- 재확인: 오류 없이 조회됐다. DEFAULT 풀이 두 줄인 것은 여러 작업 세트
--   (working set)로 버퍼를 관리하기 때문이며, 합치면 약 870MB다.
--   별도로 KEEP 풀이 약 46MB 잡혀 있다(파라미터 48M와 정합).

--------------------------------------------------------------------------------
-- [3] (해석) 히트율이 99.98~100%다. 좋아 보이지만 이것만으로 판단 금지.
--------------------------------------------------------------------------------
SYS@orcl> -- 히트율은 '물리 I/O를 얼마나 피했는가'일 뿐이다. 함께 봐야 할
SYS@orcl> -- 논리 읽기 총량을 V$SYSSTAT로 확인해 둔다(실습 02의 출발점).
SYS@orcl> SELECT name, value
  2       FROM  v$sysstat
  3       WHERE name IN ('session logical reads','physical reads')
  4       ORDER BY name;

NAME                     VALUE
--------------------- ----------
physical reads             75765
session logical reads  374886200

-- 해석: 물리 읽기는 7.5만인데 논리 읽기는 3.7억이 넘는다. 디스크는 거의
--   안 건드렸지만 메모리 안에서 블록을 3.7억 번 읽었다. 히트율이 높은 것과
--   '논리 읽기가 정말 필요했는가'는 별개다. 이 대조를 실습 02에서 판별한다.

--------------------------------------------------------------------------------
-- [정리]
--------------------------------------------------------------------------------
-- 1) 버퍼 캐시는 DEFAULT(약 870MB)와 KEEP(약 46MB, 파라미터 48M)로 구성.
-- 2) 풀별 히트율은 99.98~100%. 그러나 히트율 단독으로 건강을 판정하지 않는다.
-- 3) 조회 별칭도 예약어와 충돌할 수 있다(ORA-00904). 별칭 변경으로 해소.
-- 4) 다음 실습: 논리 읽기 3.7억의 의미(히트율의 함정)를 부하로 재현한다.
-- * 참고: V$PARAMETER.V$BUFFER_POOL_STATISTICS 조회는 라이선스와 무관하다.

SYS@orcl> EXIT
