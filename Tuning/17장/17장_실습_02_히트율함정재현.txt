================================================================================
 17장 실습 02 - 캐시 히트율의 함정 재현 (높은데 응답이 나쁜 상황)
 목표: 대형 테이블을 반복 스캔하는 부하(WL_02_io)를 걸어, 논리 읽기와
       히트율이 함께 오르는데도 응답은 나빠지는 상황을 조치 전.후로
       비교한다. '히트율 상승 = 성능 개선'이 아님을 정량으로 확인한다.
 환경: non-CDB=orcl 19.3. 조회는 SYS, 부하는 업무 계정(SQLT)로 수행.
 주의: 개인 실습 환경 전용. 부하 스크립트는 개인 환경에서만 실행한다.
================================================================================

$ sqlplus / as sysdba

--------------------------------------------------------------------------------
-- [1] (조치 전 상태) 부하를 걸기 전 논리 읽기.물리 읽기.히트율을 캡처한다.
--------------------------------------------------------------------------------
SYS@orcl> SELECT name, value
  2       FROM  v$sysstat
  3       WHERE name IN ('session logical reads','physical reads',
  4              'consistent gets','db block gets')
  5       ORDER BY name;

NAME                     VALUE
--------------------- ----------
consistent gets       374267229
db block gets            618971
physical reads            75765
session logical reads  374886200

SYS@orcl> -- 조치 전 히트율 = 1 - 75,765 / (618,971 + 374,267,229) = 99.98%
SYS@orcl> -- 이 값을 기준선으로 삼는다(baseline).

--------------------------------------------------------------------------------
-- [2] (조치) 대형 테이블을 반복 스캔하는 부하를 60초간 건다.
--     WL_02_io.sql은 인덱스를 타지 않는 대량 스캔을 반복 실행한다.
--------------------------------------------------------------------------------
-- (다른 세션) SQLT 계정에서 부하 스크립트 실행
$ sqlplus sqlt/****@orcl
SQLT@orcl> @WL_02_io.sql
  -- (내부) 대형 테이블 전체를 반복 스캔:
  --   BEGIN FOR i IN 1..<반복수> LOOP
  --     SELECT COUNT(*) INTO n FROM claim_detail;  -- 대량 논리 읽기 유발
  --   END LOOP; END;
  -- 약 60초간 실행. 같은 블록을 몇 번이고 다시 읽는다.
PL/SQL procedure successfully completed.

--------------------------------------------------------------------------------
-- [3] (조치 후 상태) 같은 지표를 다시 캡처해 조치 전과 비교한다.
--------------------------------------------------------------------------------
SYS@orcl> SELECT name, value
  2       FROM  v$sysstat
  3       WHERE name IN ('session logical reads','physical reads')
  4       ORDER BY name;

NAME                     VALUE
--------------------- ----------
physical reads          <환경값>   -- 거의 안 늘어난다(이미 캐시에 상주)
session logical reads   <환경값>   -- 크게 증가한다(반복 스캔으로 폭증)

-- 관찰 포인트(무엇과 무엇을 비교하는가):
--   * 논리 읽기 증가량(조치 후 - 조치 전): 매우 크다.
--   * 물리 읽기 증가량: 거의 0에 가깝다(대상 블록이 이미 캐시에 있음).
--   => 히트율 = 1 - (물리 증가/논리 증가)는 오히려 100%에 더 가까워진다.

--------------------------------------------------------------------------------
-- [3-1] (이상 징후 -> 원인 -> 조치 -> 재확인)
--     조치 후 히트율이 '올라서' 신입 DBA가 성능이 좋아졌다고 오판한다.
--------------------------------------------------------------------------------
SYS@orcl> -- 이상 징후: 부하 후 히트율이 조치 전(99.98%)보다 오히려 100%에
SYS@orcl> --   더 가까워졌다. "반복 스캔을 돌렸더니 히트율이 좋아졌다"고 오판.
SYS@orcl> -- 원인: 반복 읽는 블록이 이미 캐시에 있어 물리 읽기는 안 늘고 논리
SYS@orcl> --   읽기만 폭증했다. 히트율=1-(물리/논리)이므로 오히려 상승한다.
SYS@orcl> -- 조치: 히트율이 아니라 '논리 읽기 증가'와 'CPU 증가'로 다시 판정한다.
SYS@orcl> SELECT name, value FROM v$sysstat
  2       WHERE name IN ('session logical reads','CPU used by sessions')
  3       ORDER BY name;

NAME                      VALUE
--------------------- ----------
CPU used by sessions    <환경값>   -- 조치 전 대비 증가
session logical reads   <환경값>   -- 조치 전 대비 크게 증가

-- 재확인: 히트율 상승과 무관하게 논리 읽기.CPU가 늘었다 -> 성능은 나빠졌다.
--   오판 정정 완료: 히트율 상승은 개선이 아니라 반복 읽기의 부작용이다.

--------------------------------------------------------------------------------
-- [4] (해석) 히트율은 올랐는데 응답.CPU는 나빠졌음을 확인한다.
--------------------------------------------------------------------------------
SYS@orcl> -- 부하 세션이 무엇을 하느라 시간을 썼는지 대기.CPU로 본다.
SYS@orcl> SELECT n.name, s.value
  2       FROM  v$sesstat s JOIN v$statname n ON n.statistic#=s.statistic#
  3       WHERE s.sid=<부하세션SID>
  4         AND n.name IN ('session logical reads','CPU used by this session');

NAME                          VALUE
--------------------------- --------
CPU used by this session     <환경값>   -- 크게 증가
session logical reads        <환경값>   -- 크게 증가

-- 해석: 물리 I/O는 늘지 않아 히트율은 '개선'된 것처럼 보이지만, 논리 읽기
--   폭증만큼 CPU가 소모됐다. 즉 히트율 상승은 성능 개선이 아니라, 비효율
--   반복 읽기의 부작용이다. 판정 지표는 히트율이 아니라 '논리 읽기 증가와
--   CPU 증가'다. 조치 방향은 캐시 확장이 아니라 반복 스캔 SQL의 제거.

--------------------------------------------------------------------------------
-- [정리]
--------------------------------------------------------------------------------
-- 1) 반복 스캔은 논리 읽기만 폭증시키고 물리 읽기는 거의 안 늘린다.
-- 2) 그 결과 히트율은 오히려 100%에 수렴한다(히트율의 함정).
-- 3) 같은 구간의 CPU 사용은 증가 -> 응답은 나빠진다.
-- 4) 판정은 히트율이 아니라 논리 읽기.CPU 증가로 한다. 조치=SQL 수정.
-- * 부하 세션 종료 시 세션 통계는 사라지고, 시스템 통계는 누적으로 남는다.

SYS@orcl> EXIT
