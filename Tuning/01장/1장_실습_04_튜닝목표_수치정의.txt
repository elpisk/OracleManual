================================================================================
 1장 실습 04 — 튜닝 목표를 수치로 정의
 목표: 상위 부하 SQL을 골라 현재값을 측정하고, 목표값·판정 기준을 세운다.
       '절대 buffer_gets 상위'만 보고 대상을 고르는 오판을 재현하고,
       '실행당(gets_per_exec)' 기준으로 교정한다.
 환경: non-CDB=orcl 19.3 (SYS AS SYSDBA로 수행, 대상 스키마 SQLT)
 주의: 개인 실습 환경 전용. 읽기 전용 조회만 수행한다.
================================================================================

$ sqlplus / as sysdba

SYS@orcl> SET LINESIZE 200

--------------------------------------------------------------------------------
-- [1] (조치 전 상태) 업무 계정(SQLT)의 부하 상위 SQL을 논리읽기 기준으로 본다.
--------------------------------------------------------------------------------
SYS@orcl> COLUMN sql_text FORMAT A34
SYS@orcl> SELECT sql_id, executions execs, buffer_gets,
  2         ROUND(buffer_gets/GREATEST(executions,1)) gets_per_exec,
  3         ROUND(elapsed_time/1e6,2) elapsed_sec,
  4         SUBSTR(sql_text,1,34) sql_text
  5       FROM (SELECT sql_id, executions, buffer_gets, elapsed_time, sql_text
  6              FROM v$sql WHERE parsing_schema_name='SQLT'
  7              ORDER BY buffer_gets DESC)
  8       WHERE ROWNUM <= 6;

SQL_ID          EXECS BUFFER_GETS GETS_PER_EXEC ELAPSED_SEC SQL_TEXT
------------- ------- ----------- ------------- ----------- ----------------------------------
3j9gw8s0v82pc     200      618000          3090        1.23 select count(*) from medical_claims
fus9168r58axj       3       19869          6623        0.87 select /*+ full(d) */ count(*) c, s
axnpq1h1y89da       1        4586          4586        0.50 select count(*) from review_log wh
awc0yduv335rq       2        3909          1955        0.31 select count(*) from MEDICAL_CLAIMS
64cvq6trh3hwn       2        3574          1787        0.33 select count(*) from CLAIM_DETAILS
df5j2h8vw7vjx       1        3211          3211        0.44 select count(*) from patients p

--------------------------------------------------------------------------------
-- [2] (이상 징후 → 원인 → 조치)
--     이상 징후: 절대 buffer_gets 1위(3j9gw8s0v82pc, 618,000)만 보고
--       "이게 제일 나쁜 SQL"이라 단정하려 한다.
--------------------------------------------------------------------------------
SYS@orcl> -- 원인 파악: 총 buffer_gets는 '실행 횟수 × 실행당 읽기'다. 1위 SQL은
SYS@orcl> --   200회 실행이라 총량이 큰 것이고, 실행당은 3,090이다. 반면 2위
SYS@orcl> --   fus9168r58axj는 3회 실행인데 실행당 6,623로 더 무겁다.
SYS@orcl> -- 조치: 절대값이 아니라 실행당(gets_per_exec) 기준으로 다시 정렬한다.
SYS@orcl> SELECT sql_id, executions execs, buffer_gets,
  2         ROUND(buffer_gets/GREATEST(executions,1)) gets_per_exec
  3       FROM (SELECT sql_id, executions, buffer_gets
  4              FROM v$sql WHERE parsing_schema_name='SQLT'
  5              ORDER BY buffer_gets/GREATEST(executions,1) DESC)
  6       WHERE ROWNUM <= 3;

SQL_ID          EXECS BUFFER_GETS GETS_PER_EXEC
------------- ------- ----------- -------------
fus9168r58axj       3       19869          6623
axnpq1h1y89da       1        4586          4586
df5j2h8vw7vjx       1        3211          3211

-- 재확인(교정): 실행당 기준 1위는 fus9168r58axj(6,623)다. 다만 이 SQL은
--   3회만 실행됐다. 대상 선정은 '실행당 무게 × 실행 빈도(전체 부하 기여)'를
--   함께 본다. 자주 돌면서(200회) 실행당도 무거운(3,090) 3j9gw8s0v82pc가
--   전체 DB Time 기여로는 유력한 후보다. 절대값 하나로 단정하지 않는 것이 핵심.

--------------------------------------------------------------------------------
-- [3] (목표 수치화 4단계) 대상: 3j9gw8s0v82pc
--------------------------------------------------------------------------------
-- (1) 대상 선정 : 3j9gw8s0v82pc (200회 실행, 실행당 3,090 gets, 1.23초)
-- (2) 현재값    : 실행당 논리읽기 3,090 gets / 총 elapsed 1.23초
-- (3) 목표값    : 실행당 논리읽기를 3,090 → <목표값>(예: 1/3 수준)로 축소
--                 또는 실행당 응답시간을 현재 <환경값>초 → 0.3초 이내로
-- (4) 판정 기준 : 조치 후 같은 방식(buffer_gets/executions)으로 재측정해
--                 실행당 값이 목표 이하인지로 성공/실패를 판정
-- ※ 절대 수치를 그대로 목표로 박지 않는다(실행횟수·데이터량·캐시 상태 의존).
--   "무엇을(실행당 논리읽기) 무엇과 비교해(현재값) 어느 수준으로(목표값)"로 서술.

--------------------------------------------------------------------------------
-- [4] (조치 후 관점) 다음 단계로의 인계 기준
--------------------------------------------------------------------------------
-- * 이 SQL의 실행계획을 다시 쓰는 것으로 결론 나면 → SQL 튜닝 과정으로 인계.
-- * 시스템·인스턴스 차원(버퍼 캐시·공유 풀 등) 조치면 → 해당 챕터(17·18장).
-- * 이 과정의 종착점: "어느 SQL이, 어떤 대기로, DB Time의 몇 %를 쓰는가"까지.

--------------------------------------------------------------------------------
-- [정리]
--------------------------------------------------------------------------------
-- 1) 대상 선정은 절대 총량이 아니라 실행당 값 + 실행 빈도로 함께 본다.
-- 2) 목표는 반드시 수치로: 현재값 → 목표값 → 재측정 판정 기준.
-- 3) 목표 없이 파라미터부터 바꾸는 것은 이 장이 경계하는 대표 함정이다.
-- ※ 참고: V$SQL 조회는 관리 팩 라이선스가 필요 없다.

SYS@orcl> EXIT
