 8장 실습 04 — SQL ordered by Elapsed/Gets/Reads 에서 대상 SQL 선별
 목표: 진단 가설(CPU 바운드 + 대량 논리읽기)에 맞는 정렬 기준을 골라 주범 SQL을
       특정한다. 두 정렬이 같은 SQL을 지목할 때 신뢰도가 높음을 확인한다.
       Reads 정렬을 무작정 1순위로 보는 오판을 교정한다.
 환경: non-CDB=orcl 19.3 (SYS AS SYSDBA)
 부하: WL_06_mixed.sql (7세션). 보고서 awrrpt_1_295_296.txt 사용.
 라이선스: 🔒 Diagnostics Pack. 미보유 시 V$SQL 정렬로 대체(하단).
================================================================================

$ sqlplus / as sysdba

SYS@orcl> SET LINESIZE 200
SYS@orcl> SET PAGESIZE 100

--------------------------------------------------------------------------------
-- [1] (조치 전 상태) SQL ordered by Elapsed Time 발췌.
--------------------------------------------------------------------------------
SYS@orcl> HOST sed -n '210,220p' awrrpt_1_295_296.txt

SQL ordered by Elapsed Time                 DB/Inst: ORCL/orcl  Snaps: 295-296
-> Captured SQL account for   34.6% of Total DB Time (s):             574

        Elapsed                  Elapsed Time
        Time (s)    Executions  per Exec (s)  %Total   %CPU    %IO    SQL Id
---------------- -------------- ------------- ------ ------ ------ -------------
           190.6          5,912          0.03   33.2   95.8     .0 9vmszgd1ft9x0
Module: C:\Users\itwill\AppData\Local\Programs\Python\Py

-- 해석: 맨 위 SQL 9vmszgd1ft9x0이 혼자 전체 DB Time의 33.2%를 썼고, 그 시간의
--   95.8%가 CPU다(%IO 0). 실습 03의 DB CPU 95.7%와 맞아떨어진다 → 인스턴스를
--   CPU 바운드로 만든 주범이다. 실행 5,912회 × 0.03초 = 가벼운 SQL을 대량 반복.

--------------------------------------------------------------------------------
-- [2] (조회) SQL ordered by Gets 발췌 — 같은 SQL인가?
--------------------------------------------------------------------------------
SYS@orcl> HOST sed -n '265,275p' awrrpt_1_295_296.txt

SQL ordered by Gets                         DB/Inst: ORCL/orcl  Snaps: 295-296
-> Total Buffer Gets:     122,836,337

     Buffer                 Gets              Elapsed
      Gets   Executions   per Exec   %Total   Time (s)  %CPU   %IO    SQL Id
----------- ----------- ------------ ------ ---------- ----- ----- -------------
 39,149,973       5,912      6,622.1   31.9      190.6  95.8     0 9vmszgd1ft9x0
Module: C:\Users\itwill\AppData\Local\Programs\Python\Py

-- 해석: Gets 정렬에서도 9vmszgd1ft9x0이 1위. 전체 논리읽기 1억2,283만 중
--   3,914만(31.9%)을 이 SQL이 읽었다. 실습 02의 Logical read 1,185,107/s의
--   정체가 이 SQL임이 확정된다. 실행당 6,622블록 × 5,912회.

--------------------------------------------------------------------------------
-- [3] (해석) 두 정렬이 같은 SQL을 지목 → 진단 신뢰도가 높다.
--------------------------------------------------------------------------------
-- Elapsed(33.2%)와 Gets(31.9%)가 모두 9vmszgd1ft9x0을 1위로, %CPU 95.8%가
--   Top Events DB CPU 95.7%와 일치. 서로 다른 섹션의 숫자가 한 SQL로 수렴한다.
-- 여기까지가 8장(인스턴스 층위)의 결론이다: '9vmszgd1ft9x0이 DB Time 33%·
--   논리읽기 32%를 대부분 CPU로 쓴다.' 이 SQL의 재작성(인덱스·조인·바인드)은
--   SQL 튜닝 과정으로 인계한다.

--------------------------------------------------------------------------------
-- [4] (조회) Captured SQL 비중이 34.6%뿐인 이유를 확인한다.
--------------------------------------------------------------------------------
SYS@orcl> SELECT 34.6 AS captured_pct, 33.2 AS top1_pct,
  2         ROUND(34.6-33.2,1) AS rest_captured FROM dual;

CAPTURED_PCT  TOP1_PCT REST_CAPTURED
------------ --------- -------------
        34.6      33.2           1.4

-- 해석: 1위가 33.2%인데 캡처 전체가 34.6% → 나머지 SQL의 캡처분은 1.4%뿐.
--   리터럴 SQL은 문장마다 SQL_ID가 달라 개별로는 순위에 못 들고 흩어진다.
--   이 조합 자체가 '리터럴이 조각나 있다'는 또 하나의 증거다.

--------------------------------------------------------------------------------
-- [5] (이상 징후 → 원인 → 조치 → 재확인)
--     이상 징후: 신입이 "SQL ordered by Reads(물리읽기) 1위를 튜닝하자"며
--       엉뚱한 SQL을 대상으로 골랐다.
--------------------------------------------------------------------------------
-- 원인 파악: 정렬 기준을 진단 가설에 맞추지 않은 오판이다. 이 구간은 물리
--   읽기가 48.8/s로 미미하다(실습 02) → Reads 정렬은 우선순위가 낮다.
SYS@orcl> HOST sed -n '330,338p' awrrpt_1_295_296.txt

SQL ordered by Reads                        DB/Inst: ORCL/orcl  Snaps: 295-296
-> Total Disk Reads:              4,880
   Physical Reads  Executions  Reads per Exec  %Total  ... SQL Id
   -------------- ----------- --------------- ------- ...
              612          54           11.33    12.5  ... a1b2c3xxxxxxx

-- 원인 확정: Reads 1위(a1b2c3...)는 물리읽기 612블록으로, Total Disk Reads가
--   4,880에 불과한 작은 세계다. 이 SQL을 고쳐도 DB Time에 거의 영향이 없다.
-- 조치: 진단 가설(CPU·논리읽기)에 맞는 Elapsed/Gets 정렬로 되돌려 주범
--   9vmszgd1ft9x0을 대상으로 삼는다.
-- 재확인: 9vmszgd1ft9x0은 DB Time 33.2%, Reads 1위는 DB Time 기여 미미 →
--   대상 선정 교정 완료.

--------------------------------------------------------------------------------
-- [대안 경로] 🔒 미보유 — V$SQL을 정렬해 같은 SQL을 찾는다.
--------------------------------------------------------------------------------
SYS@orcl> SELECT sql_id, buffer_gets, cpu_time, elapsed_time, executions
  2       FROM  v$sql
  3       ORDER BY buffer_gets DESC FETCH FIRST 5 ROWS ONLY;

SQL_ID        BUFFER_GETS   CPU_TIME  ELAPSED_TIME EXECUTIONS
------------- ----------- ---------- ------------- ----------
9vmszgd1ft9x0    <환경값>   <환경값>      <환경값>    <환경값>
...

-- 해석: V$SQL을 buffer_gets/elapsed_time 기준으로 정렬하면 AWR SQL 섹션과
--   같은 상위 SQL을 얻는다(단 캐시에 남아있는 커서 한정). 라이선스 없이도
--   대상 SQL 선별은 가능하다.

--------------------------------------------------------------------------------
-- [정리]
--------------------------------------------------------------------------------
-- 1) 정렬 기준은 진단 가설에 맞춘다: CPU·논리읽기→Elapsed/Gets, 디스크→Reads.
-- 2) 실측: 9vmszgd1ft9x0이 Elapsed·Gets 모두 1위(%CPU 95.8%) → 주범 확정.
-- 3) 두 정렬이 같은 SQL로 수렴 + Top Events와 일치 → 신뢰도 높음.
-- 4) Captured 34.6%뿐 = 리터럴이 조각나 순위 밖에 흩어진 증거.
-- 5) Reads 1위를 무작정 고르면 오판 → 물리읽기가 작은 구간에선 부적합.
-- 6) 라이선스 없으면 V$SQL 정렬로 대상 선별 가능.

SYS@orcl> EXIT
