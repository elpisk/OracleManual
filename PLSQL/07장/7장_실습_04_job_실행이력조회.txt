[5] 실행 시간 추세를 초 단위로 본다

SQL> SELECT job_name,
  2         TO_CHAR(actual_start_date,'MM-DD HH24:MI:SS') AS started,
  3         run_duration,
  4         EXTRACT(HOUR   FROM run_duration) * 3600
  5       + EXTRACT(MINUTE FROM run_duration) * 60
  6       + EXTRACT(SECOND FROM run_duration) AS sec
  7    FROM user_scheduler_job_run_details
  8   ORDER BY log_date DESC FETCH FIRST 8 ROWS ONLY;

JOB_NAME        STARTED        RUN_DURATION           SEC
--------------- -------------- --------------- ----------
J_SLOW          08-19 13:22:11 +000 00:00:08             8
J_SLOW          08-19 13:21:36 +000 00:00:08             8
J_DEMO_HOURLY   08-19 13:14:03 +000 00:00:00             0
J_NOISY         08-19 11:05:41 +000 00:00:01             1
J_NOISY         08-19 11:05:12 +000 00:00:00             0
J_DEMO_HOURLY   08-19 11:14:03 +000 00:00:00             0
J_DEPT_REPORT   08-19 10:36:01 +000 00:00:00             0
J_DEPT_REPORT   08-19 10:34:01 +000 00:00:00             0

-- RUN_DURATION 은 INTERVAL DAY TO SECOND 타입이라 정렬·비교가 번거롭다.
-- EXTRACT 로 초 단위 숫자로 바꿔 두면 리포트 작성이 쉬워진다.

-- 지연도 함께 본다. 예정 시각과 실제 시각의 차이가 지연이다.

SQL> SELECT job_name,
  2         TO_CHAR(req_start_date,'HH24:MI:SS')    AS req_start,
  3         TO_CHAR(actual_start_date,'HH24:MI:SS') AS act_start,
  4         EXTRACT(SECOND FROM (actual_start_date - req_start_date)) AS delay_sec
  5    FROM user_scheduler_job_run_details
  6   WHERE req_start_date IS NOT NULL
  7   ORDER BY log_date DESC FETCH FIRST 3 ROWS ONLY;

JOB_NAME        REQ_START ACT_START  DELAY_SEC
--------------- --------- --------- ----------
J_DEMO_HOURLY   13:14:03  13:14:03           0
J_DEMO_HOURLY   12:14:03  12:14:04           1
J_DEMO_HOURLY   11:14:03  11:14:03           0

-- 지연이 계속 커진다면 슬레이브 부족이나 자원 경합을 의심한다.

[8] 운영 점검 질의 — 최근 24시간 요약

SQL> SELECT owner, job_name,
  2         COUNT(*)                                                AS runs,
  3         SUM(CASE WHEN status = 'SUCCEEDED' THEN 1 ELSE 0 END)   AS ok,
  4         SUM(CASE WHEN status = 'FAILED'    THEN 1 ELSE 0 END)   AS ng,
  5         MAX(TO_CHAR(log_date,'MM-DD HH24:MI'))                  AS last_run
  6    FROM dba_scheduler_job_run_details
  7   WHERE owner = 'HR'
  8     AND log_date > SYSTIMESTAMP - INTERVAL '1' DAY
  9   GROUP BY owner, job_name ORDER BY ng DESC, job_name;

OWNER    JOB_NAME              RUNS        OK        NG LAST_RUN
-------- --------------------- ----- --------- --------- ----------
HR       J_DEMO_HOURLY             4         4         0 08-19 13:14
HR       J_DEPT_REPORT             2         2         0 08-19 10:36
HR       J_SLOW                    2         2         0 08-19 13:22

-- 이 질의를 하루 한 번 도는 Job 으로 등록하면 그것이 CHECK_JOB_STATUS 다.

 정리
--------------------------------------------------------------------------------
 1. 컬럼명을 추측하면 ORA-00904 가 난다. USER_TAB_COLUMNS 로 목록을 먼저 본다.
    상태는 STATUS, 시각은 LOG_DATE, 오류 번호는 ERROR# 다.
 2. 비동기 실행 직후 이력이 비어 있는 것은 실패가 아니라 진행 중이라는 뜻이다.
    USER_SCHEDULER_RUNNING_JOBS 를 먼저 확인하고 몇 초 뒤 재조회한다.
 3. JOB_LOG 는 사건(RUN·ENABLE·DISABLE·UPDATE)을, JOB_RUN_DETAILS 는
    실행 결과(STATUS·ERROR#·RUN_DURATION)를 기록한다.
 4. logging_level 을 LOGGING_FULL 로 두면 상태 변경까지 JOB_LOG 에 남는다.
 5. RUN_DURATION 은 INTERVAL 타입이므로 EXTRACT 로 초 단위로 환산해 쓴다.
    REQ_START_DATE 와 ACTUAL_START_DATE 의 차이가 지연이다.
 6. 로그 보존 기본값은 30일이며 LOG_HISTORY 전역 속성으로 조정한다.
    PURGE_LOG 로 특정 Job 의 로그만 즉시 지울 수도 있다.
 7. DBA_ 계열 뷰는 관리 계정에서 조회하거나 필요한 뷰만 직접 GRANT 받는다.
