================================================================================
 31장 실습 01 — 성능 관리 활동 및 계획 고려사항 확인
 목표: 사전 예방적/사후 대응적 튜닝의 개념을 정리하고, 성능 진단 인프라의
       전제 조건인 STATISTICS_LEVEL 을 확인한다. BASIC 상태의 오류를 재현하고
       TYPICAL 로 되돌려 AWR/ADDM 이 동작하도록 만든다.
 환경: CDB=cdb1 (루트 컨테이너에서 수행)
================================================================================

-- [1] 성능 진단 인프라가 동작하기 위한 핵심 전제부터 확인한다.
$ sqlplus sys@cdb1 as sysdba

SYS@cdb1> SET LINESIZE 160
SYS@cdb1> SHOW PARAMETER statistics_level

NAME                                 TYPE        VALUE
------------------------------------ ----------- ------------------------------
statistics_level                     string      TYPICAL

-- TYPICAL 이면 AWR 자동 수집과 ADDM 이 정상 동작한다(권장 기본값).

--------------------------------------------------------------------------------
-- [2] 현재 AWR 수집 설정(간격/보존)과 최근 스냅샷 존재 여부를 확인한다.
--------------------------------------------------------------------------------
SYS@cdb1> COLUMN snap_interval FORMAT A20
SYS@cdb1> COLUMN retention     FORMAT A20
SYS@cdb1> SELECT snap_interval, retention FROM dba_hist_wr_control;

SNAP_INTERVAL        RETENTION
-------------------- --------------------
+00000 01:00:00.0    +00008 00:00:00.0

-- 기본 간격 60분, 기본 보존 8일. 성능 통계가 상시 축적되므로 사후 대응이 가능하다.

SYS@cdb1> SELECT COUNT(*) AS snap_cnt FROM dba_hist_snapshot;

  SNAP_CNT
----------
        48

--------------------------------------------------------------------------------
-- [3] (오류 → 원인 → 수정)
--     성능 오버헤드를 줄이겠다며 STATISTICS_LEVEL 을 BASIC 으로 낮췄더니
--     스냅샷이 더 이상 생성되지 않는 상황을 재현한다.
--------------------------------------------------------------------------------
SYS@cdb1> ALTER SYSTEM SET statistics_level = BASIC SCOPE=BOTH;

System altered.

SYS@cdb1> -- BASIC 상태에서 수동 스냅샷을 시도한다.
SYS@cdb1> EXEC DBMS_WORKLOAD_REPOSITORY.CREATE_SNAPSHOT;
BEGIN DBMS_WORKLOAD_REPOSITORY.CREATE_SNAPSHOT; END;

*
ERROR at line 1:
ORA-13541: system moving window baseline size greater than retention
ORA-06512: at "SYS.DBMS_WORKLOAD_REPOSITORY", line 878
ORA-13516: AWR Operation failed: SNAP_ID not found
ORA-06512: at line 1

SYS@cdb1> -- 원인 파악: STATISTICS_LEVEL=BASIC 이면 AWR 자동 통계 수집이 비활성화되어
SYS@cdb1> --   스냅샷을 만들 수 없고, ADDM 등 상위 진단 기능이 모두 멈춘다.
SYS@cdb1> SHOW PARAMETER statistics_level

NAME                                 TYPE        VALUE
------------------------------------ ----------- ------------------------------
statistics_level                     string      BASIC

SYS@cdb1> -- 수정: TYPICAL 로 되돌린다(오버헤드 최소 + 대부분의 진단 통계 수집).
SYS@cdb1> ALTER SYSTEM SET statistics_level = TYPICAL SCOPE=BOTH;

System altered.

SYS@cdb1> -- 다시 수동 스냅샷을 생성한다.
SYS@cdb1> EXEC DBMS_WORKLOAD_REPOSITORY.CREATE_SNAPSHOT;

PL/SQL procedure successfully completed.

SYS@cdb1> SELECT snap_id, end_interval_time
  2       FROM  dba_hist_snapshot
  3      ORDER BY snap_id DESC FETCH FIRST 1 ROWS ONLY;

   SNAP_ID END_INTERVAL_TIME
---------- ---------------------------------------------------------------------
        49 22-JUL-26 10.31.44.000 AM

-- 새 스냅샷(49)이 정상 생성되었다. 인프라가 다시 살아났다.

--------------------------------------------------------------------------------
-- [4] 사전 예방적 vs 사후 대응적 튜닝을 데이터로 이해한다.
--     상시 축적된 스냅샷이 있어야 '어제 그 시간'을 사후에 재구성할 수 있다.
--------------------------------------------------------------------------------
SYS@cdb1> SELECT MIN(begin_interval_time) AS oldest,
  2              MAX(end_interval_time)   AS newest
  3       FROM  dba_hist_snapshot;

OLDEST                              NEWEST
----------------------------------- -----------------------------------
20-JUL-26 10.00.00 AM               22-JUL-26 10.31.44 AM

-- 이 구간 안의 문제라면 사후 대응(reactive)으로도 데이터를 확보할 수 있다.
-- 반대로 이 구간을 벗어난 과거는 데이터가 없어 진단이 불가능하다 → 사전 예방(proactive)
-- 관점에서 보존 기간을 충분히 잡아 두는 것이 중요하다.

--------------------------------------------------------------------------------
-- [정리]
--------------------------------------------------------------------------------
-- 1) 성능 진단 인프라(AWR/ADDM)의 전제는 STATISTICS_LEVEL = TYPICAL 또는 ALL.
-- 2) BASIC 으로 낮추면 스냅샷 자체가 생성되지 않아 진단이 불가능해진다.
-- 3) 사후 대응의 성패는 '평소에 데이터를 얼마나 확보해 두었는가'가 좌우한다.
-- 4) 성숙한 운영은 사후 대응 비중을 줄이고 추세 기반 사전 예방으로 무게중심을 옮긴다.

SYS@cdb1> EXIT
