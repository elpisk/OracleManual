-- 1장 실습_03: 데이터베이스 샤딩(Sharding) 개념 확인

- 이 실습의 목적 두 가지:
-   (1) '왜 샤딩이 필요한가' - 단일 인스턴스에 대용량 OLTP 부하가 몰리는 상황을 확인
-   (2) '샤딩은 어떻게 다루는가' - 샤딩된 SDB는 일반 SQL*Plus DDL이 아니라
-       GDSCTL 유틸리티로 샤드 카탈로그/디렉터/샤드를 프로비저닝해야 함을 확인

======================================================================
[Part 1] 단일 인스턴스에 대용량 OLTP 부하가 몰리는 상황 확인 (샤딩 동기)
======================================================================

- 현재는 단일 인스턴스(cdb1)/단일 데이터베이스 구성임을 확인
SYS@cdb1> select instance_name, host_name, status from v$instance;

INSTANCE_NAME    HOST_NAME            STATUS
---------------- -------------------- ------------
cdb1             dbsvr                OPEN

- RAC(다중 인스턴스)가 아님을 전역 뷰 GV$INSTANCE로 확인: 인스턴스가 단 1개
SYS@cdb1> select inst_id, instance_name, status from gv$instance order by inst_id;

   INST_ID INSTANCE_NAME    STATUS
---------- ---------------- ------------
         1 cdb1             OPEN

- 대용량 주문 테이블(단일 DB에 약 8억 행) - 하나의 인스턴스가 모든 부하를 감당 중
SYS@cdb1> alter session set container = salespdb;

Session altered.

SYS@salespdb> select count(*) from sales_app.orders;

  COUNT(*)
----------
 812345678

- 루트로 복귀 후 현재 부하 지표 확인 (V$SYSMETRIC, 60초 시스템 메트릭 group_id=2)
SYS@salespdb> alter session set container = cdb$root;

Session altered.

SYS@cdb1> select metric_name, round(value,1) as value
  2  from   v$sysmetric
  3  where  metric_name in ('Average Active Sessions',
  4                         'Host CPU Utilization (%)',
  5                         'Database CPU Time Ratio')
  6  and    group_id = 2
  7  order  by metric_name;

METRIC_NAME                                             VALUE
-------------------------------------------------- ----------
Average Active Sessions                                  48.7
Database CPU Time Ratio                                  91.3
Host CPU Utilization (%)                                 96.4

- 해석: 단일 인스턴스가 CPU 96%/활성세션 48로 사실상 포화 상태.
-   서버 증설(수직 확장)만으로는 한계 -> 데이터를 여러 독립 DB로 '수평 분할'하는 샤딩 검토 대상.

======================================================================
[Part 2] 일반 CDB에서 샤딩 기능을 SQL로 직접 쓸 수 없음을 확인 (실수 -> 오류 -> 원인)
======================================================================

- (실수) 일반 CDB(cdb1)의 PDB 안에서 곧바로 샤디드 테이블을 만들려고 시도
SYS@cdb1> alter session set container = salespdb;

Session altered.

SYS@salespdb> create sharded table customers
  2  ( id      number not null,
  3    name    varchar2(60),
  4    region  varchar2(20),
  5    constraint pk_customers primary key (id) )
  6  partition by consistent hash (id) partitions auto;
create sharded table customers
*
ERROR at line 1:
ORA-43853: SHARDED or DUPLICATED clause is not allowed in a database that is
not a shard catalog or a shard database

- 원인: SHARDED/DUPLICATED 테이블은 GDSCTL로 배포된 '샤디드 데이터베이스(SDB)'
-   안에서만 생성 가능. 지금 cdb1은 일반 CDB이므로 샤딩 DDL이 거부됨.
- 결론: 샤딩은 SQL*Plus DDL이 아니라, 먼저 GDSCTL로 샤드 카탈로그 + 샤드 디렉터(GSM)
-   + 샤드들을 프로비저닝한 뒤에야 사용할 수 있다. -> Part 3에서 GDSCTL로 확인.
SYS@salespdb> exit
Disconnected from Oracle Database 19c Enterprise Edition Release 19.0.0.0.0 - Production
Version 19.3.0.0.0

======================================================================
[Part 4] RAC / 멀티테넌트 / 샤딩 아키텍처 비교 정리
======================================================================

- RAC           : 하나의 데이터베이스를 여러 인스턴스가 '공유(shared storage)'
-                 -> 고가용성 + 수직에 가까운 확장 (클러스터웨어 Grid Infrastructure 필요)
- 멀티테넌트(CDB): 여러 애플리케이션 DB(PDB)를 하나의 인스턴스로 통합하되 PDB 단위로 격리
-                 -> 통합(consolidation) + 관리 효율 (패치/업그레이드 1회로 전체 적용)
- 샤딩(SDB)     : 데이터를 여러 독립 DB(샤드)로 '수평 분할(shared-nothing)'
-                 -> 초대규모 OLTP의 선형 확장 + 결함 격리 (클러스터웨어 불필요)
-                 -> 구성요소: 샤드 카탈로그 + 샤드 디렉터(GSM) + 샤드 + 글로벌 서비스
-                 -> 구성/관리 도구: SQL*Plus가 아닌 GDSCTL 유틸리티
-
- 핵심 대비: RAC = 공유(shared) 아키텍처  /  샤딩 = 무공유(shared-nothing) 아키텍처
-   세 가지는 지향점(고가용성 / 통합·격리 / 수평 확장)이 다르며,
-   요구사항에 따라 단독으로 또는 조합하여 사용한다.
[oracle@shcat ~]$
