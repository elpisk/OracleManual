- CDB1 루트에 SYSDBA로 접속된 상태에서 시작
SYS@cdb1> show con_name

CON_NAME
------------------------------
CDB$ROOT

======================================================================
[1단계] PMAN / RECO / LREG 프로세스 존재 확인
======================================================================

- 세 프로세스가 기동되어 있는지 V$BGPROCESS로 확인
SYS@cdb1> select name, description from v$bgprocess
  2  where name in ('PMAN','RECO','LREG') and paddr <> '00'
  3  order by name;

NAME  DESCRIPTION
----- ----------------------------------------------------------------
LREG  Listener Registration
PMAN  process manager
RECO  distributed recovery

======================================================================
[2단계] PMAN: 관리 대상(공유 서버/디스패처/DRCP/잡) 관점 확인
======================================================================

- PMAN이 관리하는 풀링된 서버 프로세스가 현재 있는지 확인
-   현재 전용 서버 구성이라 공유 서버/디스패처는 없음 (0 rows)
SYS@cdb1> select name, status from v$shared_server;

no rows selected

- DRCP(데이터베이스 상주 연결 풀) 상태도 PMAN 관할. 현재 비활성 상태 확인
SYS@cdb1> select connection_pool, status, num_open_servers, num_busy_servers
  2  from v$cpool_stats;

no rows selected

- 해석: PMAN은 상시 대기하다가 공유 서버/디스패처/DRCP/잡 프로세스가 필요해지면
-   그때 생성·감시·정리함. 현재 전용 서버 구성이라 관리 대상이 비어 있음.

======================================================================
[3단계] RECO: 미해결 분산 트랜잭션 조회 (DBA_2PC_PENDING)
======================================================================

- 2단계 커밋 도중 미해결(in-doubt) 상태로 남은 분산 트랜잭션이 있는지 확인
-   RECO가 자동으로 해결하므로 평소에는 대개 0건
SYS@cdb1> select local_tran_id, global_tran_id, state, mixed
  2  from   dba_2pc_pending;

no rows selected

- 분산 트랜잭션 상대 노드 정보도 함께 확인 (역시 미해결 건이 없어 0건)
SYS@cdb1> select local_tran_id, in_out, database, dbid
  2  from   dba_2pc_neighbors;

no rows selected

- RECO 프로세스가 실제로 세션을 잡고 살아 있는지 교차 확인
SYS@cdb1> select p.spid, s.program
  2  from   v$session s join v$process p on s.paddr = p.addr
  3  where  s.program like '%(RECO)%';

SPID        PROGRAM
----------- ------------------------------------------------
3040        oracle@dbsvr (RECO)

======================================================================
[4단계] LREG: 리스너 서비스 등록 확인 (ALTER SYSTEM REGISTER)
======================================================================

- LREG가 등록한 현재 서비스 목록 확인 (인스턴스가 리스너에 알린 서비스들)
SYS@cdb1> select name, con_id from v$active_services
  2  where con_id in (1,3) order by con_id, name;

NAME                           CON_ID
------------------------------ ----------
SYS$BACKGROUND                          1
SYS$USERS                               1
cdb1                                    1
cdb1XDB                                 1
salespdb                                3

- (실수) 즉시 서비스 재등록을 하려다 명령어를 잘못 입력 (REGISTER 오타)
SYS@cdb1> alter system regsiter;
alter system regsiter
             *
ERROR at line 1:
ORA-00940: invalid ALTER command

- 원인: REGISTER 철자 오류(regsiter). 올바른 키워드로 재시도
-   ALTER SYSTEM REGISTER는 LREG가 리스너에 서비스를 '즉시' 재등록하도록 강제함
-   (평소 LREG는 약 60초 주기로 등록하는데, 리스너 재기동 후 대기 없이 바로 등록할 때 유용)
SYS@cdb1> alter system register;

System altered.

- [정리] PMAN/RECO/LREG 확인 완료:
-   PMAN = 공유서버/디스패처/DRCP/잡 등 풀링된 프로세스 관리(현재는 관리 대상 없음)
-   RECO = 분산 트랜잭션 in-doubt 자동 해결, DBA_2PC_PENDING/DBA_2PC_NEIGHBORS로 조회
-   LREG = 리스너에 서비스 동적 등록(과거 PMON 역할이 12c에서 분리), ALTER SYSTEM REGISTER로 즉시 등록
SYS@cdb1>
