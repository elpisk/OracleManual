[1] 시나리오 개요
--------------------------------------------------------------------------------
-- 입사일(hire_date) 로 연도별 RANGE 파티션 테이블을 만든다.
-- RANGE 는 가장 많이 쓰이는 방식이다. 날짜로 자르는 이력·로그·거래 테이블이 전부 이것이다.
--
-- 목표
--   (1) CREATE TABLE ... PARTITION BY RANGE 구문을 손에 익힌다
--   (2) 파티션 정보를 어느 딕셔너리에서 보는지 외운다
--       dba_part_tables / dba_tab_partitions / dba_part_key_columns
--   (3) 파티션 하나가 세그먼트 하나임을 확인한다 (그리고 8MB 라는 사실을 만난다)
--   (4) PARTITION (이름) · PARTITION FOR (값) 로 한 파티션만 조회한다
--   (5) 프루닝이 되는 계획과 안 되는 계획을 나란히 본다
-- 작업 유형 : 구조 확인

[3] 초기 상태 확인 — RANGE 파티션 테이블 생성
--------------------------------------------------------------------------------
-- VALUES LESS THAN 은 "미만" 이다. 경계값 자신은 다음 파티션으로 간다.
-- 마지막 MAXVALUE 파티션이 없으면 범위를 넘는 값은 INSERT 가 실패한다([6] 에서 확인).
-- CREATE TABLE ... AS SELECT 로 만들면서 데이터까지 한 번에 넣는다.

SYS@orcl> CREATE TABLE hr.emp_yr
  2  PARTITION BY RANGE (hire_date)
  3  (PARTITION p2004 VALUES LESS THAN (TO_DATE('2005-01-01','YYYY-MM-DD')),
  4   PARTITION p2005 VALUES LESS THAN (TO_DATE('2006-01-01','YYYY-MM-DD')),
  5   PARTITION p2006 VALUES LESS THAN (TO_DATE('2007-01-01','YYYY-MM-DD')),
  6   PARTITION pmax  VALUES LESS THAN (MAXVALUE))
  7  TABLESPACE users
  8  AS SELECT employee_id, last_name, salary, hire_date, department_id FROM hr.employees;

Table created.

--------------------------------------------------------------------------------

  2  FROM   dba_segments WHERE owner='HR' AND segment_name='EMP_YR'

SEGMENT_NA PARTITIO SEGMENT_TYPE               KB     BLOCKS    EXTENTS
---------- -------- ------------------ ---------- ---------- ----------
EMP_YR     P2004    TABLE PARTITION          8192       1024          1
EMP_YR     P2005    TABLE PARTITION          8192       1024          1
EMP_YR     P2006    TABLE PARTITION          8192       1024          1
EMP_YR     PMAX     TABLE PARTITION          8192       1024          1

-- 파티션 하나가 세그먼트 하나다. segment_type 이 TABLE PARTITION 으로 나온다.
--
-- 여기서 눈에 걸리는 숫자가 있다. 파티션마다 8192KB(8MB) · 1024블록 · 익스텐트 1개다.
-- 107건짜리 테이블이 32MB 를 잡았다. USERS 는 초기 익스텐트 64KB 의 AUTOALLOCATE 인데도 그렇다.
-- 이유는 숨은 파라미터다.
--
--   _partition_large_extents = TRUE   (12c 이후 기본값)
--     파티션 세그먼트의 첫 익스텐트를 8MB 로 잡는다. 대용량 스캔 성능을 위한 기본값이다.
--   _index_partition_large_extents = FALSE
--     인덱스 파티션은 해당되지 않는다 (실습 09 에서 확인한다)
--
-- 운영에서 의미하는 것
--   · 파티션 100개를 만들면 데이터가 없어도 800MB 를 먼저 잡는다
--   · 월별 파티션을 5년치 미리 만들어 두는 설계는 용량 계획을 다시 해야 한다
--   · 작은 파티션이 많은 설계라면 테이블스페이스를 UNIFORM SIZE 로 만들거나
--     세그먼트 생성을 늦추는(deferred) 쪽을 검토한다 (실습 03 에서 다룬다)

-- 이제 파티션 하나만 조회해 본다.

[8] 실무 포인트
--------------------------------------------------------------------------------
-- 1. 파티션 정보를 보는 딕셔너리 네 개만 외운다.
--      dba_part_tables        방식(RANGE/LIST/HASH) · 파티션 수 · 기본 테이블스페이스
--      dba_tab_partitions     파티션별 경계값 · 통계 · 테이블스페이스 · LOGGING
--      dba_tab_subpartitions  서브파티션 (실습 05)
--      dba_part_key_columns   파티션 키 컬럼과 순서   (서브파티션은 dba_subpart_key_columns)
--    인덱스는 dba_part_indexes / dba_ind_partitions 다 (실습 09·10).
--
-- 2. high_value 는 LONG 이다. WHERE 에 쓸 수 없고 SUBSTR 도 안 된다.
--    스크립트에서 다뤄야 하면 PL/SQL 변수로 받거나 XMLTYPE(dbms_xmlgen) 을 쓴다.
--
-- 3. 파티션 개수만큼 세그먼트가 생기고, 기본값으로 각각 8MB 를 먼저 잡는다.
--    "파티션을 잘게 쪼개면 좋다" 는 직관은 용량과 재귀 호출 비용 때문에 틀릴 수 있다.
--    파티션 하나가 최소 수십만 건 이상은 되도록 설계한다.
--
-- 4. MAXVALUE 파티션은 안전장치이자 함정이다.
--    안전장치 : ORA-14400 을 막는다
--    함정     : 미래 데이터가 전부 그 하나에 쌓여 프루닝 효과가 사라진다
--    정기적으로 SPLIT 해서 잘라 내는 절차를 함께 만들어야 한다 (실습 06).
--
-- 5. 이 실습에서 본 오류
--    ORA-02149  없는 파티션 이름 지정        -> dba_tab_partitions 로 이름 확인
--    ORA-14400  경계에 맞는 파티션 없음      -> MAXVALUE 또는 INTERVAL
--    ORA-12984  파티션 키 컬럼 삭제          -> 재생성 또는 온라인 재정의
