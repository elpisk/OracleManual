[1] 시나리오 개요
--------------------------------------------------------------------------------
-- RANGE 는 순서가 있는 값을 자를 때 쓴다. 남은 두 방식은 목적이 다르다.
--   HASH : 값을 고르게 흩뿌린다. 경합 분산과 병렬 처리가 목적이다.
--   LIST : 값의 목록으로 묶는다. 지역·상태코드·부서처럼 열거 가능한 값에 쓴다.
--
-- 목표
--   (1) HASH 파티션의 분포를 실제로 세어 본다 (고르게 나뉘는지)
--   (2) HASH 는 등치 조건에서만 프루닝된다는 것을 계획으로 확인한다
--   (3) HASH 파티션 수를 늘리고 줄이는 방법 (ADD / COALESCE) 을 익힌다
--   (4) LIST 파티션의 DEFAULT 파티션과 값 추가·삭제(ADD/DROP VALUES) 를 익힌다
--   (5) 19c 의 자동 LIST 파티션(AUTOMATIC) 을 확인한다
-- 작업 유형 : 구조 확인

-- 이름을 정하고 싶으면 (PARTITION h1, PARTITION h2, ...) 로 나열한다.

-- 관찰
--   · high_value 가 비어 있다. HASH 에는 경계값이라는 개념이 없다.
--   · 분포는 25 / 32 / 31 / 19 다. 107 건을 4개로 나눴으니 이상적으로는 26.75 씩이다.
--     완전히 고르지는 않다. 해시는 통계적으로 고르게 나누는 것이지 정확히 나누지 않는다.
--   · 건수가 많아질수록 편차 비율은 줄어든다.
--   · 파티션 수를 2의 거듭제곱(2·4·8·16) 으로 잡으면 분포가 더 고르다.
--     2의 거듭제곱이 아니면 일부 파티션이 두 배 크기가 된다.

-- 이것이 HASH 의 핵심 제약이다.
--
--   조건                        | 연산                  | Pstart/Pstop | Starts | Buffers
--   ----------------------------|-----------------------|--------------|--------|--------
--   employee_id = 115           | PARTITION HASH SINGLE | 2 / 2        | 1      | 2
--   employee_id BETWEEN 110 120 | PARTITION HASH ALL    | 1 / 4        | 4      | 8
--

-- 범위(BETWEEN · > · <) 는 계산할 수 없다. 해시는 순서를 보존하지 않기 때문이다.
-- -> 범위 조회가 주된 테이블에 HASH 를 쓰면 프루닝 이득이 전혀 없다.

-- 관찰
--   · ADD PARTITION 을 하면 개수가 5가 되고, 기존 한 파티션의 행이 새 파티션으로 재분배된다.
--     SYS_P615 가 25 -> 7 로 줄고 새 SYS_P619 가 18을 받았다.
--     즉 ADD 는 하나를 쪼개 두 개로 만드는 동작이다. 전체 재분배가 아니다.
--     그래서 2의 거듭제곱이 아닌 개수에서는 분포가 고르지 않다.
--   · COALESCE PARTITION 은 그 반대다. 마지막 파티션을 지우고 행을 다시 흩뿌린다.
--     25 / 32 / 31 / 19 로 정확히 원래대로 돌아왔다.
--   · DROP PARTITION 은 HASH 에 쓸 수 없다 (ORA-14255).
--     HASH 에서 파티션을 하나 지우면 그 행이 갈 곳이 없어지기 때문이다.
--     줄이려면 COALESCE 를 쓴다.

-- LIST 파티션 값 관리에서 만나는 오류 두 개다.
--   ORA-14323 : cannot add partition when DEFAULT partition exists
--     DEFAULT 가 이미 모든 값을 받고 있으므로 새 파티션을 붙일 수 없다.
--     방법 두 가지 - (1) DEFAULT 파티션을 SPLIT 한다
--                    (2) 기존 파티션에 MODIFY PARTITION ... ADD VALUES 로 값을 더한다
--     (2)를 해 보면 p_dept_2 가 50, 120 이 된다. ADD VALUES 는 데이터 이동이 없어 빠르다.
--   ORA-14312 : Value 120 already exists in partition 2
--     같은 값을 두 파티션에 둘 수 없다. 옮기려면 먼저 DROP VALUES 로 떼어 내야 한다.

-- AUTOMATIC LIST 파티션
--   · 정의할 때 값 하나만 줬는데 CTAS 가 나머지 부서값마다 파티션을 만들었다 (11개).

--   · autolist 컬럼이 YES 다. DEFAULT 파티션은 쓸 수 없다 (자동 생성과 충돌한다).
--   · INTERVAL 이 RANGE 에 해 주는 일을 AUTOMATIC 이 LIST 에 해 준다.
--   · 다만 값의 가짓수가 많으면 파티션이 폭증한다. 값 종류가 제한적일 때만 쓴다.
--

-- 1. 방식 선택 기준은 한 문장으로 정리된다.
--      범위로 자를 수 있고 범위로 조회한다        -> RANGE (또는 INTERVAL)
--      열거 가능한 코드값으로 조회·관리한다        -> LIST
--      고르게 흩뿌리는 것 자체가 목적이다          -> HASH
--    무엇으로 조회하는가가 기준이다. 무엇으로 나누고 싶은가가 아니다.
--
-- 2. HASH 파티션 수는 2의 거듭제곱으로 잡는다.
--    그리고 범위 조회에는 프루닝이 없다는 점을 반드시 확인한다.
--    HASH 의 실제 이득은 파티션 단위 병렬 처리와 파티션 와이즈 조인이다.
--
-- 3. HASH 파티션은 DROP 할 수 없고 COALESCE 로 줄인다.
--    반대로 RANGE·LIST 는 DROP·SPLIT·MERGE 가 전부 된다.
--    파티션을 주기적으로 버려야 하는 테이블에 HASH 는 맞지 않는다.
--
-- 4. DEFAULT / MAXVALUE 파티션 정책을 문서로 정해 둔다.
--    두는 쪽을 택했다면 그 파티션의 건수를 감시하는 쿼리를 함께 만든다.
--    예상 못한 코드값이 쌓이는 것을 발견하는 장치가 그것뿐이기 때문이다.
--
-- 5. 19c 의 AUTOMATIC LIST 는 코드값이 계속 추가되는 테이블에 유용하다.
--    단 값 종류가 수천 개로 늘어날 수 있는 컬럼에는 쓰지 않는다.
--
-- 6. 이 실습에서 본 오류
--    ORA-14173  복합 파티션이 아닌데 SUBPARTITION 지정   -> PARTITION 으로 바꾼다
--    ORA-14255  HASH 파티션에 DROP PARTITION             -> COALESCE PARTITION
--    ORA-14323  DEFAULT 가 있는데 ADD PARTITION          -> SPLIT 또는 ADD VALUES
--    ORA-14312  다른 파티션에 이미 있는 값 추가           -> 먼저 DROP VALUES
--    ORA-14400  DEFAULT 없는 LIST 에 새 값 INSERT        -> DEFAULT 또는 AUTOMATIC
--    ORA-00997  high_value(LONG) 를 WHERE 에 사용        -> PARTITION FOR (값)
