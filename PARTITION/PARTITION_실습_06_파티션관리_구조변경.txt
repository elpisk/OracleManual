--------------------------------------------------------------------------------
[1] 시나리오 개요
--------------------------------------------------------------------------------
-- 파티션 테이블을 만든 다음부터가 진짜 일이다.
-- 파티션은 늘려야 하고, 오래된 것은 버려야 하고, 잘못 잡은 경계는 다시 자르거나 합쳐야 한다.
-- 이 실습은 그 여섯 가지 DDL 을 전부 한 테이블에서 순서대로 수행한다.
--
--   SPLIT     하나를 둘로 자른다
--   ADD       맨 뒤에 붙인다
--   RENAME    이름만 바꾼다
--   DROP      데이터까지 버린다
--   TRUNCATE  데이터만 비운다
--   MERGE     인접한 둘을 하나로 합친다
--
-- 그리고 파티션 테이블에서만 만나는 오류 ORA-14402(파티션 키 UPDATE) 와
-- 그 해결책인 ROW MOVEMENT 를 확인한다.
-- 작업 유형 : 구조 변경 (운영 절차와 직결된다)

--------------------------------------------------------------------------------

--   숫자 키라도 RANGE 파티션의 동작은 완전히 같다

-- SPLIT 을 읽는 법
--   ALTER TABLE ... SPLIT PARTITION part3 AT (20000) INTO (PARTITION part3, PARTITION p4)
--   · AT (20000) 이 자르는 지점이다. 앞 조각이 20000 미만, 뒤 조각이 원래 상한(25000) 미만이다.
--   · INTO 에 두 이름을 준다. 앞 이름을 원래 이름으로 두는 것이 관례다.
--   · 결과 : part3 에 2건(17000 두 건), p4 에 1건(24000).
--   · 중요 : num_rows 가 비었다. SPLIT 은 통계를 무효화한다.
--     구조 변경 DDL 뒤에는 반드시 통계를 다시 수집한다. 안 하면 계획이 틀어진다.
--   · SPLIT 은 데이터를 실제로 두 세그먼트에 다시 쓴다. 큰 파티션에서는 시간이 걸린다.
--     19c 에서는 ONLINE 절을 붙일 수 있다 (SPLIT PARTITION ... ONLINE).

SYS@orcl> ALTER TABLE hr.sal_emp SPLIT PARTITION part3 AT (40000) INTO (PARTITION part3, PARTITION pzz);

Table altered.

-- ORA-14402: updating partition key column would cause a partition change
--   원인 : 101번의 급여를 17000 -> 21000 으로 올리면 part3(20000 미만) 에서
--          p4(25000 미만) 로 옮겨야 한다. 행이 세그먼트를 넘어가는 이동이다.
--          기본값은 이것을 금지한다.
--   해결 : ALTER TABLE ... ENABLE ROW MOVEMENT
--   같은 파티션 안에서 끝나는 변경(17000 -> 18000) 은 아무 설정 없이도 된다.
--
-- ROW MOVEMENT 를 켠 뒤 다시 하면 성공하고, 행이 실제로 p4 로 이동한다.
--
-- ROW MOVEMENT 의 비용과 위험
--   · 내부적으로 DELETE + INSERT 다. 따라서 ROWID 가 바뀐다.
--     ROWID 를 붙잡아 두는 애플리케이션(SELECT ... FOR UPDATE 후 ROWID 재사용)은 깨진다.
--   · REDO·UNDO 가 일반 UPDATE 보다 많다.
--   · 그래서 기본값이 DISABLE 이다. 필요한 테이블에만 켠다.
--   · SHRINK SPACE 도 ROW MOVEMENT 를 요구한다 (실습 07).
--   · 설계 원칙 : 파티션 키는 변하지 않는 컬럼으로 잡는다.
--     날짜 중에서도 등록일·거래일은 변하지 않고, 수정일은 변한다.

--------------------------------------------------------------------------------
[8] 실무 포인트
--------------------------------------------------------------------------------
-- 1. 여섯 DDL 의 비용을 구분해서 기억한다.
--      즉시 끝난다 (딕셔너리만)     : ADD · RENAME · DROP · TRUNCATE
--      데이터를 다시 쓴다 (느리다)   : SPLIT · MERGE · MOVE
--    야간 작업 창을 잡을 때 이 구분이 기준이 된다.
--
-- 2. 구조 변경 DDL 뒤에는 통계를 다시 수집한다.
--    SPLIT·MERGE 는 num_rows 를 NULL 로 만든다. 그대로 두면 옵티마이저가 기본값으로 추정한다.
--    운영 절차서에는 DDL 과 gather_table_stats 를 한 단계로 묶어 적는다.
--
-- 3. 파티션 단위 DDL 은 인덱스를 못 쓰게 만들 수 있다.
--    이 실습에는 인덱스가 없어 드러나지 않았다. 실습 09·10 에서 확인한다.
--    실제 절차서에는 항상 UPDATE INDEXES 절이나 후속 REBUILD 가 함께 들어간다.
--
-- 4. 오래된 데이터를 버리는 방법은 세 가지다.
--      DROP PARTITION            가장 빠르다. 되돌릴 수 없다
--      TRUNCATE PARTITION        구조를 남긴다
--      EXCHANGE PARTITION        데이터를 살려 둔 채 떼어 낸다 (실습 07)
--    보관 요건이 있으면 EXCHANGE 후 그 테이블을 압축·export 하는 절차가 정답이다.
--
