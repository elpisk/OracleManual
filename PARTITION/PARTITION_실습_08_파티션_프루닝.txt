--------------------------------------------------------------------------------
[1] 시나리오 개요
--------------------------------------------------------------------------------
-- 파티셔닝을 하는 이유의 절반은 프루닝(pruning) 이다.
-- 읽지 않아도 되는 파티션을 아예 건드리지 않는 것, 그것뿐이다.
-- 그러므로 "프루닝이 됐는지" 를 실행계획에서 판정하는 능력이 이 과정의 핵심 기술이다.
--
-- 53만 5천 건 테이블을 만들어 다음을 각각 측정한다.
--   정적 프루닝 (상수 조건)        -> SINGLE / ITERATOR
--   동적 프루닝 (바인드 변수)      -> KEY / KEY
--   IN 리스트                      -> INLIST / KEY(I)
--   프루닝 실패 세 가지            -> ALL
--   조인에 의한 실행 시점 프루닝   -> KEY(AP) / 블룸 필터(:BF0000)
-- 작업 유형 : 성능 분석

[2] 사전 조건
--------------------------------------------------------------------------------
-- · 실습 07 의 hr.sal_emp 가 남아 있다 ([6] 의 조인 예제에서 쓴다)
-- · USERS 테이블스페이스에 최소 60MB 의 여유
-- · 실행계획에 실측값(A-Rows·Buffers) 을 함께 보려면 두 가지가 필요하다
--     ① ALTER SESSION SET statistics_level = ALL   또는
--        /*+ gather_plan_statistics */ 힌트
--     ② dbms_xplan.display_cursor(NULL,NULL,'ALLSTATS LAST +PARTITION')
--   +PARTITION 을 빼면 Pstart/Pstop 컬럼이 나오지 않는다. 이 실습에서는 필수다

-- 1. 프루닝 판정은 세 값을 함께 본다. 연산 이름 · Pstart/Pstop · Starts.
--    연산 이름에 ALL 이 있으면 무조건 실패다. SINGLE·ITERATOR·INLIST 는 성공이다.
--    KEY 계열은 Starts 와 Buffers 로 실제 읽은 양을 확인해야 판정할 수 있다.
--
-- 2. 파티션 키에는 아무 연산도 하지 않는다.
--    이것은 인덱스 컬럼을 가공하지 말라는 원칙과 완전히 같다.
--    함수·연산·형 변환이 필요하면 조건값 쪽을 가공한다.
--
-- 3. 암시적 형 변환이 가장 찾기 어려운 원인이다.
--    문자형 파티션 키(예: yyyymm VARCHAR2(6)) 에 숫자를 넣는 코드가 흔하다.
--    파티션 키는 되도록 DATE 나 NUMBER 로 잡고, 문자형이면 조건값도 문자로 준다.
--
-- 4. 성능 검증은 운영과 같은 형태로 한다.
--    상수로 테스트하면 정적 프루닝이라 항상 빠르다.
--    애플리케이션은 바인드 변수를 쓰므로 바인드로 다시 측정해야 한다.
--
-- 5. 조인 프루닝(KEY(AP) · 블룸 필터) 은 설계할 수 있는 최적화다.
--    큰 파티션 테이블을 작은 차원 테이블과 조인하는 형태(스타 스키마) 에서 자동으로 걸린다.
--    반대로 조인 순서가 뒤집히면 사라진다. 계획이 바뀌면 이것부터 확인한다.
--
-- 6. 파티션 키 선택은 조회 패턴이 결정한다.
--    v$sql 에서 그 테이블을 읽는 상위 SQL 의 WHERE 절을 모아 빈도를 세고,
--    가장 많이 쓰이는 컬럼을 키로 잡는다. 관리 편의보다 조회 패턴이 우선이다.
