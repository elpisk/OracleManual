--------------------------------------------------------------------------------
[1] 시나리오 개요
--------------------------------------------------------------------------------
-- 파티션 테이블은 Data Pump 에서 세 가지 단위로 다룰 수 있다.
--   테이블 전체          tables=hr.sal_emp
--   파티션 하나          tables=hr.sal_emp:part2
--   파티션을 독립 테이블로  partition_options=departition
--
-- 이 실습은 실제 장애 대응 순서를 그대로 따라간다.
--   내보낸다 -> 테이블을 잃는다 -> 되살린다 -> 파티션 하나를 실수로 지운다
--   -> 덤프에서 DDL 만 뽑아 구조를 확인한다 -> 구조를 복구한다
--   -> 그 파티션 데이터만 다시 넣는다 -> 파티션 단위 백업·복원을 연습한다
--
-- 목표
--   (1) expdp / impdp 가 파티션을 어떻게 보고하는지 읽는다
--   (2) sqlfile 로 덤프에서 DDL 만 추출한다
--   (3) partition_options=merge 로 특정 파티션 데이터만 넣는다
--   (4) content=data_only 로 데이터만 복원한다
--   (5) partition_options=departition 으로 파티션을 독립 테이블로 떼어 낸다
-- 작업 유형 : 논리 백업·복구

--------------------------------------------------------------------------------
[2] 사전 조건
--------------------------------------------------------------------------------
-- · 디렉터리 객체와 OS 디렉터리가 필요하다 (SYS 로 미리 준비한다)

--     SYS@orcl> GRANT READ, WRITE ON DIRECTORY dirpump TO system;
-- · system 비밀번호를 알고 있어야 한다 (이 랩은 oracle_4U)
-- · 실습 07 이후의 hr.sal_emp 는 상태가 복잡하므로 이 실습은 새로 만들어 시작한다
-- · USERS 에 최소 40MB 여유

-- 1. expdp / impdp 로그는 파티션별 건수 증빙이다.
--    이관 검증은 "전체 건수 비교" 가 아니라 "파티션별 건수 비교" 로 한다.
--    파티션 경계가 달라지면 전체 건수는 같아도 분포가 달라질 수 있다.
--
-- 2. 파티션 단위 백업은 대용량 이력 테이블의 현실적인 해법이다.
--    수억 건 테이블을 통째로 export 하면 시간과 공간이 모두 부담이다.
--    지난 달 파티션만 내보내고 그 파티션을 DROP 하는 절차가 표준이다.
--      ① expdp tables=T:P202501
--      ② 덤프 검증 (impdp sqlfile 로 DDL 확인, 로그 건수 확인)
--      ③ ALTER TABLE T DROP PARTITION P202501 UPDATE INDEXES
--
-- 3. sqlfile 은 복구의 시작점이다.
--    덤프에서 DDL 만 뽑아 경계값·저장 옵션·인덱스 정의를 확인할 수 있고
--    DB 에는 아무 변화를 주지 않는다. 복구 계획을 세울 때 가장 먼저 쓴다.
--
-- 4. partition_options 세 값의 차이를 구분한다.
--      none         (기본) 파티션 구조를 그대로 재현한다
--      merge        파티션 데이터를 대상 테이블 구조에 맞춰 합친다
--      departition  파티션마다 독립 테이블을 만든다
--    merge 는 파티션 경계를 재설계하며 이관할 때 쓴다.
--
-- 5. table_exists_action 을 반드시 지정한다.
--      skip (기본)  이미 있으면 아무 일도 하지 않는다. 성공한 것처럼 보인다
--      append       데이터를 추가한다
--      truncate     비우고 넣는다
--      replace      테이블을 지우고 다시 만든다
--    기본값 skip 때문에 "성공했는데 데이터가 없다" 는 상황이 흔하다.
--
-- 6. Data Pump 는 논리 백업이다. 물리 복구를 대체하지 않는다.
--    파티션 하나를 되살리는 데는 Data Pump 가 가장 간편하지만
--    시점 복구(PITR) 나 전체 복구는 RMAN 의 일이다. 두 가지를 함께 갖춘다.
