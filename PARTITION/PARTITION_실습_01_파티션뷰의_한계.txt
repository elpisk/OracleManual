 파티셔닝 실습 01 : 파티션 뷰의 한계와 파티션 테이블의 필요
 과정      : Oracle Database 19c 파티셔닝 실습
 환경      : Oracle 19.3.0 / Oracle Linux 7 / non-CDB ORCL / AL32UTF8 / 8K 블록
 계정      : SYS (대상 스키마 HR)
 소요 시간 : 약 40분
================================================================================
--------------------------------------------------------------------------------
[1] 시나리오 개요
--------------------------------------------------------------------------------
-- 파티셔닝이 없던 시절에는 큰 테이블을 사람 손으로 쪼갰다.
-- 부서별로 테이블을 세 개 만들고 CHECK 제약으로 범위를 정하고 UNION ALL 뷰로 묶는다.
-- 이것을 파티션 뷰(partition view) 라고 부른다. 지금도 개념 설명에 쓰인다.
--
-- 이 실습의 목표는 세 가지다.
--   (1) 파티션 뷰가 어디까지 되는지 실행계획으로 확인한다
--   (2) 어디서 무너지는지 확인한다  -> 바인드 변수, DML, 인덱스 관리
--   (3) 그 한계가 곧 파티션 테이블이 필요한 이유임을 이해한다
-- 작업 유형 : 개념 확인 (장애 복구 아님)

--------------------------------------------------------------------------------
[2] 사전 조건
--------------------------------------------------------------------------------
-- · HR 스키마와 hr.employees(107건) 가 있다
-- · Partitioning 옵션이 켜져 있다 (Enterprise Edition)
-- · USERS 테이블스페이스에 여유가 있다 (이 실습은 1MB 도 쓰지 않는다)
-- · 실습은 원본 교안 표기를 따라 SYS 로 진행한다.
--   실무에서는 스키마 소유자나 전용 관리 계정으로 하는 것이 맞다.

-- 오류 두 개가 파티션 뷰의 본질적 한계다.
--   ORA-01732 : UNION ALL 뷰는 갱신할 수 없다.
--               넣을 때마다 애플리케이션이 "어느 테이블인지" 를 알아야 한다.
--   ORA-02290 : 잘못된 테이블에 넣으면 CHECK 제약이 막는다.
--               막아 주는 것은 좋지만, 분기 판단을 애플리케이션이 떠안는다는 뜻이다.
--
-- 정리하면 파티션 뷰로는 다음을 할 수 없다.
--   · 바인드 변수 프루닝
--   · 하나의 이름으로 INSERT / UPDATE / DELETE
--   · 인덱스·통계·권한을 한 객체로 관리
--   · 파티션 단위 TRUNCATE / EXCHANGE / 백업
-- 파티션 테이블은 이 네 가지를 전부 해결한다. 그것이 다음 실습의 주제다.

[8] 실무 포인트
--------------------------------------------------------------------------------
-- 1. 파티션 뷰는 "왜 파티셔닝이 필요한가" 를 설명하는 장치다. 신규 설계에 쓰지 않는다.
--    Partitioning 옵션 라이선스가 없는 Standard Edition 에서 흉내를 낼 때만 고려한다.
--
-- 2. filter(NULL IS NOT NULL) 는 "이 분기는 실행하지 않는다" 는 표시다.
--    파티션 뷰뿐 아니라 항상 거짓인 조건이 만들어지는 모든 경우에 나온다.
--    실행계획에서 이 줄을 보면 Starts 를 함께 확인한다.
--
-- 3. Starts 와 Buffers 를 같이 읽는 습관을 들인다.
--    Starts=0 이면 그 연산은 아예 돌지 않았다. E-Rows 만 보면 알 수 없다.
--
-- 4. 상수 조건에서만 되는 최적화는 운영에서 안 되는 최적화다.
--    성능 검증은 애플리케이션이 실제로 쓰는 형태(바인드 변수)로 해야 한다.
--
-- 5. 이 실습에서 본 오류
--    ORA-01732  UNION ALL 뷰에 DML          -> 파티션 테이블로 바꾼다
--    ORA-02290  CHECK 제약 위반             -> 분기 판단을 DB 에 맡긴다
