--------------------------------------------------------------------------------
[1] 시나리오 개요
--------------------------------------------------------------------------------
-- 조회 조건이 두 개면 파티션도 두 단계로 나눌 수 있다. 이것이 복합 파티션이다.
--   상위(파티션)  = 주로 이력 관리용 (날짜)
--   하위(서브파티션) = 주로 조회 분산용 (부서·해시)
-- 11g 이후 상위는 RANGE·LIST 둘 다, 하위는 RANGE·LIST·HASH 를 쓸 수 있다.
--
-- 목표
--   (1) RANGE-HASH 복합 파티션을 만들고 서브파티션 딕셔너리를 읽는다
--   (2) 조건이 하나일 때와 두 개일 때 프루닝이 어떻게 달라지는지 계획으로 본다
--   (3) SUBPARTITION TEMPLATE 로 서브파티션 이름을 예측 가능하게 만든다
--   (4) 실제 세그먼트는 서브파티션 단위라는 것을 확인한다
--   (5) 복합 파티션에서 LOGGING 속성이 어디에 저장되는지 확인한다
-- 작업 유형 : 구조 확인

[3] 초기 상태 확인 — RANGE-HASH 복합 파티션
--------------------------------------------------------------------------------
-- 구문 순서가 중요하다.
--   PARTITION BY RANGE (상위키)
--   SUBPARTITION BY HASH (하위키) SUBPARTITIONS n
--   (PARTITION ... VALUES LESS THAN ...)
-- SUBPARTITIONS n 을 상위 정의보다 먼저 쓴다.

SYS@orcl> CREATE TABLE hr.emp_comp
  2  PARTITION BY RANGE (salary)
  3  SUBPARTITION BY HASH (employee_id) SUBPARTITIONS 4
  4  (PARTITION p4999  VALUES LESS THAN (5000),
  5   PARTITION p9999  VALUES LESS THAN (10000),
  6   PARTITION p19999 VALUES LESS THAN (20000),
  7   PARTITION pmax   VALUES LESS THAN (MAXVALUE))
  8  TABLESPACE users
  9  AS SELECT employee_id, last_name, salary, department_id FROM hr.employees;

[6] 검증 — RANGE-LIST 와 서브파티션 템플릿
--------------------------------------------------------------------------------
-- SUBPARTITION TEMPLATE 을 쓰면 모든 상위 파티션에 같은 서브파티션 구성을 적용하고
-- 이름을 파티션명_서브파티션명 형태로 만들어 준다.

SYS@orcl> CREATE TABLE hr.emp_comp_rl
  2  PARTITION BY RANGE (hire_date)
  3  SUBPARTITION BY LIST (department_id)
  4  SUBPARTITION TEMPLATE
  5  (SUBPARTITION s_dept_1 VALUES (10,20,30,40),
  6   SUBPARTITION s_dept_2 VALUES (50),
  7   SUBPARTITION s_dept_3 VALUES (60,70,80,90,100,110),
  8   SUBPARTITION s_dept_4 VALUES (DEFAULT))
  9  (PARTITION p2004 VALUES LESS THAN (TO_DATE('2005-01-01','YYYY-MM-DD')),
 10   PARTITION p2005 VALUES LESS THAN (TO_DATE('2006-01-01','YYYY-MM-DD')),

 12   PARTITION pmax  VALUES LESS THAN (MAXVALUE))
 13  NOLOGGING
 14  TABLESPACE users
 15  AS SELECT employee_id, last_name, salary, hire_date, department_id FROM hr.employees;

[8] 실무 포인트
--------------------------------------------------------------------------------
-- 1. 복합 파티션을 쓸 이유는 하나다. 조회 조건이 항상 두 개이기 때문이다.
--    조건이 하나뿐이라면 단일 파티션이 더 단순하고 관리 비용도 낮다.
--    대표적인 조합 : RANGE(날짜) + HASH(고객ID) — 이력 관리 + 조회 분산
--                    RANGE(날짜) + LIST(지역)   — 이력 관리 + 지역별 관리
--
-- 2. SUBPARTITION TEMPLATE 은 반드시 쓴다.
--    이름이 예측 가능해야 파티션 단위 TRUNCATE·EXCHANGE·통계 수집을 스크립트로 만들 수 있다.
--
-- 3. 용량은 곱셈이다.
--    파티션 12개 x 서브파티션 8개 = 세그먼트 96개 = 최소 768MB (8MB x 96).
--    복합 파티션은 작은 테이블에 쓰면 손해다. 최소 수억 건 규모에서 검토한다.
--
-- 4. 통계 수집은 granularity 를 명시한다.
--    AUTO 가 서브파티션 통계를 수집할지 여부는 테이블마다 다르게 판단된다.
--    서브파티션 프루닝이 걸린 SQL 의 카디널리티가 이상하면 이것을 먼저 본다.
--      granularity=>'ALL'        전체 + 파티션 + 서브파티션
--      granularity=>'SUBPARTITION'  서브파티션만
--
-- 5. 실행계획의 Pstart/Pstop 은 계층마다 의미가 다르다.
--    상위 연산 행 = 상위 파티션 번호, 테이블 접근 행 = 서브파티션 절대 번호.
--    이것을 혼동하면 프루닝이 됐는지 안 됐는지를 잘못 읽는다.
--
-- 6. 이 실습에서 본 표시
--    LOGGING = NONE     복합 파티션의 상위 파티션 (속성은 서브파티션에 있다)
