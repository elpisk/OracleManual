[1] 시나리오 개요
--------------------------------------------------------------------------------
-- 실습 06 을 끝낸 hr.sal_emp 에는 이상한 숫자가 하나 있다.
-- part3 에 1건만 있는데 통계의 blocks 가 1006 이다. 이 숫자를 끝까지 추적한다.
--
-- 목표
--   (1) dbms_space.unused_space 로 파티션의 HWM(고수위선) 을 직접 읽는다
--   (2) 1건짜리 파티션을 읽는 실제 비용을 실행계획으로 확인한다
--   (3) SHRINK SPACE 로 HWM 을 내린다 (ROW MOVEMENT 가 필요하다)
--   (4) MOVE PARTITION 으로 파티션 하나만 다른 테이블스페이스로 옮긴다
--   (5) EXCHANGE PARTITION 으로 파티션과 일반 테이블을 맞바꾼다
--   (6) 파티션 단위 통계 수집(partname · granularity) 을 확인한다
-- 작업 유형 : 공간 관리 + 데이터 이동

-- unused_space 가 알려 주는 것
--   총블록  = 세그먼트에 할당된 블록 수 (8MB = 1024 블록)
--   미사용  = HWM 위쪽, 한 번도 쓰인 적 없는 블록
--   HWM     = 총블록 - 미사용. 풀 스캔이 읽어야 하는 범위다
--
--   PART1 · PART2 · P5 · PMAX  : HWM 19   (정상)
--   PART3                      : HWM 1024 (8MB 전체)
--
-- 왜 이렇게 됐는가 (실습 06 의 순서를 되짚으면 원인이 보인다)
--   ① TRUNCATE PARTITION part3  -> 세그먼트가 초기화되고 HWM 이 20 블록 아래로 내려간다
--   ② INSERT 2건                 -> 여기서 HWM 이 1024 로 뛴다
--   ASSM(자동 세그먼트 공간 관리) 은 블록을 하나씩 포맷하지 않고 묶음으로 포맷한다.
--   익스텐트가 8MB 한 개뿐인 세그먼트에 첫 행이 들어오면 그 익스텐트 전체를 포맷하고
--   HWM 을 끝까지 올린다. 그래서 1건이 1024 블록을 만든다.
--
-- 이것은 버그가 아니라 대용량 파티션을 전제로 한 기본 동작이다.
-- 문제가 되는 것은 파티션이 실제로 거의 비어 있을 때다.

-- SHRINK 를 읽는 법

--     ROWID 가 바뀐다. 그래서 ROW MOVEMENT 를 요구한다.

--   · SHRINK 는 온라인이다. 배타 잠금을 길게 잡지 않는다.
--     반면 MOVE 는 재작성이므로 더 무겁다. 공간만 회수하려면 SHRINK 를 먼저 검토한다.

-- MOVE 를 읽는 법
--   · 파티션 하나만 다른 테이블스페이스로 옮긴다. 테이블 전체를 건드리지 않는다.
--   · ONLINE 절(12c 이상) 을 붙이면 DML 을 막지 않는다. 없으면 배타 잠금이다.
--   · 용도 두 가지
--       ① 오래된 파티션을 느린 디스크·읽기 전용 테이블스페이스로 내린다 (ILM)
--       ② 단편화된 파티션을 재작성해 공간을 회수한다
--   · dba_segments 를 보면 part1 만 PART_ARCH 에 있고 크기는 8MB 다.
--     SHRINK 를 거친 part3 는 0.1875MB(24블록) 로 혼자 작다.
--   · 주의 : MOVE 는 로컬 인덱스 파티션을 UNUSABLE 로 만든다.
--     이 실습에는 인덱스가 없어 드러나지 않는다. 실습 09 에서 확인한다.

-- ORA-14099: all rows in table do not qualify for specified partition
--   기본값은 검증이다. 스테이징 테이블의 모든 행이 그 파티션의 경계 안에 있어야 한다.
--   45000 은 p5(30000 미만) 에 맞지 않으므로 거부된다. 이 검증이 데이터 정합성을 지킨다.
--
--   WITHOUT VALIDATION 을 붙이면 검사를 건너뛰고 교환한다. 빠르지만 위험하다.
--   실제로 p5 파티션에 45000 인 행이 들어갔다. 경계를 위반한 데이터가 테이블에 존재한다.
--   그 결과 salary=45000 으로 조회하면 프루닝이 pmax 를 보므로 이 행을 찾지 못한다.
--   -> WITHOUT VALIDATION 은 데이터가 경계를 만족한다고 확신할 때만 쓴다.
--      확신의 근거는 보통 "스테이징 테이블에 같은 조건의 CHECK 제약이 있다" 다.

-- 통계 수집 범위를 읽는 법
--   granularity=>'AUTO' (기본)     테이블 + 파티션. 전부 같은 시각에 갱신된다
--   partname=>'PART3', granularity=>'PARTITION'
--                                  그 파티션만 갱신된다. PART3 만 시각이 5초 뒤다
--   granularity=>'ALL'             테이블 + 파티션 + 서브파티션
--   granularity=>'GLOBAL'          테이블 수준만
--
-- 중요한 점 : 파티션 하나만 수집하면 테이블 수준 통계는 갱신되지 않는다.
--   위 결과에서 테이블 num_rows 는 여전히 108 이고 시각도 이전 값이다.
--   대용량 테이블에서 매번 전체를 수집할 수 없으므로 실무에서는
--   증분 통계(INCREMENTAL=TRUE) 를 켜서 파티션만 수집하고 전체를 합성하게 한다.
--     dbms_stats.set_table_prefs('HR','SAL_EMP','INCREMENTAL','TRUE')
--   global_stats 가 YES 면 그 파티션 통계가 실제로 수집된 값이라는 뜻이다.
--
-- hr.sal_emp 는 실습 11 에서 다시 만든다. 여기서는 남겨 둔다.
-- part_arch 테이블스페이스는 실습 09 에서도 쓴다. 지우지 않는다.

[8] 실무 포인트
--------------------------------------------------------------------------------
-- 1. 파티션의 실제 사용량은 dba_segments 가 아니라 HWM 으로 판단한다.
--    점검 쿼리를 만들어 두면 좋다 : dbms_space.unused_space 로 파티션별 HWM 을 뽑아
--    HWM 대비 실제 건수 비율이 낮은 파티션을 SHRINK 대상으로 목록화한다.
--
-- 2. TRUNCATE 뒤 소량 INSERT 는 HWM 을 8MB 끝까지 올린다.
--    일별 스테이징 파티션을 TRUNCATE 해서 쓰는 패턴이라면 이 현상이 매일 반복된다.
--    풀 스캔 비용이 데이터량과 무관해지므로 주기적 SHRINK 를 절차에 넣는다.
--
-- 3. 공간 회수 순서는 SHRINK -> MOVE 다.
--    SHRINK 는 온라인이고 가볍다. MOVE 는 재작성이라 무겁지만 단편화까지 없앤다.
--    MOVE 를 쓸 때는 ONLINE 절과 로컬 인덱스 UNUSABLE 을 함께 고려한다.
--
-- 4. EXCHANGE PARTITION 은 대용량 적재의 표준이다.
--    절차 : 스테이징 테이블에 적재 -> 인덱스 생성 -> 통계 수집 -> EXCHANGE
--    교환 자체는 건수와 무관하게 즉시 끝난다. 서비스 중단 시간이 사실상 없다.
--    거꾸로 이력 분리에도 쓴다 : 빈 테이블과 교환하면 파티션이 비고 데이터는 살아 있다.
--
-- 5. WITHOUT VALIDATION 은 마지막 수단이다.
--    경계를 위반한 행이 들어가면 프루닝 때문에 조회되지 않는 유령 데이터가 된다.
--    스테이징 테이블에 CHECK 제약을 걸어 두면 검증이 인덱스 스캔 수준으로 빨라지므로
--    굳이 건너뛸 이유가 줄어든다.
--
-- 6. 파티션 단위 통계는 증분 통계와 함께 쓴다.
--    파티션만 수집하면 테이블 통계가 낡는다. INCREMENTAL=TRUE 가 그 간극을 메운다.
--
-- 7. 이 실습에서 본 오류
--    ORA-10636  ROW MOVEMENT 없이 SHRINK       -> ENABLE ROW MOVEMENT
--    ORA-14099  경계를 벗어난 행으로 EXCHANGE   -> 데이터 정리 또는 WITHOUT VALIDATION
--    ORA-14096  컬럼 구조 불일치로 EXCHANGE     -> CTAS WHERE 1=2 로 스테이징 생성
