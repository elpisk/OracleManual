--------------------------------------------------------------------------------
[1] 시나리오 개요
--------------------------------------------------------------------------------
-- 파티션 테이블의 인덱스는 두 종류다.
--   LOCAL  : 테이블 파티션 하나에 인덱스 파티션 하나가 1:1 로 붙는다
--   GLOBAL : 인덱스가 테이블 파티션 구조와 무관하다 (실습 10)
--
-- 운영에서 LOCAL 을 기본으로 삼는 이유는 관리 때문이다.
-- 테이블 파티션을 DROP·TRUNCATE·EXCHANGE 해도 인덱스가 따라 움직이므로
-- 다른 파티션의 인덱스는 건드리지 않는다.
--
-- 목표
--   (1) LOCAL 인덱스를 만들고 locality · alignment 를 딕셔너리로 확인한다
--   (2) 접두(PREFIXED) 와 비접두(NON_PREFIXED) 의 계획 차이를 본다
--   (3) UNIQUE LOCAL 인덱스의 제약(ORA-14039) 을 확인한다
--   (4) DROP PARTITION 과 MOVE PARTITION 이 인덱스에 미치는 영향을 비교한다
--   (5) UPDATE INDEXES 절의 효과를 확인한다
-- 작업 유형 : 인덱스 설계 + 관리

-- 비접두(NON_PREFIXED) LOCAL 인덱스
--   인덱스 선두 컬럼(hire_date) 이 파티션 키(employee_id) 와 다르다 -> NON_PREFIXED.
--   hire_date 조건만 주면 어느 테이블 파티션에 있는지 알 수 없으므로
--   PARTITION RANGE ALL 로 인덱스 파티션 6개를 전부 탐색한다 (Starts=6).
--
--   접두 / 비접두 비교
--     PREFIXED     파티션 키가 조건에 있으면 인덱스 파티션 하나만 탐색
--     NON_PREFIXED 파티션 키가 없으면 인덱스 파티션 전부 탐색
--
--   비접두가 항상 나쁜 것은 아니다. 이 예에서 Buffers 는 14 로 작다.
--   인덱스 파티션 6개를 각각 조금씩 읽는 것이 테이블 풀 스캔보다 훨씬 싸다.
--   다만 파티션이 수백 개면 그 오버헤드가 커진다. 파티션 수가 판단 기준이다.

ERROR at line 1:
ORA-14039: partitioning columns must form a subset of key columns of a UNIQUE index

-- ORA-14039: partitioning columns must form a subset of key columns of a UNIQUE index
--   UNIQUE LOCAL 인덱스는 파티션 키를 반드시 포함해야 한다.
--   이유는 구조적이다. LOCAL 인덱스는 파티션마다 독립적이므로
--   파티션을 가로질러 유일성을 보장할 방법이 없다. 키를 포함하면 각 파티션 안에서만
--   비교하면 되므로 보장할 수 있다.
--
--   결과적으로 파티션 테이블의 기본키 설계는 둘 중 하나다.
--     ① 기본키에 파티션 키를 포함시킨다 -> UNIQUE LOCAL 인덱스 가능 (권장)
--     ② 기본키를 그대로 두고 GLOBAL 인덱스로 만든다 -> 관리 비용이 늘어난다 (실습 10)
--   ①을 택하려면 설계 단계에서 결정해야 한다. 나중에 바꾸기 어렵다.

--     -> 인덱스 상태 점검 쿼리를 정기적으로 돌려야 한다.

[8] 실무 포인트
--------------------------------------------------------------------------------
-- 1. 특별한 이유가 없으면 LOCAL 인덱스를 쓴다.
--    파티션 단위 DDL 이 다른 파티션의 인덱스를 건드리지 않는다는 점 하나로 충분하다.
--    이력 테이블에서 오래된 파티션을 매달 DROP 한다면 GLOBAL 은 사실상 쓸 수 없다.
--
-- 2. 가능하면 접두(PREFIXED) 로 만든다.
--    인덱스 선두 컬럼을 파티션 키로 두면 인덱스 프루닝까지 된다.
--    비접두는 파티션 수가 적을 때만 허용 범위다. 수백 개면 다시 검토한다.
--
-- 3. 기본키에 파티션 키를 포함하는 설계를 먼저 검토한다.
--    그래야 UNIQUE LOCAL 인덱스가 가능하다 (ORA-14039 회피).
--    복합 기본키가 부담이라면 GLOBAL UNIQUE 인덱스를 쓰되 관리 비용을 감수한다.
--
-- 4. 인덱스를 UNUSABLE 로 만드는 작업을 외운다.
--      MOVE PARTITION · SPLIT · MERGE · EXCHANGE · TRUNCATE(일부) · 직접 적재
--    반대로 DROP PARTITION 은 LOCAL 인덱스를 UNUSABLE 로 만들지 않는다.
--    모든 파티션 DDL 문장에 UPDATE INDEXES 를 붙이는 것을 절차서의 기본으로 삼는다.
--
-- 5. 상태 점검 쿼리를 상시 운영한다.
--      SELECT index_name, partition_name, status FROM dba_ind_partitions
--      WHERE  status <> 'USABLE';
--      SELECT index_name, status FROM dba_indexes WHERE status = 'UNUSABLE';
--    UNUSABLE 인덱스는 오류 없이 성능만 떨어뜨리므로 감시가 유일한 발견 수단이다.
--
-- 6. 이 실습에서 본 오류
--    ORA-14039  파티션 키 없는 UNIQUE LOCAL 인덱스   -> 키에 파티션 컬럼 포함
--    ORA-01502  UNUSABLE 인덱스 사용                 -> REBUILD PARTITION
