[1] 시나리오 개요
--------------------------------------------------------------------------------
-- 실습 04 에서 IOT 의 약점을 봤다. 기본키가 아닌 조건은 전체 스캔이다.
-- 보완책은 보조 인덱스(secondary index) 다. 그런데 IOT 의 보조 인덱스는
-- 힙의 인덱스와 동작이 다르다. 물리 ROWID 가 없기 때문이다.
--
--   힙의 인덱스  : 키 + 물리 ROWID          -> 곧바로 그 블록으로 간다
--   IOT의 보조   : 키 + 논리 ROWID(기본키값) -> 기본키 인덱스를 다시 타야 한다
--                  + 물리 추측(physical guess) -> 맞으면 한 번에 간다
--
-- 추측이 맞는 비율이 dba_indexes.pct_direct_access 다. 이 값이 IOT 운영의 핵심 지표다.
--
-- 목표
--   (1) 보조 인덱스를 만들고 "인덱스를 두 번 타는" 실행계획을 읽는다
--   (2) pct_direct_access 가 100 인 상태를 확인한다
--   (3) ALTER TABLE ... MOVE 로 추측을 깨뜨리고 비용 증가를 측정한다
--   (4) ALTER INDEX ... UPDATE BLOCK REFERENCES 로 복구한다
--   (5) IOT 키 압축(COMPRESS n) 효과를 측정한다
--   (6) IOT 가 못 하는 것과 할 수 있는 것(파티션) 을 확인한다
-- 작업 유형 : 인덱스 운영

-- 첫 번째 계획이 IOT 보조 인덱스의 특징이다.
--
--   |   1 |  INDEX UNIQUE SCAN| EMP_IOT_CMP_PK  |  <- 상위: 기본키 인덱스
--   |   2 |   INDEX RANGE SCAN| EMP_IOT_CMP_IX1 |  <- 하위: 보조 인덱스
--
-- 힙이라면 INDEX RANGE SCAN + TABLE ACCESS BY INDEX ROWID 다.
-- IOT 는 테이블 접근이 없는 대신 기본키 인덱스 접근이 그 자리를 채운다.
-- Buffers 5 = 보조 인덱스 4 + 기본키 인덱스 1.
--
-- 두 번째 계획은 emp_id(기본키) 만 필요하므로 보조 인덱스에서 끝난다. Buffers 4.
-- 보조 인덱스에 이미 기본키 값이 들어 있기 때문이다.
-- -> 보조 인덱스만으로 답이 나오는 쿼리는 IOT 에서 특히 싸다.

-- IOT 도 파티션할 수 있다.
--   dba_tables : iot_type IOT, partitioned YES
--   파티션 정보는 dba_tab_partitions 가 아니라 **dba_ind_partitions** 에 있다.
--     인덱스가 곧 테이블이므로 파티션도 인덱스 파티션으로 관리된다.
--   세그먼트도 INDEX PARTITION 으로 잡힌다.
--   PARTITION (이름) 표기로 파티션 단위 조회가 된다.

--------------------------------------------------------------------------------
-- 1. IOT 에 보조 인덱스를 만들면 세그먼트가 늘어난다.
--    "IOT 는 세그먼트 하나" 라는 말은 보조 인덱스가 없을 때의 이야기다.
--    보조 인덱스가 여러 개면 힙 + 인덱스 구성과 공간 차이가 없어진다.
--
-- 2. pct_direct_access 를 상시 감시한다.
--      SELECT i.index_name, i.pct_direct_access FROM dba_indexes i, dba_tables t
--      WHERE  i.index_type='NORMAL' AND t.table_name=i.table_name
--      AND    t.owner=i.owner AND t.iot_type='IOT' AND i.pct_direct_access < 100;
--    이 값이 낮아지면 보조 인덱스 조회가 조용히 비싸진다. 오류는 나지 않는다.
--
-- 3. MOVE 뒤에는 반드시 UPDATE BLOCK REFERENCES 를 한다.
--    IOT 재구성 절차서에 이 한 줄을 넣지 않으면 성능이 서서히 나빠진다.
--    REBUILD 보다 가볍고 온라인으로 가능하다.
--
-- 4. 보조 인덱스만으로 답이 나오는 쿼리를 노려 설계한다.
--    보조 인덱스에는 기본키 값이 들어 있으므로 (보조키, 기본키) 조합 조회는 매우 싸다.
--    실측에서 Buffers 4 로 끝났다.
--
-- 5. 키 압축은 IOT 에서 효과가 크다.
--    데이터 전체가 인덱스이므로 선두 컬럼 중복 제거가 테이블 크기를 바로 줄인다.
--    복합 기본키의 선두가 반복되는 구조라면 COMPRESS n 을 먼저 검토한다.
--
-- 6. 이 실습에서 본 오류
--    ORA-02160  IOT 에 LONG 컬럼            -> CLOB 으로 바꾼다
--    ORA-25175  UNIQUE 만 있고 PRIMARY KEY 없음 -> 기본키를 정의한다
