--------------------------------------------------------------------------------
[1] 시나리오 개요
--------------------------------------------------------------------------------
-- 이미 운영 중인 힙 테이블을 IOT 로 바꾸려면 어떻게 하는가.
-- 그리고 이 구조들을 운영에서 어떻게 감시하는가. 이 두 가지가 마지막 주제다.
--
-- IOT 는 ALTER TABLE 로 전환할 수 없다. 저장 구조 자체가 다르기 때문이다.
-- 방법은 두 가지다.
--   ① CTAS + RENAME      간단하고 빠르다. 서비스를 멈춰야 한다
--   ② DBMS_REDEFINITION  온라인이다. 단계가 많고 준비가 필요하다
--
-- 목표
--   (1) CTAS 로 힙을 IOT 로 옮기고 데이터를 검증한다
--   (2) RENAME 으로 이름을 바꿔 치기한다 (제약 이름이 그대로 따라오는 것을 본다)
--   (3) DBMS_REDEFINITION 으로 같은 일을 온라인으로 한다
--   (4) IOT 를 다시 힙으로 되돌린다
--   (5) 구조를 한눈에 보는 점검 쿼리 네 개를 만든다
-- 작업 유형 : 구조 전환 + 운영

-- CTAS 로 IOT 를 만들 때 주의할 점
--   컬럼 목록에 **데이터형을 쓰면 안 된다** (ORA-01773).
--   이름만 나열하고 제약 절만 붙인다.
--     CREATE TABLE t (c1, c2, c3, CONSTRAINT pk PRIMARY KEY (c1, c2))
--     ORGANIZATION INDEX ... AS SELECT c1, c2, c3 FROM 원본;
--
-- 검증은 건수와 MINUS 로 한다. 둘 다 1만 건이고 차집합이 0 이다.
-- MINUS 는 양방향으로 확인하는 것이 안전하다 (여기서는 한 방향만 보였다).
--
-- 크기는 힙 2048+256=2304KB vs IOT 2048KB 로 거의 같다 (실습 04 와 같은 결과다).

-- RENAME 으로 바꿔 치기한다. 확인할 점이 하나 있다.
--   제약 이름이 그대로 따라온다. ACCT_HEAP 의 기본키 이름이 ACCT_IOT_PK 다.
--   운영 문서·모니터링 쿼리가 제약 이름을 참조한다면 함께 바꿔야 한다.
--     ALTER TABLE acct_heap RENAME CONSTRAINT acct_iot_pk TO acct_heap_pk;
--
-- CTAS 방식의 나머지 작업 목록 (이 실습에서는 생략했다)
--   · 인덱스 재생성 (보조 인덱스는 CTAS 로 따라오지 않는다)
--   · 외래키·체크 제약 재생성
--   · 권한(GRANT) 재부여
--   · 트리거·뷰 재컴파일 확인
--   · 통계 수집
--   -> 이 목록이 길다는 점이 온라인 재정의를 쓰는 이유다.

-- 온라인 재정의 세 단계
--   ① can_redef_table   가능한지 먼저 확인한다 (cons_use_pk : 기본키 기준)
--   ② 중간 테이블 생성  목표 구조(IOT) 로 빈 테이블을 만든다
--   ③ start_redef_table 데이터를 복사한다. 이 동안에도 원본에 DML 이 가능하다
--      finish_redef_table 이름을 맞바꾼다 (짧은 잠금)
--
-- 사이에 sync_interim_table 을 호출하면 그동안 쌓인 변경을 미리 반영해
-- finish 단계의 잠금 시간을 줄일 수 있다. 대량 테이블에서는 필수다.
--
-- 결과 : ACCT_HEAP 이 IOT 가 되었고 1만 건이 그대로다.
-- 인덱스 이름이 ACCT_INT_PK 로 바뀐 것에 주의한다 (중간 테이블의 제약 이름이 남는다).
-- 실습 08 의 [6] 점검 쿼리에서 그 이름이 보인다.

-- 1. IOT 전환은 되돌릴 수 없는 결정이다.
--    ALTER TABLE 로 바꿀 수 없고, 되돌리려면 다시 CTAS 를 해야 한다.
--    전환 전 백업과 롤백 계획(원본 테이블을 며칠 남겨 두기) 을 반드시 세운다.
--
-- 2. CTAS 방식은 부수 작업 목록이 길다.
--    보조 인덱스 · 외래키 · 권한 · 트리거 · 통계가 따라오지 않는다.
--    전환 스크립트에 그 목록을 체크리스트로 넣는다.
--    dbms_metadata.get_ddl 로 원본 DDL 을 먼저 뽑아 두면 빠뜨리지 않는다.
--
-- 3. DBMS_REDEFINITION 은 무중단이지만 제약 이름이 중간 테이블 것으로 남는다.
--    운영 문서가 제약·인덱스 이름을 참조하면 RENAME CONSTRAINT 로 정리한다.
--
-- 4. 점검 쿼리 네 개를 스크립트로 만들어 둔다.
--    ① IOT · 클러스터 목록      dba_tables (iot_type, cluster_name)
--    ② 보조 인덱스 추측 상태    dba_indexes (index_type='NORMAL' + iot_type='IOT')
--    ③ 클러스터 건강 지표       dba_clusters (avg_blocks_per_key)
--    ④ 해시 클러스터 공간 낭비  dba_clusters + dba_segments 비교
--    ②는 index_type 필터를 빼면 오탐이 잔뜩 나온다.
--
-- 5. 세 구조 중 신규 설계에 쓸 만한 것은 IOT 하나다.
--    인덱스 클러스터·해시 클러스터는 진단을 위해 알아 두는 기능이다.
--    같은 목적을 지금은 파티션·IOT·머티리얼라이즈드 뷰·인메모리로 달성한다.
--
-- 6. 이 실습에서 본 오류
--    ORA-01773  IOT CTAS 에 데이터형 지정   -> 컬럼 이름만 나열한다
