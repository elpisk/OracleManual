--------------------------------------------------------------------------------
[1] 시나리오 개요
--------------------------------------------------------------------------------
-- 인덱스 클러스터는 키를 찾을 때 인덱스를 한 번 탄다. 해시 클러스터는 그마저 없앤다.
-- 키 값을 해시 함수에 넣어 블록 주소를 직접 계산한다.
--
--   인덱스 클러스터 : 키 -> [클러스터 인덱스] -> 블록   (I/O 2회 이상)
--   해시 클러스터   : 키 -> 해시 계산 -> 블록          (I/O 1회)
--
-- 대가는 공간이다. 해시 값이 들어갈 자리를 **미리 다 만들어 둔다.**
-- HASHKEYS 10000 · SIZE 1024 로 만들면 데이터가 한 건도 없어도 10MB 가 넘는다.
--
-- 목표
--   (1) HASHKEYS 가 소수로 올림되는 것을 확인한다
--   (2) 데이터 없이도 세그먼트가 미리 잡히는 것을 확인한다
--   (3) 등치 조회에서 TABLE ACCESS HASH · Buffers 1 을 측정한다
--   (4) 범위 조회에서는 해시가 쓰이지 않는 것을 확인한다
--   (5) 힙 + 인덱스와 공간·비용을 비교한다
--   (6) SINGLE TABLE 해시 클러스터와 HASH IS 를 확인한다
-- 작업 유형 : 구조 확인 + 성능 비교

--------------------------------------------------------------------------------
[2] 사전 조건
--------------------------------------------------------------------------------

-- · 해시 클러스터는 한 번 정하면 HASHKEYS 를 바꿀 수 없다.
--   바꾸려면 다시 만들어 데이터를 옮겨야 한다. 이 제약이 설계 판단의 핵심이다

-- 같은 데이터를 힙 + 기본키 인덱스로 만들어 비교한다.
--
--   조회 유형 | 해시 클러스터           | 힙 + 인덱스                      | 비고
--   ----------|-------------------------|----------------------------------|------
--   등치      | TABLE ACCESS HASH  1    | UNIQUE SCAN + BY ROWID  3        | 해시 승
--   범위 101건| INDEX RANGE SCAN   2    | INDEX RANGE SCAN        3        | 비슷
--
--   공간      | 클러스터 12MB           | 테이블 0.31MB + 인덱스 0.25MB    | 21배
--
-- 등치 조회에서 Buffers 3 -> 1 로 3분의 1 이다. 분명한 이득이다.
-- 그러나 공간은 21배다. 이 교환이 받아들일 만한지가 판단 기준이다.
--
-- 그리고 실무에서는 Buffers 3 도 이미 대부분 버퍼 캐시에서 처리된다.
-- 즉 이득이 "디스크 I/O 3회 -> 1회" 가 아니라 "메모리 접근 3회 -> 1회" 인 경우가 많다.
-- 그래서 해시 클러스터를 쓸 이유가 점점 줄었다.

--   2만 건을 더 넣어 총 3만 건이 됐지만 avg_blocks_per_key 는 여전히 1 이고

[8] 실무 포인트

-- 1. 해시 클러스터는 "등치 조회만 하는 정적인 코드 테이블" 을 위한 구조다.
--    조건 네 가지가 모두 맞아야 한다.
--      · 조회가 항상 키 등치 (= 또는 IN)
--      · 키의 개수를 미리 알 수 있고 거의 변하지 않는다
--      · 키마다 행 수가 균일하다
--      · 공간을 미리 잡아도 괜찮다
--    하나라도 어긋나면 힙 + 인덱스가 낫다.
--
-- 2. HASHKEYS 는 나중에 바꿀 수 없다.
--    재생성 + 데이터 이동이 유일한 방법이다. 초기 설계에서 증가분을 반영한다.
--    그리고 Oracle 이 소수로 올린다는 점을 기억한다 (10000 -> 10007).
--
-- 3. 공간을 미리 잡는다는 사실을 용량 계획에 반영한다.
--    HASHKEYS x SIZE 가 최소 크기다. 실측에서 데이터 0.7MB 에 12MB 를 잡았다.
--    점검 쿼리는 실습 08 에 있다.
--
-- 4. 범위 조회에는 해시가 쓰이지 않는다.
--    HASH 파티션과 같은 성질이다. 범위 조회가 필요하면 기본키 인덱스를 함께 둔다.
--    그러면 공간 이점이 더 나빠지므로, 애초에 힙을 쓰는 것이 낫다.
--
-- 5. SINGLE TABLE 을 붙일 수 있으면 붙인다.
--    대신 테이블을 나중에 추가할 수 없다 (ORA-25136).
--
-- 6. 실행계획에서 TABLE ACCESS HASH 를 보면 해시 클러스터다.
--    그 테이블의 세그먼트·통계·관리는 클러스터 기준이다. 실습 06 과 같은 주의사항이 적용된다.
--
-- 7. 이 실습에서 본 오류
--    ORA-25136  SINGLE TABLE 클러스터에 두 번째 테이블  -> 일반 해시 클러스터로 만든다
