[1] 시나리오 개요
--------------------------------------------------------------------------------
-- "IOT 가 빠른가" 는 잘못된 질문이다. 질문은 "어떤 조회에서 빠른가" 다.
-- 같은 컬럼 구성으로 힙과 IOT 를 만들고 10만 건씩 넣어 여섯 가지를 측정한다.
--
--   ① 적재 시간          ② 세그먼트 크기      ③ 기본키 단건 조회
--   ④ 기본키 범위 조회   ⑤ 키가 아닌 조건     ⑥ 전체 건수
--   그리고 ⑦ 중간 키 INSERT 로 인한 블록 분할
--
-- 오버플로 효과를 섞지 않기 위해 컬럼을 작게 잡아 OVERFLOW 없이 만든다.
-- 그래야 IOT 와 힙의 차이만 남는다.
--
-- 중요한 발견을 미리 말해 둔다.
--   힙이 기본키 순서로 적재돼 있으면 IOT 의 범위 조회 이득은 거의 없다.
--   IOT 의 이득은 힙이 정렬돼 있지 않을 때 나타난다. 이 실습에서 직접 확인한다.
-- 작업 유형 : 성능 비교

-- ② 세그먼트 크기
--
--   구조 | 세그먼트                        | 합계
--   -----|---------------------------------|------
--   힙   | 테이블 25MB + 인덱스 2MB        | 27MB
--   IOT  | 인덱스 26MB                     | 26MB
--
--    거의 같다. IOT 가 "공간을 절약한다" 는 설명은 과장이다.
--    절약되는 것은 기본키 컬럼의 중복 저장분뿐이고, 대신 인덱스 오버헤드(블록 헤더,
--    행 디렉터리) 가 데이터 전체에 붙는다. 키가 길고 컬럼이 적을 때만 이득이 뚜렷하다.
--
--    한편 통계에서 눈여겨볼 값이 두 개 있다.
--      blevel            힙 PK 1 vs IOT 2   -> IOT 인덱스가 커서 한 단계 깊다
--      clustering_factor 힙 3125 vs IOT 0    -> IOT 는 개념 자체가 없다

-- ③ 기본키 단건 조회
--
--   구조 | 계획                                              | Buffers
--   -----|---------------------------------------------------|--------
--   힙   | INDEX UNIQUE SCAN + TABLE ACCESS BY INDEX ROWID   |    3
--   IOT  | INDEX UNIQUE SCAN                                 |    3
--
--    계획 단계는 하나 줄었는데 Buffers 는 같다.
--    힙은 인덱스 2블록 + 테이블 1블록 = 3, IOT 는 인덱스 3블록(깊이 때문) = 3 이다.
--    blevel 이 1 더 깊은 것이 테이블 접근 한 번을 상쇄했다.
--    -> 단건 조회만 보면 IOT 의 이득은 거의 없다. 이것이 실측의 결론이다.

-- ④-2 같은 데이터를 무작위 순서로 다시 담았을 때
--
--   구조              | clustering_factor | 계획                  | Buffers
--   ------------------|-------------------|-----------------------|--------
--   힙 (키 순서 적재) |  3,125            | INDEX RANGE SCAN+ROWID|     36
--   힙 (무작위 적재)  | 99,973            | TABLE ACCESS FULL     |  3,230
--   IOT               |      0            | INDEX RANGE SCAN      |     36
--
--    clustering_factor 가 건수(10만) 에 가까워지면 옵티마이저는 인덱스를 아예 포기한다.
--    행마다 다른 블록을 읽어야 하므로 풀 스캔이 더 싸다고 판단한 것이다.
--    그 결과 Buffers 가 36 에서 3230 으로 90배가 됐다.
--
--    IOT 는 이 문제가 구조적으로 없다. 데이터가 항상 키 순서이기 때문이다.
--    **IOT 의 진짜 가치는 "clustering_factor 를 영구히 0 으로 고정한다" 는 것이다.**
--    힙은 DML 이 쌓이면 정렬이 깨지고 주기적으로 재구성해야 한다. IOT 는 그럴 일이 없다.

--
--    IOT 가 정확히 두 배가 됐다. 원인은 50/50 블록 분할이다.
--    PCTFREE 0 으로 꽉 채운 리프 블록 중간에 값이 들어오면
--    Oracle 은 그 블록을 반으로 쪼개고 절반을 새 블록으로 옮긴다.

--    설계 지침

[8] 실무 포인트
--------------------------------------------------------------------------------
-- 1. IOT 를 고르는 이유는 속도가 아니라 정렬의 영속성이다.
--    clustering_factor 가 항상 0 이므로 범위 조회 성능이 시간이 지나도 나빠지지 않는다.
--    힙 + 인덱스는 DML 이 쌓이면 정렬이 깨지고 재구성이 필요하다.
--
-- 2. 단건 조회에서는 이득이 거의 없다.
--    IOT 인덱스가 깊어지는 만큼(blevel +1) 테이블 접근 한 번을 상쇄한다.
--    "IOT 는 조회가 한 번에 끝나서 빠르다" 는 설명은 반쪽이다.
--
-- 3. COUNT(*) 와 키만 읽는 집계는 IOT 가 크게 불리하다 (실측 12배).
--    그런 쿼리가 주력이면 힙 + 작은 인덱스가 낫거나, IOT 에 보조 인덱스를 둔다.
--
-- 4. 공간 절약 효과는 크지 않다 (27MB vs 26MB).
--    키가 길고 컬럼 수가 적은 테이블(매핑 테이블·코드 테이블) 에서만 뚜렷하다.
--
-- 5. 중간 키 INSERT 가 많으면 IOT 는 두 배로 부풀 수 있다.
--    PCTFREE 를 확보하고 COALESCE 를 정기 작업에 넣는다.
--    적재 패턴을 먼저 확인하는 것이 IOT 도입 판단의 핵심이다.
--
-- 6. 판단 기준 한 줄
--    "기본키로 범위 조회하고, 키 순서로 데이터가 들어오고, 전체 스캔이 드물다"
--    -> 이 세 조건이 모두 맞으면 IOT. 하나라도 어긋나면 힙을 먼저 검토한다.
