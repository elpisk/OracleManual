--------------------------------------------------------------------------------
[1] 시나리오 개요
--------------------------------------------------------------------------------
-- 실습 02 에서 IOT 는 세그먼트가 둘로 나뉜다는 것을 확인했다.
--   인덱스 세그먼트   : 키 + 자주 쓰는 컬럼   -> 반복 조회된다
--   오버플로 세그먼트 : 큰 부가 컬럼          -> 한 번 읽고 버려도 된다
--
-- 성질이 다른 두 세그먼트를 같은 버퍼 캐시에 두면 큰 쪽이 작은 쪽을 밀어낸다.
-- Oracle 의 다중 버퍼 풀(multiple buffer pool) 이 이 문제를 위해 있다.
--
--   KEEP    풀 : 캐시에 계속 남기고 싶은 세그먼트
--   RECYCLE 풀 : 한 번 읽고 바로 내보내도 되는 세그먼트
--   DEFAULT 풀 : 나머지 전부
--
-- 목표
--   (1) db_keep_cache_size · db_recycle_cache_size 를 재기동 없이 설정한다
--   (2) IOT 의 인덱스 부분은 KEEP, 오버플로 부분은 RECYCLE 로 지정한다
--   (3) v$buffer_pool_statistics 로 풀별 물리 읽기를 측정한다
--   (4) v$bh 로 실제 캐시에 남은 블록 수를 확인한다
--   (5) 두 번 조회해서 KEEP 은 남고 RECYCLE 은 밀려나는 것을 본다
-- 작업 유형 : 메모리 구성 + 성능 측정

--------------------------------------------------------------------------------
[2] 사전 조건
--------------------------------------------------------------------------------
-- · SGA 에 여유가 있어야 한다. KEEP 50MB + RECYCLE 30MB 를 DEFAULT 풀에서 떼어 온다
--   DEFAULT 버퍼 캐시가 100MB 미만이면 먼저 sga_target 을 늘려야 한다
--     ALTER SYSTEM SET sga_max_size = 1200M SCOPE=SPFILE;   -- 재기동 필요
--     ALTER SYSTEM SET sga_target   = 1000M SCOPE=SPFILE;
-- · KEEP · RECYCLE 풀은 자동 SGA 관리(ASMM) 대상이 아니다. 손으로 정해야 한다
-- · 원본 교안은 SCOPE=SPFILE + 재기동 방식을 썼다.
--   두 파라미터는 동적이므로 SCOPE=BOTH 로 재기동 없이 바꿀 수 있다 (아래에서 확인한다).
--   단 sga_max_size 에 여유가 없으면 그때는 재기동이 필요하다

-- 두 번째 조회 결과가 설계 의도를 증명한다.
--   인덱스 부분  Buffers 199, Reads 컬럼이 아예 없다 -> 전부 캐시 적중
--   오버플로     Buffers 5256, Reads 4998 -> 또 디스크에서 읽었다
--                RECYCLE physical_reads 24929 -> 29927 (+4998)
--
-- 이것이 KEEP·RECYCLE 을 나누는 목적이다.
--   KEEP    : 작고 반복 조회되는 세그먼트를 확실히 캐시에 붙잡아 둔다
--   RECYCLE : 크고 한 번 읽는 세그먼트가 DEFAULT 풀을 오염시키지 않게 격리한다
--
-- 격리가 핵심이다. RECYCLE 을 쓰지 않으면 이 4998 블록이 DEFAULT 풀에 들어가
-- 다른 테이블의 블록을 밀어낸다. 그때 느려지는 것은 이 SQL 이 아니라 다른 SQL 이다.

-- 실습을 마치면 풀을 되돌린다. 남겨 두면 DEFAULT 풀이 계속 작은 상태로 있다.
--   ALTER SYSTEM SET db_keep_cache_size = 0 SCOPE=BOTH;
--   ALTER SYSTEM SET db_recycle_cache_size = 0 SCOPE=BOTH;
--   DROP TABLE hr.emp_iot_pool PURGE;
--
-- 되돌리기 전에 그 세그먼트가 KEEP·RECYCLE 을 가리키고 있으면
-- 지정만 남고 풀이 없으므로 DEFAULT 풀로 들어간다 (오류는 나지 않는다).

--------------------------------------------------------------------------------
[8] 실무 포인트
--------------------------------------------------------------------------------
-- 1. KEEP·RECYCLE 은 IOT 와 특히 잘 맞는다.
--    한 테이블이 성질이 다른 두 세그먼트로 나뉘어 있기 때문이다.
--    인덱스 부분은 KEEP, 오버플로 부분은 RECYCLE 이 기본 조합이다.
--
-- 2. 두 파라미터는 동적이다. 재기동이 필요 없다.
--    단 sga_max_size 에 여유가 있어야 하고, DEFAULT 풀에서 떼어 온다는 점을 기억한다.
--    KEEP 을 크게 잡으면 DEFAULT 가 줄어 다른 SQL 이 느려질 수 있다.
--
-- 3. KEEP 풀 크기는 대상 세그먼트 크기의 합보다 커야 의미가 있다.
--    작으면 KEEP 안에서도 밀려나므로 아무 효과가 없다. 다음 쿼리로 합을 먼저 센다.
--      SELECT buffer_pool, SUM(bytes)/1024/1024 mb FROM dba_segments
--      WHERE  buffer_pool <> 'DEFAULT' GROUP BY buffer_pool;
--
-- 4. RECYCLE 은 "빠르게 하려고" 쓰는 것이 아니다.
--    그 SQL 은 여전히 디스크에서 읽는다. 목적은 다른 SQL 을 보호하는 격리다.
--    이 점을 오해하면 RECYCLE 을 적용하고 왜 안 빨라지냐는 질문이 나온다.
--
-- 5. 측정 도구를 외운다.
--    v$sga_dynamic_components  풀 크기
--    v$buffer_pool             풀별 버퍼 개수
--    v$buffer_pool_statistics  풀별 논리·물리 읽기 (컬럼은 set_msize 다)
--    v$bh                      오브젝트별 실제 캐시 블록 수
--    dba_segments.buffer_pool  세그먼트의 풀 지정
