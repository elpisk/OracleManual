================================================================================
 LOB 실습 06 : SecureFile 과 BasicFile, 중복 제거·압축·암호화
 과정      : Oracle Database 19c LOB 실습
 환경      : Oracle 19.3.0 EE / Oracle Linux 7 / non-CDB ORCL / db_securefile=PREFERRED
 계정      : loblab (테이블스페이스 lobtbs=ASSM, lobmssm=MSSM)
 소요 시간 : 약 90분
 라이선스  : COMPRESS 는 Advanced Compression, ENCRYPT 는 Advanced Security 옵션이다.
             학습 목적으로 실행하며, 운영 적용 전 계약을 확인한다.

--------------------------------------------------------------------------------
[1] 시나리오 개요
--------------------------------------------------------------------------------
-- 첨부파일 보관 테이블의 저장 방식을 고른다.
--   ① BasicFile 과 SecureFile 의 차이와 전제 조건
--   ② 두 방식에서 서로 쓸 수 없는 절 (오류로 확인)
--   ③ 같은 데이터를 여섯 구성에 넣어 공간을 비교 — 중복 제거·압축·암호화의 실제 효과
-- 작업 유형 : 저장 옵션 설계 (장애 복구 아님)

--------------------------------------------------------------------------------
[2] 사전 조건
--------------------------------------------------------------------------------
-- · 실습 01 완료. lobtbs(ASSM), lobmssm(MSSM) 두 테이블스페이스가 있다
-- · db_securefile = PREFERRED (19c 기본). 값의 뜻은 아래와 같다
--     PERMITTED : SecureFile 을 허용하되 기본은 BasicFile
--     PREFERRED : 가능하면 SecureFile (ASSM 이 아니면 BasicFile 로 만든다)
--     ALWAYS    : ASSM 이면 SecureFile 로 강제, 아니면 오류
--     FORCE     : 항상 SecureFile 로 강제
--     IGNORE    : SECUREFILE 지정을 무시하고 BasicFile
-- · ENCRYPT 절을 쓰려면 TDE 지갑(키스토어)이 열려 있어야 한다
--     SYS@orcl> SELECT wrl_type, status, wallet_type FROM v$encryption_wallet;
--     FILE   OPEN   AUTOLOGIN        ← 이 상태여야 4-4 가 성공한다
--   지갑이 없으면 ORA-28365(wallet is not open) 계열 오류가 난다. 지갑 구성은 보안 과정에서 다룬다.

[oracle@oel7v9 ~]$ sqlplus loblab/oracle_4U

LOBLAB@orcl> SET SERVEROUTPUT ON SIZE UNLIMITED
LOBLAB@orcl> SET LINESIZE 160
LOBLAB@orcl> WHENEVER SQLERROR CONTINUE

Table created.

LOBLAB@orcl> COL table_name FOR a12
LOBLAB@orcl> SELECT table_name, securefile, pctversion, retention_type, retention_value
  2  FROM   user_lobs WHERE table_name IN ('S_BASIC','S_SECURE') ORDER BY 1;

TABLE_NAME   SEC PCTVERSION RETENTI RETENTION_VALUE
------------ --- ---------- ------- ---------------
S_BASIC      NO             YES
S_SECURE     YES            DEFAULT

-- 읽는 법
--   · BasicFile 은 이전 버전 공간을 PCTVERSION 으로 관리한다(여기서는 'YES' = 기본 정책 사용).
--   · SecureFile 은 RETENTION 으로 관리한다(DEFAULT = UNDO 설정을 따른다).
--   · 두 열은 상호 배타적이다. 한쪽을 쓰면 다른 쪽은 비어 있다.
--   · 19c 에서 BasicFile 은 여전히 만들어지지만 신규 설계에는 권장되지 않는다
--     (압축·중복 제거·암호화·FRAGMENT_* API 를 쓸 수 없다).

-- ────────────────────────────────────────────────
-- 4-4. 같은 데이터 200건을 여섯 구성에 적재
-- ────────────────────────────────────────────────
-- 반복되는 텍스트 200자를 512번 이어 붙여 102,400 문자(약 200KB)를 만든다.
-- 200건 모두 내용이 완전히 같다. 중복 제거의 상한을 보기 위한 설정이다.

LOBLAB@orcl> DECLARE
  2    v_unit VARCHAR2(400) := RPAD('ORACLE LOB COMPRESSION TEST LINE abcdefghij 0123456789 ',200,'.');
  3    PROCEDURE load_one(p_tab VARCHAR2) IS
  4      v_l CLOB;
  5    BEGIN
  6      FOR i IN 1..200 LOOP
  7        EXECUTE IMMEDIATE 'INSERT INTO ' || p_tab || ' VALUES (:1, EMPTY_CLOB()) RETURNING c INTO :2'
  8          USING i RETURNING INTO v_l;
  9        FOR j IN 1..512 LOOP DBMS_LOB.WRITEAPPEND(v_l, 200, v_unit); END LOOP;
 10      END LOOP;
 11      COMMIT;
 12    END;
 13  BEGIN
 14    load_one('s_plain');  load_one('s_dedup');  load_one('s_comp_l');
 15    load_one('s_comp_m'); load_one('s_comp_h'); load_one('s_enc');
 16    DBMS_OUTPUT.PUT_LINE('여섯 테이블에 각각 200건(각 102,400 문자) 적재 완료');
 17  END;

LOBLAB@orcl> SELECT COUNT(*) AS rows_each, MIN(DBMS_LOB.GETLENGTH(c)) AS chars FROM s_plain;

 ROWS_EACH      CHARS
---------- ----------
       200     102400

-- 해석
--   기본(S_PLAIN) 48.19MB = 200건 × 102,400 문자 × 2바이트 + 세그먼트 오버헤드.
--     여기서도 CLOB 이 문자당 2바이트로 저장된다는 사실이 확인된다(실습 01).
--   압축 3.19MB (15배 축소). LOW/MEDIUM/HIGH 가 모두 같다.
--     이 데이터가 200자 단위 반복이라 어떤 알고리즘이든 한계까지 줄었기 때문이다.
--     실제 문서·로그는 LOW < MEDIUM < HIGH 순으로 차이가 나고 CPU 비용도 그 순서다.
--     이미 압축된 파일(JPEG·ZIP·동영상)은 거의 줄지 않는다. 압축을 걸면 CPU 만 쓴다.
--   중복 제거 1.19MB. 200건이 완전히 동일하므로 실제로는 한 벌만 저장되었다.
--     같은 첨부가 여러 행에 반복되는 업무(공통 양식, 전달된 메일 첨부)에서만 이만큼 효과가 난다.
--     내용이 1바이트라도 다르면 별개로 저장된다(해시 기반).
--   암호화 48.19MB. 기본과 완전히 같다. 암호화는 공간을 늘리지 않는다.
--     비용은 CPU 와 키 관리이고, 이득은 저장 매체가 유출되어도 읽히지 않는다는 점이다.

[8] 실무 포인트
--------------------------------------------------------------------------------
-- 1) 신규 설계는 SecureFile 이 기본이다. BasicFile 을 고를 이유는 사실상 없다.
--    단 ASSM 테이블스페이스여야 한다(ORA-43853). 인수받은 DB 는 이것부터 확인한다.
--
-- 2) "SecureFile 로 만들었는데 BasicFile 인" 경우를 정기 점검한다.
--      SELECT table_name, column_name FROM dba_lobs WHERE securefile='NO' AND owner NOT LIKE 'SYS%';
--    db_securefile=PREFERRED 는 조용히 BasicFile 로 만들기도 한다.
--
-- 3) 압축 등급은 데이터로 결정한다. 표본을 실제로 넣어 보고 크기를 비교한다.
--    이 실습처럼 LOW/MEDIUM/HIGH 가 같게 나오면 가장 싼 LOW 를 쓰는 것이 합리적이다.
--    이미 압축된 바이너리에는 걸지 않는다.
--
-- 4) 중복 제거는 "같은 파일이 여러 행에 붙는가" 를 먼저 세어 본다.
--    효과가 없으면 해시 계산 비용만 추가된다.
--
-- 5) 암호화는 공간을 늘리지 않지만 CPU 를 쓰고 지갑 관리 책임이 생긴다.
--    지갑을 잃으면 데이터를 영구히 읽을 수 없다. 백업·이관 절차에 지갑을 반드시 포함한다.
--    Data Pump 로 반출할 때의 주의사항은 실습 08 에서 다룬다.
--
-- 6) 압축·중복 제거는 Advanced Compression, 암호화는 Advanced Security 옵션이다.
--    EE 바이너리에서 명령이 실행되는 것과 라이선스 보유는 별개다.
--    사용 흔적은 dba_feature_usage_statistics 에 남아 감사 대상이 된다.
