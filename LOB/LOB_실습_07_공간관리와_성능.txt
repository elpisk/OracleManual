-- "첨부를 많이 지웠는데 데이터파일이 줄지 않는다" 는 문의로 시작한다.
--   ① LOB 세그먼트의 실제 사용량을 DBMS_SPACE.SPACE_USAGE 로 본다
--   ② 삭제·RETENTION·SHRINK·MOVE 가 각각 무엇을 하는지 수치로 확인한다
--   ③ 적재 성능에 직결되는 LOGGING / NOLOGGING / FILESYSTEM_LIKE_LOGGING 의 리두량
--   ④ 읽기 성능에 직결되는 CACHE / NOCACHE 의 물리 읽기
-- 작업 유형 : 공간·성능 관리 (장애 복구 아님)

LOBLAB@orcl> DECLARE
  2    v_seg VARCHAR2(30);
  3    v_sb NUMBER; v_sby NUMBER; v_ub NUMBER; v_uby NUMBER;

 10  END;

  3    v_before NUMBER; v_after NUMBER; v_l CLOB;
  4    FUNCTION redo_now RETURN NUMBER IS v NUMBER;
  5    BEGIN
  6      SELECT s.value INTO v FROM v$mystat s JOIN v$statname n ON n.statistic# = s.statistic#
  7       WHERE n.name = 'redo size';
  8      RETURN v;
  9    END;

 11    BEGIN
 12      v_before := redo_now();
 13      FOR i IN 1..20 LOOP

 15          USING i RETURNING INTO v_l;

--   · ARCHIVELOG + FORCE LOGGING 이면 이 설정은 무시되고 항상 기록된다(Data Guard 환경 필수).
--   · 대량 초기 적재에만 쓰고, 적재가 끝나면 LOGGING 으로 되돌린다.
--       ALTER TABLE lg_nolog MODIFY LOB (c) (LOGGING);

LOBLAB@orcl> DECLARE
  2    FUNCTION pr RETURN NUMBER IS v NUMBER;
  3    BEGIN
  4      SELECT s.value INTO v FROM v$mystat s JOIN v$statname n ON n.statistic#=s.statistic#
  5       WHERE n.name='physical reads';
  6      RETURN v;
  7    END;
  8    PROCEDURE read_all(p_tab VARCHAR2, p_label VARCHAR2) IS
  9      v_b NUMBER; v_a NUMBER; v_sum NUMBER;
 10    BEGIN
 11      v_b := pr();
 12      EXECUTE IMMEDIATE 'SELECT SUM(DBMS_LOB.GETLENGTH(c)) + SUM(LENGTH(DBMS_LOB.SUBSTR(c,2000,1))) FROM ' || p_tab INTO v_sum;
 13      v_a := pr();
 14      DBMS_OUTPUT.PUT_LINE(RPAD(p_label,16) || ' 물리 읽기 = ' || (v_a - v_b) || ' 블록');
 15    END;
 16  BEGIN
 17    read_all('r_nocache','NOCACHE 1회차'); read_all('r_nocache','NOCACHE 2회차');
 18    read_all('r_cache',  'CACHE 1회차');   read_all('r_cache',  'CACHE 2회차');
 19  END;
 20  /
NOCACHE 1회차    물리 읽기 = 100 블록
NOCACHE 2회차    물리 읽기 = 100 블록
CACHE 1회차      물리 읽기 = 0 블록
CACHE 2회차      물리 읽기 = 0 블록

PL/SQL procedure successfully completed.

-- 해석
--   NOCACHE : 읽을 때마다 디스크에서 100 블록을 읽는다. 재읽기에도 이득이 없다.
--   CACHE   : 적재 때 버퍼 캐시에 들어간 블록이 남아 있어 물리 읽기가 0 이다.
--   자주 읽는 작은 LOB(썸네일·아이콘·공통 양식)은 CACHE 가 유리하다.
--   한 번 읽고 버리는 큰 LOB 은 NOCACHE 가 맞다. CACHE 로 두면 버퍼 캐시를 밀어내
--   다른 테이블의 조회까지 느려진다.

[8] 실무 포인트
--------------------------------------------------------------------------------
-- 1) "지웠는데 파일이 안 줄어요" 의 표준 답변 순서
--      ① SPACE_USAGE 로 사용/만료/미만료를 본다
--      ② 미만료가 크면 RETENTION 설정을 확인한다
--      ③ 파일 크기를 줄여야 하면 MOVE LOB (SecureFile) 또는 SHRINK SPACE (BasicFile)
--      ④ 무중단이 필요하면 DBMS_REDEFINITION
--    dba_segments 만 보고 판단하면 원인을 못 찾는다.
--
-- 2) SecureFile 에는 SHRINK SPACE 가 없다(ORA-10635). MOVE 가 그 자리를 대신한다.
--    MOVE 는 배타 잠금을 잡으므로 작업 창을 확보한다.
--
-- 3) RETENTION NONE 은 공간 회수에는 유리하지만 읽기 일관성을 희생한다.
--    긴 조회·리포트가 도는 시스템에서는 AUTO 또는 MIN <초> 를 쓴다.
--
-- 4) 대량 적재는 NOLOGGING(또는 FILESYSTEM_LIKE_LOGGING)으로 리두를 반으로 줄일 수 있다.
--    대가는 복구 불가다. 적재 직후 백업 → LOGGING 복귀를 절차로 묶는다.
--    Data Guard 를 쓰면 FORCE LOGGING 때문에 효과가 없다(그리고 그래야 한다).
--
-- 5) CACHE 결정은 "재읽기 빈도" 로 한다. 자주 읽는 작은 LOB 만 CACHE 로 둔다.
--    큰 LOB 을 CACHE 로 두면 버퍼 캐시가 LOB 에 점령된다.
--
-- 6) 속성 변경 뒤에는 반드시 MOVE 로 마무리한다. ALTER 만으로는 기존 데이터가
--    새 형식으로 정리되지 않고 세그먼트만 커진다.
--
-- 7) 정기 점검 쿼리를 하나 만들어 둔다 — 사용률이 낮은 LOB 세그먼트 찾기.
--    (SPACE_USAGE 를 반복 호출하는 PL/SQL 로 작성하고 used/segment 비율을 기록한다)
