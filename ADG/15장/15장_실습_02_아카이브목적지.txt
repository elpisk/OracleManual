          VALID_NOW · VALID_TYPE · VALID_ROLE 로 목적지를 판정한다

--------------------------------------------------------------------------------

SYS@chicago> COL recovery_mode FOR a24
SYS@chicago> COL destination FOR a14
SYS@chicago> SELECT dest_id, destination, status, type, recovery_mode
  2            FROM v$archive_dest_status WHERE dest_id IN (1,2);

   DEST_ID DESTINATION  STATUS    TYPE       RECOVERY_MODE
---------- ------------ --------- ---------- ------------------------
         1              VALID     LOCAL      IDLE
         2 boston       VALID     PHYSICAL   MANAGED REAL TIME APPLY

2 rows selected.

-- ★ 두 뷰가 다른 질문에 답한다.
--
--   V$ARCHIVE_DEST         설정이 어떻게 되어 있는가
--   V$ARCHIVE_DEST_STATUS  지금 어떤 상태인가
--
-- ★ 둘 다 STATUS 열이 있어 혼동하기 쉽다.
--   구별하는 방법은 다른 열을 보는 것이다.
--
--   RECOVERY_MODE 가 있으면  → _STATUS
--   VALID_NOW 가 있으면      → V$ARCHIVE_DEST
--
-- ★ dest_id=1 의 RECOVERY_MODE 가 IDLE 이다.
--   로컬 목적지에는 적용이라는 개념이 없다.
--   원격인 2번만 MANAGED REAL TIME APPLY 다.
--
-- ★ _STATUS 에서 1번의 DESTINATION 이 비어 있는 것도 눈여겨본다.
--   V$ARCHIVE_DEST 에서는 USE_DB_RECOVERY_FILE_DEST 로 나왔다.
--   같은 목적지를 두 뷰가 다르게 표현한다.

--------------------------------------------------------------------------------
 [2] VALID_TYPE 과 VALID_ROLE
--------------------------------------------------------------------------------

SYS@chicago> COL valid_type FOR a18
SYS@chicago> COL valid_role FOR a14
SYS@chicago> COL target FOR a10
SYS@chicago> SELECT dest_id, target, valid_type, valid_role, affirm, transmit_mode
  2            FROM v$archive_dest WHERE dest_id IN (1,2);

   DEST_ID TARGET     VALID_TYPE       VALID_ROLE     AFF TRANSMIT_MOD
---------- ---------- ---------------- -------------- --- ------------
         1 PRIMARY    ALL_LOGFILES     ALL_ROLES      NO  SYNCHRONOUS
         2 STANDBY    ONLINE_LOGFILE   ALL_ROLES      NO  ASYNCHRONOUS

2 rows selected.

-- ★ 7장에서 VALID_FOR 로 쓴 것이 여기서 열로 분해되어 나온다.
--
--   VALID_FOR=(online_logfiles, all_roles)
--     → VALID_TYPE=ONLINE_LOGFILE, VALID_ROLE=ALL_ROLES
--
-- ★ 13장에서 Broker 가 인수하며 만든 설정이 그대로 보인다.
--
-- ★ TARGET 이 목적지의 성격을 알려 준다.
--   1번 PRIMARY  = 로컬
--   2번 STANDBY  = 원격
--
-- ★ 1번이 SYNCHRONOUS 인 것에 놀라지 않는다.
--   보호 모드는 MaxPerformance 인데 왜 동기인가.
--   로컬 디스크에 쓰는 것이므로 네트워크 전송이 아니다.
--   여기서의 SYNCHRONOUS 는 프로세스가 기다린다는 뜻일 뿐이며
--   보호 모드와 무관하다.
--
-- ★ AFFIRM=NO 는 보호 모드와 관계가 있다.
--   MaxPerformance 이므로 Standby 의 쓰기 완료를 기다리지 않는다.
--   8장에서 배운 그 개념이다.

--------------------------------------------------------------------------------
 [3] VALID_NOW 의 값들
--------------------------------------------------------------------------------

SYS@chicago> COL valid_now FOR a20
SYS@chicago> SELECT valid_now, count(*) cnt FROM v$archive_dest
  2            GROUP BY valid_now ORDER BY 2 DESC;

VALID_NOW                   CNT
-------------------- ----------
UNKNOWN                      29
YES                           2

2 rows selected.

-- ★ UNKNOWN 이 29개다. 놀랄 일이 아니다.
--   이 뷰는 목적지 31개(19c 기준)를 전부 보여 준다.
--   쓰지 않는 목적지는 설정이 비어 있어 UNKNOWN 이다.
--
-- ★ 값의 종류
--
--   YES                지금 이 목적지가 유효하다
--   WRONG VALID_TYPE   로그 종류가 맞지 않는다 (10장에서 봤다)
--   WRONG VALID_ROLE   지금 역할에서는 쓰이지 않는다
--   INACTIVE           유효하지만 지금 동작하지 않는다
--   UNKNOWN            판정할 수 없다
--
-- ★ 10장에서 Far Sync 목적지를 설정한 직후에도 UNKNOWN 이었다.
--   막 바꾼 직후와 아예 쓰지 않는 목적지가 같은 값으로 보인다.
--
-- ★ 그래서 UNKNOWN 을 보면 DESTINATION 이 비어 있는지 먼저 본다.
--   비어 있으면 쓰지 않는 목적지이고,
--   값이 있는데 UNKNOWN 이면 아직 계산되지 않은 것이다.

--

--
--   ORA-00904  열 이름이 틀렸다        → 열을 고친다

>>> 조치

--
--   묻는 것                        보는 뷰

--
-- ★ 정상일 때 두 뷰 모두 STATUS=VALID 이고 ERROR 는 비어 있다.
