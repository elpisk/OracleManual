================================================================================
 제15장 실습 07 — Logical Standby 모니터링
 대상   : chicago-srv, boston-srv, 호스트(vmrun)
 목표   : 역할이 Logical 로 바뀌면 어떤 뷰가 비는지 확인하고,
          V$LOGSTDBY_TRANSACTION 으로 적용 중인 트랜잭션을 추적한다.
          멈춘 적용을 XID 로 진단해 되살린다
 소요   : 약 90분
 변경   : boston 이 LOGICAL STANDBY 가 된다 (되돌릴 수 없다).
          마지막에 스냅샷으로 완전 원복한다
================================================================================

--------------------------------------------------------------------------------
 [1] 시작하기 전에 — 스냅샷
--------------------------------------------------------------------------------

-- ★ 이 실습은 되돌릴 수 없는 명령을 쓴다.
--   RECOVER TO LOGICAL STANDBY 는 취소가 없다.
--   반드시 스냅샷을 먼저 뜬다.
--
-- ★ 스냅샷은 전원을 끈 상태에서 뜬다. 12장에서 실행 중에 떴다가
--   되돌린 뒤 적용이 이상했던 일이 있었다.

[oracle@boston-srv ~]$ sqlplus / as sysdba
SYS@boston> SHUTDOWN IMMEDIATE

SYS@chicago> SHUTDOWN IMMEDIATE

[root@boston-srv ~]# /sbin/shutdown -h now

>>> 원인 파악

-- ★ 15.3.2 절에서 정리한 규칙 그대로다.
--   ORA-00904 는 열 이름, ORA-00942 는 뷰 이름이다.
--   뷰는 있으므로 열 이름을 확인한다.

SYS@boston> DESC v$logstdby_transaction

 Name                     Type
 ------------------------ ----------
 PRIMARY_XIDUSN           NUMBER
 PRIMARY_XIDSLT           NUMBER
 PRIMARY_XIDSQN           NUMBER
 PRIMARY_XID              RAW(8)
 PRIMARY_START_SCN        NUMBER
 PRIMARY_START_TIME       DATE
 PRIMARY_PARENT_XIDUSN    NUMBER
 PRIMARY_PARENT_XIDSLT    NUMBER
 PRIMARY_PARENT_XIDSQN    NUMBER
 PRIMARY_PARENT_XID       RAW(8)
 TYPE                     VARCHAR2(32)
 MINING_STATUS            VARCHAR2(32)

 APPLY_STATUS             VARCHAR2(6)
 SID                      NUMBER
 SERIAL#                  NUMBER
 CON_ID                   NUMBER

-- ★ 전부 PRIMARY_ 접두어가 붙는다.
--   이 뷰가 보여 주는 XID 는 Standby 의 것이 아니라
--   Primary 에서 그 트랜잭션이 받았던 번호다.
--   그래야 Primary 의 V$TRANSACTION 과 대조할 수 있다.
--
-- ★ 문서에 나오는 SAVEPOINT_SCN, COMMIT_SCN 도 19c 의 이 뷰에는 없다.
--   실제로 조회하면 역시 ORA-00904 다.
--   열 이름은 외우지 말고 DESC 로 확인한다.

>>> 조치

-- 복제 대상을 만들고 큰 트랜잭션을 걸어 관찰한다.

SYS@chicago> ALTER SESSION SET CONTAINER=chicago_pdb1;
SYS@chicago> CREATE USER lg15 IDENTIFIED BY lg15 QUOTA UNLIMITED ON users;
SYS@chicago> GRANT create session, create table TO lg15;
SYS@chicago> CREATE TABLE lg15.tx(id NUMBER PRIMARY KEY, tag VARCHAR2(30),
  2                               pad VARCHAR2(200));
SYS@chicago> INSERT INTO lg15.tx SELECT level,'seed',rpad('x',200,'x')
  2            FROM dual CONNECT BY level<=10;
SYS@chicago> COMMIT;

-- ★ 기본 키를 둔다. BUILD 가 PK 보충 로깅을 켜 두었으므로
--   기본 키가 있는 표가 가장 깔끔하게 복제된다.

SYS@boston> SELECT count(*) FROM lg15.tx;      --> 10

-- 200 만 행을 한 트랜잭션으로 넣는다 (Primary 에서 약 77초).

SYS@chicago> INSERT INTO lg15.tx SELECT 2000000+level,'bulk2',rpad('y',200,'y')
  2            FROM dual CONNECT BY level<=2000000;
SYS@chicago> COMMIT;

-- Standby 에서 2초 간격으로 조회한다.

SYS@boston> SELECT to_char(sysdate,'HH24:MI:SS')||' | XID '
  2              ||primary_xidusn||'.'||primary_xidslt||'.'||primary_xidsqn
  3              ||' | '||type||' | '||mining_status||' | '||apply_status
  4              ||' | SRC_CON '||src_con_id
  5              ||' | '||to_char(primary_start_time,'HH24:MI:SS')
  6         FROM v$logstdby_transaction;

17:20:50 | XID 9.27.791 | DML | MINING COMPLETE | APPLY NONE | SRC_CON 3 | 17:19:58
17:20:50 | XID 9.30.820 | DML | MINING COMPLETE | APPLY NONE | SRC_CON 3 | 17:19:58
17:20:56 | XID 9.32.835 | DML | MINING COMPLETE | APPLY NONE | SRC_CON 3 | 17:20:09

>>> 재확인

-- ★ 읽는 법
--
--   XID 9.9.821         Primary 에서의 트랜잭션 번호 (usn.slt.sqn)
--   TYPE = DML          DDL 이면 DDL 로 나온다
--   MINING COMPLETE     리두 읽기는 끝났다
--   APPLY NONE          아직 적용 단계로 넘어가지 않았다
--   SRC_CON 3           CDB 안의 PDB 에서 온 변경이다
--   17:19:58            Primary 에서 시작한 시각
--
-- ★ 조회 시각 17:20:50 과 시작 시각 17:19:58 의 차이가 52초다.
--   이 값이 커지면 하나의 트랜잭션이 오래 붙잡고 있다는 뜻이다.
--   "적용이 느리다"를 트랜잭션 단위로 설명할 수 있는 유일한 뷰다.

SYS@boston> SELECT state FROM v$logstdby_state;        --> APPLYING (약 2분)
SYS@boston> SELECT count(*) FROM lg15.tx;              --> 2300010
SYS@boston> SELECT name, value FROM v$logstdby_stats
  2            WHERE name IN ('txns applied','peak apply rate (bytes/sec)',
  3                           'bytes of redo mined');

NAME                          VALUE
----------------------------- ------------
txns applied                  8
peak apply rate (bytes/sec)   28482812
bytes of redo mined           739945304

-- ★ 200 만 행이 약 2분에 적용됐다. 최고 속도 약 27MB/s 다.
--   한가해지면 V$LOGSTDBY_TRANSACTION 은 다시 빈다.
--   비어 있는 것이 정상이다.

-- ★ 중요한 성질이다.
--   이 뷰는 SQL Apply 가 도는 동안에만 채워진다.
--   멈추면 비어 버리므로, 멈춘 뒤에는 XID 를 여기서 찾을 수 없다.
--
-- ★ 멈춘 뒤의 XID 는 DBA_LOGSTDBY_EVENTS 에 있다.

SYS@boston> SELECT xidusn, xidslt, xidsqn, status_code
  2            FROM dba_logstdby_events WHERE status_code=26787
  3           ORDER BY event_time DESC FETCH FIRST 2 ROWS ONLY;

    XIDUSN     XIDSLT     XIDSQN STATUS_CODE
---------- ---------- ---------- -----------
         7          1        704       26787
         7          1        704       26787

-- ★ 여기서는 열 이름이 XIDUSN 이다.
--   V$LOGSTDBY_TRANSACTION 은 PRIMARY_XIDUSN,
--   DBA_LOGSTDBY_EVENTS 는 XIDUSN 이다. 뷰마다 다르다.

>>> 조치

-- 교과서적인 조치는 그 트랜잭션만 건너뛰는 것이다. 먼저 PDB 에서 시도한다.

-- ★ 이 실습에서 확인한 것
--
--   ① 스냅샷은 전원을 끈 상태에서 뜬다. shutdown -h 로 게스트가 멈춰도
--      vmrun 은 running 이므로 stop hard 로 마무리한다
--   ② Broker 하에서 MRP 를 끄면 ORA-16766 + ORA-16853,
--      구성에는 ORA-16810 만 요약되어 보인다
--   ③ 클라이언트를 죽여도 서버 세션은 계속 수행한다
--   ④ REMOVE CONFIGURATION 은 log_archive_config 와 fal_server 를
--      덮어 전송을 끊는다 — ORA-16057
--   ⑤ Logical 로 바뀌면 V$MANAGED_STANDBY 에 MRP0 이 없고
--      V$DATAGUARD_STATS 는 no rows 다
--   ⑥ V$LOGSTDBY_TRANSACTION 의 열은 전부 PRIMARY_ 접두어이며
--      SAVEPOINT_SCN·COMMIT_SCN 은 없다 (ORA-00904)
--   ⑦ 이 뷰는 적용이 도는 동안에만 채워진다. 멈춘 뒤의 XID 는
--      DBA_LOGSTDBY_EVENTS 에서 찾고, 그쪽 열 이름은 XIDUSN 이다
--   ⑧ SKIP_TRANSACTION 은 PDB 에서 ORA-65040,
--      적용이 완전히 내려간 상태에서는 ORA-16104 로 거부된다
--   ⑨ 원인이 분명하면 건너뛰기보다 원인을 없애는 편이 낫다.
--      건너뛰면 그 변경은 영원히 반영되지 않는다
--
-- ★ 이것으로 15장을 마친다. 16장에서는 역할 전환을 다룬다.
