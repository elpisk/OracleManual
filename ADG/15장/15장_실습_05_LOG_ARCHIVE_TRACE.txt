 제15장 실습 05 — LOG_ARCHIVE_TRACE 로 추적한다
 대상   : chicago-srv

 소요   : 약 30분

-- ★ 진단의 순서를 다시 정리한다.
--
--   1층  SHOW CONFIGURATION      문제가 있다
--   2층  V$ARCHIVE_DEST 의 ERROR 왜 그런지
--   3층  알림 로그               접속 문자열·프로세스
--   4층  트레이스 파일           전송 과정 자체
--
-- ★ 실습 03 의 ORA-12541 은 2층에서 끝났다.
--   원인이 분명했기 때문이다.
--
-- ★ 4층까지 내려가는 것은
--   "오류는 없는데 느리다" 같은 경우다.
--   그때 전송 과정 자체를 추적한다.

SYS@chicago> COL value FOR a12
SYS@chicago> SELECT name, value FROM v$parameter WHERE name='log_archive_trace';

NAME                 VALUE
-------------------- ------------
log_archive_trace    0

1 row selected.

-- ★ 기본값 0. 꺼져 있다.

--------------------------------------------------------------------------------
 [2] 수준을 정한다
--------------------------------------------------------------------------------

-- ★ 비트마스크다. 값을 더해서 조합한다.
--
--   1     아카이브 목적지 관련 활동
--   2     각 아카이브 로그 파일 이름
--   4     아카이브 목적지별 상태
--   8     아카이브 목적지 활동
--   16    상세 디버깅
--   128   FAL 서버 관련
--   4096  실시간 적용 관련
--
-- ★ 이번에는 12 를 쓴다. 4 + 8 이다.
--   목적지 상태와 활동을 함께 본다.
--
-- ★ 전부 켜는 값(4095)은 쓰지 않는다.
--   트레이스 파일이 폭발적으로 커진다.

SYS@chicago> ALTER SYSTEM SET log_archive_trace=12;

System altered.

SYS@chicago> SELECT name, value FROM v$parameter WHERE name='log_archive_trace';

NAME                 VALUE
-------------------- ------------
log_archive_trace    12

1 row selected.

-- ★ 동적 파라미터이므로 재기동이 필요 없다.

[oracle@chicago-srv ~]$ tail -20 .../trace/alert_chicago.log

2026-08-28T09:41:34.240579+09:00
ALTER SYSTEM SET log_archive_trace=12 SCOPE=BOTH;

-- ★ 알림 로그에 변경 사실이 남는다.
--
-- ★ SCOPE=BOTH 가 자동으로 붙었다.
--   다음 기동에도 유지된다는 뜻이다.
--   켜 둔 채로 잊으면 디스크가 찬다. 반드시 되돌려야 한다.

--------------------------------------------------------------------------------
 [7] 켤 때의 원칙
--------------------------------------------------------------------------------

-- ★ ① 필요한 수준만 켠다.
--      전부 켜는 4095 는 파일이 폭발한다.
--      수준 12 만으로도 tt04 파일이 664KB 였다.
--
-- ★ ② 시간을 정해 둔다.
--      "재현될 때까지" 가 아니라 "30분간" 처럼 정한다.
--
-- ★ ③ 켜기 전에 공간을 확인한다.
--      ADR 이 있는 파일 시스템이 차면 인스턴스에 영향을 준다.
--
-- ★ ④ 끈 뒤 V$PARAMETER 로 0 인지 확인한다.
--      SCOPE=BOTH 로 저장되므로 이 확인이 중요하다.
--
-- ★ ⑤ 오래된 트레이스는 adrci 의 purge 로 정리한다.
--
-- ★ 실무에서 가장 흔한 사고가 ②·④ 를 빠뜨리는 것이다.
--   장애가 끝난 뒤 켜 둔 것을 잊고 몇 달 뒤 디스크가 찬다.

--------------------------------------------------------------------------------
 [8] 정리
--------------------------------------------------------------------------------

-- ★ 이 실습에서 확인한 것
--
--   ① LOG_ARCHIVE_TRACE 는 비트마스크. 12 = 4 + 8
--   ② 동적 파라미터이지만 SCOPE=BOTH 로 저장된다
--   ③ 알림 로그에 변경 사실이 남는다
--   ④ 알림 로그의 LAD:1 은 로컬, LAD:2 는 원격
--   ⑤ Checkpoint not complete 는 리두 크기·수를 검토하라는 신호
--   ⑥ 트레이스는 프로세스별로 나뉜다 (<SID>_<프로세스>_<PID>.trc)
--   ⑦ 실시간 전송은 TTnn 파일에 남으며 가장 크다 (실측 664KB)
--   ⑧ 정상일 때는 Sleeping · No work found 가 반복된다
--   ⑨ 잘못된 값은 음수든 문자열이든 ORA-02017
--   ⑩ 끈 뒤 0 인지 반드시 확인한다
--
-- ★ 다음 실습에서 지금까지의 지표를 하나로 묶는다.
