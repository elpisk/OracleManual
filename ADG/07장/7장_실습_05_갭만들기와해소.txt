--------------------------------------------------------------------------------
 [3] 갭 관찰
--------------------------------------------------------------------------------

-- 15초 뒤 Standby 에서 조회한다.

SYS@boston> SELECT thread#, low_sequence#, high_sequence# FROM v$archive_gap;

   THREAD# LOW_SEQUENCE# HIGH_SEQUENCE#
---------- ------------- --------------
         1            64             65

1 row selected.

SYS@boston> SELECT MAX(sequence#) recv,
  2                MAX(CASE WHEN applied='YES' THEN sequence# END) app
  3            FROM v$archived_log;

      RECV        APP
---------- ----------
        66         61

1 row selected.

-- ★ 두 조회가 서로 다른 것을 말한다.
--
--   V$ARCHIVE_GAP  : 스레드 1의 64~65번이 **비어 있다**
--   RECV / APP     : 66번까지 받았고 61번까지 적용했다
--
-- ★ 주의할 점 — **V$ARCHIVE_GAP 은 "적용하지 않은 것"을 보여 주지 않는다.**
--   "적용해야 하는데 파일이 없는 것"을 보여 준다.
--
--   전송은 계속되고 있었으므로 파일 대부분은 도착해 있었다.
--   갭으로 잡힌 64~65번은 그중 아직 도착하지 않았거나
--   기록이 누락된 구간이다.
--
--   즉 갭이 비어 있다고 해서 뒤처지지 않았다는 뜻이 아니다.
--   지금이 그 예다 — 갭은 두 개뿐인데 적용은 다섯 개나 밀려 있다.

--------------------------------------------------------------------------------
 [4] Primary 쪽에서 본 같은 상황
--------------------------------------------------------------------------------

SYS@chicago> SELECT dest_id, status, applied_seq#, archived_seq#
  2            FROM v$archive_dest_status WHERE dest_id=2;

   DEST_ID STATUS    APPLIED_SEQ# ARCHIVED_SEQ#
---------- --------- ------------ -------------
         2 VALID               63            61

1 row selected.

-- ★ Standby 에서 본 값(적용 61)과 다르다. APPLIED_SEQ# 가 63 이다.
--   ARCHIVED_SEQ# 는 61 인데 APPLIED_SEQ# 가 더 크다. 이상해 보인다.
--
-- ★ 이유는 이 값들이 **Primary 가 마지막으로 확인한 시점**의 정보이기 때문이다.
--   Primary 는 Standby 의 진행 상황을 주기적으로 전달받아 기록한다.
--   그 사이에 시차가 생기고, 두 열의 갱신 시점도 서로 다를 수 있다.
--
-- ★ 결론 — **정확한 판단은 Standby 에서 직접 조회한 값으로 한다.**
--   Primary 쪽 값은 "대략 이쯤 왔다"는 참고용이다.
--   Standby 에 접속할 수 없을 때의 차선책으로 쓴다.

--------------------------------------------------------------------------------
 [5] 오류 재현 — 갭이 있는 상태에서 잘못 대응하기
--------------------------------------------------------------------------------

-- 갭을 발견하고 당황해 적용을 다시 켜려는데,
-- 이미 켜져 있는 줄 모르고 두 번 실행하는 상황이 흔하다.

SYS@boston> ALTER DATABASE RECOVER MANAGED STANDBY DATABASE
  2            USING CURRENT LOGFILE DISCONNECT FROM SESSION;

Database altered.

SYS@boston> ALTER DATABASE RECOVER MANAGED STANDBY DATABASE
  2            USING CURRENT LOGFILE DISCONNECT FROM SESSION;

alter database recover managed standby database using current logfile disconnect from session
*
ERROR at line 1:
ORA-01153: an incompatible media recovery is active

>>> 원인 파악
    첫 번째 명령이 이미 성공했다. MRP 는 하나만 존재할 수 있다.

    ★ 갭 상황에서 특히 이 실수가 잦다.
      첫 명령을 내리고 바로 상태를 조회했는데 아직 따라잡지 못한 것을 보고
      "명령이 안 먹었나" 싶어 다시 내리는 것이다.

      실제로는 잘 돌고 있으며 시간이 필요할 뿐이다.
      갭 다섯 개를 메우는 데도 실측에서 1분 남짓 걸렸다.

>>> 조치
    MRP0 이 있는지부터 확인한다. 있으면 기다린다.

SYS@boston> SELECT process, status, thread#, sequence#, block#
  2            FROM v$managed_standby WHERE process='MRP0';

PROCESS   STATUS        THREAD#  SEQUENCE#     BLOCK#
--------- ------------ -------- ---------- ----------
MRP0      APPLYING_LOG        1         64       2285

    ★ BLOCK# 이 있으면 진행 중이라는 뜻이다.
      몇 초 간격으로 두 번 조회해 BLOCK# 이 늘어나는지 본다.
      늘어나면 따라잡는 중이고, 멈춰 있으면 막힌 것이다.

>>> 재확인
    시간이 지나면 갭이 사라진다. [6] 에서 확인한다.

--------------------------------------------------------------------------------

-- 적용을 켜고 20초 뒤

SYS@boston> COL name FOR a16

SYS@boston> SELECT name, value FROM v$dataguard_stats WHERE name LIKE '%lag';

NAME             VALUE
---------------- --------------------
transport lag    +00 00:00:59
apply lag        +00 00:01:04

2 rows selected.

SYS@boston> SELECT COUNT(*) gaps FROM v$archive_gap;

      GAPS
----------
         0

1 row selected.

-- ★★ **갭은 0 인데 지연은 1분이다.**
--
--   두 값이 다른 것을 말한다.
--     갭   : 빠진 파일이 있는가         → 없다
--     지연 : 얼마나 뒤처져 있는가       → 1분
--
--   파일은 모두 도착했지만 아직 적용 중이라는 뜻이다.
--   **갭 해소와 지연 해소는 다른 단계다.**
--
-- ★ apply lag(64초)이 transport lag(59초)보다 크다.
--   당연한 관계다. 받아야 적용할 수 있으므로 적용이 더 뒤처진다.
--   반대로 나오면 계산 시점이 어긋난 것이다.

-- 더 기다린 뒤

SYS@boston> SELECT process, status, thread#, sequence#, block#
  2            FROM v$managed_standby WHERE process='MRP0';

PROCESS   STATUS        THREAD#  SEQUENCE#     BLOCK#
--------- ------------ -------- ---------- ----------
MRP0      WAIT_FOR_LOG        1         67          0

1 row selected.

-- ★ WAIT_FOR_LOG 로 바뀌었다. 적용할 것이 없어 기다리는 상태다.
--   시퀀스 67 을 기다린다 — 66번까지 전부 적용했다는 뜻이다.
--   따라잡았다.

--------------------------------------------------------------------------------
 [7] 갭은 누가 메우는가
--------------------------------------------------------------------------------

SYS@boston> COL name FOR a14
SYS@boston> COL value FOR a20
SYS@boston> SELECT name, value FROM v$parameter
  2            WHERE name IN ('fal_server','fal_client');

NAME           VALUE
-------------- --------------------
fal_client     boston
fal_server     chicago

2 rows selected.

-- ★ FAL 은 Fetch Archive Log 의 약자다.
--   Standby 가 빠진 아카이브를 발견하면 FAL_SERVER 에 지정된 대상에게
--   요청해 받아 온다. boston 의 FAL_SERVER 가 chicago 이므로
--   Primary 에게 요청한다.
--
--   FAL_CLIENT 는 실습 03 에서 boston 으로 바로잡았다.
--
-- ★ 갭 해소가 오래 걸릴 때의 확인 순서
--   ① V$ARCHIVE_GAP 으로 어느 시퀀스가 빠졌는지 확인한다
--   ② Primary 에서 그 시퀀스의 아카이브 파일이 아직 있는지 본다
--      — 지워졌다면 FAL 로도 가져올 수 없다
--   ③ FAL_SERVER 가 올바른지, 그 대상에 접속되는지 확인한다
--   ④ Standby 의 alert 로그에서 FAL 관련 메시지를 찾는다
--
-- ★ ②가 가장 곤란한 경우다.
--   파일이 이미 지워졌다면 Primary 에서 그 구간의 증분 백업을 받아
--   Standby 에 적용하는 절차를 밟아야 한다.
--   4장에서 FRA 관리를 강조한 이유가 여기에 있다.

--------------------------------------------------------------------------------
 [8] 정리
--------------------------------------------------------------------------------

  · 적용을 멈추고 로그를 전환하면 갭이 생긴다
  · V$ARCHIVE_GAP 은 "빠진 파일"을 보여 준다. "적용하지 않은 것"이 아니다
  · 실측: 갭은 64~65 두 개, 적용은 61 vs 받은 것 66 — 다섯 개 밀림
  · Primary 쪽 APPLIED_SEQ# 는 시차가 있다. 판단은 Standby 값으로 한다
  · 갭 0 과 지연 0 은 다르다. 실측에서 갭 0 인데 지연 1분이었다
  · apply lag 이 transport lag 보다 큰 것이 정상이다
  · MRP0 의 BLOCK# 이 늘어나면 진행 중이다. 조급하게 재실행하지 않는다
  · 갭은 FAL_SERVER 가 메운다. 원본 파일이 남아 있어야 한다
