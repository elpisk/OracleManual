================================================================================
 제7장 실습 08 — 지연 Standby 로 잘못된 DELETE 되살리기
 대상   : chicago-srv Primary · boston-srv Standby
 목표   : 7장 실무 시나리오 "오후에 실행된 잘못된 DELETE" 를 그대로 재현한다.
          적용 지연(DELAY)을 걸고, 실시간 적용이 지연을 무시하는 함정을 확인한 뒤,
          지연 덕분에 남아 있는 행을 Primary 로 되살리고 원래 상태로 돌린다
 소요   : 약 50분 (지연 10분을 실제로 기다리는 구간이 두 번 있다)
 경고   : Primary 의 테이블 행을 실제로 지운다. 개인 실습 환경에서만 수행한다
 변경   : LOG_ARCHIVE_DEST_2 에 DELAY 를 걸었다가 [11] 에서 되돌린다.
          chicago_pdb1 에 사용자 dly 를 만들고 [11] 에서 지운다
 출력   : 이 파일의 출력은 19c 문서와 이 랩의 앞 실습을 근거로 한 예상값이다(미실측).
          시각·SCN·시퀀스는 환경마다 다르다. 실행 후 실측값으로 바꾼다
================================================================================

--------------------------------------------------------------------------------
 [0] 시나리오와 이 랩의 대응
--------------------------------------------------------------------------------

  교안의 구성                              이 랩
  ---------------------------------------  ----------------------------------------
  Primary chicago                          chicago (그대로)
  실시간 적용 Standby boston               — (없다)
  4시간 지연 Standby (세 번째)             boston 이 이 실습 동안 지연 Standby 역할
  지연 4시간, 발견까지 40분                지연 10분, 발견까지 약 3분

-- ★ 랩에는 Standby 가 boston 하나뿐이다. 그래서 boston 에 지연을 걸어
--   "세 번째 Standby" 역할을 시킨다. 실시간 Standby 가 함께 있었다면
--   거기에는 DELETE 가 이미 반영돼 있다 — 이 사실은 [6] 에서 Primary 로 대신 본다.
--
-- ★ 비율은 같게 맞췄다. 교안은 지연 4시간 중 40분이 지난 뒤 발견했다(1/6).
--   랩은 지연 10분 중 약 3분 뒤 발견한다. 남은 시간 안에 멈추는 것이 핵심이다.

--------------------------------------------------------------------------------
 [3] 지연 걸기 — DELAY 는 Primary 쪽 목적지 속성이다
--------------------------------------------------------------------------------

SYS@chicago> ALTER SYSTEM SET log_archive_dest_2=
  2  'service=boston ASYNC NOAFFIRM DELAY=10
  3   valid_for=(online_logfiles,primary_role) db_unique_name=boston' SCOPE=MEMORY;

System altered.

SYS@chicago> SELECT dest_id, delay_mins, status FROM v$archive_dest WHERE dest_id=2;

   DEST_ID DELAY_MINS STATUS
---------- ---------- ---------
         2         10 VALID

-- ★ SCOPE=MEMORY 로 건다. 실습 중 인스턴스가 재기동되면 원래 값으로 돌아오게 하려는 것이다.
--
-- ★ DELAY 는 "전송을 늦추는" 속성이 아니다. 리두는 지금처럼 바로 간다.
--   Standby 가 받은 로그를 **아카이브된 시각부터 10분이 지난 뒤** 적용하라는 뜻이다.
--   그래서 지연 중에도 리두는 Standby 디스크에 있다 — 보호는 그대로다.
--
-- ★ 단위는 분이다. 교안의 4시간이라면 DELAY=240.

--------------------------------------------------------------------------------
 [4] 오류 재현 — 실시간 적용은 DELAY 를 무시한다
--------------------------------------------------------------------------------

SYS@chicago> ALTER SESSION SET CONTAINER=chicago_pdb1;
SYS@chicago> INSERT INTO dly.orders VALUES (1001,'DELAY-TEST',1,SYSDATE);
SYS@chicago> COMMIT;

-- 10초 뒤

[oracle@boston-srv ~]$ sqlplus -s dly/oracle@boston-srv:1521/chicago_pdb1 <<< "SELECT COUNT(*) FROM orders;"

  COUNT(*)
----------
      1001

>>> 원인 파악
    ★★ **지연 10분을 걸었는데 10초 만에 보인다.**

    boston 알림 로그 [예상 — 문구는 버전마다 조금 다르다]
      WARNING: Managed Standby Recovery started with USING CURRENT LOGFILE
      DELAY 10 minutes specified at primary ignored

    실시간 적용은 SRL 에서 리두를 바로 적용한다. 아카이브된 시각을 기다릴 틈이 없다.
    그래서 실시간 적용 중에는 DELAY 가 **조용히 무시**된다. 오류가 아니라 알림 로그의
    경고 한 줄뿐이다.

    ★ 실습 04 에서 본 대로 19c 는 SRL 이 있으면 USING CURRENT LOGFILE 을 주지 않아도
      실시간 적용이다. 그러니 "지연 Standby 를 만들었다" 고 믿었는데 실제로는
      실시간 Standby 인 사고가 쉽게 난다. 사고 날 때 비로소 알게 된다.

    ★ 확인 방법은 v$archive_dest 의 DELAY_MINS 가 아니다(그건 Primary 의 의도일 뿐).
      Standby 의 RECOVERY_MODE 와 실제 행으로 확인한다.

SYS@boston> ALTER DATABASE RECOVER MANAGED STANDBY DATABASE

--
-- boston 알림 로그 [예상]
--   Managed Standby Recovery not using Real Time Apply
--   ... Media Recovery Delayed for 10 minute(s) ...

OPEN_MODE
--------------------
READ ONLY WITH APPLY

-- ★ 여전히 READ ONLY WITH APPLY 다. 적용이 늦게 돌 뿐 켜져 있다.
--   지연 Standby 를 열어 두면 "10분 전의 데이터베이스" 를 조회할 수 있다.

       143 14:12:41  YES

--------------------------------------------------------------------------------

       MRP

OPEN_MODE
--------------------
READ ONLY

-- ★ WITH APPLY 가 사라졌다. 적용을 멈춘 READ ONLY 다.
--   교안의 말대로 이 상태의 조회에는 Active Data Guard 라이선스가 필요 없다
--   (적용과 조회가 동시에 일어나지 않기 때문이다).
--   이 랩은 이미 열려 있어 그대로 쓴다. MOUNT 상태였다면
--     ALTER DATABASE OPEN READ ONLY;
--     ALTER PLUGGABLE DATABASE chicago_pdb1 OPEN READ ONLY;

-- 정말 DELETE 이전에 멈췄는지 두 가지로 확인한다.

SYS@boston> SELECT current_scn FROM v$database;

CURRENT_SCN
-----------
    4717980

-- ① Standby 의 CURRENT_SCN 은 "마지막으로 적용한 SCN" 이다.
--    4717980 < 4718203(사고 직전) → DELETE 이전이다.

[oracle@boston-srv ~]$ sqlplus -s dly/oracle@boston-srv:1521/chicago_pdb1 <<< "SELECT COUNT(*) FROM orders;"

  COUNT(*)
----------
      1001

-- ② 행이 1001개 그대로 있다. 이것이 결정적 증거다.
--
-- ★ 실무에서 사고 SCN 을 모를 때는 ② 로 판단한다 — 사라진 행이 Standby 에 보이면 이전이다.
-- ★ 1001번(DELAY-TEST) 이 보이는 것에 주목한다. [4] 에서 실시간 적용으로 이미 들어간 행이다.

--------------------------------------------------------------------------------
 [9] 되살리기 — Database Link 로 Primary 에 다시 넣는다
--------------------------------------------------------------------------------

-- Primary 의 PDB 에서 지연 Standby 의 같은 PDB 를 가리키는 링크를 만든다.

[oracle@chicago-srv ~]$ sqlplus dly/oracle@chicago-srv:1521/chicago_pdb1

DLY@chicago_pdb1> CREATE DATABASE LINK stby_lnk
  2            CONNECT TO dly IDENTIFIED BY oracle
  3            USING 'boston-srv:1521/chicago_pdb1';

Database link created.

DLY@chicago_pdb1> SELECT COUNT(*) FROM orders@stby_lnk;

  COUNT(*)
----------
      1001

-- 사라진 행만 골라 넣는다. 사고 뒤에 들어온 행(2001, 2002)은 Primary 에만 있으므로
-- 겹치지 않지만, 겹칠 수 있다고 보고 NOT EXISTS 로 막는다.

DLY@chicago_pdb1> INSERT INTO orders
  2            SELECT * FROM orders@stby_lnk s
  3            WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.order_id = s.order_id);

1001 rows created.

DLY@chicago_pdb1> COMMIT;
DLY@chicago_pdb1> SELECT COUNT(*) FROM orders;

  COUNT(*)
----------
      1003

-- ★ 1001(되살린 행) + 2(사고 뒤 업무) = 1003. 사고 뒤 업무도 잃지 않았다.
--   이것이 Primary 를 Flashback Database 로 되감는 방법과의 차이다 —
--   되감으면 2001·2002 까지 사라진다.
--
-- ★ 원격 쪽(boston)은 READ ONLY 다. 링크를 통한 SELECT 는 되지만
--   링크로 원격에 쓰는 것은 안 된다. 방향을 "Primary 가 끌어온다" 로 잡는 이유다.
--
-- ★ 행이 많으면 Data Pump 를 쓴다. Standby 에서 expdp 는 안 된다
--   (작업 테이블을 만들어야 하는데 READ ONLY 다). 대신 Primary 에서 링크로 끌어온다.
--     impdp dly/oracle@chicago-srv:1521/chicago_pdb1 NETWORK_LINK=stby_lnk
--           TABLES=dly.orders TABLE_EXISTS_ACTION=APPEND
--     (APPEND 는 PK 충돌 행을 넣지 못하고 오류로 남긴다 — 겹침이 있으면 위 INSERT 방식이 낫다)

--------------------------------------------------------------------------------

  2            USING ARCHIVED LOGFILE DISCONNECT FROM SESSION;

--   **사고 이전을 잠시 보관하는 장치**다.

SYS@chicago> ALTER SYSTEM ARCHIVE LOG CURRENT;     -- 되살린 INSERT 를 담은 로그를 보낸다

[oracle@boston-srv ~]$ sqlplus -s dly/oracle@boston-srv:1521/chicago_pdb1 <<< "SELECT COUNT(*) FROM orders;"

  COUNT(*)
----------
      1003

SYS@boston> SELECT name, value FROM v$dataguard_stats WHERE name='apply lag';

NAME             VALUE
---------------- --------------------
apply lag        +00 00:10:xx

-- ★ apply lag 이 10분 안팎이다. 지연 Standby 에서는 이것이 정상 값이다.
--   실습 06 에서 본 "apply lag = 문제" 판단을 지연 Standby 에 그대로 쓰면 오경보가 난다.

--------------------------------------------------------------------------------
 [11] 정리 — 실시간 적용으로 되돌린다
--------------------------------------------------------------------------------

SYS@chicago> ALTER SYSTEM SET log_archive_dest_2=
  2  'service=boston ASYNC NOAFFIRM
  3   valid_for=(online_logfiles,primary_role) db_unique_name=boston' SCOPE=MEMORY;

SYS@boston> ALTER DATABASE RECOVER MANAGED STANDBY DATABASE CANCEL;
SYS@boston> ALTER DATABASE RECOVER MANAGED STANDBY DATABASE DISCONNECT FROM SESSION;
SYS@boston> SELECT recovery_mode FROM v$archive_dest_status WHERE dest_id=1;

RECOVERY_MODE
----------------------------------
MANAGED REAL TIME APPLY

DLY@chicago_pdb1> DROP DATABASE LINK stby_lnk;

SYS@chicago> ALTER SESSION SET CONTAINER=chicago_pdb1;
SYS@chicago> DROP USER dly CASCADE;
SYS@chicago> ALTER SESSION SET CONTAINER=CDB$ROOT;
SYS@chicago> SELECT dest_id, delay_mins FROM v$archive_dest WHERE dest_id=2;

   DEST_ID DELAY_MINS
---------- ----------
         2          0

-- ★ 순서 : Primary 의 DELAY 를 먼저 없앤다 → Standby 를 실시간 적용으로 재기동.
--   반대로 하면 실시간 적용이 DELAY 를 무시하므로 결과는 같지만, 알림 로그에
--   [4] 의 경고가 한 번 더 남는다.

================================================================================
 정리
================================================================================

  · DELAY 는 Primary 목적지(LOG_ARCHIVE_DEST_n)의 속성이다. 단위는 분이다.
    리두는 바로 가고, 적용만 "Standby 에서 아카이브된 뒤 n분" 늦춘다
  · 실시간 적용은 DELAY 를 무시한다. 19c 는 SRL 이 있으면 기본이 실시간 적용이므로
    지연 Standby 는 반드시 USING ARCHIVED LOGFILE 로 적용을 기동한다
    → 확인은 RECOVERY_MODE = MANAGED 와 실제 행으로 한다
  · 사고가 나면 순서는 ① 남은 시간 계산(v$archived_log COMPLETION_TIME + DELAY)
    ② CANCEL ③ DELETE 이전인지 확인(사라진 행이 보이는가, CURRENT_SCN)
    ④ Primary 가 링크로 끌어와 되살림 ⑤ USING ARCHIVED LOGFILE 로 재기동
  · 적용을 멈춘 READ ONLY 조회는 Active Data Guard 라이선스가 필요 없다
  · 지연 Standby 의 apply lag 은 지연 값만큼이 정상이다. 감시 임계값을 따로 둔다
  · Primary Flashback Database 와 달리 사고 뒤의 업무를 잃지 않는다.
    Flashback Query/Table 은 UNDO 가 남아 있을 때만 가능하다 — 40분 뒤라면
