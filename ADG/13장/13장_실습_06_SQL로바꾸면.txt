================================================================================
 제13장 실습 06 — Broker 가 관리하는 것을 SQL 로 바꾸면
 대상   : chicago-srv
 목표   : Broker 가 관리하는 파라미터를 SQL 로 바꿔 보고 무슨 일이 일어나는지
          확인한다. 감지에 기대지 않는 실무 지침을 세운다
 소요   : 약 25분
 변경   : 파라미터를 바꿨다가 되돌린다
================================================================================

--
--   OperationTimeout             30초   Broker 작업의 시간 초과

--

--   Broker 가 구성 전체를 가리키는 서비스를 스스로 만들고
--   ALTER SYSTEM REGISTER 로 리스너에 알린다.
--
--   이름은 Primary 의 DB_UNIQUE_NAME 에 _CFG 를 붙인 형태다.
--   역할이 바뀌어도 이 이름은 유지되므로
--   구성에 접속할 때 어느 노드가 Primary 인지 몰라도 된다.

--------------------------------------------------------------------------------
 [2] 오류 재현 — SQL 로 바꿔 본다
--------------------------------------------------------------------------------

SYS@chicago> ALTER SYSTEM SET log_archive_dest_2='service=boston async
  2    valid_for=(online_logfiles,primary_role) db_unique_name=boston' SCOPE=BOTH;

System altered.

-- ★ 명령이 성공했다. Broker 가 SQL 을 막지는 않는다.
--   여기까지는 12장의 데이터베이스 가드와 SYS 의 관계와 닮았다.

-- 30초 뒤 Broker 에게 물어본다.

Configuration - dg_chicago

--   "Broker 가 감지해서 경고한다" 는 흔한 설명이 여기서는 성립하지 않았다.
--
-- ★ 어긋남을 확인하는 전용 속성이 있으므로 그것도 본다.

DGMGRL> show database 'boston' 'InconsistentLogXptProps'

-- ★ Broker 가 만든 긴 문자열이 사라지고 사람이 적은 짧은 문자열이 들어 있다.
--
-- ★ 정확히 말하면 이렇다.
--   확인한 것은 "30초 안에는 아무 신호도 없었다" 는 사실뿐이다.
--   감지 주기나 대상 항목의 문제일 수 있고 더 기다리면 달라질 수도 있다.
--
--   그러나 실무 지침을 세울 때는 이것으로 충분하다.
--   감지에 기대지 않는다.

>>> 조치

-- ★ 회복 방법이 있다. 속성을 아무거나 다시 적용하면 된다.

 [3] 오류 재현 — 속성 이름과 값을 틀리면
--------------------------------------------------------------------------------

DGMGRL> edit database 'boston' set property 'LogXptMode'='TURBO';

Error: ORA-16790: the value of the configurable property is invalid

Failed.

>>> 원인 파악

-- ★ ORA-16790 은 값이 유효하지 않다는 뜻이다.
--   LogXptMode 가 받는 값은 SYNC / ASYNC / FASTSYNC 셋뿐이다.
--
-- ★ 이름을 틀리면 다른 오류가 난다.

DGMGRL> edit database 'boston' set property 'NoSuchProp'='1';

Error: ORA-16538: no match on requested item

Failed.

-- ★ 두 오류를 구별하면 무엇을 고쳐야 할지 바로 알 수 있다.
--
--   ORA-16790  속성은 있는데 값이 틀렸다
--   ORA-16538  속성 이름 자체가 없다
--
-- ★ 멤버 이름을 틀리면 오류 번호 없이 알려 준다.

DGMGRL> show database 'seattle'

Object "seattle" was not found

-- ★ ORA- 번호가 아니라 문장으로 답한다.
--   DGMGRL 의 오류 표현이 일관되지 않다는 점도 알아 둔다.
--   스크립트에서 결과를 판정할 때 오류 번호만 찾으면 이런 경우를 놓친다.

>>> 조치

-- 속성 이름과 값은 SHOW DATABASE VERBOSE 로 확인한다.
-- 목록에 있는 이름만 쓰고, 값은 현재 값을 참고한다.

DGMGRL> show database 'boston' 'LogXptMode'

  LogXptMode = 'ASYNC'

>>> 재확인

DGMGRL> edit database 'boston' set property 'LogXptMode'='ASYNC';

Property "LogXptMode" updated

-- ★ 올바른 이름과 값을 주면 통과한다.

--------------------------------------------------------------------------------
 [4] 원칙 하나로 정리한다
--------------------------------------------------------------------------------

-- ★ Broker 를 켰으면 Broker 로만 바꾼다.
--
--   이 원칙에는 예외가 거의 없다.
--   Broker 가 관리하지 않는 파라미터(SGA_TARGET, PROCESSES 등)는
--   SQL 로 바꿔도 되지만 구성에 관련된 것은 전부 Broker 로 한다.
--
-- ★ 판단이 애매하면 SHOW DATABASE VERBOSE 의 속성 목록을 본다.
--   거기 있으면 Broker 의 것이다.
--
-- ★ 세 가지 방법의 위험을 비교하면 이렇다.
--
--   방법                       결과
--   -------------------------  ------------------------------------------
--   Broker 명령으로 변경       정상. Intended State 도 함께 바뀐다
--   SQL 로 변경                조용히 어긋난다. 경고가 없을 수 있다
--   Broker 를 끄고 SQL 로 관리 파라미터는 남으므로 동작은 하지만
--                              혼용이 되어 가장 위험하다
--
-- ★ 마지막 항목을 덧붙인다.
--   DG_BROKER_START 를 FALSE 로 바꿔도 파라미터는 그대로 남는다.
--   Broker 가 만든 값이 그 자리에 있으므로 구성은 계속 동작한다.
--   다시 손으로 관리하려면 그 값을 직접 손봐야 한다.
--
--   그래서 Broker 도입은 되돌리기 어려운 결정은 아니지만
--   한 방향으로 정해 두어야 하는 결정이다.

 [6] 정리
--------------------------------------------------------------------------------

-- ★ 이 실습에서 확인한 것
--
--   ① 구성에도 속성이 있다 (14개)
--   ② ConfigurationWideServiceName = chicago_CFG — Broker 가 스스로 등록
--   ③ SQL 로 Broker 파라미터를 바꿔도 명령은 성공한다
--   ④ 실측에서 30초 안에는 경고가 없었고
--      InconsistentProperties 도 비어 있었다
--   ⑤ 속성을 아무거나 다시 적용하면 Broker 형식이 복구된다
--   ⑥ 원칙 — Broker 를 켰으면 Broker 로만 바꾼다
--   ⑦ 속성 값이 틀리면 ORA-16790, 이름이 없으면 ORA-16538
--   ⑧ 멤버 이름을 틀리면 오류 번호 없이 문장으로 답한다
--   ⑨ DGMGRL 명령은 20여 개. sql·export·validate 를 알아 둔다
--
-- ★ 다음 실습에서 재기동을 넘어 구성이 유지되는지 확인하고 정리한다.
