================================================================================
 제13장 실습 03 — 구성 만들기와 ORA-16698
 대상   : chicago-srv (dgmgrl)
 목표   : Primary 로 구성을 만들고 Standby 를 추가한다. 손으로 해 둔 설정이
          걸림돌이 되는 장면을 만나고 왜 그런지 이해한다
 소요   : 약 30분
 변경   : Broker 구성 dg_chicago 생성
================================================================================

--------------------------------------------------------------------------------
 [1] Primary 로 구성을 만든다
--------------------------------------------------------------------------------

[oracle@chicago-srv ~]$ dgmgrl sys/oracle@chicago

DGMGRL> create configuration 'dg_chicago' as
> primary database is 'chicago'
> connect identifier is chicago;

Configuration "dg_chicago" created with primary database "chicago"

-- ★ 세 부분으로 읽는다.
--
--   'dg_chicago'                  구성의 이름. 아무거나 정해도 된다
--   primary database is 'chicago' DB_UNIQUE_NAME 이다
--   connect identifier is chicago tnsnames 별칭이다
--
-- ★ 세 번째가 헷갈리기 쉽다.
--   DB_UNIQUE_NAME 과 별칭이 우연히 같은 이름이라 구별이 안 보이지만
--   둘은 다른 것이다.
--   별칭이 chicago_dg 였다면 connect identifier is chicago_dg 로 적는다.
--
-- ★ 작은따옴표는 이름에 대소문자나 특수문자가 있을 때 필요하다.
--   습관적으로 붙여 두면 안전하다.

DGMGRL> show configuration

Configuration - dg_chicago

  Protection Mode: MaxPerformance
  Members:
  chicago - Primary database

Fast-Start Failover:  Disabled

Configuration Status:
DISABLED

-- ★ Configuration Status 가 DISABLED 다.
--   만들었다고 바로 동작하는 것이 아니라 활성화 단계가 따로 있다.
--
-- ★ Protection Mode 가 MaxPerformance 인 것은
--   현재 데이터베이스의 보호 모드를 그대로 가져온 것이다.
--   2장에서 다룬 그 값이며 Broker 의 표기는
--   MaxPerformance / MaxAvailability / MaxProtection 이다.
--   SQL 의 MAXIMUM PERFORMANCE 와 표기만 다르다.

--------------------------------------------------------------------------------
 [2] 오류 재현 — Standby 를 추가하려 하면
--------------------------------------------------------------------------------

DGMGRL> add database 'boston' as
> connect identifier is boston;

Error: ORA-16698: member has a LOG_ARCHIVE_DEST_n parameter with SERVICE attribute set

Failed.

>>> 원인 파악

-- ★ 메시지가 명확하다.
--   추가하려는 멤버에 SERVICE 속성을 가진 LOG_ARCHIVE_DEST_n 이
--   이미 설정되어 있다는 것이다.

SYS@boston> COL value FOR a76
SYS@boston> COL name FOR a26
SYS@boston> SELECT name, value FROM v$parameter
  2            WHERE name IN ('log_archive_dest_2','log_archive_dest_state_2')
  3            ORDER BY name;

NAME                       VALUE
-------------------------- --------------------------------------------------
log_archive_dest_2         service=chicago async
                           valid_for=(online_logfile,primary_role)
                           db_unique_name=chicago
log_archive_dest_state_2   ENABLE

2 rows selected.

-- ★ 5장에서 DUPLICATE 의 SPFILE 절로 설정한 값이고
--   12장까지 그대로 쓰던 것이다.
--
--   잘못된 값이 아니다. Broker 가 그 자리를 자기가 쓰겠다고 요구할 뿐이다.
--
-- ★ Broker 의 원칙은 "내가 관리하는 것은 내가 만든다" 이다.
--
--   사람이 적어 둔 값과 Broker 가 만들 값이 공존하면
--   어느 쪽이 진짜인지 알 수 없게 된다.
--   역할 전환이 일어나면 그 값들이 서로 어긋나고 그때는 이미 늦다.
--
--   그래서 인수 시점에 자리를 비우라고 요구한다.
--   오류 메시지가 "충돌한다" 가 아니라 "설정되어 있다" 인 것도 그 때문이다.
--   값이 맞고 틀리고를 따지지 않는다.
--
-- ★ 이것이 실무에서 Broker 도입의 첫 관문이다.
--   이미 손으로 운영하던 구성을 Broker 로 옮길 때 반드시 만난다.

>>> 조치

-- 양쪽의 LOG_ARCHIVE_DEST_2 를 비운다.
-- 1번(로컬 아카이브)은 SERVICE 속성이 없으므로 그대로 둔다.

SYS@boston> ALTER SYSTEM SET log_archive_dest_2='' SCOPE=BOTH;

System altered.

SYS@chicago> ALTER SYSTEM SET log_archive_dest_2='' SCOPE=BOTH;

System altered.

-- ★ Primary 쪽도 비우는 이유는 Broker 가 그 자리에 자기 값을 쓸 것이기 때문이다.
--
-- ★ 주의 — 이 순간 전송이 끊긴다.
--   리두는 Standby 로 가지 않고 Primary 에 남는다.
--   Broker 가 목적지를 만든 뒤 따라가므로 데이터를 잃지는 않지만
--   운영에서는 변경 시간대를 잡아 두는 것이 안전하다.
--
--   이 장의 절차 중 서비스에 영향을 주는 단계는 여기 하나뿐이다.

>>> 재확인

DGMGRL> add database 'boston' as
> connect identifier is boston;

Database "boston" added

-- ★ 이번에는 성공했다.

--------------------------------------------------------------------------------
 [3] 아직 활성화되지 않았다
--------------------------------------------------------------------------------

DGMGRL> show configuration

Configuration - dg_chicago

  Protection Mode: MaxPerformance
  Members:
  chicago - Primary database
    boston  - Physical standby database (disabled)
      ORA-16905: The member was not enabled yet.

Fast-Start Failover:  Disabled

Configuration Status:
SUCCESS   (status updated 12 seconds ago)

-- ★ ORA-16905 는 오류가 아니라 상태 안내다.
--   "멤버가 아직 활성화되지 않았다" 는 뜻이며 (disabled) 표시와 짝을 이룬다.
--
-- ★ 표시 방식을 눈여겨본다.
--
--   chicago - Primary database
--     boston  - Physical standby database (disabled)
--
--   boston 이 chicago 아래로 들여쓰기되어 있다.
--   Broker 는 들여쓰기로 리두 경로를 그림처럼 보여 준다.
--   10장의 Far Sync 나 계단식 구성이라면 단계가 더 들어간다.
--
-- ★ Configuration Status 가 SUCCESS 인 것도 주목한다.
--   구성 자체는 정상이고 멤버 하나가 비활성일 뿐이다.
--   구성 상태와 멤버 상태가 따로 판정된다.

--------------------------------------------------------------------------------
 [4] 정리
--------------------------------------------------------------------------------

-- ★ 이 실습에서 확인한 것
--
--   ① CREATE CONFIGURATION 은 Primary 하나로 시작한다
--   ② connect identifier 는 tnsnames 별칭이다
--   ③ 만든 직후 Configuration Status 는 DISABLED
--   ④ 손으로 설정한 LOG_ARCHIVE_DEST_n 이 있으면 ORA-16698
--   ⑤ Broker 의 원칙 — 내가 관리하는 것은 내가 만든다
--   ⑥ 양쪽 dest_2 를 비운 뒤 추가한다. 이때 전송이 잠시 끊긴다
--   ⑦ 추가 후에는 (disabled) 와 ORA-16905
--   ⑧ 들여쓰기가 리두 경로를 나타낸다
--
-- ★ 다음 실습에서 활성화한다.
