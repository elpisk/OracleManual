================================================================================
 제13장 실습 02 — Broker 켜기
 대상   : chicago-srv, boston-srv
 목표   : DG_BROKER_START 를 켜고 DMON 프로세스를 확인한다. 오류가
          ORA-16525 에서 ORA-16532 로 바뀌는 것을 읽는다
 소요   : 약 20분
 변경   : dg_broker_start=TRUE (양쪽, SCOPE=BOTH)
================================================================================

--------------------------------------------------------------------------------
 [1] 켠다
--------------------------------------------------------------------------------

SYS@chicago> ALTER SYSTEM SET dg_broker_start=TRUE SCOPE=BOTH;

System altered.

SYS@chicago> SELECT value FROM v$parameter WHERE name='dg_broker_start';

VALUE
------
TRUE

1 row selected.

SYS@boston> ALTER SYSTEM SET dg_broker_start=TRUE SCOPE=BOTH;

System altered.

-- ★ 재기동이 필요 없다. 동적 파라미터다.
--
-- ★ SCOPE=BOTH 로 주는 이유는 다음 기동에도 유지되게 하기 위해서다.
--   MEMORY 로만 주면 재기동 후 Broker 가 꺼지고
--   구성은 남아 있는데 관리자가 없는 상태가 된다.
--
-- ★ 양쪽 모두 켜야 한다. 한쪽만 켜면 DMON 끼리 통신할 수 없다.

--------------------------------------------------------------------------------
 [2] DMON 프로세스
--------------------------------------------------------------------------------

[oracle@chicago-srv ~]$ ps -ef | grep -i [d]mon
oracle   20522     1  0 18:16 ?        00:00:00 ora_dmon_chicago

[oracle@boston-srv ~]$ ps -ef | grep -i [d]mon
oracle   24247     1  0 18:16 ?        00:00:00 ora_dmon_boston

-- ★ 프로세스 이름은 ora_dmon_<SID> 다.
--   MRP0 이나 RFS 처럼 백그라운드 프로세스의 하나다.

SYS@chicago> SELECT pname, spid FROM v$process
  2            WHERE pname LIKE 'DMON%' OR pname LIKE 'NSV%';

PNAME SPID
----- ------------------------
DMON  20522

1 row selected.

-- ★ V$PROCESS 에서도 보인다. SPID 가 OS 프로세스 ID 와 일치한다.
--
-- ★ NSV 도 함께 조회한 이유가 있다.
--   NSVn 은 Broker 가 상대 노드와 통신할 때 쓰는 프로세스인데
--   구성이 아직 없으므로 뜨지 않았다.
--   실습 04 이후에 다시 조회하면 나타난다.

--------------------------------------------------------------------------------
 [3] 오류가 바뀐다
--------------------------------------------------------------------------------

[oracle@chicago-srv ~]$ dgmgrl -silent sys/oracle@chicago "show configuration"

Connected to "chicago"
ORA-16532: Oracle Data Guard broker configuration does not exist

Configuration details cannot be determined by DGMGRL

>>> 원인 파악

-- ★ 실습 01 에서는 ORA-16525 였다. 지금은 ORA-16532 다.
--   한 걸음 나아갔다.
--
--   ORA-16525  broker is not yet available
--              → DMON 이 없다
--
--   ORA-16532  broker configuration does not exist
--              → DMON 은 응답하는데 관리할 구성이 없다
--
-- ★ 오류가 바뀌었다는 것 자체가 진전의 신호다.
--   같은 오류가 반복되면 조치가 효과가 없었다는 뜻이고,
--   오류가 바뀌면 한 단계 넘어갔다는 뜻이다.
--
-- ★ 12장에서 ORA-26676 을 고치니 ORA-26786 이 드러났던 것과 같은 구조다.

>>> 조치

-- 구성을 만든다. 실습 03 에서 한다.

>>> 재확인

-- 지금은 구성이 없는 것이 정상이므로 확인할 것은
-- DMON 이 살아 있다는 사실뿐이다.

SYS@chicago> SELECT count(*) dmon FROM v$process WHERE pname='DMON';

      DMON
----------
         1

1 row selected.

 [4] Broker 전용 로그가 생겼다
--------------------------------------------------------------------------------

[oracle@chicago-srv ~]$ ls -l $ORACLE_BASE/diag/rdbms/chicago/chicago/trace/drc*.log

-- ★ 이름 규칙은 drc<db_unique_name>.log 다.
--   chicago 에서는 drcchicago.log, boston 에서는 drcboston.log.
--
-- ★ 알림 로그와 별개다.
--   Broker 관련 진단은 이 파일을 먼저 본다.
--   실습 05 에서 내용을 읽는다.
--
-- ★ 경로는 추측하지 말고 확인한다.
--   10장·12장에서 배운 대로 V$DIAG_INFO 를 쓰거나
--   실습 05 의 SHOW DATABASE VERBOSE 출력에 경로가 나온다.

--------------------------------------------------------------------------------
 [5] 아직 아무것도 바뀌지 않았다
--------------------------------------------------------------------------------

SYS@chicago> COL value FOR a76
SYS@chicago> COL name FOR a24
SYS@chicago> SELECT name, value FROM v$parameter
  2            WHERE name IN ('log_archive_dest_2','fal_server') ORDER BY name;

NAME                     VALUE
------------------------ ----------------------------------------------------------
fal_server               boston
log_archive_dest_2       service=boston async noaffirm
                            valid_for=(online_logfiles,primary_role)
                            db_unique_name=boston

2 rows selected.

-- ★ Broker 를 켰지만 파라미터는 그대로다.
--
--   Broker 를 켜는 것과 Broker 가 관리를 인수하는 것은 다르다.
--   구성을 만들고 활성화해야 인수가 시작된다.
--
-- ★ 복제도 그대로 동작한다.

SYS@boston> COL recovery_mode FOR a28
SYS@boston> SELECT dest_id, status, recovery_mode
  2            FROM v$archive_dest_status WHERE dest_id=1;

   DEST_ID STATUS    RECOVERY_MODE
---------- --------- ----------------------------
         1 VALID     MANAGED REAL TIME APPLY

1 row selected.

-- ★ Broker 를 켜는 것 자체는 서비스에 영향을 주지 않는다.
--   안심하고 켤 수 있다.
--   영향을 주는 단계는 실습 04 의 "목적지 비우기" 다.
