 제1장 실습 05 — 구성 전 점검표
 대상   : chicago-srv Primary / boston-srv Standby
 목표   : Data Guard 구성을 세우기 전에 두 노드에서 확인해야 할 항목을 조회로
          점검하고, 무엇이 일치해야 하며 무엇은 달라도 되는지 구분한다
 소요   : 약 25분

--------------------------------------------------------------------------------
 [1] 오류 재현 — 조회를 시작하기도 전에 막힌다
--------------------------------------------------------------------------------

-- 두 노드를 오가며 같은 조회를 반복하는 실습이다.
-- 터미널을 옮겨 다니다 보면 다음 실수가 반드시 한 번은 나온다.

[oracle@boston-srv ~]$ export ORACLE_SID=chicago     # ← 노드는 boston 인데 SID 는 chicago
[oracle@boston-srv ~]$ sqlplus -s / as sysdba

SYS> SELECT 1 FROM dual;
SELECT 1 FROM dual
*
ERROR at line 1:
ORA-01034: ORACLE not available
Process ID: 0
Session ID: 0 Serial number: 0


>>> 원인 파악
    ORA-01034 는 "지정한 ORACLE_SID 의 인스턴스가 이 서버에 없다" 는 뜻이다.
    boston-srv 에는 boston 인스턴스만 있고 chicago 인스턴스는 없다.
    Process ID 가 0 인 것도 단서다. 붙을 프로세스 자체가 없었다는 뜻이다.

    Data Guard 실습에서 이 오류가 유독 잦은 이유가 있다.
    두 노드의 DB_NAME 이 chicago 로 같기 때문에 SID 와 DB_NAME 을 혼동하기 쉽다.
    인스턴스를 고르는 값은 DB_NAME 이 아니라 ORACLE_SID(=DB_UNIQUE_NAME)다.

>>> 조치

[oracle@boston-srv ~]$ export ORACLE_SID=boston
[oracle@boston-srv ~]$ sqlplus -s / as sysdba

>>> 재확인

SYS@boston> SELECT instance_name, status FROM v$instance;

INSTANCE_NAME    STATUS
---------------- ------------
boston           OPEN

1 row selected.

-- 습관 : 조회 전에 항상 instance_name 을 먼저 찍어 본다.
--        이 한 줄이 이후의 모든 혼란을 막아 준다.

 [3] 점검 항목 2 — 플랫폼과 엔디안
--------------------------------------------------------------------------------

SYS@chicago> COL platform_name FOR a34
SYS@chicago> SELECT d.platform_id, d.platform_name, t.endian_format
  2              FROM v$database d JOIN v$transportable_platform t
  3                ON d.platform_name = t.platform_name;

PLATFORM_ID PLATFORM_NAME                      ENDIAN_FORMAT
----------- ---------------------------------- --------------
         13 Linux x86 64-bit                   Little

1 row selected.

SYS@boston> COL platform_name FOR a34
SYS@boston> SELECT d.platform_id, d.platform_name, t.endian_format
  2             FROM v$database d JOIN v$transportable_platform t
  3               ON d.platform_name = t.platform_name;

PLATFORM_ID PLATFORM_NAME                      ENDIAN_FORMAT
----------- ---------------------------------- --------------
         13 Linux x86 64-bit                   Little

1 row selected.

-- 판정 : 일치. 플랫폼 ID 13, Little endian.
--
-- 이 조인 한 줄로 플랫폼명과 엔디안을 동시에 얻는다는 점을 기억해 둔다.
-- V$DATABASE 만으로는 엔디안을 알 수 없고,
-- V$TRANSPORTABLE_PLATFORM 만으로는 "내가 어느 플랫폼인지" 를 알 수 없다.
--
-- 혼합 플랫폼 구성이 아예 불가능한 것은 아니지만 제약이 많다.
-- 구축 전에 My Oracle Support 413484.1(physical) / 1085687.1(logical) 을
-- 반드시 확인한다.

 [4] 점검 항목 3 — 문자셋과 시간대
--------------------------------------------------------------------------------

SYS@chicago> COL parameter FOR a30
SYS@chicago> COL value FOR a20
SYS@chicago> SELECT parameter, value FROM nls_database_parameters
  2             WHERE parameter IN ('NLS_CHARACTERSET','NLS_NCHAR_CHARACTERSET',
  3                                 'NLS_LANGUAGE','NLS_TERRITORY','NLS_RDBMS_VERSION');

PARAMETER                      VALUE
------------------------------ --------------------
NLS_RDBMS_VERSION              19.0.0.0.0
NLS_NCHAR_CHARACTERSET         AL16UTF16
NLS_CHARACTERSET               AL32UTF8
NLS_TERRITORY                  AMERICA
NLS_LANGUAGE                   AMERICAN

5 rows selected.

SYS@boston> (동일 조회)

PARAMETER                      VALUE
------------------------------ --------------------
NLS_RDBMS_VERSION              19.0.0.0.0
NLS_NCHAR_CHARACTERSET         AL16UTF16
NLS_CHARACTERSET               AL32UTF8
NLS_TERRITORY                  AMERICA
NLS_LANGUAGE                   AMERICAN

5 rows selected.

-- 판정 : 일치.
--
-- physical standby 는 블록 단위 복제이므로 문자셋이 다를 수 없다.
-- 그런데도 이 항목을 점검표에 넣는 이유는, 구축 실수로 다른 문자셋의
-- 데이터베이스를 미리 만들어 두고 그 위에 DUPLICATE 를 시도하다 헤매는
-- 경우가 실제로 있기 때문이다.

SYS@chicago> SELECT dbtimezone, sessiontimezone FROM dual;

DBTIME SESSIONTIMEZONE
------ ---------------------------
+00:00 +09:00

1 row selected.

SYS@boston> SELECT dbtimezone, sessiontimezone FROM dual;

DBTIME SESSIONTIMEZONE
------ ---------------------------
+00:00 +09:00

1 row selected.

-- 판정 : DBTIMEZONE 일치(+00:00).
--
-- 구분해서 볼 것 :
--   DBTIMEZONE      — 데이터베이스에 저장된 값. 양쪽이 같아야 한다.
--   SESSIONTIMEZONE — 접속한 클라이언트의 설정. 달라도 아무 문제 없다.
--                     여기서 +09:00 인 것은 접속 세션의 OS 시간대일 뿐이다.
--
-- "무엇이 맞아야 하고 무엇은 달라도 되는가" 를 구분하는 것이 점검의 핵심이다.

 [5] 점검 항목 4 — 주요 초기화 파라미터
--------------------------------------------------------------------------------

SYS@chicago> COL name FOR a28
SYS@chicago> COL value FOR a44
SYS@chicago> SELECT name, value FROM v$parameter
  2             WHERE name IN ('db_name','db_unique_name','db_block_size','compatible',
  3                            'log_archive_config','remote_login_passwordfile','db_files')
  4             ORDER BY name;

NAME                         VALUE
---------------------------- --------------------------------------------
compatible                   19.0.0
db_block_size                8192
db_files                     200
db_name                      chicago
db_unique_name               chicago
log_archive_config           dg_config=(chicago,boston)
remote_login_passwordfile    EXCLUSIVE

7 rows selected.

SYS@boston> (동일 조회)

NAME                         VALUE
---------------------------- --------------------------------------------
compatible                   19.0.0
db_block_size                8192
db_files                     200
db_name                      chicago
db_unique_name               boston
log_archive_config           DG_CONFIG=(chicago,boston)
remote_login_passwordfile    EXCLUSIVE

7 rows selected.

-- 판정
--   db_name           chicago = chicago      → 일치해야 한다. OK
--   db_block_size     8192 = 8192            → 일치해야 한다. OK
--   compatible        19.0.0 = 19.0.0        → 일치해야 한다. OK
--   db_files          200 = 200              → 일치해야 한다. OK
--   db_unique_name    chicago ≠ boston       → 달라야 한다. OK
--   log_archive_config  같은 두 이름을 나열   → 대소문자 표기는 무관. OK
--   remote_login_passwordfile  EXCLUSIVE     → 양쪽 모두 필요하다. OK
--
-- log_archive_config 가 한쪽은 소문자, 한쪽은 대문자로 보이는 것은
-- 설정할 때 입력한 문자열이 그대로 저장되기 때문이며 동작에는 영향이 없다.
-- 다만 문서화 관점에서는 표기를 통일해 두는 편이 낫다.

 [7] 점검표 정리
--------------------------------------------------------------------------------

  항목                     같아야 함  확인 방법
  ------------------------ ---------- ----------------------------------------
  릴리스 / 에디션          O          V$VERSION.BANNER_FULL
  플랫폼 ID / 엔디안       O          V$DATABASE ⋈ V$TRANSPORTABLE_PLATFORM
  NLS_CHARACTERSET         O          NLS_DATABASE_PARAMETERS
  DBTIMEZONE               O          SELECT dbtimezone FROM dual
  DB_NAME                  O          V$PARAMETER
  DB_BLOCK_SIZE            O          V$PARAMETER
  COMPATIBLE               O          V$PARAMETER
  DB_FILES                 O          V$PARAMETER
  REMOTE_LOGIN_PASSWORDFILE O(EXCLUSIVE) V$PARAMETER
  ------------------------ ---------- ----------------------------------------
  DB_UNIQUE_NAME           X (달라야) V$PARAMETER
  SESSIONTIMEZONE          X (무관)   SELECT sessiontimezone FROM dual
  하드웨어 사양            X (무관)   —
  ------------------------ ---------- ----------------------------------------
  양방향 이름 해석         필수       /etc/hosts, ping
  ARCHIVELOG 모드 (Primary) 필수      V$DATABASE.LOG_MODE (4장)
  FORCE LOGGING (Primary)   필수      V$DATABASE.FORCE_LOGGING (4장)
  Standby Redo Log          필수      V$LOGFILE (4장)
