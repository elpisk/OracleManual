 제3장 실습 04 — LOG_ARCHIVE_CONFIG 의 DG_CONFIG
 대상   : chicago-srv Primary
 목표   : DG_CONFIG 가 하는 일을 확인하고, 비웠을 때 무슨 일이 일어나는지(그리고
          무슨 일이 일어나지 않는지) 실측으로 판단한다
 소요   : 약 20분
 되돌리기 : 실습 끝에 dg_config=(chicago,boston) 로 복원

--------------------------------------------------------------------------------
 [1] 현재 값 확인
--------------------------------------------------------------------------------

SYS@chicago> SET LINES 200
SYS@chicago> COL value FOR a60
SYS@chicago> SELECT name, value FROM v$parameter
  2            WHERE name IN ('log_archive_config','db_unique_name',
  3                           'fal_server','fal_client');

NAME                 VALUE
-------------------- ------------------------------------------------------------
fal_client           chicago
fal_server           boston
log_archive_config   dg_config=(chicago,boston)
db_unique_name       chicago

4 rows selected.

-- DG_CONFIG 에는 구성에 속한 모든 DB_UNIQUE_NAME 을 나열한다.
-- 이 목록이 하는 일은 두 가지다.
--   ① 목적지에 지정할 수 있는 DB_UNIQUE_NAME 을 제한한다
--   ② 어떤 구성원이 보낸 리두를 받아들일지 정한다
--
-- FAL_SERVER / FAL_CLIENT 도 함께 봐 둔다.
--   FAL = Fetch Archive Log. 갭이 생겼을 때 빠진 로그를 요청하는 경로다.
--   chicago 의 FAL_SERVER 가 boston 이라는 것은
--   "갭이 생기면 boston 에게 요청하겠다" 는 뜻이다.
--   Primary 에 이 값을 두는 이유는 역할 전환 이후를 대비하기 위해서다.

--------------------------------------------------------------------------------
 [2] DG_CONFIG 의 검증 기능 — 2장에서 본 것
--------------------------------------------------------------------------------

-- 목록에 없는 이름을 목적지에 지정하면 거부된다. (2장 실습 02 에서 재현)
--
--   SYS@chicago> ALTER SYSTEM SET log_archive_dest_2 =
--     'service=boston ASYNC NOAFFIRM
--      valid_for=(online_logfiles,primary_role) db_unique_name=wrongname' SCOPE=BOTH;
--   ERROR at line 1:
--   ORA-02097: parameter cannot be modified because specified value is invalid
--   ORA-16053: DB_UNIQUE_NAME wrongname is not in the Data Guard Configuration
--
-- ORA-16053 이 바로 이 목록에 의한 검증이다.
-- 리두가 엉뚱한 데이터베이스로 가는 사고를 막아 준다.

--------------------------------------------------------------------------------
 [3] 오류 재현(?) — 값을 비워 본다
--------------------------------------------------------------------------------

SYS@chicago> ALTER SYSTEM SET log_archive_config='' SCOPE=BOTH;

System altered.

SYS@chicago> ALTER SYSTEM SET log_archive_dest_2 =
  2    'service=boston ASYNC NOAFFIRM
  3     valid_for=(online_logfiles,primary_role) db_unique_name=boston' SCOPE=BOTH;

System altered.

-- ★ 여기서 첫 번째 관찰: db_unique_name=boston 이 그대로 통과했다.
--   목록이 비어 있으니 검증할 기준 자체가 없었던 것이다.
--   방금 전까지 ORA-16053 으로 오배송을 막아 주던 안전망이 사라졌다.

SYS@chicago> ALTER SYSTEM ARCHIVE LOG CURRENT;

System altered.

SYS@chicago> COL error FOR a48
SYS@chicago> SELECT dest_id, status, error
  2            FROM v$archive_dest_status WHERE dest_id = 2;

   DEST_ID STATUS    ERROR
---------- --------- ------------------------------------------------
         2 VALID

1 row selected.


>>> 원인 파악 — 왜 아무 일도 일어나지 않았나
    기대와 달리 전송이 멈추지 않았다. 목적지는 VALID 이고 리두도 계속 간다.

    이미 확립된 연결과 이미 설정된 목적지는 DG_CONFIG 를 비운 것만으로
    즉시 끊기지 않기 때문이다. DG_CONFIG 는 런타임에 매 전송을 검사하는
    스위치가 아니라, 설정 시점과 재기동 시점에 작동하는 검증 장치다.

    ★ 그렇다고 비워도 된다는 뜻은 결코 아니다. 비어 있으면 다음이 무너진다.

      ① 새 목적지를 추가할 때 검증이 사라진다
         → 오타 하나로 리두가 엉뚱한 곳으로 갈 수 있다
      ② Broker 구성 생성이 실패한다 (13장)
         → Broker 는 이 파라미터를 구성 정의의 근거로 삼는다
      ③ 인스턴스 재기동 이후가 위험하다
         → 목적지 파라미터가 다시 해석되는 시점에 기준이 없다

    즉 DG_CONFIG 는 "지금 당장 무언가를 막는 스위치" 가 아니라
    "실수를 걸러 주는 안전망" 이다.
    없어도 잘 돌아가는 것처럼 보이지만, 사고가 났을 때 막아 주지 못한다.
    발견이 늦어지는 만큼 위험이 길게 남는다는 점에서 오히려 더 나쁘다.

>>> 조치 — 값을 복원한다

SYS@chicago> ALTER SYSTEM SET log_archive_config='dg_config=(chicago,boston)' SCOPE=BOTH;

System altered.

SYS@chicago> ALTER SYSTEM SET log_archive_dest_2 =
  2    'service=boston ASYNC NOAFFIRM
  3     valid_for=(online_logfiles,primary_role) db_unique_name=boston' SCOPE=BOTH;

System altered.

SYS@chicago> ALTER SYSTEM ARCHIVE LOG CURRENT;

System altered.

-- 다만 문서화 관점에서는 표기를 통일해 두는 편이 낫다.
--
-- 중요한 것은 양쪽 모두 같은 두 이름을 담고 있다는 사실이다.
-- 한쪽에만 넣으면 그 방향으로만 동작한다.

--------------------------------------------------------------------------------
 [5] DG_CONFIG 관리 원칙
--------------------------------------------------------------------------------

  ① 구성에 데이터베이스를 추가할 때 **모든 노드의** DG_CONFIG 에 새 이름을 넣는다
  ② Far Sync 인스턴스도 목록에 포함시킨다 (10장)
     — 리두 경로에 있는 모든 구성원이 대상이다
  ③ 값을 비우지 않는다
     — 문제를 즉시 일으키지 않아 발견이 늦어지고, 그만큼 위험이 길게 남는다
  ④ Broker 를 쓰면 Broker 가 이 값을 관리한다. 그때부터는 손으로 고치지 않는다 (13장)
  ⑤ 대소문자는 무관하다. 다만 표기는 통일한다

SYS@chicago> EXIT
SYS@boston> EXIT
