================================================================================
 제3장 실습 01 — tnsnames.ora 구성과 tnsping 검증
 대상   : chicago-srv Primary / boston-srv Standby
 목표   : 양쪽 노드에 대칭적인 넷 서비스 이름을 구성하고, tnsping 이 무엇을
          확인해 주고 무엇은 확인해 주지 않는지 구분한다
 소요   : 약 20분
 변경   : 없음 (전부 조회)
================================================================================

--------------------------------------------------------------------------------
 [1] 양쪽 tnsnames.ora 확인
--------------------------------------------------------------------------------

[oracle@chicago-srv ~]$ cat $ORACLE_HOME/network/admin/tnsnames.ora

CHICAGO =
  (DESCRIPTION =
    (ADDRESS_LIST =
      (ADDRESS = (PROTOCOL = TCP)(HOST = chicago-srv)(PORT = 1521))
    )
    (CONNECT_DATA =
      (SERVICE_NAME = chicago)
    )
  )

BOSTON =
  (DESCRIPTION =
    (ADDRESS_LIST =
      (ADDRESS = (PROTOCOL = TCP)(HOST = boston-srv.localdomain)(PORT = 1521))
    )
    (CONNECT_DATA =
      (SERVICE_NAME = boston)
    )
  )

CHICAGO_DG =
  (DESCRIPTION =
    (ADDRESS = (PROTOCOL = TCP)(HOST = chicago-srv)(PORT = 1521))
    (CONNECT_DATA =
      (SERVICE_NAME = chicago_DGMGRL)
    )
  )

BOSTON_DG =
  (DESCRIPTION =
    (ADDRESS = (PROTOCOL = TCP)(HOST = boston-srv)(PORT = 1521))
    (CONNECT_DATA =
      (SERVICE_NAME = boston_DGMGRL)
    )
  )

-- 확인할 점
--   ① 네 개 별칭이 모두 있다. CHICAGO / BOSTON / CHICAGO_DG / BOSTON_DG
--   ② boston-srv 에도 같은 파일이 있어야 한다 (역할 전환 대비)
--   ③ _DG 항목은 Broker 전용이며 13장부터 쓴다
--   ④ BOSTON 은 boston-srv.localdomain, BOSTON_DG 는 boston-srv 로 표기가 섞여 있다
--      둘 다 /etc/hosts 에 있어 동작하지만 실무에서는 통일하는 편이 낫다

--------------------------------------------------------------------------------
 [2] sqlnet.ora 확인
--------------------------------------------------------------------------------

[oracle@chicago-srv ~]$ cat $ORACLE_HOME/network/admin/sqlnet.ora

SQLNET.ALLOWED_LOGON_VERSION_SERVER=11
SQLNET.ALLOWED_LOGON_VERSION_CLIENT=11

-- 허용할 최소 인증 프로토콜 버전이다. 값 11 은 11g 방식 검증자까지 받아들인다는 뜻.
-- 이 값이 두 노드에서 다르면 패스워드 파일이 같아도 SYS 원격 접속이 거부되어
-- ORA-01017 로 나타날 수 있다. 인증 문제가 안 풀릴 때 확인할 항목이다.
--
-- NAMES.DIRECTORY_PATH 가 없으므로 기본 순서 (TNSNAMES, EZCONNECT, HOSTNAME) 가
-- 적용된다. tnsnames.ora 를 먼저 본다는 뜻이다.

--------------------------------------------------------------------------------
 [4] 오류 재현 — 존재하지 않는 별칭
--------------------------------------------------------------------------------

[oracle@chicago-srv ~]$ tnsping newyork

TNS Ping Utility for Linux: Version 19.0.0.0.0 - Production
Used parameter files:
TNS-03505: Failed to resolve name


>>> 원인 파악
    TNS-03505 는 "이름을 풀 수 없다" 는 뜻이다. 원인은 셋 중 하나다.
      ① tnsnames.ora 에 그 별칭이 없다
      ② tnsnames.ora 파일 자체를 못 찾았다 (TNS_ADMIN 경로 문제)
      ③ 파일 문법이 깨져 파싱에 실패했다

    이 단계에서 실패했다면 네트워크나 리스너는 볼 필요가 없다.
    아직 어디로 접속할지조차 정하지 못한 상태다.

    주의: TNS_ADMIN 이 설정되어 있으면 $ORACLE_HOME/network/admin 이 아니라
          그쪽을 본다. "분명히 고쳤는데 반영이 안 된다" 는 상황의 흔한 원인이다.

SYS@chicago> HOST echo "TNS_ADMIN=[$TNS_ADMIN]"
TNS_ADMIN=[]

-- 비어 있다. 따라서 $ORACLE_HOME/network/admin 을 본다.

>>> 조치
    실제로 필요한 별칭이라면 tnsnames.ora 에 추가한다.
    이 실습에서는 존재하지 않는 별칭을 일부러 조회한 것이므로 조치하지 않는다.

>>> 재확인 — 실재하는 별칭은 정상이다

[oracle@chicago-srv ~]$ tnsping boston
OK (0 msec)

--------------------------------------------------------------------------------
 [5] tnsping 이 확인해 주지 않는 것
--------------------------------------------------------------------------------

-- tnsping OK 는 다음 세 가지만 보증한다.
--   ① 별칭이 tnsnames.ora 에서 주소로 풀렸다
--   ② 그 호스트·포트에 TCP 로 도달했다
--   ③ 그곳에 리스너가 살아 있고 응답했다
--
-- 보증하지 않는 것
--   ✗ 리스너가 요청한 SERVICE_NAME 을 알고 있는가  → 모르면 ORA-12514
--   ✗ 인스턴스가 접속을 받을 상태인가              → NOMOUNT 면 ORA-12528
--   ✗ 인증이 통과하는가                            → 다르면 ORA-01017
--
-- 진짜 검증은 실제 접속이다.

[oracle@chicago-srv ~]$ sqlplus -s "sys/oracle@boston as sysdba"

SQL> SELECT instance_name, status FROM v$instance;

INSTANCE_NAME    STATUS
---------------- ------------
boston           OPEN

SQL> EXIT

-- 여기까지 성공하면 이름 해석·네트워크·리스너·서비스 등록·인증이
-- 모두 정상이라는 뜻이다. 한 번의 접속이 다섯 계층을 동시에 검증한다.
