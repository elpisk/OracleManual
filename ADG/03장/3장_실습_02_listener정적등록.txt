================================================================================
 제3장 실습 02 — listener.ora 정적 등록
 대상   : chicago-srv Primary / boston-srv Standby
 목표   : SID_LIST_LISTENER 의 세 요소를 이해하고, lsnrctl status 의 서비스 목록과
          status(READY / UNKNOWN / BLOCKED)를 읽는 법을 익힌다
 소요   : 약 25분
 변경   : 없음 (전부 조회)
================================================================================

--------------------------------------------------------------------------------
 [1] chicago 의 listener.ora
--------------------------------------------------------------------------------

[oracle@chicago-srv ~]$ cat $ORACLE_HOME/network/admin/listener.ora

LISTENER =
  (DESCRIPTION_LIST =
    (DESCRIPTION =
      (ADDRESS = (PROTOCOL = TCP)(HOST = chicago-srv)(PORT = 1521))
    )
  )

SID_LIST_LISTENER =
  (SID_LIST =
    (SID_DESC =
      (GLOBAL_DBNAME = chicago)
      (ORACLE_HOME = /u01/app/oracle/product/19.3.0/dbhome_1)
      (SID_NAME = chicago)
    )
    (SID_DESC =
      (GLOBAL_DBNAME = chicago_DGMGRL)
      (ORACLE_HOME = /u01/app/oracle/product/19.3.0/dbhome_1)
      (SID_NAME = chicago)
    )
  )

ADR_BASE_LISTENER = /u01/app/oracle

-- SID_DESC 한 건이 정적 등록 한 건이다.
--
--   GLOBAL_DBNAME : 클라이언트가 SERVICE_NAME 으로 요청할 이름
--                   → tnsnames.ora 의 SERVICE_NAME 과 일치해야 한다
--   ORACLE_HOME   : 리스너가 인스턴스에 연결할 때 쓸 오라클 홈
--   SID_NAME      : 실제 인스턴스의 SID (이 서버의 ORACLE_SID)
--
-- SID_DESC 가 두 개인 이유 : 서비스 이름만 다르고 같은 인스턴스를 가리킨다.
--   chicago        → 일반 접속용
--   chicago_DGMGRL → Broker 용 (13장)

--------------------------------------------------------------------------------
 [2] boston 의 listener.ora
--------------------------------------------------------------------------------

[oracle@boston-srv ~]$ cat $ORACLE_HOME/network/admin/listener.ora

SID_LIST_LISTENER =
  (SID_LIST =
    (SID_DESC =
      (GLOBAL_DBNAME = boston)
      (ORACLE_HOME = /u01/app/oracle/product/19.3.0/dbhome_1)
      (SID_NAME = boston)
    )
    (SID_DESC =
      (GLOBAL_DBNAME = boston_DGMGRL)
      (ORACLE_HOME = /u01/app/oracle/product/19.3.0/dbhome_1)
      (SID_NAME = boston)
    )
  )

LISTENER =
  (DESCRIPTION =
    (ADDRESS = (PROTOCOL = TCP)(HOST = boston-srv.localdomain)(PORT = 1521))
  )

ADR_BASE_LISTENER = /u01/app/oracle

-- 구조는 같고 이름만 boston 으로 바뀌었다.
-- 주의 : GLOBAL_DBNAME 은 DB_NAME(chicago)이 아니라 DB_UNIQUE_NAME(boston)이다.
--        두 노드의 DB_NAME 이 같으므로 DB_NAME 을 쓰면 구별이 되지 않는다.

-- 이 출력이 이 실습의 핵심이다. 한 줄씩 읽는다.
--
-- ★ Service "chicago" has 2 instance(s)
--   같은 서비스 이름에 항목이 두 개다.
--     status UNKNOWN  ← listener.ora 의 정적 등록에서 온 것
--     status READY    ← 인스턴스가 스스로 등록한 동적 등록
--   같은 인스턴스를 두 경로로 알고 있는 것이며 정상이다.
--   정적 등록을 넣으면 이렇게 중복되는 것이 오히려 자연스럽다.
--
-- ★ Service "chicago_DGMGRL" — status UNKNOWN 하나뿐
--   Broker 를 켜지 않았으므로 동적 등록이 없다. 정적 등록만 있다.
--
-- ★ 16자리 16진수 이름 두 개 (59f053... / 86b637...)
--   PDB 의 GUID 다. 멀티테넌트에서 컨테이너별로 자동 등록되며 신경 쓸 필요 없다.
--
-- ★ Service "chicagoXDB" — XML DB 서비스. 기본 생성되며 Data Guard 와 무관하다.
--
-- ★ Service "chicago_pdb1" — PDB 서비스. 애플리케이션이 PDB 에 붙을 때 쓴다.

--------------------------------------------------------------------------------
 [4] status 세 가지 구분
--------------------------------------------------------------------------------

  status    출처        의미                                    접속
  --------- ----------- --------------------------------------- ------------------
  READY     동적 등록   인스턴스가 등록했고 OPEN 이다           가능
  BLOCKED   동적 등록   인스턴스가 NOMOUNT/MOUNT 라 막고 있다   불가 (ORA-12528)
  UNKNOWN   정적 등록   리스너가 인스턴스 상태를 모른다         시도해 봐야 안다

-- UNKNOWN 이 "모른다" 인 것이 핵심이다.
-- 정적 등록은 리스너가 인스턴스와 통신해 얻은 정보가 아니라 파일에 적힌 선언이다.
-- 그래서 리스너는 그 인스턴스가 떠 있는지조차 모르고, 일단 접속을 넘겨준다.
--
-- 장점 : NOMOUNT 인스턴스에도 접속할 수 있다  ← Data Guard 가 필요로 하는 성질
-- 단점 : 인스턴스가 죽어 있어도 서비스를 광고한다 (접속 시 ORA-01034)

--------------------------------------------------------------------------------
 [5] 오류 재현 — 인스턴스 없이 정적 등록된 서비스에 접속
--------------------------------------------------------------------------------

-- 정적 등록의 단점을 확인한다.
-- boston 에서 ORACLE_SID 를 chicago 로 두고 접속해 본다.
-- boston-srv 에는 chicago 인스턴스가 없다.

[oracle@boston-srv ~]$ export ORACLE_SID=chicago
[oracle@boston-srv ~]$ sqlplus -s / as sysdba

SQL> SELECT 1 FROM dual;
SELECT 1 FROM dual
*
ERROR at line 1:
ORA-01034: ORACLE not available
Process ID: 0
Session ID: 0 Serial number: 0


>>> 원인 파악
    ORA-01034 는 "지정한 ORACLE_SID 의 인스턴스가 이 서버에 없다" 는 뜻이다.
    Process ID 가 0 인 것이 단서다 — 붙을 프로세스 자체가 없었다.

    정적 등록과 연결지어 이해하면 이렇다.
    리스너는 listener.ora 에 적힌 대로 서비스를 광고하지만,
    그 인스턴스가 실제로 살아 있는지는 확인하지 않는다.
    그래서 접속 요청을 넘겨주고, 인스턴스가 없다는 사실은
    접속을 시도한 뒤에야 ORA-01034 로 드러난다.

>>> 조치

[oracle@boston-srv ~]$ export ORACLE_SID=boston
[oracle@boston-srv ~]$ sqlplus -s / as sysdba

>>> 재확인

SQL> SELECT instance_name, status FROM v$instance;

INSTANCE_NAME    STATUS
---------------- ------------
boston           OPEN

SQL> EXIT
