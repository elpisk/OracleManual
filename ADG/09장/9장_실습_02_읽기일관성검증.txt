================================================================================
 제9장 실습 02 — 읽기 일관성 검증
 대상   : chicago-srv Primary / boston-srv Standby
 목표   : Standby 조회가 커밋된 데이터만 보여 준다는 것을 정확한 방법으로
          검증한다. 잘못된 측정이 어떤 결론을 내는지도 함께 본다
 소요   : 약 30분
 변경   : 테스트 테이블을 만들었다가 지운다
================================================================================

--------------------------------------------------------------------------------
 [1] 질문을 분명히 한다
--------------------------------------------------------------------------------

  Primary 가 INSERT 했지만 **아직 커밋하지 않은** 행이
  Standby 에서 보이는가?

  ★ 이 질문이 중요한 이유
    리두는 커밋 전에도 전송되고 적용된다.
    즉 Standby 의 데이터 블록에는 커밋되지 않은 변경이
    이미 반영되어 있을 수 있다.
    그럼에도 조회 결과가 깨끗한가?

--------------------------------------------------------------------------------
 [2] 오류 재현 — 준비 단계
--------------------------------------------------------------------------------

SYS@chicago> DROP TABLE system.adg_rc PURGE;

drop table system.adg_rc purge
                  *
ERROR at line 1:
ORA-00942: table or view does not exist

>>> 원인 파악
    그런 테이블이 없다. 처음 실행이므로 정상이다.

    ★ 정리 목적의 DROP 이라면 무시해도 되는 오류다.
      다만 스크립트에서 이 오류로 중단되지 않도록 처리해 둔다.
      SQL*Plus 라면 그 구간만 WHENEVER SQLERROR CONTINUE 로 넘긴다.

>>> 조치
    테이블을 만들고 기준 데이터를 넣는다.

SYS@chicago> CREATE TABLE system.adg_rc(id NUMBER, tag VARCHAR2(20));

Table created.

SYS@chicago> INSERT INTO system.adg_rc VALUES(1,'committed');

1 row created.

SYS@chicago> COMMIT;

Commit complete.

>>> 재확인
    15초 뒤 Standby 에서 조회한다.

SYS@boston> SELECT COUNT(*) FROM system.adg_rc;

  COUNT(*)
----------
         1

1 row selected.

    커밋된 1건이 보인다. 여기서 시작한다.

--------------------------------------------------------------------------------
 [3] 커밋하지 않은 상태를 유지한다
--------------------------------------------------------------------------------

-- ★ 핵심은 **세션을 살려 두는 것**이다.
--   INSERT 후 세션이 끝나면 커밋되거나 롤백되어 시험이 성립하지 않는다.
--   그래서 하나의 세션 안에서 INSERT → 대기까지 처리한다.

[oracle@chicago-srv ~]$ nohup sqlplus -s / as sysdba <<'EOS' > /tmp/adg_hold.log 2>&1 &
insert into system.adg_rc values(2,'UNCOMMITTED');
exec dbms_session.sleep(40);
rollback;
exit
EOS

-- 백그라운드로 실행했다. 이 세션은 40초 동안 커밋하지 않고 살아 있다.

--------------------------------------------------------------------------------
 [4] 그 사이 Standby 에서 조회
--------------------------------------------------------------------------------

-- 15초 뒤

SYS@boston> COL tag FOR a14
SYS@boston> SELECT id, tag FROM system.adg_rc ORDER BY id;

        ID TAG
---------- --------------
         1 committed

1 row selected.

SYS@boston> SELECT COUNT(*) FROM system.adg_rc;

  COUNT(*)
----------
         1

1 row selected.

-- ★★ **커밋되지 않은 2번 행은 보이지 않는다.**
--
--   Standby 조회는 Primary 조회와 같은 읽기 일관성 규칙을 따른다.
--   리두와 함께 UNDO 정보도 적용되므로,
--   커밋되지 않은 변경은 조회 결과에서 제외된다.

-- Primary 의 다른 세션에서도 마찬가지다.

SYS@chicago> SELECT COUNT(*) FROM system.adg_rc;

  COUNT(*)
----------
         1

1 row selected.

-- 같은 결과다. Standby 가 특별한 것이 아니라 원래 그런 규칙이다.

--------------------------------------------------------------------------------
 [5] 롤백 후에도 같다
--------------------------------------------------------------------------------

[oracle@chicago-srv ~]$ cat /tmp/adg_hold.log

1 row created.


PL/SQL procedure successfully completed.


Rollback complete.

SYS@boston> SELECT COUNT(*) FROM system.adg_rc;

  COUNT(*)
----------
         1

1 row selected.

-- 백그라운드 세션이 롤백으로 끝났고 Standby 결과도 그대로 1건이다.
-- 애초에 보이지 않았으므로 롤백되어도 달라질 것이 없다.

--------------------------------------------------------------------------------
 [6] 측정의 함정 — 처음에는 다른 결과가 나왔다
--------------------------------------------------------------------------------

-- 이 실습을 처음 설계했을 때는 백그라운드 세션을 쓰지 않았다.
-- 그냥 INSERT 만 하고 Standby 를 조회했다.

SYS@chicago> INSERT INTO system.adg_rc VALUES(3,'implicit-commit');

1 row created.

-- (COMMIT 명령 없이 세션 종료)

-- 15초 뒤

SYS@boston> COL tag FOR a18
SYS@boston> SELECT id, tag FROM system.adg_rc ORDER BY id;

        ID TAG
---------- ------------------
         1 committed
         3 implicit-commit

2 rows selected.

-- ★★ **커밋하지 않았는데 보인다!**
--   이 결과만 보면 "Standby 는 미커밋 데이터도 보여 준다"는
--   잘못된 결론에 이른다.

>>> 원인 파악
    원인은 Data Guard 가 아니라 **SQL*Plus** 다.

    ★ **SQL*Plus 는 정상 종료(EXIT) 시 암묵적으로 커밋한다.**
      스크립트가 INSERT 후 EXIT 로 끝나면 그 시점에 커밋된다.
      비정상 종료(연결 끊김 등)에서는 롤백한다.

    즉 "커밋하지 않았다"고 생각했지만 실제로는 커밋되어 있었다.
    측정이 잘못됐지 제품이 이상한 것이 아니었다.

>>> 조치
    커밋되지 않은 상태를 유지하려면 **세션이 살아 있어야 한다.**
    [3] 처럼 하나의 세션 안에서 INSERT → 대기를 처리한다.
    DBMS_SESSION.SLEEP 으로 세션을 붙잡아 둔다.

>>> 재확인
    [4] 의 결과가 올바른 측정이다. 미커밋 행은 보이지 않는다.

--------------------------------------------------------------------------------
 [7] 이 사례가 주는 교훈
--------------------------------------------------------------------------------

  ★ Data Guard 지식이 아니라 **측정 방법**에 관한 교훈이다.

  · 도구가 세션을 닫으면서 무엇을 하는지 알아야 한다
  · SQL*Plus 는 EXIT 에서 커밋, 비정상 종료에서 롤백한다
  · 상태를 유지해야 하는 시험은 하나의 세션 안에서 처리한다
  · **예상과 다른 결과가 나오면 "제품이 이상하다"보다
    "내 측정이 이상하다"를 먼저 의심한다**

  ★ 실무에서도 같은 일이 일어난다.
    "운영에서는 되는데 테스트에서는 안 된다"는 보고의 상당수가
    테스트 방법의 차이에서 나온다.

--------------------------------------------------------------------------------
 [8] 정리
--------------------------------------------------------------------------------

SYS@chicago> DROP TABLE system.adg_rc PURGE;

Table dropped.

  · Standby 조회는 **커밋된 데이터만** 보여 준다
  · 리두는 커밋 전에도 적용되지만 UNDO 도 함께 적용되어 일관성이 유지된다
  · Primary 조회와 같은 규칙이다. Standby 가 특별한 것이 아니다
  · SQL*Plus 는 EXIT 시 암묵적으로 커밋한다
  · 미커밋 상태 시험은 세션을 살려 둔 채로 해야 한다
