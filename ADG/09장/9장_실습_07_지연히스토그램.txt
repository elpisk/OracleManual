================================================================================
 제9장 실습 07 — 지연 히스토그램
 대상   : boston-srv Standby (변경 유발은 chicago-srv)
 목표   : V$STANDBY_EVENT_HISTOGRAM 으로 지연의 분포를 읽고,
          적용 정지가 어떻게 기록되는지 관찰한다
 소요   : 약 30분
 경고   : 적용을 잠시 멈춘다. 마지막에 반드시 복귀한다
================================================================================

--------------------------------------------------------------------------------
 [1] 현재 값을 기준으로 기록한다
--------------------------------------------------------------------------------

SYS@boston> COL name FOR a20
SYS@boston> COL unit FOR a10
SYS@boston> SELECT name, time, unit, count, last_time_updated
  2            FROM v$standby_event_histogram WHERE count>0 ORDER BY time;

NAME                       TIME UNIT            COUNT LAST_TIME_UPDATED
-------------------- ---------- ---------- ---------- --------------------
apply lag                     0 seconds           650 08/27/2026 13:25:26
apply lag                     2 seconds             1 08/27/2026 13:19:04

2 rows selected.

-- ★ 히스토그램이다. 읽는 법은 이렇다.
--
--   TIME + UNIT  구간을 나타낸다 (0초, 2초, ...)
--   COUNT        그 구간에 속한 표본 수
--   LAST_TIME_UPDATED  그 구간이 마지막으로 관측된 시각
--
--   위 결과는 "지연 0초였던 표본이 650회, 2초였던 표본이 1회"라는 뜻이다.
--   대부분의 시간 동안 지연이 없었다는 것을 보여 준다.

SYS@boston> SELECT COUNT(*) total_buckets, SUM(count) total_samples
  2            FROM v$standby_event_histogram;

TOTAL_BUCKETS TOTAL_SAMPLES
------------- -------------
            3           652

1 row selected.

-- 이 값을 기록해 둔다. 뒤에서 비교한다.

--------------------------------------------------------------------------------
 [2] 기록되는 항목은 하나뿐이다
--------------------------------------------------------------------------------

SYS@boston> COL name FOR a24
SYS@boston> SELECT name, COUNT(*) buckets, SUM(count) samples
  2            FROM v$standby_event_histogram GROUP BY name ORDER BY name;

NAME                        BUCKETS    SAMPLES
------------------------ ---------- ----------
apply lag                        62       1394

1 row selected.

-- ★ **apply lag 만 있다.** transport lag 의 히스토그램은 없다.
--
--   전송이 아니라 **적용의 분포만** 누적된다는 뜻이다.
--   전송 쪽 추세가 필요하면 V$DATAGUARD_STATS 를 주기적으로
--   따로 수집해야 한다.
--
-- ★ BUCKETS 62 는 관측된 구간의 수다.
--   0초, 2~59초, 그리고 분 단위 구간까지 합한 값이다.

 [4] 오류 재현 — 그 사이 한도를 둔 조회
--------------------------------------------------------------------------------

-- 일반 사용자 세션에서 (실습 06 참고)

SQL> ALTER SESSION SET standby_max_data_delay=1;

Session altered.

SQL> SELECT COUNT(*) FROM d;

select count(*) from d
*
ERROR at line 1:
ORA-03172: STANDBY_MAX_DATA_DELAY of 1 seconds exceeded

>>> 원인 파악
    적용이 멈춰 apply lag 이 벌어졌기 때문이다.
    이 상태가 히스토그램에 어떻게 기록되는지가 이 실습의 관찰 대상이다.

    ★ 지연 값 자체는 V$DATAGUARD_STATS 로 확인한다.

SYS@boston> COL name FOR a16
SYS@boston> COL value FOR a20
SYS@boston> SELECT name, value FROM v$dataguard_stats WHERE name LIKE '%lag';

NAME             VALUE
---------------- --------------------
transport lag    +00 00:00:00
apply lag        +00 00:01:22

      1분 22초다. 이 값이 매 표본마다 히스토그램에 쌓인다.

>>> 조치
    적용을 재개한다.

SYS@boston> ALTER DATABASE RECOVER MANAGED STANDBY DATABASE
  2            USING CURRENT LOGFILE DISCONNECT FROM SESSION;

Database altered.

>>> 재확인
    따라잡은 뒤 히스토그램을 다시 조회한다. [5] 에서 확인한다.

--------------------------------------------------------------------------------
 [5] 히스토그램이 어떻게 변했는가
--------------------------------------------------------------------------------

SYS@boston> COL name FOR a20
SYS@boston> SELECT name, time, unit, count FROM v$standby_event_histogram
  2            WHERE count>0 ORDER BY name, time;

NAME                       TIME UNIT            COUNT
-------------------- ---------- ---------- ----------
apply lag                     0 seconds           854
apply lag                     2 seconds             1
apply lag                     2 minutes            59
apply lag                     3 seconds             2
apply lag                     4 seconds             2
apply lag                     5 seconds             2
apply lag                     6 seconds             2
   ... (7초부터 30초까지 대부분 2) ...
apply lag                    31 seconds             1
apply lag                    32 seconds             2
apply lag                    33 seconds             1
   ... (34초부터 59초까지 대부분 2) ...
apply lag                    59 seconds             2

60 rows selected.

-- ★★ 두 가지가 보인다.
--
-- ① **`2 minutes` 구간에 59회**가 몰려 있다.
--    적용을 멈춘 동안 계속 그 수준의 지연이 관측된 것이다.
--    표본이 대략 2초에 한 번씩 수집되므로 59회는 약 2분에 해당한다.
--
-- ② 3초부터 59초까지 구간마다 1~2회씩 있다.
--    **적용을 재개해 따라잡는 동안** 지연이 점진적으로 줄어든 흔적이다.
--    59초 → 58초 → ... → 3초로 내려오면서 각 구간을 한두 번씩 스쳤다.
--
-- ★ 0초 구간이 650 에서 854 로 늘었다.
--   따라잡은 뒤 정상 상태로 돌아와 다시 쌓이기 시작한 것이다.

--------------------------------------------------------------------------------
 [6] 이 뷰의 성격
--------------------------------------------------------------------------------

  ★ **인스턴스 기동 이후 누적된다.**
    그래서 "지금은 정상이지만 과거에 문제가 있었는가"를 판단할 수 있다.
    현재 값만 보는 V$DATAGUARD_STATS 로는 알 수 없는 정보다.

  ★ 반대로 말하면 **한 번의 조회로는 "언제" 문제가 있었는지 알 수 없다.**
    LAST_TIME_UPDATED 가 힌트를 주지만 그 구간이 마지막으로 관측된
    시각일 뿐이다.

  ★ 그리고 **재기동하면 초기화된다.**
    재기동 직후의 깨끗한 히스토그램은 안정성의 증거가 아니라
    표본이 적다는 뜻일 뿐이다.

--------------------------------------------------------------------------------
 [7] 모니터링에 쓰는 방법
--------------------------------------------------------------------------------

-- 실용적인 지표 하나로 요약한다. "0초가 아닌 구간의 비율"이다.

SYS@boston> SELECT ROUND(100 * SUM(CASE WHEN time > 0 THEN count ELSE 0 END)
  2                       / NULLIF(SUM(count),0), 2) pct_lagged
  3            FROM v$standby_event_histogram WHERE name = 'apply lag';

PCT_LAGGED
----------
       9.3

1 row selected.

-- ★ 이 값이 안정성을 한 숫자로 요약한다.
--   전체 표본 1,849개 중 지연이 0초였던 것이 1,677개다.
--   나머지 172개(9.3퍼센트)가 지연이 있었던 표본이며,
--   그 대부분이 이 장의 실습에서 적용을 멈춘 구간이다.
--
-- ★ 정상 운영만 이어졌다면 이 값은 훨씬 낮다.
--   반대로 말하면 **실습 때문에 올라간 값**이므로
--   이 숫자 자체를 기준으로 삼으면 안 된다.
--
-- ★ **누적값이므로 두 시점의 차이를 봐야 의미가 있다.**
--   정기적으로 스냅샷을 떠 두고 비교한다.
--   한 번의 조회로는 "지금까지 전체가 어땠는가"만 알 수 있고
--   "최근 한 시간이 어땠는가"는 알 수 없다.
--
-- ★ 이 값이 갑자기 올라가면 그 사이에 무슨 일이 있었다는 뜻이다.
--   구체적으로 어느 구간인지는 히스토그램을 직접 보면 된다.

--------------------------------------------------------------------------------
 [8] 세 뷰의 역할 정리
--------------------------------------------------------------------------------

  뷰                          알려 주는 것              한계
  --------------------------- ------------------------- ----------------------
  V$DATAGUARD_STATS           지금 이 순간의 지연       십수 초 전 정보 (7장)
  V$STANDBY_EVENT_HISTOGRAM   기동 이후 지연의 분포     언제인지는 모른다
  V$MANAGED_STANDBY           적용이 돌고 있는가        지연은 모른다

  ★ 셋을 함께 봐야 한다.
    · 적용이 도는가        → V$MANAGED_STANDBY
    · 지금 얼마나 뒤처졌나 → V$DATAGUARD_STATS
    · 그동안 안정적이었나  → V$STANDBY_EVENT_HISTOGRAM

  ★ 7장에서 만든 통합 점검 조회에 히스토그램 비율을 더하면
    이 세 관점이 한 화면에 들어온다.

--------------------------------------------------------------------------------
 [9] 정리
--------------------------------------------------------------------------------

  · V$STANDBY_EVENT_HISTOGRAM 은 지연의 분포를 구간별로 누적한다
  · 기록하는 항목은 apply lag 하나뿐이다. transport lag 은 없다
  · 2분 정지가 `2 minutes` 구간 59회로 남았다
  · 따라잡는 과정이 3~59초 구간에 1~2회씩 흔적을 남긴다
  · 누적값이므로 두 시점의 차이를 본다. 재기동하면 초기화된다
  · "0초가 아닌 구간의 비율"이 실용적인 요약 지표다
  · 세 뷰를 함께 봐야 적용·지연·안정성을 모두 판단할 수 있다
