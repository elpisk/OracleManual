================================================================================
 제9장 실습 05 — 리다이렉션의 제약
 대상   : boston-srv Standby
 목표   : SYS 로는 왜 실패하는지, DDL 은 왜 대상이 아닌지 확인하고
          점검 순서를 세운다
 소요   : 약 25분
 변경   : 없음 (실패하는 명령만 실행)
================================================================================

--------------------------------------------------------------------------------
 [1] 오류 재현 ① — SYS 로 시도하면
--------------------------------------------------------------------------------

SYS@boston> ALTER SESSION SET CONTAINER=chicago_pdb1;

Session altered.

SYS@boston> ALTER SESSION ENABLE ADG_REDIRECT_DML;

Session altered.

SYS@boston> INSERT INTO adgu.t VALUES(4,'sys-redirect');

insert into adgu.t values(4,'sys-redirect')
                 *
ERROR at line 1:
ORA-16397: statement redirection from Oracle Active Data Guard standby database
           to primary database failed

>>> 원인 파악
    ★ 세션 설정은 성공했다. `Session altered.` 가 나왔다.
      그런데 실행이 실패했다.

    ★ 오류 번호가 다르다는 점이 중요하다.
        ORA-16000  리다이렉션이 **시도되지 않았다** (실습 04 의 경우)
        ORA-16397  리다이렉션을 **시도했다가 실패했다** ← 지금

      즉 이번에는 Standby 가 Primary 로 넘기려고 했고 그 과정에서 막혔다.

    ★ 이유는 리다이렉션의 동작 방식에 있다.
      Standby 는 Primary 로 **새 연결을 만들어** 그 문장을 실행한다.
      그 연결은 현재 세션의 사용자로 인증되어야 하는데,
      **SYS(SYSDBA 권한 접속)는 이 경로로 재인증되지 않는다.**

    ★★ 실무적 함의
      **관리자 계정으로 시험하면 기능이 동작하지 않는다고 오판하기 쉽다.**
      실습에서도 처음에 SYS 로 시도해 이 오류를 만났고,
      일반 사용자로 바꾸자 바로 동작했다 (실습 04).

      기능 검증은 **실제 애플리케이션이 쓰는 계정과 같은 종류**로 해야 한다.

    ★ 오류 메시지가 원인을 알려 주지 않는다는 점도 기억한다.
      "리다이렉션이 실패했다"고만 말할 뿐 왜인지는 말하지 않는다.
      접속 계정, Primary 접근 가능 여부, 대상 객체의 존재를
      차례로 확인해야 한다.

>>> 조치
    일반 사용자로 접속해 실행한다.

[oracle@boston-srv ~]$ sqlplus -s adgu/oracle@boston-srv:1521/chicago_pdb1

>>> 재확인
    실습 04 에서 확인한 대로 정상 동작한다.

SQL> ALTER SESSION ENABLE ADG_REDIRECT_DML;
SQL> INSERT INTO t VALUES(3,'redirected');

1 row created.

--------------------------------------------------------------------------------
 [2] 오류 재현 ② — DDL 을 시도하면
--------------------------------------------------------------------------------

[oracle@boston-srv ~]$ sqlplus -s adgu/oracle@boston-srv:1521/chicago_pdb1

SQL> ALTER SESSION ENABLE ADG_REDIRECT_DML;

Session altered.

SQL> CREATE TABLE t2(id NUMBER);

create table t2(id number)
*
ERROR at line 1:
ORA-16000: database or pluggable database open for read-only access

>>> 원인 파악
    ★ 리다이렉션을 켰는데도 **ORA-16000** 이다.
      ORA-16397 이 아니라는 점이 핵심이다.

      **아예 시도하지 않았다**는 뜻이다.

    ★ 이름 그대로 **DML 리다이렉션**이며 DDL 은 포함하지 않는다.
      INSERT·UPDATE·DELETE 만 대상이다.

    ★ 오류 번호가 처리 경로를 알려 준다는 것을 다시 확인한다.
        ORA-16000  대상이 아니거나 리다이렉션이 꺼져 있다
        ORA-16397  대상이고 켜져 있었는데 실행이 실패했다

>>> 조치
    DDL 은 Primary 에서 실행한다. 리다이렉션으로 우회할 수 없다.

SYS@chicago> ALTER SESSION SET CONTAINER=chicago_pdb1;
SYS@chicago> CREATE TABLE adgu.t2(id NUMBER);

Table created.

>>> 재확인
    20초 뒤 Standby 에서 그 테이블이 보이는지 확인한다.
    리두로 전달되므로 조회할 수 있다.

--------------------------------------------------------------------------------
 [3] 두 오류의 대조
--------------------------------------------------------------------------------

  상황                              오류         뜻
  --------------------------------- ------------ ----------------------------
  리다이렉션 꺼짐 + DML             ORA-16000    시도하지 않았다
  리다이렉션 켜짐 + DDL             ORA-16000    대상이 아니다
  리다이렉션 켜짐 + DML + SYS       ORA-16397    시도했다가 실패했다
  리다이렉션 켜짐 + DML + 일반계정  (성공)       —

  ★ **ORA-16000 이면 설정이나 대상을 보고,
    ORA-16397 이면 접속과 경로를 본다.**
    이 구분이 진단의 출발점이다.

--------------------------------------------------------------------------------
 [4] 점검 순서
--------------------------------------------------------------------------------

  리다이렉션이 동작하지 않을 때 다음 순서로 확인한다.

  순서  확인                    방법                              실패 시
  ----  ----------------------  --------------------------------  ----------
  ①    문장이 DML 인가         DDL 이면 대상이 아니다            ORA-16000
  ②    리다이렉션이 켜졌는가   SHOW PARAMETER / 세션 설정 확인   ORA-16000
  ③    계정이 SYS 가 아닌가    SHOW USER                         ORA-16397
  ④    Primary 에 닿는가       Standby 에서 tnsping <primary>    ORA-16397
  ⑤    객체가 Primary 에 있는가 Primary 에서 조회                 객체 오류

  ★ ①과 ②는 오류 번호가 같다. 리다이렉션이 아예 시도되지 않은 경우다.
  ★ ③ 이후는 시도했다가 실패한 것이라 ORA-16397 이다.

  ★ ④는 3장의 진단이 그대로 쓰인다.
    리다이렉션은 Standby 가 Primary 로 새 연결을 만드는 것이므로
    그 경로가 막혀 있으면 실패한다.

[oracle@boston-srv ~]$ tnsping chicago

TNS Ping Utility for Linux: Version 19.0.0.0.0
...
OK (0 msec)

    **Oracle Net 이 양방향으로 살아 있어야 한다**는 뜻이며,
    이는 역할 전환을 위해서도 필요한 조건이다.

--------------------------------------------------------------------------------
 [5] 시스템 수준으로 켜면
--------------------------------------------------------------------------------

SYS@boston> SHOW PARAMETER adg_redirect_dml

NAME                  TYPE      VALUE
--------------------- --------- ------------------------------
adg_redirect_dml      boolean   FALSE

-- ★ 세션 수준으로 켠 것은 이 값에 나타나지 않는다.
--   ALTER SESSION 은 그 세션에만 적용되기 때문이다.
--
-- ★ 시스템 수준으로 켜려면
--     ALTER SYSTEM SET adg_redirect_dml=TRUE SCOPE=BOTH;
--
--   그러면 그 Standby 의 **모든 세션**이 리다이렉션 대상이 된다.
--   의도하지 않은 DML 까지 Primary 로 넘어가므로 신중히 결정한다.
--
-- ★ 권장은 세션 수준이다.
--   애플리케이션이 필요한 세션에서만 켜면
--   어떤 경로로 Primary 에 쓰기가 발생하는지 통제할 수 있다.

--------------------------------------------------------------------------------
 [6] 정리
--------------------------------------------------------------------------------

  · SYS 로는 ORA-16397 로 실패한다. 재인증 경로가 없기 때문이다
  · 관리자 계정으로 시험하면 기능이 없다고 오판하기 쉽다
  · DDL 은 대상이 아니다. ORA-16000 이 나며 시도조차 되지 않는다
  · ORA-16000 이면 설정·대상을, ORA-16397 이면 접속·경로를 본다
  · 점검은 문장 종류 → 설정 → 계정 → 경로 → 객체 순서
  · 세션 수준으로 켠 것은 SHOW PARAMETER 에 나타나지 않는다
