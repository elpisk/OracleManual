 [2] Primary 에서는 두 지연을 볼 수 없다
--------------------------------------------------------------------------------

SYS@chicago> SELECT count(*) dgs_rows FROM v$dataguard_stats;

  DGS_ROWS
----------
         0

>>> 원인 파악

-- ★ 0행이다. 오류가 아니라 행이 없는 것이다.
--
--   V$DATAGUARD_STATS 는 "리두를 받는 쪽이 얼마나 뒤처졌는가"를 계산한다.
--   Primary 는 받는 쪽이 아니므로 계산할 것이 없다.
--
-- ★ 이것이 이 실습의 출발점이다.
--   "Primary 에서 V$DATAGUARD_STATS 로 동기화를 확인한다"는 방법은
--   실제로는 성립하지 않는다. 다른 길을 찾아야 한다.
--
-- ★ 감시 스크립트를 양쪽에 똑같이 돌리면 Primary 쪽에서
--   "지연을 못 읽었다"가 나온다. 이것을 장애로 오인하면 안 된다.
--   15장에서 역할별로 다른 것을 본다는 원칙으로 정리한다.

--------------------------------------------------------------------------------
 [3] MOUNTED 로 내린다
--------------------------------------------------------------------------------

-- ★ ADG 옵션은 "Standby 를 열어 둔 채 적용하는 것"에 대한 과금이다.
--   9.2.2 에서 확인한 대로 MOUNTED 로만 두면 옵션의 영역이 아니다.
--   그렇다면 닫은 채로 운영할 수 있는지 확인한다.

SYS@boston> ALTER DATABASE RECOVER MANAGED STANDBY DATABASE CANCEL;

Database altered.

SYS@boston> SHUTDOWN IMMEDIATE
SYS@boston> STARTUP MOUNT

ORACLE instance started.
Database mounted.

SYS@boston> ALTER DATABASE RECOVER MANAGED STANDBY DATABASE
  2            USING CURRENT LOGFILE DISCONNECT FROM SESSION;

Database altered.

>>> 재확인

SYS@boston> SELECT database_role, open_mode FROM v$database;

---------------- ----------

SYS@boston> SELECT process, status, sequence# FROM v$managed_standby
  2            WHERE process='MRP0';

PROCESS   STATUS         SEQUENCE#
--------- ------------ ----------
MRP0      APPLYING_LOG         11

-- ★ 적용은 그대로 돈다.
--   USING CURRENT LOGFILE 도 그대로 받아들여졌으므로 실시간 적용이다.
--   재해 복구 능력은 조금도 줄지 않는다. 줄어드는 것은 조회뿐이다.

 [4] 오류 재현 — 닫힌 데이터베이스를 조회하면
--------------------------------------------------------------------------------

SYS@boston> SELECT count(*) FROM system.bk_t;

select count(*) from system.bk_t
                            *
ERROR at line 1:
ORA-01219: database or pluggable database not open:
           queries allowed on fixed tables or views only

>>> 원인 파악

-- ★ 9.4.1 의 ORA-16000 과 다른 번호다. 둘을 구분해야 한다.
--
--   ORA-16000  database or pluggable database open for read-only access
--              → 열려 있는데 쓰려고 했다
--   ORA-01219  database or pluggable database not open
--              → 아예 열려 있지 않다
--
--   오류 번호가 데이터베이스의 상태를 알려 준다.
--
-- ★ 그런데 메시지의 뒷부분이 더 중요하다.
--   "queries allowed on fixed tables or views only"
--   고정 뷰는 조회된다는 뜻이다.

>>> 조치

-- 사용자 표 대신 고정 뷰를 본다.

SYS@boston> SELECT name, value FROM v$dataguard_stats WHERE name LIKE '%lag';

NAME             VALUE
---------------- --------------------
transport lag    +00 00:00:00
apply lag        +00 00:00:00

>>> 재확인

-- ★ 닫혀 있는데도 두 지연이 그대로 나온다.
--
--   V$ 뷰는 메모리 구조를 읽는 것이므로 데이터베이스가 열려 있을 필요가 없다.
--   9.4.4 에서 "V$ 뷰 조회는 된다"고 했던 그 성질이
--   MOUNTED 에서도 유지된다.
--
-- ★ 결론 하나가 나온다.
--   ADG 옵션이 없어도 Standby 에 SYSDBA 로 붙을 수만 있으면
--   지연을 그대로 잴 수 있다.

-- PDB 서비스는 어떻게 되는가.

[oracle@boston-srv ~]$ sqlplus -s sys/****@//boston-srv:1521/chicago_pdb1 as sysdba

ERROR:
ORA-12514: TNS:listener does not currently know of service requested in connect
descriptor

-- ★ ORA-12514 다. 15장에서 리스너를 내렸을 때의 ORA-12541 과 구별한다.
--
--   ORA-12541  TNS:no listener            → 리스너가 없다
--   ORA-12514  service ... not known       → 리스너는 있는데 그 서비스가 없다
--
--   PDB 가 열려 있지 않으므로 리스너에 등록될 서비스가 없다.
--   리스너 자체는 살아 있다.

 [5] Primary 에서만 보고 판단한다
--------------------------------------------------------------------------------

-- ★ Standby 에 접속할 수 없는 상황을 가정한다.
--   네트워크가 분리되어 있거나 감시 도구가 Primary 에만 붙는 경우다.

SYS@chicago> ALTER SYSTEM ARCHIVE LOG CURRENT;
SYS@chicago> SELECT dest_id, destination dest, database_mode, recovery_mode,
  2                 archived_seq#, applied_seq#
  3            FROM v$archive_dest_status WHERE dest_id IN (1,2);

   DEST_ID DEST       DATABASE_MODE    RECOVERY_MODE                 ARCHIVED_SEQ# APPLIED_SEQ#
---------- ---------- ---------------- ----------------------------- ------------- ------------
         1            OPEN             IDLE                                     11            0
         2 boston     MOUNTED-STANDBY  MANAGED REAL TIME APPLY                  11           10

>>> 재확인

-- ★ [1] 과 비교한다. 두 열이 함께 바뀌었다.
--
--   DATABASE_MODE   OPEN_READ-ONLY  →  MOUNTED-STANDBY
--   RECOVERY_MODE   ... WITH QUERY  →  ... (WITH QUERY 가 사라짐)
--
--   이 두 값이 "저쪽이 열려 있는가"를 Primary 에서 답해 준다.
--   라이선스 관점에서도 쓸 수 있다.
--   WITH QUERY 가 붙어 있으면 그 Standby 는 옵션을 쓰고 있다.
--
-- ★ 진행은 두 시퀀스로 본다.
--
--   ARCHIVED_SEQ# 11   여기까지 보냈다
--   APPLIED_SEQ#  10   여기까지 적용됐다
--
--   차이가 밀린 양이다. 닫은 뒤에도 APPLIED_SEQ# 는 계속 올라간다(8 → 10).
--   적용이 도는 것을 Primary 에서 확인한 셈이다.

DGMGRL> show database 'boston'

  Transport Lag:      0 seconds (computed 0 seconds ago)
  Apply Lag:          0 seconds (computed 0 seconds ago)
  Real Time Query:    OFF

Database Status:
SUCCESS

DGMGRL> show configuration
Configuration Status:  SUCCESS

-- ★ Real Time Query 가 ON 에서 OFF 로 바뀌었다.
--   그런데 구성 상태는 여전히 SUCCESS 다.
--   닫는 것은 장애가 아니라 정상적인 선택이다.

 [8] 정리
--------------------------------------------------------------------------------

-- ★ 이 실습에서 확인한 것
--
--   ① Primary 의 V$DATAGUARD_STATS 는 0행이다.
--      "Primary 에서 두 지연을 본다"는 방법은 성립하지 않는다
--   ② MOUNTED 로 내려도 MRP0 은 그대로 돌고 실시간 적용도 유지된다
--   ③ 사용자 표 조회는 ORA-01219 로 막힌다.
--      ORA-16000(열려 있는데 쓰기)과 번호로 구분한다
--   ④ 그러나 고정 뷰는 조회되므로 MOUNTED Standby 에서
--      V$DATAGUARD_STATS 를 그대로 읽을 수 있다 — 옵션 없이 지연을 재는 방법
--   ⑤ PDB 서비스는 사라져 ORA-12514.
--      리스너가 없을 때의 ORA-12541 과 구별한다
--   ⑥ Primary 쪽 표식은 DATABASE_MODE 와 RECOVERY_MODE 의 WITH QUERY 유무다
--   ⑦ 진행은 ARCHIVED_SEQ# 와 APPLIED_SEQ# 의 차이로 본다
--   ⑧ Broker 의 Real Time Query 는 OFF 가 되지만 구성은 SUCCESS 다
--   ⑨ V$ARCHIVED_LOG 의 max(sequence#) 는 RESETLOGS 이전 번호를 집는다
--      (실측 94, 그때 현재 시퀀스는 12)
--
-- ★ 요약하면 이렇다.
--   Standby 에 붙을 수 있으면 V$DATAGUARD_STATS,
--   붙을 수 없으면 Primary 의 V$ARCHIVE_DEST_STATUS.
--   옵션이 없어도 감시는 할 수 있다.
