--------------------------------------------------------------------------------

SYS@boston> ALTER DATABASE RECOVER MANAGED STANDBY DATABASE CANCEL;

SYS@boston> ALTER DATABASE RECOVER TO LOGICAL STANDBY boston_lg;

alter database recover to logical standby boston_lg
*
ERROR at line 1:
ORA-02084: database name is missing a component

>>> 원인 파악

-- boston_lg 는 9자다. DB_NAME 은 8자 이하여야 한다.
--
-- ★ 오류 메시지가 직관적이지 않다.
--   "database name is missing a component" 는 길이 문제를 말하는 것처럼
--   들리지 않는다. 그래서 한 번 겪어 두면 다음에 빨리 알아본다.
--
-- ★ 전환 명령에는 두 형태가 있다.
--
--   ① 새 이름을 준다
--      ALTER DATABASE RECOVER TO LOGICAL STANDBY <새_DB_NAME>;
--
--   ② 이름을 유지한다
--      ALTER DATABASE RECOVER TO LOGICAL STANDBY KEEP IDENTITY;
--
-- ★ 두 방식의 차이가 중요하다.
--
--   방식           DB_NAME  DBID   역할 전환   쓰임
--   -------------  -------  -----  ----------  ---------------------------
--   새 이름        바뀐다   바뀐다  불가능      독립된 보고용 DB
--   KEEP IDENTITY  같다     같다    가능        Data Guard 구성원으로 유지
--
--   KEEP IDENTITY 를 쓰면 나중에 Switchover 대상이 될 수 있고
--   Broker 로도 관리할 수 있다.
--   이름을 바꾸면 그 관계가 끊어지고 그냥 별개의 데이터베이스가 된다.

>>> 조치

SYS@boston> ALTER DATABASE RECOVER TO LOGICAL STANDBY KEEP IDENTITY;

(응답이 없다)

-- ★ 오류는 사라졌는데 이번에는 끝나지 않는다.
--   [2] 에서 원인을 찾는다.

-- ★ 시퀀스 47 을 기다리고 있다.
--
--   전환 명령은 자기가 시작한 지점부터 앞으로 나아가며 딕셔너리를 찾는다.
--   그런데 Primary 가 조용하면 47번 리두가 생기지 않으므로 영원히 기다린다.
--
-- ★ 더 근본적인 원인은 실습 02 의 순서다.
--
--   BUILD 를 먼저 했을 때 MRP 가 아직 돌고 있었다.
--   MRP 가 딕셔너리를 담은 리두를 이미 적용해 지나가 버렸다.
--   전환 명령이 찾는 딕셔너리는 앞이 아니라 뒤에 있다.
--
-- ★ 두 가지를 확인하면 진단이 끝난다.
--
--   ① 알림 로그의 "Media Recovery Waiting for T-1.S-nn"
--      → 무엇을 기다리는지 알려 준다
--   ② 그 시퀀스가 아직 안 만들어졌는지
--      → Primary 에서 V$ARCHIVED_LOG 의 최대 시퀀스를 본다

-- 두 단계로 해결한다.
--
--   ① 리두를 만들어 준다 — 기다림 자체를 풀기 위해
--   ② 딕셔너리를 다시 만든다 — 앞쪽에 놓기 위해

SYS@chicago> ALTER SYSTEM ARCHIVE LOG CURRENT;
SYS@chicago> ALTER SYSTEM ARCHIVE LOG CURRENT;
SYS@chicago> ALTER SYSTEM ARCHIVE LOG CURRENT;

System altered.

-- 알림 로그를 다시 보면 47, 48, 49 를 차례로 적용하고
-- 다시 다음 시퀀스를 기다린다. 딕셔너리를 못 찾고 있다는 뜻이다.

SYS@chicago> SET SERVEROUTPUT ON
SYS@chicago> EXEC dbms_logstdby.build;

PL/SQL procedure successfully completed.

SYS@chicago> ALTER SYSTEM ARCHIVE LOG CURRENT;
SYS@chicago> ALTER SYSTEM ARCHIVE LOG CURRENT;

System altered.

-- Standby 에서 기다리던 명령이 그제서야 끝난다.

SYS@boston> ALTER DATABASE RECOVER TO LOGICAL STANDBY KEEP IDENTITY;

Database altered.

-- ★ 교훈 두 가지
--
--   ① 순서를 지킨다. 적용을 먼저 멈추고 그다음 BUILD 한다.
--   ② 전환이 멈춘 것 같으면 무엇을 기다리는지 알림 로그로 확인하고,
--      진행이 없으면 BUILD 를 다시 한다.

 [4] 오류 재현 — MRP 를 띄우려 하면
--------------------------------------------------------------------------------

SYS@boston> ALTER DATABASE RECOVER MANAGED STANDBY DATABASE DISCONNECT FROM SESSION;

alter database recover managed standby database disconnect from session
*
ERROR at line 1:
ORA-01665: control file is not a standby control file

>>> 원인 파악

-- ★ 이 교재에서 네 번째 만나는 오류다.
--
--   1장   Primary            CONTROLFILE_TYPE = CURRENT   → ORA-01665
--   10장  Far Sync           CONTROLFILE_TYPE = FARSYNC   → ORA-01665
--   11장  Snapshot Standby   CONTROLFILE_TYPE = CURRENT   → ORA-01665
--   12장  Logical Standby    CONTROLFILE_TYPE = CURRENT   → ORA-01665
--
--   Physical Standby 만 CONTROLFILE_TYPE = STANDBY 이고 그때만 MRP 가 뜬다.
--
-- ★ 규칙은 하나다.
--   MRP 를 띄울 수 있는 것은 Standby 컨트롤 파일뿐이다.
--   오라클이 이 판단을 역할이 아니라 컨트롤 파일 유형으로 한다.

>>> 조치

-- Logical Standby 는 MRP 대신 SQL Apply 를 쓴다.

>>> 재확인

-- ★ 이 실습에서 확인한 것
--
--   ① DB_NAME 은 8자 이하 — 9자면 ORA-02084
--   ② KEEP IDENTITY 를 쓰면 Data Guard 구성원으로 남는다
--   ③ 전환이 끝나지 않으면 알림 로그의 "Waiting for T-1.S-nn" 을 본다
--   ④ 원인은 MRP 가 딕셔너리를 지나친 것 → 다시 BUILD
--   ⑤ 알림 로그 경로는 V$DIAG_INFO 로 확인한다 (boston/boston)
--   ⑥ 전환 후 LOGICAL STANDBY / MOUNTED / CURRENT / ALL, CDB=YES
--   ⑦ MRP 는 뜨지 않는다 — ORA-01665 (네 번째)
--
-- ★ 다음 실습에서 열고 SQL Apply 를 기동한다.
