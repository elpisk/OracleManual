-- ★ 이 장의 실습은 11장과 성격이 완전히 다르다.
--
--   11장 Snapshot Standby   명령 한 줄로 되돌아간다
--   12장 Logical Standby    되돌리는 명령이 없다
--
-- ★ 되돌리려면 5·6장의 절차로 Standby 를 처음부터 다시 만들어야 한다.
--   RMAN DUPLICATE 를 다시 돌린다는 뜻이다.
--
-- ★ 그래서 시작 전에 VM 스냅샷을 만든다.

C:\> vmrun snapshot "D:\ADG\CHICAGO\ADG-CHICAGO.vmx" pre-logical
C:\> vmrun snapshot "D:\ADG\BOSTON\ADG-BOSTON.vmx"   pre-logical

C:\> vmrun listSnapshots "D:\ADG\BOSTON\ADG-BOSTON.vmx"
Total snapshots: 2
adg-configured
pre-logical

-- ★ 실행 중인 상태로 찍으면 메모리까지 저장되므로 되돌리면 그대로 돌아온다.
--   대신 시간이 걸린다. 6GB 메모리 두 노드에 10분 이상 걸렸다.
--
-- ★ 기존 adg-configured 는 5장 시점이라 되돌리면 6장부터 다시 해야 한다.
--   pre-logical 은 11장을 마친 상태이므로 13장을 바로 시작할 수 있다.
--
-- ★ 되돌릴 수 없는 작업 앞에서는 되돌릴 수 있는 지점을 먼저 만든다.
--   11장에서 오라클이 CONVERT TO SNAPSHOT STANDBY 를 설계한 방식과 같다.
--   도구가 해 주지 않으면 사람이 한다.

-- ★ 보충 로깅이 왜 필요한가.
--
--   Primary 가 UPDATE emp SET sal=3500 WHERE empno=7788 을 실행하면
--   리두에는 "파일 5, 블록 1234, 오프셋 …의 값이 바뀌었다" 가 기록된다.
--
--   블록 안의 위치는 알지만 그 행이 논리적으로 무엇인지는 없다.
--   같은 데이터가 Logical Standby 에서는 다른 블록에 있을 수 있으므로
--   이 정보로는 SQL 을 만들 수 없다.
--
--   보충 로깅은 행을 식별할 수 있는 컬럼 값을 리두에 함께 기록한다.
--
-- ★ FORCE_LOGGING 과 혼동하지 않는다.
--
--   FORCE_LOGGING  리두를 남기느냐의 문제        (4장에서 켰다)
--   보충 로깅       리두에 무엇을 더 담느냐의 문제
--
--   둘 다 필요하며 서로를 대신하지 못한다.
--
-- ★ 지금 꺼져 있는데 어떻게 켤까.
--   ALTER DATABASE ADD SUPPLEMENTAL LOG DATA 를 직접 실행할 수도 있지만
--   실습 02 에서 다른 방법을 본다.

-- ★ 실습 환경에는 걸리는 것이 없다. 사용자 데이터가 단순하기 때문이다.
--
-- ★ 여기 나온 테이블은 복제되지 않는다.
--   업무에 중요한 테이블이 나온다면 Logical Standby 는 답이 아니다.
--
-- ★ 대표적으로 걸리는 것들
--     BFILE, ROWID, UROWID
--     사용자 정의 타입, 컬렉션(중첩 테이블·VARRAY)
--     객체 관계형 뷰, XMLType 의 일부 저장 방식
--     압축 테이블의 일부 형태
--
--   목록을 외우기보다 이 뷰를 조회하는 습관이 낫다.
--   버전마다 지원 범위가 달라진다.
--
-- ★ 실습 05 에서 일부러 ROWID 컬럼을 만들어 이 뷰를 채워 본다.

--
--   그런 테이블도 복제는 된다.
--   다만 오라클이 "어느 행을 고쳐야 하는가" 를 판단하려고
--   모든 컬럼을 비교하므로 느려진다.
--
-- ★ 운영에서 이 뷰에 많은 테이블이 나온다면
--   기본 키를 추가하는 것이 Logical Standby 도입의 사전 작업이 된다.

-- ★ 이 실습에서 확인한 것
--
--   ① 전환은 되돌릴 수 없다 → VM 스냅샷 pre-logical 을 먼저 만든다
--   ② 출발점 — PRIMARY / PHYSICAL STANDBY, CDB=YES
--   ③ 보충 로깅은 전부 NO, FORCE_LOGGING 만 YES
--   ④ DBA_LOGSTDBY_UNSUPPORTED 0행 — 걸리는 것이 없다
--   ⑤ DBA_LOGSTDBY_NOT_UNIQUE 0행
--   ⑥ DBA_LOGSTDBY_SKIP 35개 — 대부분 INTERNAL SCHEMA
--   ⑦ SYSTEM 스키마는 복제되지 않는다
--
-- ★ 다음 실습에서 LogMiner 딕셔너리를 만든다.
