================================================================================
 제12장 실습 02 — LogMiner 딕셔너리 만들기
 대상   : chicago-srv Primary
 목표   : DBMS_LOGSTDBY.BUILD 를 실행하고 그것이 무엇을 바꾸는지 전후 비교로
          확인한다. 딕셔너리가 리두를 타고 가는 구조를 이해한다
 소요   : 약 25분
 변경   : Primary 의 보충 로깅이 켜진다 (스냅샷으로 원복)

--------------------------------------------------------------------------------
 [1] 왜 딕셔너리가 필요한가
--------------------------------------------------------------------------------

-- ★ 리두에는 이름이 없다.
--
--   기록되는 것   객체 번호 12345, 컬럼 번호 3
--   필요한 것     "객체 12345 는 LGU.T1 테이블이고 3번 컬럼은 TAG"
--
--   그 대응표가 LogMiner 딕셔너리다.
--
-- ★ Standby 에 직접 만들 수는 없다.
--   Standby 는 읽기 전용이라 자기 딕셔너리를 갱신할 수 없다.
--
--   그래서 Primary 가 자기 딕셔너리를 리두에 통째로 실어 보낸다.
--   Standby 는 그 리두를 받아 자기 안에 딕셔너리를 세운다.
--   전환 명령이 하는 일의 절반이 이것이다.

--------------------------------------------------------------------------------
 [3] BUILD
--------------------------------------------------------------------------------

SYS@chicago> SET SERVEROUTPUT ON
SYS@chicago> EXEC dbms_logstdby.build;

PL/SQL procedure successfully completed.

-- ★ 명령 한 줄인데 안에서 여러 가지가 일어난다.
--   실행 시간은 데이터베이스 규모에 따라 다르며
--   실습 환경에서는 수십 초가 걸렸다.

--------------------------------------------------------------------------------
 [4] 무엇이 바뀌었나 — 뜻밖의 부수 효과
--------------------------------------------------------------------------------

SYS@chicago> SELECT supplemental_log_data_min mn, supplemental_log_data_pk pk,
  2                supplemental_log_data_ui ui, supplemental_log_data_fk fk,
  3                supplemental_log_data_all al FROM v$database;

MN       PK  UI  FK  AL
-------- --- --- --- ---
IMPLICIT YES YES NO  NO

1 row selected.

-- ★ 보충 로깅이 켜졌다.
--
--   ALTER DATABASE ADD SUPPLEMENTAL LOG DATA 를 실행한 적이 없는데
--   값이 바뀌었다. BUILD 가 대신 해 준 것이다.
--
-- ★ MIN 이 YES 가 아니라 IMPLICIT 인 것에 주목한다.
--
--   YES       직접 켰다
--   IMPLICIT  직접 켜지는 않았지만 다른 설정 때문에 켜진 것과 같은 상태
--
--   PK 와 UI 가 켜졌으므로 최소 보충 로깅은 자동으로 성립한다.
--   그래서 IMPLICIT 이다.
--
-- ★ 실무 함의
--
--   ① 보충 로깅을 따로 켜지 않아도 된다. BUILD 가 처리한다.
--   ② 그러나 리두 양이 늘어난다는 사실은 그대로다.
--      Primary 의 I/O 와 전송 대역에 여유가 있는지 미리 봐야 한다.
--   ③ BUILD 를 "그냥 딕셔너리 만드는 것" 으로만 알고 있으면
--      리두가 갑자기 늘어난 이유를 못 찾는다.

--------------------------------------------------------------------------------
 [5] 딕셔너리가 리두에 담겼는가
--------------------------------------------------------------------------------

SYS@chicago> SELECT dictionary_begin b, dictionary_end e, count(*) cnt
  2            FROM v$archived_log
  3            WHERE dictionary_begin='YES' OR dictionary_end='YES'
  4            GROUP BY dictionary_begin, dictionary_end;

B   E          CNT
--- --- ----------
YES YES          2

1 row selected.

-- ★ V$ARCHIVED_LOG 에 DICTIONARY_BEGIN·DICTIONARY_END 열이 있다.
--   딕셔너리의 시작과 끝을 담은 아카이브를 표시한다.
--
-- ★ 이 두 열을 알아 두면 뒤에서 진단할 때 쓸 수 있다.
--   전환이 진행되지 않을 때 "딕셔너리가 어느 시퀀스에 있는가" 를 확인할 수 있다.

--------------------------------------------------------------------------------
 [6] 오류 재현 — 딕셔너리 흔적을 엉뚱한 열에서 찾으면
--------------------------------------------------------------------------------

SYS@chicago> SELECT sequence#, dictionary_start FROM v$archived_log
  2            WHERE rownum <= 3;

select sequence#, dictionary_start from v$archived_log
                  *
ERROR at line 1:
ORA-00904: "DICTIONARY_START": invalid identifier

>>> 원인 파악

-- 열 이름이 DICTIONARY_BEGIN 이다. START 가 아니다.
--
-- ★ 짝을 이루는 열 이름은 BEGIN/END 다.
--   START/END 나 BEGIN/FINISH 가 아니다.
--
-- ★ 이 교재에서 같은 종류의 혼동을 여러 번 만났다.
--     8장   V$LOG 에 TYPE 이 없다
--     10장  V$ARCHIVE_DEST_STATUS 에 TRANSMIT_MODE 가 없다
--     12장  DBA_LOGSTDBY_PROGRESS 에 RESTART_SCN 이 없다 (실습 04)
--
--   뷰마다 있는 열이 다르고 이름도 비슷비슷하다.
--   외우기보다 DESC 로 확인하는 편이 빠르다.

>>> 조치

SYS@chicago> DESC v$archived_log

-- DICTIONARY_BEGIN 과 DICTIONARY_END 를 확인한 뒤 다시 조회한다.

SYS@chicago> SELECT dictionary_begin b, dictionary_end e, count(*) cnt
  2            FROM v$archived_log
  3            WHERE dictionary_begin='YES' OR dictionary_end='YES'
  4            GROUP BY dictionary_begin, dictionary_end;

>>> 재확인

B   E          CNT
--- --- ----------
YES YES          2

1 row selected.

--
-- ★ 그런데 여기에 함정이 있다.
--   지금 MRP 가 돌고 있으므로 이 리두를 곧 적용해 지나가 버린다.
--   전환 명령은 자기가 시작한 지점부터 앞으로 나아가며 딕셔너리를 찾는데
--   그것이 이미 뒤에 있으면 영원히 못 찾는다.
--
--   실습 03 에서 그 상황을 실제로 만난다.

--------------------------------------------------------------------------------
 [8] 문서에 적힌 순서
--------------------------------------------------------------------------------

-- ★ 올바른 순서는 이렇다.
--
--   ① Standby 에서 적용을 멈춘다
--      ALTER DATABASE RECOVER MANAGED STANDBY DATABASE CANCEL;
--
--   ② Primary 에서 딕셔너리를 만든다
--      EXEC DBMS_LOGSTDBY.BUILD;
--
--   ③ Standby 에서 전환한다
--      ALTER DATABASE RECOVER TO LOGICAL STANDBY KEEP IDENTITY;
--
-- ★ 이 실습에서는 ②를 먼저 했다.
--   ①을 건너뛴 채로 BUILD 했으므로 MRP 가 계속 돌고 있었다.
--   그 결과가 실습 03 에서 드러난다.
--
-- ★ 일부러 순서를 어긴 것이 아니라 실제로 그렇게 진행됐고,
--   그래서 이 교재가 그 상황과 해결책을 담을 수 있게 되었다.

--------------------------------------------------------------------------------
 [9] 정리
--------------------------------------------------------------------------------

-- ★ 이 실습에서 확인한 것
--
--   ① 딕셔너리는 리두를 타고 Standby 로 간다
--   ② DBMS_LOGSTDBY.BUILD 한 줄로 만든다
--   ③ BUILD 가 보충 로깅을 자동으로 켠다
--      MN: NO → IMPLICIT, PK: NO → YES, UI: NO → YES
--   ④ IMPLICIT 은 "직접 켜지는 않았지만 켜진 것과 같다" 는 뜻
--   ⑤ V$ARCHIVED_LOG 의 DICTIONARY_BEGIN·DICTIONARY_END 로 확인한다
--   ⑥ BUILD 후 로그를 전환해야 Standby 로 넘어간다
--   ⑦ 순서는 적용 중지 → BUILD → 전환
--   ⑧ 열 이름은 DICTIONARY_BEGIN/END (START 아님) — 틀리면 ORA-00904
--
-- ★ 주의 — BUILD 는 반드시 Primary 에서 실행한다.
--   Physical Standby 에서 실행하면 ORA-65024 로 실패하는데,
--   실패하면서도 그 노드의 보충 로깅 설정과 적용 상태를 건드린다.
--   "실패했으니 아무 일도 없었다" 고 넘기면 안 되는 사례다.
--
-- ★ 다음 실습에서 전환한다. 순서를 어긴 대가를 치른다.
