 [1] 적용을 멈추고 재기동 준비
--------------------------------------------------------------------------------

SYS@boston> ALTER DATABASE RECOVER MANAGED STANDBY DATABASE CANCEL;

Database altered.

-- DUPLICATE 스크립트가 MRP 를 이미 띄워 두었으므로 먼저 멈춘다.
-- 이 상태에서 바로 OPEN READ ONLY 를 해도 되지만,
-- spfile 로 정식 기동되는지 확인하기 위해 한 번 내렸다 올린다.

--------------------------------------------------------------------------------
 [2] 오류 재현 — 설치 가이드의 불필요한 단계
--------------------------------------------------------------------------------

-- 설치 가이드는 여기서 spfile 을 만들라고 한다.
-- pfile 로 띄웠으니 spfile 이 필요하다는 논리다. 그대로 해 본다.

SYS@boston> CREATE SPFILE FROM MEMORY;

create spfile from memory
*
ERROR at line 1:
ORA-32002: cannot create SPFILE already being used by the instance

>>> 원인 파악
    "이미 인스턴스가 사용 중인 SPFILE 은 만들 수 없다."

    지금 boston 은 pfile 이 아니라 **spfile 로 돌고 있다.**
    실습 02 에서 확인한 대로다.

SYS@boston> COL value FOR a60
SYS@boston> SELECT name, value FROM v$parameter WHERE name='spfile';

NAME       VALUE
---------- ------------------------------------------------------------
spfile     /u01/app/oracle/product/19.3.0/dbhome_1/dbs/spfileboston.ora

1 row selected.

    ★ 언제 spfile 로 바뀌었는가?
      DUPLICATE 스크립트의 SPFILE 절이 만들어 주었다.
      그 절이 Primary spfile 을 가져와 SET 지시대로 고친 뒤
      Standby 에 spfileboston.ora 로 쓰고, 인스턴스를 그것으로 재기동한다.

      즉 NOMOUNT 로 띄울 때만 pfile 을 쓰고,
      복제가 시작되는 순간 spfile 로 갈아탄다.

    ★ 따라서 이 단계는 **처음부터 필요 없다.**
      설치 가이드가 SPFILE 절이 하는 일을 반영하지 못한 것이다.
      4장에서 발견한 가이드 오류(chown 그룹 이름)에 이은 두 번째 결함이다.

>>> 조치
    이 단계를 건너뛴다. 아무것도 고칠 필요가 없다.
    다만 ORA-32002 를 보고 "복제가 잘못됐나" 하고 되돌아가지 않도록
    그 뜻을 정확히 알아 두는 것이 중요하다.

>>> 재확인
    spfile 이 이미 있고 그것으로 돌고 있음을 확인하는 것으로 충분하다.

[oracle@boston-srv ~]$ ls -l $ORACLE_HOME/dbs/spfileboston.ora
-rw-r-----. 1 oracle dba 5632 Aug 27 09:27 spfileboston.ora

    5,632바이트다. 실습 02 에서 본 47바이트짜리 initboston.ora 와 비교하면
    DUPLICATE 가 얼마나 많은 파라미터를 채워 넣었는지 알 수 있다.

 [3] 재기동과 Active Data Guard 전환
--------------------------------------------------------------------------------

SYS@boston> SHUTDOWN IMMEDIATE

ORA-01109: database not open

Database dismounted.
ORACLE instance shut down.

-- ★ ORA-01109 는 오류가 아니다.
--   "데이터베이스가 열려 있지 않다"는 알림일 뿐이며,
--   바로 다음 줄에서 dismount 와 shutdown 이 정상 수행되었다.
--   MOUNTED 상태에서 SHUTDOWN IMMEDIATE 하면 늘 나온다.
--   1장 실습 04 에서 같은 메시지를 이미 만났다.

SYS@boston> STARTUP MOUNT
ORACLE instance started.

Total System Global Area 3221223192 bytes
Fixed Size                  9139992 bytes
Variable Size             654311424 bytes
Database Buffers         2550136832 bytes
Redo Buffers                7634944 bytes
Database mounted.

-- ★ SGA 가 3,221,223,192 바이트(약 3GB)로 커졌다.
--   실습 03 에서 pfile 로 띄웠을 때는 356,512,392 바이트(약 356MB)였다.
--   spfile 로 기동되면서 Primary 와 같은 규모가 된 것이다.
--   약 9배 차이다.

SYS@boston> ALTER DATABASE OPEN READ ONLY;

Database altered.

SYS@boston> ALTER PLUGGABLE DATABASE chicago_pdb1 OPEN READ ONLY;

Pluggable database altered.

-- ★ PDB 를 따로 여는 이 한 줄이 설치 가이드에 없다.
--   CDB 를 READ ONLY 로 열어도 PDB 는 자동으로 열리지 않는다.
--   1장 실습 04 에서 이미 확인한 사실이다.
--   이 줄을 빠뜨리면 ADG 실습에서 사용자 데이터를 조회할 수 없다.

SYS@boston> ALTER DATABASE RECOVER MANAGED STANDBY DATABASE
  2            USING CURRENT LOGFILE DISCONNECT FROM SESSION;

Database altered.

-- 열린 상태에서 적용을 다시 켠다.
-- USING CURRENT LOGFILE 이 실시간 적용(Real-Time Apply)을 뜻한다.
-- 이 순간부터 Active Data Guard 다.

 [4] 검증 ① — 데이터베이스 식별 정보
--------------------------------------------------------------------------------

SYS@boston> COL name FOR a10
SYS@boston> SELECT dbid, name, db_unique_name, database_role, open_mode,
  2                controlfile_type FROM v$database;

      DBID NAME       DB_UNIQUE_NAME   DATABASE_ROLE    OPEN_MODE            CONTROLFILE_TYPE
---------- ---------- ---------------- ---------------- -------------------- ----------------
1852041610 CHICAGO    boston           PHYSICAL STANDBY READ ONLY WITH APPLY STANDBY

1 row selected.

-- 실습 01 의 기준값과 대조한다.
--
--   DBID              1852041610      기준값과 같다 ✓
--   NAME              CHICAGO         기준값과 같다 ✓
--   DB_UNIQUE_NAME    boston          기준값(chicago)과 달라야 한다 ✓
--   DATABASE_ROLE     PHYSICAL STANDBY ✓
--   OPEN_MODE         READ ONLY WITH APPLY  ← Active Data Guard ✓
--   CONTROLFILE_TYPE  STANDBY         ✓
--
-- ★ DBID 가 같다는 것이 물리 복제본의 증거다.
--   일반 DUPLICATE(for standby 없이)는 새 DBID 를 부여하고 RESETLOGS 한다.
--   그러면 Data Guard 로 쓸 수 없다.
--
-- ★ READ ONLY WITH APPLY 라는 한 문장에 ADG 의 전부가 들어 있다.
--   READ ONLY  — 조회할 수 있다
--   WITH APPLY — 그러면서 동시에 리두를 적용하고 있다
--   11g 이전에는 이 둘을 동시에 할 수 없었다.

-- ★ 네 가지를 읽는다.
--
-- ① ONLINE 3그룹 — Primary 와 같다.
--    Standby 에서는 쓰이지 않지만, 역할 전환 후 Primary 가 되면 필요하다.
--
-- ② STANDBY 4그룹 — 4장에서 Primary 에 만든 SRL 이 그대로 복제되었다.
--    온라인 3그룹 + 1 = 4 라는 규칙이 지켜졌다.
--    **직접 만든 것이 아니라 DUPLICATE 가 만들어 준 것이다.**
--    4장에서 Primary 쪽 SRL 을 먼저 만들어 둔 보람이 여기서 나온다.
--
-- ③ 경로가 onlinelog/ 다. 데이터 파일의 datafile/ 과 다르다.
--    log_file_name_convert 를 따로 지정했기 때문이다.
--
-- ④ 파일 이름 stdbyredo04~07 도 Primary 와 같다.

 [11] 원상 복구 확인
--------------------------------------------------------------------------------

  이 실습이 끝난 시점의 상태가 곧 이 과정의 기준 상태다.

    chicago : PRIMARY / READ WRITE / MAXIMUM PERFORMANCE
    boston  : PHYSICAL STANDBY / READ ONLY WITH APPLY / MRP0 동작
    지연    : transport 0, apply 0
    목적지  : dest 1, 2 모두 VALID

  다음 장으로 넘어가기 전에 이 네 줄을 반드시 확인한다.
  하나라도 어긋나면 VM 스냅샷 adg-configured 로 되돌린다.

--------------------------------------------------------------------------------
 [12] 정리
--------------------------------------------------------------------------------

  · DBID 가 같아야 물리 복제본이다. 이것이 for standby 의 핵심 효과다
  · CREATE SPFILE FROM MEMORY 는 필요 없다. DUPLICATE 가 이미 만들었다
  · CDB 를 READ ONLY 로 열어도 PDB 는 따로 열어야 한다
  · SRL 은 복제되어 온다. Primary 에 미리 만들어 둔 덕분이다
  · READ ONLY WITH APPLY 가 Active Data Guard 의 표식이다
  · 검증은 기준값과의 대조다. 기준값을 미리 기록해 두는 습관이 중요하다
