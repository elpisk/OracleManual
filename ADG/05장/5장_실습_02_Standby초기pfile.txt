================================================================================
 제5장 실습 02 — Standby 초기 pfile 작성
 대상   : boston-srv Standby
 목표   : 두 줄짜리 pfile 로 충분한 이유를 이해하고, DUPLICATE 가 나머지
          파라미터를 어떻게 만들어 주는지 확인한다
 소요   : 약 15분
 변경   : pfile 작성 (기존 파일은 덮어쓰지 않고 확인만)
================================================================================

--------------------------------------------------------------------------------

--------------------------------------------------------------------------------

--   hc_boston.dat    인스턴스 상태 파일. 오라클이 관리한다
--   initboston.ora   DUPLICATE 를 시작할 때 쓴 최소 pfile (47바이트)
--   lkBOSTON         인스턴스 잠금 파일. 같은 SID 중복 기동을 막는다
--   orapwboston      패스워드 파일 (3장에서 다룬 것)
--   snapcf_boston.f  RMAN 스냅샷 컨트롤 파일. DUPLICATE 과정에서 만들어졌다 (19MB)
--   spfileboston.ora DUPLICATE 가 만들어 준 spfile. 지금은 이것을 쓴다

--------------------------------------------------------------------------------
 [2] 최소 pfile 의 내용
--------------------------------------------------------------------------------

[oracle@boston-srv ~]$ cat $ORACLE_HOME/dbs/initboston.ora

db_name=chicago
enable_pluggable_database=true

-- 두 줄이 전부다. 47바이트.
--
--   db_name=chicago
--     Primary 와 같아야 한다. 물리 복제본이기 때문이다.
--     여기에 boston 을 쓰면 DUPLICATE 가 실패한다.
--     헷갈리기 쉬운 지점이다 — 인스턴스 이름은 boston 이지만 DB_NAME 은 chicago 다.
--
--   enable_pluggable_database=true
--     CDB 를 복제하므로 필요하다.
--     이것이 없으면 PDB 를 담을 수 없어 복제가 실패한다.
--
-- ★ 나머지 파라미터는 어디로 갔는가?
--   DUPLICATE 스크립트의 SPFILE 절이 Primary 의 spfile 을 가져와
--   Standby 용으로 바꿔 준다.
--   즉 이 두 줄은 "인스턴스를 띄우기 위한 최소한" 일 뿐이고,
--   진짜 파라미터는 복제 과정에서 만들어진다.

 [3] 지금 boston 이 실제로 쓰는 파라미터 파일
--------------------------------------------------------------------------------

SYS@boston> COL value FOR a60

-- 지금은 pfile 이 아니라 spfile 을 쓰고 있다.
-- DUPLICATE 가 만든 것이며, 이후 재기동에서도 이것을 읽는다.

-- 이 사실은 spfile 을 만들어 보려 하면 곧바로 드러난다.

SYS@boston> CREATE SPFILE FROM MEMORY;

create spfile from memory
*
ERROR at line 1:
ORA-32002: cannot create SPFILE already being used by the instance

-- ★ "이미 인스턴스가 쓰고 있는 SPFILE 은 만들 수 없다."
--   즉 이 오류가 난다는 것 자체가 spfile 로 돌고 있다는 증거다.
--   NOMOUNT 로 띄울 때만 pfile 을 쓰고,
--   복제가 시작되는 순간 spfile 로 갈아탄 것이다.
--   설치 가이드가 이 단계를 넣어 둔 이유와 그것이 왜 불필요한지는
--   실습 06 에서 다시 다룬다.

-- ★ 실습 01 과 대조해 본다.
--
--   Primary 에서는 db_file_name_convert 와 log_file_name_convert 가 비어 있었다.
--   Standby 에서는 값이 들어 있다.
--   DUPLICATE 스크립트의 SET 절이 Standby spfile 에만 넣어 준 것이다.
--
--   log_archive_dest_2 의 방향이 반대다.
--     Primary : service=boston   (chicago → boston)
--     Standby : service=chicago  (boston → chicago)
--   지금은 쓰이지 않지만 역할 전환 후 즉시 필요해진다.
--   VALID_FOR 가 primary_role 이므로 현재는 VALID_NOW 가 아니다 (2장).
--
--   fal_server 도 반대다.
--     Primary : boston / Standby : chicago
--   갭이 생겼을 때 요청할 상대를 가리킨다.
--
--   db_name 은 chicago 그대로, db_unique_name 만 boston 이다.

--------------------------------------------------------------------------------
 [5] 오류 재현 — db_name 을 boston 으로 쓰면
--------------------------------------------------------------------------------

-- 흔한 실수를 재현한다. 인스턴스 이름이 boston 이니 db_name 도 boston 일 것 같지만
-- 물리 복제본은 DB_NAME 이 같아야 한다.

[oracle@boston-srv ~]$ cat > /tmp/initboston_wrong.ora <<'EOF'
db_name=boston
enable_pluggable_database=true
EOF

SYS@boston> SHUTDOWN IMMEDIATE
SYS@boston> STARTUP NOMOUNT PFILE='/tmp/initboston_wrong.ora'
ORACLE instance started.

-- 인스턴스는 뜬다. db_name 이 틀렸다는 것을 이 시점에는 알 수 없다.

[oracle@chicago-srv ~]$ rman target "'sys/oracle@chicago as sysdba'" >   auxiliary "'sys/oracle@boston as sysdba'"

connected to target database: CHICAGO (DBID=1852041610)
connected to auxiliary database: BOSTON (not mounted)

-- ★ 여기서 이미 드러난다.
--   정상이라면 auxiliary 쪽도 CHICAGO 로 표시되어야 한다.
--   BOSTON 으로 나온다는 것은 auxiliary 의 DB_NAME 이 다르다는 뜻이다.
--
--   실습 03 의 정상 접속과 대조해 본다.
--     connected to auxiliary database: CHICAGO (not mounted)   ← 정상
--     connected to auxiliary database: BOSTON  (not mounted)   ← db_name 오설정
--
--   이 한 줄만 확인해도 DUPLICATE 를 실행하기 전에 잘못을 잡을 수 있다.
--   실제로 DUPLICATE 를 실행하면 복제 도중 또는 마운트 단계에서 실패한다.


>>> 원인 파악
    물리 복제본은 DB_NAME 이 원본과 같아야 한다.
    1장에서 확인한 대로 V$DATABASE.NAME 은 양쪽 모두 CHICAGO 였다.
    구별하는 것은 DB_UNIQUE_NAME 이지 DB_NAME 이 아니다.

    ★ 헷갈리는 이유
      ORACLE_SID       = boston   (그 서버의 인스턴스 이름)
      DB_UNIQUE_NAME   = boston   (구성 안에서 구별하는 이름)
      DB_NAME          = chicago  ← 이것만 다르다
      리스너 GLOBAL_DBNAME = boston (3장)
      패스워드 파일 이름 = orapwboston (3장)

      네 개가 boston 인데 하나만 chicago 다. 실수하기 딱 좋은 구조다.

>>> 조치
    pfile 의 db_name 을 chicago 로 바로잡는다.

[oracle@boston-srv ~]$ cat $ORACLE_HOME/dbs/initboston.ora
db_name=chicago
enable_pluggable_database=true

>>> 재확인
    올바른 pfile 로 NOMOUNT 기동한 뒤 DUPLICATE 를 실행하면 정상 진행된다.

[oracle@boston-srv ~]$ rm -f /tmp/initboston_wrong.ora

--------------------------------------------------------------------------------
 [6] 정리 — 이름이 네 개, 값은 두 종류
--------------------------------------------------------------------------------

  항목                        chicago 노드          boston 노드
  --------------------------- --------------------- ---------------------
  ORACLE_SID                  chicago               boston
  DB_NAME                     chicago               chicago   ← 같다
  DB_UNIQUE_NAME              chicago               boston
  리스너 GLOBAL_DBNAME        chicago               boston
  패스워드 파일               orapwchicago          orapwboston
  tnsnames 별칭               CHICAGO               BOSTON
  데이터 경로                 .../Chicago/          .../Boston/datafile/

  ★ DB_NAME 하나만 같고 나머지는 전부 다르다.
    초기 pfile 을 작성할 때 이 한 줄을 틀리는 것이 가장 흔한 실수다.

SYS@boston> EXIT
