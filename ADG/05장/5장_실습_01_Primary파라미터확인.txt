================================================================================
 제5장 실습 01 — Primary 파라미터 확인과 기준값 기록
 대상   : chicago-srv Primary
 목표   : 2~4장에서 설정한 값들이 실제로 어떻게 들어가 있는지 확인하고,
          DUPLICATE 후 대조할 기준값을 기록한다
 소요   : 약 20분
 변경   : 없음 (전부 조회)
================================================================================

--------------------------------------------------------------------------------
 [1] Data Guard 핵심 파라미터 일괄 확인
--------------------------------------------------------------------------------

SYS@chicago> SET LINES 220 PAGES 200
SYS@chicago> COL name FOR a30
SYS@chicago> COL value FOR a76
SYS@chicago> SELECT name, value FROM v$parameter
  2            WHERE name IN ('db_name','db_unique_name','log_archive_config',
  3                           'log_archive_dest_1','log_archive_dest_2',
  4                           'log_archive_dest_state_1','log_archive_dest_state_2',
  5                           'fal_server','fal_client','standby_file_management',
  6                           'db_file_name_convert','log_file_name_convert',
  7                           'remote_login_passwordfile','log_archive_max_processes')
  8            ORDER BY name;

NAME                       VALUE
-------------------------- ----------------------------------------------------------------
db_file_name_convert
db_name                    chicago
db_unique_name             chicago
fal_client                 chicago
fal_server                 boston
log_archive_config         dg_config=(chicago,boston)
log_archive_dest_1         location=use_db_recovery_file_dest
                           valid_for=(all_logfiles,all_roles) db_unique_name=chicago
log_archive_dest_2         service=boston ASYNC NOAFFIRM
                           valid_for=(online_logfiles,primary_role) db_unique_name=boston
log_archive_dest_state_1   enable
log_archive_dest_state_2   ENABLE
log_archive_max_processes  4
log_file_name_convert
remote_login_passwordfile  EXCLUSIVE
standby_file_management    AUTO

-- 읽는 법
--
--   db_name / db_unique_name  둘 다 chicago. Primary 이므로 같다
--   fal_server = boston       갭이 생기면 boston 에게 요청한다 (역할 전환 대비)
--   fal_client = chicago      요청할 때 자신을 알리는 이름
--   standby_file_management = AUTO
--       Primary 에서 데이터 파일을 추가하면 Standby 가 자동으로 따라 만든다 (8장)
--   remote_login_passwordfile = EXCLUSIVE
--       원격 SYS 접속 허용. 이것이 없으면 DUPLICATE 자체가 불가능하다 (3장)
--
-- ★ db_file_name_convert 와 log_file_name_convert 가 **비어 있다.**
--   Primary 에서는 필요 없기 때문이다.
--   이 두 값은 DUPLICATE 스크립트의 SET 절로 Standby 쪽 spfile 에만 들어간다.
--   실습 04 에서 확인한다.

--------------------------------------------------------------------------------

-- TARGET 열이 새로 보인다.
--   dest_1 은 PRIMARY  → 이 데이터베이스 자신에게 쓴다 (로컬 아카이브)

--
-- 두 목적지 모두 VALID 이고 VALID_NOW 가 YES 다. 2장의 진단 순서 ① 통과.

--

--
-- 파일 번호 2 가 없는 것은 정상이다. CDB 에서 2번은 쓰이지 않는다.

--
-- ★ Standby 의 컨트롤 파일은 DUPLICATE 스크립트의
--   SET CONTROL_FILES 로 지정한 한 개만 만들어진다.
--   운영 환경이라면 Standby 도 이중화하는 편이 좋다.

--------------------------------------------------------------------------------
 [5] 오류 재현 — 준비가 덜 된 상태에서 DUPLICATE 를 시작하면
--------------------------------------------------------------------------------

-- DUPLICATE 는 Standby 인스턴스가 NOMOUNT 로 떠 있어야 시작된다.
-- 지금 boston 은 정상 운영 중(READ ONLY WITH APPLY)이다. 이 상태로 시도해 본다.

[oracle@chicago-srv ~]$ rman target "'sys/oracle@chicago as sysdba'" \
>   auxiliary "'sys/oracle@boston as sysdba'"

connected to target database: CHICAGO (DBID=1852041610)
connected to auxiliary database: CHICAGO (DBID=1852041610)

RMAN> run { duplicate target database for standby from active database; }

Starting Duplicate Db at 27-AUG-26
using target database control file instead of recovery catalog
allocated channel: ORA_AUX_DISK_1
channel ORA_AUX_DISK_1: SID=144 device type=DISK
RMAN-00571: ===========================================================
RMAN-00569: =============== ERROR MESSAGE STACK FOLLOWS ===============
RMAN-00571: ===========================================================
RMAN-03002: failure of Duplicate Db command at 08/27/2026 09:34:47
RMAN-05501: aborting duplication of target database
RMAN-05500: the auxiliary database must be not mounted when issuing a
            DUPLICATE command


>>> 원인 파악
    RMAN-05500 이 원인을 그대로 말해 준다.
    "DUPLICATE 를 실행할 때 auxiliary 데이터베이스는 마운트되어 있지 않아야 한다."

    접속 줄에서 이미 예고돼 있었다.
      connected to auxiliary database: CHICAGO (DBID=1852041610)

    정상이라면 다음과 같이 "(not mounted)" 가 붙는다.
      connected to auxiliary database: CHICAGO (not mounted)

    ★ RMAN 접속 직후 이 한 줄만 봐도 시작해도 되는지 알 수 있다.
      DBID 가 표시되면 이미 마운트된 것이므로 진행하면 안 된다.

>>> 조치
    Standby 를 내리고 NOMOUNT 로 다시 띄운다. 실습 03 에서 수행한다.

>>> 재확인
    RMAN 접속 시 auxiliary 쪽에 "(not mounted)" 가 표시되는지 본다.
    이 한 줄이 DUPLICATE 를 시작해도 좋다는 신호다.
