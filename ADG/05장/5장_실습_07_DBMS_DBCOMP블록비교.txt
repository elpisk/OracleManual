================================================================================
 제5장 실습 07 — DBMS_DBCOMP 로 블록 단위 검증하기
 대상   : chicago-srv Primary 에서 실행
 목표   : 19c 의 DBMS_DBCOMP 로 Primary 와 Standby 의 블록을 직접 비교하고,
          결과 보고서를 읽는 법과 이 패키지의 함정 세 가지를 익힌다
 소요   : 약 40분
 변경   : $ORACLE_HOME/dbs 아래에 보고서 파일이 생긴다 (마지막에 제거)
================================================================================

--------------------------------------------------------------------------------
 [1] DBMS_DBCOMP 란
--------------------------------------------------------------------------------

  실습 06 의 검증은 전부 **메타데이터** 비교였다.
  파일 개수, 파일 번호, 경로, 지연 시간.

  DBMS_DBCOMP 는 한 단계 더 들어간다.
  Primary 와 Standby 의 **데이터 블록을 실제로 하나씩 맞춰 본다.**
  19c 에서 새로 들어온 패키지다.

  용도는 두 가지다.
    ① 복제가 물리적으로 정확한지 확인한다 (지금 하려는 것)
    ② lost write 를 찾는다 — 디스크가 쓴 척만 하고 실제로는 쓰지 않은 경우

  호출 형태는 다음과 같다.

    DBMS_DBCOMP.DBCOMP(datafile_name, output_file, block_dump);

--------------------------------------------------------------------------------
 [2] 두 번째 인자의 함정 — 디렉터리 객체가 아니다
--------------------------------------------------------------------------------

-- 성공했다. 그런데 디렉터리를 보면 비어 있다.

[oracle@boston-srv  ~]$ ls -l /u03/dbcomp

[oracle@chicago-srv ~]$ ls -l $ORACLE_HOME/dbs/DBCOMP*

-rw-r-----. 1 oracle dba 2269 Aug 27 09:12 .../dbs/DBCOMP_DIR
-rw-r-----. 1 oracle dba 1998 Aug 27 09:12 .../dbs/DBCOMP_DIR_boston_7

-- ★ 여기 있었다. $ORACLE_HOME/dbs 아래다.
--
--   두 번째 인자는 **디렉터리 객체 이름이 아니라 파일 이름 접두어**다.
--   'DBCOMP_DIR' 이라는 문자열을 그대로 파일 이름으로 썼다.
--   디렉터리 객체 DBCOMP_DIR 은 아무 관련이 없었다.
--
--   파일이 두 개 생긴다.
--     DBCOMP_DIR            요약 보고서
--     DBCOMP_DIR_boston_7   상세 보고서
--                  ↑      ↑
--                  |      데이터 파일 번호 (users01.dbf 는 7번)
--                  상대 데이터베이스의 DB_UNIQUE_NAME
--
--   이 이름 규칙을 알아 두면 파일을 찾기 쉽다.

[oracle@boston-srv ~]$ ls -l $ORACLE_HOME/dbs/DBCOMP*
ls: cannot access /u01/app/oracle/product/19.3.0/dbhome_1/dbs/DBCOMP*:
    No such file or directory

-- ★ Standby 쪽에는 아무것도 남지 않는다.
--   보고서는 명령을 실행한 쪽(Primary)에만 생긴다.

>>> 원인 파악
    "출력 파일을 만들 수 없거나 이미 존재한다."

    앞의 실행이 만든 DBCOMP_DIR 파일이 아직 있다.
    DBMS_DBCOMP 는 덮어쓰지 않는다.

    ★ 메시지가 두 가지 가능성을 함께 말하고 있다는 점에 주의한다.
      ① 파일이 이미 있다  (지금의 경우)
      ② 파일을 만들 권한이 없다
      $ORACLE_HOME/dbs 에 쓸 수 없는 상황이라면 ②다.
      어느 쪽인지는 ls 로 확인하면 바로 갈린다.

>>> 조치
    두 가지 중 하나를 택한다.
      ① 이전 파일을 지운다
      ② 새 접두어를 쓴다   ← 이쪽을 권한다

    운영에서는 접두어에 날짜를 넣어 두면 이 오류를 피하면서
    이력도 남는다. 예: 'dgcheck_20260827'

>>> 재확인

SYS@chicago> BEGIN
  2    dbms_dbcomp.dbcomp('/u03/app/oracle/oradata/Chicago/system01.dbf',
  3                       'dgcheck1', FALSE);
  4  END;
  5  /

PL/SQL procedure successfully completed.

[oracle@chicago-srv ~]$ ls -l $ORACLE_HOME/dbs/dgcheck1*
-rw-r-----. 1 oracle dba 2772 Aug 27 09:16 .../dbs/dgcheck1
-rw-r-----. 1 oracle dba 2389 Aug 27 09:16 .../dbs/dgcheck1_boston_1

    새 접두어로는 정상 수행된다.
    이번에는 1번 파일(system01.dbf)이므로 이름 끝이 _boston_1 이다.

>>> 원인 파악
    ORA-53201 하나가 두 상황을 모두 가리킨다.
      · 인자가 NULL 이다
      · 인자가 유효하지 않다 (그런 파일이 없다)

    ★ 즉 **한 번에 한 파일씩만** 비교할 수 있다.
      전체 데이터베이스를 한 번에 비교하는 기능은 없다.
      여러 파일을 보려면 V$DATAFILE 을 돌며 반복 호출해야 한다.

    ★ 오타에도 같은 오류가 나므로, 파일 이름은
      V$DATAFILE 에서 복사해 쓰는 것이 안전하다.

>>> 조치
    비교할 파일을 명시한다. 경로는 V$DATAFILE.NAME 그대로 쓴다.

>>> 재확인
    [3] 의 마지막 실행이 정상 완료된 것으로 확인된다.

 [5] 오류 재현 ③ — 조용한 함정: 없는 디렉터리 객체 이름
--------------------------------------------------------------------------------

-- 존재하지 않는 디렉터리 객체 이름을 주면 오류가 날 것 같다. 해 본다.

SYS@chicago> BEGIN
  2    dbms_dbcomp.dbcomp('/u03/app/oracle/oradata/Chicago/users01.dbf',
  3                       'NO_SUCH_DIR_OBJECT', FALSE);
  4  END;
  5  /

PL/SQL procedure successfully completed.

>>> 원인 파악
    ★ **오류가 나지 않는다.** 이것이 가장 위험하다.

    [2] 에서 확인한 대로 두 번째 인자는 디렉터리 객체가 아니라
    파일 이름 접두어이기 때문이다.
    'NO_SUCH_DIR_OBJECT' 는 그저 파일 이름이 되었을 뿐이다.

    ★ 왜 위험한가.
      디렉터리 객체를 넣었다고 믿은 사람은 그 디렉터리를 들여다본다.
      아무것도 없다. 그런데 오류도 없었다.
      "비교했는데 아무 문제 없었나 보다" 하고 넘어가기 쉽다.
      실제로는 보고서를 엉뚱한 곳에서 찾고 있었을 뿐이다.

      ORA-24258 처럼 소리를 내는 오류보다,
      이렇게 조용히 성공하는 쪽이 훨씬 다루기 어렵다.

>>> 조치
    실행 후 반드시 $ORACLE_HOME/dbs 에서 파일을 확인하는 습관을 들인다.

[oracle@chicago-srv ~]$ ls -lt $ORACLE_HOME/dbs/ | head -5

>>> 재확인
    접두어와 같은 이름의 파일이 dbs 아래에 생겼는지 본다.
    생기지 않았다면 실행 자체가 안 된 것이다.

 [7] 열의 뜻과 판정 기준
--------------------------------------------------------------------------------

  열          뜻                                    정상값
  ----------- ------------------------------------- ---------------------
  TOTAL       찾은 블록 수                          —
  CORR        손상된 블록                           0
  SKIPPED     비교 대상에서 제외된 블록             0 이 아니어도 정상
  DIFFV       버전이 다른 블록 쌍                   0 이 아니어도 정상
  SAMEV       버전이 같은 블록 쌍                   —
  SAMEV&C     버전·체크섬·내용이 모두 같은 블록     SAMEV 와 비슷해야
  ENCERR      암호화 문제로 판정 못한 블록          0
  LWLOC       로컬(Primary)의 lost write            **0 이어야 한다**
  LWRMT       원격(Standby)의 lost write            **0 이어야 한다**
  DIFFPAIR    버전은 같은데 내용이 다른 블록        **0 이어야 한다**

  ★ 판정은 세 열만 보면 된다. **DIFFPAIR, LWLOC, LWRMT.**
    이 표에서 세 열은 모든 행이 0 이다. 복제는 정상이다.

  ★ DIFFPAIR 가 왜 결정적인가.
    "버전(SCN)은 같은데 내용이 다르다"는 것은 논리적으로 있을 수 없다.
    같은 시점의 같은 블록이라면 내용도 같아야 한다.
    0 이 아니면 데이터 불일치이며, 원인을 반드시 찾아야 한다.

  ★ DIFFV 1,645 는 정상이다.
    비교하는 동안에도 Primary 는 계속 돌아간다.
    Standby 가 아직 적용하지 않은 변경분이 있으면 버전이 달라진다.
    "지금 이 순간 조금 뒤처져 있다"는 뜻일 뿐, 오류가 아니다.
    apply lag 가 0 이어도 마이크로초 단위 시차는 존재한다.

  ★ SAMEV 91,295 와 SAMEV&C 91,148 의 차이 147 도 정상 범위다.
    버전은 같은데 체크섬이 다른 블록이 있을 수 있다
    (표의 SAMEV_NO_CHKSUM 설명 참고). 내용이 같아도 체크섬은
    다를 수 있기 때문이며, 데이터 불일치와는 다르다.

  ★ SKIPPED 가 많은 행(00, 58, 70)은 빈 블록이나 직접 로드 블록이다.
    비교할 내용이 없어 건너뛴 것이다.
    ID 00 의 17,694 블록이 전부 SKIPPED 인 것이 그 예다.

 [9] 세 번째 인자 block_dump
--------------------------------------------------------------------------------

  TRUE  로 주면 차이가 난 블록의 내용을 덤프에 함께 남긴다.
  FALSE 로 주면 집계만 남는다.

  두 실행의 파일 크기를 비교하면 감이 온다.

    DBCOMP_DIR            2,269바이트   (users01.dbf, TRUE)
    DBCOMP_DIR_boston_7   1,998바이트
    dgcheck1              2,772바이트   (system01.dbf, FALSE)
    dgcheck1_boston_1     2,389바이트

  이번 실습에서는 차이 나는 블록이 거의 없어 크기 차이가 크지 않았다.
  실제 불일치가 많다면 TRUE 쪽 파일이 훨씬 커진다.

  ★ 운영에서는 FALSE 로 먼저 돌려 집계만 본다.
    DIFFPAIR 나 LWLOC/LWRMT 가 잡히면 그때 TRUE 로 다시 돌려
    문제 블록의 내용을 확인한다.

 [10] 정리
--------------------------------------------------------------------------------

  · 두 번째 인자는 디렉터리 객체가 아니라 파일 이름 접두어다
  · 보고서는 $ORACLE_HOME/dbs 아래, 실행한 쪽에만 생긴다
  · 파일 이름은 <접두어> 와 <접두어>_<상대 DB_UNIQUE_NAME>_<파일번호>
  · 같은 접두어 재사용 → ORA-24258. 날짜를 붙이면 피할 수 있다
  · NULL 이나 없는 파일 → ORA-53201. 한 번에 한 파일씩만 된다
  · 없는 디렉터리 객체 이름은 **오류 없이 넘어간다.** 실행 후 반드시 파일 확인
  · 판정은 DIFFPAIR, LWLOC, LWRMT 세 열만 본다. 전부 0 이면 정상
  · DIFFV 가 0 이 아닌 것은 정상이다. 운영 중 비교이기 때문이다
