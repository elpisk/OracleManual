--------------------------------------------------------------------------------
 [2] OMF 방식 스크립트
--------------------------------------------------------------------------------

[oracle@chicago-srv ~]$ cat /home/oracle/dup_boston_omf.rman

run
{
  allocate channel c1 type disk;
  allocate channel c2 type disk;
  allocate auxiliary channel sby type disk;

  duplicate target database for standby from active database
  DORECOVER
  spfile
    set db_name           = 'chicago'
    set db_unique_name    = 'boston'
    set audit_file_dest   = '/u01/app/oracle/admin/boston/adump'
    set diagnostic_dest   = '/u01/app/oracle/'
    set db_create_file_dest = '/u03/app/oracle/oradata'
    set db_recovery_file_dest = '/u03/app/oracle/fast_recovery_area'
    set db_recovery_file_dest_size = '15G'
    set log_archive_dest_2 =
      'service=chicago async
       valid_for=(online_logfile,primary_role)
       db_unique_name=chicago'
    set log_archive_max_processes = '4'
    set fal_server          = 'chicago'
    set standby_file_management = 'AUTO'
    set log_archive_config  = 'dg_config=(chicago,boston)';

  sql channel sby
    "alter database recover managed standby database disconnect from session";
}

-- ★ 5장 스크립트와 대조하며 읽는다.
--
--   사라진 것 (5줄)
--     parameter_value_convert 'chicago','boston'
--     set db_file_name_convert = ...
--     set log_file_name_convert = ...
--     set control_files = ...
--     nofilenamecheck
--
--   생긴 것 (3줄)
--     set db_create_file_dest = '/u03/app/oracle/oradata'
--     set db_recovery_file_dest = '/u03/app/oracle/fast_recovery_area'
--     set db_recovery_file_dest_size = '15G'
--
-- ★ nofilenamecheck 가 없어도 되는 이유
--   OMF 가 붙이는 이름에는 매번 다른 문자열이 들어간다.
--   이름이 겹칠 수가 없으므로 충돌 검사를 끌 이유도 없다.
--
-- ★ control_files 가 없는 것은 문제가 된다.
--   실습 06 에서 다룬다. 지금은 그대로 진행한다.

 [6] 오류 재현 — 성공한 뒤 같은 스크립트를 다시 실행하면
--------------------------------------------------------------------------------

-- 첫 실행이 오래 걸려 실패한 줄 알고 다시 돌리는 경우다.
-- Standby 가 이미 만들어져 정상 운영 중인 상태에서 실행해 본다.

>>> 원인 파악
    ★ 5장에서 만난 RMAN-05500 과 **다른 오류**다.

      5장 : RMAN-05500 the auxiliary database must be not mounted ...
      6장 : RMAN-05537 ... auxiliary instance is started with spfile
                        cannot use SPFILE clause

    차이의 근원은 auxiliary 가 무엇으로 떠 있느냐다.
      복제 전  : 최소 pfile 로 NOMOUNT — SPFILE 절이 spfile 을 만들어 준다
      복제 후  : 그 spfile 로 기동 — 이미 spfile 이 있다

    즉 SPFILE 절은 "지금부터 spfile 을 만들겠다"는 지시인데,
    상대가 이미 spfile 로 돌고 있으면 그 지시가 성립하지 않는다.

    ★ 채널은 세 개 다 정상 할당됐다는 점에 주목한다.
      실습 02 의 실패는 채널 할당에서 끝났다(RMAN-03002: failure of
      allocate command). 이번에는 Starting Duplicate Db 까지 갔다가
      곧바로 중단됐다. 오류가 나는 지점이 다르면 원인도 다르다.

    ★ 중요한 것은 **Standby 가 손상되지 않았다**는 사실이다.
      복제 작업이 시작되기 전에 중단됐으므로 아무 파일도 건드리지 않았다.

>>> 조치
    다시 만들 의도가 아니라면 아무것도 하지 않는다. 그대로 두면 된다.
    정말로 다시 만들어야 한다면 실습 02 의 절차대로 헐고
    최소 pfile 로 NOMOUNT 기동한 뒤 실행한다.

--------------------------------------------------------------------------------
 [8] 정리
--------------------------------------------------------------------------------

  · 성공 판정 세 가지는 방식과 무관하게 같다 (rc=0 / 오류 0줄 / Finished)
  · 로그 390줄, 49번 Starting, 383번 Finished
  · output 경로는 BOSTON(대문자), 파일 이름은 o1_mf_... 로 바뀐다
  · mkdir 을 한 번도 하지 않았는데 디렉터리가 만들어졌다
  · OMF 는 온라인 로그를 FRA 에도 만들므로 FRA 크기를 넉넉히 준다
  · 복제 직후 상태는 5장과 동일하다. MOUNTED 이며 아직 ADG 가 아니다
