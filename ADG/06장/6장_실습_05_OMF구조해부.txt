-- ★ 최상위가 **BOSTON — 대문자다.**
--   DB_UNIQUE_NAME 은 boston(소문자)인데 디렉터리는 대문자다.
--   OMF 는 DB_UNIQUE_NAME 을 대문자로 바꿔 디렉터리 이름으로 쓴다.
--
--   5장에서 만든 것은 Boston 이었다. 사람이 정한 이름이다.
--   리눅스는 대소문자를 구별하므로 Boston 과 BOSTON 은 다른 디렉터리다.
--   실습 02 에서 5장 구조를 통째로 지웠으므로 지금은 BOSTON 만 있다.

--------------------------------------------------------------------------------
 [2] DB_NAME 이 아니라 DB_UNIQUE_NAME 인 이유
--------------------------------------------------------------------------------

SYS@boston> SELECT name, db_unique_name FROM v$database;

NAME       DB_UNIQUE_NAME
---------- ------------------------------
CHICAGO    boston

-- ★ 만약 OMF 가 DB_NAME 을 썼다면 디렉터리가 CHICAGO 가 됐을 것이다.
--   Primary 와 이름이 같아 구별할 수 없다.
--   한 서버에 Standby 를 여러 개 두는 구성에서는 서로 충돌한다.
--
--   DB_UNIQUE_NAME 을 쓰면 그 값만 다르게 주는 것으로
--   디렉터리가 자동으로 분리된다. 이것이 규칙의 근거다.

-- ★ **PDB 의 GUID 다.**
--   59F0365... 디렉터리 = PDB$SEED
--   59F053E... 디렉터리 = CHICAGO_PDB1
--
-- Primary 에서도 같은 조회를 해 본다.

SYS@chicago> SELECT con_id, name, guid FROM v$pdbs ORDER BY con_id;

    CON_ID NAME           GUID
---------- -------------- ----------------------------------
         2 PDB$SEED       59F036501C3B321DE0633CE110ACEFEB
         3 CHICAGO_PDB1   59F053E76FBD3BA1E0633CE110ACE7E5

2 rows selected.

-- ★ **값이 완전히 같다.**
--   물리 복제본이므로 GUID 까지 그대로 따라온 것이다.
--
--   실무에서 이 사실이 쓸모 있다.
--   Primary 와 Standby 의 같은 PDB 는 같은 디렉터리 이름을 갖는다.
--   서버가 달라도, 경로 접두가 달라도 GUID 부분은 일치한다.
--   파일을 대조할 때 이 부분을 기준으로 삼으면 된다.
--
-- ★ 왜 이름 대신 GUID 인가
--   PDB 는 이름을 바꿀 수 있고 다른 CDB 로 옮겨 붙일 수도 있다.
--   이름을 디렉터리로 쓰면 그때마다 디렉터리를 옮겨야 한다.
--   GUID 는 PDB 가 만들어질 때 정해져 바뀌지 않는다.
--
-- ★ 대가는 가독성이다.
--   어느 디렉터리가 어느 PDB 인지 알려면 V$PDBS 를 조회해야 한다.
--   5장의 chicago_pdb1 은 보기만 해도 알 수 있었다.

 [6] 오류 재현 — Standby 에서 OMF 파일을 만들어 보면
--------------------------------------------------------------------------------

-- OMF 가 실제로 파일을 만드는 모습을 보고 싶어진다.
-- Standby 에 테이블스페이스를 만들어 본다.

SYS@boston> CREATE TABLESPACE omftest DATAFILE SIZE 10M;

create tablespace omftest datafile size 10m
*
ERROR at line 1:
ORA-16000: database or pluggable database open for read-only access

>>> 원인 파악
    Standby 는 READ ONLY 다. 어떤 구조 변경도 할 수 없다.
    1장에서 이미 만난 오류이며, Active Data Guard 의 근본 성질이다.

    ★ OMF 인지 아닌지와 무관하다. 방식의 문제가 아니라 역할의 문제다.
      Standby 에 파일이 만들어지는 것은 Primary 의 변경이 리두로 전달될 때뿐이며,
      그 처리는 STANDBY_FILE_MANAGEMENT=AUTO 가 맡는다 (8장).

>>> 조치
    Primary 에서 만들어야 한다. Primary 로 옮겨 같은 명령을 실행해 본다.

SYS@chicago> CREATE TABLESPACE omftest DATAFILE SIZE 10M;

create tablespace omftest datafile size 10m
                                   *
ERROR at line 1:
ORA-02236: invalid file name

    ★ Primary 에서도 실패했다. 다른 이유다.
      chicago 는 db_create_file_dest 가 비어 있다(실습 01).
      OMF 가 아니므로 `DATAFILE SIZE 10M` 처럼 경로를 생략할 수 없다.
      파일 이름을 지정하라는 뜻이 ORA-02236 이다.

      ★ 이 오류가 OMF 의 존재 이유를 거꾸로 보여 준다.
        OMF 가 켜져 있으면 경로를 생략해도 되고,
        꺼져 있으면 매번 경로와 이름을 적어야 한다.

>>> 재확인
    두 시도 모두 실패했으므로 아무것도 만들어지지 않았다.

SYS@chicago> SELECT tablespace_name FROM dba_tablespaces
  2            WHERE tablespace_name='OMFTEST';

no rows selected

    잔재가 없다. 원복할 것도 없다.
    ★ Primary 를 OMF 로 바꾸는 것은 이 과정의 범위 밖이다.
      실습 환경의 Primary 는 5장까지의 구성을 유지한다.

--------------------------------------------------------------------------------
 [7] 5장 구성과의 대조표
--------------------------------------------------------------------------------

  항목                5장 (경로 지정)              6장 (OMF)
  ------------------- ---------------------------- ----------------------------
  최상위 디렉터리     Boston                       BOSTON (대문자)
  하위 디렉터리       datafile, onlinelog,         datafile, onlinelog,
                      controlfile                  PDB GUID x 2
  사전 mkdir          필요                         불필요
  PDB 디렉터리        pdbseed, chicago_pdb1        59F0365..., 59F053E...
  데이터 파일 이름    system01.dbf                 o1_mf_system_1b50qfn7_.dbf
  임시 파일 확장자    .dbf                         .tmp
  파일 번호 식별      이름으로 가능                V$DATAFILE 조회
  로그 멤버           그룹당 1                     그룹당 2 (FRA 다중화)
  V$LOGFILE 행 수     7                            14
  FRA 사용량          아카이브만                   아카이브 + 온라인 로그 1.4GB
  파일 개수·번호      11개, 1,3,4,5~12             동일
  파일 크기           동일                         동일

  ★ 마지막 두 줄이 중요하다. 담긴 내용은 완전히 같다.
    두 방식의 차이는 **어디에 어떤 이름으로 두느냐**뿐이다.

--------------------------------------------------------------------------------
 [8] 정리
--------------------------------------------------------------------------------

  · OMF 는 mkdir 없이 여덟 개 디렉터리를 만든다
  · 최상위는 DB_UNIQUE_NAME 의 대문자다 (BOSTON)
  · PDB 파일은 PDB GUID 디렉터리 아래 놓인다. GUID 는 양쪽이 같다
  · 이름 규칙은 o1_mf_<테이블스페이스>_<유일문자열>_.<확장자>
  · 파일 번호는 이름에 없다. V$DATAFILE 을 봐야 한다
  · db_recovery_file_dest 가 있으면 온라인 로그가 두 곳에 다중화된다
  · 실측 14행, FRA 1,400MB 소모 — 용량 계산에 반드시 넣는다
  · Standby 에서는 어떤 파일도 직접 만들 수 없다 (ORA-16000)
