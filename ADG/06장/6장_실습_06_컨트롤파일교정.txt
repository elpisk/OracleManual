================================================================================
 제6장 실습 06 — 컨트롤 파일 교정
 대상   : boston-srv Standby
 목표   : OMF 방식인데도 컨트롤 파일만 Primary 경로를 쓰고 있는 것을 확인하고,
          BOSTON 경로로 바로잡는다
 소요   : 약 30분
 변경   : CONTROL_FILES 파라미터와 파일 위치를 바꾼다 (되돌리지 않는다)
================================================================================

--------------------------------------------------------------------------------
 [1] 문제 발견
--------------------------------------------------------------------------------

-- 실습 05 에서 데이터 파일과 로그 파일은 모두 OMF 규칙을 따랐다.
-- 컨트롤 파일도 그런지 확인한다.

SYS@boston> COL name FOR a72
SYS@boston> SELECT name FROM v$controlfile;

NAME
------------------------------------------------------------------------
/u03/app/oracle/oradata/Chicago/control01.ctl
/u03/app/oracle/fast_recovery_area/CHICAGO/control02.ctl

2 rows selected.

-- ★ **Chicago 와 CHICAGO 다.**
--   Standby 인데 Primary 이름의 디렉터리를 쓰고 있다.
--   o1_mf_ 로 시작하는 OMF 이름도 아니다.
--
-- ★ 실습 01 에서 본 그 빈 Chicago 디렉터리가 이제 비어 있지 않다.

[oracle@boston-srv ~]$ ls -l /u03/app/oracle/oradata/Chicago/ \
>   /u03/app/oracle/fast_recovery_area/CHICAGO/

/u03/app/oracle/fast_recovery_area/CHICAGO/:
total 18576
-rw-r-----. 1 oracle dba 19021824 Aug 27 10:11 control02.ctl

/u03/app/oracle/oradata/Chicago/:
total 18576
-rw-r-----. 1 oracle dba 19021824 Aug 27 10:11 control01.ctl

-- 파일은 실제로 boston 서버에 있다. 각각 19,021,824바이트다.
-- 위치만 이상하고 동작에는 지장이 없다.

--------------------------------------------------------------------------------
 [2] 왜 이렇게 되었는가
--------------------------------------------------------------------------------

SYS@boston> COL value FOR a60
SYS@boston> SELECT name, value FROM v$parameter WHERE name='control_files';

NAME            VALUE
--------------- ------------------------------------------------------------
control_files   /u03/app/oracle/oradata/Chicago/control01.ctl, /u03/app/
                oracle/fast_recovery_area/CHICAGO/control02.ctl

1 row selected.

-- ★ 원인은 **파라미터 상속**이다.
--
--   ① CONTROL_FILES 는 Primary spfile 에 값이 들어 있다
--   ② DUPLICATE 의 SPFILE 절이 Primary spfile 을 복사해 온다
--   ③ 스크립트에 `set control_files` 가 없다
--   ④ `parameter_value_convert` 도 없어 값 안의 Chicago 도 그대로다
--   ⑤ 결과적으로 Primary 의 경로가 Standby 에 그대로 복사됐다
--
-- ★ db_create_file_dest 가 있는데 왜 OMF 가 이기지 못하는가?
--   **CONTROL_FILES 에 값이 있으면 그것이 우선한다.**
--   OMF 가 컨트롤 파일 이름을 정하는 것은 CONTROL_FILES 가
--   비어 있을 때뿐이다. 상속으로 값이 들어와 버렸으니 개입할 여지가 없다.
--
-- ★ 5장에는 이 문제가 없었다.
--   5장 스크립트에는 다음 줄이 있었다.
--     set control_files = '/u03/.../Boston/controlfile/control_standby01.ctl'
--   OMF 편 가이드가 이 줄을 지우면서 대체 수단을 두지 않은 것이 결함이다.

--------------------------------------------------------------------------------
 [3] 그대로 두면 무엇이 문제인가
--------------------------------------------------------------------------------

  동작에는 지장이 없다. 그러나 세 가지 문제가 남는다.

  ① 오해를 부른다
     Standby 서버에서 Chicago 디렉터리를 발견한 운영자가
     "Primary 파일이 왜 여기 있지?" 하고 지울 수 있다.
     컨트롤 파일이 사라지면 Standby 는 마운트되지 않는다.

  ② 정리가 어긋난다
     이 Standby 를 폐기할 때 BOSTON 디렉터리만 지우면 컨트롤 파일이 남는다.
     반대로 Chicago 를 Primary 잔재로 오인해 지우면 살아 있는 Standby 가 깨진다.

  ③ 일관성이 깨진다
     OMF 를 쓰기로 했으면 모든 파일이 같은 규칙을 따르는 편이
     관리 비용이 낮다. 하나만 예외이면 그 예외를 계속 기억해야 한다.

--------------------------------------------------------------------------------
 [4] 교정 — 순서가 중요하다
--------------------------------------------------------------------------------

-- 컨트롤 파일은 데이터베이스가 열려 있는 동안 옮길 수 없다.
-- 파라미터를 먼저 바꾸고, 내린 뒤에 파일을 옮기고, 그 다음 기동한다.

[oracle@boston-srv ~]$ mkdir -p /u03/app/oracle/oradata/BOSTON/controlfile
[oracle@boston-srv ~]$ mkdir -p /u03/app/oracle/fast_recovery_area/BOSTON/controlfile

-- ★ 여기서는 mkdir 을 한다.
--   OMF 가 관리하지 않는 파일이므로 사람이 자리를 마련해 주어야 한다.
--   OMF 를 쓴다고 mkdir 이 완전히 사라지는 것은 아니라는 사례다.

SYS@boston> ALTER SYSTEM SET control_files=
  2    '/u03/app/oracle/oradata/BOSTON/controlfile/control01.ctl',
  3    '/u03/app/oracle/fast_recovery_area/BOSTON/controlfile/control02.ctl'
  4    SCOPE=SPFILE;

System altered.

-- ★ SCOPE=SPFILE 이어야 한다. CONTROL_FILES 는 정적 파라미터이므로
--   SCOPE=BOTH 나 MEMORY 로는 바꿀 수 없다.
--   지금은 아직 옛 경로로 돌고 있고, 다음 기동부터 새 값이 적용된다.

SYS@boston> ALTER DATABASE RECOVER MANAGED STANDBY DATABASE CANCEL;

Database altered.

SYS@boston> SHUTDOWN IMMEDIATE
Database closed.
Database dismounted.
ORACLE instance shut down.

[oracle@boston-srv ~]$ mv /u03/app/oracle/oradata/Chicago/control01.ctl \
>   /u03/app/oracle/oradata/BOSTON/controlfile/control01.ctl
[oracle@boston-srv ~]$ mv /u03/app/oracle/fast_recovery_area/CHICAGO/control02.ctl \
>   /u03/app/oracle/fast_recovery_area/BOSTON/controlfile/control02.ctl
[oracle@boston-srv ~]$ rmdir /u03/app/oracle/oradata/Chicago \
>   /u03/app/oracle/fast_recovery_area/CHICAGO

[oracle@boston-srv ~]$ ls -l /u03/app/oracle/oradata/BOSTON/controlfile/control01.ctl \
>   /u03/app/oracle/fast_recovery_area/BOSTON/controlfile/control02.ctl

-rw-r-----. 1 oracle dba 19021824 Aug 27 10:12 /u03/app/oracle/fast_recovery_area/BOSTON/controlfile/control02.ctl
-rw-r-----. 1 oracle dba 19021824 Aug 27 10:12 /u03/app/oracle/oradata/BOSTON/controlfile/control01.ctl

-- ★ cp 가 아니라 mv 를 쓴다.
--   복사본을 남기면 나중에 어느 것이 진짜인지 헷갈린다.
--   rmdir 로 빈 디렉터리까지 정리하면 Chicago 라는 이름 자체가 사라진다.

--------------------------------------------------------------------------------
 [5] 오류 재현 — 컨트롤 파일 하나가 자리에 없으면
--------------------------------------------------------------------------------

-- 교정 작업에서 가장 흔한 실수가 파라미터와 파일 위치를 어긋나게 두는 것이다.
-- 그 상태가 어떻게 보이는지 확인해 둔다.
-- 파일 하나를 잠시 다른 곳으로 옮겨 재현한다.

SYS@boston> ALTER DATABASE RECOVER MANAGED STANDBY DATABASE CANCEL;

Database altered.

SYS@boston> SHUTDOWN IMMEDIATE
Database closed.
Database dismounted.
ORACLE instance shut down.

[oracle@boston-srv ~]$ mv /u03/app/oracle/oradata/BOSTON/controlfile/control01.ctl \
>   /tmp/control01.ctl.bak
[oracle@boston-srv ~]$ ls -l /tmp/control01.ctl.bak
-rw-r-----. 1 oracle dba 19021824 Aug 27 10:27 /tmp/control01.ctl.bak

SYS@boston> STARTUP MOUNT

ORACLE instance started.

Total System Global Area 3221223192 bytes
Fixed Size                  9139992 bytes
Variable Size             654311424 bytes
Database Buffers         2550136832 bytes
Redo Buffers                7634944 bytes
ORA-00205: error in identifying control file, check alert log for more info

>>> 원인 파악
    ORA-00205 는 "컨트롤 파일을 식별할 수 없다"는 뜻이다.
    CONTROL_FILES 가 가리키는 두 경로 중 하나에 파일이 없다.

    ★ 메시지가 놓이는 자리에 주의한다.
      STARTUP 출력의 **맨 끝 한 줄**로 붙어 나온다.
      바로 위에 SGA 크기가 정상으로 출력되므로
      대충 보면 성공한 것처럼 보인다.

    ★ 실제 상태를 확인하면 분명해진다.

SYS@boston> SELECT instance_name, status FROM v$instance;

INSTANCE_NAME    STATUS
---------------- ------------
boston           STARTED

1 row selected.

      STATUS 가 STARTED 다. MOUNTED 가 아니다.
      **인스턴스는 떴고 마운트에서 멈춘 것이다.**
      SGA 는 만들어졌으므로 실습 02 의 ORA-01034 와는 다른 상황이다.

    ★ 두 파일 중 **하나만** 없어도 이렇게 된다.
      CONTROL_FILES 에 적힌 모든 파일이 있어야 마운트된다.
      다중화는 안전장치이지만 "하나가 살아 있으면 뜬다"는 뜻은 아니다.
      없는 파일은 목록에서 빼야 한다.

>>> 조치
    두 가지 길이 있다.
      ① 파일을 제자리로 되돌린다  ← 파일이 살아 있으면 이쪽
      ② CONTROL_FILES 에서 없는 파일을 빼고 기동한다 (pfile 경유)

    여기서는 파일이 있으므로 ①을 택한다.

SYS@boston> SHUTDOWN ABORT
ORACLE instance shut down.

[oracle@boston-srv ~]$ mv /tmp/control01.ctl.bak \
>   /u03/app/oracle/oradata/BOSTON/controlfile/control01.ctl
[oracle@boston-srv ~]$ ls -l /u03/app/oracle/oradata/BOSTON/controlfile/control01.ctl
-rw-r-----. 1 oracle dba 19021824 Aug 27 10:27 control01.ctl

>>> 재확인

SYS@boston> STARTUP MOUNT
ORACLE instance started.

Total System Global Area 3221223192 bytes
Fixed Size                  9139992 bytes
Variable Size             654311424 bytes
Database Buffers         2550136832 bytes
Redo Buffers                7634944 bytes
Database mounted.

    `Database mounted.` 가 나오면 성공이다.
    ★ 이 한 줄의 유무가 판정 기준이다. SGA 출력은 판정 근거가 아니다.

    이 재현으로 교정 순서의 근거도 분명해진다.
    파라미터를 먼저 바꾸고(SCOPE=SPFILE), 내린 뒤에 파일을 옮기고,
    그 다음 기동해야 두 값이 어긋나는 구간이 생기지 않는다.

--------------------------------------------------------------------------------
 [8] 근본 해법 — 스크립트를 고친다
--------------------------------------------------------------------------------

  매번 사후 교정을 하는 것보다 스크립트에 한 줄을 넣는 편이 낫다.
  OMF 방식 스크립트에 다음을 추가한다.

    set control_files =
      '/u03/app/oracle/oradata/BOSTON/controlfile/control01.ctl',
      '/u03/app/oracle/fast_recovery_area/BOSTON/controlfile/control02.ctl'

  이 경우 컨트롤 파일만 OMF 이름 규칙(o1_mf_...)을 따르지 않게 되지만,
  위치는 일관되게 유지된다. 컨트롤 파일은 개수가 적고 이름이 바뀔 일이
  없으므로 실무에서 받아들일 만한 절충이다.

  ★ 이 경우 디렉터리는 미리 만들어 두어야 한다.
    OMF 가 관리하지 않는 파일이기 때문이다.
    즉 OMF 방식이라도 mkdir 이 완전히 사라지지는 않는다.

--------------------------------------------------------------------------------
 [9] 정리
--------------------------------------------------------------------------------

  · CONTROL_FILES 는 Primary 값이 그대로 상속된다
  · 값이 있으면 OMF 가 개입하지 않는다. OMF 는 빈 경우에만 이름을 정한다
  · 그 결과 Standby 에 Chicago·CHICAGO 디렉터리가 생긴다
  · 그대로 두면 오해·정리 누락·일관성 붕괴 세 가지 문제가 남는다
  · 교정 순서: SCOPE=SPFILE 변경 → 종료 → 파일 이동 → 기동
  · 순서를 어기면 ORA-00205 로 마운트에 실패한다
  · 근본 해법은 스크립트에 set control_files 를 넣는 것이다
