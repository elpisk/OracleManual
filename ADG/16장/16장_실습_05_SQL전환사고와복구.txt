================================================================================
 제16장 실습 05 — SQL 전환 사고 재현과 복구
 대상   : chicago-srv, boston-srv
 목표   : Broker 환경에서 SQL 로 전환하면 무슨 일이 생기는지 확인하고 되살린다.
          Broker 의 보호가 어디까지인지 안다
 소요   : 약 50분
 변경   : 구성이 어긋난다. 반드시 복구까지 마친다
 주의   : 실습 환경에서만 한다. 시작 전에 꺼진 상태의 VM 스냅샷을 확보한다
================================================================================

--------------------------------------------------------------------------------
 [1] 왜 해 보는가
--------------------------------------------------------------------------------

-- ★ 13장에서 "Broker 가 관리하는 것을 SQL 로 바꾸지 말라" 고 했다.
--   파라미터를 바꾸는 것까지는 확인했다.
--   Broker 는 감지하지 못했지만 큰 문제도 없었다.
--
-- ★ 역할 전환을 SQL 로 하면 어떻게 되는지는 확인하지 않았다.
--   이 실습이 그것이다.
--
-- ★ 결과가 예상과 다르다.
--   "거부될 것" 이라고 생각하기 쉬운데 그렇지 않다.

DGMGRL> show configuration

Configuration - dg_chicago

  Members:
  chicago - Primary database
    boston  - Physical standby database

Configuration Status:
SUCCESS

--------------------------------------------------------------------------------
 [2] 오류 재현 — 거부되지 않는다
--------------------------------------------------------------------------------

SYS@chicago> ALTER DATABASE SWITCHOVER TO boston;

Database altered.

>>> 원인 파악

-- ★ 성공했다. Broker 가 활성화된 상태인데도 거부되지 않는다.
--
-- ★ 13장·14장과 비교한다.
--
--   보호 모드 변경 (전제 미충족)   ORA-16627 로 거부
--   FSFO 활성화 (플래시백 없음)    ORA-16827 경고만 하고 진행
--   SQL 역할 전환                  경고조차 없음
--
-- ★ Broker 의 보호는 생각보다 얇다.
--   명령마다 검사 강도가 다르며 이 명령은 아예 검사하지 않는다.
--
-- ★ 규율은 도구가 아니라 사람이 지킨다.

SYS@chicago> SELECT db_unique_name, database_role FROM v$database;

select db_unique_name, database_role from v$database
*
ERROR at line 1:
ORA-01034: ORACLE not available
Process ID: 0
Session ID: 0 Serial number: 0

-- ★ 곧바로 다음 조회가 실패한다. chicago 인스턴스가 내려갔다.
--   SQL 전환은 Broker 처럼 상대를 다시 기동해 주지 않는다.

SYS@boston> SELECT db_unique_name, database_role, open_mode FROM v$database;

DB_UNIQUE_ DATABASE_ROLE    OPEN_MODE
---------- ---------------- --------------------
boston     PRIMARY          MOUNTED

1 row selected.

-- ★ boston 은 Primary 가 됐지만 MOUNTED 에 머물러 있다.
--   실습 02 에서 본 New primary database ... is opening 단계가 없다.
--
-- ★ 정리하면 SQL 전환은 역할만 바꾸고 뒷정리를 하지 않는다.

 [3] 상태를 맞춰 본다
--------------------------------------------------------------------------------

SYS@boston> ALTER DATABASE OPEN;

Database altered.

SYS@chicago> STARTUP MOUNT;

ORACLE instance started.
Database mounted.

SYS@chicago> SELECT db_unique_name, database_role, open_mode FROM v$database;

DB_UNIQUE_ DATABASE_ROLE    OPEN_MODE
---------- ---------------- --------------------
chicago    PHYSICAL STANDBY MOUNTED

SYS@chicago> ALTER DATABASE OPEN READ ONLY;
SYS@chicago> ALTER DATABASE RECOVER MANAGED STANDBY DATABASE
  2            USING CURRENT LOGFILE DISCONNECT FROM SESSION;

Database altered.

-- ★ 손으로 6~9장의 절차를 다시 밟은 셈이다.
--   Broker 가 해 주던 일을 사람이 한다.

--------------------------------------------------------------------------------
 [5] 복제가 멈춰 있다
--------------------------------------------------------------------------------

SYS@boston> SELECT name, value FROM v$parameter WHERE name='log_archive_dest_2';

NAME               VALUE
------------------ ------
log_archive_dest_2

1 row selected.

SYS@boston> SELECT dest_id, status FROM v$archive_dest_status WHERE dest_id IN (1,2);

   DEST_ID STATUS
---------- ---------
         1 VALID
         2 INACTIVE

2 rows selected.

SYS@chicago> SELECT process, status, sequence# FROM v$managed_standby WHERE process='MRP0';

PROCESS   STATUS         SEQUENCE#
--------- ------------ ----------
MRP0      WAIT_FOR_LOG         91

1 row selected.

-- ★ 새 Primary 의 목적지가 비어 있다.
--   SQL 전환은 옛 Primary 의 설정을 지웠을 뿐
--   새 Primary 의 전송 설정을 만들지 않았다.
--   Broker 도 역할이 어긋난 상태이므로 손대지 못한다.
--
-- ★ 15장에서 배운 대로 MRP 는 WAIT_FOR_LOG 에서 기다린다.
--   재해 복구 능력이 없는 상태다.
--
-- ★ 그런데 두 데이터베이스는 각자 잘 동작하고 있다.
--   겉으로는 문제가 보이지 않는다는 것이 이 상황의 특징이다.

--------------------------------------------------------------------------------
 [6] 오류 재현 — SQL 로 되돌리려 해도
--------------------------------------------------------------------------------

SYS@boston> ALTER DATABASE SWITCHOVER TO chicago;

alter database switchover to chicago
*
ERROR at line 1:
ORA-16468: error connecting to switchover target

>>> 원인 파악

-- ★ ORA-16468. 대상에 접속할 수 없다.
--   이때 chicago 는 MOUNTED 상태였다.
--
-- ★ 실습 02 의 Broker 전환에서는 같은 상황을
--   정적 등록으로 해결했다.
--   SQL 전환은 그 경로를 쓰지 않는다.
--
-- ★ 손으로 시작한 문제는 손으로 끝내기 어렵다.

>>> 조치

-- ★ 구성이 알고 있는 역할과 실제가 어긋났으므로
--   둘 중 하나를 맞춰야 한다.
--   구성을 다시 만드는 쪽이 확실하다.
--
-- ★ 13장에서 확인한 성질을 쓴다.
--   REMOVE CONFIGURATION 은 데이터베이스를 건드리지 않는다.

-- 현재 Primary(boston)에서

DGMGRL> remove configuration;

Removed configuration

DGMGRL> create configuration 'dg_chicago' as primary database is 'boston'
> connect identifier is boston;

Configuration "dg_chicago" created with primary database "boston"

DGMGRL> add database 'chicago' as connect identifier is chicago;

Database "chicago" added

DGMGRL> enable configuration;

-- ★ 다시 만들 때는 실제 역할대로 적는다.
--   boston 이 Primary 이므로 그렇게 선언한다.
--
-- ★ ENABLE CONFIGURATION 이 파라미터를 다시 써 준다.
--   비어 있던 log_archive_dest_2 가 채워지고 전송이 재개된다.

>>> 재확인

DGMGRL> show configuration

--------------------------------------------------------------------------------
 [8] 이 사고에서 얻을 것
--------------------------------------------------------------------------------

-- ★ ① Broker 가 막아 줄 것이라고 기대하지 않는다.
--      이 명령은 검사조차 하지 않았다.
--
-- ★ ② SUCCESS 를 결과로 받아들이지 않는다.
--      역할이 어긋난 직후에도 Broker 는 SUCCESS 였다.
--
-- ★ ③ 실제 역할은 V$DATABASE 에서 확인한다.
--      Broker 화면이 아니라 뷰가 사실이다.
--
-- ★ ④ 복구 경로를 알아 두면 두렵지 않다.
--      REMOVE → CREATE → ADD → ENABLE 은 데이터를 건드리지 않는다.
--      다만 그동안 감시 공백이 생긴다.
--
-- ★ ⑤ 전환 명령은 반드시 DGMGRL 로 한다.
--      Broker 를 쓰기로 했다면 예외를 두지 않는다.

--------------------------------------------------------------------------------
 [9] 정리
--------------------------------------------------------------------------------

-- ★ 이 실습에서 확인한 것
--
--   ① ALTER DATABASE SWITCHOVER TO 는 Broker 환경에서도 성공한다
--   ② 옛 Primary 는 내려가고 새 Primary 는 MOUNTED 에 머문다
--   ③ 새 Primary 의 log_archive_dest_2 가 비어 전송이 없다
--   ④ Broker 는 잠시 SUCCESS 를 유지하다가 ORA-16816 을 낸다
--   ⑤ SQL 로 되돌리려 하면 ORA-16468
--   ⑥ 복구는 REMOVE → CREATE → ADD → ENABLE → SWITCHOVER
--   ⑦ 전환 직후의 ORA-16854 는 판정 시차다
--
-- ★ 다음 실습에서 Failover 를 준비한다.
