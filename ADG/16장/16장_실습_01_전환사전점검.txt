 [2] SWITCHOVER_STATUS — 양쪽이 다르다
--------------------------------------------------------------------------------

SYS@chicago> COL db_unique_name FOR a10
SYS@chicago> COL switchover_status FOR a22
SYS@chicago> SELECT db_unique_name, database_role, open_mode, switchover_status
  2            FROM v$database;

DB_UNIQUE_ DATABASE_ROLE    OPEN_MODE            SWITCHOVER_STATUS
---------- ---------------- -------------------- ----------------------
chicago    PRIMARY          READ WRITE           TO STANDBY

1 row selected.

SYS@boston> SELECT db_unique_name, database_role, open_mode, switchover_status
  2            FROM v$database;

DB_UNIQUE_ DATABASE_ROLE    OPEN_MODE            SWITCHOVER_STATUS
---------- ---------------- -------------------- ----------------------
boston     PHYSICAL STANDBY READ ONLY WITH APPLY NOT ALLOWED

1 row selected.

-- ★ 두 값이 다르다. 이것이 정상이다.
--
--   TO STANDBY        Primary  지금 Standby 로 내려갈 준비가 됐다
--   NOT ALLOWED       Standby  Standby 에서는 이 명령을 시작할 수 없다
--
-- ★ NOT ALLOWED 를 문제로 읽지 않는다.
--   전환 명령은 Primary 쪽에서 낸다.
--
-- ★ 다른 값들
--
--   SESSIONS ACTIVE   Primary  활성 세션이 있다
--   TO PRIMARY        Standby  (SQL 절차에서) 올라갈 준비가 됐다
--   RECOVERY NEEDED   Standby  적용이 덜 됐다
--
-- ★ 15장에서 반복한 주제가 여기서도 나온다.
--   뷰의 값이 무엇을 뜻하는지 알아야 판정할 수 있다.

--------------------------------------------------------------------------------
 [3] DB_NAME 이 아니라 DB_UNIQUE_NAME 이다
--------------------------------------------------------------------------------

SYS@chicago> COL name FOR a10
SYS@chicago> SELECT name, db_unique_name FROM v$database;

NAME       DB_UNIQUE_NAME
---------- --------------------
CHICAGO    chicago

SYS@boston> SELECT name, db_unique_name FROM v$database;

NAME       DB_UNIQUE_NAME
---------- --------------------
CHICAGO    boston

-- ★ NAME 이 양쪽 모두 CHICAGO 다.
--   6장에서 복제할 때 DB_NAME 을 같게 만들었기 때문이며
--   전환해도 바뀌지 않는다.
--
-- ★ 구별하는 것은 DB_UNIQUE_NAME 이다.
--   Broker 의 멤버 이름도 이 값이다.
--
-- ★ 그러므로 NAME 으로 어느 쪽인지 판단하면 안 된다.
--   감시 스크립트도 DB_UNIQUE_NAME 을 쓴다.

 [4] VALIDATE 로 최종 확인
--------------------------------------------------------------------------------

DGMGRL> validate database 'boston'

  Database Role:     Physical standby database
  Primary Database:  chicago

  Ready for Switchover:  Yes
  Ready for Failover:    Yes (Primary Running)

  Flashback Database Status:
    chicago:  Off
    boston :  Off

  Managed by Clusterware:
    chicago:  NO
    boston :  NO
    Validating static connect identifier for the primary database chicago...
    The static connect identifier allows for a connection to database "chicago".

  Log Files Cleared:
    chicago Standby Redo Log Files:  Cleared
    boston Online Redo Log Files:    Not Cleared
    boston Standby Redo Log Files:   Available

-- ★ Ready for Switchover: Yes 가 진행 신호다.
--
-- ★ 14장에서 이 값이 No 가 되는 두 상황을 만들어 봤다.
--   전송이 꺼졌을 때와 DelayMins 가 걸렸을 때다.
--
-- ★ static connect identifier 검사가 여기서 의미가 커진다.
--   실습 02 의 전환 과정에 상대 인스턴스를 기동하는 단계가 있고
--   그때 이 정적 등록을 쓴다.
--
-- ★ Flashback Database Status 가 양쪽 Off 다.
--   Switchover 에는 필요 없지만 Failover 뒤 Reinstate 에는 필요하다.
--   실습 06 에서 켠다.

 [5] 15장의 지표로 교차 확인
--------------------------------------------------------------------------------

SYS@boston> SELECT count(*) srl_active FROM v$standby_log WHERE status='ACTIVE';
SYS@boston> SELECT count(*) gap_cnt FROM v$archive_gap;

SRL_ACTIVE     GAP_CNT

PROCESS   STATUS         SEQUENCE#

SYS@chicago> SELECT max(sequence#) cur_seq FROM v$log WHERE status='CURRENT';

--   SRL_ACTIVE 1        리두가 흐르고 있다
--   GAP_CNT 0           갭이 없다
--   두 SEQUENCE# 일치   따라잡고 있다
--
-- ★ VALIDATE 가 Yes 라고 해도 이 확인을 함께 한다.
--   14장에서 배운 대로 층마다 답하는 질문이 다르다.

 [6] 오류 재현 — 없는 멤버를 검증하면
--------------------------------------------------------------------------------

DGMGRL> validate database 'seattle'

Object "seattle" was not found

>>> 원인 파악

-- ★ 14장에서 본 것과 같은 표현이다.
--   ORA- 번호가 아니라 문장으로 알려 준다.
--
-- ★ 전환 스크립트를 짤 때 이 성질이 함정이 된다.
--   오류 번호만 확인하는 스크립트는 이것을 성공으로 오인한다.
--
-- ★ 멤버 이름은 SHOW CONFIGURATION 으로 먼저 확인한다.

>>> 조치

DGMGRL> show configuration

-- 멤버 이름을 확인한다. 실측에서는 chicago 와 boston 이다.

>>> 재확인

DGMGRL> validate database 'boston'

  Ready for Switchover:  Yes

-- ★ 올바른 이름을 주면 동작한다.

-- ★ SQL 쪽에서도 같은 종류의 함정이 있다.
--   역할을 고정해 조회하면 지금 역할과 맞지 않을 때 결과가 빈다.

SYS@chicago> SELECT db_unique_name FROM v$database
  2            WHERE database_role='PHYSICAL STANDBY';

no rows selected

-- ★ 오류가 아니다. chicago 는 지금 Primary 이므로 조건에 맞지 않는다.
--
-- ★ 15장에서 확인한 성질과 같다.
--   오류가 나지 않는 잘못이 더 위험하다.
--   빈 결과를 실패로 처리하면 상시 오경보가 되고
--   성공으로 처리하면 대상을 못 찾은 채 넘어간다.
--
-- ★ 그래서 전환 스크립트는 역할을 고정하지 않고 조회로 판정한다.

SYS@chicago> SELECT db_unique_name FROM v$database WHERE database_role='PRIMARY';

DB_UNIQUE_NAME
--------------------
chicago

1 row selected.

-- ★ 이렇게 현재 Primary 를 찾고 그 반대를 대상으로 삼는다.

 [7] 점검표
--------------------------------------------------------------------------------

-- ★ 전환 30분 전에 확인할 것
--
--   ① SHOW CONFIGURATION 이 SUCCESS 인가
--   ② VALIDATE 의 Ready for Switchover 가 Yes 인가
--   ③ Primary 의 SWITCHOVER_STATUS 가 TO STANDBY 인가
--      SESSIONS ACTIVE 라면 세션을 정리한다
--   ④ SRL_ACTIVE 가 1 이고 두 SEQUENCE# 가 같은가
--   ⑤ VERBOSE 의 Future 구성이 Sufficient SRLs 인가
--   ⑥ 애플리케이션 접속 문자열이 양쪽을 가리키는가
--   ⑦ 되돌릴 시간을 확보했는가
--
-- ★ 실측 소요는 약 1분이지만
--   애플리케이션 확인까지 포함해 30분을 잡는다.
