================================================================================
 제14장 실습 07 — Fast-Start Failover 켜고 끄기
 대상   : chicago-srv (dgmgrl)
 목표   : 자동 전환의 설정을 읽고, 전제를 갖추지 않은 채 켜면 어떻게 되는지 본다.
          관측 전용 모드를 거쳐 정식으로 해제한다
 소요   : 약 40분
 변경   : FSFO 를 켰다가 끈다. 관측자는 띄우지 않으므로 실제 전환은 없다
 주의   : 관측자(observer)를 시작하지 않는다. 실제 자동 전환은 16장에서 다룬다
================================================================================

--------------------------------------------------------------------------------
 [1] 지금 상태를 읽는다
--------------------------------------------------------------------------------

DGMGRL> show fast_start failover

Fast-Start Failover:  Disabled

  Protection Mode:    MaxPerformance
  Lag Limit:          30 seconds

  Threshold:          30 seconds
  Active Target:      (none)
  Potential Targets:  (none)
  Observer:           (none)
  Shutdown Primary:   TRUE
  Auto-reinstate:     TRUE
  Observer Reconnect: (none)
  Observer Override:  FALSE

Configurable Failover Conditions
  Health Conditions:
    Corrupted Controlfile          YES
    Corrupted Dictionary           YES
    Inaccessible Logfile            NO
    Stuck Archiver                  NO
    Datafile Write Errors          YES

  Oracle Error Conditions:
    (none)

-- ★ 꺼져 있어도 설정은 다 들어 있다.
--
-- ★ 위쪽 항목의 뜻
--
--   Threshold 30초       Primary 가 몇 초 응답하지 않으면 전환하는가
--   Lag Limit 30초       손실을 얼마까지 허용하는가
--   Active Target        지금 지정된 전환 대상
--   Observer             감시자. 없다
--   Shutdown Primary     전환 후 옛 Primary 를 내릴 것인가
--   Auto-reinstate       옛 Primary 가 살아 돌아오면 자동 편입할 것인가
--
-- ★ 아래쪽이 전환을 촉발할 조건이다.
--   기본값이 NO 인 둘을 눈여겨본다.
--
--   Inaccessible Logfile   NO
--   Stuck Archiver         NO
--
--   회복 가능한 상황이기 때문이다.
--   아카이버가 멈춘 것은 FRA 가 찼기 때문일 수 있고
--   공간을 비우면 풀린다. 그런 상황에 역할을 바꾸는 것은 과하다.
--
-- ★ 자동 전환의 민감도를 사람이 정한다는 뜻이다.
--   켤수록 빨리 반응하지만 불필요한 전환도 늘어난다.

-- ★ 13장과 대비된다.

--   ORA-16627 로 거부했다. 여기서는 경고만 하고 진행한다.
--
-- ★ Broker 의 검사 강도가 명령마다 다르다는 뜻이다.
--   그러므로 enable 계열 명령은 실행한 뒤 반드시 SHOW 로 확인한다.
--   화면에 Warning 이 있으면 무시해도 되는지 판단한다.

SYS@chicago> SELECT flashback_on, log_mode FROM v$database;

FLASHBACK_ON       LOG_MODE
------------------ ------------
NO                 ARCHIVELOG

1 row selected.

SYS@boston> SELECT flashback_on, log_mode FROM v$database;

FLASHBACK_ON       LOG_MODE
------------------ ------------
NO                 ARCHIVELOG

1 row selected.

-- ★ 양쪽 다 NO 다. 11장에서 Snapshot Standby 를 되돌린 뒤
--   RESTORE POINT ONLY 였다가 지금은 완전히 꺼진 상태다.
--
-- ★ 플래시백이 왜 필요한가.
--   자동 전환 뒤 옛 Primary 를 되살리려면(Reinstate) 필요하다.
--   없으면 옛 Primary 는 버리고 새로 만들어야 한다.
--
-- ★ 그래서 경고이지 금지가 아니다.
--   자동 전환 자체는 동작한다. 뒷정리가 어려워질 뿐이다.

-- ★ 두 가지가 새로 나타났다.
--
--   ① (*) 표시 — 전환 대상이라는 뜻이다. 아래에 범례까지 붙는다.
--   ② ORA-16819 — 관측자가 시작되지 않았다
--
-- ★ ORA-16819 는 지금 상황에서는 우리가 의도한 것이다.
--   실습에서 관측자를 띄우지 않기로 했으므로 당연하다.
--
-- ★ 그러나 운영에서 이 경고를 보면 심각한 상태다.
--   FSFO 를 켜 놓고 관측자가 없으면 자동 전환이 일어나지 않는다.
--   "자동 전환이 켜져 있다" 고 안심하는 사이 아무 일도 하지 않는다.
--
-- ★ Enabled in Potential Data Loss Mode 라는 표현도 읽어 둔다.
--   보호 모드가 MaxPerformance(비동기)이므로
--   전환 시 데이터 손실 가능성이 있다는 뜻이다.

DGMGRL> show database 'boston' 'FastStartFailoverTarget'

  FastStartFailoverTarget = 'boston'
  FastStartFailoverTarget = 'chicago'

--------------------------------------------------------------------------------
 [4] 관측자는 무엇인가
--------------------------------------------------------------------------------

[oracle@chicago-srv ~]$ dgmgrl -silent sys/oracle@chicago "help start"

Starts the fast-start failover observer

Syntax:

  START OBSERVER [FILE=<observer file>];

  START OBSERVER [<observer name>]
  [FILE IS <observer file>]
  [LOGFILE IS <observer log file>]
  [TRACE_LEVEL IS { USER | SUPPORT }];

  START OBSERVER [<observer name>]
  IN BACKGROUND
  [FILE IS <observer file>]
  [LOGFILE IS <observer log file>]
  CONNECT IDENTIFIER IS <connect identifier>
  [TRACE_LEVEL IS { USER | SUPPORT }];

-- ★ 이 실습에서는 실행하지 않는다.
--   START OBSERVER 는 전경에서 돌면 세션을 붙잡고,
--   IN BACKGROUND 로 띄우면 조건이 맞을 때 실제로 전환을 일으킨다.
--
-- ★ 구문에서 읽을 것이 둘 있다.
--
--   ① FILE — 관측자는 상태를 파일에 남긴다.
--      재기동해도 이어서 감시할 수 있게 하기 위해서다.
--
--   ② CONNECT IDENTIFIER — 접속 식별자를 준다.
--      즉 관측자는 tnsnames 로 양쪽에 붙는 별개의 프로세스다.
--      데이터베이스의 백그라운드 프로세스가 아니다.
--
-- ★ 그래서 제3의 호스트에 둘 수 있고, 두어야 한다.
--   Primary 나 Standby 위에 두면 그 호스트가 죽었을 때
--   판단할 주체가 함께 사라진다.
--
-- ★ 왜 별도의 주체가 필요한가.
--   Standby 가 스스로 판단하면 네트워크만 끊긴 상황에서
--   "Primary 가 죽었다" 고 오판해 승격할 수 있다.
--   그러면 Primary 가 둘이 된다(split brain).

--------------------------------------------------------------------------------
 [8] 정리
--------------------------------------------------------------------------------

-- ★ 이 실습에서 확인한 것
--
--   ① FSFO 는 꺼져 있어도 설정을 다 들고 있다
--   ② 전환 조건 다섯 중 둘은 기본이 NO — 회복 가능한 상황이므로
--   ③ 플래시백이 없어도 경고(ORA-16827)만 하고 켜진다
--   ④ 13장의 ORA-16627 과 달리 검사 강도가 약하다
--   ⑤ 대상을 지정하면 (*) 표시가 붙는다
--   ⑥ 관측자가 없으면 ORA-16819 — 켜 놓고 아무 일도 하지 않는 상태
--   ⑦ 관측자는 별개의 프로세스이며 제3의 호스트에 둔다
--   ⑧ 대상 속성만 지워서는 꺼지지 않는다. Active Target 이 남는다
--   ⑨ DISABLE 이 먼저, 대상 속성 삭제가 나중이다
--   ⑩ OBSERVE ONLY 로 먼저 관찰한 뒤 진짜로 켜는 것이 안전하다
--
-- ★ 14장의 실습이 끝났다.
--   15장에서 V$ 뷰만으로 문제를 진단하는 방법을 다룬다.
