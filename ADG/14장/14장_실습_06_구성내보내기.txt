-- ★ 쓸 수 없는 위치여서 나는 오류가 아니다.
--   /tmp 는 누구나 쓸 수 있는 디렉터리인데도 같은 오류다.
--   경로를 준다는 행위 자체가 거부된다.

-- ★ 13장에서 본 개념이 그대로 XML 이 됐다.
--
--   IntendedState        13장의 Intended State
--   DGConnectIdentifier  13장의 접속 식별자 속성
--   Status/Severity      SHOW 가 보여 주는 그 상태
--
-- ★ Default="True" 표시가 붙은 항목은 기본값이라는 뜻이다.
--   우리가 바꾼 것과 손대지 않은 것을 구별할 수 있다.

[oracle@chicago-srv ~]$ grep -iE 'Threshold|DelayMins|LogShipping|LogXptMode' \
>   /u01/.../trace/ch14_export.xml

    <LogXptMode Default="True">ASYNC</LogXptMode>
    <LogXptMode>ASYNC</LogXptMode>
    <ApplyLagThreshold>30</ApplyLagThreshold>
    <LogShipping>ON</LogShipping>
    <DelayMins>0</DelayMins>

-- ★ 실습 04 에서 손댄 것이 그대로 보인다.
--
--   ApplyLagThreshold 에 Default 표시가 없다.
--   기본값과 같은 30 인데도 그렇다.
--   한 번 명시적으로 설정하면 값이 같아도 "설정한 것" 으로 남는다.
--
--   LogXptMode 는 두 줄이다. chicago 와 boston 것이 각각 있다.
--   앞의 것에만 Default 가 붙었다.
--
-- ★ 이 차이를 읽는 것이 이 파일의 쓸모다.
--   "무엇을 손댔는가" 를 알 수 있다.

[oracle@chicago-srv ~]$ wc -l -c /u01/.../trace/ch14_export.xml

 104 4433 .../trace/ch14_export.xml

-- ★ 104줄 4,433바이트. 사람이 읽을 수 있는 크기다.
--   13장에서 본 dr1chicago.dat 은 이진 파일이라 열어도 소용이 없었다.

--------------------------------------------------------------------------------
 [5] 구성 파일이 커졌다
--------------------------------------------------------------------------------

[oracle@chicago-srv ~]$ ls -l $ORACLE_HOME/dbs/dr*chicago.dat

-rw-r-----. 1 oracle dba 12288 Aug 28 08:54 .../dbs/dr1chicago.dat
-rw-r-----. 1 oracle dba 12288 Aug 28 08:53 .../dbs/dr2chicago.dat

-- ★ 13장에서는 8,192바이트였다. 12,288 로 늘었다.
--
-- ★ 그동안 한 일이 그것이다.
--   LogShipping 을 껐다 켜고, DelayMins 를 주었다 지우고,
--   임계값을 바꾸고, FSFO 대상을 지정했다 해제했다.
--
-- ★ 이력이 누적된다는 뜻이다.
--   파일이 커졌다는 것은 기본값에서 벗어난 설정이 늘었다는 신호다.
--
-- ★ 그래서 정기적으로 EXPORT 해 두고 XML 을 비교하는 습관이 쓸모 있다.
--   diff 로 두 시점의 파일을 비교하면 무엇이 언제 바뀌었는지 나온다.
--   이진 파일로는 못 하는 일이다.

--------------------------------------------------------------------------------

DGMGRL> import configuration from 'ch14_export.xml';

ORA-16504: The Oracle Data Guard broker configuration already exists.

>>> 원인 파악

-- ★ 덮어쓰기가 아니다. 구성이 이미 있으면 아예 받지 않는다.
--
-- ★ 안전한 설계다. 실수로 오래된 XML 을 가져와
--   현재 구성이 덮이는 일을 막는다.
--
-- ★ 13장에서 본 ORA-16532(구성이 없다) 와 짝이 되는 번호다.
--
--   ORA-16504  있는데 또 만들려 한다
--   ORA-16532  없는데 쓰려 한다

>>> 조치

-- ★ 복구 절차는 두 단계가 된다.
--
--   DGMGRL> remove configuration;
--   DGMGRL> import configuration from 'ch14_export.xml';
--
-- ★ 13장에서 REMOVE CONFIGURATION 이 데이터베이스를 건드리지 않는다는 것을
--   확인해 두었으므로 이 순서 자체는 위험하지 않다.
--
-- ★ 다만 지운 순간부터 가져오기가 끝날 때까지
--   Broker 의 감시가 없는 구간이 생긴다.
--   그동안 전송과 적용은 파라미터대로 계속되지만
--   장애가 나도 알려 줄 주체가 없다.
--
-- ★ 이번 실습에서는 실제로 지우지 않는다.
--   15·16장이 이 구성을 그대로 쓴다.

 [8] 정리
--------------------------------------------------------------------------------

-- ★ 이 실습에서 확인한 것
--
--   ① EXPORT 는 어디에 만들었는지 말해 주지 않는다
--   ② 결과물은 ADR 의 trace 디렉터리에 생긴다 (권한 644)
--   ③ 경로를 주면 ORA-16540 — 인자는 파일 이름이다
--   ④ 뒤따르는 ORA-06512 가 SYS.DBMS_DRS 호출임을 드러낸다
--   ⑤ XML 은 104줄 4,433바이트. 사람이 읽는다
--   ⑥ Default="True" 로 손댄 항목을 구별할 수 있다
--   ⑦ 구성 파일이 8,192 → 12,288 로 커졌다. 이력이 쌓인다
--   ⑧ 구성이 있으면 IMPORT 는 ORA-16504 로 거부된다
--   ⑨ 복구는 REMOVE → IMPORT 두 단계이며 감시 공백이 생긴다
--
-- ★ 다음 실습에서 Fast-Start Failover 를 다룬다.
