================================================================================
 제14장 실습 02 — SHOW 와 VALIDATE 의 차이
 대상   : chicago-srv (dgmgrl), boston-srv
 목표   : 전송을 끄고 두 명령이 서로 다른 답을 내는 것을 확인한다.
          Broker 가 무엇을 정상으로 보는지 이해한다
 소요   : 약 30분
 변경   : LogShipping 을 껐다가 되돌린다
================================================================================

--------------------------------------------------------------------------------
 [1] 전송을 끈다
--------------------------------------------------------------------------------

DGMGRL> edit database 'boston' set property 'LogShipping'='OFF';

Property "LogShipping" updated

-- ★ LogShipping 은 13장에서 본 속성이다.
--   LOG_ARCHIVE_DEST_STATE_n 에 대응한다.

SYS@chicago> INSERT INTO system.bk_t VALUES(90,'ship-off');
SYS@chicago> COMMIT;
SYS@chicago> ALTER SYSTEM ARCHIVE LOG CURRENT;
SYS@chicago> ALTER SYSTEM ARCHIVE LOG CURRENT;

System altered.

-- ★ 변경을 만들고 로그를 두 번 전환했다.
--   전송이 꺼져 있으므로 Standby 로 가지 않는다.

--------------------------------------------------------------------------------
 [2] SHOW 는 뭐라고 하는가
--------------------------------------------------------------------------------

DGMGRL> show configuration

  Apply Lag:          0 seconds (computed 47 seconds ago)
  Average Apply Rate: 2.00 KByte/s
  Real Time Query:    ON
  Instance(s):

-- ★ 둘 다 SUCCESS 다. 지연도 0 이다.
--   전송을 완전히 끊어 놓았는데 아무 신호가 없다.
--
-- ★ 이유가 둘이다.
--
--   ① 13장에서 배운 Intended State 개념이 작동한다.
--      LogShipping=OFF 는 우리가 Broker 에게 지시한 것이므로
--      의도한 상태이며, Broker 는 의도와 실제가 일치하면 정상으로 본다.
--
--   ② 지연이 0 인 것도 논리적으로는 맞다.
--      전송이 꺼져 있으므로 "언제까지 받았는가" 의 기준이 갱신되지 않는다.
--      보내지 않으니 늦지도 않는다.
--
-- ★ 이것이 이 장의 핵심 장면이다.
--   SHOW 가 SUCCESS 라고 해서 안전한 것이 아니다.

  Transport-Related Property Settings:
    Property                        chicago Value            boston Value
    LogShipping                     ON                       OFF

-- ★ Ready for Switchover: No 다. 그리고 이유까지 알려 준다.
--
--   실습 01 에서는 이 표에 모든 속성이 나왔는데
--   지금은 LogShipping 한 줄만 나온다.
--   VALIDATE 는 값이 다른 것만 골라 보여 준다.
--
-- ★ 세 명령을 표로 정리한다.
--
--   명령                 묻는 것                    이 상황의 답
--   -------------------  -------------------------  ------------
--   SHOW CONFIGURATION   지금 의도대로 동작하는가    SUCCESS
--   SHOW DATABASE        이 멤버가 의도대로인가      SUCCESS
--   VALIDATE DATABASE    지금 역할을 바꿀 수 있는가  No
--
-- ★ Ready for Failover 는 Yes 인 것도 눈여겨본다.
--   Failover 는 데이터 손실을 감수하는 비계획 전환이므로
--   전송이 꺼져 있어도 "할 수는 있다".
--   Switchover 는 무손실이어야 하므로 안 된다.

--------------------------------------------------------------------------------
 [4] SQL 로 확인한다
--------------------------------------------------------------------------------

SYS@chicago> COL destination FOR a12
SYS@chicago> COL error FOR a34
SYS@chicago> SELECT dest_id, destination, status, error
  2            FROM v$archive_dest_status WHERE dest_id=2;

   DEST_ID DESTINATION  STATUS    ERROR
---------- ------------ --------- ----------------------------------
         2 boston       DEFERRED

1 row selected.

SYS@chicago> COL value FOR a76
SYS@chicago> COL name FOR a24
SYS@chicago> SELECT name, value FROM v$parameter
  2            WHERE name='log_archive_dest_state_2';

NAME                     VALUE
------------------------ ----------------------------------------------------
log_archive_dest_state_2 RESET

1 row selected.

-- ★ LOG_ARCHIVE_DEST_STATE_2 가 RESET 이다. DEFER 가 아니다.
--
--   7장에서 목적지를 껐다 켤 때는 DEFER / ENABLE 을 썼다.
--   Broker 는 RESET 을 쓴다.
--   목적지 상태는 DEFERRED 로 표시된다.
--
-- ★ 값이 다르다는 것 자체가 정보다.
--   RESET 이 보이면 "Broker 가 껐다" 는 뜻이고
--   DEFER 가 보이면 "사람이 껐다" 는 뜻이다.

SYS@boston> COL name FOR a16
SYS@boston> COL value FOR a20
SYS@boston> SELECT name, value FROM v$dataguard_stats WHERE name LIKE '%lag';

NAME             VALUE
---------------- --------------------
transport lag    +00 00:00:00
apply lag        +00 00:00:00

2 rows selected.

-- ★ SQL 로 봐도 지연은 0 이다.
--   Broker 가 잘못 계산한 것이 아니라 원래 그런 값이다.

--------------------------------------------------------------------------------
 [5] 오류 재현 — 전송이 끊긴 채로 두면
--------------------------------------------------------------------------------

-- ★ 이 상태를 오래 두면 어떻게 되는지는 7장에서 배웠다.
--   Primary 의 아카이브가 쌓이고, 결국 갭이 된다.
--   여기서는 Standby 쪽에서 무엇이 보이는지 확인한다.

SYS@boston> COL message FOR a80
SYS@boston> SELECT severity, error_code, to_char(timestamp,'HH24:MI:SS') ts, message
  2            FROM v$dataguard_status ORDER BY timestamp DESC FETCH FIRST 3 ROWS ONLY;

SEVERITY      ERROR_CODE TS       MESSAGE
------------- ---------- -------- --------------------------------------------
Warning                0 18:56:37 Media Recovery Waiting for T-1.S-69 (in transit)

>>> 원인 파악

-- ★ Standby 는 "다음 리두를 기다린다" 고만 말한다.
--   전송이 꺼졌다는 사실을 모른다.
--
-- ★ 받는 쪽에서는 "안 온다" 와 "보내지 않는다" 를 구별할 수 없다.
--   그래서 Standby 쪽만 보면 진단이 안 된다.
--   Primary 쪽 목적지 상태를 함께 봐야 한다.
--
-- ★ 이것이 10장에서 ORA-16057 을 진단할 때 배운 것과 같다.
--   오류가 보이는 쪽과 원인이 있는 쪽이 다를 수 있다.

>>> 조치

DGMGRL> edit database 'boston' set property 'LogShipping'='ON';

Property "LogShipping" updated

--------------------------------------------------------------------------------
 [6] 정리
--------------------------------------------------------------------------------

-- ★ 이 실습에서 확인한 것
--
--   ① LogShipping=OFF 인데 SHOW 는 SUCCESS
--   ② 두 지연도 0 — 보내지 않으니 늦지도 않는다
--   ③ VALIDATE 는 Ready for Switchover: No
--   ④ VALIDATE 는 값이 다른 속성만 골라 보여 준다
--   ⑤ Ready for Failover 는 Yes — 손실을 감수하는 전환이므로
--   ⑥ Broker 는 DEFER 가 아니라 RESET 을 쓴다
--   ⑦ Standby 쪽만 보면 "안 온다" 와 "안 보낸다" 를 구별할 수 없다
--
-- ★ 실무 지침
--   SHOW 는 일상 점검, VALIDATE 는 행동 직전 점검이다.
--   주간 점검 항목에 VALIDATE 를 넣어 두면
--   평소 SUCCESS 만 보다가 정작 장애 때 전환이 안 되는 상황을 막는다.
--
-- ★ 다음 실습에서 모니터링 전용 속성을 다룬다.
