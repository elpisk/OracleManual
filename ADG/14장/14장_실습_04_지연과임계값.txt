================================================================================
 제14장 실습 04 — 적용 지연과 임계값
 대상   : chicago-srv (dgmgrl), boston-srv
 목표   : DelayMins 로 지연을 만들고 경고가 뜨는 것을 관찰한다.
          임계값을 조절해 경보의 기준이 사람의 설정이라는 것을 확인한다
 소요   : 약 35분
 변경   : DelayMins·ApplyLagThreshold 를 바꿨다가 되돌린다
================================================================================

--------------------------------------------------------------------------------
 [1] 지연을 준다
--------------------------------------------------------------------------------

DGMGRL> edit database 'boston' set property 'DelayMins'='2';

Property "DelayMins" updated

-- ★ 2분이다. 실무에서는 30분에서 몇 시간을 쓴다.
--   실습에서는 관찰할 수 있는 최소 단위로 잡았다.
--
-- ★ 무엇을 사는가.
--   Primary 에서 실수로 테이블을 지워도 2분 안에 알아채면
--   Standby 에는 아직 남아 있다.
--
-- ★ 무엇을 파는가. 그것을 아래에서 확인한다.

SYS@chicago> INSERT INTO system.bk_t VALUES(91,'delayed');
SYS@chicago> COMMIT;
SYS@chicago> ALTER SYSTEM ARCHIVE LOG CURRENT;

System altered.

--------------------------------------------------------------------------------
 [2] Standby 에는 아직 없다
--------------------------------------------------------------------------------

SYS@boston> SELECT count(*) cnt FROM system.bk_t WHERE id=91;

       CNT
----------
         0

1 row selected.

SYS@boston> COL name FOR a16
SYS@boston> COL value FOR a20
SYS@boston> SELECT name, value FROM v$dataguard_stats WHERE name LIKE '%lag';

NAME             VALUE
---------------- --------------------
transport lag    +00 00:00:00
apply lag        +00 00:01:33

2 rows selected.

-- ★ 두 지연이 갈라졌다. 이 장면이 이 실습의 핵심이다.
--
--   transport lag  0        리두는 이미 도착했다
--   apply lag      1분 33초  적용을 일부러 미루고 있다
--
-- ★ 7장에서 두 지연을 나눠 본 이유가 여기서 분명해진다.
--   지금 보이는 apply lag 은 장애가 아니라 설정이다.
--   transport lag 이 0 이라는 사실이 그것을 증명한다.
--
-- ★ 반대로 transport lag 이 커지면 그때는 진짜 문제다.
--   같은 "지연" 이라는 말을 쓰지만 뜻이 다르다.

 [3] Broker 는 경고를 낸다
--------------------------------------------------------------------------------

>>> 원인 파악

-- ★ ORA-16853 이다. apply lag 이 임계값을 넘었다는 뜻이다.
--
-- ★ 그런데 이것은 우리가 설정한 결과다.
--   DelayMins=2 로 지연을 걸어 놓고 임계값은 기본 30초로 두었으니
--   경고가 뜨는 것이 당연하다.
--
-- ★ 실습 02 와 대비된다.
--
--   LogShipping=OFF   의도한 상태  → SUCCESS  (경보 없음)
--   DelayMins=2       의도한 상태  → WARNING  (경보 있음)
--
--   둘 다 사람이 설정한 것인데 하나는 알리고 하나는 알리지 않는다.
--
-- ★ 차이는 임계값이 있느냐다.
--   지연에는 임계값이라는 숫자 기준이 있어 Broker 가 비교할 수 있다.
--   "전송을 껐다" 는 비교할 숫자가 없다.
--
-- ★ 그러므로 규칙은 이렇게 정리된다.
--   Broker 는 임계값이 있는 항목만 경보한다.
--   설정 자체가 위험한 것은 알려 주지 않는다.

--------------------------------------------------------------------------------
 [4] VALIDATE 는 이유까지 말한다
--------------------------------------------------------------------------------

DGMGRL> validate database 'boston'

  Database Role:     Physical standby database
  Primary Database:  chicago

  Ready for Switchover:  No
  Ready for Failover:    Yes (Primary Running)

  Standby Apply-Related Information:
    Apply State:      Running
    Apply Lag:        1 minute 32 seconds (computed 0 seconds ago)
    Apply Delay:      2 minutes
    Error: Switchover to this standby is not possible because
    an apply delay has been set

  Apply-Related Property Settings:
    Property                        chicago Value            boston Value
    DelayMins                       0                        2

  Transport-Related Property Settings:
    Property                        chicago Value            boston Value
    DelayMins                       0                        2

-- ★ 문장으로 이유를 준다.
--   "an apply delay has been set" — 적용 지연이 걸려 있어서 안 된다.
--
-- ★ 이것이 DelayMins 가 파는 것이다.
--
--   ① 계획된 전환(Switchover)이 막힌다
--   ② 재해가 나면 밀린 만큼을 잃는다
--   ③ 밀린 리두를 다 적용할 때까지 Failover 도 늦어진다
--
-- ★ DelayMins 는 실수 대비를 사고 재해 복구 능력을 파는 거래다.
--   공짜 안전장치가 아니다.
--
-- ★ DelayMins 가 Apply 와 Transport 양쪽 표에 모두 나오는 것도 본다.
--   같은 속성이 두 관점에서 의미를 가진다.

--------------------------------------------------------------------------------
 [5] 임계값을 낮추면
--------------------------------------------------------------------------------

DGMGRL> show database 'boston' 'ApplyLagThreshold'
DGMGRL> show database 'boston' 'TransportLagThreshold'
DGMGRL> show database 'boston' 'TransportDisconnectedThreshold'

  ApplyLagThreshold = '30'
  TransportLagThreshold = '30'
  TransportDisconnectedThreshold = '30'

-- ★ 셋 다 기본 30초다. 대응하는 오류 번호는 다음과 같다.
--
--   ApplyLagThreshold               ORA-16853  적용이 늦다
--   TransportLagThreshold           ORA-16855  전송이 늦다
--   TransportDisconnectedThreshold  ORA-16857  연결이 끊겼다
--
-- ★ 0 을 주면 그 항목의 경보를 끈다.

DGMGRL> edit database 'boston' set property 'ApplyLagThreshold'='10';

Property "ApplyLagThreshold" updated

DGMGRL> show configuration

Configuration - dg_chicago

  Protection Mode: MaxPerformance
  Members:
  chicago - Primary database
    boston  - Physical standby database
      Warning: ORA-16853: apply lag has exceeded specified threshold

Fast-Start Failover:  Disabled

Configuration Status:
WARNING   (status updated 55 seconds ago)

-- ★ 구성 전체가 WARNING 으로 내려앉았다.
--   멤버 하나의 경고가 구성 상태를 끌어내린다.
--
-- ★ 이것을 반대로 이용할 수 있다.
--   임계값을 환경에 맞게 정하면 SHOW CONFIGURATION 한 줄로
--   "봐야 할 일이 있는가" 를 판정할 수 있다.
--
-- ★ 다만 임계값을 너무 짧게 잡으면 늘 WARNING 이 뜬다.
--   그러면 아무도 보지 않게 된다. 경보의 가치가 사라진다.

--------------------------------------------------------------------------------
 [6] 원복
--------------------------------------------------------------------------------

>>> 조치

DGMGRL> edit database 'boston' set property 'DelayMins'='0';
DGMGRL> edit database 'boston' set property 'ApplyLagThreshold'='30';

Property "DelayMins" updated
Property "ApplyLagThreshold" updated

-- ★ 둘을 함께 되돌린다.
--
-- ★ 실무에서 지연을 도입한다면 임계값도 함께 올려야 한다.
--   DelayMins=30 이라면 ApplyLagThreshold 는 30분보다 넉넉하게 잡는다.
--   그러지 않으면 상시 경고 상태가 되어
--   진짜 문제가 생겼을 때 구별할 수 없다.

>>> 재확인

DGMGRL> show configuration

Configuration - dg_chicago

  Protection Mode: MaxPerformance
  Members:
  chicago - Primary database
    boston  - Physical standby database

Fast-Start Failover:  Disabled

Configuration Status:
SUCCESS   (status updated 28 seconds ago)

SYS@boston> COL tag FOR a16
SYS@boston> SELECT id, tag FROM system.bk_t ORDER BY id;

        ID TAG
---------- ----------------
         1 after-restart
        90 ship-off
        91 delayed

3 rows selected.

-- ★ 밀려 있던 행이 적용됐다. 데이터는 잃지 않았다.
--   90 은 실습 02 에서, 91 은 이번 실습에서 넣은 것이다.
--
-- ★ 지연을 해제하면 밀린 리두가 한꺼번에 적용된다.
--   양이 많으면 이때 I/O 가 몰린다.
--   운영에서 지연을 해제할 때는 그 점을 예상해 둔다.

--------------------------------------------------------------------------------
 [7] 정리
--------------------------------------------------------------------------------

-- ★ 이 실습에서 확인한 것
--
--   ① DelayMins 를 주면 apply lag 만 커지고 transport lag 은 0
--   ② 두 지연이 갈라지는 것이 설정 때문임을 보여 준다
--   ③ 지연이 임계값을 넘으면 ORA-16853
--   ④ VALIDATE 는 "an apply delay has been set" 이라고 이유를 준다
--   ⑤ 지연이 걸리면 Switchover 가 막힌다
--   ⑥ 임계값 셋은 모두 기본 30초 (16853·16855·16857)
--   ⑦ 멤버 하나의 경고가 구성 전체를 WARNING 으로 만든다
--   ⑧ 지연을 두면 임계값도 함께 올린다
--
-- ★ 다음 실습에서 Broker 의 요약을 SQL 로 교차 확인한다.
