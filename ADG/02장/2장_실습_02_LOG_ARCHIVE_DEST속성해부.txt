 제2장 실습 02 — LOG_ARCHIVE_DEST_2 속성 해부

--------------------------------------------------------------------------------
 [1] 출발점 — 파라미터 문자열과 뷰를 나란히 본다
--------------------------------------------------------------------------------

SYS@chicago> SET LINES 200

service=boston async valid_for=(online_logfiles,primary_role) db_unique_name=boston

SYS@chicago> SELECT dest_id, dest_name, destination, transmit_mode, affirm,
  2                 valid_now, valid_type, valid_role

   DEST_ID DEST_NAME            DESTINATION  TRANSMIT_MOD AFF VALID_NOW        VALID_TYPE      VALID_ROLE
---------- -------------------- ------------ ------------ --- ---------------- --------------- ------------
         1 LOG_ARCHIVE_DEST_1   USE_DB_RECOV SYNCHRONOUS  NO  YES              ALL_LOGFILES    ALL_ROLES
                                ERY_FILE_DES
                                T

         2 LOG_ARCHIVE_DEST_2   boston       ASYNCHRONOUS NO  YES              ONLINE_LOGFILE  PRIMARY_ROLE

2 rows selected.

-- 파라미터 문자열의 각 속성이 뷰의 어느 열로 나타나는지 대응시킨다.
--
--   service=boston                    →  DESTINATION = boston
--   async                             →  TRANSMIT_MODE = ASYNCHRONOUS, AFFIRM = NO
--   valid_for=(online_logfiles, ...)  →  VALID_TYPE = ONLINE_LOGFILE
--   valid_for=(..., primary_role)     →  VALID_ROLE = PRIMARY_ROLE
--   (역할과 로그 유형이 지금 맞는가)  →  VALID_NOW = YES
--
-- dest_1 의 TRANSMIT_MODE 가 SYNCHRONOUS 인 것에 놀라지 말자.
-- 로컬 디스크 기록이므로 애초에 동기다. 원격 전송 방식과 무관한 값이다.

--------------------------------------------------------------------------------
 [2] SYNC AFFIRM 으로 바꾼다
--------------------------------------------------------------------------------

SYS@chicago> ALTER SYSTEM SET log_archive_dest_2 =
  2    'service=boston SYNC AFFIRM
  3     valid_for=(online_logfiles,primary_role) db_unique_name=boston' SCOPE=BOTH;

System altered.

SYS@chicago> SELECT dest_id, destination, transmit_mode, affirm
  2            FROM v$archive_dest WHERE dest_id = 2;

   DEST_ID DESTINATION  TRANSMIT_MOD AFF
---------- ------------ ------------ ---
         2 boston       PARALLELSYNC YES

1 row selected.

-- TRANSMIT_MODE : ASYNCHRONOUS  →  PARALLELSYNC
-- AFFIRM        : NO            →  YES
--
-- PARALLELSYNC 는 여러 동기 목적지가 있을 때 병렬 전송한다는 뜻이며,
-- 동기 전송이 켜졌음을 나타낸다.
-- AFFIRM=YES 는 "Standby 가 SRL 에 디스크 기록을 마친 뒤 확인을 보내라" 는 지시다.

--   LGWR → NSS2 → (네트워크) → boston 의 RFS → SRL 기록 → 확인 → LGWR 커밋 완료
--
-- 즉 커밋 응답시간에 네트워크 왕복이 그대로 더해진다.

--------------------------------------------------------------------------------
 [5] 오류 재현 ① — 속성 이름을 잘못 쓴다
--------------------------------------------------------------------------------

-- ASYNC 를 ASYNCH 로 잘못 쓴 경우

SYS@chicago> ALTER SYSTEM SET log_archive_dest_2 =
  2    'service=boston ASYNCH NOAFFIRM
  3     valid_for=(online_logfiles,primary_role) db_unique_name=boston' SCOPE=BOTH;
ALTER SYSTEM SET log_archive_dest_2 = 'service=boston ASYNCH NOAFFIRM
valid_for=(online_logfiles,primary_role) db_unique_name=boston' SCOPE=BOTH
*
ERROR at line 1:
ORA-02097: parameter cannot be modified because specified value is invalid
ORA-16024: parameter LOG_ARCHIVE_DEST_2 cannot be parsed

-- db_unique_name 을 구성에 없는 이름으로 준 경우

SYS@chicago> ALTER SYSTEM SET log_archive_dest_2 =
  2    'service=boston ASYNC NOAFFIRM
  3     valid_for=(online_logfiles,primary_role) db_unique_name=wrongname' SCOPE=BOTH;
ALTER SYSTEM SET log_archive_dest_2 = 'service=boston ASYNC NOAFFIRM
valid_for=(online_logfiles,primary_role) db_unique_name=wrongname' SCOPE=BOTH
*
ERROR at line 1:
ORA-02097: parameter cannot be modified because specified value is invalid
ORA-16053: DB_UNIQUE_NAME wrongname is not in the Data Guard Configuration


>>> 원인 파악
    두 경우 모두 ORA-02097 이 겉껍데기이고, 두 번째 줄이 실제 원인이다.
      ORA-16024 : 문자열을 파싱할 수 없다 → 속성 이름이나 문법이 틀렸다
      ORA-16053 : 지정한 DB_UNIQUE_NAME 이 Data Guard 구성에 없다
                  → LOG_ARCHIVE_CONFIG 의 DG_CONFIG 목록과 대조한다

    ORA-16053 이 알려 주는 것이 중요하다. DB_UNIQUE_NAME 속성은 단순한 표기가 아니라
    실제로 검증되는 값이며, LOG_ARCHIVE_CONFIG 에 등록된 이름만 쓸 수 있다.
    리두가 엉뚱한 데이터베이스로 가는 사고를 막는 장치다.

    잘못된 값이 반영되지 않았다는 점이 오히려 다행이다.
    올바른 문자열로 다시 실행하면 된다.

 [6] 오류 재현 ② — VALID_FOR 를 잘못 준다 (실패하지 않는 오류)
--------------------------------------------------------------------------------

-- 이 데이터베이스는 Primary 인데, 목적지를 standby_role 로 지정해 본다.

SYS@chicago> ALTER SYSTEM SET log_archive_dest_2 =
  2    'service=boston ASYNC NOAFFIRM
  3     valid_for=(online_logfiles,standby_role) db_unique_name=boston' SCOPE=BOTH;

System altered.

  2            FROM v$archive_dest_status WHERE dest_id = 2;

   DEST_ID STATUS    ERROR
---------- --------- ----------------------------------------
         2 VALID

1 row selected.


>>> 원인 파악
    이것이 VALID_FOR 오설정의 가장 위험한 점이다.
      - ALTER SYSTEM 은 성공한다 ("System altered")
      - V$ARCHIVE_DEST_STATUS 의 STATUS 는 VALID 이고 ERROR 도 비어 있다
      - 그런데 리두는 가지 않는다

    유일한 단서는 V$ARCHIVE_DEST 의 VALID_NOW 열이다.
    'WRONG VALID_ROLE' 은 "이 목적지는 이 데이터베이스가 STANDBY 일 때만 쓴다.
    지금은 PRIMARY 이므로 쓰지 않는다" 는 뜻이다.

    STATUS=VALID 와 VALID_NOW=YES 는 다른 이야기다.
      STATUS    : 이 목적지에 문제가 없는가
      VALID_NOW : 지금 이 목적지를 실제로 쓰는가

>>> 조치 — VALID_FOR 를 primary_role 로 바로잡는다

SYS@chicago> ALTER SYSTEM SET log_archive_dest_2 =
  2    'service=boston ASYNC NOAFFIRM
  3     valid_for=(online_logfiles,primary_role) db_unique_name=boston' SCOPE=BOTH;

System altered.

--------------------------------------------------------------------------------
 [7] 속성-열 대응표 정리
--------------------------------------------------------------------------------

  파라미터 속성                       V$ARCHIVE_DEST 열      값 예시
  ----------------------------------- ---------------------- -----------------------
  SERVICE=boston                      DESTINATION            boston
  ASYNC                               TRANSMIT_MODE          ASYNCHRONOUS
  SYNC                                TRANSMIT_MODE          PARALLELSYNC
  AFFIRM                              AFFIRM                 YES
  NOAFFIRM                            AFFIRM                 NO
  VALID_FOR=(online_logfiles, ...)    VALID_TYPE             ONLINE_LOGFILE
  VALID_FOR=(..., primary_role)       VALID_ROLE             PRIMARY_ROLE
  (현재 역할과 맞는가)                VALID_NOW              YES / WRONG VALID_ROLE
  DB_UNIQUE_NAME=boston               (표시되지 않음, 검증용)

  진단 순서
    ① VALID_NOW 가 YES 인가            → 아니면 설정 문제. 오류를 찾을 필요 없음
    ② V$ARCHIVE_DEST_STATUS 의 ERROR   → ORA- 번호가 있으면 그것이 원인
    ③ V$DATAGUARD_PROCESS 의 ACTION    → 전송 프로세스가 움직이는가
