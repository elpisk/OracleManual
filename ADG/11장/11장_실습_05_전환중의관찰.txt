--------------------------------------------------------------------------------
 [1] 오류 재현 — MRP 를 띄우려 하면
--------------------------------------------------------------------------------

-- 7장에서 boston 에 MRP 를 띄웠던 명령을 그대로 써 본다.

SYS@boston> ALTER DATABASE RECOVER MANAGED STANDBY DATABASE DISCONNECT FROM SESSION;

alter database recover managed standby database disconnect from session
*
ERROR at line 1:
ORA-01665: control file is not a standby control file

>>> 원인 파악

-- ★ 이 오류를 이 교재에서 세 번째 만난다.
--
--   1장   Primary 에 MRP 를 띄우려다
--   10장  Far Sync 에 MRP 를 띄우려다
--   지금  Snapshot Standby 에 MRP 를 띄우려다
--
-- ★ 이유는 매번 같다. CONTROLFILE_TYPE 이 STANDBY 가 아니다.
--
--   대상               CONTROLFILE_TYPE   MRP 기동
--   -----------------  -----------------  -----------
--   Primary            CURRENT            ORA-01665
--   Far Sync           FARSYNC            ORA-01665
--   Snapshot Standby   CURRENT            ORA-01665
--   Physical Standby   STANDBY            가능
--
-- ★ 규칙이 하나로 정리된다.
--   MRP 를 띄울 수 있는 것은 Standby 컨트롤 파일뿐이다.
--   오라클이 이 판단을 역할이 아니라 컨트롤 파일 유형으로 한다.

>>> 조치

-- Snapshot Standby 에서 적용은 하지 않는 것이 정상이다.
-- 조치할 것이 없다. 적용을 원하면 Physical Standby 로 되돌려야 한다.

>>> 재확인

-- ★ Primary 입장에서는 아무 일도 없다.
--   목적지가 VALID 이고 오류도 없다.
--   상대가 Snapshot 으로 바뀐 것이 전송에 지장을 주지 않는다.
--
-- ★ 이것이 중요한 성질이다.
--   Standby 를 잠깐 빌려 쓰는 동안 Primary 는 영향을 받지 않는다.
--   운영 데이터베이스를 건드리지 않고 시험할 수 있는 이유다.

--------------------------------------------------------------------------------
 [3] 두 지연이 갈라진다
--------------------------------------------------------------------------------

SYS@boston> COL name FOR a16
SYS@boston> COL value FOR a20
SYS@boston> SELECT name, value FROM v$dataguard_stats WHERE name LIKE '%lag';

NAME             VALUE
---------------- --------------------
transport lag    +00 00:00:00
apply lag        +00 00:02:38

2 rows selected.

-- ★ 7장에서 두 값을 구별해 배운 것이 여기서 쓰인다.
--
--   transport lag   리두가 도착하기까지        → 0. 계속 받는다
--   apply lag       리두가 적용되기까지        → 늘어난다. 적용을 안 한다
--
-- ★ 이 조합이 Snapshot Standby 의 표식이다.
--   transport 는 0 인데 apply 만 커진다면 적용이 멈춰 있다는 뜻이고,
--   그 원인 중 하나가 Snapshot 전환이다.
--
-- ★ 둘 다 커진다면 원인이 다르다. 전송 자체가 끊긴 것이다.
--   7장의 진단 절차로 돌아간다.

SYS@boston> SELECT process, status, sequence# FROM v$managed_standby
  2            WHERE process IN ('RFS','MRP0');

PROCESS   STATUS        SEQUENCE#
--------- ------------ ----------
RFS       IDLE                  0
RFS       IDLE                 41

2 rows selected.

-- ★ RFS 는 살아 있고 시퀀스 41 을 받고 있다. MRP0 은 없다.
--   "받기는 하되 적용은 안 한다" 가 프로세스 목록에 그대로 나타난다.

SYS@boston> SELECT max(sequence#) recv,
  2                max(CASE WHEN applied='YES' THEN sequence# END) app
  3            FROM v$archived_log;

      RECV        APP
---------- ----------
        40         39

1 row selected.

-- ★ 받은 것과 적용된 것의 차이가 벌어지기 시작했다.
--   전환 기간이 길수록 이 격차가 커진다.

FILE_TYPE               PERCENT_SPACE_USED NUMBER_OF_FILES

SYS@boston> SELECT space_used/1024/1024 used_mb FROM v$recovery_file_dest;

   USED_MB
----------
1941.37012

1 row selected.

-- ★ FLASHBACK LOG 항목이 새로 생겼다.
--   실습 01 에서 조회했을 때는 없던 유형이다.
--
--   실습 01   1536.07813 MB   FLASHBACK LOG 없음
--   지금      1941.37012 MB   FLASHBACK LOG 2.6% / 2개
--
--   405MB 가 늘었다.
--
-- ★ 몇 건만 바꿨는데 405MB 인 이유가 있다.
--   플래시백 로그는 바뀐 블록의 이전 이미지를 통째로 남긴다.
--   한 행을 고쳐도 그 행이 속한 블록 전체가 대상이다.
--
-- ★ 실습 03 의 STORAGE_SIZE 200MB 와 헷갈리지 않는다.
--   그것은 복원 지점에 확보된 크기이고
--   이것은 FRA 안에서 플래시백 로그가 실제로 차지한 비율이다.
--   감시는 이 값으로 한다.
--
-- ★ 시험에서 대량 갱신을 하면 이 값이 빠르게 커진다.
--   보장 복원 지점은 지워지지 않으므로 FRA 가 차면 DB 가 멈춘다.
--   임계값을 정해 두고 넘으면 시험을 중단하고 되돌린다.

--
--   ① Snapshot Standby 에서 MRP 기동 → ORA-01665

--   ⑤ RFS 는 있고 MRP0 은 없다
--   ⑥ 두 데이터베이스의 데이터가 갈라진다
--   ⑦ FRA 에 FLASHBACK LOG 유형이 새로 생긴다 (1,536MB → 1,941MB)
