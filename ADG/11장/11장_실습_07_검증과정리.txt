--------------------------------------------------------------------------------
 [1] Snapshot 에서 만든 테이블
--------------------------------------------------------------------------------

SYS@boston> SELECT count(*) FROM system.ss_test;

select count(*) from system.ss_test
                            *
ERROR at line 1:
ORA-00942: table or view does not exist

>>> 원인 파악

-- ★ 이 오류가 나는 것이 정답이다.
--
--   실습 04 에서 이 테이블을 만들고 커밋까지 했다.
--   되돌리자 만든 적이 없는 상태가 되었다.
--
-- ★ ORA-00942 는 "그런 테이블이 없다" 는 뜻이다.
--   비어 있는 것이 아니라 존재 자체가 없다.
--   복원 지점 시점의 딕셔너리로 되감겼기 때문이다.
--
-- ★ 이것이 Snapshot Standby 의 성질을 가장 잘 보여 준다.
--   시험 결과를 남기려면 되돌리기 전에 밖으로 빼내야 한다.

>>> 조치

-- 사라지는 것이 정상이므로 조치할 것이 없다.
-- 남기고 싶었다면 되돌리기 전에 다음 중 하나를 했어야 한다.
--
--   · expdp 로 덤프 파일 추출
--   · 다른 데이터베이스로 DB 링크를 통해 복사
--   · 결과를 텍스트로 받아 파일로 저장 (spool)
--
-- 실행 계획이나 소요 시간 같은 측정 결과라면 spool 이면 충분하다.

>>> 재확인

SYS@boston> SELECT count(*) FROM all_tables WHERE owner='SYSTEM' AND table_name='SS_TEST';

  COUNT(*)
----------
         0

1 row selected.

-- ★ 딕셔너리에도 흔적이 없다.

--------------------------------------------------------------------------------
 [2] 고친 행은 되돌아왔는가
--------------------------------------------------------------------------------

SYS@boston> COL tag FOR a26
SYS@boston> SELECT id, tag FROM system.ss_base ORDER BY id;

        ID TAG
---------- --------------------------
         1 before-snapshot
         2 while-snapshot
         3 while-snapshot

3 rows selected.

-- ★ 두 가지가 동시에 확인된다.
--
--   ① 고친 것이 되돌아왔다
--      실습 04 에서 1번 행을 'modified-on-snapshot' 으로 바꿨는데
--      'before-snapshot' 으로 복귀했다.
--
--   ② 그동안의 Primary 변경이 적용됐다
--      실습 05 에서 Primary 가 넣은 2·3번 행이 나타났다.
--      Snapshot 이던 동안 받아만 두었던 리두가 복귀 후 적용된 것이다.
--
-- ★ 이 두 가지가 한꺼번에 일어난다는 점이 핵심이다.
--   되돌리기는 "원래 자리로 돌아가는 것" 에서 끝나지 않는다.
--   원래 자리로 돌아간 뒤 그동안 밀린 리두를 따라잡는다.

SYS@chicago> COL tag FOR a26
SYS@chicago> SELECT id, tag FROM system.ss_base ORDER BY id;

        ID TAG
---------- --------------------------
         1 before-snapshot
         2 while-snapshot
         3 while-snapshot

3 rows selected.

-- ★ Primary 와 완전히 같다. 복제가 정상으로 돌아왔다.

  2            FROM v$flash_recovery_area_usage WHERE percent_space_used > 0;

3 rows selected.

SYS@boston> SELECT space_used/1024/1024 used_mb FROM v$recovery_file_dest;

   USED_MB
----------
1559.62061

1 row selected.

-- ★ FLASHBACK LOG 항목이 사라졌다.
--
--   실습 05   1941.37012 MB   FLASHBACK LOG 2.6% / 2개
--   지금      1559.62061 MB   FLASHBACK LOG 없음
--
--   400MB 가 회수됐다.
--
-- ★ 복원 지점이 사라졌으므로 플래시백 로그도 필요 없어졌다.
--   되돌리기가 완료되면 공간이 자동으로 돌아온다.
--
-- ★ 반대로 말하면 되돌리기 전에는 회수되지 않는다.
--   FRA 가 차서 곤란할 때 공간을 비울 유일한 방법이
--   되돌리는 것이라고 한 이유가 여기 있다.

 [7] 정리

-- ★ 이 실습에서 확인한 것
--
--   ① Snapshot 에서 만든 테이블은 ORA-00942 — 존재 자체가 없다
--   ② 고친 행은 원래 값으로 복귀
--   ③ 그동안의 Primary 변경은 모두 적용됨
--   ④ apply lag 2분 38초 → 0
--   ⑤ FLASHBACK LOG 가 사라지고 400MB 회수 (1,941MB → 1,559MB)
--   ⑥ 실습 테이블 삭제로 원상 복구
--
-- ★ 11장을 마친다.
--   12장은 Logical Standby 와 SQL Apply 를 다룬다.
--   이 상태에서 시작한다.
