================================================================================
 ■ Active Data Guard 종합 실기평가 — 3종 모범답안
 과정      : Oracle Database 19c Active Data Guard (1~16장 종합)
 환경      : Oracle 19.3.0 EE / Oracle Linux 7.9 / CDB 2노드 chicago(Primary) · boston(Standby)
================================================================================

이 문서는 문제지의 과제 1-1 부터 3-3 까지에 대응하는 모범답안이다.
각 과제를 【판정】 무엇을 보고 경로를 정했는가 · 【수행】 실제로 실행한 명령 ·
【검증】 끝났음을 무엇으로 확인했는가 세 축으로 나눈다.
채점은 명령의 정확성보다 판정 근거의 유무를 먼저 본다.

출력 표시의 뜻
  [교안 실측]  같은 랩에서 해당 장의 실습으로 실제로 얻은 출력이다. 장·실습 번호를 붙인다.
  [예상]       이 시험의 장애 스크립트로는 아직 랩에서 끝까지 돌려 보지 않은 출력이다.
               오류 번호·메시지 모양은 Oracle 19c 문서와 교안을 근거로 적었다.
               첫 시험 전 감독관 리허설(운영가이드 2장)에서 실제 값으로 바꿔 적는다.
  SCN · 시퀀스 · 시각 · 파일 번호는 환경마다 다르다. 값 자체가 아니라
  두 값의 대소 관계와 "무엇을 조회했는가" 를 본다.

================================================================================
 이 평가를 관통하는 판정 틀
================================================================================
흐름 세 질문 (15장)
  ① 리두가 오는가      Primary : v$archive_dest_status (dest_id=2) STATUS · ERROR · GAP_STATUS
                       Standby : v$standby_log 에 ACTIVE 인 그룹, v$managed_standby 의 RFS
  ② 적용되는가        Standby : MRP0 존재 · STATUS(APPLYING_LOG / WAIT_FOR_LOG / WAIT_FOR_GAP)
                       v$dataguard_stats 의 transport lag · apply lag
  ③ 원인이 처음 보이는 층   Broker 번호 → V$ → 알림 로그 → 트레이스

  transport lag 정상 · apply lag 증가  →  전송은 됐다. 문제는 적용(Standby 내부)
  두 값 모두 증가                      →  전송이 막혔다. 문제는 Primary→Standby 경로
  두 값 모두 "값 없음"                 →  지연이 없는 것이 아니라 잴 수 없는 것이다 (15장 함정)

Broker 상태 바꾸기 (13장)
  적용 멈춤/재개   EDIT DATABASE 'boston'  SET STATE='APPLY-OFF' | 'APPLY-ON'
  전송 멈춤/재개   EDIT DATABASE '<Primary>' SET STATE='TRANSPORT-OFF' | 'TRANSPORT-ON'
  SQL 로 MRP 를 멈추면 Broker 는 Intended State(APPLY-ON)를 지키려고 다시 시작한다.

공통 검증 묶음 — 이하 "검증 묶음" 이라 부른다
  SYS@<primary>> SELECT dest_id, status, error, gap_status FROM v$archive_dest_status WHERE dest_id=2;
  SYS@<primary>> SELECT thread#, MAX(sequence#) FROM v$archived_log WHERE dest_id=1
                  AND resetlogs_change#=(SELECT resetlogs_change# FROM v$database) GROUP BY thread#;
  SYS@<standby>> SELECT process, status, sequence# FROM v$managed_standby WHERE process IN ('MRP0','RFS');
  SYS@<standby>> SELECT group#, sequence#, status FROM v$standby_log WHERE status='ACTIVE';
  SYS@<standby>> SELECT name, value FROM v$dataguard_stats WHERE name IN ('transport lag','apply lag');
  SYS@<standby>> SELECT step, TO_CHAR(reg_time,'HH24:MI:SS') t FROM system.exam_log ORDER BY reg_time;
  DGMGRL> SHOW CONFIGURATION;

  "끝났다" 의 기준 : 목적지 VALID · ERROR 없음 · MRP0 APPLYING_LOG · SRL ACTIVE 1개 ·
                     Primary CURRENT 시퀀스와 Standby 적용 시퀀스의 차이 1 이내 ·
                     마지막 step 행이 Standby 에 보임 · Broker SUCCESS

 시나리오 1  [최상]  멈춘 Standby 되살리기

--------------------------------------------------------------------------------
 과제 1-1. 적용이 멈췄다 — 새 테이블스페이스  [30점]
--------------------------------------------------------------------------------
【판정】

1-1.2 Broker 와 흐름 질문  [예상]

  DGMGRL> SHOW CONFIGURATION;
    boston - Physical standby database
      Error: ORA-16766: Redo Apply is stopped
  Configuration Status:
  ERROR

  ▸ ① 전송 : Primary 목적지 2 VALID, ERROR 없음. boston 에 SRL ACTIVE 1개, RFS 있음.
  ▸ ② 적용 : MRP0 없음(또는 Broker 가 다시 띄운 직후 바로 사라짐).
  ▸ transport lag 0 초 근처, apply lag 계속 증가 → 리두는 왔다. 적용이 멈췄다.
    문제는 Standby 내부다.

1-1.3 오류 순서  [예상]

  boston 알림 로그
    ORA-01274: cannot add data file that was originally created as
               '/u03/app/oracle/oradata/Chicago/exam_ts01.dbf'
    ... MRP0: Background Media Recovery terminated with error 1274
  Broker 가 적용을 다시 시작한 뒤
    ORA-01111: name for data file 14 is unknown - rename to correct file
    ORA-01110: data file 14: '/u01/app/oracle/product/19.3.0/dbhome_1/dbs/UNNAMED00014'
    ORA-01157: cannot identify/lock data file 14 - see DBWR trace file

  ▸ 첫 번째(01274) : 파일 추가 리두를 만난 순간. STANDBY_FILE_MANAGEMENT=MANUAL 이라
    실제 파일을 만들지 않고 컨트롤 파일에만 UNNAMED 자리를 등록하고 멈췄다.
  ▸ 두 번째(01111 계열) : Broker 가 APPLY-ON 을 지키려고 MRP 를 다시 띄웠고,
    MRP 는 이미 등록된 UNNAMED 파일을 열려다 실패했다. 원인은 같고, 증상이 바뀐 것이다.
    번호만 보고 "두 번째 장애" 로 오판하지 않는다.

1-1.4 파일 특정  [예상]

  SYS@boston> SELECT file#, name, status FROM v$datafile WHERE name LIKE '%UNNAMED%';
       14  /u01/app/oracle/product/19.3.0/dbhome_1/dbs/UNNAMED00014   RECOVER
  SYS@boston> SELECT file#, error, tablespace_name FROM v$datafile_header WHERE file#=14;
       14  FILE NOT FOUND    (TABLESPACE_NAME 비어 있음)
  SYS@boston> SELECT file#, online_status, error FROM v$recover_file;
       14  ONLINE   FILE NOT FOUND

  ▸ v$datafile        : 컨트롤 파일의 기록 — 이름이 UNNAMED 로 "자리만" 있다
    v$datafile_header : 실제 파일 헤더 — 파일이 없으니 헤더 정보가 비어 있다
    v$recover_file    : 복구가 필요한 파일 목록 — 왜 필요한지(ERROR)는 알려 주지만
                        Primary 쪽 원래 이름은 알려 주지 않는다. 원래 이름은 알림 로그(01274)에 있다.

1-1.5 원인 설정

  DGMGRL> SHOW DATABASE 'boston' 'StandbyFileManagement';
    StandbyFileManagement = 'MANUAL'
  SYS@boston> SHOW PARAMETER standby_file_management
    standby_file_management   string   MANUAL

  ▸ 기록 위치 : Broker 속성 StandbyFileManagement (Broker 구성 파일 dr1/dr2) → 파라미터 standby_file_management.
  ▸ 누가 바꿨는가 : boston 알림 로그의 "ALTER SYSTEM SET standby_file_management='MANUAL' ..."
    줄과 Broker 로그 drcboston.log 의 EDIT DATABASE 기록. 시각으로 변경 시점을 특정한다.
    (19c 에서 이 속성은 Broker 가 파라미터로 관리한다 — 13장 속성 표. 직접 ALTER SYSTEM 해도
    Broker 와 어긋나므로 Broker 로 되돌린다)

【수행】

1-1.6 되살리기 — 순서가 핵심이다

  -- ① Broker 가 MRP 를 다시 띄우지 못하게 적용을 내린다
  DGMGRL> EDIT DATABASE 'boston' SET STATE='APPLY-OFF';

  -- ② MANUAL 인 채로 UNNAMED 자리에 빈 파일을 만든다 (AUTO 면 ORA-01275 로 거부된다)
  --    boston 은 OMF(db_create_file_dest) 이므로 AS NEW 로 OMF 이름을 받는다
  SYS@boston> ALTER DATABASE CREATE DATAFILE
                '/u01/app/oracle/product/19.3.0/dbhome_1/dbs/UNNAMED00014' AS NEW;
  -- [예상] READ ONLY 로 열린 상태에서 거부되면 SHUTDOWN IMMEDIATE → STARTUP MOUNT 후 같은 명령,
  --        끝나면 ALTER DATABASE OPEN READ ONLY.

  SYS@boston> SELECT file#, name FROM v$datafile WHERE file#=14;
       14  /u03/app/oracle/oradata/BOSTON/<GUID>/datafile/o1_mf_exam_ts_xxxxxxxx_.dbf

  -- ③ 원인 설정을 Broker 로 되돌린다 (다음 파일 추가에서 같은 일이 생기지 않도록)
  DGMGRL> EDIT DATABASE 'boston' SET PROPERTY 'StandbyFileManagement'='AUTO';

  -- ④ 적용을 다시 켠다
  DGMGRL> EDIT DATABASE 'boston' SET STATE='APPLY-ON';

  ▸ SQL 로 MRP 를 멈추고 켜면 : Broker 의 Intended State 와 실제가 어긋나 Broker 가 다시 띄우거나
    ORA-16766/16810 경고가 남는다. 파일을 만드는 도중 MRP 가 되살아나 같은 오류를 다시 낸다.

【검증】

1-1.7
  SYS@boston> SELECT COUNT(*) FROM system.exam_ts_t;          → 500
  SYS@boston> SELECT step FROM system.exam_log WHERE step LIKE 'S1-1%';   → S1-1a, S1-1b
  검증 묶음 : MRP0 APPLYING_LOG, apply lag 0~수 초, Broker SUCCESS
  SYS@boston> SHOW PARAMETER standby_file_management           → AUTO
  손실 : 없음 (Primary 는 계속 정상, 리두는 모두 boston 에 도착해 있었다)
  보호 : 리두는 받고 있었으므로 RPO 보호는 유지되었다. 다만 apply lag 동안 RTO 는 늘어나 있었다
         (그 시간에 Failover 했다면 밀린 리두를 모두 적용한 뒤에야 열린다 — 그리고 이 파일 때문에 멈춘다).

--------------------------------------------------------------------------------
 과제 1-2. 두 인스턴스가 모두 떠 있는데 리두가 가지 않는다  [30점]
--------------------------------------------------------------------------------
【판정】

1-2.2  [예상]

  SYS@chicago> SELECT status, error FROM v$archive_dest_status WHERE dest_id=2;
    ERROR   ORA-16191: Primary log shipping client not logged on standby
  SYS@chicago> SHOW PARAMETER log_archive_dest_state_2
    log_archive_dest_state_2   string   ENABLE

  ▸ STATUS=ERROR + STATE=ENABLE → 설정이 아니라 장애다 (15장 표 : DEFER 면 "설정", ENABLE 인데
    ERROR 면 "장애").

1-2.3  다음 층 — 알림 로그  [예상]

  chicago alert_chicago.log
    Error 1017 received logging on to the standby
    ------------------------------------------------------------
    Check that the primary and standby are using a password file
    and remote_login_passwordfile is set to SHARED or EXCLUSIVE,
    and that the SYS password is same in the password files.
          returning error ORA-16191
    ------------------------------------------------------------

  ▸ 16191 은 "로그온 실패" 라는 결과만 말한다. 원인 번호는 그 앞의 1017(비밀번호 불일치)이다.
    16장 실습 08 에서 본 ORA-01017 과 같은 계열이다 [교안 실측 16장 실습 08].

1-2.4  원인 파일

  [oracle@boston-srv ~]$ ls -l $ORACLE_HOME/dbs/orapwboston
    → 시각이 오늘, 크기·시각이 chicago 의 orapwchicago 와 다르다
  [oracle@chicago-srv ~]$ ls -l $ORACLE_HOME/dbs/orapwchicago

  ▸ 정상 원본 : 현재 Primary 의 비밀번호 파일 (chicago:$ORACLE_HOME/dbs/orapwchicago).
    Data Guard 의 비밀번호 파일은 Primary 에서 복사해 이름만 바꾼다 (4장·5장).
  ▸ ALTER USER SYS IDENTIFIED BY 가 지금 통하지 않는 이유 : 12.2 이후 Primary 의 비밀번호 파일
    변경은 리두를 타고 Standby 에 전달된다. 그런데 지금 리두가 가지 않는다(로그온 자체가 실패).
    닭과 달걀 — 길이 막힌 상태에서 그 길로 고칠 수 없다.
  ▸ 감독자 사본(_proctor)은 쓰지 않는다 — 자동 불합격.

【수행】

1-2.5
  [oracle@chicago-srv ~]$ scp $ORACLE_HOME/dbs/orapwchicago \
                             oracle@boston-srv:$ORACLE_HOME/dbs/orapwboston
  -- 비밀번호 파일은 접속 시점에 읽으므로 boston 재기동은 필요 없다

  -- 목적지가 바로 회복되지 않는 이유 : 오류가 난 목적지는 REOPEN(ReopenSecs, 기본 300초)
  --   동안 재시도를 쉰다. 최대 5분을 기다리게 된다.
  -- Broker 환경의 재촉 : Primary 의 전송 상태를 껐다 켠다
  DGMGRL> EDIT DATABASE 'chicago' SET STATE='TRANSPORT-OFF';
  DGMGRL> EDIT DATABASE 'chicago' SET STATE='TRANSPORT-ON';

  -- (SQL 의 log_archive_dest_state_2 DEFER/ENABLE 은 Broker 관리 설정을 직접 바꾸는 것이라 쓰지 않는다)

【검증】

1-2.6
  보호 없던 구간 : chicago 알림 로그의 첫 "Error 1017 received" 시각 ~ 회복 후 첫
                   "LGWR: ... Standby redo logfile selected" 또는 v$archive_dest_status VALID 확인 시각.
                   (boston 재기동 시각 ≒ 시작점)
  갭 : 그동안 쌓인 아카이브는 회복 직후 ARCH/FAL 로 자동 전송된다 (Primary 에 아직 남아 있으므로).
  SYS@boston> SELECT step FROM system.exam_log WHERE step LIKE 'S1-2%';    → S1-2a, S1-2b
  검증 묶음 정상, Broker SUCCESS.
  손실 : 없음. 단, 보호 없던 구간에 Primary 가 죽었다면 그 구간 전체가 손실이었다 — 이것을 보고서에 적는다.

--------------------------------------------------------------------------------
 과제 1-3. 메울 수 없는 갭  [40점]
--------------------------------------------------------------------------------
【판정】

1-3.2  [예상]

  SYS@boston> SELECT process, status, sequence# FROM v$managed_standby WHERE process='MRP0';
    MRP0   WAIT_FOR_GAP   N0
  SYS@boston> SELECT * FROM v$archive_gap;
    THREAD#  LOW_SEQUENCE#  HIGH_SEQUENCE#
          1             N0          N0+1

  ▸ v$archive_gap 이 비어 있는 경우 : 이 뷰는 "받은 것 사이의 구멍" 만 보인다. 갭 뒤의 로그를
    아직 하나도 못 받았거나 MRP 가 그 지점에 닿기 전이면 비어 있을 수 있다 (15장).
    그때는 MRP0 의 WAIT_FOR_GAP 과 sequence#, 그리고 RFS 가 받은 최신 시퀀스를 비교한다.

1-3.3  FAL 이 메우지 못하는 증명  [예상]

  (가) SYS@chicago> SELECT sequence#, name, deleted, status FROM v$archived_log
                    WHERE dest_id=1 AND sequence# IN (N0, N0+1)
                      AND resetlogs_change#=(SELECT resetlogs_change# FROM v$database);
       → 두 행 모두 이름이 있고 STATUS='A' — 컨트롤 파일은 "있다" 고 믿는다
  (나) [oracle@chicago-srv ~]$ ls -l <위 NAME 두 개>
       → No such file or directory — 디스크에는 없다 (OS 에서 지웠으니 컨트롤 파일이 모른다)
  (다) SYS@chicago> SELECT group#, sequence#, status FROM v$log;
       → 온라인 그룹의 시퀀스는 모두 N0+2 이상 — 온라인 리두로 덮여 사라졌다
  알림 로그 인용 (chicago)
       FAL[server, ARC..]: ... Error 2 ... archived log for thread 1 sequence N0 ... cannot be found
       (또는 "Failed to request gap sequence ... No FAL server ...")
  ▸ 세 곳 어디에도 없다 → 이 갭은 메울 수 없다 (unresolvable gap). 기다려도 해결되지 않는다.

1-3.4  선택지 비교

  | 기준              | (가) 재생성 (6장)                     | (나) Roll forward (FROM SERVICE)           |
  | 옮기는 양         | 전체 데이터 파일 (DB 크기)             | N0 이후 바뀐 블록만 (증분) + 컨트롤 파일     |
  | 걸리는 시간       | DB 크기 / 네트워크 대역                | 변경량에 비례 — 보통 훨씬 짧다              |
  | 보호 없는 시간    | 재생성 + 편입 전체                     | roll forward 동안만                        |
  | 위험              | Broker 재편입, 파라미터 재확인 필요     | 컨트롤 파일이 바뀌어 일부 설정을 다시 맞춘다 |
  ▸ (나) 를 고른다. 데이터 파일은 멀쩡하고 빠진 것은 리두 두 개뿐이다. 바뀐 블록만 가져오면 된다.

【수행】

1-3.5  [예상 — 19c RMAN 의 RECOVER STANDBY DATABASE FROM SERVICE 는 랩에서 이 시험으로 처음 수행한다]

  -- ① Broker 가 도중에 MRP 를 띄우지 않게
  DGMGRL> EDIT DATABASE 'boston' SET STATE='APPLY-OFF';

  -- ② boston 에서 RMAN — 대상은 Standby 자신, 원본은 Primary 서비스
  [oracle@boston-srv ~]$ rman target /
  RMAN> RECOVER STANDBY DATABASE FROM SERVICE chicago;

  화면에서 단계가 바뀌는 지점 (인용할 것)
    Executing: alter database flashback off          (켜져 있으면 끄고 시작한다)
    Oracle instance started / Starting restore ... restoring control file  → 컨트롤 파일 복원
    database mounted
    contents of Memory Script: ... catalog / switch datafile ...         → OMF 이름으로 다시 연결
    Starting recover ... using network backup set from service chicago   → 증분 복구
    Executing: alter database flashback on            (원래 켜져 있었다면)
    Finished recover

  -- 실패 시 : 인스턴스가 READ ONLY 면 SHUTDOWN IMMEDIATE → STARTUP NOMOUNT 후 다시 실행.

  -- ③ 열고 적용 재개
  SYS@boston> ALTER DATABASE OPEN READ ONLY;
  DGMGRL> EDIT DATABASE 'boston' SET STATE='APPLY-ON';

【검증】

1-3.6  16장 수준 점검표 (수행 전과 비교)

  | 항목            | 수행 전                  | 수행 후 (확인 값)          | 다르면 조치                                  |
  | DATABASE_ROLE   | PHYSICAL STANDBY         | PHYSICAL STANDBY           |                                              |
  | OPEN_MODE       | READ ONLY WITH APPLY     | MOUNTED → OPEN 후 WITH APPLY | ALTER DATABASE OPEN READ ONLY                 |
  | FLASHBACK_ON    | YES                      | YES / NO                   | NO 면 APPLY-OFF → ALTER DATABASE FLASHBACK ON → APPLY-ON |
  | SRL             | 4개, 1개 ACTIVE          | 이름이 Primary 경로/없음?   | v$standby_log·v$logfile 확인, 이상하면 DROP/ADD STANDBY LOGFILE |
  | CONTROL_FILES   | BOSTON 경로              | 그대로 (파라미터는 spfile) | v$controlfile 로 확인                         |
  | Broker          | ERROR                    | SUCCESS                    |                                              |

  ▸ 컨트롤 파일을 Primary 에서 가져왔으므로 컨트롤 파일 안에 있던 정보(SRL 이름, 플래시백 상태,
    데이터 파일 이름)는 반드시 다시 본다. 이것이 "끝난 뒤 16장 수준 점검" 의 이유다.

1-3.7
  SYS@boston> SELECT step FROM system.exam_log WHERE step LIKE 'S1-3%';   → S1-3a ~ S1-3d 모두
  손실 : 없음 (Primary 는 계속 정상이었다). 보호 없던 구간 : boston 중단 시각 ~ roll forward 후 SUCCESS.
  막을 수 있었던 운영 규칙
    ① 아카이브 삭제 정책 : RMAN CONFIGURE ARCHIVELOG DELETION POLICY TO APPLIED ON ALL STANDBY
       (또는 SHIPPED TO ALL STANDBY). OS rm 금지 — 정리는 RMAN DELETE 로만.
    ② 감시 : Standby 중단·목적지 ERROR 를 즉시 경고 (15장 점검 묶음을 5분 주기로, 그리고
       apply lag 임계). Standby 가 내려간 시간이 길수록 갭 위험이 커진다.

  ▸ MOUNT 면 충분하다. Failover 는 컨트롤 파일과 SRL/아카이브만 있으면 남은 리두를 적용하고

    업무 재개를 우선한다면 지금 Failover 한다 — 그 판단과 손실 범위를 먼저 기록한다.

  Primary(chicago) : 목적지 2 STATUS=ERROR, ERROR=ORA-12541: TNS:no listener
  Standby(boston)  : MRP0 WAIT_FOR_LOG, SRL ACTIVE 없음, RFS 없음
                     transport lag / apply lag : 값이 비었거나 멈춘 값
  판정 : 경고 (전송 중단, Primary 정상, 손실 위험 증가 중). 심각은 아니다 — Primary 는 살아 있고
         아카이브가 Primary 에 남아 있어 갭은 메울 수 있다.
  ▸ 두 지연 값이 비거나 변하지 않는 이유 : Standby 가 Primary 소식을 받지 못하면 lag 을 계산할 기준이
    갱신되지 않는다. "0 이거나 값 없음 = 정상" 으로 읽으면 오판한다 (15장 함정).

3-2.3  층별 표
  | 층         | 본 것                                                  | 얻은 것                         |
  | Broker     | ORA-16857 member disconnected / ORA-16778 redo transport error | 전송 문제라는 것                |
  | V$ (Primary) | dest 2 ERROR ORA-12541                               | 상대 리스너가 없다               |
  | 알림 로그  | "TNS-12541 ... Error 12541 received logging on to the standby" 와 첫 시각 | 시작 시각                       |
  | OS         | boston: lsnrctl status → TNS-12541, ps 에 tnslsnr 없음 | 원인 확정                       |

【수행】

3-2.4
  [oracle@boston-srv ~]$ lsnrctl start
  [oracle@boston-srv ~]$ lsnrctl status | grep -E 'boston(_DGMGRL)?'   → 정적·동적 서비스 확인
  ▸ 바로 VALID 가 안 되는 이유 : ReopenSecs(기본 300초) 동안 재시도를 쉰다. 그리고 boston 이 동적
    등록을 다시 하는 데 최대 1분(LREG) 걸린다.
  재촉 : DGMGRL> EDIT DATABASE 'chicago' SET STATE='TRANSPORT-OFF';
         DGMGRL> EDIT DATABASE 'chicago' SET STATE='TRANSPORT-ON';
  (기다려도 된다 — 손실 위험과 남은 시간을 보고 정한다. 정했으면 그 이유를 적는다)

3-2.5
  ▸ 고친 직후 SHOW CONFIGURATION 이 ERROR/경고가 더 늘어 보일 수 있다 : 리두가 다시 흐르며 쌓인 갭을
    따라잡는 동안 transport/apply lag 이 "드디어 계산되어" 큰 값으로 보이고 임계 경고(16853/16855)가
    뜬다. 또 Broker 의 상태 판정은 주기적이라 몇십 초 늦다 (15장 판정 시차).
  점검 묶음 재실행 → 목적지 VALID, SRL ACTIVE 1, MRP0 APPLYING_LOG, lag 수 초 → 정상.

 과제 3-3. Snapshot Standby 로 하루 시험 운용  [35점]
--------------------------------------------------------------------------------
【판정】

3-3.1
  SYS@boston> SHOW PARAMETER db_recovery_file_dest       → 설정되어 있음 (크기 확인)
  SYS@boston> SELECT flashback_on FROM v$database;        → YES (필수는 아니다 — 보장 복원 지점을 쓰므로
                                                             FRA 만 있으면 된다. 공간을 함께 본다)
  SYS@boston> SELECT space_limit, space_used FROM v$recovery_file_dest;
  DGMGRL> SHOW DATABASE 'boston';                          → APPLY-ON, lag 정상

【수행】

3-3.2
  DGMGRL> CONVERT DATABASE 'boston' TO SNAPSHOT STANDBY;
    Converting database "boston" to a Snapshot Standby database, please wait...
    Database "boston" converted successfully
  ▸ Broker 로 한다 : Broker 가 관리하는 구성에서 SQL(ALTER DATABASE CONVERT TO SNAPSHOT STANDBY)로
    바꾸면 Broker 의 역할 기록과 어긋난다 (11장).
  SYS@boston> SELECT database_role, open_mode FROM v$database;   → SNAPSHOT STANDBY  READ WRITE
  SYS@boston> SELECT name, guarantee_flashback_database FROM v$restore_point;
    → SNAPSHOT_STANDBY_REQUIRED_<날짜>  YES

3-3.3
  SYS@boston> ALTER SESSION SET CONTAINER=<PDB>;
  SYS@boston> CREATE TABLE dev_test AS SELECT LEVEL id FROM dual CONNECT BY LEVEL <= 100;
  [oracle@chicago-srv ~]$ /home/oracle/exam/exam_break3.sh 3

3-3.4  증거
  리두는 온다 : SYS@chicago> v$archive_dest_status dest 2 VALID
               SYS@boston>  v$archived_log 의 MAX(sequence#) 가 증가 (RFS 가 받아 아카이브한다)
  적용은 안 된다 : SYS@boston> MRP0 없음, SELECT COUNT(*) FROM system.exam_snap_src → ORA-00942
  하루 이어지면 : ① 적용 안 된 리두가 쌓여 되돌릴 때 그 전부를 적용해야 한다 — 그동안 RTO 가 크다
                  (지금 Primary 가 죽으면 Failover 전에 Snapshot → Physical 변환 + 적용이 필요)
                  ② FRA 가 플래시백 로그와 받은 아카이브로 찬다 — 차면 전송이 멈춘다

3-3.5
  DGMGRL> CONVERT DATABASE 'boston' TO PHYSICAL STANDBY;
    Converting database "boston" to a Physical Standby database, please wait...
    ... Continuing to convert database "boston" ...
    Database "boston" converted successfully
  SYS@boston> SELECT database_role, open_mode FROM v$database;   → PHYSICAL STANDBY  READ ONLY WITH APPLY
  [예상] READ ONLY 가 아니라 MOUNTED 로 돌아오면 : APPLY-OFF → ALTER DATABASE OPEN READ ONLY → APPLY-ON
  SYS@boston> SELECT COUNT(*) FROM <PDB>.dev_test             → ORA-00942 (사라졌다)
  SYS@boston> SELECT COUNT(*) FROM system.exam_snap_src      → 300
  SYS@boston> SELECT step FROM system.exam_log WHERE step='S3-3b';   → 보인다
  SYS@boston> SELECT * FROM v$restore_point;                 → 보장 복원 지점이 없어졌다
  DGMGRL> SHOW CONFIGURATION;                                → SUCCESS

3-3.6
  개발팀 안내 : "시험 환경은 원래의 운영 복제본으로 되돌리면서 시험 중 만든 데이터(dev_test 등)는 모두
