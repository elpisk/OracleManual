================================================================================
 ■ Active Data Guard 종합 실기평가 — 운영 가이드
 대상 : 감독관 · 응시자
================================================================================

--------------------------------------------------------------------------------
 0. 전제
--------------------------------------------------------------------------------
 - 응시자 1인당 VM 2대(chicago-srv, boston-srv). 16장을 마친 상태 그대로.
 - 시나리오는 1 → 2 → 3 순서. 시나리오 사이에는 VM 스냅샷 exam-base 로 되돌린다
   (Failover·재구축·RMAN 복원을 되돌리는 스크립트는 만들지 않는다 — 스냅샷이 가장 확실하다).
 - 스크립트는 chicago-srv 의 감독관 계정 examadm 에 둔다. 응시자는 oracle 계정을 쓰므로
   스크립트 내용(장애 내용이 그대로 적혀 있다)과 감독관 기록을 읽을 수 없다.
   응시자는 sudo 규칙으로 장애 주입 스크립트 세 개를 "실행만" 한다.
 - 파일 구성 (chicago-srv:/home/examadm/exam/ — 700, examadm 전용)
     exam.conf         SYS 비밀번호 등 설정 (600)
     exam_env.sh       공통 환경과 함수 (직접 실행하지 않는다)
     exam_prep.sh      감독관 준비 — 기준 점검, 확인용 테이블, 감독자 사본, 기준선
     exam_break1.sh    시나리오 1 장애 주입  1|2|3
     exam_break2.sh    시나리오 2 장애 주입  1|2|3
     exam_break3.sh    시나리오 3 장애 주입  1|2|3
     state/s13_deleted 과제 1-3 에서 지운 시퀀스 (감독관 대조용)
     proctor/          boston 의 orapwboston, listener.ora 감독자 사본
   응시자가 읽는 파일 (chicago-srv:/exam/pub/ — examadm 소유, 755)
     business.log      업무 입력 기록 (mark 가 남긴다 — 손실 보고의 근거)
     baseline.txt      기준선
     ticket_S3-*.txt   시나리오 3 의 문의·점검표
 - 스크립트는 DB·OS 작업을 모두 oracle 계정 SSH 로 한다 (examadm → oracle@chicago-srv,
   oracle@boston-srv). SYS 비밀번호는 exam.conf 에서 읽으므로 응시자가 export 할 것은 없다.

 [중요] 이 패키지의 스크립트와 모범답안은 문법 검사와 모의 실행(가짜 sqlplus/ssh)까지만 거쳤다.
        실제 랩에서 끝까지 돌린 적은 아직 없다. 첫 시험 전에 2장의 리허설을 반드시 한다.
        2026-10-16 에 examadm 구조로 바꾸면서 모의 실행을 다시 했다. sudo 규칙과 SSH 키는
        랩에서 1-3 의 확인 명령으로 직접 점검한다.

================================================================================
 1. 감독관 — 시험 전날
================================================================================
 1-1. 기준 상태 확인 (exam_prep.sh 가 다시 점검한다)
        chicago PRIMARY · boston PHYSICAL STANDBY READ ONLY WITH APPLY
        양쪽 FLASHBACK_ON=YES · Broker SUCCESS · FSFO Disabled · 관측자 정지
        양쪽 tnsnames.ora 에 chicago, boston 별칭 · 양쪽 _DGMGRL 정적 등록

 1-2. 디스크 여유
        boston FRA 에 Snapshot Standby(3-3) 와 RMAN roll forward(1-3) 여유 — 최소 5GB
        boston 데이터 영역에 재구축(2-3) 여유 — 데이터 파일 총량 이상
        RMAN 아카이브 삭제 정책이 1-3 의 rm 과 충돌하지 않는지 확인 (정책은 그대로 둔다)

 1-3. 감독관 계정, 공개 디렉터리, sudo 규칙, SSH 키 (chicago-srv, 처음 한 번)
        [root@chicago-srv ~]# useradd -m examadm && chmod 700 /home/examadm
        [root@chicago-srv ~]# mkdir -p /exam/pub && chown examadm: /exam/pub && chmod 755 /exam/pub
        [root@chicago-srv ~]# cat > /etc/sudoers.d/exam <<'EOF'
        oracle ALL=(examadm) NOPASSWD: /home/examadm/exam/exam_break1.sh, /home/examadm/exam/exam_break2.sh, /home/examadm/exam/exam_break3.sh
        EOF
        [root@chicago-srv ~]# chmod 440 /etc/sudoers.d/exam && visudo -cf /etc/sudoers.d/exam
      examadm → oracle 암호 없는 SSH (스크립트가 양쪽 DB·OS 를 이 경로로 조작한다)
        [examadm@chicago-srv ~]$ ssh-keygen -t rsa -N '' -f ~/.ssh/id_rsa
        [examadm@chicago-srv ~]$ ssh-copy-id oracle@chicago-srv
        [examadm@chicago-srv ~]$ ssh-copy-id oracle@boston-srv
      oracle 의 chicago → boston 암호 없는 SSH (응시자의 scp 용)
        [oracle@chicago-srv ~]$ ssh-keygen -t rsa -N '' -f ~/.ssh/id_rsa   (없을 때만)
        [oracle@chicago-srv ~]$ ssh-copy-id oracle@boston-srv
      응시자는 이 키로 chicago 에서 boston 으로 "보내는" scp 만 할 수 있다 (1-2, 2-3 의 비밀번호
      파일 복사). boston 에서 chicago 로 가는 키는 만들지 않는다 — 모범답안도 chicago 에서 보낸다.
      root 비밀번호와 examadm 비밀번호는 응시자에게 알리지 않는다.

 1-4. 스크립트 배포와 준비 (examadm)
        [examadm@chicago-srv ~]$ mkdir -p /home/examadm/exam && cp exam_*.sh /home/examadm/exam/
        [examadm@chicago-srv ~]$ chmod 700 /home/examadm/exam /home/examadm/exam/exam_*.sh
        [examadm@chicago-srv ~]$ echo "EXAM_SYS_PW='<SYS 비밀번호>'" > /home/examadm/exam/exam.conf
        [examadm@chicago-srv ~]$ chmod 600 /home/examadm/exam/exam.conf
        [examadm@chicago-srv ~]$ /home/examadm/exam/exam_prep.sh
      "준비 완료" 가 나와야 한다. FAIL 이 있으면 정리 후 다시 실행한다.
      응시자 쪽에서 막혔는지 확인한다 (둘 다 거부되어야 정상).
        [oracle@chicago-srv ~]$ cat /home/examadm/exam/exam_break1.sh     → Permission denied
        [oracle@chicago-srv ~]$ sudo -u examadm cat /home/examadm/exam/exam_break1.sh  → 허용되지 않음

 1-5. 기준 스냅샷 exam-base
        boston : SHUTDOWN IMMEDIATE → chicago : SHUTDOWN IMMEDIATE → 두 VM 전원 끄기
        (VMware) vmrun snapshot <boston.vmx> exam-base ; vmrun snapshot <chicago.vmx> exam-base
        전원 켜기 → chicago STARTUP → boston STARTUP → Broker SUCCESS 확인 (1~2분)
      두 VM 은 반드시 함께 찍고 함께 되돌린다. 한쪽만 되돌리면 SCN 이 어긋나 구성이 깨진다.

 1-6. 문제지 배포. 모범답안·이 문서의 2장 리허설 기록은 배포하지 않는다.

================================================================================
 2. 감독관 — 첫 시험 전 리허설 (처음 한 번)
================================================================================
 2-1. exam-base 에서 시나리오 1·2·3 을 모범답안대로 직접 수행한다. 시나리오 사이에 스냅샷 복원.
 2-2. 모범답안의 [예상] 출력을 실제 출력으로 바꾸고 [실측 <날짜>] 로 표시를 바꾼다.
      특히 다음을 확인한다.
        - 1-1 : MRP 가 ORA-01274 로 멈춘 뒤 Broker 가 적용을 스스로 다시 시작하는가.
                13장 실습 05 기록은 "Intended State 는 APPLY-ON 으로 남고 Broker 는 경고만 한다" 이다.
                다시 시작하지 않으면 오류는 01274 하나뿐이다 — 모범답안 1-1.3 을 그에 맞춘다.
                (READ ONLY 상태의 CREATE DATAFILE AS NEW 는 8장 실습 04 에서 MRP 정지 후 성공했다)
        - 1-3 : RECOVER STANDBY DATABASE FROM SERVICE 가 OPEN/MOUNT 상태에서 시작되는가,
                끝난 뒤 FLASHBACK_ON · SRL · 데이터 파일 이름이 어떻게 남는가
        - 2-1 : LogShipping=OFF 가 SHOW CONFIGURATION 에 언제 경고로 드러나는가,
                boston 정적 등록 오타가 boston 방향 전환에서 실제로 멈추게 하는가
        - 2-3 : 플래시백 OFF 인 옛 Primary 의 REINSTATE 오류 번호, 재구축 뒤 ADD/ENABLE 결과
        - 3-1 : SYNC WITH PRIMARY 의 오류 번호
 2-3. 각 과제의 실제 소요 시간을 잰다. 시간 제한(90/120/60분)이 리허설 시간의 2배를 넘지 않게
      필요하면 문제지의 시간을 조정한다.

================================================================================
 3. 감독관 — 시험 당일
================================================================================
 3-1. 각 시나리오 시작 전 : 두 VM 이 exam-base 에서 막 올라온 상태인지 확인
        [oracle@chicago-srv ~]$ cat /exam/pub/baseline.txt
        DGMGRL> SHOW CONFIGURATION;    → SUCCESS
 3-2. 시간은 첫 장애 주입 시각부터 센다. 시나리오 시간 안에 세 과제를 모두 한다.
 3-3. 금지 사항 고지
        - examadm 계정·sudo 규칙을 우회하거나 스크립트 내용을 보려는 시도 (자동 불합격)
        - 지시하지 않은 exam_break 스크립트 실행 (자동 불합격)
        - VM 스냅샷 조작 (자동 불합격)
        - /exam/pub 의 파일 수정, system.exam_log 의 행 수정·삭제
 3-4. 허용 : 교안·실습 파일 열람, Oracle 문서, 메모. 다른 응시자와의 대화는 금지.

================================================================================
 4. 응시자 — 진행 방식
================================================================================
 4-0. 시작 전
        장애 주입은 sudo 로 한다 (비밀번호를 묻지 않는다)
          [oracle@chicago-srv ~]$ sudo -u examadm /home/examadm/exam/exam_break1.sh 1
        답안 파일 : /home/oracle/answer_S<시나리오>_<이름>.txt  (평문, 과제 번호 순서)
        터미널 기록 : script -a /home/oracle/answer_S<시나리오>_<이름>.log  — 명령 전문의 근거

 4-1. 각 과제의 네 걸음
        ① 주입    sudo -u examadm .../exam_breakN.sh <과제> — 출력(특히 SHOW CONFIGURATION)을 답안에 붙인다
        ② 판정    흐름 세 질문 → 층을 내려가며 원인 확정. 근거를 먼저 적는다
        ③ 수행    명령 전문. 되돌릴 수 없는 명령 전에는 근거를 한 번 더 적는다
        ④ 검증    15장 주 지표 + 해당 step 행 + Broker. 손실 보고

 4-2. 다음 과제 주입이 "중단" 을 내면
        - Broker 구성이 SUCCESS 가 아니다 → 앞 과제를 끝낸다
        - 방금 고쳤다면 판정 시차일 수 있다 → 1분 뒤 다시 실행
        - 시나리오 2 에서 "Primary 가 기대와 다르다" → 2-1 의 Switchover 가 끝나지 않았다

 4-3. 막혔을 때 — 감독관에게 "구제" 를 요청할 수 있다. 감독관이 그 과제를 정리해 주고
      그 과제는 0점, 다음 과제부터 정상 채점한다. 시나리오당 1회.

================================================================================
 5. 감독관 — 시나리오 사이
================================================================================
 5-1. 답안 파일과 script 로그를 수거한다. business.log 도 함께 복사한다 (손실 보고 채점용).
        [examadm@chicago-srv ~]$ cp /exam/pub/business.log ~/collect/business_S<n>_<이름>.log
      시나리오 1 이면 /home/examadm/exam/state/s13_deleted 도 복사한다 (1-3 의 시퀀스 대조).
      collect 디렉터리는 examadm 홈에 두므로 VM 스냅샷 복원과 함께 사라진다.
      반드시 스냅샷 복원 전에 감독관 PC 로 옮긴다.
 5-2. 두 VM 을 exam-base 로 되돌린다 (응시자 성공·실패와 무관하게).
        vmrun revertToSnapshot <boston.vmx> exam-base
        vmrun revertToSnapshot <chicago.vmx> exam-base
        두 VM 전원 켜기 → chicago STARTUP → boston STARTUP
 5-3. 3-1 처럼 SUCCESS 와 baseline.txt 를 확인한다.
      스냅샷에 /exam/pub/business.log 가 비어 있는 상태로 담겨 있으므로 기록은 시나리오마다 새로 시작된다.

 구제 절차 (4-3) — 감독관 메모
   1-1 : 모범답안 1-1.6 수행
   1-2 : [examadm@chicago-srv ~]$ scp ~/exam/proctor/orapwboston oracle@boston-srv:<ORACLE_HOME>/dbs/orapwboston
         + TRANSPORT-OFF/ON
   1-3 : 시간이 부족하면 스냅샷 복원 후 시나리오 1 종료
   2-1 : LogShipping ON, 리스너 오타 수정, SWITCHOVER TO boston
   2-2 : chicago STARTUP MOUNT, FAILOVER TO chicago
   2-3 : 스냅샷 복원 후 시나리오 2 종료
   3-1 : DelayMins 0                    3-2 : boston lsnrctl start + TRANSPORT-OFF/ON
   3-3 : CONVERT DATABASE 'boston' TO PHYSICAL STANDBY

================================================================================
 6. 감독관 — 채점
================================================================================
 6-1. 모범답안의 【판정】【수행】【검증】 세 축으로 채점한다. 과제별 배점은 문제지.
      한 과제 안에서 판정 40% · 수행 30% · 검증(손실 보고 포함) 30% 를 기준으로 나눈다.
 6-2. 공통 감점 기준과 자동 불합격은 문제지 끝을 따른다.
 6-3. 손실 보고 대조
        시나리오 2 의 2-2 : business.log 의 S2-2b·c·d 와 응시자 보고를 대조. 시각 오차 ±1분 허용.
        손실 없는 과제에서 "손실 없음" 과 근거(마지막 step)가 없으면 검증 점수의 절반을 깎는다.
 6-4. 1-3 대조 : state/s13_deleted 의 두 시퀀스와 응시자가 특정한 갭 범위가 같아야 한다.
 6-5. 결과 기록 : 시나리오별 점수, 70점 미만 시나리오는 재응시 대상.
