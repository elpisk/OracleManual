--------------------------------------------------------------------------------
 [1] 왜 정적 등록이 필수인가
--------------------------------------------------------------------------------

-- 3장에서 Standby 를 만들 때 정적 등록이 필요했다.
-- 이유는 NOMOUNT 상태에서는 인스턴스가 리스너에 스스로 등록할 수 없기 때문이었다.
-- DUPLICATE 가 끝나 열리고 나면 동적 등록으로 넘어갔다.
--
-- ★ Far Sync 는 MOUNTED 를 벗어나지 않는다. 열리는 시점 자체가 없다.
--
--   그래서 처음에는 "동적 등록이 아예 안 되겠구나" 라고 짐작하기 쉽다.
--   실제로 확인해 보면 그렇지 않다. [2] 에서 실측한다.
--
-- ★ 그럼에도 정적 등록을 하는 이유는 따로 있다.
--
--   ① 기동 직후 — 인스턴스가 아직 등록하기 전 구간이 있다
--   ② 재기동 중 — 13장의 Broker 는 인스턴스를 내렸다 올린다.
--      내려가 있는 동안 동적 등록은 사라진다
--   ③ 원격 기동 — 내려가 있는 인스턴스에 붙어 STARTUP 하려면
--      리스너가 그 SID 를 알고 있어야 한다
--
--   ②③ 때문에 Data Guard 구성에서는 정적 등록을 표준으로 삼는다.

--------------------------------------------------------------------------------
 [2] listener.ora
--------------------------------------------------------------------------------

[oracle@farsync-srv ~]$ cat $ORACLE_HOME/network/admin/listener.ora
LISTENER =
  (DESCRIPTION_LIST =
    (DESCRIPTION =
      (ADDRESS = (PROTOCOL = TCP)(HOST = farsync-srv)(PORT = 1521))
    )
  )

SID_LIST_LISTENER =
  (SID_LIST =
    (SID_DESC =
      (GLOBAL_DBNAME = farsync)
      (ORACLE_HOME = /u01/app/oracle/product/19.3.0/dbhome_1)
      (SID_NAME = farsync)
    )
    (SID_DESC =
      (GLOBAL_DBNAME = farsync_DGMGRL)
      (ORACLE_HOME = /u01/app/oracle/product/19.3.0/dbhome_1)
      (SID_NAME = farsync)
    )
  )

-- ★ SID_DESC 가 두 개다.
--
--   farsync         일반 접속용. Primary 가 리두를 보낼 때 쓴다
--   farsync_DGMGRL  Broker 전용. 13장에서 쓴다
--
--   Broker 는 인스턴스를 재기동할 수 있어야 하는데, 재기동 중에는
--   동적 등록이 없으므로 별도의 정적 서비스가 필요하다.
--   지금 미리 넣어 두면 13장에서 다시 손대지 않아도 된다.

[oracle@farsync-srv ~]$ lsnrctl start

Starting /u01/app/oracle/product/19.3.0/dbhome_1/bin/tnslsnr: please wait...

Services Summary...
Service "farsync" has 1 instance(s).
  Instance "farsync", status UNKNOWN, has 1 handler(s) for this service...
Service "farsync_DGMGRL" has 1 instance(s).
  Instance "farsync", status UNKNOWN, has 1 handler(s) for this service...
The command completed successfully

-- ★ status UNKNOWN 이다.
--
--   3장에서 배운 대로 정적 등록의 표식이다.
--   리스너는 "이런 서비스가 있다고 들었지만 확인은 못 했다" 는 뜻으로
--   UNKNOWN 을 표시한다.

-- ★ 그런데 잠시 뒤 다시 보면 달라져 있다.

[oracle@farsync-srv ~]$ lsnrctl status | tail -8

Services Summary...
Service "farsync" has 2 instance(s).
  Instance "farsync", status UNKNOWN, has 1 handler(s) for this service...
  Instance "farsync", status READY, has 1 handler(s) for this service...
Service "farsync_DGMGRL" has 1 instance(s).
  Instance "farsync", status UNKNOWN, has 1 handler(s) for this service...
The command completed successfully

-- ★ farsync 서비스에 인스턴스가 둘로 보인다. 실제로는 하나다.
--
--   UNKNOWN  listener.ora 의 정적 등록
--   READY    인스턴스가 스스로 등록한 동적 등록
--
--   같은 인스턴스가 두 경로로 등록되어 두 줄로 보이는 것이다.
--
-- ★ 여기서 예상이 하나 깨진다.
--   "Far Sync 는 딕셔너리가 없으니 동적 등록도 안 될 것" 이라고
--   짐작하기 쉬운데, 실측은 READY 를 보여 준다.
--
--   서비스 등록에 딕셔너리가 필요하지는 않기 때문이다.
--   PMON 은 SERVICE_NAMES 값(기본값은 DB_UNIQUE_NAME)을 리스너에 알린다.
--   그 값은 파라미터에서 오지 딕셔너리에서 오지 않는다.
--
-- ★ farsync_DGMGRL 은 UNKNOWN 하나뿐이다.
--   이것은 인스턴스가 알리는 이름이 아니라 우리가 listener.ora 에
--   적어 넣은 이름이므로 정적 등록만 존재한다.
--   13장의 Broker 가 이 이름을 쓴다.

 [3] tnsnames.ora — 세 노드 모두에
--------------------------------------------------------------------------------

-- ★ 세 노드 전부에 FARSYNC 별칭을 추가해야 한다.
--
--   chicago  리두를 보내야 한다
--   boston   실습 07 의 계단식 구성에서 보낼 수 있어야 한다
--   farsync  자기 자신과 boston 을 알아야 한다

[oracle@chicago-srv ~]$ tail -8 $ORACLE_HOME/network/admin/tnsnames.ora
FARSYNC =
  (DESCRIPTION =
    (ADDRESS = (PROTOCOL = TCP)(HOST = farsync-srv)(PORT = 1521))
    (CONNECT_DATA =
      (SERVER = DEDICATED)
      (SERVICE_NAME = farsync)
    )
  )

-- ★ SERVICE_NAME = farsync 는 listener.ora 의 GLOBAL_DBNAME 과 같아야 한다.
--   3장에서 boston 별칭을 만들 때와 같은 규칙이다.

--------------------------------------------------------------------------------
 [6] 정리
--------------------------------------------------------------------------------

-- ★ 이 실습에서 확인한 것
--
--   ① Far Sync 도 동적 등록이 된다 (status READY 를 실측했다)
--   ② 그래도 정적 등록을 한다 — 기동 직후·재기동 중·원격 기동 때문
--   ③ 같은 인스턴스가 UNKNOWN 과 READY 두 줄로 보인다
--   ④ farsync_DGMGRL 은 정적 등록만 존재한다 (13장 대비)
--   ⑤ 별칭은 세 노드 모두에 있어야 한다
--   ⑥ 이름 해석 실패는 tnsping 이 TNS-03505 로 알려 준다
--   ⑦ SYSDBA 원격 접속이 되어야 리두 전송이 가능하다
--
-- ★ 이제 배선을 바꾼다. 다음 실습에서 리두 경로를 Far Sync 로 돌린다.
