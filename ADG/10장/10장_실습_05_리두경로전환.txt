 대상   : chicago-srv, farsync-srv, boston-srv
 목표   : Primary 의 목적지를 Far Sync 로 바꾸고 세 노드에서 리두 흐름을
          추적한다. 구성 변경의 순서를 지키지 않으면 무엇이 생기는지 본다
 소요   : 약 40분
 변경   : log_archive_dest_2, log_archive_config (실습 07 에서 원복)

 [2] 순서를 지키지 않으면 — ORA-16057
--------------------------------------------------------------------------------

-- 두 가지를 바꿔야 한다.
--
--   ① 세 노드의 log_archive_config 에 farsync 를 추가
--   ② chicago 의 log_archive_dest_2 를 farsync 로 변경
--
-- 순서가 있다. 받는 쪽을 먼저 열고 보내는 쪽을 나중에 바꾼다.
-- 실습에서는 ②를 먼저 하고 ①을 마무리하는 사이에 다음이 나타났다.

SYS@chicago> ALTER SYSTEM SET log_archive_config='dg_config=(chicago,boston,farsync)' SCOPE=BOTH;

System altered.

SYS@chicago> ALTER SYSTEM SET log_archive_dest_2=
  2    'service=farsync sync affirm valid_for=(online_logfile,primary_role)
  3     db_unique_name=farsync' SCOPE=BOTH;

System altered.

SYS@chicago> ALTER SYSTEM ARCHIVE LOG CURRENT;

System altered.

-- 잠시 뒤 farsync 에서 전달 상태를 본다.

SYS@farsync> COL destination FOR a34
SYS@farsync> COL error FOR a30

>>> 원인 파악

-- ORA-16057 은 "받는 쪽이 나를 구성원으로 인정하지 않는다" 는 뜻이다.
--
-- boston 의 log_archive_config 에 farsync 가 들어 있어야
-- boston 이 farsync 의 접속을 받아들인다.
--
-- ★ 오류가 나는 쪽(farsync)과 원인이 있는 쪽(boston)이 다르다.
--   이것이 이 오류를 헷갈리게 만드는 점이다.
--   메시지의 "server" 는 보내는 쪽인 나 자신을 가리킨다.

SYS@boston> COL value FOR a40
SYS@boston> SELECT name, value FROM v$parameter WHERE name='log_archive_config';

NAME                     VALUE
------------------------ ----------------------------------------
log_archive_config       dg_config=(chicago,boston,farsync)

1 row selected.

-- ★ 그런데 지금은 들어 있다.
--   설정 명령이 이미 나갔고, farsync 가 그 직전에 접속을 시도했던 것이다.
--   즉 설정 자체가 아니라 시점의 문제였다.

>>> 조치

-- 설정이 이미 반영되었으므로 재시도만 하면 된다.
-- 자동 재시도를 기다리거나 목적지를 껐다 켠다.

SYS@farsync> ALTER SYSTEM SET log_archive_dest_state_2='DEFER' SCOPE=MEMORY;
SYS@farsync> ALTER SYSTEM SET log_archive_dest_state_2='ENABLE' SCOPE=MEMORY;

>>> 재확인

SYS@farsync> SELECT dest_id, destination, status, error
  2            FROM v$archive_dest_status WHERE dest_id<=2;

   DEST_ID DESTINATION                        STATUS    ERROR
---------- ---------------------------------- --------- ------------------------------
         1 /u01/app/oracle/fast_recovery_area VALID
           /FARSYNC

         2 boston                             VALID

2 rows selected.

-- ★ 교훈은 순서다.
--
--   ① 받는 쪽의 log_archive_config 를 먼저 넓힌다 (boston, farsync)
--   ② 그 다음 보내는 쪽의 log_archive_dest_n 을 바꾼다 (chicago)
--
--   반대로 하면 보내는 쪽이 먼저 문을 두드리고
--   받는 쪽은 아직 명단을 갱신하지 않은 상태가 된다.
--
-- ★ 7장의 교훈도 함께 기억한다.
--   목적지의 오류 상태는 원인이 사라져도 남아 있을 수 있다.
--   DEFER → ENABLE 이 가장 확실한 초기화 방법이다.

--------------------------------------------------------------------------------
 [3] 오류 재현 — 전송 방식은 어느 뷰에 있는가
--------------------------------------------------------------------------------

-- 전송이 정말 동기인지 확인하려고 조회했다.

SYS@chicago> SELECT dest_id, transmit_mode FROM v$archive_dest_status WHERE dest_id=2;

select dest_id, transmit_mode from v$archive_dest_status where dest_id=2
                *
ERROR at line 1:
ORA-00904: "TRANSMIT_MODE": invalid identifier

>>> 원인 파악

-- 뷰를 잘못 골랐다. TRANSMIT_MODE 는 V$ARCHIVE_DEST 에 있다.
--
-- ★ 두 뷰의 역할이 다르다.
--
--   V$ARCHIVE_DEST         목적지의 "설정"
--                          TRANSMIT_MODE, AFFIRM, BINDING,
--                          VALID_NOW, VALID_ROLE, VALID_TYPE
--
--   V$ARCHIVE_DEST_STATUS  목적지의 "상태"
--                          STATUS, ERROR, RECOVERY_MODE,
--                          APPLIED_SEQ#, DESTINATION
--
-- 8장에서 V$LOG 에 TYPE 이 없어 만난 ORA-00904 와 같은 종류의 혼동이다.

>>> 조치

SYS@chicago> COL destination FOR a10
SYS@chicago> SELECT dest_id, destination, transmit_mode, affirm, valid_now
  2            FROM v$archive_dest WHERE dest_id<=2;

>>> 재확인

   DEST_ID DESTINATIO TRANSMIT_MOD AFF VALID_NOW
---------- ---------- ------------ --- ----------------
         1 USE_DB_REC SYNCHRONOUS  NO  YES
           OVERY_FILE
           _DEST

         2 farsync    PARALLELSYNC YES YES

2 rows selected.

-- ★ 2번 목적지가 PARALLELSYNC / AFFIRM=YES 다.
--   동기 전송이 실제로 걸려 있다는 확인이다.
--
-- ★ 1번이 SYNCHRONOUS 인 것은 성격이 다르다.
--   로컬 아카이브는 네트워크를 타지 않으므로
--   여기서 말하는 동기 전송과는 다른 의미다.
--
-- ★ PARALLELSYNC 는 "여러 목적지에 병렬로 보내며 기다린다" 는 뜻이다.
--   목적지가 하나뿐인 지금은 체감 차이가 없다.

--------------------------------------------------------------------------------
 [5] 정리
--------------------------------------------------------------------------------

-- ★ 이 실습에서 확인한 것
--
--   ① 구성 변경은 받는 쪽 먼저, 보내는 쪽 나중에
--   ② 순서를 어기면 ORA-16057 (오류 나는 쪽과 원인 있는 쪽이 다르다)
--   ③ DEFER → ENABLE 로 목적지 상태를 초기화한다
--   ④ TRANSMIT_MODE·AFFIRM 은 V$ARCHIVE_DEST 에 있다 (없는 뷰에서 찾으면 ORA-00904)
--   ⑤ 실측 TRANSMIT_MODE=PARALLELSYNC, AFFIRM=YES
--   ⑥ Far Sync 도 RFS·SRL·아카이브를 갖는다. 진단 방법은 Standby 와 같다
--   ⑦ 경로가 하나 늘어도 boston 의 지연은 0 이다
--
-- ★ 이제 동기 전송이 걸려 있다. 보호 모드를 올릴 수 있다.
