# 1. 제품 비전

## 1.1 무엇을 만드는가

ADMIN 과정이 기능을 순서대로 가르쳤다면 이 과정은 장애에서 출발한다. 매 시간이 장애 티켓 한 장으로 시작하고, 수강생은 진단·원인 특정·조치·재발 방지·보고까지 끝내야 그 시간을 마친다.

| 항목 | ADMIN | ADMIN_심화 |
|---|---|---|
| 출발점 | 기능 (테이블스페이스를 만든다) | 증상 (03시 배치가 ORA-01653 으로 죽었다) |
| 수강생이 하는 일 | 따라 친다 | 진단하고 고치고 보고한다 |
| 정답 | 명령어 | 근거 — 어떤 뷰·로그·OS 명령으로 무엇을 확인했는가 |
| 단위 | 장 (34개) | 케이스 (24개 + 종합 3개) |

## 1.2 이 과정이 노리는 사람

현업 DBA·DBE 3~5년차. 에러 메시지를 검색하면 해결책 첫 줄이 나오는 문제는 이미 풀 수 있는 사람이다. 이들이 막히는 곳은 다음과 같다.

- 처음 보이는 증상이 원인을 가리키지 않을 때
- 재기동·비밀번호 변경·데이터 삭제가 막힌 상태에서 조치해야 할 때
- 증상은 사라졌는데 같은 장애가 다음 주에 또 날 때
- 조치는 했는데 무엇을 근거로 그렇게 판단했는지 보고서에 쓰지 못할 때

## 1.3 케이스 채택 기준 — 3~5년차 조건

모든 케이스는 아래 셋 중 **둘 이상**을 갖춰야 한다. 케이스 카드마다 어느 조건을 갖췄는지 표시한다.

| 조건 | 뜻 | 예 |
|---|---|---|
| 오진 유도 | 처음 보이는 증상이 실제 원인과 다른 곳을 가리킨다 | 네트워크 오류처럼 보이지만 원인은 DB 안에 있다 |
| 운영 제약 | 가장 쉬운 조치가 막혀 있다 | 재기동 금지, 비밀번호 변경 금지, 감사 기록 삭제 금지 |
| 복합 원인 | 조치 하나로 증상은 사라지지만 근본 원인이 남는다 | 오류는 사라졌지만 그 오류를 미리 알리지 못한 점검 절차가 그대로다 |

"에러 번호를 검색하면 끝나는 문제"는 채택하지 않는다.

# 2. 범위

## 2.1 원칙

장애의 **원인**이 ADMIN 과정이 다룬 영역(인스턴스, 네트워크, 멀티테넌트, 저장공간, 언두, 계정·보안, 데이터 이동, 자동 유지관리)에 있는 것만 다룬다. 다른 과목 영역은 단서로만 등장한다.

| 영역 | 다루는 곳 |
|---|---|
| 백업·복구 (RMAN 복원, 미디어 복구) | BACKUP&RECOVERY 심화 |
| SQL 튜닝, 대기 이벤트 심층 분석 | DBTUNING 심화 |
| RAC, Data Guard | RAC·ADG 심화 |

## 2.2 경계에 걸친 두 주제 (포함 결정 2026-11-21)

| 주제 | 포함하는 이유 | ADMIN 심화에서 다루는 깊이 |
|---|---|---|
| 아카이브 공간 고갈로 DB 정지 | 실무 장애 빈도 1~2위 | FRA 사용량 판단, 즉시 조치, 백업 정책과의 충돌까지. RMAN 복원은 다루지 않는다 |
| 야간 통계 수집 뒤 실행 계획 변경 | 자동 유지관리 작업(ADMIN 29·30장)이 원인 | 통계 이력 확인과 복원, 수집 설정 고정까지. SQL 튜닝 기법은 다루지 않는다 |

## 4.3 주입·원복 스크립트 규약

- 주입은 `CNN_break.sh`, 원복은 `CNN_reset.sh`. 둘 다 oracle 사용자로 돌고, root 가 필요한 단계는 스크립트 안에서 `sudo` 로 나눈다.
- 주입 스크립트는 흔적을 실제 장애처럼 남긴다. 주입에 쓴 SQL 이 수강생이 볼 수 있는 곳(SQL*Plus 이력, 감사 기록, alert log)에 남으면 안 되는 경우 그 사실을 카드에 적고 지운다. alert log 에 남는 것이 진단 근거인 경우(예: `ALTER SYSTEM ... SCOPE=SPFILE` 기록)는 그대로 둔다.
- 원복 스크립트가 끝나면 `check_baseline.sh` 가 기준 상태를 점검하고, 하나라도 다르면 0 이 아닌 값으로 끝난다.
- 한 케이스의 주입은 다른 케이스의 원복을 전제하지 않는다. 언제나 기준 스냅샷에서 시작할 수 있어야 한다.
- 실측에서는 break → 진단 → 조치 → reset → check_baseline 을 **두 번** 돌려 두 번 모두 같은 증상과 같은 결과가 나와야 채택한다.

## 4.4 문체와 서식

저장소 공통 규칙을 따른다(`제작_가이드.md` 5절, `작업인계_2026-10-31.md` 1절).

- 평서체. 요약·재진술로 끝맺지 않는다
- 볼드 라벨은 경고와 표 머리에만 쓴다
- DB 테이블은 "표"가 아니라 "테이블"이라고 쓴다
- docx 에 마크다운 기호를 글자로 넣지 않는다(규칙 13)
- 오류 메시지와 출력은 실측 그대로 쓴다. 기억이나 문서에서 옮긴 출력은 쓰지 않는다

티켓은 실제 신고처럼 쓴다. 앱팀·운영팀의 말투로, 그들이 아는 만큼만 쓴다. "ORA-00845 가 발생했다"가 아니라 "재기동했는데 DB 가 안 올라옵니다. 화면에 MEMORY 어쩌고 하는 에러가 떴어요"처럼 쓴다.

# 5. 실습 환경 — 심화 전용 스냅샷

## 5.1 결정

기존 ADMIN 실습 VM 을 그대로 쓰지 않고 심화 전용 기준 스냅샷을 새로 만든다(2026-11-21 결정). 스냅샷 제작은 케이스 카드 확정 뒤에 한다.

이유

- 케이스가 요구하는 기준 상태가 기존 ADMIN 실습과 다르다(ARCHIVELOG, 크기를 제한한 파일 시스템, 비CDB 인스턴스, 업무 데이터, 업무별 OS 계정 등)
- 케이스마다 기준 상태로 되돌아갈 수 있어야 하는데, 기존 VM 은 ADMIN 실습의 흔적이 섞여 있다

## 5.2 요구 사항

세부 요구 사항은 주입 방법을 드러내므로 `_강사용/전용스냅샷_요구사항.md` 에 둔다. 공개해도 되는 수준의 개요는 다음과 같다.

| 항목 | 개요 |
|---|---|
| OS | Oracle Linux 7.9, 4 vCPU, 메모리 8GB 이상 |
| DB | Oracle 19c, CDB 1개(PDB 2개 이상) + 이관 소스용 비CDB 1개 |
| 데이터 | 업무 스키마(주문·정산 계열), 수백만 행 규모 |
| 부하 | 온라인 업무·배치를 흉내 내는 부하 스크립트 |
| 스냅샷 | 기준 상태 1개. 모든 케이스는 이 스냅샷에서 시작한다 |

# 6. 공개와 비공개

저장소가 public 이고, 문제 해결형 과정은 원인이 알려지면 과정이 성립하지 않는다. OCM 최종 실기평가(2026-11-13)와 같은 방식으로 원인·해설·실측·주입 스크립트를 저장소에서 뺀다.

| 공개 | 비공개 (`ADMIN_심화/_강사용/`) |
|---|---|
| PRD, README, 과정안내, 장애보고서 양식, 케이스별 티켓과 진단워크북 | 케이스카드, 스냅샷 요구사항, 강사해설, 실측 트랜스크립트, 주입·원복 스크립트, 모듈 리뷰 PPT, 강사운영가이드 |

비공개 자료의 보관처는 미결이다(8장).

# 7. 제작 단계

| 단계 | 내용 | 작업 장소 | 완료 조건 |
|---|---|---|---|
| 0 | PRD, 케이스 카드 27종 | 어디서나 | 카드마다 3~5년차 조건 둘 이상, 재현 방법 후보 명시 |
| 1 | 전용 스냅샷 제작 | 랩 PC | `check_baseline.sh` 통과 |
| 2 | 파일럿 3케이스(C11·C41·C53) | 랩 PC | 4.1 산출물 5종 완성, 실측 2회 일치. 여기서 규격을 고친다 |
| 3 | 양산 (모듈 단위로 커밋) | 랩 PC | 케이스마다 실측 2회 일치 |
| 4 | 블라인드 검증 | 랩 PC | 원인을 모르는 풀이자(에이전트)에게 티켓만 주고 풀게 한다. 50분 안에 풀리는지, 의도하지 않은 다른 원인으로도 증상이 설명되지 않는지 확인 |
| 5 | 종합 케이스·평가·과정 문서 | 랩 PC | Z1~Z3 실측, 과정안내·강사운영가이드 |

파일럿 세 케이스는 성격이 다른 것으로 골랐다. C11 은 인스턴스가 내려간 상태에서의 진단, C41 은 배치 창 안에 끝내야 하는 진단, C53 은 여러 세션이 얽힌 실시간 진단이다.
