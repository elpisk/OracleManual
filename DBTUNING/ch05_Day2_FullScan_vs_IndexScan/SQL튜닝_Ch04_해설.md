# Chapter 4. Full Scan vs Index Scan — 해설

`SQL튜닝_Ch04_문제.md`와 번호가 1:1로 대응합니다.

---

### 1. [상] 결과가 적어도 Buffers가 큰 이유

- Full Scan은 조건을 만족하는 행이 몇 건이든 상관없이 **테이블에 저장된 블록을 처음부터
  끝까지 전부** 읽는다. 조건 검사(filter)는 블록을 다 읽어온 "다음"에 이루어진다.
- CLAIM_DETAILS는 약 90만 건이 저장된 큰 테이블이라 3건만 필요해도 그 90만 건이 담긴
  블록을 전부 읽어야 하고(Buffers 6,621), HOSPITALS는 애초에 1,000건짜리 작은 테이블이라
  800건이 필요해도 전체를 읽는 비용이 15 Buffers에 불과했다.
- 즉 Buffers를 결정하는 것은 "몇 건이 필요한가"가 아니라 "테이블 전체가 얼마나 큰가"다.

### 2. [상] 인덱스가 있어도 안 쓰는 경우

- `PK_MEDICAL_CLAIMS`는 두 조회 모두에서 사용 가능한 인덱스였지만, 838건(0.3%)에서는
  실제로 사용(Index Range Scan)됐고 25,406건(8.5%)에서는 사용되지 않고 Full Scan으로
  전환됐다.
- 이는 옵티마이저가 "인덱스가 존재하는가"가 아니라 "이 조건에서 인덱스를 쓰는 것이 실제로
  더 저렴한가"를 통계정보로 계산해서 판단하기 때문이다. 결과 건수가 늘어나면 인덱스를 통한
  랜덤 접근(행 하나하나 흩어진 위치를 찾아가는 것)이 누적되어, 어느 지점부터는 순차적으로
  다 읽는 Full Scan보다 비싸진다.
- 따라서 "인덱스가 있으니 당연히 그걸 쓸 것"이라는 가정은 틀릴 수 있다 — 항상 실행계획으로
  확인해야 한다.

### 3. [상] Full Scan 비용이 결과 건수와 무관한 이유

- Full Scan은 테이블의 모든 블록을 읽는 작업이므로, 그중 조건에 맞는 행이 몇 건 걸러지는지는
  "다 읽은 뒤"의 문제이지 "얼마나 읽어야 하는가"에는 영향을 주지 않는다.
- 25,406건이든 274,000여건이든 어차피 MEDICAL_CLAIMS 전체(약 30만 건, 3,090블록어치)를
  다 읽어야 하므로 Buffers가 동일하게 나온 것이다.

### 4. [최상] COUNT(*)와 SUM(total_amt)의 차이

- `PK_MEDICAL_CLAIMS` 인덱스에는 `CLAIM_ID` 값만 들어있고 `TOTAL_AMT`는 들어있지 않다.
- `COUNT(*)`는 "행이 존재하는가"만 확인하면 되므로 인덱스만으로 완전히 답할 수 있다
  (Index-Only Access) — 그래서 148,028건(49%)이라는 낮은 선택도에서도 인덱스를 계속
  썼다(Buffers 910).
- `SUM(total_amt)`는 인덱스에 없는 `TOTAL_AMT` 값을 실제로 읽어야 하므로, 인덱스로 찾은
  각 행마다 테이블까지 가서(랜덤 접근) 값을 가져와야 한다. 이 랜덤 접근 비용이 누적되면서
  더 낮은 선택도(약 8.5%)에서부터 이미 Full Scan이 더 싸졌다.
- 결론: 같은 범위 조건이라도 SELECT 절에 어떤 컬럼이 필요한가에 따라 "인덱스가 유리한
  선택도의 경계"가 달라진다.

### 5. [상] 선택도와 카디널리티 계산

- 선택도(selectivity) = 조건을 만족하는 행 수 ÷ 전체 행 수
- 카디널리티(cardinality) = 조건을 만족하는 실제 행의 개수(선택도를 곱해서 구한 값)
- 계산 결과 (전체 300,000건 기준)
  - 838건 → 선택도 838/300,000 ≈ 0.28%
  - 25,406건 → 선택도 25,406/300,000 ≈ 8.5%
  - 148,028건 → 선택도 148,028/300,000 ≈ 49.3%

### 6. [최상] "선택도 10% 규칙"에 대한 반박

- 4번 문항에서 확인했듯, 같은 선택도(예: 49%)라도 `COUNT(*)`(인덱스만으로 처리)는
  인덱스가 유리했고 `SUM(total_amt)`(테이블 접근 필요)는 이미 8.5%에서부터 Full Scan이
  유리했다.
- 즉 "선택도 몇 % 이하면 무조건 인덱스"라는 단일 숫자 규칙은 **SELECT 절에서 어떤 컬럼이
  필요한지(Index-Only 여부)**를 전혀 고려하지 않은 규칙이라 실제로는 틀리는 경우가 많다.
  같은 컬럼·같은 범위 조건이라도 조회하는 컬럼이 바뀌면 최적 접근 방식의 경계도 바뀐다.

### 7. [상] 이미 저렴한 쿼리에 인덱스를 추가하는 것의 의미

- HOSPITALS Full Scan은 이미 Buffers 15로 매우 저렴하다. 인덱스를 추가로 만들면,
  조회 시 "인덱스 블록에 접근 → 조건에 맞는 ROWID 확보 → 테이블 블록에 접근"이라는 최소
  2단계 접근이 필요해진다.
- 조건에 800건이나 걸리는 상황(선택도가 매우 높음, 80%)이라면 인덱스를 쓰더라도 800번의
  개별 테이블 접근이 필요해 오히려 Full Scan(Buffers 15)보다 비쌀 가능성이 크다.
- 결론: 이미 충분히 저렴한 작은 테이블에 무조건 인덱스를 추가하는 것은 이득이 없거나
  오히려 손해일 수 있다 — "인덱스는 무조건 도움이 된다"는 가정은 틀렸다.

### 8. [상] 교차점이 고정된 숫자가 아닌 이유

- Full Scan 비용은 테이블 크기(총 블록 수)에 좌우되고, Index Scan 비용은 결과 건수·
  Index-Only 여부·클러스터링 팩터(인덱스 순서와 실제 테이블 저장 순서가 얼마나 일치하는가)
  에 좌우된다.
- 이 요소들이 테이블마다, 쿼리마다, 심지어 같은 쿼리라도 SELECT 절이 바뀌면(4번 문항)
  달라지므로, "몇 % 이하면 인덱스"라는 보편적 숫자는 존재하지 않는다. 옵티마이저가 매번
  통계정보를 근거로 계산하는 이유가 여기 있다.

### 9. [최상] REVIEW_LOG 사례 적용 (원칙 적용 훈련)

- REVIEW_LOG는 50만 건으로 HOSPITALS(1,000건, Full Scan이 항상 저렴)보다는 훨씬 크고,
  CLAIM_DETAILS(약 90만 건)와 비슷한 규모다.
- `REVIEWER_ID='SYSTEM'`인 행이 전체의 약 40%로 추정되며, 이는 이번 챕터에서 관찰한
  "Full Scan으로 전환되는 선택도"(8.5%~) 기준을 훨씬 웃도는 매우 높은 선택도다.
- 인덱스가 없는 상태이기도 하고, 설령 인덱스가 있었더라도 이렇게 선택도가 높으면
  옵티마이저가 Full Scan을 선택할 가능성이 크다. 즉 이 조회는 `TABLE ACCESS FULL`로
  처리될 것으로 예상하는 것이 합리적이다.

### 10. [최상] "Full Scan이 유리한 상황" 정의 (모범 답안 예시)

- 조건 1(테이블 크기): 테이블 자체의 총 블록 수가 작아서, 인덱스를 거치는 추가 단계
  (인덱스 접근 + 테이블 접근)의 오버헤드가 전체를 읽는 비용보다 오히려 클 때(7번 문항의
  HOSPITALS 사례)
- 조건 2(선택도): 조건을 만족하는 행의 비율이 높아서(이번 챕터 기준 약 8~10% 이상),
  인덱스를 통한 랜덤 접근이 누적되는 비용이 순차적 Full Scan 비용을 넘어설 때
- 예외: 조건 2를 만족하더라도(선택도가 높더라도) 쿼리가 인덱스에 포함된 컬럼만 필요로
  한다면(Index-Only Access) 여전히 인덱스가 유리할 수 있다(4번 문항) — 두 조건은
  독립적으로 작용하지 않고 "필요한 컬럼이 인덱스 안에 있는가"라는 세 번째 변수와 함께
  고려해야 한다.
