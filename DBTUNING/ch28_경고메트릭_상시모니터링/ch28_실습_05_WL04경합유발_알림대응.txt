================================================================================
 12장 실습 05 — WL_04_lock 경합 유발 → 알림 대응 절차 ★
 목표: WL_04_lock.sql로 잠금 경합을 유발해 활성 세션·대기가 치솟는 상황을 만들고,
       알림이 울렸을 때 '무엇부터 보는가'의 대응 절차(증상→원인)를 손에 익힌다.
 환경: non-CDB=orcl 19.3 (SYS AS SYSDBA로 관찰, SQLT 세션으로 부하 유발)
 라이선스: V$ 조회·알림은 기본 기능(라이선스 무관).
 주의: 개인 실습 환경 전용. 부하 유발이 포함된다. 마지막에 반드시 원복한다.
       원본 REVIEW_LOG 은 건드리지 않는다 — WL_04 가 복제본 REVIEW_LOG_WL 에서만 갱신한다.
================================================================================

--------------------------------------------------------------------------------
-- [0] (부하 유발) 두 개의 SQLT 세션으로 같은 행을 두고 잠금 경합을 만든다.
--     WL_04_lock.sql 의 역할(role)로 블로커(A)와 대기자(B)를 띄운다.
--     세션 A: 한 행을 UPDATE 하고 커밋하지 않은 채 wl_hold_sec 초 대기(블로커).
--     세션 B: 같은 행을 UPDATE 하려다 enq: TX 대기에 걸린다(대기자).
--------------------------------------------------------------------------------
-- [준비, 세션 A 터미널에서 1회] 복제 표 생성
$ sqlplus sqlt/sqlt@orcl
SQLT@orcl> DEFINE wl_role = SETUP
SQLT@orcl> @WL_04_lock.sql
-- (REVIEW_LOG_WL 복제본이 만들어진다)

-- [세션 A = 블로커] 같은 터미널에서 이어서
SQLT@orcl> DEFINE wl_role = A
SQLT@orcl> DEFINE wl_hold_sec = 60
SQLT@orcl> @WL_04_lock.sql
[세션 A] 나의 SID = <환경값> , SERIAL# = <환경값>
[세션 A] UPDATE 1 행 완료. 커밋하지 않는다 (TX 잠금 보유 중).
[세션 A] 60 초 동안 잠금을 유지한다...
-- (여기서 60초 멈춘 것처럼 보인다. 행 잠금을 쥐고 있다.)

-- [세션 B = 대기자, 다른 터미널]
$ sqlplus sqlt/sqlt@orcl
SQLT@orcl> DEFINE wl_role = B
SQLT@orcl> @WL_04_lock.sql
[세션 B] 나의 SID = <환경값>
[세션 B] 세션 A가 같은 행을 잡고 있으면 여기서 멈춘다.
-- (응답 없이 대기 — enq: TX - row lock contention)

--------------------------------------------------------------------------------
-- 이하 [1]~[6]은 관찰용 SYS 세션에서 수행한다.
--------------------------------------------------------------------------------
$ sqlplus / as sysdba
SYS@orcl> SET LINESIZE 200

--------------------------------------------------------------------------------
-- [1] (이상 징후 감지 → 대응 1단계) 알림/미해소 알림부터 확인한다.
--     주의: 잠금 대기 자체에 대한 서버 생성 알림은 '그 메트릭에 임계값을 걸어 둔
--     경우에만' 뜬다(기본은 임계값 없음 → no rows). 이 랩은 임계값을 걸지 않았으므로,
--     알림에 의존하지 말고 곧바로 V$ 뷰로 증상을 좁혀 간다.
--------------------------------------------------------------------------------
SYS@orcl> SELECT reason, message_level,
  2         TO_CHAR(creation_time,'HH24:MI') created
  3       FROM  dba_outstanding_alerts
  4       WHERE reason LIKE '%Lock%' OR reason LIKE '%session%'
  5          OR reason LIKE '%Wait%';

no rows selected

-- 해석: 임계값을 걸지 않았으니 잠금 관련 미해소 알림은 없다(정상). 알림이 없다고
--   문제가 없는 게 아니다 — 알림은 '걸어 둔 것만' 울린다. 원칙: 곧바로 SQL부터 보지 말고,
--   전체 부하 → 활성 세션 → 블로커 순으로 위에서 아래로 좁힌다.
--   (참고: 'Average Users Waiting on Locks' 메트릭에 SET_THRESHOLD 로 경고를 걸어 두면,
--    이런 경합이 지속될 때 Stateful 경고 알림이 뜬다. 실습 02/07 의 SET_THRESHOLD 절차.)

--------------------------------------------------------------------------------
-- [2] (대응 2단계) 전체 부하 수준 — 인스턴스 전반인가 국소인가?
--------------------------------------------------------------------------------
SYS@orcl> SELECT metric_name, ROUND(value,2) value
  2       FROM  v$sysmetric
  3       WHERE metric_name IN ('Average Active Sessions',
  4         'Database Wait Time Ratio','Database CPU Time Ratio')
  5         AND intsize_csec BETWEEN 5900 AND 6100
  6       ORDER BY metric_name;

METRIC_NAME               VALUE
------------------------- -------
Average Active Sessions   <환경값>
Database CPU Time Ratio   <환경값>
Database Wait Time Ratio  <환경값>

-- 해석: 부하가 낮은 실습 환경이라 절대치는 작지만, 평시(실습 03의 관찰)와 견주면
--   Wait Time Ratio 비중이 CPU Ratio 쪽보다 눈에 띄게 올라간다. CPU가 아니라 '기다림'이
--   커진 것 = 경합성 문제 신호다. 소수 세션에 국한된 국소 원인일 가능성이 높다.

--------------------------------------------------------------------------------
-- [3] (대응 3단계) 활성 세션을 대기 이벤트로 묶어 병목의 성격을 본다.
--------------------------------------------------------------------------------
SYS@orcl> SELECT NVL(event,'ON CPU') event, COUNT(*) sessions
  2       FROM  v$session
  3       WHERE status='ACTIVE' AND type='USER'
  4         AND sid <> USERENV('SID')
  5       GROUP BY NVL(event,'ON CPU') ORDER BY sessions DESC;

EVENT                                    SESSIONS
---------------------------------------- --------
PL/SQL lock timer                            <환경값>   -- (블로커 A: 부하 스크립트에서 sleep 중)
enq: TX - row lock contention                <환경값>   -- (대기자 B: 행 잠금 대기)

-- 해석: 활성 세션이 'enq: TX - row lock contention'에 잡혀 있다 = 잠금 경합이다.
--   (블로커 A는 WL_04 가 잠금을 유지하려고 DBMS_SESSION.SLEEP 중이라 'PL/SQL lock timer'로
--    보인다 — 실습 재현의 특성이다.) 여기서 SQL 실행계획을 보는 것은 헛수고다. SQL이
--   느린 게 아니라 막혀 있다.

--------------------------------------------------------------------------------
-- [4] (대응 4단계) 대기·블로커 추적 — 누가 누구를 막는가.
--------------------------------------------------------------------------------
SYS@orcl> COLUMN username FORMAT A8
SYS@orcl> COLUMN event FORMAT A32
SYS@orcl> SELECT s.sid, s.username, s.blocking_session, SUBSTR(s.event,1,30) event
  2       FROM  v$session s
  3       WHERE s.blocking_session IS NOT NULL;

  SID USERNAME BLOCKING_SESSION EVENT
----- -------- ---------------- ------------------------------
 <환경값> SQLT        <블로커SID> enq: TX - row lock contention

SYS@orcl> -- 블로커 세션이 무엇을 하고 있는지 확인한다.
SYS@orcl> SELECT sid, username, status, SUBSTR(event,1,28) event, last_call_et
  2       FROM  v$session WHERE sid = <블로커SID>;

  SID USERNAME STATUS   EVENT                     LAST_CALL_ET
----- -------- -------- ------------------------- ------------
 <블로커SID> SQLT   ACTIVE   PL/SQL lock timer            <환경값>

-- 원인 파악: 블로커가 행 잠금을 쥔 채 대기자를 막고 있다. 이 랩에서는 WL_04 가 잠금을
--   유지하려고 잠들어 있어 STATUS=ACTIVE / EVENT='PL/SQL lock timer'로 보인다.
--   ※ 실제 운영의 전형적 블로커는 이와 달리 STATUS=INACTIVE / 'SQL*Net message from client'
--     인 경우가 많다 — 갱신 후 커밋을 잊고 클라이언트 입력만 기다리며 '놀고 있는' 트랜잭션.
--   어느 쪽이든 근본 원인은 같다: 방치된(끝나지 않은) 트랜잭션이 행 잠금을 놓지 않는 것.

--------------------------------------------------------------------------------
-- [5] (조치) 블로커에 커밋·롤백을 유도한다. 응급 시에만 세션을 종료한다.
--------------------------------------------------------------------------------
-- 정상 조치: [세션 A]가 wl_hold_sec 뒤 스크립트 끝에서 자동 ROLLBACK(잠금 해제).
--   즉시 풀려면 세션 A 터미널에서:
SQLT@orcl> COMMIT;   -- 또는 ROLLBACK
Commit complete.

-- 응급 조치(블로커에 접근 불가 시): SYS에서 근거 캡처 후 세션 종료
-- SYS@orcl> ALTER SYSTEM KILL SESSION '<블로커SID>,<serial#>' IMMEDIATE;

--------------------------------------------------------------------------------
-- [6] (대응 6단계 · 재확인) 대기 세션 해소·지표 정상화 확인.
--------------------------------------------------------------------------------
SYS@orcl> SELECT COUNT(*) waiters FROM v$session
  2       WHERE event='enq: TX - row lock contention';

   WAITERS
----------
         0

-- 재확인: 대기 세션 0. 블로커의 트랜잭션이 끝나자(커밋/롤백) 대기가 즉시 풀렸다.
--   (만약 잠금 메트릭에 임계값을 걸어 알림이 떴었다면, 경합이 사라진 뒤 다음 감시
--    주기에 그 Stateful 알림도 자동 해소된다.) 증상(느림)이 아니라 원인(방치된 잠금)을
--   제거해 해결했다.

--------------------------------------------------------------------------------
-- [정리]
--------------------------------------------------------------------------------
-- 1) 알림은 걸어 둔 것만 울린다. 절차: 유형→전체부하→활성세션→블로커→SQL→재확인.
-- 2) Wait Ratio 상승 + enq:TX 몰림 = 잠금 경합. SQL 계획부터 보면 원인이 안 나온다.
-- 3) 블로커는 커밋/롤백 유도로 해소. 세션 종료는 근거 캡처 후 응급 수단.
-- 4) 원인을 제거하면 대기가 풀리고, (임계값을 걸었다면) Stateful 알림도 자동으로 사라진다.

-- (정리) 남은 세션에서 복제 표를 정리한다.
SQLT@orcl> DEFINE wl_role = CLEANUP
SQLT@orcl> @WL_04_lock.sql

SYS@orcl> EXIT
