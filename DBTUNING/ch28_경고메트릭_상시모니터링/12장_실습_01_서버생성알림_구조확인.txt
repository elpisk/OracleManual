================================================================================
 12장 실습 01 — 서버 생성 알림 구조 확인
 목표: 서버 생성 알림의 두 부류(Stateful/Stateless)를 구분하고,
       미해소 알림(DBA_OUTSTANDING_ALERTS)과 이력(DBA_ALERT_HISTORY)을 대조한다.
 환경: non-CDB=orcl 19.3 (SYS AS SYSDBA로 수행, 일부 일반 계정 대조)
 라이선스: 서버 생성 알림·딕셔너리 뷰 조회는 기본 기능(라이선스 무관).
 주의: 개인 실습 환경 전용. 읽기 전용 조회만 수행한다.
       알림 행은 그 환경의 이력·시점에 따라 다르다 — 아래 결과 블록은 형태를 보이는
       대표 예시(예시)이고, 실제 행 수·시각은 각자 환경 값을 따른다.
================================================================================

$ sqlplus / as sysdba

SYS@orcl> SET LINESIZE 200
SYS@orcl> SET PAGESIZE 100

--------------------------------------------------------------------------------
-- [1] (조치 전 상태) 알림 인프라의 주체 확인 — MMON이 살아 있어야 알림이 뜬다.
--------------------------------------------------------------------------------
SYS@orcl> SELECT name, description FROM v$bgprocess
  2       WHERE name = 'MMON';

NAME  DESCRIPTION
----- ----------------------------------------------------------------
MMON  Manageability Monitor Process

-- 해석: MMON이 메트릭을 계산해 임계값 초과 시 ALERT_QUE에 알림을 등록한다.
--   폴링이 아니라 사건 발생 시점의 push 구조다. (단, 테이블스페이스 사용률 같은
--   공간 알림은 MMON의 공간 점검 주기 — 기본 약 10분 — 에 맞춰 뜬다. 실습 04에서 확인.)

--------------------------------------------------------------------------------
-- [2] (조회) 지금 진행 중인 문제 = 미해소 알림. Stateful 알림이 여기 남는다.
--------------------------------------------------------------------------------
SYS@orcl> SELECT reason, message_level,
  2         TO_CHAR(creation_time,'MM-DD HH24:MI') created
  3       FROM  dba_outstanding_alerts
  4       WHERE rownum <= 10;

REASON                                          MESSAGE_LEVEL CREATED
----------------------------------------------- ------------- -----------
Tablespace [TS_ALERT_DEMO] is [100 percent] full            1 <환경값>     -- (예시)

-- 해석: 위는 대표 예시다 — 미해소 알림이 없으면 'no rows selected'가 정상이다.
--   MESSAGE_LEVEL: 1=Critical(위험), 5=Warning(경고). 이 행은 Stateful 알림이라
--   조건이 해소되면(공간 확보) 다음 감시 주기에 자동으로 사라지고 이력으로 넘어간다.
--   (실습 04에서 이 발생→해소 전 과정을 직접 재현한다.)

--------------------------------------------------------------------------------
-- [3] (조회) 지나간 사건 = 알림 이력. Stateless 알림과 해소된 알림이 여기 쌓인다.
--------------------------------------------------------------------------------
SYS@orcl> SELECT SUBSTR(reason,1,44) reason,
  2         TO_CHAR(creation_time,'MM-DD HH24:MI') created
  3       FROM (SELECT reason, creation_time
  4             FROM dba_alert_history ORDER BY creation_time DESC)
  5       WHERE rownum <= 10;

REASON                                       CREATED
-------------------------------------------- -----------
Threshold is updated on metrics "Tablespace  <환경값>     -- (예시: 임계값 변경 사건)
Instance orcl.orcl. up on node oel7v9.locald <환경값>     -- (예시: 기동 이벤트)
Instance orcl.orcl. down on node oel7v9.loca <환경값>     -- (예시: 정지 이벤트)
Operation on resumable session big_load_job  <환경값>     -- (예시: 재개가능 세션 사건)

-- 해석: 위는 대표 예시다. up/down은 인스턴스 기동·정지(Stateless), 'Threshold is updated'는
--   임계값을 바꾼 사건, 'Operation on resumable session'은 재개 가능 세션이 일시중단됐다
--   처리된 Stateless 사건이다. 성능 알림과 운영 이벤트가 섞이므로 reason으로 걸러 읽는다.
--   실제 이력은 각자 환경에서 그동안 일어난 사건으로 채워진다.

--------------------------------------------------------------------------------
-- [4] (이상 징후 → 원인 → 조치 → 재확인)
--     이상 징후: 업무용 일반 계정(SQLT)으로 알림 뷰를 조회하니 계정 구성에 따라
--       되기도(SELECT_CATALOG_ROLE 보유 시) 안 되기도 한다. 권한 경계를 확인한다.
--------------------------------------------------------------------------------
SYS@orcl> CONNECT sqlt/sqlt@orcl
Connected.
SQLT@orcl> -- SQLT는 SELECT_CATALOG_ROLE(기본 롤)을 갖고 있어 DBA_* 조회가 된다.
SQLT@orcl> -- 권한 경계를 드러내려고 이 세션의 롤을 잠시 끈다(SET ROLE NONE).
SQLT@orcl> SET ROLE NONE;

Role set.

SQLT@orcl> SELECT COUNT(*) FROM dba_outstanding_alerts;
SELECT COUNT(*) FROM dba_outstanding_alerts
                     *
ERROR at line 1:
ORA-00942: table or view does not exist

SQLT@orcl> -- 원인 파악: 롤을 끄자 DBA_* 알림 뷰가 안 보인다. 즉 그 접근은
SQLT@orcl> --   업무 계정의 '직접 권한'이 아니라 롤(SELECT_CATALOG_ROLE)로 빌린 것이다.
SQLT@orcl> -- 조치: 모니터링은 권한 있는 계정(SYSDBA 또는 관찰 전용 계정)으로 수행한다.
SQLT@orcl> CONNECT / as sysdba
Connected.
SYS@orcl> SELECT COUNT(*) outstanding FROM dba_outstanding_alerts;

OUTSTANDING
-----------
     <환경값>

-- 재확인: SYSDBA에서는 조회된다. 미해소 알림 건수는 환경·시점에 따라 다르다(<환경값>).
--   ※ 운영에서는 SELECT ANY DICTIONARY 또는 SELECT_CATALOG_ROLE 를 부여한
--     관찰 전용 계정을 별도로 둔다. 업무 계정에 상시로 열어 두지 않는다.

--------------------------------------------------------------------------------
-- [정리]
--------------------------------------------------------------------------------
-- 1) 알림 주체는 MMON, 큐는 ALERT_QUE(push). EM 없이 딕셔너리 뷰로 완전 관리.
-- 2) Stateful = 조건 지속 동안 유지·자동 해소 → DBA_OUTSTANDING_ALERTS.
-- 3) Stateless = 사건, 해소 개념 없음 → DBA_ALERT_HISTORY 직행.
-- 4) 알림 뷰 조회는 기본 기능. 단 권한(직접 권한 또는 롤)이 있어야 한다.

SYS@orcl> EXIT
