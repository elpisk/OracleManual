 11장 실습 05 — 부하 증가 때문인지 성능 저하 때문인지 구분하는 판정 실습
 목표: 이 장의 정수. 구간A(81.8초) 대 구간B(302.0초)의 DB Time 3.7배 차이가
       '느려진 것(성능 저하)'인지 '일이 늘어난 것(부하 증가)'인지, 단위 작업당
       DB Time 으로 나눠 판정한다. '부하 증가를 성능 저하로 오판'하는 함정을
       직접 재현하고 교정한다.
 환경: non-CDB=orcl 19.3 (SYS AS SYSDBA로 수행)
 부하: WL_06_mixed.sql 로 만든 구간A(497→498)/구간B(499→500) 비교 사용.
 주의: 개인 실습 환경 전용. 🔒 DBA_HIST_* 는 Diagnostics Pack 필요(대안 [5]).
================================================================================

$ sqlplus / as sysdba

SYS@orcl> SET LINESIZE 200

--------------------------------------------------------------------------------
-- [1] (조치 전 상태) 두 구간의 DB Time·DB CPU 를 시간 모델 이력에서 확인한다.
--------------------------------------------------------------------------------
SYS@orcl> COLUMN stat_name FORMAT A10

SYS@orcl> SELECT snap_id, stat_name, ROUND(value_delta/1000000,1) sec
  2       FROM (
  3         SELECT snap_id, stat_name,
  4                value - LAG(value) OVER (PARTITION BY stat_name ORDER BY snap_id)
  5                  AS value_delta
  6         FROM  dba_hist_sys_time_model
  7         WHERE stat_name IN ('DB time','DB CPU')
  8       )
  9       WHERE snap_id IN (498,500)
 10       ORDER BY snap_id, stat_name;

   SNAP_ID STAT_NAME         SEC
---------- ---------- ----------
       498 DB CPU           10.4
       498 DB time          14.3
       500 DB CPU           46.2
       500 DB time         116.7

-- 해석: 구간A DB time 14.3초, 구간B 116.7초 → 약 8.2배. CPU 비중은 A 73%, B 40% —
--   B 는 대기(7세션이 같은 공유 풀·같은 표를 두고 겨루는 경합)가 크게 늘었다.

--------------------------------------------------------------------------------
-- [2] (함정 재현) 이상 징후 → "8.7배 느려졌다"는 성급한 보고.
--------------------------------------------------------------------------------
SYS@orcl> -- 신입 DBA: "어제 14.3초 → 오늘 116.7초. 8.2배 느려졌으니 상위 SQL 을
SYS@orcl> --   잡아 실행계획을 손보겠습니다."
SYS@orcl> -- ★ 이 결론은 '분모(처리한 일)'를 보지 않은 오판이다. 교정 절차로 간다.

--------------------------------------------------------------------------------
-- [3] (조회) 분모 = 각 구간이 처리한 '일의 양'(트랜잭션)을 가져온다.
--------------------------------------------------------------------------------
SYS@orcl> COLUMN stat_name FORMAT A14

SYS@orcl> SELECT snap_id, stat_name, value_delta txns
  2       FROM (
  3         SELECT snap_id, stat_name,
  4                value - LAG(value) OVER (PARTITION BY stat_name ORDER BY snap_id)
  5                  AS value_delta
  6         FROM  dba_hist_sysstat
  7         WHERE stat_name IN ('user commits','user rollbacks')
  8       )
  9       WHERE snap_id IN (498,500)
 10       ORDER BY snap_id, stat_name;

   SNAP_ID STAT_NAME            TXNS
---------- -------------- ----------
       498 user commits        24137
       498 user rollbacks          0
       500 user commits       168860
       500 user rollbacks          0

-- 해석(Load Profile 실측 대조): 트랜잭션/초 631 → 2,072 이고 구간 길이도 38초 → 81초라
--   총 트랜잭션은 약 2.4만 → 17만, 약 7배다. DB time 은 8.2배인데 트랜잭션은 7배 늘었다.

--------------------------------------------------------------------------------
-- [4] (판정) 단위 작업당 DB Time 으로 나눠 결론을 낸다 — 손으로 나누지 말고 SQL 로.
--------------------------------------------------------------------------------
SYS@orcl> SELECT snap_id, ROUND(dbtime/1e6, 1) dbtime_sec, txns,
  2              ROUND(dbtime / 1000 / NULLIF(txns, 0), 3) ms_per_txn
  3       FROM (
  4         SELECT t.snap_id,
  5                t.value - LAG(t.value) OVER (ORDER BY t.snap_id) dbtime,
  6                s.value - LAG(s.value) OVER (ORDER BY s.snap_id) txns
  7         FROM   dba_hist_sys_time_model t
  8                JOIN dba_hist_sysstat s ON s.snap_id = t.snap_id AND s.dbid = t.dbid
  9         WHERE  t.stat_name = 'DB time' AND s.stat_name = 'user commits'
 10       )
 11       WHERE snap_id IN (498, 500) ORDER BY snap_id;

   SNAP_ID DBTIME_SEC       TXNS MS_PER_TXN
---------- ---------- ---------- ----------
       498       14.3      24137       .593
       500      116.7     168860       .691

-- 판정 절차(요약):
--   ① 총 DB Time 증가율   : 14.3초 → 116.7초  = 8.2배
--   ② 일의 양 증가율       : 트랜잭션 24,137 → 168,860 = 약 7배
--   ③ 단위 작업당 DB Time  : 0.593ms → 0.691ms = 약 1.17배
--   ④ 대기 구조 교차검증   : A 는 CPU 73%, B 는 CPU 40% + 경합 대기(7세션 동시성)
-- => 결론: 8.2배의 대부분(7배)은 '부하(일) 증가'다. 단위 작업당 17% 는 진짜 효율 저하이고,
--    그 몫은 (a) 7세션이 같은 공유 풀·같은 표를 두고 겨룬 경합, (b) 실습 03에서 잡은 회귀
--    SQL(300회 × 8.6ms ≈ 2.6초)로 설명된다. 조치 대상은 이 17% 이지 8.2배 전체가 아니다.
--
-- 교정: [2]의 "상위 SQL 실행계획을 손보겠다"는 8.2배 전체를 성능 저하로 본 과잉 조치다.
--   옳은 순서는 ① 부하 증가분은 용량 계획(CPU 헤드룸)으로, ② 단위 작업당 증가분만 원인
--   (경합·회귀 SQL)을 좁혀 조치한다.
--
-- [반례 확인] 만약 트랜잭션이 그대로인데 DB time 만 8.2배였다면? 그때는 단위
--   작업당 DB time 이 8.2배로 악화된 것이므로 '전부 성능 저하'다(실습 03의 회귀).
--   즉 판정의 갈림길은 '총량 증가율 vs 단위 작업당 증가율'의 비교에 있다.

--------------------------------------------------------------------------------
-- [5] (이상 징후 → 원인 → 조치 → 재확인 / 라이선스 대안)
--     이상 징후: 라이선스가 없어 DBA_HIST 를 못 쓰는데 같은 판정을 요구받았다.
--------------------------------------------------------------------------------
SYS@orcl> -- 원인: DBA_HIST_SYS_TIME_MODEL·DBA_HIST_SYSSTAT 은 🔒.
-- 조치: V$ 를 두 시점에 캡처해 델타로 같은 계산을 한다(라이선스 불필요, 5장 실습 06 의 표 방식).
SYS@orcl> SELECT stat_name, ROUND(value/1000000,1) sec
  2       FROM  v$sys_time_model WHERE stat_name IN ('DB time','DB CPU');   -- t0

STAT_NAME             SEC
-------------- ----------
DB time            3214.8
DB CPU             1264.3

SYS@orcl> COLUMN name FORMAT A14

SYS@orcl> SELECT name, value FROM v$sysstat
  2       WHERE name IN ('user commits','user rollbacks');                  -- t0

NAME                VALUE
-------------- ----------
user commits      1977889
user rollbacks         52

-- ... 부하 구간 경과 후 동일 조회로 t1 획득 → (t1-t0) 델타로 DB time·트랜잭션 계산 ...
-- 재확인: (DB time 델타) ÷ (트랜잭션 델타) 로 단위 작업당 DB time 을 두 구간에서
--   비교한다. 값이 그대로/감소면 부하 증가, 증가면 성능 저하. 판정 원리는 동일하다.

--------------------------------------------------------------------------------
-- [정리]
--------------------------------------------------------------------------------
-- 1) 실측: 구간A 14.3초 vs 구간B 116.7초(8.2배). B 는 CPU 비중이 40% 로 떨어지고 경합 대기가 늘었다.
-- 2) 트랜잭션 약 7배 증가 → 단위 작업당 DB Time 은 0.593ms → 0.691ms(1.17배) → '대부분 부하 증가,
--    일부 효율 저하'로 판정. 조치 대상은 그 17%(경합·회귀 SQL)다.
-- 3) 흔한 실수: 총량 8.2배만 보고 '성능 저하'로 오판해 실행계획을 손대는 과잉 조치.
-- 4) 갈림길: 총량 증가율 vs 단위 작업당 증가율. 후자도 크면 그때가 진짜 성능 저하.
-- 5) 라이선스 없으면 V$ 두 시점 델타로 같은 판정을 재현한다.
-- ※ 🔒 DBA_HIST_* 는 Diagnostics Pack 필요. V$·Statspack 은 라이선스 불필요.

SYS@orcl> EXIT
