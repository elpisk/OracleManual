-- 해석: (a)(b) 는 access — 선두 컬럼 HOSP_ID 로 인덱스 안에서 "찾아갔다". Buffers 3, 12.
--   (c) 는 filter — 인덱스가 HOSP_ID 순으로 정렬돼 있어 RECEIPT_DATE 만으로는 어디서 시작할지 모른다.
--   그래서 인덱스 전체를 훑고(FAST FULL SCAN) 걸러 냈다. 953 은 인덱스 전체 크기다.
--   그래도 표 전체(3,090)보다 싸다 — 인덱스 엔트리가 행보다 작아서다. 하지만 "인덱스를 탔다" 고
--   말하면 안 된다: 조건이 filter 면 인덱스의 정렬을 쓰지 못한 것이다(Ch03 실습 02 의 판독 규칙).

--   ┌─────────────────────────────┬───────────────────────┬─────────┬────────┐
--   │ 조건                        │ Operation             │ Buffers │ A-Rows │
--   ├─────────────────────────────┼───────────────────────┼─────────┼────────┤
--   │ HOSP_ID=1 AND RECEIPT_DATE= │ INDEX RANGE SCAN      │      3  │    11  │
--   │ HOSP_ID=1 (선두만)          │ INDEX RANGE SCAN      │     12  │ 3,058  │
--   │ RECEIPT_DATE= (후행만)      │ INDEX FAST FULL SCAN  │    953  │   789  │
--   └─────────────────────────────┴───────────────────────┴─────────┴────────┘

-- ※ 인덱스 A 는 실습 02 에서 지우고 B 로 바꾼다. 여기서는 그대로 둔 채 EXIT 한다.

-- 1) 복합 인덱스는 선두 컬럼이 조건에 있어야 access(RANGE SCAN)가 된다. 후행 컬럼만이면 filter.
-- 2) 후행 컬럼만의 FAST FULL SCAN(953)은 Full Scan(3,090)보다 싸지만 "인덱스를 탄" 것은 아니다.
-- 3) 인덱스가 만들어졌는지는 CREATE 반복이 아니라 USER_IND_COLUMNS 로 확인한다(ORA-00955).
-- 4) 튜닝 전 3,090 → 후 3. Ch14 실습 03 양식의 "튜닝 후" 열을 이 값으로 채운다.
