# 강사용 — 해답과 운영 안내

> **수강생에게 주지 않는다.** 카드별 정답과 주입 절차가 들어 있다.
> `PF_10_시나리오주입.sql` 의 화면 출력도 같은 이유로 보여 주지 않는다.

---

## 1. 카드와 스크립트 대응

| 카드 | 결함 | 주입 | 접속 |
|---|---|---|---|
| A | 리터럴 SQL 폭주 | `@PF_11_부하패턴.sql A 2000` | SQLT |
| B | 행별 커밋 | `@PF_11_부하패턴.sql PREP -` → `B 10000` | SQLT |
| C | 히스토그램 삭제 | `@PF_10_시나리오주입.sql C INJECT` | SYS |
| D | 표현식 통계 부재 | 기준 상태가 곧 결함. `D INJECT` 로 확인만 | SYS |
| E | 인덱스 부재 | 기준 상태가 곧 결함. `@PF_11 E 200` 으로 드러낸다 | SQLT |
| F | 행 잠금 경쟁 | `@PF_11 BLOCKER 60` (SYS) → `@PF_11 F 60` (SQLT) | 둘 다 |

로 지금 무엇이 걸려 있는지 확인한다.

## 2. 카드별 정답

### 카드 A — 리터럴 SQL 폭주

**원인** 값을 바인드 변수로 넘기지 않아 값마다 다른 SQL 이 된다. 공유 풀에서
찾지 못해 매번 하드 파싱한다.

**근거가 되는 자리** Load Profile 의 Hard parses 가 Parses 에 근접 · Instance
Efficiency 의 Soft Parse % 하락 · SQL ordered by Parse Calls 에 같은 모양이
여러 `SQL_ID` 로 흩어짐 · `TOPSQL` 의 `FORCE_MATCHING_SIGNATURE` 묶음 ·
Top Events 의 `latch: shared pool`, `library cache: mutex X`

**실측 (2026-10-14, 2,000번)** 경과 17.15초 · 세션 누적 하드 파싱 비율 98.6% ·
공유 풀에 남은 커서 1,323개

**정답 조치** 바인드 변수를 쓴다. 코드를 못 고치면 `CURSOR_SHARING=FORCE`.

**반드시 요구할 것** `CURSOR_SHARING=FORCE` 의 부작용. 리터럴이 바인드로
치환되면서 히스토그램을 쓸 수 없게 되고, 쏠린 분포에서 계획이 나빠진다.
카드 C 와 묶어 이야기하면 좋다.

**수강생이 놓치는 곳** 커서가 2,000개 만들어졌는데 1,323개만 남아 있다. 677개가
밀려난 것이고, 그 자체가 공유 풀 압박의 증거다. 여기까지 짚으면 가점.

### 카드 B — 행별 커밋

**원인** 행마다 커밋해 로그 라이터 왕복을 행 수만큼 한다.

**근거가 되는 자리** Top Events 의 `log file sync` · Wait Class 의 Commit ·
Load Profile 의 Transactions · `DELTA` 의 `user commits` 와 `redo synch writes`

**실측 (10,000행)** 1건씩 0.42초 vs 일괄 0.03초 = 14배

**정답 조치** 배치로 묶어 커밋한다.

**반드시 요구할 것** 맞교환. 커밋을 줄이면 잠금을 오래 쥔다. 롤백 세그먼트도
더 쓴다. 그리고 이 랩의 한계.

**이 랩의 한계** 로그 파일이 로컬 디스크라 커밋당 42마이크로초다. `log file sync`
의 절대 시간이 작게 나오고 Top Events 1위가 아닐 수 있다. 수강생이 "1위가 아닌데
어떻게 결론 내나" 로 막히면 두 가지를 짚어 준다. 14배라는 비율, 그리고
`user commits` 델타가 행 수와 같아지는 것. 운영에서 공유 스토리지를 쓰면 커밋당
수 밀리초가 되어 1위가 된다는 점도 함께 설명한다.

### 카드 C — 히스토그램 삭제

**주입**
```sql
@PF_10_시나리오주입.sql C INJECT
```
`DBMS_STATS.DELETE_COLUMN_STATS` 의 `COL_STAT_TYPE => 'HISTOGRAM'` 으로
`MEDICAL_CLAIMS.HOSP_ID` 의 히스토그램만 지운다. 컬럼 통계(NDV·최소·최대)는
남는다. 통계가 아예 없는 것보다 "분포만 모르는" 상태가 찾기 어렵다.

**원인** 히스토그램이 없어 1,000개 병원에 30만 건이 고르게 퍼져 있다고 믿는다.
건당 300건으로 계산한다.

**실측**

| | E-Rows | A-Rows | 오차 |
|---|---|---|---|
| `hosp_id = 1` 단일 표 | 3,506 → 300 | 3,058 | 10.2배 과소 |
| 상세 표 조인까지 | 10,650 → 911 | 9,000 | 9.9배 과소 |

**정답 조치**
```sql
EXEC DBMS_STATS.GATHER_TABLE_STATS('SQLT','MEDICAL_CLAIMS', -
       METHOD_OPT => 'FOR ALL COLUMNS SIZE 1 FOR COLUMNS SIZE 254 HOSP_ID', -
       NO_INVALIDATE => FALSE);
```

**원복** `@PF_10_시나리오주입.sql C UNDO` (위 명령과 같다)

**반드시 요구할 것** 오차가 조인에서 전파되는 것. 단일 표 오차와 조인 후 오차를
둘 다 보여야 한다. 추정이 10배 틀리면 조인 순서와 방식 선택이 함께 틀어진다.

**신고의 단서** "대형 병원은 괜찮고 작은 의원이 느리다" 가 결정적이다. 균등
가정은 큰 값을 과소 추정하고 작은 값을 과대 추정한다. 쏠린 분포라는 신호다.

**수강생이 놓치는 곳** 인덱스를 새로 만들어 해결하려 든다. 그러면 "어제는 왜
빨랐나" 를 설명할 수 없다. 어제와 오늘 사이에 **통계만** 바뀌었다는 점을
`LAST_ANALYZED` 로 짚게 한다.

### 카드 D — 표현식 통계 부재

**주입** 없다. 기준 상태가 곧 결함이다. `D INJECT` 는 확장 통계가 0개인지
확인만 하고, 앞 사람이 만든 것이 남아 있으면 경고한다.

**원인** `TO_CHAR(receipt_date,'YYYYMM') = '202406'` 처럼 컬럼을 가공하면
컬럼 통계를 쓸 수 없다. 기본 선택도 1% 를 끼운다. 30만의 1% = 3,000.

**실측** 전 E-Rows 3,000 vs A-Rows 24,655 (8.2배 과소) · 조치 후 24,655 로
정확히 일치. 만들어진 확장 통계 이름 `SYS_STUX6K8UYPD0XXY_DGWEAYKFE8`

**정답 조치 두 갈래**

조건절을 범위로 바꾸는 쪽이 먼저다.
```sql
WHERE receipt_date >= DATE '2024-06-01' AND receipt_date < DATE '2024-07-01'
```
컬럼을 가공하지 않으니 통계와 인덱스를 다 쓸 수 있다.

쿼리를 못 고치면 표현식 통계를 만든다.
```sql
DECLARE v VARCHAR2(200);
BEGIN
  v := DBMS_STATS.CREATE_EXTENDED_STATS('SQLT','MEDICAL_CLAIMS',
         '(TO_CHAR("RECEIPT_DATE",''YYYYMM''))');
  DBMS_STATS.GATHER_TABLE_STATS('SQLT','MEDICAL_CLAIMS',
    METHOD_OPT => 'FOR ALL COLUMNS SIZE 1 FOR COLUMNS SIZE 254 HOSP_ID '
               || 'FOR COLUMNS SIZE 254 (TO_CHAR("RECEIPT_DATE",''YYYYMM''))',
    NO_INVALIDATE => FALSE);
END;
/
```
만들기만 하면 값이 비어 있다. `METHOD_OPT` 에 그 식을 넣어 다시 수집해야 한다.
이 두 단계를 빠뜨리는 수강생이 많다.

강사가 효과를 미리 확인하려면 `@PF_10_시나리오주입.sql D VERIFY`.

**원복** `@PF_10_시나리오주입.sql D UNDO`

**반드시 요구할 것** 두 조치안의 비교. 범위 조건이 더 나은 이유(통계·인덱스·
파티션 프루닝까지 다 살아난다)와, 표현식 통계가 필요한 상황(쿼리를 고칠 수 없는
패키지 제품 등)을 둘 다 써야 한다.

**함정** 수강생이 함수 기반 인덱스를 제안할 수 있다. 틀린 답은 아니다. 다만
함수 기반 인덱스는 그 식 전용이고 공간을 더 쓴다. 범위 조건으로 고칠 수 있다면
그쪽이 낫다는 판단까지 끌어내면 좋다.

**참고 — 컬럼 그룹은 답이 아니다** `(RECEIPT_DATE, VISIT_DATE)` 컬럼 그룹을
만들어도 범위 조건에는 도움이 되지 않는다. 컬럼 그룹은 등치 조건에만 쓰인다.
그리고 표현식 두 개를 묶으려 하면 `ORA-20001 Column group can contain only
columns separated by comma` 가 난다. 실측에서 확인했다.

### 카드 E — 인덱스 부재

**주입** 없다. `MEDICAL_CLAIMS.PAT_ID` 에 원래 인덱스가 없다.
`@PF_11_부하패턴.sql E 200` 이 그 사실을 드러낸다.

**원인** 조건절에 쓰는 컬럼에 접근 경로가 없어 조회마다 표 전체(3,090 블록)를 읽는다.

**실측**

| | 논리 읽기 | 회당 버퍼 | 경과 |
|---|---|---|---|
| 인덱스 없음 (200번) | 618,004 | 3,090 | 1.16초 |
| 인덱스 있음 (200번) | 602 | 3 | 0.00초 |

| 인덱스 있음 (2,000번) | 6,025 | 3 | 0.01초 |

1,026배다.

구간 지표(2,000번 기준)

| 지표 | 전 | 후 |
|---|---|---|
| DB time | 12.95초 | 1.66초 |
| DB CPU | 12.49초 | 1.19초 |
| 대기 몫 | 3.6% | 28.1% |
| session logical reads | 6,195,158 | 39,362 |
| physical reads | 51 | — |

**정답 조치**
```sql
CREATE INDEX PF_IX_MC_PAT ON medical_claims (pat_id);
```

**반드시 요구할 것** 대기가 조용하다는 사실과 그 의미. 대기 몫 3.6% 는 Top 10
Foreground Events 가 사실상 비어 있다는 뜻이다. "대기가 없으니 정상" 으로
결론 내면 거기서 끝난다. CPU 를 쓰는 문제는 읽은 양에서 드러난다.

**수강생이 놓치는 곳 두 가지**

첫째, 실행 계획의 E-Rows 와 A-Rows 가 **정확히 맞는다**(6 vs 6). 통계가 멀쩡하다.
그래서 "통계 문제" 로 몰고 가면 막힌다. 옵티마이저는 정확히 알고도 전체 스캔을
고른다. 고를 길이 없기 때문이다.

둘째, 대기 몫이 조치 후 3.6% → 28.1% 로 **늘어난다**. 분모가 줄어서 그렇다.
대기 시간 절대값은 0.47초로 비슷하다. 비율만 보고 "조치가 나빠지게 했다" 로
읽는 수강생이 나온다. 분모를 확인하는 습관을 짚어 줄 자리다.

### 카드 F — 행 잠금 경쟁

**주입** 두 세션이 필요하다.
```sql
[SYS]  @PF_11_부하패턴.sql BLOCKER 60
[SQLT] @PF_11_부하패턴.sql F 60
```
`BLOCKER` 는 `PF_WL_T` 의 `id=1` 을 잡고 지정한 초만큼 쥐고 있는 스케줄러
작업을 띄운다. 창은 바로 돌아온다. 끝나면 롤백하고 `AUTO_DROP` 으로 사라진다.

`PF_WL_T` 가 없으면 먼저 `@PF_11_부하패턴.sql PREP -` 를 SQLT 로 돌린다.

**원인** 남이 쥔 행을 기다린다. CPU 도 디스크도 쓰지 않는다.

**실측** 44.18초 대기 · `enq: TX - row lock contention`

**근거가 되는 자리** Top Events 의 해당 이벤트 · Wait Class 의 Application ·
DB Time 은 크게 늘었는데 DB CPU 는 거의 안 늘었다 · ASH 의 `BLOCKING_SESSION`

**정답 조치** 애플리케이션의 트랜잭션 경계를 줄인다. 잠금을 쥔 채 사용자 입력을
기다리는 설계를 고친다. DB 설정으로 풀 문제가 아니라는 판단이 정답의 일부다.

**반드시 요구할 것** AWR 만으로는 부족하고 ASH 가 필요한 이유. AWR 은 "무엇을
기다렸나" 까지만 말한다. "누가 누구를 막았나" 는 ASH 에 있다.

**주의 — `BLOCKING_SESSION` 은 대기 중에만 보인다** 실측에서 이 값이 비어
있었다. 잠금을 얻은 뒤에 조회했기 때문이다. `EVENT` 는 마지막 대기로 남지만
막은 세션은 이미 풀려 NULL 이 된다. 수강생이 "막은 세션이 안 나온다" 로 막히면
이 점을 설명하고 ASH 로 보게 한다.

### 카드 G — 작업 영역 축소

**주입** `@PF_11_부하패턴.sql G 1` 이 `ALTER SESSION` 으로 작업 영역을 64 KB 로
줄인 뒤 같은 집계를 돌린다. 세션 수준이라 접속을 끊으면 사라진다.
`ALTER SYSTEM` 은 쓰지 않는다.

**원인** 정렬·해시 작업 영역이 모자라 임시 테이블스페이스로 넘친다.

**실측 (claim_details 90만 행 → 30만 그룹)**

| | 경과 | 임시 I/O | 메모리 |
|---|---|---|---|
| AUTO | 0.13초 | 없음 | 27M |
| MANUAL 64KB | 1.78초 | 읽기/쓰기 12,627/12,627 블록 | 821K, 임시 37M |

`V$SQL_WORKAREA` : `LAST_MEMORY_USED` 28,385,280 → 840,704 ·
`LAST_TEMPSEG_SIZE` 0 → 38,797,312

**정답 조치** `WORKAREA_SIZE_POLICY=AUTO` 로 두고 `PGA_AGGREGATE_TARGET` 을
적정하게 잡는다. 세션이 임의로 MANUAL 로 바꾸지 못하게 한다.

**원복** 접속 종료로 사라진다. 스크립트도 끝에서 AUTO 로 되돌린다.

**함정 둘 — 둘 다 짚어 줄 것**

첫째, 경과 시간을 믿으면 안 된다. 같은 부하를 다시 돌렸을 때 0.89초 → 1.21초로
차이가 작았다. 버퍼 캐시가 더워지면 시간 차이가 줄어든다. 임시 I/O 12,627 블록은
두 번 다 같았다. 이 카드의 근거는 시간이 아니라 그 숫자다.

둘째, MANUAL 정책에서는 `workarea executions` 통계가 쌓이지 않는다. 실측에서
optimal 6 / onepass 0 / multipass 0 이고 `sorts (disk)` 도 0 이었다. 디스크로
넘쳤는데 그 통계에는 안 잡힌다. AUTO 정책에서만 집계되고, 해시 집계라
`sorts` 통계에도 안 들어간다. "통계가 0 이니 디스크 정렬이 없었다" 로 읽으면
틀린 결론에 이른다. 여기까지 짚은 보고서에는 가점을 준다.

### 카드 H — 리소스 관리자 제한

**주입**
```sql
@PF_10_시나리오주입.sql H INJECT
```
`PF_OLTP_GROUP`(30%)·`PF_BATCH_GROUP`(10%, 활성 세션 1개, 대기 30초)·
`OTHER_GROUPS`(60%)로 `PF_DAY_PLAN` 을 만들고, `ORACLE_USER = 'SQLT'` 를
배치 그룹에 매핑한 뒤 `ALTER SYSTEM SET resource_manager_plan` 으로 켠다.

**매핑은 새 접속부터 적용된다.** SQLT 세션을 다시 접속시켜야 효과가 보인다.

**원인** DB 안에서 CPU 와 동시 세션 수를 의도적으로 제한했다.

**근거가 되는 자리** AWR 머리의 활성 플랜 이름 · Top Events 의
`resmgr: cpu quantum`(활성 세션 풀에 걸리면 `resmgr:become active`) ·
Wait Class 가 Scheduler 또는 Concurrency 로 쏠림 · DB CPU 는 안 늘고 DB Time 만
늘어남 · Resource Limit Stats

**정답 조치** 이 카드의 조치는 "되돌린다" 가 아니다. 플랜이 업무 요구에 맞는지
판단하는 것이다. 배치를 묶는 것이 의도였다면 제한값이 적절한지, 심사 업무가
배치 그룹에 잘못 매핑된 것은 아닌지 확인해야 한다. 실제로 이 시나리오에서는
`ORACLE_USER = SQLT` 매핑 때문에 **심사 업무 전체가** 배치 그룹에 들어갔다.
매핑 기준을 사용자 단위에서 모듈이나 서비스 단위로 바꾸는 것이 정답에 가깝다.

**원복** `@PF_10_시나리오주입.sql H UNDO` 가 네 단계를 한다. 플랜 해제 →
매핑 삭제 → 전환 권한 회수 → `DELETE_PLAN_CASCADE` 와 그룹 삭제.
`PF_` 로 시작하는 플랜일 때만 해제하므로 `INTERNAL_PLAN` 은 건드리지 않는다.

**운영 주의** 이 카드만 인스턴스 전체에 걸린다. 랩을 같이 쓰는 사람이 있으면
미리 알린다. 매핑을 `ORACLE_USER = 'SQLT'` 로 좁혀 두었으므로 SYS·SYSTEM 세션과
백업 크론은 영향을 받지 않는다.

**스크립트를 만들면서 걸린 것** 한 레벨의 `MGMT_P` 합은 **정확히 100** 이어야
한다. 80 + 20 + 100 으로 넣었더니 `ORA-29375 값 합계 200(1 레벨)이 100을 초과함`
으로 `VALIDATE_PENDING_AREA` 에서 걸렸다. 미결 영역이 있는 이유가 이것이다.
수강생에게 리소스 관리자를 설명할 때 좋은 예가 된다.

**반드시 요구할 것** "실행 계획이 전과 똑같다" 가 왜 단서인지. 계획도 통계도
그대로인데 느리다면 SQL 밖에서 묶인 것이다. 그리고 원복 3단계를 전부 확인했다는
로그.

### 카드 I — 호출 횟수 폭주

**주입** `@PF_11_부하패턴.sql I 30000`

**원인** 청구 3만 건을 돌면서 각 건의 병원 이름을 따로 조회한다. 조회 하나하나는
`HOSPITALS`(1,000행) PK 유니크 조회로 회당 3 블록이다. 완벽한 SQL 이다.
그런데 3만 번이면 합계가 커진다. N+1 문제다.

**실측** 1건씩 30,000번 0.16초 · 논리 읽기 90,624 블록 · 회당 3.0 블록 ·
조인 한 번 0.01초 = 16배

**근거가 되는 자리** SQL ordered by Executions 1위 · Elapsed per Exec 가
0.00 에 가까움 · Load Profile 의 Executes 와 `SQL*Net roundtrips` ·
Top Events 의 `SQL*Net message from client`

**정답 조치** 한 번의 조인이나 배치 조회로 바꾼다. SQL 을 고치는 것이 아니라
호출을 줄인다.

**반드시 요구할 것** 회당과 총합을 함께 보인 것. SQL 하나를 튜닝하는 조치안은
통과시키지 않는다. "느린 SQL 이 하나도 없다" 는 개발자 말이 맞으면서도 틀린
이유를 설명해야 한다.

**수강생이 놓치는 곳** AWR 에서 경과 시간 순으로만 보면 0.16초라 눈에 안 띈다.
Executions 30,000 이라는 숫자가 먼저 보여야 한다. 정렬 기준을 바꿔 보는 습관을
짚어 준다.

**스크립트 설계를 바꾼 이력** 처음에는 `claim_details` 를 `claim_id` 로 3만 번
조회하게 만들었다. 그 컬럼에 인덱스가 없어 회당 6,621 블록 전체 스캔이 3만 번
돌았고 74초를 넘겨도 끝나지 않아 세션을 끊었다. 그건 카드 E 지 카드 I 가 아니다.
카드 I 는 **회당이 정말 빨라야** 성립한다.

### 카드 J — 짧은 폭주

**주입** `@PF_11_부하패턴.sql J 1` 이 10초간 돈다. 조용 3초 → 폭주 3초 →
조용 3초 순서다. 폭주 구간만 디스크 정렬을 돌린다.

**실측** 조용 3초 / 폭주 3.88초 / 조용 3초, 전체 9.99초

**원인** 나쁜 것은 부하가 아니라 관측 방법이다. 1시간 구간 AWR 은 3초 폭주를
1/1200 로 희석한다. 평균은 멀쩡하다.

**근거가 되는 자리** 긴 구간 AWR 은 아무것도 보여 주지 않는다. 그게 결론의
일부다 · 같은 시각 ASH 의 Top Events 와 Top SQL · `V$ACTIVE_SESSION_HISTORY`
를 1초 단위로 센 봉우리

**정답 조치** DB 를 고치는 것이 아니다. 짧은 장애는 ASH 로 본다. 스냅샷 주기를
줄이는 것은 SYSAUX 를 먹으니 신중해야 한다.

**반드시 요구할 것** 결론이 "이상 없음" 이 되어서는 안 된다. AWR 침묵과 ASH
포착을 나란히 놓고, 왜 한쪽은 침묵하고 한쪽은 말하는지 설명해야 한다.

**수강생이 놓치는 곳** 이 카드의 결함이 DB 에 없다는 것을 받아들이기 어려워한다.
"그럼 문제가 없는 거냐" 로 가면 틀렸다. 문제는 있고, 그것을 보는 도구가
틀렸던 것이다. 그리고 그 결론을 "AWR 로 본 사람이 틀렸다" 가 아니라 "이런
장애는 ASH 로 봐야 한다" 로 쓰게 지도한다. 보고서는 비난이 아니라 제안이다.

## 3. 운영 순서

### 3.1 카드를 주기 전

```sql
[SYS] @PF_10_시나리오주입.sql - STATUS
```
네 가지를 확인한다. 카드 C 히스토그램, 카드 D 확장 통계, 카드 E 인덱스,
카드 H 활성 플랜. 앞 사람의 잔재가 남아 있으면 `@PF_99_원복.sql` 을 먼저 돌린다.

### 3.2 카드별 준비

| 카드 | 준비 |
|---|---|
| B · F | `@PF_11_부하패턴.sql PREP -` (SQLT) 로 복제표 생성 |
| C | `@PF_10_시나리오주입.sql C INJECT` (SYS) |
| H | `@PF_10_시나리오주입.sql H INJECT` (SYS). 랩 공유자에게 알린다 |
| F | 수강생 시작 직전에 `@PF_11_부하패턴.sql BLOCKER 60` (SYS) |
| A · D · E · G · I · J | 준비 없음 |

### 3.3 카드가 끝난 뒤

```sql
[SYS] @PF_10_시나리오주입.sql H UNDO    -- 카드 H 였으면
[SYS] @PF_99_원복.sql
```

`PF_99` 가 `PF_` 객체·`PF_ADDM_*` 작업·`PF_` 스케줄러 작업·확장 통계를 지우고
Day 0 통계를 다시 수집한다. 리소스 관리자 플랜 정의는 `PF_10 H UNDO` 가 지운다.

### 3.4 여러 명을 동시에 돌릴 때

C·D·H 는 인스턴스 하나에 하나만 걸 수 있다. 같은 랩에서 여러 수강생이 동시에
다른 카드를 받으면 A·B·E·F·G·I·J 로 배분한다. 이 일곱 장은 세션 수준이거나
복제표를 쓰므로 서로 간섭이 적다.

다만 카드 A 는 공유 풀에 커서를 2,000개 남기고, 카드 G 는 임시 테이블스페이스를
쓴다. 동시에 여러 명이 돌리면 서로의 숫자가 흔들린다. 측정 구간이 겹치지 않게
순서를 정해 주는 편이 낫다.

## 4. 측정 도구를 쓸 때 걸리는 것들

과제 스크립트를 만들면서 실제로 걸린 것들이다. 수강생도 같은 데서 막힌다.

| 증상 | 원인 | 대처 |
|---|---|---|
| 실행 계획에 A-Rows·Buffers 가 없다 | `SET SERVEROUTPUT ON` 상태에서 `DISPLAY_CURSOR(NULL,...)` 를 불렀다. 마지막 SQL 이 `DBMS_OUTPUT.GET_LINES` 로 잡힌다 | `SET SERVEROUTPUT OFF` 후 다시 측정 |
| `DBMS_ADDM.GET_REPORT` 가 제목만 나온다 | CLOB 이 80자에서 잘렸다 | `SET LONG 2000000 LONGCHUNKSIZE 200000` |
| ADDM 이 아무 권고도 안 낸다 | 이 4 CPU VM 에서 AAS 0.2 와 2.03 둘 다 침묵했다 | "권고 없음" 도 결과다. 그대로 적게 한다. ADDM 에 의존하는 카드는 없다 |
| 델타가 음수다 | 구간에 인스턴스 재기동이 끼었다 | 캡처를 버리고 다시 잡는다 |
| 상위 SQL 1위가 `insert into wrh$_…` | AWR 이 스냅샷을 저장한 SQL | 측정이 남긴 자기 흔적이다. 범인 후보에서 뺀다 |
| 히스토그램이 혼자 늘어나 있다 | 야간 자동 통계 수집(`METHOD_OPT` 기본값 `SIZE AUTO`)이 만든다 | `PF_99` 의 Day 0 재수집이 지운다. 실측에서 `CLAIM_DETAILS.AMT` HYBRID 254 가 이렇게 생겨 있었다 |

마지막 줄이 과정 전체에 영향을 준다. 야간 자동 통계 수집이 돌면 ch01~ch14 의
E-Rows 실측값이 달라진다. 영구히 막으려면 `SET_TABLE_PREFS('METHOD_OPT', ...)`
또는 `LOCK_TABLE_STATS` 가 필요하지만 적용하지 않았다. 과정 운영 방침에 달린
문제라 판단을 남겨 둔다.
