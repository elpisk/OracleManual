# 시나리오 카드 10종 — 수강생 배포본

> 카드에는 **신고 내용과 제약만** 적혀 있다. 원인은 없다. 원인을 찾는 것이 과제다.
> 카드 한 장을 완전히 끝낸 뒤 다음 장으로 간다.

각 카드는 세 부분으로 되어 있다.

- **신고** — 현장에서 올라온 말. 기술 용어가 아니라 사람의 말이다
- **제약** — 해도 되는 것과 하면 안 되는 것
- **제출에 반드시 포함할 것** — 이것이 빠지면 보고서가 성립하지 않는다

모든 카드에 공통으로 적용되는 것은 `00_과제안내.md` 4절에 있다. 특히
"개인 실습 VM 재현 사례" 표기와 원복 로그는 열 장 모두 필수다.

## 카드 A — "조회 화면이 점점 느려집니다"

**신고**
심사 담당자들이 오전에는 괜찮다가 사람이 몰리면 전체가 같이 느려진다고 한다.
특정 화면만 느린 게 아니라 전부 조금씩 느려진다. 어제 신규 심사원 10명이
들어왔고 그때부터 체감이 심해졌다. 데이터가 늘어난 것은 아니다.

**제약**
- 애플리케이션 코드를 고칠 수 없다는 가정에서 출발한다. 그래도 조치 제안에는
  코드 수정이 들어가야 한다
- `ALTER SYSTEM` 금지
- 부하는 `@PF_11_부하패턴.sql A 2000` 으로 재현한다. 횟수를 함부로 올리지 않는다

**제출에 반드시 포함할 것**
- Load Profile 의 Parses 와 Hard parses 를 같이 인용. 비율로 읽는다
- Instance Efficiency 의 Soft Parse %
- 같은 모양의 SQL 이 여러 `SQL_ID` 로 흩어진 증거
  (`@PF_11` 출력의 커서 개수, 그리고 `TOPSQL` 의 `FORCE_MATCHING_SIGNATURE` 묶음)
- 조치안으로 `CURSOR_SHARING=FORCE` 를 든다면 **그 부작용**을 반드시 쓴다.
  부작용을 쓰지 않으면 이 카드는 통과하지 못한다

**생각해 볼 것**
공유 풀에 커서가 몇 개 남았는지 세어 보면, 만든 수보다 적을 수 있다. 왜 그럴까.

## 카드 B — "저장 버튼을 누르면 한참 걸립니다"

**신고**
야간 배치가 1만 건을 처리하는데 예전에 5분이던 것이 20분으로 늘었다. CPU 사용률은
한가하고 디스크도 여유가 있다. 서버 담당자는 "서버는 아무 문제 없다" 고 한다.

**제약**
- 원본 7개 표에 쓰기 금지. `@PF_11_부하패턴.sql PREP -` 로 복제표를 먼저 만든다
- 부하는 `@PF_11_부하패턴.sql B 10000`
- 행 수를 10만 이상으로 올리지 않는다. 리두가 늘어 아카이브 영역에 부담이 된다

**제출에 반드시 포함할 것**
- Top 10 Foreground Events 와 Wait Class 표
- `DELTA` 의 `user commits` 와 `redo synch writes` 델타
- 1건씩 커밋과 일괄 커밋의 경과 시간 비
- 조치의 맞교환 — 커밋을 묶으면 무엇이 나빠지는가

**이 랩의 한계를 반드시 다룰 것**
이 VM 은 로그 파일이 로컬 디스크에 있어 커밋 왕복이 수십 마이크로초다. 그래서
`log file sync` 의 절대 시간이 교과서만큼 크게 나오지 않고, Top Events 1위가
아닐 수도 있다. 그 사실을 보고서에 적고, 절대 시간 대신 무엇으로 읽었는지 밝힌다.
한계를 밝히는 것은 감점이 아니다.

## 카드 C — "어제까지 1초였던 조회가 오늘 30초입니다"

**신고**
병원별 청구 조회 화면이 갑자기 느려졌다. 배포는 없었다. 데이터가 늘지도 않았다.
개발자가 같은 SQL 을 개발 DB 에서 돌려 보니 1초가 걸린다. 운영에서만 느리다.
대형 병원을 조회할 때는 괜찮고 작은 의원을 조회할 때 느리다는 제보도 있다.

**제약**
- 결함은 강사가 미리 걸어 둔다. `PF_10` 출력을 보지 않는다
- 인덱스를 새로 만들어 해결하려 들기 전에, 왜 어제와 오늘이 다른지 설명해야 한다
- `ALTER SYSTEM` 금지

**제출에 반드시 포함할 것**
- 같은 SQL 의 `PLAN_HASH_VALUE` 가 구간 전후로 달라진 증거
  (`DBA_HIST_SQLSTAT`, 또는 `TOPSQL` 과 실행 계획)
- 실행 계획의 E-Rows 와 A-Rows 를 나란히. 몇 배 틀렸는지 숫자로
- 조인이 있는 쿼리에서 그 오차가 **어떻게 전파되는지**. 단일 표 오차와 조인 후
  오차를 둘 다 보여 준다
- 조치 후 재측정

**생각해 볼 것**
"작은 의원을 조회할 때 느리다" 는 제보가 왜 결정적 단서인가.

## 카드 D — "월별 집계만 유독 느립니다"

**신고**
일별 조회는 빠른데 월별 집계가 느리다. 같은 표를 보는데 왜 다른지 모르겠다.
개발자는 "인덱스가 있는데 왜 안 타는지 모르겠다" 고 한다.

**제약**
- 인덱스를 추가하는 것만으로는 통과하지 못한다. 왜 기존 인덱스를 못 쓰는지
  설명해야 한다
- 쿼리를 고치는 조치와 통계를 고치는 조치를 **둘 다** 검토하고, 각각의 장단을 쓴다
- `ALTER SYSTEM` 금지

**제출에 반드시 포함할 것**
- 문제가 되는 조건절을 그대로 인용. 왜 컬럼 통계를 쓸 수 없는 형태인지
- 옵티마이저가 끼운 추정치와 실제 건수. 기본 선택도가 몇 %인지 계산해 보일 것
- 조치 후 E-Rows 와 A-Rows 가 맞는지
- 두 가지 조치안 비교
  - 조건절을 `receipt_date >= ... AND < ...` 범위로 바꾸는 쪽
  - 표현식 통계를 만드는 쪽
  각각 언제 쓰는지, 어느 쪽이 이 상황에 맞는지 근거를 들어 고른다

## 카드 E — "특정 환자 조회만 느립니다"

**신고**
환자 한 명의 청구 내역을 띄우는 화면이 느리다. 한 번 열 때는 참을 만한데,
심사원이 목록에서 환자를 하나씩 클릭해 가며 일할 때 화면 전환이 답답하다.
서버 CPU 가 조회할 때마다 튄다. 대기 이벤트를 봐도 이상한 것이 없다.

**제약**
- 부하는 `@PF_11_부하패턴.sql E 200` 으로 재현한다. 보고서용으로는 횟수를
  늘려도 된다
- 조치로 인덱스를 만들면 그 인덱스는 `PF_` 로 시작하는 이름을 쓴다.
  그러지 않으면 원복 스크립트가 지우지 못한다

**제출에 반드시 포함할 것**
- 회당 버퍼 읽기. 한 행을 세려고 몇 블록을 읽었는지
- Segments by Logical Reads 에서 그 표가 1위인 것
- 대기 이벤트가 조용하다는 사실. 그리고 그것이 왜 중요한지
- 조치 후 회당 버퍼 읽기. 몇 배 줄었는지
- 인덱스의 맞교환. 이 표가 읽기 위주인지 쓰기 위주인지 근거를 들 것

**생각해 볼 것**
"대기 이벤트를 봐도 이상한 것이 없다" 는 말이 왜 단서인가. 대기 이벤트만 보는
진단으로는 어떤 문제를 놓치는가.

## 카드 F — "서버는 한가한데 화면이 안 돌아옵니다"

**신고**
심사 결과를 저장하려 하면 저장 버튼이 멈춘 채로 1분 가까이 있다가 풀린다.
항상 그런 것은 아니고 몇 사람이 같이 일할 때 생긴다. 서버 CPU 는 10% 미만,
디스크도 한가하다. 재현이 어려워 개발팀이 손을 놓고 있다.

**제약**
- 두 세션이 필요하다. 강사가 SYS 창에서 방해자를 띄운다
  (`@PF_11_부하패턴.sql BLOCKER 60`), 수강생은 바로 이어서
  `@PF_11_부하패턴.sql F 60`
- 원본 7개 표에 쓰기 금지. 복제표를 쓴다

**제출에 반드시 포함할 것**
- Top 10 Foreground Events 에서 해당 대기 이벤트와 Wait Class
- DB Time 과 DB CPU 를 나란히. 둘의 차이가 이 카드의 핵심 근거다
- ASH 보고서. 누가 누구를 막았는지
- 왜 AWR 만으로는 부족하고 ASH 가 필요한지 설명
- 조치안. DB 설정으로 풀 수 있는 문제인지 판단해서 쓸 것

**주의**
`V$SESSION.BLOCKING_SESSION` 은 기다리는 **동안에만** 값이 있다. 잠금을 얻은
뒤에 조회하면 비어 있다. 지나간 일을 보려면 ASH 를 써야 한다.

## 카드 G — "같은 집계가 어떤 때는 빠르고 어떤 때는 느립니다"

**신고**
월말 정산 집계가 보통 1초인데 어떤 날은 10초가 넘는다. 데이터 양은 비슷하다.
DBA 가 "메모리 문제 같다" 고 하는데 서버 메모리는 절반이 남아 있다.

**제약**
- `ALTER SYSTEM` 절대 금지. 세션 수준(`ALTER SESSION`)으로만 재현한다
- 부하는 `@PF_11_부하패턴.sql G 1`

**제출에 반드시 포함할 것**
- Top 10 Events 에서 임시 테이블스페이스 관련 대기
- 임시 테이블스페이스 읽기·쓰기 블록 수
- 실행 계획의 `OMem` / `1Mem` / `Used-Mem` 열. 메모리에서 끝났는지 넘쳤는지
- PGA Aggr Target Stats 또는 작업 영역 실행 통계
- 왜 "서버 메모리가 남아 있다" 가 반증이 되지 못하는지

**함정 둘**
첫째, 경과 시간은 버퍼 캐시 상태에 따라 흔들린다. 같은 부하를 두 번 돌려도
시간이 다르게 나온다. 임시 I/O 블록 수를 근거로 삼는 편이 안정적이다.

둘째, 작업 영역 정책을 `MANUAL` 로 두면 `workarea executions` 통계가 쌓이지
않는다. 디스크로 넘쳤는데도 `sorts (disk)` 가 0 으로 보인다. 그 통계가 0 이라고
"디스크 정렬이 없었다" 로 읽으면 틀린 결론에 이른다. 보고서에 이 점을 적으면
가점이다.

## 카드 H — "오후 2시만 되면 전체가 느려집니다"

**신고**
오후 2시 무렵부터 심사 화면 전체가 느려진다. 그 시간에 배치가 돌지만 예전에도
돌았고 그때는 괜찮았다. 지난주 DBA 가 뭔가 설정을 바꿨다는 말이 있다.
실행 계획을 확인해 봤는데 전과 똑같다. 통계도 멀쩡하다.

**제약**
- 이 카드만 `ALTER SYSTEM` 을 쓴다. 인스턴스 전체에 걸린다
- 랩을 같이 쓰는 사람이 있으면 미리 양해를 구한다
- 끝나면 반드시 되돌린다. 되돌리지 않으면 다음 사람의 측정이 전부 틀어진다
- 결함은 강사가 건다 (`@PF_10_시나리오주입.sql H INJECT`)

**제출에 반드시 포함할 것**
- AWR 보고서 머리의 활성 플랜 이름
- Top 10 Foreground Events 에서 리소스 관리자 관련 대기 이벤트
- Wait Class 분포
- DB CPU 는 늘지 않았는데 DB Time 만 늘어난 것
- 플랜의 지시 내용. 어느 그룹에 무엇이 걸려 있었는가
- "실행 계획이 전과 똑같다" 가 왜 중요한 단서인지
- 원복 확인 — 플랜 해제, 매핑 삭제, 그룹 삭제까지 전부

**생각해 볼 것**
이 결함은 DB 가 고장난 것이 아니다. 누군가 의도를 가지고 설정한 것이다.
보고서의 조치안은 "되돌린다" 가 아니라 "이 설정이 맞는지 판단한다" 여야 한다.
그 판단에 어떤 근거가 필요한가.

## 카드 I — "목록 화면 한 장이 느립니다"

**신고**
청구 목록 화면이 느리다. 개발자가 APM 으로 들여다봤는데 느린 SQL 이 하나도 없다.
전부 1ms 안쪽이다. 그런데 화면은 3초가 걸린다. 개발자는 "DB 는 문제가 없고
네트워크나 WAS 문제" 라고 한다.

**제약**
- 부하는 `@PF_11_부하패턴.sql I 30000`
- SQL 하나를 튜닝하는 조치안은 통과하지 못한다

**제출에 반드시 포함할 것**
- SQL ordered by Executions 와 SQL ordered by Elapsed Time 을 **같이** 인용
- 그 SQL 의 회당 경과 시간과 회당 버퍼. 둘 다 작다는 것을 보일 것
- 그런데 총합이 큰 것
- Load Profile 의 Executes 와 `SQL*Net roundtrips`
- 조치 후 같은 결과를 내는 방법과 그 측정값
- "느린 SQL 이 하나도 없다" 는 개발자 말이 왜 맞으면서도 틀린지

**생각해 볼 것**
이 문제에 이름이 있다. 그 이름을 찾아 보고서에 쓰면 좋다.

## 카드 J — "오전 10시 12분에 3초간 멈췄습니다"

**신고**
사용자 한 명이 "오전 10시 12분쯤 화면이 3초 정도 멈췄다" 고 신고했다. 그 시간대
AWR 보고서를 떠 봤는데 아무 이상이 없다. 평균이 다 정상이다. 다른 신고는 없고
재현도 안 된다. 팀장은 "사용자 착각 아니냐" 고 한다.

**제약**
- 부하는 `@PF_11_부하패턴.sql J 1` (10초간 돈다. 그중 3초만 폭주한다)
- 이 카드의 결론은 "이상 없음" 이 되어서는 안 된다

**제출에 반드시 포함할 것**
- 긴 구간을 덮는 AWR 보고서. 거기서 아무것도 안 보인다는 것을 보일 것
- 같은 시각 ASH 보고서. 거기서는 보인다는 것
- 두 보고서의 차이를 설명. 왜 한쪽은 침묵하고 한쪽은 말하는가
- `V$ACTIVE_SESSION_HISTORY` 를 1초 단위로 세어 봉우리를 보인 자료
- 스냅샷 주기를 줄이는 조치의 비용. SYSAUX 를 얼마나 더 쓰는가
- "사용자 착각" 이 아니라는 근거

**생각해 볼 것**
이 카드의 결함은 DB 에 있지 않다. 어디에 있는가. 그리고 그것을 보고서에
어떻게 쓰면 비난이 아니라 제안이 되는가.

## 카드 고르기 참고

처음 하는 사람에게는 C 나 E 가 수월하다. 원인과 조치가 또렷하고 숫자 차이가 커서
보고서 쓰기가 쉽다.
