# AWR 진단 포트폴리오 과제 — 과제 안내

> 대상: DBTUNING 과정 ch20~ch25(AWR·ASH·ADDM) 학습을 마친 수강생
> 성격: 수료 후 개인 과제. 성적에 들어가지 않는다. 취업 서류에 쓰는 것이 목적이다.

---

## 1. 이 과제가 만들려는 것

면접에서 "성능 튜닝 해 봤어요" 라고 말하는 지원자는 많다. 그 말을 **숫자와 근거로**
받쳐 내는 지원자는 드물다. 이 과제의 산출물은 그 차이를 메우는 문서 한 편이다.

완성하면 아래를 갖게 된다.

- 장애 하나를 AWR 로 진단하고 조치한 보고서 1편 (PDF)
- 그 보고서의 근거가 되는 측정 파일 모음 (AWR·ASH·실행 계획·원복 로그)
- 원하면 GitHub 저장소 하나. 면접관이 링크로 들어가 볼 수 있다

보고서는 **길이로 평가되지 않는다.** 5~8쪽이면 충분하다. 다음 세 가지가 있으면 좋은
보고서고, 없으면 분량과 무관하게 약한 보고서다.

1. 조치 전과 후의 같은 지표 — 같은 단위, 같은 구간 길이로 잰 것
2. 그 숫자를 어느 보고서 어느 줄에서 가져왔는지 밝힌 출처
3. 원복까지 끝냈다는 확인

## 2. 진행 방식

### 2.1 카드를 한 장 받는다

시나리오 카드 10종이 `01_시나리오카드_10종.md` 에 있다. 강사가 한 장을 지정하거나,
수강생이 골라도 된다. 카드에는 **신고 내용과 제약만** 적혀 있고 원인은 없다.
원인을 찾는 것이 과제다.

여러 장을 하고 싶으면 한 장을 완전히 끝낸 뒤 다음 장으로 간다. 두 결함을 동시에
걸면 AWR 만으로는 원인을 가릴 수 없고, 그건 이 과제가 가르치려는 것이 아니다.

### 2.2 환경을 기록한다

```sql
SQL> CONNECT / AS SYSDBA
SQL> SPOOL 01_근거/00_환경점검.log
SQL> @PF_00_환경점검.sql
SQL> SPOOL OFF
```

이 로그가 보고서 1장이 된다. 기준과 어긋난 항목이 나와도 멈추지 않는다.
어긋난 것을 **보고서에 적고** 시작한다. 실습 랩은 여러 사람이 쓰고, 자동 통계
수집 작업이 밤마다 히스토그램을 다시 만든다. 운영 DB 도 똑같다.

### 2.3 구간을 잡고 잰다

측정은 언제나 두 시점 사이에서 한다. 누적값을 그대로 비교하면 틀린 결론이 나온다.

```sql
[SYS]   @PF_20_측정보조.sql SNAP T0 -        -- 시작점
[SQLT]  ... 부하 또는 조치 실행 ...
[SYS]   @PF_20_측정보조.sql SNAP T1 -        -- 끝점
[SYS]   @PF_20_측정보조.sql DELTA  T0 T1     -- 전/후/델타
[SYS]   @PF_20_측정보조.sql TOPSQL T0 T1     -- 상위 SQL
```

보고서 본문에 쓸 보고서는 파일로 남긴다. 화면 캡처는 근거로 쓰지 않는다.

```sql
SQL> SPOOL 01_근거/AWR_T0_T1.txt
SQL> @PF_20_측정보조.sql AWR T0 T1
SQL> SPOOL OFF
```

### 2.4 조치하고, 같은 방법으로 다시 잰다

조치 전과 후를 **같은 길이의 구간**에서 재야 비교가 성립한다. 10초 구간과 1시간
구간을 나란히 놓으면 아무 의미가 없다.

두 구간을 나란히 보려면 Compare Periods 를 쓴다.

```sql
SQL> @PF_20_측정보조.sql DIFF T0:T1 T2:T3
```

### 2.5 되돌린다

```sql
SQL> SPOOL 01_근거/99_원복.log
SQL> @PF_99_원복.sql
SQL> SPOOL OFF
```

되돌리기까지가 진단이다. 운영에서도 "재현 환경을 원상복구했다" 를 못 쓰면 작업
승인을 받지 못한다. 못 지운 것이 있으면 숨기지 말고 적는다.

## 3. 제출물

### 3.1 기본 — PDF 한 편과 근거 폴더

```
<이름>_AWR진단_<카드>/
├─ 보고서.pdf                     ← 02_보고서양식.docx 를 채워 PDF 로
└─ 01_근거/
   ├─ 00_환경점검.log
   ├─ AWR_T0_T1.txt               ← 조치 전 구간
   ├─ AWR_T2_T3.txt               ← 조치 후 구간
   ├─ DIFF_전후.txt               ← Compare Periods
   ├─ ASH_T0_T1.txt               ← 대기가 문제인 카드만
   ├─ TOPSQL_전.txt / TOPSQL_후.txt
   ├─ 실행계획_전.txt / 실행계획_후.txt
   └─ 99_원복.log
```

파일 이름에 구간 태그를 넣는다. 보고서 본문에서 "AWR_T0_T1.txt 34행" 처럼
가리킬 수 있어야 한다.

### 3.2 선택 — GitHub 저장소

링크 하나로 보여 줄 수 있어 면접에서 유리하다. `06_GitHub_README_템플릿.md` 를
쓴다. 올리기 전에 아래를 반드시 확인한다.

- 접속 문자열·계정·비밀번호가 보고서와 로그에 남아 있지 않은지
- 호스트 이름과 IP 를 가릴 것인지 (가려도 되고, 실습 VM 임을 밝히면 안 가려도 된다)
- 회사명·고객명이 들어간 문자열이 없는지

## 4. 반드시 지킬 것

### 4.1 "개인 실습 VM 재현 사례" 를 표지에 적는다

이 숫자들은 4 CPU 가상 머신에서 나온 것이다. 운영 실적이 아니다. 그 사실을
표지와 1장에 적는다. 밝히지 않으면 과장이 되고, 면접에서 한 번만 파고들면
들통난다. 밝히고 쓰면 "환경의 한계를 아는 지원자" 가 된다. 후자가 훨씬 낫다.

### 4.2 환경의 한계를 숨기지 않는다

이 랩에서는 어떤 지표가 교과서처럼 나오지 않는다. 예를 들어 로그 파일이 로컬
디스크에 있어 커밋 왕복이 수십 마이크로초다. 그래서 행별 커밋 문제를 걸어도
`log file sync` 의 절대 시간이 작게 나온다. 이럴 때 할 일은 둘 중 하나다.

- 비율로 읽는다 (14배)
- 다른 지표로 받친다 (`user commits` 델타가 행 수와 같아지는 것)

그리고 보고서에 "이 환경에서는 절대 시간이 작다" 를 적는다. 감점이 아니라 가점이다.

### 4.3 원본 데이터를 바꾸지 않는다

진료비청구심사 7개 표에는 INSERT·UPDATE·DELETE 를 하지 않는다. 쓰기가 필요한
카드는 `PF_` 로 시작하는 복제표를 만들어 쓴다. 과제 스크립트가 그렇게 만들어져 있다.

### 4.4 남의 객체를 지우지 않는다

랩에는 다른 수강생과 다른 장의 실습이 남긴 객체가 있다. `PF_99_원복.sql` 은
자기가 만든 `PF_` 객체만 지우고, 나머지는 '수동확인' 으로 적어서 보여 준다.
그 설계를 그대로 따른다. 운영에서 남의 인덱스를 지우면 그게 바로 장애다.

### 4.5 ALTER SYSTEM 은 카드 H 에서만 쓴다

인스턴스 전체에 걸리는 변경은 리소스 관리자 카드 하나뿐이다. 랩을 같이 쓰는
사람이 있으면 미리 양해를 구하고, 끝나면 반드시 되돌린다.

## 5. 흔히 빠지는 함정

측정 자체가 틀리면 그 뒤가 전부 무의미해진다. 아래는 실제로 과제 스크립트를
만들면서 걸렸던 것들이다.

| 함정 | 증상 | 대처 |
|---|---|---|
| 누적값 비교 | 숫자가 터무니없이 크다 | 델타만 읽는다. `DELTA` 가 그 일을 한다 |
| 인스턴스 재기동이 구간에 끼었다 | 델타가 음수 | 캡처를 버리고 다시 잡는다 |
| 구간 길이가 다르다 | 전/후 비교가 안 맞는다 | 같은 길이로 다시 잰다 |
| `SET SERVEROUTPUT ON` 상태 | 실행 계획을 못 가져온다 | `SET SERVEROUTPUT OFF` 후 `DISPLAY_CURSOR` |
| AWR 보존 기간을 넘긴 과거 | 스냅샷이 없다 | 사후 진단 불가. 그 사실을 적는다 |
| ADDM 이 아무 말도 안 한다 | "권고 없음" | 침묵도 결과다. 그대로 적고 다른 근거를 쓴다 |
| 측정 행위가 상위 SQL 에 섞인다 | `wrh$_` INSERT 가 올라온다 | AWR 자신의 SQL 이다. 범인 후보에서 뺀다 |

마지막 줄이 특히 중요하다. 상위 SQL 목록에 `wrh$_`·`wrm$_` 로 시작하는 INSERT 가
보이면 그건 AWR 이 스냅샷을 저장한 흔적이다. 측정이 남긴 자기 흔적을 범인으로
지목하는 일이 생각보다 자주 일어난다.

## 7. 일정 권장안

하루에 몰아서 하지 않는 편이 낫다. 측정과 해석 사이에 시간을 두면 보고서가 좋아진다.

| 날 | 할 일 | 시간 |
|---|---|---|
| 1일 | 카드 받기, 환경 점검, 결함 재현, 조치 전 구간 측정 | 2~3시간 |
| 2일 | AWR·ASH 본문 읽기, 원인 가설 세우기, 근거 줄 표시 | 2시간 |
| 3일 | 조치, 조치 후 측정, Compare Periods, 원복 | 2시간 |
| 4일 | 보고서 작성, 맞교환과 한계 서술 | 3~4시간 |
| 5일 | 다시 읽고 다듬기, PDF 변환, (선택) GitHub 올리기 | 1~2시간 |

4일의 "맞교환과 한계" 가 보고서의 수준을 가른다. 조치의 부작용을 쓰지 않은
보고서는 어느 카드든 반쪽이다.
