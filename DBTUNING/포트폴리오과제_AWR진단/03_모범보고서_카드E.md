### 1.1 기준에서 어긋난 항목

환경 점검에서 두 가지가 과정 기준과 달랐다. 조치하지 않고 그대로 두었으며,
진단에 영향이 없음을 아래에 적는다.

| 항목 | 발견 | 판단 |
|---|---|---|
| `MEDICAL_CLAIMS` 의 `IX_MC_HOSP` | 기준(PK 7개) 외 인덱스 1개 | `HOSP_ID` 컬럼 인덱스. 이번 진단 대상은 `PAT_ID` 조건이므로 무관. 다른 수강생의 것일 수 있어 손대지 않았다 |
| `PATIENTS_WL` 등 보조 표 3개 | 다른 장 실습의 잔재 | 대상 7개 표가 아니다. 읽지도 쓰지도 않았다 |

측정 환경을 "완벽한 기준" 으로 맞추고 시작하지 않았다. 실습 랩은 여러 사람이
쓰고 자동 통계 수집 작업이 밤마다 돌아 히스토그램을 다시 만든다. 운영 DB 도
마찬가지이므로, 어긋난 것을 기록하고 그 영향을 판단하는 쪽을 택했다.

### 1.2 측정 방법의 한계

실행 계획을 볼 때 `SET SERVEROUTPUT OFF` 를 먼저 실행했다. 켜진 상태에서
`DBMS_XPLAN.DISPLAY_CURSOR(NULL, ...)` 를 부르면 "마지막 SQL" 이
`DBMS_OUTPUT.GET_LINES` 로 잡혀 계획을 가져오지 못한다. 측정 초반에 이 문제로
계획을 한 차례 잃었고, 그 뒤로는 끄고 측정했다.

## 2. 신고 내용과 1차 판단

### 2.1 신고

심사원이 환자 목록에서 환자를 하나씩 클릭해 가며 일할 때 화면 전환이 답답하다는
신고가 들어왔다. 한 번 열 때는 참을 만하다. 조회할 때마다 서버 CPU 가 튄다.
대기 이벤트를 봐도 이상한 것이 없다는 말이 함께 전해졌다.

### 2.2 신고에서 읽어낸 것

세 가지가 눈에 걸렸다.

- "한 번은 참을 만한데 반복하면 답답하다" — 회당 비용이 작지 않지만 치명적이지도
  않다는 뜻이다. 횟수가 쌓여 문제가 되는 모양이다
- "CPU 가 튄다" — 디스크를 기다리는 것이 아니라 일을 하고 있다. 버퍼 캐시에서
  읽는 중일 가능성이 크다
- "대기 이벤트가 조용하다" — 이것이 가장 중요한 단서였다. 대기가 없다면 Top
  Events 를 먼저 보는 습관으로는 아무것도 못 찾는다

그래서 Top Events 가 아니라 **SQL ordered by Buffer Gets** 부터 보기로 했다.

### 3.3 이 표에서 읽은 것

DB time 12.95초 중 DB CPU 가 12.49초다. 대기 몫이 3.6% 뿐이다. 신고에 있던
"대기 이벤트가 조용하다" 가 숫자로 확인됐다. 그리고 물리 읽기가 51 블록인데
논리 읽기가 619만 블록이다. 디스크는 거의 건드리지 않고 버퍼 캐시만 쉼 없이
훑었다는 뜻이다.

여기서 방향이 정해졌다. 기다림이 아니라 **읽는 양**이 문제다.

### 3.4 상위 SQL

근거: `01_근거/TOPSQL_M0_M1.txt`

| SQL_ID | SQL | 경과 | 실행 | 회당 | 버퍼 읽기 | 회당 버퍼 |
|---|---|---|---|---|---|---|
| `dxu0rw70qzj3k` | `SELECT COUNT(*) FROM SQLT.MEDICAL_CLAIMS WHE…` | 11.85초 | 2,000 | 0.006초 | 6,180,012 | **3,090** |
| `127pytdq688t6` | `DECLARE v_cmd … UPPER('SNAP')` | 0.85초 | 1 | 0.852초 | 15,530 | 15,530 |

상위 목록에 `insert into wrh$_…` 과 `insert into wrm$_…` 로 시작하는 문장이
여러 개 올라와 있었다. AWR 이 스냅샷을 저장하는 SQL 이다. 측정 행위 자체가
남긴 흔적이므로 범인 후보에서 제외했다. 2위인 `DECLARE` 블록도 부하 스크립트
자신이다.

실제 범인은 1위 한 줄이다. 2,000번 실행되어 11.85초를 썼다.

### 3.5 결정적 숫자

회당 0.006초다. APM 으로 보면 6밀리초니 아무도 느린 SQL 이라고 부르지 않는다.
그런데 회당 버퍼가 3,090 블록이다.

이 쿼리가 돌려주는 값은 한 건의 숫자 하나다. 그 하나를 세려고 3,090 블록을 읽는다.
8 KB 블록이니 24 MB 를 읽어 숫자 하나를 만든 셈이다.

`MEDICAL_CLAIMS` 의 전체 블록 수가 3,090 이다. 즉 매번 표 전체를 읽는다.

## 4. 원인

`MEDICAL_CLAIMS.PAT_ID` 에 인덱스가 없다. 그래서 환자 한 명을 찾을 때마다
30만 행 3,090 블록을 전부 읽는다.

한 번은 6밀리초라 아무도 문제라고 부르지 않는다. 심사원이 목록을 클릭해 가며
2,000번 일하면 619만 블록, 12초가 된다. 회당 비용이 작아 눈에 띄지 않고,
대기가 없어 Top Events 에도 안 잡힌다. 그래서 오래 남아 있었다.

### 4.1 왜 이 진단이 어려웠는가

보고서에 남길 가치가 있는 부분이다. 대기 이벤트부터 보는 평소 순서로는 이 문제를
찾지 못한다. 대기 몫이 3.6% 라 Top 10 Foreground Events 가 사실상 비어 있다.
"대기가 없으니 DB 는 정상" 으로 결론 내면 거기서 끝난다.

CPU 를 쓰는 문제는 대기 목록이 아니라 **읽은 양**에서 드러난다. 봐야 할 곳은
SQL ordered by Buffer Gets, Segments by Logical Reads, 그리고 회당 비율이다.

## 5. 조치

### 5.1 조치 내용

```sql
CREATE INDEX PF_IX_MC_PAT ON medical_claims (pat_id);

BEGIN
  DBMS_STATS.GATHER_TABLE_STATS('SQLT', 'MEDICAL_CLAIMS',
      METHOD_OPT    => 'FOR ALL COLUMNS SIZE 1 FOR COLUMNS SIZE 254 HOSP_ID',
      CASCADE       => TRUE,
      NO_INVALIDATE => FALSE);
END;
/
```

인덱스 이름을 `PF_` 로 시작하게 했다. 과제 원복 스크립트가 `PF_` 로 시작하는
객체만 지우도록 되어 있어서다. 통계는 과정 기준 명령으로 다시 수집했다.
`CASCADE => TRUE` 로 새 인덱스 통계까지 같이 받았고, `NO_INVALIDATE => FALSE`
로 기존 커서를 즉시 무효화해 다음 실행에서 새 계획을 짜게 했다.

### 6.1 조치 후 상위 SQL

근거: `01_근거/TOPSQL_M1_M2.txt`

`dxu0rw70qzj3k` 가 상위 15위 안에서 사라졌다. 그 자리에 들어온 것은
`/* SQL Analyze(0) */ select /*+ full(t) …` 과
`select /*+ opt_param('_optimizer_use_auto_indexes'…` 같은 문장들이다.
통계를 다시 수집하면서 옵티마이저가 돌린 SQL 이다. 조치 자체가 남긴 흔적이고

### 6.2 숫자를 읽을 때 주의한 것

**조치 후 구간에는 조치 비용이 섞여 있다.** M1~M2 구간의 DB time 1.66초에는
인덱스 생성과 통계 재수집이 포함된다. 순수 조회는 0.01초였다. 조회만 비교하면
1,195배지만, 구간 전체로는 7.8배다. 두 숫자를 구분해 적는 편이 정확하다.

**대기 몫이 3.6% 에서 28.1% 로 늘었다.** 처음에는 조치가 뭔가 나빠지게 한 것으로
보였다. 분모를 확인하니 그렇지 않았다. DB time 자체가 12.95초에서 1.66초로
줄었고, 그 안에서 인덱스 생성의 I/O 가 차지하는 몫이 커진 것이다. 대기 시간의
절대값은 0.47초로 전과 비슷하다. 비율만 보고 거꾸로 읽을 수 있는 자리였다.

## 7. 맞교환과 남은 위험

조치가 공짜가 아니다. 이 절을 쓰지 않은 보고서는 반쪽이다.

### 7.1 쓰기가 느려진다

`MEDICAL_CLAIMS` 에 INSERT·UPDATE·DELETE 가 생길 때마다 인덱스도 함께 갱신된다.
`PAT_ID` 를 바꾸는 UPDATE 는 인덱스 항목 삭제와 삽입이 되므로 비용이 더 든다.

이 표가 읽기 위주인지 판단할 근거를 찾았다. 측정 구간의 `user commits` 델타가
13, `redo size` 델타가 3,141,692 바이트였다. 그 리두는 대부분 AWR 스냅샷 저장과
통계 수집에서 나온 것이고, 대상 표에 대한 애플리케이션 DML 은 거의 없었다.
청구 접수는 하루 단위 배치로 들어오고 조회는 종일 일어나는 업무 성격과도 맞는다.
읽기가 압도적으로 많은 표라고 판단했다.

다만 이 판단의 근거는 16초 구간 하나다. 운영에서 같은 조치를 하려면 하루 또는
한 주 구간의 `DBA_HIST_SEG_STAT` 으로 이 표의 DML 량을 확인하는 편이 옳다.

### 7.2 공간을 쓴다

30만 행 단일 컬럼 인덱스다. 측정하지 않았으나 수 MB 수준으로 예상된다.
운영 적용 시에는 `DBMS_SPACE.CREATE_INDEX_COST` 로 미리 산정해야 한다.

### 7.3 다른 쿼리의 계획이 바뀔 수 있다

새 인덱스는 이 쿼리만 쓰는 것이 아니다. `PAT_ID` 를 조건이나 조인에 쓰는 다른
쿼리의 계획도 바뀔 수 있고, 그중 일부는 나빠질 수 있다. 특히 선택도가 낮은
조건에서 인덱스를 타면 전체 스캔보다 느려지는 경우가 있다.

운영 적용 전에 `DBA_HIST_SQLSTAT` 에서 `PAT_ID` 를 참조하는 SQL 을 뽑아 적용
전후 `PLAN_HASH_VALUE` 를 비교하는 절차가 필요하다. 이번 실습에서는 하지 않았다.

### 7.4 근본 원인은 화면 설계일 수 있다

인덱스는 증상을 없앤다. 그런데 "환자를 하나씩 클릭해 가며 2,000번 조회" 하는
업무 흐름 자체를 보면, 목록 화면에서 건수를 한 번에 가져오는 설계가 가능하다.
그쪽이 더 나은 조치일 수 있다. 이번 보고서의 범위를 넘으므로 제안만 남긴다.

## 9. 정리

환자별 청구 조회가 느린 원인은 `MEDICAL_CLAIMS.PAT_ID` 의 인덱스 부재였다.
조건절에 쓰는 컬럼에 접근 경로가 없어 조회마다 30만 행을 전부 읽었다.

회당 6밀리초여서 느린 SQL 목록에 오르지 않았고, 버퍼 캐시에서 읽어 대기 이벤트도
남기지 않았다. 반복 횟수가 쌓이면서 드러난 문제다. 인덱스를 만들어 회당 버퍼
읽기를 3,090 에서 3 으로 줄였다.

이 사건에서 가져갈 것은 진단 순서다. 대기가 조용한 문제는 Top Events 로 찾을 수
없다. 읽은 양과 회당 비율을 봐야 한다. 그리고 회당 비용이 작은 SQL 을 실행 횟수와
곱해 보는 습관이 필요하다.

# 이 보고서가 왜 이렇게 쓰였는가 (강사 주석)

수강생은 이 절을 제출물에 넣지 않는다. 구성 의도만 읽는다.

**2절을 신고에서 시작했다.** 지표부터 늘어놓지 않았다. 신고의 어느 구절이
단서였는지 먼저 적으면, 뒤의 측정이 "아무거나 떠 본 것" 이 아니라 가설을 검증한
것이 된다. 면접관이 보는 것도 그 차이다.

**3.3 과 3.5 에 "이 표에서 읽은 것" 을 따로 뒀다.** 표만 붙이고 넘어가면
읽는 사람이 해석을 떠안는다. 숫자 하나를 골라 왜 그것이 결정적인지 한 문단
쓰는 편이 표 열 개보다 낫다.

**3.4 에서 AWR 자신의 SQL 을 제외한다고 밝혔다.** `wrh$_` INSERT 를 범인으로
지목하는 일이 실제로 자주 일어난다. 걸러냈다는 사실 자체가 측정을 이해하고
있다는 신호다.

**6.2 를 넣었다.** 비율이 거꾸로 움직인 것을 그냥 넘기지 않고 분모를 확인했다.
그리고 조치 후 구간에 조치 비용이 섞였다는 것을 스스로 지적했다. 유리한
숫자(1,195배)와 정직한 숫자(7.8배)를 둘 다 적었다. 이 절이 있는 보고서와 없는
보고서의 신뢰도 차이가 가장 크다.

**7절을 네 갈래로 나눴다.** 조치의 비용, 공간, 다른 쿼리에 미칠 영향, 그리고
더 나은 조치 가능성이다. 7.1 에서는 판단 근거를 제시하면서 그 근거가 16초
구간 하나라는 한계까지 적었다. 7.3 은 하지 않은 일을 "하지 않았다" 고 썼다.
한계를 밝히는 것이 감점이 아니라 가점이다.

**1.2 에 측정 실패를 적었다.** `SET SERVEROUTPUT ON` 때문에 계획을 한 번 잃은
일이다. 숨길 이유가 없고, 측정 도구를 이해하고 있다는 증거가 된다.

**9절에서 "가져갈 것" 을 썼다.** 이 사건의 요약이 아니라 다음 사건에 쓸 수 있는
판단 기준이다. 면접에서 "그래서 뭘 배웠나요" 에 답할 재료가 여기서 나온다.
