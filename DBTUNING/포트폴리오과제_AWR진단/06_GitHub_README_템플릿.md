## 올리기 전 확인

| 확인 | 왜 |
|---|---|
| 접속 문자열·계정·비밀번호가 없는가 | 로그 파일에 `sqlt/sqlt@…` 가 그대로 남아 있을 수 있다 |
| 회사명·고객명·실제 업무 데이터가 없는가 | 과정 데이터는 가상이지만 메모에 섞일 수 있다 |
| 호스트 이름과 IP 를 가릴 것인가 | 실습 VM 임을 밝히면 가리지 않아도 된다. 선택이다 |
| "개인 실습 VM 재현 사례" 가 README 와 보고서에 다 있는가 | 없으면 과장이 된다 |
| 저장소를 공개로 둘 것인가 | 비공개로 두고 면접 때 초대하는 방법도 있다 |

로그에서 접속 문자열을 지우는 법:

```bash
grep -rn "sqlt/sqlt\|@localhost\|as sysdba" 01_근거/
sed -i 's|sqlt/sqlt@[^ ]*|<접속정보 생략>|g' 01_근거/*.log
```

지운 뒤 다시 `grep` 해서 확인한다.

## 작성 요령

### 한 줄 요약

면접관이 이 한 줄만 읽고 넘어갈 수도 있다. 세 가지를 넣는다. 무엇이 문제였나,
무엇을 고쳤나, 어느 지표가 몇 배 좋아졌나.

"성능을 개선했습니다" 는 아무 정보가 없다. "회당 버퍼 읽기를 3,090 에서 3 으로
줄였습니다" 는 숫자가 있고, 그 숫자를 말할 수 있다는 것 자체가 신호다.

### 결과 표

핵심 지표를 맨 위에 둔다. 카드별로 다르다.

| 카드 | 맨 위에 둘 지표 |
|---|---|
| A | 하드 파싱 비율 |
| B | 커밋 횟수와 경과 시간 비 |
| C | E-Rows 와 A-Rows 오차 배수 |
| D | 추정 건수와 실제 건수 |
| E | 회당 버퍼 읽기 |
| F | DB Time 과 DB CPU 의 차이 |
| G | 임시 테이블스페이스 I/O 블록 수 |
| H | 리소스 관리자 대기 시간 |
| I | 실행 횟수와 회당 경과 시간 |
| J | AWR 평균과 ASH 봉우리 |

구간 길이를 꼭 적는다. 전후 길이가 다르면 비교가 성립하지 않는다는 것을 아는
지원자라는 신호가 된다.

### 진단 과정

6단계로 쪼갠 이유가 있다. 2번 "단서" 와 3번 "확인" 이 있어야 "아무거나 떠 봤다"
가 아니라 "가설을 세우고 검증했다" 가 된다. 면접에서 가장 많이 파고드는 자리다.

### 맞교환

이 절이 없으면 "조치 결과만 자랑하는 글" 이 된다. 한 번만 파고들면 무너진다.
있으면 "비용을 아는 사람" 이 된다.

### 한계

감점 요소처럼 보이지만 반대다. 4 CPU VM 에서 단일 세션으로 잰 숫자를 운영
실적처럼 쓰면 면접에서 들통난다. 밝히고 쓰면 환경의 한계를 아는 지원자가 된다.

특히 이 랩에서 교과서처럼 나오지 않는 지표가 있다. 로그 파일이 로컬 디스크라
`log file sync` 가 작게 나오고, 버퍼 캐시 상태에 따라 경과 시간이 흔들린다.
그럴 때 무엇으로 대신 읽었는지 적는다.
