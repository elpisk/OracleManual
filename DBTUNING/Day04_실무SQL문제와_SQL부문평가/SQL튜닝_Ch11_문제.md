# Chapter 11. 페이징 SQL 튜닝 — 실습문제 10제

`SQL튜닝_Ch11_교안.md`를 먼저 읽고 푸시기 바랍니다. 모든 결과는 실습 DB 실측입니다.
실습에서 만든 인덱스는 각자 실습 종료 시 반드시 `DROP INDEX`로 정리하시오.

---

**1. [상]** OFFSET 0, 200,000, 280,000 세 경우 모두 Buffers가 3,090으로 동일했다. 이
쿼리가 `TABLE ACCESS FULL`을 사용한다는 사실을 근거로 왜 OFFSET 값과 무관하게 Buffers가
같은지 설명하시오.

**2. [상]** Buffers는 동일한데 A-Time은 0.02초에서 0.18초로, Used-Mem은 2K에서 14M로
크게 증가했다. 이 증가가 어느 오퍼레이션(`WINDOW SORT PUSHED RANK`)에서 비롯됐는지,
그리고 왜 OFFSET이 클수록 그 오퍼레이션의 부담이 커지는지 설명하시오.

**3. [최상]** "Buffers가 안 늘었으니 이 페이징 쿼리는 페이지가 깊어져도 문제없다"고
판단한 개발자가 있다면, 이 판단이 왜 위험한지 실측 결과를 근거로 반박하시오.

**4. [상]** Keyset 방식(Q4)은 Buffers 25, A-Time 0.01초로 OFFSET 280,000 방식(Buffers
3,090, A-Time 0.18초)보다 압도적으로 저렴했다. 실행계획에서 `WINDOW NOSORT STOPKEY`와
`INDEX RANGE SCAN DESCENDING`이 함께 나타난 것이 이 저렴함의 핵심 이유임을 설명하시오.

**5. [상]** Keyset 방식의 `WHERE receipt_date < :마지막_날짜` 조건이 왜 "몇 번째 행인지
셀 필요가 없게" 만들어주는지, OFFSET 방식의 `ROW_NUMBER() OVER (...)` 변환과 대조해서
설명하시오.

**6. [최상]** Keyset 방식은 "10페이지에서 곧바로 500페이지로 이동"하는 것이 어렵다.
왜 이런 제약이 생기는지, 그리고 이 제약이 실무에서 어떤 종류의 화면(UI)에는 문제가 안
되고 어떤 화면에는 문제가 되는지 설명하시오.

**7. [상]** 만약 이 서비스가 "게시판처럼 페이지 번호를 클릭해서 이동하는" 화면이라면
Keyset 방식으로 완전히 대체하기 어려울 수 있다. 이런 경우 OFFSET 방식의 비용을 줄이기
위해 고려해볼 수 있는 절충안을 한 가지 이상 제안하시오. (예: 페이지 번호에 제한을 두는
것 등, 자유롭게 서술)

**8. [상]** `INDEX RANGE SCAN DESCENDING`이라는 오퍼레이션 이름에서 `DESCENDING`이
의미하는 바를 설명하시오. 인덱스는 기본적으로 오름차순으로 저장되는데, 왜 내림차순으로도
효율적으로 읽을 수 있는지 추론하시오.

**9. [최상]** 이번 챕터의 OFFSET 방식은 `receipt_date`에 인덱스가 있는데도
`TABLE ACCESS FULL` + `WINDOW SORT PUSHED RANK`를 선택했다(Keyset 방식과 달리 인덱스를
전혀 안 씀). 인덱스가 있는데도 옵티마이저가 OFFSET 쿼리에서 이를 활용하지 못한 이유를,
OFFSET 쿼리에는 `WHERE` 조건이 없다는 점과 연결지어 추론하시오.

**10. [최상]** 이번 챕터와 Chapter 9(UNION의 SORT UNIQUE)의 공통점을 찾아, "Buffers만
보고 튜닝 여부를 판단하면 안 되는 이유"를 종합적으로 정리하시오. 두 챕터에서 각각 어떤
오퍼레이션이 Buffers에 안 잡히는 비용을 유발했는지 함께 언급하시오.
