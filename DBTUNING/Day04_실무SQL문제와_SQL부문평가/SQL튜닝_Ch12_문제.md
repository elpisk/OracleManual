# Chapter 12. 실무에서 자주 발생하는 SQL 문제 — 실습문제 10제

`SQL튜닝_Ch12_교안.md`를 먼저 읽고 푸시기 바랍니다. 모든 결과는 실습 DB 실측입니다.

---

**1. [상]** N+1 패턴을 20번 반복 실행한 결과 `V$SQL`에서 `EXECUTIONS=20`,
`BUFFER_GETS=132,468`로 나타났다. 이 두 숫자로부터 "1회 평균 Buffers"를 계산하고, 이
값이 Chapter 4에서 확인한 `CLAIM_DETAILS` 단건 조회 Full Scan 비용(약 6,621)과 거의
일치하는 이유를 설명하시오.

**2. [상]** 조인 1회 버전의 실행계획에서 `CLAIM_DETAILS`에 대한 `TABLE ACCESS FULL`이
몇 번 나타나는지 확인하고, 이것이 N+1 버전과 근본적으로 다른 지점임을 설명하시오.

**3. [최상]** N+1 버전의 총 Buffers(132,468)와 조인 1회 버전의 총 Buffers(6,645)의
비율이 대략 20에 가까운 이유를 03절의 원리로 설명하시오. 만약 목록 건수가 20건이 아니라
200건이었다면 이 비율이 어떻게 달라질지(더 커질지, 비슷할지, 작아질지) 예측하시오.

**4. [상]** 교안 06절은 "개발 환경에서는 N+1 문제가 잘 안 보인다"고 설명한다. 목록이
5건일 때와 100건일 때 N+1 버전의 예상 Buffers를 각각 계산하고(6,623×건수로 근사),
왜 적은 데이터로 테스트하면 이 문제를 놓치기 쉬운지 설명하시오.

**5. [상]** N+1의 각 반복 조회는 실행계획 하나만 보면 딱히 "나쁜 SQL"처럼 안 보일 수
있다(단순한 WHERE 조건 하나짜리 SELECT). 이 문제를 실행계획 하나만 봐서는 알아채기
어려운 이유와, 대신 확인해야 할 것(`V$SQL`의 어떤 컬럼)을 설명하시오.

**6. [최상]** 교안 07절은 "인덱스를 추가하는 것은 완화책이지 근본 해법이 아니다"라고
말한다. `CLAIM_DETAILS(CLAIM_ID)`에 인덱스를 추가한 뒤에도 N+1 패턴을 그대로 유지한다면
여전히 남아있는 문제가 무엇인지 설명하시오. (힌트: 반복 횟수 자체는 줄어드는가?)

**7. [상]** 이번 실습에서 N+1 패턴은 바인드 변수(`:B1`)를 사용했다(같은 SQL_ID를
20번 재사용). 만약 바인드 변수 대신 매번 다른 리터럴 값으로 `CLAIM_ID`를 하드코딩했다면,
Chapter 2에서 배운 원리에 따라 어떤 추가 문제가 더 생겼을지 설명하시오.

**8. [상]** N+1을 조인으로 바꾸는 것 외에, 애플리케이션 레벨에서 고려할 수 있는 다른
대안을 하나 제안해보시오. (힌트: 여러 `claim_id`를 한 번에 모아서 `IN` 절로 조회하는
방법 등 — Chapter 6·8의 개념을 응용할 수 있는지 생각해볼 것)

**9. [최상]** 교안 05절의 조인 1회 실행계획을 보면 `MEDICAL_CLAIMS`(20건 대상)는
`COUNT STOPKEY`로 처리되어 Buffers 23에 그쳤지만, `CLAIM_DETAILS`(전체 90만 건)는
`TABLE ACCESS FULL`로 Buffers 6,622가 들었다. 두 테이블 접근 방식의 비용 차이가 왜
이렇게 큰지 두 테이블의 규모 차이로 설명하시오.

**10. [최상]** 코드 리뷰에서 "이 API가 목록 조회 후 각 항목마다 상세 조회를 반복하고
있다"는 코드를 발견했다고 하자. 실행계획을 하나씩 확인하는 것 외에, 이 문제를 발견하기
위해 어떤 도구나 방법(로그, APM, DB 세션 통계 등)을 쓸 수 있을지 자유롭게 제안하시오.
