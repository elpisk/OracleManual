 8장 실습 03 — Top 10 Foreground Events 판독 (상위 대기와 DB Time 비중 지목)
 목표: Top 10 Foreground Events를 % DB time 기준으로 읽어 병목을 지목한다.
       'DB CPU가 1위'의 의미를 이해하고, log file sync를 주범으로 오판하는
       상황을 재현·교정한다. 작은 Concurrency 대기들을 하드파싱 경합으로 묶는다.
 환경: non-CDB=orcl 19.3 (SYS AS SYSDBA)
 부하: WL_06_mixed.sql (7세션). 보고서 awrrpt_1_479_480.txt 사용.
 라이선스: 🔒 Diagnostics Pack. 미보유 시 V$SYSTEM_EVENT/V$SYSTEM_WAIT_CLASS 델타(하단).
================================================================================

$ sqlplus / as sysdba

SYS@orcl> SET LINESIZE 200

SYS@orcl> SET PAGESIZE 100

-- [2] (해석 1) 맨 윗줄부터 읽는다 — DB CPU 62.2%.
--------------------------------------------------------------------------------
-- DB CPU 는 대기가 아니라 '실제로 쓴 CPU 시간'이다. % DB time 62.2% 는 전체
--   DB Time 의 6할이 CPU 라는 뜻이고, 나머지 4할 가까이가 대기다.
-- 실습 02 의 Load Profile(DB CPU 0.4/s vs DB Time 0.7/s)이 여기서 확증된다.

--------------------------------------------------------------------------------
-- [3] (해석 2) 작은 대기들을 '방향'으로 묶는다.
--------------------------------------------------------------------------------
-- kksfbc child completion(23.0%) + cursor: pin S wait on X(10.0%) + library cache: mutex X(1.6%)
--   + library cache lock(.6%) + latch: shared pool(.3%) + cursor: pin S(.2%) + library cache load lock(.2%)
--   → 클래스는 Other 와 Concurrency 로 갈리지만 전부 '커서를 만들고 잡는' 공유 풀/라이브러리 캐시
--     경합이다. 합치면 약 36% — 초당 355번의 하드 파싱(실습 02)이 만든 경합이 한 방향을 가리킨다.
--     (kksfbc child completion = 다른 세션이 같은 SQL 의 자식 커서를 다 만들 때까지 기다리는 대기.)
-- Avg Wait 도 본다: kksfbc 는 48.62ms(드물지만 길다 — 231회), cursor: pin S wait on X 는 1.45ms
--   (짧지만 3,378회로 잦다). 총시간 = 횟수 × 평균 → 처방이 다르다.

--------------------------------------------------------------------------------
-- [4] (조회) 대기 클래스별 집계로 '경합(Concurrency)'의 크기를 확인한다.
--------------------------------------------------------------------------------
SYS@orcl> HOST awk '/^Wait Classes by Total Wait Time/,/^Host CPU/' awrrpt_1_479_480.txt

--   User I/O 는 .6% — 디스크는 이 구간의 문제가 아니다(실습 02 의 물리 읽기 2.6/s 와 일치).
--   V$SYSTEM_EVENT 로 같은 것을 보려면 누적값이라 구간 델타를 떠야 한다(5장 실습 06).

--------------------------------------------------------------------------------
-- [5] (이상 징후 → 원인 → 조치 → 재확인)
--     이상 징후: 동료가 "kksfbc child completion 의 평균 대기 48ms 가 제일 기니까
--       이 이벤트 자체를 튜닝하자(숨은 파라미터 검색)"고 주장한다.
--------------------------------------------------------------------------------
-- 원인 파악: 이벤트 이름을 '증상'이 아니라 '원인'으로 착각한 오판이다. 판정은
--   % DB time 과 원인의 뿌리로 해야 한다.
SYS@orcl> SELECT 23.0 + 10.0 + 1.6 + .6 + .3 + .2 + .2 AS parse_waits_pct, 62.2 AS dbcpu_pct FROM dual;

PARSE_WAITS_PCT  DBCPU_PCT
--------------- ----------
           35.9       62.2

-- 원인 확정: 파싱 계열 대기 35.9% 는 이벤트 하나가 아니라 '초당 355번 하드 파싱'이라는
--   한 원인의 여러 얼굴이다. 그 하드 파싱은 DB CPU 62.2% 의 상당 부분도 태운다
--   (Instance Efficiency 의 % Non-Parse CPU 67.5% = CPU 의 1/3 이 파싱).
-- 조치: 이벤트를 쫓지 말고 원인을 없앤다 → 실습 04에서 리터럴로 파싱을 부르는 상위
--   SQL 을 찾아 바인드 변수화(또는 CURSOR_SHARING)로 하드 파싱을 줄인다.
-- 재확인: 조치 후 같은 부하로 보고서를 다시 떠 kksfbc·cursor: pin S wait on X 와
--   Hard parses (SQL)/s 가 함께 줄어야 한다. 둘 중 하나만 줄면 원인이 틀린 것이다.

--------------------------------------------------------------------------------
-- [대안 경로] 🔒 미보유 — V$로 Top Events를 델타로 만든다.
--------------------------------------------------------------------------------
-- 부하 전/후로 아래를 두 번 찍어 (후-전)으로 상위 대기를 정렬한다.
--   SELECT event, total_waits, time_waited_micro, wait_class
--     FROM v$system_event ORDER BY time_waited_micro DESC;
-- DB CPU 상당량은 V$SYS_TIME_MODEL의 'DB CPU' 델타로 확인한다. 이렇게
-- 만든 목록을 보고서 Top Events와 동일하게 % 기준으로 판독한다(5장 실습 06 의 표 세 개).

--------------------------------------------------------------------------------
-- [정리]
--------------------------------------------------------------------------------
-- 1) Top Events 는 % DB time 으로 읽는다. 절대 Total 시간이나 평균 대기가 아니다.
-- 2) DB CPU 62.2% + 파싱 계열 대기 36% = 이 구간은 'CPU + 공유 풀 경합' 구간.
-- 3) 작은 대기(kksfbc/cursor pin S/mutex/latch/library cache)는 하드 파싱 경합으로
--    묶어 하나의 원인으로 수렴시킨다.
-- 4) 이벤트 이름을 원인으로 착각해 이벤트 자체를 튜닝하려 하면 오판 → 원인(하드 파싱) 우선.
-- 5) 라이선스 없으면 V$SYSTEM_EVENT 델타 + V$SYS_TIME_MODEL 로 동일 판독.

SYS@orcl> EXIT
