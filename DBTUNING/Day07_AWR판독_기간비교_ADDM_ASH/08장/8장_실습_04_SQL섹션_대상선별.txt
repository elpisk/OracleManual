 목표: 진단 가설(CPU 바운드 + 대량 논리읽기)에 맞는 정렬 기준을 골라 주범 SQL을
       특정한다. 두 정렬이 같은 SQL을 지목할 때 신뢰도가 높음을 확인한다.
       Reads 정렬을 무작정 1순위로 보는 오판을 교정한다.
 환경: non-CDB=orcl 19.3 (SYS AS SYSDBA)
 부하: WL_06_mixed.sql (7세션). 보고서 awrrpt_1_479_480.txt 사용.
 라이선스: 🔒 Diagnostics Pack. 미보유 시 V$SQL 정렬로 대체(하단).

-- [3] (해석) 두 정렬이 같은 SQL 무리를 지목 → 진단 신뢰도가 높다.
--------------------------------------------------------------------------------
-- Elapsed 와 Gets 가 모두 같은 SQL 들(전체 스캔·해시 조인·정렬, 그리고 대량 반복 단건 조회)로
--   수렴하고, %CPU 95~99% 가 Top Events DB CPU 와 일치한다. 서로 다른 섹션의 숫자가 한 무리로 모인다.
-- 여기까지가 8장(인스턴스 층위)의 결론이다: 'CPU 시간의 대부분은 몇 개의 전체 스캔·조인·정렬 SQL 과
--   초당 수천 번 도는 단건 조회가 쓴다.' 이 SQL 들의 재작성(인덱스·조인·바인드)은 SQL 튜닝
--   과정(Day 1~4)으로 인계한다.

--------------------------------------------------------------------------------
-- [4] (조회) Captured SQL 비중이 29.6% 뿐인 이유를 확인한다.
--------------------------------------------------------------------------------

  2         ROUND(29.6 - (8.0 + 7.2 + 6.0 + 2.3), 1) AS rest_captured FROM dual;

--   잡히는데 SQL 로는 30% 도 안 잡히는 차이 = 나머지는 문장마다 SQL_ID 가 다른 리터럴 SQL
--   (WL06_LIT)이라 개별로는 순위에 못 들고 흩어진 몫이다(실습 02 의 하드 파싱 355/s).
--   이 조합 자체가 '리터럴이 조각나 있다'는 또 하나의 증거다.

-- [대안 경로] 🔒 미보유 — V$SQL을 정렬해 같은 SQL을 찾는다.
--------------------------------------------------------------------------------
SYS@orcl> COLUMN sql_text FORMAT A40

SYS@orcl> SELECT sql_id, buffer_gets, ROUND(cpu_time/1e6,1) cpu_sec, executions, SUBSTR(sql_text,1,40) sql_text
  2       FROM  v$sql WHERE parsing_schema_name = 'SQLT' AND command_type = 3
  3       ORDER BY buffer_gets DESC FETCH FIRST 5 ROWS ONLY;

-- [정리]
--------------------------------------------------------------------------------
-- 1) 정렬 기준은 진단 가설에 맞춘다: CPU·논리읽기→Elapsed/Gets, 디스크→Reads.
-- 2) PL/SQL 블록 행은 안의 SQL 을 합산한 값 — 튜닝 대상은 그 아래 개별 SQL 이다.
-- 3) 실측: 전체 스캔(gz97yq3a3n02v)·해시 조인(8yy5q06wvrpga)·정렬(0dhsm13grpw10)·
--    대량 단건 조회(3gy9h99h9d54n)가 Elapsed·Gets 에서 함께 상위(%CPU 95~99%) → 주범 무리 확정.
-- 4) Captured SQL 29.6% 뿐 = 리터럴이 조각나 순위 밖에 흩어진 증거.
-- 5) Reads 1위를 무작정 고르면 오판 → 물리읽기가 작은 구간에선 부적합.
-- 6) 라이선스 없으면 V$SQL 정렬로 대상 선별 가능.
