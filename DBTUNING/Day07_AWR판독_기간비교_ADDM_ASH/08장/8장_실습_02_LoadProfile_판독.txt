================================================================================
 8장 실습 02 — Load Profile 판독 (초당 논리 읽기·파싱·트랜잭션 해석)
 목표: 부하 구간(295~296) 보고서의 Load Profile을 읽어 이 구간이 CPU 바운드인지,
       메모리 위 대량 스캔인지, 리터럴 하드파싱인지 판정한다. 절대값이 아니라
       항목 간 비율로 읽는 훈련. '무부하로 착각' 이상 상황을 원인·조치까지 다룬다.
 환경: non-CDB=orcl 19.3 (SYS AS SYSDBA)
 부하: WL_06_mixed.sql (7세션 종합 부하). 실측 보고서 awrrpt_1_295_296.txt 사용.
 라이선스: 🔒 Diagnostics Pack. 미보유 시 V$SYSSTAT/V$SYS_TIME_MODEL 델타로 대체(하단).
================================================================================

$ sqlplus / as sysdba

SYS@orcl> SET LINESIZE 200
SYS@orcl> SET PAGESIZE 100

--------------------------------------------------------------------------------
-- [1] (조치 전 상태) 보고서에서 Load Profile 섹션만 발췌해 본다.
--     (awrrpt_1_295_296.txt의 Load Profile 블록)
--------------------------------------------------------------------------------
SYS@orcl> HOST sed -n '61,77p' awrrpt_1_295_296.txt

--------------------------------------------------------------------------------
-- [2] (해석 1) DB Time vs DB CPU — 이 구간은 무엇에 시간을 썼나?
--------------------------------------------------------------------------------
-- DB Time(s) 5.5, DB CPU(s) 5.3 → 초당 DB Time의 약 96%가 CPU다.
--   즉 대기가 아니라 CPU를 태우며 돌아간 'CPU 바운드' 구간이다.
--   대기 튜닝(리두·I/O)이 아니라 CPU를 쓰는 SQL·논리읽기를 줄여야 한다.

--------------------------------------------------------------------------------
-- [3] (해석 2) 논리 읽기 vs 물리 읽기 — 메모리인가 디스크인가?
--------------------------------------------------------------------------------
-- Logical read 1,185,107/s vs Physical read 48.8/s.
--   물리 읽기가 미미하고 논리 읽기가 폭발적 → 데이터는 이미 버퍼 캐시에 있고
--   그 위를 대량으로 반복 스캔하고 있다. (뒤 Instance Efficiency의 Buffer Hit
--   100%와 일치한다. 실습 03·06에서 교차 확인)
-- Per Transaction 5,735.2 → 한 트랜잭션이 5천 블록 넘게 읽는 무거운 업무다.

--------------------------------------------------------------------------------
-- [4] (해석 3) 파싱 — 하드 파싱 비율을 계산한다.
--------------------------------------------------------------------------------
SYS@orcl> SELECT ROUND(319.0/433.7*100,1) AS hard_parse_pct FROM dual;

HARD_PARSE_PCT
--------------
          73.6

-- 해석: 전체 파싱 433.7/s 중 하드 파싱이 319.0/s = 약 73.6%.
--   정상 애플리케이션이라면 바인드 변수로 하드 파싱은 거의 0이어야 한다.
--   73.6%는 리터럴 SQL이 쏟아지고 있다는 강력한 신호다(→ 실습 03 대기로 확증).

--------------------------------------------------------------------------------
-- [5] (조회) 보고서 없이 V$로 같은 논리 읽기 순간값을 참고로 확인한다.
--     (부하가 끝난 뒤라 값은 환경/시점에 따라 다르다 → <환경값>)
--------------------------------------------------------------------------------
SYS@orcl> SELECT metric_name, ROUND(value) val, metric_unit
  2       FROM  v$sysmetric
  3       WHERE metric_name IN ('Logical Reads Per Sec','Hard Parse Count Per Sec')
  4         AND intsize_csec BETWEEN 5900 AND 6100
  5       ORDER BY metric_name;

METRIC_NAME                         VAL METRIC_UNIT
------------------------------ -------- -------------------------
Hard Parse Count Per Sec       <환경값> Parses Per Second
Logical Reads Per Sec          <환경값> Reads Per Second

-- 해석: V$SYSMETRIC은 최근 60초 순간값이라 보고서 구간(295~296)과 시점이
--   다르면 값이 다르다. 보고서의 델타값(1,185,107/s, 319/s)이 그 구간의
--   확정 실측이고, V$는 지금 이 순간을 보는 창이다. 두 창을 혼동하지 않는다.

--------------------------------------------------------------------------------
-- [6] (이상 징후 → 원인 → 조치 → 재확인)
--     이상 징후: 다른 신입이 "물리 읽기 48.8/s로 낮으니 I/O 성능이 완벽,
--       튜닝 필요 없음"이라 판정했다.
--------------------------------------------------------------------------------
-- 원인 파악: 물리 읽기만 보고 논리 읽기(1,185,107/s)를 놓친 오판이다.
--   물리 읽기가 낮은 것은 데이터가 캐시에 있어서일 뿐, 그 캐시를 과도하게
--   반복 스캔하는 것 자체가 CPU를 태우는 문제다.
SYS@orcl> SELECT ROUND(1185107/48.8) AS logical_to_physical_ratio FROM dual;

LOGICAL_TO_PHYSICAL_RATIO
-------------------------
                    24285

-- 원인 확정: 논리:물리 = 약 24,285:1. 디스크는 한가하지만 메모리 위에서
--   블록을 24만 배 더 훑고 있다. I/O가 아니라 논리 읽기가 병목의 씨앗이다.
-- 조치: 논리 읽기를 유발하는 상위 SQL을 찾아 개선한다(실습 04에서 9vmszgd1ft9x0
--   지목). I/O 서브시스템이나 캐시 크기를 건드리는 것이 아니다.
-- 재확인: DB CPU(s)≈DB Time(s)이므로 병목이 CPU임을 다시 확인 → I/O 튜닝은
--   이 구간의 해법이 아니다. 판정 번복.

--------------------------------------------------------------------------------
-- [대안 경로] 🔒 미보유 — V$로 Load Profile을 델타로 재구성한다.
--------------------------------------------------------------------------------
-- 부하 전/후로 아래를 두 번 찍어 (후-전)/경과초로 나누면 Per Second가 나온다.
--   SELECT name, value FROM v$sysstat
--    WHERE name IN ('session logical reads','parse count (hard)',
--                   'parse count (total)','physical reads','redo size',
--                   'user calls','user commits');
-- DB Time/CPU는 V$SYS_TIME_MODEL('DB time','DB CPU')의 델타로 구한다.
-- 이렇게 구한 값을 보고서 Load Profile과 동일한 방식으로 판독한다.

--------------------------------------------------------------------------------
-- [정리]
--------------------------------------------------------------------------------
-- 1) Load Profile은 절대값이 아니라 '항목 간 비율'로 읽는다.
-- 2) DB CPU≈DB Time → CPU 바운드. 논리 118만 : 물리 48.8 → 메모리 반복 스캔.
-- 3) 하드 파싱 73.6% → 리터럴 SQL 신호(실습 03에서 대기로 확증).
-- 4) 물리 읽기만 보고 'I/O 완벽'이라 하면 오판 → 논리 읽기·DB CPU와 함께 본다.
-- 5) 라이선스 없으면 V$SYSSTAT/V$SYS_TIME_MODEL 델타로 동일 판독 가능.

SYS@orcl> EXIT
