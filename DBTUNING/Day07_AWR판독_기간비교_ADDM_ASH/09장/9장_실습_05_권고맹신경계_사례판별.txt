 9장 실습 05 — 권고를 그대로 따르면 안 되는 사례 판별 (권고 맹신 경계)  🔒
 목표: ADDM 권고를 무비판적으로 따를 때의 두 함정(① 영향도 낮은 권고부터 처리,
       ② 부작용 검토 없는 파라미터 적용)을 실측 데이터로 판별하고 교정한다.
       "권고는 가설이지 결론이 아니다"를 절차로 각인한다.
 환경: non-CDB=orcl 19.3 (SYS AS SYSDBA). 단일 인스턴스.
 참조: 실습 01의 태스크 TUNING_CH9_ADDM_296 (스냅샷 295~296)
 라이선스: 🔒 Diagnostics Pack 필요.
 주의: 개인 실습 환경 전용. 파라미터 변경 실습이 포함된다 — 반드시 원복한다.

$ sqlplus / as sysdba

SYS@orcl> SET LINESIZE 200 PAGESIZE 100

--------------------------------------------------------------------------------
-- [1] (조치 전 상태) Finding을 영향도 순으로 다시 확인한다.
--------------------------------------------------------------------------------
SYS@orcl> SELECT f.finding_name, f.type,
  2         ROUND(f.impact/1000000,2) impact_sec,
  3         ROUND(f.impact/574000000*100,2) pct
  4       FROM dba_advisor_findings f JOIN dba_advisor_tasks t USING (task_id)
  5       WHERE t.task_name='TUNING_CH9_ADDM_296' AND f.type='PROBLEM'
  6       ORDER BY f.impact DESC;

FINDING_NAME                     TYPE      IMPACT_SEC    PCT
-------------------------------- -------- ----------- ------
Top SQL Statements               PROBLEM      348.72   60.78
Hard Parse Due to Literal Usage  PROBLEM       33.38    5.82
Commits and Rollbacks            PROBLEM       21.15    3.69
Soft Parse                       PROBLEM       13.65    2.38

--------------------------------------------------------------------------------
-- [2] (오판 사례 ①) "Soft Parse·Commits는 파라미터로 쉽게 고치니 먼저 하자"
--------------------------------------------------------------------------------
--    → 판별: 영향도 낮은 권고부터 처리하려는 오판이다.
--       Soft Parse(2.38%) + Commits(3.69%) = 6.07% 를 완벽히 없애도
--       최대 개선은 6% 남짓이다(Amdahl의 법칙). 반면 Top SQL(60.78%)을
--       절반만 줄여도 30%가 개선된다.
--    → 근거 확인: 상·하위 영향도 격차가 10배 이상이다.
SYS@orcl> SELECT ROUND(MAX(impact)/NULLIF(MIN(impact),0),1) AS gap
  2       FROM dba_advisor_findings f JOIN dba_advisor_tasks t USING (task_id)
  3       WHERE t.task_name='TUNING_CH9_ADDM_296' AND f.type='PROBLEM';

       GAP
----------
      25.5

--    → 조치(교정): ADDM이 정렬해 준 순서대로 Top SQL(60.78%)부터 처리한다.
--       권고대로 SQL_ID 9vmszgd1ft9x0 에 SQL Tuning Advisor를 돌려 다음 단계로
--       좁힌다. "쉬운 것"이 아니라 "영향 큰 것"부터가 원칙이다.

--------------------------------------------------------------------------------
-- [3] (오판 사례 ②) "Literal 권고에 CURSOR_SHARING=FORCE를 바로 운영 적용하자"
--------------------------------------------------------------------------------
-- 권고 원문: 바인드 변수를 쓰라, 어렵다면 CURSOR_SHARING을 FORCE로.
-- 조치 전 현재 값을 반드시 캡처한다(근거 남기기).
SYS@orcl> SELECT value FROM v$parameter WHERE name='cursor_sharing';

VALUE
----------
EXACT

--    → 판별: FORCE는 구현이 쉽고 하드 파싱을 줄이지만 공짜가 아니다.
--       리터럴을 강제로 바인드로 치환하면서 히스토그램 기반 카디널리티 추정이
--       흐트러져 일부 SQL의 실행계획이 나빠질 수 있다. ADDM은 이 트레이드오프를
--       대신 판단해 주지 않는다.
--    → 조치: 최선은 애플리케이션의 바인드 변수 도입이다. 파라미터 변경을
--       택한다면 세션 수준에서 먼저 시험하고 계획 변화를 관찰한 뒤 결정한다.

SYS@orcl> ALTER SESSION SET cursor_sharing=FORCE;   -- (운영 전, 세션에서만 시험)
세션이 변경되었습니다.

-- (대상 SQL을 재실행하며 V$SQL_PLAN으로 계획 변화·성능을 관찰한다 ... <환경값>)

--    → 재확인·원복: 시험이 끝나면 반드시 원래 값으로 되돌린다.
SYS@orcl> ALTER SESSION SET cursor_sharing=EXACT;
세션이 변경되었습니다.
