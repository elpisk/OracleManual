# Chapter 4. Full Scan vs Index Scan — 실습문제 10제

`SQL튜닝_Ch04_교안.md`를 먼저 읽고 푸시기 바랍니다. 모든 결과는 실습 DB 실측입니다.

---

**1. [상]** HOSPITALS(1,000건)에서 800건이 걸리는 조건을 Full Scan으로 처리했을 때
Buffers는 15였다. CLAIM_DETAILS(약 90만 건)에서 단 3건이 걸리는 조건을 Full Scan으로
처리했을 때 Buffers는 6,621이었다. 결과 건수는 CLAIM_DETAILS 쪽이 훨씬 적은데 왜 Buffers는
훨씬 많은지 설명하시오.

**2. [상]** `PK_MEDICAL_CLAIMS` 범위 조회에서 838건(0.3%)은 Index Range Scan(Buffers
731), 25,406건(8.5%)은 Full Scan(Buffers 3,090)으로 처리됐다. 이 두 결과를 근거로
"인덱스가 있다고 항상 인덱스를 쓰는 것은 아니다"라는 명제를 설명하시오.

**3. [상]** 25,406건(8.5%), 148,028건(49%), 274,000여건(91%) 세 경우 모두 Buffers가
3,090으로 동일했다. 결과 건수가 10배 넘게 차이 나는데 Buffers가 똑같은 이유를 Full Scan의
비용 특성으로 설명하시오.

**4. [최상]** `COUNT(*)`만 필요한 쿼리는 148,028건(49% 선택도)에서도 인덱스를 유지해
Buffers 910이었지만, `SUM(total_amt)`가 필요한 쿼리는 같은 범위에서 이미 Full Scan(Buffers
3,090)으로 전환되어 있었다. 두 쿼리의 차이(`COUNT(*)` vs `SUM(total_amt)`)가 왜 이런
결과 차이를 만드는지, `TOTAL_AMT` 컬럼이 인덱스에 포함되어 있는지 여부를 근거로 설명하시오.

**5. [상]** 선택도(selectivity)와 카디널리티(cardinality)의 차이를 정의하고, 이번
챕터의 838건/25,406건/148,028건 사례에 각각의 선택도(%)를 계산해 표시하시오. (전체
30만 건 기준)

**6. [최상]** "선택도가 10% 이하면 항상 인덱스를 써야 한다"는 규칙을 어떤 신입 개발자가
제안했다고 하자. 이번 챕터의 실측 결과(특히 4번 문항)를 근거로 이 규칙이 왜 항상 맞지는
않는지 반박하시오.

**7. [상]** HOSPITALS는 1,000건짜리 작은 테이블이라 Full Scan Buffers가 15에 불과했다.
만약 HOSPITALS에 `HOSP_TYPE` 인덱스를 만든다면, 이미 충분히 저렴한 이 쿼리의 성능이
개선될 여지가 있을지, 아니면 오히려 손해일 수 있는지 논하시오. (힌트: 인덱스를 통해
테이블에 접근하려면 최소 1~2블록의 인덱스 접근 + 테이블 접근이 필요하다.)

**8. [상]** 이번 챕터에서 관찰한 "선택도가 낮을 때 인덱스 유리 / 높을 때 Full Scan 유리"
경향이, 실제로는 정확히 몇 %에서 뒤바뀌는지 하나의 숫자로 단정할 수 없는 이유를 설명하시오.
(힌트: 교안 07절 — 테이블 크기, 클러스터링 팩터, 인덱스만으로 처리 가능한지 여부 등.)

**9. [최상]** REVIEW_LOG는 50만 건으로 CLAIM_DETAILS(약 90만 건)보다는 작지만
HOSPITALS(1,000건)보다는 훨씬 크다. `REVIEW_LOG`에서 `REVIEWER_ID = 'SYSTEM'`인 행을
찾는 쿼리(인덱스 없음, 전체의 약 40%가 SYSTEM으로 추정)가 Full Scan으로 처리될지
Index Scan으로 처리될지, 그리고 왜 그렇게 예상하는지 이번 챕터의 원칙을 적용해 논하시오.
(직접 실행할 필요는 없음 — 원칙 적용 훈련 문제)

**10. [최상]** 이번 챕터에서 다룬 두 축(테이블 크기, 선택도)을 종합해서, "Full Scan이
유리한 상황"을 스스로 정의해보시오. 최소 두 가지 이상의 조건(예: 테이블 크기 관련 조건 1개,
선택도 관련 조건 1개)을 포함해 서술하시오.
