 Ch04 실습 02 — 선택도에 따라 인덱스 → Full Scan 으로 전환되는 교차점 찾기 (PK 범위 확대)
 목표: PK_MEDICAL_CLAIMS 로 범위를 1일 → 1개월 → 6개월 → 11개월로 넓혀 가며 Operation 이
       INDEX RANGE SCAN(731) 에서 TABLE ACCESS FULL(3,090) 로 바뀌는 지점을 실측한다.
       "범위를 10배 넓혔는데 Buffers 가 그대로" 인 이상 징후를 Full Scan 고정 비용으로 설명한다.
 환경: non-CDB=orcl 19.3, 스키마 SQLT. 바인드 변수 :end_id 사용.
 주의: 개인 실습 환경 전용. 조회만 수행한다. 교차점의 정확한 위치는 통계·환경에 따라 다르다.
================================================================================

$ sqlplus sqlt/sqlt@orcl

SQLT@orcl> SET LINESIZE 200
SQLT@orcl> SET PAGESIZE 100
SQLT@orcl> VARIABLE end_id VARCHAR2(20)

--------------------------------------------------------------------------------
-- [1] (조치 전 상태) 약 1일 범위 — 838건, 0.3%
--------------------------------------------------------------------------------
SQLT@orcl> EXEC :end_id := '20240102-0000000'

PL/SQL procedure successfully completed.

SQLT@orcl> SELECT /*+ GATHER_PLAN_STATISTICS */ SUM(total_amt)
  2       FROM   medical_claims
  3       WHERE  claim_id BETWEEN '20240101-0000000' AND :end_id;

SUM(TOTAL_AMT)
--------------
     <환경값>

SQLT@orcl> SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR(NULL, NULL, 'ALLSTATS LAST'));

PLAN_TABLE_OUTPUT
--------------------------------------------------------------------------------------------------------
| Id  | Operation                            | Name              | Starts | E-Rows | A-Rows | Buffers |
--------------------------------------------------------------------------------------------------------
|   0 | SELECT STATEMENT                     |                   |      1 |        |      1 |     731 |
|   1 |  SORT AGGREGATE                      |                   |      1 |      1 |      1 |     731 |
|*  2 |   FILTER                             |                   |      1 |        |    838 |     731 |
|   3 |    TABLE ACCESS BY INDEX ROWID BATCHED| MEDICAL_CLAIMS   |      1 |  <환경값> |    838 |     731 |
|*  4 |     INDEX RANGE SCAN                 | PK_MEDICAL_CLAIMS |      1 |  <환경값> |    838 |       6 |
--------------------------------------------------------------------------------------------------------
   2 - filter('20240101-0000000'<=:END_ID)
   4 - access("CLAIM_ID">='20240101-0000000' AND "CLAIM_ID"<=:END_ID)

-- 해석: 인덱스에서 838건의 ROWID 를 6블록으로 찾고(Id 4), 표에서 TOTAL_AMT 를 읽는 데 725블록(Id 3).
--   838건이 725개 블록에 흩어져 있다 — 행 하나당 거의 블록 하나. CLAIM_ID 순서와 표의 물리 순서가
--   다르기 때문(클러스터링 팩터). 그래도 3,090 보다는 싸다.
--   FILTER(Id 2)는 바인드 값이 시작값보다 작으면 아예 읽지 않기 위한 방어 단계다.

--------------------------------------------------------------------------------
-- [2] (이상 징후 → 원인 → 재확인) 범위를 넓히면 — 1개월 / 6개월 / 11개월
--------------------------------------------------------------------------------
SQLT@orcl> EXEC :end_id := '20240201-0000000'            -- 약 1개월
SQLT@orcl> SELECT /*+ GATHER_PLAN_STATISTICS */ SUM(total_amt)
  2       FROM   medical_claims
  3       WHERE  claim_id BETWEEN '20240101-0000000' AND :end_id;
(결과 생략)
SQLT@orcl> SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR(NULL, NULL, 'ALLSTATS LAST'));

PLAN_TABLE_OUTPUT
------------------------------------------------------------------------------------------
| Id  | Operation          | Name           | Starts | E-Rows | A-Rows | Buffers |
------------------------------------------------------------------------------------------
|   1 |  SORT AGGREGATE    |                |      1 |      1 |      1 |    3090 |
|*  2 |   FILTER           |                |      1 |        |  25406 |    3090 |
|*  3 |    TABLE ACCESS FULL| MEDICAL_CLAIMS|      1 |  <환경값> |  25406 |    3090 |
------------------------------------------------------------------------------------------

SQLT@orcl> EXEC :end_id := '20240701-0000000'            -- 약 6개월
(같은 SQL 재실행 — 계획 발췌)
|*  3 |    TABLE ACCESS FULL| MEDICAL_CLAIMS|      1 |  <환경값> | 148028 |    3090 |

SQLT@orcl> EXEC :end_id := '20241201-0000000'            -- 약 11개월
(같은 SQL 재실행 — 계획 발췌)
|*  3 |    TABLE ACCESS FULL| MEDICAL_CLAIMS|      1 |  <환경값> | 274000+|    3090 |

SQLT@orcl> -- 이상 징후: 1개월(25,406건)에서 6개월(148,028건), 11개월(27만 건)로 대상이 10배 넘게
SQLT@orcl> --   늘었는데 Buffers 는 3,090 으로 꿈쩍도 하지 않는다.
SQLT@orcl> -- 원인 파악: 1개월부터 이미 TABLE ACCESS FULL 이다. Full Scan 은 표 전체를 한 번 읽는
SQLT@orcl> --   고정 비용(실습 01)이라 결과가 2만 건이든 27만 건이든 3,090 이다.
SQLT@orcl> --   838건(0.3%)에서 25,406건(8.5%) 사이 어딘가에서 옵티마이저가 "인덱스로 흩어진 블록을
SQLT@orcl> --   하나씩 읽는 비용" 이 "표 전체를 다중 블록으로 읽는 비용" 을 넘어선다고 판단해 전환했다.
SQLT@orcl> -- 재확인: 바인드 값이 바뀌었는데 계획이 바뀐 것에 주목한다 — 같은 SQL_ID 인데 자식 커서가
SQLT@orcl> --   여럿 생겼을 것이다(적응형 커서 공유). Ch02 실습 02 의 "값 1 의 계획이 500 에 재사용" 과
SQLT@orcl> --   달리, 여기서는 범위 조건이라 값에 따라 계획을 다시 만들었다.
SQLT@orcl> SELECT sql_id, child_number, executions, buffer_gets, is_bind_sensitive, is_bind_aware
  2       FROM   v$sql
  3       WHERE  sql_text LIKE '%claim_id BETWEEN ''20240101-0000000'' AND :end_id';

SQL_ID        CHILD_NUMBER EXECUTIONS BUFFER_GETS I I
------------- ------------ ---------- ----------- - -
<환경값>                 0          1         731 Y N
<환경값>                 1          3        9270 Y Y

-- 자식 0(인덱스 계획, 731) 과 자식 1(Full Scan, 3,090 × 3 = 9,270) 로 갈렸다.
--   IS_BIND_AWARE=Y 인 자식이 값 범위에 따라 계획을 고르는 커서다.

--------------------------------------------------------------------------------
-- [3] (조치 후 관점) 교차점 정리
--------------------------------------------------------------------------------
--   ┌────────────┬────────────┬────────┬────────────────────────────────────┬─────────┐
--   │ 범위       │ 대상 건수  │ 선택도 │ Operation                          │ Buffers │
--   ├────────────┼────────────┼────────┼────────────────────────────────────┼─────────┤
--   │ 약 1일     │      838   │  0.3%  │ INDEX RANGE SCAN + BY INDEX ROWID  │    731  │
--   │ 약 1개월   │   25,406   │  8.5%  │ TABLE ACCESS FULL                  │  3,090  │
--   │ 약 6개월   │  148,028   │ 49%    │ TABLE ACCESS FULL                  │  3,090  │
--   │ 약 11개월  │ 274,000여  │ 91%    │ TABLE ACCESS FULL                  │  3,090  │
--   └────────────┴────────────┴────────┴────────────────────────────────────┴─────────┘
-- * "몇 % 부터 Full Scan" 이라는 고정 숫자는 없다. 이 표에서는 838건에 731 Buffers 였으니 약 3,500건
--   (≈1.2%) 근처에서 인덱스 비용이 3,090 을 넘겼을 것이다. 행이 블록에 얼마나 모여 있는가(클러스터링
--   팩터)에 따라 이 점은 크게 움직인다.
-- * 다음 실습 03: SELECT 목록을 바꿔(표를 읽을 필요가 없게) 49% 에서도 인덱스가 유지되는 것을 본다.

--------------------------------------------------------------------------------
-- [정리]
--------------------------------------------------------------------------------
-- 1) 0.3% 에서는 인덱스(731), 8.5% 부터는 Full Scan(3,090). 그 사이에 교차점이 있다.
-- 2) Full Scan 은 고정 비용 — 대상이 10배 늘어도 Buffers 3,090.
-- 3) 인덱스 범위 읽기의 비용은 건수 × 흩어짐(클러스터링 팩터). 838건에 725 표 블록이 그 증거.
-- 4) 범위 조건 바인드는 값에 따라 자식 커서가 갈려 계획이 바뀔 수 있다(IS_BIND_AWARE).

SQLT@orcl> EXIT
