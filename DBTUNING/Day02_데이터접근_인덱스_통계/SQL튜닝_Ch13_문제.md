# Chapter 13. Optimizer와 통계정보 — 실습문제 10제

`SQL튜닝_Ch13_교안.md`를 먼저 읽고 푸시기 바랍니다. 모든 결과는 실습 DB 실측입니다.
`METHOD_OPT`를 바꾸는 실습은 종료 시 반드시 `FOR ALL COLUMNS SIZE AUTO`로 원상복구하시오.

---

**1. [상]** 히스토그램을 제거(`SIZE 1`)한 뒤 `hosp_id=1`과 `hosp_id=500` 두 조건의
E-Rows가 똑같이 300으로 나왔다. 이 숫자(300)가 어떻게 계산됐는지, `MEDICAL_CLAIMS`의
전체 행 수와 `HOSP_ID`의 NDV를 근거로 설명하시오.

**2. [상]** 히스토그램이 있을 때는 `hosp_id=1`의 E-Rows가 3,470, `hosp_id=500`의
E-Rows가 159로 서로 달랐다. 히스토그램이 이 차이를 만들어낼 수 있는 이유를 설명하시오.

**3. [최상]** 히스토그램 제거 후 `hosp_id=1`(실제 3,058건)의 E-Rows는 300으로,
실제보다 약 10배 적게 추정됐다. 이 SQL이 단독으로 실행될 때는 큰 문제가 없어 보일 수
있지만, 만약 이 조건이 `MEDICAL_CLAIMS`와 다른 큰 테이블을 조인하는 쿼리의 일부였다면
어떤 문제로 이어질 수 있는지, Chapter 7(JOIN 실행 원리)의 개념을 활용해 설명하시오.

**4. [상]** `USER_TAB_COL_STATISTICS`에서 `HISTOGRAM` 컬럼 값이 `NONE`에서 `HYBRID`로
바뀐 것을 확인했다. `NUM_BUCKETS`가 1에서 254로 바뀐 것은 무엇을 의미하는지 설명하시오.

**5. [상]** `METHOD_OPT => 'FOR ALL COLUMNS SIZE AUTO'`로 통계를 재수집했더니
`HOSP_ID`에 다시 히스토그램이 생겼다. 이 스키마의 다른 컬럼(예: `PATIENTS.GENDER`,
`MEDICAL_CLAIMS.CLAIM_TYPE`)에도 `SIZE AUTO`가 히스토그램을 만들어줄지, 만들어주지
않을지 예측하고 그 근거를 설명하시오. (힌트: 히스토그램이 필요한 것은 어떤 컬럼인가?)

**6. [최상]** 히스토그램 복원 후 `hosp_id=1`의 E-Rows는 3,285로, 원래 베이스라인(3,470)
과 완전히 같지는 않았다. 두 수치가 정확히 일치하지 않는데도 "히스토그램이 정상적으로
복원됐다"고 판단할 수 있는 근거는 무엇인가?

**7. [상]** 히스토그램을 만들고 유지하는 것도 공짜가 아니다 — 통계 수집 시간이 더
걸리고, 옵티마이저가 실행계획을 세울 때 참고할 데이터도 더 많아진다. 모든 컬럼에 무조건
정밀한 히스토그램을 만드는 것이 항상 좋지는 않은 이유를 추론하시오.

**8. [상]** `DBMS_STATS.GATHER_TABLE_STATS`를 실행할 때 `METHOD_OPT`를 지정하지 않으면
기본값(`FOR ALL COLUMNS SIZE AUTO`)이 적용된다. 이번 실습의 스키마 생성 스크립트가
`METHOD_OPT`를 명시하지 않고 `DBMS_STATS.GATHER_TABLE_STATS(USER, 'MEDICAL_CLAIMS')`
만 호출했는데도 `HOSP_ID`에 히스토그램이 생긴 이유를 설명하시오.

**9. [최상]** 만약 이 서비스에서 `HOSP_ID` 조건으로 조회하는 SQL을 전부 바인드 변수로
작성했다면(Chapter 2), 히스토그램이 있다는 사실이 실제로 얼마나 도움이 될지 논하시오.
(힌트: Chapter 2의 6번 문항 "바인드 변수 Peeking" 내용을 참고할 것 — 바인드 변수는
최초 파싱 시점의 값을 기준으로 계획을 재사용한다.)

**10. [최상]** 이번 챕터에서 히스토그램을 직접 제거·복원하며 확인한 원리를, Chapter 3의
Q1(카디널리티 추정 오류 사례, `CLAIM_TYPE`+`TOTAL_AMT` 조합 조건)에 적용해보시오.
그 사례의 오차가 히스토그램 부재 때문이었는지, 아니면 다른 원인 때문이었는지 판단하고
근거를 설명하시오. (힌트: Chapter 3 해설의 "컬럼 간 상관관계" 설명을 참고할 것)
