 Ch06 실습 03 — 그 밖의 SARGable 위반: 앞 % LIKE, 부정 조건, IS NULL (인덱스가 있어도 못 쓴다)
 목표: PATIENTS.PAT_NAME 과 CITY 에 인덱스를 만들고 LIKE '%값%' / != / IS NULL 세 패턴의 계획을
       실측해 filter 로 밀리는 것을 확인한다. NULL 을 = 로 찾아 "0건" 이 나오는 이상 징후를 재현·교정하고,
       B-Tree 인덱스가 전부 NULL 인 행을 담지 않는 사실을 인덱스 건수와 표 건수의 차이로 증명한다.
 환경: non-CDB=orcl 19.3, 스키마 SQLT. DDL 포함 — 마지막에 지운다. 복제 표에 NULL 을 주입한다.
 주의: 개인 실습 환경 전용. 원본 표에는 DML 을 하지 않는다.
================================================================================

$ sqlplus sqlt/sqlt@orcl

SQLT@orcl> SET LINESIZE 200
SQLT@orcl> SET PAGESIZE 100

--------------------------------------------------------------------------------
-- [1] (조치 전 상태) 복제 표 + 인덱스 준비, NULL 주입
--------------------------------------------------------------------------------
SQLT@orcl> CREATE TABLE patients_wl AS SELECT * FROM patients;

Table created.

SQLT@orcl> UPDATE patients_wl SET city = NULL WHERE MOD(pat_id, 100) = 0;    -- 1% 를 NULL 로

500 rows updated.

SQLT@orcl> COMMIT;

Commit complete.

SQLT@orcl> CREATE INDEX ix_wl_name ON patients_wl(pat_name);
SQLT@orcl> CREATE INDEX ix_wl_city ON patients_wl(city);
SQLT@orcl> EXEC DBMS_STATS.GATHER_TABLE_STATS(USER, 'PATIENTS_WL')

PL/SQL procedure successfully completed.

--------------------------------------------------------------------------------
-- [2] (실측) 앞에 % 가 붙은 LIKE — 인덱스 정렬을 쓸 수 없다
--------------------------------------------------------------------------------
SQLT@orcl> SELECT /*+ GATHER_PLAN_STATISTICS */ COUNT(*) FROM patients_wl WHERE pat_name LIKE '김%';
(결과 <환경값>)
SQLT@orcl> SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR(NULL, NULL, 'ALLSTATS LAST'));

PLAN_TABLE_OUTPUT
------------------------------------------------------------------------------------------
|*  2 |   INDEX RANGE SCAN| IX_WL_NAME |      1 |  <환경값> |  <환경값> |  <환경값> |
------------------------------------------------------------------------------------------
   2 - access("PAT_NAME" LIKE '김%')
       filter("PAT_NAME" LIKE '김%')

SQLT@orcl> SELECT /*+ GATHER_PLAN_STATISTICS */ COUNT(*) FROM patients_wl WHERE pat_name LIKE '%수%';
(결과 <환경값>)
SQLT@orcl> SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR(NULL, NULL, 'ALLSTATS LAST'));

PLAN_TABLE_OUTPUT
------------------------------------------------------------------------------------------
|*  2 |   INDEX FAST FULL SCAN| IX_WL_NAME |      1 |  <환경값> |  <환경값> |  <환경값> |
------------------------------------------------------------------------------------------
   2 - filter("PAT_NAME" LIKE '%수%')

-- 해석: '김%' 는 access — 인덱스에서 '김' 으로 시작하는 구간을 바로 찾는다. '%수%' 는 filter —
--   어디서 시작할지 몰라 인덱스 전체를 훑는다(Index-Only 라 표보다는 싸지만 "탄" 것이 아니다).
--   중간 문자열 검색은 B-Tree 로 해결되지 않는다(Oracle Text 등 별도 기법, 과정 범위 밖).

--------------------------------------------------------------------------------
-- [3] (실측) 부정 조건 — "아닌 것" 은 범위로 표현되지 않는다
--------------------------------------------------------------------------------
SQLT@orcl> SELECT /*+ GATHER_PLAN_STATISTICS */ COUNT(*) FROM patients_wl WHERE city != '서울';
(결과 <환경값>)
SQLT@orcl> SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR(NULL, NULL, 'ALLSTATS LAST'));

PLAN_TABLE_OUTPUT
------------------------------------------------------------------------------------------
|*  2 |   TABLE ACCESS FULL| PATIENTS_WL |      1 |  <환경값> |  <환경값> |  <환경값> |      -- 또는 FAST FULL SCAN
------------------------------------------------------------------------------------------
   2 - filter("CITY"<>'서울')

-- 해석: != 는 access 가 되지 않는다. "서울이 아닌 모든 값" 은 인덱스에서 한 구간이 아니라 '서울' 앞뒤
--   두 구간이고, 대개 대부분의 행이 해당돼 Full Scan 이 싸다. NOT IN·NOT LIKE 도 같다.
--   값 종류가 적고 원하는 것이 소수라면 부정 대신 긍정 목록(city IN ('부산','대구'))으로 바꾼다.

--------------------------------------------------------------------------------
-- [4] (이상 징후 → 원인 → 조치 → 재확인) NULL 을 찾는데 0건
--------------------------------------------------------------------------------
SQLT@orcl> SELECT COUNT(*) FROM patients_wl WHERE city = NULL;

  COUNT(*)
----------
         0

SQLT@orcl> -- 이상 징후: [1] 에서 500건을 NULL 로 만들었는데 0건. 오류도 나지 않았다.
SQLT@orcl> -- 원인 파악: NULL 은 "값이 없음" 이라 = 로 비교하면 결과가 참도 거짓도 아닌 UNKNOWN 이다.
SQLT@orcl> --   WHERE 는 참인 행만 통과시키므로 0건. 오류가 없어서 더 위험한 실수다.
SQLT@orcl> -- 조치: IS NULL 로 쓴다.
SQLT@orcl> SELECT /*+ GATHER_PLAN_STATISTICS */ COUNT(*) FROM patients_wl WHERE city IS NULL;

  COUNT(*)
----------
       500

SQLT@orcl> SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR(NULL, NULL, 'ALLSTATS LAST'));

PLAN_TABLE_OUTPUT
------------------------------------------------------------------------------------------
|*  2 |   TABLE ACCESS FULL| PATIENTS_WL |      1 |    500 |    500 |  <환경값> |
------------------------------------------------------------------------------------------
   2 - filter("CITY" IS NULL)

SQLT@orcl> -- 재확인: 500건이 나온다. 그런데 IX_WL_CITY 가 있는데도 Full Scan 이다. 1%(500건)면 인덱스가
SQLT@orcl> --   유리할 텐데 왜인가 — 인덱스에 NULL 행이 없기 때문이다. 인덱스 건수와 표 건수를 대조한다.
SQLT@orcl> SELECT (SELECT COUNT(*) FROM patients_wl)                       table_rows,
  2              (SELECT num_rows FROM user_indexes WHERE index_name='IX_WL_CITY') index_rows
  3       FROM   dual;

TABLE_ROWS INDEX_ROWS
---------- ----------
     50000      49500

-- 재확인: 인덱스 엔트리 49,500 = 50,000 − 500. 단일 컬럼 B-Tree 인덱스는 NULL 행을 담지 않으므로
--   IS NULL 조건은 그 인덱스로 답할 수 없다. 옵티마이저의 Full Scan 선택이 맞다.
--   (복합 인덱스에서 다른 컬럼이 NOT NULL 이면 엔트리가 생기므로 IS NULL 도 인덱스를 탈 수 있다.)

--------------------------------------------------------------------------------
-- [5] 원복
--------------------------------------------------------------------------------
SQLT@orcl> DROP TABLE patients_wl PURGE;

Table dropped.

SQLT@orcl> SELECT table_name, index_name FROM user_indexes WHERE index_name NOT LIKE 'PK%';

no rows selected

--------------------------------------------------------------------------------
-- [정리]
--------------------------------------------------------------------------------
-- 1) LIKE '값%' 는 access, LIKE '%값%' 는 filter. 중간 검색은 B-Tree 의 몫이 아니다.
-- 2) !=, NOT IN, NOT LIKE 는 access 가 되지 않는다. 소수를 원하면 긍정 목록으로 바꾼다.
-- 3) = NULL 은 오류 없이 0건이다. IS NULL 로 쓴다.
-- 4) 단일 컬럼 B-Tree 는 NULL 행을 담지 않는다(인덱스 건수 < 표 건수) — IS NULL 은 그 인덱스를 못 쓴다.

SQLT@orcl> EXIT
