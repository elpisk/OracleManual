================================================================================
 8장 실습 05 — Instance Activity Stats 에서 이상 지표 찾기
 목표: 앞 섹션(Load Profile·Top Events·SQL)에서 세운 가설을 Instance Activity
       Stats의 원시 통계로 확증/반증한다. 눈에 띄는 통계 하나로 근거 없는 새
       가설을 세우는 오판을 재현·교정한다.
 환경: non-CDB=orcl 19.3 (SYS AS SYSDBA)
 부하: WL_06_mixed.sql (7세션). 보고서 awrrpt_1_295_296.txt 사용.
 라이선스: 🔒 Diagnostics Pack. 미보유 시 V$SYSSTAT 델타로 대체(하단).

$ sqlplus / as sysdba

SYS@orcl> SET LINESIZE 200
SYS@orcl> SET PAGESIZE 100

--------------------------------------------------------------------------------
-- [1] (조치 전 상태) 확증할 가설을 먼저 적어둔다.
--------------------------------------------------------------------------------
-- 가설(실습 02~04): ① 리터럴 하드파싱(319/s) ② 대량 논리읽기(118만/s)
--   ③ 인덱스 못 타는 대량 스캔 가능성 ④ 커서 재사용 실패(Library Hit 59%).
-- Instance Activity Stats에서 이 네 가지를 뒷받침하는 통계만 골라 본다.

--------------------------------------------------------------------------------
-- [2] (조회) 보고서의 Instance Activity Stats에서 관련 통계만 발췌.
--------------------------------------------------------------------------------
SYS@orcl> HOST grep -E "parse count \(hard\)|parse count \(total\)|session logical reads|table scans \(long tables\)|table scan blocks gotten|session cursor cache hits" awrrpt_1_295_296.txt

Statistic                                     Total     per Second   per Trans
------------------------------------ -------------- -------------- -----------
parse count (hard)                           31,900         319.0        1.5
parse count (total)                          43,370         433.7        2.1
session logical reads                   118,510,700   1,185,107.0    5,735.2
table scans (long tables)                     11,824         118.2        0.6
table scan blocks gotten                109,830,441   1,098,304.4    5,314.0
session cursor cache hits                     28,140         281.4        1.4

--------------------------------------------------------------------------------
-- [3] (해석) 각 통계가 어느 가설을 확증하는가?
--------------------------------------------------------------------------------
-- parse count (hard) 31,900 = 319/s×100초 → 가설 ① 하드파싱 확증.
-- session logical reads 1억1,851만 → SQL Gets 섹션 Total 1억2,283만과 자릿수
--   일치 → 가설 ② 논리읽기 확증.
-- table scan blocks gotten 1억983만 → 논리읽기 총량의 대부분이 '대량 스캔'에서
--   나왔다 → 가설 ③ 인덱스 못 타는 스캔 확증.
SYS@orcl> SELECT ROUND(109830441/118510700*100,1) AS scan_share_pct FROM dual;

SCAN_SHARE_PCT
--------------
          92.7

-- 해석: 논리읽기의 92.7%가 테이블 스캔에서 발생 → 대량 스캔이 논리읽기 주범.
-- session cursor cache hits 281/s는 파싱 대비 낮은 편 → 가설 ④(커서 재사용
--   실패)와 방향이 맞는다(Library Hit 59%, 실습 06/Instance Efficiency와 교차).

--------------------------------------------------------------------------------
-- [4] (조회) 반증 통계도 찾아본다 — CPU 바운드 가설이 틀리지 않았나?
--------------------------------------------------------------------------------
SYS@orcl> HOST grep -E "physical reads direct|sorts \(disk\)|sorts \(memory\)" awrrpt_1_295_296.txt

physical reads direct                            120           1.2        0.0
sorts (disk)                                       0           0.0        0.0
sorts (memory)                                12,540         125.4        0.6

-- 해석: physical reads direct 1.2/s, sorts(disk) 0 → 디스크 직접 읽기·디스크
--   정렬이 사실상 없다. CPU 바운드 가설을 반증할 통계가 없다 → 가설 유지.
--   (sorts는 전부 메모리에서 처리됨 = In-memory Sort 100%와 일치)

--------------------------------------------------------------------------------
-- [5] (이상 징후 → 원인 → 조치 → 재확인)
--     이상 징후: 동료가 Instance Activity에서 'redo size'가 크다며 "리두가
--       진짜 병목"이라는 새 가설을 세웠다.
--------------------------------------------------------------------------------
-- 원인 파악: 이 섹션은 수백 개 통계라 뭐든 커 보인다. 절대값이 아니라 앞
--   가설·DB Time 비중과 연결해서 봐야 한다.
SYS@orcl> HOST grep -E "^redo size " awrrpt_1_295_296.txt

redo size                                14,001,700       140,017.0      677.6

-- 원인 확정: redo size 140,017/s는 존재하지만, 이것이 만든 대기(log file sync)는
--   실습 03에서 % DB time 3.7%로 확인됐다. DB CPU 95.7% 앞에서 리두는 주범이
--   아니다. Instance Activity의 큰 절대값만으로 새 가설을 세운 것이 오판이다.
-- 조치: 이 섹션에서는 새 이론을 세우지 않는다. 앞 섹션의 가설을 확증/반증하는
--   용도로만 쓴다. 리두는 부차적 관찰로 남긴다.
-- 재확인: redo가 만든 대기(log file sync)의 % DB time=3.7% → 병목 아님 확인.

--------------------------------------------------------------------------------
-- [대안 경로] 🔒 미보유 — V$SYSSTAT 델타로 같은 통계를 만든다.
--------------------------------------------------------------------------------
-- 부하 전/후로 두 번 찍어 (후-전)을 계산한다.
--   SELECT name, value FROM v$sysstat
--    WHERE name IN ('parse count (hard)','session logical reads',
--                   'table scan blocks gotten','sorts (disk)','redo size');
-- AWR Instance Activity Stats와 동일한 원시 통계를 얻어 확증/반증에 쓴다.

--------------------------------------------------------------------------------
-- [정리]
--------------------------------------------------------------------------------
-- 1) Instance Activity Stats는 앞 가설의 확증/반증용. 새 이론을 함부로 세우지 않음.
-- 2) parse count(hard) 31,900 / logical reads 1.18억 → 하드파싱·논리읽기 확증.
-- 3) table scan blocks gotten이 논리읽기의 92.7% → 대량 스캔이 주범.
-- 4) 확증만이 아니라 반증(sorts disk 0, physical direct 미미)도 확인 → 확증편향 경계.
-- 5) redo size 큰 값만 보고 '리두 병목'이라 하면 오판 → % DB time으로 검증.
-- 6) 라이선스 없으면 V$SYSSTAT 델타로 동일 통계 확보.

SYS@orcl> EXIT
