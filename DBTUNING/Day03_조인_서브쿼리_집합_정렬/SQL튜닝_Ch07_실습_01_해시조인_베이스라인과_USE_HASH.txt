 Ch07 실습 01 — 조인 베이스라인: 인덱스 없는 상태에서 HASH JOIN (3,093) 과 USE_HASH 힌트
 목표: HOSPITALS(작은 표) ⋈ MEDICAL_CLAIMS(큰 표) 조인의 기본 계획이 HASH JOIN 임을 실측하고,
       어느 쪽이 build(해시 테이블)이고 어느 쪽이 probe 인지 계획에서 읽는다. USE_HASH 를 강제해
       계획이 그대로(Plan hash 619494044)인 것으로 "옵티마이저가 이미 해시를 골랐다" 를 확인한다.
       Full Scan 을 막으려 build/probe 를 뒤집은 SWAP_JOIN_INPUTS 실험으로 해시 조인의 메모리를 본다.
 환경: non-CDB=orcl 19.3, 스키마 SQLT. PK 외 인덱스 없음.
 주의: 개인 실습 환경 전용. 조회만 수행한다.
================================================================================

--   고른 것이 맞다. Buffers 3,093 = 3 + 3,090. 병원 1~5 의 청구 15,029건이 조인을 통과했다.
--   Used-Mem(<환경값>): 5행짜리 해시 테이블은 수십 KB 다.

--------------------------------------------------------------------------------
-- [2] (재확인) Q3 — USE_HASH 를 강제해도 같다
--------------------------------------------------------------------------------
SQLT@orcl> SELECT /*+ GATHER_PLAN_STATISTICS USE_HASH(h m) */ h.hosp_type, COUNT(*)
  2       FROM   hospitals h, medical_claims m
  3       WHERE  h.hosp_id = m.hosp_id
  4       AND    h.hosp_id <= 5
  5       GROUP  BY h.hosp_type;

-- [3] (이상 징후 → 원인 → 재확인) build/probe 를 뒤집으면 — 메모리가 튄다
--------------------------------------------------------------------------------
SQLT@orcl> -- "MEDICAL_CLAIMS 를 build 로 쓰면 어떻게 되나" — SWAP_JOIN_INPUTS 로 뒤집어 본다.
SQLT@orcl> SELECT /*+ GATHER_PLAN_STATISTICS USE_HASH(h m) SWAP_JOIN_INPUTS(m) */ h.hosp_type, COUNT(*)
  2       FROM   hospitals h, medical_claims m
  3       WHERE  h.hosp_id = m.hosp_id
  4       AND    h.hosp_id <= 5
  5       GROUP  BY h.hosp_type;
(결과 동일)

SQLT@orcl> -- 이상 징후: Buffers 는 3,093 으로 같은데 Used-Mem 이 [1] 보다 훨씬 크다(<환경값>: 15,029행의
SQLT@orcl> --   해시 테이블 — 수백 KB~MB). 논리 읽기로는 차이가 안 보인다.
SQLT@orcl> -- 원인 파악: build 쪽 행 수가 해시 테이블 크기다. 큰 쪽을 build 로 잡으면 메모리가 커지고,
SQLT@orcl> --   PGA 한도를 넘으면 임시 세그먼트로 넘쳐(Used-Mem 뒤 (1)·(2)) 물리 I/O 가 생긴다.
SQLT@orcl> --   옵티마이저가 작은 쪽을 build 로 고른 이유가 이것이다.
SQLT@orcl> -- 재확인: Buffers 만 보면 [1] 과 [3] 은 같은 SQL 이다. 해시 조인의 비용은 +MEMSTATS 로 본다.
SQLT@orcl> --   대량 정렬·해시가 PGA 를 넘치는 상황은 TUN 19장 실습 05(WL_03_sort)에서 인스턴스 관점으로 본다.

-- 2) USE_HASH 를 줘도 Plan hash 619494044 그대로 — 힌트는 계획을 "확인" 하는 도구이기도 하다.
-- 3) build 를 큰 쪽으로 뒤집으면 Buffers 는 같아도 메모리가 튄다. 해시 조인은 +MEMSTATS 로 본다.
-- 4) Buffers 3,093 을 줄이려면 probe(MEDICAL_CLAIMS)의 Full Scan 을 없애야 한다 → 실습 02·03.
