# 브리지 01 — SQL 한 문장에서 시스템으로

Day 5 도입: SQL 부문(Day 1~4)에서 인스턴스 부문(Day 5~10)으로

Buffers 와 A-Rows 로 재던 것을 DB Time 과 대기 클래스로 다시 잰다 · "내 SQL 이 아니라 시스템이 문제" 를 판별하는 세 가지 징후 · 열흘의 진단 절차 한 장

## 학습 목표 (Objectives)

- Day 1~4 에서 쓴 측정 단위(Buffers, A-Rows, Elapsed)가 인스턴스 층위에서 어떤 단위(DB Time, 대기 클래스)로 바뀌는지 설명한다.
- 같은 느린 화면을 두고 SQL 층위의 질문과 인스턴스 층위의 질문이 어떻게 다른지 구분한다.
- "내 SQL 이 아니라 시스템이 문제" 인지 판별하는 세 가지 징후를 V$ 뷰로 확인한다.
- Day 5~10 의 진단 절차가 Day 1~4 의 어느 지점으로 되돌아오는지 한 장의 그림으로 기억한다.

**발표자 노트**  이 브리지는 Tuning 1장 도입 전에 20분 안에 끝냅니다. 목적은 새 지식을 넣는 것이 아니라 지난 나흘 동안 손에 익은 측정 습관을 그대로 들고 층위만 한 단계 올리는 것입니다. 수강생이 Day 1 에 배운 DBMS_XPLAN 의 Buffers 열과 Day 6 에 배울 DB Time 이 서로 다른 세계의 숫자가 아니라 같은 자원 소비를 다른 해상도로 본 것임을 납득하면 이 브리지의 역할은 끝납니다.

## 지금까지와 앞으로 — 층위가 바뀐다
_같은 데이터베이스, 다른 해상도_

|  | SQL 부문 (Day 1~4) | 인스턴스 부문 (Day 5~10) |
|---|---|---|
| 대상 | SQL 한 문장 | 인스턴스 전체·세션·시스템 |
| 질문 | 이 SQL 은 왜 느리고 어떻게 고치는가 | 어느 SQL 이, 어떤 대기 때문에, DB Time 의 몇 % 를 쓰는가 |
| 도구 | DBMS_XPLAN, 실행 통계, 인덱스, 힌트 | V$ 시간 모델, AWR/ADDM/ASH, 대기 이벤트, 어드바이저 |
| 측정 단위 | Buffers · Reads · A-Rows/E-Rows · Elapsed | DB Time · DB CPU · 대기 클래스별 시간 · 델타 |
| 종착점 | 실행계획이 바뀌고 Buffers 가 줄었다 | 시스템 전체 DB Time 이 줄었고 상위 대기가 바뀌었다 |

**발표자 노트**  지난 나흘의 종착점은 실행계획이 바뀌고 Buffers 가 3,091 에서 15 로 줄어든 것이었습니다. 그런데 실무에서 그 SQL 을 고친 뒤에도 "여전히 느리다" 는 전화가 오는 경우가 있습니다. 그때 필요한 것이 오른쪽 열입니다. 대상이 한 문장에서 인스턴스 전체로 넓어지고, 측정 단위가 논리 읽기 횟수에서 시간으로 바뀝니다. 도구도 바뀌지만 원리는 같습니다. 무엇이 자원을 얼마나 쓰는지 수치로 재고, 조치 전후를 비교합니다.

## 같은 화면, 두 개의 질문
_"청구 조회 화면이 느리다" 는 신고를 받았을 때_

- SQL 층위의 질문 — 그 화면이 실행하는 SQL 의 실행계획은 무엇이고, Buffers 는 얼마이며, 인덱스를 타는가? → Day 1~4 의 방법으로 답한다.
- 인스턴스 층위의 질문 — 그 시각 인스턴스의 DB Time 은 평소 대비 얼마나 늘었고, 늘어난 시간은 CPU 인가 대기인가, 대기라면 어떤 클래스인가? → Day 6~8 의 방법으로 답한다.
- 두 질문의 답이 어긋날 때가 진짜 문제다 — SQL 은 그대로인데 느려졌다면 원인은 SQL 밖에 있다.
- 그래서 순서가 중요하다 — 인스턴스 층위에서 범위를 좁힌 뒤 SQL 층위로 내려간다. 거꾸로 하면 멀쩡한 SQL 을 고치느라 하루를 쓴다.

**발표자 노트**  같은 신고를 받고도 두 층위의 질문이 다릅니다. SQL 층위에서는 그 SQL 의 실행계획과 Buffers 를 봅니다. 인스턴스 층위에서는 그 시각 DB Time 이 얼마나 늘었고 그 증가분이 CPU 인지 대기인지 봅니다. 두 답이 어긋날 때, 즉 SQL 의 실행계획과 Buffers 는 어제와 같은데 응답이 느려졌을 때 원인은 SQL 밖에 있습니다. 이 과정의 뒷부분은 그 "밖" 을 다루는 방법입니다. 순서는 항상 넓은 층위에서 좁혀 들어가는 쪽이며, 거꾸로 가면 멀쩡한 SQL 을 손대는 실수를 합니다.

## "내 SQL 이 아니라 시스템이 문제" — 세 가지 징후
_이 셋 중 하나라도 보이면 SQL 을 고치기 전에 멈춘다_

- ① 실행계획과 Buffers 는 그대로인데 Elapsed 만 늘었다 — 논리 읽기 한 번당 시간이 늘어난 것이므로 I/O·CPU·대기 쪽 문제다 (Day 8 14장, Day 10 20장).
- ② 내 SQL 의 Elapsed 합이 인스턴스 DB Time 의 몇 % 도 안 된다 — 내 SQL 을 0 으로 만들어도 시스템은 그대로다. 상위 SQL 부터 찾아야 한다 (Day 7 8장 SQL 섹션).
- ③ 특정 시간대에만 느리다 — SQL 이 시간대를 가릴 리 없다. 그 시간대에 도는 배치·자동 작업·잠금 경합을 본다 (Day 7 10장 ASH, Day 9 15장 자동 작업).
- 공통 조치 — 조치 전 상태를 먼저 캡처한다. 스냅샷 없이 고친 튜닝은 효과를 증명할 수 없다 (Day 5 3장 실습 05).

**발표자 노트**  세 가지 징후를 V$ 뷰로 확인하는 방법이 다음 슬라이드입니다. 첫째, 실행계획도 Buffers 도 그대로인데 Elapsed 만 늘었다면 읽기 한 번당 시간이 늘어난 것이므로 SQL 문제가 아닙니다. 둘째, 내 SQL 의 총 소요 시간이 인스턴스 DB Time 의 몇 퍼센트도 되지 않는다면 그 SQL 을 아무리 고쳐도 시스템은 달라지지 않습니다. 셋째, 특정 시간대에만 느리다면 SQL 이 아니라 그 시간에 함께 도는 무언가가 원인입니다. 어느 경우든 조치 전 상태를 캡처하는 것이 먼저이며, 이것은 3장에서 절차로 배웁니다.

## 징후 ②를 숫자로 — 내 SQL 은 DB Time 의 몇 % 인가
_V$SQL 의 elapsed_time 과 V$SYS_TIME_MODEL 의 DB time 을 같은 단위(초)로 놓고 비교한다_

```
-- 1) Day 1~4 에서 쓰던 그 SQL 의 SQL_ID 를 찾는다
SYS@orcl> SELECT sql_id, plan_hash_value, executions,
  2         ROUND(elapsed_time/1e6, 2) AS elapsed_s,
  3         buffer_gets
  4    FROM v$sql
  5   WHERE sql_text LIKE 'SELECT /* BR01 */%';

-- 2) 인스턴스가 기동 후 지금까지 쓴 DB Time (누적, 초)
SYS@orcl> SELECT ROUND(value/1e6, 2) AS db_time_s
  2    FROM v$sys_time_model
  3   WHERE stat_name = 'DB time';

-- 3) 비중 = elapsed_s / db_time_s * 100
--    누적값끼리의 비교이므로 방향만 본다. 구간 델타로 다시 재는 법은 5장 실습 05·06.
--    실행 결과는 실습 환경에서 캡처한다.
```

**발표자 노트**  이 코드는 지난 나흘 동안 튜닝한 SQL 에 주석 태그를 붙여 두었다면 그대로 돌릴 수 있습니다. V$SQL 의 elapsed_time 은 마이크로초 단위 누적값이고 V$SYS_TIME_MODEL 의 DB time 도 마이크로초 누적값이므로 둘 다 백만으로 나눠 초로 맞춥니다. 둘을 나눈 비율이 한 자리 퍼센트에 그친다면 그 SQL 은 시스템 관점에서 주범이 아닙니다. 다만 둘 다 기동 이후 누적값이라 정확한 비중은 아니며, 구간을 잘라 델타로 재는 방법은 5장 실습 05 와 06 에서 배웁니다. 여기서는 방향만 잡습니다.

## 열흘의 진단 절차 한 장
_Day 5~10 에서 배우는 것이 Day 1~4 의 어디로 되돌아오는가_

- ① DB Time 을 잰다 → CPU 인가 대기인가 → 어느 대기 클래스인가  (Day 6 5장)
- ② 구간 보고서로 상위 대기·상위 SQL 을 지목한다  (Day 7 8장 AWR · 9장 ADDM · 10장 ASH)
- ③ 대기 이벤트에서 원인 세그먼트·세션·SQL 로 좁힌다  (Day 8 13·14장)
- ④ 지목된 SQL 의 실행계획을 읽고 고친다  → Day 1~4 로 돌아온다 (브리지 02)
- ⑤ 손으로 고친 결과를 어드바이저 권고와 대조한다  (Day 9 15장, 브리지 03)
- ⑥ 조치 전후를 기간 비교로 증명한다  (Day 8 11장) — SQL 층위의 Buffers 비교와 짝을 이룬다
- ⑦ SQL 로 해결되지 않는 나머지는 메모리·I/O 구성으로 간다  (Day 9~10 16~20장)

**발표자 노트**  이 한 장이 남은 엿새의 지도입니다. 1번에서 3번까지는 범위를 좁히는 과정이고, 4번에서 지난 나흘의 기술로 돌아옵니다. 5번은 손으로 한 튜닝을 어드바이저와 대조해 빠뜨린 것이 없는지 확인하는 단계이고, 6번은 조치가 효과가 있었음을 시스템 수준에서 증명하는 단계입니다. 7번은 SQL 을 고쳐도 남는 문제, 즉 메모리와 I/O 구성의 영역입니다. 수강생에게 이 순서를 외우게 하기보다, 매일 수업 시작에 오늘이 이 지도의 어디인지 짚어 주십시오.

## 인스턴스 부문에서 특히 경계할 세 가지
_SQL 부문에는 없던 함정_

- 히트율 신앙 — 버퍼 캐시 히트율 99% 인데 응답시간이 나쁜 상황을 Day 9 17장에서 직접 만든다. 비율은 병목을 숨긴다.
- 권고 맹신 — ADDM·어드바이저의 권고를 그대로 적용하면 안 되는 사례를 Day 7 9장에서 판별한다. 권고는 가설이지 결론이 아니다.
- 근거 없는 조치 — 조치 전 상태를 캡처하지 않은 튜닝은 효과를 증명할 수 없다. Day 5 3장 실습 05 에서 절차로 각인한다.
- SQL 부문의 습관을 그대로 가져온다 — 실행계획을 읽기 전에 SQL 을 고치지 않았듯, 대기 이벤트를 읽기 전에 파라미터를 바꾸지 않는다.

**발표자 노트**  SQL 부문에서는 실행계획이라는 객관적 근거가 있어서 오판이 적었습니다. 인스턴스 부문에는 비율과 권고라는 그럴듯한 숫자가 많아 오판이 늘어납니다. 히트율은 병목을 숨기고, 권고는 가설일 뿐이며, 캡처 없는 조치는 증명이 안 됩니다. 지난 나흘의 습관, 즉 근거를 보기 전에 손대지 않는 태도를 그대로 가져오면 이 세 함정은 피할 수 있습니다. 세 함정은 각각 17장, 9장, 3장에서 실습으로 직접 재현하므로 여기서는 이름만 기억하게 하십시오.

## 라이선스 — 한 문장만 먼저
_자세한 내용은 바로 이어지는 1장 라이선스 절_

- Day 1~4 에서 쓴 DBMS_XPLAN·V$SQL·V$SQL_PLAN 은 Enterprise Edition 기본 기능이다 — 추가 라이선스 없음.
- Day 6~8 의 AWR·ADDM·ASH·DBA_HIST_* 는 **Diagnostics Pack**, Day 9 의 SQL Tuning/Access Advisor·SPA 는 **Tuning Pack** 이 필요하다.
- 교육 환경에서 무심코 쓰던 것을 실무에서 그대로 쓰면 라이선스 위반이 된다 — 각 장 도입부에서 다시 짚는다.
- 미보유 환경에서도 같은 것을 보는 대안 경로(Statspack, V$ 직접 조회)를 모든 해당 장에 함께 싣는다.

**발표자 노트**  지난 나흘에 쓴 도구는 전부 기본 기능이었지만 오늘부터 쓰는 도구 중 상당수는 유료 팩입니다. 이 사실을 브리지에서 한 문장으로 먼저 말하고, 이어지는 1장의 라이선스 절에서 DBA_FEATURE_USAGE_STATISTICS 와 CONTROL_MANAGEMENT_PACK_ACCESS 로 확인하는 방법을 실습합니다. 수강생 중 실무 환경이 Standard Edition 이거나 팩 미보유인 경우가 있으면 지금 손을 들게 해서, 그 사람들에게는 각 장의 대안 경로가 본편임을 미리 알려 두십시오.

- 순서가 중요하다 — 인스턴스 층위에서 좁힌 뒤 SQL 층위로 내려간다.
