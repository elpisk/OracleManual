 11장 실습 03 — SQL 단위 회귀 탐지 (실행계획 변경으로 느려진 SQL 식별)
 목표: 집계로는 부하 증가로 보여도 그 안에 숨은 SQL 회귀를 찾는다. DBA_HIST_SQLSTAT
       으로 두 구간의 실행당 지표와 plan_hash_value 를 비교해, 실행 횟수는 비슷한데
       실행당 시간이 급증하고 계획이 바뀐 SQL 을 회귀로 확정한다.
 환경: non-CDB=orcl 19.3 (SQLT 업무 계정으로 조회, SELECT_CATALOG_ROLE 보유)
 부하: WL_06_mixed.sql 로 구간A(303→304)/구간B(305→306) 생성. 구간B 직전 대상
       테이블 통계가 갱신되며 특정 조회 SQL 의 계획이 인덱스→전체 스캔으로 바뀌었다.
 주의: 개인 실습 환경 전용. 🔒 DBA_HIST_SQLSTAT 은 Diagnostics Pack 필요.
================================================================================

$ sqlplus sqlt/<환경값>@orcl

SQLT@orcl> SET LINESIZE 200
SQLT@orcl> SET PAGESIZE 100

--------------------------------------------------------------------------------
-- [1] (조치 전 상태) 보고서 SQL Statistics(실행시간 기준)에서 후보를 좁힌다.
--     "한 구간에서만 DB Time 을 크게 쓴 SQL" 이 회귀 후보다.
--------------------------------------------------------------------------------
SQLT@orcl> SELECT sql_id,
  2         SUM(CASE WHEN snap_id=304 THEN elapsed_time_delta ELSE 0 END) a_ela,
  3         SUM(CASE WHEN snap_id=306 THEN elapsed_time_delta ELSE 0 END) b_ela
  4       FROM  dba_hist_sqlstat
  5       WHERE snap_id IN (304,306)
  6         AND parsing_schema_name='SQLT'
  7       GROUP BY sql_id
  8       ORDER BY b_ela - a_ela DESC FETCH FIRST 5 ROWS ONLY;

SQL_ID              A_ELA        B_ELA
------------- ----------- ------------
9xk2p1m4qz7ab   3,100,000   58,400,000   <= 후보 : 구간B에서 급증
3j9gw8s0v82pc  12,000,000   14,600,000
...

-- 해석: 9xk2p1m4qz7ab 가 구간B에서 경과시간이 폭증했다. 회귀 후보로 지목한다.

--------------------------------------------------------------------------------
-- [2] (조회) 후보 SQL 을 DBA_HIST_SQLSTAT 으로 두 구간 상세 비교한다.
--     실행 횟수 · 실행당 경과시간 · 실행당 버퍼읽기 · plan_hash_value.
--------------------------------------------------------------------------------
SQLT@orcl> SELECT snap_id, plan_hash_value,
  2         executions_delta execs,
  3         ROUND(elapsed_time_delta/NULLIF(executions_delta,0)/1000,2) ms_exec,
  4         ROUND(buffer_gets_delta/NULLIF(executions_delta,0))          gets_exec
  5       FROM  dba_hist_sqlstat
  6       WHERE sql_id='9xk2p1m4qz7ab'
  7         AND snap_id IN (304,306)
  8       ORDER BY snap_id;

   SNAP_ID PLAN_HASH_VALUE      EXECS    MS_EXEC   GETS_EXEC
---------- --------------- ---------- ---------- -----------
       304      1388734953        500      12.40        1850
       306       983734112        520     112.31       42800

--------------------------------------------------------------------------------
-- [3] (해석) 회귀 확정 — 최소 조건 세 가지가 모두 성립하는가.
--------------------------------------------------------------------------------
-- (a) 같은 SQL_ID : 9xk2p1m4qz7ab  → 같은 문장, 비교 성립.
-- (b) 실행 횟수 유사 : 500 → 520  → '더 자주 불린 것'이 아니다.
-- (c) 실행당 악화 + 계획 변경 : 12.40ms → 112.31ms(약 9배),
--       버퍼읽기 1,850 → 42,800, plan_hash_value 1388734953 → 983734112.
-- 판정: 인덱스 계획이 전체 스캔 계획으로 바뀌며 느려진 '전형적 회귀'다.
--   집계(실습 05: DB time 81.8초→302.0초는 부하 증가로 판정)여도 이 SQL 은
--   명백한 성능 저하다 — 집계 판정과 SQL 단위 판정은 층위가 다르다.

--------------------------------------------------------------------------------
-- [4] (이상 징후 → 원인 → 조치 → 재확인)
--     이상 징후: "왜 계획이 바뀌었나?" 를 확인하지 않고 힌트부터 박으려 한다.
--------------------------------------------------------------------------------
SQLT@orcl> -- 원인 파악: 구간B 직전 대상 테이블의 통계가 갱신되며 카디널리티
SQLT@orcl> --   추정이 달라져 옵티마이저가 전체 스캔을 골랐다(통계 변화형 회귀).
SQLT@orcl> SELECT table_name, TO_CHAR(last_analyzed,'MM-DD HH24:MI') la, num_rows
  2       FROM  user_tables WHERE table_name IN ('MEDICAL_CLAIMS','CLAIM_DETAILS');
TABLE_NAME       LA            NUM_ROWS
---------------- ------------- ----------
CLAIM_DETAILS    08-25 13:18   <환경값>     -- 구간B 직전에 재분석됨

-- 조치: 급한 불은 좋았던 계획(1388734953)을 SQL Plan Management 로 고정한다.
--   (근본 조치는 대표 통계 재수집·고정. 계획 고정은 임시 조치임을 기록한다.)
SQLT@orcl> -- (SYS 권한 필요) 예: 좋은 계획을 AWR 에서 로드해 SQL Plan Baseline 생성
SYS@orcl> DECLARE n PLS_INTEGER;
  2       BEGIN
  3         n := DBMS_SPM.LOAD_PLANS_FROM_AWR(
  4                begin_snap=>303, end_snap=>304, sql_id=>'9xk2p1m4qz7ab');
  5         DBMS_OUTPUT.PUT_LINE('loaded='||n);
  6       END;
  7     /
loaded=1

-- 재확인: 다음 실행 구간에서 같은 SQL 의 plan_hash_value 가 1388734953 로
--   돌아오고 ms_exec 가 이전 수준(약 12ms)으로 회복되는지 DBA_HIST_SQLSTAT 로 확인.

--------------------------------------------------------------------------------
-- [5] (라이선스 대안)
--------------------------------------------------------------------------------
-- DBA_HIST_SQLSTAT 이 없으면(🔒), 회귀 의심 시점에 V$SQL·V$SQL_PLAN 을 바로
--   캡처해 두 시점의 계획을 비교한다. V$ 는 라이브러리 캐시에 남아 있는 동안만
--   보이므로, '의심되는 즉시' 저장하는 것이 핵심이다(DBA_HIST 가 자동으로 하던 일).

--------------------------------------------------------------------------------
-- [정리]
--------------------------------------------------------------------------------
-- 1) 회귀 = 같은 SQL_ID + 실행 횟수 유사 + 실행당 악화 + plan_hash_value 변경.
-- 2) 실측: 실행 500→520, 12.40ms→112.31ms, 계획 1388734953→983734112.
-- 3) 집계가 부하 증가여도 개별 SQL 은 회귀할 수 있다(층위가 다름).
-- 4) 조치: 좋은 계획 고정(임시) + 통계 재수집(근본), 이후 실행당 회복을 재확인.
-- ※ 🔒 DBA_HIST_SQLSTAT 은 Diagnostics Pack 필요. 없으면 V$SQL·V$SQL_PLAN 캡처.
