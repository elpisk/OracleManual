# Chapter 2. SQL은 어떻게 실행되는가? — 해설

`SQL튜닝_Ch02_문제.md`와 번호가 1:1로 대응합니다.

---

### 1. [상] SQL 처리 4단계

- **Parse**: 문법·의미 검사 후, 공유 풀에 동일 SQL 텍스트가 있는지 확인. 없으면 옵티마이저가
  통계정보를 근거로 실행계획을 새로 생성(하드 파싱)
- **Bind**: SQL에 바인드 변수가 있으면 그 자리에 실제 값을 대입
- **Execute**: 확정된 실행계획대로 데이터를 실제로 처리
- **Fetch**: 처리된 결과를 클라이언트로 전달
- 실행계획이 만들어지는 단계는 **Parse**다. 이후 단계는 이미 정해진 계획을 그대로 따라간다.

### 2. [상] 리터럴 값이 다르면 SQL_ID가 다른 이유

- Oracle은 SQL을 공유 풀에서 식별할 때 **SQL 텍스트 전체를 해시**해서 SQL_ID를 만든다.
- `hosp_id = 1`과 `hosp_id = 500`은 문자열 자체가 다르므로 해시값도 다르고, 결과적으로
  완전히 별개의 SQL로 취급된다.
- 이는 Oracle이 "이 두 SQL이 사실상 같은 로직"이라는 걸 몰라서가 아니라, **텍스트 일치
  여부만으로 공유 풀 재사용을 판단**하기 때문이다. 로직이 같아도 텍스트가 다르면 재사용
  대상이 아니다.

### 3. [최상] 리터럴 vs 바인드 변수 — 대규모 트래픽 시나리오

- 리터럴로 짠 경우: 병원 ID가 다른 요청이 들어올 때마다 SQL 텍스트가 달라지므로, 서로
  다른 SQL_ID가 공유 풀에 계속 쌓인다. 병원이 1,000곳이라면 이론상 최대 1,000개의 서로
  다른 SQL_ID(같은 로직의 SQL)가 쌓일 수 있고, 그때마다 매번 하드 파싱(문법 검사, 의미
  분석, 최적화)이 발생한다.
- 바인드 변수로 짠 경우: SQL 텍스트는 항상 `WHERE hosp_id = :b_hosp`로 동일하므로 SQL_ID가
  하나로 고정된다. 최초 1회만 하드 파싱하고, 이후 요청은 값만 바뀐 채 같은 실행계획을
  재사용(소프트 파싱)한다.
- 실무 영향: 리터럴 방식은 공유 풀 메모리를 불필요하게 소모하고(같은 로직의 SQL 사본이
  병원 수만큼 쌓임), CPU도 매번 파싱에 소모한다. 사용자가 많은 서비스일수록 이 차이가
  누적되어 커진다 — 대규모 트래픽 환경에서 바인드 변수 사용이 권장되는 이유가 여기 있다.

### 4. [상] 히스토그램에 의한 정확한 E-Rows

- `USER_TAB_COL_STATISTICS` 조회 결과 `HOSP_ID` 컬럼은 `HISTOGRAM=HYBRID`,
  `NUM_BUCKETS=254`로 확인됐다. 즉 이 컬럼은 단순 균등 분포 가정이 아니라, 실제 값별
  분포를 254개 구간(버킷)으로 나눠 저장한 히스토그램을 갖고 있다.
- `HOSP_ID=1`처럼 청구가 많이 몰린(스큐가 큰) 값과 `HOSP_ID=500`처럼 적게 몰린 값은
  히스토그램의 서로 다른 버킷에 해당하는 빈도로 기록되어 있어, 옵티마이저가 그 값의
  실제 빈도를 반영해 E-Rows를 계산할 수 있었다.
- 그 결과 E-Rows(3,039 / 109)가 A-Rows(3,058 / 177)에 상당히 근접했다 — Chapter 3의
  Q1(카디널리티 추정 오류) 사례와 대조된다. Q1은 두 컬럼 간 상관관계 때문에 오차가 컸고,
  이번 사례는 히스토그램이 정확히 대응해준 경우다.

### 5. [상] 같은 SQL 텍스트, 다른 실행계획

- "SQL 텍스트가 같으면 실행계획도 항상 같다"는 가정은 **리터럴 값까지 포함해서 텍스트가
  완전히 같을 때만** 성립한다. `hosp_id=1`과 `hosp_id=500`은 로직은 같아도 텍스트가
  다르므로 서로 독립적으로 파싱되고, 이번처럼 히스토그램이 있는 컬럼이면 Cost·E-Rows까지
  달라질 수 있다.
- 반면 바인드 변수를 쓰면 텍스트가 완전히 동일해지므로 원칙적으로 같은 실행계획을
  재사용한다 — 다만 이것이 항상 유리하지만은 않다는 게 6번 문항의 주제다.

### 6. [최상] 바인드 변수 Peeking 문제

- 바인드 변수 SQL은 SQL_ID가 하나이고, 그에 대응하는 실행계획도 원칙적으로 하나만
  캐시된다 — 즉 **최초 하드 파싱 시점에 대입된 값을 기준으로 만들어진 계획**이 이후
  다른 값에도 그대로 재사용될 수 있다(바인드 변수 Peeking).
- `HOSP_ID=1`(스큐가 큰 값, 약 3,000건)로 최초 파싱되면 그 계획이 이후
  `HOSP_ID=900`(스큐가 없는 값, 100여 건)에도 재사용될 수 있는데, 두 값은 원래 최적의
  실행 방법이 다를 수 있다(양이 많으면 Full Scan이, 양이 적으면 인덱스 스캔이 유리할
  수 있는 상황이라면 특히 문제가 된다).
- 즉 바인드 변수는 파싱 부담(3번 문항)은 줄여주지만, 히스토그램처럼 값에 따라 최적
  전략이 달라지는 컬럼에서는 "한 번 정해진 계획이 모든 값에 적용되는" 부작용을 낳을 수
  있다. 이 문제와 대응 방법(적응형 커서 공유 등)은 Chapter 13에서 다룬다.

### 7. [상] EXPLAIN PLAN vs 실제 실행

- `EXPLAIN PLAN`은 SQL을 **Parse 단계까지만** 수행한다 — 옵티마이저가 실행계획을
  만드는 것까지는 하지만, Execute·Fetch(실제 데이터 처리)는 하지 않는다. 그래서 Rows·
  Cost·Bytes는 전부 추정치이며 A-Rows나 Buffers 같은 실측치는 애초에 존재하지 않는다.
- `DBMS_XPLAN.DISPLAY_CURSOR(...'ALLSTATS LAST')`는 SQL을 **Execute·Fetch까지 실제로
  수행한 뒤** 그 결과(공유 풀에 남은 실행 통계)를 조회하는 것이라, A-Rows·Buffers·A-Time
  같은 실측치를 함께 볼 수 있다.
- 즉 전자는 "Parse 단계에서 무엇을 계획했는가", 후자는 "그 계획대로 Execute/Fetch까지
  실제로 해봤더니 어땠는가"를 보여준다.

### 8. [상] Cost가 파싱 시점에 확정되는 이유

- Cost는 Parse 단계에서 옵티마이저가 통계정보(NDV, 히스토그램, 행 수 등)를 근거로
  계산하는 값이다. 파싱이 SQL 텍스트 단위로 독립적으로 일어나므로, 텍스트가 다른
  두 리터럴 SQL은 각각 별도의 파싱 과정을 거치며 그때그때의 통계정보를 근거로 각자의
  Cost를 산출한다.
- `HOSP_ID=1`은 히스토그램상 빈도가 높은 값이라 예상 Rows(그리고 그에 연동된 Cost)가
  크게, `HOSP_ID=500`은 빈도가 낮은 값이라 작게 계산된 것이 이 원리의 결과다.

### 9. [최상] E-Rows 차이가 Buffers에 영향을 주지 못한 이유

- `HOSP_ID` 컬럼에는 인덱스가 없다(이 스키마는 PK 외 인덱스가 없는 상태). 그래서 어떤
  `HOSP_ID` 값을 찾든 옵티마이저가 선택할 수 있는 접근 경로는 `TABLE ACCESS FULL`
  하나뿐이다.
- Full Scan은 조건에 맞는 행이 많든 적든 **테이블 전체 블록을 읽어야** 하므로, E-Rows
  추정치가 얼마로 나오든 실제로 읽는 블록 수(Buffers)는 테이블 크기에 의해서만 결정된다
  — 그래서 두 조회 모두 Buffers 3,090으로 동일했다.
- 이 사례는 "E-Rows 추정이 정확했다고 해서 반드시 그 SQL의 물리적 비용이 달라지는 것은
  아니다"는 것을 보여준다 — 추정이 실제 접근 경로 선택에 영향을 주려면 애초에 선택 가능한
  대안 경로(예: 인덱스)가 있어야 한다. 인덱스가 없으면 추정이 아무리 정확해도 선택지가
  Full Scan 하나뿐이라 결과가 달라지지 않는다. Chapter 5에서 인덱스를 도입하면 이 상황이
  어떻게 달라지는지 다시 확인한다.

### 10. [최상] 반복되는 리터럴 SQL의 누적 문제

- 리터럴 SQL이 값마다 다른 SQL_ID로 쌓이면, 공유 풀(제한된 메모리 영역)에 사실상 같은
  로직의 SQL 사본이 값의 개수만큼 중복 저장된다 — 메모리 낭비이며, 오래된 SQL이 밀려
  나가고 다시 필요해지면 또 하드 파싱해야 하는 악순환이 생길 수 있다.
- 파싱 부하 관점에서는, 하드 파싱이 소프트 파싱보다 CPU를 훨씬 많이 쓴다 — 트래픽이
  몰리는 시간대에 서로 다른 리터럴 값의 요청이 동시에 쏟아지면 파싱 자체가 병목이 될 수
  있다.
- 바인드 변수는 이 문제(메모리·파싱 부하)를 줄여주지만, 6번 문항에서 확인했듯 히스토그램이
  있는 컬럼에서는 "하나의 계획이 모든 값에 적용되는" 부작용(바인드 변수 Peeking)을 낳을
  수 있다.
- 종합하면: 가능하면 바인드 변수를 기본으로 쓰되, 값에 따라 데이터 분포가 크게 갈리는
  컬럼(스큐가 큰 컬럼)에 조건을 거는 SQL이라면 바인드 변수 Peeking 부작용까지 염두에 두고
  모니터링해야 한다. "무조건 바인드 변수가 정답"도, "무조건 리터럴이 정답"도 아니다.
