================================================================================
 Ch02 실습 01 — 리터럴 SQL 은 값마다 다른 SQL_ID 를 받는다 (하드 파싱 반복 관찰)
 목표: HOSP_ID 리터럴 값만 다른 두 SQL 을 실행해 V$SQL 에 SQL_ID 가 두 개 생기는 것을
       확인한다. 같은 Full Scan(Buffers 3,090)인데 E-Rows 가 3,039 vs 109 로 다른 이유를
       미리 짚고(Ch13), 리터럴 값을 1,000개 병원으로 바꿔 돌리면 공유 풀에 무엇이 쌓이는지
       V$SQL 로 관찰한다.
 환경: non-CDB=orcl 19.3, 스키마 SQLT. V$SQL 조회 권한(SELECT_CATALOG_ROLE) 필요.
 주의: 개인 실습 환경 전용. [3] 은 공유 풀에 커서를 의도적으로 쌓는다 — 실습 후 자연 소멸.
================================================================================

$ sqlplus sqlt/sqlt@orcl

SQLT@orcl> SET LINESIZE 200
SQLT@orcl> SET PAGESIZE 100

--------------------------------------------------------------------------------
-- [1] (조치 전 상태) 리터럴 값이 다른 두 SQL 실행
--------------------------------------------------------------------------------
SQLT@orcl> SELECT /*+ GATHER_PLAN_STATISTICS */ COUNT(*) FROM medical_claims WHERE hosp_id = 1;

  COUNT(*)
----------
      3058

SQLT@orcl> SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR(NULL, NULL, 'ALLSTATS LAST'));

|*  2 |   TABLE ACCESS FULL| MEDICAL_CLAIMS |      1 |   3039 |   3058 |00:00:01.92 |    3090 |

SQLT@orcl> SELECT /*+ GATHER_PLAN_STATISTICS */ COUNT(*) FROM medical_claims WHERE hosp_id = 500;

  COUNT(*)
----------
       177

SQLT@orcl> SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR(NULL, NULL, 'ALLSTATS LAST'));

PLAN_TABLE_OUTPUT
------------------------------------------------------------------------------------------
SQL_ID  5awbw1wcprrj2, child number 0
-------------------------------------
------------------------------------------------------------------------------------------
| Id  | Operation          | Name           | Starts | E-Rows | A-Rows |   A-Time   | Buffers |
------------------------------------------------------------------------------------------
|   0 | SELECT STATEMENT   |                |      1 |        |      1 |00:00:00.01 |    3090 |
|   1 |  SORT AGGREGATE    |                |      1 |      1 |      1 |00:00:00.01 |    3090 |
|*  2 |   TABLE ACCESS FULL| MEDICAL_CLAIMS |      1 |    109 |    177 |00:00:00.01 |    3090 |
------------------------------------------------------------------------------------------
   2 - filter("HOSP_ID"=500)

-- 해석: 문장 구조가 같은데 SQL_ID 가 92p460f4hj858 / 5awbw1wcprrj2 로 다르다.
--   SQL_ID 는 SQL 텍스트의 해시라 글자 하나(1 vs 500)만 달라도 별개 SQL 이다.
--   Buffers 는 둘 다 3,090 — 인덱스가 없어 어느 값을 찾든 전체를 읽는다.
--   E-Rows 는 3,039 vs 109 로 다르다 — HOSP_ID 에 히스토그램이 있어 값별 분포를 안다(Ch13).

--------------------------------------------------------------------------------
-- [2] (이상 징후 → 원인 → 재확인) V$SQL 에 같은 문장이 두 줄
--------------------------------------------------------------------------------
SQLT@orcl> COLUMN sql_text FORMAT A58
SQLT@orcl> SELECT sql_id, executions, parse_calls, loads, sql_text
  2       FROM   v$sql
  3       WHERE  sql_text LIKE 'SELECT /*+ GATHER_PLAN_STATISTICS */ COUNT(*) FROM medical_claims WHERE hosp_id = %'
  4       ORDER  BY sql_id;

SQL_ID        EXECUTIONS PARSE_CALLS      LOADS SQL_TEXT
------------- ---------- ----------- ---------- ----------------------------------------------------------
5awbw1wcprrj2          1           1          1 SELECT /*+ GATHER_PLAN_STATISTICS */ COUNT(*) FROM medical_
92p460f4hj858          1           1          1 SELECT /*+ GATHER_PLAN_STATISTICS */ COUNT(*) FROM medical_

SQLT@orcl> -- 이상 징후: "같은 SQL 을 두 번 실행했는데" 왜 한 줄에 EXECUTIONS=2 가 아니라 두 줄인가.
SQLT@orcl> -- 원인 파악: 같은 SQL 이 아니다. 리터럴이 다르면 텍스트가 다르고, 텍스트가 다르면
SQLT@orcl> --   공유 풀에서 찾지 못해(Parse 단계) 각각 처음부터 최적화한다 = 각각 하드 파싱.
SQLT@orcl> --   LOADS=1 이 "이 커서를 공유 풀에 새로 적재했다" 는 흔적이다.
SQLT@orcl> -- 재확인: 하드 파싱 횟수를 세션 통계로 센다 — 다음 [3] 에서 델타로 잰다.

--------------------------------------------------------------------------------
-- [3] (재현) 병원 1,000개를 리터럴로 조회하면 — 커서가 1,000개 쌓인다
--------------------------------------------------------------------------------
SQLT@orcl> -- T0: 내 세션의 하드 파싱 누적값을 기록한다.
SQLT@orcl> SELECT s.value hard_parse
  2       FROM   v$mystat s, v$statname n
  3       WHERE  s.statistic# = n.statistic# AND n.name = 'parse count (hard)';

HARD_PARSE
----------
  <환경값>                                                   -- (T0)

SQLT@orcl> -- 리터럴을 바꿔 가며 100번 실행한다(1,000번은 시간이 걸리므로 100번으로 관찰).
SQLT@orcl> BEGIN
  2         FOR i IN 1..100 LOOP
  3           EXECUTE IMMEDIATE 'SELECT COUNT(*) FROM medical_claims WHERE hosp_id = ' || i;
  4         END LOOP;
  5       END;
  6       /

PL/SQL procedure successfully completed.

SQLT@orcl> SELECT s.value hard_parse
  2       FROM   v$mystat s, v$statname n
  3       WHERE  s.statistic# = n.statistic# AND n.name = 'parse count (hard)';

HARD_PARSE
----------
  <환경값>                                                   -- (T1) = T0 + 100 ± 수 회

SQLT@orcl> SELECT COUNT(*) cursors, SUM(sharable_mem) sharable_bytes
  2       FROM   v$sql
  3       WHERE  sql_text LIKE 'SELECT COUNT(*) FROM medical_claims WHERE hosp_id = %';

   CURSORS SHARABLE_BYTES
---------- --------------
       100       <환경값>

-- 재확인: 하드 파싱 델타 ≈ 100, V$SQL 에 커서 100개. 병원 1,000개 × 화면 종류 N 이면 공유 풀에
--   수천 개의 커서가 쌓이고 그때마다 하드 파싱(CPU·래치 경합)이 반복된다.
--   같은 일을 바인드 변수로 하면 커서 1개·하드 파싱 1회다 → 실습 02.

--------------------------------------------------------------------------------
-- [정리]
--------------------------------------------------------------------------------
-- 1) SQL_ID 는 텍스트 해시. 리터럴 값이 다르면 별개 SQL 이고 각각 하드 파싱된다(LOADS=1 씩).
-- 2) 같은 Full Scan 이라 Buffers 3,090 은 같지만, E-Rows 는 값에 따라 다르다(히스토그램, Ch13).
-- 3) 'parse count (hard)' 델타와 V$SQL 커서 수로 리터럴 SQL 의 비용을 숫자로 보였다.
-- 4) 인스턴스 부문 TUN 2장·18장은 이 현상이 공유 풀(라이브러리 캐시)에 남기는 흔적을 다룬다.

SQLT@orcl> EXIT
