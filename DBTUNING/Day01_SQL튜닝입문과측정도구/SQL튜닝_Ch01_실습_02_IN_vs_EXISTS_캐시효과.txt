================================================================================
 Ch01 실습 02 — IN vs EXISTS 실측: 실행계획은 같은데 시간이 23배 다른 이유 (캐시 효과)
 목표: "주사제 처방 청구" 를 IN 과 EXISTS 로 각각 작성해 실행계획·Buffers·A-Time 을 비교한다.
       "EXISTS 가 IN 보다 23배 빠르다" 는 오판을 재현하고, 원인이 SQL 구조가 아니라
       버퍼 캐시 상태(실행 순서)임을 실행 순서를 바꿔 증명한다.
 환경: non-CDB=orcl 19.3, 스키마 SQLT. 실습 01 의 측정 표준(GATHER_PLAN_STATISTICS) 사용.
 주의: 개인 실습 환경 전용. 조회만 수행한다. 첫 실행의 A-Time 은 캐시 상태에 따라 달라진다.
================================================================================

$ sqlplus sqlt/sqlt@orcl

SQLT@orcl> SET LINESIZE 200
SQLT@orcl> SET PAGESIZE 100

SQLT@orcl> -- B. EXISTS 방식
SQLT@orcl> SELECT /*+ GATHER_PLAN_STATISTICS */ COUNT(*)
  2       FROM   medical_claims mc
  3       WHERE  EXISTS (SELECT 1
  4                      FROM   claim_details cd, drug_master dm
  5                      WHERE  cd.claim_id  = mc.claim_id
  6                      AND    cd.drug_code = dm.drug_code
  7                      AND    dm.category  = '주사제');

-- [2] (이상 징후 → 원인 → 조치 → 재확인)
--     이상 징후: 같은 계획, 같은 Buffers 인데 EXISTS 가 23배 빠르다.
--       "역시 EXISTS 가 IN 보다 빠르다" 고 결론 내리기 쉽다.
--------------------------------------------------------------------------------
SQLT@orcl> -- 원인 파악: 시간 차이가 어느 단계에 몰려 있는지 본다.
SQLT@orcl> --   Id 7 (PK_MEDICAL_CLAIMS 인덱스 전체 읽기): A 는 2.88초, B 는 0.02초. 나머지 단계는 비슷하다.
SQLT@orcl> --   같은 오퍼레이션·같은 Buffers(1,891)에서 시간만 다르다 = 논리 읽기 수는 같은데
SQLT@orcl> --   블록이 디스크에서 왔는지(물리 읽기) 메모리에서 왔는지가 다르다는 뜻이다.
SQLT@orcl> --   A 를 먼저 실행해 디스크에서 읽어 캐시에 올렸고, B 는 그 블록을 캐시에서 재사용했다.
SQLT@orcl> -- 물리 읽기 여부를 V$SQL 의 DISK_READS 로 확인한다.
SQLT@orcl> SELECT sql_id, executions, buffer_gets, disk_reads, ROUND(elapsed_time/1e6,2) elapsed_s
  2       FROM   v$sql
  3       WHERE  sql_id IN ('cmm0gaqr7whs5','b0r8p72bjvc2f');

SQL_ID        EXECUTIONS BUFFER_GETS DISK_READS ELAPSED_S
------------- ---------- ----------- ---------- ---------
cmm0gaqr7whs5          1        8604   <환경값>      3.04
b0r8p72bjvc2f          1        8604          0       .13

-- 원인 확정: A 는 DISK_READS 가 있고 B 는 0 이다. 차이는 SQL 구조가 아니라 캐시 상태다.

SQLT@orcl> -- 조치: 실행 순서를 뒤집어 재확인한다 — 이번엔 A(IN) 를 두 번째로 실행한다.
SQLT@orcl> SELECT /*+ GATHER_PLAN_STATISTICS */ COUNT(*)
  2       FROM   medical_claims
  3       WHERE  claim_id IN (SELECT cd.claim_id
  4                           FROM   claim_details cd, drug_master dm
  5                           WHERE  cd.drug_code = dm.drug_code
  6                           AND    dm.category  = '주사제');

  COUNT(*)
----------
     79342

SQLT@orcl> SELECT sql_id, executions, buffer_gets, disk_reads, ROUND(elapsed_time/1e6,2) elapsed_s
  2       FROM   v$sql WHERE sql_id = 'cmm0gaqr7whs5';

SQL_ID        EXECUTIONS BUFFER_GETS DISK_READS ELAPSED_S
------------- ---------- ----------- ---------- ---------
cmm0gaqr7whs5          2       17208   <환경값>   <환경값>

-- 재확인: 두 번째 실행에서 BUFFER_GETS 는 정확히 8,604 늘었고(17,208 = 8,604 × 2) DISK_READS 는
--   늘지 않았다. ELAPSED_TIME 증가분은 B 와 같은 0.1초대다(<환경값>: 누적이므로 두 번 조회해 뺀다).
--   → IN 도 캐시에 있으면 EXISTS 만큼 빠르다. 구조적 차이는 없다.

--------------------------------------------------------------------------------
-- [3] (조치 후 관점) 무엇으로 비교해야 하는가
--------------------------------------------------------------------------------
-- * A-Time·ELAPSED 는 캐시 상태에 따라 수십 배 흔들린다. 한 번 잰 시간으로 우열을 가리지 않는다.
-- * Buffers(논리 읽기)는 캐시 상태와 무관하게 같은 계획이면 같다 — 비교의 1차 지표.
-- * 시간을 비교하려면 실행 순서를 통제한다: 같은 캐시 상태(둘 다 웜)에서 각각 2회 이상.
-- * 물리 읽기와 논리 읽기의 관계는 Ch14 실습 01 에서 FLUSH BUFFER_CACHE 로 직접 만들어 본다.

--------------------------------------------------------------------------------
-- [정리]
--------------------------------------------------------------------------------
-- 1) IN 과 EXISTS 는 옵티마이저가 같은 세미조인(HASH JOIN RIGHT SEMI)으로 변환했다. 계획 동일.
-- 2) Buffers 8,604 로 동일. A-Time 3.04초 vs 0.13초는 물리 읽기 유무(캐시)에서 왔다.
-- 3) 실행 순서를 바꾸면 IN 도 0.1초대 — "EXISTS 가 빠르다" 는 이 사례에서 성립하지 않는다.
-- 4) 시간보다 Buffers 를 먼저 보고, 시간은 캐시 상태를 통제한 뒤에만 비교한다.

SQLT@orcl> EXIT
