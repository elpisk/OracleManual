================================================================================
 20장 실습 06 — 메모리 스와핑 징후와 SGA 크기 재검토
 목표: PHYSICAL_MEMORY_BYTES와 SGA·PGA 합을 대조해 스와핑 위험을 점검하고,
       스와핑 중 SGA 확대가 왜 최악의 오조치인지 확인한다.
 환경: non-CDB=orcl 19.3, ASMM 운영(MEMORY_TARGET=0, SGA_TARGET>0)  (SYS AS SYSDBA)
 주의: 개인 실습 환경 전용. 메모리 파라미터 변경은 개인 환경에서만, 백업·원복과 함께.
================================================================================

$ sqlplus / as sysdba

SYS@orcl> SET LINESIZE 200

--------------------------------------------------------------------------------
-- [1] (조치 전 상태) 물리 메모리와 DB가 잡은 메모리를 대조한다.
--------------------------------------------------------------------------------
SYS@orcl> SELECT value phys_bytes,
  2         ROUND(value/1024/1024/1024,2) phys_gib
  3    FROM  v$osstat WHERE stat_name='PHYSICAL_MEMORY_BYTES';

PHYS_BYTES     PHYS_GIB
-------------- --------
8044179456         7.49

SYS@orcl> SELECT name, ROUND(value/1024/1024) mb FROM v$parameter
  2    WHERE name IN ('memory_target','sga_target','pga_aggregate_target',
  3                   'db_cache_size') ORDER BY name;

NAME                        MB
------------------------- ------
db_cache_size                  0     -- ASMM 자동
memory_target                  0     -- AMM 아님
pga_aggregate_target      <환경값>
sga_target                <환경값>

-- 해석: 물리 메모리 약 7.5GiB. memory_target=0·sga_target>0 → ASMM(16장 판별).
--   db_cache_size=0 → 버퍼 캐시 크기를 SGA_TARGET 안에서 자동 조정.

--------------------------------------------------------------------------------
-- [2] (조회) 실제 할당된 SGA·PGA 합이 물리 메모리 대비 얼마인지 본다.
--------------------------------------------------------------------------------
SYS@orcl> SELECT
  2    (SELECT SUM(value) FROM v$sga) sga_bytes,
  3    (SELECT value FROM v$pgastat WHERE name='total PGA allocated') pga_bytes
  4    FROM dual;

SGA_BYTES      PGA_BYTES
-------------- -------------
<환경값>       <환경값>

SYS@orcl> -- 판정 기준: (SGA + PGA + OS·기타 프로세스) 가 물리 메모리에 근접·초과하면
SYS@orcl> --   스와핑 위험. 여유가 크면 안전. (절대값은 환경 의존 → <환경값>)

--------------------------------------------------------------------------------
-- [3] (조회) 스와핑의 직접 징후는 OS에서 본다(오라클 밖).
--------------------------------------------------------------------------------
SYS@orcl> HOST vmstat 1 3
-- procs -----------memory---------- ---swap-- ...
--  r  b   swpd   free   buff  cache   si   so ...
--  0  0      0 <환경값> ...            0    0    ← si/so(스왑 인/아웃)가 0이면 정상
-- 해석: si/so가 지속적으로 0보다 크면 스와핑 발생. 실습기 무부하에선 대개 0.

--------------------------------------------------------------------------------
-- [4] (이상 징후 → 원인 → 조치 → 재확인)
--     이상 징후: "버퍼 캐시 히트율이 낮다"며 SGA_TARGET을 크게 키우자는 제안.
--       그런데 [2]에서 SGA+PGA가 이미 물리 메모리에 근접하고 [3]에서 si/so>0이다.
--------------------------------------------------------------------------------
SYS@orcl> -- 원인 파악: 메모리가 이미 빠듯한데 SGA를 키우면 물리 메모리를 더 잠식해
SYS@orcl> --   스와핑이 악화된다. 게다가 늘린 버퍼 캐시가 스왑으로 밀려나 있어
SYS@orcl> --   캐시 접근이 디스크 접근이 되어 오히려 더 느려진다.
SYS@orcl> --   → '스와핑 중 SGA 확대'는 이 장이 경계하는 최악의 오조치다.
SYS@orcl> --   (히트율은 원인이 아니라 증상일 수 있다 — 17장의 함정.)

SYS@orcl> -- 조치(올바른 순서):
SYS@orcl> --   (1) 스와핑부터 해소 — 불필요한 프로세스 정리, 필요하면 SGA 축소.
SYS@orcl> --   (예, 개인 환경에서만) ALTER SYSTEM SET sga_target=<더 작은 값> SCOPE=BOTH;
SYS@orcl> --   (2) 그래도 캐시가 부족하면 물리 메모리를 증설한 뒤 SGA를 확대.
SYS@orcl> -- ※ 절대 스와핑 상태에서 SGA를 먼저 키우지 않는다.

SYS@orcl> -- 재확인: 조치 후 스왑 인/아웃과 응답을 다시 본다.
SYS@orcl> HOST vmstat 1 3
--  r  b   swpd   free ...   si   so ...
--  0  0      0 <환경값> ...  0    0    ← si/so가 0으로 돌아오면 스와핑 해소 확인
-- 재확인: si/so가 0으로 안정되면 스와핑이 멈춘 것이다. 그 뒤에 캐시를 논한다.

--------------------------------------------------------------------------------
-- [정리]
--------------------------------------------------------------------------------
-- 1) 물리 메모리(V$OSSTAT PHYSICAL_MEMORY_BYTES 약 7.5GiB)와 SGA+PGA 합을 대조한다.
-- 2) 스와핑의 직접 징후는 OS의 vmstat si/so로 본다.
-- 3) 스와핑 중 SGA 확대는 최악 — 물리 메모리 잠식·캐시가 스왑으로 나감.
-- 4) 조치 순서: 스와핑 해소(또는 SGA 축소) → 필요 시 메모리 증설 → 그 뒤 확대.
-- ※ 이 인스턴스는 ASMM. 메모리 방식 판별은 16장, 이 장은 I/O·OS 자원 관점.

SYS@orcl> EXIT
