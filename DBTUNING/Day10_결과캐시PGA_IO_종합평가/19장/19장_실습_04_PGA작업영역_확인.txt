================================================================================
 19장 실습 04 — PGA 작업 영역 확인(V$PGASTAT, V$SQL_WORKAREA_HISTOGRAM)
 목표: 인스턴스 PGA 상태를 조회해 target·over allocation·cache hit를 읽고,
       작업 영역 히스토그램으로 optimal/one-pass/multi-pass 분포를 확인한다.
       '건강한 기본 상태'의 정상값을 몸에 익힌다(나쁜 상태는 실습 05에서 재현).
 환경: non-CDB=orcl 19.3 (SYS), 메모리 관리=ASMM
 주의: 개인 실습 환경 전용. 이 실습은 읽기 전용 조회만 수행한다.
================================================================================

$ sqlplus / as sysdba

SYS@orcl> SET LINESIZE 200

--------------------------------------------------------------------------------
-- [1] (조치 전 상태·조회) V$PGASTAT — 인스턴스 전체 PGA 상태.
--------------------------------------------------------------------------------
SYS@orcl> SELECT name, ROUND(value/1024/1024,2) mb
  2         FROM  v$pgastat
  3         WHERE name IN ('aggregate PGA target parameter','total PGA inuse',
  4                'total PGA allocated','maximum PGA allocated')
  5         ORDER BY 2 DESC;

NAME                              MB
-------------------------------- --------
aggregate PGA target parameter   700
maximum PGA allocated            <환경값>
total PGA allocated              <환경값>
total PGA inuse                  <환경값>

SYS@orcl> SELECT name, value
  2         FROM  v$pgastat
  3         WHERE name IN ('over allocation count','cache hit percentage');

NAME                     VALUE
------------------------ ----------
over allocation count    <환경값>
cache hit percentage     <환경값>

-- 해석: 핵심은 두 줄이다. over allocation count=0 이면 target 700M이 워크로드를 감당해
--   목표를 넘겨 억지로 더 할당한 적이 없다는 뜻(가장 강한 건강 신호). cache hit percentage
--   가 100에 가까우면 작업 영역이 대부분 optimal로 돌았다는 뜻이다. 값은 기동 이후 누적이라
--   <환경값>이고, 가동이 길면 100에서 조금 내려올 수 있다(디스크 정렬이 몇 번 섞이면).
--   total PGA allocated 가 target(700) 이내면 정상 — target은 '목표'이지 '한도'가 아니다.

--------------------------------------------------------------------------------
-- [2] (조회) V$SQL_WORKAREA_HISTOGRAM — 작업 영역 크기별 실행 분포.
--------------------------------------------------------------------------------
SYS@orcl> SELECT low_optimal_size/1024 low_kb,
  2                (high_optimal_size+1)/1024 high_kb,
  3                optimal_executions opt, onepass_executions onepass,
  4                multipasses_executions multi
  5         FROM  v$sql_workarea_histogram
  6         WHERE total_executions > 0
  7         ORDER BY low_optimal_size;

  LOW_KB   HIGH_KB     OPT   ONEPASS   MULTI
-------- --------- ------- --------- -------
  <환경값>  <환경값> <환경값>  <환경값> <환경값>
     ...       ...     ...       ...     ...

-- 해석: 버킷별 실행 분포다. ONEPASS·MULTI 가 (거의) 0이면 작업 영역이 크기와 무관하게
--   대부분 optimal로 돌았다는 뜻이다 — 이것이 [1]의 over allocation 0·높은 cache hit 와
--   같은 이야기다. ONEPASS/MULTI 가 눈에 띄게 잡히면 작업 영역 부족 신호다(실습 05에서 재현).
--   값은 누적이라 <환경값>.

--------------------------------------------------------------------------------
-- [3] (조회) 정렬 통계로 같은 상태를 교차 확인한다.
--------------------------------------------------------------------------------
SYS@orcl> SELECT name, value
  2         FROM  v$sysstat
  3         WHERE name IN ('sorts (memory)','sorts (disk)','sorts (rows)')
  4         ORDER BY name;

NAME             VALUE
---------------- ----------
sorts (disk)     <환경값>
sorts (memory)   <환경값>
sorts (rows)     <환경값>

-- 해석: sorts (disk)가 sorts (memory)에 비해 극히 작으면(예: 수십 대 수백만) 사실상
--   모든 정렬이 메모리에서 끝난 것이다. over allocation 0·높은 cache hit·히스토그램의
--   optimal 우세와 함께 보면 같은 이야기 → 이 PGA는 건강하다. (가동이 길면 sorts(disk)가
--   0이 아니라 작은 값일 수 있다 — 절대 0이 아니라 '메모리 정렬 대비 비율'로 본다.)

--------------------------------------------------------------------------------
-- [4] (이상 가정 → 원인 → 조치 → 재확인) 만약 지표가 나빴다면?
--------------------------------------------------------------------------------
-- * 이상 징후 가정: over allocation count가 계속 증가하거나 히스토그램에
--     onepass/multipass가 잡힌다.
-- * 원인: PGA_AGGREGATE_TARGET이 현재 워크로드에 비해 작아, 작업 영역이
--     optimal을 못 채우고 디스크로 넘치고 있다는 신호다.
SYS@orcl> -- 조치: 추측하지 말고 V$PGA_TARGET_ADVICE로 근거를 확보한다.
SYS@orcl> SELECT ROUND(pga_target_for_estimate/1024/1024) target_mb,
  2                estd_pga_cache_hit_percentage cache_hit_perc,
  3                estd_overalloc_count
  4         FROM  v$pga_target_advice
  5         ORDER BY target_mb;
-- (over allocation=0이 되는 지점 이상으로 target을 올리고, 그 안에서 cache hit를
--  최대화한다. 지금은 지표가 건강하므로 조정이 필요 없다.)

-- 재확인: 실측은 건강한 상태이므로 여기서 어떤 파라미터도 바꾸지 않는다.
--   '지표가 건강한데 PGA부터 키우는 것'은 근거 없는 조치다.

--------------------------------------------------------------------------------
-- [정리]
--------------------------------------------------------------------------------
-- 1) V$PGASTAT: over allocation 0 + 높은 cache hit = 작업 영역이 대부분 optimal.
-- 2) V$SQL_WORKAREA_HISTOGRAM: onepass/multipass 가 (거의) 0 (건강).
-- 3) V$SYSSTAT: sorts (disk)가 sorts (memory) 대비 극히 작음으로 교차 확인.
-- 4) target은 목표이지 한도가 아니다. 조정은 V$PGA_TARGET_ADVICE 근거로.
-- ※ 이 V$ 조회들은 관리 팩 라이선스와 무관하다.

SYS@orcl> EXIT
