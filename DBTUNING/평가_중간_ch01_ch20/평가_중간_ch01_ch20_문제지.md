# 문제 1. 느린 조회 두 개를 끝까지 (40점)

심사 화면과 정산 보고에서 각각 느리다는 신고가 올라왔다.

> **신고 A** "청구 목록을 뒤로 넘길수록 느려진다. 1페이지는 참을 만한데 50페이지는 체감이 다르다."
> **신고 B** "한 달치만 보는데 왜 전체를 읽는지 모르겠다. 인덱스를 만들면 빨라지냐고 개발팀이 묻는다."

두 SQL 은 `scripts/EX_01_대상SQL.sql` 에 있다. **이 파일을 고치지 않는다.**
먼저 그대로 실행해 베이스라인을 잡는다.

```sql
SQL> @EX_01_대상SQL.sql
```

### 1-(1) 베이스라인 (6점)

|---|---|---|---|---|---|---|---|

### 1-(2) 원인 지목 (10점)

Q1 의 `Predicate Information` 에서 `MEDICAL_CLAIMS` 에 붙은 조건을 **그대로 옮겨 적고**,
그것이 `access` 인지 `filter` 인지 쓴다. 그리고 다음에 답한다.

- (a) 이 조건이 그 판정을 받는 이유는 무엇인가. 한 문장.
- (b) Q1 의 `TABLE ACCESS FULL MEDICAL_CLAIMS` 단계에서 **E-Rows 와 A-Rows 가 몇 배 차이**나는가.
      옵티마이저가 그렇게 추정한 이유를 쓴다.
- (c) Q1 이 느려지는 원인을 **서로 다른 세 가지**로 나눠 적는다. 각각 어느 장에서 다룬 것인지 장 번호를 붙인다.

### 1-(3) 조치 1 — SQL 만 고친다 (8점)

인덱스를 만들지 않은 상태에서 Q1 의 **WHERE 절만** 고쳐 다시 측정한다.

- (a) 고친 SQL 전문
- (b) 고친 뒤의 `Buffers` 와 `E-Rows`
- (c) **`Buffers` 가 거의 그대로인데도 이 조치가 필요한 이유**를 쓴다. (이 문항의 핵심이다)

### 1-(4) 조치 2 — 인덱스 (10점)

인덱스를 **1개만** 만들어 Q1 과 Q2 를 **동시에** 개선한다.

- (a) `CREATE INDEX` 문 전문. 컬럼 순서를 그렇게 정한 이유를 컬럼별로 한 줄씩.
- (b) 인덱스 생성 후 `USER_INDEXES` 에서 `BLEVEL` · `LEAF_BLOCKS` · `CLUSTERING_FACTOR` 를 적는다.
- (c) Q1·Q2 를 재측정해 아래를 채운다. `TABLE ACCESS` 단계가 계획에서 사라졌는지 확인한다.

| | 조치 전 Buffers | 조치 후 Buffers | 개선 배수 | 조치 후 Operation |
|---|---|---|---|---|
| Q1 | | | | |
| Q2 | | | | |

- (d) Q2 는 `ORDER BY total_amt DESC` 인데 인덱스 선두 컬럼은 `total_amt` 가 아니다.
      그런데도 빨라졌다. **정렬이 없어진 것인지, 다른 이유인지** 계획을 근거로 판정한다.

### 1-(5) 조치 3 — 깊은 페이징의 구조적 한계 (6점)

조치 2 를 해도 **50페이지가 1페이지보다 느리다는 사실 자체는 남는다.**

- (a) 계획의 어느 단계가 그 원인인지 지목하고, 페이지가 깊어질 때 그 단계의 `A-Rows` 가
      어떻게 변하는지 **1페이지와 50페이지를 각각 측정해** 보인다.
- (b) Keyset(무한 스크롤) 방식으로 50페이지에 해당하는 20건을 가져오는 SQL 을 쓰고 측정한다.
      49페이지 마지막 행의 키 값은 직접 구한다.
- (c) Keyset 을 쓸 수 없는 업무 요구 **두 가지**를 쓴다.

# 문제 2. 야간 배치가 2시간을 넘긴다 (35점)

운영 중인 심사 반려 배치가 밤마다 점점 늦게 끝난다. 데이터 양은 거의 늘지 않았다.
배치 원본은 `scripts/EX_02_배치원본.sql` 이다. **이 파일을 고치지 않는다.**

```sql
SQL> @EX_90_측정보조.sql SNAP B0 -
SQL> @EX_02_배치원본.sql
SQL> @EX_90_측정보조.sql SNAP B1 -
SQL> @EX_90_측정보조.sql DELTA B0 B1
```

### 2-(1) 낭비를 수치로 지목한다 (12점)

델타에서 **지표 이름을 그대로 인용해** 세 가지 낭비를 각각 증명한다.
각 낭비마다 지표 2개 이상, 값까지 적는다.

| 낭비 | 근거 지표(이름) | 델타 값 | 이 값이 그 낭비를 뜻하는 이유 |
|---|---|---|---|
| ① | | | |
| ② | | | |
| ③ | | | |

### 2-(2) 커밋 비용은 어디에 나타났는가 (7점)

델타를 보면 `user commits` 는 2,000회인데 **`log file sync` 대기는 한 자리 수**다.
그런데 LGWR 쪽 지표는 크게 움직였다.

- (a) 크게 움직인 그 지표 이름과 델타 값
- (b) 세션은 거의 기다리지 않았는데 비용이 발생한 이 현상을 설명한다.
- (c) 이 환경에서 "건당 커밋이 비싸다"를 증명하려면 어느 지표를 근거로 써야 하는가.

### 2-(3) 파싱이 DB Time 에서 차지한 몫 (6점)

`DELTA` 출력 끝의 `DB Time 분해` 를 쓴다.

- (a) 구간 `DB time`, `parse time elapsed`, 그 **비율(%)**
- (b) 이 비율을 보고 "I/O 를 먼저 보겠다"는 판단이 왜 틀렸는지 한 문장.

### 2-(4) 고쳐서 재측정 (10점)

세 낭비를 모두 고친 배치를 작성해 같은 방법으로 측정한다(태그 `C0` / `C1`).

- (a) 고친 PL/SQL 전문
- (b) 전후 대조표 — **최소 다음 6개 지표**를 포함한다.
      `parse count (hard)` · `parse count (total)` · `user commits` · `session logical reads` ·
      `redo size` · `parse time elapsed`
- (c) `V$SQL` 에서 **커서 개수와 커서당 실행 횟수**가 어떻게 바뀌었는지 보인다.
- (d) 구획 B 를 조인 1회로 바꿨을 때 **실행당 논리 읽기**가 어떻게 바뀌었는지 보인다.

# 문제 3. "어제 오후에 느렸다"는 신고 한 줄 (25점)

> 사용자 민원: "어제 오후에 화면이 느렸다."
> SQL 도, 정확한 시각도, 세션 정보도 없다. 지금 재현해 원인을 확정해야 한다.

```sql
SQL> @EX_90_측정보조.sql SNAP E0 -
SQL> @EX_03_사건재현.sql
SQL> @EX_90_측정보조.sql SNAP E1 -
SQL> @EX_90_측정보조.sql DELTA E0 E1
```

### 3-(1) 측정 경로 선택 (4점)

이 환경에서 사후 진단에 쓸 수 있는 경로를 **세 가지** 적고, 각각 쓸 수 있는지 판정한다.
판정 근거는 조회 결과여야 한다(라이선스 파라미터, 보존 기간, SYSAUX 사용량 등).

| 경로 | 쓸 수 있나 | 근거(조회 결과) |
|---|---|---|
| AWR | | |
| Statspack | | |
| V$ 델타 직접 캡처 | | |

그리고 **"어제 오후"를 사후에 진단할 수 있었는지**를 보존 설정 근거로 답한다.

### 3-(2) DB Time 분해 (5점)

사건 구간의 `DB time` 을 `DB CPU` / 대기 / 파싱으로 나눠 적고, **대기 몫의 %** 를 계산한다.
그리고 "느렸다"의 원인이 **대기인지 CPU인지** 판정한다.

### 3-(3) 상위 대기 클래스 (3점)

`V$SYSTEM_WAIT_CLASS` 델타로 상위 3개를 적는다. `Idle` 을 어떻게 처리했는지도 쓴다.

### 3-(4) 원인 SQL 지목 — 함정이 있다 (8점)

- (a) `V$SQL` 의 `buffer_gets` **절대값 상위 5개**를 그대로 적는다.
- (b) 그중 **이 사건과 무관한 것**을 고르고 왜 무관한지 쓴다.
- (c) 사건 구간에 실제로 읽은 SQL 을 찾아 **SQL_ID · 실행 횟수 · 실행당 논리 읽기**를 적는다.
- (d) **이 사건의 논리 읽기 대부분을 만든 SQL 은 `V$SQL` 의 어떤 상위 목록에도 보이지 않는다.**
      이유를 설명하고, 그것을 드러내는 집계 방법을 SQL 로 제시해 실제로 찾아낸다.

### 3-(5) 조치 설계와 근거 보존 (5점)

- (a) 확정한 원인 **세 가지**와 각각의 조치안. 조치는 실제로 적용하지 않는다(설계만).
- (b) 이 진단의 근거를 다음 담당자가 재현할 수 있도록 남기는 방법을 쓴다.
      무엇을 어떤 순서로 캡처해야 하는지 ch17 에서 배운 양식으로 적는다.
