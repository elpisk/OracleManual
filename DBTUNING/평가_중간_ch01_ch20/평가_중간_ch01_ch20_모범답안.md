# 문제 1 모범답안 (40점)

## 1-(1) 베이스라인 (6점)

| | Operation(비용 단계) | Starts | E-Rows | A-Rows | Buffers | A-Time | Used-Mem |
|---|---|---|---|---|---|---|---|
| **Q1** | `TABLE ACCESS FULL MEDICAL_CLAIMS` | 1 | **3,000** | **24,655** | 3,091 | 0.04s | — |
| | `HASH JOIN` | 1 | 789 | 132→16,897 | 3,106 | 0.03s | 1,362K (0) |
| | `SORT ORDER BY STOPKEY` | 1 | 789 | 1,000 | 3,106 | 0.04s | 14,336 (0) |
| | **전체 (Id 0)** | 1 | — | 20 | **3,106** | 0.04s | — |
| **Q2** | `TABLE ACCESS FULL MEDICAL_CLAIMS` | 1 | 25,477 | 24,655 | 3,090 | 0.01s | — |

있다는 지목이 있으면 만점. 3,090 은 ch01 실습 01 의 Full Scan 베이스라인과 같은 값이다.

## 1-(2) 원인 지목 (10점)

**조건 원문과 판정**

```
   7 - filter(TO_CHAR(INTERNAL_FUNCTION("C"."RECEIPT_DATE"),'YYYYMM')='202406')
```

→ **`filter`** 다. (`access` 가 아니다)

- **(a)** 인덱스 컬럼을 `TO_CHAR` 로 가공했기 때문이다. 가공된 값은 인덱스에 저장된 값과
  달라서 B-Tree 를 탐색할 키로 쓸 수 없다. 그래서 행을 다 읽은 뒤 버리는 `filter` 가 된다.
  (ch07 — SARGable)

- **(b)** `E-Rows 3,000` vs `A-Rows 24,655` → **약 8.2배 과소추정**.
  `TO_CHAR(컬럼)=상수` 는 옵티마이저가 선택도를 계산할 수 없어 **기본 선택도 1%**
  (300,000 × 0.01 = 3,000)를 쓴다. `RECEIPT_DATE` 에 히스토그램이 있어도 쓰이지 않는다.
  (ch08 — 통계가 있어도 가공하면 못 쓴다)

- **(c)** 세 가지 원인
  1. **SARGable 위반** — `TO_CHAR(receipt_date)` 가공으로 인덱스 사용 불가 + 추정 붕괴 (**ch07**)
  2. **인덱스 부재** — `MEDICAL_CLAIMS` 에 PK(`CLAIM_ID`) 말고 없어서 8.2% 를 읽으려고
     전체 3,090 블록을 읽는다 (**ch05 · ch06**)
  3. **깊은 OFFSET 페이징** — 50페이지(20건)를 위해 1,000행을 만들어 정렬한다.
     `COUNT STOPKEY` 와 `SORT ORDER BY STOPKEY` 의 `A-Rows` 가 1,000 인 것이 증거 (**ch13**)

  (추가로 `h.city='서울'` 이 `HOSPITALS` 쪽 `filter` 라 조인 후에야 줄어드는 점,
  `HASH JOIN` 이 1,362K 작업 영역을 쓰는 점을 들면 가점)

## 1-(3) 조치 1 — SQL 만 고친다 (8점)

**(a)**

```sql
AND c.receipt_date >= DATE '2024-06-01'
AND c.receipt_date <  DATE '2024-07-01'
```

`TO_CHAR` 를 버리고 **반열린 구간**으로 바꾼다. `BETWEEN ... AND DATE '2024-06-30'` 은
6월 30일 00:00:00 이후 시각을 놓치므로 감점(이 데이터는 시각이 00:00:00 이라 건수는
같게 나오지만, 조건 자체가 틀렸다).

**(b)** `Buffers` **3,106 → 3,106 (변화 없음)**.
`Plan hash value` 도 2104355456 그대로다. 그러나 `TABLE ACCESS FULL` 의
`E-Rows` 가 **3,000 → 25,477** 로 바뀐다 (A-Rows 24,655 대비 오차 **3.3%**).
`Predicate` 도 `filter(...)` 에서 범위 조건으로 바뀐다.

**(c)** 핵심 두 가지를 모두 써야 만점.

1. **추정이 맞아야 계획이 맞는다.** 8.2배 과소추정 상태에서는 인덱스를 만들어도
   옵티마이저가 "3,000건만 나온다"고 믿어 엉뚱한 계획을 고를 수 있다. 조치 1 은
   조치 2 의 **전제 조건**이다.
2. **가공을 없애야 인덱스가 `access` 로 쓰일 수 있다.** 가공이 남아 있으면 인덱스를
   만들어도 `filter` 로만 쓰여 비용이 줄지 않는다.

> "Buffers 가 안 줄었으니 효과가 없다" 라고 답하면 0점. 이 문항이 묻는 것이 바로 그 함정이다.

## 1-(4) 조치 2 — 인덱스 (10점)

**(a)**

```sql
CREATE INDEX ex_ix_mc_dt ON medical_claims(receipt_date, claim_id, total_amt, hosp_id);
```

| 컬럼 | 그 자리에 둔 이유 |
|---|---|
| `receipt_date` | 선두. Q1·Q2 의 유일한 범위 조건이고 선택도 8.2% 로 가장 좁힌다 |
| `claim_id` | Q1 의 2차 정렬 키이자 SELECT 목록. 커버링을 만든다 |
| `total_amt` | Q2 의 정렬 키이자 SELECT 목록. 이것이 있어야 Q2 도 테이블에 가지 않는다 |
| `hosp_id` | Q1 의 조인 키. 이것까지 넣어야 Q1 도 테이블 접근이 0 이 된다 |

> 정답은 하나가 아니다. **선두가 `receipt_date` 이고, Q1·Q2 의 참조 컬럼을 모두 담아
> 테이블 접근을 없앴다면** 순서가 달라도 만점. 선두를 `total_amt` 나 `hosp_id` 로 두면
> 범위 조건을 못 써서 개선이 작아지므로 감점.

**(b)** 실측

| 항목 | 값 |
|---|---|
| `BLEVEL` | 2 |
| `LEAF_BLOCKS` | 1,864 |
| `DISTINCT_KEYS` | 300,000 |
| `CLUSTERING_FACTOR` | 263,835 |

`CLUSTERING_FACTOR` 263,835 / 300,000 행 → 행마다 거의 블록 하나씩 흩어져 있다.
**테이블로 가야 했다면** 이 인덱스는 손해였다는 뜻이고, 커버링이 유일한 해법인 근거다
(ch05 실습 02 의 "838건 → 724블록" 과 같은 구조).

**(c)**

| | 조치 전 Buffers | 조치 후 Buffers | 개선 배수 | 조치 후 Operation |
|---|---|---|---|---|
| **Q1** | 3,106 | **171** | **18.2배** | `INDEX RANGE SCAN EX_IX_MC_DT`(156) + `HASH JOIN` + `SORT ORDER BY STOPKEY` |
| **Q2** | 3,090 | **156** | **19.8배** | `WINDOW SORT PUSHED RANK` + `INDEX RANGE SCAN EX_IX_MC_DT` |

Q1 `Plan hash value: 409403334`. **두 계획에서 `TABLE ACCESS` 단계가 사라졌다**(Index-Only).
Q1 의 `Predicate` 가 `access("C"."RECEIPT_DATE">=... AND "C"."RECEIPT_DATE"<...)` 로
바뀐 것을 확인했으면 가점.

**(d)** **정렬은 사라지지 않았다.**
Q2 의 계획에 `WINDOW SORT PUSHED RANK` 가 그대로 있고, `Used-Mem` 은 오히려
2,048 → 4,096 으로 늘었다. 인덱스 선두가 `total_amt` 가 아니므로 정렬을 대신해 줄 수 없다.

빨라진 이유는 **정렬의 입력을 얻는 비용**이다. 24,655행을 모으는 데 테이블 전체
3,090 블록을 읽던 것이 인덱스 리프 156 블록으로 줄었다. 정렬 대상 행 수(24,655)는
그대로다. (ch12 — 넓은 범위 `ORDER BY` 는 PK 컬럼이라도 정렬된다)

## 1-(5) 조치 3 — 깊은 페이징 (6점)

**(a)** 원인 단계는 **`COUNT STOPKEY` + `SORT ORDER BY STOPKEY`** 다.
페이지가 깊어질수록 `ROWNUM <= N` 의 N 이 커져 이 단계의 `A-Rows` 가 함께 커진다.

| 페이지 | `ROWNUM <=` | `SORT ORDER BY STOPKEY` 의 A-Rows |
|---|---|---|
| 1페이지 | 20 | 20 |
| 50페이지 | 1,000 | **1,000** |

`Buffers` 는 둘 다 171 로 같다. **읽는 블록은 같은데 정렬·순위 매김 대상만 50배**다
— ch13 실습 01 의 "Buffers 같고 시간과 메모리만 급증" 과 같은 구조.

**(b)** 49페이지 마지막 행(실측) : `receipt_date = 2024-06-29`, `claim_id = '20240629-0076332'`

```sql
SELECT * FROM (
  SELECT c.claim_id, c.receipt_date, c.total_amt, h.hosp_name
    FROM medical_claims c, hospitals h
   WHERE c.hosp_id = h.hosp_id
     AND c.receipt_date >= DATE '2024-06-01'
     AND c.receipt_date <  DATE '2024-07-01'
     AND h.city = '서울'
     AND (c.receipt_date < DATE '2024-06-29'
          OR (c.receipt_date = DATE '2024-06-29'
              AND c.claim_id  < '20240629-0076332'))
   ORDER BY c.receipt_date DESC, c.claim_id DESC)
WHERE ROWNUM <= 20;
```

튜플 비교(`(a,b) < (x,y)`)는 쓸 수 없으므로 `OR` 로 풀어 쓴다(ch13 실습 02).

**(c)** Keyset 을 쓸 수 없는 요구 — 아래 중 둘

- **임의 페이지 점프** — "37페이지로 바로" 가 불가능하다. 직전 페이지의 키가 있어야 한다.
- **전체 건수·페이지 수 표시** — "1,234건 중 981~1,000" 을 보여 주려면 어차피 전체를 세야 한다.
- **정렬 키에 동률이 많을 때** — 유일성을 보장하는 꼬리 키(여기서는 `claim_id`)를
  정렬과 조건에 모두 넣지 않으면 행이 빠지거나 겹친다(ch13 실습 03).
- **임의 정렬 컬럼 선택** — 사용자가 정렬 기준을 바꿀 수 있으면 조합마다 인덱스가 필요하다.

## 2-(2) 커밋 비용은 어디에 나타났는가 (7점)

**(a)** `log file parallel write` — **1,896회 / 4,089ms**.
(`log file sync` 는 **5회 / 16ms** 뿐이었다)

**(b)** `log file sync` 는 **전경 세션이 커밋 응답을 기다린 시간**이고,
`log file parallel write` 는 **LGWR 가 리두 파일에 쓴 시간**이다. 이 장비의 리두 쓰기가
빠르고 19c 의 적응형 `log file sync`(폴링/post-wait 전환)가 동작해, 세션은 거의
기다리지 않았지만 **LGWR 는 1,896번 일했다**. 즉 일은 그대로 발생했고 대기만 안 보인다.

**(c)** 이 환경에서 "건당 커밋이 비싸다"의 근거는
`user commits` · `log file parallel write`(횟수와 시간) · `redo entries` 다.
**`log file sync` 만 보고 "커밋은 문제없다"고 결론 내리면 틀린다.**

> 이것이 이 문항의 핵심이다. 대기 이벤트가 0 에 가깝다는 것은 "비용이 없다"가 아니라
> "그 지표에 안 나타난다"는 뜻이다(ch19 — 일의 양과 대기를 분리해 읽는다).

| 지표 | 값 |

## 2-(4) 고쳐서 재측정 (10점)

**(a)** 고친 배치 — 세 곳을 모두 바꾼다

               WHERE review_status = '심사중' AND ROWNUM <= 2000) LOOP

            'INSERT INTO REVIEW_LOG_EX_WL '
         || '(log_id, claim_id, reviewer_id, process_date, action_msg, error_code) '

            USING v_id, r.claim_id, 'SYSTEM',

                  'E' || TO_CHAR(10 + MOD(v_id, 89));
        IF MOD(v_id, 500) = 0 THEN COMMIT; END IF;
    END LOOP;
    COMMIT;

    -- 구획 B' : 조인 1회

      FROM (SELECT d.claim_id, COUNT(*) cnt
              FROM claim_details d
             WHERE d.claim_id IN (SELECT claim_id FROM medical_claims
                                   WHERE receipt_date >= DATE '2024-06-01'
                                     AND receipt_date <  DATE '2024-06-02'

**(d)** N+1 → 조인 1회 (실측)

| | 실행 횟수 | 실행당 논리 읽기 | 20건 처리에 드는 총량 |
|---|---|---|---|
| `EX02_DETAIL` (N+1) | 20 | **6,622** (실측) | 6,622 × 20 = **132,440** |
| `N2_JOIN1` (조인 1회) | **1** | **6,699** (실측) | **6,699** |

(`V$SQL` 의 `executions` 는 누적이므로 실행당 값으로 비교한다. 총량은 그 값 × 20 이다)

**20배**다. ch14 실습 01·02 의 "132,468블록 → 6,645블록" 과 같은 값이 재현된다.
근본 해법은 반복을 없애는 것이고, 반복을 못 없앨 때의 완화책이
`CLAIM_DETAILS(CLAIM_ID)` FK 인덱스다 — 다만 이 평가에서는 인덱스를 1개만 쓸 수 있고
그 1개는 문제 1 에 썼으므로, **설계만 적고 만들지 않는 것이 정답이다.**

**"어제 오후"를 사후 진단할 수 있었는가** — 스냅샷이 있어야만 가능하다.

```sql
SELECT snap_interval, retention FROM dba_hist_wr_control;
SELECT MIN(begin_interval_time), MAX(begin_interval_time) FROM dba_hist_snapshot;
```

보존 기간이 기본 8일이고 스냅샷 주기가 1시간이면 어제 오후는 **남아 있다**.
그러나 **V$ 뷰만으로는 불가능하다** — 누적값뿐이라 "어제 오후" 구간을 떼어낼 수 없다.
**사건이 지나간 뒤에는 미리 잡아 둔 스냅샷만이 근거가 된다**는 것이 이 문항의 결론이고,
그래서 ch20 이 스냅샷 주기·보존·베이스라인을 먼저 다룬다.

## 3-(2) DB Time 분해 (5점)

> 대기 이벤트부터 뒤진 답안은 과정을 거꾸로 밟은 것이다. `DB time` 을 먼저 쪼개는 것이

**(b)** 1·2·4·5위가 **이 사건과 무관**하다.

|---|---|---|---|---|
| `6q2sbm3nv7prh` | 12 | 79,458 | **6,622** | `/*+ EX03_A */ COUNT(*) FROM CLAIM_DETAILS WHERE amt > ...` |
| `9f1y5cvfjysva` | 8 | 24,728 | **3,091** | `/*+ EX03_B */ ... ROW_NUMBER() OVER (ORDER BY total_amt ...)` |

**(d)** **가장 큰 덩어리는 어떤 상위 목록에도 안 보인다.**

사건 구간 논리 읽기는 **325,295** 블록인데 위 두 SQL 을 더해도 104,186 뿐이다.
나머지는 구획 3 이 만든 **리터럴 SQL** 이고, `hosp_id` 값마다 문장이 달라
**커서 80개로 쪼개졌다.** 커서 하나당 3,093 블록이라 어느 상위 N 목록에도 걸리지 않는다.

같은 모양을 하나로 묶는 집계 방법은 `FORCE_MATCHING_SIGNATURE` 다.

```sql
SELECT force_matching_signature AS sig,
       COUNT(*)            AS 커서수,
       SUM(executions)     AS 총실행,
       SUM(buffer_gets)    AS 총논리읽기,
       ROUND(SUM(buffer_gets) / DECODE(SUM(executions), 0, 1, SUM(executions))) AS 실행당
  FROM v$sql
 WHERE force_matching_signature <> 0
 GROUP BY force_matching_signature
 ORDER BY SUM(buffer_gets) DESC
 FETCH FIRST 5 ROWS ONLY;
```

실측 결과 — 쪼개진 80개를 묶으면 **247,440 블록**으로 단번에 상위권에 올라온다.

| 서명 | 커서수 | 총 실행 | 총 논리 읽기 |
|---|---|---|---|
| `1.8616E+18` | **80** | 80 | **247,440** |

247,440 / 325,295 = **구간 논리 읽기의 76%**. 이것이 진짜 원인 SQL 이다.
`MEDICAL_CLAIMS` 를 `hosp_id` 조건으로 읽는데 그 컬럼에 인덱스가 없어 매번 3,090 블록을
전부 읽는다(ch05). 그리고 리터럴이라 파싱도 매번 한다(ch16) — 3-(2) 의 파싱 55% 와 이어진다.

채점: (d) 는 "리터럴 때문에 커서가 쪼개져 순위에 안 보인다" + `FORCE_MATCHING_SIGNATURE`
집계 제시 + 실제로 찾아낸 수치, 세 가지가 있어야 만점(각 2점, 수치 2점).
