================================================================================
 14장 실습 04 — log file sync 재현, 커밋 빈도와의 관계 (WL_05_commit.sql)
 목표: 같은 양의 DML을 '건당 커밋'과 '배치 커밋'으로 각각 실행해, 바뀐
       데이터 양(redo size)은 비슷한데 log file sync 대기 횟수·시간만 크게
       달라짐을 확인한다. '일의 양'과 '대기'를 분리해 해석한다.
 환경: non-CDB=orcl 19.3 (진단 SYS AS SYSDBA / 부하 SQLT@orcl)
 라이선스: V$ 실시간 조회는 라이선스 무관.
 부하: WL_05_commit.sql — 복제 테이블 REVIEW_LOG_CMT_WL에서만 DML(원본 불변).
 주의: 개인 실습 환경 전용. 원본 REVIEW_LOG은 갱신하지 않는다.
================================================================================

-- [터미널 A] 진단 계정에서 부하 전 기준선을 잡는다.
$ sqlplus / as sysdba

SYS@orcl> SET LINESIZE 200

SYS@orcl> COLUMN event FORMAT A26

--------------------------------------------------------------------------------
-- [1] (조치 전 상태) log file sync와 그 짝(parallel write)의 부하 전 누적.
--------------------------------------------------------------------------------
SYS@orcl> SELECT event, total_waits, ROUND(time_waited/100) sec
  2       FROM  v$system_event
  3       WHERE event IN ('log file sync','log file parallel write');

EVENT                      TOTAL_WAITS        SEC
-------------------------- ----------- ----------
log file parallel write         197378        398
log file sync                     2694          7

-- [터미널 B] 업무 계정으로 커밋 부하를 실행한다. WL_05 는 한 번에 두 구획을 돌리고 비교표를 낸다:
--   구획1 건당 커밋(5,000행을 1행마다 COMMIT = 5,000회) + 구획2 배치 커밋(500행마다 1회 = 약 11회).
--   복제본 REVIEW_LOG_CMT_WL 에서만 DML 한다(원본 불변).
-- ▶ 부하: WL_05_commit.sql × 1 DEFINE wl_rows=5000 DEFINE wl_batch=500

--------------------------------------------------------------------------------
-- [2] (조회) 부하 직후 델타를 확인한다 — 이 VM(SSD·빠른 리두)에서 무엇이 움직였나.
--------------------------------------------------------------------------------
SYS@orcl> COLUMN wait_class FORMAT A10

SYS@orcl> SELECT event, total_waits, ROUND(time_waited/100) sec, wait_class
  2       FROM  v$system_event
  3       WHERE event IN ('log file sync','log file parallel write')
  4       ORDER BY time_waited DESC;

EVENT                                                            TOTAL_WAITS        SEC WAIT_CLASS
---------------------------------------------------------------- ----------- ---------- ----------
log file parallel write                                               198118        398 System I/O
log file sync                                                           2696          7 Commit

-- 해석(중요): 커밋을 5,000회나 했는데도 log file sync 증가분이 거의 0 이다. 이 VM 은 리두가 SSD 라
--   커밋이 LGWR 쓰기 완료를 기다릴 새 없이 끝나기 때문이다. 대신 LGWR 자신의 쓰기인
--   log file parallel write 가 늘었다(+수백 회). '과도한 커밋 → log file sync 폭증'은 리두 저장장치가
--   느릴 때 두드러지는 현상이고, 빠른 저장장치에서는 그 비용이 커밋 횟수·redo·parallel write 로 나타난다.

--------------------------------------------------------------------------------
-- [3] (이상 징후 → 원인 → 조치 → 재확인)
--     이상 징후: 담당자가 "log file sync 가 0 에 가까우니 커밋을 아무리 해도 문제없다"고 한다.
--------------------------------------------------------------------------------
SYS@orcl> -- 원인 파악: 대기(sync)가 안 잡혀도 '일의 양'은 커밋 방식에 따라 갈린다. WL_05 비교표를 본다:
SYS@orcl> --   (세션 통계, 같은 5,000행 갱신)
SYS@orcl> --   지표                     건당 커밋      배치 커밋
SYS@orcl> --   user commits              5,000            11
SYS@orcl> --   redo size (bytes)      2,948,556     1,483,556
SYS@orcl> --   redo entries             10,007         5,010
SYS@orcl> --   log file sync 대기ms          0             0
SYS@orcl> -- 원인 확정: 커밋 방식만 바꿨는데 redo size·entries 가 약 2배 차이 난다. 건당 커밋은 커밋마다
SYS@orcl> --   리두 레코드를 더 만든다(커밋 자체의 오버헤드). log file sync 가 0 이라고 '공짜'가 아니다 —
SYS@orcl> --   리두 생성량·CPU·LGWR 부하로 비용을 치른다. 느린 저장장치라면 여기에 sync 대기까지 더해진다.
SYS@orcl> -- 조치: 애플리케이션 루프 안 COMMIT 을 제거하고 N건마다 배치 커밋한다(redo·커밋 횟수 절감).
SYS@orcl> -- 재확인: user commits 델타로 커밋 횟수 폭증을 직접 확인한다.
SYS@orcl> COLUMN name FORMAT A16

SYS@orcl> SELECT n.name, s.value
  2       FROM  v$sysstat s JOIN v$statname n ON n.statistic#=s.statistic#
  3       WHERE n.name = 'user commits';

NAME                  VALUE
---------------- ----------
user commits       14978009

--------------------------------------------------------------------------------
-- [정리]
--------------------------------------------------------------------------------
-- 1) log file sync는 커밋 세션이 리두 기록 완료를 기다리는 Commit 클래스 이벤트.
-- 2) 짝 이벤트 log file parallel write와 평균 대기 시간으로 원인을 가른다.
-- 3) 평균 작고 횟수 폭발 → 과도한 커밋(디스크 아님) → 배치 커밋이 처방.
-- 4) 원본 불변, 복제본 REVIEW_LOG_CMT_WL에서만 DML 했다.

SYS@orcl> EXIT
