================================================================================
 14장 실습 02 — db file sequential / scattered read 유발과 구분 (WL_02_io.sql)
 목표: 인덱스 경유 단일 블록 읽기(sequential)와 대량 풀스캔의 다중 블록
       읽기(scattered)를 각각 유발해, 같은 'physical reads'라도 어떤 대기
       이벤트로 나타나는지, 한 번에 몇 블록을 읽는지를 수치로 구분한다.
 환경: non-CDB=orcl 19.3 (진단 SYS AS SYSDBA / 부하 SQLT@orcl)
 라이선스: V$ 실시간 조회는 라이선스 무관.
 부하: 공용 부하 스크립트 WL_02_io.sql (SELECT만 수행, 원본 불변).
 주의: 개인 실습 환경 전용. WL_02는 원본 데이터를 변경하지 않는다.
================================================================================

-- [터미널 A] 진단 계정으로 부하 전 기준선을 먼저 잡는다.
$ sqlplus / as sysdba

SYS@orcl> SET LINESIZE 200

--------------------------------------------------------------------------------
-- [1] (조치 전 상태) 부하 전 두 I/O 이벤트의 누적 대기를 적어 둔다(기준선).
--------------------------------------------------------------------------------
SYS@orcl> COLUMN event FORMAT A34

SYS@orcl> SELECT event, total_waits, ROUND(time_waited/100) sec
  2       FROM  v$system_event
  3       WHERE event IN ('db file sequential read','db file scattered read');

EVENT                              TOTAL_WAITS        SEC
---------------------------------- ----------- ----------
db file sequential read                 145179        236
db file scattered read                   19741         62

-- 해석: 절대값은 환경마다 다르다. 중요한 것은 부하 후 '증가분(델타)'이다.

-- [터미널 B] 업무 계정으로 I/O 부하를 건다: PK 경유 랜덤 단일 블록 읽기 + CLAIM_DETAILS 대량 스캔.
--   각 세션: DEFINE wl_rand = 200000 / DEFINE wl_scan = 20 / DEFINE wl_flush = 1 → @WL_02_io.sql
-- ▶ 부하: WL_02_io.sql × 2 DEFINE wl_rand=200000 DEFINE wl_scan=20 DEFINE wl_flush=1

--------------------------------------------------------------------------------
-- [2] (조회) 부하 후 누적을 다시 읽어 두 이벤트를 비교한다.
--------------------------------------------------------------------------------
SYS@orcl> COLUMN event FORMAT A26

SYS@orcl> COLUMN wait_class FORMAT A10

SYS@orcl> SELECT SUBSTR(event,1,26) event, total_waits,
  2         ROUND(time_waited/100) sec, wait_class
  3       FROM  v$system_event
  4       WHERE event IN ('db file sequential read','db file scattered read')
  5       ORDER BY time_waited DESC;

EVENT                      TOTAL_WAITS        SEC WAIT_CLASS
-------------------------- ----------- ---------- ----------
db file sequential read         145179        236 User I/O
db file scattered read           19741         62 User I/O

-- 해석: [1] 기준선 대비 두 이벤트가 모두 늘었다(누적값이라 절대치는 환경마다 다르다).
--   이 부하에서는 sequential read(PK 랜덤 단일 블록 읽기 20만 회)가 scattered read(전체 스캔 20회)보다
--   횟수가 훨씬 많다. 둘 다 User I/O 지만 성격이 다르다 —
--   sequential=단일 블록=인덱스 경유, scattered=다중 블록=대량 스캔.

--------------------------------------------------------------------------------
-- [3] (조회) 한 번의 요청이 몇 블록을 읽었나 — 이름이 반대인 근거를 확인.
--------------------------------------------------------------------------------
SYS@orcl> SELECT n.name, s.value blocks
  2       FROM  v$sysstat s JOIN v$statname n ON n.statistic#=s.statistic#
  3       WHERE n.name IN ('physical reads','physical reads direct',
  4                        'physical read total multi block requests',
  5                        'table scan blocks gotten');

NAME                                                                 BLOCKS
---------------------------------------------------------------- ----------
physical read total multi block requests                              55692
physical reads                                                      1012329
physical reads direct                                                408782
table scan blocks gotten                                          222006853

-- 해석: scattered read는 multiblock 요청 1회에 DB_FILE_MULTIBLOCK_READ_COUNT
--   만큼의 블록을 한꺼번에 읽어 버퍼의 흩어진 빈 자리에 담는다(그래서 scattered).
--   sequential read는 요청 1회에 블록 1개다. '순차'는 버퍼 배치를 뜻하지
--   디스크를 순차로 훑는다는 뜻이 아니다.

--------------------------------------------------------------------------------
-- [4] (이상 징후 → 원인 → 조치 → 재확인)
--     이상 징후: 담당자가 "db file scattered read가 보이니 I/O가 느리다,
--       디스크를 늘리자"고 한다.
--------------------------------------------------------------------------------
SYS@orcl> -- 원인 파악: 이벤트가 아니라 그 읽기를 유발한 SQL로 내려간다.
SYS@orcl> -- 어느 '세그먼트'가 이 I/O 의 진원지인가 — V$SEGMENT_STATISTICS 는 커서보다 오래 남아 안정적이다.
SYS@orcl> COLUMN object_name FORMAT A16

SYS@orcl> SELECT object_name, statistic_name, value
  2       FROM  v$segment_statistics
  3       WHERE owner='SQLT' AND statistic_name IN ('physical reads','logical reads')
  4         AND value > 0
  5       ORDER BY value DESC FETCH FIRST 4 ROWS ONLY;

OBJECT_NAME      STATISTIC_NAME                                                        VALUE
---------------- ---------------------------------------------------------------- ----------
CLAIM_DETAILS    logical reads                                                     162107760
PK_CLAIM_DETAILS logical reads                                                      62592688
MEDICAL_CLAIMS   logical reads                                                      57776656
PK_PATIENTS      logical reads                                                      32798608

-- 원인 확정: CLAIM_DETAILS 가 논리·물리 읽기 모두 1위다. 이 세그먼트를 반복 풀스캔하는 SQL
--   (WL_02 의 /*+ FULL(d) */ 집계)이 scattered read 를 냈다. 디스크가 느린 게 아니라
--   '풀스캔을 부르는 SQL'이 원인이다 — scattered read=다중 블록=풀스캔의 신호였다.
--   (커서 단위 V$SQL.disk_reads 는 SSD·캐시라 재조회 시 작아질 수 있어, 세그먼트 통계가 더 안정적이다.)
-- 조치: 조건절에 맞는 인덱스가 있는지/옵티마이저가 외면하는지 실행 계획을 본다.
--   (결론이 'SQL 한 문장 재작성'이면 SQL 튜닝 과정으로 인계한다.)
SYS@orcl> -- 재확인: 인덱스 접근이 되면 다음 부하에서 scattered↓ sequential↑ 로
SYS@orcl> --   대기의 성격이 바뀐다. 델타를 다시 측정해 확인한다.

--------------------------------------------------------------------------------
-- [정리]
--------------------------------------------------------------------------------
-- 1) sequential read=단일 블록=인덱스, scattered read=다중 블록=풀스캔.
-- 2) 어느 쪽이 큰지로 접근 방식(인덱스 vs 풀스캔)을 추론한다.
-- 3) 이벤트에서 멈추지 않고 V$SQL(disk_reads 순)로 원천 SQL을 지목한다.
-- 4) 'scattered가 보인다=디스크 교체'가 아니라 'SQL·인덱스 설계부터'.

SQLT@orcl> EXIT
