================================================================================
 16장 실습 04 — 자동 조정 이력 추적(V$SGA_RESIZE_OPS, V$MEMORY_RESIZE_OPS)
 목표: ASMM에서 SGA 풀들이 어떻게 자동으로 커지고 줄었는지 이력을 추적한다.
       GROW/SHRINK가 짝을 이루는 원리를 확인하고, 방식에 따라 어느 뷰가 채워지는지 본다.
 환경: non-CDB=orcl 19.3 (SYS AS SYSDBA로 수행), 조회 위주.
 주의: 조회만 수행한다. 이력은 인스턴스가 쌓아 둔 값이라 <환경값>이다.
================================================================================

$ sqlplus / as sysdba

SYS@orcl> SET LINESIZE 200
SYS@orcl> SET PAGESIZE 100

--------------------------------------------------------------------------------
-- [1] (조치 전 상태) 지금 각 풀이 어느 범위에서 움직여 왔는지 동적 구성을 본다.
--------------------------------------------------------------------------------
SYS@orcl> SELECT component, ROUND(current_size/1024/1024,1) cur_mb,
  2         ROUND(min_size/1024/1024,1) min_mb,
  3         ROUND(max_size/1024/1024,1) max_mb
  4       FROM v$sga_dynamic_components
  5       WHERE current_size>0 ORDER BY current_size DESC;

COMPONENT                CUR_MB  MIN_MB  MAX_MB
------------------------ ------- ------- -------
DEFAULT buffer cache      864     832     864
shared pool               416     416     416
Shared IO Pool             64      64      64
KEEP buffer cache          48      48      48
DEFAULT 4K buffer cache    48      48      48
streams pool               32      32      32
large pool                 16      16      48

-- 관찰: DEFAULT buffer cache는 832~864 사이를, large pool은 16~48 사이를 오갔다.
--   min≠max인 풀은 자동 조정을 겪었다는 뜻이다. shared pool은 min=cur=max로 고정.

--------------------------------------------------------------------------------
-- [2] (조회) 완료된 조정 이력을 시간순으로 본다.
--------------------------------------------------------------------------------
SYS@orcl> SELECT component, oper_type,
  2         ROUND(initial_size/1024/1024,1) from_mb,
  3         ROUND(final_size/1024/1024,1) to_mb,
  4         TO_CHAR(start_time,'MM-DD HH24:MI') t
  5       FROM (SELECT * FROM v$sga_resize_ops ORDER BY start_time DESC)
  6       WHERE ROWNUM<=10;

COMPONENT             OPER_TYPE FROM_MB TO_MB  T
--------------------- --------- ------- -----  -----------
large pool            GROW       16      32    08-25 17:28
DEFAULT buffer cache  GROW      848     864    08-25 17:28
DEFAULT buffer cache  SHRINK    864     848    08-25 17:28
large pool            SHRINK     32      16    08-25 17:28
large pool            SHRINK     32      16    08-25 14:35
DEFAULT buffer cache  GROW      848     864    08-25 14:35
large pool            GROW       16      32    08-25 14:35
DEFAULT buffer cache  SHRINK    864     848    08-25 14:35
large pool            SHRINK     48      16    08-25 14:34
DEFAULT buffer cache  GROW      832     864    08-25 14:34

--------------------------------------------------------------------------------
-- [3] (해석) GROW/SHRINK가 짝을 이루는 원리.
--------------------------------------------------------------------------------
-- - 17:28: large pool GROW(16→32)와 DEFAULT buffer cache SHRINK(864→848)가 함께 났다.
--     이후 large pool SHRINK(32→16)와 buffer cache GROW(848→864)로 되돌아왔다.
-- - 원리: SGA 총량(SGA_TARGET=1504M)은 고정이다. 한 풀이 16MB 커지려면 다른 풀이
--     16MB 내놓아야 한다. 그래서 조정은 반대 방향으로 짝을 이룬다.
-- - 모든 증감이 16의 배수(16→32, 848→864)인 것은 그래뉼이 16MB이기 때문이다.
-- - 이것이 '전체는 고정, 내부는 자동 재분배'라는 ASMM의 본질이다.
-- - 이 이력은 정상이다: 짧게 왕복하고 되돌아왔다(thrashing 아님). large pool을 쓰는
--     작업(병렬·RMAN 등)이 잠깐 메모리를 요구했다 반납한 정황으로 읽힌다.

--------------------------------------------------------------------------------
-- [4] (이상 → 원인 → 조치 → 재확인) V$MEMORY_RESIZE_OPS가 비어 있어 당황한다.
--------------------------------------------------------------------------------
SYS@orcl> SELECT component, oper_type, final_size
  2       FROM v$memory_resize_ops
  3       WHERE final_size IS NOT NULL AND ROWNUM<=5;

no rows selected

-- * 이상 징후: SGA_RESIZE_OPS에는 이력이 많은데 MEMORY_RESIZE_OPS는 비었다.
--     "뷰가 고장 났나?"라는 의심이 들 수 있다.
-- * 원인: V$MEMORY_RESIZE_OPS는 SGA와 PGA를 아우르는 '통합' 조정 이력이며, SGA↔PGA
--     통합 재분배는 AMM(MEMORY_TARGET>0)에서 일어난다. 이 인스턴스는 ASMM
--     (MEMORY_TARGET=0)이라 통합 조정 자체가 없어 결과가 빈약한 것이다. 뷰 결함이 아니다.
-- * 조치: 방식에 맞는 뷰를 고른다. ASMM에서 SGA 조정 이력은 V$SGA_RESIZE_OPS로 본다
--     (이미 [2]에서 확인). 통합 이력을 보려면 AMM 환경(실습 02)에서 조회한다.

SYS@orcl> SELECT display_value FROM v$parameter WHERE name='memory_target';
DISPLAY_VALUE
--------------
0
-- * 재확인: memory_target=0이므로 통합 조정 이력이 없는 것이 정상임을 확정했다.
--     ASMM에서는 V$SGA_RESIZE_OPS가 올바른 뷰다.

--------------------------------------------------------------------------------
-- [정리]
--------------------------------------------------------------------------------
-- 1) V$SGA_DYNAMIC_COMPONENTS의 min≠max가 자동 조정을 겪은 흔적이다.
-- 2) V$SGA_RESIZE_OPS의 GROW/SHRINK는 짝을 이룬다(총량 고정 → 한쪽이 커지면 다른쪽 축소).
-- 3) 모든 증감은 그래뉼(16MB) 단위. 오라클은 최근 800건을 보관한다.
-- 4) 뷰 선택이 핵심: ASMM=V$SGA_RESIZE_OPS, AMM=V$MEMORY_RESIZE_OPS(SGA+PGA 통합).
-- ※ 이력 값·시각은 환경 의존 <환경값>이다. 핵심은 '짝 원리'와 '뷰 선택'이다.

SYS@orcl> EXIT
