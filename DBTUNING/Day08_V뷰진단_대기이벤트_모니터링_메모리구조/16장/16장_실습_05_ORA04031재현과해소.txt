 16장 실습 05 — 공유 풀 압박과 ORA-04031: 원인 영역 식별·조정 (실측)
 목표: 공유 풀을 실제로 좁혀(재기동) 라이브러리 캐시를 압박하고, 그 압박이
       어떻게 나타나는지(예약 풀 할당 실패·커서 축출/재적재 = thrashing)를 관찰한다.
       ORA-04031 메시지의 원인 영역 식별법을 정리하고, 근본 조치(바인드 변수)로 해소한다.
 환경: non-CDB=orcl 19.3, ASMM. SYS 로 파라미터·재기동, SQLT 로 부하.
 *** 경고: 개인 격리 환경 전용 ***
   공유 풀을 좁히고 부하를 퍼붓는다. 인스턴스 성능이 크게 떨어지고 다른 세션의 파싱까지
   영향받는다. 다른 세션(RMAN 포함)이 없는 개인 DB에서만, 반드시 [원복]까지 수행한다.
 ⚠ 실측 요지(중요): 이 실습은 "리터럴을 퍼부으면 곧 ORA-04031 이 뜬다"가 아니다. 19c 공유
   풀은 작은 커서를 LRU 로 축출/재적재하며 상당히 버틴다 — 그래서 리터럴 폭주는 대개 '하드
   파싱 폭증·커서 재적재·예약 풀 할당 실패(request_failures)' 로 나타나고, 완전히 raise 되는
   ORA-04031 은 '더 크거나 고정(pinned)된 연속 할당'에서 난다. 아래는 그 실측을 그대로 담는다.
================================================================================

-- (별도 터미널) SQLT 에서 리터럴 폭증(cursor_sharing=EXACT 로 리터럴 그대로 파싱):
$ sqlplus sqlt/sqlt@orcl
SQLT@orcl> ALTER SESSION SET cursor_sharing=EXACT;
Session altered.
SQLT@orcl> DECLARE n NUMBER;
  2  BEGIN
  3    FOR i IN 1..200000 LOOP
  4      EXECUTE IMMEDIATE
  5        'SELECT /*WL01_LIT*/ COUNT(*) FROM medical_claims c1, medical_claims c2 '||
  6        q'[WHERE c1.claim_id='X]'||i||q'[' AND c2.claim_id=c1.claim_id]' INTO n;
  7    END LOOP;
  8  END;
  9  /

PL/SQL procedure successfully completed.

-- * 실측(핵심): 좁은 224MB 풀에 리터럴 수십만을 퍼부었는데도 블록은 '성공'으로 끝났다.
--   19c 라이브러리 캐시가 오래된 커서를 LRU 로 축출·재적재하며 버틴 것이다(하드 파싱 폭증).
--   즉 리터럴 폭주의 1차 증상은 ORA-04031 이 아니라 '커서 재사용 실패(재적재)와 예약 풀
--   할당 실패'다. 이걸 [5]에서 지표로 확인한다.

--------------------------------------------------------------------------------
-- [5] (원인 영역 식별) 압박의 흔적 — 예약 풀 실패·free·커서 수.
--------------------------------------------------------------------------------
SYS@orcl> SELECT ROUND(SUM(bytes)/1024/1024,2) sp_free_mb
  2       FROM v$sgastat WHERE pool='shared pool' AND name='free memory';

SP_FREE_MB
----------
     <환경값>   -- 여유가 거의 바닥(예: 16MB 안팎)

SYS@orcl> SELECT request_failures, last_failure_size
  2       FROM v$shared_pool_reserved;

REQUEST_FAILURES LAST_FAILURE_SIZE
---------------- -----------------
        <환경값>              4096   -- 0에서 증가: 예약 풀이 연속 청크(4096B)를 못 얻은 횟수

SYS@orcl> SELECT COUNT(*) lit_cursors
  2       FROM v$sqlarea WHERE sql_text LIKE '%WL01_LIT%';

LIT_CURSORS
-----------
        <환경값>   -- 퍼부은 수만 개 중 소수만 생존(대부분 축출됨) → 재적재가 잦았다는 증거

-- * 감별: request_failures 가 0에서 증가했다 — 예약 풀이 4096바이트 연속 청크를 못 얻어
--   실패한 것으로, ORA-04031 의 '작은 형태'다. 본 풀은 축출로 흡수해 raise 까지 가지 않았다.
--   free 는 바닥이고 리터럴 커서는 대부분 축출됐다 → '공간 부족 + 단편화 + 하드 파싱' 이 겹친
--   전형적 압박 상태다. 원인은 '리터럴(바인드 미사용)' 이고, 여기에 좁힌 풀이 더해진 것이다.
--
-- * (참고) ORA-04031 이 완전히 raise 되면 이런 형태다 — 원인 영역이 괄호에 박혀 나온다:
--     ORA-04031: unable to allocate 4160 bytes of shared memory
--       ("shared pool","SELECT ... WHERE ...","SQLA","kkscsAddChildNode")
--       (실패영역)      (방아쇠 SQL=리터럴)     (하위영역) (할당 요청 함수)
--   raise 는 '더 크거나 고정된 연속 할당'(예: 대형 SQL 텍스트·패키지·고정 메모리)에서 난다.
--   할당 바이트·문제 SQL·함수명은 환경마다 다른 <환경값>이다.

--------------------------------------------------------------------------------
-- [6] (조치) 근본은 바인드 변수 — 같은 부하를 바인드로 돌리면 커서가 1개로 수렴한다.
--------------------------------------------------------------------------------
SYS@orcl> -- (임시책) 연속 공간을 즉시 확보하려면 FLUSH — 단 캐시를 날려 하드 파싱이 급증한다.
SYS@orcl> ALTER SYSTEM FLUSH SHARED_POOL;
System altered.

-- (근본책) 애플리케이션을 바인드 변수로 고친다. 리터럴 대신 :b 를 쓴다.
SQLT@orcl> DECLARE n NUMBER;
  2  BEGIN
  3    FOR i IN 1..200000 LOOP
  4      EXECUTE IMMEDIATE
  5        'SELECT /*WL01_BIND*/ COUNT(*) FROM medical_claims WHERE claim_id=:1'
  6        INTO n USING TO_CHAR(i);
  7    END LOOP;
  8  END;
  9  /

PL/SQL procedure successfully completed.

SQLT@orcl> SELECT COUNT(*) bind_cursors
  2       FROM v$sqlarea WHERE sql_text LIKE '%WL01_BIND%';

BIND_CURSORS
-----------
          1

-- * 실측: 바인드 모드는 리터럴 20만 건이 커서 1개(claim_id=:1)를 공유한다 — 좁은 풀에서도
--   문제없이 완료됐다. 하드 파싱·재적재·예약 풀 실패가 사라진다. 공유 풀 압박의 근본 해법이다.

-- [정리]
--------------------------------------------------------------------------------
-- 1) SHARED_POOL_SIZE 는 하한이라 큰 풀을 못 줄인다. 실행 중 SGA 축소도 ORA-00827 로 거부 —
--    공유 풀을 진짜로 좁히려면 SGA 상한/목표를 spfile 에 낮추고 재기동한다.
-- 2) 좁힌 풀에 리터럴을 퍼부으면 1차로 '하드 파싱 폭증·커서 재적재·예약 풀 할당 실패
--    (request_failures)'로 나타난다. 19c 는 축출로 버텨 ORA-04031 raise 까지는 잘 안 간다.
-- 3) 완전한 ORA-04031 은 '더 크거나 고정된 연속 할당'에서 난다. 메시지 괄호 4조각으로
--    실패 영역·방아쇠 SQL·하위영역·요청 함수를 읽어 원인을 지목한다.
-- 4) 임시책은 FLUSH(하드 파싱 급증), 근본책은 바인드 변수화(커서 1개 공유). 크기 확대는 최후.
-- 5) 재기동·오류 유발은 개인 격리 환경 전용. pfile 백업으로만 확실히 원복된다.
