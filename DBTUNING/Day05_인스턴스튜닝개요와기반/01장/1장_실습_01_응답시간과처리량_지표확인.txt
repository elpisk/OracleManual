================================================================================
 1장 실습 01 — 응답시간과 처리량 지표 확인
 목표: 응답시간(DB Time·시간 모델)과 처리량(V$SYSMETRIC)을 각각 조회해
       무엇이 다른지 확인한다. '무부하 시 지표가 0'을 성능 우수로 오판하는
       이상 징후를 재현하고, 그 원인(부하 부재)과 올바른 판정법을 익힌다.
 환경: non-CDB=orcl 19.3 (SYS AS SYSDBA로 수행)
 주의: 개인 실습 환경 전용. 이 실습은 읽기 전용 조회만 수행한다.
================================================================================

$ sqlplus / as sysdba

SYS@orcl> SET LINESIZE 200
SYS@orcl> SET PAGESIZE 100

--------------------------------------------------------------------------------
-- [1] (조치 전 상태) 응답시간의 뿌리 = DB Time 구성을 먼저 본다.
--     DB Time = DB CPU + 대기. 시간 모델로 그 구성을 확인한다.
--------------------------------------------------------------------------------
SYS@orcl> SELECT stat_name, value
  2       FROM  v$sys_time_model
  3       WHERE stat_name IN ('DB time','DB CPU',
  4              'sql execute elapsed time','parse time elapsed')
  5       ORDER BY value DESC;

STAT_NAME                          VALUE
------------------------------ ----------
DB time                          49551722
sql execute elapsed time         12277777
DB CPU                            8662345
parse time elapsed                1935695

-- 해석: 이 값들은 인스턴스 기동 이후의 누적값(마이크로초)이다.
--   DB CPU / DB time = 8,662,345 / 49,551,722 ≈ 0.175 → 약 17.5%가 CPU,
--   나머지 약 82.5%가 대기 및 기타다. 'DB Time = DB CPU + 대기'가 확인된다.
--   parse time(1,935,695) < sql execute(12,277,777) → 파싱보다 실행에 시간을
--   더 썼다. 만약 반대였다면 하드 파싱 폭증을 의심했을 것이다(2·18장).

--------------------------------------------------------------------------------
-- [2] (조회) 처리량·응답시간 대표 메트릭을 V$SYSMETRIC(최근 60초)로 본다.
--------------------------------------------------------------------------------
SYS@orcl> SELECT metric_name, ROUND(value,2) value, metric_unit
  2       FROM  v$sysmetric
  3       WHERE metric_name IN ('Database Time Per Sec','Average Active Sessions',
  4              'User Transaction Per Sec','Executions Per Sec',
  5              'Response Time Per Txn','SQL Service Response Time')
  6         AND intsize_csec BETWEEN 5900 AND 6100
  7       ORDER BY metric_name;

METRIC_NAME                    VALUE METRIC_UNIT
------------------------------ ----- -------------------------
Average Active Sessions            0 Active Sessions
Database Time Per Sec              0 CentiSeconds Per Second
Executions Per Sec              0.36 Executes Per Second
Response Time Per Txn              0 CentiSeconds Per Txn
SQL Service Response Time          0 CentiSeconds Per Call
User Transaction Per Sec           0 Transactions Per Second

--------------------------------------------------------------------------------
-- [3] (이상 징후 → 원인 → 조치)
--     이상 징후: 응답시간(Response Time Per Txn)·처리량(User Transaction Per Sec)이
--       모두 0으로 나온다. 신입 DBA가 "성능이 완벽하다"고 오판할 수 있다.
--------------------------------------------------------------------------------
SYS@orcl> -- 원인 파악: 지표가 0인 것이 성능이 좋아서인지, 잴 대상이 없어서인지 가른다.
SYS@orcl> -- Average Active Sessions(평균 동시 활성 세션 수)를 확인한다.
SYS@orcl> SELECT ROUND(value,3) aas
  2       FROM  v$sysmetric
  3       WHERE metric_name='Average Active Sessions'
  4         AND intsize_csec BETWEEN 5900 AND 6100;

       AAS
----------
         0

-- 원인 확정: AAS가 0 → 캡처 순간 활성 세션이 사실상 없었다.
--   즉 지표가 0인 것은 '측정할 부하가 없었다'는 뜻이지 성능이 좋다는 뜻이 아니다.
--   (반면 [1]의 시간 모델 누적값은 기동 이후 누적이라 0이 아니다 — 대조 포인트)

SYS@orcl> -- 조치: 부하가 있는 시간대에 다시 측정해야 한다. 이 과정은 5장부터
SYS@orcl> --   공용 부하 스크립트 WL_06_mixed.sql 등으로 부하를 유발한 뒤 측정한다.
SYS@orcl> --   (여기서는 조치 방향만 확인한다. 실제 부하 유발은 5장 실습에서 수행)

--------------------------------------------------------------------------------
-- [4] (조치 후 관점) 응답시간과 처리량은 '다른 것'임을 정리한다.
--------------------------------------------------------------------------------
-- * 응답시간: 한 요청이 끝날 때까지의 시간(= 서비스 시간 + 대기). 사용자 체감.
--   → 목표는 평균이 아니라 95/99 백분위수로 잡는다.
-- * 처리량: 단위 시간당 완료 작업량(TPS·초당 실행 수). 배치·DW의 핵심 지표.
-- * 둘은 상충할 수 있어 워크로드별 우선순위를 정한다(OLTP=응답시간, 배치=처리량).

--------------------------------------------------------------------------------
-- [정리]
--------------------------------------------------------------------------------
-- 1) DB Time은 CPU와 대기의 합이며, 실측에서 CPU 약 17.5% / 대기 약 82.5%였다.
-- 2) V$SYSMETRIC의 0은 오류가 아니라 무부하의 정상 결과다(AAS로 확인).
-- 3) 성능 지표는 부하가 있어야 나타난다 → 조회만으로는 성능을 잴 수 없다.
-- 4) 이후 모든 판단은 이 DB Time 축에서 출발한다(5장에서 심화).
-- ※ 참고: 시간 모델·V$SYSMETRIC 조회 자체는 관리 팩 라이선스가 필요 없다.

SYS@orcl> EXIT
