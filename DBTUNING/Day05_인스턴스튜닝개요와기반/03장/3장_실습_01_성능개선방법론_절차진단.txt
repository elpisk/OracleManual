================================================================================
 3장 실습 01 — 오라클 성능 개선 방법론 절차대로 현재 인스턴스 1회 진단
 목표: 방법론의 초기 표준 점검과 개념 모델 세 갈래(단일 사용자 / CPU 소진 /
       CPU 여유+대기)를 따라 현재 인스턴스를 1회 진단하고, DB Time 을 CPU 와
       대기로 갈라 어디를 파고들지 결정하는 절차를 익힌다.
 환경: non-CDB=orcl 19.3. 진단은 SYS@orcl>.
 주의: 개인 실습 환경 전용. 조회 위주이며 파라미터는 확인만 한다.
       환경마다 달라지는 수치는 <환경값>으로 두고 '판정 기준'을 서술한다.
================================================================================

$ sqlplus / as sysdba

SYS@orcl> SET LINESIZE 200
SYS@orcl> SET PAGESIZE 100

--------------------------------------------------------------------------------
-- [1] (초기 점검) 자동 통계·진단이 동작하는 상태인가 — STATISTICS_LEVEL.
--------------------------------------------------------------------------------
SYS@orcl> SELECT name, value FROM v$parameter
  2       WHERE name IN ('statistics_level','control_management_pack_access');

NAME                             VALUE
-------------------------------- -----------------
statistics_level                 TYPICAL
control_management_pack_access    DIAGNOSTIC+TUNING

-- 해석: STATISTICS_LEVEL 이 TYPICAL 이므로 시간 모델·대기 통계가 수집된다.
--   BASIC 이면 AWR 스냅샷이 멎어 상위 진단이 멈춘다(1장). 진단의 전제 확인.

--------------------------------------------------------------------------------
-- [2] (조치 전 상태 · 개념모델 2·3갈래) DB Time 을 CPU 와 대기로 가른다.
--     V$SYS_TIME_MODEL 은 기동 이후 누적값(마이크로초)이다.
--------------------------------------------------------------------------------
SYS@orcl> SELECT stat_name, value FROM v$sys_time_model
  2       WHERE stat_name IN ('DB time','DB CPU')
  3       ORDER BY value DESC;

STAT_NAME              VALUE
--------------- ------------
DB time             <환경값>
DB CPU              <환경값>

-- 판정 기준: CPU% = DB CPU / DB time.
--   CPU% 가 높으면(예: 코어 수 대비 과다) 개념모델 2갈래 → 고부하 SQL·자원.
--   CPU% 가 낮은데 시스템이 느리면 3갈래 → 직렬화(대기). 대기 클래스를 본다.
--   (누적값이므로 '지금'을 보려면 [3]처럼 구간 델타나 순간 대기를 함께 본다.)

--------------------------------------------------------------------------------
-- [3] (조치 전 상태 · 3갈래 심화) 대기 클래스별 비중 — 어디가 직렬화인가.
--------------------------------------------------------------------------------
SYS@orcl> SELECT wait_class, ROUND(time_waited/100,1) sec
  2       FROM  v$system_wait_class
  3       WHERE wait_class <> 'Idle'
  4       ORDER BY time_waited DESC FETCH FIRST 5 ROWS ONLY;

WAIT_CLASS               SEC
-------------------- -------
<환경값>             <환경값>

-- 판정 기준: Idle 을 제외한 상위 대기 클래스가 병목의 방향을 가리킨다.
--   Application → 잠금 경합(3장 실습 04), Concurrency → 라이브러리 캐시,
--   User I/O → I/O(14·17·20장). 상위 하나만 보고 결론 내지 않고 DB Time 비중과
--   함께 본다(1장 원칙).

--------------------------------------------------------------------------------
-- [4] (조치 전 상태 · 흔한 실수 대조) 상위 부하 SQL 을 본다.
--------------------------------------------------------------------------------
SYS@orcl> SELECT sql_id, executions execs, buffer_gets,
  2         ROUND(elapsed_time/1e6,2) elapsed_sec,
  3         SUBSTR(sql_text,1,30) sql_text
  4       FROM  v$sql WHERE parsing_schema_name='SQLT'
  5       ORDER BY buffer_gets DESC FETCH FIRST 5 ROWS ONLY;

SQL_ID        EXECS BUFFER_GETS ELAPSED_SEC SQL_TEXT
------------- ----- ----------- ----------- ------------------------------
<환경값>      ...       ...         ...      select ...

-- 해석: 논리 읽기 상위 SQL 이 '나쁜 SQL / 긴 전체 스캔'(열 가지 실수 3·8번)에
--   해당하는지 대조한다. 대상이 정해지면 '실행당 논리 읽기'를 목표 지표로 잡는다.

--------------------------------------------------------------------------------
-- [5] (이상 징후 → 원인 → 조치 → 재확인) 누적값을 그대로 읽은 오판.
--     이상 징후: "DB CPU 가 수천만이니 CPU 병목"이라고 단정.
--------------------------------------------------------------------------------
SYS@orcl> -- 원인: V$SYS_TIME_MODEL 은 기동 이후 누적이라 절대값이 크게 마련이다.
SYS@orcl> --   절대값만 보면 항상 'CPU 가 크다'로 보인다(오판).
SYS@orcl> -- 조치: 관심 구간의 시작·끝에서 두 번 떠 델타로 비교한다.
SYS@orcl> COLUMN db_time_us NEW_VALUE t1
SYS@orcl> SELECT value db_time_us FROM v$sys_time_model WHERE stat_name='DB time';
  DB_TIME_US
-----------
   <환경값>
SYS@orcl> -- (관심 구간 동안 대기)  … 이후 다시 조회 …
SYS@orcl> SELECT value - &t1 AS db_time_delta_us FROM v$sys_time_model
  2       WHERE stat_name='DB time';
DB_TIME_DELTA_US
----------------
       <환경값>
-- 재확인: 델타로 본 DB Time 증가분이 '이 구간'의 실제 부하다. 절대 누적값이
--   아니라 델타로 판정해야 한다. CPU% 도 같은 두 시점의 델타로 계산한다.

--------------------------------------------------------------------------------
-- [정리]
--------------------------------------------------------------------------------
-- 1) 초기 점검: STATISTICS_LEVEL=TYPICAL → 진단 통계가 수집되는 상태 확인.
-- 2) 개념모델: DB Time 을 CPU 와 대기로 갈라 방향을 정한다(CPU% 로 2·3갈래).
-- 3) 3갈래(대기)면 대기 클래스 상위로 좁힌다. Application → 잠금 경합(실습 04).
-- 4) 상위 부하 SQL 을 열 가지 실수와 대조해 대상을 고른다.
-- 5) 누적값은 델타로 판정한다. 절대 누적값을 그대로 읽으면 오판한다.
-- ※ 인스턴스 튜닝 효과는 <10%, 큰 효과는 애플리케이션 비효율 제거에서 나온다.
SYS@orcl> EXIT
