       메모리 위 대량 스캔인지, 리터럴 하드파싱인지 판정한다. 절대값이 아니라
       항목 간 비율로 읽는 훈련. '무부하로 착각' 이상 상황을 원인·조치까지 다룬다.
 환경: non-CDB=orcl 19.3 (SYS AS SYSDBA)
 부하: WL_06_mixed.sql (7세션 종합 부하). 실측 보고서 awrrpt_1_479_480.txt 사용.
 라이선스: 🔒 Diagnostics Pack. 미보유 시 V$SYSSTAT/V$SYS_TIME_MODEL 델타로 대체(하단).

SYS@orcl> SET LINESIZE 200

-- [2] (해석 1) DB Time vs DB CPU — 이 구간은 무엇에 시간을 썼나?
--------------------------------------------------------------------------------
-- 머리말: Elapsed 1.22분, DB Time 0.81분 → 평균 활성 세션(AAS) ≈ 0.66. 7세션이 돌았는데
--   0.66 인 것은 세션들이 대부분의 시간을 대기가 아니라 '짧은 커밋·파싱을 반복'하며 보냈고
--   그 사이사이 유휴가 섞였기 때문이다(WL_06 은 주기 사이 5초를 쉰다).
-- DB Time(s) 0.7, DB CPU(s) 0.4 → 초당 DB Time 의 약 57%가 CPU 이고 나머지 약 43%는 대기다.
--   즉 순수 CPU 바운드가 아니다. 무엇을 기다렸는지는 실습 03(Top 10)에서 본다.

--------------------------------------------------------------------------------
-- [3] (해석 2) 논리 읽기 vs 물리 읽기 — 메모리인가 디스크인가?
--------------------------------------------------------------------------------
-- Logical read 40,924/s vs Physical read 2.6/s.
--   물리 읽기가 사실상 없고 논리 읽기만 많다 → 데이터는 이미 버퍼 캐시에 있고
--   그 위를 반복해서 읽고 있다. (뒤 Instance Efficiency 의 Buffer Hit 99.99% 와 일치.
--   실습 03·06에서 교차 확인)
-- Per Transaction 31.0 → 트랜잭션 하나가 31블록을 읽는 가벼운 OLTP 형 업무이고,
--   초당 트랜잭션 1,318건이 모여 논리 읽기 4만/s 를 만든다.

--------------------------------------------------------------------------------
-- [4] (해석 3) 파싱 — 하드 파싱 비율을 계산한다.
--------------------------------------------------------------------------------
SYS@orcl> SELECT ROUND(355.5/1381.1*100,1) AS hard_parse_pct FROM dual;

HARD_PARSE_PCT
--------------
          25.7

-- 해석: 전체 파싱 1,381/s 중 하드 파싱이 355.5/s = 약 25.7%(Instance Efficiency 의
--   Soft Parse % 74.26 과 같은 말이다). 정상 애플리케이션이라면 바인드 변수로 하드 파싱은
--   거의 0 이어야 한다. 초당 355회의 하드 파싱은 리터럴 SQL 이 쏟아지고 있다는 강력한
--   신호다(→ 실습 03 의 대기 kksfbc child completion·cursor: pin S wait on X 로 확증).

--------------------------------------------------------------------------------
-- [5] (조회) 보고서 없이 V$로 같은 논리 읽기 순간값을 참고로 확인한다.
--     (부하가 끝난 뒤라 값은 환경/시점에 따라 다르다 → <환경값>)
--------------------------------------------------------------------------------
SYS@orcl> COLUMN metric_name FORMAT A30

SYS@orcl> COLUMN metric_unit FORMAT A24

SYS@orcl> SELECT metric_name, ROUND(value) val, metric_unit
  2       FROM  v$sysmetric
  3       WHERE metric_name IN ('Logical Reads Per Sec','Hard Parse Count Per Sec')
  4         AND intsize_csec BETWEEN 5900 AND 6100
  5       ORDER BY metric_name;

METRIC_NAME                           VAL METRIC_UNIT
------------------------------ ---------- ------------------------
Hard Parse Count Per Sec                0 Parses Per Second
Logical Reads Per Sec                  32 Reads Per Second

-- 해석: V$SYSMETRIC 은 최근 60초 순간값이라 보고서 구간(479~480)과 시점이
--   다르면 값이 다르다(부하가 끝난 지금은 0 근처). 보고서의 델타값(40,924/s, 355/s)이
--   그 구간의 확정 실측이고, V$ 는 지금 이 순간을 보는 창이다. 두 창을 혼동하지 않는다.

--------------------------------------------------------------------------------
-- [6] (이상 징후 → 원인 → 조치 → 재확인)
--     이상 징후: 다른 신입이 "물리 읽기 2.6/s 로 낮으니 I/O 성능이 완벽,
--       튜닝 필요 없음"이라 판정했다.
--------------------------------------------------------------------------------
-- 원인 파악: 물리 읽기만 보고 논리 읽기(40,924/s)와 하드 파싱(355/s)을 놓친 오판이다.
--   물리 읽기가 낮은 것은 데이터가 캐시에 있어서일 뿐, 그 위에서 SQL 을 초당 5,900번
--   실행하고 355번 하드 파싱하는 것 자체가 CPU 와 공유 풀을 태우는 문제다.
SYS@orcl> SELECT ROUND(40924.4/2.6) AS logical_to_physical_ratio FROM dual;

LOGICAL_TO_PHYSICAL_RATIO
-------------------------
                    15740

-- 원인 확정: 논리:물리 = 약 15,740:1. 디스크는 한가하지만 메모리 위에서
--   블록을 1만 5천 배 더 훑고 있다. I/O 가 아니라 실행 횟수·파싱이 병목의 씨앗이다.
-- 조치: 실행이 많고 하드 파싱을 부르는 상위 SQL 을 찾아 개선한다(실습 04에서 지목).
--   I/O 서브시스템이나 캐시 크기를 건드리는 것이 아니다.
-- 재확인: DB CPU 57% + 파싱 계열 대기 ≈ 40% 이므로 병목은 CPU·공유 풀 쪽임을 다시 확인
--   → I/O 튜닝은 이 구간의 해법이 아니다. 판정 번복.

--------------------------------------------------------------------------------
-- [대안 경로] 🔒 미보유 — V$로 Load Profile을 델타로 재구성한다.
--------------------------------------------------------------------------------
-- 부하 전/후로 아래를 두 번 찍어 (후-전)/경과초로 나누면 Per Second가 나온다.
--   SELECT name, value FROM v$sysstat
--    WHERE name IN ('session logical reads','parse count (hard)',
--                   'parse count (total)','physical reads','redo size',
--                   'user calls','user commits');
-- DB Time/CPU는 V$SYS_TIME_MODEL('DB time','DB CPU')의 델타로 구한다(5장 실습 05·06).
-- 이렇게 구한 값을 보고서 Load Profile과 동일한 방식으로 판독한다.

--------------------------------------------------------------------------------
-- [정리]
--------------------------------------------------------------------------------
-- 1) Load Profile은 절대값이 아니라 '항목 간 비율'로 읽는다.
-- 2) DB CPU 57% / 대기 43% → CPU 만의 문제가 아니다. 논리 4만 : 물리 2.6 → 메모리 위 반복 실행.
-- 3) 하드 파싱 25.7%(355/s) → 리터럴 SQL 신호(실습 03에서 대기로 확증).
-- 4) 물리 읽기만 보고 'I/O 완벽'이라 하면 오판 → 논리 읽기·DB CPU·파싱과 함께 본다.
-- 5) 라이선스 없으면 V$SYSSTAT/V$SYS_TIME_MODEL 델타로 동일 판독 가능.

SYS@orcl> EXIT
