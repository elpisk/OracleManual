 과정      : Oracle Database 19c Backup & Recovery

--------------------------------------------------------------------------------
[1] 시나리오 개요
--------------------------------------------------------------------------------
-- 백업 범위를 좁혀 테이블스페이스와 데이터파일 단위로 백업한다.
-- SKIP 옵션의 동작을 확인한다.
-- NOT BACKED UP SINCE TIME 으로 중단된 백업을 이어받는다.
-- 범위를 나눌 때 파일이 누락되는 상황을 재현하고 발견한다.
-- 작업 유형 : 백업 수행(장애 복구 아님)

SYS@orcl> DROP TABLESPACE tbs_new INCLUDING CONTENTS AND DATAFILES;

Tablespace dropped.

SYS@orcl> DROP TABLESPACE tbs_ro INCLUDING CONTENTS AND DATAFILES;

Tablespace dropped.

-- 실무 포인트
-- 1) 백업 범위는 DATABASE, TABLESPACE, DATAFILE 세 단위로 지정한다.
--    데이터파일은 번호와 경로 어느 쪽으로도 지정할 수 있다.
--    RMAN 프롬프트에서 SQL 문을 바로 실행할 수 있고 카탈로그 접속이면 자동 resync 된다.
--
-- 2) SKIP READONLY 는 읽기 전용 파일을 건너뛴다.
--    내용이 바뀌지 않으므로 한 번만 백업하면 되기 때문이다.
--    다만 읽기 쓰기로 되돌린 뒤에는 반드시 다시 백업해야 한다.
--    SKIP OFFLINE 은 RMAN-06060 경고를 남긴다. OFFLINE 파일은 내용이 바뀔 수 있어서다.
--
-- 3) NOT BACKED UP SINCE TIME 은 중단된 백업을 이어받을 때 쓴다.
--    이미 백업된 파일을 건너뛰므로 처음부터 다시 하지 않아도 된다.
--    야간 백업이 시간을 넘겨 끊긴 다음 날 아침에 유용하다.
--
-- 4) 범위를 나눠 백업하면 파일 누락 위험이 생긴다.
--    새 테이블스페이스가 스크립트에 추가되지 않는 것이 대표적이다.
--    REPORT SCHEMA 목록과 백업 범위를 정기적으로 대조한다.
--
-- 5) REPORT NEED BACKUP 을 매일 확인하면 누락을 조기에 발견한다.
--    백업이 한 번도 없는 파일은 정책과 무관하게 여기에 오른다.
--    RMAN-20202 는 이름 오타다. 새 테이블스페이스는 BACKUP 시작 때 자동 resync 된다.
--
-- 6) 근본 대책은 BACKUP DATABASE 로 범위를 지정하는 것이다.
--    구조가 바뀌어도 자동으로 포함되므로 누락이 원천적으로 사라진다.
