 실습 14-2 : 테이블스페이스·데이터파일 단위 백업
 과정      : Oracle Database 19c Backup & Recovery
 환경      : Oracle 19.3.0 / Oracle Linux 7 / non-CDB ORCL / ARCHIVELOG
 소요 시간 : 약 25분
================================================================================

--------------------------------------------------------------------------------
[1] 시나리오 개요
--------------------------------------------------------------------------------
-- 백업 범위를 좁혀 테이블스페이스와 데이터파일 단위로 백업한다.
-- SKIP 옵션의 동작을 확인한다.
-- NOT BACKED UP SINCE TIME 으로 중단된 백업을 이어받는다.
-- 범위를 나눌 때 파일이 누락되는 상황을 재현하고 발견한다.
-- 작업 유형 : 백업 수행(장애 복구 아님)

--------------------------------------------------------------------------------

--------------------------------------------------------------------------------
[7] 오류 발생 → 원인 파악 → 수정
--------------------------------------------------------------------------------
-- 요일별 순환 백업을 구성했다고 가정하고 새 테이블스페이스를 추가한다.

RMAN> SQL 'CREATE TABLESPACE tbs_new DATAFILE
  2>   ''/u02/oradata/ORCL/tbs_new01.dbf'' SIZE 10M';

sql statement: CREATE TABLESPACE tbs_new ...

-- 기존 순환 스크립트는 users, tbs13, tbs_ro 만 백업한다.

RMAN> BACKUP TABLESPACE users, tbs13, tbs_ro TAG 'ROTATION';

Starting backup at 14-MAY-25
Finished backup at 14-MAY-25

-- 며칠이 지난 상황을 가정하고 정책 충족 여부를 확인한다.

RMAN> REPORT NEED BACKUP DAYS 0;

Report of files that have been backed up less than 0 days
File Days  Name
---- ----- -----------------------------------
10   0     /u02/oradata/ORCL/tbs_new01.dbf

-- << 원인 파악 >>
-- 새로 만든 tbs_new 가 백업 범위에 들어 있지 않다.
-- 테이블스페이스 단위로 나눠 백업하면 이런 누락이 생긴다.
-- 구조 변경 시 백업 스크립트를 함께 갱신하지 않으면 발견이 늦어진다.

RMAN> REPORT SCHEMA;

-- 스크립트의 테이블스페이스 이름을 고치다 오타를 낸 경우도 흔하다.

RMAN> BACKUP TABLESPACE tbs_nwe TAG 'ROTATION';

-- << 원인 파악 >>
-- RMAN-20202는 그 이름의 테이블스페이스가 리포지터리에 없다는 뜻이다.
-- 오타이거나 아직 RESYNC되지 않은 새 테이블스페이스일 수 있다.
-- REPORT SCHEMA 목록과 대조하면 두 경우를 바로 구분할 수 있다.
-- 배치 스크립트라면 이 오류로 그날 백업이 통째로 빠질 수 있으므로
-- 로그에서 RMAN- 문자열을 찾는 검사가 반드시 필요하다.

-- << 수정 >>

Tablespace dropped.

-- 실무 포인트
-- 1) 백업 범위는 DATABASE, TABLESPACE, DATAFILE 세 단위로 지정한다.
--    데이터파일은 번호와 경로 어느 쪽으로도 지정할 수 있다.
--
-- 2) SKIP READONLY 는 읽기 전용 파일을 건너뛴다.
--    내용이 바뀌지 않으므로 한 번만 백업하면 되기 때문이다.
--    다만 읽기 쓰기로 되돌린 뒤에는 반드시 다시 백업해야 한다.
--
-- 3) NOT BACKED UP SINCE TIME 은 중단된 백업을 이어받을 때 쓴다.
--    이미 백업된 파일을 건너뛰므로 처음부터 다시 하지 않아도 된다.
--    야간 백업이 시간을 넘겨 끊긴 다음 날 아침에 유용하다.
--
-- 4) 범위를 나눠 백업하면 파일 누락 위험이 생긴다.
--    새 테이블스페이스가 스크립트에 추가되지 않는 것이 대표적이다.
--    REPORT SCHEMA 목록과 백업 범위를 정기적으로 대조한다.
--
-- 5) REPORT NEED BACKUP 을 매일 확인하면 누락을 조기에 발견한다.
--    이 명령이 비어 있어야 정책 요건이 충족된 상태다.
--
-- 6) 근본 대책은 BACKUP DATABASE 로 범위를 지정하는 것이다.
--    구조가 바뀌어도 자동으로 포함되므로 누락이 원천적으로 사라진다.
