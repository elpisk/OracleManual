================================================================================
 실습 14-4 : Block Change Tracking 활성화와 효과 확인
 과정      : Oracle Database 19c Backup & Recovery
 환경      : Oracle 19.3.0 / Oracle Linux 7 / non-CDB ORCL / ARCHIVELOG
 소요 시간 : 약 30분
================================================================================

--------------------------------------------------------------------------------
[1] 시나리오 개요
--------------------------------------------------------------------------------
-- BCT를 켜지 않은 상태의 증분 백업 읽기량을 먼저 측정한다.
-- BCT를 활성화하고 같은 변경량으로 다시 측정해 비교한다.
-- 활성화 직후 첫 증분이 전체를 읽는다는 점을 확인한다.
-- BCT 파일을 잃었을 때의 동작과 복구 방법을 확인한다.
-- 작업 유형 : 백업 최적화(장애 복구 아님)

--------------------------------------------------------------------------------
[2] 사전 조건
--------------------------------------------------------------------------------
-- 실습 14-3이 완료되어 증분 백업 체계가 있어야 한다.

[oracle@oel7v9 ~]$ sqlplus / as sysdba

SYS@orcl> SET LINESIZE 200
SYS@orcl> COL filename FOR a40
SYS@orcl> SELECT status, filename FROM v$block_change_tracking;

STATUS     FILENAME
---------- ----------------------------------------
DISABLED

-- 아직 꺼져 있다.

SYS@orcl> SELECT COUNT(*) FROM hr.incr_test;

  COUNT(*)
----------
      2000

[oracle@oel7v9 ~]$ sqlplus / as sysdba

SYS@orcl> SET LINESIZE 200
SYS@orcl> SELECT file#, incremental_level AS lv, blocks, blocks_read, datafile_blocks,
  2         ROUND(blocks_read/datafile_blocks, 2) AS read_ratio
  3  FROM   v$backup_datafile
  4  WHERE  file# = 8 AND incremental_level = 1
  5  ORDER  BY completion_time DESC FETCH FIRST 1 ROWS ONLY;

     FILE#         LV     BLOCKS BLOCKS_READ DATAFILE_BLOCKS READ_RATIO
---------- ---------- ---------- ----------- --------------- ----------
         8          1         68         896            2560        .35

-- 실제로 담은 블록은 68개인데 읽은 블록은 896개다.
-- 파일은 2,560블록이지만 한 번도 쓰인 적 없는 뒷부분은 BCT 없이도 읽지 않는다.
-- 그래서 비율이 1 이 아니라 .35 다. 그러나 데이터가 들어 있는 896블록은 변경 여부와
-- 무관하게 전부 읽었다. 백업 크기는 줄었지만 읽기 부담은 전체 백업과 같다.

--------------------------------------------------------------------------------
[4] 작업 수행 : BCT 활성화
--------------------------------------------------------------------------------
SYS@orcl> ALTER DATABASE ENABLE BLOCK CHANGE TRACKING
  2    USING FILE '/u02/oradata/orcl/bct_orcl.chg' REUSE;

Database altered.

SYS@orcl> COL filename FOR a40
SYS@orcl> SELECT status, filename, bytes/1024/1024 AS mb
  2  FROM   v$block_change_tracking;

STATUS     FILENAME                                         MB
---------- ---------------------------------------- ----------
ENABLED    /u02/oradata/orcl/bct_orcl.chg              11.0625

SYS@orcl> !ls -l /u02/oradata/orcl/bct_orcl.chg
-rw-r-----. 1 oracle dba 11600384 May 15 10:22 /u02/oradata/orcl/bct_orcl.chg

-- 최소 크기가 11MB 남짓이다. 데이터베이스 크기의 1/30000 정도가 기준이다.
-- alert 에 "Starting background process CTWR" 와 "Block change tracking service is active." 가 남는다.

[oracle@oel7v9 ~]$ sqlplus / as sysdba

SYS@orcl> SET LINESIZE 200
SYS@orcl> SELECT TO_CHAR(completion_time,'HH24:MI') AS done, blocks, blocks_read,
  2         ROUND(blocks_read/datafile_blocks, 2) AS read_ratio
  3  FROM   v$backup_datafile
  4  WHERE  file# = 8 AND incremental_level = 1
  5  ORDER  BY completion_time DESC FETCH FIRST 3 ROWS ONLY;

DONE      BLOCKS BLOCKS_READ READ_RATIO
----- ---------- ----------- ----------
10:41         68         125        .05
10:31         69         896        .35
10:22         68         896        .35

-- 읽은 블록이 896에서 125로 줄었다. 같은 200행 변경인데 7분의 1만 읽었다.
-- 백업 크기(68블록)는 이전과 같다. 읽기 부담이 사라진 것이 핵심이다.
-- 파일이 작아 시간 차이는 1초 안이지만 대형 파일에서는 시간 단위로 벌어진다.

[8] 검증 및 실무 포인트
--------------------------------------------------------------------------------
[oracle@oel7v9 ~]$ rman target / catalog rcatowner@rcat

RMAN> BACKUP INCREMENTAL LEVEL 0 TABLESPACE tbs13 TAG 'L0_REENABLE';
RMAN> EXIT

[oracle@oel7v9 ~]$ sqlplus / as sysdba

SYS@orcl> UPDATE hr.incr_test SET pad = RPAD('g',2000,'g')
  2  WHERE id BETWEEN 601 AND 700;

100 rows updated.

SYS@orcl> COMMIT;
SYS@orcl> EXIT

[oracle@oel7v9 ~]$ rman target / catalog rcatowner@rcat
RMAN> BACKUP INCREMENTAL LEVEL 1 TABLESPACE tbs13 TAG 'BCT_RECHECK';
RMAN> EXIT

[oracle@oel7v9 ~]$ sqlplus -s / as sysdba <<< \
> "SELECT blocks, blocks_read, ROUND(blocks_read/datafile_blocks,2) AS ratio
   FROM v\$backup_datafile WHERE file#=8 AND incremental_level=1
   ORDER BY completion_time DESC FETCH FIRST 1 ROWS ONLY;"

    BLOCKS BLOCKS_READ      RATIO
---------- ----------- ----------
        35          65        .03

-- 다시 정상 동작한다.

[oracle@oel7v9 ~]$ sqlplus -s / as sysdba <<< \
> "SELECT status, bytes/1024/1024 AS mb FROM v\$block_change_tracking;"

STATUS             MB
---------- ----------
ENABLED       11.0625

-- 실무 포인트
-- 1) BCT가 없으면 증분 백업은 크기만 줄고 읽기량은 줄지 않는다.
--    v$backup_datafile 의 blocks_read 로 확인한다. 쓰인 적 있는 블록은 전부 읽는다.
--    (한 번도 쓰이지 않은 블록은 BCT 없이도 읽지 않으므로 비율이 1 은 아니다.)
--
-- 2) 활성화 직후 첫 증분은 여전히 전체를 읽는다.
--    기준이 될 Level 0 이후의 변경 기록이 아직 없기 때문이다.
--    다음 Level 0 이후부터 안정적으로 동작하므로 그때 측정한다.
--
-- 3) 효과는 읽기량으로 나타난다. 이 실습에서는 896블록이 125블록으로 줄었다.
--    대형 데이터베이스에서는 그 차이가 시간 단위로 벌어진다.
--
-- 4) BCT 파일 크기는 데이터베이스 크기의 1/30000 정도이며 최소 11MB 남짓이다.
--    데이터파일과 같은 디스크에 두면 함께 잃을 수 있으므로 위치를 검토한다.
--
-- 5) 파일을 잃어도 업무는 계속되지만 정상 종료가 인스턴스 강제 종료(ORA-19755, ORA-03113)로
--    끝난다. 백업 성능을 위해 켠 기능이 가용성을 해치는 지점이다.
--    v$block_change_tracking 조회가 곧 파일 존재 점검이므로 정기 점검 항목에 넣는다.
--
-- 6) 복구 방법은 재기동이다. 기동 때 파일이 없으면 새로 만들어진다.
--    추적 정보는 비므로 곧바로 Level 0 을 다시 받아 기준을 세운다.
