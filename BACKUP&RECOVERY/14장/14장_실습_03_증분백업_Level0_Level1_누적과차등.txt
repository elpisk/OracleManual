 실습 14-3 : 증분 백업 Level 0/1 — 누적과 차등 비교
 과정      : Oracle Database 19c Backup & Recovery

--------------------------------------------------------------------------------
[1] 시나리오 개요
--------------------------------------------------------------------------------
-- Level 0을 기준점으로 삼고 Level 1을 여러 번 받는다.
-- 차등과 누적의 크기 차이를 같은 변경량으로 비교한다.
-- FULL을 기준점으로 삼으려 할 때 무슨 일이 생기는지 확인한다.
-- 증분 백업의 복원 동작을 PREVIEW로 확인한다.
-- 작업 유형 : 백업 수행(장애 복구 아님)

--------------------------------------------------------------------------------
[2] 사전 조건
--------------------------------------------------------------------------------
-- 실습 14-2까지 완료되어 있어야 한다.
-- 변경을 만들 테이블을 준비한다.

[oracle@oel7v9r1 ~]$ sqlplus / as sysdba

SYS@orcl> CREATE TABLE hr.incr_test(id NUMBER, pad VARCHAR2(2000))
  2    TABLESPACE tbs13;

Table created.

SYS@orcl> INSERT INTO hr.incr_test
  2  SELECT LEVEL, RPAD('x', 2000, 'x') FROM dual CONNECT BY LEVEL <= 2000;
SYS@orcl> COMMIT;

Commit complete.

SYS@orcl> EXIT

[4] 작업 수행 : FULL을 기준으로 시도
--------------------------------------------------------------------------------
-- 먼저 흔한 실수를 재현한다.
-- 주간 백업을 FULL로 받고 Level 1을 이어 받는 구성이다.

RMAN> BACKUP TABLESPACE tbs13 TAG 'WEEKLY_FULL';

Starting backup at 15-MAY-25
Finished backup at 15-MAY-25

RMAN> BACKUP INCREMENTAL LEVEL 1 TABLESPACE tbs13 TAG 'L1_AFTER_FULL';

Starting backup at 15-MAY-25
channel ORA_DISK_1: starting incremental level 1 datafile backup set
no parent backup or copy of datafile 8 found
channel ORA_DISK_1: starting full datafile backup set
input datafile file number=00008 name=/u02/oradata/ORCL/tbs13_01.dbf
Finished backup at 15-MAY-25

-- << 원인 파악 >>
-- 'no parent backup or copy of datafile 8 found' 라는 줄이 나온다.
-- Level 1의 기준이 될 Level 0이 없다는 뜻이다.
-- FULL 백업은 증분 체계에 참여하지 않으므로 기준점이 되지 못한다.
-- 결과적으로 Level 1이 전체를 담는 백업이 되었다.

RMAN> LIST BACKUP OF TABLESPACE tbs13 SUMMARY;

Key     TY LV S Device Type Completion Time #Pieces Tag
------- -- -- - ----------- --------------- ------- ---------------
40      B  F  A DISK        15-MAY-25       1       WEEKLY_FULL
41      B  F  A DISK        15-MAY-25       1       L1_AFTER_FULL

-- Level 1로 요청했는데 LV 컬럼이 F로 기록되었다.

-- << 수정 >> 주간 백업을 Level 0으로 바꾼다.

RMAN> BACKUP INCREMENTAL LEVEL 0 TABLESPACE tbs13 TAG 'L0_WEEKLY';

[oracle@oel7v9r1 ~]$ sqlplus / as sysdba

SYS@orcl> SELECT bs.recid, bs.incremental_level AS lv,
  2         DECODE(bd.incremental_change#, 0, 'BASE',
  3                TO_CHAR(bd.incremental_change#)) AS from_scn,
  4         ROUND(bs.bytes/1024/1024, 1) AS mb
  5  FROM   v$backup_set bs, v$backup_datafile bd
  6  WHERE  bs.set_stamp = bd.set_stamp AND bs.set_count = bd.set_count
  7  AND    bd.file# = 8 ORDER BY bs.recid;

     RECID LV FROM_SCN          MB
---------- -- ------------ --------
        42  0 BASE             18.2
        43  1 2551200           3.4
        44  1 2552800           3.3
        45  1 2554400           3.4
        46  1 2551200           9.8

-- RECID 45가 차등이고 46이 누적이다.
-- 차등은 직전 Level 1 이후 변경분만 담아 3.4MB다.
-- 누적은 Level 0 이후 전체 변경분을 담아 9.8MB다.
-- from_scn 값이 그 차이를 보여 준다. 누적은 Level 0의 SCN을 기준으로 한다.

-- 복구 시 적용 대상
--   차등 → L0 + 월 + 화 + 수  (4개)
--   누적 → L0 + 누적 수요일   (2개)

-- 실무 포인트
-- 1) FULL은 증분의 기준점이 되지 못한다.
--    'no parent backup or copy of datafile n found' 가 그 신호다.
--    Level 1로 요청해도 실제로는 전체를 담는 백업이 만들어진다.
--    LIST 출력의 LV 컬럼으로 실제 결과를 반드시 확인한다.
--
-- 2) 차등과 누적의 차이는 from_scn 으로 확인할 수 있다.
--    차등은 직전 백업의 SCN, 누적은 Level 0의 SCN을 기준으로 한다.
--    같은 변경량에서 누적이 약 세 배 컸다.
--
-- 3) 복구 관점에서는 반대다.
--    차등은 Level 0과 모든 Level 1을 순서대로 적용해야 하고
--    누적은 Level 0과 마지막 하나만 적용하면 된다.
--
-- 4) 증분 레벨은 0과 1만 지원한다.
--    9i의 Level 2~4는 10g에서 사라졌으며 19c도 두 레벨만 쓴다.
--
-- 5) RESTORE PREVIEW 로 복원에 필요한 백업을 미리 확인한다.
--    목록이 길어지면 Level 0 주기를 짧게 조정할 근거가 된다.
--
-- 6) 백업 크기만 보고 판단하지 않는다.
--    다음 실습에서 BCT 없이는 소요 시간이 줄지 않는다는 점을 확인한다.
