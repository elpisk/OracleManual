 시험 안내
--------------------------------------------------------------------------------
접속   : [oracle@oel7v9 ~]$ sqlplus / as sysdba   →   SYS@orcl>
         [oracle@oel7v9 ~]$ rman target /         →   RMAN>
         (Recovery Catalog 는 쓰지 않는다. 컨트롤파일 리포지터리 + 자동백업만으로 푼다)

경로   : 데이터파일·TEMP        /u01/app/oracle/oradata/orcl/
         컨트롤파일 01·02       /u01/app/oracle/oradata/orcl/
         컨트롤파일 03          /u02/oradata/orcl/control03.ctl
         리두 a·b 멤버          /u01/app/oracle/oradata/orcl/, /u02/oradata/orcl/
         아카이브               /home/oracle/arch1/  (LOG_ARCHIVE_DEST_1)
         파라미터·패스워드      $ORACLE_HOME/dbs  (spfileorcl.ora, orapworcl)
         RMAN 백업              /home/oracle/backup/exam_rman/
                                  ORCL_<날짜>_<n>_<p>.bkp  백업 세트 조각 (Level 0 + 아카이브)
                                  cf_c-<DBID>-<날짜>-<nn>  컨트롤파일·spfile 자동백업
                                  dpump/hr_exam.dmp       Data Pump 논리백업 (디렉터리 객체 EXAM_DP)
         새 위치 (과제 1-3)     /u02/oradata/orcl/
         장애 유발 스크립트     /home/oracle/exam/

         ※ 위 경로는 교안 기준 배치다. 자기 환경이 다르면 v$datafile, v$controlfile,
            v$logfile, v$archive_dest 로 확인한 경로를 쓴다. 스크립트도 그 뷰에서 경로를 읽는다.

전제   : 사전 준비 때 CONFIGURE 로 백업 위치와 자동백업이 설정되어 있고,
         Level 0 백업(TAG EXAM_L0)과 아카이브 백업(TAG EXAM_ARC)이 한 번 받아져 있다.
         DBID 는 알려 주지 않는다. 필요하면 스스로 찾는다 (자동백업 파일명, 기준선 조회).
         사용자 관리 복구(cp, RECOVER DATABASE)는 쓰지 않는다. 파일 복원은 RMAN 으로만 한다.

답안 작성 규칙
  ① 판정 근거   무엇을 조회해 어떤 값을 보고 그 경로를 골랐는가
  ② 명령 전문   실제로 실행한 명령을 그대로 (RMAN 의 RUN 블록 전체)
  ③ 복구 후 검증 무엇으로 복구가 끝났음을 확인했는가
  세 가지가 모두 있어야 그 과제를 완료로 인정한다. 명령만 나열한 답은 배점의 절반을 깎는다.
  오류를 만난 것 자체는 감점하지 않는다. 오류를 만나고도 판단 과정을 적지 않으면 감점한다.
  되돌릴 수 없는 명령(RESETLOGS, FLASHBACK TABLE, impdp REPLACE) 전에 현재 상태를
  기록하거나 사본을 확보하고 그 기록을 남긴다.

손실 보고
  손실이 발생한 과제는 반드시 "무엇을, 어느 시점부터 어느 시점까지 잃었는가" 를
  업무 시각으로 환산해 적는다. 기술 용어만으로 적은 보고는 절반을 깎는다.
  확인용 테이블 hr.exam_log (step, memo, reg_time, scn) 의 행이 그 근거가 된다.
  손실이 없는 과제도 "손실 없음" 과 그 근거(마지막 행의 step 과 시각)를 적는다.

경고
  이 평가의 장애 유발 작업은 데이터파일·컨트롤파일·spfile·백업 조각을 실제로 삭제하고,
  데이터 블록을 dd 로 덮어쓴다. 반드시 개인 실습 환경(ORCL)에서만 수행한다.

진행 방식
  한 시나리오의 과제는 한꺼번에 깨지지 않는다. 과제마다 장애를 따로 주입한다.
  각 과제의 첫 항목에 적힌 스크립트를 그때 실행한다.

      $ /home/oracle/exam/exam_break1.sh 1     ← 과제 1-1 만 깨진다
        (진단 → 복구 → 검증 → 답안 작성)
      $ /home/oracle/exam/exam_break1.sh 2     ← 과제 1-2 만 깨진다

  앞 과제를 복구해야 다음 과제를 주입할 수 있다. 복구가 끝나지 않은 상태에서
  실행하면 스크립트가 "중단" 메시지를 내고 아무것도 건드리지 않은 채 종료한다.
  복구를 이어서 하거나, 그 과제를 포기하고 감독관에게 알린다.

  앞 과제가 RESETLOGS 로 끝났다면 다음 장애 스크립트는 먼저 새 Level 0 백업을 받고
  (운영 원칙 : RESETLOGS 직후 전체 백업) 그 뒤에 장애를 주입한다. 화면에 그 사실이 표시된다.

감독자 사전 준비
  $ /home/oracle/exam/exam_prep.sh      기준선, RMAN 설정, Level 0, 논리백업, 확인용 테이블, 복원점
  시나리오 사이에 되돌릴 때는
  $ /home/oracle/exam/exam_reset.sh     감독자 복원점으로 원상 복귀 (반드시 시나리오 사이마다)

모든 과제의 답안에 LIST / REPORT / CROSSCHECK 중 무엇으로 그것을 확인했는지 적을 것.

--------------------------------------------------------------------------------
 과제 1-1. 백업 조각 소실 — 백업 체계 점검과 증분 백업          [30점]
--------------------------------------------------------------------------------
관리자가 백업 디렉터리를 정리하다 파일 하나를 지웠다. 데이터베이스는 정상이다.
Level 0 이후 업무가 계속되어 아카이브가 쌓였다. 지금 이 백업 체계로 복구가 가능한지 점검하고
보강해야 한다.

 1-1.1 장애를 유발할 것.
       $ /home/oracle/exam/exam_break1.sh 1

 1-1.2 DBID 를 찾아 기록할 것. 어디에서 찾았는지 두 가지 방법을 적을 것.
       (데이터베이스가 열려 있을 때와 열려 있지 않을 때 각각)

 1-1.3 LIST BACKUP SUMMARY 로 리포지터리가 아는 백업을 적고, CROSSCHECK BACKUP 으로
       디스크와 대조할 것. 무엇이 EXPIRED 가 되었는지, 그 조각에 무엇이 들어 있었는지
       (LIST EXPIRED BACKUP) 적을 것.

 1-1.4 EXPIRED 항목을 리포지터리에서 지울 것. 지우지 않으면 복구 때 무슨 일이 생기는지 적을 것.
       AVAILABLE 과 EXPIRED 와 DELETED 의 차이를 한 줄씩 적을 것.

 1-1.5 사라진 조각이 담고 있던 아카이브가 아직 디스크에 있는지 확인하고, Level 1 증분 백업을
       아카이브와 함께 받을 것 (TAG EXAM_L1). PLUS ARCHIVELOG 가 그 아카이브를 다시 백업하는
       이유를 BACKUP OPTIMIZATION 설정과 함께 적을 것.

 1-1.6 RESTORE DATABASE PREVIEW SUMMARY 로 "지금 복구한다면 어떤 백업이 쓰이는가" 를 확인하고,
       Level 0·Level 1·아카이브가 각각 어떻게 쓰이는지 적을 것.
       REPORT NEED BACKUP 과 REPORT OBSOLETE 의 결과와 뜻을 적을 것.

 제출 : 1-1.2 의 DBID 와 방법, 1-1.3 의 조회 결과, 1-1.4 의 명령과 서술, 1-1.5 의 명령과 서술,
        1-1.6 의 조회와 해석

 1-2.5 hr.exam_log 로 손실이 없음을 증명할 것. 사용자 관리 복구(8장)와 비교해

================================================================================
이 시나리오의 세 과제는 모두 "리포지터리(컨트롤파일)가 없는 상태에서 무엇으로 시작하는가" 를 묻는다.

--------------------------------------------------------------------------------
 과제 2-1. spfile 유실                                         [25점]
--------------------------------------------------------------------------------
정상 종료된 뒤 spfile 이 사라졌다. pfile 도 없다. 데이터파일·컨트롤파일은 멀쩡하다.

 2-1.1 장애를 유발할 것.
       $ /home/oracle/exam/exam_break2.sh 1

 2-1.2 SQL*Plus 의 STARTUP 이 무슨 오류로 실패하는지 기록할 것 (ORA-01078, LRM-00109).

 2-1.3 RMAN 에서 STARTUP NOMOUNT 를 실행할 것. 파라미터 파일이 없는데도 인스턴스가 뜨는
       이유를 화면 문구로 인용할 것 ("starting Oracle instance without parameter file ...").

 2-1.4 DBID 를 지정하고 자동백업에서 spfile 을 복원할 것.
       자동백업 위치를 RMAN 이 모르는 이유와, 그것을 알려 주는 방법(SET CONTROLFILE AUTOBACKUP
       FORMAT, 또는 RESTORE SPFILE FROM '<조각>')을 적을 것.

 2-1.5 복원한 spfile 로 다시 기동하고(STARTUP FORCE) SHOW PARAMETER spfile 로 확인할 것.
       hr.exam_log 로 손실이 없음을 증명하고, 왜 spfile 유실은 데이터 손실과 무관한지 적을 것.

 제출 : 2-1.2 의 오류, 2-1.3 의 인용, 2-1.4 의 명령 전문과 서술, 2-1.5 의 검증과 서술

--------------------------------------------------------------------------------
 과제 2-2. 비정상 종료 + 컨트롤파일 전손                         [30점]
--------------------------------------------------------------------------------
인스턴스가 ABORT 로 죽었고 컨트롤파일이 전부 사라졌다. 데이터파일·리두 로그·아카이브는 멀쩡하다.

 2-2.1 장애를 유발할 것.
       $ /home/oracle/exam/exam_break2.sh 2

 2-2.2 기동이 멈춘 단계와 오류 번호(ORA-00205)를 기록할 것.

 2-2.3 자동백업에서 컨트롤파일을 복원할 것. 몇 곳에 복원되었는지 출력에서 인용할 것.
       DBID 지정이 왜 필요한지 적을 것.

 2-2.4 MOUNT 한 뒤 RECOVER DATABASE 를 실행할 것. RMAN 이 아카이브 뒤에 온라인 리두 로그까지
       적용했는지 출력("media recovery complete")과 alert log 로 확인할 것.

 2-2.5 그대로 ALTER DATABASE OPEN 을 시도하고 오류를 기록한 뒤, RESETLOGS 로 열 것.
       현재 리두를 다 적용했는데도 왜 RESETLOGS 가 필요한지 적을 것.

 2-2.6 hr.exam_log 로 손실이 없음을 증명하고 (S2-2b 행이 있어야 한다), LIST INCARNATION 으로
       인카네이션 변화를 확인할 것. 이 시점에 즉시 해야 할 일을 적을 것.

 제출 : 2-2.2 의 오류, 2-2.3 의 명령과 인용, 2-2.4 의 인용, 2-2.5 의 오류와 서술,
        2-2.6 의 검증과 조회

--------------------------------------------------------------------------------
 과제 2-3. 사용자 실수 — 시점 기반 불완전 복구                    [45점]
--------------------------------------------------------------------------------
업무 담당자가 hr.exam_orders 를 DROP ... PURGE 해 버렸다. 파일 장애는 없다.
신고 시각은 화면과 /home/oracle/exam/incident.txt 에 있다. 실수 이후에도 업무는 계속되었다.
※ 앞 과제가 RESETLOGS 로 끝났으므로 장애 스크립트가 먼저 새 Level 0 를 받는다.

 2-3.1 장애를 유발할 것.
       $ /home/oracle/exam/exam_break2.sh 3

 2-3.2 휴지통으로 되돌릴 수 없는 이유(PURGE)와, 그래서 백업으로 돌아가야 하는 이유를 적을 것.
       되돌릴 시각을 정하고 그 근거(신고 시각과 몇 초 차이를 둘지)를 적을 것.
       hr.exam_log 에서 그 시각 앞뒤의 행을 미리 조회해 무엇이 사라질지 예측해 적을 것.

 2-3.3 RUN 블록 하나로 복구할 것 : STARTUP FORCE MOUNT → SET UNTIL TIME → RESTORE DATABASE →
       RECOVER DATABASE. SET UNTIL TIME 의 시각 형식을 어떻게 맞췄는지 적을 것
       (NLS_DATE_FORMAT 을 바꾸거나 TO_DATE 를 쓴다).

 2-3.4 RESETLOGS 로 열고 hr.exam_orders 의 행 수(2000)로 복구를 검증할 것.
       hr.exam_log 로 사라진 행을 확인해 2-3.2 의 예측과 대조하고 손실을 업무 시각으로 보고할 것.

 2-3.5 LIST INCARNATION 으로 인카네이션 변화를 확인할 것. 이전 인카네이션의 백업이 아직
       쓸모가 있는지(RESET DATABASE TO INCARNATION 이 언제 필요한지) 적을 것.

 2-3.6 이 손실(실수 이후의 정상 업무)을 없앨 수 있었던 방법을 두 가지 적을 것.
       (힌트 : 16장 RECOVER TABLE, 18장 Flashback)

 시나리오 3  블록 손상·Flashback·Data Pump (16·18·19장)           100점 / 60분

이 시나리오는 "백업에서 파일을 통째로 되돌리지 않고" 푸는 세 가지 길을 묻는다.
각 과제의 답안 첫 줄에 "왜 이 방법인가 — 다른 방법은 왜 안 되는가" 를 적을 것.

 과제 3-1. 데이터 블록 물리 손상 — Block Media Recovery           [30점]
--------------------------------------------------------------------------------
hr.exam_items 의 데이터 블록 하나가 디스크에서 0 으로 덮였다. 데이터베이스는 OPEN 이다.

 3-1.1 장애를 유발할 것.
       $ /home/oracle/exam/exam_break3.sh 1

 3-1.2 오류 번호(ORA-01578)와 파일 번호·블록 번호를 기록할 것. ORA-26040 이 붙어 있는지
       확인하고 그 유무가 무엇을 뜻하는지 적을 것.
       SELECT COUNT(*) 는 오류 없이 5000 이 나온다. 왜 그런지(어느 세그먼트를 읽는지) 적고,
       테이블 블록을 읽는 조회(예: SUM(price))로 증상을 드러낼 것.

 3-1.3 RMAN 으로 그 데이터파일을 VALIDATE 해 손상을 리포지터리에 기록하고,
       v$database_block_corruption 에서 file#, block#, corruption_type 을 읽을 것.

 3-1.4 손상 블록만 복구할 것 (RECOVER DATAFILE n BLOCK m 또는 RECOVER CORRUPTION LIST).
       RMAN 이 그 블록을 어디에서 가져와 어떻게 최신으로 만들었는지 출력에서 인용할 것.

 3-1.5 hr.exam_items 의 행 수(5000)와 v$database_block_corruption 이 비었음을 확인할 것.
       파일 전체를 RESTORE 하지 않은 것이 왜 중요한지 (서비스 관점) 적을 것.

 3-1.6 Data Recovery Advisor(LIST FAILURE) 가 이 손상을 어떻게 보고했는지 적을 것.

--------------------------------------------------------------------------------
 과제 3-2. 사용자 실수 두 건 — Flashback Drop / Flashback Table   [35점]
--------------------------------------------------------------------------------
두 가지 실수가 잇달아 일어났다. ① hr.exam_orders 를 DROP (PURGE 없음).
② hr.exam_items 전 행의 price 를 0 으로 바꾸고 커밋. 두 시각은 화면과 incident.txt 에 있다.
백업을 쓰지 말고, 데이터베이스를 내리지도 말고 되돌려야 한다.

 3-2.1 장애를 유발할 것.
       $ /home/oracle/exam/exam_break3.sh 2

 3-2.2 두 실수가 각각 어디에 흔적을 남겼는지 적을 것 (휴지통 / UNDO).
       UNDO 보존 시간(undo_retention)을 확인하고 왜 서둘러야 하는지 적을 것.

 3-2.3 ① 휴지통(dba_recyclebin)에서 원래 이름과 삭제 시각을 확인하고 FLASHBACK TABLE ...
       TO BEFORE DROP 으로 되살릴 것. 행 수(2000)로 검증할 것.

 3-2.4 ② Flashback Version Query 로 한 행(item_id = 1)의 price 가 언제 어떻게 바뀌었는지 보일 것.
       Flashback Query(AS OF TIMESTAMP)로 실수 직전 시점의 price = 0 행 수가 0 임을 확인할 것.

 3-2.5 ROW MOVEMENT 없이 FLASHBACK TABLE ... TO TIMESTAMP 를 먼저 시도하고 오류(ORA-08189)를
       기록할 것. ENABLE ROW MOVEMENT 뒤 다시 실행해 되돌릴 것. 왜 ROW MOVEMENT 가 필요한지 적을 것.

 3-2.6 price = 0 인 행이 0 개임을 확인하고, hr.exam_log 의 다른 행(S3-2b)은 그대로임을 보일 것.
       Flashback Table 이 다른 테이블에 영향을 주지 않는 이유를 적을 것.

--------------------------------------------------------------------------------
 과제 3-3. TRUNCATE — Flashback 이 안 될 때, Data Pump 로 복원       [35점]
--------------------------------------------------------------------------------
논리백업(hr_exam.dmp) 이후 hr.exam_items 에 200 행이 추가되었고, 그 뒤 누군가 테이블을
TRUNCATE 했다. 시각은 화면과 incident.txt 에 있다.

 3-3.1 장애를 유발할 것.
       $ /home/oracle/exam/exam_break3.sh 3

 3-3.2 Flashback Query 와 FLASHBACK TABLE ... TO TIMESTAMP 를 시도하고 오류(ORA-01466)를 기록할 것.
       DELETE 는 되돌릴 수 있는데 TRUNCATE 는 왜 안 되는지 적을 것.

 3-3.3 남은 선택지를 두 가지 적고 (Data Pump 논리백업 / RMAN RECOVER TABLE), 각각의 손실 범위와
       소요 시간·자원을 비교해 어느 쪽을 택할지 정할 것.

 3-3.4 디렉터리 객체 EXAM_DP 의 경로와 덤프 파일을 확인하고, impdp 로 hr.exam_items 만
       복원할 것. TABLE_EXISTS_ACTION 을 무엇으로 했는지와 그 이유를 적을 것.

 3-3.5 행 수를 확인하고, 논리백업 이후 입력된 200 행이 사라졌음을 hr.exam_log (S3-3a) 의
       시각으로 환산해 손실을 보고할 것.

 3-3.6 만약 손실 없이 되살려야 한다면 RECOVER TABLE 을 어떻게 쓰는지 명령을 적을 것
       (UNTIL TIME, AUXILIARY DESTINATION, REMAP TABLE). 실행하지 않아도 된다.
       실행하려면 무엇이 필요하고 얼마나 걸리는지(16장 실습의 경험) 적을 것.

        3-3.5 의 손실 보고, 3-3.6 의 명령과 서술
