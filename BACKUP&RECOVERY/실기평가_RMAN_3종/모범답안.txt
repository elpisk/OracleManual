================================================================================
 ■ RMAN·Flashback·Data Pump 복구 실기평가 — 3종 모범답안
 과정      : Oracle Database 19c Backup & Recovery (13~19장 범위)
 환경      : Oracle 19.3.0 / Oracle Linux 7 / non-CDB ORCL / ARCHIVELOG
================================================================================

이 문서는 문제지의 과제 1-1 부터 3-3 까지에 대응하는 모범답안이다.
각 과제를 【판정】 무엇을 보고 경로를 정했는가 · 【수행】 실제로 실행한 명령 ·
【검증】 복구가 끝났음을 무엇으로 확인했는가 세 축으로 나눈다.

채점은 명령의 정확성보다 판정 근거의 유무를 먼저 본다.

[검증됨] 표시가 붙은 출력은 이 문서를 만들 때 별도 랩(SID sales, DBID 1117727320,
데이터파일 6개, 2026-09-22)에서 장애 스크립트와 아래 명령을 그대로 실행해 얻은 값이다.
경로와 SID 만 문제지의 표기(orcl, /u01/app/oracle/oradata/orcl, /home/oracle/arch1,
/home/oracle/backup/exam_rman)로 옮겼고 SCN·시퀀스·시각·오류 번호·행 수·조각 번호는
실측값 그대로다. DBID·파일 번호(exam_tbs = 2 등)·블록 번호는 환경마다 다르다.

 과제 1-3. 디렉터리를 못 쓰게 됨 — 새 위치로 복구 (SET NEWNAME)  [40점]
--------------------------------------------------------------------------------
【판정】

1-3.2 증상과 위험  [검증됨]

  SYS@orcl> SELECT COUNT(*) FROM hr.exam_items;
  ORA-01116: error in opening database file 2
  ORA-01110: data file 2: '/u01/app/oracle/oradata/orcl/exam_tbs01.dbf'

  ▸ 그냥 RESTORE DATAFILE 2 를 하면 컨트롤파일이 아는 원래 경로(/u01/.../exam_tbs01.dbf)에
    복원한다. 그 디렉터리를 못 쓴다고 가정했으므로 복원 자체가 실패하거나, 되더라도 같은
    장애를 다시 겪는다. 컨트롤파일의 경로를 먼저 바꿔야 한다.

1-3.6 사용자 관리 복구라면

 과제 3-1. 데이터 블록 물리 손상 — Block Media Recovery  [30점]
--------------------------------------------------------------------------------
【판정】

3-1.2 증상  [검증됨]

  SYS@orcl> SELECT COUNT(*) FROM hr.exam_items;
        5000                                          ← 오류가 없다!
  SYS@orcl> SELECT SUM(price) FROM hr.exam_items;
  ORA-01578: ORACLE data block corrupted (file # 2, block # 143)
  ORA-01110: data file 2: '/u01/app/oracle/oradata/orcl/exam_tbs01.dbf'

  ▸ COUNT(*) 는 PK 인덱스만 훑어(index fast full scan) 테이블 블록을 읽지 않는다.
    price 는 인덱스에 없으므로 SUM(price) 가 테이블 블록을 읽다가 손상 블록에서 멈춘다.
    "조회가 되니 멀쩡하다" 는 판단이 왜 위험한지 보여 주는 대목이다.
  ▸ ORA-26040 이 없다 = NOLOGGING 으로 생긴 논리적 손상이 아니라 물리적 손상이다.
    (ORA-26040 이 붙으면 백업에도 그 블록의 내용이 없어 Block Media Recovery 로 못 살린다)

3-1.3 VALIDATE  [검증됨]

  RMAN> VALIDATE DATAFILE 2;
  List of Datafiles
  File Status Marked Corrupt Empty Blocks Blocks Examined High SCN
  2    FAILED 0              2377         2560            2317695
    File Name: /u01/app/oracle/oradata/orcl/exam_tbs01.dbf
    Block Type Blocks Failing Blocks Processed

    Index      0              23
    Other      1              136
  validate found one or more corrupt blocks

  SYS@orcl> SELECT file#, block#, blocks, corruption_change#, corruption_type FROM v$database_block_corruption;

  ▸ dd 로 0 을 채운 블록은 헤더가 없어 'Other' 유형, corruption_type 'ALL ZERO' 로 잡힌다.
    VALIDATE 는 이 뷰에 기록만 하고 고치지 않는다.

【수행】

3-1.4 블록만 복구  [검증됨]

  channel ORA_DISK_1: restoring block(s)
  channel ORA_DISK_1: specifying block(s) to restore from backup set

  SYS@orcl> SELECT COUNT(*), SUM(price) FROM hr.exam_items;

  ▸ 파일 전체를 RESTORE 하지 않은 것이 중요한 이유 : 파일을 OFFLINE 할 필요가 없고, 그 파일의

  Database Role: PRIMARY

    or more corrupt blocks" 류의 실패가 잡히고 ADVISE FAILURE → REPAIR FAILURE 로 같은 블록

--------------------------------------------------------------------------------
 과제 3-2. 사용자 실수 두 건 — Flashback Drop / Flashback Table  [35점]
--------------------------------------------------------------------------------
【판정】

3-2.2 흔적과 시간 제한

  ▸ ① DROP (PURGE 없음) → 휴지통(dba_recyclebin) 에 테이블과 인덱스가 이름을 바꿔 남아 있다.
    ② UPDATE 커밋 → 이전 값은 UNDO 세그먼트에 남아 있다. undo_retention(이 랩 900초)이 지나거나
    UNDO 공간이 부족하면 덮여 사라진다 → Flashback Query/Table 이 ORA-01555 로 실패한다.
    그래서 ②를 먼저 처리하는 것이 안전하다 (①은 휴지통이 지워지지 않는 한 급하지 않다).

【수행】

3-2.3 Flashback Drop  [검증됨]

  SYS@orcl> SELECT object_name, original_name, type, TO_CHAR(droptime) droptime
    2       FROM dba_recyclebin WHERE owner = 'HR';
  OBJECT_NAME                    ORIGINAL_NAME        TYPE     DROPTIME
  BIN$XA5x+I9YYg7gYzLhEKzJmw==$0 SYS_C007604          INDEX    2026-09-22:16:37:56
  BIN$XA5x+I9ZYg7gYzLhEKzJmw==$0 EXAM_ORDERS          TABLE    2026-09-22:16:37:56
  SYS@orcl> FLASHBACK TABLE hr.exam_orders TO BEFORE DROP;
  Flashback complete.
  SYS@orcl> SELECT COUNT(*) FROM hr.exam_orders;
        2000

3-2.4 Flashback Version Query / Flashback Query  [검증됨]

  SYS@orcl> SELECT versions_starttime, versions_operation op, price
    2       FROM hr.exam_items VERSIONS BETWEEN TIMESTAMP MINVALUE AND MAXVALUE
    3       WHERE item_id = 1 ORDER BY versions_startscn NULLS FIRST;
  VERSIONS_STARTTIME              O      PRICE
                                         677.42          ← 원래 값 (버전 시작 시각 없음 = 조회 범위 이전)
  22-SEP-26 04.37.59 PM           U          0           ← 16:37:59 의 UPDATE

  SYS@orcl> SELECT COUNT(*), SUM(CASE WHEN price = 0 THEN 1 END) zero_then
    2       FROM hr.exam_items AS OF TIMESTAMP TO_TIMESTAMP('2026-09-22 16:37:59','YYYY-MM-DD HH24:MI:SS');
        5000                                              ← 실수 직전 시점에는 price=0 인 행이 없다

  ▸ incident.txt 의 update_time 은 16:38:00 이고 실제 UPDATE 는 16:37:59 에 시작됐다.
    Version Query 로 확인한 시각(16:37:59) 직전을 되돌릴 시점으로 잡는다.

3-2.5 Flashback Table  [검증됨]

  SYS@orcl> FLASHBACK TABLE hr.exam_items TO TIMESTAMP TO_TIMESTAMP('2026-09-22 16:37:59','YYYY-MM-DD HH24:MI:SS');
  ORA-08189: cannot flashback the table because row movement is not enabled
  SYS@orcl> ALTER TABLE hr.exam_items ENABLE ROW MOVEMENT;
  Table altered.
  SYS@orcl> FLASHBACK TABLE hr.exam_items TO TIMESTAMP TO_TIMESTAMP('2026-09-22 16:37:59','YYYY-MM-DD HH24:MI:SS');
  Flashback complete.

  ▸ Flashback Table 은 행을 지우고 다시 넣는 방식이라 ROWID 가 바뀔 수 있다. ROWID 가 바뀌는
    것을 허용한다는 선언이 ENABLE ROW MOVEMENT 다. (ROWID 를 저장해 쓰는 응용이 있으면 위험하다)

【검증】

3-2.6 확인  [검증됨]

  SYS@orcl> SELECT COUNT(*), SUM(CASE WHEN price = 0 THEN 1 END) zero_price FROM hr.exam_items;
        5000                                              ← 0 원 행 없음
  SYS@orcl> SELECT COUNT(*) FROM hr.exam_orders;
        2000
  SYS@orcl> SELECT step FROM hr.exam_log WHERE step = 'S3-2b';
  S3-2b                                                   ← 다른 테이블의 정상 입력은 그대로

  ▸ Flashback Table 은 그 테이블의 행만 UNDO 로 되돌린다. 다른 테이블·리두·데이터파일은
    건드리지 않으므로 데이터베이스를 내리지 않고 그 테이블만 과거로 보낸다.

--------------------------------------------------------------------------------
 과제 3-3. TRUNCATE — Flashback 이 안 될 때, Data Pump 로 복원  [35점]
--------------------------------------------------------------------------------
【판정】

3-3.2 Flashback 시도  [검증됨]

  SYS@orcl> SELECT COUNT(*) FROM hr.exam_items AS OF TIMESTAMP TO_TIMESTAMP('2026-09-22 16:38:25','YYYY-MM-DD HH24:MI:SS');
  ORA-01466: unable to read data - table definition has changed
  SYS@orcl> FLASHBACK TABLE hr.exam_items TO TIMESTAMP TO_TIMESTAMP('2026-09-22 16:38:25','YYYY-MM-DD HH24:MI:SS');
  ORA-01466: unable to read data - table definition has changed

  ▸ DELETE 는 행마다 UNDO 를 남기는 DML 이라 되돌릴 수 있다. TRUNCATE 는 DDL 이다. 세그먼트의
    HWM 을 재설정하고 UNDO 를 남기지 않으며, 테이블 정의(데이터 객체 번호)가 바뀐다.
    Flashback 은 UNDO 로 과거를 재구성하므로 TRUNCATE 앞으로는 갈 수 없다.

3-3.3 남은 선택지

  ▸ Data Pump 논리백업(hr_exam.dmp, 16:26 시점) : 몇 분 안에 끝나고 자원이 거의 안 든다.
    손실 = 논리백업 이후 입력된 200 행.
  ▸ RMAN RECOVER TABLE ... UNTIL TIME '16:38:25' : 보조 인스턴스(SGA 2GB, 디스크 수 GB)를 띄워
    SYSTEM·UNDO·SYSAUX·exam_tbs 를 복원·복구한다. 16장 실습에서 약 10분. 손실 0.
  ▸ 결정 : 시험 시간과 자원 안에서 끝낼 수 있고 손실 200 행이 재입력 가능한 범위이면 Data Pump.
    손실이 허용되지 않으면 RECOVER TABLE. 어느 쪽이든 손실 범위를 보고하고 결정 근거를 적으면 정답.

【수행】

3-3.5 손실 보고  [검증됨]

  ▸ 손실 보고 : 논리백업(16:26:39) 이후 TRUNCATE(16:38:26) 까지 hr.exam_items 에 입력된 200 행

3-3.6 RECOVER TABLE 이었다면

  RMAN> RECOVER TABLE hr.exam_items
          UNTIL TIME "TO_DATE('2026-09-22 16:38:25','YYYY-MM-DD HH24:MI:SS')"
          AUXILIARY DESTINATION '/u02/aux'
          REMAP TABLE hr.exam_items:exam_items_rec;

  ▸ 필요한 것 : Level 0 + 그 뒤의 아카이브(있다), 보조 인스턴스용 메모리 약 2GB 와
    SYSTEM·SYSAUX·UNDO·exam_tbs 를 담을 디스크, 약 10분 (16-1 실측). REMAP TABLE 로 다른 이름으로
    들여온 뒤 200 행만 골라 원본에 넣으면 손실 0 이 된다.
