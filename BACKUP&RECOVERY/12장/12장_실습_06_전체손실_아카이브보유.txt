--------------------------------------------------------------------------------
[1] 시나리오 개요
--------------------------------------------------------------------------------
-- 데이터파일, 리두 로그, 컨트롤파일이 모두 사라졌다.
-- 백업본과 아카이브는 다른 디스크에 있어 온전하다.
-- 컨트롤파일을 재생성하고 전체 복원 후 아카이브를 적용한다.
-- 아카이브된 마지막 시퀀스까지 복구되며 CURRENT 구간만 손실된다.
-- 복구 유형 : 불완전 복구(UNTIL CANCEL), 마지막 스위치 이후 손실

--------------------------------------------------------------------------------

--------------------------------------------------------------------------------

SYS@orcl> SELECT file#, checkpoint_change#, fuzzy FROM v$datafile_header ORDER BY file#;

     FILE# CHECKPOINT_CHANGE# FUZ
---------- ------------------ ---
         1            2481200 YES
         3            2481240 YES
         4            2481260 YES
         7            2481210 YES

-- Hot Backup이므로 SCN이 파일마다 다르고 FUZZY가 YES다.
-- 아카이브를 적용해 일관성을 맞춰야 한다.

-- 컨트롤파일을 새로 만들었으므로 일반 복구를 시도해 본다.

SYS@orcl> RECOVER DATABASE;
ORA-00283: recovery session canceled due to errors
ORA-01610: recovery using the BACKUP CONTROLFILE option must be used

-- << 원인 파악 >>
-- 재생성한 컨트롤파일은 데이터파일의 최신 SCN 정보를 갖고 있지 않다.
-- 어디까지 복구해야 하는지 판단할 근거가 없으므로
-- USING BACKUP CONTROLFILE 로 그 판단을 사람에게 넘기라는 뜻이다.

-- << 수정 >>

SYS@orcl> SET AUTORECOVERY ON
SYS@orcl> RECOVER DATABASE USING BACKUP CONTROLFILE UNTIL CANCEL;
ORA-00279: change 2481200 generated at 05/13/2025 15:22:40 needed for thread 1
ORA-00289: suggestion : /u02/arch1/1_32_1190000001.dbf
Log applied.
ORA-00279: change 2483100 needed for thread 1
ORA-00289: suggestion : /u02/arch1/1_34_1190000001.dbf
Log applied.
ORA-00308: cannot open archived log '/u02/arch1/1_35_1190000001.dbf'
ORA-27037: unable to obtain file status

-- << 원인 파악 >>
-- 시퀀스 35는 아카이브되지 않은 CURRENT 그룹의 내용이다.
-- 온라인 리두도 함께 사라져 이 구간은 어디에도 없다.
-- 34까지 적용된 상태가 도달 가능한 최대치다.

-- << 수정 >> CANCEL로 마무리한다.

-- 실무 포인트
-- 1) 모든 파일이 사라져도 백업본과 아카이브가 있으면 복구는 성공한다.
--    손실은 마지막 아카이브 이후, 즉 CURRENT 구간뿐이다.
--    두 가지를 데이터 디스크와 분리해 두는 것이 이 결과를 만든다.
--
-- 2) 손실 범위는 로그 스위치 간격에 비례한다.
--    백업 스크립트 마지막에 ALTER SYSTEM ARCHIVE LOG CURRENT 를 넣어 두면
--    그 시점까지의 리두가 아카이브로 확보되어 손실 후보 구간이 줄어든다.
--
-- 3) 재생성한 컨트롤파일로 일반 RECOVER를 시도하면 ORA-01610이 나온다.
--    복구 한계를 판단할 근거가 컨트롤파일에 없기 때문이다.
--    USING BACKUP CONTROLFILE 로 그 판단을 사람이 맡는다.
--
-- 4) 마지막에 없는 시퀀스를 요구하면 CANCEL로 마무리한다.
--    ORA-00308은 오류가 아니라 도달 가능한 한계에 이르렀다는 신호다.
--
-- 5) 복구 후 SCN_TO_TIMESTAMP 로 복구 시점을 확인해 현업에 통보한다.
--    그 시각 이후의 업무가 재처리 대상이다.
--
-- 6) 전체 복원 후 일부 객체가 INVALID로 남을 수 있다.
--    compile_schema 또는 UTL_RECOMP 로 정리한 뒤 서비스를 재개한다.
