 과정      : Oracle Database 19c Backup & Recovery

--------------------------------------------------------------------------------
[1] 시나리오 개요
--------------------------------------------------------------------------------
-- 운영 중 로그 스위치가 멈추고 스위치를 기다리는 세션이 쌓인다.
-- 인스턴스는 살아 있고 OPEN 상태다.
-- 원인은 두 가지 중 하나다. 리두 파일 문제이거나 아카이브 대상 문제다.
-- 증상이 같아 원인을 먼저 확정해야 한다. 조치가 전혀 다르기 때문이다.
-- 복구 유형 : 원인별 대응, 손실 없음

SYS@orcl> !rm -f /u01/app/oracle/oradata/orcl/redo01.log /u02/oradata/orcl/redo01b.log

SYS@orcl> ALTER SYSTEM SWITCH LOGFILE;

-- 아직 아무 증상이 없다. 그룹 1 차례가 되었을 때 LGWR 는 열어 둔 핸들로 지워진 파일에
-- 그대로 썼고(11-3), 다음 스위치도 정상이다. 문제는 아카이버가 그룹 1 을 이름으로
-- 다시 열려 할 때부터다.

SYS@orcl> SELECT group#, sequence#, archived, status FROM v$log ORDER BY group#;

    GROUP#  SEQUENCE# ARC STATUS
---------- ---------- --- ----------------
         1          4 NO  ACTIVE
         3          5 NO  CURRENT
         4          3 YES ACTIVE

-- 그룹 1 의 시퀀스 4 가 ARCHIVED NO 로 남았다. 아카이브가 실패한 것이다.

SYS@orcl> ALTER SYSTEM SWITCH LOGFILE;
System altered.

SYS@orcl> ALTER SYSTEM SWITCH LOGFILE;
-- 응답이 없다. 다음 차례가 아카이브되지 않은 그룹 1 이라 스위치가 멈춘 것이다.
-- 세션이 멈춘 것처럼 보인다.

-- 판정
--   ① 원인 : 리두 파일 부재 (아카이브 대상 문제 아님)
--   ② 손상 그룹 : 1번, 상태 INACTIVE, ARCHIVED NO
--   ③ 멤버 : 전손
--   → 아카이브할 원본이 없으므로 CLEAR로 처리한다.

--------------------------------------------------------------------------------
[7] 복구 절차 : 오류 발생 → 원인 파악 → 수정
--------------------------------------------------------------------------------
-- 먼저 밀린 아카이브를 처리해 본다. 대상이 정상이므로 될 수도 있다.

SYS@orcl> ALTER SYSTEM ARCHIVE LOG ALL;
ALTER SYSTEM ARCHIVE LOG ALL
*
ERROR at line 1:

Linux-x86_64 Error: 2: No such file or directory
Additional information: 7
ORA-00312: online log 1 thread 1: '/u01/app/oracle/oradata/orcl/redo01.log'
ORA-27037: unable to obtain file status
Linux-x86_64 Error: 2: No such file or directory
Additional information: 7

-- << 원인 파악 >>
-- 아카이브 대상은 정상인데도 실패했다.
-- 아카이브할 원본 파일 자체가 없기 때문이다. 가장 오래된 그룹 1 에서 멈추므로
-- 뒤에 밀린 시퀀스 5 도 처리되지 않는다(10-7).
-- 이 두 확인으로 파일 부재가 원인임이 확정되었다.

-- 일반 CLEAR로 처리해 본다.

SYS@orcl> ALTER DATABASE CLEAR LOGFILE GROUP 1;
ALTER DATABASE CLEAR LOGFILE GROUP 1
*
ERROR at line 1:
ORA-00350: log 1 of instance orcl (thread 1) needs to be archived
ORA-00312: online log 1 thread 1: '/u01/app/oracle/oradata/orcl/redo01.log'
ORA-00312: online log 1 thread 1: '/u02/oradata/orcl/redo01b.log'

-- << 원인 파악 >>
-- ARCHIVED가 NO이므로 아직 아카이브되지 않은 그룹이다.
-- Oracle은 아카이브되지 않은 리두를 그냥 버리지 못하게 막는다.
-- 그러나 이 그룹은 파일이 없어 아카이브할 방법이 없다.
-- 위에서 두 가지를 확인했으므로 UNARCHIVED 옵션이 정당하다.

-- << 수정 >>

SYS@orcl> ALTER DATABASE CLEAR UNARCHIVED LOGFILE GROUP 1;

Database altered.

-- 그룹이 INACTIVE 라 바로 성공했다. 스위치 직후처럼 아직 ACTIVE 라면 ORA-01624 가
-- 나온다. 그때는 ALTER SYSTEM CHECKPOINT 로 INACTIVE 로 내린 뒤 다시 한다(10-7, 11-4).

-- 업무용 세션의 멈춰 있던 스위치가 그 순간 풀린다.

SYS@orcl> ALTER SYSTEM SWITCH LOGFILE;
System altered.

SYS@orcl> SELECT group#, sequence#, archived, status FROM v$log ORDER BY group#;

    GROUP#  SEQUENCE# ARC STATUS
---------- ---------- --- ----------------
         1          7 NO  CURRENT
         3          5 YES INACTIVE
         4          6 YES ACTIVE

-- 새로 만들어진 그룹 1 이 시퀀스 7 로 CURRENT 가 되었고,
-- 밀려 있던 5·6 은 아카이버가 즉시 처리해 YES 가 되었다.

-- 실무 포인트
-- 1) 정지 상태의 원인은 두 가지이며 증상이 같다.
--    리두 파일 문제라면 ORA-00312·00313이 나오고
--    아카이브 대상 문제라면 ORA-19504·19809 계열이 나온다.
--    alert log의 오류 코드로 먼저 구분한다.
--
-- 2) v$archive_dest 의 STATUS와 df 로 아카이브 대상을 확인한다.
--    VALID이고 공간이 충분하면 대상 문제가 아니다.
--
-- 3) 멤버가 지워져도 인스턴스는 바로 멈추지 않는다. LGWR 는 열어 둔 핸들로 계속 쓰고,
--    아카이버가 그 그룹을 이름으로 다시 열 때 실패한다. 아카이버는 시퀀스 순서로
--    처리하므로 한 그룹이 막히면 뒤 그룹도 밀리고, 다음 순환에서 스위치가 멈춘다.
--
-- 4) ORA-00350이 나오면 ARCHIVED가 NO인 이유를 확인한다.
--    대상 문제로 밀린 것이면 대상을 고쳐 처리하면 손실이 없다.
--    파일이 없어 아카이브할 수 없는 경우에만 UNARCHIVED가 정당하다.
--
-- 5) ORA-01624는 그룹이 ACTIVE라는 뜻이다.
--    ALTER SYSTEM CHECKPOINT 로 INACTIVE로 내린 뒤 CLEAR 한다.
--    ORA-00350과 ORA-01624는 원인이 다르므로 조치도 다르다.
--
-- 6) CLEAR UNARCHIVED 로 버려진 시퀀스는 아카이브 연속성을 끊는다.
--    그 이전 백업본으로는 이 지점을 넘어 복구할 수 없다.
--    수행 직후 반드시 전체 백업을 다시 받는다.
--
-- 7) 이 사례는 아카이브 대상 문제라면 조치가 전혀 달랐다.
--    대상을 고친 뒤 log_archive_dest_state_1=ENABLE 로 손실 없이 해결된다(11-4).
--    확인 없이 CLEAR UNARCHIVED 를 수행하면 불필요한 손실을 만든다.
