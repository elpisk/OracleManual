--------------------------------------------------------------------------------
[1] 시나리오 개요
--------------------------------------------------------------------------------
-- 정상 종료 상태에서 리두 로그 전부와 컨트롤파일 전부가 사라졌다.
-- 데이터파일은 온전하고 컨트롤파일 trace 백업이 있다.
-- 리두가 없으므로 NORESETLOGS 형식은 성립하지 않는다.
-- 정상 종료였다면 적용할 리두가 없어 데이터파일 복원조차 필요 없다.
-- 복구 유형 : 컨트롤파일 재생성(RESETLOGS 형식) 후 즉시 오픈, 손실 없음

[7] 복구 절차 : 오류 발생 → 원인 파악 → 수정
--------------------------------------------------------------------------------
-- NORESETLOGS 형식을 먼저 시도해 본다.

[oracle@oel7v9r1 ~]$ sed -n '41,95p' /home/oracle/backup/cf_ch12.sql \
>   > /home/oracle/backup/cf_ch12_noresetlogs.sql

SYS@orcl> @/home/oracle/backup/cf_ch12_noresetlogs.sql
CREATE CONTROLFILE REUSE DATABASE "ORCL" NORESETLOGS  ARCHIVELOG
*

ORA-01503: CREATE CONTROLFILE failed
ORA-01565: error in identifying file
'/u01/app/oracle/oradata/ORCL/redo01.log'
ORA-27037: unable to obtain file status

-- << 원인 파악 >>
-- NORESETLOGS 형식은 LOGFILE 절에 나열된 파일이 실제로 존재해야 한다.
-- 기존 리두를 그대로 인식시켜 연속성을 유지하는 형식이기 때문이다.
-- 리두가 전부 없어진 지금은 성립할 수 없다.
-- RESETLOGS 형식은 리두를 새로 만들어 인식시키므로 파일이 없어도 된다.

-- << 수정 >>

SYS@orcl> @/home/oracle/backup/cf_ch12_resetlogs.sql

Control file created.

-- 실무 포인트
-- 1) 손상 파일이 두 종류인데도 가장 간단하게 끝나는 조합이다.
--    복합 장애라고 해서 항상 복잡한 것은 아니다.
--    종료 방식이 결과를 가르는 결정적 변수다.
--
-- 2) 리두가 없으면 NORESETLOGS 형식은 ORA-01503과 ORA-01565로 실패한다.
--    LOGFILE 절의 파일이 실제로 있어야 하기 때문이다.
--    RESETLOGS 형식은 리두를 새로 만들므로 이 상황의 유일한 선택지다.
--
-- 3) 재생성 직후 v$datafile_header 의 FUZZY를 반드시 확인한다.
--    모두 NO면 적용할 리두가 없어 데이터파일 복원이 필요 없다.
--    YES가 있으면 백업본 복원과 아카이브 적용이 필요하다.
--
-- 4) 정상 종료 여부는 alert log의 CLOSE NORMAL 로 확인한다.
--    이 한 줄의 유무가 절차 전체를 바꾼다.
--
-- 5) 컨트롤파일 trace 백업은 구조 변경 시마다 다시 받는다.
--    구조가 바뀐 뒤의 trace가 없으면 재생성 문에 파일이 빠지고
--    그 파일은 UNNAMED로 등록되어 별도 보정이 필요해진다.
