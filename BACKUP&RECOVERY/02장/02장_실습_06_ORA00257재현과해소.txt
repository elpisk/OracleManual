================================================================================
 실습 2-6 : ORA-00257 재현과 해소
 과정      : Oracle Database 19c Backup & Recovery
 환경      : Oracle 19.3.0 / Oracle Linux 7 / non-CDB ORCL
 소요 시간 : 약 15분
================================================================================

--------------------------------------------------------------------------------
[1] 실습 개요
--------------------------------------------------------------------------------
-- 아카이브 대상 공간을 의도적으로 고갈시켜 데이터베이스가 멈추는 상황을 만든다.
-- ORA-00257 의 증상과 진단 절차, 세 가지 해소 방법을 확인한다.
-- 이 실습은 데이터베이스를 정지 상태로 만드므로 반드시 해소까지 마쳐야 한다.
-- 복구 유형 : 해당 없음(장애 재현과 구성 조치)

--------------------------------------------------------------------------------
[2] 사전 조건
--------------------------------------------------------------------------------
-- ARCHIVELOG 모드이고 LOG_ARCHIVE_DEST_1 이 MANDATORY 로 설정되어 있어야 한다.
-- 다른 사용자가 접속하지 않은 개별 실습 환경이어야 한다.
-- 공간 고갈을 손쉽게 재현하기 위해 작은 전용 파일시스템을 아카이브 대상으로 쓴다.

[oracle@oel7v9r1 ~]$ sudo mkdir -p /archsmall
[oracle@oel7v9r1 ~]$ sudo mount -t tmpfs -o size=30m tmpfs /archsmall
[oracle@oel7v9r1 ~]$ sudo chown oracle:oinstall /archsmall
[oracle@oel7v9r1 ~]$ df -h /archsmall
Filesystem      Size  Used Avail Use% Mounted on
tmpfs            30M     0   30M   0% /archsmall

-- 30MB 짜리 임시 파일시스템이다. 리두 로그가 10MB 이므로 세 번이면 가득 찬다.

[oracle@oel7v9r1 ~]$ sqlplus / as sysdba

[4] 작업 수행 : 공간 고갈 유발
--------------------------------------------------------------------------------
-- MANDATORY 대상을 작은 파일시스템으로 옮긴다.
-- 다른 대상은 잠시 비활성화해 고갈을 빨리 재현한다.

SYS@orcl> ALTER SYSTEM SET log_archive_dest_1 = 'location=/archsmall mandatory' SCOPE=both;
System altered.

SYS@orcl> ALTER SYSTEM SET log_archive_dest_2 = '' SCOPE=both;
System altered.

SYS@orcl> ALTER SYSTEM SET log_archive_dest_10 = '' SCOPE=both;
System altered.

SYS@orcl> SELECT dest_id, status, destination FROM v$archive_dest WHERE status <> 'INACTIVE';

   DEST_ID STATUS    DESTINATION
---------- --------- --------------------------
         1 VALID     /archsmall

[6] 해소 방법 1 : 공간 확보 (오류 → 원인 파악 → 수정)
--------------------------------------------------------------------------------
-- 먼저 아카이브를 강제로 재시도해 본다.

SYS@orcl> ALTER SYSTEM ARCHIVE LOG ALL;
ALTER SYSTEM ARCHIVE LOG ALL
*
ERROR at line 1:
ORA-16020: fewer destinations available than specified by
LOG_ARCHIVE_MIN_SUCCEED_DEST
ORA-16038: log 3 sequence# 34 cannot be archived
ORA-19502: write error on file ""
ORA-00312: online log 3 thread 1: '/u01/app/oracle/oradata/ORCL/redo03.log'

-- << 원인 파악 >>
-- 공간이 아직 그대로이므로 재시도해도 같은 지점에서 실패한다.
-- ARCHIVE LOG ALL 은 "밀린 것을 지금 처리하라"는 명령일 뿐 공간을 만들어 주지 않는다.
-- 순서가 잘못됐다. 공간을 먼저 확보하고 나서 재개시켜야 한다.

SYS@orcl> !df -h /archsmall
Filesystem      Size  Used Avail Use% Mounted on
tmpfs            30M   30M     0 100% /archsmall

-- << 수정 >>
-- 백업이 끝난 오래된 아카이브를 다른 위치로 옮겨 공간을 만든 뒤 재개시킨다.
-- 이 실습에서는 백업을 받지 않았으므로 학습 목적으로 이동만 한다.
-- 실무에서는 반드시 백업 완료를 확인한 뒤 옮기거나 지운다.

SYS@orcl> !mkdir -p /home/oracle/arch_old
SYS@orcl> !mv /archsmall/arch_1_33_1200525254.arc /home/oracle/arch_old/

SYS@orcl> !df -h /archsmall
Filesystem      Size  Used Avail Use% Mounted on
tmpfs            30M   20M   11M  66% /archsmall

SYS@orcl> ALTER SYSTEM ARCHIVE LOG ALL;

System altered.

SYS@orcl> SELECT dest_id, status, error FROM v$archive_dest WHERE dest_id = 1;

   DEST_ID STATUS    ERROR

[7] 해소 방법 2·3 과 원상 복구
--------------------------------------------------------------------------------
-- 방법 2 : FRA 를 쓰는 경우 상한을 늘린다.
--   SYS@orcl> ALTER SYSTEM SET db_recovery_file_dest_size = 20G SCOPE=both;
--   즉시 적용되며 재기동이 필요 없다. 단 실제 디스크에 여유가 있어야 한다.

-- 방법 3 : 대상을 여유 있는 경로로 즉시 변경한다. 가장 빠른 조치다.

SYS@orcl> ALTER SYSTEM SET log_archive_dest_1 = 'location=/home/oracle/arch1 mandatory' SCOPE=both;
System altered.

SYS@orcl> ALTER SYSTEM ARCHIVE LOG CURRENT;
System altered.

SYS@orcl> SELECT dest_id, status, destination, error FROM v$archive_dest WHERE dest_id = 1;

   DEST_ID STATUS    DESTINATION                ERROR
---------- --------- -------------------------- ----------------------------------------
         1 VALID     /home/oracle/arch1

-- 나머지 대상도 원래대로 되돌린다.

SYS@orcl> ALTER SYSTEM SET log_archive_dest_2 = 'location=/home/oracle/arch2 optional' SCOPE=both;
System altered.

SYS@orcl> ALTER SYSTEM SET log_archive_dest_10 = 'location=USE_DB_RECOVERY_FILE_DEST' SCOPE=both;
System altered.

SYS@orcl> SELECT dest_id, status, destination FROM v$archive_dest WHERE status <> 'INACTIVE';

   DEST_ID STATUS    DESTINATION
---------- --------- --------------------------
         1 VALID     /home/oracle/arch1
         2 VALID     /home/oracle/arch2
        10 VALID     USE_DB_RECOVERY_FILE_DEST

arch_1_34_1200525254.arc  arch_1_35_1200525254.arc  arch_1_36_1200525254.arc

[oracle@oel7v9r1 ~]$ sudo umount /archsmall
[oracle@oel7v9r1 ~]$ sudo rmdir /archsmall

-- /archsmall 에 있던 아카이브는 tmpfs 라 사라진다.
-- 다른 대상(arch1, arch2, FRA)에는 남아 있지 않은 구간이므로,
-- 실습 후에는 전체 백업을 새로 받아 기준점을 다시 세우는 것이 좋다.

--------------------------------------------------------------------------------
[8] 실무 포인트
--------------------------------------------------------------------------------
-- 1) 증상 순서를 기억한다.
--    alert log 에 Archival stopped 기록 → 새 접속·DML 대기 → ORA-00257 반환.
--    사용자는 "DB 가 멈췄다"고만 신고하므로 SYSDBA 로 접속해 v$archive_dest 를 보는 것이 첫 단계다.
--
-- 2) Oracle 은 아카이브되지 않은 리두를 절대 덮어쓰지 않는다.
--    복구 재료가 사라지기 때문이며, 그래서 멈추는 쪽을 택한다.
--    "왜 그냥 덮어쓰지 않느냐"는 질문의 답이 여기 있다.
--
-- 3) 세 가지 해소 방법 중 대상 변경이 가장 빠르지만 아카이브가 여러 경로에 흩어진다.
--    복구 시 두 곳을 모두 뒤져야 하므로 어디로 옮겼는지 반드시 기록한다.
--
-- 4) 발생한 뒤에는 이미 서비스가 멈춘 상태이므로 대응 시간이 곧 장애 시간이다.
--    예방이 유일한 실질 대책이며, FRA 85% 경고 모니터링과 정기 정리 자동화가 그 수단이다.
--
-- 5) 아카이브 삭제를 자동화할 때는 백업 성공 여부를 반드시 조건으로 건다.
--    "백업 → 삭제"를 무조건 이어 붙이면 백업이 실패해도 삭제만 실행되어 아카이브를 잃는다.
