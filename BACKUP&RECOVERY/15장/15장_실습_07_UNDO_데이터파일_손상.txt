 실습 15-7 : UNDO 데이터파일 손상 복구
 과정      : Oracle Database 19c Backup & Recovery
 환경      : Oracle 19.3.0 / Oracle Linux 7 / non-CDB ORCL / ARCHIVELOG
 소요 시간 : 약 30분

--------------------------------------------------------------------------------
[1] 시나리오 개요
--------------------------------------------------------------------------------
-- UNDO 테이블스페이스의 데이터파일이 손상되었다.
-- UNDO는 활성 트랜잭션의 되돌리기 정보를 담고 있어 OFFLINE으로 내릴 수 없다.
-- 전면 중단 후 MOUNT 상태에서 복구한다.
-- 9장의 UNDO 손상 판단이 RMAN에서도 그대로 적용됨을 확인한다.
-- 복구 유형 : 완전 복구, 전면 중단, 손실 없음

[4] 장애 유발 : UNDO 데이터파일 삭제

ERROR at line 1:
ORA-01552: cannot use system rollback segment for non-system tablespace 'USERS'

-- << 원인 파악 >>
-- [7] 에서 내린 OFFLINE 표시가 남아 있다. 복원·복구가 끝나도 상태는 저절로 돌아오지 않고,
-- UNDO 파일이 OFFLINE 인 채로 데이터베이스가 열린다. 그러면 UNDO 세그먼트를 못 써서
-- 모든 DML 이 ORA-01552 로 막힌다. 파일을 OFFLINE 했다면 반드시 되돌린다.

SYS@orcl> ALTER DATABASE DATAFILE 4 ONLINE;

Database altered.

SYS@orcl> INSERT INTO hr.rec157 VALUES (3, 'after recover');
SYS@orcl> COMMIT;

Commit complete.

-- DML이 정상적으로 진행된다. UNDO가 복구되었다.

SYS@orcl> SELECT id, memo FROM hr.rec157 ORDER BY id;

        ID MEMO
---------- ------------------------------
         1 committed
         2 in current redo
         3 after recover

SYS@orcl> SELECT status, COUNT(*) FROM dba_rollback_segs
  2  WHERE  tablespace_name = 'UNDOTBS1' GROUP BY status;

STATUS             COUNT(*)
---------------- ----------
NEEDS RECOVERY           10
ONLINE                    1

-- OFFLINE 이었던 사이에 세그먼트가 NEEDS RECOVERY 로 남았다. 새 DML 은 ONLINE 세그먼트
-- 하나로 처리되지만 정상 상태가 아니다. 재기동하면 Undo 초기화가 모두 되돌린다.

SYS@orcl> SHUTDOWN IMMEDIATE
SYS@orcl> STARTUP

SYS@orcl> SELECT status, COUNT(*) FROM dba_rollback_segs
  2  WHERE  tablespace_name = 'UNDOTBS1' GROUP BY status;

STATUS             COUNT(*)
---------------- ----------
ONLINE                   10
OFFLINE                   1

-- UNDO 세그먼트가 정상 상태다(OFFLINE 하나는 예비 세그먼트).

SYS@orcl> SELECT COUNT(*) FROM v$transaction;

  COUNT(*)
----------
         0

SYS@orcl> EXIT

[oracle@oel7v9 ~]$ rman target / catalog rcatowner@rcat
RMAN> BACKUP DATABASE TAG 'AFTER_UNDO' PLUS ARCHIVELOG;
RMAN> EXIT

-- 실무 포인트
-- 1) UNDO 테이블스페이스는 OFFLINE으로 내릴 수 없다.
--    ORA-30042가 그 사실을 명시적으로 알려 준다.
--    SYSTEM과 함께 무중단 복구가 불가능한 두 대상이다.
--
-- 2) 데이터파일 단위 OFFLINE 명령은 적용되지만 해결책이 아니다.
--    그 세션이 ORA-00603 으로 죽고 모든 DML 이 ORA-00376 으로 막히며 정상 종료도 안 된다.
--    복구 뒤에도 OFFLINE 표시가 남아 ORA-01552 를 만든다. 쓰지 않는다.
--
-- 3) 올바른 절차는 SHUTDOWN ABORT → STARTUP MOUNT → RESTORE → RECOVER → OPEN 이다.
--    파일을 OFFLINE 한 적이 있다면 OPEN 뒤 ONLINE 으로 되돌리고 재기동해 세그먼트를 정리한다.
--
-- 4) UNDO 손상은 새 세션의 DML을 즉시 막는다.
--    조회와 이미 파일을 연 세션은 잠시 동작할 수 있어 장애를 늦게 인지하는 경우가 있다.
--
-- 5) 9장의 판단이 그대로 적용된다.
--    도구가 RMAN으로 바뀌어도 UNDO의 성격은 변하지 않는다.
--    판정 흐름은 같고 명령만 짧아진다.
--
-- 6) 복구 후 UNDO 세그먼트 상태를 확인한다.
--    dba_rollback_segs 의 STATUS가 ONLINE이어야 정상이다. NEEDS RECOVERY 가 남으면 재기동한다.
--
-- 7) UNDO 데이터파일도 다중화 대상은 아니지만 백업 주기는 짧게 가져간다.
--    손상 시 전면 중단이므로 복원 시간이 그대로 중단 시간이 된다.
