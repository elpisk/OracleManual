================================================================================
 실습 15-7 : UNDO 데이터파일 손상 복구
 과정      : Oracle Database 19c Backup & Recovery
 환경      : Oracle 19.3.0 / Oracle Linux 7 / non-CDB ORCL / ARCHIVELOG
 소요 시간 : 약 30분
================================================================================

--------------------------------------------------------------------------------
[1] 시나리오 개요
--------------------------------------------------------------------------------
-- UNDO 테이블스페이스의 데이터파일이 손상되었다.
-- UNDO는 활성 트랜잭션의 되돌리기 정보를 담고 있어 OFFLINE으로 내릴 수 없다.
-- 전면 중단 후 MOUNT 상태에서 복구한다.
-- 9장의 UNDO 손상 판단이 RMAN에서도 그대로 적용됨을 확인한다.
-- 복구 유형 : 완전 복구, 전면 중단, 손실 없음

--------------------------------------------------------------------------------
[2] 사전 조건
--------------------------------------------------------------------------------
-- 실습 15-6까지 완료되어 있어야 한다.

[oracle@oel7v9r1 ~]$ rman target / catalog rcatowner@rcat

RMAN> BACKUP DATABASE PLUS ARCHIVELOG TAG 'BASE_157';
RMAN> EXIT

-- 판정
--   ① 손상 파일 : 4번, UNDO 테이블스페이스
--   ② UNDO는 OFFLINE 불가 → 전면 중단 확정
--   ③ 백업과 아카이브 있음 → 완전 복구 가능
--   → MOUNT 상태에서 복구한다.

-- 9장의 판단과 같다. 도구가 바뀌어도 이 판정은 변하지 않는다.

--------------------------------------------------------------------------------
[7] 복구 절차 : 오류 발생 → 원인 파악 → 수정
--------------------------------------------------------------------------------
-- 무중단 복구를 시도해 본다.

SYS@orcl> EXIT
[oracle@oel7v9r1 ~]$ rman target / catalog rcatowner@rcat

RMAN> SQL 'ALTER TABLESPACE undotbs1 OFFLINE IMMEDIATE';

RMAN-00571: ===========================================================
RMAN-00569: =============== ERROR MESSAGE STACK FOLLOWS ===============
RMAN-00571: ===========================================================
RMAN-03009: failure of sql command on default channel at 05/16/2025 16:02:41
ORA-30042: Cannot offline the undo tablespace

-- << 원인 파악 >>
-- ORA-30042는 UNDO 테이블스페이스를 OFFLINE으로 내릴 수 없다는 뜻이다.
-- 활성 트랜잭션의 되돌리기 정보가 들어 있어 데이터베이스가 그것을 놓을 수 없다.
-- SYSTEM과 함께 무중단 복구가 불가능한 두 대상이다.

-- 데이터파일 단위로도 시도해 본다.

RMAN> SQL 'ALTER DATABASE DATAFILE 4 OFFLINE';

sql statement: ALTER DATABASE DATAFILE 4 OFFLINE

-- 명령은 통과한다. 하지만 이 상태로는 문제가 남는다.

RMAN> SQL 'SELECT COUNT(*) FROM v$transaction';

-- 활성 트랜잭션이 그 UNDO 세그먼트를 참조하면 되돌릴 수 없다.
-- 데이터베이스를 열어 둔 채로는 정합성을 보장할 수 없으므로
-- UNDO는 MOUNT 상태에서 복구하는 것이 원칙이다.

-- << 수정 >> 전면 중단 후 MOUNT 상태에서 복구한다.

RMAN> SHUTDOWN IMMEDIATE

database closed
database dismounted
Oracle instance shut down

RMAN> STARTUP MOUNT

Oracle instance started
database mounted

RMAN> SQL 'ALTER DATABASE DATAFILE 4 ONLINE';

sql statement: ALTER DATABASE DATAFILE 4 ONLINE

-- MOUNT 상태이므로 ONLINE으로 되돌려도 접근이 일어나지 않는다.

RMAN> RESTORE DATAFILE 4;

Starting restore at 16-MAY-25

channel ORA_DISK_1: restore complete, elapsed time: 00:00:18
Finished restore at 16-MAY-25

RMAN> RECOVER DATAFILE 4;

[oracle@oel7v9r1 ~]$ rman target / catalog rcatowner@rcat
RMAN> BACKUP DATABASE PLUS ARCHIVELOG TAG 'AFTER_UNDO';
RMAN> EXIT

-- 실무 포인트
-- 1) UNDO 테이블스페이스는 OFFLINE으로 내릴 수 없다.
--    ORA-30042가 그 사실을 명시적으로 알려 준다.
--    SYSTEM과 함께 무중단 복구가 불가능한 두 대상이다.
--
-- 2) 데이터파일 단위 OFFLINE 명령은 통과하지만 해결책이 아니다.
--    활성 트랜잭션이 그 UNDO 세그먼트를 참조하면 정합성을 보장할 수 없다.
--    MOUNT 상태에서 복구하는 것이 원칙이다.
--
-- 3) UNDO 손상은 DML을 즉시 막는다.
--    조회는 버퍼에 있는 블록을 읽는 동안 잠시 동작할 수 있어
--    장애를 늦게 인지하는 경우가 있다.
--
-- 4) 9장의 판단이 그대로 적용된다.
--    도구가 RMAN으로 바뀌어도 UNDO의 성격은 변하지 않는다.
--    판정 흐름은 같고 명령만 짧아진다.
--
-- 5) 복구 후 UNDO 세그먼트 상태를 확인한다.
--    dba_rollback_segs 의 STATUS가 ONLINE이어야 정상이다.
--
-- 6) UNDO 데이터파일도 다중화 대상은 아니지만 백업 주기는 짧게 가져간다.
--    손상 시 전면 중단이므로 복원 시간이 그대로 중단 시간이 된다.
