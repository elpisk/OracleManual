================================================================================
 실습 13-5 : Retention Policy 설정과 REPORT / DELETE OBSOLETE
 과정      : Oracle Database 19c Backup & Recovery
 환경      : Oracle 19.3.0 / Oracle Linux 7 / non-CDB ORCL + RCAT
 소요 시간 : 약 30분
================================================================================

--------------------------------------------------------------------------------
[1] 시나리오 개요
--------------------------------------------------------------------------------
-- 같은 백업 세트에 두 보존 정책을 적용해 판정 결과를 비교한다.
-- REDUNDANCY는 개수 기준, RECOVERY WINDOW는 시점 기준이다.
-- 정책은 판정 기준일 뿐이며 DELETE를 수행해야 실제로 지워진다.
-- 기록 수명이 정책보다 짧을 때 생기는 문제도 확인한다.
-- 작업 유형 : 운영 관리(장애 복구 아님)

--------------------------------------------------------------------------------
[2] 사전 조건
--------------------------------------------------------------------------------
-- 실습 13-4까지 완료되어 설정이 적용되어 있어야 한다.
-- 백업을 세 번 받아 비교 대상을 만든다.

[oracle@oel7v9r1 ~]$ rman target / catalog rcatowner@rcat

RMAN> SHOW RETENTION POLICY;

CONFIGURE RETENTION POLICY TO RECOVERY WINDOW OF 7 DAYS;

RMAN> CONFIGURE RETENTION POLICY TO RECOVERY WINDOW OF 7;

RMAN-00571: ===========================================================

RMAN-00571: ===========================================================
RMAN-00558: error encountered while parsing input commands
RMAN-01009: syntax error: found "end-of-file": expecting one of: "days"
RMAN-01007: at line 1 column 52 file: standard input

-- << 원인 파악 >>
-- RECOVERY WINDOW OF 뒤에는 숫자와 DAYS 키워드가 함께 와야 한다.
-- RMAN-01009가 기대하는 키워드를 알려 준다.

-- << 수정 >>

RMAN> CONFIGURE RETENTION POLICY TO RECOVERY WINDOW OF 7 DAYS;

new RMAN configuration parameters are successfully stored

-- 이번에는 기록 수명 문제를 재현해 본다.

RMAN> EXIT

[oracle@oel7v9r1 ~]$ sqlplus / as sysdba

SYS@orcl> ALTER SYSTEM SET control_file_record_keep_time = 1 SCOPE = BOTH;

System altered.

-- 보존 정책 7일보다 짧은 1일로 줄였다.
-- 이 상태로 며칠이 지나면 기록이 먼저 사라진다.

SYS@orcl> SELECT type, records_total, records_used
  2  FROM   v$controlfile_record_section WHERE type = 'BACKUP PIECE';

TYPE                 RECORDS_TOTAL RECORDS_USED
-------------------- ------------- ------------
BACKUP PIECE                  1004            9

-- << 원인 파악 >>
-- 기록 수명이 지나면 이 영역의 오래된 항목이 새 기록으로 덮인다.
-- 백업 파일이 남아 있어도 RMAN이 존재를 모르게 되어
-- DELETE OBSOLETE 가 삭제 대상을 찾지 못하고 파일만 쌓인다.

-- << 수정 >>

SYS@orcl> ALTER SYSTEM SET control_file_record_keep_time = 31 SCOPE = BOTH;

System altered.

-- 보존 정책 기간보다 크게 되돌린다.
-- 카탈로그를 쓰면 이 제약에서 벗어나지만 컨트롤파일 기록도 맞춰 두는 편이 좋다.

-- 실무 포인트
-- 1) 같은 백업 세트라도 정책에 따라 판정이 전혀 다르다.
--    REDUNDANCY 2에서는 세 개가 obsolete였지만 7일 윈도우에서는 하나도 없었다.
--    정책은 복구 요건을 표현하는 것이므로 요건 문서와 대응시켜 정한다.
--
-- 2) 보존 정책은 판정 기준일 뿐 자동으로 지우지 않는다.
--    DELETE OBSOLETE 를 정기 작업에 넣어야 실제로 공간이 확보된다.
--    FRA를 쓰는 경우에만 공간 압박 시 자동 삭제가 일어난다.
--
-- 3) 삭제 전에 REPORT OBSOLETE 로 목록을 확인하고 로그로 남긴다.
--    배치에서는 NOPROMPT를 붙이되 대화형에서는 붙이지 않는 편이 안전하다.
--
-- 4) REPORT NEED BACKUP 이 비어 있어야 정책이 충족된 상태다.
--    이 명령을 정기 점검 항목으로 넣어 두면 백업 누락을 조기에 발견한다.
--
-- 5) 기록 수명이 보존 정책보다 짧으면 삭제 대상을 찾지 못한다.
--    백업 파일만 쌓이므로 두 값을 함께 확인한다.
--    이미 기록을 잃은 파일은 CATALOG START WITH 로 되살릴 수 있다.
--
-- 6) 구문 오류는 RMAN-01009가 기대하는 키워드를 알려 준다.
--    RECOVERY WINDOW OF 뒤에는 숫자와 DAYS가 모두 필요하다.
