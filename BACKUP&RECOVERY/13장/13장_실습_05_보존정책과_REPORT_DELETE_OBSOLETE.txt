 실습 13-5 : Retention Policy 설정과 REPORT / DELETE OBSOLETE
 과정      : Oracle Database 19c Backup & Recovery
 환경      : Oracle 19.3.0 / Oracle Linux 7 / non-CDB ORCL + RCAT / ARCHIVELOG
 소요 시간 : 약 30분

--------------------------------------------------------------------------------
[1] 시나리오 개요
--------------------------------------------------------------------------------
-- 같은 백업 세트에 두 보존 정책을 적용해 판정 결과를 비교한다.
-- REDUNDANCY는 개수 기준, RECOVERY WINDOW는 시점 기준이다.
-- 정책은 판정 기준일 뿐이며 DELETE를 수행해야 실제로 지워진다.
-- 기록 수명이 정책보다 짧을 때 생기는 문제도 확인한다.
-- 작업 유형 : 운영 관리(장애 복구 아님)

--------------------------------------------------------------------------------

-- 실무 포인트
-- 1) 같은 백업 세트라도 정책에 따라 판정이 전혀 다르다.
--    REDUNDANCY 2에서는 열두 세트가 obsolete였지만 7일 윈도우에서는 하나도 없었다.
--    정책은 복구 요건을 표현하는 것이므로 요건 문서와 대응시켜 정한다.
--
-- 2) 보존 정책은 판정 기준일 뿐 자동으로 지우지 않는다.
--    DELETE OBSOLETE 를 정기 작업에 넣어야 실제로 공간이 확보된다.
--    FRA를 쓰는 경우에만 공간 압박 시 자동 삭제가 일어난다.
--
-- 3) 컨트롤파일 자동 백업도 같은 정책으로 판정된다.
--    백업마다 하나씩 따라오므로 데이터파일 백업 수만큼 쌓이고 같이 정리된다.
--
-- 4) 삭제 전에 REPORT OBSOLETE 로 목록을 확인하고 로그로 남긴다.
--    배치에서는 NOPROMPT를 붙이되 대화형에서는 붙이지 않는 편이 안전하다.
--
-- 5) REPORT NEED BACKUP 이 비어 있어야 정책이 충족된 상태다.
--    이 명령을 정기 점검 항목으로 넣어 두면 백업 누락을 조기에 발견한다.
--
-- 6) 기록 수명이 보존 정책보다 짧으면 삭제 대상을 찾지 못한다.
--    백업 파일만 쌓이므로 두 값을 함께 확인한다.
--    이미 기록을 잃은 파일은 CATALOG START WITH 로 되살릴 수 있다.
--
-- 7) 구문 오류는 RMAN-01009가 기대하는 키워드를 알려 준다.
--    RECOVERY WINDOW OF 뒤에는 숫자와 DAYS가 모두 필요하다.
