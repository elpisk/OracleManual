================================================================================
 실습 7-2 : 비정상 종료 후 리두 로그와 컨트롤파일 동시 손상
 과정      : Oracle Database 19c Backup & Recovery
 환경      : Oracle 19.3.0 / Oracle Linux 7 / non-CDB ORCL / NOARCHIVELOG
 소요 시간 : 약 25분
================================================================================

--------------------------------------------------------------------------------
[1] 시나리오 개요
--------------------------------------------------------------------------------
-- SHUTDOWN ABORT 뒤 리두 로그 전부와 컨트롤파일 전부가 유실되었다.
-- 데이터파일에 반영되지 않은 커밋 변경이 있는데 그 리두가 사라졌다.
-- 불완전 복구를 시도하고 실패하면 전체 복원으로 전환한다.
-- 실습 7-1과 같은 장애이지만 종료 방식 하나로 결과가 달라진다.
-- 복구 유형 : 불완전 복구 또는 전체 복원

--------------------------------------------------------------------------------
[2] 사전 조건
--------------------------------------------------------------------------------
-- 실습 7-1을 마친 상태에서 이어서 진행한다.
-- /home/oracle/backup/ch07 백업본이 온전해야 한다.

[oracle@oel7v9r1 ~]$ ls /home/oracle/backup/ch07/ | wc -l
14

[oracle@oel7v9r1 ~]$ sqlplus / as sysdba

SYS@orcl> SET LINESIZE 200
SYS@orcl> COL name FOR a48

--------------------------------------------------------------------------------
[4] 장애 유발 : ABORT 후 리두·컨트롤파일 삭제
--------------------------------------------------------------------------------

SYS@orcl> COMMIT;
Commit complete.

-- 커밋되었으나 데이터파일에는 아직 반영되지 않았다.

SYS@orcl> SHUTDOWN ABORT

SYS@orcl> !rm -f /u01/app/oracle/oradata/ORCL/*.log /u02/oradata/ORCL/*.log

--------------------------------------------------------------------------------
[6] 진단
--------------------------------------------------------------------------------
-- 판정
--   ① 컨트롤파일 : trace 있음
--   ② 리두 로그 : 전부 없음 → RESETLOGS 형식 필수
--   ③ 종료 : abort → 적용해야 할 리두가 있는데 그 리두가 사라짐
--   → 불완전 복구 시도, 실패 시 전체 복원

SYS@orcl> !ls /u01/app/oracle/oradata/ORCL/*.dbf | grep -v temp | wc -l
5

SYS@orcl> !mkdir -p /home/oracle/before_recover_72
SYS@orcl> !cp -p /u01/app/oracle/oradata/ORCL/*.dbf /home/oracle/before_recover_72/

-- 시도가 실패하면 이 사본으로 되돌린다.

-- 적용되지 않은 리두가 있는데 그 리두가 사라졌다.
-- 새로 만든 리두 로그는 비어 있으므로 적용할 내용이 없다.
-- 데이터파일은 일관성 없는 상태로 남아 있어 그대로 열 수 없다.
-- 실습 7-1에서는 FUZZY가 NO였기에 이 오류가 나오지 않았다.

-- 전체 복원으로 전환한다.

                 /home/oracle/backup/ch07/redo04.log /u01/app/oracle/oradata/ORCL/
SYS@orcl> !cp -p /home/oracle/backup/ch07/redo01b.log /home/oracle/backup/ch07/redo03b.log \

-- 복구 명령 없이 열렸다. 일관성 있는 상태 전체를 되돌렸기 때문이다.

-- 전체 복원은 백업 시점의 컨트롤파일을 되돌렸으므로 인카네이션이 늘지 않았다.

SYS@orcl> UPDATE hr.employees SET salary = salary WHERE ROWNUM = 1;
1 row updated.
SYS@orcl> ROLLBACK;
Rollback complete.

-- DML이 정상 동작한다.

-- 실무 포인트
-- 1) 같은 장애라도 종료 방식 하나로 결과가 완전히 달라진다.
--    실습 7-1은 손실이 없었고 이 실습은 백업 이후 전량을 잃었다.
--    차이는 FUZZY 컬럼에서 그대로 드러난다.
--
-- 2) 리두가 하나도 없으면 불완전 복구조차 성립하지 않는다.
--    적용할 리두가 없어 데이터파일의 일관성을 맞출 수 없기 때문이다.
--    ORA-01194가 그 상태를 알려 준다.
--
-- 3) ORA-01547의 "RECOVER succeeded" 문구에 속지 않는다.
--    이어지는 ORA-01194가 미완료를 알리고 OPEN에서 ORA-01113이 다시 나온다.
--
-- 4) 전환 시점을 미리 정해 둔다.
--    이 상황에서 여러 조합을 반복 시도해도 결과는 같다.
--    판정에서 리두 부족이 확인되면 즉시 전체 복원으로 방향을 정하는 편이 낫다.
--
-- 5) 시도 전 사본을 확보했기 때문에 여러 방법을 시험할 수 있었다.
--    before_recover_72 디렉터리가 없었다면 첫 시도의 결과가 그대로 최종 상태가 된다.
--
-- 6) 근본 원인은 배치다. 리두 로그와 컨트롤파일이 같은 디스크에 있었다.
--    2장의 배치 원칙을 지켰다면 사본이 남아 이 상황 자체가 발생하지 않았다.

SYS@orcl> EXIT
