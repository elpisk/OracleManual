 실습 7-5 : INACTIVE 로그 파일 삭제 후 비정상 종료
 과정      : Oracle Database 19c Backup & Recovery
 환경      : Oracle 19.3.0 / Oracle Linux 7 / non-CDB ORCL / NOARCHIVELOG
 소요 시간 : 약 20분
================================================================================

--------------------------------------------------------------------------------
[1] 시나리오 개요
--------------------------------------------------------------------------------
-- 리두 로그 그룹 하나가 전손된 상태에서 인스턴스가 ABORT로 멈췄다.
-- 인스턴스 복구가 필요한 상황이라 CLEAR가 거부될 수 있다.
-- ORA-01624와 UNARCHIVED 옵션의 필요성을 실제로 확인한다.
-- 실습 7-4와 같은 장애이지만 종료 방식이 결과를 바꾼다.
-- 복구 유형 : 완전 복구 또는 불완전 복구(상황에 따라)

--------------------------------------------------------------------------------

[6] 진단
--------------------------------------------------------------------------------
SYS@orcl> SELECT group#, sequence#, status FROM v$log ORDER BY group#;

    GROUP#  SEQUENCE# STATUS
---------- ---------- ----------------
         1          9 INACTIVE
         3          7 INACTIVE
         4          8 CURRENT

-- 손상된 그룹 3은 여전히 INACTIVE다.
-- 인스턴스 복구에 실제로 필요한 것은 CURRENT인 그룹 4다.

SYS@orcl> SELECT group#, member, status FROM v$logfile ORDER BY group#;

    GROUP# MEMBER                                       STATUS
---------- -------------------------------------------- -------
         1 /u01/app/oracle/oradata/ORCL/redo01.log
         1 /u02/oradata/ORCL/redo01b.log
         3 /u01/app/oracle/oradata/ORCL/redo03.log      INVALID
         3 /u02/oradata/ORCL/redo03b.log                INVALID
         4 /u01/app/oracle/oradata/ORCL/redo04.log
         4 /u02/oradata/ORCL/redo04b.log

6 rows selected.

-- 그룹 4의 멤버는 온전하다. 인스턴스 복구 재료가 살아 있다.

SYS@orcl> SELECT * FROM v$recover_file;

no rows selected

-- 판정
--   ① 멤버 : 그룹 3만 전손, CURRENT 그룹은 온전
--   ② 그룹 상태 : 손상 그룹이 INACTIVE
--   ③ 종료 : abort → 인스턴스 복구 필요, 다만 필요한 그룹은 4번
--   → CLEAR LOGFILE GROUP 3 후 OPEN. 손실 없이 처리 가능할 것으로 예상.

SYS@orcl> !mkdir -p /home/oracle/before_recover_75
SYS@orcl> !cp -p /u01/app/oracle/oradata/ORCL/*.ctl \
                 /u01/app/oracle/oradata/ORCL/*.log /home/oracle/before_recover_75/

--------------------------------------------------------------------------------
[7] 복구 절차 : 오류 발생 → 원인 파악 → 수정
--------------------------------------------------------------------------------
-- 손상되지 않은 그룹까지 함께 CLEAR 해 본다(잘못된 접근).

SYS@orcl> ALTER DATABASE CLEAR LOGFILE GROUP 4;
ALTER DATABASE CLEAR LOGFILE GROUP 4
*
ERROR at line 1:
ORA-01624: log 4 needed for crash recovery of instance orcl (thread 1)
ORA-00312: online log 4 thread 1: '/u01/app/oracle/oradata/ORCL/redo04.log'

-- << 원인 파악 >>
-- 그룹 4는 CURRENT이며 인스턴스 복구에 필요한 리두를 담고 있다.
-- Oracle이 이를 거부한 것은 손실을 막아 준 것이다.
-- 여기서 UNARCHIVED 옵션을 붙여 강제로 비우면 명령은 성공하지만
-- 커밋된 변경을 스스로 버리게 된다.
-- 애초에 그룹 4는 손상되지 않았으므로 CLEAR 대상이 아니다.
-- 대상은 실제로 손상된 그룹 3뿐이다.

SYS@orcl> SELECT group#, status FROM v$log WHERE group# = 4;

    GROUP# STATUS
---------- ----------------
         4 CURRENT

-- << 수정 >>
-- 손상된 그룹만 CLEAR 한다.

SYS@orcl> ALTER DATABASE CLEAR LOGFILE GROUP 3;

Database altered.

SYS@orcl> SELECT group#, sequence#, status FROM v$log WHERE group# = 3;

    GROUP#  SEQUENCE# STATUS
---------- ---------- ----------------
         3          0 UNUSED

SYS@orcl> SELECT member, status FROM v$logfile WHERE group# = 3;

MEMBER                                       STATUS
-------------------------------------------- -------
/u01/app/oracle/oradata/ORCL/redo03.log
/u02/oradata/ORCL/redo03b.log

SYS@orcl> ALTER DATABASE OPEN;

Database altered.

SYS@orcl> !tail -5 /u01/app/oracle/diag/rdbms/orcl/orcl/trace/alert_orcl.log
Beginning crash recovery of 1 threads
Started redo scan
Completed redo application of 0.14MB
Completed crash recovery at
Completed: ALTER DATABASE OPEN

-- 인스턴스 복구가 그룹 4의 리두로 정상 완료되었다.

--------------------------------------------------------------------------------
[8] 검증 및 실무 포인트
--------------------------------------------------------------------------------
SYS@orcl> SELECT * FROM hr.emp75 ORDER BY id;

        ID MEMO
---------- ------------------------------
         1 committed early
         2 in current redo

-- CURRENT 리두에만 있던 2번 행까지 살아났다. 손실이 없다.

SYS@orcl> SELECT * FROM v$recover_file;

no rows selected

SYS@orcl> SELECT incarnation#, resetlogs_change#, status FROM v$database_incarnation
  2  WHERE  status = 'CURRENT';

INCARNATION# RESETLOGS_CHANGE# STATUS
------------ ----------------- -------
           6           2393981 CURRENT

-- 인카네이션이 올라가지 않았다. RESETLOGS를 쓰지 않았기 때문이다.

SYS@orcl> SELECT group#, sequence#, status FROM v$log ORDER BY group#;

    GROUP#  SEQUENCE# STATUS
---------- ---------- ----------------
         1          9 INACTIVE
         3          0 UNUSED
         4         10 CURRENT

SYS@orcl> ALTER SYSTEM SWITCH LOGFILE;
SYS@orcl> ALTER SYSTEM SWITCH LOGFILE;
SYS@orcl> SELECT group#, sequence#, status FROM v$log ORDER BY group#;

    GROUP#  SEQUENCE# STATUS
---------- ---------- ----------------
         1         12 CURRENT
         3         11 ACTIVE
         4         10 INACTIVE

-- 그룹 3이 순환에 복귀했다.

-- 실무 포인트
-- 1) 손상되지 않은 그룹을 CLEAR 하려 하지 않는다.
--    ORA-01624는 오류가 아니라 Oracle이 손실을 막아 준 것이다.
--    여기서 UNARCHIVED를 붙이면 커밋된 변경을 스스로 버리게 된다.
--
-- 2) CLEAR 대상은 실제로 손상된 그룹뿐이다.
--    ORA-00313에 지목된 그룹 번호를 그대로 쓴다.
--    다른 그룹까지 손대면 복구 재료가 줄어들 뿐이다.
--
-- 3) 비정상 종료라도 인스턴스 복구에 필요한 그룹이 온전하면 손실이 없다.
--    이 실습에서 필요한 것은 CURRENT인 그룹 4였고 그것은 살아 있었다.
--    손상된 그룹 3은 INACTIVE라 인스턴스 복구에 쓰이지 않는다.
--
-- 4) 종료 방식만으로 결과가 정해지지는 않는다.
--    '어느 그룹이 손상되었는가'와 '그 그룹이 인스턴스 복구에 필요한가'가 함께 결정한다.
--    두 질문을 v$log의 STATUS로 확인한다.
--
-- 5) alert log의 crash recovery 기록이 판단의 근거가 된다.
--    Completed crash recovery 뒤에 오류가 없으면 인스턴스 복구가 정상 완료된 것이다.
--
-- 6) CLEAR 후 그룹이 순환에 복귀하는지 스위치를 몇 번 돌려 확인한다.
--    UNUSED 상태로만 남아 있으면 아직 한 번도 쓰이지 않았다는 뜻이다.

SYS@orcl> EXIT
