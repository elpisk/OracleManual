 실습 7-3 : 백업 컨트롤파일과 현재 데이터파일 정보 불일치
 과정      : Oracle Database 19c Backup & Recovery
 환경      : Oracle 19.3.0 / Oracle Linux 7 / non-CDB ORCL / NOARCHIVELOG
 소요 시간 : 약 20분

--------------------------------------------------------------------------------
[1] 시나리오 개요
--------------------------------------------------------------------------------
-- 컨트롤파일 백업 이후 데이터파일을 추가했다.
-- 그 백업본으로 복구하면 추가된 파일이 목록에서 빠진다.
-- 오류 없이 데이터베이스가 열리므로 발견이 늦다.
-- UNNAMED 파일을 RENAME FILE로 해소하고 예방책을 정리한다.
-- 복구 유형 : 완전 복구(구조 보정 필요)

--------------------------------------------------------------------------------

ERROR at line 1:
ORA-00376: file 9 cannot be read at this time

ORA-01110: data file 9:
           '/u01/app/oracle/product/19.3.0/dbhome_1/dbs/UNNAMED00009'

-- << 원인 파악 >>
-- 백업 컨트롤파일에 파일 9번이 등록되어 있지 않았다.
-- 복구 과정에서 리두를 적용하다 그 파일의 존재를 알게 되어
-- UNNAMED00009 라는 임시 이름으로 자리만 잡아 두었다.
-- 데이터베이스는 정상적으로 열렸고 오류도 없었기 때문에 발견이 늦다.
-- 그 파일에 든 테이블을 실제로 읽을 때가 되어서야 드러난다.

SYS@orcl> SELECT file#, name, status FROM v$datafile WHERE file# = 9;

     FILE# NAME                                                       STATUS
---------- ---------------------------------------------------------- -------
         9 /u01/app/oracle/product/19.3.0/dbhome_1/dbs/UNNAMED00009   RECOVER

SYS@orcl> !ls -l /u01/app/oracle/oradata/ORCL/users03.dbf
-rw-r-----. 1 oracle oinstall 52436992 May 10 19:36 users03.dbf

-- 실제 파일은 그대로 있다. 이름만 연결하면 된다.

-- << 수정 >>

SYS@orcl> SHUTDOWN IMMEDIATE
SYS@orcl> STARTUP MOUNT

SYS@orcl> ALTER DATABASE RENAME FILE
  2    '/u01/app/oracle/product/19.3.0/dbhome_1/dbs/UNNAMED00009'
  3  TO '/u01/app/oracle/oradata/ORCL/users03.dbf';

Database altered.

SYS@orcl> SELECT file#, name, status FROM v$datafile WHERE file# = 9;

     FILE# NAME                                          STATUS
---------- --------------------------------------------- -------
         9 /u01/app/oracle/oradata/ORCL/users03.dbf      ONLINE

SYS@orcl> ALTER DATABASE OPEN;

Database altered.

-- 매니페스트도 함께 남긴다.

SYS@orcl> SPOOL /home/oracle/backup/manifest_20250510.txt
SYS@orcl> SELECT file#, name, bytes/1024/1024 AS mb FROM v$datafile ORDER BY file#;
SYS@orcl> SELECT group#, member FROM v$logfile ORDER BY group#;
SYS@orcl> SELECT name FROM v$controlfile;
SYS@orcl> SPOOL OFF

-- 실무 포인트
-- 1) 이 실수는 오류를 내지 않는다는 점이 가장 위험하다.
--    데이터베이스는 정상적으로 열리고 대부분의 조회도 성공한다.
--    누락된 파일에 든 데이터를 읽을 때가 되어서야 ORA-00376이 나타난다.
--
-- 2) UNNAMEDnnnnn 경로를 보면 즉시 이 상황을 떠올린다.
--    컨트롤파일에 등록되지 않은 파일의 자리만 잡아 둔 임시 이름이다.
--    v$datafile을 조회해 어느 file#인지 확인한다.
--
-- 3) 실제 파일이 있으면 RENAME FILE 로 해소된다.
--    MOUNT 상태에서 수행하며 이후 STATUS가 ONLINE인지 확인한다.
--    RECOVER 상태면 미디어 복구가 추가로 필요하다.
--
-- 4) 실제 파일이 없다면 ALTER DATABASE CREATE DATAFILE 로 자리를 만들고 리두를 적용해야 한다.
--    NOARCHIVELOG 환경에서는 리두가 부족해 성공 확률이 낮다.
--    즉 복구 기술로 완전히 해결되지 않는 문제다.
--
-- 5) 복원 전 목록 대조가 예방의 핵심이다.
--    ls 로 뽑은 데이터파일 개수와 백업본의 항목 수를 비교하면 사전에 걸러진다.
--    이 실습에서는 6개와 5개의 차이를 진단 단계에서 이미 확인할 수 있었다.
--
-- 6) 구조 변경 작업의 마지막 단계에 컨트롤파일 백업을 넣는다.
--    Binary와 trace를 함께 받고 매니페스트에 파일 목록을 남긴다.
--    작업 티켓의 체크 항목으로 만들면 담당자가 바뀌어도 누락되지 않는다.

SYS@orcl> EXIT
