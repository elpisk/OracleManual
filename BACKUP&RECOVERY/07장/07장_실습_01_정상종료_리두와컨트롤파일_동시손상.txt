================================================================================
 실습 7-1 : 정상 종료 후 리두 로그와 컨트롤파일 동시 손상
 과정      : Oracle Database 19c Backup & Recovery
 환경      : Oracle 19.3.0 / Oracle Linux 7 / non-CDB ORCL / NOARCHIVELOG
 소요 시간 : 약 20분
================================================================================

--------------------------------------------------------------------------------
[1] 시나리오 개요
--------------------------------------------------------------------------------
-- 정상 종료 뒤 리두 로그 전부와 컨트롤파일 전부가 유실되었다.
-- 데이터파일이 같은 SCN에서 일관성 있게 닫혀 있어 적용할 리두가 없다.
-- 따라서 리두 로그가 통째로 없어져도 손실이 발생하지 않는다.
-- NORESETLOGS 형식이 실패하는 이유를 확인하고 RESETLOGS 형식으로 재생성한다.
-- 복구 유형 : 완전 복구(RESETLOGS 강제, 손실 없음)

--------------------------------------------------------------------------------
[7] 복구 절차 : 오류 발생 → 원인 파악 → 수정
--------------------------------------------------------------------------------
-- 준비 : trace 파일은 그대로 실행할 수 없다.
-- 두 형식이 한 파일에 들어 있고, 각 형식 앞뒤로 주석과 STARTUP NOMOUNT,
-- RECOVER DATABASE, ALTER DATABASE OPEN 이 함께 적혀 있다.
-- CREATE CONTROLFILE 문만 잘라 두 개의 스크립트로 나눈다.

SYS@orcl> !sed -n '/^CREATE CONTROLFILE.*NORESETLOGS/,/^;/p' /home/oracle/backup/cf_71.sql \
        > /home/oracle/backup/cf_71_noresetlogs.sql
SYS@orcl> !sed -n '/^CREATE CONTROLFILE.*[^O]RESETLOGS/,/^;/p' /home/oracle/backup/cf_71.sql \
        > /home/oracle/backup/cf_71_resetlogs.sql

-- 두 번째 패턴 앞에는 공백이 있다.
-- 공백이 없으면 NORESETLOGS 쪽까지 함께 걸린다.
-- 잘라 낸 뒤 head -1 로 각 파일의 첫 줄이 의도한 형식인지 확인하고 진행한다.

-- 판정을 무시하고 NORESETLOGS 형식으로 먼저 시도해 본다.
-- [5] 의 STARTUP 은 인스턴스를 띄운 뒤 MOUNT 단계에서 멈췄다.
-- 따라서 인스턴스는 이미 NOMOUNT 상태다.
-- 여기서 STARTUP NOMOUNT 를 다시 실행하면 ORA-01081 이 발생하므로
-- 그대로 진행한다.

SYS@orcl> @/home/oracle/backup/cf_71_noresetlogs.sql
CREATE CONTROLFILE REUSE DATABASE "ORCL" NORESETLOGS NOARCHIVELOG
*
ERROR at line 1:
ORA-01503: CREATE CONTROLFILE failed
ORA-01565: error in identifying file '/u01/app/oracle/oradata/orcl/redo01.log'
ORA-27037: unable to obtain file status
Linux-x86_64 Error: 2: No such file or directory
Additional information: 7

-- << 원인 파악 >>
-- ORA-01503은 총괄 오류이고 ORA-01565가 실제 원인이다.
-- NORESETLOGS 형식은 LOGFILE 절에 나열된 리두 파일을 그대로 인식하려 한다.
-- 그 파일이 실제로 존재하지 않으므로 문 자체가 실패했다.
-- RESETLOGS 형식은 리두 로그를 새로 만들어 인식시키므로 파일이 없어도 성립한다.

SYS@orcl> !ls /u01/app/oracle/oradata/orcl/redo01.log
ls: cannot access '/u01/app/oracle/oradata/orcl/redo01.log': No such file or directory

-- << 수정 >>

SYS@orcl> !ls -l /u01/app/oracle/oradata/orcl/*.ctl 2>/dev/null
[oracle@oel7v9 ~]$

    GROUP#  SEQUENCE# STATUS

-- 시퀀스가 1부터 다시 시작한다.

SYS@orcl> SELECT incarnation#, resetlogs_change#, status FROM v$database_incarnation;

INCARNATION# RESETLOGS_CHANGE# STATUS
------------ ----------------- -------
           1           2391041 CURRENT

-- 한 행뿐이다. 여기에 두 가지가 함께 담겨 있다.
--   ① OPEN RESETLOGS 를 했으므로 RESETLOGS_CHANGE# 가 갱신되었다.
--   ② 그런데 과거 인카네이션 이력이 남아 있지 않다.
--      이력은 컨트롤파일에 저장되는데 그 컨트롤파일을 새로 만들었기 때문이다.
--
-- 컨트롤파일 재생성은 인카네이션 이력뿐 아니라 RMAN 저장소 정보(백업 이력)와
-- TEMP 파일 등록 정보도 함께 지운다. Binary 백업본이 있으면 그쪽을 먼저 쓰는
-- 이유가 여기에 있다. trace 재생성은 마지막 수단이다.

SYS@orcl> SELECT COUNT(*) FROM v$tempfile;

  COUNT(*)
----------
         0

SYS@orcl> ALTER TABLESPACE temp ADD TEMPFILE
  2    '/u01/app/oracle/oradata/orcl/temp01.dbf' SIZE 60M REUSE;
Tablespace altered.

SYS@orcl> SELECT group#, COUNT(*) AS members FROM v$logfile GROUP BY group# ORDER BY group#;

    GROUP#    MEMBERS
---------- ----------
         1          2
         3          2
         4          2

-- 다중화 구성이 재생성 후에도 유지되었다. trace 파일에 그대로 적혀 있었기 때문이다.

-- 인카네이션이 달라졌으므로 전체 백업을 새로 받는다.

SYS@orcl> SHUTDOWN IMMEDIATE
SYS@orcl> !rm -rf /home/oracle/backup/ch07 && mkdir -p /home/oracle/backup/ch07

                 /u01/app/oracle/oradata/orcl/*.log /home/oracle/backup/ch07/
SYS@orcl> !cp -p /u02/oradata/orcl/*.ctl /u02/oradata/orcl/*.log /home/oracle/backup/ch07/
SYS@orcl> !rm -f /home/oracle/backup/ch07/temp01.dbf
SYS@orcl> STARTUP

-- 실무 포인트
-- 1) 정상 종료 상태에서는 리두 로그가 통째로 없어져도 손실이 없다.
--    종료 시 체크포인트가 완료되어 리두에만 있는 변경이 남지 않기 때문이다.
--    FUZZY가 전부 NO이고 SCN이 같다는 것이 그 증거다.
--
-- 2) NORESETLOGS 형식은 리두 파일이 실제로 있어야 성립한다.
--    없으면 ORA-01565 계열 오류로 문 자체가 실패한다.
--    두 형식이 한 파일에 함께 들어 있으므로 실패 즉시 다른 쪽을 시도할 수 있다.
--
-- 3) 실패한 CREATE CONTROLFILE 은 컨트롤파일을 남기지 않는다.
--    따라서 그대로 다른 형식으로 다시 시도할 수 있다.
--    다만 일부 상황에서는 잔여 파일이 남으므로 재시도 전 ls 로 확인하는 편이 안전하다.
--
-- 4) RESETLOGS 형식은 리두 로그를 새로 만든다.
--    trace 파일의 LOGFILE 절에 적힌 그룹·멤버·크기가 그대로 재현되므로
--    다중화 구성도 함께 복원된다. 이것이 trace 백업의 큰 가치다.
--    다만 trace 파일 자체는 그대로 실행할 수 없다. 주석과 STARTUP NOMOUNT,
--    RECOVER, ALTER DATABASE OPEN 이 함께 적혀 있으므로
--    CREATE CONTROLFILE 문만 잘라 형식별로 나눠 두어야 한다.
--
-- 5) 손실이 없어도 인카네이션은 올라간다.
--    리두를 새로 만들었으므로 연속성이 끊긴 것이며, 즉시 전체 백업이 필요하다.
--    덧붙여 컨트롤파일을 재생성하면 인카네이션 이력 자체가 사라진다.
--    v$database_incarnation 이 한 행만 남는 것이 그 증거다.
--    RMAN 백업 이력도 함께 사라지므로 카탈로그를 쓰지 않는 환경에서는
--    재생성 직후 백업을 다시 받고 기록을 새로 시작해야 한다.
--
-- 6) 리두 로그와 컨트롤파일을 같은 디스크에 두면 이 상황이 실제로 발생한다.
--    이 실습은 정상 종료였기에 손실이 없었을 뿐이며, 다음 실습에서 반대 경우를 본다.

SYS@orcl> EXIT
