================================================================================
 실습 7-6 : CURRENT 리두 로그 파일 삭제
 과정      : Oracle Database 19c Backup & Recovery
 환경      : Oracle 19.3.0 / Oracle Linux 7 / non-CDB ORCL / NOARCHIVELOG
 소요 시간 : 약 25분
================================================================================

--------------------------------------------------------------------------------
[1] 시나리오 개요
--------------------------------------------------------------------------------
-- CURRENT 그룹의 모든 멤버가 유실된 상태에서 인스턴스가 ABORT로 멈췄다.
-- 그 그룹에는 커밋되었으나 데이터파일에 반영되지 않은 변경이 들어 있다.
-- 아카이브 사본이 없으므로 그 변경을 되살릴 수 없다.
-- 불완전 복구를 수행하고 손실 범위를 산정해 보고한다.
-- 복구 유형 : 불완전 복구(RESETLOGS, 미반영분 손실)

--------------------------------------------------------------------------------
[2] 사전 조건
--------------------------------------------------------------------------------
-- 실습 7-5를 마친 상태에서 이어서 진행한다.
-- 실습 직전에 Cold Backup을 새로 받아 전체 복원 경로도 확보해 둔다.

[oracle@oel7v9r1 ~]$ sqlplus / as sysdba

SYS@orcl> SET LINESIZE 200
SYS@orcl> COL member FOR a44

SYS@orcl> SHUTDOWN IMMEDIATE
SYS@orcl> !rm -rf /home/oracle/backup/ch07 && mkdir -p /home/oracle/backup/ch07
SYS@orcl> !cp -p /u01/app/oracle/oradata/ORCL/*.dbf /u01/app/oracle/oradata/ORCL/*.ctl \
                 /u01/app/oracle/oradata/ORCL/*.log /home/oracle/backup/ch07/
SYS@orcl> !cp -p /u02/oradata/ORCL/*.ctl /u02/oradata/ORCL/*.log /home/oracle/backup/ch07/
SYS@orcl> !rm -f /home/oracle/backup/ch07/temp01.dbf
SYS@orcl> STARTUP

SYS@orcl> SELECT name, log_mode FROM v$database;

ORCL      NOARCHIVELOG

-- 아카이브 사본도 없다.

-- 판정
--   ① 멤버 : CURRENT 그룹 전손, 생존 멤버 없음
--   ② 그룹 상태 : CURRENT → 미반영 커밋 변경이 그 안에 있음
--   ③ 종료 : abort → 인스턴스 복구에 그 그룹이 필요
--   → 불완전 복구. 미반영분 손실 확정. 실패 시 전체 복원.

SYS@orcl> !mkdir -p /home/oracle/before_recover_76
SYS@orcl> !cp -p /u01/app/oracle/oradata/ORCL/*.dbf \
                 /u01/app/oracle/oradata/ORCL/*.ctl /home/oracle/before_recover_76/
SYS@orcl> !cp -p /u02/oradata/ORCL/*.ctl /home/oracle/before_recover_76/

-- 되돌릴 수 없는 명령을 쓰기 전에 사본을 확보한다.

--------------------------------------------------------------------------------
[7] 복구 절차 : 오류 발생 → 원인 파악 → 수정
--------------------------------------------------------------------------------
-- 실습 7-4처럼 CLEAR 로 처리해 본다.

SYS@orcl> ALTER DATABASE CLEAR LOGFILE GROUP 1;
ALTER DATABASE CLEAR LOGFILE GROUP 1
*
ERROR at line 1:
ORA-01624: log 1 needed for crash recovery of instance orcl (thread 1)
ORA-00312: online log 1 thread 1: '/u01/app/oracle/oradata/ORCL/redo01.log'

-- << 원인 파악 >>
-- 그룹 1은 CURRENT이며 인스턴스 복구에 필요한 리두를 담고 있다.
-- 실습 7-5에서는 손상된 그룹이 INACTIVE라 이 오류가 나오지 않았다.
-- 이번에는 손상된 그룹 자체가 인스턴스 복구에 필요하므로 거부된다.
-- 그런데 그 그룹의 멤버가 하나도 없어 리두를 읽을 방법이 없다.
-- 즉 CLEAR 없이는 진행할 수 없고 CLEAR 하면 리두를 잃는다.
-- 손실이 확정되는 지점이며, 그 사실을 인지한 상태에서 UNARCHIVED를 붙인다.

SYS@orcl> SELECT COUNT(*) FROM v$logfile WHERE group# = 1 AND status IS NULL;

  COUNT(*)
----------
         0

-- 살아 있는 멤버가 없음을 다시 확인했다.

-- << 수정 >>

SYS@orcl> ALTER DATABASE CLEAR UNARCHIVED LOGFILE GROUP 1;

Database altered.

SYS@orcl> SELECT group#, sequence#, status FROM v$log WHERE group# = 1;

    GROUP#  SEQUENCE# STATUS
---------- ---------- ----------------
         1          0 UNUSED

SYS@orcl> ALTER DATABASE OPEN;

-- 실무 포인트
-- 1) 커밋되었어도 잃을 수 있다는 사실을 이 실습이 보여 준다.
--    커밋은 리두에 기록되었음을 보장할 뿐 데이터파일 반영을 보장하지 않는다.
--    그 리두가 사라지면 커밋된 변경도 되살릴 수 없다.
--
-- 2) 손상된 그룹이 CURRENT인지 INACTIVE인지가 결과를 가른다.
--    실습 7-5는 INACTIVE라 손실이 없었고 이 실습은 CURRENT라 손실이 생겼다.
--    같은 명령을 써도 결과가 다른 이유가 여기에 있다.
--
-- 3) ORA-01624가 나왔을 때 두 경우를 구분해야 한다.
--    손상되지 않은 그룹이면 CLEAR 대상이 아니므로 그대로 두고,
--    손상된 그룹이면 손실을 인지한 상태에서 UNARCHIVED를 붙인다.
--
-- 4) CLEAR 후 ORA-01113이 나오는 것은 정상적인 진행이다.
--    인스턴스 복구 요구가 해소되고 미디어 복구 요구가 드러난 것이다.
--    UNTIL CANCEL 로 남은 리두까지 적용한 뒤 RESETLOGS로 연다.
--
-- 5) 손실 구간은 반드시 업무 시각으로 환산해 통보한다.
--    SCN_TO_TIMESTAMP 로 복구 시점을 구하고 업무 테이블의 최종 시각으로 검증한다.
--    기술 용어만으로 보고하면 현업이 재처리 범위를 판단할 수 없다.
--
-- 6) 예방책은 하나뿐이다. 멤버 다중화다.
--    멤버가 서로 다른 디스크에 하나라도 살아 있었다면 이 손실은 없었다.
--    ARCHIVELOG로 전환해도 CURRENT 리두는 아직 아카이브되기 전이라 보호되지 않는다.

SYS@orcl> EXIT
