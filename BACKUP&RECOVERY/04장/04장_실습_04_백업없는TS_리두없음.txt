--------------------------------------------------------------------------------
[7] 복구 절차 : 오류 발생 → 원인 파악 → 수정
--------------------------------------------------------------------------------
-- 먼저 CREATE DATAFILE + RECOVER를 시도해 실제로 막히는 것을 확인한다.

SYS@orcl> SHUTDOWN ABORT
SYS@orcl> STARTUP MOUNT
Database mounted.

SYS@orcl> ALTER DATABASE CREATE DATAFILE
  2    '/u01/app/oracle/oradata/ORCL/tbs02.dbf'
  3    AS '/u01/app/oracle/oradata/ORCL/tbs02.dbf';

Database altered.

SYS@orcl> SET AUTORECOVERY OFF
SYS@orcl> RECOVER DATAFILE 9;
ORA-00279: change 2353104 generated at 05/09/2025 17:02:44 needed for thread 1
ORA-00289: suggestion : /u01/app/oracle/product/19.3.0/dbhome_1/dbs/arch1_53_1200525254.dbf
ORA-00280: change 2353104 for thread 1 is in sequence #53

Specify log: {<RET>=suggested | filename | AUTO | CANCEL}
CANCEL
ORA-01547: warning: RECOVER succeeded but OPEN RESETLOGS would get error below
ORA-01194: file 9 needs more recovery to be consistent
ORA-01110: data file 9: '/u01/app/oracle/oradata/ORCL/tbs02.dbf'

-- 빈 파일은 만들어졌으나 채울 리두가 없다.

SYS@orcl> ALTER DATABASE OPEN;
ALTER DATABASE OPEN
*
ERROR at line 1:
ORA-01113: file 9 needs media recovery
ORA-01110: data file 9: '/u01/app/oracle/oradata/ORCL/tbs02.dbf'

-- 이 파일 하나 때문에 데이터베이스 전체가 열리지 않는다.

-- << 오류 발생 : DROP TABLESPACE를 먼저 시도 >>
-- 데이터베이스를 열어야 DROP TABLESPACE를 쓸 수 있는데 열리지 않는 상황이다.
-- 순서를 바꿔 파일을 먼저 떼어 낸다.

-- << 원인 파악 >>
-- ORA-01113은 그 파일이 복구되지 않았다는 뜻이다.
-- 복구할 수 없는 파일이 목록에 남아 있으면 데이터베이스는 열리지 않는다.
-- 따라서 그 파일을 데이터베이스에서 떼어 내야 한다.
-- NOARCHIVELOG에서는 OFFLINE이 금지되므로 OFFLINE DROP을 쓴다.

-- << 수정 >>

SYS@orcl> ALTER DATABASE DATAFILE 9 OFFLINE;
ALTER DATABASE DATAFILE 9 OFFLINE
*
ERROR at line 1:
ORA-01145: offline immediate disallowed unless media recovery enabled

SYS@orcl> ALTER DATABASE DATAFILE 9 OFFLINE DROP;

Database altered.

SYS@orcl> SELECT file#, name, status FROM v$datafile WHERE file# = 9;

     FILE# NAME                                       STATUS
---------- ------------------------------------------ -------
         9 /u01/app/oracle/oradata/ORCL/tbs02.dbf     RECOVER

SYS@orcl> ALTER DATABASE OPEN;

Database altered.

-- 열렸다. 이제 딕셔너리를 정리할 수 있다.

SYS@orcl> DROP TABLESPACE tbs2 INCLUDING CONTENTS AND DATAFILES;

Tablespace dropped.

SYS@orcl> SELECT COUNT(*) FROM hr.emp1;

  COUNT(*)
----------
         2

SYS@orcl> SELECT COUNT(*) FROM hr.employees;

  COUNT(*)
----------
       107

-- 다른 테이블스페이스의 데이터는 최신 상태로 유지되었다.
-- 전체 복원을 택했다면 이 데이터도 백업 시점으로 되돌아갔을 것이다.

SYS@orcl> SELECT COUNT(*) FROM hr.emp2;
SELECT COUNT(*) FROM hr.emp2
                     *
ERROR at line 1:
ORA-00942: table or view does not exist

-- emp2는 테이블스페이스와 함께 사라졌다. 예상된 손실이다.

-- 실무 포인트
-- 1) 순서가 핵심이다. OFFLINE DROP → OPEN → DROP TABLESPACE 순으로 진행한다.
--    OPEN 상태에서 DROP TABLESPACE를 먼저 시도하면 세그먼트 정보를 읽어야 하는데
--    데이터 파일을 열 수 없어 실패한다.
--
-- 2) OFFLINE이 아니라 OFFLINE DROP을 써야 한다(ORA-01145).
--    NOARCHIVELOG에서는 미디어 복구가 비활성이라 OFFLINE이 허용되지 않는다.
--
-- 3) OFFLINE DROP은 파일을 지우지 않는다. STATUS를 RECOVER로 바꿀 뿐이다.
--    실제 정리는 DROP TABLESPACE ... INCLUDING CONTENTS AND DATAFILES가 한다.
--
-- 4) 복구 불가 파일 하나가 데이터베이스 전체의 오픈을 막는다.
--    그것을 떼어 내는 것이 서비스 재개의 유일한 길인 경우가 있다.
--
-- 5) 손실 범위를 정확히 파악해 통보한다.
--    이 경우 "TBS2 테이블스페이스의 모든 객체"가 손실 범위이며,
--    dba_segments를 미리 조회해 두었다면 어떤 객체가 있었는지 목록을 제시할 수 있다.
--
-- 6) 근본 원인은 테이블스페이스 생성 후 백업을 받지 않은 것이다.
--    구조 변경 직후 전체 백업을 받는 원칙이 지켜졌다면 완전 복구가 가능했다.

SYS@orcl> EXIT
