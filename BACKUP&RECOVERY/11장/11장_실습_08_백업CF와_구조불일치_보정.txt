 실습 11-8 : 백업 컨트롤파일과 현재 구조 불일치 보정
 과정      : Oracle Database 19c Backup & Recovery
 환경      : Oracle 19.3.0 / Oracle Linux 7 / non-CDB ORCL / ARCHIVELOG
 소요 시간 : 약 25분

--------------------------------------------------------------------------------
[1] 시나리오 개요
--------------------------------------------------------------------------------
-- 컨트롤파일 백업 이후 데이터파일을 추가하고 다른 테이블스페이스를 삭제했다.
-- 그 백업본으로 복구하면 추가된 파일은 UNNAMED로, 삭제된 파일은 부재로 나타난다.
-- RENAME FILE 과 CREATE DATAFILE, OFFLINE DROP 세 가지 보정을 모두 다룬다.
-- ARCHIVELOG 환경에서는 대부분의 어긋남을 보정할 수 있다.
-- 복구 유형 : 완전 복구(구조 보정 포함)

SYS@orcl> SET AUTORECOVERY ON

ORA-01110: data file 12: '/u02/oradata/ORCL/tbs02.dbf'
ORA-01157: cannot identify/lock data file 12 - see DBWR trace file

-- << 원인 파악 >>
-- 12번 파일은 백업 이후 DROP TABLESPACE 로 지운 것이다.
-- 컨트롤파일은 그 사실을 모르므로 파일을 요구한다.
-- 실제로는 필요 없는 파일이므로 복구 대상에서 제외해야 한다.
-- OFFLINE DROP 으로 떼어 내면 그 파일을 무시하고 진행할 수 있다.

SYS@orcl> SELECT file#, name, status FROM v$datafile WHERE file# = 12;

     FILE# NAME                                                       STATUS
---------- ---------------------------------------------------------- -------
        12 /u02/oradata/ORCL/tbs02.dbf                                RECOVER

-- 실무 포인트
-- 1) 구조 변경은 두 방향으로 어긋남을 만든다.
--    추가된 파일은 UNNAMED로 등록되고 삭제된 파일은 부재로 나타난다.
--    두 경우의 보정 방법이 다르므로 구분해야 한다.
--
-- 2) 삭제된 파일은 OFFLINE DROP 으로 떼어 낸다.
--    복구가 그 파일을 요구해 ORA-01157로 막히므로 복구 전에 처리한다.
--    OPEN 후 DROP TABLESPACE INCLUDING CONTENTS 로 완전히 정리한다.
--
-- 3) 추가된 파일은 오류 없이 열린 뒤에 드러난다.
--    그 테이블을 읽는 순간 ORA-00376과 ORA-01111이 나온다.
--    복구 직후 v$datafile 에서 UNNAMED 경로를 확인하면 미리 발견할 수 있다.
--
-- 4) 실제 파일이 있으면 RENAME FILE, 없으면 CREATE DATAFILE 이다.
--    RENAME은 OFFLINE 상태에서 수행하며 이후 RECOVER 로 마무리한다.
--    ARCHIVELOG 환경이므로 두 방법 모두 성공률이 높다.
--
-- 5) 근본 대책은 구조 변경 직후 컨트롤파일 백업이다.
--    이 실습의 모든 절차는 백업을 미룬 데서 비롯되었다.
--    Binary와 trace를 함께 받고 매니페스트도 갱신한다.
--
-- 6) 매니페스트의 파일 개수를 백업본과 대조하는 절차를 만든다.
--    이 실습에서는 백업본 7개와 실제 7개가 같았지만 내용이 달랐다.
--    개수만이 아니라 파일 목록 자체를 비교해야 한다.
