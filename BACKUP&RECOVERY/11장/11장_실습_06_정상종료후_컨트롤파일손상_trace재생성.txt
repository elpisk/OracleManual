 실습 11-6 : 정상 종료 후 컨트롤파일 손상 — trace 재생성
 과정      : Oracle Database 19c Backup & Recovery
 환경      : Oracle 19.3.0 / Oracle Linux 7 / non-CDB ORCL / ARCHIVELOG

--------------------------------------------------------------------------------
[1] 시나리오 개요
--------------------------------------------------------------------------------
-- 정상 종료 후 컨트롤파일이 전손되었고 trace 백업이 있다.
-- NORESETLOGS 형식으로 재생성하면 복구 없이 열린다.
-- RESETLOGS 가 없어 기존 백업본과 아카이브가 계속 유효하다.
-- 다만 재생성한 컨트롤파일은 인카네이션 이력을 모른다.
-- 실습 11-5의 Binary 경로와 결과를 비교한다.
-- 복구 유형 : 복구 불필요(NORESETLOGS 재생성)

--------------------------------------------------------------------------------

-- 실무 포인트
-- 1) NORESETLOGS 형식은 RESETLOGS 를 요구하지 않는다.
--    resetlogs_change# 가 유지되어 기존 백업본과 아카이브를 그대로 쓸 수 있다.
--    실습 11-5의 Binary 복원은 RESETLOGS가 강제되어 인카네이션이 올라갔다.
--    같은 장애에서 trace가 있으면 명확히 유리한 선택이다.
--
-- 2) 재생성한 컨트롤파일은 인카네이션 이력을 모른다.
--    번호가 1 부터 다시 시작한다. 이력은 컨트롤파일에만 있기 때문이다.
--    RMAN 저장소 정보도 같은 이유로 사라진다(13장 이후).
--
-- 3) 성립 조건은 두 가지다. 정상 종료였고 리두 로그가 온전해야 한다.
--    alert log의 CLOSE NORMAL 기록과 리두 파일 존재로 확인한다.
--
-- 4) trace 백업도 구조 변경 후에는 다시 받아야 한다.
--    이 실습에서 이미 정리한 테이블스페이스가 문에 남아 ORA-01565가 발생했다.
--    Binary 백업과 달리 편집으로 해결할 수 있다는 점이 trace의 장점이다.
--    지운 줄이 마지막이면 앞 줄의 쉼표도 함께 손본다.
--
-- 5) 실행 전 DATAFILE 절의 항목 수와 실제 파일 수를 대조한다.
--    개수가 다르면 어긋난 것이 확실하고, 같아도 이름까지 대조해야 안심할 수 있다.
--
-- 6) trace 재생성은 TEMP 정보를 남기지 않는다.
--    Binary 복원과 달리 ADD TEMPFILE 이 필요하다.
--    빠뜨리면 큰 정렬에서 ORA-01652가 발생한다.
--
-- 7) 다중화 구성은 trace에 적혀 있어 그대로 재현된다.
--    컨트롤파일 경로와 리두 그룹·멤버가 모두 복원되므로
--    구성 문서 역할도 겸한다.

SYS@orcl> EXIT
