================================================================================
 실습 11-2 : CURRENT 리두 로그 삭제 후 비정상 종료
 과정      : Oracle Database 19c Backup & Recovery
 환경      : Oracle 19.3.0 / Oracle Linux 7 / non-CDB ORCL / ARCHIVELOG
 소요 시간 : 약 25분
================================================================================

--------------------------------------------------------------------------------
[1] 시나리오 개요
--------------------------------------------------------------------------------
-- SHUTDOWN ABORT 뒤 CURRENT 리두 로그 그룹이 전손되었다.
-- 데이터파일에 반영되지 않은 커밋 변경이 그 그룹에 있었다.
-- 아카이브 사본이 없으므로 그 구간을 되살릴 수 없다.
-- 전체 복원 후 불완전 복구로 전환하고 손실 구간을 산정한다.
-- 실습 11-1과 종료 방식만 다른데 결과가 달라진다.
-- 복구 유형 : 불완전 복구(마지막 스위치 이후 손실)

--------------------------------------------------------------------------------
[2] 사전 조건
--------------------------------------------------------------------------------
-- 실습 11-1을 마친 상태에서 이어서 진행한다.
-- /home/oracle/backup/ch11 백업본이 최신(11-1 끝에 받은 것)이어야 한다.

[oracle@oel7v9 ~]$ sqlplus / as sysdba

SYS@orcl> SET LINESIZE 200
SYS@orcl> ALTER SESSION SET nls_date_format = 'YYYY-MM-DD HH24:MI:SS';

-- 판정
--   ① 멤버 : 전손
--   ② 그룹 : CURRENT, ARCHIVED NO
--   ③ 종료 : abort → 미적용 리두 존재
--   ④ 복구 한계 : 아카이브된 마지막 시퀀스 10의 끝 = SCN 2431520 직전
--   → 불완전 복구. 10:12:40 이후 변경 손실 확정.

--------------------------------------------------------------------------------
[7] 복구 절차 : 오류 발생 → 원인 파악 → 수정
--------------------------------------------------------------------------------
-- 실습 11-1과 같은 방법으로 처리해 본다.

SYS@orcl> ALTER DATABASE CLEAR UNARCHIVED LOGFILE GROUP 3;
ALTER DATABASE CLEAR UNARCHIVED LOGFILE GROUP 3
*
ERROR at line 1:
ORA-01624: log 3 needed for crash recovery of instance orcl (thread 1)
ORA-00312: online log 3 thread 1: '/u01/app/oracle/oradata/orcl/redo03.log'
ORA-00312: online log 3 thread 1: '/u02/oradata/orcl/redo03b.log'

-- << 원인 파악 >>
-- 11-1 에서는 통했던 명령이 거부되었다.
-- 비정상 종료라 적용해야 할 리두가 있고 그것이 CURRENT 그룹에 있다.
-- Oracle 은 크래시 복구에 필요한 그룹을 비우지 못하게 막는다(ORA-01624).
-- 11-1 에서는 FUZZY가 NO여서 적용할 리두 자체가 없었다.
-- 종료 방식 하나가 같은 명령의 결과를 갈랐다.

SYS@orcl> ALTER DATABASE OPEN RESETLOGS;
ALTER DATABASE OPEN RESETLOGS
*
ERROR at line 1:
ORA-01139: RESETLOGS option only valid after an incomplete database recovery

SYS@orcl> SELECT file#, error, change# FROM v$recover_file;

no rows selected

-- 미디어 복구 대상도 아니다. 파일은 최신인데 크래시 복구에 쓸 리두가 없는 상태다.
-- 남은 길은 하나다. 모든 데이터파일을 백업본으로 되돌리고 아카이브가 있는 곳까지만 적용한다.

-- << 수정 >>
-- 전체 복원 후 불완전 복구로 전환한다.

SYS@orcl> SHUTDOWN ABORT
SYS@orcl> !cp -p /home/oracle/backup/ch11/*.dbf /u01/app/oracle/oradata/orcl/

SYS@orcl> STARTUP MOUNT
ORACLE instance started.
Database mounted.

--------------------------------------------------------------------------------
SYS@orcl> SELECT * FROM v$recover_file;

no rows selected

SYS@orcl> SELECT id, memo FROM hr.emp111 ORDER BY id;

        ID MEMO
---------- ------------------------------
         1 before shutdown
         2 in current redo
         3 archived

-- 4번 행이 사라졌다. CURRENT 리두에만 있던 변경이다.
-- 커밋했음에도 잃었다는 점이 이 실습의 핵심이다.

SYS@orcl> SELECT resetlogs_change#, TO_CHAR(resetlogs_time, 'HH24:MI:SS') AS resetlogs_time
  2  FROM   v$database;

RESETLOGS_CHANGE# RESETLOGS_TIME
----------------- --------------
          2431521 10:31:10

-- 복구 지점(2431520, 마지막 스위치)의 다음 SCN 에서 새 인카네이션이 시작한다.

SYS@orcl> SELECT incarnation#, resetlogs_change#, status FROM v$database_incarnation
  2  WHERE  status = 'CURRENT';

INCARNATION# RESETLOGS_CHANGE# STATUS
------------ ----------------- -------
           8           2431521 CURRENT

SYS@orcl> SELECT COUNT(*) FROM v$tempfile;

  COUNT(*)
----------
         1

-- 템프파일은 그대로다. 컨트롤파일을 되돌리거나 다시 만들지 않았기 때문이다.
-- RESETLOGS 오픈은 템프파일 기록을 지우지 않는다.
-- 여기서 ADD TEMPFILE 을 하면 ORA-01537(file already part of database)로 거부된다.
-- 컨트롤파일을 재생성한 경우에만 템프파일이 사라지며 그때 다시 만든다(11-6, 11-7).

-- 손실 구간을 정리한다.
--   복구 지점 : 10:12:40 (마지막 스위치 시각)
--   손실 구간 : 10:12:40 이후 ~ 장애 시각(10:18:22 이후)
--   영향 : 그 시간대의 모든 커밋된 변경

SYS@orcl> SHUTDOWN IMMEDIATE
SYS@orcl> !rm -rf /home/oracle/backup/ch11; mkdir -p /home/oracle/backup/ch11
SYS@orcl> !cp -p /u01/app/oracle/oradata/orcl/*.dbf /home/oracle/backup/ch11/
SYS@orcl> !rm -f /home/oracle/backup/ch11/temp01.dbf
SYS@orcl> STARTUP
SYS@orcl> ALTER DATABASE BACKUP CONTROLFILE TO
  2    '/home/oracle/backup/control_ch11.bkp' REUSE;

-- 실무 포인트
-- 1) 종료 방식 하나가 같은 명령의 결과를 가른다.
--    실습 11-1은 CLEAR UNARCHIVED 로 손실 없이 끝났고
--    이 실습은 같은 명령이 ORA-01624 로 거부되어 불완전 복구로 전환했다.
--    차이는 FUZZY 컬럼에서 미리 드러난다.
--
-- 2) 커밋했어도 잃을 수 있다.
--    커밋은 리두에 기록되었음을 보장할 뿐 데이터파일 반영을 보장하지 않는다.
--    그 리두가 CURRENT 그룹에 있었고 사본이 없으면 되살릴 수 없다.
--
-- 3) 손실 구간은 마지막 로그 스위치 이후다.
--    복구 지점이 정확히 스위치 시각과 일치하는 것을 확인할 수 있다.
--    스위치 간격이 길수록 손실이 커지므로 RPO 설계와 직결된다.
--
-- 4) 불완전 복구는 모든 데이터파일을 복원해야 한다.
--    현재 파일은 크래시 복구에 쓸 리두를 잃어 열 수도, 비울 수도 없다.
--    10장에서 익힌 원칙이 그대로 적용된다.
--
-- 5) 아카이브된 마지막 시퀀스가 복구 한계다.
--    CURRENT 시퀀스는 사본이 없으므로 프롬프트에서 CANCEL 로 끝낸다.
--
-- 6) 예방은 멤버 다중화뿐이다.
--    멤버 하나가 다른 디스크에 살아 있었다면 그것으로 복구가 끝났을 상황이다.

SYS@orcl> EXIT
