================================================================================
 실습 10-4 : Sequence-based 불완전 복구
 과정      : Oracle Database 19c Backup & Recovery
 환경      : Oracle 19.3.0 / Oracle Linux 7 / non-CDB ORCL / ARCHIVELOG
 소요 시간 : 약 20분
================================================================================

--------------------------------------------------------------------------------
[1] 시나리오 개요
--------------------------------------------------------------------------------
-- 아카이브 정리 스크립트가 필요한 시퀀스까지 지웠다.
-- 첫 결손 시퀀스의 시작 SCN 을 복구 한계로 삼는다.
-- 시퀀스 경계는 SCN 으로 정확히 정해지므로 Cancel 방식보다 실수 여지가 적다.
-- 결손 구간을 찾는 점검 쿼리도 함께 다룬다.
-- 복구 유형 : 불완전 복구(Sequence-based)

SYS@orcl> SHUTDOWN ABORT
SYS@orcl> !cp -p /home/oracle/backup/ch10/*.dbf /u01/app/oracle/oradata/orcl/
SYS@orcl> STARTUP MOUNT

-- 시퀀스 번호를 그대로 지정해 본다.

SYS@orcl> SET AUTORECOVERY ON
SYS@orcl> RECOVER DATABASE UNTIL SEQUENCE 3 THREAD 1;
ORA-00277: illegal option to the UNTIL recovery flag SEQUENCE

-- << 원인 파악 >>
-- SQL*Plus 의 RECOVER(와 ALTER DATABASE RECOVER)가 받는 UNTIL 은
-- CANCEL / TIME / CHANGE / CONSISTENT 네 가지뿐이다.
-- UNTIL SEQUENCE 는 RMAN 의 SET UNTIL SEQUENCE 구문이다(13장 이후).
-- 사용자 관리 복구에서 시퀀스 경계는 SCN 으로 지정한다.
-- "시퀀스 n 직전까지" = UNTIL CHANGE <시퀀스 n 의 FIRST_CHANGE#> 이다.
-- 결손이 3 이면 v$archived_log 에서 읽은 2424559 를 지정하면 된다.

-- 먼저 결손 뒤의 SCN(시퀀스 5 의 시작 2425240)을 지정하면 어떻게 되는지 본다.
-- READ ONLY 로 검증할 것이므로 USING BACKUP CONTROLFILE 을 붙인다(10-2).

SYS@orcl> RECOVER DATABASE UNTIL CHANGE 2425240 USING BACKUP CONTROLFILE;

-- "정리했다" 는 표시만 붙는다. 방금 정리한 인카네이션(2423418)만 걸러서 봤다.

-- RESETLOGS 로 인카네이션이 올라갔다. 이전 백업본과 아카이브는 그대로 쓸 수 없다.
-- 즉시 전체 백업을 받는다.

SYS@orcl> SHUTDOWN IMMEDIATE
SYS@orcl> !rm -rf /home/oracle/backup/ch10; mkdir -p /home/oracle/backup/ch10
SYS@orcl> !cp -p /u01/app/oracle/oradata/orcl/*.dbf /home/oracle/backup/ch10/
SYS@orcl> !rm -f /home/oracle/backup/ch10/temp01.dbf
SYS@orcl> STARTUP
SYS@orcl> ALTER DATABASE BACKUP CONTROLFILE TO
  2    '/home/oracle/backup/control_ch10.bkp' REUSE;

-- 실무 포인트
-- 1) 사용자 관리 복구에는 UNTIL SEQUENCE 가 없다(ORA-00277).
--    시퀀스 경계는 그 시퀀스의 FIRST_CHANGE# 를 UNTIL CHANGE 로 준다.
--    UNTIL CHANGE 는 지정한 SCN 직전까지 적용하므로 결손 시퀀스의 시작 SCN 을
--    그대로 지정하면 그 앞 시퀀스까지 적용되어 의도와 일치한다.
--    RMAN 에서는 SET UNTIL SEQUENCE n THREAD 1 이 같은 뜻이다(13장 이후).
--
-- 2) SCN 경계는 프롬프트 조작이 없어 Cancel 방식보다 실수 여지가 적다.
--    결손 지점이 명확할 때 가장 간단한 방법이다.
--
-- 3) OS로 아카이브를 지우면 컨트롤파일 기록과 어긋난다.
--    v$archived_log 에는 STATUS가 A로 남아 있어 연속성 점검이 실제와 다르게 나온다.
--    CROSSCHECK 로 상태를 맞춰야 정확한 판단이 가능하다.
--
-- 4) CROSSCHECK 후 STATUS가 X(EXPIRED)로 바뀐다.
--    그 값을 기준으로 첫 결손 시퀀스를 찾을 수 있다.
--    RESETLOGS 뒤에는 시퀀스가 1부터 다시 시작하므로 resetlogs_change# 로 걸러 본다.
--
-- 5) 복구를 다시 수행해도 이미 적용한 구간은 반복되지 않는다.
--    이 실습에서 결손 뒤의 SCN 을 지정한 시도가 실패한 뒤 바로 다시 수행해 즉시 완료되었다.
--    복원부터 다시 할 필요가 없었다.
--
-- 6) 원인은 아카이브 정리 정책이다.
--    백업 완료 여부를 조건으로 걸어야 하며 날짜만 보고 지우면 이 상황이 반복된다.

SYS@orcl> EXIT
