================================================================================
 실습 10-2 : Time-based 불완전 복구와 READ ONLY 검증
 과정      : Oracle Database 19c Backup & Recovery
 환경      : Oracle 19.3.0 / Oracle Linux 7 / non-CDB ORCL / ARCHIVELOG
 소요 시간 : 약 25분
================================================================================

--------------------------------------------------------------------------------
[1] 시나리오 개요
--------------------------------------------------------------------------------
-- 사용자가 대량 UPDATE를 잘못 수행해 그 직전 시점으로 되돌린다.
-- 사고 시각을 근거로 UNTIL TIME 을 지정한다.
-- RESETLOGS 전에 READ ONLY로 열어 복구 지점을 검증한다.
-- 목표보다 이른 지점이면 이어서 적용할 수 있음을 확인한다.
-- 복구 유형 : 불완전 복구(Time-based, 의도적 시점 복귀)

--------------------------------------------------------------------------------
[2] 사전 조건
--------------------------------------------------------------------------------
-- 실습 10-1을 마친 상태에서 이어서 진행한다. 10-1 끝에 받은 전체 백업을 쓴다.
-- Flashback 등 대안이 없는 상황을 가정한다.

[oracle@oel7v9 ~]$ sqlplus / as sysdba

SYS@orcl> SET LINESIZE 200
SYS@orcl> ALTER SESSION SET nls_date_format = 'YYYY-MM-DD HH24:MI:SS';
Session altered.

[4] 장애 유발 : 잘못된 대량 UPDATE
--------------------------------------------------------------------------------
-- [터미널 2] 사용자가 WHERE 절을 빠뜨린 UPDATE를 수행한다.

[oracle@oel7v9 ~]$ sqlplus hr/hr

107 rows updated.

HR@orcl> COMMIT;

HR@orcl> SELECT TO_CHAR(SYSDATE, 'HH24:MI:SS') AS now FROM dual;

--------
10:22:40

-- [터미널 1]

SYS@orcl> SELECT COUNT(*), MAX(salary) FROM hr.emp102;

  COUNT(*) MAX(SALARY)
---------- -----------
       107           0

-- 모든 급여가 0이 되었다.

SYS@orcl> ALTER SYSTEM ARCHIVE LOG CURRENT;
SYS@orcl> INSERT INTO hr.insa_2025 VALUES (11, SYSDATE);
SYS@orcl> COMMIT;
SYS@orcl> ALTER SYSTEM ARCHIVE LOG CURRENT;
System altered.

[6] 진단
--------------------------------------------------------------------------------
-- 대안을 먼저 검토한다.

SYS@orcl> SELECT COUNT(*), MAX(salary) FROM hr.emp102 AS OF TIMESTAMP
  2    TO_TIMESTAMP('2025-05-12 10:20:00', 'YYYY-MM-DD HH24:MI:SS');

  COUNT(*) MAX(SALARY)
---------- -----------
       107       24000

-- 사고 직후라 UNDO 가 아직 남아 있어 Flashback Query 가 된다.
-- 실무라면 여기서 FLASHBACK TABLE 로 끝낸다. 이것이 첫 번째 선택지다.
-- 이 실습은 사고를 늦게 발견해 UNDO_RETENTION(기본 900초)을 넘긴 상황,
-- 즉 이 조회가 ORA-01555 로 실패하는 상황을 가정하고 시점 복구를 연습한다.

SYS@orcl> SELECT flashback_on FROM v$database;

FLASHBACK_ON
------------------
NO

-- Flashback Database 도 켜져 있지 않다. 전체 시점 복구를 선택한다.

SYS@orcl> SELECT sequence#, first_change#, next_change#,
  2         TO_CHAR(first_time, 'HH24:MI:SS') AS first_time
  3  FROM   v$log_history
  4  WHERE  resetlogs_change# = (SELECT resetlogs_change# FROM v$database)
  5  ORDER BY sequence# DESC FETCH FIRST 5 ROWS ONLY;

 SEQUENCE# FIRST_CHANGE# NEXT_CHANGE# FIRST_TIME
---------- ------------- ------------ ----------
         5       2422600      2422940 10:23:05
         4       2422180      2422600 10:22:50
         3       2421800      2422180 10:14:30
         2       2421400      2421800 10:08:02
         1       2420101      2421400 09:31:20

-- 그냥 ORDER BY sequence# 로 하면 안 된다. 10-1 의 RESETLOGS 로 시퀀스가 1부터
-- 다시 시작했으므로 이전 인카네이션의 60번대가 위로 올라온다.
-- 현재 인카네이션(resetlogs_change#)으로 걸러서 본다.
-- 사고(10:22:40)는 시퀀스 3 안에 있다. 10번 행(10:14:22)은 시퀀스 2 다.

SYS@orcl> !ls /home/oracle/backup/ch10/*.dbf | wc -l
7

-- 판정
--   ① 사고 시각 : 10:22:40 (COMMIT 시각)
--   ② 목표 지점 : 10:22:40 직전
--   ③ 백업본 : 10-1 종료 시점(SCN 2421380)의 전체 백업 보유
--   ④ 아카이브 : 시퀀스 1~5 연속 보유
--   → UNTIL TIME 으로 사고 직전까지 복구

--------------------------------------------------------------------------------
[7] 복구 절차 : 오류 발생 → 원인 파악 → 수정
--------------------------------------------------------------------------------
SYS@orcl> SHUTDOWN IMMEDIATE
SYS@orcl> !cp -p /home/oracle/backup/ch10/*.dbf /u01/app/oracle/oradata/orcl/
SYS@orcl> STARTUP MOUNT

-- 안전하게 잡으려고 목표보다 이른 시각을 지정한다.

SYS@orcl> SET AUTORECOVERY ON
SYS@orcl> RECOVER DATABASE UNTIL TIME '2025-05-12 10:10:00';
ORA-00279: change 2421380 generated at 05/12/2025 09:57:10 needed for thread 1
ORA-00289: suggestion : /home/oracle/arch1/arch_1_1_1200536880.arc
ORA-00280: change 2421380 for thread 1 is in sequence #1


ORA-00279: change 2421400 generated at 05/12/2025 10:08:02 needed for thread 1
ORA-00289: suggestion : /home/oracle/arch1/arch_1_2_1200536880.arc
ORA-00280: change 2421400 for thread 1 is in sequence #2


Log applied.
Media recovery complete.

SYS@orcl> ALTER DATABASE OPEN READ ONLY;
ALTER DATABASE OPEN READ ONLY
*
ERROR at line 1:
ORA-16005: database requires recovery

-- << 원인 파악 >>
-- 10-1 에서 본 것과 같다. 컨트롤파일이 현재 것이라 리두 스레드가 시퀀스 6 까지
-- 이어진 것을 알고 있고, 그 앞에서 멈춘 파일들을 "복구가 덜 됐다" 고 본다.
-- READ ONLY 로 열려면 컨트롤파일도 복구 지점에서 멈춘 것으로 다뤄야 한다.
-- USING BACKUP CONTROLFILE 을 붙이면 현재 컨트롤파일을 백업본처럼 취급해
-- 복구 지점을 컨트롤파일에도 기록한다. 이후에는 RESETLOGS 로만 열 수 있다.
-- 어차피 불완전 복구는 RESETLOGS 로 끝나므로 잃는 것이 없다.

-- << 수정 >>

SYS@orcl> RECOVER DATABASE UNTIL TIME '2025-05-12 10:10:00' USING BACKUP CONTROLFILE;
Media recovery complete.

-- 이미 그 지점까지 적용되어 있어 더 읽을 로그가 없다. 컨트롤파일 표시만 바뀐다.

SYS@orcl> SELECT controlfile_type FROM v$database;

CONTROL
-------
BACKUP

SYS@orcl> ALTER DATABASE OPEN READ ONLY;

Database altered.

SYS@orcl> SELECT COUNT(*), MAX(salary) FROM hr.emp102;

  COUNT(*) MAX(SALARY)
---------- -----------
       107       24000

-- 잘못된 UPDATE는 사라졌다.

SYS@orcl> SELECT id, TO_CHAR(order_date, 'HH24:MI:SS') AS t FROM hr.insa_2025 ORDER BY id;

        ID T
---------- --------
         1 09:04:11
         2 09:08:30

-- << 원인 파악 >>
-- 10:14:22에 넣은 10번 행이 사라졌다.
-- 그것은 정상 업무 데이터이며 되돌릴 대상이 아니었다.
-- 목표 시각을 10:10으로 잡아 12분 이르게 복구된 것이다.
-- 되돌릴 변경만 사라져야 하고 정상 데이터는 남아야 한다.
-- 아직 RESETLOGS를 하지 않았으므로 더 적용할 수 있다.

SYS@orcl> SELECT checkpoint_change#, TO_CHAR(checkpoint_time, 'HH24:MI:SS') AS stopped_at
  2  FROM   v$datafile_header WHERE file# = 1;

CHECKPOINT_CHANGE# STOPPED_AT
------------------ ----------
           2421520 10:10:04

-- 멈춘 지점은 파일 헤더로 본다. 백업본에서 복원한 SYSTEM 의 SCN-시각 매핑 표는
-- 백업 시점까지만 있어서 SCN_TO_TIMESTAMP 는 ORA-08181 로 실패한다.
-- UNTIL TIME 은 초 단위 근사다. 지정한 10:10:00 을 지난 첫 리두 레코드 앞에서
-- 멈추므로 헤더 시각은 목표보다 몇 초 뒤일 수 있다.

-- << 수정 >>
-- 사고 직전인 10:22:30 까지 이어서 적용한다.

SYS@orcl> SHUTDOWN IMMEDIATE
SYS@orcl> STARTUP MOUNT

SYS@orcl> SET AUTORECOVERY ON
SYS@orcl> RECOVER DATABASE UNTIL TIME '2025-05-12 10:22:30';
ORA-00283: recovery session canceled due to errors
ORA-01610: recovery using the BACKUP CONTROLFILE option must be done

-- 컨트롤파일이 BACKUP 으로 표시된 뒤에는 그 옵션 없이는 복구를 이어 갈 수 없다.

SYS@orcl> RECOVER DATABASE UNTIL TIME '2025-05-12 10:22:30' USING BACKUP CONTROLFILE;
ORA-00279: change 2421520 generated at 05/12/2025 10:10:04 needed for thread 1
ORA-00289: suggestion : /home/oracle/arch1/arch_1_2_1200536880.arc
ORA-00280: change 2421520 for thread 1 is in sequence #2


ORA-00279: change 2421800 generated at 05/12/2025 10:14:30 needed for thread 1
ORA-00289: suggestion : /home/oracle/arch1/arch_1_3_1200536880.arc
ORA-00280: change 2421800 for thread 1 is in sequence #3
ORA-00278: log file '/home/oracle/arch1/arch_1_2_1200536880.arc' no longer needed for this recovery


Log applied.
Media recovery complete.

-- 복원을 다시 하지 않았다. 첫 번째로 멈춘 2421520 부터 이어서 적용되었다.

SYS@orcl> SELECT checkpoint_change#, TO_CHAR(checkpoint_time, 'HH24:MI:SS') AS stopped_at
  2  FROM   v$datafile_header WHERE file# = 1;

------------------ ----------
           2422560 10:22:33

SYS@orcl> SELECT COUNT(*), MAX(salary), MIN(salary) FROM hr.emp102;

  COUNT(*) MAX(SALARY) MIN(SALARY)

SYS@orcl> SELECT resetlogs_change#, TO_CHAR(resetlogs_time, 'HH24:MI:SS') AS resetlogs_time,
  2         controlfile_type
  3  FROM   v$database;

RESETLOGS_CHANGE# RESETLOGS_TIME CONTROL
----------------- -------------- -------
          2422561 10:41:10       CURRENT

-- 새 인카네이션은 멈춘 지점 다음 SCN(2422560 + 1)에서 시작한다.
-- RESETLOGS 로 열리면서 컨트롤파일은 다시 CURRENT 가 되었다.
-- (RESETLOGS 뒤의 SCN_TO_TIMESTAMP 는 10-1 에서 본 대로 엉뚱한 시각을 낸다.)

SYS@orcl> SELECT incarnation#, resetlogs_change#, status FROM v$database_incarnation
  2  ORDER BY incarnation#;

INCARNATION# RESETLOGS_CHANGE# STATUS
------------ ----------------- -------
           1                 1 PARENT
           2           2420101 PARENT
           3           2422561 CURRENT

SYS@orcl> SELECT id FROM hr.insa_2025 ORDER BY id;

        ID
----------
         1
         2
        10

-- 사고 이후 넣은 11번은 사라졌다. 예상된 손실이다.

SYS@orcl> SELECT COUNT(*) FROM v$tempfile;

  COUNT(*)
----------
         1

-- 템프파일은 그대로다. 컨트롤파일을 되돌리거나 다시 만들지 않았기 때문이다.
-- USING BACKUP CONTROLFILE 은 현재 컨트롤파일에 표시만 한 것이라 템프파일 기록도 남는다.
-- RESETLOGS 오픈은 템프파일 기록을 지우지 않는다.
-- 여기서 ADD TEMPFILE 을 하면 ORA-01537(file already part of database)로 거부된다.
-- 컨트롤파일을 재생성한 경우에만 템프파일이 사라지며 그때 다시 만든다(11-6, 11-7).

-- 손실 구간을 정리한다.
--   복구 지점 : SCN 2422560 / 10:22:33
--   손실 구간 : 10:22:33 이후 ~ 복구 시작 시각
--   영향 : hr.insa_2025 의 11번 이후 데이터, 그 시간대의 모든 업무

SYS@orcl> SHUTDOWN IMMEDIATE
SYS@orcl> !rm -rf /home/oracle/backup/ch10; mkdir -p /home/oracle/backup/ch10
SYS@orcl> !cp -p /u01/app/oracle/oradata/orcl/*.dbf /home/oracle/backup/ch10/
SYS@orcl> !rm -f /home/oracle/backup/ch10/temp01.dbf
SYS@orcl> STARTUP
SYS@orcl> ALTER DATABASE BACKUP CONTROLFILE TO
  2    '/home/oracle/backup/control_ch10.bkp' REUSE;

-- 실무 포인트
-- 1) 논리적 오류에는 대안을 먼저 검토한다.
--    Flashback Query, Flashback Table, Flashback Database, RECOVER TABLE 순으로 확인한다.
--    UNDO 가 남아 있는 동안은 Flashback Table 이 답이다.
--    전체 시점 복구는 정상 업무까지 되돌리므로 최후의 선택지다.
--
-- 2) NLS_DATE_FORMAT 을 먼저 지정한다.
--    형식이 환경마다 달라 지정하지 않으면 혼동이 생긴다.
--
-- 3) READ ONLY 검증은 USING BACKUP CONTROLFILE 과 짝이다.
--    현재 컨트롤파일 그대로면 ORA-16005 로 열리지 않는다.
--    한 번 붙이면 이후 RECOVER 도 같은 옵션이 필요하다(ORA-01610).
--
-- 4) 목표보다 이르게 잡고 READ ONLY로 확인하며 나아간다.
--    부족하면 이어서 적용할 수 있지만 지나치면 복원부터 다시 해야 한다.
--    이 비대칭이 보수적 접근을 권장하는 이유다.
--
-- 5) 검증은 두 방향으로 한다.
--    되돌리려던 변경이 사라졌는가와 정상 데이터가 남아 있는가를 함께 본다.
--    한쪽만 보면 이 실습의 첫 시도처럼 잘못된 판단을 하게 된다.
--
-- 6) 이어서 적용할 때는 복원이 필요 없다.
--    SHUTDOWN 후 MOUNT에서 RECOVER를 다시 수행하면 멈춘 지점부터 진행된다.
--    이미 적용한 리두를 다시 적용하지 않는다. 멈춘 지점은 v$datafile_header 로 본다.
--
-- 7) 사고 이후의 정상 업무도 함께 사라진다.
--    이 실습에서 11번 행이 그렇다. 손실 구간을 현업에 정확히 통보해야 한다.

SYS@orcl> EXIT
