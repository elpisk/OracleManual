================================================================================
 실습 10-1 : 아카이브 손상 — Cancel-based 불완전 복구
 과정      : Oracle Database 19c Backup & Recovery
 환경      : Oracle 19.3.0 / Oracle Linux 7 / non-CDB ORCL / ARCHIVELOG
 소요 시간 : 약 25분

--------------------------------------------------------------------------------
[1] 시나리오 개요
--------------------------------------------------------------------------------
-- 데이터파일이 손상되었고 복구에 필요한 아카이브 하나가 함께 손상되었다.
-- 연속되지 않은 리두는 적용할 수 없으므로 완전 복구가 불가능하다.
-- 적용 가능한 마지막 지점까지 넣고 CANCEL로 멈춘 뒤 RESETLOGS로 연다.
-- 불완전 복구의 기본 절차를 익히는 실습이다.
-- 복구 유형 : 불완전 복구(Cancel-based)

--------------------------------------------------------------------------------
[2] 사전 조건
--------------------------------------------------------------------------------
-- ARCHIVELOG 모드이며 실습 직전에 전체 백업을 새로 받는다.
-- 데이터파일은 /u01/app/oracle/oradata/orcl 에 있다.
-- 아카이브 대상은 2장에서 정한 /home/oracle/arch1 이다.

[oracle@oel7v9 ~]$ sqlplus / as sysdba

SYS@orcl> SET LINESIZE 200
SYS@orcl> COL name FOR a44

-- 실무 포인트
-- 1) 불완전 복구는 모든 데이터파일을 복원해야 한다.
--    손상된 파일만 복원하면 RECOVER 는 현재 파일 기준으로 CURRENT 리두부터 달라고 하고,
--    CANCEL 하면 ORA-01194(UNTIL CANCEL) 또는 ORA-01152(UNTIL TIME/CHANGE)가 난다.
--    데이터베이스 전체를 과거의 한 시점으로 되돌리는 작업이기 때문이다.
--
-- 2) 리두는 앞으로만 적용되고 뒤로 되돌릴 수 없다.
--    그래서 모든 파일이 목표 시점보다 이전 상태에서 출발해야 한다.
--    v$datafile_header 의 체크포인트 시각을 비교하면 어긋난 파일을 찾을 수 있다.
--
-- 3) 아카이브 손상은 파일 존재 여부로는 알 수 없다.
--    v$archived_log 에는 STATUS가 A로 남아 있어도 내용이 깨져 있을 수 있다.
--    리두 블록이 깨지면 적용 도중 ORA-00353/ORA-00354(또는 ORA-00368)로,
--    헤더가 깨지면 열지도 못하고 ORA-00308/ORA-27048 로 드러난다.
--
-- 4) 온라인 리두로 대체 가능한지 먼저 확인한다.
--    필요한 시퀀스가 온라인 리두에 남아 있으면 RECOVER 가 알아서 그것을 읽고
--    완전 복구로 끝난다. 이 실습은 그것을 막으려고 스위치를 세 번 더 했다.
--    v$log 의 최소 first_change# 가 복구 시작 SCN 보다 크면 대체할 수 없다.
--
-- 5) RESETLOGS 전의 검증은 파일 헤더와 로그 이력으로 한다.
--    현재 컨트롤파일로는 READ ONLY 오픈이 ORA-16005 로 막힌다.
--    v$datafile_header 의 체크포인트가 모두 같은지, 그 SCN 이 v$log_history 의
--    어느 시퀀스 경계인지 확인한다. 부족하면 RESETLOGS 전이므로 RECOVER 를 이어 갈 수 있다.
--    데이터로 검증하려면 USING BACKUP CONTROLFILE 로 복구해야 한다(10-2).
--
-- 6) 데이터파일 수준과 테이블스페이스 수준은 별개다.
--    OFFLINE IMMEDIATE 로 내린 파일은 RECOVER DATABASE 가 건너뛴다.
--    MOUNT 에서 ALTER DATABASE DATAFILE n ONLINE 으로 복구 대상에 넣어야 한다.
--    딕셔너리의 테이블스페이스 상태는 복구 지점의 것으로 돌아간다.
--
-- 7) RESETLOGS 이후 즉시 전체 백업을 받는다.
--    인카네이션이 달라져 이전 백업본과 아카이브를 그대로 쓸 수 없다.

SYS@orcl> EXIT
