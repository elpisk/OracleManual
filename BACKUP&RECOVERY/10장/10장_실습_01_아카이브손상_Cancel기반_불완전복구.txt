================================================================================
 실습 10-1 : 아카이브 손상 — Cancel-based 불완전 복구
 과정      : Oracle Database 19c Backup & Recovery
 환경      : Oracle 19.3.0 / Oracle Linux 7 / non-CDB ORCL / ARCHIVELOG
 소요 시간 : 약 25분
================================================================================

--------------------------------------------------------------------------------
[1] 시나리오 개요
--------------------------------------------------------------------------------
-- 데이터파일이 손상되었고 복구에 필요한 아카이브 하나가 함께 손상되었다.
-- 연속되지 않은 리두는 적용할 수 없으므로 완전 복구가 불가능하다.
-- 적용 가능한 마지막 지점까지 넣고 CANCEL로 멈춘 뒤 RESETLOGS로 연다.
-- 불완전 복구의 기본 절차를 익히는 실습이다.
-- 복구 유형 : 불완전 복구(Cancel-based)

--------------------------------------------------------------------------------
[2] 사전 조건
--------------------------------------------------------------------------------
-- ARCHIVELOG 모드이며 실습 직전에 전체 백업을 새로 받는다.
-- 데이터파일은 /u02/oradata/ORCL 에 있다(9장 실습에서 이전됨).

SYS@orcl> COL name FOR a44

--------------------------------------------------------------------------------
[7] 복구 절차 : 오류 발생 → 원인 파악 → 수정
--------------------------------------------------------------------------------
-- 손상된 파일만 복원한 채 불완전 복구를 시도한다.

SYS@orcl> SHUTDOWN ABORT
SYS@orcl> STARTUP MOUNT

SYS@orcl> SET AUTORECOVERY OFF
SYS@orcl> RECOVER DATABASE UNTIL CANCEL;
ORA-00283: recovery session canceled due to errors
ORA-01152: file 1 was not restored from a sufficiently old backup
ORA-01110: data file 1: '/u02/oradata/ORCL/system01.dbf'

-- << 원인 파악 >>
-- 파일 1은 현재 상태 그대로다. 목표 시점보다 미래에 있다.
-- 불완전 복구는 데이터베이스 전체를 과거의 한 시점으로 되돌리는 작업이다.
-- 모든 데이터파일이 그 시점보다 이전 백업본에서 출발해야 한다.
-- 리두는 앞으로만 적용되고 뒤로 되돌릴 수 없기 때문이다.
-- 완전 복구에서 손상된 파일만 복원하던 습관이 여기서 문제가 된다.

SYS@orcl> SELECT file#, checkpoint_change#,
  2         TO_CHAR(checkpoint_time, 'HH24:MI:SS') AS ckpt_time
  3  FROM   v$datafile_header ORDER BY file#;

     FILE# CHECKPOINT_CHANGE# CKPT_TIME
---------- ------------------ ----------
         1            2420900 09:16:05
         3            2420900 09:16:05
         4            2420900 09:16:05
         7            2419200 09:02:11

-- 파일 7만 백업 시점이고 나머지는 현재 상태다.

-- << 수정 >>

SYS@orcl> !cp -p /home/oracle/backup/ch10/*.dbf /u02/oradata/ORCL/

SYS@orcl> SELECT file#, checkpoint_change# FROM v$datafile_header ORDER BY file#;

     FILE# CHECKPOINT_CHANGE#
---------- ------------------
         1            2419200
         3            2419200
         4            2419200
         7            2419200

-- 모든 파일이 같은 시점이다.

SYS@orcl> RECOVER DATABASE UNTIL CANCEL;

ORA-00280: change 2419200 for thread 1 is in sequence #60

-- 손상된 시퀀스 62 직전에서 멈췄다.

SYS@orcl> ALTER DATABASE OPEN READ ONLY;

Database altered.

SYS@orcl> SELECT id, TO_CHAR(order_date, 'HH24:MI:SS') AS t FROM hr.insa_2025 ORDER BY id;

        ID T
---------- --------
         1 09:04:11
         2 09:08:30

-- 09:12:44에 넣은 3번이 없다. 예상한 복구 지점이 맞다.

SYS@orcl> SHUTDOWN IMMEDIATE
SYS@orcl> STARTUP MOUNT
SYS@orcl> ALTER DATABASE OPEN RESETLOGS;

Database altered.

--   손실 구간 : 09:12:40 이후 ~ 장애 시각

-- 즉시 전체 백업을 받는다.

SYS@orcl> SHUTDOWN IMMEDIATE
SYS@orcl> !rm -rf /home/oracle/backup/ch10 && mkdir -p /home/oracle/backup/ch10
SYS@orcl> !cp -p /u02/oradata/ORCL/*.dbf /home/oracle/backup/ch10/
SYS@orcl> !rm -f /home/oracle/backup/ch10/temp01.dbf
SYS@orcl> STARTUP

-- 실무 포인트
-- 1) 불완전 복구는 모든 데이터파일을 복원해야 한다.
--    손상된 파일만 복원하면 ORA-01152가 발생한다.
--    데이터베이스 전체를 과거의 한 시점으로 되돌리는 작업이기 때문이다.
--
-- 2) 리두는 앞으로만 적용되고 뒤로 되돌릴 수 없다.
--    그래서 모든 파일이 목표 시점보다 이전 상태에서 출발해야 한다.
--    v$datafile_header 의 체크포인트 시각을 비교하면 어긋난 파일을 찾을 수 있다.
--
-- 3) 아카이브 손상은 파일 존재 여부로는 알 수 없다.
--    v$archived_log 에는 STATUS가 A로 남아 있어도 내용이 깨져 있을 수 있다.
--    적용 시점에 ORA-00368이나 ORA-00353으로 드러난다.
--
-- 4) 온라인 리두로 대체 가능한지 먼저 확인한다.
--    이 실습에서는 최소 온라인 리두 SCN이 복구 시작 SCN보다 커서 대체할 수 없었다.
--    가능했다면 완전 복구로 끝났을 것이다.
--
-- 5) RESETLOGS 전에 READ ONLY로 확인한다.
--    복구 지점이 예상과 맞는지 데이터로 검증할 수 있다.
--    부족하면 다시 MOUNT로 내려 이어서 적용할 수 있다.
--
-- 6) RESETLOGS 이후 즉시 전체 백업을 받는다.
--    인카네이션이 달라져 이전 백업본과 아카이브를 그대로 쓸 수 없다.

SYS@orcl> EXIT
