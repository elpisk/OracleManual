 실습 10-7 : INACTIVE 리두 로그 삭제 — 정상 종료 후와 운영 중
 과정      : Oracle Database 19c Backup & Recovery
 환경      : Oracle 19.3.0 / Oracle Linux 7 / non-CDB ORCL / ARCHIVELOG
 소요 시간 : 약 22분

--------------------------------------------------------------------------------
[1] 시나리오 개요
--------------------------------------------------------------------------------
-- INACTIVE 리두 로그 그룹이 전손된 두 경우를 비교한다.
--   정상 종료 후 유실 → 아카이브 완료 상태, CLEAR로 손실 없이 처리
--   운영 중 유실, 아카이브 미완료 → ORA-00350, 원인 확인이 먼저
-- ARCHIVED 컬럼 확인이 판단의 출발점임을 확인한다.
-- 복구 유형 : 복구 불필요(CLEAR) 또는 리두 구간 손실

-- 스위치 직후의 그룹은 체크포인트가 끝날 때까지 ACTIVE 다.
-- ACTIVE 인 그룹은 CLEAR 자체가 ORA-01624(크래시 복구에 필요)로 거부되므로
-- 체크포인트를 끝내 INACTIVE 로 만들어 둔다.

SYS@orcl> SELECT group#, sequence#, archived, status FROM v$log ORDER BY group#;

    GROUP#  SEQUENCE# ARC STATUS
---------- ---------- --- ----------------
         1          4 NO  CURRENT
         3          2 NO  INACTIVE
         4          3 NO  INACTIVE

-- 아카이브가 밀려 ARCHIVED가 NO다.

SYS@orcl> !rm -f /u01/app/oracle/oradata/orcl/redo03.log /u02/oradata/orcl/redo03b.log

    GROUP# MEMBER                                       STATUS

         3 /u01/app/oracle/oradata/orcl/redo03.log

[7] 복구 절차 : 오류 발생 → 원인 파악 → 수정
--------------------------------------------------------------------------------
SYS@orcl> ALTER DATABASE CLEAR LOGFILE GROUP 3;
ALTER DATABASE CLEAR LOGFILE GROUP 3
*
ERROR at line 1:
ORA-00350: log 3 of instance orcl (thread 1) needs to be archived
ORA-00312: online log 3 thread 1: '/u01/app/oracle/oradata/orcl/redo03.log'
ORA-00312: online log 3 thread 1: '/u02/oradata/orcl/redo03b.log'

-- << 원인 파악 >>
-- ARCHIVED가 NO이므로 그 내용이 아카이브에 남아 있지 않다.
-- 여기서 습관적으로 UNARCHIVED를 붙이면 그 구간의 리두를 버리게 된다.
-- 먼저 NO인 이유를 확인해야 한다.
-- 파일이 없어서인지, 아카이브 대상에 문제가 있어서인지 구분해야 한다.

SYS@orcl> COL destination FOR a20
SYS@orcl> COL error FOR a40
SYS@orcl> SELECT dest_id, destination, status, error FROM v$archive_dest
  2  WHERE  destination IS NOT NULL;

   DEST_ID DESTINATION          STATUS    ERROR
---------- -------------------- --------- ----------------------------------------
         1 /home/oracle/arch1   ERROR     ORA-19504: failed to create file ""

SYS@orcl> !ls -ld /home/oracle/arch1
dr-x------. 2 oracle dba 4096 May 12 15:02 /home/oracle/arch1

-- 대상 디렉터리에 쓸 수 없다. 이것이 아카이브가 밀린 원인이다.
-- 그룹 4는 파일이 멀쩡하므로 대상을 고치면 아카이브할 수 있다.
-- 그룹 3은 파일이 이미 없어 아카이브할 원본이 없다.

-- << 수정 >>
-- 먼저 대상을 고치고 밀린 아카이브를 처리한다.

SYS@orcl> !chmod 700 /home/oracle/arch1

SYS@orcl> ALTER SYSTEM ARCHIVE LOG ALL;
ALTER SYSTEM ARCHIVE LOG ALL
*
ERROR at line 1:
ORA-00313: open failed for members of log group 3 of thread 1
ORA-00312: online log 3 thread 1: '/u02/oradata/orcl/redo03b.log'
ORA-27037: unable to obtain file status
Linux-x86_64 Error: 2: No such file or directory
Additional information: 7
ORA-00312: online log 3 thread 1: '/u01/app/oracle/oradata/orcl/redo03.log'
ORA-27037: unable to obtain file status
Linux-x86_64 Error: 2: No such file or directory
Additional information: 7

SYS@orcl> SELECT group#, sequence#, archived, status FROM v$log ORDER BY group#;

    GROUP#  SEQUENCE# ARC STATUS
---------- ---------- --- ----------------
         1          4 NO  CURRENT
         3          2 NO  INACTIVE
         4          3 NO  INACTIVE

-- ARCHIVE LOG ALL 은 가장 오래된 시퀀스부터 순서대로 처리한다.
-- 첫 번째인 그룹 3(시퀀스 2)의 파일이 없어 거기서 멈췄고 그룹 4도 처리되지 않았다.
-- 아카이버도 아직 손을 놓고 있다. 대상이 ERROR 로 표시되면 REOPEN(기본 300초)이
-- 지나야 다시 시도하기 때문이다.

SYS@orcl> SELECT dest_id, status, error, reopen_secs FROM v$archive_dest WHERE dest_id = 1;

   DEST_ID STATUS    ERROR                                    REOPEN_SECS
---------- --------- ---------------------------------------- -----------
         1 ERROR     ORA-19504: failed to create file ""              300

SYS@orcl> ALTER SYSTEM SET log_archive_dest_state_1 = ENABLE;

System altered.

SYS@orcl> SELECT dest_id, status, error FROM v$archive_dest WHERE dest_id = 1;

   DEST_ID STATUS    ERROR
---------- --------- ----------------------------------------
         1 VALID

-- 상태를 다시 ENABLE 로 주면 기다리지 않고 바로 VALID 가 된다.
-- 이제 그룹 3만 원본이 없다. 이 경우에만 UNARCHIVED가 정당하다.

SYS@orcl> ALTER DATABASE CLEAR UNARCHIVED LOGFILE GROUP 3;

Database altered.

SYS@orcl> SELECT group#, sequence#, archived, status FROM v$log ORDER BY group#;

    GROUP#  SEQUENCE# ARC STATUS
---------- ---------- --- ----------------
         1          4 NO  CURRENT
         3          0 YES UNUSED
         4          3 NO  INACTIVE

-- 그룹 4(시퀀스 3)는 아직 NO 다. 파일이 있으니 다음 스위치 때 아카이버가 처리한다.

    GROUP#  SEQUENCE# ARC STATUS

         4          6 NO  CURRENT

-- 그룹 3이 순환에 복귀했고 밀렸던 시퀀스 3·4 도 아카이브되었다.

SYS@orcl> SELECT sequence#, status FROM v$archived_log
  2  WHERE  resetlogs_change# = (SELECT resetlogs_change# FROM v$database)
  3  ORDER BY sequence#;

 SEQUENCE# S
---------- -
         1 A
         2 D
         3 A
         4 A
         5 A

SYS@orcl> SELECT MIN(sequence#), MAX(sequence#), COUNT(*),
  2         MAX(sequence#) - MIN(sequence#) + 1 AS expected
  3  FROM   v$archived_log
  4  WHERE  status = 'A'
  5  AND    resetlogs_change# = (SELECT resetlogs_change# FROM v$database);

MIN(SEQUENCE#) MAX(SEQUENCE#)   COUNT(*)   EXPECTED
-------------- -------------- ---------- ----------
             1              5          4          5

-- 시퀀스 2가 빠졌다. 버린 구간이며 기록은 D 로 남는다.
-- 이 시점 이전의 백업본은 사실상 무효가 되었다.

-- 버린 구간이 있으므로 즉시 전체 백업을 받는다.

SYS@orcl> SHUTDOWN IMMEDIATE
SYS@orcl> !rm -rf /home/oracle/backup/ch10; mkdir -p /home/oracle/backup/ch10
SYS@orcl> !cp -p /u01/app/oracle/oradata/orcl/*.dbf /home/oracle/backup/ch10/
SYS@orcl> !rm -f /home/oracle/backup/ch10/temp01.dbf
SYS@orcl> STARTUP
SYS@orcl> ALTER DATABASE BACKUP CONTROLFILE TO
  2    '/home/oracle/backup/control_ch10.bkp' REUSE;

-- 실무 포인트
-- 1) 판단의 출발점은 v$log의 ARCHIVED 컬럼이다.
--    YES이면 CLEAR LOGFILE 로 손실 없이 처리된다.
--    NO이면 UNARCHIVED가 필요하며 그 구간의 리두를 잃는다.
--
-- 2) 온라인 리두 그룹이 전손된 채 STARTUP 하면 OPEN 단계에서 인스턴스가 내려간다.
--    클라이언트에는 ORA-03113 만 보이고 ORA-00313 은 alert 로그에 있다.
--    STARTUP MOUNT 로 올려 CLEAR 한 뒤 OPEN 한다.
--
-- 3) ARCHIVED가 NO인 이유를 먼저 확인한다.
--    아카이브 대상 문제로 밀린 것이라면 대상을 고치고 처리하면 손실이 없다.
--    파일이 이미 없어 아카이브할 수 없는 경우에만 UNARCHIVED를 쓴다.
--    확인 없이 두 그룹 모두 UNARCHIVED로 처리했다면 불필요한 손실이 생겼을 것이다.
--
-- 4) 대상을 고쳐도 아카이버는 바로 돌아오지 않는다.
--    v$archive_dest 가 ERROR 이면 REOPEN(기본 300초) 뒤에 재시도한다.
--    log_archive_dest_state_n 을 ENABLE 로 다시 주면 즉시 VALID 가 된다.
--    ARCHIVE LOG ALL 은 가장 오래된 그룹부터 처리하므로 그 그룹이 없으면 거기서 멈춘다.
--
-- 5) ORA-00350과 ORA-01624를 구분한다.
--    전자는 아카이브가 완료되지 않았다는 뜻이고,
--    후자는 인스턴스 복구에 필요한 그룹(ACTIVE)이라는 뜻이다. 체크포인트로 INACTIVE 가 되어야 한다.
--
-- 6) UNARCHIVED로 비운 뒤에는 시퀀스가 빠진다.
--    연속성 점검에서 개수와 기대값이 달라지며 그 이전 백업본이 무효가 된다.
--    즉시 전체 백업을 받아야 한다.
--
-- 7) 커밋된 데이터는 사라지지 않는다.
--    이 실습에서 3번 행이 그대로 남아 있다.
--    리두를 버리는 것은 미래의 복구 수단을 잃는 것이지 현재 데이터를 잃는 것이 아니다.

SYS@orcl> EXIT
