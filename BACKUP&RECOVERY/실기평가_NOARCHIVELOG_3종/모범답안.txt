================================================================================
 ■ NOARCHIVELOG 복구 실기평가 — 3종 모범답안
 과정      : Oracle Database 19c Backup & Recovery (1~7장 범위)
 환경      : Oracle 19.3.0 / Oracle Linux 7 / non-CDB ORCL / NOARCHIVELOG
================================================================================

이 문서는 문제지의 과제 1-1 부터 3-3 까지에 대응하는 모범답안이다.
각 과제를 【판정】 무엇을 보고 경로를 정했는가 · 【수행】 실제로 실행한 명령 ·
【검증】 복구가 끝났음을 무엇으로 확인했는가 세 축으로 나눈다.

채점은 명령의 정확성보다 판정 근거의 유무를 먼저 본다.

[검증됨] 표시가 붙은 출력은 이 문서를 만들 때 실제 랩에서 실행해 얻은 값이다.
표시가 없는 출력은 형태만 보인 것이므로 시험장에서는 그 자리에서 얻은 값으로 대체한다.
SCN·시퀀스·시각은 매 실행마다 달라진다. 중요한 것은 값 자체가 아니라 두 값의 대소 관계다.

================================================================================
 이 평가를 관통하는 판정 틀
================================================================================
데이터파일 계열 (시나리오 1)
  ① 무엇이 손상되었는가        v$recover_file
  ② 백업본에 그 파일이 있는가   !ls
  ③ 필요한 리두가 살아 있는가   v$recover_file.change# >= MIN(first_change#)
  ④ 떼어 낼 수 있는가          OFFLINE DROP 성공 여부

컨트롤파일 계열 (시나리오 2) — 위 네 단계 앞에 0단계가 붙는다
  ⓪ MOUNT 가 되는가            되지 않으면 ①~④ 조회 자체가 불가능하다

리두 계열 (시나리오 3) — 두 질문이 결과를 가른다
  ① 손상된 그룹이 CURRENT 인가 INACTIVE 인가
  ② 종료가 정상이었는가 비정상이었는가

================================================================================
 시나리오 1  데이터파일 계열 장애
================================================================================

--------------------------------------------------------------------------------
 과제 1-1. USERS 데이터파일 유실 — 리두 생존  [30점]
--------------------------------------------------------------------------------
【판정】

1-1.2 증상  [검증됨]

  SYS@orcl> SELECT COUNT(*) FROM hr.exam_log;
  SELECT COUNT(*) FROM hr.exam_log
                       *
  ERROR at line 1:
  ORA-01116: error in opening database file 7
  ORA-01110: data file 7: '/u01/app/oracle/oradata/orcl/users01.dbf'
  ORA-27041: unable to open file
  Linux-x86_64 Error: 2: No such file or directory
  Additional information: 3

  ▸ 데이터베이스는 OPEN 을 유지한다. 파일 7 을 건드리는 조회만 실패한다.
    다른 테이블스페이스 조회는 성공한다. SGA 와 컨트롤파일은 멀쩡하고
    그 파일 하나만 열리지 않기 때문이다.
  ▸ 채점 포인트 : ORA-01116 / ORA-01110 / ORA-27041 세 개를 모두 적었는가,
    "OPEN 유지" 를 확인했는가.

1-1.3 네 단계 판정  [검증됨]

  ① 무엇이 손상되었는가 — DB 가 OPEN 인 동안에는 v$recover_file 이 비어 있다.
     SYS@orcl> SELECT file#, error, change# FROM v$recover_file;
     no rows selected

     ▸ 여기서 "문제 없음" 으로 오해하면 안 된다. 컨트롤파일은 아직 그 파일이
       정상이라고 알고 있다. 파일이 필요해지는 순간에야 오류가 난다.
       MOUNT 로 내려가야 제대로 보인다.

     SYS@orcl> SHUTDOWN ABORT
     SYS@orcl> STARTUP MOUNT
     SYS@orcl> SELECT file#, error, change# FROM v$recover_file;

          FILE# ERROR                          CHANGE#
     ---------- ------------------------- ------------
              7                                5878925

  ② 백업본에 있는가
     SYS@orcl> !ls -l /home/oracle/backup/exam_nolog/users01.dbf
     -rw-r-----. 1 oracle dba 2169249792 ... users01.dbf     → 있다

  ③ 필요한 리두가 살아 있는가  ← 이 과제의 핵심
     SYS@orcl> SELECT MIN(first_change#) FROM v$log WHERE status <> 'UNUSED';

     MIN(FIRST_CHANGE#)
     ------------------
                5862520

     ▸ 필요한 SCN 5878925  >=  온라인 리두 최소 SCN 5862520  → 참
       백업 이후의 리두가 아직 온라인 리두 안에 남아 있다. 부분 복원이 성립한다.
     ▸ WHERE status <> 'UNUSED' 를 빼면 안 된다. 한 번도 쓰지 않은 그룹은
       first_change# 가 0 이라 최소값이 0 이 되어 판정이 무너진다.

  ④ ③이 참이므로 ④는 볼 필요가 없다.

  → 경로 : 부분 복원 + RECOVER  (완전 복구, 손실 없음)

1-1.4 OFFLINE 시도  [검증됨]

  SYS@orcl> ALTER DATABASE DATAFILE 7 OFFLINE;
  ALTER DATABASE DATAFILE 7 OFFLINE
  *
  ERROR at line 1:
  ORA-01145: offline immediate disallowed unless media recovery enabled

  ▸ ARCHIVELOG 가 아니면 그냥 OFFLINE 은 막힌다. 오프라인으로 둔 사이의 변경을
    나중에 아카이브로 따라잡을 수 없기 때문이다. NOARCHIVELOG 에서 쓸 수 있는 것은
    OFFLINE DROP 뿐이며, 그것은 그 파일을 영구히 버리겠다는 선언이다.
  ▸ 채점 포인트 : ORA-01145 를 적고, "아카이브가 없으니 따라잡을 수단이 없다" 는
    이유를 설명했는가. 여기서 OFFLINE DROP 으로 넘어가 버린 답안은 크게 감점한다.
    ③이 참인데 파일을 버린 것이므로 지킬 수 있었던 데이터를 스스로 버린 셈이다.

【수행】

1-1.5 부분 복원 + RECOVER  [검증됨]

  -- 되돌릴 수 없는 명령 전에 현재 상태 사본을 확보한다
  SYS@orcl> !mkdir -p /home/oracle/before_11
  SYS@orcl> !cp -p /u01/app/oracle/oradata/orcl/*.log /home/oracle/before_11/

  SYS@orcl> SHUTDOWN ABORT
  ORACLE instance shut down.

  -- 사라진 파일 하나만 되돌린다
  SYS@orcl> !cp -p /home/oracle/backup/exam_nolog/users01.dbf \
                   /u01/app/oracle/oradata/orcl/users01.dbf

  SYS@orcl> STARTUP MOUNT
  Database mounted.

  SYS@orcl> SELECT file#, checkpoint_change#, fuzzy FROM v$datafile_header
    2       WHERE file# IN (1,7);

       FILE# CHECKPOINT_CHANGE# FUZ
  ---------- ------------------ ---
           1            5878928 YES
           7            5878925 NO

  ▸ 되돌린 파일 7 만 SCN 이 뒤처져 있고 FUZZY 가 NO 다. 백업 시점에서 멈춰 있다는 뜻이다.
    나머지 파일은 앞서 있고 FUZZY 가 YES 다. 이 격차를 리두로 메우는 것이 RECOVER 다.

  SYS@orcl> RECOVER DATAFILE 7;
  Media recovery complete.

  SYS@orcl> SELECT file#, error FROM v$recover_file;
  no rows selected

  SYS@orcl> ALTER DATABASE OPEN;
  Database altered.

  ▸ 컨트롤파일과 리두 로그를 되돌리지 않는 이유
    - 컨트롤파일 : 지금 컨트롤파일은 장애 이후의 최신 상태를 알고 있다.
      백업본으로 되돌리면 그 사이의 구조 정보를 잃고 RESETLOGS 가 강제된다.
    - 리두 로그   : 되돌리려는 그 리두가 바로 복구 재료다. 덮어 버리면
      ③에서 참이었던 조건이 스스로 거짓이 된다. 이 과제에서 가장 치명적인 실수다.

【검증】

1-1.6 손실 없음 증명  [검증됨]

  SYS@orcl> SELECT step, memo, TO_CHAR(reg_time,'HH24:MI:SS') t
    2       FROM hr.exam_log ORDER BY reg_time;

  STEP   MEMO                                          T
  ------ --------------------------------------------- --------
  BASE   cold backup 직전                              18:20:09
  S1-1   리두가 살아 있으면 이 행은 지킬 수 있다        18:22:44

  ▸ 백업 시점의 BASE 행과 백업 이후에 들어온 S1-1 행이 모두 있다. 손실 0.
  ▸ 채점 포인트 : 행 수만 세지 말고 "백업 이후에 들어온 행이 살아 있다" 는
    사실을 짚었는가. 그것이 부분 복원의 가치다.

--------------------------------------------------------------------------------
 과제 1-2. 같은 장애 — 리두 소진  [30점]
--------------------------------------------------------------------------------
【판정】

1-2.2 같은 방법을 시도했을 때  [검증됨]

  -- 부분 복원까지는 동일하다
  SYS@orcl> SHUTDOWN ABORT
  SYS@orcl> !cp -p /home/oracle/backup/exam_nolog/users01.dbf \
                   /u01/app/oracle/oradata/orcl/
  SYS@orcl> STARTUP MOUNT
  SYS@orcl> RECOVER DATAFILE 7;

  ORA-00279: change 5878925 generated at 09/07/2026 18:20:21 needed for thread 1
  ORA-00289: suggestion : /arch/0001_0000000239_1239893756.arc
  ORA-00280: change 5878925 for thread 1 is in sequence #239

  Specify log: {<RET>=suggested | filename | AUTO | CANCEL}
  CANCEL
  Media recovery cancelled.

  ▸ ORA-00279 가 요구하는 것은 시퀀스 239 의 리두다.
    ORA-00289 는 그것을 아카이브 파일에서 찾겠다고 제안한다.
    그러나 이 데이터베이스는 NOARCHIVELOG 다. 그 파일은 애초에 만들어진 적이 없다.
  ▸ 프롬프트에서 CANCEL 을 입력해 빠져나온다. 엔터를 계속 치면 없는 파일을
    찾다가 ORA-00308 계열 오류만 반복된다.
  ▸ 채점 포인트 : 오류 세 개를 모두 인용했는가, CANCEL 로 빠져나왔다고 적었는가,
    "아카이브가 없다" 를 근거로 들었는가.

1-2.3 되고 안 되고를 가르는 두 숫자  [검증됨]

  SYS@orcl> SELECT MIN(first_change#) FROM v$log WHERE status <> 'UNUSED';

  MIN(FIRST_CHANGE#)
  ------------------
             6080476

              필요한 SCN     온라인 리두 최소 SCN     판정
  과제 1-1      5878925          5862520            5878925 >= 5862520  → 참
  과제 1-2      5878925          6080476            5878925 <  6080476  → 거짓

  ▸ 로그 스위치가 세 그룹을 여러 바퀴 돌면서 백업 시점의 리두를 덮어썼다.
    파일은 그대로인데 그 안의 내용이 바뀐 것이다.
    NOARCHIVELOG 에서는 덮이기 전에 아카이브로 빼 두지 않으므로 영구히 사라진다.
  ▸ 채점 포인트 : 두 숫자를 나란히 놓고 부등호로 판정했는가.
    "리두가 없어서" 라고만 쓰고 숫자를 대지 않은 답안은 절반만 인정한다.

【수행】

1-2.4 남은 두 경로

  경로 A. OFFLINE DROP + DROP TABLESPACE   → USERS 만 손실, 나머지는 현재 시점 유지
  경로 B. 전체 복원                        → 전부 백업 시점으로 복귀

  이 랩에서는 USERS 에 hr 스키마의 업무 데이터가 있으므로 그것을 버릴 수 없다.
  따라서 경로 B 를 택한다.

  ※ 만약 손상된 것이 임시 작업용 테이블스페이스였다면 경로 A 가 옳다.
     그 하나만 버리고 나머지는 현재 시점을 지킬 수 있기 때문이다.
     선택의 기준은 "그 테이블스페이스를 버릴 수 있는가" 하나다.

  -- 경로 B  [검증됨]
  SYS@orcl> SHUTDOWN ABORT
  $ cp -p /home/oracle/backup/exam_nolog/*.dbf   /u01/app/oracle/oradata/orcl/
  $ cp -p /home/oracle/backup/exam_nolog/control01.ctl \
          /home/oracle/backup/exam_nolog/control02.ctl /u01/app/oracle/oradata/orcl/
  $ cp -p /home/oracle/backup/exam_nolog/control03.ctl /u02/oradata/orcl/
  $ cp -p /home/oracle/backup/exam_nolog/redo01.log \
          /home/oracle/backup/exam_nolog/redo03.log \
          /home/oracle/backup/exam_nolog/redo04.log /u01/app/oracle/oradata/orcl/
  $ cp -p /home/oracle/backup/exam_nolog/redo01b.log \
          /home/oracle/backup/exam_nolog/redo03b.log \
          /home/oracle/backup/exam_nolog/redo04b.log /u02/oradata/orcl/
  SYS@orcl> STARTUP
  Database opened.

  ▸ 복구 명령이 필요 없다. 데이터파일·컨트롤파일·리두를 한 시점에서 통째로
    되돌렸으므로 일관성이 이미 맞기 때문이다. 이것이 Cold Backup 의 성질이다.
  ▸ 채점 포인트 : 리두와 컨트롤파일까지 함께 되돌렸는가.
    데이터파일만 되돌리고 STARTUP 하면 다시 ORA-01113 계열로 막힌다.

【검증】

1-2.5 손실 보고  [검증됨]

  SYS@orcl> SELECT step, memo FROM hr.exam_log ORDER BY reg_time;

  STEP   MEMO
  ------ -------------------------
  BASE   cold backup 직전

  ▸ S1-2 행이 사라졌다. 백업 시점 이후의 모든 입력이 없어졌다.
  ▸ 보고 예시
      "USERS 테이블스페이스 데이터파일 유실로 전체 복원을 수행했습니다.
       복구 시점은 Cold Backup 시점인 18:20 이며,
       18:20 이후 ~ 장애 시각까지 입력된 업무는 전량 재처리가 필요합니다.
       확인용 테이블 기준 2행 중 1행이 사라졌습니다."
  ▸ 채점 포인트 : 시각을 업무 시각으로 환산해 적었는가. "SCN 5878925 이후 손실"
    처럼 기술 용어만으로 적은 보고는 절반을 깎는다.

--------------------------------------------------------------------------------
 과제 1-3. UNDO 데이터파일 유실  [25점]
--------------------------------------------------------------------------------
【판정】

1-3.2 기동이 멈추는 지점

  SYS@orcl> STARTUP
  ORACLE instance started.
  Database mounted.
  ORA-01157: cannot identify/lock data file 4 - see DBWR trace file
  ORA-01110: data file 4: '/u01/app/oracle/oradata/orcl/undotbs01.dbf'

  ▸ MOUNT 까지는 된다. 컨트롤파일은 멀쩡하기 때문이다.
    OPEN 단계에서 막힌다. UNDO 없이는 되돌리지 않은 트랜잭션을 정리할 수 없다.

1-3.3 OFFLINE DROP 시도

  SYS@orcl> ALTER DATABASE DATAFILE 4 OFFLINE DROP;
  ALTER DATABASE DATAFILE 4 OFFLINE DROP
  *
  ERROR at line 1:
  ORA-01547: warning: RECOVER succeeded but OPEN RESETLOGS would get error below
  ORA-01152: file 1 was not restored from a sufficiently old backup
  ORA-01110: data file 1: '/u01/app/oracle/oradata/orcl/system01.dbf'

  또는 OPEN 단계에서
  ORA-01147 / ORA-30013 계열로 UNDO 테이블스페이스가 온라인이어야 한다는 오류

  ▸ USERS 는 버릴 수 있지만 UNDO 는 버릴 수 없다.
    ABORT 로 멈췄으므로 되돌려야 할 트랜잭션이 있고, 그 정보가 UNDO 안에 있다.
    SYSTEM 과 활성 UNDO 는 데이터베이스가 열리기 위한 최소 조건이다.
  ▸ 채점 포인트 : "USERS 와 달리 UNDO 는 오프라인으로 뗄 수 없다" 와
    그 이유(활성 트랜잭션 복구에 필요)를 설명했는가.

【수행】

1-3.4 전체 복원

  ③ 판정을 먼저 한다. UNDO 는 ABORT 직전까지의 리두가 필요하고, ABORT 로 멈춘
  이상 데이터파일과의 격차가 크다. 부분 복원 + RECOVER 가 성립하는지 확인한 뒤
  성립하지 않으면 전체 복원으로 간다.

  -- 부분 복원이 성립하는 경우
  SYS@orcl> !cp -p /home/oracle/backup/exam_nolog/undotbs01.dbf \
                   /u01/app/oracle/oradata/orcl/
  SYS@orcl> RECOVER DATAFILE 4;
  SYS@orcl> ALTER DATABASE OPEN;

  -- 성립하지 않으면 과제 1-2 의 경로 B 와 동일한 전체 복원

【검증】

1-3.5

  SYS@orcl> SELECT tablespace_name, status FROM dba_tablespaces
    2       WHERE contents = 'UNDO';
  SYS@orcl> SHOW PARAMETER undo_tablespace
  SYS@orcl> SELECT * FROM v$recover_file;
  no rows selected

  ▸ UNDO 테이블스페이스가 ONLINE 이고 undo_tablespace 파라미터가 그것을 가리키며
    복구 대상 파일이 없어야 완료다.

--------------------------------------------------------------------------------
 과제 1-4. TEMP 파일 유실  [15점]
--------------------------------------------------------------------------------
【판정】

1-4.2  데이터베이스는 정상적으로 열린다.

  ▸ TEMP 는 복구 대상이 아니다. 영구 데이터가 없고 리두를 생성하지 않기 때문이다.
    컨트롤파일에 등록만 되어 있고 실제 파일이 없어도 OPEN 은 성공한다.

1-4.3 증상

  SYS@orcl> SELECT * FROM dba_objects ORDER BY object_name;
  ERROR at line 1:
  ORA-01565: error in identifying file '/u01/app/oracle/oradata/orcl/temp01.dbf'
  ORA-27037: unable to obtain file status

  또는 ORA-25153: Temporary Tablespace is Empty

1-4.4

--------------------------------------------------------------------------------
 과제 3-1. 멤버 한 개 유실  [20점]
--------------------------------------------------------------------------------
【판정】

3-1.2

  SYS@orcl> SELECT group#, member, status FROM v$logfile ORDER BY group#, member;

      GROUP# MEMBER                                       STATUS
  ---------- -------------------------------------------- -------
           N /u01/app/oracle/oradata/orcl/redo0N.log
           N /u02/oradata/orcl/redo0Nb.log                INVALID

  ▸ 데이터베이스는 계속 서비스된다. 같은 그룹의 다른 멤버가 살아 있기 때문이다.
    이것이 멤버 다중화의 목적이다.
  ▸ STATUS 가 INVALID 인 것은 Oracle 이 그 멤버에 쓰려다 실패했다는 뜻이다.
    스위치가 그 그룹을 한 번 지나가야 값이 채워진다.

  ① CURRENT 인가 INACTIVE 인가 → 손상된 것은 그룹이 아니라 멤버 하나다.
  ② 종료 방식 → 무관하다. 내리지 않았다.

【수행】

3-1.3 온라인 처리 — 두 가지 방법

  대상 그룹이 INACTIVE 일 때만 손댄다. CURRENT 면 스위치와 체크포인트로
  INACTIVE 로 만든 뒤에 한다.

  SYS@orcl> ALTER SYSTEM SWITCH LOGFILE;
  SYS@orcl> ALTER SYSTEM CHECKPOINT;
  SYS@orcl> SELECT group#, status FROM v$log WHERE group# = N;

  방법 A. 멤버를 떼었다 다시 붙인다  (권장)
  SYS@orcl> ALTER DATABASE DROP LOGFILE MEMBER '/u02/oradata/orcl/redo0Nb.log';
  SYS@orcl> ALTER DATABASE ADD LOGFILE MEMBER '/u02/oradata/orcl/redo0Nb.log'
    2       TO GROUP N;

  방법 B. 같은 그룹의 살아 있는 멤버를 복사한다
  SYS@orcl> !cp -p /u01/app/oracle/oradata/orcl/redo0N.log \
                   /u02/oradata/orcl/redo0Nb.log

  ▸ 방법 A 를 권장한다. Oracle 이 파일을 새로 만들고 헤더까지 스스로 맞추므로
    확실하다. 방법 B 는 그룹이 INACTIVE 가 아닌 순간에 하면 내용이 어긋난다.
  ▸ 어느 쪽이든 데이터베이스를 내리지 않는다.

【검증】

3-1.4

  SYS@orcl> ALTER SYSTEM SWITCH LOGFILE;
  SYS@orcl> ALTER SYSTEM CHECKPOINT;
  SYS@orcl> SELECT group#, member, status FROM v$logfile WHERE group# = N;

      GROUP# MEMBER                                       STATUS
  ---------- -------------------------------------------- -------
           N /u01/app/oracle/oradata/orcl/redo0N.log
           N /u02/oradata/orcl/redo0Nb.log

  ▸ STATUS 가 비어 있는 것이 정상이다. NULL 은 "특별히 보고할 상태가 없다",
    즉 정상적으로 쓰이고 있다는 뜻이다. INVALID 나 STALE 이 아니어야 한다.
  ▸ 스위치를 한 바퀴 돌려 그 그룹이 실제로 쓰인 뒤에 확인해야 의미가 있다.

--------------------------------------------------------------------------------
 과제 3-2. INACTIVE 그룹 전손 + 정상 종료  [35점]
--------------------------------------------------------------------------------
【판정】

3-2.2

  SYS@orcl> STARTUP
  ORACLE instance started.
  Database mounted.
  ORA-00313: open failed for members of log group N of thread 1
  ORA-00312: online log N thread 1: '/u01/app/oracle/oradata/orcl/redo0N.log'
  ORA-00312: online log N thread 1: '/u02/oradata/orcl/redo0Nb.log'
  ORA-27037: unable to obtain file status

  ▸ MOUNT 는 된다. 컨트롤파일이 멀쩡하기 때문이다. OPEN 에서 막힌다.
  ▸ ORA-00312 가 두 줄이다. 멤버 두 개를 모두 열지 못했다는 뜻이며
    그래서 ORA-00313(그룹 전손)이 함께 나온다.
    한 줄만 나오면 멤버 하나 손상이고 서비스는 멈추지 않는다.
    줄 수를 세는 것이 진단의 열쇠다.

3-2.3 종료 방식 확인

  SYS@orcl> !grep -n 'CLOSE NORMAL\|Shutting down instance (abort)' \
          /u01/app/oracle/diag/rdbms/orcl/orcl/trace/alert_orcl.log | tail -2
  ...:Completed: ALTER DATABASE CLOSE NORMAL

  ▸ 마지막 기록이 CLOSE NORMAL 이면 정상 종료다.
    SHUTDOWN IMMEDIATE 도 알럿 로그에는 CLOSE NORMAL 로 남는다.

3-2.4 판정

  ① 손상된 그룹은 INACTIVE 다.
     SYS@orcl> SELECT group#, sequence#, status FROM v$log ORDER BY group#;
  ② 정상 종료였다.

  → 그 그룹의 리두는 이미 데이터파일에 반영되었고, 정상 종료라 적용할 리두도 없다.
    CLEAR 로 다시 만들면 된다. 손실 없음. RESETLOGS 불필요.

【수행】

3-2.5 DROP 을 먼저 시도

  SYS@orcl> ALTER DATABASE DROP LOGFILE GROUP N;
  ERROR at line 1:
  ORA-00313: open failed for members of log group N of thread 1
  ORA-00312: online log N thread 1: '...'
  ORA-27037: unable to obtain file status

  ▸ DROP 은 그룹을 없애는 명령이라 대상 파일에 접근할 수 있어야 한다.
    파일이 사라졌으므로 없애는 것조차 되지 않는다.
  ▸ 필요한 것은 제거가 아니라 재생성이다. CLEAR 는 내용을 비우고
    파일이 없으면 새로 만들어 준다. 이 상황에 맞는 명령은 CLEAR 다.
  ▸ 채점 포인트 : DROP 과 CLEAR 의 목적 차이를 설명했는가.

3-2.6 복구

  SYS@orcl> ALTER DATABASE CLEAR LOGFILE GROUP N;
  Database altered.

  SYS@orcl> SELECT group#, sequence#, status FROM v$log WHERE group# = N;
      GROUP#  SEQUENCE# STATUS
  ---------- ---------- ----------------
           N          0 UNUSED

  SYS@orcl> !ls -l /u01/app/oracle/oradata/orcl/redo0N.log /u02/oradata/orcl/redo0Nb.log
  ▸ 멤버 두 개가 모두 새로 만들어져 있다.

  SYS@orcl> ALTER DATABASE OPEN;
  Database altered.

  ▸ RESETLOGS 는 필요 없다. 리두를 새로 만들었지만 그 그룹에는 적용해야 할
    내용이 없었기 때문이다. 기존 백업이 계속 유효하다는 뜻이기도 하다.

【검증】

3-2.7

  SYS@orcl> SELECT COUNT(*) FROM hr.exam_log;         -- 장애 전과 같아야 한다
  SYS@orcl> SELECT * FROM v$recover_file;             -- no rows selected
  SYS@orcl> SELECT incarnation#, status FROM v$database_incarnation
    2       WHERE status = 'CURRENT';                 -- 올라가지 않았다

  -- 그룹이 순환에 복귀하는지 확인
  SYS@orcl> ALTER SYSTEM SWITCH LOGFILE;   (두세 번)
  SYS@orcl> SELECT group#, sequence#, status FROM v$log ORDER BY group#;

  ▸ 손실 없음. 근거는 "손상된 그룹이 INACTIVE 였다" 는 것이다.
    INACTIVE 는 그 리두가 이미 데이터파일에 반영되었다는 뜻이므로
    없어져도 잃을 것이 없다.
  ▸ UNUSED 로만 남아 있으면 아직 한 번도 쓰이지 않은 것이다.
    스위치를 돌려 실제로 쓰이는지까지 확인해야 완료다.

--------------------------------------------------------------------------------
 과제 3-3. CURRENT 그룹 전손 + 비정상 종료  [45점]
--------------------------------------------------------------------------------
【판정】

3-3.2

  SYS@orcl> STARTUP
  ORACLE instance started.
  Database mounted.
  ORA-00313: open failed for members of log group N of thread 1
  ORA-00312: online log N thread 1: '/u01/app/oracle/oradata/orcl/redo0N.log'
  ORA-00312: online log N thread 1: '/u02/oradata/orcl/redo0Nb.log'
  ORA-27037: unable to obtain file status

  -- alert log
  Beginning crash recovery of 1 threads
  Started redo scan
  ORA-00313: open failed for members of log group N of thread 1
  ORA-313 signalled during: ALTER DATABASE OPEN...

  ▸ 과제 3-2 와 오류 번호는 같지만 alert log 가 다르다.
    여기에는 crash recovery 를 시작하려다 막힌 기록이 있다.
    정상 종료였다면 crash recovery 자체가 없다. 이 차이가 결정적이다.

3-3.3 CURRENT 확인

  SYS@orcl> SELECT group#, sequence#, status FROM v$log ORDER BY group#;
  ▸ 손상된 그룹 N 의 STATUS 가 CURRENT 다. 과제 3-2 와 정반대다.

  SYS@orcl> SELECT COUNT(*) FROM v$logfile
    2       WHERE group# = N AND status IS NULL;
    COUNT(*)
  ----------
           0

  ▸ STATUS 가 NULL 인 멤버가 하나도 없다 = 살아 있는 멤버가 없다.
    리두를 읽을 방법이 완전히 사라졌다는 증명이다.

  SYS@orcl> SELECT name, log_mode FROM v$database;
  ▸ NOARCHIVELOG 다. 아카이브 사본도 없다.

  ① CURRENT 다.  ② 비정상 종료다.  → 최악의 조합이다.

3-3.4 CLEAR 시도

  SYS@orcl> ALTER DATABASE CLEAR LOGFILE GROUP N;
  ERROR at line 1:
  ORA-01624: log N needed for crash recovery of instance orcl (thread 1)
  ORA-00312: online log N thread 1: '/u01/app/oracle/oradata/orcl/redo0N.log'

  ▸ 이것은 오류가 아니라 Oracle 이 막아 준 것이다.
    그 그룹에는 인스턴스 복구에 필요한 리두가 들어 있다.
    비워 버리면 커밋된 변경을 스스로 버리게 되므로 기본적으로 거부한다.
  ▸ 채점 포인트 : "Oracle 이 손실을 막아 준 것" 이라고 해석했는가.
    단순히 "오류가 났다" 로 적은 답안은 감점한다.

3-3.5 손실 확정

  ▸ 진퇴양난이다.
    - CLEAR 하지 않으면 데이터베이스를 열 수 없다.
    - CLEAR 하면 그 리두에만 있던 커밋 변경을 잃는다.
    - 그 리두를 읽을 방법은 없다. 멤버도 없고 아카이브도 없다.
  ▸ 따라서 손실은 이미 확정되어 있다. 선택의 문제가 아니라
    "손실을 인지한 상태에서 열 것인가, 열지 않을 것인가" 의 문제다.
  ▸ 인지했음을 기록으로 남기고 진행한다. 이것이 실무에서 가장 중요한 단계다.

【수행】

3-3.6 열기

  -- 되돌릴 수 없는 명령이다. 먼저 현재 상태 사본을 확보한다
  SYS@orcl> !mkdir -p /home/oracle/before_33
  SYS@orcl> !cp -p /u01/app/oracle/oradata/orcl/*.dbf \
                   /u01/app/oracle/oradata/orcl/*.ctl /home/oracle/before_33/
  SYS@orcl> !cp -p /u02/oradata/orcl/*.ctl /home/oracle/before_33/

  SYS@orcl> ALTER DATABASE CLEAR UNARCHIVED LOGFILE GROUP N;
  Database altered.

  SYS@orcl> ALTER DATABASE OPEN;
  ERROR at line 1:
  ORA-01113: file 1 needs media recovery
  ORA-01110: data file 1: '/u01/app/oracle/oradata/orcl/system01.dbf'

  ▸ 오류가 바뀐 것이 진행의 신호다.
    ORA-01624(인스턴스 복구 요구)는 해소되었고
    ORA-01113(미디어 복구 요구)이 새로 드러났다.
    데이터파일이 서로 다른 시점에서 멈춰 있어 일관성이 맞지 않기 때문이다.

  SYS@orcl> SELECT file#, error, change# FROM v$recover_file;
  SYS@orcl> RECOVER DATABASE UNTIL CANCEL;
  ORA-00279: change ... needed for thread 1
  ORA-00289: suggestion : /arch/...
  ORA-00280: change ... for thread 1 is in sequence #N

  Specify log: {<RET>=suggested | filename | AUTO | CANCEL}
  CANCEL
  Media recovery cancelled.

  SYS@orcl> ALTER DATABASE OPEN RESETLOGS;
  Database altered.

  ▸ 요구된 시퀀스의 리두가 바로 우리가 비워 버린 그것이다. 적용할 수 없으므로
    CANCEL 하고 불완전한 상태로 연다. RESETLOGS 가 강제된다.
  ▸ 만약 여기서도 열리지 않으면 전체 복원으로 전환한다.
    그 판단 기준은 "몇 번 더 시도하면 될 것 같은가" 가 아니라
    "적용할 리두가 존재하는가" 다. 존재하지 않으면 몇 번을 시도해도 같다.

【검증】

3-3.7 손실 산정

  SYS@orcl> SELECT step, memo, TO_CHAR(reg_time,'HH24:MI:SS') t
    2       FROM hr.exam_log ORDER BY reg_time;

  ▸ 'S3-3' 행은 있고 'S3-3x' 행은 사라져 있다.
    S3-3 은 체크포인트로 데이터파일에 반영된 뒤였고,
    S3-3x 는 CURRENT 리두에만 있었기 때문이다.
  ▸ 커밋했는데도 잃었다는 사실이 이 과제의 핵심이다.
    커밋은 "리두에 기록되었음" 을 보장할 뿐 데이터파일 반영을 보장하지 않는다.

  SYS@orcl> SELECT checkpoint_change# FROM v$database;
  SYS@orcl> SELECT SCN_TO_TIMESTAMP(<위 값>) FROM dual;
  SYS@orcl> SELECT MAX(reg_time) FROM hr.exam_log;

  ▸ 보고 예시
      "CURRENT 리두 그룹 전손과 비정상 종료가 겹쳐 불완전 복구를 수행했습니다.
       복구 시점은 마지막 체크포인트인 HH:MM 이며,
       그 이후 ~ 장애 시각 HH:MM 사이에 커밋된 업무는 복구할 수 없습니다.
       확인용 테이블 기준 마지막 1건이 사라졌습니다.
       해당 구간의 업무는 원장 대조 후 재처리가 필요합니다."

3-3.8 인카네이션

  SYS@orcl> SELECT incarnation#, resetlogs_change#, status
    2       FROM v$database_incarnation WHERE status = 'CURRENT';

  ▸ 올라가 있다. RESETLOGS 를 했기 때문이다.
  ▸ 즉시 전체 Cold Backup 을 새로 받는다. 이전 백업은 이 인카네이션에 쓸 수 없다.
  ▸ TEMP 도 확인한다.

3-3.9 예방책

  ▸ 리두 멤버를 서로 다른 디스크에 다중화한다.
    이번 장애에서 두 멤버가 함께 사라진 것은 같은 사고 하나에 둘 다 노출되어
    있었기 때문이다. 멤버 하나만 다른 디스크에 살아 있었다면
    과제 3-1 처럼 온라인으로 처리되고 손실은 0 이었다.
  ▸ ARCHIVELOG 전환은 이 경우의 완전한 해답이 되지 못한다.
    CURRENT 리두는 아직 아카이브되기 전이므로 보호되지 않는다.
    CURRENT 리두를 지키는 것은 다중화뿐이다.
  ▸ 채점 포인트 : 다중화를 답했는가.
    "ARCHIVELOG 로 바꾼다" 만 적은 답안은 절반만 인정한다.
