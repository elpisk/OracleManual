================================================================================
 실습 16-1 : RMAN Table Recovery — RECOVER TABLE ... UNTIL
 과정      : Oracle Database 19c Backup & Recovery
 환경      : Oracle 19.3.0 / Oracle Linux 7 / non-CDB ORCL / ARCHIVELOG
 소요 시간 : 약 40분
================================================================================

--------------------------------------------------------------------------------
[1] 시나리오 개요
--------------------------------------------------------------------------------
-- 테이블 하나가 잘못된 작업으로 지워졌다.
-- UNDO는 이미 덮여 Flashback을 쓸 수 없다.
-- RECOVER TABLE로 그 시점의 테이블만 되살린다.
-- REMAP TABLE로 다른 이름으로 가져와 확인한 뒤 반영한다.
-- 복구 유형 : 테이블 단위 복구, 다른 업무에 영향 없음

--------------------------------------------------------------------------------
[2] 사전 조건
--------------------------------------------------------------------------------
-- 15장까지의 실습이 완료되어 백업과 아카이브가 있어야 한다.
-- 보조 인스턴스용 공간이 필요하다.

[5] 증상 관찰
--------------------------------------------------------------------------------
-- Flashback Query를 먼저 시도해 본다.

SYS@orcl> SELECT COUNT(*) FROM hr.emp160
  2  AS OF TIMESTAMP TO_TIMESTAMP('2025-05-18 09:10:00','YYYY-MM-DD HH24:MI:SS');
SELECT COUNT(*) FROM hr.emp160
                     *
ERROR at line 1:
ORA-01555: snapshot too old: rollback segment number 3 with name
"_SYSSMU3_1930754532$" too small

-- << 원인 파악 >>
-- UNDO가 이미 덮여 그 시점의 이전 이미지를 만들 수 없다.
-- UNDO_RETENTION을 넘겼거나 UNDO 테이블스페이스가 작아 재사용된 것이다.
-- Flashback 계열은 UNDO에 의존하므로 이 상황에서는 쓸 수 없다.
-- 백업과 아카이브를 쓰는 RECOVER TABLE 로 전환한다.

SYS@orcl> SHOW PARAMETER undo_retention

NAME                 TYPE        VALUE
-------------------- ----------- -----
undo_retention       integer     900

-- 900초, 즉 15분이다. 그 이전 시점은 보장되지 않는다.

[7] 복구 절차 : 오류 발생 → 원인 파악 → 수정
--------------------------------------------------------------------------------
-- AUXILIARY DESTINATION 없이 시도해 본다.

RMAN> RECOVER TABLE hr.emp160
  2>   UNTIL TIME "TO_DATE('2025-05-18 09:10:00','YYYY-MM-DD HH24:MI:SS')";

RMAN-00571: ===========================================================

RMAN-05902: must specify AUXILIARY DESTINATION or set DB_RECOVERY_FILE_DEST

-- << 원인 파악 >>
-- 보조 인스턴스가 파일을 만들 위치가 필요하다.

SYS@orcl> INSERT INTO hr.emp160
  2  SELECT * FROM hr.emp160_recovered r

  4                     WHERE e.employee_id = r.employee_id);

-- 실무 포인트
-- 1) Flashback이 안 되는 상황에서 RECOVER TABLE이 답이 된다.
--    ORA-01555는 UNDO가 이미 덮였다는 뜻이며 Flashback 계열을 쓸 수 없다.
--    RECOVER TABLE은 백업과 아카이브를 쓰므로 UNDO와 무관하다.
--
-- 2) AUXILIARY DESTINATION 은 필수다.
--    FRA가 구성되어 있으면 생략할 수 있으나 그렇지 않으면 RMAN-05902가 나온다.
--    SYSTEM·SYSAUX·UNDO와 대상 TS만큼의 공간이 필요하다.
--
-- 3) REMAP TABLE을 기본으로 쓴다.
--    생략하면 현재 테이블을 덮어쓰며 되돌릴 수 없다.
--    다른 이름으로 가져와 확인한 뒤 필요한 행만 반영하는 편이 안전하다.
--
-- 4) 로그는 다섯 구간으로 읽는다.
--    보조 인스턴스 생성, Memory Script, 복원과 복구, Export/Import, 정리다.
--    clone 이 붙은 명령이 보조 인스턴스를 대상으로 하는 것이다.
--
-- 5) Export 단계의 행 수를 확인한다.
--    기대한 수와 다르면 시점을 잘못 지정한 것이다.
--
-- 6) 작업 후 AUXILIARY DESTINATION 을 확인한다.
--    정리가 실패하면 파일이 남아 다음 수행 때 공간 부족을 만든다.
