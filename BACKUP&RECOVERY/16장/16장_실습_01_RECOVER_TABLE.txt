================================================================================
 실습 16-1 : RMAN Table Recovery — RECOVER TABLE ... UNTIL
 과정      : Oracle Database 19c Backup & Recovery
 환경      : Oracle 19.3.0 / Oracle Linux 7 / non-CDB ORCL / ARCHIVELOG
 소요 시간 : 약 40분
================================================================================

--------------------------------------------------------------------------------
[1] 시나리오 개요
--------------------------------------------------------------------------------
-- 테이블 하나가 잘못된 작업(TRUNCATE)으로 지워졌다.
-- TRUNCATE 는 UNDO 를 남기지 않아 Flashback 을 쓸 수 없다.
-- RECOVER TABLE로 그 시점의 테이블만 되살린다.
-- REMAP TABLE로 다른 이름으로 가져와 확인한 뒤 반영한다.
-- 복구 유형 : 테이블 단위 복구, 다른 업무에 영향 없음

--------------------------------------------------------------------------------
[2] 사전 조건
--------------------------------------------------------------------------------
-- 15장까지의 실습이 완료되어 백업과 아카이브가 있어야 한다.
-- 보조 인스턴스용 공간이 필요하다.

[oracle@oel7v9 ~]$ mkdir -p /u03/aux
[oracle@oel7v9 ~]$ df -h /u03 | tail -1
/dev/sdc1        20G  4.2G   16G  21% /u03

[oracle@oel7v9 ~]$ sqlplus -s / as sysdba <<< \
> "SELECT tablespace_name, ROUND(SUM(bytes)/1024/1024) AS mb
   FROM dba_data_files
   WHERE tablespace_name IN ('SYSTEM','SYSAUX','UNDOTBS1','USERS')
   GROUP BY tablespace_name ORDER BY 1;"

--------------------------------------------------------------------------------
[5] 증상 관찰
--------------------------------------------------------------------------------
-- Flashback Query를 먼저 시도해 본다.

SYS@orcl> SELECT COUNT(*) FROM hr.emp160
  2  AS OF TIMESTAMP TO_TIMESTAMP('2025-05-18 09:10:00','YYYY-MM-DD HH24:MI:SS');
SELECT COUNT(*) FROM hr.emp160
                        *
ERROR at line 1:
ORA-01466: unable to read data - table definition has changed

-- << 원인 파악 >>
-- TRUNCATE 는 DDL 이라 행마다 UNDO 를 남기지 않고 세그먼트를 통째로 비운다.
-- 그 이전 시점의 이미지를 UNDO 로 만들 수 없으니 Flashback Query 가 막힌다.
-- FLASHBACK TABLE 도 같은 이유로 안 된다(행 이동을 켜도 ORA-01466).
-- UNDO 에 의존하지 않고 백업과 아카이브를 쓰는 RECOVER TABLE 로 전환한다.

SYS@orcl> SELECT * FROM v$recover_file;

no rows selected

-- 파일 손상이 아니다. 데이터베이스 전체를 되돌릴 일도 아니다.

-- 실무 포인트
-- 1) Flashback이 안 되는 상황에서 RECOVER TABLE이 답이 된다.
--    TRUNCATE·DROP 뒤 PURGE 처럼 UNDO 가 없는 경우(ORA-01466), UNDO 가 이미 덮인 경우(ORA-01555)다.
--    RECOVER TABLE은 백업과 아카이브를 쓰므로 UNDO와 무관하다.
--
-- 2) 같은 이름의 테이블이 있으면 RMAN-05112 로 거부된다. 덮어쓰지 않는다.
--    REMAP TABLE 로 다른 이름으로 가져와 확인한 뒤 필요한 행만 반영하는 것이 기본이다.
--    (원본을 먼저 DROP 하면 REMAP 없이도 되지만 되돌릴 수 없다.)
--
-- 3) AUXILIARY DESTINATION 은 FRA 가 없으면 필수다.
--    없으면 원본 파일 위치로 복원하려다 RMAN-05001/05517 로 중단된다.
--    SYSTEM·SYSAUX·UNDO와 대상 TS만큼의 공간이 필요하다.
--
-- 4) 로그는 여섯 구간으로 읽는다.
--    보조 인스턴스 생성, 컨트롤파일 복원·RESYNC, 보조 세트 복원·복구,
--    대상 TS 복원·RESETLOGS, Export/Import, 정리다.
--
-- 5) Export 단계의 행 수를 확인한다.
--    기대한 수와 다르면 시점을 잘못 지정한 것이다.
--
-- 6) 작업 후 AUXILIARY DESTINATION 을 확인한다.
--    정리가 실패하면 파일이 남아 다음 수행 때 공간 부족을 만든다.
