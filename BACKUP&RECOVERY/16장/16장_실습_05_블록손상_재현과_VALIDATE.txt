================================================================================
 실습 16-5 : 블록 손상 재현과 VALIDATE로 감지
 과정      : Oracle Database 19c Backup & Recovery
 환경      : Oracle 19.3.0 / Oracle Linux 7 / non-CDB ORCL / ARCHIVELOG
 소요 시간 : 약 30분
================================================================================

--------------------------------------------------------------------------------
[1] 시나리오 개요
--------------------------------------------------------------------------------
-- dd 명령으로 데이터파일의 특정 블록을 손상시킨다.
-- 조회 시 나타나는 오류와 VALIDATE의 감지 결과를 비교한다.
-- v$database_block_corruption 에 등록되는 과정을 확인한다.
-- 손상 블록이 속한 객체를 찾는다.
-- 작업 유형 : 손상 재현과 진단(복구는 16-7에서)

--------------------------------------------------------------------------------
[2] 사전 조건
--------------------------------------------------------------------------------
-- 반드시 실습 환경에서만 수행한다. 운영 데이터베이스에서는 절대 수행하지 않는다.
-- 공용 테이블스페이스를 망가뜨리지 않도록, 버릴 수 있는 실습용 테이블스페이스를 따로 만든다.

--------------------------------------------------------------------------------
[4] 장애 유발 : dd로 블록 손상
--------------------------------------------------------------------------------
[oracle@oel7v9 ~]$ sqlplus -s / as sysdba <<< "SHUTDOWN IMMEDIATE"

Database closed.
ORACLE instance shut down.

-- 데이터베이스를 내린 상태에서 손상시킨다.
-- 열린 상태에서 하면 버퍼 캐시의 내용과 어긋나 결과가 불확실해진다.

[oracle@oel7v9 ~]$ cp -p /u01/app/oracle/oradata/orcl/tbs16_01.dbf /tmp/tbs16_ok.dbf

-- 만일을 위해 원본을 복사해 둔다.

[oracle@oel7v9 ~]$ dd if=/dev/zero of=/u01/app/oracle/oradata/orcl/tbs16_01.dbf \
>   bs=8192 seek=142 count=3 conv=notrunc

3+0 records in
3+0 records out
24576 bytes (25 kB) copied, 5.7421e-05 s, 428 MB/s

-- 142번 블록부터 3개를 0으로 채웠다.
-- seek는 건너뛸 블록 수, count는 쓸 블록 수다.

[oracle@oel7v9 ~]$ sqlplus -s / as sysdba <<< "STARTUP"

ORACLE instance started.
Database opened.

ORA-01110: data file 9: '/u01/app/oracle/oradata/orcl/tbs16_01.dbf'

-- ORA-26040이 없다. NOLOGGING이 아니라 물리적 손상이라는 뜻이다.

SYS@orcl> SELECT COUNT(*) FROM hr.blk165 WHERE id <= 10;
SELECT COUNT(*) FROM hr.blk165 WHERE id <= 10
       *
ERROR at line 1:
ORA-01578: ORACLE data block corrupted (file # 9, block # 142)
ORA-01110: data file 9: '/u01/app/oracle/oradata/orcl/tbs16_01.dbf'

-- 이 테이블의 데이터는 손상 블록에 걸려 모두 오류가 난다(작은 테이블이라 첫 블록에 몰려 있다).

SYS@orcl> SELECT * FROM v$database_block_corruption;

     FILE#     BLOCK#     BLOCKS CORRUPTION_CHANGE# CORRUPTIO     CON_ID
---------- ---------- ---------- ------------------ --------- ----------
         9        142          3                  0 ALL ZERO           0

-- << 관찰 >>
-- 19c 는 손상 블록을 읽는 순간 자동 진단(Health Check)이 돌아 이 뷰를 채운다.
-- 옛 자료에서는 "VALIDATE를 해야 채워진다"고 하지만 19c 에서는 접근만으로도 등록된다.
-- corruption_type 이 ALL ZERO 인 것이 dd로 0을 채운 흔적이다.

--------------------------------------------------------------------------------
[7] 오류 발생 → 원인 파악 → 수정
--------------------------------------------------------------------------------
-- 손상이 있는 상태로 백업을 시도해 본다.

SYS@orcl> EXIT
[oracle@oel7v9 ~]$ rman target / catalog rcatowner@rcat

RMAN> BACKUP DATAFILE 9;

Starting backup at 18-MAY-25
allocated channel: ORA_DISK_1
channel ORA_DISK_1: starting full datafile backup set
RMAN-00571: ===========================================================
RMAN-00569: =============== ERROR MESSAGE STACK FOLLOWS ===============
RMAN-00571: ===========================================================
RMAN-03009: failure of backup command on ORA_DISK_1 channel at 05/18/2025 11:16:12
ORA-19566: exceeded limit of 0 corrupt blocks for file
 /u01/app/oracle/oradata/orcl/tbs16_01.dbf

-- << 원인 파악 >>
-- 손상 블록 허용치가 기본 0이므로 백업이 실패한다.
-- 손상을 담은 백업은 복구에 쓸 수 없으므로 막는 것이 정상 동작이다.
-- 근본 해결은 블록을 먼저 복구하는 것이다.
-- 당장 백업이 필요하다면 MAXCORRUPT로 허용치를 정할 수 있다.

-- << 수정 >> 임시로 허용치를 지정해 백업한다.

RMAN> RUN {
  2>   SET MAXCORRUPT FOR DATAFILE 9 TO 10;
  3>   BACKUP DATAFILE 9 TAG 'WITH_CORRUPT';
  4> }

executing command: SET MAX CORRUPT
Starting backup at 18-MAY-25
channel ORA_DISK_1: starting full datafile backup set
channel ORA_DISK_1: backup set complete, elapsed time: 00:00:03
Finished backup at 18-MAY-25

-- 백업은 되었지만 손상 블록이 그대로 들어갔다.
-- 이 백업으로는 그 블록을 복구할 수 없다.

-- dbv 결과도 3개로 일치한다.
-- dbv 는 파일을 직접 읽는 도구라 'Marked Corrupt' 에 3을 그대로 표시한다.
-- 복구는 실습 16-7에서 수행한다.

-- 실무 포인트
-- 1) dd 명령으로 블록을 손상시키는 실습은 반드시 실습 환경에서만, 버릴 수 있는
--    테이블스페이스에서만 수행한다. conv=notrunc를 빠뜨리면 파일이 그 지점에서 잘린다.
--
-- 2) 19c 에서는 손상 블록을 읽는 순간 자동 진단이 v$database_block_corruption 을 채운다.
--    옛 자료의 "VALIDATE를 해야 채워진다"는 19c 에는 맞지 않는다.
--    다만 정확한 목록과 갱신을 위해 VALIDATE(또는 BACKUP)를 한 번 돌리는 것은 여전히 권장된다.
--
-- 3) ORA-01578에 ORA-26040이 없으면 물리적 손상이다.
--    alert log의 'Completely zero block' 같은 표현이 원인을 짐작하게 한다.
--    corruption_type 이 ALL ZERO 이면 블록 전체가 0으로 덮인 경우다.
--
-- 4) VALIDATE 의 손상 건수는 상단 'Marked Corrupt'가 아니라
--    블록 유형표의 'Blocks Failing'에 잡히고 Status가 FAILED가 된다.
--    dd 로 0을 채운 블록은 'Other' 유형으로 분류된다.
--
-- 5) 손상이 있으면 백업이 ORA-19566으로 실패한다.
--    손상을 담은 백업은 복구에 쓸 수 없으므로 막는 것이 정상 동작이다.
--    MAXCORRUPT는 임시 조치이며 백업 후 반드시 블록 복구를 수행한다.
--
-- 6) dba_extents 로 손상 블록이 속한 객체를 확인한다.
--    인덱스라면 REBUILD가 블록 복구보다 빠르고 확실하다.
