================================================================================
 실습 17-5 : 복제 DB 검증과 삭제 — DROP DATABASE
 과정      : Oracle Database 19c Backup & Recovery
 환경      : Oracle 19.3.0 / Oracle Linux 7 / non-CDB ORCL → CLONE / ARCHIVELOG
 소요 시간 : 약 25분
================================================================================

--------------------------------------------------------------------------------
[1] 시나리오 개요
--------------------------------------------------------------------------------
-- 복제본이 원본과 독립적인지 검증한다.
-- 복제본에서 데이터를 변경해도 원본에 영향이 없는지 확인한다.
-- 복제 작업 기록을 남긴다.
-- DROP DATABASE로 정식 절차에 따라 삭제한다.
-- 작업 유형 : 검증과 정리(장애 복구 아님)

--------------------------------------------------------------------------------

--------------------------------------------------------------------------------

[3] 초기 상태 확인
--------------------------------------------------------------------------------
-- 원본과 복제본의 식별자를 나란히 확인한다.

SYS@CLONE> SELECT dbid, name, resetlogs_change# FROM v$database;

      DBID NAME      RESETLOGS_CHANGE#
---------- --------- -----------------
1200530011 CLONE               2761326

SYS@CLONE> EXIT

[oracle@oel7v9 ~]$ export ORACLE_SID=orcl
[oracle@oel7v9 ~]$ sqlplus -s / as sysdba <<< \
> "SELECT dbid, name, resetlogs_change# FROM v\$database;"

      DBID NAME      RESETLOGS_CHANGE#
---------- --------- -----------------
1200530011 ORCL                2672396

-- 이름과 인카네이션 기준(RESETLOGS SCN)은 다르지만 DBID 는 같다.
-- 파일과 인스턴스는 완전히 분리돼 있어도, RMAN 과 카탈로그는 DBID 로 데이터베이스를 구분한다.
-- 이 상태의 위험을 [5] 에서 본다.

[oracle@oel7v9 ~]$ ps -ef | grep [p]mon
oracle    3021     1  0 08:40 ?        00:00:01 ora_pmon_orcl
oracle    4188     1  0 08:52 ?        00:00:00 ora_pmon_rcat
oracle    9812     1  0 10:38 ?        00:00:00 ora_pmon_CLONE

-- 두 인스턴스가 동시에 떠 있다.

--------------------------------------------------------------------------------
[4] 작업 수행 : 독립성 검증
--------------------------------------------------------------------------------
-- 복제본에서 데이터를 바꾼다.

[oracle@oel7v9 ~]$ export ORACLE_SID=CLONE
[oracle@oel7v9 ~]$ sqlplus / as sysdba

SYS@CLONE> CREATE TABLE hr.clone_only(id NUMBER, memo VARCHAR2(30))
  2    TABLESPACE users;

Table created.

SYS@CLONE> INSERT INTO hr.clone_only VALUES (1, 'created in clone');
SYS@CLONE> COMMIT;

SYS@CLONE> DELETE FROM hr.job_history;

10 rows deleted.

SYS@CLONE> COMMIT;

SYS@CLONE> SELECT COUNT(*) FROM hr.job_history;

  COUNT(*)
----------
         0

-- 복제본에서 10건을 지웠다.
-- (employees 를 지우려 하면 departments.manager_id 가 참조하는 사원이 있어 ORA-02292 로 막힌다.
--  자식이 없는 job_history 를 골랐다.)

SYS@CLONE> EXIT

-- 원본을 확인한다.

[oracle@oel7v9 ~]$ export ORACLE_SID=orcl
[oracle@oel7v9 ~]$ sqlplus -s / as sysdba <<< \
> "SELECT COUNT(*) FROM hr.job_history;
   SELECT COUNT(*) FROM hr.clone_only;"

  COUNT(*)
----------
        10

SELECT COUNT(*) FROM hr.clone_only
                        *
ERROR at line 1:
ORA-00942: table or view does not exist

-- 원본은 10건 그대로이고 복제본에서 만든 테이블도 없다.
-- 두 데이터베이스의 파일이 완전히 독립적임이 확인되었다.

--------------------------------------------------------------------------------
[7] 삭제 절차 : 오류 발생 → 원인 파악 → 수정
--------------------------------------------------------------------------------
[oracle@oel7v9 ~]$ export ORACLE_SID=CLONE
[oracle@oel7v9 ~]$ sqlplus / as sysdba

-- 열린 상태에서 삭제를 시도해 본다.

SYS@CLONE> DROP DATABASE;
DROP DATABASE
*
ERROR at line 1:
ORA-01586: database must be mounted EXCLUSIVE and not open for this operation

-- << 원인 파악 >>
-- DROP DATABASE는 MOUNT EXCLUSIVE RESTRICT 상태에서만 수행할 수 있다.
-- 열린 상태에서는 파일을 지울 수 없기 때문이다.
-- 이 제약이 실수로 실행하는 것을 어느 정도 막아 준다.

-- << 수정 >>

SYS@CLONE> SHUTDOWN IMMEDIATE

Database closed.
Database dismounted.
ORACLE instance shut down.

SYS@CLONE> STARTUP MOUNT EXCLUSIVE RESTRICT;

ORACLE instance started.

Total System Global Area  536868920 bytes
Fixed Size                  8898616 bytes
Variable Size             218103808 bytes
Database Buffers          301989888 bytes
Redo Buffers                7876608 bytes
Database mounted.

-- 실행 전 반드시 이름을 확인한다.

SYS@CLONE> SELECT name, dbid FROM v$database;

NAME            DBID
--------- ----------
CLONE     1200530011

-- CLONE이 맞다. 원본이 아니다. DBID 는 같으므로 DBID 로는 구분할 수 없다. 이름과 SID 로 확인한다.

SYS@CLONE> DROP DATABASE;

Database dropped.

[8] 검증 및 실무 포인트
--------------------------------------------------------------------------------
SYS@CLONE> EXIT

[oracle@oel7v9 ~]$ ls -l /u04/clone/CLONE/
total 0

-- 데이터파일, 컨트롤파일, 리두, 임시 파일이 모두 지워졌다.

[oracle@oel7v9 ~]$ ls -l /u04/clone/arch/ | head -3
total 3892
-rw-r-----. 1 oracle dba  528384 May 19 10:41 arch_1_1_1200621700.arc
-rw-r-----. 1 oracle dba  563200 May 19 09:18 arch_1_12_1200606000.arc

-- 아카이브는 남아 있다. DROP DATABASE가 지우지 않는다.

[oracle@oel7v9 ~]$ ls $ORACLE_HOME/dbs/initCLONE.ora
/u01/app/oracle/product/19.3.0/dbhome_1/dbs/initCLONE.ora

[oracle@oel7v9 ~]$ ls $ORACLE_HOME/dbs/c-1200530011-*
/u01/app/oracle/product/19.3.0/dbhome_1/dbs/c-1200530011-20250519-00

-- pfile 도, 복제본이 만든 컨트롤파일 자동 백업도 남아 있다.
-- 자동 백업은 이름에 원본 DBID 가 박혀 있어 나중에 원본 것으로 오인하기 쉽다. 지금 지운다.

-- 남은 것을 정리한다.

[oracle@oel7v9 ~]$ rm -f $ORACLE_HOME/dbs/initCLONE.ora $ORACLE_HOME/dbs/c-1200530011-20250519-00
[oracle@oel7v9 ~]$ rm -rf /u01/app/oracle/admin/CLONE
[oracle@oel7v9 ~]$ rm -rf /u04/clone

[oracle@oel7v9 ~]$ ps -ef | grep [p]mon
oracle    3021     1  0 08:40 ?        00:00:01 ora_pmon_orcl
oracle    4188     1  0 08:52 ?        00:00:00 ora_pmon_rcat

-- 복제본 인스턴스가 사라졌다.

[oracle@oel7v9 ~]$ export ORACLE_SID=orcl
[oracle@oel7v9 ~]$ sqlplus -s / as sysdba <<< \
> "SELECT COUNT(*) FROM hr.employees;
   SELECT COUNT(*) FROM hr.job_history;
   SELECT * FROM v\$recover_file;"

  COUNT(*)
----------
       107

  COUNT(*)
----------
        10

no rows selected

-- 원본은 아무 영향도 받지 않았다.

-- 실무 포인트
-- 1) 수동 복제본은 DBID 가 원본과 같다.
--    SET DATABASE 는 이름만 바꾼다. RMAN·카탈로그·자동 백업 파일명은 DBID 로 데이터베이스를 구분하므로
--    복제본의 자동 백업이 원본 것과 같은 이름으로 생기고, 카탈로그에 함께 등록할 수 없다.
--    이것이 nid 로 DBID 를 바꾸는 가장 실질적인 이유다(17-8).
--
-- 2) 복제본의 변경은 원본에 전혀 영향을 주지 않는다.
--    파일 경로가 완전히 분리되어 있기 때문이다.
--    반대로 경로가 겹쳐 있으면 그 순간 원본이 위험해진다.
--
-- 3) DROP DATABASE는 MOUNT EXCLUSIVE RESTRICT 상태를 요구한다.
--    ORA-01586이 그 제약을 알려 준다.
--    이 제약이 실수 실행을 어느 정도 막아 주지만 완전하지는 않다.
--
-- 4) 실행 전 반드시 데이터베이스 이름을 확인한다.
--    v$database 의 name 컬럼을 보고 복제본이 맞는지 확인한 뒤 실행한다.
--    ORACLE_SID만 믿지 않는다. DBID 는 원본과 같아 근거가 못 된다.
--
-- 5) DROP DATABASE는 데이터파일·컨트롤파일·리두·임시 파일만 지운다.
--    아카이브, pfile, adump 디렉터리, 복제본이 만든 자동 백업은 별도로 지워야 한다.
--
-- 6) 복제 작업 기록을 남긴다.
--    목적, 시점, 사용 백업, 식별자(DBID 동일 여부 포함), 경로, 삭제 예정일, 담당자가 항목이다.
--    기록이 없으면 정체를 알 수 없는 인스턴스가 자원을 계속 쓰게 된다.
