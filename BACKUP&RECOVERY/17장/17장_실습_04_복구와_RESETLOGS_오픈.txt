[1] 시나리오 개요
--------------------------------------------------------------------------------
-- 컨트롤파일을 만든 복제본을 복구해 연다.
-- UNTIL CANCEL 로 아카이브를 적용한다.
-- RESETLOGS로 열고 임시 파일을 새로 만든다.
-- 10장의 불완전 복구 절차와 같다는 점을 확인한다.
-- 작업 유형 : 복제 수행(장애 복구 아님)

[4] 작업 수행 : 복구 시도
--------------------------------------------------------------------------------
-- 일반 복구를 먼저 시도해 본다.

SYS@CLONE> RECOVER DATABASE;

ORA-00283: recovery session canceled due to errors
ORA-01610: recovery using the BACKUP CONTROLFILE option must be used

-- << 원인 파악 >>
-- 새로 만든 컨트롤파일은 데이터파일의 최신 SCN 정보를 갖고 있지 않다.
-- 어디까지 복구해야 하는지 판단할 근거가 없다.
-- USING BACKUP CONTROLFILE 로 그 판단을 사람에게 넘기라는 뜻이다.
-- 6장과 11장에서 컨트롤파일을 재생성한 뒤 만난 것과 같은 오류다.

-- << 수정 >>

SYS@CLONE> SET AUTORECOVERY ON
SYS@CLONE> RECOVER DATABASE USING BACKUP CONTROLFILE UNTIL CANCEL;

ORA-00279: change 2760100 generated at 05/19/2025 09:12:04 needed for thread 1

Log applied.

ORA-00289: suggestion : /u04/clone/arch/1_45_1190530011.dbf

Log applied.

[7] 오류 발생 → 원인 파악 → 수정
--------------------------------------------------------------------------------
-- 아카이브가 어디에 만들어지는지 확인한다.

SYS@CLONE> ALTER SYSTEM SWITCH LOGFILE;

System altered.

SYS@CLONE> !ls -lt /u04/clone/arch/*.dbf | head -2
-rw-r-----. 1 oracle oinstall  2148352 May 19 10:41 1_1_1190812441.dbf
-rw-r-----. 1 oracle oinstall 45213696 May 19 09:41 1_58_1190530011.dbf

-- 복제본의 아카이브가 복제본 경로에 만들어졌다.
-- 시퀀스가 1부터 다시 시작한다. RESETLOGS로 열었기 때문이다.

SYS@CLONE> !ls -lt /u02/arch1/*.dbf | head -2
-rw-r-----. 1 oracle oinstall 41258496 May 19 10:02 1_58_1190530011.dbf
-rw-r-----. 1 oracle oinstall 38293504 May 19 09:41 1_57_1190530011.dbf

-- 원본 경로에는 복제본의 아카이브가 섞이지 않았다.
-- log_archive_dest_1 을 제대로 바꾼 결과다.

-- 만약 이 값을 바꾸지 않았다면 어떻게 되는지 확인해 본다.

SYS@CLONE> ALTER SYSTEM SET log_archive_dest_1='LOCATION=/u02/arch1' SCOPE=MEMORY;

System altered.

SYS@CLONE> ALTER SYSTEM SWITCH LOGFILE;

System altered.

SYS@CLONE> !ls -lt /u02/arch1/*.dbf | head -2
-rw-r-----. 1 oracle oinstall  1052672 May 19 10:44 1_2_1190812441.dbf
-rw-r-----. 1 oracle oinstall 41258496 May 19 10:02 1_58_1190530011.dbf

-- << 원인 파악 >>
-- 복제본의 아카이브(시퀀스 2)가 원본 디렉터리에 만들어졌다.
-- 파일명의 리셋 스탬프가 달라 구분은 되지만 섞여 있다.
-- 원본에서 아카이브 정리 스크립트를 돌리면 판단이 어려워진다.
-- 반대로 복제본에서 정리하면 원본 아카이브를 지울 위험이 있다.

-- << 수정 >>

SYS@CLONE> ALTER SYSTEM SET log_archive_dest_1='LOCATION=/u04/clone/arch'
  2    SCOPE=BOTH;

System altered.

SYS@CLONE> !rm -f /u02/arch1/1_2_1190812441.dbf

-- 섞인 파일을 지운다. 리셋 스탬프로 복제본 것을 구분했다.

SYS@CLONE> ALTER SYSTEM SWITCH LOGFILE;
SYS@CLONE> !ls -lt /u04/clone/arch/*.dbf | head -1
-rw-r-----. 1 oracle oinstall  1048576 May 19 10:47 1_3_1190812441.dbf

-- 실무 포인트
-- 1) 재생성한 컨트롤파일로 일반 RECOVER를 시도하면 ORA-01610이 나온다.
--    복구 한계를 판단할 근거가 컨트롤파일에 없기 때문이다.
--    USING BACKUP CONTROLFILE 로 그 판단을 사람이 맡는다.
--
-- 2) 마지막 아카이브까지 적용되면 ORA-00308이 나온다.
--    오류가 아니라 도달 가능한 한계에 이르렀다는 신호다.
--    CANCEL로 마무리하면 된다. 10장과 같은 흐름이다.
--
-- 3) RESETLOGS로 열어야 하며 리두 파일이 그때 만들어진다.
--    복제본의 리두 시퀀스가 1부터 시작하는 것을 확인할 수 있다.
--
-- 4) 임시 파일은 반드시 새로 만든다.
--    없으면 정렬이 필요한 조회에서 ORA-01652가 발생한다.
--    복제 절차의 마지막 단계로 넣어 둔다.
--
-- 5) 아카이브 경로를 반드시 확인한다.
--    복제본의 아카이브가 원본 디렉터리에 섞이면 정리 작업이 위험해진다.
--    리셋 스탬프로 구분은 되지만 실수 여지가 크다.
--
-- 6) 복제본이 열리면 파일 목록을 전수 조회한다.
--    v$datafile, v$tempfile, v$logfile, v$controlfile 네 뷰를 모두 본다.
--    하나라도 원본 경로가 있으면 즉시 조치한다.
