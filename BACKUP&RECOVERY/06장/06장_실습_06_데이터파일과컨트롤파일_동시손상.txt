--------------------------------------------------------------------------------
[1] 시나리오 개요
--------------------------------------------------------------------------------
-- 데이터파일 하나와 컨트롤파일 전체가 동시에 유실되었다.
-- 컨트롤파일을 먼저 세워야 데이터파일 상태를 판정할 수 있다.
-- 순서를 뒤집었을 때 무슨 일이 생기는지 먼저 확인한 뒤 올바른 순서로 처리한다.
-- 리두 유무에 따라 부분 복원과 전체 복원으로 갈린다.
-- 복구 유형 : 완전 복구(RESETLOGS 강제)

[7] 복구 절차 : 오류 발생 → 원인 파악 → 수정

-- 순서를 뒤집어 데이터파일부터 복원해 본다.

SYS@orcl> SELECT file#, error FROM v$recover_file;
SELECT file#, error FROM v$recover_file
                         *
ERROR at line 1:
ORA-01507: database not mounted

SYS@orcl> RECOVER DATAFILE 7;
ORA-01507: database not mounted

-- << 원인 파악 >>
-- 복원은 했지만 그것이 맞는 판단이었는지 확인할 방법이 없다.
-- 복구 명령도 실행되지 않는다. MOUNT 상태가 아니기 때문이다.
-- 진단 뷰와 복구 명령은 모두 컨트롤파일을 읽어야 동작한다.
-- 따라서 데이터파일이 아니라 컨트롤파일이 언제나 먼저다.

-- << 수정 >>

-- 실무 포인트
-- 1) 컨트롤파일이 언제나 먼저다.
--    진단 뷰와 복구 명령이 모두 MOUNT 이후에만 동작하기 때문이다.
--    순서를 뒤집으면 복원이 맞았는지 확인할 방법조차 없다.
--
-- 2) 컨트롤파일을 세운 뒤에는 4장의 네 단계 판정을 그대로 적용한다.
--    손상 파일 확인 → 백업본 보유 → 리두 생존 → 떼어 낼 수 있는가 순이다.
--    장애 유형이 달라져도 판정 흐름은 하나다.
--
-- 3) NORESETLOGS 형식으로 만들었어도 RESETLOGS가 강제될 수 있다.
--    USING BACKUP CONTROLFILE 로 복구하면 그 자체가 RESETLOGS를 요구한다.
--    형식 선택과 최종 오픈 방식은 별개의 문제다.
--
-- 4) 리두가 없었다면 이 실습은 전체 복원으로 끝났을 것이다.
--    복원한 파일과 나머지 파일의 SCN 간격을 메울 수단이 없기 때문이다.
--    판정 3단계에서 리두 부족이 확인되면 그 시점에 전체 복원으로 방향을 정한다.
--
-- 5) 복구 시도 전 리두 로그를 별도 위치로 복사해 둔다.
--    이 실습에서도 before_recover_66 에 사본을 만들어 두었다.
--    시도가 실패해도 원상 복귀할 수 있어야 여러 방법을 시험할 수 있다.
--
-- 6) 마무리는 TEMP 추가와 전체 백업이다.
--    데이터베이스가 열렸다는 사실만으로 복구가 끝났다고 보고하지 않는다.

SYS@orcl> EXIT
