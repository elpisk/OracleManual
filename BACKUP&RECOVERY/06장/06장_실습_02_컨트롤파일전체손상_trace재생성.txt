================================================================================
 실습 6-2 : 컨트롤파일 전체 손상 — trace로 재생성
 과정      : Oracle Database 19c Backup & Recovery
 환경      : Oracle 19.3.0 / Oracle Linux 7 / non-CDB ORCL / NOARCHIVELOG
 소요 시간 : 약 25분
================================================================================

--------------------------------------------------------------------------------
[1] 시나리오 개요
--------------------------------------------------------------------------------
-- 컨트롤파일 사본이 모두 유실되었고 Binary 백업본도 없다.
-- TO TRACE 로 뽑아 둔 CREATE CONTROLFILE 문으로 재생성한다.
-- 텍스트이므로 경로와 목록을 편집할 수 있다는 점이 Binary와 다르다.
-- 데이터파일이 추가된 상황을 함께 다뤄 편집의 필요성을 확인한다.
-- 복구 유형 : 완전 복구(NORESETLOGS 또는 RESETLOGS)

--------------------------------------------------------------------------------
[2] 사전 조건
--------------------------------------------------------------------------------
-- 실습 6-1을 마친 상태에서 이어서 진행한다.
-- 데이터베이스가 OPEN 상태여야 TO TRACE 를 수행할 수 있다.

[oracle@oel7v9r1 ~]$ sqlplus / as sysdba

SYS@orcl> SET LINESIZE 200
SYS@orcl> COL name FOR a48

-- << 원인 파악 >>
-- DATAFILE 절에 users02.dbf 를 넣지 않았다.
-- 컨트롤파일에는 그 파일이 등록되지 않았고 Oracle은 UNNAMED00008 이라는
-- 임시 이름으로 자리만 잡아 두었다.
-- 오류 없이 열렸기 때문에 발견이 늦다는 점이 이 실수의 위험이다.
-- CREATE CONTROLFILE 문의 DATAFILE 절은 실제 파일 목록과 반드시 일치해야 한다.

SYS@orcl> SELECT file#, name, status FROM v$datafile WHERE file# = 8;

     FILE# NAME                                                        STATUS
---------- ----------------------------------------------------------- -------
         8 /u01/app/oracle/product/19.3.0/dbhome_1/dbs/UNNAMED00008    RECOVER

-- << 수정 >>
-- 방법 1 : RENAME FILE 로 실제 경로를 지정한다.

SYS@orcl> SHUTDOWN IMMEDIATE
SYS@orcl> STARTUP MOUNT

SYS@orcl> ALTER DATABASE RENAME FILE
  2    '/u01/app/oracle/product/19.3.0/dbhome_1/dbs/UNNAMED00008'
  3  TO '/u01/app/oracle/oradata/ORCL/users02.dbf';

Database altered.

SYS@orcl> SELECT file#, name, status FROM v$datafile WHERE file# = 8;

     FILE# NAME                                          STATUS
---------- --------------------------------------------- -------
         8 /u01/app/oracle/oradata/ORCL/users02.dbf      ONLINE

SYS@orcl> ALTER DATABASE OPEN;

Database altered.

-- 방법 2 : 처음부터 DATAFILE 절에 넣어 재생성한다(권장).
--   CREATE CONTROLFILE 실행 전에 아래를 확인하면 이 오류 자체가 발생하지 않는다.
--   !ls /u01/app/oracle/oradata/ORCL/*.dbf | grep -v temp
--   위 목록과 문의 DATAFILE 절 항목 수가 같아야 한다.

-- 현재 구조를 반영한 백업을 새로 받는다.

SYS@orcl> ALTER DATABASE BACKUP CONTROLFILE TO TRACE
  2    AS '/home/oracle/backup/cf_after_add.sql';
Database altered.

SYS@orcl> !grep -c 'users02' /home/oracle/backup/cf_after_add.sql
1

-- 새 백업에는 users02.dbf 가 포함되어 있다.

-- 실무 포인트
-- 1) DATAFILE 절 누락은 오류 없이 지나간다는 점이 가장 위험하다.
--    데이터베이스는 정상적으로 열리고, 그 파일을 실제로 읽을 때가 되어서야 드러난다.
--    파일이 UNNAMEDnnnnn 이라는 임시 이름으로 등록된 것이 그 증거다.
--
-- 2) 실행 전 목록 대조를 절차로 만든다.
--    ls 로 뽑은 데이터파일 개수와 문의 DATAFILE 항목 수가 같은지 확인한다.
--    TEMP 파일은 제외해야 하므로 grep -v temp 를 함께 쓴다.
--
-- 3) 누락이 발견되면 ALTER DATABASE RENAME FILE 로 되살릴 수 있다.
--    MOUNT 상태에서 UNNAMED 경로를 실제 경로로 바꿔 준다.
--    다만 처음부터 목록을 맞추는 편이 훨씬 안전하다.
--
-- 4) 정상 종료 상태였으므로 NORESETLOGS 형식으로 복구 없이 열렸다.
--    인카네이션이 올라가지 않아 기존 백업본이 계속 유효하다.
--    같은 상황을 Binary 백업본으로 처리했다면 RESETLOGS를 치러야 했다.
--
-- 5) trace 재생성은 TEMP 정보를 남기지 않는다.
--    Binary 복원과 다른 점이며, 마무리 작업에서 반드시 TEMPFILE을 추가한다.
--
-- 6) 구조를 변경했으면 그 자리에서 컨트롤파일 백업을 다시 받는다.
--    이 실습의 모든 문제는 데이터파일 추가 후 백업을 미룬 데서 시작됐다.

SYS@orcl> EXIT
