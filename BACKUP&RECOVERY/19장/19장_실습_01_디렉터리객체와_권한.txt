 실습 19-1 : 디렉터리 객체 생성과 권한 부여
 과정      : Oracle Database 19c Backup & Recovery
 환경      : Oracle 19.3.0 / Oracle Linux 7 / non-CDB ORCL / ARCHIVELOG

--------------------------------------------------------------------------------
[1] 실습 개요
--------------------------------------------------------------------------------
-- Data Pump는 서버 프로세스가 파일을 읽고 쓴다.
-- 그래서 클라이언트 경로를 지정할 수 없고 디렉터리 객체를 통해야 한다.
-- 권한은 두 겹이다. 데이터베이스 쪽 READ/WRITE와 OS 쪽 쓰기 권한이다.
-- 두 권한이 각각 없을 때의 증상을 재현하고 구분하는 법을 익힌다.
-- 작업 유형 : 사전 준비(장애 복구 아님)

[7] 오류 발생 → 원인 파악 → 수정
--------------------------------------------------------------------------------
-- << 원인 파악 : 첫 번째 오류 >>
-- ORA-39087 directory name ... is invalid 가 핵심이다.
-- 디렉터리 객체가 없거나 사용 권한이 없을 때 같은 메시지가 나온다.
-- 둘을 구분해서 확인한다.

SYS@orcl> SELECT directory_name FROM dba_directories
  2  WHERE  directory_name = 'DP_DIR';

DIRECTORY_NAME
---------------
DP_DIR

-- 객체는 있다. 그렇다면 권한 문제다.

SYS@orcl> SELECT grantee, privilege FROM dba_tab_privs
  2  WHERE  table_name = 'DP_DIR' AND grantee = 'HR';

no rows selected

-- << 수정 >>

SYS@orcl> GRANT READ, WRITE ON DIRECTORY dp_dir TO hr;

Grant succeeded.

SYS@orcl> GRANT READ, WRITE ON DIRECTORY dp_bad TO hr;
SYS@orcl> GRANT READ, WRITE ON DIRECTORY dp_none TO hr;

Grant succeeded.

[oracle@oel7v9r1 ~]$ expdp hr/oracle_4U directory=dp_dir \
>   dumpfile=hr_t1.dmp logfile=hr_t1.log schemas=hr

Starting "HR"."SYS_EXPORT_SCHEMA_01":  hr/******** directory=dp_dir ...
. . exported "HR"."EMPLOYEES"                17.05 KB     107 rows
. . exported "HR"."DEPARTMENTS"               7.12 KB      27 rows
Job "HR"."SYS_EXPORT_SCHEMA_01" successfully completed at 09:22:40

-- 데이터베이스 권한 문제는 해결되었다.

-- << 원인 파악 : 두 번째 오류 >>
-- OS 권한이 없는 경로로 실행해 본다.

[oracle@oel7v9r1 ~]$ expdp hr/oracle_4U directory=dp_bad \
>   dumpfile=hr_t2.dmp logfile=hr_t2.log schemas=hr

ORA-39002: invalid operation
ORA-39070: Unable to open the log file.
ORA-29283: invalid file operation
ORA-06512: at "SYS.UTL_FILE", line 536
ORA-29283: invalid file operation

-- ORA-29283이 따라온 점이 앞의 오류와 다르다.
-- 이것은 OS 계층의 문제라는 신호다.
-- 데이터베이스 권한은 이미 부여했으므로 경로 권한을 확인한다.

[oracle@oel7v9r1 ~]$ ls -ld /u03/dpdump_bad

drwx------. 2 root root 6 May 21 09:13 /u03/dpdump_bad

-- 소유자가 root이고 다른 사용자에게는 권한이 전혀 없다.
-- 서버 프로세스는 oracle 사용자 권한으로 동작하므로 쓸 수 없다.

-- << 수정 >>

[oracle@oel7v9r1 ~]$ su -
[root@oel7v9r1 ~]# chown oracle:oinstall /u03/dpdump_bad
[root@oel7v9r1 ~]# chmod 750 /u03/dpdump_bad
[root@oel7v9r1 ~]# exit

[oracle@oel7v9r1 ~]$ expdp hr/oracle_4U directory=dp_bad \
>   dumpfile=hr_t2.dmp logfile=hr_t2.log schemas=hr

Job "HR"."SYS_EXPORT_SCHEMA_01" successfully completed at 09:26:02

--------------------------------------------------------------------------------
[8] 검증 및 실무 포인트
--------------------------------------------------------------------------------
-- 세 번째 경우 : 경로 자체가 없는 디렉터리 객체

[oracle@oel7v9r1 ~]$ expdp hr/oracle_4U directory=dp_none \
>   dumpfile=hr_t3.dmp logfile=hr_t3.log schemas=hr

ORA-39002: invalid operation
ORA-39070: Unable to open the log file.
ORA-29283: invalid file operation

-- OS 권한 부족과 같은 메시지가 나온다.
-- 따라서 경로 존재 여부를 별도로 확인해야 한다.

[oracle@oel7v9r1 ~]$ ls -ld /u03/no_such_path

ls: cannot access /u03/no_such_path: No such file or directory

-- 정리 : 진단 순서

SYS@orcl> SELECT directory_name, directory_path FROM dba_directories
  2  WHERE  directory_name = 'DP_DIR';
-- ① 객체가 있는가

SYS@orcl> SELECT grantee, privilege FROM dba_tab_privs
  2  WHERE  table_name = 'DP_DIR';
-- ② 권한이 있는가

[oracle@oel7v9r1 ~]$ ls -ld /u03/dpdump
-- ③ 경로가 있고 oracle이 쓸 수 있는가

[oracle@oel7v9r1 ~]$ ls -l /u03/dpdump/

-rw-r-----. 1 oracle oinstall  212992 May 21 09:22 hr_t1.dmp
-rw-r--r--. 1 oracle oinstall    1834 May 21 09:22 hr_t1.log

-- 덤프 파일은 640, 로그는 644로 만들어진다.

SYS@orcl> DROP DIRECTORY dp_none;

Directory dropped.

-- 실무 포인트
-- 1) 권한은 두 겹이다.
--    데이터베이스의 READ/WRITE 권한과 OS의 oracle 사용자 쓰기 권한이 모두 필요하다.
--    하나만 빠져도 실패하며 메시지가 어느 쪽인지 바로 알려 주지 않는다.
--
-- 2) 오류 조합으로 계층을 가른다.
--    ORA-39087만 나오면 데이터베이스 권한이나 객체 문제다.
--    ORA-29283이 따라오면 OS 계층 문제다.
--    이 구분만 알아도 진단 시간이 크게 줄어든다.
--
-- 3) 디렉터리 객체는 경로 존재를 검사하지 않는다.
--    없는 경로로도 만들어지며 실행할 때에야 실패한다.
--    만든 직후 작은 스키마로 시험 실행해 두는 편이 안전하다.
--
-- 4) 서버 프로세스는 oracle 사용자로 동작한다.
--    자기 계정으로 쓸 수 있는 경로라고 해도 oracle이 못 쓰면 소용없다.
--    NFS 마운트 경로는 특히 주의한다. 마운트 옵션에 따라 막힐 수 있다.
--
-- 5) 기본 제공되는 DATA_PUMP_DIR을 그대로 쓰지 않는 편이 좋다.
--    ORACLE_BASE 아래에 있어 공간이 부족해지기 쉽다.
--    전용 경로를 만들고 여유 공간을 감시 대상에 넣는다.
--
-- 6) 권한은 롤이 아니라 개별 계정에 부여하는 것이 추적에 유리하다.
--    누가 어떤 경로에 파일을 쓸 수 있는지 dba_tab_privs로 확인할 수 있다.
