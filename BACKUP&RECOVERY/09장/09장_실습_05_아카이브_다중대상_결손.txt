 실습 9-5 : 아카이브 다중 대상 중 한쪽 결손
 과정      : Oracle Database 19c Backup & Recovery
 환경      : Oracle 19.3.0 / Oracle Linux 7 / non-CDB ORCL / ARCHIVELOG

--------------------------------------------------------------------------------
[1] 시나리오 개요
--------------------------------------------------------------------------------
-- 아카이브를 두 대상에 생성하도록 구성한 환경이다.
-- 복구에 필요한 시퀀스가 1번 대상에만 없고 2번 대상에는 있다.
-- 프롬프트에 다른 대상의 경로를 입력해 복구를 이어 간다.
-- 사전 복사 방식과 경로 지정 방식을 모두 확인한다.
-- 복구 유형 : 완전 복구(다중 대상 활용)

--------------------------------------------------------------------------------

-- 실제 파일은 1번 대상에 두 개, 2번 대상에 세 개다.
-- 시퀀스 47이 1번 대상에서 사라졌다.

-- 판정
--   ① 백업본 : 있음
--   ② 필요한 아카이브 : 46~48
--   ③ 1번 대상에 47 없음, 2번 대상에는 있음
--   → 2번 대상의 파일을 쓰면 완전 복구가 가능하다.

--------------------------------------------------------------------------------
[7] 복구 절차 : 오류 발생 → 원인 파악 → 수정
--------------------------------------------------------------------------------
SYS@orcl> ALTER TABLESPACE users OFFLINE IMMEDIATE;
Tablespace altered.

SYS@orcl> !cp -p /home/oracle/backup/ch09/users01.dbf /u02/oradata/ORCL/

-- AUTORECOVERY를 켠 채 복구를 시도한다.

SYS@orcl> SET AUTORECOVERY ON
SYS@orcl> RECOVER TABLESPACE users;
ORA-00279: change 2415100 generated at 11/05/2025 14:08:33 needed for thread 1
ORA-00289: suggestion : /u02/arch1/1_46_1200530011.dbf
ORA-00280: change 2415100 for thread 1 is in sequence #46

Log applied.

ORA-00308: cannot open archived log '/u02/arch1/1_47_1200530011.dbf'
ORA-27037: unable to obtain file status
Linux-x86_64 Error: 2: No such file or directory

-- << 원인 파악 >>
-- 시퀀스 46은 적용되었고 47에서 멈췄다.
-- AUTORECOVERY는 기본 대상 경로에서만 파일을 찾는다.
-- 2번 대상에 같은 파일이 있지만 스스로 찾아가지는 않는다.
-- 결손이 예상되면 AUTORECOVERY를 끄고 프롬프트에서 경로를 지정해야 한다.

SYS@orcl> !ls -l /u03/arch2/1_47_1200530011.dbf
-rw-r-----. 1 oracle oinstall 12583424 May 11 14:10 /u03/arch2/1_47_1200530011.dbf

-- << 수정 : 방법 1 — 프롬프트에서 경로 지정 >>

SYS@orcl> SET AUTORECOVERY OFF
SYS@orcl> RECOVER TABLESPACE users;
ORA-00279: change 2415440 generated at 11/05/2025 14:09:12 needed for thread 1
ORA-00289: suggestion : /u02/arch1/1_47_1200530011.dbf
ORA-00280: change 2415440 for thread 1 is in sequence #47

Specify log: {<RET>=suggested | filename | AUTO | CANCEL}
/u03/arch2/1_47_1200530011.dbf
Log applied.

ORA-00279: change 2415820 generated at 11/05/2025 14:09:55 needed for thread 1
ORA-00280: change 2415820 for thread 1 is in sequence #48

Specify log: {<RET>=suggested | filename | AUTO | CANCEL}
AUTO
Media recovery complete.

-- 결손 구간만 손으로 넘기고 나머지는 AUTO로 처리했다.

SYS@orcl> ALTER TABLESPACE users ONLINE;

-- 여러 시퀀스가 빠져 있다면 이 방식이 훨씬 편하다.

-- 컨트롤파일 기록과 실제 파일의 불일치를 정리한다.

[oracle@oel7v9r1 ~]$ rman target /

RMAN> CROSSCHECK ARCHIVELOG ALL;

validation succeeded for archived log
archived log file name=/u02/arch1/1_46_1200530011.dbf RECID=61 STAMP=1200534120
validation succeeded for archived log
archived log file name=/u02/arch1/1_47_1200530011.dbf RECID=63 STAMP=1200534180
Crosschecked 6 objects

RMAN> EXIT

-- 실무 포인트
-- 1) 아카이브는 위치와 무관하게 내용이 같다.
--    어느 대상의 파일이든 복구에 쓸 수 있으므로 경로만 알려 주면 된다.
--    다중 대상 구성의 실질적 가치가 여기서 드러난다.
--
-- 2) AUTORECOVERY는 기본 대상 경로에서만 찾는다.
--    다른 대상에 파일이 있어도 스스로 찾아가지 않고 ORA-00308로 멈춘다.
--    결손이 예상되면 AUTORECOVERY를 끄고 수동으로 진행한다.
--
-- 3) 결손 구간만 손으로 넘기고 이후 AUTO를 입력하면 나머지가 자동 처리된다.
--    빠진 시퀀스가 하나뿐이라면 이 방식이 가장 빠르다.
--
-- 4) 여러 시퀀스가 빠져 있으면 미리 복사해 두는 편이 낫다.
--    2번 대상에서 기본 경로로 복사한 뒤 AUTO로 한 번에 진행한다.
--    SET LOGSOURCE 로 아카이브 위치 자체를 바꿔 지정할 수도 있다.
--
-- 5) OS로 아카이브를 지우면 컨트롤파일 기록과 어긋난다.
--    v$archived_log 에는 남아 있는데 실제 파일이 없는 상태가 된다.
--    RMAN CROSSCHECK 로 상태를 맞춰야 이후 판단이 정확해진다.
--
-- 6) 정리 스크립트를 점검한다.
--    이 실습의 원인은 필요한 구간까지 지운 정리 작업이었다.
--    백업 완료 여부를 조건으로 걸어야 하며 날짜만 보고 지우는 방식은 위험하다.

SYS@orcl> EXIT
