-- 새벽 3시 31분. 운영 서버 oel7v9 이 응답하지 않는다.
-- 데이터센터에서 연락이 왔다. 해당 랙의 전원 계통 사고로
-- 서버와 로컬 디스크가 모두 손상되었다. 복구 불가 판정이다.
-- sales 의 주간 전체 백업이 03:31:05 에 끝났고 그 2초 뒤에 서버가 죽었다.
--
-- 사라진 것
--   - oel7v9 서버 전체
--   - /u01/app/oracle/oradata/SALES/ (모든 데이터파일, 컨트롤파일, 온라인 리두)
--   - /home/oracle/arch_sales/ (아카이브 로그)
--   - $ORACLE_HOME/dbs/spfilesales.ora, orapwsales
--   - 같은 서버의 orcl (이 실습에서는 다루지 않는다. 절차는 같다)
--
-- 남아 있는 것
--   - oel7v9r2 서버 (rcat, hrdb 가 돌고 있다)
--   - /backup (NFS 로 oel7v9r2 에서도 보인다)
--   - /archive_keep (별도 스토리지, 무사)
--   - Recovery Catalog (rcat)
--
-- 업무 요구
--   "오전 8시 전까지 sales 를 되살릴 것. 데이터 손실은 최소화."
--
-- 이 상황에서 카탈로그가 하는 일은 결정적이다.
--   - sales 의 DBID 를 알려 준다
--   - 데이터파일이 몇 개였고 각각 어느 테이블스페이스였는지 알려 준다
--   - 리두 로그 그룹 구성과 크기를 알려 준다
--   - 어떤 백업으로 어디까지 복구할 수 있는지 알려 준다
--
-- 이 정보 없이는 복구 계획조차 세울 수 없다.
--
-- 요구 사항
--   ① 카탈로그에서 복구에 필요한 정보를 모두 수집한다
--   ② 경로가 완전히 다른 서버에 복구한다
--   ③ 데이터 손실 범위를 정확히 산정하고 보고한다
--   ④ 복구 후 백업 체계를 정상화한다
--   ⑤ 소요 시간을 측정해 RTO 산정 근거로 남긴다

--------------------------------------------------------------------------------
[2] 사전 설계
--------------------------------------------------------------------------------
-- 2-1. 카탈로그에서 수집해야 할 정보
--
--   정보              | 조회 대상                | 없으면 생기는 문제
--   ------------------|--------------------------|--------------------------
--   DBID·인카네이션   | rc_database_incarnation  | 자동 백업을 찾지 못한다
--   데이터파일 구성   | rc_datafile              | SET NEWNAME 목록을 못 만든다
--   테이블스페이스    | rc_tablespace            | 구조를 파악할 수 없다
--   리두 로그 구성    | rc_redo_log              | 재생성될 로그를 예측 못 한다
--   임시 파일         | rc_tempfile              | 오픈 후 TEMP 를 못 만든다
--   마지막 백업 시각  | rc_backup_set_details    | 손실 범위를 산정할 수 없다
--   마지막 아카이브   | rc_archived_log          | 복구 종점을 모른다
--   백업 조각 경로    | rc_backup_piece          | 매체를 준비할 수 없다
--   CONFIGURE 설정    | rc_rman_configuration    | 채널 구성을 재현할 수 없다
--
--   이 중 DBID 하나만 있어도 시작은 할 수 있다.
--   그러나 계획 수립과 시간 산정에는 나머지가 모두 필요하다.
--   뷰 이름과 열 이름은 기억에 의존하지 않는다. [7-1]의 스크립트가 그것을 대신한다.

-- 2-2. 경로 매핑 설계
--
--   구분           | 원본 (oel7v9)                    | 대상 (oel7v9r2)
--   ---------------|----------------------------------|---------------------
--   데이터파일     | /u01/app/oracle/oradata/SALES/   | /u02/oradata/sales/
--   온라인 리두    | /u01/app/oracle/oradata/SALES/   | /u02/oradata/sales/
--   컨트롤파일     | /u01/app/oracle/oradata/SALES/   | /u02/oradata/sales/
--   임시 파일      | /u01/app/oracle/oradata/SALES/   | /u02/oradata/sales/
--   아카이브       | /home/oracle/arch_sales/         | /u02/arch_sales/
--   감사 로그      | /u01/app/oracle/admin/sales/adump| /u02/admin/sales/adump
--   변경 추적 파일 | /u01/app/oracle/oradata/SALES/   | 사용하지 않음 (08 참조)
--
--   경로 변경 수단 두 가지
--     SET NEWNAME + SWITCH        데이터파일 개별 지정. 정밀하다
--     DB_FILE_NAME_CONVERT        일괄 치환. spfile 파라미터
--
--   이 실습에서는 SET NEWNAME 을 쓴다.
--   재해 상황에서는 원본 경로 구조를 그대로 유지할 수 없는 경우가 많고
--   파일별로 다른 위치에 두어야 할 수도 있다.
--
--   데이터파일 외의 것은 각각 다른 수단으로 옮긴다.
--     온라인 리두     ALTER DATABASE RENAME FILE (RESETLOGS 전)
--     임시 파일       DROP 후 오픈 뒤 ADD TEMPFILE
--     변경 추적 파일  DISABLE BLOCK CHANGE TRACKING (오픈 전)

-- 2-3. 복구 순서
--
--   ① 카탈로그에서 정보 수집          (10분)
--   ② 대상 서버 준비 — 경로, 비밀번호 파일, 최소 pfile  (10분)
--   ③ NOMOUNT 기동                    (2분)
--   ④ spfile 복원                     (3분)
--   ⑤ spfile 수정 후 재기동           (5분)
--   ⑥ 컨트롤파일 복원 후 MOUNT        (5분)
--   ⑦ SET NEWNAME + RESTORE + SWITCH + RECOVER (한 RUN 블록)  (20분)
--   ⑧ 리두·임시·변경추적 파일 정리     (5분)
--   ⑨ OPEN RESETLOGS                  (5분)
--   ⑩ 리스너·tnsnames·검증            (15분)
--   ⑪ 새 인카네이션 전체 백업         (10분)
--
--   추정 합계 약 1시간 30분. 목표 시각(08시)까지 여유가 있다.

-- 2-4. 데이터 손실 산정 방법
--
--   손실 범위 = 마지막으로 백업된 아카이브 이후의 변경
--
--   온라인 리두 로그가 사라졌으므로
--   백업되지 않은 아카이브와 현재 리두의 내용은 복구할 수 없다.
--   이것이 물리 백업 체계에서 RPO 를 결정하는 지점이다.
--
--   산정에 필요한 두 값
--     ① 마지막으로 백업된 아카이브의 종료 SCN 과 시각
--     ② 장애 발생 시각
--   이 둘의 차이가 손실 구간이다.

RC_REPORT@rcat> SELECT s.bs_key, s.backup_type, s.incremental_level,
  2         TO_CHAR(s.completion_time,'MM-DD HH24:MI:SS') AS done,
  3         ROUND(s.output_bytes/1024/1024) AS mb
  4  FROM   rc_backup_set_details s
  5  WHERE  s.db_name = 'SALES' AND s.completion_time > SYSDATE - 1
  6  AND    (s.backup_type = 'L' OR EXISTS (SELECT 1 FROM rc_backup_datafile d
  7                                         WHERE d.bs_key = s.bs_key AND d.file# > 0))
  8  ORDER  BY s.completion_time;

-- 7-3. 확장 과제
--
-- 과제 A. 카탈로그도 함께 잃었다면
--   이 실습은 카탈로그가 살아 있는 것을 전제로 했다.
--   카탈로그와 운영 서버를 동시에 잃었을 때의 복구 절차를 작성하시오.
--   고급 실습 05의 절차 D와 결합해 전체 순서를 만든다.
--   DBID_LIST.txt 가 어디에 보관되어야 하는지도 재검토한다.
--
-- 과제 B. 손실 구간 축소
--   이 실습의 손실은 14초였지만 백업 주기가 하루면 최대 하루다.
--   손실을 10분 이내로 줄이는 방안을 세 가지 제시하고
--   각각의 비용과 운영 부담을 비교하시오.
--   아카이브 백업 주기 단축 / 아카이브 다중 대상 / Data Guard 를 검토한다.
--
-- 과제 C. 복구 순서의 근거
--   [2-3]의 11단계에서 순서를 바꿀 수 있는 단계와
--   절대 바꿀 수 없는 단계를 구분하고 이유를 설명하시오.
--   [5] 오류 ③의 "한 RUN 블록" 조건이 어느 단계에 해당하는지도 밝힌다.
--
-- 과제 D. orcl 재구축
--   같은 절차로 orcl(8.7GB, 파일 6개, 그중 하나는 예외 경로)을 재구축하시오.
--   [6-7]의 표를 다시 채우고 크기에 비례해 늘어나는 단계와 그렇지 않은 단계를 구분한다.
--
-- 과제 E. 애플리케이션 전환
--   DB 복구는 끝났지만 서비스는 아직 정상이 아니다.
--   접속 정보 변경, 커넥션 풀 재시작, 배치 재개 순서를 포함한
--   서비스 전환 절차를 작성하시오. [6-5]의 local_listener 도 절차에 넣는다.

-- 7-4. 정리 — 이 실습에서 남는 것
--
--   ① dr_collect_info.sql : 재해 시 정보 수집 (10개 항목)
--   ② dr_rebuild.sh       : 준비와 구문 생성 자동화
--   ③ 경로 매핑 설계표    : [2-2]
--   ④ 복구 순서 11단계    : [2-3]
--   ⑤ RTO 실측 근거표     : [6-7]
--   ⑥ 훈련 후 원복 절차   : [6-8]
--
-- 다음 예제에서는 이 복구 시간을 좌우하는 백업 성능을 다룬다.

-- 실무 포인트
-- 1) 카탈로그가 복구 계획의 출발점이다.
--    DBID 없이는 자동 백업을 찾지 못하고
--    파일 목록 없이는 SET NEWNAME 을 만들 수 없다.
--    dr_collect_info.sql 을 평시에 정기 실행해 결과를 별도 보관한다.
--
-- 2) SET NEWNAME · RESTORE · SWITCH · RECOVER 는 한 RUN 블록이다.
--    19c 는 SWITCH 를 자동으로 해 주지만, 세션을 끊으면 카탈로그가 그것을 모른다.
--    백업 컨트롤파일은 resync 가 안 되므로(ORA-00236) RMAN-06094 로 막힌다.
--
-- 3) spfile 은 원본 경로를 그대로 담고 있다.
--    복원한 뒤 반드시 pfile 로 변환해 경로를 고치고 다시 만든다.
--    control_files, 아카이브, 감사 경로뿐 아니라 local_listener 와 지갑 파라미터도 본다.
--
-- 4) 데이터파일 말고도 옮길 것이 셋 있다.
--    리두(RENAME FILE), 임시 파일(DROP 후 ADD), 변경 추적 파일(DISABLE).
--    셋 다 컨트롤파일에 원본 경로로 남아 있고 RESETLOGS 전에 정리해야 한다.
--
-- 5) 재해 복구는 복제가 아니다.
--    DBID 가 유지되어야 하며 카탈로그의 기존 이력을 이어서 쓴다.
--    17장의 DUPLICATE 는 새 DBID 를 만든다는 점에서 목적이 다르다.
--
-- 6) 손실 범위를 먼저 산정해 보고한다.
--    복구 시작 전에 "어디까지 살릴 수 있는가"를 확정해야
--    업무 측이 수작업 복원 계획을 병행할 수 있다.
--    이 판단이 늦으면 전체 복구 시간이 길어진다.
--
-- 7) 복구 완료는 오픈이 아니라 백업 체계 정상화까지다.
--    RESETLOGS 후 새 기준 백업을 받지 않으면
--    다음 장애에서 인카네이션을 거슬러야 하는 훨씬 어려운 상황이 된다.
--    훈련이었다면 원본이 돌아온 뒤 카탈로그 인카네이션도 확인한다([6-8]).
