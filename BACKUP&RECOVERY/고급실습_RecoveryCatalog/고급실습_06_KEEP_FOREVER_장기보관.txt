================================================================================
 고급 실습 06 : KEEP FOREVER 장기 보관과 보존 요건 대응
 과정      : Oracle Database 19c Backup & Recovery — Recovery Catalog 고급
 환경      : Oracle 19.3.0 / Oracle Linux 7 / oel7v9(운영계) + oel7v9r2(관리계) / ARCHIVELOG
 대상 DB   : orcl, sales (oel7v9) / hrdb (oel7v9r2)
 카탈로그  : rcat @ oel7v9r2
 소요 시간 : 약 2시간 30분
 선행 조건 : 고급 실습 01~05 완료
================================================================================

--------------------------------------------------------------------------------
[1] 실무 상황
--------------------------------------------------------------------------------
-- 규제 대응 부서에서 요구가 내려왔다.
--
--   "분기 마감 시점의 데이터베이스 상태를 5년간 보관할 것.
--    감사 요청 시 해당 시점의 데이터를 조회할 수 있어야 함."
--
-- 지금 상태로는 불가능하다.
--   - 보존 정책이 21일이다
--   - 매일 05시 정기 정리(고급 실습 04)가 21일 넘은 백업을 지운다
--   - 작년 4분기 마감 백업을 찾아봤으나 이미 없다
--
-- 동시에 개발팀에서 요청이 왔다.
--   "작년 3월 말 상태의 sales 스키마가 필요합니다. 통계 재계산 검증용입니다."
--
-- 실무자가 시도한 우회책도 문제가 있었다.
--   분기말 백업을 별도 디렉터리에 cp 로 복사해 두었는데
--   그 파일이 어느 시점의 것인지, 복원에 필요한 아카이브가 무엇인지
--   기록이 남아 있지 않다.
--
-- 요구 사항
--   ① 분기말 백업이 정기 정리에서 제외되어야 한다
--   ② 5년 뒤에도 그 백업만으로 복원할 수 있어야 한다
--   ③ 어떤 백업이 장기 보관 대상인지 조회할 수 있어야 한다
--   ④ 보존 기한이 지난 것은 자동으로 해제되어야 한다
--   ⑤ 보관 목록을 감사에 제출할 수 있어야 한다
--
-- KEEP 옵션이 정확히 이 요구를 위해 있다.
-- 그리고 KEEP FOREVER 는 Recovery Catalog 가 있어야만 쓸 수 있다.

--------------------------------------------------------------------------------
[2] 사전 설계
--------------------------------------------------------------------------------
-- 2-1. KEEP 옵션의 세 가지 형태
--
--   구문                          | 보존 기한   | 카탈로그 | 용도
--   ------------------------------|-------------|----------|----------------
--   KEEP UNTIL TIME '<날짜>'      | 지정 시각   | 불필요   | 기한이 정해진 보관
--   KEEP FOREVER                  | 무기한      | 필수     | 영구 보관 (nocatalog 는 RMAN-06522)
--   KEEP ... RESTORE POINT <이름> | 위와 동일   | 위와 동일| 시점에 이름 부여
--
--   KEEP FOREVER 에 카탈로그가 필요한 이유
--     컨트롤파일은 순환 재사용 영역이다.
--     CONTROL_FILE_RECORD_KEEP_TIME 이 지나면 기록이 덮인다.
--     "영원히"를 보장할 수 있는 저장소가 카탈로그뿐이다.

-- 2-2. KEEP 백업의 성질
--
--   ① 보존 정책의 대상에서 제외된다
--      REPORT OBSOLETE 에 나타나지 않는다
--      DELETE OBSOLETE 로 지워지지 않는다
--
--   ② 자기 완결적으로 만들어진다
--      복원에 필요한 아카이브 로그와 spfile, 컨트롤파일이 별도 세트로 함께 백업된다 (세트 4개)
--      그래서 KEEP 백업 하나만 있으면 그 시점으로 복원할 수 있다
--
--   ③ FRA 에 저장할 수 없다 (ORA-19811)
--      FRA 는 보존 정책에 따라 자동 관리되는 공간이다
--      "지우지 말 것"과 "자동 관리"는 양립하지 않는다
--
--   ④ RESTORE POINT 로 시점에 이름을 붙일 수 있다
--      SCN 을 외우지 않고 이름으로 복원 시점을 지정한다

-- 2-3. 보관 설계
--
--   대상       | 주기      | 보존 기한 | 저장 위치           | 태그
--   -----------|-----------|-----------|---------------------|-------------------
--   orcl       | 분기말    | 5년       | /archive_keep/ORCL  | ORCL_QTR_YYYYQn
--   sales      | 분기말    | 5년       | /archive_keep/SALES | SALES_QTR_YYYYQn
--   hrdb       | 연말      | 7년       | /archive_keep/HRDB  | HRDB_YEAR_YYYY
--   임시 보관  | 요청 시   | 90일      | /archive_keep/ADHOC | ADHOC_<사유>_YYYYMMDD
--
--   복원 지점 이름 규칙 : <DB>_Q<분기>_<YYYY>  예) ORCL_Q1_2025
--
--   저장 위치를 정기 백업과 분리하는 이유
--     ① 정기 백업 경로의 정리 작업이 실수로 건드리는 것을 막는다
--     ② 장기 보관 매체(테이프, 오브젝트 스토리지)로 옮기기 쉽다
--     ③ 용량 산정과 비용 배분이 분리된다

-- 2-4. 5년 보관의 현실적 문제
--
--   문제 1. 5년 뒤 그 버전의 오라클이 있는가
--     19c 백업은 19c 이상에서만 복원된다.
--     장기 보관은 소프트웨어 보관 계획과 함께 세워야 한다.
--
--   문제 2. 매체 수명
--     디스크는 5년을 보장하지 않는다.
--     정기적으로 매체를 교체하고 검증해야 한다.
--
--   문제 3. 용량
--     분기 4회 × 5년 = 20세대. DB 크기의 20배가 필요하다.
--     압축을 반드시 적용한다.
--
--   대안 검토
--     데이터만 필요하다면 19장의 Data Pump 논리 백업이 더 적합할 수 있다.
--     버전 종속이 낮고 크기도 작다.
--     반면 "그 시점 전체 상태"가 필요하면 KEEP 백업이 맞다.

-- 7-2. 분기말 자동 수행 스크립트

[oracle@oel7v9 ~]$ cat /home/oracle/rcadm/rc_quarterly_keep.sh

#!/bin/bash
# 분기말 장기 보관 백업
# 사용법 : rc_quarterly_keep.sh <ORACLE_SID>
set -u
SID=$1
DBNAME=$(echo $SID | tr 'a-z' 'A-Z')
export ORACLE_HOME=/u01/app/oracle/product/19.3.0/dbhome_1
export ORACLE_SID=$SID
export PATH=$ORACLE_HOME/bin:$PATH

# 분기 계산
YEAR=$(date +%Y)
MON=$(date +%m)
QTR=$(( (10#$MON - 1) / 3 + 1 ))
TAG="${DBNAME}_QTR_${YEAR}Q${QTR}"
RP="${DBNAME}_Q${QTR}_${YEAR}"
KEEPDIR=/archive_keep/$DBNAME
LOG=/home/oracle/rcadm/log/keep_${SID}_${YEAR}Q${QTR}.log
MAILTO="dba-team@example.com"

mkdir -p $KEEPDIR

# --- 안전장치 1 : 카탈로그 필수 (KEEP FOREVER 요건)
if ! echo "exit" | rman target / catalog rcatowner/oracle_4U@rcat >/dev/null 2>&1
then
  echo "[ABORT] recovery catalog required for KEEP FOREVER" | tee -a $LOG
  mailx -s "[ABORT] quarterly keep - catalog down ($SID)" $MAILTO < $LOG
  exit 2
fi

# --- 안전장치 2 : 보관 경로가 FRA 밖인가 (ORA-19811 방지)
FRA=$(sqlplus -s / as sysdba << 'EOF'
SET PAGESIZE 0 FEEDBACK OFF HEADING OFF
SELECT value FROM v$parameter WHERE name='db_recovery_file_dest';
EXIT
EOF
)
case "$KEEPDIR" in
  ${FRA}*) echo "[ABORT] keep path is inside FRA" | tee -a $LOG; exit 2 ;;
esac

# --- 안전장치 3 : 중복 방지
if rman target / catalog rcatowner/oracle_4U@rcat << EOF 2>/dev/null | grep -q "$TAG"
LIST BACKUP SUMMARY TAG '$TAG';
EXIT
EOF
then
  echo "[SKIP] $TAG already exists" | tee -a $LOG
  exit 0
fi

# --- 수행
rman target / catalog rcatowner/oracle_4U@rcat >> $LOG 2>&1 << EOF
RUN {
  ALLOCATE CHANNEL c1 DEVICE TYPE DISK FORMAT '$KEEPDIR/%d_Q${QTR}_${YEAR}_%U';
  BACKUP AS COMPRESSED BACKUPSET DATABASE
    TAG '$TAG' KEEP FOREVER RESTORE POINT $RP;
  RELEASE CHANNEL c1;
}
EXIT
EOF

# --- 즉시 검증 (요구 사항 ②)
rman target / catalog rcatowner/oracle_4U@rcat >> $LOG 2>&1 << EOF
RESTORE DATABASE UNTIL RESTORE POINT $RP VALIDATE;
LIST BACKUP TAG '$TAG';
EXIT
EOF

if grep -qE 'ORA-[0-9]+|RMAN-[0-9]+' $LOG; then
  mailx -s "[FAIL] quarterly keep $TAG" $MAILTO < $LOG
  exit 1
fi

echo "[OK] $TAG completed and validated"
exit 0

-- 7-5. 정리 — 이 실습에서 남는 것
--
--   ① rc_keep_audit.sql       : 장기 보관 감사 리포트 (분기 누락 점검 포함)
--   ② rc_quarterly_keep.sh    : 분기말 자동 보관 (안전장치 3중)
--   ③ rc_keep_verify.sh       : 연 1회 전량 복원 검증
--   ④ 보관 설계표             : [2-3]
--   ⑤ 용량 산정 근거          : [6-5]
--
-- 다음 예제에서는 이 백업들을 실제로 다른 서버에서 복구해 본다.

-- 실무 포인트
-- 1) KEEP FOREVER 는 카탈로그가 있어야만 쓸 수 있다 (nocatalog 는 RMAN-06522).
--    컨트롤파일은 순환 재사용 영역이라 영구 보관을 보장할 수 없다.
--    장기 보관 요건이 있는 조직에서 카탈로그는 선택이 아니다.
--
-- 2) KEEP 백업은 FRA 에 둘 수 없다.
--    ORA-19811 로 거부된다. 자동 관리와 영구 보관은 양립하지 않는다.
--    채널 FORMAT 을 명시해 FRA 밖으로 보낸다.
--
-- 3) 장기 보관은 처음부터 KEEP 으로 받는다.
--    사후에 CHANGE ... KEEP 을 걸면 keep_options 만 바뀌고 아카이브는 따라오지 않는다.
--    RESTORE ... PREVIEW 는 그 상태를 오류가 아니라 "not found in repository" 한 줄로 알린다.
--
-- 4) KEEP 백업은 자기 완결적으로 만들어진다.
--    데이터파일, 아카이브, spfile, 컨트롤파일이 함께 백업된다.
--    그래서 그 세트만으로 해당 시점 복원이 가능하다.
--
-- 5) 목록에 있는 것과 복원되는 것은 다르다.
--    KEEP 백업은 오래 방치되므로 정기 검증이 반드시 필요하다.
--    받을 때 한 번, 그리고 연 1회 전량 검증을 절차로 만든다.
--    LIST BACKUP KEEP 같은 명령은 없다. 목록은 rc_backup_set.keep_options 로, 속성은 LIST BACKUP TAG 의 "Keep:" 줄로 본다.
--
-- 6) 5년 보관은 소프트웨어 보관 계획과 함께 세운다.
--    19c 백업은 19c 이상에서만 복원된다.
--    매체 수명, 용량 증가, 버전 지원 종료를 함께 고려해야 실제로 쓸 수 있다.
