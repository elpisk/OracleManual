--------------------------------------------------------------------------------
[1] 실무 상황
--------------------------------------------------------------------------------
-- 고급 실습 02의 일일 리포트에서 추세 이상이 잡혔다.
--
--   ORCL 소요     402  411  408  415  491  478  491   (초)
--   ORCL 크기    1.18 1.19 1.20 1.21 1.22 1.23 1.24   (GB)
--
-- 크기는 5% 늘었는데 시간은 22% 늘었다. 비례하지 않는다.
--
-- 그 뒤로도 계속 늘어 지금은 이렇게 되었다.
--   - 일일 증분 백업이 02:00 에 시작해 03:40 에 끝난다
--   - 배치 작업이 03:00 에 시작하므로 40분간 겹친다
--   - 배치 담당자로부터 성능 저하 항의가 들어왔다
--
-- 백업 창(backup window)은 02:00~03:00 한 시간이다.
-- 지금은 100분이 걸린다.
--
-- 운영팀 의견은 갈린다.
--   A : "채널을 늘리면 된다"
--   B : "압축을 켜면 I/O 가 줄어 빨라진다"
--   C : "증분인데 왜 오래 걸리나. Block Change Tracking 을 켜자"
--
-- 셋 다 그럴듯하지만 근거가 없다.
-- 카탈로그에 3개월치 이력이 있으므로 먼저 분석한다.
--
-- 요구 사항
--   ① 소요 시간 증가의 원인을 데이터로 규명한다
--   ② 각 개선안의 효과를 측정해 비교한다
--   ③ 백업 창 60분 안에 들어오게 만든다
--   ④ 복구 시간에 미치는 영향도 함께 평가한다
--   ⑤ 이상 징후를 조기에 감지하는 지표를 만든다

--------------------------------------------------------------------------------
[2] 사전 설계
--------------------------------------------------------------------------------
-- 2-1. 분석 축
--
--   축                | 지표                        | 조회 대상
--   ------------------|-----------------------------|------------------------
--   처리량            | input_bytes / elapsed_sec   | rc_rman_backup_job_details
--   압축률            | input_bytes / output_bytes  | 위와 동일
--   읽은 양 vs 쓴 양  | 증분에서 특히 중요          | v$backup_datafile
--   변경 추적 사용    | used_change_tracking        | v$backup_datafile
--   채널별 편중       | 채널별 처리 파일 수         | v$backup_async_io
--   대기 이벤트       | 백업 중 세션의 event        | v$session_wait
--
--   핵심 질문
--     "증분 백업이 왜 전체 백업만큼 오래 걸리는가"
--     증분은 변경된 블록만 쓰지만 기본 동작은 전체 블록을 읽는다.
--     읽는 양이 줄지 않으면 시간도 줄지 않는다.

-- 2-2. 개선안과 예상 효과
--
--   개선안                  | 줄이는 것    | 부작용
--   ------------------------|--------------|---------------------------
--   채널 증가               | 병렬로 분산  | CPU·I/O 경합
--   Block Change Tracking   | 읽는 양      | 소량의 쓰기 부하 상시 발생
--   압축                    | 쓰는 양      | CPU 사용 증가. 라이선스
--   SECTION SIZE            | 파일 단위 편중| 조각 수 증가
--   FILESPERSET 조정        | 세트 구성    | 복원 시 읽는 단위 변화
--   DURATION MINIMIZE LOAD  | 부하         | 시간이 더 걸린다
--
--   측정 없이 여러 개를 동시에 적용하면 무엇이 효과였는지 알 수 없다.
--   하나씩 적용하고 매번 측정한다.

-- 2-3. 측정 프로토콜
--
--   ① 기준선 3회 측정 후 중앙값 사용
--   ② 매 측정 전 버퍼 캐시 초기화는 하지 않는다 (운영 조건 유지)
--   ③ 다른 부하가 없는 시간대에 수행
--   ④ 측정마다 카탈로그의 job_details 를 기록
--   ⑤ 개선안 적용 후 최소 2회 측정
--
--   비교 지표는 elapsed_seconds 와 input_bytes/sec 두 가지를 함께 본다.
--   시간만 보면 데이터 증가와 개선 효과가 섞인다.

-- 2-4. 복구 시간과의 관계 (요구 사항 ④)
--
--   백업을 빠르게 만드는 선택이 복구를 느리게 만들 수 있다.
--
--   선택            | 백업 시간 | 복구 시간
--   ----------------|-----------|----------------------------
--   차등 증분       | 짧다      | 길다 (모든 Level 1 적용)
--   누적 증분       | 길다      | 짧다 (마지막 하나만)
--   압축            | 길다      | 길다 (해제 부하)
--   채널 증가       | 짧다      | 짧다 (복원도 병렬)
--
--   백업 창만 보고 결정하면 RTO 를 해칠 수 있다.

[oracle@oel7v9r1 ~]$ cat /home/oracle/rcadm/bench_backup.sh

#!/bin/bash
# 백업 성능 측정 (단일 실행)
SID=$1; LABEL=$2
export ORACLE_HOME=/u01/app/oracle/product/19.3.0/dbhome_1
export ORACLE_SID=$SID
export PATH=$ORACLE_HOME/bin:$PATH
LOG=/home/oracle/rcadm/bench/${SID}_${LABEL}_$(date +%H%M%S).log
mkdir -p /home/oracle/rcadm/bench

S=$(date +%s)
rman target / catalog rcatowner/oracle_4U@rcat > $LOG 2>&1 << EOF
BACKUP INCREMENTAL LEVEL 1 DATABASE TAG 'BENCH_$LABEL';
EOF
E=$(date +%s)
echo "$LABEL elapsed=$((E-S))s"
grep -E 'Finished backup|piece handle' $LOG | tail -3

-- 7-1. rc_perf_analysis.sql — 백업 성능 분석 리포트

[oracle@oel7v9r2 ~]$ cat /home/oracle/rcadm/rc_perf_analysis.sql

-- 백업 성능 분석
-- 실행 : sqlplus -s rc_report/<pw>@rcat @rc_perf_analysis.sql
SET LINESIZE 190 PAGESIZE 200 FEEDBACK OFF VERIFY OFF
DEFINE window_minutes = 60
DEFINE slow_pct = 30

PROMPT ================================================================
PROMPT  백업 성능 분석 리포트
PROMPT ================================================================

PROMPT === 1. 주간 추세 (DB별) ===
SELECT db_name, TO_CHAR(start_time,'IYYY-IW') AS week,
       COUNT(*) AS runs,
       ROUND(AVG(elapsed_seconds)) AS avg_sec,
       ROUND(AVG(input_bytes)/1024/1024/1024,2) AS read_gb,
       ROUND(AVG(output_bytes)/1024/1024/1024,2) AS write_gb,
       ROUND(AVG(input_bytes/NULLIF(elapsed_seconds,0))/1024/1024) AS mb_sec
FROM   rc_rman_backup_job_details
WHERE  input_type = 'DB INCR' AND start_time > SYSDATE - 90
GROUP  BY db_name, TO_CHAR(start_time,'IYYY-IW')
ORDER  BY db_name, week;

PROMPT === 2. 증분 효율 (읽은 양 / 쓴 양) ===
PROMPT     ratio 가 크면 전체를 읽고 조금만 쓴다는 뜻 = BCT 검토 대상
SELECT db_name,
       ROUND(AVG(input_bytes)/1024/1024/1024,2) AS avg_read_gb,
       ROUND(AVG(output_bytes)/1024/1024/1024,2) AS avg_write_gb,
       ROUND(AVG(input_bytes)/NULLIF(AVG(output_bytes),0),1) AS ratio
FROM   rc_rman_backup_job_details
WHERE  input_type = 'DB INCR' AND start_time > SYSDATE - 7
GROUP  BY db_name ORDER BY ratio DESC;

PROMPT === 3. 처리량 하락 감지 ===
SELECT db_name, recent_mb_sec, prev_mb_sec,
       ROUND((prev_mb_sec - recent_mb_sec)/NULLIF(prev_mb_sec,0)*100) AS drop_pct,
       CASE WHEN (prev_mb_sec - recent_mb_sec)/NULLIF(prev_mb_sec,0)*100
                 >= &slow_pct THEN '*** WARN ***' ELSE 'OK' END AS judge
FROM (
  SELECT db_name,
    ROUND(AVG(CASE WHEN start_time > SYSDATE-7
          THEN input_bytes/NULLIF(elapsed_seconds,0) END)/1024/1024) AS recent_mb_sec,
    ROUND(AVG(CASE WHEN start_time BETWEEN SYSDATE-30 AND SYSDATE-7
          THEN input_bytes/NULLIF(elapsed_seconds,0) END)/1024/1024) AS prev_mb_sec
  FROM rc_rman_backup_job_details
  WHERE input_type = 'DB INCR' GROUP BY db_name)
ORDER BY drop_pct DESC NULLS LAST;

PROMPT === 4. 백업 창 소진율 ===
SELECT db_name,
       ROUND(MAX(elapsed_seconds)/60,1) AS max_min,
       &window_minutes AS window_min,
       ROUND(MAX(elapsed_seconds)/60/&window_minutes*100) AS used_pct,
       CASE WHEN MAX(elapsed_seconds)/60/&window_minutes >= 0.7
            THEN '*** WARN ***' ELSE 'OK' END AS judge
FROM   rc_rman_backup_job_details
WHERE  input_type = 'DB INCR' AND start_time > SYSDATE - 7
GROUP  BY db_name ORDER BY used_pct DESC;

PROMPT === 5. 작업 시간 중복 ===
SELECT a.db_name AS db1, b.db_name AS db2,
       TO_CHAR(a.start_time,'MM-DD HH24:MI') AS a_start,
       TO_CHAR(b.start_time,'HH24:MI') AS b_start,
       ROUND(LEAST(a.end_time,b.end_time)
             - GREATEST(a.start_time,b.start_time)) * 24 * 60 AS overlap_min
FROM   rc_rman_backup_job_details a, rc_rman_backup_job_details b
WHERE  a.db_name < b.db_name
AND    a.start_time > SYSDATE - 7 AND b.start_time > SYSDATE - 7
AND    a.start_time < b.end_time AND b.start_time < a.end_time
ORDER  BY overlap_min DESC FETCH FIRST 10 ROWS ONLY;

#!/bin/bash
# 기동 전 필수 파일 확인 (BCT 파일 유실로 인한 기동 실패 방지)
SID=$1
export ORACLE_HOME=/u01/app/oracle/product/19.3.0/dbhome_1
export ORACLE_SID=$SID
export PATH=$ORACLE_HOME/bin:$PATH

BCT=$(sqlplus -s / as sysdba << 'EOF'
SET PAGESIZE 0 FEEDBACK OFF HEADING OFF
SELECT NVL(filename,'NONE') FROM v$block_change_tracking;
EXIT
EOF
)

if [ "$BCT" != "NONE" ] && [ ! -f "$BCT" ]; then
  echo "[WARN] change tracking file missing : $BCT"
  echo "       기동 전 DISABLE BLOCK CHANGE TRACKING 이 필요할 수 있다"
  exit 1
fi
echo "[OK] pre-startup check passed"

-- 5) 압축은 시간이 아니라 공간을 위한 선택이다.
