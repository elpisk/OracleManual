 환경      : Oracle 19.3.0 / Oracle Linux 7 / oel7v9(운영계) + oel7v9r2(관리계) / ARCHIVELOG
 대상 DB   : orcl, sales (oel7v9) / hrdb (oel7v9r2)
 카탈로그  : rcat @ oel7v9r2
 소요 시간 : 약 3시간
 선행 조건 : 고급 실습 01~07 완료

--------------------------------------------------------------------------------
[1] 실무 상황
--------------------------------------------------------------------------------
-- 고급 실습 02의 일일 리포트에서 추세 이상이 잡혔다.
--
--   ORCL 소요     402  411  408  415  491  478  491   (초)
--   ORCL 크기    1.18 1.19 1.20 1.21 1.22 1.23 1.24   (GB)
--
-- 크기는 5% 늘었는데 시간은 22% 늘었다. 비례하지 않는다.
--
-- 그 뒤로도 계속 늘어 지금은 이렇게 되었다.
--   - 일일 증분 백업이 02:00 에 시작해 03:40 에 끝난다
--   - 배치 작업이 03:00 에 시작하므로 40분간 겹친다
--   - 배치 담당자로부터 성능 저하 항의가 들어왔다
--
-- 백업 창(backup window)은 02:00~03:00 한 시간이다.
-- 지금은 100분이 걸린다.
--
-- 운영팀 의견은 갈린다.
--   A : "채널을 늘리면 된다"
--   B : "압축을 켜면 I/O 가 줄어 빨라진다"
--   C : "증분인데 왜 오래 걸리나. Block Change Tracking 을 켜자"
--
-- 셋 다 그럴듯하지만 근거가 없다.
-- 카탈로그에 3개월치 이력이 있으므로 먼저 분석한다.
--
-- 요구 사항
--   ① 소요 시간 증가의 원인을 데이터로 규명한다
--   ② 각 개선안의 효과를 측정해 비교한다
--   ③ 백업 창 60분 안에 들어오게 만든다
--   ④ 복구 시간에 미치는 영향도 함께 평가한다
--   ⑤ 이상 징후를 조기에 감지하는 지표를 만든다

--------------------------------------------------------------------------------
[2] 사전 설계
--------------------------------------------------------------------------------
-- 2-1. 분석 축
--
--   축                | 지표                        | 조회 대상
--   ------------------|-----------------------------|------------------------
--   처리량            | input_bytes / elapsed_sec   | rc_rman_backup_job_details
--   압축률            | input_bytes / output_bytes  | 위와 동일
--   읽은 양 vs 쓴 양  | 증분에서 특히 중요          | v$backup_datafile
--   변경 추적 사용    | used_change_tracking        | v$backup_datafile
--   채널별 편중       | 채널별 처리 파일 수         | v$backup_async_io
--   대기 이벤트       | 백업 중 세션의 event        | v$session_wait
--
--   핵심 질문
--     "증분 백업이 왜 전체 백업만큼 오래 걸리는가"
--     증분은 변경된 블록만 쓰지만 기본 동작은 전체 블록을 읽는다.
--     읽는 양이 줄지 않으면 시간도 줄지 않는다.

-- 2-2. 개선안과 예상 효과
--
--   개선안                  | 줄이는 것    | 부작용
--   ------------------------|--------------|---------------------------
--   채널 증가               | 병렬로 분산  | CPU·I/O 경합
--   Block Change Tracking   | 읽는 양      | 소량의 쓰기 부하 상시 발생
--   압축                    | 쓰는 양      | CPU 사용 증가. 라이선스
--   SECTION SIZE            | 파일 단위 편중| 조각 수 증가
--   FILESPERSET 조정        | 세트 구성    | 복원 시 읽는 단위 변화
--   DURATION MINIMIZE LOAD  | 부하         | 시간이 더 걸린다
--
--   측정 없이 여러 개를 동시에 적용하면 무엇이 효과였는지 알 수 없다.
--   하나씩 적용하고 매번 측정한다.

-- 2-3. 측정 프로토콜
--
--   ① 기준선 3회 측정 후 중앙값 사용
--   ② 매 측정 전 버퍼 캐시 초기화는 하지 않는다 (운영 조건 유지)
--   ③ 다른 부하가 없는 시간대에 수행
--   ④ 측정마다 카탈로그의 job_details 를 기록
--   ⑤ 개선안 적용 후 최소 2회 측정
--
--   비교 지표는 elapsed_seconds 와 input_bytes/sec 두 가지를 함께 본다.
--   시간만 보면 데이터 증가와 개선 효과가 섞인다.

-- 2-4. 복구 시간과의 관계 (요구 사항 ④)
--
--   백업을 빠르게 만드는 선택이 복구를 느리게 만들 수 있다.
--
--   선택            | 백업 시간 | 복구 시간
--   ----------------|-----------|----------------------------
--   차등 증분       | 짧다      | 길다 (모든 Level 1 적용)
--   누적 증분       | 길다      | 짧다 (마지막 하나만)
--   압축            | 길다      | 길다 (해제 부하)
--   채널 증가       | 짧다      | 짧다 (복원도 병렬)
--
--   백업 창만 보고 결정하면 RTO 를 해칠 수 있다.

-- 4-2. 기준선 측정

-- 다른 작업이 없는 시간에 단독으로 3회 측정한다.

[oracle@oel7v9 ~]$ cat /home/oracle/rcadm/bench_backup.sh

#!/bin/bash
# 백업 성능 측정 (단일 실행)
SID=$1; LABEL=$2
export ORACLE_HOME=/u01/app/oracle/product/19.3.0/dbhome_1
export ORACLE_SID=$SID
export PATH=$ORACLE_HOME/bin:$PATH
export NLS_DATE_FORMAT='YYYY-MM-DD HH24:MI:SS'
LOG=/home/oracle/rcadm/bench/${SID}_${LABEL}_$(date +%H%M%S).log
mkdir -p /home/oracle/rcadm/bench

S=$(date +%s)
rman target / catalog rcatowner/oracle_4U@rcat > $LOG 2>&1 << EOF
BACKUP INCREMENTAL LEVEL 1 DATABASE TAG 'BENCH_$LABEL';
EOF
E=$(date +%s)
echo "$LABEL elapsed=$((E-S))s"
grep -E 'Finished backup|piece handle' $LOG | tail -3

-- 세 번째가 갑자기 12초다. 앞의 두 번이 데이터파일을 OS 캐시에 올려놓았고
-- 세 번째는 디스크 대신 메모리에서 읽었다. [3-2]에서 본 buff/cache 5GB 다.
-- 야간 배치 뒤에는 캐시에 남아 있지 않으므로 운영 조건은 앞의 두 값이다.
-- 3회 측정에서 중앙값을 쓰는 이유가 바로 이것이다. 기준선은 45초.

-- 카탈로그에서 같은 측정을 본다.
-- rc_backup_set 에는 tag 도 session_key 도 없다.
-- 세션 키는 rc_backup_set_details, 태그는 rc_backup_piece 에 있다.

RC_REPORT@rcat> COLUMN tag FORMAT A16
RC_REPORT@rcat> SELECT DISTINCT p.tag, j.elapsed_seconds,
  2    ROUND(j.input_bytes/1024/1024/1024,2) AS read_gb,
  3    ROUND(j.output_bytes/1024/1024,1) AS write_mb,
  4    ROUND(j.input_bytes/NULLIF(j.elapsed_seconds,0)/1024/1024) AS mb_sec
  5  FROM  rc_rman_backup_job_details j
  6    JOIN rc_backup_set_details s
  7         ON s.session_key = j.session_key AND s.db_key = j.db_key
  8    JOIN rc_backup_piece p ON p.bs_key = s.bs_key
  9  WHERE j.db_name = 'SALES' AND p.tag LIKE 'BENCH_BASE%'
 10  ORDER BY j.elapsed_seconds DESC;

TAG              ELAPSED_SECONDS    READ_GB   WRITE_MB     MB_SEC
---------------- --------------- ---------- ---------- ----------
BENCH_BASE1                   43       1.56       18.1         37
BENCH_BASE2                   41       1.56       10.8         39
BENCH_BASE3                    8       1.56       10.9        199

-- 카탈로그의 elapsed_seconds 는 백업 작업 자체의 시간이다.
-- 셸에서 잰 시간은 접속과 자동백업까지 포함하므로 몇 초 더 크다.
-- 비교 지표로는 카탈로그 값을 쓴다. 기준선 41초(중앙값).
--

-- 백업 창이 목적이면 압축은 근거가 없다. 저장 공간이 목적이면 근거가 있다.

-- 6-1. 개선안별 측정 결과 (요구 사항 ②)
--
-- 카탈로그 elapsed_seconds 기준. sales 1.75GB, 채널 2 가 기본.
--
-- 구성                              | 소요  | 읽기   | 쓰기   | 판정
-- ----------------------------------|-------|--------|--------|------------------
-- 기준선 (Level 1, BCT 없음)        |  41초 | 1.56GB |   11MB |
-- + BCT (기준 Level 0 없음)         |   8초*| 1.56GB |   11MB | 효과 없음 (*캐시)
-- + BCT (기준 Level 0 후)           |   5초 | 0.01GB |   11MB | 읽기 1/150
-- + 채널 4                          |   5초 | 0.01GB |   11MB | 차이 없음
-- + SECTION SIZE 256M               |   5초 | 0.01GB |   11MB | 차이 없음
-- + 압축 BASIC                      |   5초 | 0.01GB |   11MB | 압축률 1
-- Level 0 채널 2                    |  20초 | 1.56GB | 1190MB |
-- Level 0 채널 4                    |  19초 | 1.56GB | 1190MB | 차이 없음
-- Level 0 SECTION 256M              |  16초 | 1.56GB | 1191MB | 오차 범위
-- Level 0 압축 BASIC                |  18초 | 1.56GB |  310MB | 쓰기 1/4, 시간 같음
--
-- 최종 채택 : BCT

-- 7-2. rc_bct_check.sh — 변경 추적 파일 점검
--
-- [5] 오류 ③에서 본 대로 파일이 없어도 기동은 된다. 기동 전 점검으로는 잡히지 않는다.
-- 기동 후·야간 백업 전에 세 가지를 확인한다.
--   파일을 열 수 있는가 / 마지막 기동 때 재생성되었는가 / 최근 증분이 추적을 썼는가

[oracle@oel7v9 ~]$ cat /home/oracle/rcadm/rc_bct_check.sh

#!/bin/bash
# Block Change Tracking 상태 점검 (기동 후, 야간 백업 전)
# 사용 : rc_bct_check.sh <SID>
SID=$1
export ORACLE_HOME=/u01/app/oracle/product/19.3.0/dbhome_1
export ORACLE_SID=$SID
export PATH=$ORACLE_HOME/bin:$PATH
ALERT=$ORACLE_BASE/diag/rdbms/${SID}/${SID}/trace/alert_${SID}.log
[ -z "$ORACLE_BASE" ] && ALERT=/u01/app/oracle/diag/rdbms/${SID}/${SID}/trace/alert_${SID}.log
RC=0

# 1) 상태와 파일
LINE=$(sqlplus -s / as sysdba << 'EOF'
SET PAGESIZE 0 FEEDBACK OFF HEADING OFF
SELECT status || ' ' || NVL(filename,'-') FROM v$block_change_tracking;
EXIT
EOF
)
if echo "$LINE" | grep -q 'ORA-19755'; then
  BCT=$(echo "$LINE" | grep 'ORA-19750' | awk -F"'" '{print $2}')
  echo "[FAIL] change tracking 파일을 열 수 없다 (ORA-19755) : $BCT"
  echo "       종료·체크포인트 때 인스턴스가 비정상 종료될 수 있다. 즉시 DISABLE 후 재설정한다"
  RC=2
else
  STATUS=$(echo $LINE | awk '{print $1}'); BCT=$(echo $LINE | awk '{print $2}')
  echo "status=$STATUS file=$BCT"
  [ "$STATUS" != "ENABLED" ] && { echo "[WARN] change tracking 이 꺼져 있다"; RC=1; }
fi

# 2) CTWR 프로세스
pgrep -f ora_ctwr_${SID} > /dev/null || { echo "[WARN] ora_ctwr_${SID} 프로세스 없음"; RC=1; }

# 3) 마지막 기동 때 파일이 재생성되었는데 그 뒤 추적을 쓴 증분이 아직 없으면 경고
#    (재생성되면 추적 정보가 초기화되어 다음 증분 한 번은 전체 블록을 읽는다)
LAST=$(grep -n 'Starting ORACLE instance' $ALERT | tail -1 | cut -d: -f1)
if [ -n "$LAST" ] && tail -n +$LAST $ALERT | grep -q 'Recreating the file'; then
  USED=$(sqlplus -s / as sysdba << 'EOF'
SET PAGESIZE 0 FEEDBACK OFF HEADING OFF
SELECT NVL(MAX(b.used_change_tracking) KEEP (DENSE_RANK LAST ORDER BY b.completion_time),'NONE')
FROM   v$backup_datafile b, v$instance i
WHERE  b.incremental_level = 1 AND b.completion_time > i.startup_time;
EXIT
EOF
)
  if [ "$(echo $USED)" != "YES" ]; then
    echo "[WARN] 마지막 기동 때 change tracking 파일이 재생성되었다 (추적 정보 초기화)"
    echo "       다음 증분 백업 한 번은 전체 블록을 읽는다 (백업 창 초과 가능)"; RC=1
  fi
fi

# 4) 최근 증분이 실제로 추적 정보를 썼는지
sqlplus -s / as sysdba << 'EOF'
SET PAGESIZE 20 FEEDBACK OFF
COLUMN used_change_tracking FORMAT A5 HEADING 'USED'
SELECT TO_CHAR(MAX(completion_time),'MM-DD HH24:MI') AS last_incr, used_change_tracking,
       COUNT(*) AS files, ROUND(SUM(blocks_read)/SUM(datafile_blocks)*100,1) AS pct_read
FROM   v$backup_datafile WHERE incremental_level = 1
AND    completion_time = (SELECT MAX(completion_time) FROM v$backup_datafile WHERE incremental_level = 1)
GROUP  BY used_change_tracking;
EXIT
EOF
[ $RC -eq 0 ] && echo "[OK] BCT check passed"
exit $RC

-- 7-3. 확장 과제
--
-- 과제 A. orcl 과 HRDB 에 적용
--   같은 절차로 orcl 과 HRDB 를 측정하시오. DB 크기와 파일 구성이 다르므로
--   채널·SECTION SIZE 의 결과가 sales 와 다를 수 있다.
--   측정 프로토콜([2-3])을 그대로 따르고 [6-1] 표를 DB 마다 만든다.
--
-- 과제 B. 압축의 시간 비용이 드러나는 조건 만들기
--   이 실습에서는 압축이 시간을 늘리지 않았다. CPU 가 놀고 있었기 때문이다.
--   백업과 동시에 CPU 부하(예: 4개의 무한 루프 프로세스)를 걸고 다시 측정해
--   압축의 시간 비용이 CPU 여유에 달렸음을 확인하시오.
--
-- 과제 C. SECTION SIZE 값 최적화
--   256M 은 임의로 정한 값이다.
--   64M, 128M, 512M, 1G 로 바꿔 가며 측정하고
--   조각 수 증가와 소요 시간의 관계를 정리하시오.
--   조각이 지나치게 많아질 때의 부작용(카탈로그 행 수, 조각 관리)도 확인한다.
--
-- 과제 D. DURATION 옵션 검토
--   BACKUP ... DURATION 0:10 MINIMIZE LOAD 를 적용해 보고
--   부하는 줄지만 시간이 늘어나는 관계를 확인하시오.
--   백업 창이 넉넉하고 운영 부하가 문제인 시스템에 적합한지 판단한다.
--
-- 과제 E. OS 캐시를 통제한 측정
--   [4-2]에서 세 번째 측정이 캐시 때문에 12초가 되었다.
--   root 로 sync; echo 3 > /proc/sys/vm/drop_caches 를 매 측정 전에 실행해
--   캐시 없는 조건의 값을 얻고, 운영 야간의 조건과 어느 쪽이 가까운지 논하시오.

-- 7-4. 정리 — 이 실습에서 남는 것
--
--   ① rc_perf_analysis.sql       : 성능 분석 리포트 7절
--   ② bench_backup.sh            : 측정 스크립트
--   ③ rc_nightly.sh              : 순차 실행기
--   ④ rc_bct_check.sh            : 변경 추적 파일 점검
--   ⑤ 개선안별 측정 결과표       : [6-1]
--   ⑥ 조기 감지 지표 3종         : [6-5]
--
-- 다음 예제에서는 백업의 기밀성을 다룬다.

-- 실무 포인트
-- 1) 의견이 아니라 데이터로 판단한다.
--    세 사람의 제안 중 실제로 효과가 컸던 것은 하나였다.
--    나머지 둘은 이 환경에서 효과를 입증하지 못했고, 그래서 채택하지 않았다.
--    카탈로그에 3개월치 이력이 있었기에 원인을 특정할 수 있었다.
--
-- 2) 증분 백업의 병목은 대개 읽기다.
--    쓰는 양은 적은데 읽는 양이 DB 전체 크기라면 BCT 를 검토한다.
--    input_bytes / output_bytes 비율이 그 신호다.
--
-- 3) BCT 는 새 Level 0 이후부터 효과가 난다.
--    켠 직후 측정하면 효과가 없다고 잘못 판단한다.
--    used_change_tracking 컬럼으로 실제 적용 여부를 확인한다.
--
-- 4) 시간만 보면 속는다.
--    OS 캐시가 세 번째 측정을 12초로 만들었고, BCT 를 켠 뒤에는 MB/sec 가 2 로
--    떨어졌다. 둘 다 성능과 무관하다. 읽은 양(input_bytes)을 함께 봐야 한다.
--
-- 5) 채널을 파일 수보다 늘려도 소용없다.
--    가장 큰 파일 하나가 전체 시간을 결정한다. 그때 필요한 것이 SECTION SIZE 다.
--    다만 그 효과는 파일이 클 때 나타난다. 작은 DB 에서는 측정 오차 안이다.
--
-- 6) MEDIUM 이상의 압축은 소프트웨어가 막지 않는다.
--    CONFIGURE 도 BACKUP 도 성공하고 dba_feature_usage_statistics 에 기록만 남는다.
--    라이선스 위반은 오류가 아니라 감사로 드러난다. 설정 점검을 리포트에 넣는다.
--
-- 7) 변경 추적 파일을 잃으면 두 가지가 일어난다.
--    열린 인스턴스는 다음 접근에서 비정상 종료되고, 기동은 파일을 조용히 다시 만든다.
--    막히지 않기 때문에 모른 채 지나가고, 다음 증분이 전체를 읽어 백업 창을 넘긴다.
--    점검 스크립트가 필요한 이유다.
