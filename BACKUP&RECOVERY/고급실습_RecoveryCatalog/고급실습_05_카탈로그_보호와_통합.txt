 환경      : Oracle 19.3.0 / Oracle Linux 7 / oel7v9r1(운영계) + oel7v9r2(관리계)
 대상 DB   : orcl, sales (oel7v9r1) / hrdb (oel7v9r2)
 카탈로그  : rcat @ oel7v9r2 (스키마 rcatowner, rcatowner2)

--------------------------------------------------------------------------------
[1] 실무 상황
--------------------------------------------------------------------------------
-- 고급 실습 03에서 확인한 약점이 현실이 되었다.
-- 지난 금요일 밤 rcat 서버의 디스크가 고장 났다.
--   - 세 대의 야간 백업이 모두 실패했다 (RMAN-06171)
--   - 표준 스토어드 스크립트를 쓸 수 없었다
--   - 복구 이력을 조회할 수 없어 장애 대응 판단이 늦어졌다
--
-- 카탈로그가 백업 체계 전체의 단일 장애점이 되어 있다.
--
-- 동시에 다른 요구가 들어왔다.
--   인접 팀이 별도로 운영하던 카탈로그(rcatowner2)를 통합하라는 지시다.
--   그 카탈로그에는 hrdb 를 포함한 두 대의 백업 이력이 3년치 들어 있다.
--   재등록하면 이력이 사라지므로 그대로 옮겨야 한다.
--
-- 그리고 다음 분기에 21c 타깃이 들어온다.
--   카탈로그 스키마 버전이 낮으면 접속 자체가 거부된다는 것을 알게 되었다.
--
-- 요구 사항
--   ① 카탈로그 DB 자체를 백업하고 복구 절차를 검증한다
--   ② 카탈로그를 잃어도 백업 체계가 멈추지 않게 한다
--   ③ 별도 카탈로그를 이력 손실 없이 통합한다
--   ④ 카탈로그 버전 관리 규칙을 정하고 업그레이드 절차를 만든다
--
-- 이 실습은 "백업을 관리하는 것을 백업하는" 문제를 다룬다.

--------------------------------------------------------------------------------
[2] 사전 설계
--------------------------------------------------------------------------------
-- 2-1. 카탈로그 보호 3중 구조
--
--   계층   | 수단                       | 복구 대상        | 소요 시간
--   -------|----------------------------|------------------|----------
--   1차    | rcat DB의 RMAN 백업        | DB 전체          | 30분~1시간
--   2차    | 카탈로그 스키마 Data Pump  | 스키마만         | 5~10분
--   3차    | 스토어드 스크립트 파일 추출| 절차만           | 즉시
--
--   1차는 완전하지만 느리다.
--   2차는 다른 DB에 옮겨 붙일 수 있어 유연하다.
--   3차는 고급 실습 03의 rc_export_scripts.sh 가 담당한다.
--
--   중요한 원칙
--     rcat 의 백업은 카탈로그를 쓰지 않는다. nocatalog 로 받는다.
--     자기 자신을 저장소로 쓰면 그 저장소가 사라졌을 때 복구할 수 없다.

-- 2-2. 카탈로그가 없을 때의 운영 (요구 사항 ②)
--
--   대상 DB의 컨트롤파일이 2차 저장소 역할을 한다.
--   그래서 CONTROL_FILE_RECORD_KEEP_TIME 이 중요해진다.
--
--   설정 원칙
--     CONTROL_FILE_RECORD_KEEP_TIME >= 보존 기간 + 카탈로그 복구 여유
--     이 실습 환경 : 21일 + 9일 = 30일
--
--   고급 실습 04의 4-1에서 이미 30으로 올려 두었다.
--   이 값이 있으면 카탈로그가 며칠 없어도 nocatalog 로 버틸 수 있다.

-- 2-3. 통합 방식 비교 (요구 사항 ③)
--
--   방식              | 이력 보존 | 소요 시간 | 위험
--   ------------------|-----------|-----------|------------------
--   IMPORT CATALOG    | 완전 보존 | 분 단위   | DBID 충돌
--   재등록(REGISTER)  | 전부 소실 | 즉시      | 과거 복구 불가
--   Data Pump 스키마  | 별도 스키마| 분 단위  | 통합되지 않음
--
--   IMPORT CATALOG 를 쓴다. 3년치 이력을 잃을 수 없다.
--
--   IMPORT CATALOG 의 규칙
--     - 원본 카탈로그 스키마 버전 <= 대상 카탈로그 스키마 버전
--     - 같은 DBID 가 대상에 이미 있으면 실패한다
--     - 기본 동작은 원본에서 등록을 해제한다. NO UNREGISTER 로 막을 수 있다
--     - DBID 나 DB_NAME 을 지정해 일부만 가져올 수 있다

-- 2-4. 버전 규칙 (요구 사항 ④)
--
--   카탈로그 스키마 버전 >= RMAN 클라이언트 버전
--
--   이 조건이 깨지면 접속 단계에서 RMAN-06429 로 거부된다.
--   새 버전의 타깃이 들어오기 전에 카탈로그를 먼저 올려야 한다는 뜻이다.
--
--   운영 규칙으로 정리하면
--     ① 카탈로그 DB 버전은 관리 대상 중 가장 높은 버전 이상으로 유지한다
--     ② 타깃 업그레이드 계획이 잡히면 카탈로그를 먼저 올린다
--     ③ UPGRADE CATALOG 전에 반드시 스키마 백업을 받는다

-- 2-5. 작업 순서
--
--   ① rcat 의 ARCHIVELOG 모드와 백업 구성 확인
--   ② 카탈로그 스키마 Data Pump 백업
--   ③ 두 번째 카탈로그 스키마 준비 (통합 대상 재현)
--   ④ IMPORT CATALOG 로 통합
--   ⑤ UPGRADE CATALOG 절차 확인
--   ⑥ 카탈로그 유실과 재구축 훈련
--   ⑦ 정기 보호 작업 등록

-- ────────────────────────────────────────────────
-- 오류 ① DBID 충돌로 IMPORT CATALOG 실패
-- ────────────────────────────────────────────────
-- 4-3에서 만난 오류를 해결한다.

-- << 원인 파악 >>
-- hrdb 가 rcatowner 와 rcatowner2 양쪽에 등록되어 있다.
-- IMPORT CATALOG 는 원본의 모든 DB를 대상에 옮기려 한다.
-- 같은 DBID 가 이미 있으므로 RMAN-20002 로 중단된다.
--
-- 이 상황은 통합 작업에서 매우 흔하다.
-- 두 팀이 같은 DB를 각자 카탈로그에 등록해 두는 경우다.
--
-- 판단해야 할 것
--   어느 쪽 이력을 살릴 것인가.
--   rcatowner2 에 3년치가 있고 rcatowner 에는 최근 것만 있다면
--   대상에서 먼저 등록을 해제하고 가져오는 편이 낫다.

-- 양쪽 이력의 범위를 비교한다.

SYSTEM@rcat> SELECT 'rcatowner ' AS cat,
  2         TO_CHAR(MIN(completion_time),'YYYY-MM-DD') AS oldest,
  3         COUNT(*) AS pieces
  4  FROM   rcatowner.rc_backup_piece p
  5    JOIN rcatowner.rc_database d ON p.db_key = d.db_key
  6  WHERE  d.name = 'HRDB'
  7  UNION ALL
  8  SELECT 'rcatowner2',
  9         TO_CHAR(MIN(completion_time),'YYYY-MM-DD'), COUNT(*)
 10  FROM   rcatowner2.rc_backup_piece;

CAT        OLDEST     PIECES
---------- ---------- ------
rcatowner  2025-05-05     96
rcatowner2 2025-06-06      2

-- 이 실습 환경에서는 rcatowner 쪽이 더 오래되었다.
-- 실제 통합 상황이라면 반대인 경우가 많다.

-- << 수정 방법 1 >> 충돌하지 않는 DB만 선택해 가져온다

-- 7-1. rc_catalog_backup.sh — 3중 보호 일괄 수행

[oracle@oel7v9r2 ~]$ cat /home/oracle/rcadm/rc_catalog_backup.sh

#!/bin/bash
# 카탈로그 3중 보호 : RMAN 백업 + 스키마 덤프 + 스크립트 추출
set -u
export ORACLE_HOME=/u01/app/oracle/product/19.3.0/dbhome_1
export ORACLE_SID=rcat
export PATH=$ORACLE_HOME/bin:$PATH
D=$(date +%Y%m%d)
LOG=/home/oracle/rcadm/log/rcat_protect_$D.log
DUMPDIR=/u03/dpdump_rcat
MAILTO="dba-team@example.com"

echo "=== $(date) 카탈로그 보호 작업 시작 ===" > $LOG

# --- 1차 : rcat DB 백업 (반드시 nocatalog)
rman target / nocatalog >> $LOG 2>&1 << 'EOF'
BACKUP DATABASE PLUS ARCHIVELOG TAG 'RCAT_FULL' DELETE INPUT;
DELETE NOPROMPT OBSOLETE;
EOF

# --- 2차 : 카탈로그 스키마 논리 백업
expdp system/oracle_4U directory=dp_rcat \
  dumpfile=rcatowner_${D}.dmp logfile=rcatowner_${D}.log \
  schemas=rcatowner flashback_time=systimestamp >> $LOG 2>&1

# --- 3차 : 글로벌 스크립트 추출
sh /home/oracle/rcadm/rc_export_scripts.sh >> $LOG 2>&1

# --- DBID 목록 갱신 (컨트롤파일 유실 대비)
sqlplus -s rc_report/oracle_4U@rcat >> /home/oracle/rcadm/DBID_LIST.txt << 'EOF'
SET PAGESIZE 0 FEEDBACK OFF HEADING OFF
SELECT name || '  DBID = ' || dbid FROM rc_database ORDER BY name;
EXIT
EOF

# --- 판정
if grep -qE 'ORA-[0-9]+|RMAN-[0-9]+' $LOG; then
  mailx -s "[FAIL] catalog protection $D" $MAILTO < $LOG
  exit 1
fi

# --- 보관 정리 (덤프 14세대)
ls -1t $DUMPDIR/rcatowner_*.dmp | tail -n +15 | xargs -r rm -f

echo "[OK] catalog protection completed"
exit 0

□ 중복 DB의 이력 범위 비교 — 어느 쪽을 살릴지 결정
□ 대상 카탈로그 Data Pump 백업 (되돌리기 대비)
□ 원본 카탈로그 Data Pump 백업
□ 검증 기간 동안은 NO UNREGISTER 옵션 사용
□ IMPORT CATALOG 수행
□ LIST DB_UNIQUE_NAME ALL 로 등록 확인
□ 각 DB에서 RESTORE ... VALIDATE 로 실사용 검증
□ 대상 DB들의 접속 문자열을 새 카탈로그로 변경
□ 원본 카탈로그 스키마 제거 (검증 완료 후 2주 경과)

-- 7-5. 정리 — 이 실습에서 남는 것
--
--   ① rc_catalog_backup.sh          : 3중 보호 일괄 수행
--   ② RUNBOOK_catalog_recovery.md   : 장애 유형별 복구 절차
--   ③ CHECKLIST_catalog_import.txt  : 통합 작업 체크리스트
--   ④ DBID_LIST.txt                 : 자동 갱신되는 DBID 목록
--   ⑤ 복구 훈련 소요 시간 실측치    : [6-6]
--
-- 다음 예제에서는 보존 정책의 예외인 장기 보관 백업을 다룬다.

-- 실무 포인트
-- 1) 카탈로그의 백업은 카탈로그를 쓰지 않는다.
--    nocatalog 로 받아야 한다. 자기 자신을 저장소로 삼으면
--    그것이 사라졌을 때 복구 경로가 없다.
--
-- 2) 스키마 논리 백업이 가장 실용적인 보호 수단이다.
--    22MB 짜리 덤프 하나로 11분 만에 복구되었다.
--    DB 전체 복원은 30분 이상 걸린다. 상황에 맞게 고른다.
--
-- 3) 세 가지 오류를 구분한다.
--    ORA-01017 계정 문제, RMAN-06428 미설치, RMAN-20001 미등록.
--    장애 상황에서 이 구분이 대응 속도를 좌우한다.
--
-- 4) IMPORT CATALOG 는 방향이 정해져 있다.
--    대상 카탈로그로 접속해 원본을 지정한다.
--    같은 DBID 가 대상에 있으면 RMAN-20002 로 막힌다.
--    검증 기간에는 NO UNREGISTER 를 쓴다.
--
-- 5) 카탈로그 스키마 버전은 클라이언트 버전 이상이어야 한다.
--    낮으면 RMAN-06429 로 접속 자체가 거부된다.
--    타깃을 올리기 전에 카탈로그를 먼저 올린다.
--
-- 6) 카탈로그가 없어도 며칠은 버틸 수 있게 설계한다.
--    CONTROL_FILE_RECORD_KEEP_TIME 을 보존 기간보다 넉넉히 잡고
--    스토어드 스크립트를 파일로 추출해 두면
--    카탈로그 복구 시간을 벌 수 있다.
