================================================================================
 고급 실습 01 : Virtual Private Catalog와 DBA 권한 분리
 과정      : Oracle Database 19c Backup & Recovery — Recovery Catalog 고급
 환경      : Oracle 19.3.0 / Oracle Linux 7 / oel7v9(운영계) + oel7v9r2(관리계) / ARCHIVELOG
 대상 DB   : orcl, sales (oel7v9) / hrdb (oel7v9r2)
 카탈로그  : rcat @ oel7v9r2
 소요 시간 : 약 2시간 30분
 선행 조건 : BR 1~19장 이수, 종합 실습 과제 수행
================================================================================

--------------------------------------------------------------------------------
[1] 실무 상황
--------------------------------------------------------------------------------
-- 데이터베이스 세 대를 DBA 세 명이 나눠 맡고 있다.
--   orcl  : 코어 업무 시스템
--   sales : 영업 시스템
--   hrdb  : 인사 시스템
--
-- 세 사람 모두 rcatowner 계정으로 카탈로그에 접속한다.
-- 그래서 다음이 가능하다.
--   - 영업 담당자가 코어 시스템의 백업을 DELETE 할 수 있다
--   - 인사 담당자가 다른 시스템의 백업 이력을 전부 조회할 수 있다
--   - 누가 무엇을 지웠는지 추적할 수 없다
--
-- 실제로 지난 분기 감사에서 지적을 받았다.
--   "백업 저장소에 대한 접근 권한이 담당 범위와 일치하지 않음"
--
-- 요구 사항
--   ① 각 DBA는 자기 담당 DB의 백업만 보고 다룰 수 있어야 한다
--   ② 다른 DB의 백업 이력은 조회조차 되지 않아야 한다
--   ③ 새 DB를 등록할 수 있는 사람은 따로 정한다
--   ④ 기존 백업 이력과 스크립트는 그대로 유지되어야 한다
--
-- 13장에서 만든 카탈로그는 소유자 한 명이 전부를 갖는 구조였다.
-- 이 실습에서는 그 위에 Virtual Private Catalog를 얹어 범위를 나눈다.

--------------------------------------------------------------------------------
[2] 사전 설계
--------------------------------------------------------------------------------
-- 설계를 먼저 확정하고 명령을 실행한다.
-- 권한을 나눈 뒤에 되돌리는 것은 가능하지만 혼란이 크다.

-- 2-1. 용어 정리
--
--   기본 카탈로그(Base Catalog)
--     rcatowner 스키마. 실제 데이터가 들어 있는 테이블의 소유자.
--     등록된 모든 DB의 메타데이터를 갖는다.
--
--   가상 사설 카탈로그(Virtual Private Catalog, VPC)
--     별도 사용자 계정. 기본 카탈로그의 뷰를 VPD 정책이 걸러서 보여 준다.
--     자기에게 부여된 DB만 보인다. 자기 스키마에는 아무것도 만들지 않는다.
--     데이터를 복제하지 않는다. 접근 범위만 제한한다.
--     (11g 까지는 VPC 사용자 스키마에 뷰와 동의어를 만드는 방식이었다. 19c 는 VPD 방식이다.)

-- 2-2. 권한 매트릭스
--
--   사용자        | 담당 DB | CATALOG FOR DATABASE | REGISTER DATABASE
--   --------------|---------|----------------------|-------------------
--   rcatowner     | 전체    | (소유자)             | (소유자)
--   vpc_core      | orcl    | orcl                 | 없음
--   vpc_sales     | sales   | sales                | 있음
--   vpc_hr        | hrdb    | hrdb                 | 없음
--
--   REGISTER DATABASE 를 vpc_sales 에게만 준 이유
--     영업 시스템은 분기마다 테스트 DB가 늘어난다.
--     매번 기본 카탈로그 소유자를 부르는 것이 비효율적이다.
--     나머지 둘은 DB 수가 고정이므로 등록 권한이 필요 없다.

-- 2-3. 명명 규칙
--
--   VPC 사용자명 : vpc_<업무영역>
--   기본 테이블스페이스 : rcat_data (rcatowner와 동일)
--   임시 : temp
--   비밀번호 정책 : 조직 표준을 따르며 이 실습에서는 oracle_4U

-- 2-4. 되돌리기 계획
--
--   REVOKE CATALOG FOR DATABASE <db> FROM <vpc사용자>;
--   DROP CATALOG;                      -- VPC 사용자로 접속해 실행 (CREATE VIRTUAL CATALOG 를 했던 경우)
--   DROP USER <vpc사용자> CASCADE;
--
--   기본 카탈로그의 데이터는 영향을 받지 않는다.
--   VPC는 뷰와 동의어의 모음이므로 지워도 백업 이력이 사라지지 않는다.

-- 4-1. VPC 사용자 생성
--
-- 필요한 것은 두 가지뿐이다.
--   CREATE SESSION 권한
--   RECOVERY_CATALOG_USER 롤
--
-- RECOVERY_CATALOG_USER 롤에는 시스템 권한이 하나도 없다.
-- 오라클의 VPC 정리 스크립트가 VPC 사용자에게 표준으로 부여하는 표식 롤이며,
-- 점검 보고서(-scan)가 이 롤로 VPC 사용자를 식별한다.

SYS@rcat> SELECT privilege FROM dba_sys_privs
  2  WHERE  grantee = 'RECOVERY_CATALOG_USER' ORDER BY privilege;

no rows selected

-- RECOVERY_CATALOG_OWNER 롤은 주지 않는다. 그것은 기본 카탈로그 소유자의 롤이다.
-- VPC 사용자에게 주면 접속할 때마다 경고가 뜬다(오류 ① 참고).

SYS@rcat> CREATE USER vpc_core IDENTIFIED BY oracle_4U
  2    DEFAULT TABLESPACE rcat_data
  3    TEMPORARY TABLESPACE temp
  4    QUOTA UNLIMITED ON rcat_data;

User created.

SYS@rcat> CREATE USER vpc_sales IDENTIFIED BY oracle_4U
  2    DEFAULT TABLESPACE rcat_data
  3    TEMPORARY TABLESPACE temp
  4    QUOTA UNLIMITED ON rcat_data;

SYS@rcat> CREATE USER vpc_hr IDENTIFIED BY oracle_4U
  2    DEFAULT TABLESPACE rcat_data
  3    TEMPORARY TABLESPACE temp
  4    QUOTA UNLIMITED ON rcat_data;

User created.

SYS@rcat> GRANT CREATE SESSION, RECOVERY_CATALOG_USER TO vpc_core, vpc_sales, vpc_hr;

Grant succeeded.

SYS@rcat> SELECT grantee, granted_role FROM dba_role_privs

--------------------------------------------------------------------------------
-- 실무에서 반드시 만나게 되는 세 가지를 재현한다.

-- ────────────────────────────────────────────────
-- 오류 ① 옛 방식대로 RECOVERY_CATALOG_OWNER 롤을 부여

PROMPT === VPC 사용자와 롤 ===
SELECT u.username AS vpc_user, u.created, u.account_status, r.granted_role
FROM   dba_users u LEFT JOIN dba_role_privs r ON r.grantee = u.username
WHERE  u.username LIKE 'VPC%'
ORDER  BY u.username;

PROMPT === 기본 카탈로그 등록 DB ===
SELECT dbid, name, resetlogs_time FROM rcatowner.rc_database ORDER BY name;

PROMPT === VPC 사용자별 담당 DB와 등록 권한 ===
SELECT u.filter_user AS vpc_user, r.name, u.add_new_db
FROM   rcatowner.vpc_users u
       LEFT JOIN rcatowner.vpc_databases d ON d.filter_user = u.filter_user
       LEFT JOIN rcatowner.rc_database r ON r.dbid = d.db_id
ORDER  BY u.filter_user, r.name;

-- 7-5. 정리 — 이 실습에서 남는 것
--
--   ① rc_vpc_setup.sql   : 신규 담당자 계정 생성 절차
--   ② rc_vpc_audit.sql   : 분기 감사 대응 조회
--   ③ 권한 매트릭스 표   : [2]의 설계 문서
--   ④ 권한 회수 절차     : 7-3의 4단계
--
-- 다음 예제에서는 이 구조 위에서 세 대의 백업 현황을
-- 한 화면으로 보는 리포팅 체계를 만든다.

-- 실무 포인트
-- 1) 19c 의 VPC 는 VPD 정책이다. 데이터를 복제하지 않는다.
--    VPC 사용자 스키마에는 아무것도 없고(동의어 둘이 전부), 기본 카탈로그의 뷰를 걸러서 보여 준다.
--    DROP CATALOG 로 지워도 백업 이력은 사라지지 않는다.
--
-- 2) 13장 방식으로 만든 카탈로그는 VPD 가 꺼져 있다. 첫 GRANT 에서 RMAN-07543 이 난다.
--    dbmsrmanvpc.sql -vpd <소유자> 를 SYS 로 실행하고 UPGRADE CATALOG 를 두 번 넣어야 켜진다.
--
-- 3) 권한 부여는 RMAN 명령이고 계정 생성은 SQL이다.
--    GRANT CATALOG FOR DATABASE 는 SQL*Plus에서 실행되지 않는다.
--    두 도구를 오가야 한다는 점이 처음에는 혼란스럽다.
--
-- 4) VPC 사용자에게 주는 것은 CREATE SESSION 과 RECOVERY_CATALOG_USER 뿐이다.
--    RECOVERY_CATALOG_OWNER 를 주면 접속마다 RMAN-07540 이 찍히고 정리 스크립트 대상이 된다.
--    부여 순서는 VPD 활성화 → 계정 생성 → 범위 부여다. CREATE VIRTUAL CATALOG 는 옛 클라이언트용이다.
--
-- 5) 권한 없는 DB는 "없는 DB"로 취급된다.
--    ORA-01031 이 아니라 RMAN-20001 이 나온다.
--    다른 시스템의 존재 자체가 노출되지 않는 것이 설계 의도다.
--
-- 6) 접속 성공이 권한 충분을 뜻하지 않는다.
--    범위를 받기 전에는 "connected to recovery catalog database" 다음 명령에서
--    RMAN-06428: recovery catalog is not installed 가 난다. 설치 문제가 아니라 권한 문제다.
--
-- 7) CATALOG FOR DATABASE 를 받은 DB 는 그 사용자가 직접 등록할 수 있다.
--    REGISTER DATABASE 권한은 부여받지 않은 DB 를 등록할 때만 필요하고,
--    그렇게 등록하면 그 DB 의 범위가 등록한 사람에게 자동으로 붙는다.
--
-- 8) 글로벌 스토어드 스크립트는 VPC 경계를 넘어 공유된다.
--    표준 백업 절차를 한 곳에서 관리하고 데이터만 나누는 구성이 가능하다.
--    다만 그 스크립트를 수정할 수 있는 사람은 통제해야 한다.
