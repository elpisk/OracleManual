--------------------------------------------------------------------------------
[1] 실무 상황
--------------------------------------------------------------------------------
-- 임원 보고 자리에서 질문이 나왔다.
--
--   "지금 이 순간 장애가 나면 몇 시간 만에 복구됩니까?
--    그리고 그 답을 어떻게 확신합니까?"
--
-- 답할 수 있는 것은 이것뿐이었다.
--   "매일 백업이 성공하고 있습니다."
--
-- 그러나 성공한 백업이 복원된다는 보장은 없다.
--   - 백업 파일이 읽히는지 확인한 적이 없다
--   - 블록 손상이 백업에 그대로 담겼을 수 있다
--   - 아카이브 로그 연결이 끊긴 구간이 있을 수 있다
--   - 실제로 복원해 본 것은 고급 실습 07의 재해 상황이 유일하다
--
-- 고급 실습 02의 일일 리포트는 "백업이 있는가"를 본다.
-- 이 실습은 "그 백업으로 복구되는가"를 본다. 다른 질문이다.
--
-- 요구 사항
--   ① 복구 가능성을 매일 자동으로 검증한다
--   ② 검증 수준을 단계로 나누고 각 단계의 주기를 정한다
--   ③ 실제 복원 훈련을 정기적으로 수행하고 시간을 측정한다
--   ④ RTO 와 RPO 를 수치로 선언하고 그 근거를 남긴다
--   ⑤ 장애 발생 시 누구나 따라 할 수 있는 런북을 만든다
--
-- 이 실습은 고급 실습 01~09에서 만든 모든 것을 검증하는 마지막 단계다.

--------------------------------------------------------------------------------
[2] 사전 설계
--------------------------------------------------------------------------------
-- 2-1. 검증 4단계
--
--   단계 | 이름        | 확인하는 것              | 명령                      | 주기
--   -----|-------------|--------------------------|---------------------------|------
--   L1   | 메타 검증   | 복원 경로가 존재하는가   | RESTORE PREVIEW           | 매일
--   L2   | 읽기 검증   | 백업 파일이 읽히는가     | RESTORE ... VALIDATE      | 매일
--   L3   | 논리 검증   | 블록이 온전한가          | VALIDATE CHECK LOGICAL    | 주간
--   L4   | 실복원 훈련 | 실제로 열리는가          | DUPLICATE / 전체 복원     | 분기
--
--   각 단계가 잡아내는 것이 다르다.
--     L1 은 백업이 없거나 아카이브가 끊긴 것을 잡는다
--     L2 는 파일이 사라졌거나 헤더가 깨진 것을 잡는다
--     L3 은 블록 내부 손상을 잡는다
--     L4 는 나머지 전부를 잡는다. 실제로 열리는지는 열어 봐야 안다
--
--   L1~L3 은 자동화한다. L4 는 사람이 수행한다.

-- 2-2. 각 단계가 놓치는 것
--
--   L1 이 통과해도 파일이 손상되었을 수 있다
--   L2 가 통과해도 블록 내부가 깨졌을 수 있다 (CHECK LOGICAL 없이는)
--   L3 이 통과해도 열리지 않을 수 있다 (파라미터, 경로, 자원 문제)
--   L4 가 통과해도 다음 주에는 실패할 수 있다 (그래서 주기적으로 한다)
--
--   완전한 검증은 없다. 비용과 확신도의 균형을 정하는 문제다.

-- 2-3. 훈련 등급
--
--   등급  | 범위                        | 소요    | 주기   | 서비스 영향
--   ------|-----------------------------|---------|--------|------------
--   드릴A | 테이블 하나 복원            | 30분    | 월간   | 없음
--   드릴B | 다른 서버에 DUPLICATE       | 1시간   | 분기   | 없음 (메모리·공간 확보 필요)
--   드릴C | 운영 DB 실제 복구           | 3시간   | 연간   | 계획 정지
--
--   이 실습에서는 드릴 A 와 B 를 수행한다.
--   드릴 C 는 절차만 런북에 담는다.

-- 2-4. RTO / RPO 산정 근거 (요구 사항 ④)
--
--   RPO = 마지막으로 백업된 아카이브 이후 구간
--       = 아카이브 백업 주기에 좌우된다
--
--   RTO = 감지 + 판단 + 복구 + 검증 + 서비스 전환
--       = 각 단계를 실측해 합산한다
--
--   고급 실습 07에서 실측한 값이 있다 (sales 1.8GB).
--     복구(오픈까지)  : 10분
--     정상화 포함     : 15분
--   여기에 감지·판단·서비스 전환 시간을 더해야 하고, 크기가 다른 DB 는 다시 재야 한다.

-- 7-1. rc_restore_validate.sh — L1~L3 자동 검증

-- 전문은 운영스크립트/rc_restore_validate.sh. 골격은 다음과 같다.

[oracle@oel7v9 ~]$ cat /home/oracle/rcadm/rc_restore_validate.sh

#!/bin/bash
# 복구 가능성 검증 (L1~L3)
# 사용법 : rc_restore_validate.sh <ORACLE_SID> <레벨:1|2|3>
set -u
SID=$1
LEVEL=${2:-2}
export ORACLE_HOME=/u01/app/oracle/product/19.3.0/dbhome_1
export ORACLE_SID=$SID
export PATH=$ORACLE_HOME/bin:$PATH
CATALOG="rcatowner/oracle_4U@rcat"
MAILTO="dba-team@example.com"
VDIR=/home/oracle/rcadm/verify
LOG=$VDIR/verify_${SID}_L${LEVEL}_$(date +%Y%m%d_%H%M).log
mkdir -p $VDIR
log() { echo "$(date '+%Y-%m-%d %H:%M:%S') $*" | tee -a "$LOG"; }

log "=== $SID L$LEVEL 복구 가능성 검증 시작 ==="

# --- L1 : 메타 검증
log "--- L1 : metadata ---"
rman target / catalog $CATALOG >> $LOG 2>&1 << 'EOF'
REPORT NEED BACKUP;
REPORT UNRECOVERABLE;
RESTORE DATABASE PREVIEW SUMMARY;
RESTORE ARCHIVELOG ALL PREVIEW SUMMARY;
RESTORE SPFILE PREVIEW;
EXIT
EOF
# 구문 오류(RMAN-00558/01009)도 실패로 본다. 검증이 실행조차 안 된 것을 통과로 판정하면 안 된다.
if grep -qE 'RMAN-060(23|25|26)|RMAN-00558|RMAN-01009' $LOG; then
  log "[CRIT] L1 실패 : 복원 경로 결손 (또는 구문 오류)"
  mailx -s "[CRIT] L1 restore path broken ($SID)" $MAILTO < $LOG
  exit 1
fi
log "[OK] L1 통과"
[ "$LEVEL" = "1" ] && exit 0

# --- L2 : 읽기 검증
log "--- L2 : readability ---"
rman target / catalog $CATALOG >> $LOG 2>&1 << 'EOF'
RESTORE DATABASE VALIDATE;
RESTORE ARCHIVELOG ALL VALIDATE;
RESTORE SPFILE FROM AUTOBACKUP VALIDATE;
RESTORE CONTROLFILE FROM AUTOBACKUP VALIDATE;
EXIT
EOF
if grep -qE 'ORA-19870|ORA-19501|ORA-19505|RMAN-06172|RMAN-00558|RMAN-01009' $LOG; then
  log "[CRIT] L2 실패 : 백업 조각을 읽을 수 없다"
  mailx -s "[CRIT] L2 backup unreadable ($SID)" $MAILTO < $LOG
  exit 1
fi
log "[OK] L2 통과"
[ "$LEVEL" = "2" ] && exit 0

# --- L3 : 논리 검증 (부하가 있으므로 주간 수행)
log "--- L3 : logical (block) ---"
rman target / catalog $CATALOG >> $LOG 2>&1 << 'EOF'
BACKUP VALIDATE CHECK LOGICAL DATABASE ARCHIVELOG ALL;
EXIT
EOF
CORRUPT=$(sqlplus -s / as sysdba << 'EOF'
SET PAGESIZE 0 FEEDBACK OFF HEADING OFF
SELECT COUNT(*) FROM v$database_block_corruption;
EXIT
EOF
)
if [ "${CORRUPT:-0}" -gt 0 ]; then
  log "[CRIT] L3 실패 : 손상 블록 ${CORRUPT}건"
  mailx -s "[CRIT] L3 block corruption ($SID)" $MAILTO < $LOG
  exit 1
fi
log "[OK] L3 통과 - 손상 블록 없음"
find $VDIR -name "verify_*.log" -mtime +90 -delete
exit 0

-- 첫 버전은 L2 의 SPFILE 검증이 VALIDATE FROM AUTOBACKUP 어순이라 RMAN-01009 로 실행조차
-- 되지 않았고, 그 오류를 잡는 패턴이 없어 "[OK] L2 통과" 를 찍었다.
-- 검증 스크립트가 통과를 남발하면 없느니만 못하다. 만든 날 로그를 끝까지 읽는다.

--   그리고 반입한 날 한 번 돌려 로그를 끝까지 읽는다. 이 과정에서 그렇게 잡은 결함이
--   rc_secure_export.sh(09), rc_restore_validate.sh(10) 에 하나씩 있었다.

-- 실무 포인트
-- 1) "백업이 있는가"와 "복구되는가"는 다른 질문이다.
--    일일 리포트는 전자를, 이 검증 체계는 후자를 본다.
--    이번 검증에서 세 가지 문제를 새로 발견했고
--    셋 다 일일 리포트에서는 정상으로 보였다.
--
-- 2) 검증 단계마다 잡아내는 것이 다르다.
--    L2 가 통과해도 블록 손상은 남아 있을 수 있다.
--    MAXCORRUPT 를 설정했다면 L3 검증이 필수다.
--    PREVIEW 는 UNTIL 을 줘야 갭을 오류로 말한다. 없으면 "up to SCN" 숫자로만 말한다.
--
-- 3) 아카이브 삭제 정책을 반드시 설정한다.
--    CONFIGURE ARCHIVELOG DELETION POLICY TO BACKED UP 1 TIMES 가
--    백업되지 않은 아카이브의 삭제를 구조적으로 막는다.
--    보존 정책만으로는 이 사고를 막을 수 없다.
--
-- 4) 원본 없이 하는 DUPLICATE 는 카탈로그가 아는 마지막 아카이브까지 가려 한다.
--    그 아카이브가 백업되지 않았으면 복원까지 다 하고 복구에서 실패한다.
--    훈련 전에 아카이브를 백업한다. 그것이 5분을 아낀다.
--
-- 5) DROP DATABASE INCLUDING BACKUPS 를 복제본에 쓰지 않는다.
--    복제하다 만 인스턴스의 컨트롤파일은 원본 것이다. 원본의 백업을 지우려 든다.
--    실패한 복제본은 ABORT 하고 파일을 지운다. 완성된 복제본은 DROP DATABASE 만 쓴다.
--    어느 쪽이든 "database name is ... DBID is ..." 줄을 읽고 나서 진행한다.
--
-- 6) RTO 와 RPO 는 선언이 아니라 실측이다.
--    "3시간"이라고 적어 두는 것과
--    "실측 63분에 여유 2배"라고 말하는 것은 다르다.
--    후자만이 임원 질문에 답이 된다.
--
-- 7) 런북은 훈련 후에 갱신한다.
--    이번 훈련에서 런북의 드릴 B 정리 절차 자체가 위험한 것으로 드러났다.
--    훈련에서 발견한 것이 반영되지 않은 런북은
--    실제 장애에서 그 문제를 다시 만나게 한다.
--    문서로만 있는 절차는 동작하지 않는다.
