[1] 실무 상황
--------------------------------------------------------------------------------
-- 임원 보고 자리에서 질문이 나왔다.
--
--   "지금 이 순간 장애가 나면 몇 시간 만에 복구됩니까?
--    그리고 그 답을 어떻게 확신합니까?"
--
-- 답할 수 있는 것은 이것뿐이었다.
--   "매일 백업이 성공하고 있습니다."
--
-- 그러나 성공한 백업이 복원된다는 보장은 없다.
--   - 백업 파일이 읽히는지 확인한 적이 없다
--   - 블록 손상이 백업에 그대로 담겼을 수 있다
--   - 아카이브 로그 연결이 끊긴 구간이 있을 수 있다
--   - 실제로 복원해 본 것은 고급 실습 07의 재해 상황이 유일하다
--
-- 고급 실습 02의 일일 리포트는 "백업이 있는가"를 본다.
-- 이 실습은 "그 백업으로 복구되는가"를 본다. 다른 질문이다.
--
-- 요구 사항
--   ① 복구 가능성을 매일 자동으로 검증한다
--   ② 검증 수준을 단계로 나누고 각 단계의 주기를 정한다
--   ③ 실제 복원 훈련을 정기적으로 수행하고 시간을 측정한다
--   ④ RTO 와 RPO 를 수치로 선언하고 그 근거를 남긴다
--   ⑤ 장애 발생 시 누구나 따라 할 수 있는 런북을 만든다
--
-- 이 실습은 고급 실습 01~09에서 만든 모든 것을 검증하는 마지막 단계다.

--------------------------------------------------------------------------------
[2] 사전 설계
--------------------------------------------------------------------------------
-- 2-1. 검증 4단계
--
--   단계 | 이름        | 확인하는 것              | 명령                      | 주기
--   -----|-------------|--------------------------|---------------------------|------
--   L1   | 메타 검증   | 복원 경로가 존재하는가   | RESTORE PREVIEW           | 매일
--   L2   | 읽기 검증   | 백업 파일이 읽히는가     | RESTORE ... VALIDATE      | 매일
--   L3   | 논리 검증   | 블록이 온전한가          | VALIDATE CHECK LOGICAL    | 주간
--   L4   | 실복원 훈련 | 실제로 열리는가          | DUPLICATE / 전체 복원     | 분기
--
--   각 단계가 잡아내는 것이 다르다.
--     L1 은 백업이 없거나 아카이브가 끊긴 것을 잡는다
--     L2 는 파일이 사라졌거나 헤더가 깨진 것을 잡는다
--     L3 은 블록 내부 손상을 잡는다
--     L4 는 나머지 전부를 잡는다. 실제로 열리는지는 열어 봐야 안다
--
--   L1~L3 은 자동화한다. L4 는 사람이 수행한다.

-- 2-2. 각 단계가 놓치는 것
--
--   L1 이 통과해도 파일이 손상되었을 수 있다
--   L2 가 통과해도 블록 내부가 깨졌을 수 있다 (CHECK LOGICAL 없이는)
--   L3 이 통과해도 열리지 않을 수 있다 (파라미터, 경로, 자원 문제)
--   L4 가 통과해도 다음 주에는 실패할 수 있다 (그래서 주기적으로 한다)
--
--   완전한 검증은 없다. 비용과 확신도의 균형을 정하는 문제다.

-- 2-3. 훈련 등급
--
--   등급  | 범위                        | 소요    | 주기   | 서비스 영향
--   ------|-----------------------------|---------|--------|------------
--   드릴A | 테이블 하나 복원            | 30분    | 월간   | 없음
--   드릴B | 다른 서버에 DUPLICATE       | 2시간   | 분기   | 없음
--   드릴C | 운영 DB 실제 복구           | 3시간   | 연간   | 계획 정지
--
--   이 실습에서는 드릴 A 와 B 를 수행한다.
--   드릴 C 는 절차만 런북에 담는다.

-- 2-4. RTO / RPO 산정 근거 (요구 사항 ④)
--
--   RPO = 마지막으로 백업된 아카이브 이후 구간
--       = 아카이브 백업 주기에 좌우된다
--
--   RTO = 감지 + 판단 + 복구 + 검증 + 서비스 전환
--       = 각 단계를 실측해 합산한다
--
--   고급 실습 07에서 실측한 값이 있다.
--     복구(오픈까지)  : 67분
--     정상화 포함     : 95분
--   여기에 감지·판단·서비스 전환 시간을 더해야 한다.

# --- L1 : 메타 검증
rman target / catalog $CATALOG >> $LOG 2>&1 << 'EOF'
REPORT NEED BACKUP;
REPORT UNRECOVERABLE;
RESTORE DATABASE PREVIEW SUMMARY;
RESTORE ARCHIVELOG ALL PREVIEW SUMMARY;
RESTORE SPFILE PREVIEW;
EXIT
EOF

if grep -qE 'RMAN-060(23|25|26)' $LOG; then
  echo "[CRIT] L1 실패 : 복원 경로 결손" >> $LOG
  grep -E 'RMAN-060(23|25|26)' $LOG >> $LOG
  mailx -s "[CRIT] L1 restore path broken ($SID)" $MAILTO < $LOG
  exit 1
fi
echo "[OK] L1 통과" >> $LOG
[ "$LEVEL" = "1" ] && exit 0

# --- L2 : 읽기 검증
rman target / catalog $CATALOG >> $LOG 2>&1 << 'EOF'
RESTORE DATABASE VALIDATE;
RESTORE ARCHIVELOG ALL VALIDATE;
RESTORE SPFILE VALIDATE FROM AUTOBACKUP;
EXIT
EOF

if grep -qE 'ORA-19870|ORA-19501|RMAN-06172' $LOG; then
  echo "[CRIT] L2 실패 : 백업 조각 읽기 불가" >> $LOG
  mailx -s "[CRIT] L2 backup unreadable ($SID)" $MAILTO < $LOG
  exit 1
fi
echo "[OK] L2 통과" >> $LOG
[ "$LEVEL" = "2" ] && exit 0

# --- L3 : 논리 검증 (부하가 있으므로 주간 수행)
rman target / catalog $CATALOG >> $LOG 2>&1 << 'EOF'
BACKUP VALIDATE CHECK LOGICAL DATABASE ARCHIVELOG ALL;
EXIT
EOF

CORRUPT=$(sqlplus -s / as sysdba << 'EOF'
SET PAGESIZE 0 FEEDBACK OFF HEADING OFF
SELECT COUNT(*) FROM v$database_block_corruption;
EXIT
EOF
)
if [ "$CORRUPT" -gt 0 ]; then
  echo "[CRIT] L3 실패 : 손상 블록 ${CORRUPT}건" >> $LOG
  sqlplus -s / as sysdba >> $LOG << 'EOF'
SELECT file#, block#, blocks, corruption_type FROM v$database_block_corruption;
EOF
  mailx -s "[CRIT] L3 block corruption ($SID)" $MAILTO < $LOG
  exit 1
fi

echo "[OK] L3 통과 - 손상 블록 없음" >> $LOG
find /home/oracle/rcadm/verify -name "verify_*.log" -mtime +90 -delete
exit 0

PROMPT === 1. DB별 요약 ===
SELECT d.name AS db_name,
  TO_CHAR(MAX(s.completion_time),'MM-DD HH24:MI') AS last_backup,
  ROUND((SYSDATE - MAX(s.completion_time))*24,1) AS hours_ago,
  (SELECT COUNT(*) FROM rc_backup_set k
   WHERE k.db_key = d.db_key AND k.keep_options IS NOT NULL) AS keep_sets,
  (SELECT COUNT(*) FROM rc_unusable_backupfile_details u
   WHERE u.db_name = d.name) AS unusable,
  (SELECT MAX(c.value) FROM rc_rman_configuration c
   WHERE c.db_key = d.db_key AND c.value LIKE 'RETENTION%') AS retention
FROM rc_database d LEFT JOIN rc_backup_set s ON d.db_key = s.db_key
GROUP BY d.name, d.db_key ORDER BY d.name;

PROMPT === 2. 설정 표준 준수 ===
SELECT d.name AS db_name,
  MAX(CASE WHEN c.value LIKE '%CONTROLFILE AUTOBACKUP ON%' THEN 'Y' END) AS cf_auto,

  MAX(CASE WHEN c.value LIKE '%ENCRYPTION FOR DATABASE ON%' THEN 'Y' END) AS enc,
  MAX(CASE WHEN c.value LIKE '%RETENTION%21 DAYS%' THEN 'Y' END) AS ret21
FROM rc_database d LEFT JOIN rc_rman_configuration c ON d.db_key = c.db_key
GROUP BY d.name ORDER BY d.name;

SELECT db_name, COUNT(*) AS jobs,

PROMPT === 4. 복구 가능 범위 ===
SELECT d.name AS db_name,

--

-- 실무 포인트
-- 1) "백업이 있는가"와 "복구되는가"는 다른 질문이다.
--    일일 리포트는 전자를, 이 검증 체계는 후자를 본다.
--    이번 검증에서 두 가지 문제를 새로 발견했고
--    둘 다 일일 리포트에서는 정상으로 보였다.
--
-- 2) 검증 단계마다 잡아내는 것이 다르다.
--    L2 가 통과해도 블록 손상은 남아 있을 수 있다.
--    MAXCORRUPT 를 설정했다면 L3 검증이 필수다.
--
-- 3) 아카이브 삭제 정책을 반드시 설정한다.
--    CONFIGURE ARCHIVELOG DELETION POLICY TO BACKED UP 1 TIMES 가
--    백업되지 않은 아카이브의 삭제를 구조적으로 막는다.
--    보존 정책만으로는 이 사고를 막을 수 없다.
--
-- 4) 훈련은 정리까지가 한 작업이다.
--    복제본을 남겨 두면 다음 훈련을 막고 운영 파일 시스템까지 압박한다.
--    DROP DATABASE 는 SID 를 반드시 확인하고 실행한다.
--
-- 5) RTO 와 RPO 는 선언이 아니라 실측이다.
--    "3시간"이라고 적어 두는 것과
--    "실측 112분에 여유 1.5배"라고 말하는 것은 다르다.
--    후자만이 임원 질문에 답이 된다.
--
-- 6) 런북은 훈련 후에 갱신한다.
--    훈련에서 발견한 것이 반영되지 않은 런북은
--    실제 장애에서 그 문제를 다시 만나게 한다.
--    문서로만 있는 절차는 동작하지 않는다.
