================================================================================
 고급 실습 02 : 다중 데이터베이스 중앙 등록과 백업 현황 리포팅
 과정      : Oracle Database 19c Backup & Recovery — Recovery Catalog 고급
 환경      : Oracle 19.3.0 / Oracle Linux 7 / oel7v9r1(운영계) + oel7v9r2(관리계)
 대상 DB   : orcl, sales (oel7v9r1) / hrdb (oel7v9r2)
 카탈로그  : rcat @ oel7v9r2
 소요 시간 : 약 3시간
 선행 조건 : 고급 실습 01 완료 (VPC 구성)
================================================================================

--------------------------------------------------------------------------------
[1] 실무 상황
--------------------------------------------------------------------------------
-- 지금은 매일 아침 이렇게 확인한다.
--   ① 서버 세 대에 각각 접속한다
--   ② 백업 로그 파일을 열어 마지막 줄을 본다
--   ③ "Finished backup" 이 있으면 정상으로 판단한다
--
-- 지난달에 사고가 있었다.
--   sales 의 아카이브 로그 백업이 11일간 수행되지 않았다.
--   로그 파일에는 매일 "Finished backup" 이 찍혀 있었다.
--   전체 백업은 성공했고 아카이브 백업 구문만 스크립트에서 빠져 있었다.
--   마지막 줄만 보는 점검으로는 잡을 수 없는 유형이었다.
--
-- 그 사이 아카이브 대상이 가득 차 DB가 두 시간 멈췄다.
--
-- 요구 사항
--   ① 세 대의 백업 현황을 한 화면에서 본다
--   ② 성공 여부가 아니라 "복구 가능한 상태인가"를 판정한다
--   ③ 판정 기준을 수치로 정의하고 임계값을 넘으면 경고한다
--   ④ 매일 아침 자동으로 생성되어 메일로 도착한다
--   ⑤ 감사 제출용으로 월간 이력을 뽑을 수 있다
--
-- 카탈로그에는 세 대의 백업 이력이 이미 모여 있다.
-- 이 실습에서는 그 데이터를 판정 가능한 형태로 가공한다.

--------------------------------------------------------------------------------
[2] 사전 설계
--------------------------------------------------------------------------------
-- 2-1. 점검 항목과 판정 기준
--
--   항목                      | 조회 대상                    | 경고 기준
--   --------------------------|------------------------------|-------------------
--   최근 백업 작업 결과       | rc_rman_backup_job_details   | FAILED 또는 오류 존재
--   전체 백업 최신성          | rc_backup_set                | 7일 초과
--   아카이브 백업 최신성      | rc_backup_set (input_type)   | 1일 초과
--   백업이 없는 데이터파일    | rc_datafile / rc_backup_datafile | 1건 이상
--   사용 불가 백업            | rc_unusable_backupfile_details | 1건 이상
--   컨트롤파일 자동 백업      | rc_backup_controlfile        | 1일 초과
--   카탈로그 동기화 시각      | rc_resync                    | 1일 초과
--   백업 소요 시간 급증       | rc_rman_backup_job_details   | 직전 평균의 150%
--
--   ※ "성공 여부"가 아니라 "복구 가능한가"로 기준을 잡은 것이 핵심이다.
--     명령이 성공했어도 대상이 빠졌으면 복구할 수 없다.

-- 2-2. 리포트 구성
--
--   섹션 1. 요약     — DB별 한 줄. 신호등(OK / WARN / CRIT)
--   섹션 2. 상세     — 항목별 수치와 임계값
--   섹션 3. 예외     — 경고 항목만 모아서
--   섹션 4. 추세     — 최근 7일 백업 크기와 소요 시간
--
--   출력은 고정폭 텍스트로 한다.
--   메일 본문에 그대로 붙일 수 있고 터미널에서도 읽힌다.

-- 2-3. 리포팅 전용 계정
--
--   고급 실습 01의 확장 과제 A에서 제기된 문제를 여기서 해결한다.
--   VPC는 조회와 변경 권한을 함께 부여하므로 읽기 전용 감사자를 만들 수 없다.
--   대신 rc_ 뷰에 대한 SELECT 권한만 가진 별도 계정을 만든다.
--
--   계정명 : rc_report
--   권한   : CREATE SESSION + rcatowner 소유 rc_ 뷰에 대한 SELECT
--   제약   : 어떤 RMAN 명령도 실행할 수 없다

-- 2-4. 리포트가 판정하지 못하는 것
--
--   카탈로그에 기록되지 않은 백업은 리포트에 나타나지 않는다.
--   nocatalog 로 수행한 백업이 대표적이다.
--   그래서 리포트에 "카탈로그 동기화 시각" 항목을 넣는다.
--   이 값이 오래되었으면 리포트 자체를 믿을 수 없다는 뜻이다.

-- 7-3. 월간 감사 제출용 조회

[oracle@oel7v9r2 ~]$ cat /home/oracle/rcadm/rc_monthly_audit.sql

SET LINESIZE 180 PAGESIZE 200
COLUMN db_name FORMAT A10
COLUMN day FORMAT A6

PROMPT === 월간 백업 수행 이력 (DB별 일자별) ===
SELECT db_name, TO_CHAR(start_time,'MM-DD') AS day, input_type,
       status, time_taken_display, output_bytes_display
FROM   rc_rman_backup_job_details
WHERE  start_time >= TRUNC(ADD_MONTHS(SYSDATE,-1),'MM')
AND    start_time <  TRUNC(SYSDATE,'MM')
ORDER  BY db_name, start_time;

PROMPT === 월간 성공률 ===
SELECT db_name,
       COUNT(*) AS total_jobs,
       SUM(CASE WHEN status = 'COMPLETED' THEN 1 ELSE 0 END) AS ok_jobs,
       ROUND(SUM(CASE WHEN status='COMPLETED' THEN 1 ELSE 0 END)
             / COUNT(*) * 100, 1) AS success_pct
FROM   rc_rman_backup_job_details
WHERE  start_time >= TRUNC(ADD_MONTHS(SYSDATE,-1),'MM')
AND    start_time <  TRUNC(SYSDATE,'MM')
GROUP  BY db_name ORDER BY db_name;

-- 7-4. 확장 과제
--
-- 과제 A. 임계값의 근거 만들기
--   전체 백업 7일, 아카이브 1일이라는 임계값은 임의로 정한 값이다.
--   각 DB의 복구 목표 시간(RTO)과 복구 지점 목표(RPO)를 정의하고
--   그로부터 임계값을 도출하시오.
--   힌트 : RPO가 4시간이면 아카이브 백업 주기도 4시간 이내여야 한다.
--
-- 과제 B. 백업되지 않은 아카이브 지표 추가
--   6-3의 조회를 섹션 2에 넣고 임계값을 정하시오.
--   개수보다 "가장 오래된 미백업 아카이브의 나이"가 더 나은 지표인지 검토하시오.
--
-- 과제 C. 리포트의 사각지대 찾기
--   현재 리포트가 잡지 못하는 장애 유형을 세 가지 이상 찾으시오.
--   힌트 : 백업 파일이 실제로 읽히는지는 검사하지 않는다.
--          이 부분은 고급 실습 10에서 다룬다.
--
-- 과제 D. HTML 출력
--   메일 클라이언트에서 색으로 구분되도록 HTML 리포트를 만드시오.
--   SET MARKUP HTML ON 을 쓰거나 SQL에서 태그를 직접 생성한다.
--   CRIT는 붉은색, WARN은 주황색으로 표시한다.
--
-- 과제 E. 신규 DB 자동 감지
--   카탈로그에 새 DB가 등록되면 리포트에 자동으로 포함된다.
--   반대로 등록되어야 할 DB가 빠진 것은 감지하지 못한다.
--   기대 DB 목록을 별도 테이블로 관리하고 대조하는 방법을 구현하시오.

-- 7-5. 정리 — 이 실습에서 남는 것
--
--   ① rc_daily_report.sql   : 일일 점검 리포트
--   ② rc_daily_report.sh    : 크론 실행기와 메일 발송
--   ③ rc_monthly_audit.sql  : 월간 감사 제출용
--   ④ rc_report 계정        : 읽기 전용 리포팅 계정 구성 절차
--   ⑤ 점검 항목과 임계값 표 : [2-1]의 설계 문서

-- 실무 포인트
-- 1) "성공했는가"가 아니라 "복구 가능한가"로 판정한다.
--    명령이 성공해도 대상이 빠져 있으면 복구할 수 없다.
--    SALES 사례가 정확히 그 경우였다.
--
-- 2) 작업 건수의 변화가 누락의 신호다.
--    성공률 93.8% 는 그럴듯해 보이지만 작업 수가 다른 DB보다 적었다.
--    비율 지표만 보면 이런 유형을 놓친다.
--
-- 3) 리포트는 반드시 전체를 볼 수 있는 계정으로 돌린다.
--    VPC 계정으로 돌리면 조용히 일부만 점검하고 정상으로 보고한다.
--    조회 가능 DB 수를 리포트 첫 줄에 찍어 안전장치로 삼는다.
--
-- 4) rc_ 뷰만 사용한다.
--    내부 테이블은 버전 간 구조가 바뀌고 VPC 필터링도 우회한다.
--    rc_ 뷰가 오라클이 보장하는 공개 인터페이스다.
--
-- 5) 카탈로그 동기화 시각을 반드시 점검 항목에 넣는다.
--    이 값이 오래되었으면 리포트의 다른 모든 항목을 믿을 수 없다.
--    nocatalog 백업이 있었는지 사후에 잡아내는 유일한 수단이다.
--
-- 6) 리포팅 계정은 조회만 되게 만든다.
--    RMAN 도구로 접속조차 되지 않는 편이 안전하다.
--    감사에서 "조회 권한과 변경 권한이 분리되어 있는가"를 묻는다.
