================================================================================
 Ch14 실습 01 — 콜드 캐시 vs 웜 캐시: Buffers 는 같은데 Reads 와 시간이 346배 다르다
 목표: 버퍼 캐시를 비운 직후와 직후 재실행의 실행 통계를 대조해 Buffers(논리 읽기)와
       Reads(물리 읽기)가 서로 다른 것을 센다는 사실을 숫자로 확인한다. SQLT 로 FLUSH 를
       시도해 ORA-01031 을 재현하고 SYS 로 교정한다. Ch01 실습 02 의 "IN 이 23배 느렸던"
       현상의 근본 원인을 재현한다.
 환경: non-CDB=orcl 19.3, 스키마 SQLT + SYS AS SYSDBA (별도 터미널).
 주의: 개인 실습 환경 전용. FLUSH BUFFER_CACHE 는 모든 세션의 캐시를 비워 운영에서는 금지다.
================================================================================

$ sqlplus sqlt/sqlt@orcl

SQLT@orcl> SET LINESIZE 200
SQLT@orcl> SET PAGESIZE 100

--------------------------------------------------------------------------------
-- [1] (오류 → 원인 → 조치) 콜드 캐시를 만들려다 ORA-01031
--------------------------------------------------------------------------------
SQLT@orcl> ALTER SYSTEM FLUSH BUFFER_CACHE;
ALTER SYSTEM FLUSH BUFFER_CACHE
*
ERROR at line 1:
ORA-01031: insufficient privileges

SQLT@orcl> -- 원인 파악: ALTER SYSTEM 권한이 업무 계정에 없다(Ch02 실습 03 과 같은 이유).
SQLT@orcl> -- 조치: 별도 터미널의 SYS 세션에서 비운다. 이 세션(SQLT)은 그대로 둔다.

$ sqlplus / as sysdba
SYS@orcl> ALTER SYSTEM FLUSH BUFFER_CACHE;

System altered.

SYS@orcl> -- 정말 비었는지: 버퍼 캐시에 남은 MEDICAL_CLAIMS 블록 수
SYS@orcl> SELECT COUNT(*) cached_blocks
  2       FROM   v$bh b, dba_objects o
  3       WHERE  b.objd = o.data_object_id
  4       AND    o.owner = 'SQLT' AND o.object_name = 'MEDICAL_CLAIMS'
  5       AND    b.status <> 'free';

CACHED_BLOCKS
-------------
            0

SYS@orcl> EXIT

--------------------------------------------------------------------------------
-- [2] (조치 전 상태) 콜드 캐시 — 첫 실행
--------------------------------------------------------------------------------
SQLT@orcl> SET AUTOTRACE TRACEONLY STATISTICS
SQLT@orcl> SELECT /*+ GATHER_PLAN_STATISTICS */ claim_id, total_amt
  2       FROM   medical_claims
  3       WHERE  claim_id BETWEEN '20240601-0000000' AND '20240602-0000000';

804 rows selected.

Statistics
----------------------------------------------------------
       3144  consistent gets
       3085  physical reads
        804  rows processed
(관심 항목만 발췌)

SQLT@orcl> SET AUTOTRACE OFF
SQLT@orcl> SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR(NULL, NULL, 'ALLSTATS LAST'));

PLAN_TABLE_OUTPUT
------------------------------------------------------------------------------------------------
SQL_ID  <환경값>, child number 0
-------------------------------------
------------------------------------------------------------------------------------------------
| Id  | Operation         | Name           | Starts | E-Rows | A-Rows |   A-Time   | Buffers | Reads  |
------------------------------------------------------------------------------------------------
|   0 | SELECT STATEMENT  |                |      1 |        |    804 |00:00:03.46 |    3144 |   3085 |
|*  1 |  TABLE ACCESS FULL| MEDICAL_CLAIMS |      1 |  <환경값> |    804 |00:00:03.46 |    3144 |   3085 |
------------------------------------------------------------------------------------------------
   1 - filter(("CLAIM_ID"<='20240602-0000000' AND "CLAIM_ID">='20240601-0000000'))

-- 해석: 요청한 블록 3,144 중 3,085 를 디스크에서 읽었다(Reads 열은 물리 읽기가 있을 때만 나타난다).
--   3.46초 — 거의 전부가 디스크 I/O 대기 시간이다.
--   (참고) 이 범위는 PK 범위인데도 Full Scan 이다: 0.27% 선택도라도 옵티마이저가 인덱스를 고르지
--   않은 것은 SELECT 목록에 TOTAL_AMT 가 있어 표까지 가야 하기 때문 — Ch04 실습 02 의 교차점 소재.

--------------------------------------------------------------------------------
-- [3] (재확인) 웜 캐시 — 즉시 재실행
--------------------------------------------------------------------------------
SQLT@orcl> SET AUTOTRACE TRACEONLY STATISTICS
SQLT@orcl> SELECT /*+ GATHER_PLAN_STATISTICS */ claim_id, total_amt
  2       FROM   medical_claims
  3       WHERE  claim_id BETWEEN '20240601-0000000' AND '20240602-0000000';

804 rows selected.

Statistics
----------------------------------------------------------
       3144  consistent gets
          0  physical reads
        804  rows processed

SQLT@orcl> SET AUTOTRACE OFF
SQLT@orcl> SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR(NULL, NULL, 'ALLSTATS LAST'));

PLAN_TABLE_OUTPUT
------------------------------------------------------------------------------------------------
| Id  | Operation         | Name           | Starts | E-Rows | A-Rows |   A-Time   | Buffers |
------------------------------------------------------------------------------------------------
|   0 | SELECT STATEMENT  |                |      1 |        |    804 |00:00:00.01 |    3144 |
|*  1 |  TABLE ACCESS FULL| MEDICAL_CLAIMS |      1 |  <환경값> |    804 |00:00:00.01 |    3144 |
------------------------------------------------------------------------------------------------

-- 재확인: Buffers 3,144 — 완전히 같다. Reads 열이 사라졌다(0). A-Time 3.46초 → 0.01초, 약 346배.
--   같은 SQL·같은 계획·같은 논리 읽기인데 시간이 346배 다르다. 차이는 전부 물리 읽기다.

--   ┌──────────────────┬─────────┬───────┬─────────┐
--   │ 상태             │ Buffers │ Reads │ A-Time  │
--   ├──────────────────┼─────────┼───────┼─────────┤
--   │ 콜드(비운 직후)  │  3,144  │ 3,085 │ 3.46초  │
--   │ 웜(즉시 재실행)  │  3,144  │     0 │ 0.01초  │
--   └──────────────────┴─────────┴───────┴─────────┘

--------------------------------------------------------------------------------
-- [4] (조치 후 관점) 이 차이가 실무에서 뜻하는 것
--------------------------------------------------------------------------------
-- * 개발자가 같은 SQL 을 반복 테스트하면 항상 웜 캐시다 — "빠르다" 는 체감이 운영의 새벽 배치,
--   오랜만에 읽는 과거 데이터, 재기동 직후에는 재현되지 않는다.
-- * Buffers 를 줄이는 튜닝은 캐시 상태와 무관하게 유효하다. 콜드 캐시의 최악(전부 물리 읽기)에서
--   피해가 Buffers 만큼으로 제한되기 때문 — 이 과정 전체(인덱스·조인·N+1)가 Buffers 를 줄이는 기법이다.
-- * 인스턴스 부문 TUN 17장은 이 물리 읽기를 인스턴스 전체 관점(버퍼 캐시 크기·히트율의 함정)에서 다룬다.
--   히트율이 99% 여도 남은 1% 가 어느 SQL 에 몰려 있으면 그 SQL 은 346배 느리다.

--------------------------------------------------------------------------------
-- [정리]
--------------------------------------------------------------------------------
-- 1) Buffers(consistent gets) = 요청한 블록 수. Reads(physical reads) = 그중 디스크까지 간 수.
-- 2) 같은 SQL 이 콜드 3.46초 / 웜 0.01초. Buffers 는 3,144 로 동일 — 시간 차이는 전부 Reads.
-- 3) 시간으로 SQL 을 비교하려면 캐시 상태를 통제한다. 비교의 1차 지표는 Buffers.
-- 4) FLUSH BUFFER_CACHE 는 SYS 만, 개인 환경에서만.

SQLT@orcl> EXIT
