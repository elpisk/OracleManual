 Ch09 실습 02 — PK 컬럼의 DISTINCT 는 옵티마이저가 지운다 (Plan hash 1619867082 동일), 조인 뒤엔 못 지운다
 목표: HOSPITALS.HOSP_ID(PK)에 DISTINCT 를 붙여도 SORT/HASH UNIQUE 가 계획에 없고 DISTINCT 없는 조회와
       Plan hash 가 같은 것을 실측한다. 같은 컬럼을 조인 뒤에 DISTINCT 하면 HASH UNIQUE 가 생기는
       것으로 "유일성을 증명할 수 있을 때만 생략" 을 확인한다. 유니크 제약을 비활성화하면 생략이
       사라지는 이상 징후를 재현한다.
 환경: non-CDB=orcl 19.3, 스키마 SQLT. 복제 표로 제약 실험.
 주의: 개인 실습 환경 전용. 원본 표 제약은 건드리지 않는다.
================================================================================

-- 해석: DISTINCT 를 썼는데 SORT UNIQUE 도 HASH UNIQUE 도 없다. Plan hash 까지 같다. HOSP_ID 는 PK 라
--   중복이 있을 수 없음을 옵티마이저가 안다 — DISTINCT 요청을 비용 없이 통째로 생략했다.

--------------------------------------------------------------------------------
-- [2] (재확인) 조인을 거치면 — 같은 컬럼인데 HASH UNIQUE 가 생긴다
--------------------------------------------------------------------------------
SQLT@orcl> SELECT /*+ GATHER_PLAN_STATISTICS */ DISTINCT h.hosp_id
  2       FROM   hospitals h, medical_claims m
  3       WHERE  h.hosp_id = m.hosp_id AND h.hosp_id <= 100;

<환경값> rows selected.
SQLT@orcl> SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR(NULL, NULL, 'ALLSTATS LAST'));

PLAN_TABLE_OUTPUT
------------------------------------------------------------------------------------------
| Id  | Operation          | Name           | Starts | A-Rows | Buffers |
------------------------------------------------------------------------------------------
|   1 |  HASH UNIQUE       |                |      1 |  <환경값> |    3090 |
|*  2 |   TABLE ACCESS FULL| MEDICAL_CLAIMS |      1 |  <환경값> |    3090 |
------------------------------------------------------------------------------------------

-- 재확인: 이번엔 HASH UNIQUE 가 있다. h.hosp_id 는 PK 지만 조인 결과에서는 청구 건수만큼 반복되므로
--   중복이 실제로 있다 — 옵티마이저도 안다. (HOSPITALS 자체는 계획에서 사라졌다: FK 조인 제거, Ch01 실습 03.)
--   생략은 "결과 집합에서 유일성이 증명될 때" 만이다. 컬럼이 PK 라는 사실만으로는 부족하다.

--------------------------------------------------------------------------------
-- [3] (이상 징후 → 원인 → 재확인) 제약을 끄면 생략이 사라진다
--------------------------------------------------------------------------------
SQLT@orcl> CREATE TABLE hospitals_wl AS SELECT * FROM hospitals;
SQLT@orcl> ALTER TABLE hospitals_wl ADD CONSTRAINT pk_hosp_wl PRIMARY KEY (hosp_id);
SQLT@orcl> EXEC DBMS_STATS.GATHER_TABLE_STATS(USER, 'HOSPITALS_WL')

SQLT@orcl> SELECT /*+ GATHER_PLAN_STATISTICS */ DISTINCT hosp_id FROM hospitals_wl WHERE hosp_id <= 100;
(100 rows)
SQLT@orcl> SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR(NULL, NULL, 'BASIC'));

PLAN_TABLE_OUTPUT
------------------------------------------------
| Id  | Operation        | Name        |
------------------------------------------------
|   1 |  INDEX RANGE SCAN| PK_HOSP_WL  |            -- 원본과 같이 UNIQUE 단계 없음
------------------------------------------------

SQLT@orcl> -- 제약을 끈다(유니크 인덱스는 남긴 채 제약만 비활성 — KEEP INDEX).
SQLT@orcl> ALTER TABLE hospitals_wl MODIFY CONSTRAINT pk_hosp_wl DISABLE KEEP INDEX;

Table altered.

SQLT@orcl> SELECT /*+ GATHER_PLAN_STATISTICS */ DISTINCT hosp_id FROM hospitals_wl WHERE hosp_id <= 100;
(100 rows)
SQLT@orcl> SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR(NULL, NULL, 'BASIC'));

PLAN_TABLE_OUTPUT
------------------------------------------------
| Id  | Operation          | Name        |
------------------------------------------------
|   1 |  HASH UNIQUE       |             |          -- 생겼다
|   2 |   INDEX RANGE SCAN | PK_HOSP_WL  |
------------------------------------------------

SQLT@orcl> -- 이상 징후: 데이터도 인덱스도 그대로인데 HASH UNIQUE 가 생겼다.
SQLT@orcl> -- 원인 파악: 옵티마이저가 유일성의 근거로 삼는 것은 "ENABLED 제약" 이다. 인덱스가 유니크해도
SQLT@orcl> --   제약이 꺼져 있으면 중복이 들어올 수 있다고 본다(실제로 DISABLE 상태에선 중복 INSERT 가 된다).
SQLT@orcl> --   Ch01 실습 03 의 조인 제거도 같은 조건(ENABLED·VALIDATED FK)이었다 — 제약은 무결성 장치이자
SQLT@orcl> --   옵티마이저의 정보다. 운영에서 "성능 때문에" 제약을 끄면 계획이 나빠질 수 있다.
SQLT@orcl> ALTER TABLE hospitals_wl MODIFY CONSTRAINT pk_hosp_wl ENABLE;
SQLT@orcl> DROP TABLE hospitals_wl PURGE;

Table dropped.

--------------------------------------------------------------------------------
-- [정리]
--------------------------------------------------------------------------------
-- 1) PK/유니크 컬럼의 DISTINCT 는 옵티마이저가 통째로 생략한다(Plan hash 동일, Buffers 9).
-- 2) 조인 뒤에는 같은 컬럼도 중복이 생기므로 HASH UNIQUE 가 붙는다 — 생략은 결과 집합 기준.
-- 3) 유일성의 근거는 ENABLED 제약이다. 제약을 끄면 인덱스가 있어도 생략이 사라진다.
-- 4) "불필요한 DISTINCT 는 낭비" 는 조건부다. 계획에 UNIQUE 단계가 있는지로 판정한다.
