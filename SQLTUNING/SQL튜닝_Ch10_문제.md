# Chapter 10. SORT / GROUP BY / 집계 — 실습문제 10제

`SQL튜닝_Ch10_교안.md`를 먼저 읽고 푸시기 바랍니다. 모든 결과는 실습 DB 실측입니다.

---

**1. [상]** Q1(`WHERE`로 먼저 필터)과 Q2(불필요하게 `claim_type`까지 그룹핑한 뒤 바깥에서
필터)의 실행계획이 Plan hash value까지 완전히 동일했다. Q2가 겉보기엔 더 많은 그룹
(`hosp_id`×`claim_type` 조합)을 만드는 것처럼 보이는데 왜 실제로는 그렇지 않았는지
설명하시오.

**2. [상]** 1번 문항의 현상을 "predicate pushdown"이라는 용어와 "그룹 키에 대한 필터"라는
개념으로 설명하시오.

**3. [최상]** Chapter 8에서 다룬 인라인 뷰 사례(`WHERE v.cnt > 1000`, 집계 결과에 대한
필터)와 이번 챕터의 Q2(`WHERE claim_type='입원'`, 그룹 키에 대한 필터)는 둘 다 "인라인
뷰 바깥에서 필터링"하는 모양이다. 하지만 하나는 필터가 그룹화 이전으로 밀려들어갈 수 있고
(이번 챕터), 다른 하나는 그럴 수 없다(Chapter 8, `COUNT(*)`는 그룹화가 끝나야 값을 알
수 있음). 이 차이가 왜 발생하는지 설명하시오.

**4. [상]** 넓은 범위(8.5% 선택도)에서는 `ORDER BY claim_id`(PK 컬럼)조차 `SORT ORDER
BY`가 발생했다. `claim_id`가 PK인데도 정렬이 생략되지 않은 이유를 실행계획의 접근
경로(`TABLE ACCESS FULL`)와 연결지어 설명하시오.

**5. [상]** 좁은 범위(0.27% 선택도)에서는 `ORDER BY claim_id`가 정렬을 완전히 생략했다
(Buffers 776, `SORT` 오퍼레이션 없음). 왜 이 범위에서는 정렬이 생략될 수 있었는지, 4번
문항과 대조해서 설명하시오.

**6. [최상]** "ORDER BY 대상 컬럼에 인덱스만 있으면 정렬이 생략된다"는 말이 4·5번
문항의 실측 결과를 종합했을 때 왜 부정확한지, 더 정확한 조건은 무엇인지 서술하시오.

**7. [상]** 좁은 범위에서 `ORDER BY total_amt`(비인덱스 컬럼, Buffers 717)와 `ORDER BY
claim_id`(인덱스 컬럼, Buffers 776)를 비교하면, 오히려 정렬이 발생한 total_amt 쪽의
Buffers가 더 작다. 이 결과가 "정렬이 없으면 항상 더 저렴하다"는 단순한 가정에 대해
무엇을 시사하는지 논하시오. (힌트: `TABLE ACCESS BY INDEX ROWID`와 `... BATCHED`의
차이, Chapter 3 4번 해설을 참고할 것)

**8. [상]** `HASH GROUP BY`는 이번 챕터의 모든 GROUP BY 쿼리에서 공통으로 나타났다.
`SORT`(정렬)와 달리 `HASH GROUP BY`는 특정 인덱스 순서를 활용해서 생략될 수 있는
연산인지, 아니면 항상 발생하는 연산인지 논하시오.

**9. [최상]** 만약 리포트 화면에서 "병원별 청구 건수를 병원 ID 순으로 정렬해서
보여달라"는 요구가 있다면, `GROUP BY hosp_id ORDER BY hosp_id`처럼 작성할 수 있다. 이때
`GROUP BY`가 이미 `HASH GROUP BY`로 처리된다면, 그 결과에 대해 별도의 `SORT ORDER BY`가
추가로 필요할지, 아니면 `HASH GROUP BY` 대신 다른 방식(`SORT GROUP BY` 등)이 선택되어
정렬까지 한 번에 해결될 수도 있을지 추론하시오. (직접 실행할 필요는 없음 — 원칙 적용
훈련 문제)

**10. [최상]** 이번 챕터에서 확인한 두 가지 사례(GROUP BY 필터 위치는 대체로 중요하지
않음, ORDER BY 정렬 생략은 선택도에 크게 좌우됨)를 근거로, "튜닝할 때 SQL 문장의 겉모양
(필터를 어디에 썼는지)보다 무엇을 먼저 확인해야 하는가"에 대한 결론을 한 문장으로
정리하시오.
