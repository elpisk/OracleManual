# Oracle SQL 튜닝 교안 및 실습 과정 PRD

> **문서 상태**: 개정판. `참고PRD.md`(사용자 제공, 범용 커머스 예시 기반)의 커리큘럼·설계원칙·
> 평가체계를 뼈대로 삼되, 예시 스키마를 이 저장소의 실제 **진료비청구심사 스키마**로 전면
> 교체하고, 라이브 DB(실습 DB의 `SQLT` 스키마)에서 **실제로 캡처한 실측 데이터**(19절
> 부록)로 뒷받침했습니다. `참고PRD.md`는 원본 그대로 저장소에 남겨두고, 이 문서가 실제
> 제작에 쓸 확정 PRD 역할을 합니다.

핵심 방향은 참고 문서와 동일합니다: 단순한 SQL 문법 교육이 아니라 **"느린 SQL을 발견 → 원인
분석 → 실행계획 해석 → 개선안 수립 → 튜닝 → 개선 효과 검증"**의 전체 사이클을 반복 실습하는
과정으로 설계합니다.

## 1. 문서 개요

### 1.1 제품명

**Oracle SQL 튜닝 실전 과정 — 진료비 청구·심사 시스템 기반**

### 1.2 목적

Oracle 데이터베이스를 사용하는 백엔드 개발자 및 DBA가 SQL 성능 문제를 스스로 분석하고
개선할 수 있도록, 이론 교안과 실습 문제를 하나의 교육 과정으로 설계한다.

본 과정은 SQL 문법 자체보다 **SQL 실행 원리와 성능 문제의 원인을 이해하고, 실행계획과 다양한
성능 지표를 기반으로 튜닝하는 능력**을 습득하는 것을 핵심 목표로 한다.

### 1.3 대상 학습자

* SQL 및 데이터베이스 기본 사용 경험이 있는 초급 개발자
* 경력 2~3년 수준의 백엔드 개발자
* 경력 2~3년 수준의 DBA
* Oracle SQL을 작성할 수 있지만 성능 문제를 체계적으로 분석해본 경험이 부족한 개발자
* 실행계획을 볼 수 있지만 각 항목의 의미와 튜닝 방법을 명확하게 설명하기 어려운 학습자

### 1.4 실습 환경 (확정)

참고 문서는 "실습 환경은 교육 과정에서 동일한 Oracle 버전을 사용 권장"이라고만 되어 있었으나,
이번엔 실제 환경이 이미 준비되어 있습니다.

| 항목 | 값 |
|---|---|
| DB 버전 | Oracle Database 19c (19.3.0), Linux(OEL7) |
| 접속 정보 | 실습 DB(스키마 `SQLT`). 호스트·SID·비밀번호는 이 문서에 기재하지 않으며 교육 운영 시 별도 안내한다 |
| 문자셋 | `AL32UTF8` (한글 데이터 정상 처리 확인됨) |
| 접근 방식 | SSH(계정 `oracle`) → `sqlplus` — 본 과정 제작 과정에서 이미 이 경로로 실측 완료 |
| 데이터 상태 | 아래 12절의 실제 테이블·건수로 이미 적재 완료. **PK 외 인덱스는 없음** — 이는 실수가 아니라 튜닝 실습을 위한 의도된 "Before 상태" |

**이미 갖춰진 자산** (이번 과정 제작에 바로 재사용):

- 스키마 DDL·데이터 생성 스크립트(버그 9건 수정 반영본), ERD, erwin 리버스 엔지니어링용 DDL
- SQL 고급 활용 실습문제 두 세트(각 50문항, 문제지/해설 분리) — 조인·서브쿼리·분석함수 등
  SQL 문법 자체를 다루는 자료로, 이번 튜닝 과정과는 성격이 달라 **대체가 아니라 병행**한다
  (16절 MVP 범위 참고)

## 2. 문제 정의

현업에서 SQL 성능 문제는 단순히 SQL 문법을 잘 작성한다고 해결되지 않는다. 예를 들어 다음과
같은 상황이 발생할 수 있다.

* 인덱스가 있는데도 Full Table Scan이 발생한다.
* 같은 SQL인데 특정 조건에서만 느려진다.
* JOIN 대상 데이터가 많아지면서 응답 시간이 급격하게 증가한다.
* WHERE 조건을 조금 변경했더니 실행계획이 달라진다.
* `SELECT *` 또는 불필요한 JOIN 때문에 조회 비용이 증가한다.
* 함수나 형 변환 때문에 인덱스를 제대로 사용하지 못한다.
* 실행계획상 비용은 낮아 보이는데 실제 실행 시간은 길다.
* OFFSET 기반 페이징이 데이터 증가에 따라 느려진다.
* 서브쿼리, JOIN, EXISTS 등의 작성 방식에 따라 성능이 달라진다.
* 통계정보나 데이터 분포에 따라 Oracle 옵티마이저의 판단이 달라진다.

**우리 스키마에서 실제로 재현한 사례** (19절 부록 참고): `MEDICAL_CLAIMS`에서 특정 병원·특정
접수일로 청구를 조회하면, 인덱스가 없을 때 Full Table Scan으로 Buffers 3,091을 소비하지만,
`(HOSP_ID, RECEIPT_DATE)` 복합 인덱스를 만들면 Buffers가 15로 줄어든다(약 206배 감소) —
반면 같은 세션에서 측정한 Elapsed Time은 두 경우 모두 0.01초로 거의 차이가 안 보였다. 이 괴리
자체가 좋은 교육 소재다: 소규모·캐시된 단일 세션 테스트에서는 Elapsed Time만으로 튜닝 효과를
판단하면 안 되고, Buffers(논리적 I/O)처럼 데이터 규모·동시성에 덜 흔들리는 지표를 함께 봐야
한다는 걸 첫 실습에서부터 체감시킬 수 있다.

따라서 교육에서는 단순히 "이렇게 작성하면 빠르다"를 가르치는 것이 아니라,

> **왜 느린가? → Oracle은 어떻게 실행하는가? → 실행계획은 무엇을 말하는가? → 어떤 방법으로
> 개선할 것인가? → 정말 빨라졌는가? (그리고 무엇을 근거로 그렇게 판단했는가?)**

라는 사고 과정을 반복적으로 훈련해야 한다.

## 3. 교육 목표

교육 종료 후 학습자는 다음 역량을 갖추는 것을 목표로 한다.

### 3.1 SQL 실행 원리 이해
- SQL의 논리적 처리 순서와 실제 실행 과정의 차이를 이해한다.
- Oracle 옵티마이저의 기본적인 역할을 설명할 수 있다.
- Parsing, Optimization, Execution의 기본 개념을 이해한다.
- 데이터 접근 방식과 JOIN 처리 방식의 차이를 이해한다.

### 3.2 실행계획 분석
- 실행계획을 직접 생성하고 읽을 수 있다.
- 주요 Operation의 의미를 설명할 수 있다.
- Table Access Full, Index Scan 등의 차이를 설명할 수 있다.
- JOIN 방식의 차이를 이해할 수 있다.
- 예상 Rows(E-Rows)와 실제 Rows(A-Rows)의 차이를 통해 문제를 추적할 수 있다.

### 3.3 인덱스 튜닝
- 인덱스의 구조와 동작 원리를 이해한다.
- 적절한 인덱스 설계 기준을 이해한다.
- 단일 컬럼/복합 인덱스를 설계할 수 있다.
- 인덱스를 사용할 수 없는 대표적인 SQL 패턴을 식별할 수 있다.
- 인덱스가 항상 성능을 개선하지 않는 이유를 설명할 수 있다.

### 3.4 SQL 자체 튜닝
- 불필요한 데이터 접근을 줄일 수 있다.
- WHERE 조건을 효율적으로 작성할 수 있다.
- JOIN을 효율적으로 구성할 수 있다.
- 서브쿼리와 JOIN, EXISTS 등의 특성을 비교할 수 있다.
- 함수, 형 변환, LIKE 등의 조건이 인덱스 사용에 미치는 영향을 분석할 수 있다.
- 페이징 SQL의 성능 문제를 개선할 수 있다.

### 3.5 실전 성능 분석
- 느린 SQL을 발견할 수 있다.
- 실행계획 및 실행 통계를 기반으로 병목을 찾을 수 있다.
- 여러 튜닝 방법을 비교하고 최적의 방법을 선택할 수 있다.
- 튜닝 전/후 성능을 측정하고 개선 효과를 수치로 설명할 수 있다.

## 4. 교육 설계 원칙

**원칙 1. 이론보다 실행계획 중심** — 각 개념은 다음 구조로 설명한다.
**개념 → 예제 SQL → 실행계획 → 문제 발생 원인 → 튜닝 SQL → 실행계획 비교 → 성능 측정**

**원칙 2. 모든 챕터에 실습 포함** — 각 챕터는 최소 다음 구성으로 제작한다.
핵심 개념 → 간단한 예제 → 실행계획 분석 → 잘못된 SQL → 튜닝 문제 → 실습 → 해설 → 핵심 정리

**원칙 3. "정답 SQL"보다 "튜닝 과정"을 평가** — 다음 항목을 평가한다.
문제 원인을 설명했는가? 실행계획을 근거로 판단했는가? 적절한 튜닝 방법을 선택했는가?
튜닝 전/후를 비교했는가? 개선 효과를 수치로 설명했는가? 데이터 규모가 변경되어도 해당 튜닝이
유효한지 설명할 수 있는가?

**원칙 4 (신규). 라이브 DB 실측을 우선한다** — 이 과정은 정적으로 상상한 예시 수치
("8.2초 → 0.08초" 같은 가상값) 대신, 가능한 모든 곳에서 실습 DB에 직접 접속해
실제로 재현·측정한 값을 싣는다. 이미 19절에서 한 건을 실측해 이 방식이 동작함을 확인했다.
다만 5절의 운영 원칙을 반드시 지켜야 실습 환경이 오염되지 않는다.

## 5. 리스크 및 운영 원칙 (신규 섹션)

라이브 DB를 반복적으로 실습에 쓰기 위한 규칙. `참고PRD.md`에는 없던 항목이며, 이번 스키마가
실제로 살아있는 공유 자원이기 때문에 명문화가 필요하다.

| 리스크 | 대응 원칙 |
|---|---|
| 실습용으로 만든 인덱스를 안 지우고 넘어가면, 이후 "인덱스가 없어서 Full Scan이 나야 하는" 다른 챕터의 데모가 깨진다 | **매 실습 스크립트는 반드시 자체적으로 `DROP INDEX`로 마무리**한다. 19절 부록 스크립트가 이 패턴의 템플릿이다. 실습 종료 후 `USER_INDEXES`를 조회해 PK만 남았는지 확인하는 절차를 표준 마무리 단계로 포함한다 |
| 히스토그램 실습을 위해 통계정보를 일부러 왜곡했다가 원복을 안 하면 이후 챕터 결과가 흔들린다 | 통계정보를 바꾸는 실습은 챕터 종료 시 `DBMS_STATS.GATHER_TABLE_STATS`로 표준 상태 재수집을 마무리 단계에 포함한다 |
| 대량 데이터 재생성/파티션 재구성 등은 시간이 걸린다(과거 30만 건 트랜잭션 생성에 1분 16초 소요 이력 있음) | 오래 걸리는 작업은 백그라운드로 실행하고 완료 후 결과를 캡처하는 방식을 유지한다 |
| 여러 챕터를 동시에/반복해서 준비하다 세션이 꼬이면 어느 인덱스가 "지금 챕터 것"인지 헷갈릴 수 있다 | 실습용 오브젝트 이름에 챕터 번호를 접두어로 붙인다 (예: `IX_CH05_HOSP_RECEIPT`) |
| SQLT 계정에 처음엔 `SELECT_CATALOG_ROLE`이 없어 `DBMS_XPLAN.DISPLAY_CURSOR`가 `V$SESSION` 권한 오류로 실패했던 이력이 있음(19절에서 실제 발생) | 계정 생성 스크립트에 `GRANT SELECT_CATALOG_ROLE TO sqlt;`를 기본 포함해, 향후 재생성 시 같은 오류를 반복하지 않는다 |
| 이 DB는 개인 연습용 VM이라 위험도는 낮지만, 그래도 실측 작업 전에는 어떤 DDL을 실행할지 먼저 공유한다 | 매 실측 세션 전 어떤 인덱스/통계 변경을 할지 간단히 안내 후 진행 |

## 6. 전체 커리큘럼

`참고PRD.md`의 15개 챕터 구조를 그대로 채택하되, 모든 실습 예시를 우리 스키마의 컬럼·시나리오로
치환했다.

### Part 1. SQL 튜닝 입문

**Chapter 1. SQL 튜닝이란?**
학습 내용: SQL 성능의 의미, DB 성능 문제의 주요 원인, SQL 튜닝과 애플리케이션 튜닝의 관계,
SQL 실행 비용의 개념, CPU/I/O/Memory 관점에서 SQL 바라보기, 좋은 SQL과 나쁜 SQL의 차이
실습: `MEDICAL_CLAIMS`에서 동일 결과를 반환하는 여러 SQL(예: `EXISTS` vs `IN` vs `JOIN`으로
"주사제를 처방받은 청구 찾기") 비교, 실행 시간·Buffers 비교

**Chapter 2. SQL은 어떻게 실행되는가?**
학습 내용: SQL 처리 과정(Parse/Bind/Execute/Fetch), 옵티마이저의 역할, 실행계획의 개념,
Cost의 의미
실습: `HOSP_ID` 리터럴 값을 바꿔가며 동일 SQL을 재실행, 실행계획 변화 관찰

**Chapter 3. 실행계획 기초**
학습 내용: Id/Operation/Options/Object Name/Rows/Cost/Bytes/Predicate Information,
실행 순서 해석, 주요 Operation(TABLE ACCESS FULL, TABLE ACCESS BY INDEX ROWID,
INDEX RANGE/UNIQUE/FULL/FAST FULL SCAN)
실습: "`MEDICAL_CLAIMS`는 왜 Full Table Scan을 하는가?" — 19절 부록의 BEFORE 실행계획을
그대로 첫 실습 자료로 사용

### Part 2. 데이터 접근과 인덱스

**Chapter 4. Full Scan vs Index Scan**
학습 내용: Full Table Scan, Index Scan, Selectivity, Cardinality, 데이터 분포, 작은
테이블에서 Full Scan이 유리한 이유, 인덱스가 있다고 무조건 사용하는 것은 아닌 이유
실습: `HOSPITALS`(1,000건, 작음) vs `CLAIM_DETAILS`(약 90만 건, 큼)에서 동일 패턴 조건의
실행계획이 어떻게 달라지는지 비교

**Chapter 5. 인덱스 설계**
학습 내용: B-Tree Index 기본 구조, 단일/복합 인덱스, 컬럼 순서·선두 컬럼·선택도, 인덱스의
장점과 비용, 인덱스를 너무 많이 생성하면 발생하는 문제
실습: 19절 부록 시나리오 재현 — `(HOSP_ID, RECEIPT_DATE)` 복합 인덱스 생성 전/후 비교,
컬럼 순서를 `(RECEIPT_DATE, HOSP_ID)`로 바꿨을 때의 차이도 추가로 실측

### Part 3. 인덱스를 방해하는 SQL

**Chapter 6. SARGable SQL**
학습 내용: 함수와 인덱스, 묵시적 형 변환, 연산식, LIKE, 부정 조건, NULL 조건, 컬럼 가공
예제 주제: `PATIENTS.BIRTH_DATE`는 `VARCHAR2(8)` YYYYMMDD 문자열이라 이 주제에 최적화된
컬럼이다.
```sql
WHERE TO_NUMBER(SUBSTR(birth_date,1,4)) <= 1990   -- 함수로 인덱스 무력화
```
vs.
```sql
WHERE birth_date <= '19901231'                     -- 문자열 그대로 비교, 인덱스 가능
```
실습: `RECEIPT_DATE`에 `TO_CHAR(receipt_date,'YYYYMM')='202406'`처럼 함수를 씌운 경우와
`receipt_date >= DATE'2024-06-01' AND receipt_date < DATE'2024-07-01'`로 재작성한 경우의

일반론으로 설명하던 "데이터 분포가 다른 컬럼"을 우리 스키마는 실제로 갖고 있다는 뜻

실습 (19절 부록의 실측값을 그대로 사용):
```text
튜닝 전 (TABLE ACCESS FULL):  Buffers 3,091 / A-Rows 11 / E-Rows 6
튜닝 후 (INDEX RANGE SCAN):   Buffers    15 / A-Rows 11 / E-Rows 7
```
단순히 "빨라졌다"가 아니라, 이번엔 Elapsed Time이 두 경우 모두 0.01초로 거의 같았다는 점까지
정직하게 보여주고 "그렇다면 무엇이 실제로 개선된 것인가?"를 Buffers 수치로 설명하게 만든다.

Chapter 3 파일럿 제작 중 두 차례 문체 피드백을 받았다. **구조(10단계 골격)는 처음부터

1. 1차: 산문이 "AI적인 느낌"이 난다 — 재진술형 문단 끝맺음, 볼드 라벨 리스티클 과다

2. 2차(과잉 수정): 아예 교수학습지도안 형식(학습목표/교수학습활동/준비물및유의점/교사발화)
   으로 구조 자체를 바꿨으나, 이는 요청 범위를 넘어선 것이었음 — 되돌림.
3. 최종: **`참고PRD.md`의 10단계 구조(01. Why → 02. Concept → 03. Oracle Internals →
   04. Example → 05. Execution Plan → 06. Bad SQL → 07. Tuning → 08. Benchmark →
   09. Practice → 10. Review)는 그대로 유지**하되, 각 절의 내용을 서술형 문장이 아니라
   **개조식(글머리 기호) + 행동 중심 평서체**로 작성한다.

**최종 확정 문체 규칙**:
- 각 절은 짧은 개조식 항목(글머리 기호 `-`)으로 구성한다. 긴 서술형 문단을 쓰지 않는다.
- 종결어미는 평서형·3인칭화한다 (`~다`, `~함`, `~됨`). "여러분", "~해보자", "~합니다"
  같은 독자를 직접 부르는 구어체·경어체는 쓰지 않는다.
- 재진술형 마무리("~것이 핵심이다", "~라는 뜻이다")를 반복하지 않는다. 사실을 한 번만
  간결하게 진술한다.
- SQL·실행계획 원문은 코드블록으로 그대로 유지한다(개조식 규칙은 산문 설명에만 적용,
  코드/표는 원래 형식 유지).

## 12. 교육용 데이터셋 설계 (핵심 — 실제 스키마로 전면 교체)

`참고PRD.md`는 가상의 CUSTOMER/PRODUCT/ORDERS/ORDER_ITEM/PAYMENT/DELIVERY/LOGIN_HISTORY
(수백만~5천만 건)를 예시로 제시했다. 이번엔 이미 실제로 준비되고 검증된 스키마를 그대로 쓴다.

| 테이블 | 건수 | 역할 |
|---|---:|---|
| HOSPITALS | 1,000 | 요양기관 (병원·의원·약국) |
| PATIENTS | 50,000 | 수진자(환자) |
| DRUG_MASTER | 10,000 | 수가/약가 마스터 |
| MEDICAL_CLAIMS | 300,000 | 진료비 청구 명세서 (Master) |
| CLAIM_DETAILS | 899,894 | 진료 내역 상세 (Detail) |
| DISEASES | 399,551 | 상병 내역 |
| REVIEW_LOG | 500,000 | 심사 이력 로그 |

참고 문서가 "의도적으로 포함해야 한다"고 제안한 데이터 특성은 이미 다음과 같이 실제로
존재한다.

| 참고 문서가 요구한 특성 | 우리 스키마의 실제 대응 |
|---|---|
| 대용량 테이블 | `CLAIM_DETAILS`(899,894), `REVIEW_LOG`(500,000) |
| 데이터 분포가 불균등한 컬럼 | `MEDICAL_CLAIMS.HOSP_ID` — 1~50번 병원에 청구의 약 50% 집중 (핵심 스큐) |
| 선택도가 높은 컬럼 | `MEDICAL_CLAIMS.CLAIM_ID`(PK), `PATIENTS.PAT_ID` |
| 선택도가 낮은 컬럼 | `PATIENTS.GENDER`(M/F), `MEDICAL_CLAIMS.CLAIM_TYPE`(입원/외래), `REVIEW_STATUS`(심사중/심사완료) |
| 날짜 데이터 | `RECEIPT_DATE`, `VISIT_DATE`, `EST_DATE` |
| NULL 데이터 | `REVIEW_LOG.ERROR_CODE`(정상 처리 시 NULL), `REVIEW_LOG.CLAIM_ID`(로그가 없는 청구 존재 가능) |
| 중복(쏠린) 데이터 | `DISEASES.DIS_CODE`('J00' 약 30%), `HOSPITALS.HOSP_TYPE`(의원 약 80%) |
| 대량 JOIN | `MEDICAL_CLAIMS`↔`HOSPITALS`↔`PATIENTS`↔`CLAIM_DETAILS`↔`DRUG_MASTER`↔`DISEASES` 6-way 조인 가능 |
| 1:N 관계 | `MEDICAL_CLAIMS`:`CLAIM_DETAILS` = 1:1~5, `MEDICAL_CLAIMS`:`DISEASES` = 1:1~2 |
| 복합 인덱스가 필요한 상황 | `(HOSP_ID, RECEIPT_DATE)` — 19절에서 이미 실측 검증 |
| 잘못된/불필요한 인덱스가 존재하는 상황 | 아직 없음 — Chapter 5·12 실습 제작 시 의도적으로 설계해 추가 예정(예: 컬럼 순서가 잘못된 복합 인덱스를 만들어 두고 "왜 이 인덱스가 안 쓰이는지" 진단하게 하는 문제) |

이를 통해 학습자가 단순히 "인덱스를 추가하면 된다"는 잘못된 습관을 갖지 않도록 한다.

```text
SQL 실행 원리 → 실행계획 읽기 → Full Scan/Index Scan → 인덱스 설계 → WHERE 조건 튜닝
→ JOIN 튜닝 → Subquery 튜닝 → GROUP BY/SORT → 페이징 튜닝 → 통계정보/Optimizer
→ 복합적인 성능 문제 → 종합 SQL 튜닝 프로젝트
```

## 14. 학습 성과 기준

과정을 수료한 학습자는 다음 질문에 답할 수 있어야 한다.

**초급**: 실행계획이 무엇인가? Full Table Scan은 무엇인가? Index Scan은 무엇인가? 인덱스는
왜 사용하는가?

**중급**: 인덱스가 있는데 왜 사용하지 않는가? 복합 인덱스의 컬럼 순서는 어떻게 결정하는가?
Nested Loops와 Hash Join은 언제 유리한가? 함수가 포함된 WHERE 조건이 왜 문제가 되는가?
예상 Rows와 실제 Rows의 차이는 무엇을 의미하는가?

**실무 (도메인 예시 추가)**: 이 SQL이 느린 이유는 무엇인가? 어디에서 I/O가 많이 발생하는가?
어떤 인덱스를 만들어야 하는가? SQL을 어떻게 변경해야 하는가? 튜닝 전/후 성능 개선을 어떻게
증명할 것인가? **"1~50번 병원(대형병원)만 쏠려서 느린 쿼리와, 전체 병원에 골고루 걸리는
쿼리는 왜 같은 인덱스로 해결이 안 되는가?"** 같은 스큐 특화 질문에 답할 수 있는가? 인덱스
추가로 인해 발생할 수 있는 부작용은 무엇인가?

## 18. 핵심 제품 방향

이 교육 과정의 핵심은 **"SQL 문법을 가르치는 과정"이 아니라 "성능 문제를 해결하는 사고방식을
훈련하는 과정"**으로 정의한다. 모든 교육 콘텐츠는 다음 질문을 중심으로 설계한다.

> SQL이 왜 느린가? → Oracle은 이 SQL을 어떻게 실행하고 있는가? → 실행계획에서 병목은
> 어디인가? → SQL/Index/데이터 접근 방식을 어떻게 바꿀 것인가? → 실제로 얼마나 개선되었는가?
> → 데이터가 증가해도 이 튜닝이 유효한가?

최종적으로 학습자가 새로운 SQL 성능 문제를 만났을 때, 특정 튜닝 기법을 암기해서 적용하는 것이
아니라 **실행계획과 측정 데이터를 근거로 스스로 원인을 찾고 해결할 수 있는 수준**에 도달하는
것을 본 과정의 최종 목표로 한다.

## 19. 부록 — 실측 Before/After 캡처 결과 (2026-08-10, 실습 DB 실행)

3절 "실측데이터 사용" 요구사항을 검증하기 위해 실제로 재현한 결과. Chapter 3·5·14 교안의
1차 소재로 그대로 쓸 수 있다.

**시나리오**: `HOSP_ID=1`(대형병원), `RECEIPT_DATE='2024-06-15'` 조건으로 청구 조회

```sql
SELECT claim_id, hosp_id, receipt_date, total_amt, review_status
FROM medical_claims
WHERE hosp_id = 1 AND receipt_date = TO_DATE('2024-06-15','YYYY-MM-DD');
```

**BEFORE (인덱스 없음 — 스키마 원래 상태)**

```text
| Id | Operation         | Name            | Starts | E-Rows | A-Rows | A-Time      | Buffers |
| 0  | SELECT STATEMENT  |                 |      1 |        |     11 | 00:00:00.01 |    3091 |
| 1  | TABLE ACCESS FULL | MEDICAL_CLAIMS  |      1 |      6 |     11 | 00:00:00.01 |    3091 |
```

**AFTER (`(HOSP_ID, RECEIPT_DATE)` 복합 인덱스 생성 후)**

```text
| Id | Operation                          | Name                  | Starts | E-Rows | A-Rows | A-Time      | Buffers |
| 0  | SELECT STATEMENT                   |                       |      1 |        |     11 | 00:00:00.01 |      15 |
| 1  | TABLE ACCESS BY INDEX ROWID BATCHED| MEDICAL_CLAIMS        |      1 |      7 |     11 | 00:00:00.01 |      15 |
| 2  | INDEX RANGE SCAN                   | IX_DEMO_HOSP_RECEIPT  |      1 |      7 |     11 | 00:00:00.01 |       4 |
```

**핵심 수치**: Buffers 3,091 → 15 (**약 206배 감소**). Elapsed Time은 두 경우 모두
0.01초로 동일하게 표시됨 — 단일 세션·캐시된 소규모 결과셋에서는 벽시계 시간만으로 튜닝
효과를 판단하기 어렵고, 논리적 I/O(Buffers) 같은 안정적 지표가 필요하다는 걸 보여주는
정직한(과장하지 않은) 예시.

**실습 후 정리 확인**: `DROP INDEX ix_demo_hosp_receipt` 및 `DBMS_STATS.GATHER_TABLE_STATS`
재수집 후 `USER_INDEXES` 조회 결과 `PK_MEDICAL_CLAIMS` 하나만 남은 것을 확인 — 5절 운영
원칙(실습 후 원상복구)이 실제로 지켜짐을 검증.

**이 과정에서 발견한 운영상 이슈 1건**: `SQLT` 계정에 `SELECT_CATALOG_ROLE`이 없어
`DBMS_XPLAN.DISPLAY_CURSOR`가 `V$SESSION` 권한 부족으로 실패했다가, 권한을 추가하고 재시도해
해결했다. 이번 PRD의 5절 표에 반영해, 향후 계정 생성 스크립트에 이 권한을 기본 포함하도록
정리했다.
