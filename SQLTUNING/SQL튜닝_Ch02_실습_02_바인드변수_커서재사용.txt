 Ch02 실습 02 — 바인드 변수: 값이 달라도 SQL_ID 하나, 하드 파싱 1회 (SP2-0552 교정 포함)
 목표: :b_hosp 에 1 과 500 을 대입해 두 번 실행하고 V$SQL 에서 SQL_ID 하나에 EXECUTIONS=2
       가 되는 것을 확인한다. 바인드 변수를 선언하지 않고 EXEC 로 대입하다 나는 SP2-0552 를
       재현·교정한다. 리터럴 100회(실습 01) 와 바인드 100회의 하드 파싱 델타를 대조한다.
 환경: non-CDB=orcl 19.3, 스키마 SQLT.
 주의: 개인 실습 환경 전용. 조회만 수행한다.
================================================================================

$ sqlplus sqlt/sqlt@orcl

SQLT@orcl> SET LINESIZE 200
SQLT@orcl> SET PAGESIZE 100

--------------------------------------------------------------------------------
-- [1] (오류 → 원인 → 조치 → 재확인) 바인드 변수 대입에서 SP2-0552
--------------------------------------------------------------------------------
SQLT@orcl> EXEC :b_hosp := 1
SP2-0552: Bind variable "B_HOSP" not declared.

SQLT@orcl> -- 원인 파악: SP2- 접두어는 ORA- 와 달리 데이터베이스가 아니라 SQL*Plus 가 낸 오류다.
SQLT@orcl> --   SQL*Plus 의 바인드 변수는 서버로 보내기 전에 클라이언트에서 VARIABLE 로 먼저
SQLT@orcl> --   선언해야 한다. 선언 없이 :b_hosp 를 쓰면 SQL*Plus 가 서버에 보내지도 않고 거부한다.
SQLT@orcl> -- 조치: 자료형과 함께 선언한 뒤 대입한다.
SQLT@orcl> VARIABLE b_hosp NUMBER
SQLT@orcl> EXEC :b_hosp := 1

PL/SQL procedure successfully completed.

SQLT@orcl> PRINT b_hosp

    B_HOSP
----------
         1

-- 재확인: 선언 후에는 대입·출력이 된다. (JDBC 등 애플리케이션에서는 드라이버가 이 선언을 대신한다.)

--------------------------------------------------------------------------------
-- [2] (조치 전 상태) 같은 SQL 텍스트로 값만 바꿔 두 번 실행
--------------------------------------------------------------------------------
SQLT@orcl> SELECT /*+ GATHER_PLAN_STATISTICS */ COUNT(*) FROM medical_claims WHERE hosp_id = :b_hosp;

  COUNT(*)
----------
      3058

SQLT@orcl> EXEC :b_hosp := 500

PL/SQL procedure successfully completed.

SQLT@orcl> SELECT /*+ GATHER_PLAN_STATISTICS */ COUNT(*) FROM medical_claims WHERE hosp_id = :b_hosp;

  COUNT(*)
----------
       177

SQLT@orcl> COLUMN sql_text FORMAT A58
SQLT@orcl> SELECT sql_id, child_number, executions, parse_calls, loads, sql_text
  2       FROM   v$sql
  3       WHERE  sql_text LIKE '%medical_claims WHERE hosp_id = :b_hosp';

SQL_ID        CHILD_NUMBER EXECUTIONS PARSE_CALLS      LOADS SQL_TEXT
------------- ------------ ---------- ----------- ---------- ----------------------------------------------------------
3zakhp3a1b0ac            0          2           2          1 SELECT /*+ GATHER_PLAN_STATISTICS */ COUNT(*) FROM medical_

-- 해석: SQL_ID 하나(3zakhp3a1b0ac)에 EXECUTIONS=2. LOADS=1 — 공유 풀 적재(하드 파싱)는 한 번뿐이고
--   두 번째는 그 커서를 찾아 재사용했다(소프트 파싱). PARSE_CALLS=2 는 "파싱을 요청한 횟수" 이지
--   하드 파싱 횟수가 아니다 — 두 번째 요청은 공유 풀에서 찾았으므로 소프트 파싱이다.

--------------------------------------------------------------------------------

SQLT@orcl> -- 이상 징후: 마지막 실행(500)의 A-Rows 는 177 인데 E-Rows 는 3,039 — 값 1 의 추정치다.
SQLT@orcl> -- 원인 파악: 바인드 변수 SQL 은 최초 하드 파싱 때 들여다본 값(bind peeking, 여기서는 1)으로
SQLT@orcl> --   계획과 추정치를 만들고, 이후 실행은 그 커서를 그대로 재사용한다. 값이 500 으로 바뀌어도
SQLT@orcl> --   다시 최적화하지 않으므로 E-Rows 가 실제와 멀어진다.
SQLT@orcl> -- 재확인: 이 SQL 은 어느 값이든 Full Scan 이라 계획이 같아 손해가 없다. 그러나 값에 따라
SQLT@orcl> --   인덱스 vs Full Scan 이 갈리는 컬럼(Ch04 선택도)이라면 한쪽 값의 계획이 다른 값에
SQLT@orcl> --   잘못 재사용된다 — 이것이 "바인드 변수가 항상 유리하지는 않다" 의 실체다(Ch13).

-- [정리]
--------------------------------------------------------------------------------
-- 1) SQL*Plus 바인드 변수는 VARIABLE 로 먼저 선언한다. SP2-0552 는 서버가 아니라 SQL*Plus 오류.
-- 2) 바인드 변수 SQL 은 값이 달라도 SQL_ID 하나, LOADS(하드 파싱) 1회, 이후 소프트 파싱.
-- 3) 대신 최초 값으로 만든 계획·추정치가 재사용된다(bind peeking) — 값에 따라 계획이 갈리는
--    컬럼에서는 손해가 날 수 있다(Ch13 에서 히스토그램과 함께 본다).
-- 4) 리터럴 100회 = 하드 파싱 ≈100 / 바인드 100회 = 하드 파싱 1. 이 차이가 TUN 2장 WL_01 부하의 정체다.
