 Ch11 실습 01 — OFFSET 페이징: 깊이가 커져도 Buffers 는 3,090, 시간은 9배·정렬 메모리는 2K → 14M (ORA-00933 교정)
 목표: RECEIPT_DATE 인덱스를 만든 상태에서 OFFSET 0 / 200,000 / 280,000 을 실측해 Buffers 가 그대로인데
       A-Time 과 WINDOW SORT PUSHED RANK 의 Used-Mem 이 급증하는 것을 본다. MySQL 식 LIMIT 를 써서 나는
       ORA-00933 을 교정하고, "Buffers 가 같으니 비용도 같다" 는 오판을 +MEMSTATS 로 바로잡는다.
 환경: non-CDB=orcl 19.3, 스키마 SQLT. DDL 포함(IX_RECEIPT — 실습 03 끝에 지운다).
 주의: 개인 실습 환경 전용.
================================================================================

$ sqlplus sqlt/sqlt@orcl

SQLT@orcl> SET LINESIZE 200
SQLT@orcl> SET PAGESIZE 100
SQLT@orcl> CREATE INDEX ix_receipt ON medical_claims(receipt_date);

Index created.

--------------------------------------------------------------------------------
-- [1] (오류 → 원인 → 조치) 다른 DBMS 습관 — ORA-00933
--------------------------------------------------------------------------------
SQLT@orcl> SELECT claim_id, receipt_date FROM medical_claims
  2       ORDER  BY receipt_date DESC LIMIT 20 OFFSET 0;
ORDER  BY receipt_date DESC LIMIT 20 OFFSET 0
                            *
ERROR at line 2:
ORA-00933: SQL command not properly ended

SQLT@orcl> -- 원인 파악: LIMIT 는 Oracle 문법이 아니다. ORDER BY 뒤에 파서가 모르는 토큰이 와서 "문장이 끝나야
SQLT@orcl> --   하는 자리에 다른 것이 있다" 는 오류가 났다. Oracle 12c 부터는 OFFSET n ROWS FETCH NEXT m ROWS ONLY.
SQLT@orcl> -- 조치: 표준 행 제한 절로 쓴다. 바인드 :offs 로 깊이를 바꿔 가며 잰다.
SQLT@orcl> VARIABLE offs NUMBER

--------------------------------------------------------------------------------
-- [2] (조치 전 상태) 1페이지 — OFFSET 0
--------------------------------------------------------------------------------
SQLT@orcl> EXEC :offs := 0
SQLT@orcl> SELECT /*+ GATHER_PLAN_STATISTICS */ claim_id, receipt_date
  2       FROM   medical_claims
  3       ORDER  BY receipt_date DESC
  4       OFFSET :offs ROWS FETCH NEXT 20 ROWS ONLY;

20 rows selected.
(출력 생략)

SQLT@orcl> SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR(NULL, NULL, 'ALLSTATS LAST +MEMSTATS'));

PLAN_TABLE_OUTPUT
--------------------------------------------------------------------------------------------------------
| Id  | Operation                | Name           | Starts | A-Rows |   A-Time   | Buffers | Used-Mem |
--------------------------------------------------------------------------------------------------------
|   0 | SELECT STATEMENT         |                |      1 |     20 |00:00:00.02 |    3090 |          |
|*  1 |  VIEW                    |                |      1 |     20 |00:00:00.02 |    3090 |          |
|*  2 |   WINDOW SORT PUSHED RANK|                |      1 |     20 |00:00:00.02 |    3090 |   2048 (0)|
|   3 |    TABLE ACCESS FULL     | MEDICAL_CLAIMS |      1 |   300K |00:00:00.01 |    3090 |          |
--------------------------------------------------------------------------------------------------------

-- 해석: 인덱스가 있는데 Full Scan 이다 — WHERE 가 없어 30만 행 전부가 대상이라 옵티마이저는 표를 한 번
--   읽고 상위 20건만 골라내는(PUSHED RANK) 쪽을 골랐다. Used-Mem 2K: 상위 20건만 유지하면 되니 작다.

--------------------------------------------------------------------------------
-- [3] (이상 징후 → 원인 → 재확인) 깊은 페이지 — OFFSET 200,000 / 280,000
--------------------------------------------------------------------------------
SQLT@orcl> EXEC :offs := 200000
SQLT@orcl> SELECT /*+ GATHER_PLAN_STATISTICS */ claim_id, receipt_date
  2       FROM   medical_claims ORDER BY receipt_date DESC
  3       OFFSET :offs ROWS FETCH NEXT 20 ROWS ONLY;
(20 rows)
SQLT@orcl> SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR(NULL, NULL, 'ALLSTATS LAST +MEMSTATS'));

PLAN_TABLE_OUTPUT
--------------------------------------------------------------------------------------------------------
|*  2 |   WINDOW SORT PUSHED RANK|                |      1 |    20 |00:00:00.14 |    3090 |    10M (0)|
|   3 |    TABLE ACCESS FULL     | MEDICAL_CLAIMS |      1 |   300K |00:00:00.01 |    3090 |          |
--------------------------------------------------------------------------------------------------------

SQLT@orcl> EXEC :offs := 280000
(같은 SQL 재실행)
SQLT@orcl> SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR(NULL, NULL, 'ALLSTATS LAST +MEMSTATS'));

PLAN_TABLE_OUTPUT
--------------------------------------------------------------------------------------------------------
|*  2 |   WINDOW SORT PUSHED RANK|                |      1 |    20 |00:00:00.18 |    3090 |    14M (0)|
|   3 |    TABLE ACCESS FULL     | MEDICAL_CLAIMS |      1 |   300K |00:00:00.01 |    3090 |          |
--------------------------------------------------------------------------------------------------------

SQLT@orcl> -- 이상 징후: Buffers 는 세 번 다 3,090. "페이지가 깊어져도 비용이 같다" 고 읽기 쉽다.
SQLT@orcl> -- 원인 파악: Full Scan 1회는 OFFSET 과 무관하니 Buffers 가 같은 것이 맞다. 그러나 PUSHED RANK 가
SQLT@orcl> --   유지해야 하는 행 수가 20 → 200,020 → 280,020 으로 늘어 정렬 메모리가 2K → 10M → 14M, 시간이
SQLT@orcl> --   0.02 → 0.14 → 0.18초(9배)다. 비용은 Buffers 가 아니라 CPU·메모리에 쌓였다(Ch09·Ch14 의 교훈).
SQLT@orcl> --   메모리가 PGA 한도를 넘으면 (0) 이 (1) 로 바뀌며 임시 세그먼트 I/O 가 생긴다 — 그때는 Buffers 에도 보인다.
SQLT@orcl> -- 재확인: 세션 통계로도 확인한다 — 'sorts (rows)' 델타가 OFFSET 만큼 늘어난다.
SQLT@orcl> SELECT n.name, s.value FROM v$mystat s, v$statname n
  2       WHERE  s.statistic# = n.statistic# AND n.name IN ('sorts (memory)','sorts (disk)','sorts (rows)');

NAME                        VALUE
---------------------- ----------
sorts (disk)                    0                          -- 0 이면 넘치지 않았다
sorts (memory)           <환경값>
sorts (rows)             <환경값>                           -- 세 번 실행 뒤 델타 ≈ 300K × 3

--   ┌──────────┬─────────┬─────────┬────────────────┐
--   │ OFFSET   │ Buffers │ A-Time  │ Used-Mem       │
--   ├──────────┼─────────┼─────────┼────────────────┤
--   │       0  │  3,090  │ 0.02초  │   2K           │
--   │ 200,000  │  3,090  │ 0.14초  │  10M           │
--   │ 280,000  │  3,090  │ 0.18초  │  14M           │
--   └──────────┴─────────┴─────────┴────────────────┘

-- ※ IX_RECEIPT 는 실습 02·03 에서 계속 쓴다. 지우지 않고 EXIT.

--------------------------------------------------------------------------------
-- [정리]
--------------------------------------------------------------------------------
-- 1) Oracle 의 행 제한은 OFFSET n ROWS FETCH NEXT m ROWS ONLY. LIMIT 는 ORA-00933.
-- 2) OFFSET 페이징은 깊이와 무관하게 표를 한 번 읽지만(3,090), 순위 매김 대상이 OFFSET+20 행이라
--    시간·메모리가 깊이에 비례한다(2K → 14M, 9배).
-- 3) Buffers 만 보면 이 비용이 안 보인다. +MEMSTATS 와 A-Time, sorts 통계로 본다.
-- 4) 인덱스가 있어도 WHERE 가 없으면 옵티마이저는 인덱스를 고르지 않는다 — 실습 02 의 Keyset 이 WHERE 를 만든다.

SQLT@orcl> EXIT
