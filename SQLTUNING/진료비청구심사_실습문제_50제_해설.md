# 진료비 청구 및 심사 시스템 — 실습문제 50제 · 해설 및 모범답안

`진료비청구심사_실습문제_50제.md`와 문제 번호가 1:1로 대응합니다. 모든 SQL은 **Oracle
전통(원본) 조인 문법**만 사용합니다 — `JOIN`, `LEFT JOIN`, `ON` 같은 ANSI SQL:99 구문은
쓰지 않고, `FROM`절에 테이블을 콤마로 나열한 뒤 `WHERE`절에 조인 조건을 적으며, 아우터
조인은 `(+)` 연산자로 표현합니다.

> **데이터 특성 안내**: 이 스키마의 데이터는 `DBMS_RANDOM`으로 대량 생성되어 실행마다 값이
> 달라집니다. 따라서 해설의 "예상 결과"는 정확한 행 단위 계산이 아니라 편중 비율 기반의
> **추정치·구조 설명**이거나, 형식만 보여주는 **예시(실제 값과 다를 수 있음)**입니다.
> DDL/PL/SQL 오브젝트 생성 문항의 "결과"는 쿼리 결과 대신 컴파일/실행 성공 메시지와 예상
> 동작으로 대체합니다.

## Oracle 전통 조인 문법 요약 (첫 등장 시 필독)

| 구분 | ANSI 문법 (사용 안 함) | Oracle 전통 문법 (이 문서에서 사용) |
|---|---|---|
| 내부 조인 | `FROM a JOIN b ON a.id=b.id` | `FROM a, b WHERE a.id = b.id` |
| 왼쪽(외부) 조인 | `FROM a LEFT JOIN b ON a.id=b.id` | `FROM a, b WHERE a.id = b.id(+)` — `(+)`는 **결측(행 없음)을 허용할 쪽**, 즉 b쪽에 붙인다 |
| 조인 + 추가 필터 | `... ON a.id=b.id AND b.col='X'` | `WHERE a.id = b.id(+) AND b.col(+) = 'X'` — 아우터 조인 대상 테이블의 컬럼이면 **필터 조건에도 `(+)`를 붙여야** 결측 행이 보존된다 |

**`(+)` 연산자 제약 (반드시 기억)**
- `(+)`는 조인의 **한쪽에만** 붙일 수 있다. 양쪽에 붙이면 `ORA-01468: a predicate may
  reference only one outer-joined table` 오류가 나며, FULL OUTER JOIN은 이 문법으로 표현
  불가하다(두 쿼리를 `UNION`으로 합쳐야 함).
- `(+)`가 붙은 컬럼은 **서브쿼리·`IN` 리스트·`OR`로 연결된 조건**과 함께 쓸 수 없다.
- 아우터 조인 대상 테이블의 필터 조건에서 `(+)`를 빠뜨리면, 보존됐던 NULL 행이 그 필터에서
  다시 걸러져 결과적으로 INNER JOIN과 동일해진다(대표적 실수).

# Ⅰ. SQL 고급 활용 (1~18번)

## 1. [상] 3-테이블 등가 조인 — 3월 입원 청구

```sql
SELECT h.hosp_name, h.hosp_type, p.pat_name,
       c.claim_id, c.total_amt
FROM   hospitals h, patients p, medical_claims c
WHERE  c.hosp_id = h.hosp_id
AND    c.pat_id  = p.pat_id
AND    c.claim_type = '입원'
AND    c.receipt_date >= DATE '2024-03-01'
AND    c.receipt_date <  DATE '2024-04-01'
ORDER  BY c.total_amt DESC;
```

**예상 결과 (예시이며 실제 값은 다를 수 있음)**

| HOSP_NAME | HOSP_TYPE | PAT_NAME | CLAIM_ID | TOTAL_AMT |
|---|---|---|---|---|
| 서울대형병원1 | 종합병원 | 김환자 | 20240315-0001234 | 3,250,000 |
| ... | ... | ... | ... | ... |

**해설**
- **(a) 사용 개념**: 세 테이블(HOSPITALS, PATIENTS, MEDICAL_CLAIMS)을 콤마로 나열하고
  각 FK 조인 조건(`c.hosp_id=h.hosp_id`, `c.pat_id=p.pat_id`)을 `AND`로 연결한 전형적인
  Oracle 전통 등가 조인. MEDICAL_CLAIMS의 두 FK는 NOT NULL이라 항상 매칭되므로 아우터 조인이
  필요 없는 **내부 조인**이다.
- **(b) 방식 선택 이유**: 날짜 범위 조건을 `receipt_date >= '2024-03-01' AND < '2024-04-01'`로
  쓴 것은, `TO_CHAR(receipt_date,'YYYYMM')='202403'`처럼 컬럼에 함수를 씌우면 **인덱스를
  못 타기 때문**이다(39·41·47번에서 재론). 또한 `BETWEEN '2024-03-01' AND '2024-03-31'`은
  3/31 00:00:00 이후 시각 데이터를 놓칠 수 있어 `< 다음달 1일`이 더 안전하다.
- **(c) 흔한 실수 / ORA**: 세 테이블 중 한 조인 조건을 빠뜨리면 카티션 곱(Cartesian product)이
  발생해 결과가 폭증한다. 조인 조건 개수는 보통 "테이블 수 − 1" 이상이어야 한다.
- **(d) 실무/성능**: 300만건 급 대용량에서는 `receipt_date`에 인덱스가 있어야 3월분만 Range
  Scan으로 빠르게 뽑는다(41번 참조).

## 2. [상] 셀프 조인 — 같은 환자의 두 병원 조합

```sql
SELECT p.pat_name,
       c1.hosp_id AS hosp_a,
       c2.hosp_id AS hosp_b
FROM   medical_claims c1, medical_claims c2, patients p
WHERE  c1.pat_id = c2.pat_id
AND    c1.pat_id = p.pat_id
AND    c1.hosp_id < c2.hosp_id
GROUP  BY p.pat_name, c1.hosp_id, c2.hosp_id
ORDER  BY p.pat_name, hosp_a, hosp_b;
```

**해설**
- **(a) 개념**: 같은 테이블 MEDICAL_CLAIMS에 두 개의 별칭(c1, c2)을 주어 자기 자신과 조인하는
  **셀프 조인(self join)**. 같은 PAT_ID를 공유하되 서로 다른 병원에 청구한 쌍을 찾는다.
- **(b) `c1.hosp_id < c2.hosp_id`의 의미**: 등호가 아닌 부등호 조인 조건을 써서 (A,B)와
  (B,A) 두 방향 중복, 그리고 (A,A) 자기 자신 쌍을 한 번에 제거한다. `!=`만 쓰면 (A,B),(B,A)가
  둘 다 나온다.
- **(c) 흔한 실수**: 조인 키를 빠뜨려 카티션 곱이 되거나, `GROUP BY`(또는 `DISTINCT`) 없이
  쓰면 한 환자가 각 병원에 여러 청구를 낸 경우 같은 병원쌍이 여러 번 중복 출력된다.
- **(d) 실무/성능**: 셀프 조인은 대용량에서 조인 결과가 제곱으로 커질 수 있어 반드시 선행
  필터(예: 특정 기간, 특정 지역)로 대상을 좁히는 것이 안전하다.

## 3. [상] 아우터 조인 + 필터에 `(+)` — 반려 로그 포함 조회

```sql
SELECT c.claim_id, c.review_status, r.error_code
FROM   medical_claims c, review_log r
WHERE  c.claim_id = r.claim_id(+)
AND    r.error_code(+) BETWEEN 'E10' AND 'E99'
AND    c.claim_id LIKE '20240101%'
ORDER  BY c.claim_id;
```

**해설**
- **(a) 개념**: 반려 로그가 없는 청구서도 보존해야 하므로 REVIEW_LOG 쪽에 `(+)`를 붙인
  **왼쪽 아우터 조인**. 핵심은 필터 조건 `r.error_code BETWEEN 'E10' AND 'E99'`에도 `(+)`를
  붙였다는 점이다.
- **(b) 왜 필터에도 `(+)`인가**: `(+)`를 빼고 `AND r.error_code BETWEEN ...`로 쓰면, 아우터
  조인으로 보존됐던 NULL(로그 없는 청구, 정상 로그) 행이 이 조건에서 다시 탈락해 결과가
  INNER JOIN과 같아진다. ANSI에서 `ON`절과 `WHERE`절을 구분하는 것과 동일한 함정이 전통
  문법에서는 "이 조건에 `(+)`를 붙였는가"로 나타난다.
- **(c) ORA / 제약**: `(+)`는 한쪽에만, 서브쿼리·`IN`·`OR`와 함께 못 쓴다(위 요약 참조).
  `WHERE c.claim_id = r.claim_id(+) OR ...`처럼 OR로 묶으면 오류/의도치 않은 동작.
- **(d) 실무**: 한 CLAIM_ID에 반려 로그가 여러 건이면 청구 행이 로그 수만큼 복제된다.
  "반려 여부"만 알면 되는 경우 `EXISTS`가 더 낫다.

## 4. [상] GROUP BY / HAVING — 병원 유형별 집계

```sql
SELECT h.hosp_type,
       COUNT(*)          AS claim_cnt,
       SUM(c.total_amt)  AS sum_amt,
       ROUND(AVG(c.total_amt)) AS avg_amt
FROM   hospitals h, medical_claims c
WHERE  h.hosp_id = c.hosp_id
GROUP  BY h.hosp_type
HAVING COUNT(*) >= 10000
ORDER  BY claim_cnt DESC;
```

**해설**
- **(a) 개념**: 조인 후 GROUP BY로 유형별 집계, 집계 결과에 대한 조건은 `HAVING`.
- **(b) WHERE vs HAVING**: "건수 10,000건 이상"은 그룹화 후에만 알 수 있으므로 HAVING.
  `WHERE COUNT(*)>=10000`은 `ORA-00934: group function is not allowed here` 오류.
- **(c) 흔한 실수**: HAVING에 SELECT 별칭(`claim_cnt`)을 쓰면 `ORA-00904`(별칭은 아직
  미정의). HAVING엔 원식 `COUNT(*)`를 다시 써야 한다. 실행 순서 `FROM→WHERE→GROUP BY→
  HAVING→SELECT→ORDER BY`상 별칭은 SELECT 이후인 ORDER BY에서만 사용 가능.
- **(d) 추정**: 편중상 '의원'이 압도적으로 많고, '종합병원'(1/20)이 대형병원(1~50번)과
  겹쳐 건당 금액이 높을 것으로 예상된다.

## 5. [최상] ROLLUP + GROUPING — 지역/유형별 소계·총계

```sql
SELECT
   CASE WHEN GROUPING(h.city)=1 THEN '★전체합계'
        ELSE h.city END           AS city,
   CASE WHEN GROUPING(h.hosp_type)=1 AND GROUPING(h.city)=0 THEN '  ┗지역합계'
        WHEN GROUPING(h.hosp_type)=1 THEN ' '
        ELSE h.hosp_type END      AS hosp_type,
   COUNT(*)         AS claim_cnt,
   SUM(c.total_amt) AS sum_amt
FROM   hospitals h, medical_claims c
WHERE  h.hosp_id = c.hosp_id
GROUP  BY ROLLUP(h.city, h.hosp_type)
ORDER  BY GROUPING(h.city), h.city, GROUPING(h.hosp_type), h.hosp_type;
```

**해설**
- **(a) 개념**: `ROLLUP(a, b)`는 `(a,b)` 상세 → `(a)` 소계 → `()` 총계 순의 계층 소계를
  자동 생성한다. `GROUPING(col)`은 그 행이 해당 컬럼에 대한 소계 행이면 1, 아니면 0을
  반환해 소계/총계 라벨링에 쓴다.
- **(b) 대안 비교**: `CUBE(a,b)`는 모든 조합 소계(지역별 + 유형별 + 전체)를, `GROUPING
  SETS`는 원하는 소계만 지정. 문제는 "지역>유형" 계층 소계라 `ROLLUP`이 정확히 맞는다.
- **(c) 흔한 실수**: 소계 행에서 `h.city`가 NULL로 나오는데 이를 실제 NULL 데이터와
  혼동. 반드시 `GROUPING()`으로 구분해야 한다. 단순 `NVL(h.city,'합계')`는 원본에 NULL이
  있으면 오판.
- **(d) 실무**: 정렬도 `GROUPING()`을 앞에 두어 소계 행이 각 그룹 끝에 오도록 제어한다.

## 6. [상] 단일행 서브쿼리 — 평균 총액 초과

```sql
SELECT c.claim_id, c.hosp_id, c.total_amt
FROM   medical_claims c
WHERE  c.total_amt > (SELECT AVG(total_amt) FROM medical_claims)
AND    c.receipt_date >= DATE '2024-06-01'
AND    c.receipt_date <  DATE '2024-07-01'
ORDER  BY c.total_amt DESC;
```

**해설**
- **(a) 개념**: `(SELECT AVG(total_amt) FROM medical_claims)`는 정확히 한 행·한 컬럼을
  반환하는 **스칼라(단일행) 서브쿼리**라 `>` 비교에 그대로 쓸 수 있다.
- **(b) 평가 시점**: 상관 서브쿼리가 아니므로 서브쿼리는 **한 번만** 평가되어 상수처럼
  재사용된다. 전체 평균 기준이므로 6월 필터는 바깥 쿼리에만 적용된다(전체 평균 대비 6월의
  고액 청구를 보는 의미).
- **(c) ORA**: 서브쿼리가 여러 행을 반환하는 구조면 `ORA-01427: single-row subquery
  returns more than one row`.
- **(d) 주의**: TOTAL_AMT가 0(미갱신)인 청구가 평균을 낮출 수 있으므로, 정확히 하려면
  서브쿼리에 `WHERE total_amt > 0`을 넣는 것도 고려한다.

## 7. [상] 다중행 서브쿼리 IN — 주사제 포함 청구

```sql
SELECT DISTINCT c.claim_id, h.hosp_name
FROM   medical_claims c, hospitals h
WHERE  c.hosp_id = h.hosp_id
AND    c.receipt_date >= DATE '2024-12-01'
AND    c.receipt_date <  DATE '2025-01-01'
AND    c.claim_id IN (
          SELECT d.claim_id
          FROM   claim_details d, drug_master m
          WHERE  d.drug_code = m.drug_code
          AND    m.category = '주사제'
       );
```

**해설**
- **(a) 개념**: 서브쿼리가 "주사제를 포함한 CLAIM_ID 목록"(여러 행)을 반환하므로 다중행
  연산자 `IN`을 사용.
- **(b) 대안 비교**: 동일 로직을 `EXISTS` 상관 서브쿼리로도 작성 가능하며, 대용량에서
  선택도에 따라 옵티마이저가 세미조인(SEMI JOIN)으로 변환한다. `IN`은 목록 크기가 클 때
  `EXISTS`보다 불리할 수 있으나 옵티마이저가 대개 동등 변환한다.
- **(c) 흔한 실수**: `IN` 서브쿼리 결과에 NULL이 섞여도 `IN`은 안전하지만, `NOT IN`은
  NULL 하나로 전체가 UNKNOWN이 되어 결과가 사라진다(9번 참조). 여기선 `IN`이라 안전.
- **(d) 실무**: `DISTINCT`는 한 청구에 주사제가 여러 건이어도 CLAIM_ID 중복을 막기 위함.

## 8. [최상] 상관 서브쿼리 — 진료과별 최고액 청구

```sql
SELECT c1.dept_code, c1.claim_id, c1.hosp_id, c1.total_amt
FROM   medical_claims c1
WHERE  c1.total_amt = (
          SELECT MAX(c2.total_amt)
          FROM   medical_claims c2
          WHERE  c2.dept_code = c1.dept_code
       )
ORDER  BY c1.dept_code;
```

**해설**
- **(a) 개념**: 안쪽이 바깥 `c1.dept_code`를 참조하는 **상관 서브쿼리**. "그룹의 최댓값"이
  아니라 "그 최댓값을 가진 행 전체(CLAIM_ID 등)"가 필요할 때 쓰는 정석 패턴.
- **(b) 대안 비교**: 분석 함수 `RANK() OVER (PARTITION BY dept_code ORDER BY total_amt
  DESC)=1`로도 가능하며 스캔 1회로 끝나 대용량에서 유리. 상관 서브쿼리는 `c1` 각 행마다
  `c2`를 재평가하므로 DEPT_CODE 인덱스가 없으면 비쌀 수 있다.
- **(c) 동점**: `=` 비교라 최고액이 동점이면 여러 건이 나온다(정상). 1건만 원하면 분석
  함수 `ROW_NUMBER`로 tie-break 규칙을 정해야 한다(16번).
- **(d) 실무**: DEPT_CODE는 D1~D9로 카디널리티 9라, 히스토그램/인덱스 효용이 제한적.

## 9. [최상] NOT EXISTS 안티조인 — 청구 없는 환자

```sql
SELECT p.pat_id, p.pat_name, p.gender, p.ins_type, p.city
FROM   patients p
WHERE  NOT EXISTS (
          SELECT 1
          FROM   medical_claims c
          WHERE  c.pat_id = p.pat_id
       )
ORDER  BY p.pat_id;
```

**해설**
- **(a) 개념**: 청구가 하나도 없는 환자를 찾는 **안티조인**을 `NOT EXISTS`로 구현.
- **(b) 왜 NOT EXISTS인가 (NOT IN과 비교)**: `WHERE p.pat_id NOT IN (SELECT pat_id
  FROM medical_claims)`는 서브쿼리 결과에 NULL이 **하나라도** 있으면 `NOT IN` 전체가
  UNKNOWN이 되어 **결과가 0건**이 된다. MEDICAL_CLAIMS.PAT_ID는 NOT NULL이라 이번엔
  괜찮지만, NULL 허용 컬럼이면 치명적이라 `NOT EXISTS`가 방어적으로 안전하다. 또한
  `NOT EXISTS`는 첫 매칭에서 즉시 중단(단락 평가)돼 대개 더 효율적.
- **(c) 흔한 실수**: 아우터 조인 + `IS NULL`(`WHERE p.pat_id = c.pat_id(+) AND c.pat_id
  IS NULL`)로도 가능하나, 이때 IS NULL 검사는 반드시 조인 키에 걸어야 한다.
- **(d) 결과 규모(근거)**: MEDICAL_CLAIMS 300,000건의 PAT_ID는 1~50,000에 균등 무작위로
  배정되므로 환자 1인당 평균 청구는 300,000 / 50,000 = **6건**이고, 특정 환자에게 한 건도
  배정되지 않을 확률은 (1 − 1/50,000)^300,000 ≈ e⁻⁶ ≈ 0.0025다. 따라서 50,000 × 0.0025 ≈
  **약 120~130명 내외**가 조회된다. 데이터가 `DBMS_RANDOM`으로 생성되어 시드에 따라 정확한
  수는 매번 달라지므로, `SELECT COUNT(*) FROM patients` − `SELECT COUNT(DISTINCT pat_id)
  FROM medical_claims` 값이 이 쿼리의 결과 행 수와 일치하는지로 검산한다.
- **(e) 왜 병원이 아니라 환자인가**: 같은 질문을 HOSPITALS로 던지면 병원당 평균 청구가
  150,000 / 950 ≈ 158건(1~50번 대형병원은 3,000건)이라 0건 병원이 나올 확률이 e⁻¹⁵⁸로
  사실상 0이다. 결과가 항상 0행이면 안티조인을 제대로 썼는지 검증할 수 없으므로, 실제로
  결과가 나오는 PATIENTS를 대상으로 삼는다.

## 10. [상] UNION — 입원 환자 ∪ 의료급여 환자

```sql
SELECT pat_id
FROM   medical_claims
WHERE  claim_type = '입원'
UNION
SELECT pat_id
FROM   patients
WHERE  ins_type = '의료급여'
ORDER  BY pat_id;
```

**해설**
- **(a) 개념**: 두 결과 집합을 `UNION`으로 합치면 자동으로 중복 제거된다.
- **(b) UNION vs UNION ALL**: 중복 제거가 필요 없으면 `UNION ALL`이 정렬/중복제거 연산이
  없어 빠르다. 여기선 "중복 없이"가 요구라 `UNION`.
- **(c) 규칙**: 두 SELECT의 **컬럼 수·타입이 일치**해야 하고, `ORDER BY`는 전체의 맨
  마지막에 한 번만.
- **(d) 실무**: 의료급여는 전체의 약 10%(5,000명), 입원 청구 환자와 일부 겹칠 것이므로
  합집합 크기는 단순 합보다 작을 것으로 추정.

## 11. [상] MINUS — 심사완료지만 자동반려 없는 청구

```sql
SELECT claim_id
FROM   medical_claims
WHERE  review_status = '심사완료'
AND    receipt_date >= DATE '2024-01-01'
AND    receipt_date <  DATE '2024-02-01'
MINUS
SELECT claim_id
FROM   review_log
WHERE  reviewer_id = 'SYSTEM';
```

**해설**
- **(a) 개념**: `A MINUS B` = "A에는 있고 B에는 없는" 집합. 심사완료 청구에서 자동반려
  이력이 있는 청구를 제거.
- **(b) 순서 중요**: `MINUS`는 방향성이 있어 순서를 바꾸면 의미가 완전히 달라진다.
- **(c) 대안**: `WHERE review_status='심사완료' AND NOT EXISTS (SELECT 1 FROM review_log
  WHERE claim_id=c.claim_id AND reviewer_id='SYSTEM')`로도 동일 결과.
- **(d) 실무**: `MINUS`도 내부적으로 정렬/중복제거가 일어난다. 대용량이면 인덱스 유무가
  성능을 좌우.

## 12. [상] INTERSECT — 입원·외래 모두 낸 병원

```sql
SELECT hosp_id FROM medical_claims WHERE claim_type = '입원'
INTERSECT
SELECT hosp_id FROM medical_claims WHERE claim_type = '외래'
ORDER  BY hosp_id;
```

**해설**
- **(a) 개념**: `INTERSECT`는 양쪽 모두에 존재하는 교집합. 입원과 외래를 둘 다 접수한
  병원을 구한다.
- **(b) 대안**: `EXISTS` 이중 상관 서브쿼리, 또는 `GROUP BY hosp_id HAVING COUNT(DISTINCT
  claim_type)>=2`로도 가능. 후자가 대개 스캔 1회로 더 효율적.
- **(c) 규칙**: SET 연산자는 컬럼 구조 일치 필수.
- **(d) 추정**: 대형병원 대부분은 입원·외래를 모두 취급하므로 상당수 병원이 나올 것.
  '약국'은 보통 외래만이라 제외될 가능성.

## 13. [최상] RANK / DENSE_RANK — 병원별 청구 건수 순위

```sql
SELECT hosp_id, claim_cnt,
       RANK()       OVER (ORDER BY claim_cnt DESC) AS rnk,
       DENSE_RANK() OVER (ORDER BY claim_cnt DESC) AS dense_rnk
FROM (
   SELECT hosp_id, COUNT(*) AS claim_cnt
   FROM   medical_claims
   GROUP  BY hosp_id
)
ORDER  BY claim_cnt DESC
FETCH  FIRST 20 ROWS ONLY;
```

**해설**
- **(a) 개념**: 인라인 뷰에서 병원별 건수를 먼저 집계한 뒤, 그 결과에 분석 함수 `RANK`/
  `DENSE_RANK`로 순위를 매긴다.
- **(b) RANK vs DENSE_RANK**: 동점이 있을 때 `RANK`는 다음 순위를 건너뛰고(1,1,3),
  `DENSE_RANK`는 건너뛰지 않는다(1,1,2). 두 값을 나란히 출력해 차이를 확인.
- **(c) 흔한 실수**: 집계(`COUNT`)와 분석 함수를 한 레벨에서 섞으려다 오류. 분석 함수는
  그룹 집계 **이후** 단계이므로 인라인 뷰로 분리하는 것이 명확.
- **(d) 스큐 확인**: HOSP_ID 1~50번(전체의 50% 집중)이 상위 20위를 사실상 독식할 것으로
  예상. 이 편중이 인덱스/히스토그램 설계(13→48번)의 근거다.

## 14. [최상] SUM() OVER / 누적 비중 — 스큐 분석

```sql
SELECT hosp_id, claim_cnt,
       ROUND(RATIO_TO_REPORT(claim_cnt) OVER () * 100, 2)          AS pct,
       ROUND(SUM(claim_cnt) OVER (ORDER BY claim_cnt DESC
                                  ROWS BETWEEN UNBOUNDED PRECEDING
                                  AND CURRENT ROW)
             / SUM(claim_cnt) OVER () * 100, 2)                     AS cum_pct
FROM (
   SELECT hosp_id, COUNT(*) AS claim_cnt
   FROM   medical_claims
   GROUP  BY hosp_id
)
ORDER  BY claim_cnt DESC;
```

**해설**
- **(a) 개념**: `RATIO_TO_REPORT(x) OVER ()`는 전체 합 대비 각 행의 비중을, `SUM(x) OVER
  (ORDER BY ... ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)`는 정렬 순 **누적합**을
  계산한다. 누적합을 전체합으로 나눠 누적 비중(%)을 얻는다.
- **(b) 왜 이 문제가 핵심인가**: 이 스키마의 스큐(1~50번에 50% 집중)를 수치로 증명한다.
  결과를 위에서부터 읽으면 **상위 약 50개 병원에서 누적 비중이 50%에 도달**하고, 나머지
  950개가 나머지 절반을 나눠 갖는 구조가 드러난다.
- **(c) 흔한 실수**: 윈도우 프레임(`ROWS BETWEEN ...`)을 생략하면 `ORDER BY`가 있는
  `SUM() OVER`의 기본 프레임이 `RANGE ... CURRENT ROW`가 되어 동점 처리가 달라질 수 있다.
  누적합은 명시적 `ROWS` 프레임을 쓰는 것이 안전.
- **(d) 실무 함의**: 이런 파레토형 분포에서는 상위 병원 조회가 압도적으로 빈번하므로
  HOSP_ID 인덱스 + 히스토그램이 필수(42·44·48번).

## 15. [상] LAG / LEAD — 월별 청구 증감

```sql
SELECT mon, claim_cnt,
       LAG(claim_cnt)  OVER (ORDER BY mon) AS prev_cnt,
       claim_cnt - LAG(claim_cnt) OVER (ORDER BY mon) AS diff_prev,
       LEAD(claim_cnt) OVER (ORDER BY mon) AS next_cnt
FROM (
   SELECT TO_CHAR(receipt_date, 'YYYYMM') AS mon, COUNT(*) AS claim_cnt
   FROM   medical_claims
   GROUP  BY TO_CHAR(receipt_date, 'YYYYMM')
)
ORDER  BY mon;
```

**해설**
- **(a) 개념**: `LAG`는 이전 행, `LEAD`는 다음 행 값을 현재 행으로 끌어온다. 시계열 증감
  분석의 표준 도구.
- **(b) 대안**: 셀프 조인(전월 데이터를 조인)으로도 가능하나 코드가 장황하고 첫 달 처리가
  번거롭다. `LAG`/`LEAD`가 훨씬 간결.
- **(c) 흔한 실수**: 1월의 `LAG`, 12월의 `LEAD`는 참조 대상이 없어 NULL. 필요하면
  `LAG(claim_cnt, 1, 0)`처럼 기본값 지정. 또 `ORDER BY mon`을 문자열로 하므로 'YYYYMM'
  형식이라 사전순=시간순이 보장됨(정렬 안정성).
- **(d) 실무**: 접수일이 2024년 전체 균등 분포라 월별 건수는 대체로 평탄할 것으로 추정.

## 16. [상] ROW_NUMBER — 병원별 최고액 1건

```sql
SELECT hosp_id, claim_id, total_amt
FROM (
   SELECT hosp_id, claim_id, total_amt,
          ROW_NUMBER() OVER (PARTITION BY hosp_id
                             ORDER BY total_amt DESC, claim_id ASC) AS rn
   FROM   medical_claims
)
WHERE  rn = 1
ORDER  BY hosp_id;
```

**해설**
- **(a) 개념**: `ROW_NUMBER() OVER (PARTITION BY hosp_id ORDER BY ...)`로 병원별 순번을
  매기고 `rn=1`만 남기는 **Top-1-per-group** 패턴.
- **(b) RANK와 차이**: `ROW_NUMBER`는 동점이어도 유일한 번호를 부여해 정확히 1건만 뽑힌다.
  `RANK`를 쓰면 동점 시 여러 건. tie-break를 위해 `ORDER BY total_amt DESC, claim_id ASC`로
  결정적 순서를 지정.
- **(c) 흔한 실수**: 분석 함수는 `WHERE`절에서 직접 못 쓴다(`WHERE ROW_NUMBER()...`는
  `ORA-30483`). 반드시 인라인 뷰로 감싼 뒤 바깥에서 `rn=1`.
- **(d) 실무**: 대용량에서 이 패턴은 8번의 상관 서브쿼리보다 스캔 1회로 효율적.

## 17. [상] TOP-N + 뷰 — 최고액 상위 10건

```sql
-- 방법 1: 인라인 뷰 + ROWNUM
SELECT *
FROM (
   SELECT claim_id, hosp_id, total_amt
   FROM   medical_claims
   ORDER  BY total_amt DESC
)
WHERE  ROWNUM <= 10;

-- 방법 2: FETCH FIRST (12c 이상)
SELECT claim_id, hosp_id, total_amt
FROM   medical_claims
ORDER  BY total_amt DESC
FETCH  FIRST 10 ROWS ONLY;

-- 뷰 생성
CREATE OR REPLACE VIEW v_top10_claims AS
SELECT claim_id, hosp_id, total_amt
FROM (
   SELECT claim_id, hosp_id, total_amt
   FROM   medical_claims
   ORDER  BY total_amt DESC
)
WHERE  ROWNUM <= 10;
```

**결과**: `뷰가 생성되었습니다.` (View V_TOP10_CLAIMS created.)

**해설**
- **(a) 개념**: `ROWNUM`은 정렬 **전** 부여되므로, 반드시 정렬을 끝낸 인라인 뷰를 바깥에서
  잘라야 한다. `SELECT ... WHERE ROWNUM<=10 ORDER BY ...`(한 문장)는 임의 10건을 먼저
  뽑고 정렬하는 **대표적 오답**.
- **(b) FETCH FIRST**: 12c부터 이 함정 없이 간결하게 Top-N을 표현. `WITH TIES`를 붙이면
  10위 동점을 모두 포함.
- **(c) ORA**: 뷰 정의에 `ORDER BY`가 있으면 옵티마이저가 뷰 병합 시 순서를 보장 안 할
  수 있어, ROWNUM 필터를 뷰 안에 함께 두어 Top-N을 확정.
- **(d) 실무**: `v_top10_claims`는 조회 시마다 재평가되는 논리 뷰. 자주 쓰면 결과를
  캐시하는 MATERIALIZED VIEW를 고려.

## 18. [최상] BIRTH_DATE 연령대 통계 + 시퀀스

```sql
SELECT age_band,
       COUNT(*)                                   AS pat_cnt,
       SUM(CASE WHEN gender='M' THEN 1 ELSE 0 END) AS male_cnt,
       SUM(CASE WHEN gender='F' THEN 1 ELSE 0 END) AS female_cnt
FROM (
   SELECT gender,
          FLOOR( ( TO_NUMBER(TO_CHAR(DATE '2024-12-31','YYYYMMDD'))
                   - TO_NUMBER(birth_date) ) / 10000 )      AS age,
          CASE
            WHEN FLOOR((TO_NUMBER(TO_CHAR(DATE '2024-12-31','YYYYMMDD'))
                        - TO_NUMBER(birth_date))/10000) >= 80 THEN '80대 이상'
            ELSE TO_CHAR(FLOOR(FLOOR((TO_NUMBER(TO_CHAR(DATE '2024-12-31','YYYYMMDD'))
                        - TO_NUMBER(birth_date))/10000)/10)*10) || '대'
          END                                               AS age_band
   FROM   patients
   WHERE  birth_date IS NOT NULL
   AND    LENGTH(birth_date) = 8
)
GROUP  BY age_band
ORDER  BY age_band;

-- 시퀀스 생성
CREATE SEQUENCE seq_pat_id
   START WITH 50001
   INCREMENT BY 1
   CACHE 20
   NOCYCLE;
```

**결과**: 연령대별 집계 결과(예시), 그리고 `시퀀스가 생성되었습니다.`

**해설**
- **(a) 개념**: 만 나이를 `(기준일 YYYYMMDD − 생일 YYYYMMDD)/10000`의 정수부로 계산하는
  기법. YYYYMMDD를 숫자로 만들어 빼면 만 나이가 자연스럽게 나온다(월/일 보정 자동). 이는
  BIRTH_DATE가 문자열이라 `MONTHS_BETWEEN`보다 간명한 방식.
- **(b) 대안**: `TRUNC(MONTHS_BETWEEN(기준일, TO_DATE(birth_date,'YYYYMMDD'))/12)`도
  가능. 다만 문자열→날짜 변환(`TO_DATE`)이 들어가 잘못된 날짜(예: '20240230')면
  `ORA-01839` 위험. 숫자 연산 방식은 그 위험이 없다.
- **(c) 흔한 실수**: 연령대 라벨을 만들 때 `FLOOR(age/10)*10 || '대'`를 쓰되 80대 이상을
  하나로 묶는 처리를 빼먹기 쉽다. 또 잘못된 형식의 BIRTH_DATE 방어를 위해 `LENGTH=8` 필터.
- **(d) 시퀀스**: `CACHE 20`은 성능(메모리 선점)과 트레이드오프로, 인스턴스 재시작/롤백
  시 번호 구멍(gap)이 생길 수 있음을 인지해야 한다. PK 채번엔 gap이 문제 없음.

## 19. [상] 익명 블록 — 변수/제어문/SELECT INTO

```sql
SET SERVEROUTPUT ON;
DECLARE
   v_claim_id  medical_claims.claim_id%TYPE := '20240315-0001234';
   v_amt       medical_claims.total_amt%TYPE;
   v_grade     VARCHAR2(20);
BEGIN
   SELECT total_amt INTO v_amt
   FROM   medical_claims
   WHERE  claim_id = v_claim_id;

   IF v_amt >= 1000000 THEN
      v_grade := '고액청구';
   ELSIF v_amt >= 100000 THEN
      v_grade := '일반청구';
   ELSE
      v_grade := '소액청구';
   END IF;

   DBMS_OUTPUT.PUT_LINE(v_claim_id || ' → ' || v_amt || '원 (' || v_grade || ')');
EXCEPTION
   WHEN NO_DATA_FOUND THEN
      DBMS_OUTPUT.PUT_LINE('해당 청구접수번호가 존재하지 않습니다: ' || v_claim_id);
END;
/
```

**예상 출력**: `20240315-0001234 → 1250000원 (고액청구)` (값은 예시)

**해설**
- **(a) 개념**: `%TYPE`로 컬럼과 동일 타입 선언(스키마 변경에 강함), `SELECT ... INTO`로
  단일 행을 변수에 담고, `IF/ELSIF/ELSE`로 분기.
- **(b) 방식 선택**: 리터럴 대신 `%TYPE`을 쓰면 컬럼 타입이 바뀌어도 코드 수정 불필요.
- **(c) ORA**: `SELECT INTO`가 0건이면 `NO_DATA_FOUND`, 2건 이상이면 `TOO_MANY_ROWS`.
  PK 조회라 후자는 없지만 전자는 반드시 처리.
- **(d) 실무**: `SET SERVEROUTPUT ON` 없으면 `DBMS_OUTPUT`이 화면에 안 보인다(자주 하는 실수).

## 20. [상] 익명 블록 — 반복문(FOR LOOP)

```sql
SET SERVEROUTPUT ON;
DECLARE
   v_cnt    NUMBER;
   v_total  NUMBER := 0;
BEGIN
   FOR mm IN 1 .. 12 LOOP
      SELECT COUNT(*) INTO v_cnt
      FROM   medical_claims
      WHERE  hosp_id = 1
      AND    receipt_date >= ADD_MONTHS(DATE '2024-01-01', mm-1)
      AND    receipt_date <  ADD_MONTHS(DATE '2024-01-01', mm);

      v_total := v_total + v_cnt;
      DBMS_OUTPUT.PUT_LINE('2024-' || LPAD(mm,2,'0') || '월: ' || v_cnt || '건');
   END LOOP;
   DBMS_OUTPUT.PUT_LINE('연간 합계: ' || v_total || '건');
END;
/
```

**해설**
- **(a) 개념**: `FOR mm IN 1..12` 숫자 루프. 루프 카운터로 월 경계를 `ADD_MONTHS`로 생성.
- **(b) 방식 선택**: 월별 경계를 문자열 조작 대신 `ADD_MONTHS`로 만들면 윤년·월말 걱정
  없이 정확. `receipt_date >= 시작 AND < 다음달`은 인덱스 친화적 범위 조건.
- **(c) 흔한 실수**: 루프 안에서 12번 쿼리를 도는 것은 학습용. 실무에선 `GROUP BY
  TO_CHAR(receipt_date,'MM')` 한 방이 훨씬 효율적(루프 내 반복 SQL은 컨텍스트 스위치 비용).
- **(d) 실무**: 대량 반복 SQL은 성능 안티패턴 — 38번의 BULK 기법과 대조.

## 21. [상] 명시적 커서 + %ROWTYPE

```sql
SET SERVEROUTPUT ON;
DECLARE
   CURSOR c_claims IS
      SELECT claim_id, hosp_id, total_amt
      FROM   medical_claims
      WHERE  review_status = '심사중'
      AND    ROWNUM <= 100
      ORDER  BY receipt_date;
   v_row  c_claims%ROWTYPE;
BEGIN
   OPEN c_claims;
   LOOP
      FETCH c_claims INTO v_row;
      EXIT WHEN c_claims%NOTFOUND;
      DBMS_OUTPUT.PUT_LINE(v_row.claim_id || ' / ' || v_row.hosp_id
                           || ' / ' || v_row.total_amt);
   END LOOP;
   CLOSE c_claims;
END;
/
```

**해설**
- **(a) 개념**: 명시적 커서 `OPEN-FETCH-EXIT WHEN %NOTFOUND-CLOSE`의 정석 루프. `c_claims%ROWTYPE`은
  커서 SELECT 목록 구조에 맞춘 레코드 타입.
- **(b) 왜 %ROWTYPE**: 개별 변수 여러 개 대신 레코드 하나로 받아 유지보수 용이. 커서 컬럼이
  바뀌어도 자동 반영.
- **(c) 흔한 실수**: `EXIT WHEN c_claims%NOTFOUND`를 FETCH **뒤**에 두어야 마지막 행 중복
  처리를 막는다. `ROWNUM <= 100`과 `ORDER BY`를 함께 쓰면 정렬 전 100건이 잘리므로,
  "접수일 순 상위 100건"을 정확히 원하면 인라인 뷰로 정렬 후 ROWNUM을 적용해야 한다(여기선
  단순화).
- **(d) 실무**: 명시적 커서는 세밀한 제어가 필요할 때. 단순 순회는 22번 FOR LOOP가 안전.

## 22. [상] CURSOR FOR LOOP

```sql
SET SERVEROUTPUT ON;
BEGIN
   FOR rec IN (
      SELECT h.hosp_type, COUNT(*) AS cnt
      FROM   hospitals h, medical_claims c
      WHERE  h.hosp_id = c.hosp_id
      GROUP  BY h.hosp_type
      ORDER  BY cnt DESC
   ) LOOP
      DBMS_OUTPUT.PUT_LINE('유형: ' || rec.hosp_type || ', 건수: ' || rec.cnt);
   END LOOP;
END;
/
```

**해설**
- **(a) 개념**: `FOR rec IN (SELECT ...)` — 커서를 암시적으로 OPEN/FETCH/CLOSE하며 레코드
  `rec`를 자동 선언.
- **(b) 왜 더 안전한가**: OPEN/CLOSE를 수동 관리하지 않아 **CLOSE 누락으로 인한 커서 누수
  (ORA-01000: maximum open cursors exceeded)** 위험이 없고, 예외 발생 시에도 자동 정리된다.
- **(c) 흔한 실수**: 루프 밖에서 `rec`를 참조하려 하면 스코프 밖이라 컴파일 오류.
- **(d) 실무**: 대량 행을 이 방식으로 한 줄씩 처리하면 느리다 — 그럴 땐 BULK COLLECT(38번).

## 23. [최상] 파라미터 커서

```sql
SET SERVEROUTPUT ON;
DECLARE
   CURSOR c_by_hosp (p_hosp_id NUMBER, p_min_amt NUMBER) IS
      SELECT claim_id, total_amt
      FROM   medical_claims
      WHERE  hosp_id = p_hosp_id
      AND    total_amt >= p_min_amt;
   v_cnt NUMBER;

   PROCEDURE count_it(p_h NUMBER, p_m NUMBER) IS
   BEGIN
      v_cnt := 0;
      FOR r IN c_by_hosp(p_h, p_m) LOOP
         v_cnt := v_cnt + 1;
      END LOOP;
      DBMS_OUTPUT.PUT_LINE('병원 ' || p_h || ', 최소 ' || p_m
                           || '원 이상 청구: ' || v_cnt || '건');
   END;
BEGIN
   count_it(1, 500000);
   count_it(2, 1000000);
END;
/
```

**해설**
- **(a) 개념**: 커서에 파라미터를 선언해 OPEN(또는 FOR LOOP) 시점에 다른 인자를 넘겨
  **하나의 커서 정의를 여러 조건으로 재사용**한다.
- **(b) 왜 파라미터 커서**: 조건만 다른 유사 커서를 여러 개 만들 필요 없이 한 정의로 재활용.
  바인드처럼 동작해 SQL 공유풀 재사용에도 유리.
- **(c) 흔한 실수**: 파라미터에 기본값을 안 주고 인자 없이 열면 오류. 필요하면 `(p_min_amt
  NUMBER DEFAULT 0)`.
- **(d) 실무**: 위처럼 로컬 프로시저로 감싸 반복 호출 구조를 만들면 코드가 깔끔.

## 24. [상] 사용자 정의 예외

```sql
SET SERVEROUTPUT ON;
DECLARE
   v_claim_id  medical_claims.claim_id%TYPE := '20240315-0001234';
   v_amt       medical_claims.total_amt%TYPE;
   e_unposted_amount EXCEPTION;
BEGIN

END;
/
```

**해설**
- **(a) 개념**: `EXCEPTION` 타입 변수를 선언하고 `RAISE`로 발생, `WHEN 예외명 THEN`으로

  전파하려면 25번의 `RAISE_APPLICATION_ERROR`로 호출자에게 코드를 전달.
- **(d) 실무**: 이 스키마 설정상 TOTAL_AMT=0은 "아직 CLAIM_DETAILS로 사후 갱신 안 됨"을
  뜻하므로, 배치(38번)로 채우기 전 조회 시 흔히 마주치는 상태.

## 25. [상] RAISE_APPLICATION_ERROR

```sql
CREATE OR REPLACE PROCEDURE sp_validate_hosp(p_hosp_id NUMBER) IS
   v_status hospitals.status%TYPE;
BEGIN
   SELECT status INTO v_status FROM hospitals WHERE hosp_id = p_hosp_id;

   IF v_status = '폐업' THEN
      RAISE_APPLICATION_ERROR(-20002, '폐업한 요양기관에는 청구를 접수할 수 없습니다.');
   END IF;
   DBMS_OUTPUT.PUT_LINE('접수 가능한 요양기관입니다.');
EXCEPTION
   WHEN NO_DATA_FOUND THEN
      RAISE_APPLICATION_ERROR(-20001, '존재하지 않는 요양기관입니다.');
END;
/
```

**해설**
- **(a) 개념**: `RAISE_APPLICATION_ERROR(에러번호, 메시지)`로 호출자에게 커스텀 오류를
  전파. 번호는 반드시 **-20000 ~ -20999** 범위.
- **(b) 왜 이 방식**: 사용자 정의 예외(24번)는 PL/SQL 내부 전용이지만, `RAISE_APPLICATION_ERROR`는
  애플리케이션(JDBC 등)까지 SQLCODE/SQLERRM으로 전달돼 클라이언트가 처리 가능.
- **(c) ORA**: 범위를 벗어난 번호(예: -19999)를 쓰면 `ORA-21000: error number argument
  to raise_application_error out of range`.
- **(d) 실무**: 존재 여부 검사에 `NO_DATA_FOUND`를 활용하는 것이 `SELECT COUNT(*)` 후
  IF 검사보다 간결.

## 26. [최상] 예외 처리 종합 — 계층적 처리 + 재던지기

```sql
CREATE OR REPLACE PROCEDURE sp_post_amt_safe(p_claim_id VARCHAR2) IS
   v_sum   medical_claims.total_amt%TYPE;
   e_no_detail EXCEPTION;
BEGIN
   SELECT SUM(amt) INTO v_sum
   FROM   claim_details WHERE claim_id = p_claim_id;

   IF v_sum IS NULL THEN
      RAISE e_no_detail;              -- 상세내역 자체가 없음
   END IF;

   UPDATE medical_claims SET total_amt = v_sum WHERE claim_id = p_claim_id;
   COMMIT;
EXCEPTION
   WHEN e_no_detail THEN
      RAISE_APPLICATION_ERROR(-20010, '상세내역이 없어 금액을 계산할 수 없습니다: '
                              || p_claim_id);
   WHEN NO_DATA_FOUND THEN
      DBMS_OUTPUT.PUT_LINE('데이터 없음');
   WHEN TOO_MANY_ROWS THEN
      DBMS_OUTPUT.PUT_LINE('단일행 조회에 다중행 반환');
   WHEN OTHERS THEN
      INSERT INTO review_log(log_id, claim_id, reviewer_id, process_date,
                             action_msg, error_code)
      VALUES (seq_log_id.NEXTVAL, p_claim_id, 'SYSTEM', SYSDATE,
              'SQLERR:' || SQLCODE || ':' || SUBSTR(SQLERRM,1,200), 'E99');
      COMMIT;
      RAISE;   -- 로깅 후 예외를 호출자에게 다시 전파
END;
/
```

**해설**
- **(a) 개념**: 여러 `WHEN` 절을 구체적인 것부터 나열하고 마지막에 `WHEN OTHERS`. `SQLCODE`
  (오류 번호)·`SQLERRM`(오류 메시지)으로 원인을 기록.
- **(b) 로깅 후 RAISE**: `WHEN OTHERS`에서 로그만 남기고 예외를 삼키면(silent) 호출자가
  실패를 모른 채 진행하는 위험. `RAISE`로 다시 던져 상위가 인지·롤백하도록 한다. 로그
  INSERT는 별도로 COMMIT(자율 트랜잭션이면 더 확실 — `PRAGMA AUTONOMOUS_TRANSACTION`).
- **(c) ORA/실수**: `WHEN OTHERS THEN NULL;`은 최악의 안티패턴(오류 은폐). `SQLERRM`은
  최대 512바이트라 컬럼 길이에 맞춰 `SUBSTR`.
- **(d) 실무**: 로깅용 시퀀스 `seq_log_id`가 REVIEW_LOG의 LOG_ID 채번에 필요(PK 없어도
  식별용). 로그 기록은 자율 트랜잭션으로 분리하면 본 트랜잭션 롤백에도 로그는 남는다.

- **(d) 실무**: 화면 출력용이라 `DBMS_OUTPUT` 사용. 값을 프로그램이 받아야 하면 28번의

## 28. [상] 저장 프로시저 — IN/OUT 파라미터

```sql
CREATE OR REPLACE PROCEDURE sp_claim_stat(
   p_hosp_id IN  NUMBER,
   p_cnt     OUT NUMBER,
   p_sum     OUT NUMBER,
   p_avg     OUT NUMBER) IS
BEGIN
   SELECT COUNT(*), NVL(SUM(total_amt),0), NVL(ROUND(AVG(total_amt)),0)
   INTO   p_cnt, p_sum, p_avg
   FROM   medical_claims
   WHERE  hosp_id = p_hosp_id;
END;
/

-- 호출 블록
SET SERVEROUTPUT ON;
DECLARE
   v_c NUMBER; v_s NUMBER; v_a NUMBER;
BEGIN
   sp_claim_stat(1, v_c, v_s, v_a);
   DBMS_OUTPUT.PUT_LINE('건수=' || v_c || ', 합계=' || v_s || ', 평균=' || v_a);
END;
/
```

**해설**
- **(a) 개념**: `OUT` 파라미터로 여러 값을 호출자에게 반환. 한 번의 스캔으로 COUNT/SUM/AVG를
  동시에 구해 효율적.
- **(b) 왜 함수 대신 프로시저**: 함수는 보통 값 하나를 반환. 여러 값을 돌려주려면 OUT
  파라미터를 가진 프로시저(또는 레코드/컬렉션 반환)가 적합.
- **(c) 흔한 실수**: `NVL`을 빼면 청구 0건인 병원에서 SUM/AVG가 NULL로 반환. 호출부 변수는
  반드시 초기화 불필요하나 선언 필수.
- **(d) 실무**: OUT 파라미터는 호출 전 값이 무시되고 호출 후 채워진다. IN OUT은 입력값을
  받아 수정 후 반환할 때.

## 29. [최상] 저장 프로시저 — TOTAL_AMT 사후 갱신

```sql
CREATE OR REPLACE PROCEDURE sp_post_total_amt(
   p_claim_id IN  VARCHAR2,
   p_new_amt  OUT NUMBER,
   p_rows     OUT NUMBER) IS
   v_sum NUMBER;
BEGIN
   SELECT SUM(amt) INTO v_sum
   FROM   claim_details WHERE claim_id = p_claim_id;

   IF v_sum IS NULL THEN
      RAISE_APPLICATION_ERROR(-20010, '상세내역이 없습니다: ' || p_claim_id);
   END IF;

   UPDATE medical_claims SET total_amt = v_sum WHERE claim_id = p_claim_id;
   p_rows    := SQL%ROWCOUNT;
   p_new_amt := v_sum;

   INSERT INTO review_log(log_id, claim_id, reviewer_id, process_date,
                          action_msg, error_code)
   VALUES (seq_log_id.NEXTVAL, p_claim_id, 'SYSTEM', SYSDATE, '금액 재계산 완료', NULL);

   COMMIT;
EXCEPTION
   WHEN OTHERS THEN
      ROLLBACK;
      RAISE;
END;
/
```

**해설**
- **(a) 개념**: 상세 합계 계산 → UPDATE → 로그 INSERT를 한 트랜잭션으로 묶고 `SQL%ROWCOUNT`로
  처리 행 수를 OUT 반환.
- **(b) 원자성**: UPDATE와 로그 INSERT가 함께 성공/실패해야 하므로 정상 시 `COMMIT`,
  예외 시 `ROLLBACK` 후 `RAISE`. 부분 반영을 막는다.
- **(c) ORA/실수**: 상세가 없으면 SUM이 NULL → -20010으로 명확히 실패시킴. NULL을
  그대로 UPDATE하면 TOTAL_AMT가 NULL이 되어 이후 집계 왜곡.
- **(d) 실무**: 이 로직을 36번 트리거로 자동화하면 애플리케이션이 명시 호출할 필요가
  줄지만, 대량 배치 갱신은 38번 BULK 방식이 빠르다.

## 30. [상] 저장 함수 — 만 나이 계산

```sql
CREATE OR REPLACE FUNCTION fn_get_age(p_birth VARCHAR2)
RETURN NUMBER
DETERMINISTIC IS
   v_age NUMBER;
BEGIN
   IF p_birth IS NULL OR LENGTH(p_birth) <> 8 THEN
      RETURN NULL;
   END IF;
   v_age := FLOOR( (TO_NUMBER(TO_CHAR(SYSDATE,'YYYYMMDD')) - TO_NUMBER(p_birth)) / 10000 );
   RETURN v_age;
EXCEPTION
   WHEN VALUE_ERROR THEN      -- TO_NUMBER 변환 실패(숫자 아님)
      RETURN NULL;
END;
/
```

**해설**
- **(a) 개념**: YYYYMMDD 숫자 차이/10000의 정수부로 만 나이 산출(18번과 동일 로직을 함수화).
- **(b) 방어 로직**: NULL·길이 불일치·비숫자 입력을 모두 NULL로 방어. `VALUE_ERROR`로
  `TO_NUMBER` 실패를 포착.
- **(c) DETERMINISTIC**: 같은 입력에 항상 같은 결과이므로 `DETERMINISTIC` 선언 — 함수 기반
  인덱스(43번)에 활용 가능하고 옵티마이저 캐싱에 유리. 단, 기준일이 SYSDATE라 엄밀히는
  날짜가 바뀌면 결과가 달라지므로 FBI 대상으로 삼을 땐 기준일을 인자로 받는 편이 안전.
- **(d) 실무**: SQL에서 대량 호출되면 함수 컨텍스트 스위치 비용 발생 — 31번 참조.

## 31. [상] SQL 문 내 함수 호출

```sql
SELECT pat_id, pat_name, birth_date, fn_get_age(birth_date) AS age
FROM   patients
WHERE  fn_get_age(birth_date) >= 65
ORDER  BY age DESC;
```

**해설**
- **(a) 개념**: 저장 함수를 SELECT 목록과 WHERE 조건에서 직접 호출.
- **(b) 제약(순수성/WNPS)**: SQL에서 호출되는 함수는 부작용이 없어야 한다. `WNDS`(no DB
  writes), `RNPS/WNPS`(패키지 상태 미변경) 규칙을 위반하면 예측 불가/오류. `INSERT/UPDATE`를
  하는 함수를 SELECT에서 호출하면 `ORA-14551: cannot perform a DML operation inside a
  query`.
- **(c) 성능 함정**: `WHERE fn_get_age(birth_date) >= 65`는 컬럼에 함수를 씌운 꼴이라
  일반 인덱스를 못 탄다 → **함수 기반 인덱스**(43번)가 필요. 또 행마다 PL/SQL을 호출하는
  컨텍스트 스위치 비용이 크다.
- **(d) 대안**: 순수 SQL 표현식으로 바꿔 인라인하면(함수 없이 직접 계산) 컨텍스트 스위치가
  사라진다. 12c의 `WITH FUNCTION` 인라인 정의도 방법.

## 32. [최상] 패키지 — 스펙 + 바디 분리

```sql
-- 스펙
CREATE OR REPLACE PACKAGE pkg_claim IS
   FUNCTION  get_claim_count(p_hosp_id NUMBER) RETURN NUMBER;
   FUNCTION  get_claim_sum(p_hosp_id NUMBER)   RETURN NUMBER;
   PROCEDURE print_stat(p_hosp_id NUMBER);
END pkg_claim;
/

-- 바디
CREATE OR REPLACE PACKAGE BODY pkg_claim IS
   FUNCTION get_claim_count(p_hosp_id NUMBER) RETURN NUMBER IS
      v NUMBER;
   BEGIN
      SELECT COUNT(*) INTO v FROM medical_claims WHERE hosp_id = p_hosp_id;
      RETURN v;
   END;

   FUNCTION get_claim_sum(p_hosp_id NUMBER) RETURN NUMBER IS
      v NUMBER;
   BEGIN
      SELECT NVL(SUM(total_amt),0) INTO v FROM medical_claims WHERE hosp_id = p_hosp_id;
      RETURN v;
   END;

   PROCEDURE print_stat(p_hosp_id NUMBER) IS
   BEGIN
      DBMS_OUTPUT.PUT_LINE('병원 ' || p_hosp_id
         || ' | 건수=' || get_claim_count(p_hosp_id)
         || ' | 총액=' || get_claim_sum(p_hosp_id));
   END;
END pkg_claim;
/
-- 호출: EXEC pkg_claim.print_stat(1);
```

**해설**
- **(a) 개념**: **스펙**(공개 인터페이스)과 **바디**(구현)를 분리. 스펙만 안정적으로 유지하면
  바디를 바꿔도 의존 객체 재컴파일 영향이 적다.
- **(b) 왜 패키지**: 관련 함수/프로시저를 논리적으로 묶고, 바디 내부에서 서로 호출(예:
  `print_stat`이 다른 함수 재사용). 캡슐화·성능(메모리 로드 단위) 이점.
- **(c) 흔한 실수**: 스펙에 선언한 서브프로그램을 바디에 구현 안 하면 `PLS-00323`. 시그니처
  불일치도 오류.
- **(d) 실무**: 스펙에 없는 바디 전용 프로시저는 패키지 내부에서만 쓰는 private 루틴.

## 33. [상] 패키지 상태 변수(세션 유지)

```sql
CREATE OR REPLACE PACKAGE pkg_counter IS
   PROCEDURE increment;
   FUNCTION  get_value RETURN NUMBER;
   PROCEDURE reset;
END pkg_counter;
/
CREATE OR REPLACE PACKAGE BODY pkg_counter IS
   g_cnt NUMBER := 0;                 -- 패키지 상태 변수
   PROCEDURE increment IS BEGIN g_cnt := g_cnt + 1; END;
   FUNCTION  get_value RETURN NUMBER IS BEGIN RETURN g_cnt; END;
   PROCEDURE reset IS BEGIN g_cnt := 0; END;
END pkg_counter;
/
```

**동작 예시**
```sql
EXEC pkg_counter.increment;
EXEC pkg_counter.increment;
-- SELECT pkg_counter.get_value FROM dual;  → 2
```

**해설**
- **(a) 개념**: 바디에 선언한 `g_cnt`는 **패키지 상태 변수**로, 한 **세션 안에서** 값이
  유지된다(호출 간 지속).
- **(b) 세션 스코프**: 세션이 처음 패키지를 참조할 때 초기화되고 세션 종료까지 유지.
  다른 세션은 각자의 사본을 갖는다(공유 아님).
- **(c) 함정**: 상태 변수는 SQL에서 호출되는 함수의 순수성(WNPS)을 깨뜨릴 수 있어, 그런
  함수를 SELECT에서 쓰면 결과가 비결정적이 될 수 있다. 또 `DBMS_SESSION.RESET_PACKAGE`나
  패키지 재컴파일 시 상태가 초기화(`ORA-04068`)될 수 있다.
- **(d) 실무**: 세션 캐시·카운터·설정값 보관에 유용하나, RAC/커넥션 풀 환경에선 세션
  재사용으로 예상 밖 값이 남을 수 있어 주의.

## 34. [최상] 패키지 종합 — 심사 처리 + 초기화 블록

```sql
CREATE OR REPLACE PACKAGE pkg_review IS
   PROCEDURE review_claim(p_claim_id VARCHAR2, p_reviewer_id VARCHAR2);
   PROCEDURE reject_claim(p_claim_id VARCHAR2, p_error_code VARCHAR2);
END pkg_review;
/
CREATE OR REPLACE PACKAGE BODY pkg_review IS
   g_started TIMESTAMP;               -- 상태 변수: 세션 처리 시작 시각

   PROCEDURE review_claim(p_claim_id VARCHAR2, p_reviewer_id VARCHAR2) IS
   BEGIN
      UPDATE medical_claims SET review_status = '심사완료'
      WHERE  claim_id = p_claim_id;

      INSERT INTO review_log(log_id, claim_id, reviewer_id, process_date,
                             action_msg, error_code)
      VALUES (seq_log_id.NEXTVAL, p_claim_id, p_reviewer_id, SYSDATE,
              '심사 처리 완료', NULL);
      COMMIT;
   END;

   PROCEDURE reject_claim(p_claim_id VARCHAR2, p_error_code VARCHAR2) IS
   BEGIN
      INSERT INTO review_log(log_id, claim_id, reviewer_id, process_date,
                             action_msg, error_code)
      VALUES (seq_log_id.NEXTVAL, p_claim_id, 'SYSTEM', SYSDATE,
              '자동 심사 반려', p_error_code);
      COMMIT;
   END;
BEGIN
   g_started := SYSTIMESTAMP;         -- 패키지 초기화 블록(세션 최초 참조 시 1회 실행)
END pkg_review;
/
```

**해설**
- **(a) 개념**: 바디 맨 아래 `BEGIN ... END`는 **패키지 초기화 블록**으로, 세션이 패키지를
  처음 참조할 때 딱 한 번 실행된다. 여기서 상태 변수 `g_started`를 세팅.
- **(b) 설계 의도**: `review_claim`은 정상 처리(상태 변경 + EMP 로그), `reject_claim`은
  자동 반려(SYSTEM 로그 + Exx 코드) — 데이터 편중 설정(정상 30만/반려 20만 로그)을 그대로
  반영한 업무 시나리오.
- **(c) 흔한 실수**: 각 프로시저 내부 `COMMIT`은 즉시 확정이라 상위 트랜잭션과 경계가
  분리됨. 호출자가 트랜잭션을 통제하려면 프로시저에서 COMMIT을 빼는 설계도 고려.
- **(d) 실무**: 초기화 블록 예외는 `ORA-04068`/`ORA-06508`로 이어질 수 있어 가볍게 유지.

## 35. [상] 행 레벨 트리거 — AMT 자동 계산

```sql
CREATE OR REPLACE TRIGGER trg_claim_detail_amt
BEFORE INSERT OR UPDATE ON claim_details
FOR EACH ROW
BEGIN
   :NEW.amt := NVL(:NEW.unit_price,0) * NVL(:NEW.qty,0) * NVL(:NEW.days,0);
END;
/
```

**동작 시나리오**: `INSERT INTO claim_details(... unit_price=1000, qty=2, days=3, amt=999)`을
실행해도, 트리거가 `amt`를 1000*2*3=6000으로 덮어써서 저장한다.

**해설**
- **(a) 개념**: `BEFORE ... FOR EACH ROW` 트리거에서 `:NEW`를 수정하면 그 값이 실제 저장된다.
- **(b) 왜 BEFORE**: 값을 저장 전에 바꿔야 하므로 `BEFORE`. `AFTER`에서는 `:NEW` 수정이
  반영되지 않는다.
- **(c) 흔한 실수**: `AFTER` 트리거에서 `:NEW := ...`를 시도하면 `ORA-04084: cannot change
  NEW values for this trigger type`. NULL 곱셈으로 AMT가 NULL이 되지 않도록 `NVL` 방어.
- **(d) 실무**: 계산 컬럼 강제는 트리거 대신 **가상 컬럼**(`amt GENERATED ALWAYS AS
  (unit_price*qty*days)`)으로도 가능하며 오버헤드가 더 적다. 다만 가상 컬럼은 물리 저장이
  안 돼 요건에 따라 선택.

## 36. [최상] 복합 트리거 — TOTAL_AMT 재계산 + 뮤테이팅 회피

```sql
CREATE OR REPLACE TRIGGER trg_recalc_total
FOR INSERT OR UPDATE OR DELETE ON claim_details
COMPOUND TRIGGER

   TYPE t_ids IS TABLE OF medical_claims.claim_id%TYPE INDEX BY PLS_INTEGER;
   g_ids   t_ids;
   g_seen  VARCHAR2(32767);           -- 중복 방지용 마커(간이)

   AFTER EACH ROW IS
   BEGIN
      IF INSERTING OR UPDATING THEN
         g_ids(g_ids.COUNT+1) := :NEW.claim_id;
      END IF;
      IF UPDATING OR DELETING THEN
         g_ids(g_ids.COUNT+1) := :OLD.claim_id;
      END IF;
   END AFTER EACH ROW;

   AFTER STATEMENT IS
   BEGIN
      FOR i IN 1 .. g_ids.COUNT LOOP
         UPDATE medical_claims m
         SET    m.total_amt = (SELECT NVL(SUM(d.amt),0)
                               FROM   claim_details d
                               WHERE  d.claim_id = g_ids(i))
         WHERE  m.claim_id = g_ids(i);
      END LOOP;
   END AFTER STATEMENT;

END trg_recalc_total;
/
```

**해설**
- **(a) 뮤테이팅 문제**: 단순 행 레벨 `AFTER EACH ROW` 트리거에서 변경 중인 CLAIM_DETAILS를
  다시 `SELECT SUM(amt)`하면 **ORA-04091: table CLAIM_DETAILS is mutating, trigger/function
  may not see it** 오류가 난다.
- **(b) 회피 설계(복합 트리거)**: 12c의 `COMPOUND TRIGGER` 하나로 (1) `AFTER EACH ROW`에서
  영향받은 CLAIM_ID를 컬렉션에 모으고, (2) `AFTER STATEMENT`에서 그 CLAIM_ID들에 대해서만
  합계를 다시 계산해 UPDATE한다. 문장 완료 후 시점이라 CLAIM_DETAILS가 더 이상 뮤테이팅
  상태가 아니다.
- **(c) 대안**: 11g 이전 방식은 "패키지 컬렉션 + 행 레벨 트리거(수집) + 문장 레벨 트리거
  (반영)" 3분할. 복합 트리거는 이를 한 객체로 통합한 것.
- **(d) 실무 주의**: 대량 DML 시 영향 CLAIM_ID가 많으면 문장 트리거 루프가 비쌀 수 있어,
  중복 제거(같은 CLAIM_ID 한 번만) 및 배치 UPDATE 최적화가 필요. 또 재귀 트리거 방지를
  위해 이 트리거가 MEDICAL_CLAIMS를 갱신할 뿐 CLAIM_DETAILS를 다시 건드리지 않도록 설계.

## 37. [상] 문장 레벨 트리거 — 삭제 감사 로그

```sql
CREATE OR REPLACE TRIGGER trg_claim_audit
AFTER DELETE ON medical_claims
BEGIN
   INSERT INTO review_log(log_id, claim_id, reviewer_id, process_date,
                          action_msg, error_code)
   VALUES (seq_log_id.NEXTVAL, NULL, USER, SYSDATE,
           '청구 삭제 이벤트 발생 (' || TO_CHAR(SYSDATE,'YYYY-MM-DD HH24:MI:SS') || ')',
           NULL);
END;
/
```

**해설**
- **(a) 개념**: `FOR EACH ROW`가 없으면 **문장 레벨 트리거** — DELETE 문장당 1회 발동
  (삭제 행 수와 무관).
- **(b) 왜 문장 레벨**: "삭제 이벤트가 일어났다"는 사실만 1건 남기면 되므로 행 레벨은
  불필요(오히려 대량 삭제 시 로그 폭증). 개별 행 값이 필요 없으니 문장 레벨이 적합.
- **(c) 흔한 실수**: 문장 레벨에선 `:OLD/:NEW`를 쓸 수 없다(참조 시 `ORA-04082`). 개별
  행 정보가 필요하면 행 레벨이나 복합 트리거를 써야 한다.
- **(d) 실무**: `USER`로 실행 계정 기록, 삭제 행 수까지 남기려면 `SQL%ROWCOUNT`는 트리거
  안에서 못 쓰므로 복합 트리거의 카운터로 집계.

## 38. [최상] BULK COLLECT + FORALL — 대량 금액 갱신

```sql
DECLARE
   CURSOR c_target IS
      SELECT claim_id FROM medical_claims WHERE total_amt = 0;

   TYPE t_id  IS TABLE OF medical_claims.claim_id%TYPE;
   TYPE t_amt IS TABLE OF NUMBER;
   v_ids  t_id;
   v_sums t_amt;
BEGIN
   OPEN c_target;
   LOOP
      FETCH c_target BULK COLLECT INTO v_ids LIMIT 5000;   -- 배치 5000건
      EXIT WHEN v_ids.COUNT = 0;

      -- 각 CLAIM_ID의 상세 합계 계산
      v_sums := t_amt();
      v_sums.EXTEND(v_ids.COUNT);
      FOR i IN 1 .. v_ids.COUNT LOOP
         SELECT NVL(SUM(amt),0) INTO v_sums(i)
         FROM   claim_details WHERE claim_id = v_ids(i);
      END LOOP;

      -- 일괄 UPDATE
      FORALL i IN 1 .. v_ids.COUNT
         UPDATE medical_claims SET total_amt = v_sums(i)
         WHERE  claim_id = v_ids(i);

      COMMIT;
      EXIT WHEN c_target%NOTFOUND;
   END LOOP;
   CLOSE c_target;
END;
/
```

**해설**
- **(a) 개념**: `BULK COLLECT ... LIMIT n`으로 여러 행을 컬렉션에 한 번에 담고, `FORALL`로
  DML을 한 번에 엔진에 넘긴다. 행 단위 루프 대비 **PL/SQL ↔ SQL 엔진 컨텍스트 스위치**를
  대폭 줄여 대용량에서 수 배~수십 배 빠르다.
- **(b) 왜 LIMIT**: `LIMIT` 없이 전체를 한 번에 BULK COLLECT하면 수십만 건이 PGA 메모리에
  올라가 `ORA-04030`(메모리 부족) 위험. 5000건씩 배치로 나눠 메모리와 UNDO를 통제.
- **(c) 흔한 실수**: `FORALL`은 단일 DML만 반복(그 안에 임의 PL/SQL 로직 불가). 합계 계산은
  별도 루프에서 미리 수행. 예외 시 부분 실패를 추적하려면 `SAVE EXCEPTIONS` + `SQL%BULK_EXCEPTIONS`.
- **(d) 실무 대안**: 사실 이 특정 갱신은 상관 서브쿼리 하나로 **순수 SQL** 처리하는 것이
  가장 빠르다:
  ```sql
  UPDATE medical_claims m
  SET    total_amt = (SELECT NVL(SUM(amt),0) FROM claim_details d
                      WHERE d.claim_id = m.claim_id)
  WHERE  m.total_amt = 0;
  ```
  BULK/FORALL은 행별 추가 로직(로깅·검증)이 섞일 때 진가를 발휘한다. "가능하면 SQL 한 방,
  안 되면 BULK, 최후에 행 루프"가 성능 원칙.

## 39. [상] EXPLAIN PLAN / DBMS_XPLAN — 범위 검색 계획 확인

```sql
EXPLAIN PLAN FOR
SELECT * FROM medical_claims
WHERE  receipt_date BETWEEN DATE '2024-03-01' AND DATE '2024-03-31';

SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY);
```

**예상 계획 (인덱스 없을 때, 예시)**
```
| Id | Operation         | Name           | Rows | Cost |
|  0 | SELECT STATEMENT  |                | ~25K |  ... |
|  1 |  TABLE ACCESS FULL| MEDICAL_CLAIMS | ~25K |  높음 |
```

**해설**
- **(a) 개념**: `EXPLAIN PLAN FOR`는 실제 실행 없이 예상 계획을 PLAN_TABLE에 저장하고,
  `DBMS_XPLAN.DISPLAY`로 보기 좋게 출력.
- **(b) 무엇을 확인**: (1) **접근 경로** — `TABLE ACCESS FULL`이면 인덱스 미사용, (2)
  **Rows(예상 카디널리티)** — 옵티마이저 추정치가 실제와 큰 차이면 통계/히스토그램 문제,
  (3) **Cost**, (4) 조인 방식.
- **(c) 흔한 실수**: `EXPLAIN PLAN`은 **예상**이라 실제와 다를 수 있다. 실측은 `AUTOTRACE`
  (40번)나 `DBMS_XPLAN.DISPLAY_CURSOR(format=>'ALLSTATS LAST')`로 A-Rows(실제 행)와 비교.
- **(d) 진단**: 2024년 균등 분포라 3월분은 전체의 약 1/12(약 25,000건). 이 정도 선택도면
  인덱스 Range Scan이 유리할 수 있어 41번으로 이어진다.

## 40. [최상] AUTOTRACE — 실측 통계 비교

```sql
SET AUTOTRACE ON
SET TIMING ON

-- (A)
SELECT hosp_id, COUNT(*) FROM medical_claims GROUP BY hosp_id;
-- (B)
SELECT COUNT(*) FROM medical_claims WHERE hosp_id = 1;
```

**해설**
- **(a) 개념**: `SET AUTOTRACE ON`은 실행 후 실행계획 + 통계(`consistent gets`(논리 읽기),
  `physical reads`, `sorts` 등)를 함께 보여준다.
- **(b) 두 쿼리 비교**: (A)는 전체 집계라 어차피 **FULL SCAN**이 최적(모든 병원 필요).
  (B)는 특정 HOSP_ID=1(대형병원, 전체의 약 1~2%)만 필요 → 인덱스가 있으면 **INDEX RANGE
  SCAN**이 유리할 수 있다.
- **(c) 스큐 + 히스토그램**: HOSP_ID=1은 대형병원이라 매우 많은 행(수천~수만), HOSP_ID=999
  같은 소형은 극소수다. **히스토그램이 없으면** 옵티마이저는 "1,000개 병원에 균등 분포"로
  가정해 HOSP_ID=1의 카디널리티를 `전체행/1000`으로 **과소추정** → 인덱스가 유리하다 오판할
  수 있다. 히스토그램이 있으면 HOSP_ID=1이 실제로 많다는 걸 알고 **FULL SCAN**을 택할 수도
  있다(같은 컬럼이라도 값에 따라 다른 계획 = 바인드 변수 peeking / adaptive).
- **(d) 실무**: `consistent gets`가 계획 우열의 핵심 지표. 실행시간(TIMING)은 캐시 상태에
  좌우되므로 논리 읽기로 판단.

## 41. [상] 단일 인덱스 설계 — RECEIPT_DATE Range Scan

```sql
CREATE INDEX idx_claims_rcpt ON medical_claims(receipt_date);

-- 통계 갱신 후 재확인
EXEC DBMS_STATS.GATHER_TABLE_STATS(USER, 'MEDICAL_CLAIMS');
```

**Before/After 실행계획(예시)**
```
Before: TABLE ACCESS FULL  MEDICAL_CLAIMS   (전체 300만건 스캔)
After : TABLE ACCESS BY INDEX ROWID BATCHED MEDICAL_CLAIMS
          INDEX RANGE SCAN  IDX_CLAIMS_RCPT  (3월분 ~25K건만)
```

**해설**
- **(a) 개념**: `receipt_date`는 **범위 조건(BETWEEN)**의 대상이므로 B-Tree 인덱스의 **INDEX
  RANGE SCAN**에 이상적. 정렬된 인덱스에서 시작~끝 리프만 스캔.
- **(b) 왜 이 컬럼**: 접수일이 2024년 균등 분포라 특정 월/일 조회의 선택도가 충분히 낮아
  (전체의 소수%) 인덱스가 FULL SCAN을 이긴다.
- **(c) 임계 선택도**: 조회 범위가 넓어 전체의 대략 5~10%를 넘으면 오히려 FULL SCAN이
  나을 수 있다(테이블 랜덤 액세스 비용 > 순차 읽기). 3월 한 달(약 8%)은 경계선이라
  실측 필요.
- **(d) 실무**: `SELECT *`라 인덱스 조회 후 테이블 랜덤 액세스가 불가피. 필요 컬럼만 뽑으면
  커버링 인덱스(포함 컬럼)로 테이블 액세스를 없앨 수도 있다.

## 42. [최상] 복합 인덱스 컬럼 순서

```sql
-- 권장안
CREATE INDEX idx_claims_multi
   ON medical_claims(hosp_id, review_status, receipt_date);
```

**해설**
- **(a) 컬럼 순서 원칙**: (1) **등가(=) 조건 컬럼을 앞, 범위(BETWEEN) 컬럼을 뒤**에 둔다.
  범위 컬럼 뒤의 컬럼은 인덱스 정렬성을 활용 못 하기 때문. 쿼리는 `hosp_id=:h`(등가),
  `review_status='심사중'`(등가), `receipt_date BETWEEN`(범위)이므로 등가 둘을 앞, 범위를
  맨 뒤로.
- **(b) 후보 비교**:
  - `(hosp_id, review_status, receipt_date)` ← 권장. 등가 2개로 좁힌 뒤 날짜 범위 스캔.
  - `(receipt_date, hosp_id, ...)` ← 선두가 범위라 뒤 컬럼 정렬성 상실, 등가 필터를 인덱스
    스캔 단계에서 못 걸러 비효율.
  - `(review_status, ...)` ← 선두 카디널리티가 2로 너무 낮아(심사중 10%) 선두로 부적합.
- **(c) 선택도/스큐 고려**: `hosp_id`는 스큐가 크지만 등가 조건이라 특정 값의 선택도가
  중요. 대형병원(1~50)은 값 자체 행이 많아 선택도가 나빠질 수 있어, 그런 경우 날짜 범위가
  더 앞서 걸러주는 게 나을 수도 있다 → 실제 바인드 값 분포로 검증.
- **(d) 실무**: 복합 인덱스는 선두 컬럼이 없는 쿼리엔 못 쓰이므로(또는 비효율 skip scan),
  대표 쿼리 패턴에 맞춰 설계. 인덱스가 많아지면 DML 부담이 커지는 트레이드오프.

## 43. [최상] 함수 기반 인덱스 — 출생연도 추출

```sql
-- FBI: 출생연도(문자 4자리)를 인덱싱
CREATE INDEX idx_pat_birthyear
   ON patients( SUBSTR(birth_date, 1, 4) );

-- 이 인덱스를 타려면 쿼리도 동일 식을 써야 한다
SELECT pat_id, pat_name
FROM   patients
WHERE  SUBSTR(birth_date, 1, 4) <= TO_CHAR(EXTRACT(YEAR FROM SYSDATE) - 60);
```

**해설**
- **(a) 개념**: BIRTH_DATE가 문자열이라 `WHERE SUBSTR(birth_date,1,4)...`처럼 컬럼에 함수를
  씌우면 일반 인덱스는 못 탄다. **함수 기반 인덱스(FBI)**는 그 함수식 자체를 인덱싱해 해결.
- **(b) 정의식 = 쿼리식 일치 필수**: FBI는 인덱스 정의에 쓴 식과 **정확히 동일한 식**이
  쿼리 WHERE에 나타나야 사용된다. `SUBSTR(birth_date,1,4)`로 만들었으면 쿼리도 같은 SUBSTR을
  써야 한다.
- **(c) 제약**: FBI에 쓰는 함수는 **결정적(DETERMINISTIC)**이어야 한다. `SYSDATE` 같은
  비결정적 함수는 인덱스 식에 직접 못 쓴다(그래서 나이 대신 출생연도를 인덱싱하고, 비교
  대상 연도는 쿼리 쪽에서 SYSDATE로 계산). 사용자 정의 함수를 FBI에 쓰려면 `DETERMINISTIC`
  선언 필요(30번의 `fn_get_age`).
- **(d) 실무**: FBI 생성 후 `DBMS_STATS`로 통계 재수집해야 옵티마이저가 가상 컬럼 통계를
  얻는다. 안 하면 카디널리티 오판.

## 44. [최상] B-Tree vs 비트맵 + 히스토그램 필요성

**해설(설계·판단형)**

- **(a) 카디널리티 낮은 컬럼의 인덱스 딜레마**: REVIEW_STATUS(2종), GENDER(2종),
  CLAIM_TYPE(2종)은 값 종류가 매우 적어 **일반 B-Tree 단일 인덱스는 대개 무익**하다(한 값이
  전체의 절반~90%를 가리켜 선택도가 나쁘면 옵티마이저가 FULL SCAN 선택).
- **(b) 비트맵 인덱스의 장점**: 저카디널리티 컬럼에 비트맵 인덱스는 저장 효율이 높고,
  여러 저카디널리티 조건을 **비트 AND/OR로 결합**하는 데 매우 강하다(예: `gender='F' AND
  claim_type='입원' AND review_status='심사중'`).
- **(c) OLTP에서 비트맵이 위험한 이유**: MEDICAL_CLAIMS는 청구 접수/심사로 **DML이 빈번한
  OLTP** 테이블이다. 비트맵 인덱스는 한 비트맵 조각이 다수 행을 커버하므로, 한 행을 갱신해도
  **비트맵 조각 전체에 락**이 걸려 동시 DML 성능이 급락하고 데드락 위험이 커진다. 그래서
  비트맵은 주로 **읽기 위주 DW/배치** 환경에 적합하고, OLTP에는 부적절하다. → MEDICAL_CLAIMS엔
  비트맵보다 복합 B-Tree(42번)나 선별적 인덱스가 안전.
- **(d) 히스토그램이 필요한 이유(스큐)**: REVIEW_STATUS는 '심사중' 10% / '심사완료' 90%로
  **편중**돼 있다. 히스토그램이 없으면 옵티마이저는 "값 2종 = 각 50%"로 균등 가정해
  `review_status='심사중'`의 카디널리티를 실제(10%)보다 **과대추정**(50%)해 인덱스 대신
  FULL SCAN을 택할 수 있다. **빈도수 히스토그램(frequency histogram)**을 만들면 '심사중'이
  10%임을 알고 인덱스 사용을 올바르게 판단한다. HOSP_ID(1~50에 50% 집중)는 값이 많아
  **Top-Frequency/Height-Balanced/Hybrid 히스토그램**이 필요(48번).

## 45. [상] RANGE 파티셔닝 — RECEIPT_DATE 월 단위

```sql
CREATE TABLE medical_claims_part (
   claim_id      VARCHAR2(20) NOT NULL,
   hosp_id       NUMBER(10)   NOT NULL,
   pat_id        NUMBER(10)   NOT NULL,
   receipt_date  DATE,
   visit_date    DATE,
   dept_code     VARCHAR2(10),
   claim_type    VARCHAR2(20),
   total_amt     NUMBER(12),
   review_status VARCHAR2(20)
)
PARTITION BY RANGE (receipt_date) (
   PARTITION p_2024_01 VALUES LESS THAN (DATE '2024-02-01'),
   PARTITION p_2024_02 VALUES LESS THAN (DATE '2024-03-01'),
   PARTITION p_2024_03 VALUES LESS THAN (DATE '2024-04-01'),
   -- ... 04 ~ 11 ...
   PARTITION p_2024_12 VALUES LESS THAN (DATE '2025-01-01'),
   PARTITION p_max     VALUES LESS THAN (MAXVALUE)
);
```

**해설**
- **(a) 개념**: `PARTITION BY RANGE(receipt_date)`로 접수월별 물리 분할. 각 파티션은
  독립적으로 저장·관리된다.
- **(b) 파티션 키 선정 근거**: 조회가 대부분 **접수일 범위**로 이뤄지고(월별 리포트,
  기간 정산), 데이터도 시간순으로 증가하므로 RECEIPT_DATE가 최적. 키가 조회·적재 패턴과
  일치해야 프루닝(47번)과 관리 이점을 얻는다.
- **(c) MAXVALUE 파티션**: 범위를 벗어난(미래/오류) 날짜를 받는 안전판. 없으면 범위 밖
  INSERT가 `ORA-14400: inserted partition key does not map to any partition`.
- **(d) 관리 이점**: 오래된 달은 `ALTER TABLE ... DROP PARTITION p_2024_01`로 즉시 삭제
  (DELETE보다 훨씬 빠르고 UNDO 없음), 파티션 단위 백업/압축/이관 가능. 실무에선 다음 절의
  **인터벌 파티션**으로 월 파티션 자동 생성을 권장.

## 46. [최상] 로그성 테이블 파티셔닝 — REVIEW_LOG

```sql
-- 인터벌 파티션: 월 파티션 자동 생성
CREATE TABLE review_log_part (
   log_id       NUMBER(15),
   claim_id     VARCHAR2(20),
   reviewer_id  VARCHAR2(20),
   process_date DATE DEFAULT SYSDATE,
   action_msg   VARCHAR2(500),
   error_code   VARCHAR2(10)

PARTITION BY RANGE (process_date)
INTERVAL (NUMTOYMINTERVAL(1,'MONTH')) (
   PARTITION p_start VALUES LESS THAN (DATE '2024-01-01')

-- 로컬 인덱스(파티션별 독립 인덱스)
CREATE INDEX idx_rlog_claim ON review_log_part(claim_id) LOCAL;
```

**해설**

  기간 기준 파티셔닝이 조회·보관정책(retention) 관리에 최적.
- **(b) INTERVAL의 이점**: `INTERVAL (NUMTOYMINTERVAL(1,'MONTH'))`은 새 달 데이터가

- **(c) 관리(TRUNCATE/DROP)**: 보존기간(예: 13개월) 초과 파티션을 `ALTER TABLE ... DROP/
  TRUNCATE PARTITION`으로 즉시 정리 — 대량 DELETE의 UNDO/REDO 폭증과 인덱스 단편화를 피한다.
- **(d) 로컬 인덱스**: 로그성 테이블은 파티션 추가/삭제가 잦으므로 **LOCAL 인덱스**(파티션과
  1:1)가 관리에 유리. 글로벌 인덱스는 파티션 DROP 시 무효화(rebuild 필요)되어 로그엔
  부적합. CLAIM_ID로 특정 청구의 로그를 찾는 조회를 위해 LOCAL 인덱스를 둔다.

```sql
EXPLAIN PLAN FOR
SELECT COUNT(*) FROM medical_claims_part

SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY);
```

**예상 계획(예시)**
```
| Id | Operation             | Name              | Pstart | Pstop |
|  1 | PARTITION RANGE SINGLE|                   |   6    |   6   |   ← 6월 파티션만!
|  2 |  TABLE ACCESS FULL    | MEDICAL_CLAIMS_PART|  6    |   6   |
```

- **(b) 확인 방법**: 실행계획의 **`Pstart`/`Pstop`** 컬럼을 본다. `6/6`(또는 `KEY/KEY`)이면

  전 파티션 스캔. 반드시 키 컬럼을 **가공하지 않은 채** 범위 비교해야 한다. 바인드 변수면
  런타임 프루닝(`Pstart=KEY`).
- **(d) 실무**: 45·46번 파티셔닝의 실효는 이 프루닝에서 나온다. 프루닝 없는 파티셔닝은
  관리 이점만 있고 조회 성능 이점은 없다.

## 48. [상] DBMS_STATS — 통계/히스토그램 수집

```sql
-- HOSP_ID(스큐 심함)에 히스토그램 집중 수집
BEGIN
   DBMS_STATS.GATHER_TABLE_STATS(
      ownname          => USER,
      tabname          => 'MEDICAL_CLAIMS',
      method_opt       => 'FOR COLUMNS SIZE 254 HOSP_ID, SIZE 2 REVIEW_STATUS',
      estimate_percent => DBMS_STATS.AUTO_SAMPLE_SIZE,
      cascade          => TRUE);          -- 인덱스 통계도 함께
END;
/
```

**해설**
- **(a) 개념**: `DBMS_STATS.GATHER_TABLE_STATS`로 테이블/컬럼/인덱스 통계를 수집. 옵티마이저는
  이 통계로 카디널리티·비용을 추정한다.
- **(b) method_opt / SIZE**: `FOR COLUMNS SIZE n col`에서 `n`은 히스토그램 버킷 수. `SIZE
  254`(최대)는 값 분포를 세밀히 반영 → 스큐가 큰 HOSP_ID에 적합. `SIZE 1`은 히스토그램
  없음(균등 가정), `SIZE 2`는 REVIEW_STATUS(2종) 빈도 히스토그램에 충분. `SIZE AUTO`는
  Oracle이 컬럼 사용 이력(SYS.COL_USAGE$) 기반으로 자동 판단.
- **(c) 왜 필요(스큐)**: 히스토그램이 없으면 HOSP_ID=1(대형)과 =999(소형)를 같은 선택도로
  오판(44번). 히스토그램으로 값별 실제 빈도를 알아야 대형병원 조회는 FULL SCAN, 소형병원
  조회는 인덱스처럼 **값에 맞는 계획**을 세운다.
- **(d) AUTO와 차이**: 야간 자동 통계 작업(`AUTO_STATS_JOB`)은 변경량이 큰 객체만 갱신하고
  method_opt도 자동. 스큐를 반드시 잡아야 하는 핵심 테이블은 위처럼 **수동으로 히스토그램을
  명시**하는 것이 안전. 대량 적재/삭제 직후엔 즉시 재수집 권장.

## 49. [최상] 힌트 — LEADING / USE_NL / INDEX / FULL

```sql
SELECT /*+ LEADING(h) USE_NL(c) INDEX(c idx_claims_multi) INDEX(h pk_hospitals) */
       c.claim_id, h.hosp_name
FROM   medical_claims c, hospitals h
WHERE  c.hosp_id = h.hosp_id
AND    h.city = '서울'
AND    c.review_status = '심사중';
```

**해설**
- **(a) 각 힌트의 의미**:
  - `LEADING(h)` — 조인 순서에서 HOSPITALS를 **선행(구동) 테이블**로. 서울 병원(약 400곳)이
    먼저 걸러지도록.
  - `USE_NL(c)` — HOSPITALS 각 행에 대해 MEDICAL_CLAIMS를 **Nested Loop**로 조인.
  - `INDEX(c idx_claims_multi)` — MEDICAL_CLAIMS 접근에 특정 인덱스 사용 강제.
  - `FULL(x)` — 반대로 인덱스 무시하고 전체 스캔 강제(대량 매칭 시 유리).
- **(b) 언제 타당한가(시나리오)**: 선행 테이블 결과가 작고(서울 병원 소수), 각 병원당
  '심사중' 청구가 소수라 인덱스로 콕 집는 게 유리하면 `LEADING + USE_NL + INDEX` 조합이
  맞는다. 반대로 매칭 행이 대량이면 `USE_HASH` + `FULL`이 낫다.
- **(c) 흔한 실수**: 힌트에 **잘못된 별칭/인덱스명**을 쓰면 오류 없이 **조용히 무시**된다
  (힌트는 구문상 주석). 별칭을 반드시 쿼리와 일치시키고, `DBMS_XPLAN`의 `Note` 섹션에서
  힌트 적용 여부를 확인해야 한다.
- **(d) 실무**: 힌트는 진단·검증 도구로 먼저 쓰고(계획 비교), 영구 고정은 신중히 — 50번의
  위험성 참조.

## 50. [최상] 힌트 남용의 위험성 + 근본 튜닝

**해설(정책·판단형)**

- **(a) 힌트가 독이 되는 이유**:
  1. **데이터 분포 변화에 취약** — `INDEX` 힌트로 특정 인덱스를 고정하면, 나중에 데이터가
     늘어 FULL SCAN이 유리해져도 옵티마이저가 더 나은 계획으로 못 바꾼다. 힌트가 **옵티마이저의
     적응 능력을 봉인**한다.
  2. **통계 갱신·버전 업그레이드와 충돌** — 통계가 정확해지거나 옵티마이저가 개선돼도
     힌트가 낡은 계획을 강제해 성능이 **오히려 퇴보**.
  3. **스키마 변경 시 무효화** — 힌트에 박은 인덱스명이 바뀌거나 삭제되면 조용히 무시되어
     예상과 다른 계획이 나온다.
  4. **바인드 변수/스큐와 상호작용** — 한 바인드 값엔 좋은 힌트가 다른 값(대형병원 vs
     소형병원)엔 최악일 수 있다.
- **(b) 근본 튜닝을 우선하는 이유**:
  - **통계·히스토그램 정비(48번)** — 옵티마이저가 스스로 옳은 계획을 세우게 하는 것이
    가장 지속 가능. 스큐엔 히스토그램이 힌트보다 근본적.
  - **인덱스 재설계(41·42·43번)** — 쿼리 패턴에 맞는 인덱스가 있으면 힌트 없이도 최적
    계획 유도.
  - **SQL Plan Baseline / SQL Profile** — 검증된 좋은 계획을 힌트처럼 **선언적으로 고정**하되,
    더 나은 계획이 나오면 검증 후 진화하도록 관리(하드코딩 힌트보다 안전).
- **(c) 힌트가 정당화되는 예외**: (1) 옵티마이저 버그를 임시 우회, (2) 통계로도 못 잡는
  특수 분포에서 검증된 계획을 단기 고정, (3) 배치 전용 쿼리에서 병렬(`PARALLEL`)을 명시적
  지정, (4) 튜닝 진단 중 여러 계획을 강제 비교. 이 경우도 **주석으로 이유·기한을 남기고**
  주기적으로 재검토해야 한다.
- **(d) 원칙 요약**: "힌트는 최후의 수단, 통계·인덱스·베이스라인이 먼저." 힌트로 증상을
  덮기 전에 **왜 옵티마이저가 틀렸는가**(통계 부재? 히스토그램 부재? 인덱스 부재?)를 먼저
  규명하는 것이 성능 튜닝의 정도(正道)다.
