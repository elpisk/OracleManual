 제12장 실습 05 — 파라미터 세 분류 실측
 대상   : rac1
 목표   : 반드시 같아야 하는 것, 반드시 달라야 하는 것, 같은 것이 권장되는 것을
          양 노드 대조로 확인하고 관리 원칙을 세운다
 소요   : 약 20분
 선행   : racdb 양 노드 OPEN
 계정   : oracle

--------------------------------------------------------------------------------
 [1] 세 분류
--------------------------------------------------------------------------------

--  분류            예                                        이유
--  -------------  ----------------------------------------  --------------------
--  반드시 같아야   db_name, db_block_size, control_files,     다르면 같은 DB 로
--                 cluster_database, compatible               동작할 수 없다
--  반드시 달라야   instance_number, thread, undo_tablespace   같으면 두 인스턴스가
--                                                            충돌한다
--  같은 것이 권장  sga_target, processes, open_cursors,       달라도 동작하지만
--                 pga_aggregate_target                       예측이 어려워진다
--
-- 이 틀이 이 장에서 가장 오래 쓸 도구다.
-- 파라미터를 개별로 외우는 것이 아니라 어느 분류인지로 판단한다.

--------------------------------------------------------------------------------
 [2] 양 노드 대조 — 피벗으로 한 화면에
--------------------------------------------------------------------------------

--   cluster_database, compatible, control_files, db_block_size,
--   db_name, db_unique_name, undo_management
--
-- 다른 것 (반드시 달라야 하는 분류 + instance_name)
--   instance_name, instance_number, thread, undo_tablespace

--------------------------------------------------------------------------------
 [3] undo_management 와 undo_tablespace
--------------------------------------------------------------------------------

-- 이름이 비슷한 두 파라미터가 서로 다른 분류에 속한다.
--
--   undo_management  = AUTO  → 두 인스턴스가 같다 (반드시 같아야)
--   undo_tablespace  = UNDOTBS1 / UNDOTBS2 → 다르다 (반드시 달라야)
--
-- 방식은 공통이고 대상만 인스턴스별이다.
-- 두 인스턴스 모두 자동 UNDO 관리를 쓰지만 각자 자기 UNDO 테이블스페이스를
-- 쓴다. 같은 것을 쓰면 UNDO 세그먼트를 두고 다투게 된다.
--
-- 이름이 비슷하다고 같은 분류라고 짐작하면 안 된다는 사례다.

--------------------------------------------------------------------------------
 [4] control_files 가 완전히 같은지 확인
--------------------------------------------------------------------------------

SQL> select count(distinct value) from gv$parameter where name='control_files';

  COUNT(DISTINCT VALUE)
-----------------------
                      1

1 row selected.

-- 1 이면 두 인스턴스의 값이 완전히 같다는 뜻이다.
-- [2] 의 피벗은 눈으로 비교해야 하지만 이 방법은 판정이 자동이다.
--
-- 점검 스크립트에 넣을 때는 이 형태가 편하다. 값이 길거나 여러 개인
-- 파라미터도 한 줄로 판정된다.

--------------------------------------------------------------------------------
 [5] "반드시 달라야" 하는 것이 같으면
--------------------------------------------------------------------------------

SQL> select name, count(distinct value) cnt from gv$parameter
  2   where name in ('instance_number','thread','undo_tablespace')
  3   group by name order by name;

NAME                          CNT
-------------------------- ------
instance_number                 2
thread                          2
undo_tablespace                 2

3 rows selected.

-- 여기서는 2 가 정상이다. 인스턴스가 둘이므로 값도 둘이어야 한다.
-- 1 이 나오면 두 인스턴스가 같은 값을 쓰고 있다는 뜻으로 즉시 조치해야 한다.
--
-- 앞의 [4] 와 판정 방향이 반대라는 점에 주의한다.
--   반드시 같아야 → count(distinct value) = 1 이어야 정상
--   반드시 달라야 → count(distinct value) = 인스턴스 수여야 정상

--------------------------------------------------------------------------------
 [6] 같은 것이 권장되는 분류
--------------------------------------------------------------------------------

SQL> col name for a24
SQL> select name, count(distinct value) cnt from gv$parameter
  2   where name in ('sga_target','pga_aggregate_target','processes','open_cursors')
  3   group by name order by name;

NAME                        CNT
------------------------ ------
open_cursors                  1
pga_aggregate_target          1
processes                     1
sga_target                    1

4 rows selected.

-- 넷 다 1 이다. 두 인스턴스가 같은 값을 쓰고 있다.
-- 이 분류는 달라도 동작한다. 다만 권장은 같게 두는 것이다.
--
-- 다르게 잡는 정당한 경우
--   노드의 하드웨어가 다르다 (메모리가 다른 서버로 확장한 경우 등)
--   부하가 한쪽에 의도적으로 몰려 있다
--
-- 다르게 두었을 때의 위험
--   어느 노드에 접속했느냐에 따라 동작이 달라진다
--   장애 조치로 세션이 다른 노드로 넘어갔을 때 예상 밖의 결과가 나온다
--   성능 문제를 진단할 때 변수가 하나 늘어난다
--
-- 특별한 이유가 없으면 같게 둔다.

--------------------------------------------------------------------------------
 [7] 판정이 반대라는 것을 놓치면
--------------------------------------------------------------------------------

-- [4] 와 [5] 의 판정 방향이 반대라는 점을 다시 확인한다.
-- 이것을 놓치면 점검 스크립트가 조용히 잘못된 판정을 낸다.

SQL> select sid, name from v$spparameter where name='cluster_database' and sid<>'*';

no rows selected

-- 0 행이 나왔다. 여기서 두 가지 해석이 가능하다.
--
-- 원인 파악 : cluster_database 는 "반드시 같아야" 분류이므로 인스턴스별
--             항목이 없는 것이 정상이다. 0 행이 곧 "이상 없음" 이다.
--             그런데 같은 조회를 instance_number 에 대해 실행하면
--             0 행은 오히려 이상 신호가 된다. 그 파라미터는 인스턴스별로
--             지정되어 있어야 하기 때문이다.
-- 조치     : 파라미터마다 기대값을 미리 정해 두고 비교한다.
--             "0 행이면 정상" 이라는 규칙을 모든 파라미터에 적용하면 안 된다.
-- 재확인   : instance_number 로 같은 조회를 실행해 대조한다.

SQL> select sid, name from v$spparameter where name='instance_number' and sid<>'*';

SID      NAME
-------- --------------------
racdb1   instance_number
racdb2   instance_number

2 rows selected.

-- 같은 형태의 조회인데 기대값이 정반대다.
--   cluster_database  → 0 행이어야 정상
--   instance_number   → 2 행이어야 정상 (2노드 기준)
--
-- 점검 스크립트를 만들 때는 파라미터 목록과 기대값을 함께 정의한다.
-- 조회 결과만 보고 일괄 판정하면 안 된다.

--------------------------------------------------------------------------------
