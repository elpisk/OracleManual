================================================================================
 제12장 실습 03 — 정상 종료와 비정상 종료 : CRS 의 반응 차이
 대상   : rac1 (조작은 rac2)
 목표   : SQL*Plus 로 정상 종료했을 때와 프로세스를 강제로 죽였을 때 CRS 가
          어떻게 다르게 반응하는지 TARGET 값으로 확인한다
 소요   : 약 30분
 선행   : racdb 양 노드 OPEN, 부하 4 이하
 계정   : oracle, grid, root
 주의   : 인스턴스를 두 번 내렸다 올린다. 각 40~110초가 걸린다
================================================================================

--------------------------------------------------------------------------------
 [1] 먼저 예상해 본다
--------------------------------------------------------------------------------

-- 실습 01 에서 srvctl stop instance 는 TARGET 을 OFFLINE 으로 바꿨다.
-- 그렇다면 SQL*Plus 로 shutdown immediate 를 하면 어떻게 될 것인가.
--
-- 흔한 예상 : CRS 는 SQL*Plus 로 내린 것을 모르므로 TARGET 이 ONLINE 으로
--             남고, TARGET 과 STATE 가 어긋나 다시 올릴 것이다.
--
-- 실제로 해 보고 확인한다.

--------------------------------------------------------------------------------
 [2] 정지 전 상태
--------------------------------------------------------------------------------

[grid@rac1 ~]$ crsctl stat res ora.racdb.db -t
--------------------------------------------------------------------------------
ora.racdb.db
      1        ONLINE  ONLINE       rac1     Open,HOME=/u01/app/oracle/...,STABLE
      2        ONLINE  ONLINE       rac2     Open,HOME=/u01/app/oracle/...,STABLE
--------------------------------------------------------------------------------

--------------------------------------------------------------------------------
 [3] SQL*Plus 로 정상 종료
--------------------------------------------------------------------------------

[oracle@rac2 ~]$ sqlplus -s / as sysdba

SQL> shutdown immediate
Database closed.
Database dismounted.
ORACLE instance shut down.

                                                              (54.0초 소요)

-- 세 줄이 순서대로 나왔다. 정상 종료 절차를 모두 밟았다는 뜻이다.
--   Database closed      — 데이터파일을 닫았다
--   Database dismounted  — 컨트롤파일을 닫았다
--   ORACLE instance shut down — SGA 를 해제하고 프로세스를 정리했다

--------------------------------------------------------------------------------
 [4] CRS 를 20초 간격으로 100초 관찰
--------------------------------------------------------------------------------

[  0초] pmon=0
ora.racdb.db
      1        ONLINE  ONLINE       rac1     Open,HOME=/u01/app/oracle/...,STABLE
      2        OFFLINE OFFLINE               STABLE

[ 20초] pmon=0   → 같은 출력
[ 40초] pmon=0   → 같은 출력
[ 60초] pmon=0   → 같은 출력
[ 80초] pmon=0   → 같은 출력
[100초] pmon=0   → 같은 출력

[oracle@rac1 ~]$ srvctl status database -d racdb -v
Instance racdb1 is running on node rac1. Instance status: Open.
Instance racdb2 is not running on node rac2

SQL> select inst_id, instance_name, status from gv$instance order by 1;

   INST_ID INSTANCE_NAME    STATUS
---------- ---------------- ------------
         1 racdb1           OPEN

1 row selected.

-- 예상과 다른 결과다.
--
-- 원인 파악 : TARGET 이 OFFLINE 으로 바뀌었다.
--             오라클 에이전트가 정상 종료를 감지하고 TARGET 을 함께 내린 것이다.
--             사람이 의도적으로 내렸다고 판단했다는 뜻이다.
--             TARGET 과 STATE 가 일치하므로 CRS 는 할 일이 없다.
-- 조치     : 조치할 것이 없다. 의도한 정지라면 이것이 올바른 동작이다.
-- 재확인   : 100 초 동안 pmon 프로세스가 계속 0 개였다. 재기동 시도조차 없었다.
--
-- 그렇다면 CRS 는 언제 다시 올리는가. [6] 에서 확인한다.

--------------------------------------------------------------------------------
 [5] 다시 기동
--------------------------------------------------------------------------------

[oracle@rac1 ~]$ srvctl start instance -d racdb -i racdb2

                                                             (111.2초 소요)

[grid@rac1 ~]$ crsctl stat res ora.racdb.db -t
ora.racdb.db
      1        ONLINE  ONLINE       rac1     Open,...,STABLE
      2        ONLINE  ONLINE       rac2     Open,...,STABLE

-- 111.2 초다. 실습 01 의 40.6 초보다 훨씬 길다.
-- 같은 명령인데 시간이 다른 것은 그때그때의 노드 부하 때문이다.
-- 자원이 빠듯한 환경에서는 기동 시간이 일정하지 않다는 점을 감안해야 한다.

--------------------------------------------------------------------------------
 [6] 비정상 종료 재현 — pmon 을 죽인다
--------------------------------------------------------------------------------

[root@rac2 ~]# ps -ef | grep '[o]ra_pmon_racdb2' | awk '{print $2}'
26984

[root@rac2 ~]# kill -9 26984

-- pmon 은 인스턴스의 핵심 프로세스다. 이것이 죽으면 인스턴스 전체가 죽는다.
-- 정상 종료 절차를 밟지 않으므로 인스턴스가 갑자기 사라지는 상황을 흉내 낸다.
-- 실제 장애에서는 메모리 부족, OS 오류, 하드웨어 문제로 이런 일이 생긴다.

--------------------------------------------------------------------------------
 [7] CRS 반응 관찰
--------------------------------------------------------------------------------

[ 20초] pmon=1 | 2  ONLINE  OFFLINE  rac2  STARTING
[ 41초] pmon=1 | 2  ONLINE  OFFLINE  rac2  STARTING
[ 61초] pmon=1 | 2  ONLINE  ONLINE   rac2  Open,HOME=/u01/app/oracle/...

[oracle@rac1 ~]$ srvctl status database -d racdb -v
Instance racdb1 is running on node rac1. Instance status: Open.
Instance racdb2 is running on node rac2. Instance status: Open.

-- 이번에는 CRS 가 다시 올렸다.
--
-- 원인 파악 : TARGET 이 ONLINE 으로 남아 있다.
--             정상 종료 절차를 밟지 않았으므로 에이전트가 TARGET 을 내릴
--             기회가 없었다. TARGET(ONLINE) 과 STATE(OFFLINE) 가 어긋났고
--             CRS 는 이것을 장애로 판단해 자원을 다시 올렸다.
-- 조치     : CRS 가 알아서 복구했으므로 사람이 할 일은 없다.
--             다만 왜 죽었는지는 알림 로그에서 확인해야 한다.
-- 재확인   : 20 초 시점에 이미 pmon 이 1 개이고 STATE 가 STARTING 이다.
--             감지가 거의 즉시 일어났음을 알 수 있다. 61 초에 ONLINE 이 되었다.

--------------------------------------------------------------------------------
 [8] 재시작 정책 확인
--------------------------------------------------------------------------------

[grid@rac1 ~]$ crsctl stat res ora.racdb.db -p | grep -iE '^RESTART_ATTEMPTS|^UPTIME_THRESHOLD|^TYPE'

TYPE=ora.database.type
RESTART_ATTEMPTS=2
UPTIME_THRESHOLD=1h

[oracle@rac1 ~]$ srvctl config database -d racdb | grep -i 'management policy'
Management policy: AUTOMATIC

-- RESTART_ATTEMPTS=2
--   CRS 는 두 번까지 다시 올려 본다. 두 번 다 실패하면 포기하고
--   자원을 OFFLINE 으로 둔다. 그때는 사람이 개입해야 한다.
--
-- UPTIME_THRESHOLD=1h
--   재시작 횟수를 세는 기준이다. 한 시간 이상 정상 동작하면 그동안의
--   실패 이력을 잊는다.
--   그래서 하루에 한 번씩 죽는 인스턴스는 매번 두 번의 기회를 다시 받는다.
--   반복 장애가 누적으로 잡히지 않는 이유이므로, 이런 패턴은 CRS 가 아니라
--   알림 로그를 봐야 발견된다.

--------------------------------------------------------------------------------
 [9] 복구된 뒤 확인 — 중복 기동을 시도하면
--------------------------------------------------------------------------------

-- [7] 에서 CRS 가 이미 인스턴스를 올렸다. 그것을 모르고 수동으로 올리면
-- 어떻게 되는지 확인한다.

[oracle@rac1 ~]$ srvctl start instance -d racdb -i racdb2
PRCC-1015 : racdb was already running on rac1
PRCR-1004 : Resource ora.racdb.db is already running

-- 오류 : PRCC-1015 / PRCR-1004
--
-- 원인 파악 : CRS 가 이미 복구를 끝냈으므로 자원이 ONLINE 이다.
--             중복 기동은 거부된다.
--             비정상 종료 후에는 사람이 손대기 전에 CRS 가 먼저 움직인다는
--             것을 기억해야 한다.
-- 조치     : 조치할 것이 없다. 이미 원하는 상태다.
--             장애 상황에서 이 메시지를 보면 CRS 가 이미 처리했다는 신호다.
-- 재확인   : srvctl status database -d racdb -v 로 상태를 확인한다.

[oracle@rac1 ~]$ srvctl status database -d racdb -v
Instance racdb1 is running on node rac1. Instance status: Open.
Instance racdb2 is running on node rac2. Instance status: Open.

-- 실무 요령 : 인스턴스가 죽었다는 알림을 받으면 바로 기동 명령을 내리기 전에
--             crsctl stat res ora.racdb.db -t 로 상태를 먼저 본다.
--             STARTING 이면 CRS 가 이미 처리 중이므로 기다리면 된다.
--             동시에 기동을 시도하면 자원 잠금 경합만 만든다.

--------------------------------------------------------------------------------
 [10] 정리 — 세 경우 비교
--------------------------------------------------------------------------------

--  방식                          TARGET        STATE              CRS 반응
--  ---------------------------  ------------  -----------------  --------------
--  srvctl stop instance          OFFLINE 로    OFFLINE            재시작 안 함
--  SQL*Plus shutdown immediate   OFFLINE 로    OFFLINE            재시작 안 함
--  kill -9 pmon                  ONLINE 유지   OFFLINE→STARTING   61초 만에 복구
--
-- 결론 : CRS 가 보는 것은 "어떤 도구로 내렸는가" 가 아니라
--        "정상 종료인가 비정상 종료인가" 다.
--
-- 그렇다면 왜 srvctl 을 권하는가.
--   1) 의존 자원까지 순서대로 처리한다 (서비스 등)
--   2) 어느 노드에서든 실행할 수 있다
--   3) -stopconcurrency, -drain_timeout 같은 RAC 전용 옵션을 쓸 수 있다
--
-- 주의 : srvctl 로 내린 인스턴스는 노드를 재부팅해도 올라오지 않는다.
--        TARGET 이 OFFLINE 으로 저장되어 있기 때문이며,
--        올릴 때도 srvctl 로 올려야 TARGET 이 ONLINE 으로 돌아온다.
