================================================================================
 제3장 실습 01 — 네트워크 요건 확인
 대상   : rac1(172.16.225.101) / rac2(172.16.225.102)
 목표   : 공용·사설 인터페이스와 주소를 식별하고, oifcfg 의 두 하위 명령이
          서로 다른 것을 말한다는 점을 확인하며, 두 네트워크가 실제로
          분리되어 있는지 검증한다
 소요   : 약 25분
 선행   : 두 노드 기동, Clusterware 정상
 계정   : root, grid
================================================================================

--------------------------------------------------------------------------------
 [1] 주소 목록
--------------------------------------------------------------------------------

[root@rac1 ~]# ip -o -4 addr show | awk '{print $2, $4}'
lo      127.0.0.1/8
ens33   172.16.225.101/24
ens33   172.16.225.111/24
ens33   172.16.225.120/24
ens160  172.16.119.101/24
ens160  169.254.27.118/19

[root@rac2 ~]# ip -o -4 addr show | awk '{print $2, $4}'
lo      127.0.0.1/8
ens33   172.16.225.102/24
ens33   172.16.225.112/24
ens160  172.16.119.102/24
ens160  169.254.26.245/19

-- 읽는 법
--   ens33 172.16.225.101   공용 IP. OS 가 올린다
--   ens33 172.16.225.111   rac1-vip. Clusterware 가 올린 것
--   ens33 172.16.225.120   rac-scan. Clusterware 가 올린 것
--   ens160 172.16.119.101  사설 IP. OS 가 올린다
--   ens160 169.254.27.118  HAIP. GI 가 자동으로 올린 것
--
-- 설치 전이라면 ens33 에 .101 하나, ens160 에 172.16.119.101 하나만 있어야 한다.
-- VIP·SCAN·HAIP 세 종류는 설치 과정에서 추가된 것이다.
--
-- rac1 에 SCAN 주소가 있고 rac2 에는 없다. SCAN VIP 는 클러스터에 하나뿐이며
-- 지금 rac1 에 배치되어 있다. 2장 실습에서 rac2 를 정지했을 때 옮겨 온 뒤
-- 돌아가지 않은 결과다(페일백 없음).

--------------------------------------------------------------------------------
 [2] oifcfg — 두 하위 명령이 다른 것을 말한다
--------------------------------------------------------------------------------

[root@rac1 ~]# su - grid
[grid@rac1 ~]$ oifcfg getif
ens160  172.16.119.0  global  cluster_interconnect,asm
ens33   172.16.225.0  global  public

[grid@rac1 ~]$ oifcfg iflist -p -n
ens33   172.16.225.0  PRIVATE  255.255.255.0
ens160  172.16.119.0  PRIVATE  255.255.255.0
ens160  169.254.0.0   UNKNOWN  255.255.224.0

-- 두 출력이 정반대로 보인다. getif 는 ens33 을 public 이라 하는데
-- iflist 는 PRIVATE 이라 한다. 모순이 아니다.
--
--   getif  : Clusterware 가 등록해 둔 용도. 설치 시 응답 파일의
--            networkInterfaceList 로 지정한 값이다. 운영에 쓰이는 정보다.
--   iflist : 운영체제가 본 주소 대역의 성격. PRIVATE 은 RFC 1918
--            사설 대역(10.x, 172.16~31.x, 192.168.x)이라는 뜻이지
--            Oracle 의 인터커넥트라는 뜻이 아니다.
--            172.16.225.x 도 사설 대역이므로 PRIVATE 으로 분류된다.
--
-- 세 번째 줄의 169.254.0.0 UNKNOWN 은 HAIP 대역이다. 링크 로컬 주소라
-- 사설도 공용도 아니므로 UNKNOWN 이다.
--
-- 판단 근거는 항상 getif 다. 용도를 바꾸는 명령도 oifcfg setif 이지
-- iflist 가 아니다. 현장에서 iflist 만 보고 "두 인터페이스가 모두 사설로
-- 잡혀 있으니 공용 설정이 잘못됐다"고 보고하는 오해가 잦다.

--------------------------------------------------------------------------------
 [3] 두 네트워크가 실제로 분리되어 있는가
--------------------------------------------------------------------------------

[root@rac1 ~]# ip route
default via 172.16.225.2 dev ens33 proto static metric 100
169.254.0.0/19 dev ens160 proto kernel scope link src 169.254.27.118
172.16.119.0/24 dev ens160 proto kernel scope link src 172.16.119.101 metric 101
172.16.225.0/24 dev ens33 proto kernel scope link src 172.16.225.101 metric 100

-- 172.16.225.0/24 는 ens33 으로, 172.16.119.0/24 는 ens160 으로 나간다.
-- 두 대역이 서로 다른 인터페이스에 묶여 있다.
-- 기본 경로가 ens33 에만 있는 것도 맞다. 인터커넥트는 클러스터 안에서만
-- 쓰이므로 외부로 나갈 일이 없다.

[root@rac1 ~]# for h in rac2 rac2-priv; do
>   printf '%-12s ' $h
>   ping -c2 -W2 $h 2>&1 | tail -2 | head -1
> done
rac2         2 packets transmitted, 2 received, 0% packet loss, time 1047ms
rac2-priv    2 packets transmitted, 2 received, 0% packet loss, time 1022ms

-- 인터페이스를 지정해 각 경로가 살아 있는지 확인한다.
[root@rac1 ~]# ping -c2 -W2 -I ens33 rac2 | tail -2 | head -1
2 packets transmitted, 2 received, 0% packet loss, time 1057ms

[root@rac1 ~]# ping -c2 -W2 -I ens160 rac2-priv | tail -2 | head -1
2 packets transmitted, 2 received, 0% packet loss, time 1000ms

-- -I 로 인터페이스를 지정하면 그 인터페이스로만 나간다.
-- 두 경로가 각각 살아 있다는 뜻이다. 설치 전 점검에서 이 두 줄은 반드시 확인한다.

--------------------------------------------------------------------------------
 [4] 오류 재현 — 존재하지 않는 노드로 도달 검사
--------------------------------------------------------------------------------

-- 노드 이름을 잘못 적으면 cluvfy 가 무엇이라고 하는지 확인한다.

[grid@rac1 ~]$ cluvfy comp nodereach -n rac1,rac9

Failures were encountered during execution of CVU verification request
"node reachability".

Verifying Node Reachability ...FAILED
rac9: PRVF-4083 : Node reachability check failed from node "rac1"
      PRKN-1034 : Failed to retrieve IP address of host "rac9"
      unknown host exception for host "rac9"


CVU operation performed:      node reachability
Date:                         Sep 1, 2026 2:28:13 PM
CVU home:                     /u01/app/19.3.0/grid/
User:                         grid

-- 원인 파악
--   세 줄이 계층적으로 원인을 좁혀 준다. 아래에서 위로 읽는다.
--     unknown host exception   근본 원인 — 이름 해석 자체가 실패했다
--     PRKN-1034                원인 — 그래서 IP 주소를 얻지 못했다
--     PRVF-4083                결과 — 도달 검사가 실패했다
--
--   첫 줄만 읽으면 "도달할 수 없다"로 해석해 네트워크나 방화벽을 뒤지게 된다.
--   실제 원인은 이름 해석이므로 엉뚱한 곳을 고치는 셈이다.

-- 확인할 것 세 가지
[grid@rac1 ~]$ nslookup rac9
** server can't find rac9: NXDOMAIN

[grid@rac1 ~]$ grep rac9 /etc/hosts
(출력 없음)

--   1) 이름 철자가 맞는가 — rac9 는 존재하지 않는 노드다
--   2) /etc/hosts 에 등록되어 있는가 — 없다
--   3) 지정된 네임서버가 그 이름을 아는가 — 모른다

-- 조치 — 올바른 노드 이름으로 실행한다.
[grid@rac1 ~]$ cluvfy comp nodereach -n rac1,rac2

Verifying Node Reachability ...PASSED

Verification of node reachability was successful.

-- 재확인
--   PASSED 로 바뀌었다. 이름 해석 문제였음이 확정된다.
--   실제 설치 준비에서 이 오류를 만난다면 세 가지를 순서대로 확인한다.

--------------------------------------------------------------------------------
 [6] 정리
--------------------------------------------------------------------------------

-- 확인한 것
--   1) 설치 후 인터페이스에는 공용·VIP·SCAN·사설·HAIP 다섯 종류가 올라온다
--   2) 설치 전에는 공용과 사설만 있어야 한다
--   3) oifcfg getif 는 Clusterware 용도, iflist 의 PRIVATE 은 RFC 1918 대역
--   4) ip route 로 두 대역이 다른 인터페이스에 묶였는지 확인한다
--   5) ping -I 로 각 경로가 살아 있는지 검증한다
--   6) cluvfy 오류는 아래에서 위로 읽는다
--   7) comp nodecon 이 주소 쌍·MTU·마스크·멀티캐스트를 한 번에 검사한다
--
-- 이 실습은 조회만 했으므로 원상 복구할 것이 없다.
