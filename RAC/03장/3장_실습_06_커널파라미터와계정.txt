 [4] 오류 재현 — 파일만 보고 판단했을 때
--------------------------------------------------------------------------------

[root@rac1 ~]# grep -rn "rp_filter" /etc/sysctl.conf /etc/sysctl.d/ 2>/dev/null
/etc/sysctl.conf:24:net.ipv4.conf.all.rp_filter = 2
/etc/sysctl.conf:25:net.ipv4.conf.default.rp_filter = 2
/etc/sysctl.d/99-oracle-database-preinstall-19c-sysctl.conf:11:net.ipv4.conf.all.rp_filter = 2
/etc/sysctl.d/99-oracle-database-preinstall-19c-sysctl.conf:12:net.ipv4.conf.default.rp_filter = 2

-- 원인 파악
--   같은 항목이 두 파일에 있다. 이 실습 환경은 preinstall 패키지가 이미
--   값을 넣었는데 준비 스크립트가 /etc/sysctl.conf 에 같은 값을 또 넣어
--   중복이 생겼다. 값이 같아 문제는 없지만, 값이 달랐다면 어느 쪽이
--   이기는지 파일만 봐서는 알 수 없다.
--
--   sysctl.d 의 파일은 이름 순으로 읽히고 나중에 읽힌 값이 이긴다.
--   99-sysctl.conf 가 ../sysctl.conf 로의 링크이므로 /etc/sysctl.conf 도
--   같은 순서 규칙에 들어간다.

-- 조치 — 파일이 아니라 커널의 유효값을 확인한다.
[root@rac1 ~]# sysctl -n fs.file-max kernel.shmmax net.ipv4.ip_local_port_range net.ipv4.conf.all.rp_filter
6815744
4398046511104
9000    65500
2

-- 재확인
--   rp_filter 가 2 다. RAC 요건을 만족한다.
--   cluvfy 도 이 유효값을 본다. 파일에 무엇이 적혀 있느냐가 아니라
--   커널이 지금 무슨 값을 쓰고 있느냐가 기준이다.
--
-- 배운 것
--   sysctl 항목이 여러 파일에 흩어져 있는 것은 흔한 상황이다.
--   점검은 항상 sysctl -n 으로 한다. 값을 바꾼 뒤에는 sysctl -p 또는
--   sysctl --system 으로 반영하고 다시 유효값을 확인한다.

--------------------------------------------------------------------------------
 [5] rp_filter 가 특히 중요한 이유
--------------------------------------------------------------------------------

-- 값의 뜻
--   0  역경로 검사를 하지 않는다
--   1  엄격. 패킷이 들어온 인터페이스가 그 출발지 주소로 나갈 때 쓰는
--      인터페이스와 같아야 한다. 다르면 버린다
--   2  느슨. 어느 인터페이스로든 그 출발지로 갈 경로가 있으면 통과시킨다
--
-- RAC 에서 1 이면 문제가 되는 이유
--   인터페이스가 여럿이고 HAIP 가 169.254 대역을 별칭으로 얹는다.
--   인터커넥트로 들어온 패킷의 출발지가 다른 인터페이스 경로로 판정되면
--   커널이 버린다.
--
-- 증상이 고약하다
--   ping 은 정상이다. 클러스터는 형성되지만 불안정하다.
--   노드가 간헐적으로 축출된다. 네트워크 담당자는 문제가 없다고 하고
--   데이터베이스 로그에도 원인이 남지 않는다.
--   준비 단계에서 이 값 하나를 확인하면 피할 수 있다.

-- 열 개 그룹이 54321 부터 연속으로 잡혀 있다.
-- 각 그룹의 구성원도 의미가 있다.
--   dba, asmdba                          oracle 과 grid 가 모두 들어 있다
--   asmoper, asmadmin                    grid 만. ASM 운영 권한
--   oper, backupdba, dgdba, kmdba, racdba oracle 만. 데이터베이스 권한

[root@rac2 ~]# getent group | grep -E '^(oinstall|dba|asmadmin|racdba):'
oinstall:x:54321:
dba:x:54322:oracle,grid
asmadmin:x:54329:grid
racdba:x:54330:oracle

-- 두 노드의 GID 가 같다. 공유 스토리지의 파일 소유권은 숫자로 기록되므로
-- 번호가 같아야 판정이 어긋나지 않는다.

[root@rac1 ~]# id grid
uid=1001(grid) gid=54321(oinstall) groups=54321(oinstall),54322(dba),54327(asmdba),54328(asmoper),54329(asmadmin)

[root@rac1 ~]# id oracle
uid=1000(oracle) gid=54321(oinstall) groups=54321(oinstall),54322(dba),54323(oper),54324(backupdba),54325(dgdba),54326(kmdba),54330(racdba),54327(asmdba)

[root@rac1 ~]# id -gn grid; id -gn oracle
oinstall
oinstall

-- 두 계정 모두 기본 그룹이 oinstall 이다.
-- 설치 관리자가 설치 사용자의 기본 그룹과 인벤토리 그룹이 같을 것을 요구하므로
-- 이 조건이 맞아야 한다. 이것을 놓쳐 실제로 INS-13013 에 걸렸고
-- 4장에서 그 과정을 다룬다.

--------------------------------------------------------------------------------
 [8] 정리
--------------------------------------------------------------------------------

-- 확인한 것
--   1) preinstall 패키지가 sysctl 14개와 limits 를 넣는다
--   2) limits 에는 oracle 만 있다. grid 는 직접 넣어야 한다
--   3) 같은 항목이 여러 파일에 있을 수 있다
--   4) 기준은 sysctl -n 의 유효값이다
--   5) rp_filter 는 2 여야 하고 1 이면 간헐적 축출을 일으킨다
--   6) 그룹 열 개의 GID 가 두 노드에서 같다
--   7) 두 계정의 기본 그룹이 모두 oinstall 이다
--   8) hostname -s, SELinux, cvuqdisk, NTP 설정 파일, 두 노드 시각을 확인한다
--
-- 이 실습은 조회만 했으므로 원상 복구할 것이 없다.
