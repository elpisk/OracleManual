 [4] 5장과 비교한다
--------------------------------------------------------------------------------

-- 5장에서 +CRS 의 디스크를 내렸을 때는 REPAIR_TIMER 가 0이었다.
-- 1분을 기다려도 움직이지 않아 의아했다.
--
-- 이유는 alert.log 의 표현에 있었다.
--   op = clear mandatory
--
-- Voting File 을 담은 디스크는 mandatory 속성을 갖는다. 그 속성이 해제되면
-- 통상적인 repair timer 관리 대상에서 빠진다. Voting File 은 이미 재배치로
-- 처리되었으므로 타이머로 관리할 이유가 없었다.
--
-- TESTN 에는 Voting File 이 없다. 그래서 정상적으로 180초가 잡혔다.

SQL> select name, voting_files from v$asm_diskgroup where name in ('CRS','TESTN');

 [10] 헤더는 정리되지 않았다
--------------------------------------------------------------------------------

-- 리밸런스가 끝난 뒤 확인한다.

SQL> select path, name, header_status, mount_status, group_number, total_mb, os_mb
  2    from v$asm_disk where path like '%test6%';

PATH                 NAME  HEADER_STATU MOUNT_S GROUP_NUMBER   TOTAL_MB      OS_MB
-------------------- ----- ------------ ------- ------------ ---------- ----------
/dev/asmdisk/test6         MEMBER       CLOSED             0          0       4096

-- HEADER_STATUS 가 FORMER 가 아니라 MEMBER 다.
-- ASM 이 FORCE 로 제거했기 때문이다. 실습 04 의 수동 FORCE 제거와 같다.
--
-- 그래서 이 디스크를 다시 넣으려면 ORA-15033 을 만난다.

SQL> alter diskgroup TESTN add failgroup fgC disk '/dev/asmdisk/test6' name d_c;
alter diskgroup TESTN add failgroup fgC disk '/dev/asmdisk/test6' name d_c
*
ERROR at line 1:
ORA-15032: not all alterations performed
ORA-15033: disk '/dev/asmdisk/test6' belongs to diskgroup "TESTN"

-- 오류 : ORA-15032, ORA-15033
-- 원인 파악 : 타이머 만료로 ASM 이 FORCE 제거했으므로 헤더가 MEMBER 로
--             남았다. 사람이 실수한 것이 아니라 자동 동작의 결과다.
--             DISK_REPAIR_TIME 을 짧게 두면 계획하지 않은 상황에서 이런
--             일이 생긴다.
-- 조치     : add 에도 FORCE 를 붙인다. GROUP_NUMBER 가 0인지 먼저 확인한다.
-- 재확인   : 실습 07 에서 복구한다.

--------------------------------------------------------------------------------
 [11] 정리
--------------------------------------------------------------------------------

-- 재현한 오류
--   ORA-15032 / ORA-15033   자동 FORCE 제거 후 재사용 시도
--
-- 시각 기록
--   20:09:55  오프라인 직전
--   20:10:07  오프라인 완료. REPAIR_TIMER 180
--   20:13:06  ASM 이 스스로 drop disk force 실행 (정확히 3분 뒤)
--   20:14:20  _DROPPED_0002_TESTN / FORCING, 리밸런스 진행 중
--
-- 확인한 것
--   1) 오프라인 시 REPAIR_TIMER 에 disk_repair_time 이 초로 잡힌다
--   2) STATE 는 NORMAL 이다. 제거(DROPPING)와 다르다
--   3) USED_MB 가 유지된다. 데이터를 지우지 않는다
--   4) REPAIR_TIMER 는 카운트다운하지 않고 설정값을 그대로 보여 준다
--   5) 5장에서 0이었던 것은 Voting File 디스크의 mandatory 속성 때문
--   6) 만료 시 ASM 이 drop disk force 를 스스로 실행한다
--   7) alert.log 의 /* ASM SERVER */ 주석이 자동 동작의 단서다
--   8) 데이터베이스는 아무 영향을 받지 않았다
--   9) 헤더가 MEMBER 로 남아 재사용이 막힌다
--
-- 실무 교훈
--   DISK_REPAIR_TIME 을 임의로 줄이면 안 된다. 기본값 3.6시간은 대부분의
--   일시적 장애를 흡수한다. 실습을 위해 줄였다면 반드시 되돌린다.
