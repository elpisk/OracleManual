================================================================================
 제11장 실습 01 — 생성 전 점검
 대상   : rac1, rac2
 목표   : 데이터베이스를 만들기 전에 클러스터·공간·메모리·부하를 확인하고
          생성 절차를 확정한다
 소요   : 약 15분
 선행   : racdb 양 노드 OPEN
 계정   : oracle, grid
================================================================================

--------------------------------------------------------------------------------
 [1] 클러스터가 건강한가
--------------------------------------------------------------------------------

[grid@rac1 ~]$ crsctl check cluster -all | grep -c "is online"
6

[grid@rac1 ~]$ olsnodes -n -s -t
rac1    1       Active  Unpinned
rac2    2       Active  Unpinned

-- 6 은 노드당 CRS·CSS·EVM 세 줄씩 두 노드분이다.
-- olsnodes 는 노드 이름·번호·활성 여부를 함께 보여 준다.
--
-- 두 명령의 역할이 다르다.
--   crsctl   — CRS 스택 자체가 정상인지
--   olsnodes — 각 노드가 클러스터 멤버로 활성인지
--
-- olsnodes 의 이름이 중요하다. dbca 의 -nodelist 에는 여기 나온 이름을
-- 그대로 넣어야 한다. rac1.localdomain 처럼 FQDN 을 붙이면 일치하지 않는다.

--------------------------------------------------------------------------------
 [2] 디스크그룹 여유
--------------------------------------------------------------------------------

[grid@rac1 ~]$ sqlplus -s / as sysasm

SQL> col name for a8
SQL> select name, type, total_mb, free_mb, usable_file_mb
  2    from v$asm_diskgroup order by group_number;

NAME     TYPE     TOTAL_MB    FREE_MB USABLE_FILE_MB
-------- ------ ---------- ---------- --------------
CRS      NORMAL      12288      11324           3614
DATA     EXTERN      61440      56906          56906
FRA      EXTERN      24576      23636          23636

3 rows selected.

-- 9장에서 배운 대로 판단 기준은 FREE_MB 가 아니라 USABLE_FILE_MB 다.
-- External 중복도라 두 값이 같아 여기서는 차이가 없지만,
-- Normal 이었다면 절반으로 줄었을 것이다.
--
-- General_Purpose 템플릿으로 만드는 데이터베이스는 +DATA 를 3.5GB 정도 쓴다.
-- 여유가 56GB 이므로 충분하다.
--
-- 이 값을 기록해 둔다. 실습 07 에서 삭제 후 이 값과 비교한다.

--------------------------------------------------------------------------------
 [3] 메모리 — 양 노드 모두 확인
--------------------------------------------------------------------------------

[oracle@rac1 ~]$ free -m
              total        used        free      shared  buff/cache   available
Mem:           8668        3128         495        2697        5044        2582

[oracle@rac2 ~]$ free -m
              total        used        free      shared  buff/cache   available
Mem:           8668        2938         259        2695        5470        2734

-- available 이 rac1 2582MB, rac2 2734MB 다.
-- 새 데이터베이스에 800MB 를 주면 여유가 있다.
--
-- 양 노드를 모두 봐야 하는 이유가 있다. RAC 에서는 노드마다 인스턴스가 뜬다.
-- 한 노드만 보고 진행하면 두 번째 인스턴스에서 실패한다.
--
-- 메모리가 모자라면 dbca 가 도중에 실패하거나,
-- 더 나쁘게는 기존 racdb 까지 영향을 받는다.

--------------------------------------------------------------------------------
 [4] 부하 — 이 랩의 경험에서 추가된 항목
--------------------------------------------------------------------------------

[oracle@rac1 ~]$ cat /proc/loadavg
3.38 3.49 4.08 1/1063 12722

[oracle@rac2 ~]$ cat /proc/loadavg
2.95 3.60 4.84 1/1024 12691

-- 첫 값이 1분 평균이다. 4 vCPU 환경에서 4 미만이면 진행해도 된다.
--
-- 이 항목은 일반적인 설치 문서에 없다. 이 랩에서 실패를 겪고 추가한 것이다.
-- 부하가 높은 상태로 시작하면 생성 도중에 더 올라가 노드가 축출된다.
--
-- 4 를 넘으면 기다린다. 무엇이 부하를 만들고 있는지 확인해도 좋다.

--------------------------------------------------------------------------------
 [5] 호스트 자원 — 가장 중요한 준비
--------------------------------------------------------------------------------

-- 가상 환경이라면 호스트에서 이 클러스터와 무관한 가상 머신을 모두 내린다.
--
-- 이 랩의 실측 대비.
--   다른 VM 이 떠 있을 때  → 부하 4.9분 42.8 / 8분 122.6 / 10분 139.4
--                            → 양 노드 축출, dbca 7% 지점에서 중단
--   다른 VM 을 내린 뒤     → 부하 3.4 ~ 7.4 유지
--                            → 24분 54초에 정상 완료
--
-- 명령과 인자는 사실상 같았다. 차이는 호스트의 여유 CPU 하나뿐이었다.
-- 물리 서버 환경이라면 이 항목은 해당되지 않는다.

--------------------------------------------------------------------------------
 [6] 기존 데이터베이스 확인
--------------------------------------------------------------------------------

[oracle@rac1 ~]$ srvctl config database
racdb

[oracle@rac1 ~]$ cat /etc/oratab | grep -v '^#' | grep -v '^$'
orcl:/u01/app/oracle/product/19.3.0/dbhome_1:N
PROD:/u01/app/oracle/product/19.3.0/dbhome_1:N
KNH:/u01/app/oracle/product/19.3.0/dbhome_1:N

-- 두 목록이 다르다.
--
-- 원인 파악 : srvctl 은 CRS 에 등록된 데이터베이스를 보여 준다. racdb 하나다.
--             /etc/oratab 의 세 이름은 이 노드를 만들 때 쓴 템플릿 VM 의
--             흔적이다. CRS 에 등록되지 않았으므로 RAC 데이터베이스가 아니다.
-- 조치     : 이름 충돌 여부는 srvctl 목록을 기준으로 판단한다.
--             testdb 는 어느 목록에도 없으므로 쓸 수 있다.
-- 재확인   : 생성 후 srvctl config database 에 testdb 가 추가되는지 본다.
--
-- 실무에서도 단일 인스턴스를 RAC 으로 전환한 환경이라면 이런 흔적이 남는다.
-- RAC 에서 신뢰할 목록은 srvctl 쪽이다.
--
-- 만들려는 이름이 이미 쓰이고 있는지 직접 조회해 확인할 수도 있다.

[oracle@rac1 ~]$ srvctl config database -d testdb
PRCD-1120 : The resource for database testdb could not be found.
PRCR-1001 : Resource ora.testdb.db does not exist

-- 오류 : PRCD-1120, PRCR-1001
--
-- 원인 파악 : 여기서는 오류가 나오는 것이 원하는 결과다.
--             testdb 라는 이름의 자원이 없다는 뜻이므로 그 이름을 쓸 수 있다.
--             반대로 이 명령이 구성 정보를 출력했다면 이미 그 이름이
--             쓰이고 있는 것이므로 다른 이름을 골라야 한다.
-- 조치     : 조치할 것이 없다. 계획대로 testdb 를 쓴다.
-- 재확인   : 생성 후 같은 명령을 실행하면 구성 정보가 출력될 것이다.
--             실습 04 [6] 에서 확인한다.
--
-- 오류 메시지가 곧 정상 확인인 경우가 있다는 점을 기억한다.
-- 메시지의 내용을 읽지 않고 오류라는 사실만 보고 판단하면 안 된다.

--------------------------------------------------------------------------------
 [7] 신규 환경이라면 cluvfy
--------------------------------------------------------------------------------

-- 운영 환경에서는 다음을 먼저 돌린다.
--   cluvfy stage -pre dbinst -n rac1,rac2
--
-- 커널 파라미터, 사용자 그룹, 공유 스토리지 접근성 등을 한 번에 검사한다.
--
-- 이 랩은 이미 racdb 가 정상 동작하고 있으므로 그 전제 조건이 모두
-- 충족된 상태다. 그래서 실습에서는 생략하고 dbca 에 -ignorePreReqs 를 준다.
--
-- 주의 : 실무에서 -ignorePreReqs 를 습관적으로 쓰면 안 된다.
--        새 환경이라면 반드시 사전 점검을 통과시킨 뒤 진행한다.

--------------------------------------------------------------------------------
 [8] 계획 확정
--------------------------------------------------------------------------------

-- 여기까지의 확인으로 절차가 정해진다.
--
--  1. 노드      : rac1, rac2 (olsnodes 에서 확인한 이름 그대로)
--  2. 스토리지  : ASM, +DATA (여유 56GB, 충분)
--  3. FRA       : '+FRA' 5000MB (권고보다 작아 경고가 나올 것)
--  4. 메모리    : totalMemory 800 (available 2582/2734 를 감안)
--  5. 부하      : 3.38 / 2.95 — 진행 가능
--  6. 호스트    : 다른 VM 내림 확인
--  7. 이름      : testdb (srvctl 목록과 충돌 없음)
--
-- 5 번과 6 번을 빠뜨리는 것이 이 장에서 가장 위험한 실수다.
