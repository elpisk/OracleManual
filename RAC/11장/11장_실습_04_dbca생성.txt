================================================================================
 제11장 실습 04 — dbca -silent 로 RAC 데이터베이스 생성  ⚠
 대상   : rac1 (인스턴스는 양 노드)
 목표   : 명령행 인자만으로 2노드 RAC 데이터베이스를 만들고, 진행 과정과
          자원 사용을 관찰한다
 소요   : 약 30분 (생성에만 24분 54초)
 선행   : 실습 01 의 점검표를 모두 통과할 것
 계정   : oracle
 주의   : 이 과정에서 가장 무거운 실습이다. 시작 전에 반드시
          호스트의 다른 가상 머신을 내리고 부하가 4 미만인지 확인한다
================================================================================

--------------------------------------------------------------------------------
 [1] 시작 직전 확인
--------------------------------------------------------------------------------

[oracle@rac1 ~]$ cat /proc/loadavg
3.38 3.49 4.08 1/1063 12722

[oracle@rac2 ~]$ cat /proc/loadavg
2.95 3.60 4.84 1/1024 12691

[oracle@rac1 ~]$ free -m | head -2 | tail -1
Mem:           8668        3128         495        2697        5044        2582

-- 부하 3.38 / 2.95, 메모리 2582MB. 진행 가능한 상태다.
-- 이 값들을 기록해 둔다. 생성 중 감시할 때 기준이 된다.

--------------------------------------------------------------------------------
 [2] 실행
--------------------------------------------------------------------------------

[oracle@rac1 ~]$ dbca -silent -createDatabase \
>   -templateName General_Purpose.dbc \
>   -gdbName testdb -sid testdb \
>   -databaseConfigType RAC -adminManaged -nodelist rac1,rac2 \
>   -storageType ASM -diskGroupName DATA \
>   -recoveryAreaDestination '+FRA' -recoveryAreaSize 5000 \
>   -createAsContainerDatabase true -pdbName testpdb \
>   -sysPassword Oracle_4U -systemPassword Oracle_4U -pdbAdminPassword Oracle_4U \
>   -totalMemory 800 -redoLogFileSize 20 \
>   -emConfiguration NONE -sampleSchema false \
>   -ignorePreReqs

[WARNING] [DBT-06801] Specified Fast Recovery Area size (5,000 MB) is less than
   the recommended value.
   CAUSE: Fast Recovery Area size should at least be three times the database
          size (2,384 MB).

Prepare for db operation
7% complete
Copying database files
   ...

-- 실습 02 [4] 에서 확인한 경고가 그대로 나온다.
--
-- 원인 파악 : DBT-06801 은 FRA 크기가 권고보다 작다는 것이다.
--             권고는 데이터베이스 크기 2384MB 의 3 배인 7152MB 인데
--             5000MB 를 줬다.
--             중요한 것은 대괄호 안의 등급이다. [WARNING] 이므로 진행된다.
--             [FATAL] 이었다면 여기서 멈췄을 것이다.
-- 조치     : 실습에서는 그대로 진행한다. FRA 를 백업 용도로 쓰지 않기 때문이다.
--             운영에서는 권고를 따른다. 무시하면 나중에 FRA 가 가득 차
--             아카이브가 멈춘다.
-- 재확인   : 경고 뒤에 "Prepare for db operation" 이 이어지는지 본다.
--             이어진다면 실제로 진행 중이라는 뜻이다.
--
-- 경고가 두 번 나오는 것도 정상이다. 검증 단계와 실행 단계에서 각각 확인한다.

--
--   Creating cluster database views
--     RAC 전용 단계다. GV$ 계열 뷰를 만든다.

--     씨앗 PDB 를 복사해 testpdb 를 만든다.
--
-- 진행률의 폭이 단계마다 다르다. 41% 에서 53% 로 건너뛰기도 한다.
-- 시간에 비례하지 않으므로 진행률만 보고 남은 시간을 짐작하면 안 된다.

-- 부하가 3.4 에서 7.4 사이를 유지했다. 4 vCPU 환경에서 감당할 수 있는 수준이다.
-- 메모리는 3.2 분 시점에 922MB 로 급감했다. 새 인스턴스가 SGA 를 잡은 시점이다.
-- 이후 740MB 까지 내려갔다가 회복했다.
--
-- 비교 — 호스트에 다른 가상 머신이 떠 있을 때의 같은 명령
--
--   [ 4.9분] load=42.78  avail=1137MB
--   [ 8.0분] load=122.59 avail=866MB
--   [10.0분] load=139.42 avail=871MB
--   [12.0분] load=62.33  avail=717MB
--   → 양 노드 축출, dbca 는 7% Copying database files 에서 중단
--
-- 명령과 인자는 사실상 같았다. 차이는 호스트의 여유 CPU 하나뿐이다.
-- 이것이 실습 01 [5] 를 이 장에서 가장 중요한 준비라고 하는 이유다.

[oracle@rac1 ~]$ grep -oE '[0-9]+% complete' \
>   /u01/app/oracle/cfgtoollogs/dbca/testdb/testdb0.log | tail -1
100% complete

-- 25 분짜리 작업이므로 다른 창에서 로그를 따라가면 편하다.
-- 화면 출력이 멈춘 것처럼 보여도 로그는 계속 갱신된다.
--
-- 단계 이름이 파일명에 드러나므로 어디까지 갔는지 알 수 있다.
-- PDBCreation.log 가 보이면 마지막 단계에 들어선 것이다.
--
-- 판단이 필요할 때 세 가지를 본다.
--   1) 로그의 진행률이 올라가는가
--   2) ps -ef | grep dbca 로 프로세스가 살아 있는가
--   3) cat /proc/loadavg 로 실제로 일하고 있는가
--
-- 부하가 0 에 가까운데 진행률도 멈춰 있다면 무언가 대기 중이다.
-- 반대로 부하가 지나치게 높다면 그것이 위험 신호다.

 [6] 완료 직후 확인

      1        ONLINE  ONLINE       rac1     Open,HOME=/u01/app/oracle/...,STABLE
      2        ONLINE  ONLINE       rac2     Open,HOME=/u01/app/oracle/...,STABLE

[oracle@rac1 ~]$ srvctl config database
racdb
testdb

[oracle@rac1 ~]$ srvctl status database -d testdb -v
Instance testdb1 is running on node rac1. Instance status: Open.
Instance testdb2 is running on node rac2. Instance status: Open.

-- CRS 자원이 자동으로 등록되었고 양 노드에서 ONLINE 이다.
-- srvctl config database 에 testdb 가 추가되었다.
--
-- 9장에서 asmca 가 디스크그룹을 만들며 CRS 자원을 함께 등록한 것과 같다.
-- Oracle 의 구성 도구들은 CRS 등록까지 함께 처리한다.
--
-- 수동으로 데이터베이스를 만들었다면 srvctl add database 로 직접 등록해야 하고
-- 그 단계를 빠뜨리면 노드 재부팅 후 자동으로 올라오지 않는다.
--
-- 여기까지는 "만들어졌다" 는 확인이다.
-- "RAC 으로 만들어졌는가" 는 실습 05 에서 검증한다.
