--
-- 실습 01 [2] 의 생성 전 값과 비교하면
--   +DATA  56906 → 53371  (3535MB 감소, testdb 가 차지)

--   +CRS   11324 → 11324  (변화 없음)
--
-- /etc/oratab 에 testdb 항목이 없는 것이 눈에 띈다.
-- RAC 데이터베이스는 CRS 가 관리하므로 oratab 에 넣지 않는다.
-- 실습 01 [6] 에서 두 목록이 다를 수 있다고 한 것과 이어진다.

--------------------------------------------------------------------------------
 [2] 오류 재현 — 없는 데이터베이스를 지우려 하면
--------------------------------------------------------------------------------

[oracle@rac1 ~]$ dbca -silent -deleteDatabase -sourceDB nosuchdb \
>   -sysDBAUserName sys -sysDBAPassword Oracle_4U

[FATAL] [DBT-05511] Specified database (nosuchdb) does not exist.
   ACTION: Provide an existing database.
[WARNING] [DBT-11503] The instance (nosuchdb) is not running on the local node.
   This may result in partial delete of Oracle database.
   CAUSE: A locally running instance is required for complete deletion of
          Oracle database instance and database files.
   ACTION: Specify a locally running database, or execute DBCA on a node where
           the database instance is running.

-- 오류 : DBT-05511, DBT-11503(경고)
--
-- 원인 파악 : DBT-05511 은 이름이 틀렸다는 것을 알려 준다. 단순한 오타 확인이다.
--             더 중요한 것은 DBT-11503 이다.
--             "완전한 삭제를 위해서는 로컬에 인스턴스가 돌고 있어야 한다."
--             삭제할 때 실행 노드를 아무 데나 골라서는 안 된다는 뜻이다.
-- 조치     : 인스턴스가 살아 있는 노드에서 실행한다.
--             데이터베이스가 이미 내려가 있다면 먼저 올린 뒤 지운다.
-- 재확인   : srvctl status database -d testdb -v 로 로컬 노드에 인스턴스가
--             running 인지 확인하고 삭제를 진행한다.

[oracle@rac1 ~]$ srvctl status database -d testdb -v
Instance testdb1 is running on node rac1. Instance status: Open.
Instance testdb2 is running on node rac2. Instance status: Open.

-- rac1 에 testdb1 이 돌고 있으므로 rac1 에서 실행하면 된다.
-- dbca 는 실행 노드를 기준으로 다른 노드의 것까지 정리하므로 한 번만 실행한다.

--------------------------------------------------------------------------------

--   /etc/oratab 항목
--
-- 양 노드를 모두 확인하는 것이 중요하다.
-- dbca 는 실행 노드에서 다른 노드의 것까지 정리하지만 확인은 직접 해야 한다.

--------------------------------------------------------------------------------
 [5] 무엇이 남았는가
--------------------------------------------------------------------------------

[grid@rac1 ~]$ asmcmd ls +DATA
RACDB/
TESTDB/

[grid@rac1 ~]$ asmcmd ls +FRA
RACDB/

-- +FRA 는 깨끗한데 +DATA 에 TESTDB 디렉터리가 남았다.
-- 위험한 상태인지 확인한다.

[grid@rac1 ~]$ asmcmd du +DATA/TESTDB
Used_MB      Mirror_used_MB
      0                   0

[grid@rac1 ~]$ asmcmd ls -l +DATA/TESTDB
   (파일 없음)

-- 원인 파악 : 0MB 다. 파일은 모두 지워졌고 빈 디렉터리만 남았다.
--             ASM 의 디렉터리는 파일이 만들어질 때 자동으로 생기지만
--             파일이 없어져도 자동으로 사라지지 않는다.
--             7장에서 다룬 별칭 계층의 특성이다.
-- 조치     : 0MB 임을 확인한 뒤 수동으로 지운다.
-- 재확인   : 지운 뒤 +DATA 에 RACDB 만 남는지 본다.

[grid@rac1 ~]$ asmcmd rm -rf +DATA/TESTDB

[grid@rac1 ~]$ asmcmd ls +DATA
RACDB/

-- 정리되었다.
-- 공간을 차지하지는 않으므로 급하지는 않지만, 남겨 두면 다음 사람이
-- "이 데이터베이스가 아직 있나" 하고 혼란스러워한다.

[oracle@rac1 ~]$ ls /u01/app/oracle/cfgtoollogs/dbca/
KNH  orcl  PROD  racdb  testdb  wdba
silent.log_2026-09-04_10-46-46AM
trace.log_2026-09-04_10-46-46AM
   ... 이전 실행 기록들

-- 로그 디렉터리도 남았다. 이것은 의도적이며 지우지 않는 것을 권한다.
-- 무엇을 어떻게 만들고 지웠는지가 기록으로 남아야 하기 때문이다.
-- 삭제 명령이 알려 준 testdb1.log 도 여기 있다.
--
-- 목록에 KNH, orcl, PROD 도 보인다. 이 노드를 만들 때 쓴 템플릿 VM 에서
-- 물려받은 것으로, 데이터베이스를 지워도 로그는 남는다는 것을 보여 준다.

 [6] 정리 대상 요약
--------------------------------------------------------------------------------

--  대상                      dbca -deleteDatabase   사람이 할 일
--  ------------------------  ---------------------  -----------------
--  CRS 자원 등록              지운다                 확인만
--  데이터파일·리두·컨트롤     지운다                 확인만
--  admin 디렉터리 (양 노드)   지운다                 확인만
--  /etc/oratab 항목           지운다                 확인만
--  ASM 의 빈 디렉터리         남긴다                 asmcmd rm -rf
--  cfgtoollogs 로그           남긴다                 보존 권장

--------------------------------------------------------------------------------
 [7] 생성이 중간에 실패했다면 — 수동 정리
--------------------------------------------------------------------------------

-- 이 실습에서는 삭제가 정상적으로 끝났지만, 생성이 도중에 실패하면 다르다.
-- 이 랩에서 실제로 그런 일이 있었다.
--
-- 호스트 자원이 부족한 상태로 dbca 를 돌렸다가 7% 지점에서 중단시켰을 때
-- 남은 것들은 이랬다.
--   CRS 에 ora.testdb.db 자원이 등록되어 있었다
--   srvctl config database 에 testdb 가 보였다
--   +DATA 에 TESTDB 디렉터리가 있었다
--   양 노드에 admin 디렉터리가 만들어져 있었다
--   /etc/oratab 에는 항목이 없었다
--
-- 이 상태에서는 dbca -deleteDatabase 가 동작하지 않을 수 있다.
-- 데이터베이스가 정상적으로 만들어지지 않아 인스턴스를 띄울 수 없기 때문이다.
-- DBT-11503 이 요구하는 "로컬에 돌고 있는 인스턴스" 가 없다.
--
-- 수동 정리 순서
--
--   1. CRS 자원을 제거한다
--      $ srvctl remove database -d testdb -force -noprompt
--      -force 는 자원이 정상 상태가 아니어서 필요하고
--      -noprompt 는 확인 질문을 건너뛴다
--
--   2. 제거되었는지 확인한다
--      $ srvctl config database
--      $ crsctl stat res -t | grep -i testdb
--
--   3. ASM 디렉터리를 지운다
--      $ asmcmd ls +DATA        (남은 것 확인)
--      $ asmcmd rm -rf +DATA/TESTDB
--      +FRA 쪽도 확인한다
--
--   4. 양 노드의 admin 디렉터리를 지운다
--      $ rm -rf /u01/app/oracle/admin/testdb    (rac1, rac2 각각)
--
--   5. /etc/oratab 에 항목이 있으면 지운다 (양 노드)
--
--   6. 디스크그룹 여유가 원래 값으로 돌아왔는지 본다
--
-- 순서가 중요하다. CRS 자원을 먼저 지워야 한다.
-- 파일을 먼저 지우면 CRS 가 없는 파일을 찾으며 오류를 내고 정리가 복잡해진다.

--------------------------------------------------------------------------------
 [8] 기준선 복귀 확인
--------------------------------------------------------------------------------

[grid@rac1 ~]$ sqlplus -s / as sysasm

SQL> select name, total_mb, free_mb from v$asm_diskgroup order by group_number;

NAME       TOTAL_MB    FREE_MB
-------- ---------- ----------
CRS           12288      11300
DATA          61440      56896
FRA           24576      23636

3 rows selected.

SQL> select header_status, count(*) from v$asm_disk group by header_status order by 1;

HEADER_STATU   COUNT(*)
------------ ----------
FORMER                6
MEMBER                8

2 rows selected.

-- 생성 전 값과 비교한다.
--   +FRA   23636 → 23636   정확히 같다
--   +DATA  56906 → 56896   10MB 적다
--   +CRS   11324 → 11300   24MB 적다
--
-- 원인 파악 : 이 차이는 잔여 파일이 아니라 메타데이터다.
--             디스크그룹에 파일을 만들고 지우면 익스텐트 맵과 디렉터리
--             항목이 갱신되면서 소량이 소비된다.
--             +CRS 쪽 감소는 자원을 OCR 에 등록하고 해제한 흔적이다.
--             데이터베이스 파일이 하나도 들어가지 않은 +CRS 가 줄어든 것이
--             그 증거다.
-- 조치     : 조치할 것이 없다. 정상이다.
-- 재확인   : 판단 기준은 규모다. 10~30MB 수준은 정상이고
--             수백 MB 이상 벌어져 있다면 잔여 파일을 찾아야 한다.
--             그때는 asmcmd du 로 디스크그룹을 훑어 어디가 차 있는지 본다.
--
-- 디스크 헤더 상태는 FORMER 6 / MEMBER 8 로 변화가 없다.
-- 이 장에서 디스크를 건드리지 않았으므로 당연하다.

[oracle@rac1 ~]$ srvctl config database
racdb

[grid@rac1 ~]$ crsctl check cluster -all | grep -c "is online"
6

[oracle@rac1 ~]$ srvctl status database -d racdb -v
Instance racdb1 is running on node rac1. Instance status: Open.
Instance racdb2 is running on node rac2. Instance status: Open.

[oracle@rac1 ~]$ export ORACLE_SID=racdb1
SQL> select sid, count(*) cnt from v$spparameter where isspecified='TRUE'
  2   group by sid order by 1;

SID               CNT
---------- ----------
*                  24
racdb1              3
racdb2              3

SQL> col name for a12
SQL> select inst_id, con_id, name, open_mode from gv$pdbs order by 1,2;

   INST_ID     CON_ID NAME         OPEN_MODE
---------- ---------- ------------ ----------
         1          2 PDB$SEED     READ ONLY
         1          3 RACPDB1      READ WRITE
         2          2 PDB$SEED     READ ONLY
         2          3 RACPDB1      READ WRITE

4 rows selected.

-- 확인 항목과 기대값
--   1. 등록된 데이터베이스     → racdb 만                 ✓
--   2. CRS 자원                → testdb 관련 없음         ✓
--   3. ASM                     → +DATA 와 +FRA 에 RACDB 만 ✓
--   4. 디스크그룹 여유         → FRA 23636, 소량 차이 정상 ✓
--   5. 디스크 헤더             → FORMER 6 / MEMBER 8      ✓
--   6. OS 잔여물               → admin·oratab 없음        ✓
--   7. 클러스터                → online 6줄               ✓
--   8. racdb                   → 두 인스턴스 Open         ✓
--   9. racdb SPFILE            → 24 / 3 / 3               ✓
--  10. racdb PDB               → 4행, 양 노드 READ WRITE  ✓
--
-- 8~10 이 중요하다. 새 데이터베이스를 만들고 지우는 동안
-- 기존 racdb 가 아무 영향도 받지 않았음을 확인하는 것이다.
