 제14장 실습 10 — crsctl 필터와 출력 형식, 필요한 줄만 뽑아 읽기
 대상   : rac1
 목표   : -w 필터, -t · -p · -v 출력, -attr · -noname 조합으로 자원 목록에서
          점검에 필요한 것만 뽑는다. 필터를 틀리게 썼을 때 오류가 나는 경우와
          조용히 빈 결과가 나오는 경우를 구분한다
 소요   : 약 20분
 선행   : 실습 03 · 05 완료
 계정   : grid
 주의   : 조회만 한다
================================================================================

--------------------------------------------------------------------------------
 [1] 기준선
--------------------------------------------------------------------------------

[grid@rac1 ~]$ crsctl stat res | grep -c '^NAME='
18
[grid@rac1 ~]$ crsctl stat res -t | wc -l
68

-- 자원은 18 개인데 -t 표는 68 줄이다. 인스턴스마다 줄이 생기고
-- 상태 설명이 줄을 넘기기 때문이다. 점검 때 이 표를 다 읽지 않고 걸러 본다.

--------------------------------------------------------------------------------
 [3] 점검용 필터 — 떠 있어야 하는데 안 떠 있는 것
--------------------------------------------------------------------------------

[grid@rac1 ~]$ crsctl stat res -t -w "((TARGET = ONLINE) and (STATE != ONLINE))"
--------------------------------------------------------------------------------
Name           Target  State        Server                   State details
--------------------------------------------------------------------------------
Cluster Resources
--------------------------------------------------------------------------------
ora.ASMNET1LSNR_ASM.lsnr(ora.asmgroup)
      3        ONLINE  OFFLINE                               STABLE
--------------------------------------------------------------------------------

-- 실습 03 의 판단 기준(TARGET 과 STATE 가 다르면 본다)을 필터 하나로 만든 것이다.
-- 68 줄 표가 한 건으로 줄었다. 매일 보는 점검 명령으로 쓰기 좋다.
--
-- 그런데 걸린 한 건이 장애인가. 카디널리티를 본다.

[grid@rac1 ~]$ crsctl stat res ora.ASMNET1LSNR_ASM.lsnr -p -attr CARDINALITY
NAME=ora.ASMNET1LSNR_ASM.lsnr
CARDINALITY=3
[grid@rac1 ~]$ crsctl stat res ora.asm -p -attr CARDINALITY
NAME=ora.asm
CARDINALITY=3

-- Flex ASM 의 기본 카디널리티가 3 이다. 노드는 둘뿐이라 세 번째를 띄울 곳이 없다.
-- ASM 리스너의 3 번은 TARGET 이 ONLINE 이라 필터에 걸렸고, ASM 과 디스크그룹의
-- 3 번은 TARGET 이 OFFLINE 이라 걸리지 않았다([4]).
-- 이 랩에서는 정상이다. 이 한 줄을 기준선으로 적어 두고, 다른 것이 걸리면 본다.

-- -p 가 정의라면 -v 는 지금 상태다. 인스턴스마다 한 덩어리씩 나온다.
--
-- 점검에서 볼 값.
--   RESTART_COUNT · FAILURE_COUNT  Clusterware 가 되살린 횟수 · 실패 횟수
--   LAST_RESTART                    마지막으로 기동된 시각
--   INCARNATION                     기동될 때마다 올라간다
-- 두 번째 인스턴스는 INCARNATION 이 4, LAST_RESTART 가 14:16:17 이다.
-- 실습 08 에서 racdb2 를 재기동한 시각이다. RESTART_COUNT 는 0 이다.
-- 사람이 srvctl 로 올린 것은 "되살린 것" 으로 세지 않는다.

[grid@rac1 ~]$ crsctl stat res ora.racdb.db -v -attr RESTART_COUNT,FAILURE_COUNT,LAST_SERVER,LAST_STATE_CHANGE,STATE_DETAILS -noname
RESTART_COUNT=0
FAILURE_COUNT=0
LAST_SERVER=rac1
LAST_STATE_CHANGE=1794191657
STATE_DETAILS=Open,HOME=/u01/app/oracle/product/19.3.0/dbhome_rac
RESTART_COUNT=0
FAILURE_COUNT=0
LAST_SERVER=rac2
LAST_STATE_CHANGE=1794201377
STATE_DETAILS=Open,HOME=/u01/app/oracle/product/19.3.0/dbhome_rac

-- -attr 로 고르면 짧아진다. -noname 은 NAME= 줄을 뺀다.
-- 같은 LAST_STATE_CHANGE 가 이번에는 숫자(유닉스 시각)로 나왔다.
-- 1794201377 은 2026-11-09 14:16:17(KST)다. 출력 형식에 따라 값의 표현이
-- 달라지므로, 스크립트로 비교할 때는 한 형식으로 정해 쓴다.

--------------------------------------------------------------------------------
 [6] -p -attr — 재기동 규칙만 뽑기
--------------------------------------------------------------------------------

[grid@rac1 ~]$ crsctl stat res ora.racdb.db -p -attr RESTART_ATTEMPTS,UPTIME_THRESHOLD,FAILURE_THRESHOLD,FAILURE_INTERVAL,CHECK_INTERVAL,SCRIPT_TIMEOUT,START_TIMEOUT,STOP_TIMEOUT
NAME=ora.racdb.db
RESTART_ATTEMPTS=2
UPTIME_THRESHOLD=1h
FAILURE_THRESHOLD=1
FAILURE_INTERVAL=60
CHECK_INTERVAL=900
SCRIPT_TIMEOUT=60
START_TIMEOUT=600
STOP_TIMEOUT=600

-- 실습 05 에서 전체 속성으로 본 값 중 재기동에 관한 것만 골랐다.
--   RESTART_ATTEMPTS 2 · UPTIME_THRESHOLD 1h
--     한 시간 안에 두 번까지 같은 노드에서 되살린다(20장 실습 06 의 CRS-2771).
--   CHECK_INTERVAL 900
--     에이전트가 정기 점검을 하는 간격이 900 초다(15 분).
--   START_TIMEOUT · STOP_TIMEOUT 600
--     10 분 안에 기동 · 정지가 끝나지 않으면 실패로 본다.

--------------------------------------------------------------------------------
 [7] 흔한 오류 — 필터를 틀리게 쓰면
--------------------------------------------------------------------------------

[grid@rac1 ~]$ crsctl stat res -t -w "TYPE =ora.database.type"
CRS-2594: Filter specification 'TYPE =ora.database.type' is invalid

CRS-4000: Command Status failed, or completed with errors.

[grid@rac1 ~]$ crsctl stat res -t -w "TYPE = ora.databse.type"
[grid@rac1 ~]$

-- 원인 파악 : 두 실수가 전혀 다르게 나타난다.
--               연산자 뒤 공백 누락     CRS-2594. 필터를 해석하지 못했다
--               값의 철자 오류          아무것도 안 나온다. 오류도 없다
--             필터 문법은 "속성 연산자 값" 을 공백으로 나눠 쓴다.
--             값이 틀린 경우는 "맞는 자원이 없다" 와 구분이 안 된다.
--             점검 스크립트에서 이 명령의 결과가 비었을 때 "문제없음" 으로
--             처리하면 철자 하나 때문에 점검이 통째로 무력해진다.
-- 조치     : 유형 이름은 crsctl stat res -p -attr TYPE 이나 [5] 의 TYPE= 줄에서 복사한다.
--             점검 스크립트에는 반드시 결과가 나오는 필터(예: [2] 의 첫 명령)를
--             함께 돌려 필터가 살아 있는지 확인한다.
-- 재확인   : 같은 필터에서 -t 를 빼고 NAME= 줄 수를 센다.
