================================================================================
 제15장 실습 01 — 기본 서비스 확인, 뷰와 리스너에서 읽기
 대상   : rac1
 목표   : 사용자 서비스가 없는 상태에서도 존재하는 기본 서비스를 확인하고,
          로컬 리스너와 SCAN 리스너가 무엇을 다르게 보여 주는지 익힌다
 소요   : 약 25분
 선행   : racdb 양 노드 OPEN, 부하 4 이하
 계정   : oracle, grid
================================================================================

--------------------------------------------------------------------------------
 [0] 상태 확인
--------------------------------------------------------------------------------

Instance racdb1 is running on node rac1. Instance status: Open.
Instance racdb2 is running on node rac2. Instance status: Open.

-- 이 실습은 조회뿐이라 부하를 거의 만들지 않는다.

--------------------------------------------------------------------------------
 [1] 사용자 서비스는 하나도 없다
--------------------------------------------------------------------------------

[oracle@rac1 ~]$ srvctl status service -d racdb
[oracle@rac1 ~]$ echo $?
0

[oracle@rac1 ~]$ srvctl config service -d racdb
[oracle@rac1 ~]$ echo $?
0

-- 아무것도 출력되지 않는다. 오류가 아니라 사용자 서비스가 없다는 뜻이다.
-- 종료 코드가 0 인 것이 근거다.
--
-- 출력이 없는 것과 실패하는 것을 구분하는 습관이 필요하다.
-- 14장에서 crsctl add resource 가 성공해도 아무것도 출력하지 않았던 것과
-- 같은 관례다.

[oracle@rac1 ~]$ srvctl config database -d racdb | grep -i 'Services'
Services:

-- 데이터베이스 정의에도 Services 항목이 비어 있다.

--------------------------------------------------------------------------------
 [2] 그런데 데이터베이스에는 서비스가 있다
--------------------------------------------------------------------------------

SQL> select inst_id, name, network_name, con_id
  2    from gv$active_services order by inst_id, name;

   INST_ID NAME             NETWORK_NAME     CON_ID
---------- ---------------- ---------------- ------
         1 SYS$BACKGROUND                         1
         1 SYS$USERS                              1
         1 racdb            racdb                 1
         1 racdbXDB         racdbXDB              1
         1 racpdb1          racpdb1               3
         2 SYS$BACKGROUND                         1
         2 SYS$USERS                              1
         2 racdb            racdb                 1
         2 racdbXDB         racdbXDB              1
         2 racpdb1          racpdb1               3

10 rows selected.

-- 다섯 개가 인스턴스마다 하나씩이라 10 행이다. 5 x 2 = 10.
-- 이 숫자를 기준선으로 기록해 둔다. 실습 07 에서 이 값으로 돌아와야 한다.
--
-- 각각의 성격이 다르다.
--
--   SYS$BACKGROUND  백그라운드 프로세스의 서비스. 내부용.
--   SYS$USERS       서비스 이름 없이 접속한 세션이 속하는 곳. 내부용.
--                   이 둘은 지울 수도 옮길 수도 없다.
--   racdb           DB 이름과 같은 기본 서비스. dbca 가 만들었다.
--   racdbXDB        XML DB 용. 쓰지 않으면 신경 쓰지 않아도 된다.
--   racpdb1         PDB 서비스. PDB 를 만들 때 자동으로 생긴다.
--
-- NETWORK_NAME 이 비어 있는 둘이 내부 서비스다. 클라이언트가 그 이름으로
-- 접속할 수 없다는 뜻이다.
--
-- CON_ID 를 눈여겨본다. racpdb1 만 3 이고 나머지는 1 이다.
-- 12장에서 다룬 컨테이너 번호이며 3 이 RACPDB1 이다.

--------------------------------------------------------------------------------
 [3] DBA_SERVICES 는 왜 4행뿐인가
--------------------------------------------------------------------------------

SQL> select service_id, name, network_name, goal, clb_goal
  2    from dba_services order by service_id;

SERVICE_ID NAME             NETWORK_NAME     GOAL   CLB_G
---------- ---------------- ---------------- ------ -----
         1 SYS$BACKGROUND                           LONG
         2 SYS$USERS                                LONG
         5 racdbXDB         racdbXDB                LONG
         6 racdb            racdb                   LONG

4 rows selected.

-- racpdb1 이 없다.
--
-- 이 뷰가 현재 컨테이너의 서비스만 보여 주기 때문이다.
-- CDB$ROOT 에서 조회했으므로 CON_ID 3 의 PDB 서비스는 나오지 않는다.
-- PDB 에 접속해 같은 뷰를 조회하면 racpdb1 이 나온다.
--
-- 두 뷰의 시야가 다르다는 것을 알아 두자.
--   GV$ACTIVE_SERVICES  인스턴스 전체를 본다. 지금 활성인 것.
--   DBA_SERVICES        현재 컨테이너의 정의를 본다.
--
-- SERVICE_ID 가 1·2·5·6 으로 건너뛴다. 3·4 는 CDB 내부용으로 예약되어 있다.
-- 10장에서 데이터파일 번호가 연속이 아니었던 것과 같은 이야기다.
-- 번호를 세어 개수를 짐작하는 습관은 버려야 한다.

SQL> select con_id, name, open_mode from v$pdbs order by con_id;

    CON_ID NAME                 OPEN_MODE
---------- -------------------- ------------
         2 PDB$SEED             READ ONLY
         3 RACPDB1              READ WRITE

2 rows selected.

-- CON_ID 3 이 RACPDB1 임을 확인했다. [2] 의 racpdb1 서비스가 이 PDB 의 것이다.

--   (1) Endpoints 에 IP 가 둘이다.

--       리스너 하나가 둘 다 듣는다.

--------------------------------------------------------------------------------
 [5] 진단 — 리스너에 남은 옛 서비스
--------------------------------------------------------------------------------

-- 위 목록에 +ASM_CH9DG 가 있다. 9장에서 만들었다 지운 디스크그룹의 것이다.

[grid@rac1 ~]$ asmcmd lsdg | awk '{print $1, $NF}'
State Name
MOUNTED CRS/
MOUNTED DATA/
MOUNTED FRA/

[grid@rac1 ~]$ crsctl stat res ora.CH9DG.dg
CRS-2613: Could not find resource 'ora.CH9DG.dg'.

-- 원인 파악 : 디스크그룹도 CRS 자원도 이미 없다. 리스너에만 남았다.
--             리스너의 서비스 목록은 인스턴스가 등록해 준 것을 담고 있고,
--             등록을 취소하는 신호가 오지 않으면 리스너를 재시작할 때까지
--             그대로 남는다.
--             14장에서 데이터베이스 자원의 pullup 절에 ora.CH9DG.dg 가
--             남아 있던 것과 같은 종류의 흔적이다.
-- 조치     : 접속에는 영향이 없으므로 급히 고칠 일은 아니다.
--             없는 서비스로 접속하면 ORA-12514 가 날 뿐이다.
--             정리하려면 리스너를 재시작한다.
--               srvctl stop listener -n rac1
--               srvctl start listener -n rac1
--             이 실습에서는 관찰만 하고 그대로 둔다.
-- 재확인   : 재시작 후 lsnrctl status LISTENER 에서 +ASM_CH9DG 가
--             사라졌는지 본다.

-- 배울 것 하나. 테스트로 만든 것을 지울 때 여러 곳에 자국이 남는다.
-- 정리 절차를 만들 때 지워야 할 곳이 하나가 아니라는 감각이 필요하다.

-- 차이가 분명하다.
--
--   Endpoint 가 SCAN IP 172.16.225.120 하나다.
--   각 서비스가 has 2 instance(s) 이고 양 인스턴스가 등록되어 있다.
--   +ASM 계열 서비스는 없다. ASM 은 SCAN 을 통해 접속하지 않는다.
--
-- 이 숫자가 SCAN 이 고를 수 있는 후보의 수다.
--   1 이면 갈 곳이 하나뿐이라 결정적이다.
--   2 이면 부하 기반 선택이 일어난다. 실습 07 에서 확인한다.
--
-- 트러블슈팅에서 두 리스너를 구분해야 한다.
--   로컬에 없다  → 그 노드의 인스턴스가 등록하지 않았다.
--                   그 서비스가 다른 노드에서 돌고 있을 수 있다.
--   SCAN 에 없다 → 클러스터 어디에서도 그 서비스가 돌지 않는다.

--------------------------------------------------------------------------------
 [7] 왜 서비스가 필요한가
--------------------------------------------------------------------------------

-- 서비스 없이도 접속은 된다. 기본 서비스 racdb 로 붙으면
-- SCAN 이 알아서 인스턴스를 골라 준다. 그런데 그것으로 부족한 경우가 있다.
--
--   (1) 부하를 의도적으로 나누고 싶을 때.
--       13장에서 rac1 의 redo size 가 rac2 의 약 1.8배였다.
--       OLTP 는 rac1, 야간 배치는 rac2 로 보내면 서로 방해하지 않는다.
--
--   (2) 접속의 성격을 이름으로 구분하고 싶을 때.
--       GV$SESSION 의 SERVICE_NAME 으로 세션을 분류할 수 있다.
--
--   (3) 장애 시 접속을 옮기고 싶을 때.
--       선호 인스턴스가 죽으면 가용 인스턴스로 옮겨 간다.
--
--   (4) 유지보수 때 접속을 미리 비우고 싶을 때.
--       노드를 내리기 전에 서비스를 옮기면 새 접속이 그쪽으로 가지 않는다.
--
-- 다음 실습에서 (1) 을 위한 서비스 둘을 만든다.
