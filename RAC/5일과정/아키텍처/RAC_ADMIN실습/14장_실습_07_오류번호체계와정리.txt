 대상   : rac1, rac2

          익힌다. 실습 06 에서 만든 자원과 파일을 모두 지우고 기준선을 확인한다
 소요   : 약 25분

--------------------------------------------------------------------------------
 [1] 접두어별로 정리
--------------------------------------------------------------------------------

접두어      계층                        이 장에서 만난 예
---------- --------------------------- ------------------------------------
CRS-       Clusterware 자원 계층        CRS-2613, CRS-4995, CRS-4000,
                                        CRS-2672/2676, CRS-2673/2677
PRKO-      srvctl 명령행 해석           PRKO-2002, PRKO-3032
PRCD-      srvctl 데이터베이스 계층     PRCD-1120
PRCR-      srvctl 자원 계층             PRCR-1001, PRCR-1004
PRCC-      srvctl 공통 계층             PRCC-1015

-- 앞선 장에서 만난 것도 함께 정리해 둔다.
--
--   CLSRSC-   root.sh 같은 root 스크립트     (2장)
--   INS-      설치 프로그램                  (3장)
--   PRV-      cluvfy 검증 도구               (4장)
--   ORA-      데이터베이스                   (전 장)
--   DBT-      dbca                           (11장)
--
-- 접두어만 봐도 어디를 볼지 좁혀진다.
--   PRKO 면 내가 친 명령을 다시 본다
--   CRS 면 자원 상태를 본다
--   CLSRSC 면 설치 로그를 본다
--   ORA 면 데이터베이스 알럿 로그를 본다

--------------------------------------------------------------------------------
 [2] 겹쳐 나오는 오류를 읽는 규칙
--------------------------------------------------------------------------------

[oracle@rac1 ~]$ srvctl status database -d nodb
PRCD-1120 : The resource for database nodb could not be found.   <- 상위
PRCR-1001 : Resource ora.nodb.db does not exist                  <- 하위

-- 원인 파악 : 두 줄은 계층이 다르다. 위는 상위 계층의 해석이고
--             아래는 하위 계층의 사실이다.
--             상위는 "무엇을 하려다 실패했는가" 를,
--             하위는 "왜 실패했는가" 를 말한다.
--             진짜 원인은 아래에 있다.
-- 조치     : 마지막 줄을 먼저 읽는다. 여기서는 ora.nodb.db 라는 자원이
--             없다는 것이 사실이며, 데이터베이스 이름을 확인해야 한다.
--               srvctl config database -h 로 목록 조회 방법을 보거나
--               crsctl stat res | grep '\.db$' 로 등록된 DB 자원을 찾는다.
-- 재확인   : 올바른 이름으로 실행해 정상 출력이 나오는지 본다.

[oracle@rac1 ~]$ crsctl stat res | grep '.db$'
NAME=ora.racdb.db

[oracle@rac1 ~]$ srvctl status database -d racdb -v
Instance racdb1 is running on node rac1. Instance status: Open.
Instance racdb2 is running on node rac2. Instance status: Open.

-- 같은 구조를 앞선 장에서도 만났다.
--   13장  ORA-02097 (파라미터를 못 바꾼다) + ORA-30013 (UNDO 가 사용 중)
--         위는 정보가 없고 아래가 진짜 이유였다.
--
-- 규칙 하나로 정리된다. 마지막 줄을 먼저 읽는다.

--------------------------------------------------------------------------------
 [3] 오류처럼 보이지만 정상인 경우
--------------------------------------------------------------------------------

[oracle@rac1 ~]$ srvctl start instance -d racdb -i racdb1
PRCC-1015 : racdb was already running on rac1
PRCR-1004 : Resource ora.racdb.db is already running

-- 이것은 원하는 결과다. 이미 떠 있다는 뜻이다.
--
-- 야간 당직에서 알림 시스템이 첫 줄만 잘라 보내면 이것을 장애로
-- 오해하기 쉽다. 대처는 이렇다.
--
--   (1) 같은 조회 명령을 직접 실행해 전체 메시지를 본다.
--       조회 명령은 상태를 바꾸지 않으므로 안전하다.
--   (2) 가능하면 알림이 두 줄까지 보내도록 설정을 고친다.
--   (3) 종료 코드도 함께 기록하게 한다. 메시지만으로는
--       정상인 경우와 진짜 오류를 구분하기 어렵다.
--
-- 스크립트에서는 기동 전에 srvctl status 로 상태를 먼저 확인하는 것이
-- 깔끔하다. 기동·정지 스크립트는 멱등해야 한다.

--------------------------------------------------------------------------------
 [4] 정리 — 자원 정지와 삭제
--------------------------------------------------------------------------------

-- 먼저 실습 06 에서 만든 플래그 파일을 지워 스크립트를 정상으로 되돌린다.

[root@rac1 ~]# rm -f /tmp/ch14app.broken /tmp/ch14app.nostart
[root@rac2 ~]# rm -f /tmp/ch14app.broken /tmp/ch14app.nostart

[grid@rac1 ~]$ crsctl stat res ch14.app -t
ch14.app
      1        ONLINE  OFFLINE                               STABLE

-- 순서가 있다. 정지한 뒤에 지운다.

[grid@rac1 ~]$ crsctl stop resource ch14.app
[grid@rac1 ~]$ crsctl delete resource ch14.app

[grid@rac1 ~]$ crsctl stat res ch14.app
CRS-2613: Could not find resource 'ch14.app'.

-- CRS-2613 이 나오면 정상적으로 지워진 것이다.
-- 실습 03 에서 자원 이름을 잘못 써서 만난 그 오류와 같은 번호인데
-- 여기서는 확인 수단으로 쓰인다. 같은 오류가 상황에 따라 다르게 읽힌다.

--------------------------------------------------------------------------------

-- 양 노드를 함께 확인한다. 한 노드만 지우기 쉬운 실수다.

--------------------------------------------------------------------------------
 [6] 기준선 확인
--------------------------------------------------------------------------------

[grid@rac1 ~]$ crsctl stat res | grep -c '^NAME='
17

[grid@rac1 ~]$ crsctl stat res -init | grep -c '^NAME='
13

[grid@rac2 ~]$ crsctl stat res -init | grep -c '^NAME='
13

[grid@rac1 ~]$ crsctl check cluster -all
**************************************************************
rac1:
CRS-4537: Cluster Ready Services is online
CRS-4529: Cluster Synchronization Services is online
CRS-4533: Event Manager is online
**************************************************************
rac2:
CRS-4537: Cluster Ready Services is online
CRS-4529: Cluster Synchronization Services is online
CRS-4533: Event Manager is online
**************************************************************

[oracle@rac1 ~]$ srvctl status database -d racdb -v
Instance racdb1 is running on node rac1. Instance status: Open.
Instance racdb2 is running on node rac2. Instance status: Open.

-- 일반 자원 17개로 돌아왔다. -init 은 13개로 변화 없다.
-- 사용자 자원은 -init 목록에 영향을 주지 않으므로 당연하다.
-- 스택과 데이터베이스도 정상이다.

--------------------------------------------------------------------------------
 [7] 이 장의 점검 항목
--------------------------------------------------------------------------------

주기      확인 항목                          명령
-------- ---------------------------------- ------------------------------------
매일      모든 노드의 스택                   crsctl check cluster -all
매일      자원 상태와 개수 (17)              crsctl stat res -t
매일      인스턴스 상태                      srvctl status database -d racdb -v
주간      각 노드의 -init 자원 (13)          crsctl stat res -t -init
수시      사용자 자원의 상태와 액션 로그     crsctl stat res <이름> -t + 로그 파일

-- 12장의 SPFILE 점검, 13장의 스토리지 점검과 합치면 일상 점검의
-- 뼈대가 갖춰진다.
--
-- 배열 순서를 클러스터 계층(14장) → 인스턴스 계층(12장) →
-- 스토리지 계층(13장) 으로 잡으면 장애 시 그대로 진단 순서가 된다.
--
-- 자원 개수를 기준선으로 기록해 두는 것이 특히 유용하다.
-- 개수가 달라졌다는 것은 누군가 자원을 추가하거나 제거했다는 뜻이며
-- 변경 이력을 추적할 실마리가 된다.
