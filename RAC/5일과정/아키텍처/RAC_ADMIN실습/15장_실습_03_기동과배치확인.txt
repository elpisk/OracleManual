================================================================================
 제15장 실습 03 — 서비스 기동과 배치 확인
 대상   : rac1
 목표   : 서비스를 기동하고 배치를 네 각도로 확인한다. 실제 접속이 의도한
          인스턴스로 가는지까지 검증한다
 소요   : 약 25분
 선행   : 실습 02 완료 (서비스 2개가 정지 상태로 존재)
 계정   : oracle, grid
================================================================================

--------------------------------------------------------------------------------
 [1] 기동
--------------------------------------------------------------------------------

[oracle@rac1 ~]$ srvctl start service -d racdb -s ch15_oltp
[oracle@rac1 ~]$ srvctl start service -d racdb -s ch15_batch
[oracle@rac1 ~]$ echo $?
0

>>> 둘 합쳐 6.0초 (각각 3초 남짓)

[oracle@rac1 ~]$ srvctl status service -d racdb
Service ch15_batch is running on instance(s) racdb2
Service ch15_oltp is running on instance(s) racdb1

-- 정확히 의도한 대로다. 선호 인스턴스에 배치되었다.
--
-- 서비스는 어느 노드에서 기동해도 상관없다. 위 명령을 rac1 에서
-- 실행했지만 ch15_batch 는 racdb2 에서 떴다. CRS 가 정의를 보고
-- 올바른 인스턴스에 올린다. 14장에서 본 srvctl 의 특징이다.

--------------------------------------------------------------------------------
 [2] 배치 확인 ① — srvctl (CRS 가 아는 것)
--------------------------------------------------------------------------------

[oracle@rac1 ~]$ srvctl status database -d racdb -v
Instance racdb1 is running on node rac1 with online services ch15_oltp.
Instance status: Open.
Instance racdb2 is running on node rac2 with online services ch15_batch.
Instance status: Open.

-- "with online services" 문구가 붙었다. 실습 01 에서는 없던 것이다.
-- 서비스가 없으면 이 문구가 아예 나오지 않는다.
--
-- 인스턴스와 서비스를 한 번에 볼 수 있으므로 장애 대응에서 첫 번째로
-- 칠 만한 명령이다.

[grid@rac1 ~]$ crsctl stat res -t | grep -A3 'ora.racdb.ch15'
ora.racdb.ch15_batch.svc
      1        ONLINE  ONLINE       rac2                     STABLE
ora.racdb.ch15_oltp.svc
      1        ONLINE  ONLINE       rac1                     STABLE

-- CRS 자원으로도 ONLINE 이다. Server 열에 노드 이름이 들어갔다.

--------------------------------------------------------------------------------
 [3] 배치 확인 ② — GV$ (인스턴스가 아는 것)
--------------------------------------------------------------------------------

SQL> select inst_id, name from gv$active_services
  2   where name like 'ch15%' order by name, inst_id;

   INST_ID NAME
---------- ------------
         2 ch15_batch
         1 ch15_oltp

2 rows selected.

-- 데이터베이스 쪽에서도 같은 배치가 보인다.
--
-- 두 출처가 서로 다른 곳에서 온다는 점이 중요하다.
--   srvctl status  CRS 가 아는 것 (OCR 의 정의와 자원 상태)
--   GV$ACTIVE_SERVICES  인스턴스가 아는 것 (지금 활성인 서비스)
--
-- 둘이 일치해야 정상이다. 어긋난다면 CRS 와 인스턴스의 인식이 다른 것이고
-- 그 자체가 이상 신호다.
--
-- 실습 01 에서 기본 서비스가 인스턴스마다 하나씩이라 10 행이었던 것과
-- 대비된다. 이 두 서비스는 각각 한 인스턴스에만 있다. Cardinality 가 1 이다.

SQL> select inst_id, name from gv$active_services order by inst_id, name;
   (12 rows selected — 기본 10행 + ch15 두 행)

--------------------------------------------------------------------------------
 [4] 배치 확인 ③ — 리스너 (클라이언트가 보는 것)
--------------------------------------------------------------------------------

[grid@rac1 ~]$ lsnrctl status LISTENER | grep -A2 'ch15'
Service "ch15_oltp" has 1 instance(s).
  Instance "racdb1", status READY, has 1 handler(s) for this service...

-- rac1 의 로컬 리스너에는 ch15_oltp 만 있다. ch15_batch 는 없다.
-- 그 서비스가 rac1 에서 돌지 않기 때문이다.

[grid@rac1 ~]$ lsnrctl status LISTENER_SCAN1 | grep -A3 'ch15'
Service "ch15_batch" has 1 instance(s).
  Instance "racdb2", status READY, has 1 handler(s) for this service...
Service "ch15_oltp" has 1 instance(s).
  Instance "racdb1", status READY, has 1 handler(s) for this service...

-- SCAN 리스너에는 둘 다 있다. 그런데 각각 has 1 instance(s) 다.
-- 실습 01 에서 기본 서비스 racdb 가 has 2 instance(s) 였던 것과 다르다.
--
-- 이 숫자가 SCAN 이 고를 수 있는 후보의 수다.
-- ch15_oltp 는 후보가 racdb1 하나뿐이므로 선택의 여지가 없다.
-- 접속이 결정적으로 그쪽으로 간다.

--------------------------------------------------------------------------------
 [5] 배치 확인 ④ — 실제로 접속해 본다
--------------------------------------------------------------------------------

-- 확인의 마지막 단계는 실제 접속이다.
-- 정의와 상태가 맞아도 실제 접속은 다르게 갈 수 있다.

[oracle@rac1 ~]$ cat /tmp/svc_check.sh
#!/bin/bash
# 인자로 받은 서비스로 10회 접속해 인스턴스 이름을 센다
export ORACLE_HOME=/u01/app/oracle/product/19.3.0/dbhome_rac
for i in $(seq 10); do
  $ORACLE_HOME/bin/sqlplus -s system/<암호>@rac-scan:1521/$1 <<'EOS'
set head off feed off pages 0
select instance_name from v$instance;
exit
EOS
done

[oracle@rac1 ~]$ /tmp/svc_check.sh ch15_oltp | grep -v '^$' | sort | uniq -c
     10 racdb1

[oracle@rac1 ~]$ /tmp/svc_check.sh ch15_batch | grep -v '^$' | sort | uniq -c
     10 racdb2

-- 열 번 모두 의도한 인스턴스에 붙었다. 예외가 없다.
--
-- 이것이 서비스의 힘이다. 클라이언트는 SCAN 주소 하나만 알면 되고
-- 어느 인스턴스에 붙을지는 서비스 이름이 정한다.
-- 접속 문자열에서 ch15_oltp 를 ch15_batch 로 바꾸는 것만으로
-- 접속이 다른 노드로 간다.

--------------------------------------------------------------------------------
 [6] 흔한 오류 — 로컬 리스너 주소로 확인하면
--------------------------------------------------------------------------------

[oracle@rac1 ~]$ sqlplus system/<암호>@rac1:1521/ch15_batch
ERROR:
ORA-12514: TNS:listener does not currently know of service requested in connect
descriptor

-- 원인 파악 : rac1 의 로컬 리스너에는 ch15_batch 가 없다.
--             그 서비스는 racdb2 에서 돌고 rac2 의 로컬 리스너에만 등록된다.
--             [4] 의 lsnrctl status LISTENER 출력이 이미 그것을 말해 주고 있었다.
--             서비스가 없는 것이 아니라 이 리스너가 모르는 것이다.
-- 조치     : SCAN 주소로 접속한다.
--               sqlplus system/<암호>@rac-scan:1521/ch15_batch
--             SCAN 리스너는 클러스터 전체의 등록을 받으므로
--             그 서비스를 제공하는 인스턴스로 넘겨 준다.
-- 재확인   : 접속해 instance_name 을 조회하면 racdb2 가 나온다.

[oracle@rac1 ~]$ /tmp/svc_check.sh ch15_batch | grep -v '^$' | sort | uniq -c
     10 racdb2

-- 실무의 접속 문자열도 SCAN 을 쓴다.
--   rac-scan:1521/<서비스이름>
-- 노드가 늘거나 줄어도 클라이언트를 바꿀 필요가 없기 때문이다.
--
-- 접속 확인 스크립트를 하나 만들어 두면 유용하다.
-- 서비스를 옮길 때마다 이 스크립트로 검증하면 실수를 즉시 잡을 수 있다.

--------------------------------------------------------------------------------
 [7] 네 각도를 정리하면
--------------------------------------------------------------------------------

확인 대상          명령                                   무엇을 알려 주는가
------------------ -------------------------------------- ---------------------
CRS 의 인식        srvctl status service / status database CRS 가 아는 배치
자원 상태          crsctl stat res ... -t                 TARGET 과 STATE
인스턴스의 인식    gv$active_services                     지금 활성인 서비스
클라이언트의 시야  lsnrctl status LISTENER_SCAN1          등록과 후보 수
실제 경로          SCAN 접속 스크립트                     결정적인 최종 확인

-- 앞의 넷이 모두 정상인데 마지막에서 다르게 갈 수 있다.
-- 클라이언트 쪽 설정이나 DNS 문제일 수 있기 때문이다.
-- 그래서 변경할 때마다 마지막 항목을 실행한다.
