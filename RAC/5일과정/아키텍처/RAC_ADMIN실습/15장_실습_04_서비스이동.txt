================================================================================
 제15장 실습 04 — 서비스 이동, 접속 중인 세션은 어떻게 되는가
 대상   : rac1, rac2
 목표   : relocate 가 새 접속과 기존 세션에 각각 어떻게 작용하는지 확인하고,
          현실이 바뀌어도 정의는 그대로라는 것을 본다
 소요   : 약 30분
 선행   : 실습 03 완료. 두 세션을 함께 열어 둔다
 계정   : oracle
================================================================================

--------------------------------------------------------------------------------
 [1] 이동 전 상태
--------------------------------------------------------------------------------

[oracle@rac1 ~]$ srvctl status service -d racdb
Service ch15_batch is running on instance(s) racdb2
Service ch15_oltp is running on instance(s) racdb1

--------------------------------------------------------------------------------
 [2] 이동
--------------------------------------------------------------------------------

[oracle@rac1 ~]$ srvctl relocate service -d racdb -s ch15_oltp \
>                  -oldinst racdb1 -newinst racdb2
[oracle@rac1 ~]$ echo $?
0

>>> 2.1초 (세 번 측정에 2.1 / 2.0 / 1.7초)

[oracle@rac1 ~]$ srvctl status service -d racdb
Service ch15_batch is running on instance(s) racdb2
Service ch15_oltp is running on instance(s) racdb2

-- 2초면 끝난다. 유지보수 창을 잡을 때 무시해도 될 수준이다.
--
-- -oldinst 와 -newinst 를 모두 지정한다. 지금 어디에 있는지를 명시하게
-- 하는 것은 안전장치다. 여러 인스턴스에서 도는 서비스라면 어느 것을
-- 옮길지 특정해야 하며, 실수로 엉뚱한 것을 옮기는 일을 막아 준다.
--
-- 이제 두 서비스가 모두 racdb2 에 있다. rac1 은 이 서비스들의 접속을
-- 받지 않는다.

[oracle@rac1 ~]$ srvctl status database -d racdb -v
Instance racdb1 is running on node rac1. Instance status: Open.
Instance racdb2 is running on node rac2 with online services
ch15_batch,ch15_oltp. Instance status: Open.

-- racdb1 에는 "with online services" 문구가 사라졌다.

--------------------------------------------------------------------------------
 [3] 새 접속은 따라 옮겨 간다
--------------------------------------------------------------------------------

[oracle@rac1 ~]$ /tmp/svc_check.sh ch15_oltp | grep -v '^$' | sort | uniq -c
     10 racdb2

-- 열 번 모두 racdb2 다.
-- 클라이언트는 아무것도 바꾸지 않았다. 같은 접속 문자열로 붙었는데
-- 다른 노드에 앉았다.

--------------------------------------------------------------------------------
 [4] 접속 중인 세션은 어떻게 되는가
--------------------------------------------------------------------------------

-- 중요한 질문이다. 이동하는 순간 이미 붙어 있던 세션은 끊어지는가.
-- 측정한다. 45초 동안 대기하는 세션을 띄우고 12초 뒤에 서비스를 옮긴다.

-- 먼저 서비스를 racdb1 로 되돌려 둔다.
[oracle@rac1 ~]$ srvctl relocate service -d racdb -s ch15_oltp \
>                  -oldinst racdb2 -newinst racdb1

-- 세션 스크립트
[oracle@rac1 ~]$ cat /tmp/sess15.sh
#!/bin/bash
export ORACLE_HOME=/u01/app/oracle/product/19.3.0/dbhome_rac
$ORACLE_HOME/bin/sqlplus -s system/<암호>@rac-scan:1521/ch15_oltp <<'EOS' > /tmp/sess15.out 2>&1
set head off feed off pages 0
select 'BEFORE '||instance_name||' sid='||sys_context('userenv','sid') from v$instance;
exec dbms_session.sleep(45);
select 'AFTER  '||instance_name||' sid='||sys_context('userenv','sid') from v$instance;
exit
EOS

-- 백그라운드로 띄운다
[oracle@rac1 ~]$ nohup /tmp/sess15.sh >/dev/null 2>&1 &

-- 12초 뒤에 이동
[oracle@rac1 ~]$ srvctl relocate service -d racdb -s ch15_oltp \
>                  -oldinst racdb1 -newinst racdb2
[oracle@rac1 ~]$ srvctl status service -d racdb
Service ch15_batch is running on instance(s) racdb2
Service ch15_oltp is running on instance(s) racdb2

-- 45초가 지난 뒤 결과를 본다
[oracle@rac1 ~]$ cat /tmp/sess15.out
BEFORE racdb1 sid=20
AFTER  racdb1 sid=20

-- 끊어지지 않았다. 같은 인스턴스, 같은 세션 ID 다.
--
-- 서비스가 racdb2 로 옮겨 간 뒤에도 이 세션은 racdb1 에 그대로 남아
-- 자기 작업을 끝냈다.
--
-- 즉 relocate 는 새 접속의 방향만 바꾼다. 이미 맺어진 접속은 건드리지 않는다.

[oracle@rac1 ~]$ /tmp/svc_check.sh ch15_oltp | grep -v '^$' | sort | uniq -c
     10 racdb2

-- 세션이 끝난 뒤 새로 접속하면 racdb2 로 간다. 두 결과가 함께 있어야
-- "새 접속만 바뀐다" 는 결론이 선다.

--------------------------------------------------------------------------------
 [5] 이것이 유지보수 절차에 그대로 쓰인다
--------------------------------------------------------------------------------

-- 한 노드를 내리기 전에 그 노드의 서비스를 먼저 옮기면
--   새 접속은 다른 노드로 가고
--   기존 세션은 자기 일을 마칠 시간을 얻는다
-- 세션이 모두 빠진 뒤에 노드를 내리면 아무도 끊기지 않는다.
--
-- 세션이 빠지는지는 이렇게 본다.

SQL> select inst_id, count(*) from gv$session where type='USER'
  2   group by inst_id order by inst_id;

-- 기존 세션까지 정리하고 싶다면 -drain_timeout 과 -stopoption 을 쓴다.
-- 정해진 시간 동안 세션이 빠지기를 기다리고 그래도 남으면 끊는다.
-- 유지보수 창이 짧을 때 쓰는 방법이다.
--
--   srvctl relocate service -d racdb -s ch15_oltp \
--     -oldinst racdb1 -newinst racdb2 -drain_timeout 300 -stopoption IMMEDIATE
--
-- 이 실습에서는 지정하지 않았으므로 기다리지도 끊지도 않았다.

--------------------------------------------------------------------------------
 [5-1] 흔한 오류 — 옮긴 뒤 옛 노드로 접속하면
--------------------------------------------------------------------------------

-- ch15_oltp 가 racdb2 로 옮겨 간 상태에서 rac1 의 로컬 주소로 붙어 본다.

[oracle@rac1 ~]$ sqlplus system/<암호>@rac1:1521/ch15_oltp
ERROR:
ORA-12514: TNS:listener does not currently know of service requested in connect
descriptor

-- 원인 파악 : 서비스가 racdb2 로 옮겨 갔으므로 rac1 의 로컬 리스너에는
--             더 이상 등록되어 있지 않다. 실습 03 에서 ch15_batch 로
--             확인한 것과 같은 이유다.
--             lsnrctl 로 직접 확인할 수 있다.
--               [grid@rac1 ~]$ lsnrctl status LISTENER | grep ch15_oltp
--               (출력 없음)
--               [grid@rac1 ~]$ lsnrctl status LISTENER_SCAN1 | grep -A2 ch15_oltp
--               Service "ch15_oltp" has 1 instance(s).
--                 Instance "racdb2", status READY, ...
--             SCAN 리스너에는 있고 로컬에는 없다. 서비스가 사라진 것이
--             아니라 이 리스너가 모르는 것이다.
-- 조치     : SCAN 주소로 접속한다.
--               sqlplus system/<암호>@rac-scan:1521/ch15_oltp
--             접속 문자열에 노드 이름이나 VIP 를 박아 둔 클라이언트가
--             있다면 이것이 서비스 이동을 무력화한다. SCAN 으로 고친다.
-- 재확인   : SCAN 으로 접속해 instance_name 이 racdb2 로 나오는지 본다.

[oracle@rac1 ~]$ /tmp/svc_check.sh ch15_oltp | grep -v '^$' | sort | uniq -c
     10 racdb2

-- 이것이 서비스 이동을 도입할 때 반드시 함께 점검해야 할 항목이다.
-- 서버 쪽에서 아무리 잘 옮겨도 클라이언트가 노드 주소로 붙어 있으면
-- 이동의 효과가 없다.

--------------------------------------------------------------------------------
 [6] 진단 — 정의는 바뀌지 않았다
--------------------------------------------------------------------------------

[oracle@rac1 ~]$ srvctl config service -d racdb -s ch15_oltp | egrep 'Service name|Preferred|Available'
Service name: ch15_oltp
Preferred instances: racdb1
Available instances: racdb2

-- 서비스는 racdb2 에서 돌고 있는데 정의는 그대로다. 선호가 여전히 racdb1 이다.
--
-- 원인 파악 : relocate 는 현실만 바꾸고 정의는 건드리지 않는다.
--             14장에서 배운 status 와 config 의 구분이 그대로 적용된다.
--             status 는 현실, config 는 CRS 안에 저장된 정의다.
-- 조치     : 임시 이동이 목적이라면 조치할 것이 없다. 정상이다.
--             다만 데이터베이스를 재기동하면 서비스는 정의를 보고
--             선호 인스턴스에서 뜬다. 즉 원위치된다.
--             영구히 바꾸려면 정의를 고친다.
--               srvctl modify service -d racdb -s ch15_oltp \
--                 -preferred racdb2 -available racdb1
-- 재확인   : srvctl config service 로 Preferred 가 바뀌었는지 보고,
--             재기동 후에도 그 자리에 뜨는지 확인한다.

-- 이것은 대체로 바람직한 동작이다. 임시 조치가 영구히 남지 않는 편이
-- 안전하고, 영구 변경은 명시적인 명령으로만 이뤄지는 것이 좋다.
--
-- 다만 재기동 시점을 모르면 놀랄 수 있으므로 옮겨 둔 서비스는 기록해 둔다.
--
-- 주의할 점 하나. modify 로 정의를 바꾸면 다른 서비스와의 배치 균형이
-- 깨질 수 있다. 두 서비스를 엇갈리게 배치해 두었다면 하나만 옮길 때
-- 둘 다 한 인스턴스에 몰리지 않는지 확인해야 한다.

--------------------------------------------------------------------------------
 [7] 원위치
--------------------------------------------------------------------------------

[oracle@rac1 ~]$ srvctl relocate service -d racdb -s ch15_oltp \
>                  -oldinst racdb2 -newinst racdb1
[oracle@rac1 ~]$ srvctl status service -d racdb
Service ch15_batch is running on instance(s) racdb2
Service ch15_oltp is running on instance(s) racdb1

-- 1.7초. 다음 실습을 위해 원래 배치로 돌려 둔다.
