================================================================================
 제4장 실습 03 — root.sh 출력 읽기
 대상   : rac1 / rac2
 목표   : root.sh 가 첫 노드에서 무엇을 하는지 출력으로 확인하고, 노드별
          소요 시간 차이의 이유를 이해한다
 소요   : 약 30분
 선행   : GI 설치가 완료되어 있을 것
 계정   : root, grid
 주의   : 이 실습에서 root.sh 를 다시 실행하지 않는다. 설치 당시의 로그를 읽는다.
================================================================================

--------------------------------------------------------------------------------
 [1] 설치 관리자가 알려 준 순서
--------------------------------------------------------------------------------

-- gridSetup.sh 가 끝날 때 출력한 안내다.

As a root user, execute the following script(s):
        1. /u01/app/19.3.0/grid/root.sh

Execute /u01/app/19.3.0/grid/root.sh on the following nodes:
[rac1, rac2]

Run the script on the local node first. After successful completion,
you can start the script in parallel on all other nodes.

-- 마지막 두 줄이 이 실습의 근거다.
--   로컬 노드에서 먼저 실행한다
--   성공적으로 완료된 뒤에 나머지 노드에서 병렬로 시작할 수 있다
-- 2노드에서는 결국 순차 실행이 된다.

--   (4) 보팅 파일 배치  +CRS 를 만들고 보팅 파일 3벌을 넣는다
--
-- 마지막 줄의 Succeeded 를 반드시 눈으로 확인한다. 이 줄이 없으면 실패다.

--------------------------------------------------------------------------------

-- replaced 라는 표현에 주목한다. root.sh 는 초기에 임시 위치에 보팅 파일을
-- 만든 뒤 +CRS 디스크그룹으로 옮긴다. 그래서 replaced 다.
--
-- File Universal Id 는 보팅 파일마다 부여되는 고유 식별자다. 32자리 16진수이며
-- 디스크를 교체하면 이 값이 바뀐다. 5장에서 보팅 파일을 다룰 때 다시 본다.
--
-- 개수가 3인 이유는 응답 파일의 diskGroup.redundancy=NORMAL 때문이다.
-- EXTERNAL 이었다면 1개, HIGH 였다면 5개가 만들어진다.

-- 지금도 같은 값인지 확인해 본다.
[grid@rac1 ~]$ crsctl query css votedisk
##  STATE    File Universal Id                File Name Disk group
--  -----    -----------------                --------- ---------
 1. ONLINE   838fca0461384f6cbfe0440187190bd9 (/dev/asmdisk/crs1) [CRS]
 2. ONLINE   4c38f09d6d7b4f1fbfc0e6b7055c8515 (/dev/asmdisk/crs2) [CRS]
 3. ONLINE   370e2d1c1e604f6ebfd6c8aa3b8c0d35 (/dev/asmdisk/crs3) [CRS]
Located 3 voting disk(s).

-- 설치 당시와 같다. 그동안 보팅 파일을 교체한 적이 없다는 뜻이다.
-- 이 출력을 저장해 두면 5장에서 교체 후 비교할 기준이 된다.

 [4] 두 번째 노드의 출력

[root@rac2 ~]# /u01/app/19.3.0/grid/root.sh

2026/08/31 19:16:20 /u01/app/19.3.0/grid/root.sh: Succeeded

-- 소요 1.9분. 첫 노드의 3분의 1이다.
--
-- 출력에 보팅 파일 생성 부분이 없다. 이미 만들어진 것에 합류만 하기 때문이다.
-- 첫 노드만 하는 일이 세 가지였다.
--   OCR 초기화
--   +CRS 디스크그룹 생성과 보팅 파일 3벌 배치
--   클러스터 이름, 노드 목록, SCAN 등록
--
-- 두 노드에서 동시에 실행하면 양쪽이 OCR 을 초기화하려 들어 충돌한다.
-- 그래서 순서가 있다.

--------------------------------------------------------------------------------
 [5] 오류 재현 — root.sh 를 grid 로 실행하면
--------------------------------------------------------------------------------

-- 계정을 잘못 쓰면 어떻게 되는지 확인한다. 안전하다 — 아무것도 바꾸지 않는다.

[root@rac1 ~]# su - grid
[grid@rac1 ~]$ /u01/app/19.3.0/grid/root.sh
Check /u01/app/19.3.0/grid/install/root_rac1.localdomain_2026-09-01_15-01-34-311480080.log
for the output of root script

-- 화면에는 로그 파일 경로만 나온다. 성공했는지 실패했는지 알 수 없다.
-- 반드시 그 파일을 열어야 한다.

[grid@rac1 ~]$ cat /u01/app/19.3.0/grid/install/root_rac1.localdomain_2026-09-01_15-01-34-311480080.log
You must be logged in as user with UID as zero (e.g. root user) to run root
configuration script.
Log in as user with UID as zero (e.g. root user) and restart root configuration
script execution.

-- 원인 파악
--   root.sh 는 권한이 755 라 누구나 실행할 수 있다. 그러나 스크립트 안에서
--   UID 가 0 인지 검사하고 아니면 즉시 중단한다.
[grid@rac1 ~]$ ls -l /u01/app/19.3.0/grid/root.sh
-rwxr-xr-x. 1 root oinstall 405 Aug 31 19:03 /u01/app/19.3.0/grid/root.sh

[grid@rac1 ~]$ id -u
1001

--   UID 가 1001 이라 검사에 걸렸다. 실행 권한과 내부 검사가 두 겹으로 걸려 있다.
--   참고로 rootcrs.sh 는 권한 자체가 750 이라 실행조차 되지 않는다.
[grid@rac1 ~]$ ls -l /u01/app/19.3.0/grid/crs/install/rootcrs.sh
-rwxr-x---. 1 root oinstall 8046 Aug 31 19:03 rootcrs.sh

-- 조치 — root 로 실행한다. 다만 이 실습에서는 실제로 실행하지 않는다.
--   이미 구성이 끝난 클러스터에서 root.sh 를 다시 실행하는 것은 위험하다.
--   설치 시점에만 실행하는 스크립트다.

-- 재확인 — 아무것도 바뀌지 않았음을 검증한다.
[grid@rac1 ~]$ crsctl check cluster -all
**************************************************************
rac1:
CRS-4537: Cluster Ready Services is online
CRS-4529: Cluster Synchronization Services is online
CRS-4533: Event Manager is online
**************************************************************
rac2:
CRS-4537: Cluster Ready Services is online
CRS-4529: Cluster Synchronization Services is online
CRS-4533: Event Manager is online
**************************************************************

[grid@rac1 ~]$ crsctl query css votedisk
Located 3 voting disk(s).

[grid@rac1 ~]$ olsnodes -s -n
rac1    1       Active
rac2    2       Active

[oracle@rac1 ~]$ srvctl status database -d racdb -v
Instance racdb1 is running on node rac1. Instance status: Open.
Instance racdb2 is running on node rac2. Instance status: Open.

-- 보팅 파일 3개, 두 노드 Active, 두 인스턴스 Open. 무손상이다.
--
-- 배운 것
--   root.sh 는 실행 결과를 화면이 아니라 로그 파일로 안내한다.
--   경로만 보고 성공했다고 판단하면 안 된다. 파일을 열어야 한다.
--   계정 문제라면 로그가 세 줄 정도로 짧다. 실제 실행이었다면 CRS 메시지가
--   길게 이어진다. 크기만 봐도 구분된다.
--   가드가 있어도 실행 전에 whoami 로 계정을 확인하는 습관이 우선이다.

--------------------------------------------------------------------------------
 [6] 자동화한다면
--------------------------------------------------------------------------------

-- 스크립트로 순서를 지키려면 첫 노드의 성공을 두 가지로 확인한다.
--
--   rc=$?                                  종료 코드
--   grep -q 'Succeeded' "$LOG"             성공 문자열
--
-- 둘 다 확인해야 하는 이유가 있다. root.sh 는 grid 로 실행해도 종료 코드가
-- 0 으로 나올 수 있다. 문자열 확인이 없으면 실패를 성공으로 오인한다.
--
-- 이 교재의 배포 스크립트(RAC/scripts/node/21_root_sh.sh)가 그렇게 되어 있다.
-- 두 번째 노드에서 실행할 때는 첫 노드의 성공을 확인했는지 되묻는다.

--------------------------------------------------------------------------------
 [7] 정리
--------------------------------------------------------------------------------

-- 확인한 것
--   1) 설치 관리자가 root.sh 실행 순서를 직접 안내한다
--   2) 첫 노드는 환경 확인, 스택 재기동, 저수준 자원 기동, 보팅 파일 배치
--   3) 보팅 파일 3벌은 redundancy=NORMAL 의 결과다
--   4) File Universal Id 는 보팅 파일마다 부여되며 교체하면 바뀐다
--   5) 두 번째 노드는 합류만 하므로 1.9분으로 짧다
--   6) root.sh 를 grid 로 실행하면 UID 검사에 걸려 무손상으로 중단된다
--   7) 자동화할 때는 종료 코드와 Succeeded 문자열을 함께 검사한다
--
-- 이 실습에서 root.sh 를 실제로 다시 실행한 것은 grid 계정 시도뿐이며
-- 아무것도 바꾸지 않았다. 클러스터 상태를 확인하고 종료한다.
