================================================================================
 제10장 실습 05 — SPFILE 과 컨트롤파일 : 절차가 다른 이유
 대상   : rac1
 목표   : 컨트롤파일이 데이터파일과 다른 절차를 요구하는 이유를 파라미터 속성으로
          확인하고, RAC 에서 SPFILE 위치가 두 곳에 기록되는 구조를 파악한다
 소요   : 약 25분
 선행   : racdb 양 노드 OPEN
 계정   : oracle
 주의   : 이 실습은 조회와 오류 재현만 수행한다. 실제 이동은 하지 않는다
================================================================================

--------------------------------------------------------------------------------
 [1] 왜 이 둘만 따로 다루는가
--------------------------------------------------------------------------------

-- 실습 02~04 에서 데이터파일은 세 번 옮겼다. 절차는 언제나 같았다.
--   OFFLINE → BACKUP AS COPY → SWITCH → (RECOVER) → ONLINE
--
-- 컨트롤파일과 SPFILE 에는 이 절차를 쓸 수 없다.
-- 이유가 서로 다르므로 나눠서 확인한다.

--------------------------------------------------------------------------------
 [2] 오류 재현 — 컨트롤파일 위치를 동적으로 바꾸려 하면
--------------------------------------------------------------------------------

[oracle@rac1 ~]$ sqlplus -s / as sysdba

SQL> col name for a54
SQL> select name from v$controlfile;

NAME
------------------------------------------------------
+DATA/RACDB/CONTROLFILE/current.261.1242761745
+FRA/RACDB/CONTROLFILE/current.256.1242761745

2 rows selected.

-- 두 벌이 있다. 디스크그룹 하나를 통째로 잃어도 컨트롤파일은 남는다.
-- 이제 위치를 바꿔 본다.

SQL> alter system set
  2    control_files='+DATA/RACDB/CONTROLFILE/current.261.1242761745'
  3    scope=memory;
alter system set control_files='+DATA/RACDB/CONTROLFILE/current.261.1242761745' scope=memory
                 *
ERROR at line 1:
ORA-02095: specified initialization parameter cannot be modified

-- 오류 : ORA-02095
--
-- 원인 파악 : 파라미터 속성을 보면 답이 나온다.

SQL> col name for a20
SQL> select name, issys_modifiable, isinstance_modifiable
  2    from v$parameter
  3   where name in ('control_files','spfile','db_create_file_dest',
  4                  'log_archive_dest_1')
  5   order by name;

NAME                 ISSYS_MOD ISINS
-------------------- --------- -----
control_files        FALSE     FALSE
db_create_file_dest  IMMEDIATE TRUE
log_archive_dest_1   IMMEDIATE TRUE
spfile               IMMEDIATE TRUE

4 rows selected.

--             네 파라미터 중 control_files 만 ISSYS_MODIFIABLE 이 FALSE 다.
--             나머지 셋은 IMMEDIATE 로 ALTER SYSTEM 으로 즉시 바꿀 수 있다.
--
--             FALSE 는 "인스턴스가 살아 있는 동안에는 어떤 방법으로도
--             못 바꾼다" 는 뜻이다. scope=memory 든 scope=both 든 거부된다.
--
-- 조치     : SPFILE 에 새 값을 써 두고 (scope=spfile) 재기동해야 한다.
-- 재확인   : scope=spfile 로는 명령이 통과하는지 확인한다.
--             다만 이 실습에서는 실제로 값을 바꾸지 않으므로 절차만 익힌다.

--------------------------------------------------------------------------------
 [3] 컨트롤파일 이동 절차 — RAC 의 추가 제약
--------------------------------------------------------------------------------

-- 위 확인에 따라 절차는 이렇게 된다.
--
--  1. SPFILE 에 새 위치를 기록한다.
--     SQL> alter system set control_files='<새 경로 목록>' scope=spfile;
--     지금은 아무 일도 일어나지 않는다. 다음 기동 때 쓰인다.
--
--  2. 데이터베이스를 내린다.
--     $ srvctl stop database -d racdb
--     RAC 에서는 두 인스턴스가 같은 컨트롤파일을 봐야 하므로
--     데이터베이스 전체를 내려야 한다. 노드별 순차 처리가 불가능하다.
--     롤링 방식이 통하지 않는 몇 안 되는 작업 중 하나다.
--
--  3. 한 인스턴스를 NOMOUNT 로 올리고 새 위치에 컨트롤파일을 만든다.
--     RMAN> restore controlfile from '<기존 경로>';
--     컨트롤파일을 읽어야 MOUNT 가 되므로 이 단계가 필요하다.
--
--  4. MOUNT 후 OPEN 한다.
--     SQL> alter database mount;
--     SQL> alter database open;
--
--  5. 나머지 인스턴스를 기동하고 양 노드에서 확인한다.
--     SQL> select name from v$controlfile;
--     두 노드가 같은 경로를 봐야 한다.

-- 실무 권장 : 옮기기보다 늘리는 편이 안전하다.
--             새 위치에 사본을 추가하고 운영이 안정된 뒤 옛 것을 뺀다.
--             어느 쪽이든 재기동은 피할 수 없지만, 중간 상태에서 사본이
--             하나도 없는 순간이 생기지 않는다는 점이 다르다.

--------------------------------------------------------------------------------
 [4] SPFILE — 위치가 두 곳에 기록되어 있다
--------------------------------------------------------------------------------

SQL> show parameter spfile

NAME       TYPE     VALUE
---------- -------- -----------------------------------------------
spfile     string   +DATA/RACDB/PARAMETERFILE/spfile.272.1242762487

[oracle@rac1 ~]$ srvctl config database -d racdb | grep -i 'spfile\|password\|disk group'
Spfile: +DATA/RACDB/PARAMETERFILE/spfile.272.1242762487
Password file: +DATA/RACDB/PASSWORD/pwdracdb.256.1242761627
Disk Groups: DATA,FRA

-- 값은 같지만 출처가 다르다.
--   show parameter spfile   → 지금 돌고 있는 인스턴스가 실제로 읽은 파일
--   srvctl config database  → CRS 가 다음에 인스턴스를 띄울 때 쓸 값
--
-- 단일 인스턴스에는 이런 이중 기록이 없다. 사람이 직접 인스턴스를 띄우므로
-- 위치가 한 곳에만 있으면 된다.
-- RAC 에서는 CRS 가 인스턴스를 띄우므로 CRS 가 아는 값이 따로 존재한다.
--
-- 지금은 두 값이 같아 문제가 드러나지 않는다.
-- SPFILE 을 옮기는 순간 갈라질 수 있다.

--------------------------------------------------------------------------------
 [5] SPFILE 을 텍스트로 내려받기
--------------------------------------------------------------------------------

SQL> create pfile='/tmp/pf_ch10.ora' from spfile;

File created.

[oracle@rac1 ~]$ ls -l /tmp/pf_ch10.ora
-rw-r--r--. 1 oracle asmadmin 1877 Sep  3 19:35 /tmp/pf_ch10.ora

[oracle@rac1 ~]$ grep -c . /tmp/pf_ch10.ora
55

[oracle@rac1 ~]$ grep -i 'control_files\|db_create' /tmp/pf_ch10.ora
*.control_files='+DATA/RACDB/CONTROLFILE/current.261.1242761745',
                '+FRA/RACDB/CONTROLFILE/current.256.1242761745'
*.db_create_file_dest='+DATA'

-- 1877 바이트, 55 줄짜리 텍스트 파일이다.
-- 여기에 컨트롤파일 위치를 포함한 모든 파라미터가 들어 있다.
--
-- 파라미터 이름 앞의 *. 은 모든 인스턴스에 적용된다는 뜻이다.
-- RAC 에서는 racdb1.parameter=value 처럼 인스턴스별 값도 들어갈 수 있다.
-- undo_tablespace 가 대표적이다. 인스턴스마다 다른 UNDO 를 쓰기 때문이다.

--------------------------------------------------------------------------------
 [6] SPFILE 이동 절차와 두 가지 실패
--------------------------------------------------------------------------------

-- 절차는 네 단계다.
--
--  1. 현재 SPFILE 을 pfile 로 내려받는다.
--     SQL> create pfile='/tmp/pf_ch10.ora' from spfile;
--     [5] 에서 수행했다.
--
--  2. 새 위치에 SPFILE 을 만든다.
--     SQL> create spfile='+FRA/RACDB/PARAMETERFILE/spfile_new.ora'
--          from pfile='/tmp/pf_ch10.ora';
--
--  3. CRS 에 새 위치를 알린다.
--     $ srvctl modify database -d racdb -spfile '+FRA/RACDB/PARAMETERFILE/...'
--
--  4. 데이터베이스를 재기동한다.
--     $ srvctl stop database -d racdb
--     $ srvctl start database -d racdb
--
-- 실패 유형 1 — 3 단계를 빠뜨림
--   새 SPFILE 을 만들고 재기동했는데 파라미터 변경이 반영되지 않는다.
--   CRS 가 여전히 옛 경로를 들고 있어 옛 SPFILE 로 인스턴스를 띄우기 때문이다.
--   확인 : show parameter spfile 이 새 것이 아니라 옛 것을 가리킨다.
--   조치 : srvctl modify 를 실행하고 다시 재기동한다.
--
-- 실패 유형 2 — 3 단계는 했는데 그 경로에 파일이 없음
--   인스턴스가 아예 기동되지 않는다.
--   확인 : asmcmd ls 로 그 경로에 파일이 있는지 본다.
--   조치 : 파일을 먼저 만들고 재기동한다.
--
-- 두 실패를 모두 피하는 방법은 순서를 지키는 것이다.
--   파일을 먼저 만들고 → srvctl 을 고치고 → 마지막에 재기동한다.
--   재기동 전에 srvctl config database -d racdb 로 값을 눈으로 확인한다.

--------------------------------------------------------------------------------
 [7] 정리 — 세 종류 파일의 절차 비교
--------------------------------------------------------------------------------

--  파일 종류      이동 방법                    재기동   RAC 추가 제약
--  ------------  --------------------------  -------  ----------------------
--  데이터파일     BACKUP AS COPY + SWITCH      불필요   없음 (테이블스페이스만
--                                                       OFFLINE)
--  컨트롤파일     scope=spfile + RESTORE       필요     DB 전체 정지,
--                                                       순차 처리 불가
--  SPFILE        create spfile + srvctl        필요     srvctl modify 필수
--                modify
--
-- 데이터파일만 서비스를 열어 둔 채 옮길 수 있다.
-- 나머지 둘은 재기동이 필요하므로 중단 창을 확보해야 한다.

[oracle@rac1 ~]$ rm -f /tmp/pf_ch10.ora

-- 임시로 만든 pfile 을 지운다.

SQL> exit
