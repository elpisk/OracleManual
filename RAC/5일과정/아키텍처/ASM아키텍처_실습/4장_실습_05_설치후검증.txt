 [1] 버전 조회 네 가지
--------------------------------------------------------------------------------

[grid@rac1 ~]$ crsctl query crs activeversion -f
Oracle Clusterware active version on the cluster is [19.0.0.0.0].
The cluster upgrade state is [NORMAL].
The cluster active patch level is [724960844].

[grid@rac1 ~]$ crsctl query crs softwareversion
Oracle Clusterware version on node [rac1] is [19.0.0.0.0]

[grid@rac1 ~]$ crsctl query crs releaseversion
Oracle High Availability Services release version on the local node is [19.0.0.0.0]

[grid@rac1 ~]$ crsctl query crs softwarepatch
Oracle Clusterware patch level on node rac1 is [724960844].

-- 비슷해 보이지만 각각 다른 것을 말한다.
--   activeversion -f   클러스터 전체가 합의한 활성 버전, 업그레이드 상태,
--                      활성 패치 수준. 클러스터 관점의 기준값이다
--   softwareversion    이 노드에 설치된 소프트웨어 버전. 노드별 대조에 쓴다
--   releaseversion     이 노드의 OHAS 릴리스 버전. 상세 확인용
--   softwarepatch      이 노드의 패치 수준. 노드별 대조에 쓴다
--
-- 정상 상태의 판정 기준
--   activeversion 의 patch level 724960844
--   각 노드의 softwarepatch 724960844
--   두 값이 같다. upgrade state 가 NORMAL 이다.
--
-- 롤링 패치 중이거나 중단된 채 남아 있으면 두 값이 다르고
-- upgrade state 가 ROLLING PATCH 로 표시된다.

-- 두 노드를 대조한다.
[grid@rac1 ~]$ for h in rac1 rac2; do
>   printf '%-6s ' $h
>   ssh $h '/u01/app/19.3.0/grid/bin/crsctl query crs softwarepatch'
> done
rac1   Oracle Clusterware patch level on node rac1 is [724960844].
rac2   Oracle Clusterware patch level on node rac2 is [724960844].

-- 두 노드가 같다. 패치 수준이 일치한다.

[grid@rac1 ~]$ cd /u01/app/19.3.0/grid
[grid@rac1 grid]$ ./runcluvfy.sh stage -pre crsinst -n rac1,rac2

rac1: PRVG-11750 : File "/var/tmp/.oracle/mdnsd.pid" exists on node "rac1".

Verifying Grid Infrastructure home path: /u01/app/19.3.0/grid ...FAILED
  Verifying '/u01/app/19.3.0/grid' ...FAILED
  rac2: PRVG-11931 : Path "/u01/app/19.3.0/grid" is not writeable on node
  rac1: PRVG-11931 : Path "/u01/app/19.3.0/grid" is not writeable on node

-- 소요 0.7분.

-- 원인 파악
--   두 실패 모두 설치가 이미 되어 있어서 나는 것이다.
--
--   PRVG-11750 /var/tmp/.oracle 아래에 파일이 존재한다
--     이 디렉터리는 Clusterware 프로세스들이 소켓과 잠금 파일을 두는 곳이다.
--     설치 전이라면 비어 있어야 정상이고, 남아 있다면 이전 설치의 잔재이므로
--     정리하라는 뜻이다. 지금은 Clusterware 가 돌고 있으니 당연히 차 있다.
[root@rac1 ~]# ls /var/tmp/.oracle | head -6
mdnsd
mdnsd.pid
npohasd2
ora_gipc_GPNPD_rac1
ora_gipc_GPNPD_rac1_lock
ora_gipc_gipcd_rac1

--   PRVG-11931 Grid 홈 경로에 쓰기 권한이 없다
--     설치 전이라면 grid 가 홈에 쓸 수 있어야 소프트웨어를 풀 수 있다.
--     설치가 끝나면 root.sh 가 Grid 홈의 소유권을 root 로 바꾼다.
[root@rac1 ~]# ls -ld /u01/app/19.3.0/grid
drwxr-xr-x. 86 root oinstall 4096 Aug 31 19:08 /u01/app/19.3.0/grid

--     root 소유에 다른 사용자는 읽기와 실행만 가능하다. 이것이 정상 상태다.

-- 조치 — 명령을 시점에 맞게 고른다.
[grid@rac1 ~]$ cluvfy stage -post crsinst -n rac1,rac2 | tail -3

Post-check for cluster services setup was successful.

-- 재확인
--   같은 시스템인데 결과가 다르다. 검사 기준이 다르기 때문이다.
--
-- 절대 하면 안 되는 조치가 두 가지다.
--   PRVG-11750 을 보고 /var/tmp/.oracle 을 지우면 Clusterware 프로세스 간
--   통신이 끊겨 클러스터가 멈춘다.
--   PRVG-11931 을 보고 Grid 홈 소유권을 grid 로 바꾸면 보안 구성이 깨진다.
--
-- 배운 것
--   cluvfy 의 stage 는 시점을 지정하는 것이다. 시점에 맞지 않는 stage 를 쓰면
--   정상 상태를 실패로 보고한다. FAILED 라고 무작정 고치려 들면 오히려
--   클러스터를 망가뜨린다.

--------------------------------------------------------------------------------
 [5] 인수인계용 자료 남기기
--------------------------------------------------------------------------------

-- 설치 직후 상태를 파일로 남겨 두면 나중에 비교 기준이 된다.

[grid@rac1 ~]$ D=$(date +%Y%m%d)
[grid@rac1 ~]$ mkdir -p ~/install_record_$D
[grid@rac1 ~]$ cd ~/install_record_$D
[grid@rac1 install_record_20260901]$ cluvfy stage -post crsinst -n rac1,rac2 > cluvfy_post.txt 2>&1
[grid@rac1 install_record_20260901]$ for c in activeversion softwareversion releaseversion softwarepatch; do
>   echo "=== $c ==="; crsctl query crs $c -f 2>/dev/null || crsctl query crs $c
> done > crs_version.txt
[grid@rac1 install_record_20260901]$ crsctl status resource -t > resource.txt
[grid@rac1 install_record_20260901]$ crsctl query css votedisk > votedisk.txt
[grid@rac1 install_record_20260901]$ ls -l
cluvfy_post.txt
crs_version.txt
resource.txt
votedisk.txt

-- 자원 배치(resource.txt)가 특히 유용하다. 페일오버가 반복되면 배치가
-- 달라지므로 설치 직후 상태를 알아야 어디로 되돌릴지 판단할 수 있다.
-- ocrcheck 는 root 권한이 필요하므로 root 로 따로 저장한다.

 [6] 정리
--------------------------------------------------------------------------------

-- 확인한 것
--   1) crsctl query crs 의 네 하위 명령이 각각 다른 것을 말한다
--   2) activeversion 의 patch level 과 노드별 softwarepatch 가 일치해야 정상
--   3) 두 노드의 패치 수준을 ssh 로 대조할 수 있다
--   4) cluvfy stage -post crsinst 가 28개 항목을 1.6분에 검사한다
--   5) 설치 완료 환경에서 stage -pre 를 쓰면 PRVG-11750 과 PRVG-11931 로 실패
--   6) 두 실패 모두 정상 상태이며 손대면 안 된다
--   7) 설치 직후 상태를 파일로 남겨 인수인계에 쓴다
--
-- 이 실습은 조회와 결과 파일 저장뿐이다. 원상 복구할 것이 없다.
