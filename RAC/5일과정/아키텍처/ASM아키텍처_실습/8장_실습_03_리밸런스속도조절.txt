--------------------------------------------------------------------------------
 [4] 비교
--------------------------------------------------------------------------------

-- 실습 02 의 추가 파워 1과 함께 정리한다.
--
--   작업        파워   소요 시간   비고
--   ----        ----   ---------   ----
--   추가          1     239.1초    실습 02
--   추가          8      68.4초    3.5배 빠름
--   제거          1      88.4초    추가보다 빠름
--
-- 두 가지를 읽는다.
--
-- 첫째, 파워를 8배 올렸는데 3.5배만 빨라졌다. 선형이 아니다.
--   파워는 동시에 도는 ARB 슬레이브 수를 정할 뿐이다. 슬레이브를 늘려도
--   디스크 I/O 대역폭이나 CPU 가 한계에 이르면 더 빨라지지 않는다.
--   실습 환경은 여러 가상 디스크가 하나의 물리 디스크에 얹혀 있어 이
--   한계가 일찍 온다. 실제 스토리지에서는 배율이 더 나올 수 있다.
--
-- 둘째, 제거(88.4초)가 추가(239.1초)보다 빨랐다. 같은 파워 1이다.
--   직관과 반대로 느껴지지만 이유가 있다.
--     제거 — 나가는 디스크의 데이터만 남은 디스크로 옮기면 끝난다
--     추가 — 기존 모든 디스크에서 새 디스크로 옮겨 전체를 고르게 만든다
--   옮기는 총량이 다르다. 디스크가 많을수록 이 차이가 커진다.
--
-- 작업 계획을 세울 때 추가 쪽에 더 넉넉한 시간을 잡아야 한다.

--------------------------------------------------------------------------------
 [5] 리밸런스 중에 파워를 바꿀 수 있다
--------------------------------------------------------------------------------

-- 리밸런스가 이미 돌고 있어도 파워를 바꿀 수 있다. 구문은 이렇다.
--
--   alter diskgroup <디스크그룹> rebalance power <N>;
--
-- 새 리밸런스를 시작하는 것이 아니라 진행 중인 작업의 병렬도를 조정한다.
-- v$asm_operation 의 POWER 컬럼이 바뀌는 것으로 확인할 수 있다.
-- [8] 에서 실제로 파워 0에서 8로 바꾸며 이 동작을 확인한다.
--
-- 실무에서 유용하다. 파워 1로 시작해 EST_MINUTES 를 보고 너무 오래 걸릴
-- 것 같으면 올리고, 업무 응답이 나빠지면 낮춘다.

--------------------------------------------------------------------------------
 [6] 오류 재현 — 범위를 벗어난 파워
--------------------------------------------------------------------------------

SQL> alter diskgroup TESTN rebalance power 2000;
alter diskgroup TESTN rebalance power 2000
                                      *
ERROR at line 1:
ORA-15102: invalid POWER expression

SQL> alter diskgroup TESTN rebalance power -1;
alter diskgroup TESTN rebalance power -1
                                      *
ERROR at line 1:
ORA-15102: invalid POWER expression

-- 오류 : ORA-15102
-- 원인 파악 : 파워의 유효 범위는 0에서 1024 다. 위와 아래 모두 같은 코드가
--             나온다. 별표가 문제가 된 값을 정확히 가리킨다.
--             6장에서 asm_power_limit 파라미터에 2000 을 넣었을 때는
--             ORA-00068: invalid value ... must be between 0 and 1024 가
--             나왔다. 여기서는 ORA-15102 다.
--             검증하는 계층이 다르기 때문이다. ORA-00068 은 파라미터 값
--             검증이고 ORA-15102 는 SQL 명령의 인자 검증이다.
--             다만 ORA-15102 는 허용 범위를 알려 주지 않는다는 점이 아쉽다.
-- 조치     : 0에서 1024 사이의 값을 쓴다.
-- 재확인   : 실패한 명령이 진행 중인 작업에 영향을 주지 않았는지 본다.

--------------------------------------------------------------------------------
 [7] 파워 0 — 멈춘다
--------------------------------------------------------------------------------

-- 조건을 만들기 위해 디스크를 다시 넣는다.
SQL> alter diskgroup TESTN add failgroup fgC disk '/dev/asmdisk/test6'
  2    name d_c rebalance power 1;

Diskgroup altered.

-- 60초 뒤 진행 상황을 본다.
SQL> select operation, state, power, sofar, est_work from v$asm_operation;

OPERA STAT      POWER      SOFAR   EST_WORK
----- ---- ---------- ---------- ----------
REBAL RUN           1         69          0
REBAL DONE          1       1335       1335
REBAL DONE          1          0          0
REBAL DONE          1          0          0

4 rows selected.

-- 여기서 중요한 것을 발견한다. v$asm_operation 에 행이 하나가 아니다.
-- 네 행이 나오고 STATE 가 RUN 과 DONE 으로 섞여 있다.
--
-- 리밸런스가 여러 단계(phase)로 나뉘어 있고 각 단계가 별도 행으로 보인다.
-- 이미 끝난 단계는 DONE, 진행 중인 단계는 RUN 이다.
--
-- 실습 02 에서 조회했을 때 한 줄만 보였던 것은 state='RUN' 조건을 걸었기
-- 때문이다. 조건 없이 조회하면 이렇게 여러 행이 나온다.
--
-- 따라서 완료 판단은 이렇게 해야 한다.
--   select count(*) from v$asm_operation;   -- 0이면 완료
-- 또는
--   select count(*) from v$asm_operation where state='RUN';  -- 0이면 완료
--
-- DONE 행의 존재만으로 완료를 판단하면 안 된다.

SQL> alter diskgroup TESTN rebalance power 0;

Diskgroup altered.

SQL> select count(*) ops from v$asm_operation;

       OPS
----------
         4

-- 명령은 성공했는데 행이 여전히 4개다.
-- 이 실습에서는 파워 0을 실행한 시점에 리밸런스가 이미 거의 끝나 있었다.
-- 데이터도 이미 고르게 분배되어 있었다.

SQL> select d.name, d.failgroup, d.total_mb-d.free_mb used_mb
  2    from v$asm_disk d, v$asm_diskgroup g
  3   where d.group_number=g.group_number and g.name='TESTN' order by d.disk_number;

NAME     FAILGR    USED_MB
-------- ------ ----------
D_A      FGA          1336
D_B      FGB          1338
D_C      FGC          1331
D_D      FGD          1339

[grid@rac1 ~]$ asmcmd lsdg | grep TESTN
MOUNTED  NORMAL  Y   512  512  4096  1048576  16384  11040  4096  3472  0  N  TESTN/

-- Rebal 이 여전히 Y 다. 남은 단계가 정리되는 중이다.
--
-- 여기서 배울 것은 파워 0이 즉시 모든 것을 멈추는 스위치가 아니라는 점이다.
-- 새로 시작할 작업의 병렬도를 0으로 만드는 것에 가깝고, 이미 진행 중인
-- 단계는 마무리된다.
--
-- 실무에서 업무 영향이 급해 멈춰야 한다면 파워 0을 실행한 뒤 실제로
-- ARB 프로세스가 사라지는지 ps 로 확인하는 편이 확실하다.

--------------------------------------------------------------------------------
 [9] 정리
--------------------------------------------------------------------------------

-- 재현한 오류
--   ORA-15102   범위를 벗어난 파워 값 (0~1024)
--
-- 실측 결과
--   추가 파워 1   239.1초
--   추가 파워 8    68.4초  (3.5배)
--   제거 파워 1    88.4초
--
-- 확인한 것
--   1) 파워는 선형이 아니다. 8배를 줘도 3.5배만 빨라졌다
--   2) 병목은 파워가 아니라 I/O 대역폭과 CPU 다
--   3) 제거가 추가보다 빠르다. 옮기는 총량이 다르기 때문
--   4) 리밸런스 중에도 파워를 바꿀 수 있다
--   5) 파워 0은 취소가 아니라 중단이다
--   6) 재개하면 중단 지점부터 이어진다. est_work 가 줄어든 것이 증거
--   7) ORA-15102 는 명령 인자 검증, ORA-00068 은 파라미터 값 검증
--
-- 실무 기준
--   0     업무 시간 긴급 중단
--   1     기본값. 업무 영향 최소
--   4~8   야간·주말
--   그 이상은 디스크가 많고 대역폭이 넉넉할 때만 의미가 있다
