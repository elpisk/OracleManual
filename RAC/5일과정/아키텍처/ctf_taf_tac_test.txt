================================================================================
 CTF · TAF · TAC — 접속 장애와 실행 중 장애를 클라이언트가 넘기는 세 가지 방법
 대상   : rac1 (클라이언트 역할), rac2
 랩     : racdb (racdb1 · racdb2), PDB racpdb1, VIP rac1-vip · rac2-vip, SCAN rac-scan
 소요   : 약 60분 (인스턴스 재기동 대기 포함)
 계정   : oracle, grid, root
 주의   : racdb1 을 두 번 내린다. 한 번은 shutdown abort, 한 번은 pmon kill
 실측   : 2026-11-10, Oracle 19.3.0.0.0, SQL*Plus 19.3
================================================================================

 1부  개념
################################################################################

--------------------------------------------------------------------------------
 1.1 장애는 두 시점에 온다
--------------------------------------------------------------------------------

- 접속하는 순간의 장애
  - 리스너가 죽었거나, 노드가 꺼졌거나, 서비스가 없는 리스너로 갔을 때
  - 아직 세션이 없으므로 잃을 것도 없음. 다른 주소로 다시 시도하면 끝남
  - 이것을 다루는 것이 CTF(Connect-Time Failover)
- 일하는 도중의 장애
  - 이미 세션이 있고, 조회 결과를 받는 중이거나 트랜잭션을 진행하는 중
  - 세션 · 열린 커서 · 커밋 안 한 변경 · 세션 설정(NLS, 패키지 변수)을 잃음
  - 세션과 조회까지만 되살리는 것이 TAF(Transparent Application Failover)
  - 진행 중이던 트랜잭션까지 다시 실행해 주는 것이 AC(Application Continuity),
    그 19c 판이 TAC(Transparent Application Continuity)
- 셋은 서로 대체하는 관계가 아님
  - CTF 는 TAF · TAC 의 바탕. TAF 도 TAC 도 다시 붙을 때 결국 주소 목록을 따라감
  - TAF 와 TAC 는 같은 세션에 겹쳐 쓰지 않음. 서비스 하나에 하나를 고름

--------------------------------------------------------------------------------
 1.2 CTF — 접속할 때 다음 주소로 넘어가기
--------------------------------------------------------------------------------

- 동작
  - 클라이언트(Oracle Net)가 tnsnames 의 ADDRESS_LIST 를 차례로 시도
  - 앞 주소에서 연결이 거절되거나 시간이 지나면 다음 주소로 감
  - 서버 쪽 설정은 없음. 순전히 클라이언트 접속 기술자(descriptor)의 일
- 관련 매개변수
  - FAILOVER=ON : 앞 주소가 실패하면 다음 주소로. ADDRESS_LIST 안에서는 기본값이 ON 이지만
    원본처럼 적어 두는 편이 읽기 쉬움
  - FAILOVER=OFF : 첫 주소에서 실패하면 바로 오류. [2] 의 NOCTF 가 이것
  - LOAD_BALANCE=ON : 주소 순서를 매번 무작위로 섞음. 접속을 리스너 사이에 나눔([1])
  - LOAD_BALANCE=OFF : 늘 첫 주소부터. 주 · 예비 구성이 됨
- 시간 관련 매개변수 (DESCRIPTION 바로 아래에 둔다)
  - TRANSPORT_CONNECT_TIMEOUT : 주소 하나에 TCP 연결이 맺어지기를 기다리는 시간
  - CONNECT_TIMEOUT : 주소 하나에서 세션을 받기까지 기다리는 전체 시간
  - RETRY_COUNT · RETRY_DELAY : 주소 목록을 다 돌고도 실패하면 RETRY_DELAY 초 쉬고
    목록 전체를 RETRY_COUNT 번 더 돔
  - 이 넷은 DESCRIPTION 의 매개변수. ADDRESS_LIST 안에 적으면 오류 없이 무시됨([3])
- 왜 VIP 를 쓰나
  - 노드가 통째로 꺼지면 그 노드의 실제 IP 로 보낸 연결 요청은 응답이 없음.
    클라이언트는 TCP 시간 초과(수십 초 ~ 수 분)까지 기다린 뒤에야 다음 주소로 감
  - VIP 는 노드가 죽으면 살아 있는 노드로 옮겨 감. 옮겨 간 VIP 에는 리스너가 없으므로
    연결 요청이 즉시 거절되고(RST), 클라이언트는 곧바로 다음 주소로 넘어감
  - 그래서 클라이언트 주소 목록에는 노드 IP 가 아니라 VIP 를 적음
  - SCAN 을 쓰면 주소 목록을 클라이언트가 들고 있을 필요가 없음. SCAN 이름 하나가
    여러 SCAN VIP 로 풀리고 SCAN 리스너가 서비스가 있는 인스턴스로 넘겨 줌
- 한계
  - 접속하는 순간에만 동작. 이미 맺은 세션이 끊기는 것은 CTF 와 무관
  - 리스너를 바꿔 줄 뿐 인스턴스를 고르지 않음. 다음 리스너 뒤에 그 서비스가 없으면
    ORA-12514 로 실패함([2] 의 CTF_TAC). 노드 리스너는 자기 노드 인스턴스의 서비스만 앎
  - 실제 노드 장애라면 Clusterware 가 서비스를 살아 있는 인스턴스로 옮기므로 이 문제가
    덜 드러남. 리스너만 내린 [2] 에서는 서비스가 racdb1 에 남아 있어 그대로 드러남

--------------------------------------------------------------------------------
 1.3 TAF — 끊긴 세션을 다시 만들고 조회를 이어 주기
--------------------------------------------------------------------------------

- 동작
  - OCI 클라이언트 라이브러리가 세션이 끊긴 것을 알아채면 같은 접속 기술자로 새 세션을 만듦
    (이때 CTF 의 주소 목록을 따라감)
  - 같은 사용자로 다시 로그인하고, TYPE=SELECT 이면 끊길 때 실행 중이던 SELECT 를
    새 인스턴스에서 다시 실행
  - 이미 받은 행 수만큼 건너뛰고 그 다음 행부터 넘겨줌. 애플리케이션은 조회가 잠깐
    멈췄다가 이어진 것으로 봄
- FAILOVER_MODE 의 항목
  - TYPE=SESSION : 세션만 다시 만듦. 열린 조회는 ORA-25401 로 끊김
  - TYPE=SELECT : 세션 + 실행 중이던 SELECT 를 이어 줌
  - TYPE=NONE : TAF 를 쓰지 않음
  - METHOD=BASIC : 장애가 난 뒤에 새 세션을 만듦. 평소 비용 없음
  - METHOD=PRECONNECT : 예비 인스턴스에 미리 세션을 하나 더 열어 둠. 빨리 넘어가지만
    세션이 두 배. BACKUP= 으로 예비 접속 별칭을 지정해야 함
  - RETRIES · DELAY : 다시 붙지 못하면 DELAY 초 간격으로 RETRIES 번 시도.
    인스턴스 장애 뒤 서비스가 옮겨 가는 데 몇 초 걸리므로 넉넉히 줌(이 실습은 30 · 5)
- 설정하는 두 곳
  - 클라이언트 쪽 : tnsnames 의 CONNECT_DATA 안 FAILOVER_MODE (원본과 이 실습의 방식)
  - 서버 쪽 : srvctl add/modify service -failovertype SELECT -failovermethod BASIC
    -failoverretry 30 -failoverdelay 5
  - 둘 다 있으면 서버 쪽 설정이 이김. 그래서 이 실습은 서버 쪽 TAF 가 없는 ctfsrv 를 씀
  - 서버 쪽 설정은 클라이언트 tnsnames 를 고치지 않고 서비스 하나로 모두에게 적용됨
- TAF 가 살리지 못하는 것
  - 진행 중이던 DML · PL/SQL 호출 : ORA-25408 (can not safely replay call) 을 받고
    트랜잭션은 롤백됨([4])
  - 끊길 때 열려 있던 트랜잭션 : 세션은 새로 생기지만 커밋 안 한 변경은 사라짐.
    애플리케이션이 ROLLBACK 하고 처음부터 다시 내야 함
  - 세션 설정 : ALTER SESSION, PL/SQL 패키지 변수, 임시 테이블 내용. 필요하면 OCI
    장애 콜백(OCI_ATTR_FOCBK)에서 다시 설정
  - 결과가 매번 달라지는 조회 : 행마다 SYSTIMESTAMP · 시퀀스 · 인스턴스 이름을 찍거나
    ORDER BY 없이 순서가 바뀔 수 있으면 앞 행을 재현하지 못해 ORA-25401
  - 쉬고 있던 세션의 다음 호출 : 첫 호출은 ORA-03113 을 받고, 그 다음 호출부터 이어짐
    (RAC_ADMIN실습 16장 실습 10)
- 쓸 수 있는 클라이언트
  - OCI 기반만 : SQL*Plus, OCI · Pro*C, JDBC OCI 드라이버, ODP.NET unmanaged
  - JDBC thin 은 TAF 를 지원하지 않음(thin 은 AC/TAC 를 씀)

--------------------------------------------------------------------------------
 1.4 AC 와 TAC — 진행 중이던 요청을 다시 실행하기
--------------------------------------------------------------------------------

- Application Continuity (12.1~)
  - 드라이버가 요청(request) 하나 동안 낸 호출을 기억해 둠
  - 복구 가능한 오류(인스턴스 장애, 네트워크 끊김, kill session 등)로 세션을 잃으면
    새 세션을 만들고, 롤백된 트랜잭션을 처음부터 다시 실행(replay)
  - 다시 실행한 결과가 처음과 같은지 확인하고, 같으면 애플리케이션에 정상 응답을 돌려줌
  - 애플리케이션은 장애가 있었다는 것을 모르고 지나감. 느려졌다는 것만 앎
  - 요청의 시작 · 끝은 커넥션 풀의 대여(getConnection) · 반납(close)으로 정함
- Transaction Guard 가 받침
  - 다시 실행하기 전에 "끊긴 세션의 마지막 커밋이 실제로 끝났나" 를 LTXID 로 확인
  - 이미 커밋됐으면 다시 실행하지 않음. 같은 주문이 두 번 들어가는 일을 막음
  - 그래서 -commit_outcome TRUE 가 없으면 AC 서비스를 만들 수 없음(16장 실습 05 의
    PRCD-1259). 커밋 결과는 SYS.LTXID_TRANS 에 -retention 초 동안 남음
- Transparent Application Continuity (18c~, 19c 에서 -failovertype AUTO)
  - AC 는 요청 경계를 풀이 알려 줘야 하고, 세션 상태를 애플리케이션이 일정하게 유지해야
    했음(-session_state STATIC/DYNAMIC 을 개발자가 판단)
  - TAC 는 드라이버와 서버가 세션 상태를 스스로 추적해, 상태가 깨끗한 시점을 요청
    경계로 잡음(Session State Consistency: AUTO)
  - 풀을 쓰지 않는 애플리케이션, 코드를 고칠 수 없는 애플리케이션도 대상이 됨
  - 이 랩의 SQL*Plus 19.3 에서도 PL/SQL 블록이 재실행돼 커밋까지 끝남([5])
- TAC 서비스 속성
  - -failovertype AUTO : TAC. (TRANSACTION 이면 AC)
  - -commit_outcome TRUE : Transaction Guard. 필수
  - -failover_restore AUTO : 다시 실행하기 전에 세션 상태(NLS 등)를 되돌려 놓음.
    AC 는 LEVEL1, TAC 는 AUTO
  - -replay_init_time 300 (기본) : 요청이 시작된 지 이 초가 지나면 다시 실행하지 않음.
    오래 도는 배치는 늘려야 함
  - -retention 86400 (기본) : 커밋 결과를 보관하는 초
  - 이 넷을 주면 Failover retries 30, delay 10 이 자동으로 들어감([준비 2] 의 출력)
- 다시 실행하지 않는 것
  - 이미 커밋된 요청 : Transaction Guard 가 커밋됨을 확인하고 결과만 돌려줌
  - 외부에 흔적을 남기는 호출(UTL_HTTP, UTL_SMTP, UTL_FILE, DBMS_PIPE 등) : TAC 는
    이런 호출을 만나면 그 요청을 다시 실행 대상에서 뺌
  - ALTER SYSTEM · ALTER DATABASE
  - replay_init_time 을 넘긴 요청
  - 다시 실행하면 값이 바뀌는 함수(SYSDATE, SYSTIMESTAMP, 시퀀스 NEXTVAL, SYS_GUID) 는
    처음 값을 그대로 쓰도록 권한을 줌
      GRANT KEEP DATE TIME TO app_user;
      GRANT KEEP SYSGUID TO app_user;
      GRANT KEEP SEQUENCE ON app.order_seq TO app_user;   (+ ALTER SEQUENCE ... KEEP)
    권한이 없으면 다시 실행한 결과가 달라져 재실행이 거부될 수 있음
- 쓸 수 있는 클라이언트
  - JDBC thin replay 드라이버(oracle.jdbc.replay.OracleDataSourceImpl 등), UCP
  - OCI(19c 클라이언트), ODP.NET unmanaged, SQL*Plus 19c
  - 클라이언트 라이브러리가 18c 보다 낮으면 TAC 서비스에 붙어도 재실행하지 않음

--------------------------------------------------------------------------------
 1.6 FAN 은 어디에 끼나
--------------------------------------------------------------------------------

- 위 셋은 모두 "끊긴 것을 알아챈 뒤" 의 일. 알아채는 것이 늦으면 전부 늦어짐
- 세션이 쉬고 있으면 다음 호출을 낼 때까지 끊긴 것을 모름. 노드가 통째로 죽으면 TCP
  시간 초과까지 기다릴 수도 있음
- FAN(Fast Application Notification) 은 서버가 "racdb1 의 서비스가 내려갔다" 를 먼저
  알려 줌. 풀은 그 인스턴스의 연결을 바로 버리고, TAC/AC 는 바로 재실행을 시작함
- 19c 드라이버는 FAN 을 자동으로 켬(auto-configured FAN). 실습 [5] 의 kill 직후 8 초
  안에 서비스가 racdb2 로 옮겨 간 것도 FAN 이벤트로 나감(16장 실습 07 · 08)

[oracle@rac1 admin]$ cp tnsnames.ora tnsnames.ora.bak
[oracle@rac1 admin]$ cat >> tnsnames.ora <<'EOF'

LB =
 (DESCRIPTION =
   (ADDRESS_LIST =
     (LOAD_BALANCE=ON)
     (FAILOVER=ON)
     (ADDRESS=(PROTOCOL=TCP)(HOST=rac1-vip)(PORT=1521))
     (ADDRESS=(PROTOCOL=TCP)(HOST=rac2-vip)(PORT=1521))
   )
   (CONNECT_DATA=(SERVICE_NAME=ctfsrv))
 )

CTF =
 (DESCRIPTION =
   (ADDRESS_LIST =
