 [3] 문제 유형별로 볼 곳
--------------------------------------------------------------------------------

--  문제                        볼 파일
--  Clusterware 기동·자원 상태  diag/crs/<노드>/crs/trace/alert.log
--  멤버십·축출                 같은 폴더의 ocssd.trc
--  자원 기동 실패              crsd_oraagent_<계정>.trc 또는
--                              crsd_orarootagent_root.trc
--  부팅 중 저수준 자원 문제    ohasd_orarootagent_root.trc
--  ASM 인스턴스                diag/asm/+asm/+ASM1/trace/alert_+ASM1.log
--  리스너                      diag/tnslsnr/<노드>/listener/alert/log.xml
--  SCAN 리스너                 diag/tnslsnr/<노드>/listener_scan1/alert/log.xml
--  노드 재부팅 사유            /etc/oracle/lastgasp/*.lgl

[grid@rac1 ~]$ ls -la /u01/app/grid/diag/asm/+asm/+ASM1/trace/alert_+ASM1.log

 [5] 오류 재현 — oracle 계정의 adrci 에는 Clusterware 홈이 없다
--------------------------------------------------------------------------------

-- Clusterware 로그를 보려고 oracle 계정에서 adrci 를 실행한다.

[oracle@rac1 ~]$ adrci exec="show homes"
ADR Homes:
diag/rdbms/orcl/orcl
diag/rdbms/knh/KNH
diag/rdbms/prod/PROD
diag/rdbms/racdb/racdb1
diag/clients/user_oracle/host_3192166451_110
diag/clients/user_oracle/host_203307297_110
diag/tnslsnr/oel7v9/listener
diag/tnslsnr/oel7v9/lsnr
diag/tnslsnr/oel7v9/lsnrprod

-- diag/crs/rac1/crs 가 없다. Clusterware 홈이 목록에 나오지 않는다.
-- 여기서 "Clusterware 진단 정보가 없다"고 판단하면 잘못이다.

-- 원인 파악
--   adrci 는 그 계정의 ORACLE_BASE 아래 진단 홈만 보여 준다.

[oracle@rac1 ~]$ echo $ORACLE_BASE
/u01/app/oracle

[grid@rac1 ~]$ echo $ORACLE_BASE
/u01/app/grid

--   Clusterware 홈은 /u01/app/grid 아래에 있으므로 oracle 계정의 목록에
--   나올 수 없다. 계층마다 계정이 다르듯 ADR base 도 다르다.
--
--   목록에 orcl, knh, prod 처럼 낯선 데이터베이스가 보이는 것도 눈여겨볼 만하다.
--   이 실습 환경은 기존 이미지를 링크드 클론으로 복제해 만들었으므로 원본
--   이미지에 있던 단일 인스턴스 데이터베이스들의 진단 홈이 그대로 남아 있다.
--   tnslsnr/oel7v9 도 원본 호스트명 시절의 흔적이다. 실제로 쓰지 않는 항목이다.

-- 조치 — grid 계정으로 실행한다.
[oracle@rac1 ~]$ exit
[root@rac1 ~]# su - grid
[grid@rac1 ~]$ adrci exec="show homes" | grep crs
diag/crs/rac1/crs

-- 재확인
--   grid 계정에서는 Clusterware 홈이 정상적으로 나온다.

-- 다만 파일 읽기 자체는 oracle 로도 된다. 권한을 확인해 본다.
[root@rac1 ~]# ls -l /u01/app/grid/diag/crs/rac1/crs/trace/alert.log
-rw-rw----. 1 grid oinstall 35072 Sep  1 13:05 alert.log

[root@rac1 ~]# id oracle
uid=1000(oracle) gid=54321(oinstall) groups=54321(oinstall),54322(dba),...

[oracle@rac1 ~]$ tail -3 /u01/app/grid/diag/crs/rac1/crs/trace/alert.log
2026-09-01 13:05:03.369 [OCSSD(3445)]CRS-1601: CSSD Reconfiguration complete. Active nodes are rac1 rac2 .
2026-09-01 13:05:23.135 [CRSD(4611)]CRS-2772: Server 'rac2' has been assigned to pool 'Generic'.
2026-09-01 13:05:23.136 [CRSD(4611)]CRS-2772: Server 'rac2' has been assigned to pool 'ora.racdb'.

--   읽힌다. 파일이 grid:oinstall 소유에 그룹 읽기 권한이 있고, oracle 의
--   기본 그룹도 oinstall 이기 때문이다. 3장에서 두 계정의 기본 그룹을
--   모두 oinstall 로 맞춘 결과가 여기서 나타난다.
--
-- 배운 것
--   경로를 알면 oracle 로도 읽을 수 있다. 문제는 adrci 로 경로를 찾을 때다.
--   Clusterware 진단은 grid 계정으로 하는 것이 원칙이며, 그래야 adrci 가
--   올바른 홈 목록을 보여 준다.
--   덤으로 CRS-2772 라는 새 코드도 보인다. 서버가 풀에 배정됐다는 뜻으로,
--   rac2 가 복귀하면서 Generic 과 ora.racdb 풀에 다시 들어간 기록이다.

--------------------------------------------------------------------------------
 [6] 두 노드 로그를 함께 보는 방법
--------------------------------------------------------------------------------

-- 축출처럼 두 노드가 얽힌 사건은 양쪽 로그를 시각 순으로 대조해야 한다.
[grid@rac1 ~]$ for n in rac1 rac2; do
>   echo "===== $n ====="
>   ssh $n "grep 'CRS-1601' /u01/app/grid/diag/crs/$n/crs/trace/alert.log | tail -1"
> done
===== rac1 =====
2026-09-01 13:05:03.369 [OCSSD(3445)]CRS-1601: CSSD Reconfiguration complete. Active nodes are rac1 rac2 .
===== rac2 =====
2026-09-01 13:05:03.365 [OCSSD(24692)]CRS-1601: CSSD Reconfiguration complete. Active nodes are rac1 rac2 .

-- 두 노드의 시각이 13:05:03.369 와 13:05:03.365 로 4밀리초 차이다.
-- 같은 재구성 사건을 양쪽이 함께 기록한 것이며, 두 노드의 시각이 CTSS 로
-- 정확히 맞춰져 있다는 증거이기도 하다.
--
-- rac2 의 이력을 더 보면 이 실습 과정이 그대로 남아 있다.
[grid@rac2 ~]$ grep 'CRS-1601' /u01/app/grid/diag/crs/rac2/crs/trace/alert.log | tail -3
2026-09-01 12:32:55.552 [OCSSD(27256)]CRS-1601: ... Active nodes are rac1 rac2 .
2026-09-01 12:41:42.954 [OCSSD(8276)]CRS-1601: ... Active nodes are rac1 rac2 .
2026-09-01 13:05:03.365 [OCSSD(24692)]CRS-1601: ... Active nodes are rac1 rac2 .

-- OCSSD 의 PID 가 27256 → 8276 → 24692 로 바뀌었다. 실습 05 에서 스택을
-- 세 번 내렸다 올렸기 때문이다. PID 변화만 봐도 재기동 횟수를 알 수 있다.
-- grid 계정의 SSH 등가성이 설정되어 있어 ssh 로 바로 넘어갈 수 있다.

--------------------------------------------------------------------------------
 [7] 정리
--------------------------------------------------------------------------------

-- 확인한 것
--   1) adrci exec="show homes" 가 진단의 지도다
--   2) ADR 은 노드마다 별개이며 계정마다 보이는 홈이 다르다
--   3) trace 디렉터리에 파일이 395개 — 먼저 볼 것은 alert.log 하나
--   4) 파일 이름이 <데몬>_<에이전트>_<계정>.trc 규칙을 따른다
--   5) alert.log 가 상세 .trc 로 가는 길을 알려 준다
--   6) 노드 재부팅 사유는 /etc/oracle/lastgasp 에 남는다
--   7) adrci 는 그 계정의 ORACLE_BASE 아래 홈만 보여 준다. Clusterware 진단은
--      grid 계정으로 한다. 파일 읽기 자체는 oinstall 그룹이면 oracle 로도 된다
--
-- 이 실습은 조회만 했으므로 원상 복구할 것이 없다.
