================================================================================
 제20장 실습 03 — 경합의 원인 객체 특정
 대상   : rac1
 목표   : 시스템 전체 대기에서 출발해 어느 세그먼트의 어떤 블록이
          경합을 만드는지까지 좁혀 들어간다
 소요   : 약 15분
 선행   : 실습 02 완료 (부하를 한 번 건 상태)
 계정   : oracle
 주의   : 읽기 전용 실습이다
================================================================================

--------------------------------------------------------------------------------
 [1] 세그먼트 통계 — 먼저 잘못된 조건으로
--------------------------------------------------------------------------------

SQL> select inst_id, object_name, statistic_name, value
  2    from gv$segment_statistics
  3   where owner='SYS' and object_name='ch20_t' and value > 0;

no rows selected

-- 원인 파악: OBJECT_NAME 은 딕셔너리에 대문자로 저장된다.
--            소문자로 조건을 주면 일치하는 행이 없다.
--            앞 실습과 마찬가지로 오류가 아니라 빈 결과라는 점이 함정이다.
--            "통계가 없다" 와 "조건이 틀렸다" 를 화면만 보고는 구분할 수 없다.
-- 조치     : 대문자로 쓰거나 UPPER 를 씌운다.

SQL> select inst_id, object_name, statistic_name, value
  2    from gv$segment_statistics
  3   where owner='SYS' and object_name='CH20_T' and value > 0
  4     and statistic_name like 'gc%'
  5   order by statistic_name, inst_id;

   INST_ID OBJECT_NAME  STATISTIC_NAME                VALUE
---------- ------------ ---------------------------- ------
         2 CH20_T       gc cr blocks received            523
         1 CH20_T       gc current blocks received      3786
         2 CH20_T       gc current blocks received      3787
         1 CH20_T       gc remote grants                 263

-- 재확인: 값이 나온다.
--
-- CH20_T 하나가 양 노드에서 3786 과 3787 을 받았다.
-- 실습 02 의 시스템 전체 증가분이 +3987 과 +3996 이었으므로
-- 거의 전부가 이 테이블 하나에서 나왔다. 범인이 특정되었다.

--------------------------------------------------------------------------------
 [2] 이름을 모를 때 — 상위부터 훑는다
--------------------------------------------------------------------------------

SQL> select inst_id, owner, object_name, object_type, statistic_name, value
  2    from gv$segment_statistics
  3   where statistic_name = 'gc current blocks received' and value > 0
  4   order by value desc fetch first 10 rows only;

-- 실무에서는 객체 이름을 모르는 상태로 시작한다.
-- 통계 이름 하나를 고정하고 값 순으로 정렬해 상위 몇 개를 뽑는다.
-- 대개 소수의 테이블이나 인덱스가 대부분을 만든다.
--
-- 이때 SYS 소유 객체가 상위에 올라오는 경우가 많은데 대부분 딕셔너리이며
-- 애플리케이션 문제가 아니다. 소유자로 한 번 걸러 보는 편이 좋다.

--------------------------------------------------------------------------------
 [3] 어떤 종류의 블록이 오갔는가
--------------------------------------------------------------------------------

SQL> select instance, class, cr_block, cr_2hop, current_block, current_2hop,
  2         cr_busy, current_busy
  3    from gv$instance_cache_transfer
  4   where cr_block + current_block > 0 order by instance, class;

  INSTANCE CLASS              CR_BLOCK   CR_2HOP CURRENT_BLOCK CURRENT_2HOP  CR_BUSY CURRENT_BUSY
---------- ---------------- ---------- --------- ------------- ------------ -------- ------------
         1 data block             1042      1042          7372         7372        3         4407
         1 segment header           21        21           328          328        0            8
         1 undo header            2009      2009            14           14      530          210
         2 data block              337       337          1385         1385       33         4452
         2 segment header            8         8            61           61        0           12
         2 undo header            3634      3634             4            4      495          199

-- 세 가지를 읽는다.
--
-- 하나, data block 의 CURRENT_BUSY 가 4407 과 4452 로 가장 크다.
--       실제 데이터 블록을 두고 다툰 결과이며 실습 02 의 대기와 일치한다.
--
-- 둘, undo header 의 CR_BLOCK 이 2009 와 3634 로 크다.
--     읽기 일관성 사본을 만들려면 상대 인스턴스의 UNDO 헤더를 봐야 한다.
--     13장에서 UNDO 를 인스턴스별로 나눈 설계가 여기서 비용으로 나타난다.
--     그래도 나누는 편이 낫다. 공유하면 UNDO 세그먼트 할당 자체가 경합한다.
--
-- 셋, CR_2HOP 이 항상 CR_BLOCK 과 같다.
--     2 노드에서는 모든 전송이 2-way 이므로 당연하다.
--     노드가 셋 이상이면 3HOP 열에 값이 생긴다.

--------------------------------------------------------------------------------
 [4] 좁혀 들어가는 순서 정리
--------------------------------------------------------------------------------

--   1  GV$SYSTEM_EVENT   — gc 대기가 상위인가, busy 인가 2-way 인가
--   2  GV$SEGMENT_STATISTICS — 어느 객체인가
--   3  GV$INSTANCE_CACHE_TRANSFER — 어떤 종류의 블록인가
--   4  애플리케이션 — 무엇이 그 블록을 만지는가
--
-- 1 에서 멈추면 "느리다" 만 알고 어디를 고칠지 모른다.
-- 2 까지 가야 손댈 대상이 정해진다.
-- 3 은 대응 방법을 고를 때 쓴다. data block 이면 애플리케이션이나 서비스 배치,
-- undo header 면 설계상 불가피한 부분이 크다.

--------------------------------------------------------------------------------
 [5] 대응 방법 세 가지
--------------------------------------------------------------------------------

-- 하나, 서비스로 그 업무를 한 인스턴스에 모은다.
--   srvctl modify service -d racdb -s <서비스> -preferred racdb1 -available racdb2
--   캐시 퓨전이 아예 필요 없어진다. 가장 빠르고 확실하다.
--
-- 둘, 물리 설계를 바꾼다.
--   시퀀스에 CACHE 를 크게 주고 NOORDER 로 둔다.
--   시퀀스로 채우는 인덱스는 해시 파티션으로 오른쪽 끝 경합을 분산한다.
--
-- 셋, 애플리케이션을 고친다.
--   상태 플래그나 카운터를 매 건 갱신하지 않도록 바꾼다.
--   근본 해결이지만 가장 오래 걸린다.
