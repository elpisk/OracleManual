 [6] 자동 복구가 멈추는 경우
--------------------------------------------------------------------------------

-- 이 실습을 준비하며 같은 장애를 4 분 간격으로 두 번 냈다.
-- 두 번째에는 CRS 가 인스턴스를 살리지 않았다.

[grid@rac1 ~]$ crsctl stat res ora.racdb.db -t
ora.racdb.db
      1        ONLINE  ONLINE       rac1     Open,HOME=...,STABLE
      2        ONLINE  OFFLINE               Instance Shutdown,STABLE

[grid@rac1 ~]$ grep 'CRS-277' /u01/app/grid/diag/crs/rac1/crs/trace/alert.log | tail -2
2026-09-04 18:07:17.934 [CRSD(5998)]CRS-2771: Maximum restart attempts reached
                        for resource 'ora.racdb.db'; will not restart.
2026-09-04 18:07:17.962 [CRSD(5998)]CRS-2769: Unable to failover resource
                        'ora.racdb.db'.

-- 원인 파악: 자원 속성이 다음과 같다.
--
--   [grid@rac1 ~]$ crsctl stat res ora.racdb.db -p | grep -E 'RESTART_ATTEMPTS|UPTIME'
--   RESTART_ATTEMPTS=2
--   UPTIME_THRESHOLD=1h
--
--            14장에서 본 두 속성이다. 자원이 한 시간 넘게 살아 있어야
--            재시도 횟수가 초기화된다. 두 장애 사이가 4 분이었으므로
--            초기화되지 않았고 두 번째에 한도를 넘었다.
--            TARGET 은 여전히 ONLINE 이다. CRS 는 떠 있어야 한다고 알지만
--            더 시도하지 않는다.
-- 조치     : 사람이 올린다.

[oracle@rac1 ~]$ srvctl start instance -d racdb -i racdb2
   (42.9초)

[oracle@rac1 ~]$ srvctl status database -d racdb -v
Instance racdb1 is running on node rac1. Instance status: Open.
Instance racdb2 is running on node rac2. Instance status: Open.

SQL> select inst_id, instance_name, status from gv$instance order by inst_id;

   INST_ID INSTANCE_NAME    STATUS
---------- ---------------- ------------
         1 racdb1           OPEN
         2 racdb2           OPEN

SQL> select thread#, count(*) from v$log where status='CURRENT'
  2   group by thread# order by thread#;

   THREAD#   COUNT(*)
---------- ----------
         1          1
         2          1

-- 재확인: 정상으로 돌아왔다. 재시도 횟수도 이때 초기화된다.
--
-- 실무 규칙
--   점검이 FAIL 을 보고했는데 몇 분이 지나도 그대로면 CRS 를 더 기다리지 말고
--   crsctl stat res <자원> -t 와 CRS 알럿 로그를 본다.
--   CRS-2771 이 있으면 CRS 는 이미 포기한 것이며 사람이 올려야 한다.
--
--   그리고 반복 장애 자체가 신호다. 한 시간에 두 번 죽었다면 원인이 남아 있다.
--   올려 놓고 끝낼 것이 아니라 왜 죽었는지 봐야 한다.

 [7] 하나의 사건이 여섯 계층에

--   클러스터  자원 상태가 어긋났다        (14장)
--   인스턴스  개수가 줄었다               (12장)
--   스토리지  스레드가 사라졌다           (13장)
--   백업      아카이브 대상이 하나로 줄었다 (17장)
--
-- 그래서 계층 순으로 점검하면 어디서 시작된 문제인지 추적할 수 있다.
-- 반대로 한 계층만 보면 오진한다.
-- 백업 계층만 보는 사람은 "아카이브 대상이 하나로 줄었다" 를 아카이브 설정
-- 문제로 오해할 수 있다. 실제 원인은 인스턴스가 죽은 것이다.
