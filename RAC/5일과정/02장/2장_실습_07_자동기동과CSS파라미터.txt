================================================================================
 제2장 실습 07 — 자동 기동과 CSS 파라미터
 대상   : rac2(172.16.225.102)
 목표   : 자동 기동 설정을 조회·변경·복원하고, CSS 의 축출 판단 파라미터를
          확인해 두 값의 차이가 무엇을 뜻하는지 정리한다
 소요   : 약 25분
 선행   : Clusterware 가 기동되어 있을 것
 계정   : root(config/enable/disable), grid(get css)
 주의   : 자동 기동 설정을 바꾼다. 반드시 enable 로 되돌리고 종료한다.
================================================================================

--------------------------------------------------------------------------------
 [1] 오류 재현 — grid 계정으로 조회하면
--------------------------------------------------------------------------------

[root@rac2 ~]# su - grid
[grid@rac2 ~]$ crsctl config crs
CRS-4563: Insufficient user privileges.

CRS-4000: Command Config failed, or completed with errors.

[grid@rac2 ~]$ crsctl config has
CRS-4563: Insufficient user privileges.

CRS-4000: Command Config failed, or completed with errors.

-- 원인 파악
--   CRS-4563 은 권한 부족이다. crsctl 의 모든 하위 명령이 grid 로 되는 것은
--   아니다. config 계열은 조회조차 root 를 요구한다.
--   어떤 명령이 grid 로 되는지 대조해 본다.

[grid@rac2 ~]$ crsctl check has
CRS-4638: Oracle High Availability Services is online

[grid@rac2 ~]$ crsctl get css misscount
CRS-4678: Successful get misscount 30 for Cluster Synchronization Services.

[grid@rac2 ~]$ crsctl status resource -t | head -3
--------------------------------------------------------------------------------
Name           Target  State        Server                   State details
--------------------------------------------------------------------------------

--   check, get, status 계열은 grid 로 된다. config 계열만 root 를 요구한다.
--   설정을 바꾸는 명령(enable, disable, set)도 당연히 root 다.

-- 조치
[grid@rac2 ~]$ exit
[root@rac2 ~]# /u01/app/19.3.0/grid/bin/crsctl config crs
CRS-4622: Oracle High Availability Services autostart is enabled.

-- 재확인
[root@rac2 ~]# /u01/app/19.3.0/grid/bin/crsctl config has
CRS-4622: Oracle High Availability Services autostart is enabled.

--   root 로 실행할 때는 PATH 에 Grid 홈이 없으므로 전체 경로를 쓴다.
--   편의를 위해 변수로 잡아 두면 편하다.
[root@rac2 ~]# GB=/u01/app/19.3.0/grid/bin

--------------------------------------------------------------------------------
 [2] 자동 기동 설정 변경과 복원
--------------------------------------------------------------------------------

-- 현재 상태를 먼저 기록한다. 이것이 되돌릴 기준이다.
[root@rac2 ~]# $GB/crsctl config crs
CRS-4622: Oracle High Availability Services autostart is enabled.

-- 끈다.
[root@rac2 ~]# $GB/crsctl disable crs
CRS-4621: Oracle High Availability Services autostart is disabled.

[root@rac2 ~]# $GB/crsctl config crs
CRS-4621: Oracle High Availability Services autostart is disabled.

-- 여기서 중요한 점 — 지금 Clusterware 는 여전히 돌고 있다.
[root@rac2 ~]# $GB/crsctl check crs
CRS-4638: Oracle High Availability Services is online
CRS-4537: Cluster Ready Services is online
CRS-4529: Cluster Synchronization Services is online
CRS-4533: Event Manager is online

--   disable 은 "다음 부팅 때 자동으로 올리지 말라"는 설정일 뿐
--   지금 돌고 있는 것을 내리지 않는다. stop 과 disable 은 다른 명령이다.

-- 되돌린다.
[root@rac2 ~]# $GB/crsctl enable crs
CRS-4622: Oracle High Availability Services autostart is enabled.

[root@rac2 ~]# $GB/crsctl config crs
CRS-4622: Oracle High Availability Services autostart is enabled.

--   반드시 이 확인까지 하고 넘어간다. enable 명령의 출력만 보고 끝내지 않는다.
--   config 로 다시 물어 CRS-4622 가 나오는 것을 눈으로 봐야 한다.

--------------------------------------------------------------------------------
 [3] 왜 disable 이 필요한가
--------------------------------------------------------------------------------

-- 쓰는 상황은 정해져 있다.
--   OS 패치나 커널 업그레이드로 노드를 여러 번 재부팅해야 할 때
--   하드웨어 점검으로 노드를 오래 내려 둘 때
--   문제 노드를 클러스터에서 잠시 빼고 조사할 때
--
-- 매번 부팅할 때마다 Clusterware 가 올라와 ASM 을 마운트하고 데이터베이스를
-- 기동하면 작업이 느려지고 상태가 뒤엉킨다. 그래서 꺼 두고 작업한다.
--
-- 작업 순서
--   1) crsctl config crs 로 현재 설정을 기록
--   2) crsctl disable crs        → CRS-4621 확인
--   3) crsctl stop crs           → 스택 정지 (약 2.6분)
--   4) OS 작업 · 재부팅 반복
--   5) crsctl enable crs         → CRS-4622 확인
--   6) crsctl start has          → 스택 기동
--   7) crsctl config crs 로 CRS-4622 재확인   ← 가장 빠뜨리기 쉬운 단계

--------------------------------------------------------------------------------
 [4] 되돌리지 않으면 무슨 일이 생기는가
--------------------------------------------------------------------------------

-- disable 인 채로 노드를 재부팅하면 이렇게 된다.
--   노드는 정상적으로 부팅된다
--   OS 도 네트워크도 정상이다
--   그런데 Clusterware 가 올라오지 않는다
--   아무 오류도 나지 않는다 — 설정대로 동작한 것이기 때문이다
--
-- 살아 있는 노드에서 보면 이렇게 보인다.
[grid@rac1 ~]$ olsnodes -s -n
rac1    1       Active
rac2    2       Inactive

-- 이 상태를 알아채지 못하면 한 노드로만 운영하는 셈이 된다. 부하도 두 배가
-- 되고, 남은 노드에 장애가 나면 서비스 전체가 멈춘다. 몇 주 뒤에야 발견되는
-- 일이 실제로 있다.
--
-- 재발 방지
--   작업 체크리스트의 마지막 항목에 crsctl config crs 로 CRS-4622 확인을 넣는다
--   정기 점검에 모든 노드의 olsnodes -s 가 Active 인지 보는 항목을 넣는다

--------------------------------------------------------------------------------
 [5] CSS 축출 파라미터
--------------------------------------------------------------------------------

[root@rac2 ~]# su - grid
[grid@rac2 ~]$ crsctl get css misscount
CRS-4678: Successful get misscount 30 for Cluster Synchronization Services.

[grid@rac2 ~]$ crsctl get css disktimeout
CRS-4678: Successful get disktimeout 200 for Cluster Synchronization Services.

[grid@rac2 ~]$ crsctl get css reboottime
CRS-4678: Successful get reboottime 3 for Cluster Synchronization Services.

-- 세 값의 뜻
--   misscount 30초    인터커넥트 하트비트가 이 시간 동안 끊기면
--                     네트워크 장애로 판단한다
--   disktimeout 200초 보팅 파일 I/O 가 이 시간 동안 응답하지 않으면
--                     디스크 장애로 판단한다
--   reboottime 3초    축출을 결정한 뒤 노드를 재부팅하기까지 주는 시간
--
-- 왜 30초와 200초로 크게 다른가
--   스토리지는 멀티패스 전환이나 컨트롤러 페일오버 같은 정상적인 일시 지연이
--   흔하다. 성급히 판단하면 오탐이 많아지므로 여유를 크게 준다.
--   반면 인터커넥트 지연은 곧 Cache Fusion 지연이다. 오래 두면 데이터베이스
--   전체가 멈추므로 빨리 판단해 문제 노드를 빼는 편이 낫다.
--   두 값의 차이 자체가 설계 의도를 말해 준다.

-- 시간 동기 상태도 함께 확인해 둔다. CTSS 는 축출 판단의 전제다.
[grid@rac2 ~]$ crsctl check ctss
CRS-4701: The Cluster Time Synchronization Service is in Active mode.
CRS-4702: Offset (in msec): 0

--   Active mode 는 CTSS 가 시간 동기를 직접 맡고 있다는 뜻이다.
--   외부 NTP 를 쓰면 Observer mode 가 된다. 이 실습 환경은 폐쇄망이라
--   chronyd 를 비활성화하고 CTSS 에 맡겼다(3장).
--   Offset 0 은 기준 노드와 시각 차이가 없다는 뜻이다. 노드 간 시각이 어긋나면
--   로그 대조가 불가능해지므로 축출 조사에서 이 값이 중요하다.

--------------------------------------------------------------------------------
 [6] 값을 바꾸는 것에 대하여
--------------------------------------------------------------------------------

-- 변경 명령 자체는 있다.
--   crsctl set css misscount <초>
--   crsctl set css disktimeout <초>
--
-- 그러나 신중해야 한다.
--   misscount 를 늘리면 일시적 네트워크 지연에 노드가 죽는 오탐은 줄어든다.
--   그러나 진짜 장애를 감지하는 시간도 그만큼 늦어진다. 그동안 서로 상대가
--   살아 있다고 믿는 노드들이 같은 데이터를 갱신할 위험, 즉 스플릿 브레인에
--   노출된다.
--   Oracle 은 기본값 유지를 권장한다. 변경은 클러스터 전체를 정지한 상태에서만
--   가능하며, 모든 노드에 같은 값을 적용해야 한다.
--
-- 노드가 자주 축출된다면 값을 늘리기 전에 원인을 찾는 것이 순서다.
--   인터커넥트에 다른 트래픽이 함께 흐르는가 (1장의 사례)
--   스위치 포트에 오류·드롭이 쌓이는가
--   스토리지 경로에 문제가 있는가
--   서버가 스왑을 심하게 쓰고 있는가
-- 20장에서 축출 분석을 본격적으로 다룬다. 이 실습에서는 값을 바꾸지 않는다.

--------------------------------------------------------------------------------
 [8] 정리
--------------------------------------------------------------------------------

-- 확인한 것
--   1) crsctl config 계열은 조회에도 root 가 필요하다(CRS-4563)
--   2) check, get, status 계열은 grid 로 된다
--   3) CRS-4622 enabled / CRS-4621 disabled
--   4) disable 은 다음 부팅 설정일 뿐 지금 돌고 있는 것을 내리지 않는다
--   5) 되돌리지 않으면 오류 없이 노드가 조용히 빠진다
--   6) misscount 30초, disktimeout 200초, reboottime 3초
--   7) 두 값이 다른 이유는 네트워크와 스토리지의 지연 성격이 다르기 때문
--   8) CTSS 는 Active mode, Offset 0
--
-- 원상 복구
--   자동 기동 설정을 enable 로 되돌렸고 CRS-4622 를 확인했다.
--   CSS 파라미터는 조회만 했고 변경하지 않았다.
