================================================================================
 제2장 실습 02 — 두 스택의 구분
 대상   : rac1(172.16.225.101)
 목표   : crsctl check has 와 crsctl check crs 가 무엇을 다르게 보는지 확인하고,
          -init 옵션의 의미와 OLR/OCR 의 차이를 조회로 정리한다
 소요   : 약 20분
 선행   : Clusterware 가 기동되어 있을 것
 계정   : grid, root(ocrcheck)
================================================================================

--------------------------------------------------------------------------------
 [1] 정상 상태에서 두 명령
--------------------------------------------------------------------------------

[root@rac1 ~]# su - grid

[grid@rac1 ~]$ crsctl check has
CRS-4638: Oracle High Availability Services is online

[grid@rac1 ~]$ crsctl check crs
CRS-4638: Oracle High Availability Services is online
CRS-4537: Cluster Ready Services is online
CRS-4529: Cluster Synchronization Services is online
CRS-4533: Event Manager is online

-- 정상일 때는 차이가 눈에 잘 띄지 않는다. check has 는 한 줄, check crs 는
-- 네 줄이라는 것만 보인다. 그런데 check crs 의 첫 줄이 check has 와 같다.
-- 왜 그럴까 -- crs 를 확인하려면 그 아래 OHAS 도 확인해야 하기 때문이다.
-- 계층 구조가 출력 순서에 그대로 드러나 있다.

[grid@rac1 ~]$ crsctl check cluster
CRS-4537: Cluster Ready Services is online
CRS-4529: Cluster Synchronization Services is online
CRS-4533: Event Manager is online

-- check cluster 는 OHAS 줄이 빠진다. 클러스터 계층만 본다는 뜻이다.
-- 여기에 -all 을 붙이면 모든 노드를 한 번에 본다(1장 실습 1).

[grid@rac1 ~]$ crsctl check css
CRS-4529: Cluster Synchronization Services is online

[grid@rac1 ~]$ crsctl check evm
CRS-4533: Event Manager is online

[grid@rac1 ~]$ crsctl check ctss
CRS-4701: The Cluster Time Synchronization Service is in Active mode.
CRS-4702: Offset (in msec): 0

-- 개별 확인도 가능하다. ctss 는 형식이 조금 다르다. Active mode 는 CTSS 가
-- 시간 동기를 직접 맡고 있다는 뜻이다. 외부 NTP 를 쓰면 Observer mode 가 된다.
-- 이 실습 환경은 폐쇄망이라 chronyd 를 비활성화하고 CTSS 에 맡겼다(3장).
-- Offset 0 은 기준 노드와 시각 차이가 없다는 뜻이다.

-- 여기서 가장 중요한 발견이 있다. ora.crsd 가 자원 목록에 들어 있다.
-- 위층 스택 전체가 아래층에게는 자원 하나에 불과하다는 뜻이다.
-- 두 스택은 병렬이 아니라 포함 관계다.
--
-- ora.ctssd 의 State details 가 ACTIVE:0 이다. CTSS 가 Active mode 이고
-- offset 이 0 이라는 뜻으로, crsctl check ctss 의 결과와 일치한다.
--
-- ora.diskmon 이 OFFLINE 인 것은 정상이다. Exadata 스토리지 셀을 감시하는
-- 자원이라 일반 환경에서는 쓰이지 않는다. 1장의 ora.asmgroup 3번과 같은
-- 종류의 함정이다. 환경별로 정상 OFFLINE 목록을 문서화해 두면 좋다.

-- -init 없이 조회하면 완전히 다른 목록이 나온다(1장 실습 1의 그 화면이다).

-- 두 출력을 나란히 놓고 읽는다.
--   위치   OLR 은 로컬 파일 /u01/app/grid/crsdata/rac1/olr/rac1_19.olr
--          OCR 은 ASM 디스크그룹 +CRS
--   ID     OLR 1636561748 / OCR 665666554 — 완전히 별개의 저장소다
--   크기   둘 다 491684KB 로 같아 보이지만 기본 크기로 만들어졌을 뿐
--          같은 파일이어서가 아니다
--
-- OCR 출력의 "Device/File not configured" 네 줄은 오류가 아니다.
-- OCR 은 최대 5벌까지 다중화할 수 있는데 지금은 1벌만 쓰고 있어
-- 나머지 네 자리가 비어 있다는 뜻이다. 5장에서 다중화를 다룬다.
--
-- 이 차이가 부팅 순서를 결정한다. 노드가 막 부팅했을 때 ASM 은 아직 없으므로
-- OCR 을 읽을 수 없다. OHAS 스택은 로컬의 OLR 만으로 시작할 수 있어야 하고,
-- ASM 이 뜬 뒤에야 crsd 가 OCR 을 읽고 올라온다.

--------------------------------------------------------------------------------
 [4] 오류 재현 — ocrcheck 의 -local 을 빠뜨리면
--------------------------------------------------------------------------------

-- OLR 을 점검하려는데 -local 을 빠뜨리는 실수가 흔하다. 그러면 OCR 을 본다.
-- 두 명령이 비슷해 보여 결과를 잘못 해석하기 쉽다.
-- ASM 이 내려간 상황을 가정하면 차이가 극명해진다. rac2 의 CRS 계층을
-- 잠시 내린 상태에서 두 명령을 실행해 본다(실습 05 에서 자세히 다룬다).

[root@rac2 ~]# /u01/app/19.3.0/grid/bin/ocrcheck
PROT-602: Failed to retrieve data from the cluster registry
PROC-26: Error while accessing the physical storage Storage layer error
[Insufficient quorum to open OCR devices] [0]

[root@rac2 ~]# /u01/app/19.3.0/grid/bin/ocrcheck -local
Status of Oracle Local Registry is as follows :
         Version                  :          4
         Total space (kbytes)     :     491684
         Used space (kbytes)      :      83132
         Available space (kbytes) :     408552
         ID                       :  877385927
         Device/File Name         : /u01/app/grid/crsdata/rac2/olr/rac2_19.olr
                                    Device/File integrity check succeeded

         Local registry integrity check succeeded

         Logical corruption check succeeded

-- 원인 파악
--   ASM 이 내려가 있으므로 +CRS 에 접근할 수 없어 OCR 조회가 실패한다.
--   PROC-26 의 메시지가 원인을 정확히 말해 준다 --
--   "Insufficient quorum to open OCR devices". 보팅/OCR 장치를 열 정족수를
--   확보하지 못했다는 뜻이며, ASM 이 없으니 당연한 결과다.
--   반면 OLR 은 로컬 파일이라 ASM 과 무관하게 조회된다.
--   여기서 -local 을 빠뜨리고 실행했다면 레지스트리가 깨졌다고
--   잘못 판단했을 수 있다.
--
--   한 가지 더 눈여겨볼 것이 있다. rac2 의 OLR ID 는 877385927 로
--   rac1 의 1636561748 과 다르다. OLR 은 노드마다 별개의 레지스트리이지
--   같은 내용을 복제해 둔 것이 아니다. 반면 OCR ID 는 665666554 로
--   두 노드에서 같다 -- 하나를 공유하기 때문이다.

-- 조치
--   레지스트리가 손상된 것이 아니라 ASM 이 없는 것이므로,
--   ASM 을 포함한 스택을 올리면 해소된다.
[root@rac2 ~]# /u01/app/19.3.0/grid/bin/crsctl start cluster

-- 재확인
[root@rac2 ~]# /u01/app/19.3.0/grid/bin/ocrcheck | head -8
Status of Oracle Cluster Registry is as follows :
         Version                  :          4
         Total space (kbytes)     :     491684
         Used space (kbytes)      :      84208
         Available space (kbytes) :     407476
         ID                       :  665666554
         Device/File Name         :       +CRS
                                    Device/File integrity check succeeded

-- 배운 것
--   ocrcheck 와 ocrcheck -local 은 서로 다른 저장소를 본다.
--   OCR 조회가 실패하면 레지스트리 손상을 의심하기 전에 ASM 이 떠 있는지
--   먼저 확인한다. OCR 은 ASM 안에 있으므로 ASM 이 없으면 당연히 못 읽는다.
--   이 판별을 건너뛰고 OCR 복구 절차를 시작하면 없던 문제를 만든다.

--------------------------------------------------------------------------------
 [5] 정리
--------------------------------------------------------------------------------

-- 두 스택 대조표
--   구분        OHAS 스택              CRS 스택
--   진입점      ohasd                  crsd
--   저장소      OLR(로컬 파일)         OCR(+CRS, ASM 안)
--   확인        crsctl check has       crsctl check crs
--   자원 조회   status resource -t -init   status resource -t
--   관리 대상   저수준 자원            리스너·VIP·DB·서비스
--
-- 포함 관계의 증거 : -init 목록에 ora.crsd 가 자원으로 들어 있다.
--
-- 이 실습은 조회 중심이며 [4]에서 잠시 내린 스택은 start cluster 로
-- 되살렸다. crsctl check cluster -all 로 양쪽 확인 후 종료한다.
