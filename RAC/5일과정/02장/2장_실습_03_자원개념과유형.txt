--
-- 목록 전체를 외울 필요는 없다. 기본 유형 넷의 구분만 잡으면 충분하다.

-- DHCP 프록시처럼 이 실습 환경에서 쓰지 않는 기능의 것이다.
-- 등록되어 있다고 모두 쓰이는 것은 아니다.

--------------------------------------------------------------------------------
 [3] 자원 하나를 자세히 들여다본다
--------------------------------------------------------------------------------

-- -p 를 붙이면 자원의 속성이 모두 나온다. 데이터베이스 자원을 본다.
[grid@rac1 ~]$ crsctl status resource ora.racdb.db -p | grep -E '^(NAME|TYPE|ACL|AUTO_START|CARDINALITY|PLACEMENT|RESTART_ATTEMPTS|START_DEPENDENCIES|STOP_DEPENDENCIES)='

NAME=ora.racdb.db
TYPE=ora.database.type
ACL=owner:oracle:rwx,pgrp:oinstall:r--,other::r--,group:dba:r-x,group:oper:r-x,group:racdba:r-x,user:grid:r-x
AUTO_START=restore
CARDINALITY=2
PLACEMENT=restricted
RESTART_ATTEMPTS=2
START_DEPENDENCIES=hard(global:uniform:ora.FRA.dg, global:uniform:ora.DATA.dg)
  pullup(global:ora.DATA.dg, global:ora.FRA.dg)
  weak(type:ora.listener.type, global:type:ora.scan_listener.type,
       uniform:ora.ons, global:ora.gns)
STOP_DEPENDENCIES=hard(global:intermediate:ora.asm, global:shutdown:ora.DATA.dg,
                       global:shutdown:ora.FRA.dg)

-- 이 출력이 2.3 절에서 말한 "Clusterware 가 의존 관계를 알고 순서를 스스로
-- 도출한다"의 실제 증거다. 하나씩 읽는다.
--
--   CARDINALITY=2        인스턴스가 2개 필요하다. -nodelist 로 노드 둘을
--                        지정해 DBCA 를 돌렸기 때문이다.
--   PLACEMENT=restricted 정해진 노드에만 배치한다(관리자 관리형 데이터베이스).
--   RESTART_ATTEMPTS=2   죽으면 같은 노드에서 두 번까지 재기동을 시도한다.
--   AUTO_START=restore   재부팅 시 마지막 상태로 되돌린다. 정지 상태였으면
--                        올리지 않고, 기동 상태였으면 올린다.
--
--   START_DEPENDENCIES 의 hard(...ora.FRA.dg, ...ora.DATA.dg)
--     두 디스크그룹이 반드시 먼저 올라와 있어야 데이터베이스가 뜬다.
--     그래서 부팅 순서에서 디스크그룹이 데이터베이스보다 앞선다.
--   pullup(...)
--     디스크그룹이 올라오면 데이터베이스도 따라 올린다는 뜻이다.
--   weak(type:ora.listener.type, ...)
--     리스너는 있으면 좋지만 없어도 기동은 한다. hard 와 weak 의 차이다.
--
--   STOP_DEPENDENCIES 의 hard(...shutdown:ora.DATA.dg, ...)
--     디스크그룹을 내리면 데이터베이스도 함께 내려간다.
--     실습 05 의 정지 출력에서 위층부터 순서대로 내려간 이유가 여기 있다.
--
-- ACL 도 눈여겨볼 만하다. 소유자가 oracle 이고 grid 에게는 r-x 만 주어져 있다.
-- grid 계정으로 이 자원을 기동·정지할 수 없다는 뜻이다. 계정 분리가
-- 권한 수준에서 실제로 강제되고 있다.

--------------------------------------------------------------------------------
 [4] local 자원과 cluster 자원
--------------------------------------------------------------------------------

[grid@rac1 ~]$ crsctl status resource ora.LISTENER.lsnr -p | grep -E '^(NAME|TYPE|AUTO_START)='
NAME=ora.LISTENER.lsnr
TYPE=ora.listener.type
AUTO_START=restore

-- 리스너 자원에는 CARDINALITY 가 없다. local_resource 계열이라 모든 노드에
-- 하나씩 뜨는 것이 정해져 있어 개수를 지정할 필요가 없기 때문이다.
-- 반면 데이터베이스는 cluster_resource 계열이라 CARDINALITY=2 가 필요했다.
--
-- 이 차이가 crsctl status resource -t 화면의 두 덩어리로 나타난다.
--   Local Resources    노드 이름이 줄마다 나온다 (리스너, ONS, 네트워크, chad)
--   Cluster Resources  왼쪽에 인스턴스 번호가 붙는다 (SCAN, VIP, DB, 디스크그룹)

--------------------------------------------------------------------------------
 [5] 서버 풀
--------------------------------------------------------------------------------

[grid@rac1 ~]$ crsctl status serverpool
NAME=Free
ACTIVE_SERVERS=

NAME=Generic
ACTIVE_SERVERS=rac1 rac2

NAME=ora.racdb
ACTIVE_SERVERS=rac1 rac2

-- Free 는 어느 풀에도 배정되지 않은 노드가 들어가는 곳이다. 지금은 비어 있다.
-- Generic 은 관리자 관리형 데이터베이스가 쓰는 기본 풀이다.
-- ora.racdb 는 이 데이터베이스를 위해 만들어진 풀이며 두 노드가 모두 들어 있다.
-- 정책 관리형 데이터베이스를 쓰면 관리자가 만든 풀에 노드를 넣고 Clusterware 가
-- 인스턴스 배치를 결정한다. 12장에서 두 방식의 차이를 다룬다.

--------------------------------------------------------------------------------
 [6] 오류 재현 — 존재하지 않는 자원 이름
--------------------------------------------------------------------------------

-- 자원 이름을 정확히 쓰지 않으면 어떻게 되는지 확인한다.
-- 데이터베이스 자원을 ora.racdb 로 기억하고 조회해 본다.

[grid@rac1 ~]$ crsctl status resource ora.racdb
CRS-2613: Could not find resource 'ora.racdb'.
CRS-4000: Command Status failed, or completed with errors.

-- 원인 파악
--   자원 이름이 틀렸다. ora.racdb 는 서버 풀 이름이고 데이터베이스 자원의
--   이름은 ora.racdb.db 다. 이름 규칙이 있다.
--     ora.<DB이름>.db          데이터베이스
--     ora.<노드>.vip           노드 VIP
--     ora.<디스크그룹>.dg      ASM 디스크그룹
--     ora.LISTENER.lsnr        로컬 리스너
--     ora.LISTENER_SCAN1.lsnr  SCAN 리스너
--   정확한 이름은 목록에서 찾는다.

[grid@rac1 ~]$ crsctl status resource | grep "^NAME" | grep -i racdb
NAME=ora.racdb.db

-- 조치
[grid@rac1 ~]$ crsctl status resource ora.racdb.db -t

--------------------------------------------------------------------------------
Cluster Resources
--------------------------------------------------------------------------------
ora.racdb.db
      1        ONLINE  ONLINE       rac1                     Open,HOME=...,STABLE
      2        ONLINE  ONLINE       rac2                     Open,HOME=...,STABLE

-- 재확인
--   CRS-2613 은 자원이 없다는 뜻이지 클러스터에 문제가 있다는 뜻이 아니다.
--   CRS-4535 나 CRS-4639 와 혼동하지 않는다. 전자는 이름 문제이고
--   후자들은 통신 문제다. 오류 코드의 계열을 구분하는 감각이 필요하다.

 [7] 정리
--------------------------------------------------------------------------------

-- 확인한 것
--   1) 자원 17개, 유형 69개. 등록된 유형이 모두 쓰이는 것은 아니다
--   2) 모든 자원 이름에 ora. 접두어가 붙어 있다 — Oracle 정의 자원
--   3) -p 로 보면 CARDINALITY, PLACEMENT, RESTART_ATTEMPTS, AUTO_START 와
--      START/STOP_DEPENDENCIES 가 나온다
--   4) 의존 관계의 hard / weak / pullup 이 기동·정지 순서를 결정한다
--   5) ACL 로 계정별 권한이 강제된다 — grid 는 DB 자원에 r-x 뿐
--   6) local_resource 는 CARDINALITY 가 없고 cluster_resource 는 있다
--   7) 서버 풀은 Free, Generic, ora.racdb 세 개
--
-- 이 실습은 조회만 했으므로 원상 복구할 것이 없다.
