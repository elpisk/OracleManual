 [2] 기준선 — 24 / 3 / 3

-------- ----------

racdb1             3

3 rows selected.

-- 이 세 숫자가 이 랩의 기준선이다.
-- SPFILE 이 깨끗한지 한 번에 확인하는 지표로 쓴다.
--
-- 인스턴스별 항목이 3 개보다 많으면 누군가 무언가를 넣은 것이다.

-- 잔뜩 나눠 관리하는 것이 아니다. 24 대 6 이다.

--------------------------------------------------------------------------------
 [3] 인스턴스마다 다른 셋
--------------------------------------------------------------------------------

SQL> col name for a26
SQL> col value for a44
SQL> select name, sid, value from v$spparameter
  2   where isspecified='TRUE' and sid <> '*' order by name, sid;

NAME                 SID      VALUE
-------------------- -------- ----------
instance_number      racdb1   1
instance_number      racdb2   2
thread               racdb1   1
thread               racdb2   2
undo_tablespace      racdb1   UNDOTBS1
undo_tablespace      racdb2   UNDOTBS2

6 rows selected.

-- 세 파라미터뿐이고 셋 다 "달라야만 하는" 값이다.
--
--  instance_number
--    인스턴스를 구분하는 번호. 같으면 두 인스턴스가 서로를 자기라고 여겨
--    클러스터 멤버십이 성립하지 않는다.
--
--  thread
--    리두 스레드 번호. 10장 실습 01 에서 V$LOG 의 THREAD# 로 확인한 그것이다.
--    각 인스턴스가 자기 스레드의 리두로그에만 쓴다.
--    같으면 두 인스턴스가 같은 리두로그에 동시에 쓰려 해 로그가 망가진다.
--
--  undo_tablespace
--    각 인스턴스가 쓸 UNDO. 같으면 UNDO 세그먼트를 두고 다투게 되어
--    경합이 발생하고 일관성 읽기가 꼬인다.
--
-- 셋 다 dbca 가 데이터베이스를 만들 때 자동으로 지정한다.
-- 사람이 신경 쓸 일은 노드를 추가할 때뿐이다.

--------------------------------------------------------------------------------
 [4] 10장의 리두 스레드와 연결해 보기
--------------------------------------------------------------------------------

SQL> select group#, thread#, status from v$log order by group#;

    GROUP#    THREAD# STATUS
---------- ---------- ----------------
         1          1 INACTIVE
         2          1 CURRENT
         3          2 CURRENT
         4          2 INACTIVE

4 rows selected.

-- SPFILE 의 racdb1.thread=1 과 racdb2.thread=2 가 여기에 대응한다.
--   그룹 1·2 → THREAD# 1 → racdb1 이 쓴다
--   그룹 3·4 → THREAD# 2 → racdb2 가 쓴다
--
-- 스레드마다 CURRENT 가 하나씩 있다. 각 인스턴스가 독립적으로 로그 스위치를
-- 하기 때문이다. 어느 그룹이 CURRENT 인지는 조회 시점마다 달라진다.
--
-- 노드를 추가하면 리두 스레드도 함께 만들어야 하는 이유가 이 구조에 있다.
-- 새 인스턴스가 쓸 스레드가 없으면 기동되지 않는다.

--------------------------------------------------------------------------------
 [5] 조회가 비었을 때 — 실패인가 답인가
--------------------------------------------------------------------------------

-- 특정 파라미터가 인스턴스별로 지정되어 있는지 확인해 본다.

SQL> select sid, name from v$spparameter where name='sga_target' and sid<>'*';

no rows selected

-- 여기서 판단이 갈린다. 조회가 잘못된 것인가, 아니면 답인가.
--
-- 원인 파악 : 0 행은 실패가 아니라 답이다.
--             sga_target 은 `*` 로만 지정되어 있어 인스턴스별 항목이 없다.
--             [1] 의 목록에서 확인한 그대로다.
-- 조치     : 조건을 고칠 것이 아니라 반대 조건으로 대조해 조회 자체가
--             동작하는지 확인한다.
-- 재확인   : 아래 두 조회로 구분한다.

SQL> select sid, name from v$spparameter where name='no_such_param';

no rows selected

SQL> select sid, name, value from v$spparameter where name='sga_target'
  2     and isspecified='TRUE';

SID      NAME                 VALUE
-------- -------------------- ------------
*        sga_target           1887436800

1 row selected.

-- 첫 조회는 파라미터 자체가 없어서 0 행이고,
-- 두 번째는 파라미터가 있고 `*` 로 지정되어 있음을 보여 준다.
--
-- 점검 스크립트를 쓸 때 이 구분이 중요하다.
-- 0 행이 "이상 없음" 인지 "조회가 잘못됨" 인지 구별해야 한다.
-- 반대 조건으로 한 번 대조하면 확실해진다.

--------------------------------------------------------------------------------
 [6] SPFILE 에 없는데 다른 값도 있다
--------------------------------------------------------------------------------

SQL> col name for a20
SQL> col v1 for a24
SQL> col v2 for a24
SQL> select p1.name,
  2         max(case when p1.inst_id=1 then p1.value end) v1,
  3         max(case when p1.inst_id=2 then p1.value end) v2
  4    from gv$parameter p1
  5   where p1.name in ('instance_name','instance_number','thread')
  6   group by p1.name order by p1.name;

NAME                 V1                       V2
-------------------- ------------------------ ------------------------
instance_name        racdb1                   racdb2
instance_number      1                        2
thread               1                        2

3 rows selected.

-- instance_name 은 [1] 의 SPFILE 목록에 없었다. 그런데 값이 다르다.
--
-- 원인 파악 : 기동할 때 ORACLE_SID 에서 결정되기 때문이다.
--             SPFILE 에 기록되지 않아도 인스턴스마다 다른 값을 갖는다.
-- 조치     : SPFILE 목록만 보고 "나머지는 다 공통" 이라고 판단하지 않는다.
-- 재확인   : 실제 적용된 값을 알려면 V$SPPARAMETER 가 아니라
--             GV$PARAMETER 를 봐야 한다. 앞은 SPFILE 의 내용이고
--             뒤는 지금 인스턴스가 쓰고 있는 값이다.
--
-- 두 뷰의 차이를 정리하면 이렇다.
--   V$SPPARAMETER  — SPFILE 에 무엇이 적혀 있는가 (다음 기동에 쓸 값)
--   V$PARAMETER    — 지금 이 인스턴스가 무엇을 쓰고 있는가
--   GV$PARAMETER   — 모든 인스턴스가 무엇을 쓰고 있는가

SQL> exit
