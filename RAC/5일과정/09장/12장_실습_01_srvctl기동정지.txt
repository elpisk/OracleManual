 제12장 실습 01 — srvctl 기동·정지와 옵션
 대상   : rac1
 목표   : srvctl 이 CRS 안에 저장된 무엇을 알고 있는지 확인하고, 인스턴스 하나를
          내렸다 올리며 database 와 instance 단위의 차이를 익힌다
 소요   : 약 25분
 선행   : racdb 양 노드 OPEN, 부하 4 이하
 계정   : oracle, grid
================================================================================

--------------------------------------------------------------------------------

-- 이것이 CRS 안에 저장된 racdb 의 정의다. 데이터베이스가 내려가 있어도 남는다.
--
-- 눈여겨볼 줄.
--   Start options: open      → srvctl start 를 옵션 없이 하면 OPEN 까지 간다
--   Stop options: immediate  → srvctl stop 은 shutdown immediate 를 뜻한다
--   Management policy: AUTOMATIC → 노드 부팅 시 CRS 가 자동으로 올린다
--   Disk Groups: DATA,FRA    → racdb 의 시작 의존성 (8장의 CRS-2640 과 관련)
--   Database instances / Configured nodes → 어느 노드에 무엇이 있는가

--------------------------------------------------------------------------------
 [2] start 와 stop 의 옵션 비교
--------------------------------------------------------------------------------

[oracle@rac1 ~]$ srvctl start database -h
Starts the database.
Usage: srvctl start database -db <db_unique_name> [-startoption <start_options>]
       [-startconcurrency <start_concurrency>] [-node <node> | -serverpool "..."]
       [-eval] [-verbose]
    -startoption <start_options>   Options to startup command
                                   (e.g. OPEN, MOUNT, or "READ ONLY")
    -startconcurrency <n>          Number of instances to be started simultaneously
    -eval                          Evaluates the effects of event without making
                                   any changes to the system

[oracle@rac1 ~]$ srvctl stop database -h
Stops the database.
Usage: srvctl stop database -db <db_unique_name> [-stopoption <stop_options>]
       [-stopconcurrency <stop_concurrency>] [-drain_timeout <timeout>] [-force]
       [-eval] [-verbose]
    -stopoption <stop_options>     Options to shutdown command
                                   (e.g. NORMAL, TRANSACTIONAL, IMMEDIATE, or ABORT)
    -drain_timeout <drain_timeout> Service drain timeout specified in seconds
    -force                         Force stop, will stop database and any
                                   associated services and any dependent resources

-- 읽어 낼 것.
--  1) -startoption 이 SQL*Plus 인자를 그대로 받는다
--     → srvctl 이 결국 그 명령을 대신 실행한다는 뜻이다
--  2) -startconcurrency / -stopconcurrency 는 RAC 전용이다
--     → 자원이 빠듯한 환경에서는 1 로 지정해 순차 처리하는 것이 안전하다
--  3) -force 와 -drain_timeout 은 stop 에만 있다
--     → 정지에는 "의존하는 것들도 함께" 라는 요구가 있지만 기동에는 없다
--  4) -eval 은 실행하지 않고 영향만 계산한다
--     → 운영에서 정지 전에 무엇이 함께 내려가는지 확인할 때 쓴다

--------------------------------------------------------------------------------
 [3] 정지 전 상태 기록
--------------------------------------------------------------------------------

[oracle@rac1 ~]$ srvctl status database -d racdb -v
Instance racdb1 is running on node rac1. Instance status: Open.
Instance racdb2 is running on node rac2. Instance status: Open.

[grid@rac1 ~]$ crsctl stat res ora.racdb.db -t
--------------------------------------------------------------------------------
ora.racdb.db
      1        ONLINE  ONLINE       rac1     Open,HOME=/u01/app/oracle/...,STABLE
      2        ONLINE  ONLINE       rac2     Open,HOME=/u01/app/oracle/...,STABLE
--------------------------------------------------------------------------------

-- 앞 두 열이 TARGET 과 STATE 다.
--   TARGET — CRS 가 이 자원을 어떤 상태로 유지하려 하는가 (의도)
--   STATE  — 지금 실제로 어떤 상태인가 (현실)
--
-- CRS 의 역할은 이 둘을 일치시키는 것이다. 지금은 둘 다 ONLINE 이라 할 일이 없다.
-- 이 두 열의 구분이 실습 03 의 핵심이 된다.

--------------------------------------------------------------------------------
 [4] 인스턴스 하나만 정지
--------------------------------------------------------------------------------

[oracle@rac1 ~]$ srvctl stop instance -d racdb -i racdb2

                                                              (50.1초 소요)

-- rac1 에서 실행했는데 rac2 의 인스턴스가 내려간다.
-- srvctl 은 어느 노드에서든 실행할 수 있다.

[oracle@rac1 ~]$ srvctl status database -d racdb -v
Instance racdb1 is running on node rac1. Instance status: Open.
Instance racdb2 is not running on node rac2

SQL> col host_name for a10
SQL> select inst_id, instance_name, host_name, status from gv$instance order by 1;

   INST_ID INSTANCE_NAME    HOST_NAME  STATUS
---------- ---------------- ---------- ------------
         1 racdb1           rac1.local OPEN
                            domain

1 row selected.

-- GV$INSTANCE 가 한 행으로 줄었다.
-- 데이터베이스는 계속 살아 있다. 내려간 것은 인스턴스 하나뿐이다.
-- 단일 인스턴스에서는 인스턴스 정지가 곧 데이터베이스 정지지만 RAC 은 다르다.
-- 이 차이가 롤링 패치와 노드별 유지보수를 가능하게 한다.

--------------------------------------------------------------------------------
 [5] CRS 쪽에서 본 결과
--------------------------------------------------------------------------------

[grid@rac1 ~]$ crsctl stat res ora.racdb.db -t
--------------------------------------------------------------------------------
ora.racdb.db
      1        ONLINE  ONLINE       rac1     Open,HOME=/u01/app/oracle/...,STABLE
      2        OFFLINE OFFLINE               Instance Shutdown,STABLE
--------------------------------------------------------------------------------

-- 2 번 인스턴스의 TARGET 이 ONLINE 에서 OFFLINE 으로 바뀌었다.
-- srvctl stop 은 TARGET 과 STATE 를 함께 내린다.
--
-- State details 열도 읽는다. "Instance Shutdown" 은 왜 내려가 있는지를
-- CRS 가 기록해 둔 것이다. 이 열을 보는 습관을 들이면 자원 상태를 빨리 판단한다.
--
-- 둘이 일치하므로 CRS 는 아무것도 하지 않는다. 다시 올리려 시도하지 않는다.

 [7] 다시 기동
--------------------------------------------------------------------------------

[oracle@rac1 ~]$ srvctl start instance -d racdb -i racdb2

                                                              (40.6초 소요)

SQL> select inst_id, instance_name, status from gv$instance order by 1;

   INST_ID INSTANCE_NAME    STATUS
---------- ---------------- ------------
         1 racdb1           OPEN
         2 racdb2           OPEN

2 rows selected.

[grid@rac1 ~]$ crsctl stat res ora.racdb.db -t
ora.racdb.db
      1        ONLINE  ONLINE       rac1     Open,...,STABLE
      2        ONLINE  ONLINE       rac2     Open,...,STABLE

-- 정지 50.1 초, 기동 40.6 초다.
-- 기동이 더 빠른 것이 의외로 보이지만 정지 쪽에 세션 정리와 체크포인트가
-- 포함되기 때문이다.
--
-- TARGET 이 ONLINE 으로 돌아왔다. 이것이 중요하다.
-- srvctl 로 내린 인스턴스는 srvctl 로 올려야 TARGET 이 복구된다.
-- 그렇지 않으면 노드를 재부팅해도 올라오지 않는다.

--------------------------------------------------------------------------------
 [8] 오류 재현 — 인스턴스 이름을 잘못 쓰면
--------------------------------------------------------------------------------

[oracle@rac1 ~]$ srvctl stop instance -d racdb -i racdb9
PRKO-3032 : Invalid instance name(s): racdb9

-- 오류 : PRKO-3032
--
-- 원인 파악 : srvctl 은 CRS 에 등록된 인스턴스 목록과 대조한다.
--             실습 01 [1] 의 Database instances: racdb1,racdb2 가 그 목록이다.
--             거기 없는 이름은 실행 전에 걸러진다.
-- 조치     : srvctl config database -d racdb 로 정확한 인스턴스 이름을 확인한다.
-- 재확인   : 올바른 이름으로 실행하면 정상 동작한다.
--
-- 이 검증이 있어서 오타로 엉뚱한 인스턴스를 내리는 일은 생기지 않는다.
-- 다만 노드 이름과 인스턴스 이름을 혼동하는 실수는 여전히 가능하므로
-- -i 뒤에는 인스턴스 이름(racdb1)을, -node 뒤에는 노드 이름(rac1)을 쓴다.

--------------------------------------------------------------------------------
 [9] 이미 떠 있는 인스턴스를 다시 기동하면
--------------------------------------------------------------------------------

[oracle@rac1 ~]$ srvctl start instance -d racdb -i racdb1
PRCC-1015 : racdb was already running on rac1
PRCR-1004 : Resource ora.racdb.db is already running

-- 오류 : PRCC-1015 / PRCR-1004
--
-- 원인 파악 : 자원이 이미 ONLINE 이므로 CRS 가 중복 기동을 거부했다.
--             오류처럼 보이지만 실제로는 아무것도 망가지지 않았다.
-- 조치     : 조치할 것이 없다. 이미 원하는 상태다.
-- 재확인   : srvctl status database -d racdb -v 로 두 인스턴스가 모두
--             running 인지 확인한다.
--
-- 스크립트에서 이 메시지를 실패로 처리하지 않도록 주의한다.
-- "이미 떠 있음" 은 대개 원하는 결과이지 오류가 아니다.

--------------------------------------------------------------------------------
 [10] 자원이 빠듯한 환경에서의 주의
--------------------------------------------------------------------------------

-- srvctl start database 는 기본적으로 여러 인스턴스를 동시에 올린다.
-- 이 랩처럼 호스트 CPU 가 넉넉하지 않으면 부하가 급등해 노드가 축출될 수 있다.
--
-- 안전한 방법 두 가지.
--   (1) srvctl start database -d racdb -startconcurrency 1
--   (2) srvctl start instance 로 하나씩 올리고 사이에 부하를 확인
--
-- 기동 전에 cat /proc/loadavg 로 4 이하인지 확인하는 습관을 권한다.
