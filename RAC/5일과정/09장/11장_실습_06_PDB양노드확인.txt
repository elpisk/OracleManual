 제11장 실습 06 — PDB 를 양쪽 노드에서 확인하기
 대상   : rac1
 목표   : dbca 가 PDB 에 대해 하는 일과 하지 않는 일을 구분하고, 재기동 후의
          함정을 직접 확인한 뒤 예방한다
 소요   : 약 15분 (재기동에 약 2분)
 선행   : 실습 05 완료
 계정   : oracle
================================================================================

--------------------------------------------------------------------------------
 [1] 생성 직후의 상태
--------------------------------------------------------------------------------

[oracle@rac1 ~]$ export ORACLE_SID=testdb1
[oracle@rac1 ~]$ $ORACLE_HOME/bin/sqlplus -s / as sysdba

SQL> col name for a12
SQL> select inst_id, con_id, name, open_mode from gv$pdbs order by 1,2;

   INST_ID     CON_ID NAME         OPEN_MODE
---------- ---------- ------------ ----------
         1          2 PDB$SEED     READ ONLY
         1          3 TESTPDB      READ WRITE
         2          2 PDB$SEED     READ ONLY
         2          3 TESTPDB      READ WRITE

4 rows selected.

-- 4 행이다. PDB 둘 × 인스턴스 둘이다.
-- 양 노드에서 TESTPDB 가 READ WRITE 다. dbca 가 만들면서 열어 둔 것이다.
--
-- 여기까지만 보면 아무 문제가 없어 보인다.
-- 애플리케이션 연결 테스트도 통과할 것이다.
--
-- 그런데 한 가지가 빠져 있다.

--------------------------------------------------------------------------------
 [2] 빠진 것 — 저장 상태
--------------------------------------------------------------------------------

SQL> select con_name, instance_name, state from dba_pdb_saved_states;

no rows selected

-- 저장된 상태가 없다.
--
-- 원인 파악 : dbca 는 PDB 를 만들고 열기까지 한다.
--             다만 그 상태를 dba_pdb_saved_states 에 기록하지 않는다.
--             PDB 의 열림 상태는 기본적으로 인스턴스 재기동 후 유지되지 않으며,
--             저장해 두어야 CDB 가 열릴 때 함께 열린다.
-- 조치     : 생성 직후에 사람이 저장해야 한다. [5] 에서 수행한다.
-- 재확인   : 먼저 저장하지 않은 상태로 재기동해 어떻게 되는지 본다. [3]·[4]
--
-- 12장에서 racdb 를 조회했을 때는 RACPDB1 이 두 인스턴스 모두 OPEN 으로
-- 저장되어 있었다. 그것은 누군가 나중에 저장했기 때문이다.
-- 둘 다 dbca 로 만들었는데 차이가 나는 이유가 이것이다.

--------------------------------------------------------------------------------
 [3] 재기동
--------------------------------------------------------------------------------

[oracle@rac1 ~]$ srvctl stop database -d testdb
                                                              (43.8초 소요)

[oracle@rac1 ~]$ srvctl start instance -d testdb -i testdb1
                                                              (30.2초 소요)

[oracle@rac1 ~]$ srvctl start instance -d testdb -i testdb2
                                                              (34.6초 소요)

-- 12장에서 배운 대로 순차로 기동했다.
-- 자원이 빠듯한 환경에서는 동시 기동보다 안전하다.
-- srvctl start database -startconcurrency 1 로도 같은 효과를 낸다.
--
-- 정지 43.8 초, 기동 30.2 + 34.6 초다.
-- racdb 보다 빠른 것은 데이터가 없고 SGA 가 작기 때문이다.

--------------------------------------------------------------------------------
 [4] 재기동 후 — 예상과 확인
--------------------------------------------------------------------------------

SQL> col name for a12
SQL> select inst_id, con_id, name, open_mode from gv$pdbs order by 1,2;

   INST_ID     CON_ID NAME         OPEN_MODE
---------- ---------- ------------ ----------
         1          2 PDB$SEED     READ ONLY
         1          3 TESTPDB      MOUNTED
         2          2 PDB$SEED     READ ONLY
         2          3 TESTPDB      MOUNTED

4 rows selected.

-- TESTPDB 가 양 노드 모두 MOUNTED 로 바뀌었다.
-- CDB 는 열렸지만 PDB 는 닫힌 상태다.
--
-- PDB$SEED 가 READ ONLY 를 유지하는 것과 대비된다.
-- 씨앗 PDB 는 CDB 가 열리면 항상 READ ONLY 로 열린다.
--
-- 이 시점에 이 데이터베이스에 접속하는 애플리케이션은 동작하지 않는다.

--------------------------------------------------------------------------------
 [5] 증상이 애매한 이유
--------------------------------------------------------------------------------

[oracle@rac1 ~]$ srvctl status database -d testdb -v
Instance testdb1 is running on node rac1. Instance status: Open.
Instance testdb2 is running on node rac2. Instance status: Open.

-- 관리자 관점의 지표가 모두 정상이다.
--   srvctl status  → Open
--   crsctl stat res → ONLINE / ONLINE
--   리스너         → 정상
--
-- 그런데 사용자가 PDB 에 접속하면 실패한다.
-- 12장 실습 07 에서 본 오류가 이때 나온다.
--   조회 시도 → ORA-01219
--   DML 시도  → ORA-01109
--
-- 12장 때와 다른 점이 하나 있다.
-- 그때는 한 노드만 닫혀 있어 SCAN 접속이 어느 노드로 가느냐에 따라
-- 간헐적으로 실패했다.
-- 여기서는 양 노드가 모두 닫혀 있으므로 항상 실패한다.
-- 간헐적이 아니라는 점에서 오히려 진단은 쉽다.

--------------------------------------------------------------------------------
 [6] 조치 — 열고 저장한다
--------------------------------------------------------------------------------

SQL> alter pluggable database testpdb open instances=all;

Pluggable database altered.

SQL> alter pluggable database testpdb save state instances=all;

Pluggable database altered.

-- 두 명령이 필요하다. 여는 것과 그 상태를 저장하는 것은 별개다.
-- 둘 다 instances=all 을 붙였다.
--
-- 12장에서 다룬 대로 저장 상태도 인스턴스별로 기록된다.
-- 한 노드에서만 저장하면 그 노드에서만 자동으로 열리고,
-- 결과적으로 노드별 상태가 어긋나 간헐적 오류가 재기동 후에 나타난다.

SQL> col name for a12
SQL> select inst_id, name, open_mode from gv$pdbs where name='TESTPDB' order by 1;

   INST_ID NAME         OPEN_MODE
---------- ------------ ----------
         1 TESTPDB      READ WRITE
         2 TESTPDB      READ WRITE

2 rows selected.

SQL> select con_name, instance_name, state from dba_pdb_saved_states order by 2;

CON_NAME   INSTANCE_NAME   STATE
---------- --------------- --------
TESTPDB    testdb1         OPEN
TESTPDB    testdb2         OPEN

2 rows selected.

-- 재확인 : 양 노드 READ WRITE 이고 저장 상태가 인스턴스마다 한 행씩 생겼다.
--          이제 다음 재기동부터는 자동으로 열린다.
--
-- 12장에서 racdb 를 조회했을 때와 같은 모양이 되었다.

--------------------------------------------------------------------------------
 [7] 생성 후 점검표
--------------------------------------------------------------------------------

-- dbca 가 끝났다고 작업이 끝난 것이 아니다.
--
--  1. CRS 자원이 양 노드에서 ONLINE 인가        (실습 04 [6])
--  2. 인스턴스가 둘이고 스레드가 둘인가          (실습 05 [2])
--  3. UNDO 가 인스턴스 수만큼 있는가             (실습 05 [4])
--  4. PDB 를 열고 상태를 저장했는가              ← dbca 는 하지 않는다
--  5. 재기동 시험을 했는가                       ← 지금이 가장 좋은 때
--
-- 4 와 5 가 자주 빠진다.
--
-- 5 를 생성 직후에 하라고 권하는 이유는 데이터가 없어 위험이 가장 낮기
-- 때문이다. 운영 데이터가 들어간 뒤에 처음 재기동하면 그때 문제가 드러나고
-- 되돌리기 어렵다.
--
-- 이 실습에서 3·4·5 를 한 번에 했다.
-- 재기동해 보니 PDB 가 닫혔고, 그것을 열고 저장했으며, 이제 다시 재기동해도
-- 열려 있을 것이다. 신규 데이터베이스 인수인계 전에 반드시 밟을 순서다.

SQL> exit
