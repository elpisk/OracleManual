 [2] 디스크를 추가한다 — 파워 1
--------------------------------------------------------------------------------

SQL> alter diskgroup TESTN add failgroup fgC disk '/dev/asmdisk/test6'
  2    name d_c rebalance power 1;

Diskgroup altered.

-- 명령이 즉시 끝났다. 그러나 작업은 이제 시작이다.
-- 장애 그룹 이름 fgC 와 디스크 이름 d_c 를 명시적으로 지정한 점을 눈여겨보라.
-- 빠뜨리면 ASM 이 디스크 이름을 장애 그룹 이름으로 쓴다. 6장에서 확인했다.

--------------------------------------------------------------------------------
 [3] v$asm_operation 을 반복 조회한다
--------------------------------------------------------------------------------

-- 15초 간격으로 조회한 결과를 시각과 함께 정리하면 이렇다.

[  1.2s] REBAL RUN power=1 sofar=0    est_work=0
[ 28.3s] REBAL RUN power=1 sofar=210  est_work=1535
[ 50.6s] REBAL RUN power=1 sofar=608  est_work=1535
[ 73.2s] REBAL RUN power=1 sofar=873  est_work=1535
[ 95.5s] REBAL RUN power=1 sofar=1139 est_work=1535
[116.8s] REBAL RUN power=1 sofar=38   est_work=0
[144.7s] REBAL RUN power=1 sofar=193  est_work=0
[166.0s] REBAL RUN power=1 sofar=336  est_work=0
[192.9s] REBAL RUN power=1 sofar=601  est_work=0
[239.1s] 완료 (v$asm_operation 이 비었다)

-- 세 가지를 읽는다.
--
-- 첫째, 처음 조회(1.2초)에서 est_work 가 0이다. ASM 이 아직 작업량을
-- 계산하지 못한 상태다. 곧 1535 로 잡힌다. ARBA 프로세스가 계산한다.
--
-- 둘째, sofar 가 1139 까지 올라간 뒤 116.8초 시점에 38 로 떨어졌다.
-- 리밸런스가 여러 단계(phase)로 나뉘어 있고 단계가 바뀔 때 카운터가
-- 초기화되기 때문이다.
--
-- 셋째, 두 번째 단계에서는 est_work 도 0이다. 작업량을 미리 계산하지 않는다.
--
-- 결론 — sofar 나누기 est_work 로 진행률을 계산하면 안 된다.
--   0으로 나누기 오류가 나거나
--   퍼센트가 갑자기 뒤로 가서 실패한 것처럼 보인다
-- 완료 판단은 v$asm_operation 에 행이 있는지로만 한다.

MOUNTED  NORMAL  Y         512   4096  1048576     12288     6956  ...  TESTN/

-- Rebal 이 Y 로 바뀌었다. 여러 디스크그룹을 한눈에 볼 때 편하다.

[root@rac1 ~]# ps -u grid -o pid,cmd | grep asm_arb | grep -v grep
13779 asm_arba_+ASM1
13781 asm_arb0_+ASM1

-- 평상시에는 0개였던 ARB 프로세스가 두 개 떴다.
--   ARBA  작업량 추정. EST_WORK 와 EST_MINUTES 를 계산한다
--   ARB0  실제 익스텐트 복사. 파워 1이므로 하나만 떴다
--
-- 파워를 8로 주면 ARB0 부터 여러 개가 뜬다. 이 개수로 파워가 실제
-- 적용되었는지 확인할 수 있다.

SQL> select x.disk_kffxp disk, count(*) extents

  4   group by x.disk_kffxp order by 1;

      DISK    EXTENTS

         1       1775

-- 2610MB 씩 쓰던 두 디스크가 1779, 1778, 1775MB 로 나뉘었다.
-- 익스텐트 개수도 1776, 1775, 1772 로 거의 같다.
--
-- 리밸런스의 목표가 이것이다. 새 디스크에만 새 데이터를 쓰는 것이 아니라
-- 기존 데이터를 옮겨 와 전체를 고르게 만든다. 그래서 시간이 걸린다.
--
-- 디스크가 100장인 디스크그룹에 한 장을 추가해도 전체 재분배가 일어난다.
-- 용량이 다른 디스크가 섞여 있으면 절대량이 아니라 사용 비율을 맞춘다.

--------------------------------------------------------------------------------
 [7] 쓸 수 있는 공간이 줄었다
--------------------------------------------------------------------------------

SQL> select name, total_mb, free_mb, required_mirror_free_mb, usable_file_mb
  2    from v$asm_diskgroup where name='TESTN';

NAME       TOTAL_MB    FREE_MB REQUIRED_MIRROR_FREE_MB USABLE_FILE_MB
-------- ---------- ---------- ----------------------- --------------
TESTN         12288       6956                    4096           1430

-- 비교하면 이렇다.
--                        추가 전    추가 후
--   TOTAL_MB               8192      12288   (늘었다)
--   FREE_MB                2972       6956   (늘었다)
--   REQUIRED_MIRROR_FREE      0       4096   (생겼다)
--   USABLE_FILE_MB         1486       1430   (줄었다)
--
-- 물리 용량이 1.5배가 되었는데 쓸 수 있는 공간은 오히려 줄었다.
-- 처음 보면 당황스럽지만 계산해 보면 이유가 분명하다.
--
--   USABLE_FILE_MB = (FREE_MB - REQUIRED_MIRROR_FREE_MB) / 미러 배수
--                  = (6956 - 4096) / 2
--                  = 1430
--
-- REQUIRED_MIRROR_FREE_MB 4096 은 디스크 한 장 크기와 같다. 디스크 한 장이
-- 죽었을 때 그만큼의 미러를 다시 만들 공간을 예약한 것이다.
--
-- 손해가 아니다. 계산이 정확해진 것이다. 디스크 2장일 때의 0은 손실 대비가
-- 불가능해서 계산하지 않은 값이었다. 3장이 되어서야 비로소 한 장 손실을
-- 견딜 수 있게 되었고 그 비용이 드러났다.

 [8b] 오류 재현 — 같은 디스크를 한 번 더 추가하면
--------------------------------------------------------------------------------

SQL> alter diskgroup TESTN add failgroup fgE disk '/dev/asmdisk/test6' name d_e;
alter diskgroup TESTN add failgroup fgE disk '/dev/asmdisk/test6' name d_e
*
ERROR at line 1:
ORA-15032: not all alterations performed
ORA-15029: disk '/dev/asmdisk/test6' is already mounted by this instance

-- 오류 : ORA-15032, ORA-15029
-- 원인 파악 : 방금 추가한 디스크를 또 추가하려 했다. 6장에서 +DATA 의
--             디스크로 새 디스크그룹을 만들려 했을 때 나온 것과 같은 코드다.
--             already mounted by this instance 는 그 디스크를 현재 이
--             ASM 인스턴스가 어느 디스크그룹의 일부로 열고 있다는 뜻이다.
--
--             비슷하지만 다른 오류가 ORA-15033(belongs to diskgroup)이다.
--             구분 기준은 GROUP_NUMBER 다.
--               0이 아니다  -> 현재 사용 중. ORA-15029
--               0인데 MEMBER -> FORCE 제거의 잔재. ORA-15033
-- 조치     : v$asm_disk 에서 대상 디스크의 상태를 먼저 확인하고
--             CANDIDATE 나 FORMER 인 디스크를 지정한다.
-- 재확인   : 현재 구성이 바뀌지 않았는지 본다.

SQL> select path, name, header_status, group_number
  2    from v$asm_disk where path like '%test6%';

PATH                   NAME  HEADER_STATU GROUP_NUMBER
---------------------- ----- ------------ ------------
/dev/asmdisk/test6     D_C   MEMBER                  5

SQL> select count(*) disks from v$asm_disk
  2   where group_number=(select group_number from v$asm_diskgroup where name='TESTN');

     DISKS
----------
         4

-- GROUP_NUMBER 가 5다. TESTN 이 현재 쓰고 있으므로 정상적인 거절이었다.
-- 디스크 수도 그대로다. 실패한 명령이 아무것도 바꾸지 않았다.

--------------------------------------------------------------------------------
 [9] 정리
--------------------------------------------------------------------------------

-- 확인한 것
--   1) 추가 명령은 즉시 끝나지만 리밸런스는 239초 걸렸다
--   2) est_work 는 처음에 0이다가 ARBA 가 계산한 뒤 채워진다
--   3) sofar 는 단계가 바뀌면 초기화된다. 진행률로 쓰면 안 된다
--   4) 완료 판단은 v$asm_operation 이 비었는지로 한다
--   5) 리밸런스 중 Rebal 이 Y, ARB 프로세스가 뜬다
--   6) 사용량이 1779/1778/1775 로 고르게 재분배되었다
--   7) USABLE_FILE_MB 는 1486 에서 1430 으로 줄었다. 계산이 정확해진 것
--   8) 데이터베이스는 아무 영향을 받지 않았다
--
-- 실무 지침
--   디스크 추가 명령이 끝났다고 작업이 끝난 것이 아니다.
--   업무 시간에는 파워 1로 시작하고 응답 시간을 지켜본다.
