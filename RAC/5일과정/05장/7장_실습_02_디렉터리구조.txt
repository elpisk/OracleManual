-- Sys 컬럼이 핵심이다.
--   +DATA 아래의 RACDB 는 N
--   그 아래의 GUID 디렉터리와 파일 종류 디렉터리는 모두 Y
--
-- 왜 RACDB 만 N 인가. ASM 관점에서 RACDB 는 사용자가 만든 디렉터리다.
-- 데이터베이스가 첫 파일을 만들 때 DB_UNIQUE_NAME 으로 디렉터리를 요청한
-- 것이지 ASM 이 스스로 만든 것이 아니다.
-- 반면 DATAFILE, CONTROLFILE 같은 파일 종류 디렉터리는 ASM 이 파일 종류를
-- 보고 자동으로 만든다.

ASMCMD> ls -l +DATA/RACDB/DATAFILE
Type      Redund  Striped  Time             Sys  Name

DATAFILE  UNPROT  COARSE   SEP 01 19:00:00  Y    SYSTEM.257.1242761643
DATAFILE  UNPROT  COARSE   SEP 01 19:00:00  Y    UNDOTBS1.259.1242761683
DATAFILE  UNPROT  COARSE   SEP 01 19:00:00  Y    UNDOTBS2.269.1242762281

-- 파일 이름도 Sys 가 Y 다. 시스템이 만든 정규 이름이다.
-- 대문자로 표시되는 것이 눈에 띈다. v$datafile 에서는 소문자였다.
-- asmcmd 가 대문자로 보여 줄 뿐 실제로는 대소문자를 구분하지 않는다.

--------------------------------------------------------------------------------
 [2] 컨트롤파일은 왜 다른가
--------------------------------------------------------------------------------

ASMCMD> ls -ls +DATA/RACDB/CONTROLFILE
Type         Redund  Striped  Time             Sys  Block_Size  Blocks     Bytes     Space  Name
CONTROLFILE  UNPROT  FINE     SEP 01 19:00:00  Y         16384    1203  19709952  25165824  Current.261.1242761745

-- 세 가지가 데이터파일과 다르다.
--
--   Striped     FINE (데이터파일은 COARSE)
--   Block_Size  16384 (데이터파일은 8192)
--   Bytes ≠ Space  19,709,952 를 저장하는 데 25,165,824 를 썼다
--
-- FINE 인 이유는 접근 패턴이다. 컨트롤파일은 크기가 작고(19MB), 갱신이
-- 매우 잦으며, RAC 에서는 두 인스턴스가 동시에 접근한다. COARSE 로 AU
-- 하나에 몰아 두면 그 AU 를 가진 디스크 한 장에 모든 갱신이 집중된다.
-- FINE 은 128KB 단위로 잘게 나눠 여러 디스크에 퍼뜨린다.
--
-- Bytes 와 Space 가 다른 이유는 AU 단위 할당이다. +DATA 의 AU 는 1MB 이고
-- ASM 은 AU 단위로만 공간을 준다. 19,709,952 바이트는 약 18.8MB 이므로
-- 24개 AU 가 필요하고, 그것이 25,165,824 바이트다.

--
-- Rebal — 리밸런스 진행 여부. 지금은 셋 다 N 으로 조용하다.

--   4장의 gridsetup.rsp 에 oracle.install.asm.diskGroup.AUSize=4 가 있었다.
--   +DATA 와 +FRA 는 DBCA 가 만들면서 지정하지 않아 기본값 1MB 다.
--
-- Req_mir_free_MB — +CRS 만 4096 이다.
--   Normal 중복도이고 실제 데이터가 들어 있으므로 디스크 한 장 손실에
--   대비한 공간이 잡혔다. 6장에서 갓 만든 빈 디스크그룹은 0이었다.
--   그 결과 Free_MB 11324 인데 Usable_file_MB 는 3614 다.

 [5] 오류 재현 — find 의 인자 순서

ASMCMD> find --type CONTROLFILE +DATA
usage: find [--type <type>] <dir> <pattern>
help:  help find

-- 오류 : usage 출력
-- 원인 파악 : find 는 디렉터리와 패턴을 모두 요구한다. 패턴을 빼먹었다.
--             주목할 점은 오류 메시지가 아니라 사용법이 나온다는 것이다.
--             종료 코드도 0이므로 스크립트에서는 성공한 줄 알고 지나친다.
--             결과가 없는데 성공으로 처리되는 조용한 실패다.
-- 조치     : 패턴을 함께 준다. 셸이 별표를 확장하지 않도록 따옴표로 감싼다.
-- 재확인   : 올바른 인자로 실행한다.

ASMCMD> find --type CONTROLFILE + '*'

 [6] 경로는 저장되지 않는다 — 인덱스로 계산된다
--------------------------------------------------------------------------------

[grid@rac1 ~]$ sqlplus -s / as sysasm

SQL> select a.name, a.alias_index, a.parent_index, a.reference_index,
  2         a.alias_directory ad, a.system_created sc
  3    from v$asm_alias a, v$asm_diskgroup g
  4   where a.group_number=g.group_number and g.name='FRA'
  5   order by a.reference_index;

--------------------------- ----------- ------------ --------------- - -
RACDB                                 0     50331648        50331701 Y Y
CONTROLFILE                          53     50331701        50331754 Y Y
ONLINELOG                            54     50331701        50331807 Y Y
group_4.260.1242762483              162     50331807        67108863 N Y
group_2.257.1242761759              159     50331807        67108863 N Y
group_1.258.1242761759              160     50331807        67108863 N Y
group_3.259.1242762467              161     50331807        67108863 N Y
Current.256.1242761745              106     50331754        67108863 N Y

8 rows selected.

-- 읽는 규칙은 둘이다.
--
--   REFERENCE_INDEX  이 항목이 디렉터리일 때 자식들이 가리킬 번호.
--                    파일이면 67108863(0x3FFFFFF) 고정. 자식을 가질 수 없다는 표시
--   PARENT_INDEX     부모 디렉터리의 REFERENCE_INDEX
--
-- 트리를 복원해 본다.
--   RACDB 의 REFERENCE_INDEX 는 50331701
--   CONTROLFILE 과 ONLINELOG 의 PARENT_INDEX 가 50331701  -> RACDB 의 자식
--   ONLINELOG 의 REFERENCE_INDEX 는 50331807
--   group_1 ~ group_4 의 PARENT_INDEX 가 50331807         -> ONLINELOG 의 자식
--
-- 조립하면 +FRA/RACDB/ONLINELOG/group_1.258.1242761759 이 된다.
--
-- 즉 ASM 내부에는 경로 문자열이 저장되어 있지 않다. 부모-자식 관계만 있고
-- asmcmd 가 그것을 따라 올라가며 경로를 계산한다.
-- 유닉스 파일시스템의 아이노드 구조와 같은 발상이다.

--------------------------------------------------------------------------------
 [7] 시스템과 사용자의 경계
--------------------------------------------------------------------------------

-- +FRA 의 모든 항목이 SYSTEM_CREATED='Y' 다. 사용자가 만든 것이 없다.
-- 실습 03 에서 별칭과 디렉터리를 만들면 N 인 행이 생긴다.
--
-- 경계를 정리하면 이렇다.
--
--   S=Y  파일 종류 디렉터리 (DATAFILE, CONTROLFILE, ONLINELOG ...)
--        시스템이 만든 정규 파일 이름 (system.257.1242761643)
--        -> 지울 수 없다. ORA-15177
--
--   S=N  데이터베이스 이름 디렉터리 (RACDB)
--        사용자가 add directory 로 만든 디렉터리
--        사용자가 add alias 로 만든 별칭
--        -> 지울 수 있다 (RACDB 는 안에 파일이 있어 실제로는 막힌다)
--
-- 설계 의도는 접근 경로 보존이다. 시스템이 만든 정규 이름은 데이터베이스가
-- 참조하는 유일한 이름이므로 지우면 파일에 접근할 방법이 사라진다.

 [8] 정리
--------------------------------------------------------------------------------

-- 재현한 오류
--   asmcmd find 인자 누락 — 오류가 아니라 usage 가 나오는 조용한 실패
--
-- 확인한 것
--   1) Sys 컬럼이 시스템과 사용자를 가른다
--   2) RACDB 는 N, 파일 종류 디렉터리는 Y
--   3) 컨트롤파일은 FINE, Block_Size 16384, Bytes 와 Space 가 다르다
--   4) lsdg 의 Rebal / AU / Req_mir_free_MB 세 컬럼이 중요하다
--   5) +CRS 만 AU 4MB — 응답 파일의 AUSize=4 때문
--   6) lsof 로 열린 파일을 확인하면 ORA-15027 을 미리 피한다
--   7) 경로는 저장되지 않고 PARENT_INDEX 로 계산된다
--   8) 파일 행의 REFERENCE_INDEX 는 67108863 고정
--
-- 점검에 쓸 명령
--   asmcmd lsdg              용량과 리밸런스 상태
--   asmcmd lsof -G <DG>      열린 파일 (모든 노드에서)
--   asmcmd du <경로>         디렉터리 이하 사용량
