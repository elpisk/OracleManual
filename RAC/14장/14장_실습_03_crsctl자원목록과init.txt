-- 읽는 순서.
--
--   (1) 두 구획을 먼저 본다.
--       Local Resources   — 노드마다 하나씩 있어야 하는 자원.
--                           왼쪽에 번호가 없고 노드 이름으로 행이 나뉜다.
--       Cluster Resources — 클러스터 전체에서 정해진 개수만 도는 자원.
--                           왼쪽에 번호가 붙는다.
--
--   (2) 왼쪽 번호는 슬롯 번호다. 인스턴스 번호가 아니다.
--       SCAN 리스너는 하나뿐이라 슬롯이 1 하나다.
--       Flex ASM 은 슬롯이 셋인데 노드는 둘이다.
--       데이터베이스는 CARDINALITY 가 2 라 슬롯이 둘이며,
--       우연히 인스턴스 번호와 일치할 뿐이다.
--
--   (3) State details 에 부가 정보가 있다.
--       데이터베이스는 Open 과 HOME= 을 함께 보여 준다.
--       홈이 여럿인 환경에서 어느 홈으로 도는지 알 수 있다.

-- 변경 이력을 추적할 실마리가 된다.

--------------------------------------------------------------------------------
 [3] OFFLINE 을 판단한다
--------------------------------------------------------------------------------

-- 위 출력에 OFFLINE 이 여럿 있다. 하나씩 판단해 본다.

-- (가) ora.CRS.dg / ora.DATA.dg 의 2번 슬롯
--      TARGET 도 OFFLINE 이다. CRS 도 이 슬롯을 내려 둘 생각이라는 뜻이며
--      불일치가 아니다. Flex ASM 카디널리티가 3 인데 노드가 둘이라 비었다.
--
-- (나) ora.asm / ora.ASMNET1LSNR_ASM 의 2번 슬롯
--      TARGET 은 ONLINE 인데 STATE 가 OFFLINE 이다.
--      역시 빈 슬롯이며 노드를 하나 더 붙이면 채워진다.
--
-- (다) ora.chad 의 rac2
--      이것만 성격이 다르다. 아래에서 따로 본다.

[grid@rac1 ~]$ crsctl stat res ora.chad
NAME=ora.chad
TYPE=ora.chad.type
TARGET=ONLINE        , ONLINE
STATE=ONLINE on rac1, OFFLINE

[grid@rac1 ~]$ crsctl stat res ora.chad -p | egrep '^NAME=|^TYPE=|AUTO_START|RESTART_ATTEMPTS|^ENABLED|^DESCRIPTION'
NAME=ora.chad
TYPE=ora.chad.type
AUTO_START=restore
DESCRIPTION=Oracle CHAD resource
ENABLED=1
RESTART_ATTEMPTS=5

[grid@rac1 ~]$ srvctl status cha -node rac2
Oracle Cluster Health Analysis Service is enabled on node rac2.
Oracle Cluster Health Analysis Service is not running on node rac2

-- crsctl 은 OFFLINE 이라는 사실까지만 알려 주고
-- srvctl 이 "enabled 이지만 running 이 아니다" 라고 한 겹 더 설명해 준다.
--
-- CHAD 는 Cluster Health Advisor 다. 클러스터 상태를 학습해 이상을
-- 예측하는 부가 서비스이며 데이터베이스 동작에 필수가 아니다.
-- 데이터베이스가 정상 동작한다는 사실 자체도 근거가 된다.
--
-- 필요하면 srvctl start cha -node rac2 로 올린다.
-- 자원이 넉넉하지 않은 환경에서는 켜지 않는 편이 낫다.

-- 이름이 완전히 다르다. 앞 목록에 없던 것들이다.
-- Server 열이 전부 rac1 이다. 실행한 노드의 것만 보여 준다.
--
-- 이유는 이 자원들을 OHAS(Oracle High Availability Services)가 관리하기
-- 때문이다. OHAS 는 노드마다 독립적으로 뜨는 최하위 데몬이므로
-- 다른 노드의 정보를 모아 줄 수 없다.
--
-- 계층은 이렇다.
--   OHAS 가 먼저 뜬다
--     → GIPCD·GPNPD·MDNSD 를 띄운다
--     → CSSD 를 띄워 클러스터 멤버십을 잡는다
--     → CRSD 가 뜬다
--     → CRSD 가 일반 자원(-init 없는 목록)을 관리한다
--
-- ora.diskmon 이 OFFLINE 인 것은 정상이다. AUTO_START 가 never 이며
-- Exadata 의 스토리지 서버 감시용이라 일반 환경에서는 올리지 않는다.

-- rac2 를 보려면 rac2 에서 실행한다.

--------------------------------------------------------------------------------
 [5] 두 목록에 모두 나오는 이름
--------------------------------------------------------------------------------

-- 겹치는 이름은 ora.asm 하나다.
--
--   -init 쪽  이 노드의 ASM 인스턴스를 OHAS 가 띄우는 자원.
--             Clusterware 가 OCR 과 투표 디스크를 읽어야 하는데
--             그것들이 ASM(+CRS)에 있으므로 ASM 이 CRSD 보다 먼저 떠야 한다.
--             닭과 달걀 문제를 이렇게 푼 것이다.
--
--   일반 쪽   ora.asmgroup 아래에 있고 슬롯이 셋이다.
--             Flex ASM 관점에서 클러스터 전체에 ASM 서비스를 제공한다.
--
-- 같은 프로세스를 두 계층이 각각의 목적으로 보고 있는 것이다.

--------------------------------------------------------------------------------
 [6] 흔한 오류 — 자원 이름을 정확히 쓰지 않으면
--------------------------------------------------------------------------------

[grid@rac1 ~]$ crsctl stat res ora.racdb.database
CRS-2613: Could not find resource 'ora.racdb.database'.

-- 원인 파악 : crsctl 은 부분 일치나 패턴을 받지 않는다.
--             자원 이름이 정확히 일치해야 한다.
--             데이터베이스 자원은 ora.<db_unique_name>.db 형식이므로
--             이 랩에서는 ora.racdb.db 다.
-- 조치     : crsctl stat res -t 로 전체 목록을 먼저 보고 정확한 이름을 쓴다.
--             또는 crsctl stat res | grep -i racdb 로 찾는다.
-- 재확인   : 올바른 이름으로 조회해 자원 정보가 나오는지 본다.

[grid@rac1 ~]$ crsctl stat res | grep -i racdb
NAME=ora.racdb.db

-- 참고로 이 CRS-2613 은 실습 06·07 에서 자원을 삭제한 뒤
-- 정상 삭제를 확인하는 신호로도 쓰인다. 같은 오류가 상황에 따라
-- 문제이기도 하고 확인 수단이기도 하다.
