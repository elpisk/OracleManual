 제14장 실습 06 — 사용자 스크립트를 클러스터 자원으로 등록
 대상   : rac1, rac2
 목표   : 액션 스크립트를 만들어 CRS 자원으로 등록하고, 장애를 주입해
          자동 복구를 관찰한다. 노드 간 이동과 복구 실패도 재현한다
 소요   : 약 45분
 선행   : 실습 05 완료. 두 세션(rac1·rac2)을 함께 열어 둔다
 계정   : root(파일 배포), grid(자원 조작)

--------------------------------------------------------------------------------
 [1] 액션 스크립트 작성
--------------------------------------------------------------------------------

-- CRS 는 등록된 스크립트를 인자 하나와 함께 호출한다.
--
--   start  자원을 기동한다        0=성공
--   stop   자원을 정지한다        0=성공
--   check  지금 살아 있는가       0=살아 있음, 0 이외=죽었음
--   clean  실패한 자원의 잔재 정리 0=성공
--
-- check 의 규칙을 뒤집으면 CRS 가 정상인 자원을 계속 되살리려 든다.
-- 가장 실수하기 쉬운 부분이다.

[root@rac1 ~]# cat /u01/app/grid/ch14/ch14app.sh
#!/bin/bash
# ch14app.sh - 사용자 자원 액션 스크립트
STATE=/tmp/ch14app.state
LOG=/tmp/ch14app.log
echo "$(date '+%F %T') $1" >> $LOG
case "$1" in
  start) echo "running since $(date '+%F %T')" > $STATE; exit 0 ;;
  stop)  rm -f $STATE; exit 0 ;;
  check) [ -f $STATE ] && exit 0 || exit 1 ;;
  clean) rm -f $STATE; exit 0 ;;
  *)     exit 1 ;;
esac

-- 실제 데몬 대신 상태 파일 하나로 살아 있음을 표현한다.
-- 로그 한 줄을 남기는 것이 핵심 장치다. CRS 가 언제 무엇을 호출했는지
-- 이 파일로 확인할 수 있다. 운영 스크립트에서도 유지할 습관이다.

-- 한 노드에만 있으면 페일오버 시 실패한다.

 [3] 자원 등록
--------------------------------------------------------------------------------

[grid@rac1 ~]$ crsctl add resource ch14.app -type cluster_resource \
>  -attr "ACTION_SCRIPT=/u01/app/grid/ch14/ch14app.sh,\
> PLACEMENT=restricted,HOSTING_MEMBERS=rac1 rac2,\
> CHECK_INTERVAL=30,RESTART_ATTEMPTS=2,\
> START_DEPENDENCIES=hard(ora.net1.network),\
> STOP_DEPENDENCIES=hard(ora.net1.network)"

[grid@rac1 ~]$ echo $?
0

-- 성공하면 아무것도 출력하지 않는다. 유닉스 도구의 관례 그대로다.
--
-- 속성 설명.
--   -type cluster_resource  클러스터 전체에서 정해진 개수만 도는 자원.
--                           노드마다 하나씩 필요하면 local_resource 를 쓴다.
--   PLACEMENT=restricted    지정한 노드에서만 돈다.
--   HOSTING_MEMBERS         그 노드 목록. 공백으로 구분한다.
--   CHECK_INTERVAL=30       30초마다 check 를 호출한다.
--                           이 값이 곧 장애 감지 지연의 상한이다.
--   START_DEPENDENCIES      네트워크가 살아 있어야 올린다.
--                           실제 배치 데몬이라면 DB 자원에 의존을 건다.

[grid@rac1 ~]$ crsctl stat res ch14.app -t
--------------------------------------------------------------------------------

ch14.app
      1        OFFLINE OFFLINE                               STABLE

[grid@rac1 ~]$ crsctl stat res ch14.app -p | egrep '^NAME=|^TYPE=|ACTION_SCRIPT|^AUTO_START|^CARDINALITY|^CHECK_INTERVAL|^ENABLED|HOSTING_MEMBERS|^PLACEMENT|^RESTART_ATTEMPTS'

-- 등록만 하고 기동하지 않았으므로 TARGET·STATE 모두 OFFLINE 이다.
-- 지정하지 않은 속성에 기본값이 들어갔다.
--   AUTO_START=restore, CARDINALITY=1, ENABLED=1
--
-- 속성 이름이 ora. 자원과 완전히 같다. 자원 모델이 하나뿐이며
-- 오라클 자원도 이 틀 위에 만들어져 있기 때문이다.

--------------------------------------------------------------------------------

-- 등록 명령을 스크립트나 원격 셸로 감싸 실행하면 이런 일이 생긴다.

[grid@rac1 ~]$ crsctl start resource ch14.app
CRS-2613: Could not find resource 'ch14.app'.
CRS-4000: Command Start failed, or completed with errors.

-- 원인 파악 : 자원이 등록되지 않았다. 앞선 add 명령이 실패했는데
--             그것을 확인하지 않고 다음 단계로 넘어간 것이다.
--             원인은 -attr 값 안의 괄호다.
--             START_DEPENDENCIES=hard(ora.net1.network) 의 괄호가
--             큰따옴표 밖으로 노출되면 셸이 이것을 서브셸 문법으로 읽고
--             syntax error near unexpected token `(' 를 낸다.
--             su - grid -c "..." 처럼 따옴표를 한 겹 더 쌓으면
--             안쪽 따옴표가 상쇄되어 이 일이 벌어진다.
-- 조치     : add 명령의 종료 코드를 반드시 확인한다.
--               crsctl add resource ... ; echo $?
--             중첩 따옴표가 필요하면 명령을 스크립트 파일에 적고
--             그 파일을 실행한다. 따옴표가 한 겹만 남아 안전하다.
--               cat > /tmp/add14.sh <<'EOS'
--               crsctl add resource ch14.app -type cluster_resource \
--                 -attr "ACTION_SCRIPT=...,START_DEPENDENCIES=hard(ora.net1.network)"
--               EOS
--               chmod 755 /tmp/add14.sh && /tmp/add14.sh
-- 재확인   : crsctl stat res ch14.app -t 로 자원이 목록에 나오는지 본다.
--             CRS-2613 이 나오면 아직 등록되지 않은 것이다.

-- 교훈 하나. 성공하면 아무것도 출력하지 않는 명령일수록 종료 코드를
-- 확인해야 한다. 출력이 없다는 것과 성공했다는 것은 다르다.

 [5] 장애 주입 — 자동 복구 관찰
--------------------------------------------------------------------------------

[root@rac1 ~]# rm -f /tmp/ch14app.state
[root@rac1 ~]# date '+%T'
12:03:16

-- 상태 파일을 지웠으므로 check 가 1 을 반환하게 된다.
-- 20초 간격으로 네 번 관찰했다.

[grid@rac1 ~]$ crsctl stat res ch14.app -t
ch14.app
      1        ONLINE  ONLINE       rac1                     STABLE
    ( 12:03:36 / 12:03:56 / 12:04:17 / 12:04:47 네 번 모두 같음 )

[grid@rac1 ~]$ cat /tmp/ch14app.state
running since 2026-09-04 12:03:27

-- 상태는 계속 ONLINE 이었다. 그런데 상태 파일의 시각이 12:03:27 로 바뀌었다.
-- 지운 뒤 다시 만들어졌다는 뜻이다. 무슨 일이 있었는지는 로그로 본다.

[rac1]$ cat /tmp/ch14app.log
2026-09-04 12:02:56 start
2026-09-04 12:02:56 check
2026-09-04 12:03:26 check      <- 여기서 실패 (상태 파일 없음)
2026-09-04 12:03:27 start      <- CRS 가 자동으로 재기동
2026-09-04 12:03:27 check
2026-09-04 12:03:57 check
2026-09-04 12:04:27 check

-- 시간축으로 정리하면 이렇다.
--
--   12:02:56  기동. 직후 한 번, 이후 30초마다 check (CHECK_INTERVAL=30)
--   12:03:16  상태 파일 삭제 = 장애 발생. CRS 는 아직 모른다
--   12:03:26  다음 check 에서 감지. 감지 지연 10초
--   12:03:27  start 호출로 복구. 복구 1초
--
-- 전체 복구 시간 = 감지 지연 + 복구 시간 = 10 + 1 = 11초.
-- 최악의 경우는 30 + 1 = 31초다. 감지 지연의 상한이 CHECK_INTERVAL 이다.
--
-- 중요한 관찰. 복구가 1초 만에 끝났기 때문에 crsctl stat res -t 는
-- 한 번도 OFFLINE 을 보여 주지 않았다. 자동 복구는 조용히 일어난다.
-- "장애가 있었는가" 를 상태 명령만으로 판단하면 놓친다.
--
-- 오라클 자원이라면 같은 정보를 아래에서 찾는다.
--   $ORACLE_BASE/diag/crs/<노드>/crs/trace/  의 에이전트 로그
--
-- 12장에서 pmon 을 죽였을 때 61초 만에 인스턴스가 되살아났던 것도
-- 같은 종류의 사건이다. 그때는 61초라 관찰이 됐지만 짧았다면 못 봤을 것이다.

 [7] 되살리지 못하는 경우
--------------------------------------------------------------------------------

-- 스크립트가 실패하도록 플래그를 두고 양 노드에 배포한 뒤 장애를 낸다.

-- 읽는다. 오라클 자원이라면 양 노드의 에이전트 트레이스를 같은 방식으로
-- 병합한다.

--------------------------------------------------------------------------------
 [8] RESTART_ATTEMPTS 는 보장이 아니다
--------------------------------------------------------------------------------

-- 이 자원의 RESTART_ATTEMPTS 는 2 였다. 그런데 위 로그에는 각 노드에서
-- start 를 한 번씩만 호출한 흔적이 있다.
--
-- 조건을 바꿔 두 번 더 확인했다.
--
--   (1) clean 이 성공하도록 스크립트를 고쳤다 → 여전히 start 는 한 번
--   (2) HOSTING_MEMBERS 를 rac1 하나로 줄여 옮겨 갈 노드를 없앴다
--       → 여전히 start 는 한 번
--
--   [grid@rac1 ~]$ crsctl modify resource ch14.app -attr "HOSTING_MEMBERS=rac1"
--   [grid@rac1 ~]$ crsctl stat res ch14.app -p | egrep '^HOSTING_MEMBERS|^PLACEMENT|^RESTART_ATTEMPTS'
--   HOSTING_MEMBERS=rac1
--   PLACEMENT=restricted
--   RESTART_ATTEMPTS=2
--
--   [rac1]$ cat /tmp/ch14app.log
--   2026-09-04 12:16:14 start
--   2026-09-04 12:16:15 check
--   2026-09-04 12:16:45 check
--   2026-09-04 12:16:45 start
--   2026-09-04 12:16:45 start FAILED(nostart)
--   2026-09-04 12:16:46 check
--   2026-09-04 12:16:46 clean
--   2026-09-04 12:16:46 check
--
-- 세 번의 실측 모두 start 호출은 한 번이었다.
--
-- 그러므로 RESTART_ATTEMPTS=2 를 보고 "두 번은 시도할 것" 이라고
-- 단정하면 안 된다. 이 값은 상한이며 실제 호출 횟수는 실패 유형과
-- 자원 유형에 따라 달라진다.
--
-- 운영에서 얻을 결론. 자동 복구가 몇 번 시도되었는지는 속성값이 아니라
-- 로그로 확인한다. 사용자 자원이면 액션 스크립트 로그, 오라클 자원이면
-- 에이전트 트레이스다.
