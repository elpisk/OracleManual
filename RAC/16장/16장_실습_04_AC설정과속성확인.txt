--------------------------------------------------------------------------------
 [1] AC 가 푸는 문제
--------------------------------------------------------------------------------

-- 15장에서 kill -9 로 인스턴스를 죽였다. 서비스는 10초 안에 옮겨 갔지만
-- 그때 racdb1 에서 작업 중이던 세션은 사라졌다.
--
-- 그 세션이 트랜잭션 중간이었다면 클라이언트는 무엇을 겪는가.
-- 접속이 끊어졌다는 오류를 받는데 커밋이 되었는지 안 되었는지 알 수 없다.
-- 커밋 요청은 보냈고 응답을 못 받은 상황이기 때문이다.
--
-- 다시 실행하면 중복 처리될 수 있고, 안 하면 누락될 수 있다.
-- 재시도해도 안전한지 판단할 근거가 없다는 것이 핵심이다.
--
-- AC 는 두 가지로 이 문제를 다룬다.
--   commit_outcome  트랜잭션에 논리 ID 를 붙여 커밋 여부를 조회 가능하게 한다.
--   재생            드라이버가 호출을 기록해 두었다가 다시 실행한다.
--
-- 두 장치는 짝을 이룬다. 재생하려면 먼저 커밋 여부를 알아야 하기 때문이다.

--------------------------------------------------------------------------------
 [2] AC 관련 옵션 목록
--------------------------------------------------------------------------------

[oracle@rac1 ~]$ srvctl add service -help 2>&1 | grep -E 'failovertype|failovermethod|failover_restore|commit_outcome|replay_init_time|session_state|retention'
    -failovertype     (NONE | SESSION | SELECT | TRANSACTION | AUTO)   Failover type
    -failovermethod   (NONE | BASIC)   Failover method
    -failover_restore <failover_restore>  Option to restore initial environment
                                          for Application Continuity and TAF
                                          (NONE or LEVEL1)
    -commit_outcome   (TRUE | FALSE)   Commit outcome
    -retention <retention>  Specifies the number of seconds the commit outcome
                            is retained
    -replay_init_time <replay_initiation_time>  Seconds after which replay will
                                                not be initiated
    -session_state <session_state>  Session state consistency (STATIC or DYNAMIC)

-- -failovertype 의 값이 다섯 단계다.
--   NONE         아무것도 하지 않는다
--   SESSION      세션만 다시 만든다
--   SELECT       진행 중이던 조회를 이어서 한다
--   TRANSACTION  트랜잭션까지 재생한다 (이것이 Application Continuity)
--   AUTO         오라클이 판단한다

--------------------------------------------------------------------------------
 [3] AC 서비스 생성
--------------------------------------------------------------------------------

[oracle@rac1 ~]$ srvctl add service -d racdb -s ch16_ac \
>                  -preferred racdb1 -available racdb2 \
>                  -failovertype TRANSACTION -commit_outcome TRUE \
>                  -failover_restore LEVEL1 -replay_init_time 600 \
>                  -retention 86400 -session_state DYNAMIC \
>                  -failoverretry 30 -failoverdelay 10 -notification TRUE
[oracle@rac1 ~]$ echo $?
0

[oracle@rac1 ~]$ srvctl start service -d racdb -s ch16_ac
[oracle@rac1 ~]$ srvctl status service -d racdb
Service ch16_ac is running on instance(s) racdb1
Service ch16_lb is running on instance(s) racdb1,racdb2

-- 옵션이 많지만 서로 연결되어 있다.
--
--   -failovertype TRANSACTION   트랜잭션까지 재생한다
--   -commit_outcome TRUE        위와 짝을 이룬다. 없으면 거부된다
--   -failover_restore LEVEL1    재접속 후 세션 환경을 복원한다
--                               NLS 설정이나 ALTER SESSION 으로 바꿔 둔 것들
--   -replay_init_time 600       600초를 넘기면 재생하지 않는다
--   -retention 86400            커밋 결과를 하루 보관한다
--   -session_state DYNAMIC      상태 변화를 추적해 재생 가능 여부를 판정한다
--   -failoverretry 30           재접속을 30번 시도한다
--   -failoverdelay 10           재시도 사이에 10초 쉰다
--
-- failoverretry 30 × failoverdelay 10 = 최대 300초 재접속 시도.
-- replay_init_time 600 과 함께 보면 전체 재생 시도 창이 정해진다.
-- 두 값이 서로 무관하지 않다.

-- srvctl config 는 CRS 가 아는 것이고 이쪽은 데이터베이스가 아는 것이다.
-- 두 출처가 일치해야 정상이며, 어긋나면 그 자체가 이상 신호다.
-- 15장에서 세운 원칙이 여기서도 그대로 적용된다.
--
-- 세 서비스를 나란히 놓으면 차이가 분명하다.
--   ch16_ac  AC 를 켠 서비스. 모든 값이 채워져 있다.
--   ch16_lb  AC 를 안 켠 서비스. FAILOVER_TYPE 이 비어 있고 재시도가 0 이다.
--   racdb    dbca 가 만든 기본 서비스. 아예 값이 없다.

--------------------------------------------------------------------------------
 [6] commit_outcome 을 조회하는 패키지
--------------------------------------------------------------------------------

SQL> select object_name, object_type, status from dba_objects
  2   where object_name in ('DBMS_APP_CONT','DBMS_APP_CONT_PRVT')
  3   order by object_name, object_type;

OBJECT_NAME          OBJECT_TYPE      STATUS
-------------------- ---------------- -------
DBMS_APP_CONT        PACKAGE          VALID
DBMS_APP_CONT        PACKAGE BODY     VALID
DBMS_APP_CONT        SYNONYM          VALID
DBMS_APP_CONT_PRVT   PACKAGE          VALID
DBMS_APP_CONT_PRVT   PACKAGE BODY     VALID
DBMS_APP_CONT_PRVT   SYNONYM          VALID

6 rows selected.

-- DBMS_APP_CONT 가 있고 VALID 다.
-- commit_outcome 으로 만들어진 논리 트랜잭션 ID 의 결과를 조회하는
-- GET_LTXID_OUTCOME 프로시저가 여기에 있다.
--
-- 애플리케이션이 커밋 응답을 못 받았을 때 이 프로시저로
-- "그 트랜잭션이 커밋되었는가" 를 물을 수 있다.
-- 재생 드라이버가 내부적으로 쓰는 것도 이것이다.
--
-- 패키지가 INVALID 라면 AC 가 동작하지 않는다.
-- 데이터베이스 업그레이드 후에는 이 상태를 확인해 두는 편이 좋다.

--------------------------------------------------------------------------------
 [7] 흔한 오류 — 서비스 이름을 잘못 쓰면
--------------------------------------------------------------------------------

[oracle@rac1 ~]$ srvctl config service -d racdb -s ch16_AC
PRKO-2382 : Service ch16_AC does not exist for database racdb.

-- 원인 파악 : 서비스 이름의 대소문자가 다르다. 만든 것은 ch16_ac 다.
--             srvctl 은 서비스 이름을 그대로 비교하므로 대소문자를 가린다.
--             정확한 이름은 다음으로 확인한다.
--               srvctl config service -d racdb | grep 'Service name'
-- 조치     : 소문자로 다시 실행한다.
--             서비스 이름을 지을 때 소문자로 통일하면 이런 혼란이 줄어든다.
-- 재확인   : config 출력이 나오는지 본다.

[oracle@rac1 ~]$ srvctl config service -d racdb | grep 'Service name'
Service name: ch16_ac
Service name: ch16_lb

-- 참고로 데이터베이스 쪽 DBA_SERVICES 의 NAME 열도 대소문자를 그대로
-- 저장한다. 접속 문자열에서도 마찬가지이므로 이름 규칙을 정해 두는 것이 좋다.
