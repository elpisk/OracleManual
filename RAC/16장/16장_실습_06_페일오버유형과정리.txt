 [1] 실험 설계
--------------------------------------------------------------------------------

-- 실습 04 에서 서비스에 -failovertype TRANSACTION 을 지정했다.
-- 그런데 클라이언트의 tnsnames.ora 에도 FAILOVER_MODE 절이 있다.
-- 둘 중 어느 것이 작동하는가.
--
-- 두 축을 조합해 네 경우를 만든다.
--   축 1  서비스에 -failovertype 이 있는가
--         ch16_ac = TRANSACTION / ch16_lb = 없음
--   축 2  tnsnames 에 FAILOVER_MODE 가 있는가
--
-- 두 요인이 있을 때 하나씩만 바꿔서는 상호작용을 알 수 없다.
-- 네 칸을 모두 채워야 결론이 난다.
--
-- 먼저 결과를 예측해 보고 시작한다. 대부분 클라이언트 설정이
-- 이길 것이라고 예상하는데 결과는 반대다.

CH16_TAF =

CH16_LB_TAF =

CH16_PLAIN =

-- 세 항목을 추가했다.

--   CH16_PLAIN   ch16_ac + FAILOVER_MODE 없음 (EZConnect 와 같은 조건)

-- 세 가지 결론이 나온다.
--
--   첫째, 서비스에만 지정해도 클라이언트가 아무것도 하지 않고 적용된다.
--         첫 줄이 그 증거다. EZConnect 로 붙었는데 TRANSACTIONAL 이다.
--
--   둘째, 클라이언트에만 지정해도 적용된다.
--         셋째 줄과 넷째 줄의 대조가 그 증거다.
--         같은 서비스인데 tnsnames 설정 유무로 NONE 과 SELECT 가 갈렸다.
--
--   셋째, 둘 다 있으면 서비스 설정이 이긴다.
--         둘째 줄에서 클라이언트는 SELECT 를 요청했는데
--         결과는 TRANSACTIONAL 이었다.
--
-- 세 번째가 특히 중요하다. 클라이언트 쪽 설정이 무시될 수 있다는 뜻이다.

--------------------------------------------------------------------------------
 [6] 진단 — 설정 파일을 믿지 말 것
--------------------------------------------------------------------------------

-- 애플리케이션 팀이 "tnsnames 에 TYPE=SELECT 를 넣었는데
-- 실제로는 TRANSACTIONAL 로 동작한다" 고 문의하는 상황을 생각해 보자.

-- 원인 파악 : 서비스 쪽에 -failovertype TRANSACTION 이 설정되어 있고
--             그것이 클라이언트 설정을 덮어썼다. [5] 의 둘째 줄 그대로다.
--             확인은 두 곳을 함께 본다.
--               서버   srvctl config service -d racdb -s <서비스> | grep 'Failover type'
--                      select name, failover_type from dba_services where name='<서비스>'
--               세션   select service_name, failover_type, failover_method
--                        from v$session where sid = sys_context('userenv','sid')
-- 조치     : 무엇이 의도인지에 따라 갈린다.
--             TRANSACTION 이 맞다면 클라이언트의 FAILOVER_MODE 절을 지운다.
--               적용되지도 않는 설정이 남아 있으면 다음 사람이 또 헷갈린다.
--             SELECT 가 맞다면 서비스 쪽을 바꾼다.
--               srvctl modify service -d racdb -s <서비스> -failovertype SELECT
--               다만 트랜잭션 재생을 포기하는 것이므로 합의가 필요하다.
-- 재확인   : 변경 후 V$SESSION 으로 다시 확인하고 결과를 문서에 남긴다.

-- 운영상의 함의가 크다.
-- 서버에서 서비스 설정을 바꾸면 클라이언트를 손대지 않고도
-- 페일오버 동작이 바뀐다. 편리하지만 추적이 어렵다.
--
-- 그러므로 실제로 무엇이 적용되었는지는 V$SESSION 으로 확인해야 한다.
-- 설정 파일을 보고 짐작하면 안 된다.

-- 표기가 다르다는 것도 짚어 둔다.
-- 서비스에는 TRANSACTION 을 넣는데 V$SESSION 에는 TRANSACTIONAL 로 나온다.
-- 같은 것이지만 자동 점검 스크립트로 두 값을 비교할 때 걸린다.

--------------------------------------------------------------------------------
 [7] V$SESSION 이 보여 주지 않는 것
--------------------------------------------------------------------------------

-- FAILOVER_TYPE 이 TRANSACTIONAL 이라는 것은
-- 이 세션에 그 유형이 협상되었다는 뜻이다.
-- 실제로 재생이 성공할지는 별개의 문제다.
--
-- 재생은 클라이언트 드라이버가 세션의 호출을 기록해야 가능하다.
--   JDBC 씬   재생 드라이버를 쓰고 커넥션 풀 설정을 맞춘다
--   OCI 계열  그에 맞는 라이브러리 버전이 필요하다
--
-- FAILED_OVER 열이 실제 페일오버가 일어났는지를 알려 준다.
-- 평상시에는 NO 이고 재접속이 일어난 뒤에 YES 가 된다.
-- 위 네 경우 모두 NO 였다. 아무 장애도 만들지 않았기 때문이다.
--
-- AC 도입을 검증하려면 세 단계를 밟아야 한다.
--   1. 서비스 설정을 srvctl config service 로 확인      → 이 랩에서 가능
--   2. 세션 협상을 V$SESSION 으로 확인                  → 이 랩에서 가능
--   3. 실제 장애를 만들어 FAILED_OVER 가 YES 로 바뀌면서
--      애플리케이션이 오류를 보지 않는지 확인           → 이 랩에서 불가
--
-- 3 단계는 재생을 지원하는 애플리케이션이 있어야 하며
-- SQL*Plus 로는 완전히 재현할 수 없다.
-- 실무에서는 이 단계를 위한 계획을 따로 세워야 한다.

--------------------------------------------------------------------------------
 [8] 재생 조건 정리
--------------------------------------------------------------------------------

-- 재생이 시도되는 조건 (셋이 AND 로 묶인다)
--   1. 서비스에 -failovertype TRANSACTION 과 -commit_outcome TRUE
--   2. 끊어진 뒤 -replay_init_time 안에 재접속
--   3. 클라이언트가 재생을 지원
--
-- 재생이 거부되는 경우
--   결과가 이미 클라이언트에 전달된 조회
--     화면에 일부를 뿌린 뒤라면 다시 실행해 다른 결과가 나오면 곤란하다.
--   세션 상태가 재생 중에 달라진 경우
--     -session_state DYNAMIC 이면 추적해 판정하고 STATIC 이면 전제한다.
--   결정적이지 않은 함수
--     SYSDATE, SYSTIMESTAMP, SYS_GUID. 재생 시점이 달라 값이 달라진다.
--   데이터베이스 밖으로 나가는 부수 효과
--     UTL_HTTP, UTL_FILE. 재생하면 두 번 일어난다.
--
-- 애플리케이션 쪽에서 볼 것
--   1. 결정적이지 않은 함수를 쓰는 곳을 찾는다.
--      컬럼 기본값으로 쓰는 것은 문제가 없다.
--      애플리케이션이 값을 계산해 넘기는 방식이라면 검토가 필요하다.
--   2. 외부 호출이 있는 트랜잭션을 찾아 밖으로 빼거나 멱등하게 만든다.
--   3. 세션 설정을 어디서 하는지 확인한다.
--      커넥션 풀에서 빌릴 때마다 ALTER SESSION 을 한다면
--      -failover_restore LEVEL1 이 복원해 주는지 본다.
--   4. 커넥션 풀 설정을 맞춘다. 재생 드라이버, 풀 크기.
--   5. 실제 장애를 만들어 검증한다.
--
-- 서버 설정은 명령 한 줄이지만 실제 일은 여기 있다.

-- 출력이 없고 종료 코드가 0 이면 사용자 서비스가 하나도 없다는 뜻이다.

ORA-12514: TNS:listener does not currently know of service requested in connect

-- 원인 파악 : 서비스를 지웠으므로 리스너에 등록되어 있지 않다.
--             ORA-12514 의 뜻은 "그런 서비스가 없다" 가 아니라
--             "리스너가 지금 그 서비스를 모른다" 다.
--             존재 여부가 아니라 등록 여부를 말한다. 15장에서 정리한 대로다.
--             확인은 세 단계다.
--               srvctl config service -d racdb   정의가 있는가
--               srvctl status service -d racdb   돌고 있는가
--               lsnrctl status LISTENER_SCAN1    등록되어 있는가
-- 조치     : 여기서는 의도한 결과이므로 조치할 것이 없다.
--             삭제가 제대로 되었다는 확인이다.
--             운영 중에 이 오류를 만났다면 서비스가 정지되었는지,
--             그 인스턴스가 죽었는지, 이름을 잘못 적었는지를 순서대로 본다.
-- 재확인   : lsnrctl status LISTENER_SCAN1 에 ch16 서비스가 없는지 본다.

[grid@rac1 ~]$ lsnrctl status LISTENER_SCAN1 | grep -c ch16
0
