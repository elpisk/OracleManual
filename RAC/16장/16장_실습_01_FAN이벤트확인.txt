================================================================================
 제16장 실습 01 — FAN 이벤트 확인, ONS 상태와 구성
 대상   : rac1, rac2
 목표   : FAN 이벤트를 나르는 ONS 의 구조를 확인하고, 두 노드가 서로를
          잡고 있는지 진단하는 절차를 익힌다
 소요   : 약 25분
 선행   : racdb 양 노드 OPEN, 부하 4 이하
 계정   : grid
================================================================================

--------------------------------------------------------------------------------
 [0] 상태 확인
--------------------------------------------------------------------------------

[oracle@rac1 ~]$ cat /proc/loadavg
5.62 5.70 5.29 1/1064 4556

[oracle@rac1 ~]$ srvctl status database -d racdb -v
Instance racdb1 is running on node rac1. Instance status: Open.
Instance racdb2 is running on node rac2. Instance status: Open.

-- 이 실습은 조회뿐이라 부하를 거의 만들지 않는다.

--------------------------------------------------------------------------------
 [1] 왜 이것을 보는가
--------------------------------------------------------------------------------

-- 15장에서 kill -9 로 racdb1 을 죽였을 때 서비스는 10초 안에 racdb2 로
-- 옮겨 갔다. 서버 쪽 복구는 빨랐다.
--
-- 그런데 그때 racdb1 에 붙어 있던 세션은 어떻게 되었나.
-- 아무 통지가 없다면 클라이언트는 TCP 타임아웃이 날 때까지 기다린다.
-- 운영체제 기본값으로는 수 분이 걸릴 수 있다.
--
-- 서버가 10초에 복구했는데 클라이언트가 5분을 기다린다면
-- 고가용성 구성의 의미가 없다. FAN 이 이 간극을 메운다.
--
-- FAN 이벤트를 나르는 것이 ONS 데몬이다. 15장의
-- srvctl status nodeapps 출력에 이미 나왔지만 그때는 넘어갔다.

--------------------------------------------------------------------------------
 [2] ONS 구성과 상태
--------------------------------------------------------------------------------

[grid@rac1 ~]$ srvctl config nodeapps -onsonly
ONS exists: Local port 6100, remote port 6200, EM port 2016, Uses SSL true
ONS is enabled
ONS is individually enabled on nodes:
ONS is individually disabled on nodes:

[grid@rac1 ~]$ srvctl status nodeapps | grep -i ons
ONS is enabled
ONS daemon is running on node: rac1
ONS daemon is running on node: rac2

-- 포트가 둘이다. 이 구분이 ONS 구조의 핵심이다.
--
--   Local port 6100   같은 노드 안의 프로세스가 붙는다.
--                     데이터베이스 인스턴스와 그 노드의 클라이언트.
--   Remote port 6200  다른 ONS 데몬과 이야기한다.
--                     노드끼리 이벤트를 주고받고 원격 클라이언트도 여기로.
--
-- Uses SSL true 도 눈여겨본다. ONS 통신이 암호화되어 있다.

--------------------------------------------------------------------------------
 [3] 포트 바인딩 — 두 포트의 성격 차이
--------------------------------------------------------------------------------

[grid@rac1 ~]$ netstat -tlnp | grep -E '6100|6200'
tcp   0  0 127.0.0.1:6100    0.0.0.0:*   LISTEN   23152/ons
tcp6  0  0 ::1:6100          :::*        LISTEN   23152/ons
tcp6  0  0 :::6200           :::*        LISTEN   23152/ons

-- 바인딩 주소가 다르다는 것이 결정적이다.
--
--   6100 은 127.0.0.1 과 ::1 에만 붙어 있다. 루프백이다.
--          다른 노드에서 이 포트로 붙을 수 없다.
--   6200 은 ::: 다. 모든 주소에서 받는다.
--
-- 방화벽 설정의 함의가 분명하다. 6200 만 열면 되고 6100 은 열 필요가 없다.
-- 포트 번호만 외우고 바인딩을 확인하지 않으면 불필요하게 둘 다 열게 된다.
--
-- PID 가 23152 로 세 줄이 같다. ONS 데몬 하나가 세 소켓을 다 듣는다.

--------------------------------------------------------------------------------
 [4] 데몬에게 직접 물어본다
--------------------------------------------------------------------------------

[grid@rac1 ~]$ /u01/app/19.3.0/grid/opmn/bin/onsctl ping
ons is running ...
[grid@rac1 ~]$ echo $?
0

-- onsctl 은 Grid 홈의 opmn/bin 아래에 있다. PATH 에 없으므로 전체 경로를 쓴다.
--
-- srvctl status nodeapps 와 무엇이 다른가.
--   srvctl  CRS 가 아는 것. 자원 상태를 본다.
--   onsctl  데몬에게 직접 묻는다.
--
-- 두 출처가 일치해야 정상이다. 14장에서 srvctl 과 crsctl 을 함께 쓴 것과
-- 같은 방식이다.

--------------------------------------------------------------------------------
 [5] 진단 — ping 만으로는 부족하다
--------------------------------------------------------------------------------

[grid@rac2 ~]$ /u01/app/19.3.0/grid/opmn/bin/onsctl debug
== rac2.localdomain:6200 24452 (4) 26/09/04 14:27:38 ==
Build: ONS_19.0.0.0.0_LINUX.X64_181205.1445 2018/12/6 0:16:24 UTC
Home: /u01/app/19.3.0/grid

======== ONS ========

           IP ADDRESS                   PORT    TIME   SEQUENCE  FLAGS
--------------------------------------- ----- -------- -------- --------
                         172.16.225.102  6200 6a9a10d3 00000038 00000008

Listener:

  TYPE                BIND ADDRESS               PORT  SOCKET
-------- --------------------------------------- ----- ------
Local                                        ::1  6100      6
Local                                  127.0.0.1  6100      7
Remote                                        ::  6200      8
Remote                                   0.0.0.0  6200      -

Servers: (1)

            IP ADDRESS                  PORT    TIME   SEQUENCE FL   DEFER
--------------------------------------- ----- -------- -------- -- ----------
                         172.16.225.101  6200 6a9a10d3 00000004 02          0

-- Servers: 절이 핵심이다.
-- rac2 의 ONS 가 172.16.225.101:6200, 즉 rac1 의 ONS 를 상대로 잡고 있다.
--
-- 두 데몬이 서로를 알고 있어야 한쪽에서 만든 이벤트가 다른 쪽으로 간다.
-- 이 목록이 비어 있으면 이벤트가 그 노드에 갇힌다.
--
-- DEFER 열이 0 이다. 보내지 못하고 쌓인 이벤트가 없다는 뜻이다.
-- 이 값이 계속 올라간다면 상대를 잡고는 있는데 통신이 안 되는 것이다.
--
-- 위쪽 ONS 절의 IP 는 자기 주소(172.16.225.102)다.
-- Servers 절의 IP 가 상대 주소다. 둘을 혼동하지 않는다.

-- 진단 순서를 정리하면 이렇다.
--   1. onsctl ping         데몬이 살아 있는가
--   2. Servers 절          상대를 잡고 있는가
--   3. DEFER               밀린 이벤트가 없는가
--
-- ping 만 하고 넘어가면 2 번 문제를 놓친다.
-- 데몬은 살아 있는데 이벤트가 전달되지 않는 상태가 가장 진단하기 어렵다.

--------------------------------------------------------------------------------
 [6] 흔한 오류 — 환경변수를 안 풀고 실행하면
--------------------------------------------------------------------------------

[grid@rac1 ~]$ $ORACLE_HOME/opmn/bin/onsctl ping
-bash: /opmn/bin/onsctl: No such file or directory

-- 원인 파악 : $ORACLE_HOME 이 비어 있어 경로가 /opmn/bin/onsctl 이 되었다.
--             grid 계정으로 붙었더라도 프로파일이 실행되지 않는 방식으로
--             명령을 던지면 환경변수가 설정되지 않는다.
--             원격 실행이나 su - 없이 su 만 쓴 경우에 자주 일어난다.
--             echo $ORACLE_HOME 으로 즉시 확인할 수 있다.
-- 조치     : 전체 경로를 쓰거나 환경을 먼저 설정한다.
--               /u01/app/19.3.0/grid/opmn/bin/onsctl ping
--             또는
--               export ORACLE_HOME=/u01/app/19.3.0/grid
--               $ORACLE_HOME/opmn/bin/onsctl ping
-- 재확인   : "ons is running ..." 이 나오는지 본다.

[grid@rac1 ~]$ echo $ORACLE_HOME
/u01/app/19.3.0/grid
[grid@rac1 ~]$ $ORACLE_HOME/opmn/bin/onsctl ping
ons is running ...

-- 스크립트를 짤 때는 전체 경로를 쓰는 편이 안전하다.
-- 환경변수에 의존하면 실행 방식에 따라 결과가 달라진다.

--------------------------------------------------------------------------------
 [7] 구성 파일 — 손대지 않는다
--------------------------------------------------------------------------------

[grid@rac1 ~]$ cat /u01/app/19.3.0/grid/opmn/conf/ons.config
usesharedinstall=true
allowgroup=true
localport=6100                  # line added by Agent
remoteport=6200                 # line added by Agent
nodes=rac1:6200,rac2:6200       # line added by Agent
walletfile=/u01/app/grid/crsdata/rac1/onswallet/    # line added by Agent
allowunsecuresubscriber=yes     # line added by Agent
allowpublish=::ffff:172.16.225.101,172.16.225.101,::ffff:172.16.225.102,172.16.225.102

-- "# line added by Agent" 주석이 붙어 있다.
-- 사람이 쓴 것이 아니라 CRS 에이전트가 만들었다는 뜻이다.
--
-- 그러므로 이 파일을 직접 고치면 안 된다. 에이전트가 다시 덮어쓴다.
-- 바꾸려면 srvctl modify nodeapps 를 쓴다.
-- 14장에서 자원 속성을 crsctl modify 로 바꿨던 것과 같은 원칙이다.
--
-- 항목별로 읽으면.
--
--   nodes=rac1:6200,rac2:6200
--     이 ONS 가 상대로 잡을 노드 목록. [5] 의 Servers 절이 여기서 나온다.
--     노드를 추가하면 이 줄이 자동으로 늘어난다.
--
--   walletfile
--     SSL 통신에 쓰는 지갑 위치. [2] 의 Uses SSL true 와 짝을 이룬다.
--
--   allowpublish
--     이벤트를 발행할 수 있는 주소 목록. 두 노드의 IPv4 주소와
--     IPv4-mapped IPv6 주소만 적혀 있다.
--     아무나 가짜 FAN 이벤트를 뿌릴 수 없게 하는 장치다.

--------------------------------------------------------------------------------
 [8] 서버만 준비하면 안 된다
--------------------------------------------------------------------------------

-- ONS 가 잘 돌고 있어도 클라이언트가 구독하지 않으면 소용이 없다.
-- 클라이언트 종류에 따라 방법이 다르다.
--
--   JDBC 씬   UCP 를 쓰고 setFastConnectionFailoverEnabled(true)
--   OCI 계열  서비스의 -notification TRUE
--   ODP.NET   접속 문자열에 HA Events=true
--
-- 서비스 쪽 설정은 config 에서 확인한다.

[oracle@rac1 ~]$ srvctl config service -d racdb -s ch16_lb
PRCR-1001 : Resource ora.racdb.ch16_lb.svc does not exist

-- 원인 파악 : 아직 서비스를 만들지 않았다. 15장의 실습 정리에서 모두
--             지웠으므로 사용자 서비스가 하나도 없는 상태다.
--             srvctl config service -d racdb 를 인자 없이 실행하면
--             출력이 없고 종료 코드가 0 이다. 그것이 "없다" 는 뜻이다.
--             특정 이름을 지정했을 때만 PRCR-1001 이 나온다.
-- 조치     : 다음 실습에서 서비스를 만든 뒤 확인한다.
--             기존 서비스의 값을 보려면 기본 서비스로 확인할 수도 있다.
--               srvctl config service -d racdb -s racdb
--             다만 racdb 는 dbca 가 만든 것이라 사용자 서비스 목록에 없다.
-- 재확인   : srvctl config service -d racdb 로 목록이 비어 있는지 본다.

[oracle@rac1 ~]$ srvctl config service -d racdb
[oracle@rac1 ~]$ echo $?
0

-- 실습 02 에서 서비스를 만들면 이 항목을 확인할 수 있다.
-- 그때 -notification TRUE 를 지정하면 AQ HA notifications 가 true 가 된다.
-- 기본값은 false 다. 자주 빠뜨리는 옵션이며 다음 실습에서
-- -notification TRUE 를 지정해 이 값이 바뀌는 것을 확인한다.
--
-- 15장에서 클라이언트가 노드 주소로 붙어 있으면 서비스 이동이
-- 무력화된다고 했다. 같은 종류의 이야기다.
-- 서버 쪽 고가용성 설정은 클라이언트가 받쳐 주어야 완성된다.
