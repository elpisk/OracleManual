-- 세 줄을 눈여겨본다.
--
--   CONTROLFILE AUTOBACKUP ON
--     백업할 때마다 컨트롤파일과 SPFILE 이 함께 백업된다. 실습 07 에서 쓴다.
--
--   ARCHIVELOG DELETION POLICY TO NONE
--     자동으로 지우지 않는다. 실습 07 에서 수동으로 지운다.
--
--   SNAPSHOT CONTROLFILE NAME 이 로컬 경로이고 인스턴스 번호가 붙어 있다
--     백업 중 컨트롤파일의 일관된 사본을 잠시 만드는 임시 파일이다.
--     백업을 한 노드에서 시작하는 구성이면 기본값으로 충분하다.
--     여러 노드에서 동시에 백업을 시작하는 구성이라면 공유 위치로 옮긴다.

--------------------------------------------------------------------------------
 [2] 채널을 특정 인스턴스에 붙이는 방법
--------------------------------------------------------------------------------

-- RMAN 은 채널마다 데이터베이스에 접속한다.
-- 기본 채널은 실행한 노드의 인스턴스에 붙는다.
-- 채널을 여럿 두고 각각 다른 인스턴스에 붙이면 두 노드의 CPU 와 I/O 를
-- 함께 쓸 수 있다.
--
-- 문제는 어떻게 특정 인스턴스를 지목하느냐다.
-- 서비스 racdb 는 양쪽에서 돌므로 SCAN 으로 붙으면 어디로 갈지 모른다.
--
-- 답은 노드의 VIP 다. 15장에서 확인했듯 로컬 리스너는
-- 그 노드의 인스턴스만 등록한다.

[oracle@rac1 ~]$ sqlplus -s system/<암호>@rac1-vip:1521/racdb
SQL> select instance_name from v$instance;   →  racdb1

[oracle@rac1 ~]$ sqlplus -s system/<암호>@rac2-vip:1521/racdb
SQL> select instance_name from v$instance;   →  racdb2

-- 결정적이다. 예외가 없다.
--
-- 15장에서는 접속 확인을 SCAN 으로 하라고 했다.
-- 그것은 서비스가 제대로 동작하는지 검증할 때의 이야기다.
-- 여기서는 반대로 특정 인스턴스를 지목해야 하므로 VIP 를 쓴다.
-- 목적이 다르면 쓰는 주소도 다르다.

 [4] 노드 분산 백업
--------------------------------------------------------------------------------

RMAN> run {
  allocate channel ch1 device type disk connect 'sys/<암호>@rac1-vip:1521/racdb';
  allocate channel ch2 device type disk connect 'sys/<암호>@rac2-vip:1521/racdb';
  backup as compressed backupset database format '+FRA';
  release channel ch1;
  release channel ch2;
}

--------------------------------------------------------------------------------
 [7] 채널을 몇 개 둘 것인가
--------------------------------------------------------------------------------

-- 노드가 둘이면 채널도 둘이면 되는가. 그렇지 않다.
-- 노드당 채널 수는 그 노드의 CPU 와 I/O 대역폭이 정한다.
--
-- 일반적인 출발점은 노드당 CPU 코어 수의 절반 정도다.
-- 이 랩은 노드당 4 vCPU 이므로 노드당 2, 전체 4 채널이 상한에 가깝다.
--
-- 그런데 이 실습에서는 채널을 둘만 썼다. 호스트 CPU 가 넉넉하지 않기 때문이다.
-- 11장에서 dbca 가 부하 139 에서 노드 축출을 일으킨 것을 떠올리면
-- 백업도 같은 위험을 안고 있다.
--
-- 백업 전에 부하를 확인하는 습관을 권한다.
--   [oracle@rac1 ~]$ cat /proc/loadavg
--
-- 압축을 쓸지도 함께 정한다.
-- as compressed backupset 은 I/O 를 줄이는 대신 CPU 를 더 쓴다.
-- 스토리지가 병목이면 이득이고 CPU 가 병목이면 손해다.
-- 이 랩처럼 CPU 가 빠듯하면 압축을 빼는 편이 나을 수도 있다.
