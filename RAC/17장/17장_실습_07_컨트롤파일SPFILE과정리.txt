-- 컨트롤파일이 두 개다. +DATA 와 +FRA 에 하나씩이며 dbca 가 다중화했다.
-- 13장에서 리두 멤버를 두 디스크그룹에 나눈 것과 같은 원리다.
-- 디스크그룹 하나를 잃어도 컨트롤파일이 남는다.
--
-- SPFILE 은 +DATA 에 하나뿐이다.
-- 12장에서 다룬 그 파일이며 두 인스턴스가 공유한다.
--
-- 둘 다 ASM 에 있다는 것이 RAC 의 조건이다.
-- 로컬에 두면 그 노드가 죽었을 때 다른 노드가 데이터베이스를 올릴 수 없다.

--------------------------------------------------------------------------------

-- 대신 SPFILE 을 임시 위치로 복원해 자동 백업이 쓸 만한지 확인한다.
-- 비파괴적이면서 실제 복구 절차와 같은 명령을 쓴다.

--
-- racdb1. 과 racdb2. 접두어가 보인다.
-- 12장에서 다룬 RAC SPFILE 의 표기가 백업에도 그대로 보존되었다.
-- 이것이 복원 후 두 인스턴스가 각자의 설정을 되찾는 근거다.
--
-- 이 확인이 뜻하는 바가 크다.
-- 자동 백업만 있으면 SPFILE 을 잃어도 되살릴 수 있고,
-- 되살린 SPFILE 에 인스턴스별 설정이 온전히 들어 있다.

RMAN> restore spfile to '/tmp/spfile_test2.ora' from autobackup;

recovery area destination: +FRA

channel ORA_DISK_1: no AUTOBACKUP in 7 days found

RMAN-00571: ===========================================================
RMAN-00569: =============== ERROR MESSAGE STACK FOLLOWS ===============
RMAN-00571: ===========================================================
RMAN-03002: failure of restore command at 09/04/2026 15:40:12
RMAN-06172: no AUTOBACKUP found or specified handle is not a valid copy or piece

-- 원인 파악 : 자동 백업이 없다. 세 가지 경우가 있다.
--             하나, CONFIGURE CONTROLFILE AUTOBACKUP 이 OFF 였다.
--             둘, 자동 백업을 삭제했다 (delete backup 으로 함께 지워진다).
--             셋, 기본 검색 범위인 최근 7 일 안에 없다.
--             확인은 다음으로 한다.
--               RMAN> show controlfile autobackup;
--               RMAN> list backup of spfile;
--               asmcmd ls +FRA/RACDB/AUTOBACKUP/
-- 조치     : 자동 백업이 꺼져 있으면 켜고 백업을 한 번 돌린다.
--               RMAN> configure controlfile autobackup on;
--               RMAN> backup current controlfile;
--             오래된 자동 백업을 찾으려면 검색 범위를 넓힌다.
--               RMAN> set until time 'sysdate-30';
--               RMAN> restore spfile from autobackup maxdays 30;
-- 재확인   : restore spfile to '<임시경로>' from autobackup 이 성공하는지 본다.

RMAN> show controlfile autobackup;
CONFIGURE CONTROLFILE AUTOBACKUP ON; # default

-- 여기서 얻을 점검 항목 하나.
-- 자동 백업이 켜져 있는지, 그리고 최근 것이 있는지 정기적으로 확인한다.
-- 필요할 때 없으면 복구가 훨씬 어려워진다.

--------------------------------------------------------------------------------
 [5] 참고 — 컨트롤파일을 모두 잃었을 때의 절차
--------------------------------------------------------------------------------

-- 이 랩에서는 실행하지 않고 절차만 익힌다.
--
--   1. 데이터베이스를 모두 내린다.
--      srvctl stop database -d racdb -o abort
--      컨트롤파일이 없으므로 정상 종료가 되지 않는다.
--      srvctl status database -d racdb -v 로 둘 다 not running 인지 확인한다.
--
--   2. 한 노드에서 NOMOUNT 로 올린다.
--      SQL> startup nomount
--      SPFILE 이 있으면 그것으로 올라간다.
--      SPFILE 도 잃었다면 먼저 restore spfile from autobackup 을 하고
--      다시 올린다.
--
--   3. DBID 를 지정하고 컨트롤파일을 복원한다.
--      RMAN> set dbid 1240378513;
--      RMAN> restore controlfile from autobackup;
--
--   4. MOUNT 하고 데이터베이스를 복구한다.
--      SQL> alter database mount;
--      RMAN> recover database;
--      컨트롤파일이 백업 시점의 것이므로 그 이후의 리두를 적용해야 한다.
--
--   5. RESETLOGS 로 연다.
--      SQL> alter database open resetlogs;
--      컨트롤파일을 복원하면 리셋로그가 필요하다.
--
--   6. 나머지 인스턴스를 올린다.
--      srvctl start instance -d racdb -i racdb2
--
-- RAC 에서 특히 주의할 것은 3 단계 전에 다른 인스턴스가 완전히
-- 내려가 있어야 한다는 점이다.
-- 하나만 살아 있어도 컨트롤파일을 잡고 있어 복원이 실패한다.
--
-- 그리고 DBID 를 어딘가에 적어 두어야 한다.
-- 컨트롤파일이 없으면 데이터베이스가 자기 DBID 를 모른다.
-- 이 랩은 1240378513 이며 실습 01 에서 기록해 두었다.
-- RMAN 접속 시 출력되는 값이기도 하다.
--   connected to target database: RACDB (DBID=1240378513)
-- 운영 문서의 첫 페이지에 적어 두는 것이 관례다.

--------------------------------------------------------------------------------
 [8] 무엇을 되돌리고 무엇을 되돌리지 않는가
--------------------------------------------------------------------------------

-- 되돌린 것
--   실습 테이블스페이스 ts_ch17 과 테이블
--   백업 12 개, 아카이브 24 개
--   로컬 아카이브 디렉터리 (실습 02)
--   임시 SPFILE 파일
--
-- 되돌리지 않은 것
--   ARCHIVELOG 모드
--
-- ARCHIVELOG 를 유지하는 이유는 그것이 백업과 복구가 가능한
-- 데이터베이스의 정상 구성이기 때문이다.
-- NOARCHIVELOG 로 되돌리면 이후 장에서 다시 켜야 하고
-- 10장에서 겪은 제약도 그대로 돌아온다.
--
-- 다만 조건이 붙는다.
-- 아카이브가 계속 쌓이므로 정기적으로 지우거나 삭제 정책을 걸어야 한다.
-- 이 랩은 정책이 NONE 이므로 실습이 끝날 때마다 수동으로 지운다.
--
-- 운영이라면 다음을 걸어 두는 것이 출발점이다.
--   RMAN> configure archivelog deletion policy to backed up 1 times to disk;
--
-- 이것이 이 과정에서 유일하게 기준선을 바꾸고 끝나는 장이다.
-- 랩 문서에 그 사실을 기록해 두어야 한다.

--------------------------------------------------------------------------------
 [9] 이 장의 점검 항목
--------------------------------------------------------------------------------

주기      확인 항목                          조회
-------- ---------------------------------- ------------------------------------
매일      스레드별 아카이브 최근 생성 시각    v$archived_log 를 thread# 로 group by
매일      FRA 사용률                         v$recovery_file_dest
매일      아카이브 대상 상태                 gv$archive_dest 의 status 가 VALID
주간      다른 노드에서 백업 유효성          restore database validate
주간      스레드별 시퀀스 끊김               thread# 별 min/max sequence#
주간      자동 백업 존재                     list backup of controlfile
변경 후   DBID 기록이 최신인가               운영 문서와 v$database 대조

-- 세 번째가 이 장에서 얻은 항목이다.
-- 실습 02 에서 STATUS 가 INACTIVE 가 되어 ORA-16014 가 났다.
-- 그 상태를 미리 잡아 준다.
--
-- 네 번째와 다섯 번째가 RAC 특유다.
-- 백업이 유효해도 한 노드에서만 유효하면 반쪽이고,
-- 스레드마다 시퀀스가 독립적이므로 한 스레드만 끊길 수 있다.
-- 전체를 뭉뚱그려 세면 그 끊김이 보이지 않는다.
