================================================================================
 제17장 실습 05 — 인스턴스 복구 관찰  [주의]
 대상   : rac1, rac2
 목표   : 인스턴스 하나를 강제 종료하고 다른 인스턴스가 그 스레드를
          복구하는 과정을 알럿 로그로 관찰한다
 소요   : 약 30분
 선행   : 실습 04 완료. 부하 4 이하일 때 진행한다
 계정   : oracle, root
 주의   : 인스턴스를 강제로 죽인다. 다른 실습과 겹치지 않게 한다
================================================================================

--------------------------------------------------------------------------------
 [1] 인스턴스 복구란 무엇인가
--------------------------------------------------------------------------------

-- 13장에서 리두 스레드를 다루며 이렇게 말했다.
-- "인스턴스 하나가 죽으면 살아남은 인스턴스가 죽은 인스턴스의
--  스레드를 읽어 복구한다."
--
-- 그 과정을 여기서 실제로 관찰한다.
--
-- 미디어 복구와 다른 점은 데이터파일이 멀쩡하다는 것이다.
-- 잃은 것은 메모리(버퍼 캐시)에 있던 커밋된 변경이며,
-- 그것이 리두에 있으므로 리두를 읽어 데이터파일에 반영하면 된다.
--
--   인스턴스 복구  데이터파일 정상. 자동으로 일어난다.
--   미디어 복구    데이터파일 자체를 잃었다. 관리자가 명령을 내린다.

--------------------------------------------------------------------------------
 [2] 복구 예측치를 미리 본다
--------------------------------------------------------------------------------

SQL> select inst_id, recovery_estimated_ios, actual_redo_blks, target_redo_blks,
  2         estimated_mttr, target_mttr
  3    from gv$instance_recovery order by inst_id;

   INST_ID RECOVERY_ESTIMATED_IOS ACTUAL_REDO_BLKS TARGET_REDO_BLKS ESTIMATED_MTTR TARGET_MTTR
---------- ---------------------- ---------------- ---------------- -------------- -----------
         1                   1161             9651           331776              1           0
         2                   1018             7507           331776              1           0

-- 읽는 법.
--
--   ESTIMATED_MTTR = 1
--     지금 인스턴스가 죽으면 약 1초 만에 복구된다는 예측이다.
--     뒤에서 실측과 비교한다.
--
--   ACTUAL_REDO_BLKS = 9651, TARGET_REDO_BLKS = 331776
--     지금 복구해야 할 리두 블록 수와 상한이다.
--     실제가 상한의 3% 도 안 되므로 여유가 크다.
--
--   TARGET_MTTR = 0
--     fast_start_mttr_target 을 설정하지 않았다는 뜻이다.
--     목표를 정하지 않았으므로 오라클이 알아서 한다.
--
-- 이 값을 미리 기록해 두면 실측과 비교할 수 있다.

 [8] 두 시간을 구분한다
--------------------------------------------------------------------------------

-- 시각을 정리하면 이렇다.
--
--   15:10:09.000  kill -9
--   15:10:14.229  Reconfiguration started   ← 감지, 약 5초
--   15:10:14.329  Reconfiguration complete  (0.1초)
--   15:10:14.506  Beginning instance recovery
--   15:10:15.155  Completed instance recovery
--   15:11:06      racdb2 가 Open 으로 복귀
--
-- 인스턴스 복구 = 15:10:14.229 → 15:10:15.155 = 0.93초
-- 인스턴스 재기동 = 15:10:09 → 15:11:06 = 57초
--
-- [2] 에서 조회한 ESTIMATED_MTTR 가 1초였다. 실측 0.93초와 거의 일치한다.
-- 그 지표를 신뢰할 근거가 생겼다.
--
-- 두 시간이 영향을 주는 대상이 다르다.
--
--   살아 있는 인스턴스(racdb1)의 세션
--     인스턴스 복구 시간만 영향을 받는다.
--     GRD 가 얼어 있는 0.93초 동안 잠시 멈추지만 세션은 유지된다.
--
--   죽은 인스턴스(racdb2)의 세션
--     아예 끊어진다. 복구 시간과 무관하며 재접속이 필요하다.
--     그 재접속을 빠르게 만드는 것이 16장의 FAN 이고
--     끊긴 작업을 이어 주는 것이 AC 다.
--
-- 이 구분이 장애 보고서를 쓸 때 결정적이다.
-- "1초 미만의 영향" 과 "57초 동안 한 노드 사용 불가" 는 전혀 다른 이야기다.

 [8-1] 흔한 오류 — 죽은 인스턴스에 붙어 있던 세션은
--------------------------------------------------------------------------------

-- rac2 에 붙어 있던 세션에서 무언가 실행하면 이렇게 된다.

[rac2 세션] SQL> select count(*) from dual;
select count(*) from dual
*
ERROR at line 1:
ORA-03113: end-of-file on communication channel
Process ID: 11512
Session ID: 149 Serial number: 51263

-- 원인 파악 : 그 세션이 붙어 있던 인스턴스가 죽었다.
--             ORA-03113 은 서버 프로세스와의 통신이 끊어졌다는 뜻이며
--             인스턴스 비정상 종료의 전형적인 증상이다.
--             인스턴스 복구가 0.93초에 끝나도 이 세션은 돌아오지 않는다.
--             복구된 것은 데이터이지 세션이 아니기 때문이다.
--             확인은 다른 노드에서 한다.
--               srvctl status database -d racdb -v
--               select inst_id, instance_name, status from gv$instance;
-- 조치     : 재접속한다. SCAN 으로 붙으면 살아 있는 인스턴스로 간다.
--             애플리케이션이라면 16장에서 다룬 FAN 이 이 재접속을
--             빠르게 만들고, AC 가 끊긴 작업을 이어 준다.
--             통지가 없으면 TCP 타임아웃까지 수 분을 기다린다.
-- 재확인   : 재접속 후 instance_name 이 살아 있는 인스턴스인지 보고
--             필요하면 끊긴 트랜잭션의 커밋 여부를 확인한다.

[oracle@rac1 ~]$ sqlplus system/<암호>@rac-scan:1521/racdb
SQL> select instance_name from v$instance;   →  racdb1

-- 이것이 두 시간을 구분해야 하는 이유다.
-- 살아 있는 인스턴스의 세션은 0.93초만 영향을 받지만
-- 죽은 인스턴스의 세션은 재접속이 필요하다.
