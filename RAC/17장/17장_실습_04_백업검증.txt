================================================================================
 제17장 실습 04 — 백업 검증, 양 노드에서 restore validate
 대상   : rac1, rac2
 목표   : 백업이 어느 노드에서든 쓸 수 있는지 검증하는 방법을 익힌다.
          RAC 백업 설계가 옳은지 판정하는 기준을 세운다
 소요   : 약 20분
 선행   : 실습 03 완료 (백업이 있는 상태)
 계정   : oracle
================================================================================

--------------------------------------------------------------------------------
 [1] 왜 다른 노드에서도 확인해야 하는가
--------------------------------------------------------------------------------

-- 백업을 만들었으면 그것이 쓸 수 있는지 확인해야 한다.
-- 단일 인스턴스라면 한 번 확인하면 끝이다.
--
-- RAC 는 다르다. 백업이 유효해도 한 노드에서만 유효하면 반쪽이다.
-- 실습 02 에서 본 것이 바로 그 상황이다.
-- rac1 에서는 멀쩡한 아카이브가 rac2 에서는 validation failed 였다.
--
-- 복구는 어느 노드에서 하게 될지 모른다.
-- 장애가 난 노드가 복구를 수행할 노드일 수도 있고 아닐 수도 있다.
-- 그러므로 모든 노드에서 유효해야 한다.

--------------------------------------------------------------------------------
 [2] rac1 에서 검증
--------------------------------------------------------------------------------

[rac1] RMAN> restore database validate;

   ( 백업셋 여섯 개를 차례로 검증 )

>>> 71.2초

-- restore database validate 는 실제로 복원하지 않는다.
-- 백업을 읽어 보고 손상이 없는지만 확인한다.
-- 데이터파일을 덮어쓰지 않으므로 운영 중에 돌려도 안전하다.
--
-- 백업셋 여섯 개를 하나씩 읽는다. 실습 03 에서 만든 그 여섯이다.

--------------------------------------------------------------------------------
 [3] rac2 에서 같은 검증
--------------------------------------------------------------------------------

[rac2] RMAN> restore database validate;

Starting restore at 04-SEP-26
allocated channel: ORA_DISK_1
channel ORA_DISK_1: SID=... instance=racdb2 device type=DISK

channel ORA_DISK_1: starting validation of datafile backup set
channel ORA_DISK_1: validation complete, elapsed time: 00:00:26
   ( 백업셋 여섯 개를 차례로 검증 )
Finished restore at 04-SEP-26

>>> 71.4초

-- 71.4초다. rac1 의 71.2초와 사실상 같다.
--
-- 중요한 것은 시간이 아니라 성공했다는 사실이다.
-- 백업이 +FRA 에 있고 컨트롤파일이 공유되므로
-- 어느 노드에서든 같은 백업을 본다.

--------------------------------------------------------------------------------
 [4] 백업 목록도 같은가
--------------------------------------------------------------------------------

[rac2] RMAN> list backup summary;

Key     TY LV S Device Type Completion Time #Pieces Compressed Tag
------- -- -- - ----------- --------------- ------- ---------- ---
6       B  A  A DISK        04-SEP-26       1       YES        TAG20260904T150401
7       B  F  A DISK        04-SEP-26       1       NO         TAG20260904T150404
8       B  F  A DISK        04-SEP-26       1       YES        TAG20260904T150409
   ( 이하 rac1 에서 본 것과 동일 )

-- 목록도 같다. rac1 에서 만든 백업을 rac2 가 그대로 안다.
-- RMAN 이 컨트롤파일을 카탈로그로 쓰고 그 컨트롤파일이 공유되기 때문이다.
--
-- 실습 02 에서 로컬 아카이브가 rac2 에서 validation failed 였던 것과
-- 대비된다. 그때는 카탈로그에는 있는데 파일이 없었고,
-- 여기서는 카탈로그와 파일이 모두 공유된다.

--------------------------------------------------------------------------------
 [5] 아카이브까지 검증한다
--------------------------------------------------------------------------------

[rac2] RMAN> restore archivelog all validate;

-- 데이터파일 백업이 유효해도 아카이브가 없으면 시점 복구가 안 된다.
-- 백업 시점 이후의 변경을 적용할 수 없기 때문이다.
--
-- 두 검증을 한 세트로 돌리는 것이 안전하다.
--   restore database validate;
--   restore archivelog all validate;

[rac2] RMAN> crosscheck backup;
[rac2] RMAN> crosscheck archivelog all;

-- crosscheck 는 조금 다른 일을 한다.
-- validate 는 백업 내용을 읽어 손상 여부를 보고,
-- crosscheck 는 파일이 그 자리에 있는지만 본다.
--
-- 실습 02 에서 쓴 것이 crosscheck 였다.
-- 파일이 없으면 validation failed 로 표시되고 EXPIRED 가 된다.
-- 이번에는 모두 succeeded 여야 한다.

--------------------------------------------------------------------------------
 [6] 오류 재현 — 백업이 없는 데이터파일을 검증하면
--------------------------------------------------------------------------------

-- 아직 백업하지 않은 파일을 검증하려 하면 어떻게 되는지 본다.
-- 실습 06 에서 만들 테이블스페이스를 미리 가정한 상황이다.

RMAN> restore datafile 99 validate;

RMAN-00571: ===========================================================
RMAN-00569: =============== ERROR MESSAGE STACK FOLLOWS ===============
RMAN-00571: ===========================================================
RMAN-03002: failure of restore command at 09/04/2026 15:22:33
RMAN-06023: no backup or copy of datafile 99 found to restore

-- 원인 파악 : 그 데이터파일의 백업이 없다. 파일 번호가 틀렸을 수도 있다.
--             확인은 두 가지로 한다.
--               select file#, name from v$datafile order by file#;
--               RMAN> list backup of datafile <번호>;
--             파일이 존재하는데 백업이 없다면 백업 대상에서 빠진 것이다.
--             새로 만든 테이블스페이스를 백업하지 않은 경우가 흔하다.
-- 조치     : 그 파일을 백업한다.
--               RMAN> backup as compressed backupset datafile <번호> format '+FRA';
--             테이블스페이스 단위라면 backup tablespace <이름> 이다.
--             정기 백업이 database 전체를 대상으로 한다면
--             다음 백업에 자동으로 포함된다.
-- 재확인   : list backup of datafile <번호> 로 백업이 생겼는지 보고
--             restore datafile <번호> validate 를 다시 돌린다.

RMAN> list backup of datafile 27;
   ( 백업이 있으면 목록이 나오고 없으면 비어 있다 )

-- 여기서 얻을 점검 항목 하나.
-- 새 테이블스페이스를 만들면 그것이 백업 대상에 들어갔는지 확인한다.
-- database 전체를 백업한다면 자동이지만, 테이블스페이스를 지정해
-- 백업하는 구성이라면 목록에 추가해야 한다.

--------------------------------------------------------------------------------
 [7] 검증이 실패했을 때의 확인 순서
--------------------------------------------------------------------------------

-- rac2 에서 실패하고 rac1 에서 성공한다면 무언가 로컬에 있는 것이다.
-- 차례로 확인한다.
--
--   1. 백업 조각 경로
--      RMAN> list backup;
--      piece handle 이 모두 +FRA 나 +DATA 로 시작하는가.
--      로컬 경로가 섞여 있으면 백업 스크립트의 format 을 고친다.
--
--   2. 아카이브 경로
--      select thread#, name from v$archived_log where deleted='NO';
--      +FRA 가 아닌 것이 있으면 실습 02 의 상황이다.
--      log_archive_dest_1 을 공유 위치로 고친다.
--
--   3. 스냅숏 컨트롤파일 위치
--      RMAN> show snapshot controlfile name;
--      여러 노드에서 동시에 백업하는 구성이라면 공유 위치여야 한다.
--
--   4. 파일 자체의 존재
--      양 노드에서 asmcmd ls 나 ls 로 확인한다.
--      양쪽 모두 없으면 로컬 문제가 아니라 파일이 사라진 것이다.
--      crosscheck 후 delete expired 로 카탈로그를 정리하고 새로 백업한다.

--------------------------------------------------------------------------------
 [8] 이것이 RAC 백업 설계의 검증법
--------------------------------------------------------------------------------

-- 절차로 정리하면 이렇다.
--
--   1. 한 노드에서 백업을 만든다.
--   2. 다른 노드에서 restore database validate 를 돌린다.
--   3. 다른 노드에서 restore archivelog all validate 도 돌린다.
--   4. 셋 다 성공하면 그 백업은 어느 노드에서든 복구에 쓸 수 있다.
--
-- 이 절차를 백업 구성을 바꿀 때마다 실행한다.
-- 경로를 바꾸거나 새 디스크그룹을 쓰거나 노드를 추가한 뒤가 그때다.
--
-- 주간 점검 항목으로도 넣을 만하다.
-- 백업이 도는 것과 그 백업이 쓸 수 있는 것은 다른 이야기다.
