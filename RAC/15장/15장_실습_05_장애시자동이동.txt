 대상   : rac1, rac2
 목표   : 계획된 정지와 실제 장애에서 서비스의 운명이 어떻게 다른지 확인하고
          그 차이의 원인을 안다. 계획 정지의 올바른 절차를 익힌다
 소요   : 약 40분
 선행   : 실습 04 완료. 부하 4 이하일 때 진행한다
 계정   : oracle, root
 주의   : 이 실습은 인스턴스를 두 번 죽인다. 다른 실습과 겹치지 않게 한다

 [1] 오류 재현 — 서비스가 도는 인스턴스를 그냥 내리려 하면
--------------------------------------------------------------------------------

[oracle@rac1 ~]$ srvctl stop instance -d racdb -i racdb1
PRCD-1131 : Failed to stop database racdb and its services on nodes rac1
PRCR-1133 : Failed to stop database racdb and its running services
PRCR-1132 : Failed to stop resources using a filter
CRS-2974: unable to act on resource 'ora.racdb.db' on server 'rac1' because that
would require stopping or relocating resource 'ora.racdb.ch15_oltp.svc' but the
appropriate force flag was not specified

-- 원인 파악 : 네 줄이 겹쳐 나왔고 앞의 셋은 정보가 거의 없다.
--             14장의 규칙대로 마지막 줄을 먼저 읽는다.
--             CRS-2974 의 내용이 정확하다. 이 인스턴스를 내리려면
--             그 위에서 도는 서비스 자원(ora.racdb.ch15_oltp.svc)을
--             정지하거나 옮겨야 하는데 force 플래그가 없다는 것이다.
-- 조치     : 두 갈래다.
--             (a) 올바른 방법 — 서비스를 먼저 옮긴 뒤 내린다. [4] 참고
--             (b) 강행 — -force 를 붙인다. 그 결과는 [2] 에서 본다
--             실무에서는 (a) 를 쓴다.
-- 재확인   : 데이터베이스가 그대로인지 본다. 거부되었으므로 변화가 없다.

[oracle@rac1 ~]$ srvctl status database -d racdb -v
Instance racdb1 is running on node rac1 with online services ch15_oltp.
Instance status: Open.

-- 이 거부는 좋은 설계다. 서비스가 도는 인스턴스를 무심코 내리는 일을
-- 막아 준다. 서비스가 없었다면 이 명령은 그냥 통과했을 것이다.

--------------------------------------------------------------------------------
 [2] -force 로 강행하면 — 흔한 오해
--------------------------------------------------------------------------------

-- 흔한 기대는 "가용 인스턴스를 지정해 두었으니 서비스가 옮겨 갈 것" 이다.
-- 측정 결과는 달랐다.

[oracle@rac1 ~]$ srvctl stop instance -d racdb -i racdb1 -stopoption abort -force
[oracle@rac1 ~]$ echo $?
0

>>> 9.0초

-- rac2 에서 관찰한다. rac1 의 인스턴스가 죽었으므로.

[oracle@rac2 ~]$ date '+%T'; srvctl status service -d racdb
12:52:38
Service ch15_batch is running on instance(s) racdb2
Service ch15_oltp is not running.

[oracle@rac2 ~]$ srvctl status database -d racdb -v
Instance racdb1 is not running on node rac1
Instance racdb2 is running on node rac2 with online services ch15_batch.
Instance status: Open.

-- ch15_oltp 가 racdb2 로 가지 않고 그냥 멈췄다.
-- 12:53:03, 12:53:25, 12:53:52 세 번 더 확인했지만 계속 같았다.
-- 60초 동안 네 번 관찰했고 변화가 없었다.

[oracle@rac2 ~]$ sqlplus system/<암호>@rac-scan:1521/ch15_oltp
ERROR:
ORA-12514: TNS:listener does not currently know of service requested in connect
descriptor

-- 서비스가 어디에도 없으므로 SCAN 리스너가 넘길 곳이 없다.
-- rac2 는 멀쩡히 살아 있는데 그 서비스는 쓸 수 없다.
--
-- 이유는 -force 의 의미에 있다.
--   -force = "서비스를 옮겨라" 가 아니다
--   -force = "서비스가 돌고 있어도 강행하라" 다
--
-- CRS 는 관리자가 의도적으로 내린다고 보고 서비스 자원의 TARGET 도
-- 함께 OFFLINE 으로 내린다.
--
-- 12장에서 배운 그 원리다. 정상 종료면 CRS 는 다시 올리지 않는다.
-- 서비스도 자원이므로 같은 규칙을 따른다.

--------------------------------------------------------------------------------
 [3] 인스턴스를 다시 올린다
--------------------------------------------------------------------------------

[oracle@rac2 ~]$ srvctl start instance -d racdb -i racdb1

>>> 122.9초

[oracle@rac2 ~]$ srvctl status service -d racdb
Service ch15_batch is running on instance(s) racdb2
Service ch15_oltp is running on instance(s) racdb1

-- 인스턴스가 뜨자 서비스도 함께 떴다. Management policy 가 AUTOMATIC 이고
-- 정의상 선호 인스턴스가 racdb1 이기 때문이다.
--
-- 122.9초가 걸린 것을 눈여겨보자. 12장에서 잰 기동 시간은 40.6초였고
-- 뒤의 [5] 에서는 47초였다. 세 배 차이다.
--
-- 명령이 다르기 때문이 아니라 호스트 부하가 달랐다.
-- 이때의 loadavg 는 7.68 이었고 다른 두 경우는 4 대였다.
--
-- 기동 시간으로 이상 여부를 판단하려면 부하를 함께 기록해야 한다.
-- "평소 40초인데 오늘 120초 걸렸다" 는 관찰만으로는 데이터베이스 문제인지
-- 호스트 문제인지 알 수 없다. cat /proc/loadavg 를 기동 전후에 함께
-- 남기는 것이 간단한 해법이다.

--------------------------------------------------------------------------------
 [4] 계획 정지의 올바른 절차
--------------------------------------------------------------------------------

-- [2] 의 실패에서 배운 절차다. 네 단계로 정리한다.
--
--   1. 서비스를 먼저 옮긴다
--      srvctl relocate service -d racdb -s ch15_oltp -oldinst racdb1 -newinst racdb2
--      2초면 끝나고 새 접속은 즉시 racdb2 로 간다.
--      확인: srvctl status service -d racdb 로 모두 옮겨졌는지
--
--   2. 기존 세션이 빠질 시간을 준다
--      relocate 는 기존 세션을 끊지 않으므로 그들이 작업을 마칠 때까지 기다린다.
--      확인: select inst_id, count(*) from gv$session where type='USER'
--              group by inst_id;
--
--   3. 인스턴스를 내린다
--      srvctl stop instance -d racdb -i racdb1
--      이제 그 인스턴스에 서비스가 없으므로 -force 없이도 통과한다.
--      force 를 써야 한다면 1단계에서 빠뜨린 서비스가 있다는 뜻이다.
--
--   4. 작업 후 인스턴스를 올리고 서비스를 되돌린다
--      srvctl start instance -d racdb -i racdb1
--      srvctl relocate service -d racdb -s ch15_oltp -oldinst racdb2 -newinst racdb1
--      4단계를 빠뜨리면 부하 분산이 원래대로 돌아오지 않는다.
--
-- 3단계에서 -force 가 필요 없어진다는 것이 절차가 옳다는 증거다.

--------------------------------------------------------------------------------
 [5] 실제 장애 — kill -9
--------------------------------------------------------------------------------

Service ch15_oltp is running on instance(s) racdb1

[root@rac1 ~]# ps -ef | grep ora_pmon_racdb1 | grep -v grep

[root@rac1 ~]# date '+%T'; pkill -9 -f ora_pmon_racdb1

-- rac2 에서 관찰한다.

[oracle@rac2 ~]$ date '+%T'; srvctl status service -d racdb
12:58:16
Service ch15_batch is running on instance(s) racdb2
Service ch15_oltp is running on instance(s) racdb2

[oracle@rac2 ~]$ srvctl status database -d racdb -v
Instance racdb1 is not running on node rac1
Instance racdb2 is running on node rac2 with online services
ch15_batch,ch15_oltp. Instance status: Open.

-- 10초 안에 옮겨 갔다. racdb1 은 죽어 있고 ch15_oltp 는 racdb2 에서 돈다.
--
-- 이것이 가용 인스턴스를 지정해 둔 효과다.
-- 선호 인스턴스가 사라지자 CRS 가 가용 인스턴스로 서비스를 올렸다.
--
-- [2] 의 계획된 정지와 정확히 대비된다.
-- 같은 서비스, 같은 가용 인스턴스인데 결과가 반대다.
-- 차이는 정상 종료인가 비정상 종료인가 하나뿐이다.
--
-- 12장에서 인스턴스를 두고, 14장에서 사용자 자원을 두고 확인한 것과
-- 완전히 같은 원리다. CRS 가 보는 것은 어떤 도구를 썼느냐가 아니라
-- 정상 종료인가 비정상 종료인가다.

--------------------------------------------------------------------------------
 [6] 인스턴스는 되살아나는데 서비스는 안 돌아온다
--------------------------------------------------------------------------------

[oracle@rac2 ~]$ date '+%T'; srvctl status database -d racdb -v
12:58:53
Instance racdb1 is running on node rac1. Instance status: Open.
Instance racdb2 is running on node rac2 with online services
ch15_batch,ch15_oltp. Instance status: Open.

-- 47초 만에 racdb1 이 되살아났다.
-- 12장에서 pmon 을 죽였을 때 61초였던 것과 같은 자동 복구다.
--
-- 그런데 서비스는 racdb2 에 그대로 있다.
-- racdb1 옆에 "with online services" 문구가 없는 것이 그 증거다.

-- 계속 관찰한다.

[oracle@rac2 ~]$ (12:59:20 / 12:59:57 / 13:00:44 — +75초, +111초, +158초)
Service ch15_oltp is running on instance(s) racdb2
Instance racdb1 is running on node rac1. Instance status: Open.

-- 158초까지 지켜봤지만 그대로였다.
-- 선호 인스턴스가 살아 돌아와도 서비스는 자동으로 복귀하지 않는다.
--
-- 이유는 옮기는 데 비용이 들기 때문이다. 서비스를 옮기면 그 인스턴스의
-- 세션 배치가 다시 흔들린다. CRS 는 "지금 잘 돌고 있는데 굳이 옮길
-- 이유가 없다" 고 본다.

--------------------------------------------------------------------------------
 [7] 복귀는 관리자의 일
--------------------------------------------------------------------------------

[oracle@rac1 ~]$ srvctl relocate service -d racdb -s ch15_oltp \
>                  -oldinst racdb2 -newinst racdb1
[oracle@rac1 ~]$ srvctl status service -d racdb
Service ch15_batch is running on instance(s) racdb2
Service ch15_oltp is running on instance(s) racdb1

>>> 1.7초

-- 1.7초면 된다. 어려운 일이 아니라 잊기 쉬운 일이다.
--
-- 장애 대응 절차서의 마지막 항목에 이것을 넣어 두어야 한다.
-- "인스턴스 복구 확인" 에서 끝내면 부하가 한쪽에 몰린 채로 며칠이 지나간다.
-- 13장에서 본 편중이 이렇게 생기기도 한다.
--
-- 자동 복귀 설정은 기본으로 제공되지 않는다. 대신 점검으로 잡는다.
-- srvctl status service 의 출력을 srvctl config service 의 Preferred 와
-- 비교하는 스크립트를 두면 어긋난 서비스를 찾아낼 수 있다.
--
-- 자동으로 되돌리는 것까지는 권하지 않는다. 서비스가 옮겨 가 있다는 것은
-- 무슨 일이 있었다는 뜻이므로, 사람이 원인을 확인한 뒤 되돌리는 편이 안전하다.
