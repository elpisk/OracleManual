          그것이 CRS 자원이 된다는 것과 정의에 어떤 기본값이 들어가는지 본다
 소요   : 약 25분
 선행   : 실습 01 완료
 계정   : oracle, grid

--------------------------------------------------------------------------------
 [1] 만들기 전 자원 개수를 세어 둔다
--------------------------------------------------------------------------------

[grid@rac1 ~]$ crsctl stat res | grep -c '^NAME='
17

-- 14장에서 기록한 기준선이다. 서비스를 만들면 이 숫자가 늘어난다.

--------------------------------------------------------------------------------
 [2] 서비스 둘을 만든다
--------------------------------------------------------------------------------

[oracle@rac1 ~]$ srvctl add service -d racdb -s ch15_oltp \
>                  -preferred racdb1 -available racdb2
[oracle@rac1 ~]$ echo $?
0

>>> 6.3초

[oracle@rac1 ~]$ srvctl add service -d racdb -s ch15_batch \
>                  -preferred racdb2 -available racdb1
[oracle@rac1 ~]$ echo $?
0

-- 성공하면 아무것도 출력하지 않는다. 종료 코드로 확인한다.
--
-- 지정한 것은 셋뿐이다.
--   -s          서비스 이름
--   -preferred  평소에 어느 인스턴스에서 돌 것인가
--   -available  그것이 죽으면 어디로 갈 것인가
--
-- 두 서비스가 서로 반대로 배치되어 있다.
--   ch15_oltp   선호 racdb1, 가용 racdb2
--   ch15_batch  선호 racdb2, 가용 racdb1
--
-- 이 엇갈린 배치가 부하 분산의 기본형이다.
-- 평소에는 나뉘어 돌고 한쪽이 죽으면 남은 쪽이 둘 다 받는다.
--
-- 가용 인스턴스를 지정하지 않으면 선호가 죽었을 때 서비스가 그냥 사라진다.
-- 반드시 지정해야 한다.

--------------------------------------------------------------------------------
 [3] 오류 재현 — 없는 인스턴스를 선호로
--------------------------------------------------------------------------------

[oracle@rac1 ~]$ srvctl add service -d racdb -s ch15_bad \
>                  -preferred racdb9 -available racdb2
PRKO-2101 : Failed to find database instances racdb9

-- 원인 파악 : racdb9 라는 인스턴스가 없다. 이 랩은 2 노드이며
--             인스턴스는 racdb1 과 racdb2 뿐이다.
--             PRKO 는 srvctl 의 명령행 해석 계층이다. 14장에서 정리한
--             접두어 체계로 보면 내가 친 명령이 틀렸다는 뜻이며
--             자원을 조회하러 가기도 전에 거부되었다.
-- 조치     : 실제 인스턴스 이름을 확인하고 바로잡는다.
--               srvctl config database -d racdb | grep instances
--             노드를 세 번째로 추가할 계획이었다면 노드와 인스턴스를
--             먼저 추가한 뒤 서비스를 만든다.
-- 재확인   : srvctl config service -d racdb 목록에 ch15_bad 가 없는지 본다.
--             거부되었으므로 만들어지지 않았다.

[oracle@rac1 ~]$ srvctl config database -d racdb | grep -i instances
Database instances: racdb1,racdb2

[oracle@rac1 ~]$ srvctl add service -d nodb -s ch15_bad2 -preferred racdb1
PRCD-1120 : The resource for database nodb could not be found.
PRCR-1001 : Resource ora.nodb.db does not exist

-- 이쪽은 접두어가 다르다. PRCD 는 데이터베이스 계층, PRCR 은 자원 계층이다.
-- 두 줄로 나왔고 진짜 원인은 아래에 있다. 14장의 규칙 그대로다.
--
-- 이 오류들이 만들기 전에 나는 것이 다행이다.
-- 잘못된 정의가 저장되면 기동할 때가 되어서야 문제를 알게 되고,
-- 그때는 이미 애플리케이션 접속 문자열이 그 서비스 이름에 의존하고 있을 수 있다.

--------------------------------------------------------------------------------
 [4] 서비스는 CRS 자원이 된다
--------------------------------------------------------------------------------

[grid@rac1 ~]$ crsctl stat res -t | grep -A3 'ora.racdb.ch15'
ora.racdb.ch15_batch.svc
      1        OFFLINE OFFLINE                               STABLE
ora.racdb.ch15_oltp.svc
      1        OFFLINE OFFLINE                               STABLE

[grid@rac1 ~]$ crsctl stat res | grep -c '^NAME='
19

-- 이름이 ora.<DB이름>.<서비스이름>.svc 형식이다.
-- 14장에서 다룬 자원 모델 그대로이며 TARGET·STATE 도 같은 방식으로 읽는다.
--
-- 만들기만 하고 기동하지 않았으므로 둘 다 OFFLINE 이다.
-- 자원 개수가 17 에서 19 로 늘었다. 14장에서 개수를 기록해 두라고 한
-- 이유가 여기서 드러난다. 서비스를 만들면 늘고 지우면 준다.

[grid@rac1 ~]$ crsctl stat res ora.racdb.ch15_oltp.svc -p | egrep '^NAME=|^TYPE=|^AUTO_START|^CARDINALITY|^ENABLED'
NAME=ora.racdb.ch15_oltp.svc
TYPE=ora.service.type
AUTO_START=restore
CARDINALITY=1
ENABLED=1

-- 속성 이름이 14장에서 본 것과 완전히 같다.
-- 자원 모델이 하나뿐이며 서비스도 그 틀 위의 한 종류일 뿐이다.

-- 지정한 것은 셋뿐인데 항목이 많다. 나머지는 기본값이다.
-- 실무에서 만지는 것은 몇 개뿐이므로 중요한 것만 짚는다.
--
--   Cardinality: 1
--     한 번에 한 인스턴스에서만 돈다. 선호를 둘 지정하면 2 가 되고
--     양쪽에서 동시에 돌면서 SCAN 분산도 받는다.
--
--   Service role: PRIMARY
--     Data Guard 관련. 이 DB 가 프라이머리일 때만 이 서비스가 돈다.
--     스탠바이에서 읽기 전용 서비스를 두려면 PHYSICAL_STANDBY 로 만든다.
--
--   Management policy: AUTOMATIC
--     DB 가 뜰 때 이 서비스도 함께 뜬다. MANUAL 이면 직접 올려야 한다.
--
--   Connection Load Balancing Goal: LONG
--     접속을 나눌 때의 기준. LONG 은 세션 수, SHORT 는 응답 시간이다.
--     실습 07 에서 이 값의 의미를 확인한다.
--
--   Retention: 86400 seconds
--     서비스 통계를 하루 보관한다.
--
--   Failover 계열과 TAF policy
--     클라이언트 쪽 장애 조치 설정. 이 장에서는 비워 두고
--     16장에서 Application Continuity 와 함께 다룬다.
--
--   Pluggable database name 이 비어 있다
--     -pdb 를 지정하지 않았으므로 CDB$ROOT 에 붙는 서비스다.
--     접속하면 CDB 루트에 들어간다.

--------------------------------------------------------------------------------
 [6] 참고 — PDB 서비스로 만들려면
--------------------------------------------------------------------------------

-- 실무에서는 PDB 마다 서비스를 두는 편이 낫다.
--
--   srvctl add service -d racdb -s app_svc -pdb RACPDB1 \
--     -preferred racdb1 -available racdb2
--
-- 이유는 둘이다.
--   애플리케이션이 어느 PDB 를 쓰는지 이름으로 드러난다.
--   PDB 를 다른 CDB 로 옮길 때 서비스 이름만 유지하면
--   클라이언트를 바꾸지 않아도 된다.
--
-- 12장에서 PDB 를 한 인스턴스에서만 열어 두는 실습을 했다.
-- 그 상태에서 PDB 서비스를 두면 서비스가 곧 "이 PDB 가 열려 있는
-- 인스턴스" 를 가리키게 되어 관리가 단순해진다.
--
-- 이 실습에서는 CDB 레벨 서비스로 진행한다. 개념을 익히는 것이 목적이고
-- PDB 를 끼우면 확인해야 할 것이 늘어나기 때문이다.
